AWS Security Pillar 3: Permissions Management

Source: AWS Well-Architected Framework, Security Pillar, "Permissions management", SEC03. Own-words summary, much shorter than the source. Previous: AWS Security Pillar 2: Identity Management. Next: AWS Security Pillar 4: Detection.

Takeaways
  • Permissions say who can do what, to which resource, under which conditions. Some policy types grant; others only limit.
  • Aim for least privilege that shrinks over time: start from what people actually use (CloudTrail, Access Analyzer), then remove what is unused.
  • Put guardrails (SCPs, permission boundaries, session policies) above everything so that mistakes in individual policies cannot exceed them.
  • Plan the unusual cases too: emergency access, leavers, public and cross-account sharing, third parties.

3.1 Policy types

Policy type Attached to Effect
Identity-based (AWS-managed, customer-managed, inline) users, groups, roles grants; customer-managed policies are the usual choice for least privilege
Resource-based a resource (an S3 bucket policy) grants to a principal in the same or another account
Permissions boundary a user or role the most a delegated admin can grant, so developers cannot escalate by creating roles
ABAC (attribute-based access control) tags on principals and resources one reusable policy grants access where tags match
Service control policy (SCP) account, OU or organisation maximum permissions for members; limits, does not grant
Session policy one assumed-role or federated session limits that session; does not grant
  • ABAC example from the source:
    • one IAM policy lets developers manage resources that carry their project's tag, so new resources are covered without policy edits
    • Role chaining from IAM Identity Center does not carry source-identity or principal tags forward.

3.2 SEC03-BP01 Define access requirements (risk: high)

  • For every component, decide who or what needs access, with which identity type and method.
  • Anti-patterns: hard-coded secrets; custom permissions per user; long-lived credentials.
  • Workforce access uses federation and follows the employee lifecycle (a job change changes group membership).
  • Non-human access uses IAM roles built for least privilege; AWS managed policies cover common cases. Secrets Manager and Systems Manager Parameter Store keep secrets out of applications.

3.3 SEC03-BP02 Grant least privilege access (risk: high)

  • Grant only the actions needed, on named resources, under stated conditions, and use group and identity attributes so access follows project membership automatically.
  • Anti-patterns: administrator by default; root for daily work; over-broad policies.
  • Techniques:
    • Separate dev and prod into different accounts and control the boundary with SCPs, resource policies and identity policies.
    • Base policies on real API usage from CloudTrail; IAM Access Analyzer can generate a policy from activity; IAM Access Advisor shows last-accessed data.
    • Start with AWS managed job-function policies (billing, database administrator, data scientist) while you write finer ones.

3.4 SEC03-BP03 Establish emergency access process (risk: medium)

  • Needed when the central identity provider fails or federation is misconfigured and nobody can sign in.
  • Anti-pattern: no documented, tested emergency process.
  • Common steps for every failure mode:
    • A dedicated emergency-access account with pre-created IAM roles (optionally identity providers).
    • Cross-account roles in the workload accounts that trust those roles, pushed with CloudFormation StackSets.
    • SCPs that deny deleting or changing those roles.
    • CloudTrail on the emergency account, sent to the central log archive.
  • Document each failure mode and its assumptions, use the account only in emergencies, and test the process regularly.

3.5 SEC03-BP04 Reduce permissions continuously (risk: medium)

  • Anti-patterns: administrator by default; policies kept after they are needed; permissive but not quite admin.
  • Use IAM Access Analyzer (shared-resource findings and policy generation).
  • Test permissions in lower environments first, tighten progressively through test and staging, and let SCPs cap the maximum while lower environments stay looser.
  • Use last-accessed timestamps to find unused users, roles and actions, and set an agreed timeframe for removing them.

3.6 SEC03-BP05 Define permission guardrails for your organisation (risk: medium)

  • Anti-pattern: creating member accounts but not using SCPs to restrict them.
  • Steps: isolate workloads into accounts; use SCPs for the maximum permissions; use resource policies and trust-policy conditions to narrow further.
  • Two SCP strategies, both with trade-offs:
    • an allow list (name what is permitted, block the rest) or a deny list (name what is forbidden, allow the rest)
    • The choice depends on your risk model.

3.7 SEC03-BP06 Manage access based on lifecycle (risk: medium)

  • Adjust access at joining, role change and leaving.
  • Steps:
    • document grant, review and offboarding
    • use IAM roles, groups and boundaries
    • make the identity provider (Active Directory, Okta, Ping Identity) the source of truth for IAM Identity Center
    • sync with SCIM
    • create permission sets per job role
    • run regular access reviews and train staff.

3.8 SEC03-BP07 Analyse public and cross-account access (risk: low)

  • Anti-patterns: no inventory of shared resources; no approval process for cross-account or public access.
  • Tools: AWS Config aggregated across the organisation to a delegated administrator, IAM Access Analyzer findings, Config auto-remediation that re-enables S3 Block Public Access, alerts when Block Public Access is turned off, and an SCP that prevents changing it.

3.9 SEC03-BP08 Share resources securely within your organisation (risk: medium)

  • Sharing overlapping components avoids recreating them in every account.
  • Anti-patterns: no monitoring or alerts for unexpected external shares; no baseline of what may be shared; defaulting to broad policies.
  • Steps:
    • use AWS Organizations
    • use trusted access for integrated services (service-linked roles are created in member accounts)
    • establish a data perimeter, a clear boundary of trust and ownership.

3.10 SEC03-BP09 Share resources securely with a third party (risk: medium)

  • Use just-in-time, least-privilege access with temporary credentials.
  • Anti-patterns: the default trust policy without conditions; long-term keys; reusing external IDs.
  • Use cross-account roles rather than access keys; IAM Roles Anywhere for third-party workloads; do due diligence on SaaS providers, including their shared responsibility model.

Summary points

  • Grants live in identity and resource policies; limits live in SCPs, boundaries and session policies.
  • Reduce permissions by evidence, not by guessing.
  • Test the break-glass process before you need it.
Terms to carry forward
  • Permissions boundary, SCP, session policy: the three limits.
  • ABAC: access by matching tags on principal and resource.
  • IAM Access Analyzer: finds external sharing and generates policies from activity.
  • Data perimeter: boundary of trusted identities, resources and networks.
  • Break-glass: emergency access path used only when normal sign-in fails.
