Building Event-Driven Microservices 4: Schemas and Data Contracts

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 4 (an earlier version appeared in Building an Event-Driven Data Mesh, O'Reilly 2023). Previous: Building Event-Driven Microservices 3: Fundamentals of Event-Driven Microservices. Next: Building Event-Driven Microservices 5: Designing Events.

Takeaways
  • A schema is an explicit declaration of structure, names, types, defaults and limits. Technically optional, but "effectively essential": without one, every consumer interprets the data its own way.
  • Use Protobuf or Avro (JSON Schema is a reasonable third). Never use schemaless JSON on event streams.
  • Schema evolution is governed by compatibility modes; start with full-transitive, because loosening later is easy and tightening is extremely hard.
  • A data contract is the schema plus SLOs, ownership, access restrictions, field-level encryption and evolution rules.
  • A schema registry replaces the per-event schema with an ID, validates evolution, enables discovery and documentation. Field-level encryption and data catalogues extend it.

4.1 Serialisation and deserialisation

  • Serialisation
    • converts an in-memory event object into bytes sent over the network and written to the stream
    • the schema specifies the conversion. A field length declared Integer throws an exception if set to the String "six feet" (Figure 4-1).
  • The consumer reverses it (Figure 4-2): bytes back into an object it understands, which needs the schema. By default the schema travels with the event; the registry (below) avoids that.

4.2 What is a schema?

  • Like a database table definition: at minimum names, types, restrictions and defaults, giving producer and all consumers a shared understanding.
  • Without schemas interpretation is left to consumers
    • With only one consumer it may work (not advisable), but important data has many consumers across business units, languages and databases: two streams and five consumers give ten unique interpretations (Figure 4-3)
    • Less structure means more misinterpretation, divergent results and avoidable mistakes.
  • Example 4-1, a Protobuf Person schema (field numbers give wire position and cannot change):
// Example 4-1: Person schema with Protobuf
message Person {
    // The person's unique ID.
    // The field number = 1, indicating its position in the wire format.
    // You cannot change the field number once it is established.
    int32 id = 1;
    // The person's full legal name
    string name = 2;
    // Measured in centimeters, rounded to the nearest centimeter
    int32 height = 3;

    enum CountryCode {
        ABW = 0;
        AFG = 1;
        // ...
        ZWE = 248;
    }
    // ISO3166-1-alpha-3 standard. AAA=OTHER
    CountryCode country = 4;
}
  • Errors can still creep in: a developer might record height in inches instead of centimetres.
  • Code generation
    • (Figure 4-4): a Java producer generates classes with the Protobuf generator
    • a C++ consumer generates its own structs. Avro and Protobuf have generators for Rust, Go, Java, Kotlin, Python, C++, C#, Dart, JavaScript and more.
// Example 4-2: populate a Person object generated from the Protobuf schema (file as placeholder for the event)
Person jeremiah = Person.newBuilder()
    .setId(8675309)
    .setName("Jeremiah Wasabullfrog")
    .setHeight(167)
    .setCountryCode("CAD")
    .build();
output = new FileOutputStream("ProtoPerson.data");
jeremiah.writeTo(output);

// Example 4-3: C++ consumer parsing the serialised Person
Person jeremiah;
fstream input(argv[1],
    ios::in | ios::binary);
jeremiah.ParseFromIstream(&input);

// jeremiah is now populated with the id, name, and height received in the event
id = jeremiah.id();
name = jeremiah.name();
height = jeremiah.height();
cc = jeremiah.countryCode();
  • Benefits:
    • Schemas as code: reviews and commit history show who changed what and why.
    • Data protection: the producer fails to serialise non-conforming data instead of publishing it; bypassing needs a deliberate choice.
    • Embedded documentation, easy to keep current.
    • A foundation for discussion in pull requests.
    • Code generation: code against typed classes, not generic maps.
    • Schema evolution with safeguards (below).
    • Test data generators: for example Kafka Connect Datagen with constraints, such as userid matching the regex User_[1-9] (Example 4-4).

4.3 Schema technologies

  • Protobuf (Google; open source 2008; popular for gRPC):
    • scalar and complex types; schema not stored with the event but in a separate file, usually shared through a registry; composition via other files; no dynamic types.
    • v2:
      • required or optional fields, custom defaults
      • v3: removed required and custom defaults (all fields optional; implicit defaults only empty string, empty bytes, false or 0, so you cannot tell whether the default was applied or the data matched it), leading to a long-running schism
      • Protobuf Editions (2024): write edition="2023" instead of syntax="proto2"/"proto3", and choose how defaults, optionals and other features work.
  • Apache Avro (initial release 2009; common with Kafka and as a row-based big-data format):
    • primitive and complex types
      • the schema is stored alongside the event by default (or in a registry)
      • this allows dynamic deserialisation into a GenericRecord when no generator is available
      • composition via other files
      • evolution is possible but not explicitly part of the standard.
{
    "type": "record",
    "name": "Person",
    "namespace": "com.event.driven.microservices",
    "doc": "Example of a Person record",
    "fields": [
        {
            "name": "id",
            "type": "integer",
            "doc": "The person's unique ID"
        },
        {
            "name": "name",
            "type": "string",
            "doc": "The person's full legal name"
        },
        {
            "name": "height",
            "type": "integer",
            "doc": "Measured in centimeters, rounded to the nearest centimeter"
        },
        {
            "name": "countryCode",
            "type": "enum",
            "symbols": ["AAA", "ABW", "...", "ZWE"],
            "doc": "ISO3166-1-alpha-3 standard. AAA=OTHER"
        }
    ]
}
  • Example 4-6 above is shown as in the book (the integer and inline enum type names are as printed). In Avro the type and doc properties live inside the field definition
    • Protobuf uses C/C++ style comments.
  • JSON Schema:
    • annotates and validates JSON
      • unlike Avro and Protobuf you can use JSON with no schema, which the book says not to do (schemaless JSON leaves room for error, misinterpretation and missing data)
    • Six primitive types (null, boolean, object, array, number, string), references, validation keywords for numbers, strings, arrays and objects, producers validate before writing
    • It is the only one here with a language for validation ranges: height limited to 1 to 300 would catch millimetres but not inches (72 inches fits).
{
    "$id": "https://example.com/person.schema.json",
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "title": "Person",
    "type": "object",
    "properties": {
        "id": {
            "type": "number",
            "description": "The person's unique ID"
        },
        "name": {
            "type": "string",
            "description": "The person's full legal name"
        },
        "height": {
            "type": "number",
            "description": "Measured in centimeters, rounded to the nearest centimeter",
            "minimum": 1,
            "maximum": 300
        },
        "countryCode": {
            "type": "string",
            "enum": ["AAA", "ABW", "...", "ZWE"],
            "description": "ISO3166-1-alpha-3 standard. AAA=OTHER"
        }
    }
}
  • Avro and Protobuf stayed at the top five years on; Kleppmann's Designing Data-Intensive Applications, chapter 4, analyses JSON, XML, Protobuf, Thrift and Avro.

4.4 Schema evolution

  • Even a perfect model may change (new products, new demands)
    • Evolution lets new consumers get new data without breaking existing consumers, using compatibility modes (so no if schema.version == 1 code in consumers).
Mode Meaning
Backward consumers on the new schema can read old data; deleting a field is backward compatible
Forward consumers on an old schema can read new events (seeing only what matches their version); matters when an existing consumer rewinds its offset to historical data
Full convertible forward and backward to the immediately adjacent version
Full-transitive convertible to any other version in the stream; strongest guarantee
  • Worked example:
    • version 1 has id and foobar; version 2 drops foobar
    • Version 2 is backward compatible (drop the field), but not forward compatible, since version 1 has no default for foobar to fill the gap
    • Add a default to version 1 before publishing it:
{
    "type": "record",
    "name": "Example",
    "doc": "This is Version 1, but with a default value for foobar",
    "fields": [
        {
            "name": "id",
            "type": "integer"
        },
        {
            "name": "foobar",
            "type": "string",
            "default": "DEFAULT_VALUE_STRING"
        }
    ]
}
  • Defaults apply at read time, not write time,
    • and only when the record lacks the field (unlike a database default)
    • Converting a version 2 record to version 1 sets foobar to the default instead of throwing
    • Developers often use a marker value to flag that data is missing due to conversion, not a real null.
  • Avro, JSON Schema and Protobuf v2 allow custom defaults; Protobuf v3 deliberately removed them, so it is harder to evolve. Always check your chosen format's specifics.
  • Tip:
    • start at full-transitive: consumers only update code when the business case changes, not when a schema breaks. Loosening later is easy
    • tightening is extremely difficult. Add compatibility tests to pull requests.

4.5 What is a data contract?

  • Like a service contract (Chapter 3) but about the data guarantees of the event stream itself: the compact between a producer and all consumers past, present and future, answering "what are the guarantees for this data?" Seen in data mesh, data lakes and warehouses too.
  • Warning: not every stream needs one. Tightly coupled clusters of services (a highly orchestrated workflow) owned by one team may skip it.
  • Components:
    • Schema(s): one, or several through evolution or colocated event types (Chapter 5).
    • Service-level objectives: if streams stop, the business stops; offer SLOs as for request-response services.
    • Ownership: the team or person who handles change requests, support and SLOs.
    • Access restrictions: know your consumers so you can warn them of changes; per-service credentials (Chapter 19).
    • Field-level encryption (below).
    • Schema evolution rules.

4.6 Negotiating a breaking schema change

  • Breaking changes usually come from shifting domain boundaries as the business expands
    • Example: a User with an address string (Example 4-11) becomes User_v2 with home_address and work_address as nested Address records (with an optional phone_number; Example 4-12)
    • Downstream consumers of the string field are affected.
{
    "type": "record",
    "name": "User",
    "namespace": "user.namespace",
    "fields": [
        { "name": "first_name", "type": "string" },
        { "name": "last_name", "type": "string" },
        {
          "name": "address",
          "type": "string"
        }
    ]
}

{
    "type": "record",
    "name": "User_v2",
    "namespace": "user.namespace",
    "fields": [
        { "name": "first_name", "type": "string" },
        { "name": "last_name", "type": "string" },
        {
            "name": "home_address",
            "type": {
                "type": "record",
                "name": "Address",
                "namespace": "user.namespace.inner",
                "fields": [
                    { "name": "phone_number", "type": ["null", "string"] },
                    { "name": "address", "type": "string" },
                    { "name": "city", "type": "string" },
                    {
                      "name": "country",
                      "type": "string"
                    }
                ]
            }
        },
        {
            "name": "work_address",
            "type": "user.namespace.inner.Address"
        }
    ]
}
  • Follow the API deprecation precedent (libraries, frameworks, REST APIs keep legacy support, then deprecate, then remove):
    1. Design the new schema (the owning team); consumers review since they must migrate.
    2. Consult consumers and gain approval, ideally via code review; expect iterations; then write a release guide and a deprecation plan.
    3. Plan release, migration and deprecation: estimate migration time plus padding; consumers may rebuild state stores. Historical data is the hard part: remodelling existing fields can be migrated, but net-new data cannot (is the old address home or work? the source cannot fill the other field). Backfilling the new stream captures only the current state. Support both streams for a period (such as 8 to 12 weeks).
    4. Execute: release the new stream beside the old; mark the old one deprecated to block new registrations and redirect people to User_v2 (ideally through a central data portal, Chapter 19).
  • Tip:
    • set a hard cut-off date, send many warnings, or consumers (lacking resources, with competing priorities) will never finish
    • Do not keep two versions forever: inconsistent data, partial outages, accumulating technical debt.

4.7 The schema registry

  • A service that registers schemas in association with event streams
    • Main purpose: cut network bytes
    • Plain serialisation appends a full schema to every record (Figure 4-5: lower throughput, higher replication cost, more consumer load)
    • With a registry the schema is stored once and each event carries a unique ID (Figure 4-6).
  • Producer flow: query the registry
    • , register the schema
    • , replace the schema with a short ID (3, 4), produce
    • Consumer: read from the stream
    • , query the registry by ID (7, 8), obtain the schema
    • , deserialise (10, 11). Confluent's Kafka Schema Registry uses a 5-byte prefix; serialisers must follow the registry's proprietary format and registries differ
  • Other benefits:
    • Data discovery: stream to schema mapping; self-service search on fields, docs and tags.
    • Schema evolution validation: registration is mandatory on the write path, a hook to throw on unauthorised evolution (such as breaking backward compatibility), a completely invalid schema, or a malformed event.
    • Automatically updated documentation: names, types and doc fields, likelier to be current because embedded.
    • Downloadable schemas to generate classes and unit-test events.
  • Tip: a custom registration script can check every field has a non-empty doc, scan for PII patterns and request extra verification, or generate classes and run validation tests before deployment.

4.8 Field-level encryption (FLE)

  • A producer encrypts specific fields; only consumers granted access can decode them
    • PII, financial, health and legal data often need special handling
    • A bank transfer (Table 4-1) encrypts email, user and account while amount and datetime stay readable, so an analytics system can total movement without decrypting
    • No separate stream per security level is needed.
  • Format-preserving encryption
    • keeps the same characters, spacing and length, so the schema still describes the data and legacy streams need no schema renegotiation
    • other encryption can malform (a long account ID becomes a 64-character string, a nested object an array of hashed bytes).
  • Tip: finer-grained access and per-field decryption keys reduce the leak surface. Encrypting sensitive data also helps with the right to be forgotten (Chapter 18).

4.9 Integration with data catalogues

  • A data catalogue stores schemas, location and business metadata (ownership, evolution restrictions, sample data, tags such as PII or financial). A registry gives operational schema management
    • a catalogue adds one place to browse, search, discover and publish data sets, historically for data at rest (databases, Parquet files), now increasingly for event streams too.
  • Options:
    • AWS Glue, Azure Data Catalog, Google's Dataplex Universal Catalog
    • open source Apache Atlas, OpenMetadata, DataHub. Many add governance, dependency modelling and access control. Not strictly required, but likely to be adopted
    • weigh schema compatibility, vendor lock-in and build versus buy.

Summary points

  • Schemas give structure and clarity; code generators bridge schema and business logic for both producers and consumers; quality control happens as close to the source as possible.
  • Evolution gives explicit up-front rules; breaking changes follow a negotiated process; schema changes go through the same review as code.
  • Avro and Protobuf remain the best options, JSON Schema a reasonable third; decide centrally with a federated governance team.
Terms to carry forward
  • Serialisation, deserialisation; schema; code generation.
  • Backward, forward, full, full-transitive compatibility.
  • Data contract; schema registry; field-level encryption; format-preserving encryption; data catalogue.
