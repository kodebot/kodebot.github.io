Building Event-Driven Microservices 5: Designing Events

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 5 (an earlier version appeared in Building an Event-Driven Data Mesh, O'Reilly 2023). Previous: Building Event-Driven Microservices 4: Schemas and Data Contracts. Next: Building Event-Driven Microservices 6: Integrating Event-Driven Architectures with Existing Systems.

Takeaways
  • Events are state (the full entity, a database row) or delta (the transition). State events are the best choice for cross-domain communication, via event-carried state transfer.
  • Prefer current state over before/after events: smaller, compactable, no leftover data.
  • Delta events belong inside a bounded context (event sourcing, tightly coupled apps). Across domains they have five major problems.
  • Hybrid and notification events are to be used with caution, if at all. Measurement events record occurrences and suit aggregation.
  • Design for privacy early: encrypt, keep keys in a KMS, and use crypto-shredding to meet the right to be forgotten.

5.1 Introduction to event types

  • Every change has three stages (Figure 5-1, a square wave):
    • the initial state, the delta that alters it, and the final state (the initial state of the next change)
    • Most events are state or delta.
  • State events:
    • fully describe an entity at a point in time, like a database row
    • the most flexible and useful for sharing business data between teams and systems
    • also called level, noun or fact events.
  • Delta events:
    • describe the transition and typically contain only what changed
    • more common between highly coupled systems, since the event definition and its interpretation are tightly linked
    • also edge, verb or action events.
  • Hybrid events describe both state and transition: usually a kludge when a deeper rework is not possible ("trying to make the quarter's profit goal"), and tend to cause undesirable coupling.

5.2 State events and event-carried state transfer

  • The key is the entity's unique ID
    • the value is the full set of data available to consumers. Examples: Item, Order, User (commerce)
    • Truck, Package, Driver (shipping)
    • Payment, Debit, Account (banking).
  • Benefits:
    • ECST: the event carries state to any number of consumers, who can reason about and react to it.
    • Materialisation: consume the stream and build your own state store.
    • Strong decoupling: the definition stays inside the producer's bounded context with no coupling to its internal logic.
    • Infer changes from state: compare the current event with the previous one for the key (Figure 5-2: name, price and stock changed, so update signage, order inventory or re-rank search).
  • Two design strategies: current state and before/after state (popular via change-data capture).

Current state events

  • Contain only the current public state (for example the latest quantity for an item_id). Benefits:
    • Lean: minimal space and network.
    • Simple: the broker keeps earlier events, so rewind and replay offsets for history; set compaction per stream.
    • Compactable: stream size is proportional to unique keys (1,000 keys gives just over 1,000 events).
  • Properties to consider:
    • Agnostic to why it changed: consumers cannot couple to the producer's internal transitions (like a database table, which does not say why a row changed). (Hybrid events bend this.)
    • Consumers must maintain state to detect transitions:
      • for example a customer moving country may need new legal documents depending on both countries
      • the consumer stores the subset of state it cares about, giving clean separation and flexibility when business logic changes.

Before/after state events

Key: 26
Value: {
    before: { name: "Adam", country: "Madagascar" },
    after: { name: "Adam", country: "Canada" }
}

Key: 26
Value: {
    before: { name: "Adam", country: "Canada" },
    after: null
}
  • Benefits:
    • every changed (and unchanged) field in one transaction in one event (but not the reason)
    • simple detection without consumer state (Madagascar to Canada). It fails with two moves in quick succession (Madagascar to Ethiopia, then Canada), and the theoretical stateless consumer is seldom realised since most services keep state.
  • Drawbacks:
    • Compaction is difficult:
      • a deletion sets after to null but the whole value is not null, so Kafka does not treat it as a tombstone. You must write a secondary tombstone event (Figure 5-3), as Debezium (a change-data capture service) does
      • rewriting compaction logic is rarely feasible, especially with SaaS.
    • Leftover information: old data stays in before, and there is a variable delay before asynchronous compaction.
    • Doubled storage and network:
      • on average double over the wire and on disk, borne by producers, consumers and broker
      • costly for high-volume streams, including cross-region transfer fees.
  • Verdict: current state events are far better. Consumers keep only what they need, disk is cheap, broker operations simplify, and the leak risk from improper deletion disappears.

5.3 Delta events

  • Represent the change within a domain (the edge in Figure 5-1):
    • only information about the change, not past or current state
    • Phrased as past-tense verbs: itemAddedToCart, itemRemovedFromCart, orderPaid, orderShipped, orderReturned, userMoved, userDeleted
    • Historically common, particularly with the lambda architecture, and used inside a domain for event sourcing.

Delta events for event sourcing

  • Event sourcing
    • records what happened as a sequence of immutable, append-only events and builds current state by applying them in order with domain logic
    • It is promoted as an alternative to CRUD, where the mutable state is modified directly and only the final state retained (an audit log serves auditing, not business logic).
  • CRUD limits:
    • operations hit the data store directly (slow under heavy use, timeouts)
    • high-concurrency operations on the same entity cause conflicts and failed transactions. CRUD strengths: strong read-after-write consistency (depending on the database), intuitive, abundant tooling (Figure 5-4: one create and two updates to a refrigerator's contents).
  • In event sourcing (Figure 5-5) the same operations are events in a durable log (often a single local table). A domain aggregator
  • is separate from the writer
  • so they scale independently; a domain can have several aggregators building different state stores. The owner can design deltas freely (turn_lights_on, open_door)
  • Using Kafka for event sourcing adds network latency both ways and an availability risk
    • The main drawback is eventual consistency: a delay between writing and seeing the materialised result, and concurrent writers make it hard to attribute a change to your own delta, so it can be unsuitable where strong consistency is needed.
  • The problem arises when event sourcing is used as interdomain communication: others couple on and misinterpret private domain events that change over time
    • You may expose events outside, but each becomes part of the public data contract whose meaning must not drift
    • Keep "events in here" and "events out there" separate.

The problems with delta events across domains

  • Deltas are not bad per se, but often misused. Five problems:
    1. An infinite number of delta types. The real set is finite, but every consumer must know how to apply each into its own state. Shopping cart (Figure 5-6): ItemAdded, ItemRemoved; adding ItemQuantityUpdated (Figure 5-7) changes how consumers aggregate; coupons, shipping estimates and subscriptions make it sprawl (Figure 5-8). People choose deltas to avoid consumer state, but this is a trap.
    2. The interpretation logic must be replicated to each consumer (Figure 5-9). Consumers must identify, understand and correctly apply each event; lagging brokers deliver events out of order, causing wrong transitions; one consumer may wait up to 30 seconds for late events while another discards them, so aggregates differ. Any producer change must reach every consumer: "tightly couples the producer, the event definitions, and the consumers".
    3. Delta events map poorly to event streams. How do consumers learn of new deltas? "Put it all in one stream" only gives them events they cannot use, raising exceptions or silent wrong results, and violates one evolvable schema per stream. New streams are easier to discover but still need notification and code updates. State events encapsulate everything in the producer and change only through schema evolution.
    4. Inversion of ownership: consumers push their business logic into the producer. A "package shipped" email needs the producer to compute that delta (Figure 5-10); each new need adds another (Figure 5-11): userReturnedItemAfterTelephoneComplaint, userSawAtLeastThreeAdsThenPurchasedIt. Even then a consumer needing ads from one service and payments from another (Figure 5-12) must keep state; changing three ads to four needs a whole new event definition. Better: general-purpose state, with consumers deciding.
    5. Inability to maintain historical data: deltas cannot be compacted. Ten years of cart events could take, for example, three weeks to replay (Figure 5-13). Purging loses data; offloading to a side store needs the order preserved; building a snapshot of state (Figure 5-14) means creating the public state definition you tried to avoid, and the consumer must then switch from snapshot to stream, which is the lambda architecture again (Figure 5-15).

Where to use delta and state events

  • Delta events are best within a private domain's boundary,
    • where tight coupling can be managed consistently
    • fine inside one application (event sourcing) and between tightly coupled applications.
  • Insufficient arguments for deltas between domains (quoted from "that person who doesn't want to use state events"): maintaining duplicate state is wasteful and takes too much disk
    • consumers will know what an event means, how could they misinterpret it
    • "I really only care about this one transition, just publish a custom event for me".
  • Reality: disk is extremely cheap, a software engineer's time is not (break-fix work dwarfs storage cost).
  • Good practice (Figure 5-16):
    • context 1 has deltas and state streams, tightly coupled but owned by one team
    • the deltas stay private and one service composes state events for others. Contexts 2 and 3 independently consume that state
    • context 4 consumes context 3's state and uses deltas internally (maybe multi-type streams and side snapshot stores), which is nobody else's concern.

5.4 Hybrid events: state with a bit of delta

  • Warning: exposing how or why may tightly couple consumers to the producer's business logic.
  • Example:
    • users sign up via the home page, an email advertising link, a third-party account, or an administrator
    • Consumers want to know which (an onboarding workflow; analytics on sign-up methods)
    • Instead of four delta events, a user state event with an enum:
Key: "USERID-9283716596927463"
Value: {
    name: "Randolph L. Bandito",
    signup_time: "2022-02-22T22:22:22Z",
    birthday: "2000-01-01T00:00:00Z",
    // An enum of (MAIN, VIA_AD_EMAIL, THIRD_PARTY, or ADMIN)
    method_of_signup: "VIA_AD_EMAIL"
}
  • Risks:
    • how a user signs up is a private detail
    • what "main" means may drift, the enum may grow (VIA_MOBILE_APP), and consumers must be told before the definition changes or they can hit fatal errors.
  • Risk here is low but not zero:
    • the sign-up method is immutable
    • the logic is simple (a binary delta)
    • and clear schema documentation prevents drift. By contrast userReturnedItemAfterTelephoneComplaint has many sequential dependencies and drifts easily.
  • A hybrid event is a trade-off: risk is proportional to the delta's complexity and likelihood of change. Try to decouple further; a delta-type field becomes part of your data contract.

5.5 Measurement events

  • A complete record of an occurrence at a point in time: web analytics (Google Analytics), behaviour tracking, a user seeing an ad:
Key: "USERID-8271949472726174"
Value: {
    utc_timestamp: "2022-01-22T15:39:19Z",
    ad_id: 1739487875123,
    page_id: 364198769786,
    url: https://www.somewebsite.com/welcome.html
}
  • Enable aggregations
    • (most popular page_id, when users see the most ads, average ads per session)
    • Sources may be lossy (ad-blockers), good enough for much analysis
    • Can power time-sensitive applications
      • (factory temperature and humidity: trends for analytics, quick reaction for operations)
      • after a connectivity gap, a stream may drop 30 to 60 seconds of old data and publish the latest, or keep everything, depending on SLOs.
  • Practice (the author at RIM, now BlackBerry):
    • when a bad thing happened on a developer device (dropped call, failed message, modem reset, custom triggers) it dumped measurements to backend servers for problem reports. Lessons: a well-defined schema makes automated processing easier
    • completeness mattered more than real time (events hours, days or weeks old, such as a device offline on a flight), and the SLOs said so.

5.6 Notification events

  • A minimal fact that something happened plus a link or URI to more information (phone notifications)
    • Example: NEW_MESSAGE with a click-through URI
    • The misuse: sending a pointer instead of state:
Key: 12309131238218
Value: {
    status: "PARTIAL_RETURN",
    utc_timestamp: "2021-21-13T13:11:42Z",
    access_uri: "serverURI:8080/orders/values/12309131238218"
}
  • Problems:
    • The event is not a record of state at that moment unless the target is immutable (usually mutable): a race condition
      • SOLD, PARTIAL_RETURN, FULL_RETURN emit three events, but a lagging consumer may find only FULL_RETURN, and a new consumer sees only the current state.
    • More complexity: the owner must also serve synchronous requests, with access control, authorisation and scaling for both the producer and the query API.
  • Better: publish the state as an immutable record of that point in time.

5.7 Event design for data privacy and the right to be forgotten

  • PII and financial data have high security requirements, often legal
    • GDPR applies to any organisation processing data of people in Europe; Article 17 gives individuals the right to have personal data deleted without significant delay
    • But streams are immutable (Chapter 18 covers bad-data techniques), so encrypt first.
  • Use field-level encryption or encrypt the whole event, with a key-management service (KMS) holding keys and a secure API
    • Use a unique key per user, account or other entity: to delete someone's data, delete the key, making all encrypted data inaccessible
    • This is crypto-shredding: cryptographically unavailable, usually enough for privacy law, but check with your lawyers
    • Consumers ask the KMS for keys (with permission) and decrypt themselves.
  • Warning: consumers must keep the same encryption in their private stores; avoid storing sensitive data unless necessary.
  • Why it matters:
    • Large amounts of data in backups, tape and cold storage are costly and slow to read, delete from and rewrite.
    • Partial encryption keeps non-PII data useful (deleting only the PII can satisfy Article 17).
    • Multiple systems: deleting the keys halts access everywhere at once, even where slow to delete.
    • Defence in depth: leaked encrypted data is far less damaging.
  • It does not protect against consumers who negligently store decrypted data or keys: give clear policies, time-limit key retention and never write decrypted data to disk
    • Adding encryption later is hard and probably a breaking change (decryption, KMS connectivity, retention validation).

Summary points

  • State events (ECST, with indefinite retention, durable state and compaction) are the best way to share data between domains, enabling kappa and avoiding lambda.
  • Deltas stay in event sourcing and tightly coupled communication inside a bounded context; never allow cross-domain coupling on them.
  • Measurement events record occurrences for aggregates and rapid reaction. Use hybrid and notification events with caution, if at all.
Terms to carry forward
  • State, delta, hybrid, measurement, notification events.
  • Current state versus before/after events; event sourcing; CRUD; domain aggregator.
  • Crypto-shredding; KMS; right to be forgotten (GDPR Article 17).
