Building Event-Driven Microservices 8: Stateful Event-Driven Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 8. Previous: Building Event-Driven Microservices 7: Denormalization and Eventification. Next: Building Event-Driven Microservices 9: Deterministic Stream Processing.

Takeaways
  • Almost every useful microservice keeps state, and state goes hand in hand with partition assignment: when a partition moves, its state must too.
  • Internal stores (RocksDB on local SSD) scale with the broker and are fast; external stores survive restarts and give full data locality but add latency, cost and operational work.
  • Changelogs (compacted streams of state changes) are the usual way to rebuild internal state; hot replicas trade disk for zero-downtime failover.
  • To change an external store's data model, rebuild it from the input stream; avoid data migrations.
  • Effectively once processing comes from broker transactions, or from deduplication, or from committing state and offsets in one store transaction.

8.1 Partition assignment, repartitioning and copartitioning

  • Most event-driven microservices do three things:
    • react to an event (a stream, a request, a sensor reading, a row insert)
    • process it
    • produce output events. State is needed beyond toy complexity, and each microservice is responsible for its own state (create, read, update, destroy).
  • Each service has a consumer group tracking offsets, plus partition assignment to instances
    • Kafka delegates assignment to the first online client of the group (the leader); Apache Pulsar keeps it in the broker
    • Both use group identities for progress.
  • Work is momentarily suspended during reassignment so revoked partitions are no longer processed by another instance (no duplicate output)
    • A rebalance runs when an instance joins, or when one leaves and does not rejoin within a period (for example one minute).
  • State built from previously assigned partitions may need reassignment too: use a framework's internal stores (Chapters 12, 13) or external stores independent of repartitioning.

Repartitioning

  • Event streams are partitioned by key and the producer's partitioner, usually a deterministic hash (same key, same partition)
    • Repartitioning produces a new stream with a different partition count (more parallelism, or a count to copartition with another stream), different key (rekey on data in the value) or different partitioner.
  • Example (Figure 8-1): unkeyed user interaction events carry an id and other data x; the service keys them by id into a new stream with 3 partitions. Observations:
    • Events can be introduced out of order (id=2 has events in partitions 0 and 1 of the original; their order in the output is not deterministic; see "Out-of-Order and Late-Arriving Events").
    • Repartitioning gives parallelism and key locality, not throughput: a 2-partition stream repartitioned to 1,000 partitions is still limited by the 2-partition input.
  • Tip: if order is extremely important, generate it in order and in the same partition (here key by id from the start).

Copartitioning

  • Copartitioning
    • is repartitioning into a new stream with the same partition count and same assignor as another stream
    • Joins and multi-stream aggregations need all events of a key at one instance
    • Example (Figure 8-2): join the repartitioned user event stream with a user entity stream keyed on the same id; each join runs on its own instance.

Assigning partitions within a consumer group

  • With no relationships, round-robin is enough. Full-featured frameworks (Chapters 12, 13) infer which streams must be copartitioned or repartitioned and assign accordingly
    • basic consumer clients usually do not, so you manage it manually, which is hard with several copartitioned sets.
  • Figure 8-3:
    • two instances, three streams (two copartitioned for a join)
    • C0 has two sets of copartitioned partitions and C1 one. Figure 8-4: adding two instances causes a rebalance
    • C2 gets the copartitioned P2s plus stream A's P2, C3 only stream A's P3. More instances than partitions add no parallelism.
  • Warning: mechanics depend on your broker and framework; read the documentation and test before production.

8.2 Selecting a state store

  • Example service (Figure 8-5):
    • package customer orders against available inventory
    • It materialises Orders and Inventory, decides what ships now and what waits (at worst an order is delayed awaiting inventory, and packing has no flaws), and prepares the box with label
    • Which store?
  • Internal state stores: in the same container or VM, typically in memory or on volatile disk, online only when the service is; restarting the service restarts the store.
  • External state stores: outside the container or VM, largely independent of the service's life cycle, with a durability objective; failures do not affect the data.

8.3 Internal state stores

  • Each instance materialises the events of its assigned partitions, keeping each partition's data logically separate, so after a rebalance it can drop the state of a revoked partition. That avoids leaks and multiple sources of truth
    • new assignments are rebuilt from input events or the changelog.
  • RocksDB
    • (a high-performance key-value store) is typical: efficient with local SSDs for data sets beyond main memory
    • Relational or document stores are possible but must live inside each instance.
  • Internal stores are volatile, so state must be reloaded from a snapshot to an external location or from a changelog.

Changelog as state recovery

  • A changelog records all changes to the state store:
    • the stream half of table-stream duality
    • a permanent copy outside the instance that serves as a checkpoint (Figure 8-6). Tip: changelogs let a recovering processor avoid reprocessing all input events.
  • Figure 8-6:
    • an orders table of orders ready to package
    • once packed, the record is deleted, which writes a tombstone for key 181 to the orders changelog. Changelogs live in the broker with read and write permissions limited to the owning application, and are commonly compacted (they restore state, not track history).
  • Restoration (Figure 8-7):
    • the new instance loads its changelog partitions as fast as events can be read and inserted
    • key 181 may already be compacted, or loaded then deleted
    • no business logic is triggered during restoration.
  • Changelogs are built in (Kafka Streams client) or implemented by the developer; basic producer/consumer clients do not provide them.

Global state

  • A global (broadcast) state store materialises all partitions of a stream on every instance (Figure 8-8)
    • Example: the full inventory in every packaging instance, so each can check availability before asking the warehouse
    • Fits when every instance needs the whole data set and it is small, commonly used and seldom changing; used for lookups, not to drive event-driven logic.

Advantages of internal state stores

  • Scalability offloaded to the broker and compute cluster (change the instance count); the capability team provides common scaling mechanisms.
  • High-performance disk:
    • keeping everything in memory is not always possible
    • local SSDs suit random access. A RocksDB random read from SSD is about 65 microseconds, so a single thread tops out near 15.4k requests/second
    • in-memory serves millions per second.
  • Flexibility to use network-attached disk:
    • much higher latency; with a 1 ms round trip the same pattern is capped at about 939 requests/second, and events must be processed in offset order so parallelism is limited
    • Generally fine for modest-performance services
    • Benefit: the volume can be reattached to new hardware so state is not rebuilt (less downtime, flexible movement across cheap on-demand nodes).

Disadvantages of internal state stores

  • Limited to runtime-defined disk: changing volume size or count usually means halting; many platforms only let volumes grow.
  • Wasted disk space: cyclical traffic (3 p.m. versus 3 a.m.) needs large peak disk but little otherwise; external services charging per byte can be cheaper.

Scaling and recovery of internal state

  • A new or recovered instance must materialise its state before processing; the quickest way is to reload the changelog for each stateful store.
  • Hot replicas:
    • materialise a standby copy of a partition on another instance (Kafka Streams has a simple configuration setting): highly available state, tolerating instance failure with zero downtime
      • Example (Figure 8-9): orders and inventory copartitioned on productId, one partition per instance
    • a failure otherwise means stopping, moving partitions, reloading the changelog, resuming
      • With a replication factor of 2 (Figure 8-10), each partition is primary on one instance and replica on another (replicas drive no logic)
      • When an instance terminates (Figure 8-11), the leader's assignor places the partitions on the instance holding the hot replicas
    • new replicas are then built from the changelog to restore the minimum count
    • if the original returns, workloads move back once it has rebuilt state.
  • Note:
    • details are framework-specific
    • Hot replicas cost disk and replica maintenance in exchange for less downtime: valuable for low-latency use cases, unnecessary where higher latency and periodic outages are tolerable.
  • Restoring from changelogs: the instance should not process new events while loading (nondeterministic, erroneous results).
  • Restoring from input event streams
    • (no changelog): consume from the beginning of assigned partitions in strict order, update state and produce output events
    • Warning: consider output from full reprocessing: downstream consumers may need to process idempotently or drop duplicates, or you can halt output until a progress condition is met
    • It is much slower; use only for simple topologies where duplicate output does not matter, entity streams are well compacted and input retention is short.

8.4 External state stores

  • On dedicated hardware, in its own container or VM, or (most commonly now) a managed cloud service: relational, document, graph, geospatial, distributed key-value
    • Choose by the problem space
    • The data set must stay logically isolated from other microservices, or coupling makes refactoring the internal model very hard.
  • Warning: do not share direct state access between microservices; each materialises its own copy (extra processing and storage buys decoupling).
  • Advantages:
    • Full data locality:
      • each instance can reach all the data (lookups, foreign-key relational queries, geospatial queries), while still processing only its assigned partitions
      • Tip: use stores with strong read-after-write guarantees to avoid inconsistent results across instances.
    • State survives outages: independent of instance life cycles; restarts need no rebuild.
    • Technology options: familiar stores speed delivery; good for basic producer/consumer (Chapter 11) and functions as a service (Chapter 15).
  • Drawbacks:
    • Management of multiple technologies:
      • the owner must scale and monitor the store (managed services help). Note: each team fully manages its stores
      • keep a list of acceptable external data services with guides rather than creating a technical cross-team dependency.
    • Network latency: caching and parallelisation add complexity and cost, and many patterns just block awaiting a reply.
    • Financial cost: hosted stores charge by transactions, payload size and retention, may need over-provisioning; on-demand pricing may help if performance holds.
    • Full data locality has a catch:
      • data comes from many processors, each at its own rate, so it is hard to reason about and debug
      • race conditions and nondeterminism arise because each instance has its own stream time (one instance may join on a foreign key another has not populated yet; reprocessing later may produce a different, nonreproducible result).

Scaling and recovery with external state stores

  • Scaling the service is easy: a new instance with credentials. Scaling and recovery of the store depend on the technology. Strategies: source streams, changelogs, snapshots.
    • Source streams:
      • rewind offsets to the start
      • longest downtime but easily reproducible, relying only on the broker
      • a full application reset that reproduces output events unless discarded.
    • Changelogs:
      • external stores seldom use broker changelogs, but you may
      • create a fresh store and rebuild everything before resuming. Warning: both of these can be prohibitively slow from network latency
      • check SLAs.
    • Snapshots or checkpoints:
      • the store offloads an image (for example to Amazon S3); far more common
      • The challenge is aligning consumer offsets with the restored state: too late loses events, too early duplicates
      • If idempotent, set offsets before the snapshot time (at-least-once)
      • Otherwise store partition offsets with the data in one atomic transaction, then restore the offsets from the snapshot for effectively once semantics.

Rebuilding the external state store

  • New requirements (extra fields, new joins, newly derived data) usually mean rebuilding rather than migrating the store
    • Warning: data migrations are very risky and can be inconsistent with the source of truth; "any time or money saved ..
    • is often accounted for tenfold" in fixing consequences.
  • Steps:
    • update and test the code
    • create a new store and keep the old as a fallback
    • rewind the consumer offsets to the very start
    • start and repopulate (you may need to mute output events, or just emit new results)
    • verify, then delete the old store and any changelogs or snapshots
  • Tip: if the service depends critically on input data, keep it available for reprocessing; it is your snapshot.
  • Example (Figure 8-12):
    • the company starts international shipping and collects customer Country
    • the customer stream's schema evolves, and the packaging service rewinds to the start of the customer stream to rebuild its store with country.

8.5 Transactions and effectively once processing

  • Effectively once processing
    • guarantees that updates to the single source of truth are applied consistently regardless of producer, consumer or broker failure, notably by committing consumer offsets and output stream records in one transaction
    • It needs transactional support (Apache Kafka and Apache Pulsar), which atomically writes several events to several streams.
  • It is also called "exactly once", which is not quite accurate: a service may process data several times (crash before committing offsets) and still run the business logic and side effects (external endpoints, third parties) for every event.
  • Idempotent writes
    • (Kafka, Pulsar): an event is written to a stream once, using unique process IDs and monotonically increasing sequences to fence out duplicates
    • safe producer retries. Not every broker supports transactions or idempotent production
    • sometimes it does not matter, sometimes you build a workaround.

Example: inventory accounting

  • Emits an event when an item's stock is low from a chain of additions (shipments received, returns, found stock) and subtractions (sales, damage, theft) in one stream (Figure 8-13)
    • a running total in its data store, a threshold that triggers a purchase event
    • Every input must be applied effectively once: at-least-once and at-most-once give wrong results
    • It suits effectively once because it is entirely event-driven, makes no external requests, and can commit state and offsets atomically.

With client-broker transactions

  • Output events, changelog events and consumer offset events commit atomically (Figure 8-14)
    • If failure outlasts retry timeouts the broker aborts and commits nothing (Figure 8-15); transient errors can retry since commit is idempotent
    • Consumers do not process events from uncommitted transactions but respect offset order, waiting for commit or abort.
  • After a fatal producer error the replacement restores from changelogs and the last good input offsets from the offset stream (Figure 8-16)
    • the broker fails and cleans up incomplete transactions. Mechanisms vary by broker.

Without client-broker transactions

  • More work and careful duplicate handling:
    • (1) identify and filter duplicates created upstream
    • (2) update state and offsets in a local transaction, so the state matches the logical narrative of the inputs.
  • Warning: prefer a broker and client with idempotent writes; deduplicating after the fact does not scale (each consumer must implement safeguards).
  • Duplicates arise when:
    • the producer does not receive an ack and retries (same data, maybe same timestamps, new offsets; idempotent production filters these), or crashes after writing but before updating its offsets (logically identical copies with new timestamps and offsets, hard to recognise)
    • Note: idempotent production handles crash and retry failures between client and broker, not duplicates from faulty business logic.
  • Identifying duplicates:
    • first check whether duplicates matter at all (often negligible)
      • Otherwise have the producer generate a unique dedupe ID (a hash of key, value and event time, or the query time of a triggering request): works for events with large data domains (a bank transfer's source, destination, amount, date and time; an order's products, purchaser, time, total and payment provider; inventory debited per orderId), poorly for logically equivalent events
      • The ID should have high-cardinality elements
    • best generated with the event so all consumers benefit and the logic can change freely
      • Warning: unkeyed events are extremely hard to guard because partition locality is not guaranteed
    • produce with keys, respect partition locality and use idempotent writes.
  • Guarding against duplicates:
    • an effectively once consumer must identify and discard duplicates, perform idempotent operations, or use idempotent producers. Dedupe stores can grow very large
    • in practice deduplication is a rolling time or offset window, best effort
      • Tip: use TTL, a maximum cache size and periodic deletion
      • Deduplicate within a single partition (across partitions is prohibitively expensive; keyed events always map to one)
      • Figure 8-17: events pass through a dedupe store (TTL arbitrarily 8,000 seconds, to be set from business needs) before the business logic
    • also keep durable backups of the dedupe table, which must be rebuilt before resuming.
  • State store transactions:
    • use the data store's own transactions: move the input offset management from the broker into the data store
    • one transaction updates state and offsets (Figures 8-18 to 8-20). On a failure such as a commit timeout, abandon the transaction and revert to the last good state
    • consumption halts until the store returns, then resumes from the last good offset
      • Note: this gives effectively once processing but not production: output remains at-least-once (no atomic transaction between producer and broker).

Summary points

  • Internal stores support high-performance processing; external stores give flexible options; latency, throughput, cost, scaling and access patterns decide.
  • Changelogs are native to a narrow range of frameworks; alternatively use a transactional database with scheduled snapshots.
  • Brokers with transactions give powerful effectively once processing; deduplication provides it where they are unavailable.
