Building Event-Driven Microservices 9: Deterministic Stream Processing

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 9. Previous: Building Event-Driven Microservices 8: Stateful Event-Driven Microservices. Next: Building Event-Driven Microservices 10: Building Workflows with Microservices.

Takeaways
  • Deterministic processing means the same output whether a service runs in near real time or catches up from the start of the streams. Only best-effort determinism is possible with unbounded streams.
  • It needs consistent timestamps, well-chosen keys, event scheduling across partitions, and a strategy for late events.
  • Watermarks (Spark, Flink, Samza, Beam) and stream time (Kafka Streams) track event-time progress and define what is late.
  • Windows (tumbling, sliding, session) are where lateness matters most; choose to discard, delay, allow a grace period, or route late events elsewhere, as a business decision.
  • Plan reprocessing carefully (start point, volume, time, side effects).

9.1 Determinism with event-driven workflows

  • Three questions:
    • how does a service choose the order of events across partitions
    • how does it handle out-of-order and late events
    • how do we ensure deterministic results in near-real-time versus from the beginning? Answers: timestamps, event scheduling, watermarks and stream time
      • Bugs, errors and business logic changes force reprocessing, which makes determinism important.
  • A service is either processing near real time or processing the past to catch up (underscaled or new services)
    • If you rewound the consumer offsets to the beginning, would you get the same output? That is the goal.
  • Some workflows are explicitly nondeterministic: those based on current wall-clock time and those that query external services whose answers change. Watch for them.
  • Fully deterministic processing (every event on time, no failures, no network issues) is the ideal
    • reality gives best effort, enough in most cases. You need: consistent timestamps, well-selected event keys, partition assignment, event scheduling and late-event strategies.

9.2 Timestamps

  • An event in a stream has an offset (what has been read) and a timestamp (when it was created, for temporal order relative to other events). Timestamp types (Figure 9-1):
    • Event time: local timestamp assigned by the producer when the event occurred.
    • Broker ingestion time: assigned by the broker; configurable as event time or ingestion time (event time is much more common); a substitute when producer clocks are unreliable.
    • Consumer ingestion time: when the consumer ingests it; can be the event time from the broker record or wall-clock time.
    • Processing time: the wall-clock time of processing.
  • Event time can propagate to the consumer so its logic decides by when something happened.

Synchronising distributed timestamps

  • Two independent systems cannot share precisely the same clock time (material tolerances, temperature, network delays)
    • Clocks can be nearly in sync, which is good enough
    • Main mechanism: Network Time Protocol (NTP) servers; cloud providers such as Amazon and Google offer redundant satellite-connected and atomic clocks per region.
  • On a LAN, NTP gives a drift of only a few ms after 15 minutes, reducible to 1 ms or less with more frequent synchronisation in best cases (according to David Mills, NTP's inventor), though network issues may prevent it
    • Over the open internet skew reaches +/- 100 ms, relevant when reconciling events from different regions
    • NTP can fail (outages, misconfiguration, unreliable servers; multitenancy affects VM clocks)
    • Improvements to NTP servers and GPS are pushing accuracy into the sub-millisecond range
    • Minor out-of-order issues will still occur.
  • Offsets compare events only within one partition; many use cases need temporal order across streams
    • Example (Figure 9-2): a bank keeps a running tally from a deposits stream and a withdrawals stream, applying an overdraft penalty below $0
    • A naive round-robin consumer processes the $10 deposit, the $25 withdrawal (negative balance, penalty) and then the $20 deposit: wrong, since that is not the temporal order.
  • Warning: the consumer needs copartitioned streams so a key's deposits and withdrawals meet; otherwise repartition or rekey.

9.3 Event scheduling and deterministic processing

  • Event scheduling
    • chooses the next events to process across input partitions
    • Logs are consumed in offset order, but across partitions you must interleave by event time (Figure 9-2)
    • Tip: the common implementation dispatches the event with the oldest timestamp across all assigned partitions.
  • Present in many stream-processing frameworks, typically absent from basic consumers. Warning: you need it if event order matters to the business logic.
  • Custom event schedulers:
    • Apache Samza's MessageChooser can choose by stream priority, wall-clock time, event time, metadata or content
    • take care since many custom schedulers are nondeterministic and cannot reproduce results.
  • Which time to use:
    • locally assigned event time or broker ingestion time occur once per produce-consume workflow
    • wall-clock and consumer ingestion times vary with when the app runs. With healthy producers and consumers and no backlog all four are within seconds
    • when processing history, event time and consumer ingestion time differ a lot. Prefer event time if you can rely on it
    • else broker ingestion time (rarely, substantial delay when producer and broker cannot communicate reliably).
  • Timestamp extraction:
    • at consumer ingestion a timestamp extractor takes the timestamp from the key, value or metadata
    • it becomes the record's event time for the rest of processing.
  • Request-response calls to external systems may give nondeterministic results because their state and answers change; whether it matters is a business assessment.

9.4 Watermarks and stream time

Watermarks

  • A technique used by Apache Spark, Flink, Samza and Beam to track event-time progress through a topology and declare that all data of a given event time or earlier has been processed
    • A watermark is a specialised event injected by the framework and propagated along the topology
    • a node receiving it updates its own event time and forwards it (Figure 9-3)
      • The consumer node has the highest watermark, generating new ones periodically (after a period of wall-clock or event time, or a number of events): in the figure it has just generated Watermark(24)
    • Watermark(20) sits between events with timestamps 22 and 20
    • once the map stage processes event 20 and then Watermark(20), its internal watermark moves from t=10 to t=20.
  • A Google whitepaper describes watermarks; chapters 2 and 3 of Akidau, Chernyak and Lax, Streaming Systems (O'Reilly, 2018) go deeper.
  • In parallel processing
    • (Figure 9-4): two instances each consume a partition, groupByKey then aggregate, with a shuffle sending same-key events across instances
      • Watermarks are generated at the source and propagated
    • a node with several inputs keeps the minimum of its inputs' event times
      • Both aggregate nodes move from 13 to 15 when the groupByKey-1 watermark arrives
      • A watermark does not affect scheduling
    • it only tells the node events earlier than it are late.
  • Spark, Flink and Beam need a dedicated cluster that also provides cross-task communication and central coordination: repartitioning (groupByKey plus aggregate) uses cluster-internal communication, not event streams in the broker.

Stream time

  • Kafka Streams' approach:
    • stream time is the highest event timestamp last seen by the node
    • The consumer buffers events, applies event scheduling to select the next, and raises stream time if larger
    • Events processed with a lower stream time than the highest are out of order
      • Kafka Streams delays advancing the stream time (the watermark) until the grace period has passed, so windows can include late data rather than discard it.
  • Figure 9-5:
    • stream time is 20
    • the next event is the smallest across the two input buffers, event time 30
    • dispatched, and stream time becomes 30. It is maintained by processing each event completely through the topology before the next (depth first)
    • in a topology with a repartition stream, each subtopology has its own distinct stream time
      • Unlike watermarks, where events can be buffered at each node with independently updated event times.
  • Kafka Streams shuffles through internal repartition topics (streams) within a single topology
    • Spark, Flink and Beam use their own shuffle mechanism without the broker. Figure 9-6: groupByKey then aggregate
    • keys A and B go to repartition stream P1, X and Z to P0
    • event time is preserved but data is no longer in strictly ascending order per key, so subtopologies must accommodate out-of-order data
      • Check the documentation on stream time and topologies, since it is largely limited to Kafka Streams.
  • Tip: watermarking can also use repartition streams (Samza's standalone mode is similar to Kafka Streams but with watermarks).

9.5 Out-of-order and late-arriving events

  • An event is out of order if its timestamp is not equal to or greater than the events ahead of it in the stream (Figure 9-7: F is out of order because its timestamp is lower than G's; H lower than I's).
  • Bounded
    • data processed in batch resists out-of-order data (the whole batch is one large window) and gives high determinism, at high latency (nightly batch: results only after the 24-hour period plus processing). For unbounded streams you must weigh latency versus determinism, a business as well as technical question: "Does my microservice handle out-of-order and late-arriving events according to business requirements?" Bank example: a deposit then an immediate withdrawal must be ordered correctly
    • the app may keep state for a business-defined grace window such as one hour.
  • Tip: events from a single partition should always be processed by offset order regardless of timestamp (which can lead to out-of-order events).
  • Lateness is relative to the consumer: one service treats any out-of-order event as late, another waits hours.
    • Watermarks: t' is late when it arrives after watermark W(t); the node decides how to handle it.
    • Stream time: t' is late when stream time has moved past t'; each operator in the subtopology decides.
    • Tip: an event is late only when it has missed a deadline specific to the consumer.

Causes and impacts

  • Out-of-order sources (a stream already out of order, or an external system with out-of-order timestamps).
  • Multiple producers to multiple partitions,
    • such as repartitioning (Figure 9-8: two instances repartition two partitions by user ID, for session analysis; Harry interacted with products ID12 and ID77)
    • Each instance has its own stream time with no synchronisation, so time skew (Figure 9-9: events at t = 90 and t = 95 end up out of order although instance 0 was only slightly ahead)
      • worse with unbalanced partition sizes, unequal rates and big backlogs
    • You cannot depend on consistently increasing time in each stream
    • Tip: a single-threaded producer will not create out-of-order events in normal operation unless its source is out of order
    • A jump in stream time can make many events late after reordering.

Time-sensitive functions and windowing

  • Late events matter for time-based business logic (aggregations over a period, timers)
    • A late event arrives after logic for that period has finished
    • Windowing groups events by time (usually per key)
    • Tip: windows can use event time or processing time; event-time windows typically have more business applications.
    • Tumbling window (Figure 9-10): fixed size, non-overlapping; "when is the peak hour for product usage?"
    • Sliding window (Figure 9-11): fixed size with an incremental step (window slide), reflecting only events currently in it; "how many users clicked on my product in the past hour?"
    • Session window (Figure 9-12): dynamic size, ends on an inactivity timeout, then a new session; "what does a user look at in a browsing session?"
  • Each must deal with out-of-order events:
    • decide how long to wait
    • You can never be sure you have received all events; waiting works but you eventually give up
    • Consider state size, likelihood of late events and business impact of ignoring them.

Handling late events

  • Decide the strategy at business level first:
    • financial transactions and system failures may need handling wherever they appear
    • measurement events (temperature, force) may be discarded. Waiting raises determinism but also latency, which hurts time-sensitive applications and tight SLAs
    • microservices let you tailor it per service.
  • When a window sees an event past its cut-off it starts a new window and emits the old. For an event that belonged in the old window:
    • Discard it (the window is closed).
    • Keep the window open and delay output for a fixed time (more complete, higher latency).
    • Grace period: emit as soon as complete but keep the window available for a set grace period; merge late events and write the updated output to the stream.
    • Route to a separate stream: log it and send it to a dedicated stream, with some reconciliation or compensation or it sits unresolved ("The Compensation Workflow Pattern").
  • There is no technical rule
    • if requirements do not specify, the business must resolve it. Guiding questions: How likely are late events? How long must you guard against them? Business impact of dropping them? Business benefit of waiting? Disk or memory for state? Do waiting costs outweigh benefits?

9.6 Reprocessing versus processing in near real time

  • Immutable streams let consumers rewind offsets and replay:
    • reprocessing, which every designer must consider
    • Typically only for services using event time, not wall-clock aggregation and windowing
    • A new service effectively reprocesses some, all or none of history: point offsets to the start and let it process, materialise state, compute and write output.
  • Event scheduling is important for reprocessing correctly (same order as near real time), as is handling out-of-order events, because repartitioning through the broker (rather than inside Spark, Flink or Beam) can cause reordering.
  • Steps:
    1. Determine the starting point: best practice is the very beginning for stateful consumers, especially entity streams (a service interested in only the last 30 days may reprocess just that).
    2. Determine which consumer offsets to reset: stateful streams to the very beginning (a bank balance without earlier paychecks is wrong).
    3. Consider the volume of data: how long and what bottlenecks; quotas (Chapter 19) so the broker is not overwhelmed.
    4. Consider the time to reprocess: possibly many hours; tell downstream consumers about stale data; scale to maximum parallelism, then back down.
    5. Consider the impact: do not, for example, re-email users that their packages shipped.

9.7 Intermittent failures and late events

  • An event can be late during near-real-time processing (watermark or stream time advanced) but in place in the stream when reprocessed, which is hard to detect and shows how upstream problems affect downstream consumers.
  • Producer or broker connectivity issues
    • (Figures 9-13 to 9-15): records are created in timestamp order but cannot be published; the producer retries and either succeeds later or gives up (ideally a noisy failure)
    • The consumer reads stream A and advances its watermark or stream time, but stream B shows nothing, so it concludes no new data exists and does not know about the outage
    • When the producer reconnects, events are published in correct event-time order, but the near-real-time consumer has already marked them late
    • This can go unnoticed even in retrospect.
  • Mitigations: wait a predetermined time before processing (adds latency and only helps if delays are shorter than the wait) or use robust late-event handling in the business logic.

Summary and further reading

  • Full determinism can never be completely achieved with unbounded streams and intermittent failures; reasonable best-effort solutions give the best latency and correctness trade-off.
  • Further reading: Tyler Akidau's "Streaming 101: The World Beyond Batch" and "Streaming 102"; Mikito Takada, Distributed Systems for Fun and Profit (online).
