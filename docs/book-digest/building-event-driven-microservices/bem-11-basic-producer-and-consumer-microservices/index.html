Building Event-Driven Microservices 11: Basic Producer and Consumer Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 11. Previous: Building Event-Driven Microservices 10: Building Workflows with Microservices. Next: Building Event-Driven Microservices 12: Heavyweight Framework Microservices.

Takeaways
  • A basic producer and consumer (BPC) microservice uses plain consumer and producer clients only: no event scheduling, watermarks, built-in materialisation, changelogs, or scaling beyond consumer group balancing.
  • It fits stateless transformations and stateful logic that does not depend on event order, usually with an external state store.
  • Good uses: the sidecar pattern for legacy systems, gating (all inputs must arrive, in any order), work done by the data store, and independent scaling of processing and storage.
  • Weakness: no joins between streams, materialisation or timestamp-based decisions; those need the frameworks of Chapters 12 and 13.

11.1 What is a BPC?

  • BPC microservices ingest events from one or more streams, apply transformations or business logic, and emit events to output streams. Synchronous request-response I/O may also be involved (Chapter 17)
    • this chapter is strictly about event-driven components.
  • They use basic clients providing only consuming and producing
    • They lack event scheduling, watermarks, built-in materialisation, changelogs and horizontal scaling beyond consumer group balancing
    • You can build your own libraries for these, but that is out of scope, so check whether BPC meets your requirements.
  • Strengths:
    • clients exist in most languages (low cognitive overhead)
    • the whole bounded-context workflow lives in one application, keeping responsibilities local and easy to understand
    • it can be wrapped in one or more containers and run by your container management solution.

11.2 Where BPCs work well

  • Despite lacking stream-processing components, BPCs fulfil many requirements: stateless transformations are easy, and so are stateful patterns where deterministic event scheduling is not required.
  • External state stores
    • are more common than internal ones: scaling local state across instances and recovering from instance failure is hard without a full framework
    • External stores give all instances uniform access, plus backup and recovery.

Integration with existing systems: the sidecar pattern

  • A basic producer and consumer client is an optimal way to integrate event-driven services into legacy codebases
    • A legacy system can write its own events with at-least-once semantics and consume events to insert into its database or run reactive code.
  • When it is not safe to modify the legacy codebase, the sidecar pattern adds event-driven functionality without affecting the source codebase.
  • Example:
    • an ecommerce frontend displays inventory and product data, previously synchronised from a read-only subordinate data store by a scheduled batch job (Figure 11-1)
    • In the event-driven world there are two streams, Product Info and Product Inventory, each a mirror of its source table; the frontend needs both
    • A sidecar service sinks both streams into the data store, using a BPC to consume and upsert (Figure 11-2)
    • The frontend gains a near-real-time feed of product updates with no code change.
  • The sidecar lives in its own container but is part of the single deployable of the frontend: for example a Kubernetes sidecar, or even in the same container as the application
    • It adds new functionality to a system without significant legacy changes, most often to bring event-driven processing to applications otherwise left out.
  • Drawbacks:
    • more complexity and coordination
    • testing is harder because the stream-processing component is part of the test scope
    • the bounded context spans the microservice and the stream component, so you must deploy and roll back the components together.

Stateful business logic that does not depend on event order

  • Many processes do not care about order but need all necessary events to eventually arrive: the gating pattern
    • Example: a book publisher needs three things before a book goes to the printer, in any order:
    • Contents: the contents are written.
    • Cover art: the cover art is created.
    • Pricing: prices are set for regions and formats.
  • Each stream drives logic:
    • a new event is materialised into its table, then every other table is looked up to see whether the other events are present (Figure 11-3). The book ending in ISBN 0010 has already been published to the output book stream
    • the one ending 0011 is waiting for cover art and has not been published.
  • Tip: the gating pattern may also need explicit human approval ("Example: Newspaper Publishing Workflow (Approval Pattern)").

When the data store does much of the work

  • A BPC suits cases where the underlying data store performs most of the business logic: a geospatial store, a document store, machine learning, AI and neural network applications.
  • Examples:
    • an ecommerce company ingests products scraped from websites and classifies them with a BPC using a batch-trained machine learning categoriser in the backend (complex logic offline in batch, classification real time via per-event lookups)
    • or user behaviour events correlated with a geospatial store to find the nearest retailers for advertisements.
  • The producer and consumer only provide the means to consume, process and emit.

Independent scaling of processing and data store

  • Processing and storage needs are not linearly related. Example load pattern: the sleep/wake cycle of a local population: intensive by day, very low at night.
  • Example:
    • aggregate user behaviour events into 24-hour sessions to find each user's recently popular products and drive related advertisements
    • on completing a session the service emits the result and flushes the data store. Table 11-1: a key-value store with a composite primary key userId, timestamp and a List(productId) value.
  • Processing needs follow the cycle, so the service scales down at night to save money: the partition assignor reassigns input partitions to a single instance
    • But the domain of potential users remains constant (anyone may be logged in), so the service needs access to every user aggregation: scaling down processing does not reduce the state's upper size boundary.
  • By day, more instances come online; the data store's query rate rises too, but caching, partitioning and batching keep load lighter than the linear increase in processing.
  • Tip: cloud providers typically offer high-performance key-value storage with independent read and write scaling and costs proportional to access patterns.

Summary points

  • BPC is simple yet powerful and the foundation of many stateless and stateful event-driven patterns.
  • It is flexible: pairs with data stores that do most of the work, serves as an interface layer between streams and legacy systems, and can use external stream-processing systems to augment it.
  • Major shortcoming:
    • no advanced handling of relationships between streams (joins require loading everything into a database), and no out-of-the-box state materialisation, event scheduling or timestamp-based decisions
    • The next two chapters cover heavyweight and lightweight frameworks, which provide all of these.
Terms to carry forward
  • BPC; sidecar pattern; gating pattern.
  • Composite primary key state; independent scaling of compute and store.
