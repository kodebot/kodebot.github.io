Building Event-Driven Microservices 12: Heavyweight Framework Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 12. Previous: Building Event-Driven Microservices 11: Basic Producer and Consumer Microservices. Next: Building Event-Driven Microservices 13: Lightweight Framework Microservices.

Takeaways
  • Heavyweight frameworks (Apache Spark, Flink, the Beam model) are full-featured stream processors that need their own cluster, use their own mechanisms for failures, scheduling, storage and coordination, and shuffle data automatically.
  • They descend from batch processing (Hadoop, MapReduce) and suit analytical use cases: ETL, windows and sessions, anomaly detection, aggregation. They can also run batch jobs.
  • Weaknesses for microservices: a dedicated cluster to run, Java and Python mostly, and uneven support for materialising tables and joins.
  • Run them hosted, on your own cluster, or on Kubernetes per application. State lives in internal stores with checkpoints to durable storage.
  • Scale by restart (all) or while running (some); watch multitenancy.

12.1 What makes a framework heavyweight

  • Streaming frameworks give primary-key joins, foreign-key joins, aggregations and time-based operations, and handle data sets far beyond a single instance
    • Basic producer/consumer and FaaS lack these
    • This chapter and the next are overviews, not comparisons; examples come from Spark, Flink and the Beam model.
  • Warning: the first edition also discussed Apache Storm and Apache Heron; removed since use has greatly dwindled.
  • Three defining characteristics:
    1. An independent cluster of processing resources: shareable worker nodes plus resource managers that schedule and coordinate.
    2. Its own internal mechanisms for failures, recovery, resource allocation, task distribution, data storage, communication and coordination (unlike lightweight frameworks, FaaS and BPCs, which rely on the container management system (CMS) and the event broker).
    3. An automated mechanism for shuffling data between instances, critical for joins and aggregations at scale (all data of a key ends up in the right instance).
  • Managing these clusters independently of the broker and CMS is no small task, hence "heavyweight". A fourth property: they can process data in batch jobs, reflecting their origins.

A brief history

  • Apache Hadoop
    • (released 2006) bundled massive parallel processing, failure recovery, data durability and internode communication, so users could use commodity hardware to solve problems needing thousands of nodes
    • MapReduce was among the first widely available ways to process very large batches ("big data"), since overtaken by more performant options
    • Data sizes grew from hundreds or thousands of gigabytes to terabytes and petabytes, driving demand for faster processing and near-real-time streams.
  • Spark
    • started as a high-performance MapReduce replacement, largely batch only, with stream processing added later
    • Flink could process streams from the start. Many organisations begin with event-driven processing when data science and analytics teams convert batch jobs into streaming pipelines.

12.2 Example: session windowing of clicks and views

  • An online advertising company buys ad space and resells it
    • customers want click-through rate as return on investment. Engagement is billed per session: continuous activity with no break longer than 30 minutes.
  • Two streams: Click (userId, productId, createdEventTime) and AdView (userId, adId, productId, createdEventTime), both Protobuf (Examples 12-1, 12-2):
// Example 12-1: the Click schema in Protobuf
message Click {
    int32 userId = 1;
    string productId = 2;
    Timestamp createdEventTime = 3;
}

// Example 12-2: the AdView schema in Protobuf
message AdView {
    int32 userId = 1;
    string adId = 2;
    string productId = 3;
    Timestamp createdEventTime = 4;
}
  • Goal:
    • aggregate into session windows and emit once event time (not wall-clock) of 30 minutes passes without a new event (see Chapter 9). Operations: group by userId (data locality)
    • window with a 30-minute timeout
    • within each session compute the AdView events that have a corresponding Click, mark them AdEngagement and emit the list. An AdView is generated only when an ad is shown
    • a Click only when the user clicks (possibly without seeing an ad).
  • Example 12-3, Flink (abbreviated, as printed):
// Example 12-3: snippet of Flink code showing the stream-processing operations
// Create streams of click and view events (super type is UserEvent)
DataStream<Either<ClickEvent, AdViewEvent>> eitherClicks = ...
DataStream<Either<ClickEvent, AdViewEvent>> eitherViews = ...

eitherClicks
    .union(eitherViews)
    .keyBy(t -> {
        if (t.isRight())
            return t.right().getProductId();
        else
            return t.left().getProductId();
    })
    .window(EventTimeSessionWindows.withGap(Duration.ofMinutes(30)))
    .process(new ProcessClickViewWindowFunction())
    .addSink(new KafkaTopicSink(...));
  • Example 12-4's ProcessClickViewWindowFunction iterates the windowed grouping and pairs views with clicks by ad, emitting a List<String> of engaged adIds
    • its output is userId to List<String> adEngagements (Table 12-1). (The code, as in the book, ignores event time and assumes the view precedes the click.)
// Example 12-4: the innards of ProcessClickViewWindowFunction that matches ad views with clicks
public class ProcessClickViewWindowFunction extends
    ProcessWindowFunction<
        Either<ClickEvent, AdViewEvent>,
        List<String>,
        Long,
        TimeWindow> {

    @Override
    public void process(Long key,
                        Context context,
                        Iterable<Either<ClickEvent, AdViewEvent>> input,
                        Collector<List<String>> out) {

        // Create an empty list where we store the adIds for engagements
        List<String> adEngagements = new ArrayList<>();

        // Map<ProductId, Tuple2<AdId, wasClicked>>
        Map<Long, Tuple2<String, Boolean>> map = new HashMap<>();

        // First, get all the Advertisements that have both a click and a view.
        // This example ignores event time, but assumes that the view must come
        // before the click.
        for (Either<ClickEvent, AdViewEvent> event : input) {

            // Reminder that (key = productId)
            Tuple2<String, Boolean> adEngage =
                map.getOrDefault(key, new Tuple2<>("", false));

            if (event.isLeft()) {
                // If it is a click event then set wasClicked=true.
                // Keep the same value for f0.
                map.put(key, new Tuple2<>(adEngage.f0, true));
            } else {
                // If it is a view event populate with the adId
                AdViewEvent adv = event.right();
                String adId = adv.getAdId();
                Boolean wasClicked = adEngage.f1;
                // Set the AdId and the original value of wasClicked
                map.put(key, new Tuple2<>(adId, wasClicked));
            }
        }

        for (Map.Entry<Long, Tuple2<String, Boolean>> clickViews : map.entrySet()) {
            if (clickViews.getValue().f0.length() > 0 && clickViews.getValue().f1) {
                adEngagements.add(clickViews.getValue().f0);
            }
        }
        // key=(String) -> the userId
        // value=(List<String>) -> a List of adIds with both a view and a click
        out.collect(adEngagements);
    }
}
  • The listings are reproduced as printed (including keyBy on the product ID in one place and the user ID in a comment)
    • the book adds braces to the original if and else here for formatting only.
  • Stages
    • (Figure 12-1, two instances): Stage 1: executors get tasks and input partitions
    • the click and view streams are unioned into one logical stream and prepared with keyBy
      • Stage 2: keyBy with downstream window and process needs a shuffle so all events of a key are consumed by one instance
      • Stage 3: session windows yield a list of adIds with both a view and a click per user
    • each pair is written to the AdEngagements output stream.
  • Tip: frameworks offer many more window controls, such as retaining closed sessions so late events can be applied and an update emitted.
  • Scaling to one instance
    • (Figure 12-2): without dynamic scaling, halt the processor and restore from a checkpoint with the new parallelism
    • keyed state is read back and operator state restored to assigned partitions
    • instance 0 then consumes every partition and still groups and shuffles (to itself) through stage 3.
  • These frameworks treat streams and events as building-block primitives for declaratively grouping, aggregating, joining, processing and storing.

12.3 Inner workings

  • Spark and Flink operate similarly at a coarse level (development, deployment, scaling, storage, failure handling)
    • Google's Dataflow (running Beam applications) probably too, though it is closed. Consult your framework's documentation for nuances.
  • A cluster has two roles:
    • The resource manager prioritises, assigns and manages workers and tasks, with backup nodes to fail over to.
    • The worker (executor) node runs the business logic of its tasks using CPU, memory and disk.
  • Tasks
    • are generated from the application's topology, connect directly to the broker and consume and produce streams (Figure 12-3). A job is an application written with the framework's SDK (the word is a batch leftover)
    • a streaming job runs indefinitely like any microservice.
  • Apache ZooKeeper
    • provides distributed coordination to decide which resource manager is in charge
    • on failure it helps elect a new leader
      • Frameworks are built to survive failure of a worker, resource manager or ZooKeeper node
      • Note: ZooKeeper has historically been a major component
    • newer frameworks may not use it, but distributed coordination remains essential.
  • On submission, the application is split into tasks assigned to workers (Figure 12-4)
    • a task manager monitors tasks, restarting and rebalancing as needed, set up for high availability (otherwise all jobs fail and an expensive restart follows). Parallelism is configurable: tasks map 1:1 to partitions in the figure, but one task can consume all partitions or many tasks one partition (as with a queue).

12.4 Benefits and limitations

  • Roots in analytics:
    • quicker decisions from large volumes of events in near real time. Common patterns: ETL
    • session and window analysis
    • detecting abnormal behaviour
    • aggregating and keeping state
    • stateless streaming operations. They are powerful and mature, with extensive documentation, books and samples.
  • Limitations (not prohibitive):
    1. Not designed for microservice-style deployment: a dedicated cluster beyond the broker and CMS adds complexity at scale (some mitigations later in the chapter).
    2. Java and Python only historically; a common workaround is to let the heavyweight framework perform transformations as its own standalone application, and serve business functionality from the transformed state store in another application (or use streaming SQL, Chapter 14).
    3. Materialising an entity stream into an indefinitely retained table is not supported out of the box by all: that blocks table-table and stream-table joins and long-running aggregations.
  • Acid test:
    • a framework's ability to serve joins (as streams or materialised tables), hard to implement and a substantial barrier
    • Many focus on time-based aggregation with limited windows
      • the leading ones offer a global window for indefinite materialisation, from which you can build custom joins (less documented than they should be)
    • Tip: if a framework does not handle joins, it likely has not addressed some harder problems.
  • Though born for analytics, they can power operational event-driven microservices; the next choice is build or buy.

12.5 Cluster setup options and execution modes

  • Hosted service:
    • the simplest: pay someone to run it
      • Highest sticker price compared with free open source, but a total cost that includes hardware, development, maintenance, upgrades, debugging, monitoring, scaling and opportunity cost
      • Examples: Confluent (co-creators of Kafka) fully managed, serverless Flink SQL with Kafka
    • Amazon managed Flink and Spark
    • Google, Databricks and Microsoft offerings of Spark
    • Google Dataflow (a Beam runner). Warning: not all are equal
    • some are fully serverless, others need hands-on maintenance
    • the trend is serverless with the cluster invisible, which may not suit your security, performance or isolation needs.
  • Build and run your own:
    • historically dedicated commodity-hardware clusters. Warning: "How hard could it be?" is common
    • a proof of concept is easy but hardening to a reliable production service is very challenging and expensive. Large, well-staffed companies may afford it
    • smaller ones may choose managed services and optimise costs after product-market fit.
  • Alongside the CMS:
    • Mode one:
      • deploy the cluster on CMS-provisioned resources
      • Resource managers, workers and ZooKeeper run in containers or VMs, monitored and restarted like any other
      • Tip: statically assign resource managers and other high-availability services so the CMS does not shuffle them (avoids excess alerts).
    • Mode two:
      • use the CMS to specify resources per application, increasingly popular with containers
        • Spark and Flink can use Kubernetes (Flink: each application in its own isolated session cluster; Spark: Kubernetes as resource manager with isolated workers) (Figure 12-5)
        • Tip: nearly identical to deploying non-heavyweight microservices
        • Advantages: uses the CMS resource model including scaling
      • complete isolation between jobs
      • different frameworks and versions
      • same deployment process as microservices. Disadvantages: not supported by all frameworks or CMSs
      • features of full cluster mode such as automatic scaling may be missing.

Application submission modes

  • Driver mode
    • (Spark, Flink): a single local standalone driver coordinates execution while the application runs in the cluster
    • it reports errors, logs, etc. Terminating the driver terminates the application, a simple way to deploy and stop
    • deploy the driver as a microservice via the CMS.
  • Cluster mode:
    • the whole application is submitted to the cluster, which returns a unique ID used to command it via the cluster API
    • deploy and halt commands go directly to the cluster, which may not suit a microservice deployment pipeline.

12.6 State and checkpoints

  • Stateful operations may use internal or external state (Chapter 8), but most heavyweight frameworks favour internal state for performance and scalability: records in memory, spilled to disk for durability and when state exceeds memory. Risks: disk or node failure, temporary outages from aggressive CMS scaling
    • the performance usually outweighs them with planning.
  • A checkpoint is a snapshot of internal state, persisted to durable storage external to the workers, used to rebuild state after scaling or failures
    • Historically HDFS; now Amazon S3, Google Cloud Storage, Azure Blob Storage
    • A failed instance restores from the latest checkpoint and resets its consumer offsets to resume.
  • Two states (Figure 12-6):
    • Operator state: pairs of <partitionId, offset>; each partitionId is unique among all input topics.
    • Key state: pairs of <key, state> (aggregations, reductions, windowing, joins and other stateful operations).
  • The mechanism synchronously records both so they match:
    • otherwise events may be skipped or processed twice
    • Tip: functionally equivalent to restoring external stores from snapshots (Chapter 8)
    • State must be completely loaded from the checkpoint before new data, and the framework verifies operator state matches keyed state per task for correct partition assignment
    • Each framework implements this differently.

12.7 Scaling and autoscaling

  • Maximum parallelism is typically limited by input partition counts, since data is read in order
    • Cyclical patterns (Figure 12-7: heavy by day, light at night) benefit from scaling up and down: enough capacity without overprovisioning, minimal latency (though many apps tolerate temporarily higher latency)
    • Warning: scaling an application is separate from scaling a cluster; assume the cluster has resources.
  • Stateless apps scale easily (join or leave the consumer group, rebalance). Stateful apps must load state matching the partition assignment.

Scaling by restarting

  • Pause, checkpoint, stop, restart with the new parallelism, reload from checkpoints and resume
    • Supported by all heavyweight frameworks (batch roots)
    • Why? State redistribution takes time, and data shuffling: scaling down a node mid-shuffle can lose data, and adding a node without changing the shuffler's destination at the right moment can lose or duplicate data
    • Figure 12-8:
      • if an instance terminates abruptly, the reduce nodes no longer know where to source their shuffled events, causing a fatal exception
      • so pause, let shuffles finish, and checkpoint.
  • Safe and simple; consider the downtime, which relates to checkpoint size. It is also a good way to validate disaster recovery (equivalent to recovering from the last good state).

Scaling while running

  • Removing, adding or reassigning instances without stopping:
    • only in some frameworks (careful state and shuffled-event handling)
    • still redistributes partitions and reloads state from the last checkpoint.
  • Spark's dynamic resource allocation
    • needs coarse-grained mode and an external shuffle service (ESS) as an isolation layer: the ESS receives shuffled events from upstream tasks and stores them for downstream tasks (Figure 12-9), so tasks scale down on demand (Figure 12-10: instance 0 takes both partitions while the downstream continues via the ESS)
    • Spark also offers shuffle tracking (keep executors that generated shuffle files alive while downstream jobs use them) and shuffle block decommissioning (the block manager migrates shuffled blocks on graceful shutdown)
    • Flink's adaptive scheduler relies on declarative resource management to abstract resources from the job.
  • Active autoscaling for live applications is still an area of active development for both.

Autoscaling

  • Automatic scaling on metrics (processing latency, consumer lag, memory, CPU). Built into some (Google Dataflow, Spark Streaming's dynamic allocation)
    • otherwise collect your own and wire them to the framework's scaling, such as the lag monitor tooling (Chapter 19).

12.8 Recovering from failures, multitenancy, languages, choosing

  • Failures:
    • worker node failure moves its tasks to another worker with state reloaded from the latest checkpoint plus partition assignments
    • resource-manager failure should be transparent to running applications (you may be unable to deploy new jobs during an outage)
    • high-availability mode backed by ZooKeeper or similar mitigates it. Tip: monitor and alert on resource managers and workers
    • a single failure may not halt processing but can degrade it and prevent recovery from successive failures.
  • Multitenancy:
    • consider priority of resource acquisition, ratio of spare to committed resources and the rate at which applications claim resources
    • A new application replaying from the start may take most free resources and starve running ones, breaking SLOs
    • Mitigations:
    • Run multiple smaller clusters (per team or business unit; best when requisitioned programmatically; higher cost from coordinating nodes and monitoring).
    • Namespacing (a cluster divided into namespaces with resource allocations; apps cannot starve others; downside: spare resources must be allocated to each namespace, leaving a larger fragmented pool of unused resources).
  • Languages and syntax:
    • rooted in the JVM (Java most common, then Scala)
    • Python well represented (data scientists and ML specialists)
    • MapReduce-style APIs (chained immutable operations on data sets)
    • fairly restrictive.
  • Choosing a framework:
    • decide how much operational overhead (monitoring, scaling, troubleshooting, debugging, cost assignment) your organisation will authorise
    • hosted options are fewer than for CMS or brokers
    • popularity: Apache Flink is a leader with significant growth since the first edition
    • Spark structured streaming is popular
    • Apache Beam is popular mainly as a way to run on Google Dataflow, without the growth of Spark and Flink. Warning: a heavyweight framework may not suit your microservice
    • verify first.

Summary points

  • Heavyweight frameworks are highly scalable and support many analytical patterns, but may not meet the requirements of some stateful event-driven microservice patterns.
  • They use centralised resource clusters with extra operational overhead, monitoring and coordination
    • recent integration with container managers such as Kubernetes allows more granular, microservice-like deployment.
Terms to carry forward
  • Heavyweight framework; resource manager, worker (executor), task, job; ZooKeeper.
  • Driver mode, cluster mode; checkpoint, operator state, key state.
  • External shuffle service (ESS); scale by restart; autoscaling; multitenancy.
