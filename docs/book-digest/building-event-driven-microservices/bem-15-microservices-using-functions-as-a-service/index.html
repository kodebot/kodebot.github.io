Building Event-Driven Microservices 15: Microservices Using Functions as a Service

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 15. Previous: Building Event-Driven Microservices 14: Streaming SQL. Next: Building Event-Driven Microservices 16: Eventual Consistency.

Takeaways
  • Functions as a service (FaaS) is a serverless way to build microservices: a function runs when a trigger fires, then terminates; the framework supplies scaling, state, monitoring and compute.
  • Best for simple to moderately complex, stateless, variable-load work that does not need event scheduling; think of a basic producer/consumer that stops after a set time.
  • Triggers: event-stream listener, consumer group lag, schedule, webhook, resource events. Mind cold starts, termination and rebalancing thrash.
  • State is external (or durable functions). Functions calling functions: event-driven, asynchronous direct (out of order risk) or synchronous orchestration (order kept).
  • Make functions idempotent; for stronger guarantees use durable function orchestration (AWS Step Functions, Google Cloud Workflows, Azure Durable Functions).

15.1 What FaaS is and why use it

  • A function is code executed when a triggering condition occurs: it starts, runs to completion and terminates. Scaling, state and monitoring are typically provided by the FaaS framework, which also requisitions and releases compute
    • executions scale up and down to track highly variable loads.
  • Think of FaaS as a basic consumer/producer that regularly and predictably stops after a set time: like a microservice that crashes every few minutes but stores its data externally and picks up where it left off.
  • It removes the overhead of creating and managing a microservice (given an existing FaaS framework): write the function, specify when it triggers, deploy. Use cases:
    • Simple reactions to events: load data into a database; trigger a customer email.
    • Sequential workflow steps: receive an image, generate an AI assessment, pick a subset to validate with a human; each step is its own function.
    • Processing large amounts of data in parallel: ingest a large product listing file from FTP and split it into events for a stream.
    • Simple transformations and validations: mask fields for PII compliance, validate structure.
    • Routing data by content to services, brokers or data stores.
  • Fits:
    • simple topologies, stateless work, no need for deterministic processing of multiple streams, very wide scaling (queue-based processing), highly variable volume
    • Many functions can together make up a bounded context
    • Where determinism matters, take great care: like basic consumers (Chapter 11), FaaS needs an event scheduler for consistent results (as the frameworks have).

15.2 Building microservices with functions

  • Four components: the function, input event stream, triggering logic, error and scaling policies with metadata. A function in any supported language:
public int myFunction(Event[] events, Context context) {
    println("hello world!");
    return 0;
}
  • events is the array to process, each with a key, value, timestamp, offset and partition_id; context has the function's name, stream ID and remaining lifespan.
  • The function-trigger map (usually hidden by the framework) wires streams to functions: myFunction on myInputStream with onNewEvent
    • otherFunction on anotherStream
    • yetAnotherFunction on fooStream,barStream (a function may consume several)
      • The "Policies and metadata" column covers consumer group, consumer properties (batch size and batch window), retry and error handling and scaling policies.
  • The event-stream listener pattern:
    • a new event starts the function, passes a batch, and it terminates on completion
    • Tip: every function-based microservice needs its own independent consumer group
    • Requirements and triggering vary by provider.

Cold and warm starts, termination and shutdown

  • Cold start:
    • first start, or after enough inactivity; load code, start, connect to the broker and other resources
    • Warm once ready
    • Warm start: resumed from hibernation with connections already established, processing the next events immediately
    • Frameworks reuse terminated functions where possible: a function on a steady stream may hit its timeout, be briefly terminated and revived by the trigger, resuming immediately if connections have not expired.
  • A function terminates when done or at the end of its lifespan, generally 5 to 10 minutes
    • it is suspended into hibernation (may be revived immediately, or evicted from the cache)
      • Decide how to handle open connections and partition assignments: terminating without revoking them may delay processing until a timeout or rebalance
      • A function almost always online need not close connections and rebalance
    • an intermittent function should close all connections and relinquish partitions
      • When in doubt clean up: lighter load on stores and broker, fewer suspended functions claiming partitions.

Choosing a FaaS provider

  • Open source or paid cloud providers
    • an organisation with an in-house CMS can benefit from in-house FaaS
      • AWS, GCP and Azure have proprietary FaaS with deep integration with their other services, and legal hurdles already cleared: major factors in their dominance versus slower open source growth
      • The first edition (2020) named OpenWhisk, OpenFaaS and Kubeless: the first two persist but have not supplanted the cloud offerings
    • Kubeless is no longer maintained (archive).
  • Change since 2020:
    • cloud FaaS is now more deeply integrated with open source brokers like Apache Kafka
      • previously Google Functions required Google PubSub triggers, AWS required Kinesis, Azure required Event Hubs
    • That lifts maximum time-based retention limits of those brokers: AWS Kinesis 365 days, Azure Event Hubs 7 to 90 days, Google PubSub 31 days
    • And you no longer need a connector framework to trigger from a third-party broker: lower overhead and latency, fewer moving parts, lower cost.

15.3 Starting functions with triggers

  • Triggers tell a function to start; they vary by framework but fall into categories.
  • Event-stream listener
    • (Figure 15-1): fires when an event is produced
    • the integrated consumer hides consumption, injecting an array of events from a stream or a cluster of unordered events from a queue
      • Google, Microsoft and Amazon provide it for their brokers
    • others (Kafka, Pulsar, Warpstream, NATS) may or may not be supported
    • Kafka Connect can trigger functions otherwise (Figure 15-2, an external listener). Functions may output events, including logging and error data to their own stream.
    • Synchronous
      • triggers wait for completion before issuing the next events (keeps order, limited by partition count)
      • asynchronous triggers issue events to many functions at once (no order; use only when order does not matter).
    • Batch size (maximum events dispatched) and batch window (maximum wait for more events) spread the start-up overhead over the batch to reduce cost.
public int myEventFunction(Event[] events, Context context) {
    for (Event event : events) {
        try {
            println(event.key + ", " + event.value);
        } catch (Exception e) {
            println("error printing " + event.toString());
        }
    }
    // Indicates to the FaaS framework that batch processing was completed
    context.success();
    return 0;
}
  • Tip: like containerised microservices, listener triggers can start from the latest, earliest or any offsets.
  • Consumer group lag:
    • poll an application's group offsets and compute the delta between the current offset and the stream's head (see "Consumer Offset Lag Monitoring")
    • also usable to scale non-FaaS microservices. A monitoring framework calls the FaaS framework to start functions
    • high lag lets the autoscaler start more instances, low lag keeps the count steady or reduces it, tailored per microservice for SLAs
      • Unlike the listener, the trigger only signals events exist: the function creates its client, consumes and commits offsets itself, like a basic producer/consumer with limited lifespan
      • A frequently triggered function may still be warm
    • for long inactivity rebalancing and cold starts reduce the work per lifespan.
public int myLagConsumerFunction(Context context) {
    String consumerGroup = context.consumerGroup;
    String streamName = context.streamName;

    // Establish a connection to the broker
    EventBrokerClient client = new EventBrokerClient(consumerGroup, ...);

    // Poll for a batch of events to process
    Event[] events = client.consumeBatch(streamName, ...);

    for (Event event : events) {
        // Process each event one at a time
        doWork(event);
    }
    // Commit the offsets of the processed events back to the event broker
    client.commitOffsets();

    // Indicates to the FaaS framework that the function succeeded
    context.success();

    // Return, letting the lag-triggering system know processing was a success
    return 0;
}
  • Schedule:
    • start periodically or at set times, poll the source streams and process
    • not particularly common for asynchronous event-driven architectures
    • the client code looks identical to the lag trigger example.
  • Webhooks: direct invocation for custom integration with monitoring frameworks, schedulers and third parties.
  • Resource events: changes to resources (create, update or delete a file; modify a row); not used often, but handy for external sources that drop files via FTP.

Scaling

  • FaaS parallelises exceptionally for queues and streams where order does not matter
    • if order matters, parallelism is limited by partition count. Scaling policies are mostly the framework's (consumer input lag, time of day, throughput, performance characteristics).
  • For functions that manage their own broker connections, partition rebalancing on joining and leaving matters: frequent churn can leave a group in near-constant rebalancing, even a rebalancing deadlock, with many short-lived functions with small batches and aggressive scaling
    • Use a step-based scaling policy or a hysteresis loop
    • Caution: avoid thrashing triggers and scaling policy (frequent rebalancing is expensive and lowers throughput).

Maintaining state

  • Because of short lifespans, most stateful FaaS solutions need an external stateful service: providers want quick, scalable processing units independent of data location, so local state from earlier executions would limit them to the nodes that hold it, and they enforce a "no local state" policy
    • Previous local state may exist after a warm start but is not guaranteed
    • Functions connect to external stores like any client and persist and retrieve state explicitly.
  • Tip: use strict access controls so nothing outside the function's bounded context can reach its state stores.
  • Some frameworks have durable stateful functions (Microsoft Azure Durable Functions): local memory is persisted automatically and functions suspended and revived without explicit storage code
    • this simplifies stateful workflows and standardises state management. Watch for improvements.

15.4 Functions calling other functions

  • Functions are often used to execute other functions and for choreography and orchestration, communicating asynchronously through events, request-response calls, or both.
  • Asynchronous event-driven communication
    • (Figure 15-3): one function writes to a stream
    • downstream functions trigger on it
      • A bounded context may consist of many functions and internal streams, each with its own triggering and scaling logic
      • Function A triggers on stream 1 and writes to stream 2 or 3 (internal streams)
    • A, B and C can share a consumer group to tie them into one logical microservice. Each function manages its own offsets and commits after finishing
    • no outside coordination. Choreography is shown
    • orchestration is possible at more complexity. Function failures lose no data: the broker stores events and the next instance reprocesses them.
  • Direct-call pattern: a function calls others from its code like request-response; asynchronous (fire and forget) or synchronous (await the return value).
    • Choreography with asynchronous calls
      • (Figure 15-4): A invokes B per batch and then updates offsets and terminates
      • Downsides:
        • offsets commit only on A's success (B has no feedback to A), so B's errors can lose events (which may not matter for some workflows)
        • and out-of-order processing, since several B instances run independently and later executions finish before earlier ones (a race)
      • Invoking B with the whole batch after A's loop does not fix ordering either:
public int functionA(Event[] events, Context context) {
    for (Event event : events) {
        // Do function A's processing work
        doLocalWork(event);
        // Asynchronously invoke function B
        asyncFunctionB(event);
        // Does not wait for return value
    }
    context.success();
    return 0;
}

public int functionA(Event[] events, Context context) {
    for (Event event : events) {
        // Do function A's processing per event
        doLocalWork(event);
    }
    // Invoke function B asynchronously with full batch of events
    asyncFunctionB(events);

    context.success();
    return 0;
}
  • In-order processing needs strict execution of A before B for each event, completely, before the next (especially if both act on the same external store, where B may depend on data A wrote)
    • Otherwise consider orchestrated synchronous calls.
  • Orchestration with synchronous calls
    • (Chapter 10): the function awaits results
      • Figure 15-5: an orchestration function takes the batch and, per event, calls A, then B with A's result, composes the output, writes to the output stream
    • each event is fully processed before the next so offset order is respected
    • on success it updates the offsets.
public int orchestrationFunction(Event[] events, Context context) {
    for (Event event : events) {
        // Synchronous function calls
        Result resultFromA = invokeFunctionA(event);
        Result resultFromB = invokeFunctionB(event, resultFromA);
        Output output = composeOutputEvent(resultFromA, resultFromB);
        // Write to the output stream
        producer.produce("Output Stream", output);
    }
    // This will tell the FaaS framework to update the consumer offsets
    context.success();
    return 0;
}

15.5 Handling function failures

  • You can always reprocess the source streams:
    • the worst case is re-running from the last failed iteration
    • Side effects: a retry re-executes logic up to the failure, so make processing idempotent
    • Common failures:
    • Intermittent failures: connectivity (a service, broker, store, third-party SaaS) or a late reply from another function; generally resolve themselves, but verify it is not chronic.
    • Resource failures:
      • a subset of intermittent: claiming more than allowed (downloading and decompressing a large compressed file runs out of memory)
      • restoring the last offset repeats it. Plan resources at design time
      • split into several function calls, or reimplement as a conventional microservice.
    • Event batch too big:
      • if a batch cannot be processed within the lifespan the execution fails and repeats
      • increase the maximum execution time
        • or decrease the maximum batch size
        • Tip: functions that manage their own broker connections can commit offsets periodically during execution (partial completion)
      • not when given the batch. Some listeners (Amazon, Microsoft) can halve the batch on failure and retry until it fits.
    • An orchestration function failure:
      • return values from workers vanish
      • an external state store could track the workflow but you must build it
        • Default: reprocess the failed batch with a new orchestrator: reprocesses everything including successful operations, repeats side effects and calls (third parties may not deduplicate), and may cost a lot
        • Compensation can fail again too
      • for stronger guarantees on orchestrated workflows, compensation, recovery and durability you may need durable function orchestration.

15.6 Durable function orchestrators

  • Durable function orchestration (DFO):
    • serverless computing with strong guarantees on stateful processing under intermittent failures; a subtype of the durable execution architecture (Chapter 10)
    • Growing since the first edition
    • Examples:
      • AWS Step Functions Redrive
      • Google Cloud Workflows
      • Azure Durable Functions: all from the three major cloud platforms and deeply integrated, so possibly unhelpful for a fully open-source or cloud-agnostic strategy.
  • Encoding the orchestrator in a proprietary document:
    • AWS Step Functions and Google Cloud Workflows describe workflows in YAML, JSON or JSONata documents outside the function code (sequence, branching, looping)
    • Example 15-1 is an Amazon States Language definition in JSONata with a choice state (taken from Amazon's State Language homepage), shown here as printed with a placeholder for the function names:
{
    "Comment": "An example of the Amazon States Language using a choice state.",
    "QueryLanguage": "JSONata",
    "StartAt": "FirstState",
    "States": {
        "FirstState": {
            "Type": "Task",
            "Assign": {
                "foo": "{% $states.input.foo_input %}"
            },
            "Resource": "arn:aws:lambda:region:123456789012:function:FUNCTION_NAME",
            "Next": "ChoiceState"
        },
        "ChoiceState": {
            "Type": "Choice",
            "Default": "DefaultState",
            "Choices": [
                {
                    "Next": "FirstMatchState",
                    "Condition": "{% $foo = 1 %}"
                },
                {
                    "Next": "SecondMatchState",
                    "Condition": "{% $foo = 2 %}"
                }
            ]
        },
        "FirstMatchState": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:123456789012:function:OnFirstMatch",
            "Next": "NextState"
        },
        "SecondMatchState": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:123456789012:function:OnSecondMatch",
            "Next": "NextState"
        },
        "DefaultState": {
            "Type": "Fail",
            "Error": "DefaultStateError",
            "Cause": "No Matches!"
        },
        "NextState": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:123456789012:function:FUNCTION_NAME",
            "End": true
        }
    }
}
  • Figure 15-6 shows the resulting directed acyclic graph:
    • start at FirstState with foo_input
    • ChoiceState evaluates the value: 1 goes to FirstMatchState, 2 to SecondMatchState, anything else to the DefaultState error
    • all matches end at NextState. The format is verbose and harder to read than code-first frameworks.
  • Figure 15-7 (an AWS example):
    • check stock prices, request human approval, then buy or sell
    • The AWS backend executes functions, maintains state and retries, and with redrive restores state right before the crash (Figure 15-8: three invocations, two failures) from the underlying durable log: no second human approval, no rebuy or resell (still keep it idempotent for races), no republished report.
  • Encoding the orchestrator in source code:
    • like durable execution engines, some DFOs (Azure Durable Functions) let you write the functions and the workflow logic in code, no YAML/JSON/JSONata
    • Example 15-2 (Azure's Python sample): http_start (HTTP-triggered, starts an orchestration and returns a check-status response), hello_orchestrator (yields three call_activity("hello", city) calls for Seattle, Tokyo and London and returns the list), and the hello activity (returns a greeting):
import azure.functions as func
import azure.durable_functions as df

myApp = df.DFApp(http_auth_level=func.AuthLevel.ANONYMOUS)

# An HTTP-triggered function with a Durable Functions client binding
@myApp.route(route="orchestrators/hello_orchestrator")
@myApp.durable_client_input(client_name="client")
async def http_start(req: func.HttpRequest, client):
    function_name = req.route_params.get('functionName')
    instance_id = await client.start_new(function_name)
    response = client.create_check_status_response(req, instance_id)
    return response

# Orchestrator
@myApp.orchestration_trigger(context_name="context")
def hello_orchestrator(context):
    result1 = yield context.call_activity("hello", "Seattle")
    result2 = yield context.call_activity("hello", "Tokyo")
    result3 = yield context.call_activity("hello", "London")

    return [result1, result2, result3]

# Activity
@myApp.activity_trigger(input_name="city")
def hello(city: str):
    return f"Hello {city}"
  • The main difference between document-first and code-first is where the workflow definition lives. In code you use familiar tools and IDEs
    • you may find framework-specific notations cumbersome and prefer the clean separation of documents.
  • Limits:
    • you rarely see an organisation (especially a large one) move to another major cloud provider just for durable function orchestration
    • the likely outcome is using the orchestrator that comes with your cloud provider.

Summary points

  • FaaS is growing rapidly, with tools for development, management, deployment, triggering, testing and scaling
    • triggers include event streams, queues, consumer group lag, wall-clock time, APIs and webhooks.
  • Function solutions suit stateless and simple stateful problems that do not need event scheduling
    • orchestration calls functions in strict sequence while respecting event order
    • durable function orchestrators handle complex multi-step workflows and avoid rerunning completed computations and calls.
Terms to carry forward
  • FaaS, trigger, function-trigger map, batch size and window.
  • Cold start, warm start, lag trigger, hysteresis loop.
  • Direct-call pattern; durable function orchestration; redrive.
