Building Event-Driven Microservices 17: Integrating Event-Driven and Request-Response Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 17. Previous: Building Event-Driven Microservices 16: Eventual Consistency. Next: Building Event-Driven Microservices 18: Handling Bad Data in Event Streams.

Takeaways
  • Request-response is unavoidable: metrics from phones and IoT devices, third-party APIs, real-time content for web and mobile, dynamic requests (location, time, weather). Combine it with event-driven patterns.
  • Requests into events: a dedicated endpoint (high throughput, isolation) or a REST proxy (simple, not fast). Send a schema ID with plain-text payloads where clients are tiny.
  • Calling third-party APIs brings head-of-line blocking, nondeterminism, API drift and request surges on reprocessing: rate-limit in the service.
  • Serving data: from internal state (route to the owning instance), external state (all-in-one or composite service); access state only via the API.
  • Turn requests into events for audit and replay; design asynchronous UIs; use micro frontends to align frontend, backend and data to one business concern.

17.1 Why integrate

  • Request-response appears in:
    • collecting metrics from external sources (a user's phone app, IoT devices)
    • integrating with other request-response services, particularly third-party
    • serving content in real time to web and mobile users
    • serving dynamic requests based on real-time information (location, time, weather).
  • Note: here "request-response services" means services that call each other's API directly (HTTP is the prime example), synchronous (the caller waits) or asynchronous (the caller works while awaiting a callback).
  • Three subjects: turning requests into events, integrating with third-party APIs, building micro frontends.

17.2 Turning requests into events

  • Two common ways: a dedicated endpoint, or a REST proxy.
  • Dedicated endpoint:
    • the client reports to a backend server that writes to the event stream
    • It gives very high throughput and load isolation, ideal for thousands of events per second
    • Example:
      • a media streaming app (like Netflix) on a smart TV or phone emits which titles a viewer started, how far they got and whether they stopped
      • Example 17-1 is a Protobuf MediaClick:
// Example 17-1: Proto3 MediaClick event
message MediaClick {
    // Account Id
    string id = 1;

    // When the click happened
    Timestamp time = 2;

    // The media Id that the user clicked on
    int32 mediaId = 3;

    enum Media {
        Movie = 0;
        Show = 1;
        MovieTrailer = 2;
        ShowTrailer = 3;
    }

    // The type of media
    Media mediaType = 4;
}
  • Client-side serialisation
    • (Figure 17-1): the client populates the Protobuf schema, serialises and sends it; reasonable when the client is relatively heavyweight
    • In constrained environments (a browser, a tiny microcontroller) you often cannot package the libraries for Protobuf, Avro or JSON Schema, so serialise on the backend server (Figure 17-2): the client sends simple JSON or even plain text
    • Risk: data not matching the server's schemas, causing data loss and repetitive break-fix.
  • Avoid the risk with a schema ID:
    • at build and deployment, get the compatible schema ID from the registry and store it in the client
    • add it to each payload (Example 17-2, plain text; schemaId = 623). The server parses and encodes it into that Protobuf schema:
id = 123419873144,
time = 1748890957,
mediaId = 14997977211,
mediaType = "Movie",
schemaId = 623
  • This is brittle:
    • any deviation from the plain-text format may break the parser. Tip: plain text plus schemaId suits endpoints where every byte matters (web pages, low-connectivity regions)
    • server-side serialisation suits cases where client serialisation is too expensive, difficult or impossible
      • An incorrect enum or value type breaks downstream serialisation and can fail the service, so test both the creating and parsing logic before production
    • with proper tests most of the risk disappears.

REST proxy

  • A service exposing a REST API to the event broker:
    • list streams, create streams, publish events, consume. Options: the Confluent REST proxy
    • Azure REST Proxy (Kafka)
    • Apache Pulsar's built-in proxy
    • Google PubSub's REST API.
  • Publish singly or in batches to POST /topics/(string:topic_name). Example 17-3 sends three already serialised records: only value is mandatory
    • key and partition are optional (without them the default partitioner such as round-robin applies):
POST /topics/test HTTP/1.1
Host: kafkaproxy.host.com
Content-Type: application/vnd.kafka.binary.v2+json
Accept: application/vnd.kafka.v2+json, application/vnd.kafka+json, application/json

{
    "records": [
        { "key": "b1B6", "value": "Z33nAnn12481" },
        { "value": "c2233Gna1F=", "partition": 6 },
        { "value": "newb718==" }
    ]
}
  • Example 17-4 sends a value_schema with the records
    • the proxy validates against the schema registry and, if incompatible, throws, returns an error and refuses to write: it fences out bad data:
POST /topics/test HTTP/1.1
Host: kafkaproxy.host.com
Content-Type: application/vnd.kafka.avro.v2+json
Accept: application/vnd.kafka.v2+json, application/vnd.kafka+json, application/json

{
    "value_schema": "{\"name\":\"firstname\",\"type\": \"string\"}",
    "records": [
        { "value": "Bob" },
        { "value": "Milhouse", "partition": 1 }
    ]
}
  • Consuming via a REST proxy needs a durable consumer to store offset progress: create the consumer, subscribe to streams, consume, commit successfully processed offsets, delete the consumer (each proxy's API differs).
  • A REST proxy is not typically high-performance: moderate loads may need several, and you may want to move to native producers and consumers.

17.3 Integrating with third-party request-response APIs

  • Your service calls the API like any remote function call, awaiting the reply or continuing
    • If it waits while processing a stream it suffers head-of-line blocking (see "Queues via Apache Kafka"): no further events until the call returns or times out
    • If order does not matter, consume as a queue to reduce blocking
    • Then parse the response and continue (Figure 17-3).
  • Example 17-5 makes a blocking HTTP call inside a Kafka transaction so output and consumer offsets commit atomically:
// Example 17-5: a blocking call to a request-response API inside a Kafka transaction
// Set up producer with transactional.id and
// call initTransactions() once at startup
producer.initTransactions();

while (true) {
    // Poll for records
    ConsumerRecords<String, Event> records =
        consumer.poll(Duration.ofMillis(1000));
    if (records.isEmpty()) continue;

    try {
        producer.beginTransaction();

        for (ConsumerRecord<String, Event> record : records) {
            Event event = record.value();
            Request request = generateRequest(event, ...);

            Response response =
                RequestService.makeBlockingRequest(request, timeout, retries, ...);

            if (response.code == 200) {
                <Class Type> parsedObj = parseResponseToObject(response);
                OutputEvent outEvent = applyBusinessLogic(parsedObj, event, ...);

                // Write the results to the output event stream
                // using the transactional producer
                producer.send(new ProducerRecord<>("output-stream-name", outEvent));
            } else {
                // Handle non-200 responses (log, skip, etc.)
            }
        }

        // Send offsets to transaction before committing
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (TopicPartition partition : records.partitions()) {
            List<ConsumerRecord<String, Event>> pr = records.records(partition);
            long lastOffset = pr.get(pr.size() - 1).offset();
            offsets.put(partition, new OffsetAndMetadata(lastOffset + 1));
        }
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());

        // Commit the transaction
        producer.commitTransaction();
    } catch (Exception e) {
        // Log and handle the error, then abort the transaction
        producer.abortTransaction();
    }
}
  • Benefits: mix event processing with request-response APIs; call whatever external APIs however you need; process in parallel with many nonblocking requests.
  • Drawbacks:
    • Nondeterminism (Chapter 9): reprocessing a failed event may differ, even a second later.
    • The API and response format may change: monitor for breaking changes (reputable third parties are careful; internal APIs owned by small or inexperienced teams may break more).
    • Request frequency:
      • after finding a bug and rewinding the input, a service consuming as fast as it can floods the endpoint, which may fail or block your IP addresses, causing failed requests, tight retry loops and more nondeterminism. Use quotas (Chapter 19) but best rate-limit in the microservice
      • external APIs may block you, and some charge more above your agreed limit.

17.4 Serving data with a request-response API

  • An event-driven microservice can expose an endpoint:
    • it consumes, processes, applies its logic, stores state internally or externally
    • the API (usually inside the application) serves reads of that state.

Internal state stores

  • Figure 17-4:
    • a client request goes to a load balancer that routes to an instance; with one instance, all data is in it (inputs A and B, changelog to the broker)
    • With several instances the state is sharded, so route requests to the owner
    • Kafka Streams offers interactive queries that handle requests, routing and forwarding (check whether your framework supports it).
  • Two properties locate a key:
    • a key maps to only a single partition (see "Repartitioning Event Streams"), and a partition is assigned to only a single consumer instance (see "The Basics of Event-Driven Microservices")
    • An instance knows its own and its peers' partition assignments, so it applies the partitioner to the request's key, then cross-references the partition ID with the group's assignments (Figure 17-5; Figure 17-6: the partitioner says P1, assigned to instance 1)
    • After a rebalance the route may change.
  • Drawback:
    • the more instances, the more spread the state
    • with even keys and a round-robin balancer: success rate = 1/(number of instances), so for many instances almost every request misses and is redirected, raising latency and load.
  • A smart load balancer (Figure 17-7) applies the partitioner logic, compares to its table of group assignments (inferred from repartition or changelog streams) and forwards correctly
    • It entangles application logic with the balancer: renaming state stores or changing topology breaks forwarding, so ship it in the single deployable and testing process
    • Warning: best effort only; races and dynamic rebalancing mean every instance must still redirect misdirected requests.
  • Sharded serving is hard if your framework does not support it; you will likely use an external store.

External state stores

  • All state is typically directly available to each instance
    • (no forwarding; for massive state route to the right shard or query shards in parallel)
    • Rebalances do not rebuild internal stores, allowing easy zero-downtime scaling and scaling serving capacity separately from data store capacity.
  • Caution: access state through the microservice's request-response API, not directly from the store; direct access introduces coupling that makes change difficult and risky.
  • All-in-one microservice
    • (Figure 17-8): each instance consumes events, materialises to the external store and serves the API
    • both scale with instance count (beyond partition counts extra instances still serve requests)
      • Advantages: simplicity, short rebalances
      • Drawback: resource use with asymmetric loads (many instances for REST traffic, one for event processing)
    • alternatively split them.
  • The Composite Service
    • (Figure 17-9): the API is completely separate from the event-driven microservice that materialises state to the external store
    • two microservices but one bounded context, treated as one composite service in one repository, tested, built and deployed together
      • Advantages: different languages and scaling policies (a lightweight stream framework to populate state; the organisation's usual web stack for the customer experience)
    • fault isolation
      • (bugs in event processing do not take down request handling, though state goes stale)
      • Disadvantages: complexity and risk (data structures, topologies and request patterns may need changes in both), harder end-to-end tests
      • Useful and widely used in production
    • manage deployments carefully and test integration comprehensively.

17.5 Handling requests within an event-driven workflow

  • Handle a request directly (do it and respond) or convert it into an event, inject it into its own stream and process it like any other event
    • a service may mix the two (Figure 17-10): left, a traditional create via the API written directly to the database
    • right, event-first: package the request as an event, publish it, then materialise it into the internal store and process it with other business logic.
  • Benefits:
    • a durable record for auditing and replaying
    • cross-reference the request's timestamp with the most recently consumed events and postpone fulfilling the request until all earlier-timestamped events are processed.
  • Trade-off: extra latency and complexity; the response waits until the request is published and processed (async/await lets the caller do other work). Not for every use case.

Processing events for user interfaces

  • A UI is how people interact with the bounded context. Request-response UIs respond synchronously
    • services that handle requests as events need asynchronous UI frameworks that stay responsive and update as results arrive.
  • Manage expectations:
    • a synchronous click expects success or failure in maybe 500 ms or less
    • an asynchronous service may need seconds, especially with a large backlog. Show that the request was sent and discourage more actions until done, like airline and car-rental sites' "making reservation, please wait" spinner that blanks out the page.
  • Tip:
    • research best practices for asynchronous UIs. Also decide when to push UI updates: business rules guide you
    • ask the impact of a user deciding on stale state and the performance and experience impact of pushing an update.
  • Warning: intermittent network failures can create duplicate requests and events; make consumers idempotent (see "Generating duplicate events").

Example: newspaper publishing workflow (approval pattern)

  • A newspaper publisher's app manages layout with templates that decide where articles and advertisements go: the latest and most important news on the front pages
    • ads placed by size, content, budget and placement agreements (a children's toy company may not want its ad next to a missing-child story). A designer places items
    • the editor checks cohesion, article order by estimated importance and ad placement per contracts, and must approve before printing or send it back
      • Advertisers can reject only after the editor approves, and the paper seeks approval only from the most important advertisers (significant ad spend)
    • others have no overriding say (Figure 17-11).
  • Two bounded contexts, design and approval, as two microservices (Figure 17-12, omitting accounts and login)
    • The newspaper populator consumes layout templates, advertisements and articles into a relational database
      • an employee arranges them, compiles a PDF into an external store and sends it for approval (1) as a candidate by writing to the event stream
    • Example 17-6, the populated newspaper event (the PDF is referenced by URI):
Key: String pn_key        // Populated newspaper key
Value: {
    String pdf_uri        // Location of the stored PDF
    int version           // Version of the populated newspaper
    Pages[] page_metadata // Metadata about what is on each page
    - int page_number
    - Enum content        // Ad, article
    - String id           // ID of the ad or article
}
  • Tip:
    • store a large PDF externally and reference it by URI
    • you manage the permissions yourself. The populator does not turn the employee's human interactions into events: not all human interaction needs to be an event
    • it may be a monolithic request-response framework that only produces events when writing to the output stream
      • Warning: risk of the stream getting out of sync with the populator's state: see "Data Liberation Patterns" (outbox table, change-data capture logs).
  • The approval service consumes the populated newspaper into local storage for the editor to view and mark up, comment and give tentative approval toward advertiser approval
    • the editor may reject at any point. Example 17-7, the editor approval event:
Key: String pn_key                // Populated newspaper key
Value: {
    String marked_up_pdf_uri      // Optional URI of the marked-up PDF
    int version                   // Version of the populated newspaper
    Enum status                   // awaiting_approval, approved, rejected
    String editor_id
    String editor_comments
    RejectedAdvertisements[] rejectedAds  // Optional, if rejected
    - int page_number
    - String advertisement_id
    - String advertiser_id
    - String advertiser_comments
}
  • Advertisers get a UI to approve ad size and placement
    • the service decides which ads need approval, cuts the PDF into pieces for them and must not leak news stories or competitors' ads
    • Example 17-8, the advertiser approval event (keyed on pn_key; several events per newspaper, non-entity events; the aggregate decides the advertiser approval; the editor approval's rejectedAds array aggregates rejections)
    • Advertisers act independently, and the process moves on only after all have replied or timed out:
Key: String pn_key                // Populated newspaper key
Value: {
    String advertiser_pdf_uri     // The PDF piece shown to the advertiser
    int version                   // Version of the populated newspaper
    int page_number
    boolean approved              // Approved or not
    String advertisement_id
    String advertiser_id          // ID of the approver
    String advertiser_comments
}
  • Benefit: the three event types form the canonical narrative of candidate and final newspapers, rejections, comments and approvals, auditable at any point to find where things went wrong.

Separating the editor and advertiser approval services

  • New requirements split them into two services
    • Advertiser components: choose which advertisers to ask, slice the PDF, manage advertiser-facing components, controls and branding, and handle public-facing exposure (security practices, patches)
    • Editor components: approve overall layout, design and flow
    • assess the summary of retailer responses (not each one)
    • suggest to the designer how to handle rejections (Figure 17-13).
  • Two new streams: the **editor-approved populated newspaper stream
    • ** (same format as stream
    • , produced only when the editor releases it for advertiser approval) and the **advertiser approvals summary stream
    • **. Advantage: all editor gating logic stays inside the editor service
      • versions of one pn_key live entirely there, so the editor controls which versions go for approval and gates further revisions until satisfied with initial advertiser feedback. Which ads need approval is opaque to the editor and layout service. Example 17-9, the summary event, shows the advertiser approval service encapsulating approval state
      • the editor still decides:
Key: String pn_key
Value: {
    int version                        // Version of the populated newspaper
    AdApprovalStatus[] ad_app_status
    - Enum status                      // Waiting, Approved, Rejected, Timedout

    - String advertisement_id

    - String advertiser_comments

17.6 Micro frontends

  • A micro frontend is a microservice that handles a specific business concern and provides the API for a consumer-facing interface. Figure 17-14 compares three ways to organise customer-facing content
    • in the first two, frontend and backend are owned by separate teams behind a single frontend layer, while micro frontends align the data store, backend and frontend on the business concern.
    • Monolithic backend:
      • a dedicated backend team (many subteams in large monoliths) with headcount growing with the monolith
      • a separate frontend team using a request-response API
      • coordinating changes across team and technology boundaries is hard.
    • Microservice backend:
      • many teams end up here, and many stay: independent, product-focused services each owned by one team, exposing request-response APIs and event streams up to an aggregation layer. Downside: the aggregation layer invites ad hoc business logic (convenient because of team and deployment boundaries) and suffers the tragedy of the commons (everyone relies on it, no one is responsible)
      • stewardship helps, but small, innocent changes accumulate.
    • Micro frontends: split the monolithic frontend into independent components, each backed by a supporting backend microservice: modularity, separation of business concerns, team autonomy, and language, deployment and codebase independence extended to the frontend.

Example: experience search and review application

  • An app connecting vacationers with local guides, attractions, entertainment and food: search local experiences, see details and contacts, leave reviews
    • Version 1 (Figure 17-15): one service materialises experiences and reviews into a single endpoint with a basic key-value store with limited search
    • no geolocation search though users ask for it
      • Version 2 (Figure 17-16): split reviews into their own microservice (a distinct bounded context) and make a product micro frontend stitching search and review together as an aggregation layer with no business logic of its own
    • each micro frontend may be owned by its own team or one team
      • The product boundary contains search and review micro frontends
      • Search must support geolocation: the user's address becomes lat-lon coordinates for distance to nearby experiences
    • the review micro frontend's responsibilities are unchanged but it is freed from coupling to search.
  • Notes on Figure 17-17:
    • reviews are published first as events and then ingested back into the data store (in both versions): keeping core business data external to the implementation lets you break out the review service with no data synchronisation errors (if kept internal to v1's store you would need to liberate it first, Chapter 6, and plan a long-term migration)
      • Tip: being able to materialise and consume any stream, however the service needs, makes event-driven backends pair so well with micro frontends
      • Search replaced its store with one supporting plain-text and geolocation search
    • it also consumes the user profile entity stream to personalise results, and the smaller services clarify which business function uses user data (an observer sees each context's input streams; in v1 one must read code)
      • Both versions read the same streams: change backends without maintaining a specific state store or migrating data, just replay
    • unlike a monolith where data is tightly coupled to the database. The combination is limited only by the granularity and detail of the event data.

Benefits and drawbacks

  • Benefits:
    • Composable: build interfaces from services; spin up new microservices from streams to try products and turn them off with no code remnants.
    • Pluggable: add frontends without disturbing the old; one micro frontend can power several products.
    • Independent: any frameworks, languages and stores; test and release on your own schedule; ownership is easier to determine.
    • Leverages full-stack skill sets: frontend, backend and data store work, in a narrower scope.
  • Drawbacks:
    • Inconsistent UI elements and styling (colours, fonts, sizing, layouts): coordinate a style guide and a common library of basic elements, with cross-team testing.
    • Cross-service updates are harder than in a monolith and more frequent (shared libraries shape the experience).
    • Varying performance and load times,
      • or failures: the composite frontend must degrade gracefully (for example spinners)
      • stitching them is a UI-design exercise beyond the book's scope.

Summary points

  • External systems (human or machine) mostly use request-response, so requests and responses may need converting to events. Machine input can be schematised ahead of time and collected server-side
    • third-party API responses need parsing and wrapping into your own event definition and tend to be brittle.
  • Requests can become events processed asynchronously, which needs a UI that cues users that handling is asynchronous.
  • Micro frontends give full-stack product alignment on event-driven backends: purpose-built frontends with a compositional layer, with autonomy mirroring backend microservices and flexible options for experimentation, segmentation and custom experiences.
Terms to carry forward
  • Dedicated endpoint, REST proxy, schemaId payloads; head-of-line blocking.
  • Interactive queries, smart load balancer, all-in-one microservice, composite service.
  • Event-first request; asynchronous UI; approval pattern; micro frontend; aggregation layer.
