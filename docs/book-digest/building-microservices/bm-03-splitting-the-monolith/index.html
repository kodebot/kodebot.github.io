Building Microservices 3: Splitting the Monolith

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 3. Previous: Building Microservices 2: How to Model Microservices. Next: Building Microservices 4: Microservice Communication Styles.

Takeaways
  • Microservices are not the goal. Have a clear end goal, and try simpler ways first (for scaling, "a few more copies behind a load balancer" may beat a long decomposition).
  • Migrate incrementally: chip away at the monolith one piece at a time. "If you do a big-bang rewrite, the only thing you're guaranteed of is a big bang" (Martin Fowler).
  • The monolith is rarely the enemy; it often remains, diminished. Do not decompose prematurely: Snap CI merged its services back and split again a year later.
  • Choose what to split first by balancing benefit against ease; start with something easier to get quick wins.
  • Patterns: strangler fig, parallel run, feature toggle, reporting database. Splitting a database costs performance, integrity, transactions and tooling.

3.1 Have a goal

  • Adopt microservices only if you cannot find an easier way towards your goal. "You don't 'win' by having microservices."
  • Without a goal you confuse activity with outcome, stop considering alternatives, and cannot decide which microservice to create first.
  • Tip from the book: microservices are not easy; try the simple stuff first.
  • State the change you want, consider easier routes, and if microservices really are best, track progress against the goal and change course.

3.2 Incremental migration

  • Think of the monolith as a block of marble: do not blow it up, chip away.
  • Break the journey into small steps you can learn from; a retrograde step is only a small one. Small pieces give quick wins, momentum, and let you unlock value incrementally.
  • Stock advice: start somewhere small. Pick one or two areas, implement them as microservices, deploy to production, then reflect on whether they moved you towards the goal.
You will not appreciate the true horror of a microservice architecture until you run it in production.

3.3 The monolith is rarely the enemy

  • A monolith is not inherently bad; focus on the benefits you expect, not on "not having the monolith".
  • It often remains after the shift, diminished. Example: to handle more load, remove the 10% of functionality that is bottlenecked and leave the other 90%.
  • A coexisting monolith and microservices can feel "messy", but real architecture is never clean (chapter 16 returns to this). Incremental migration also tells you when to stop.
  • A hard requirement to kill the monolith is rare: usually dead or dying technology, infrastructure being retired, or an expensive third-party system. Even then, go incrementally.

3.4 The dangers of premature decomposition

  • Snap CI
    • (Thoughtworks, hosted CI/CD): the team had built the similar GoCD earlier (now open source, deployable locally)
    • Snap CI was a new codebase, but past domain experience emboldened them to define service boundaries quickly.
  • After a few months the use cases proved subtly different, so the boundaries were wrong, causing many cross-service changes and high cost of change
    • They merged the services back into one monolith to learn the domain, then a year later split it into microservices with much more stable boundaries.
  • Newman has seen this often. Decomposing an existing codebase is easier than starting with microservices, for this reason.

3.5 What to split first?

  • Use your goal to prioritise:
    • scaling: functionality constraining load goes high on the list
    • time to market:
      • look at volatility to find the parts that change most often
      • static analysis tools like CodeScene find hotspots (Figure 3-1 shows hotspots in Apache ZooKeeper)
  • Also consider viability: some functionality is too baked into the monolith to detangle, or too critical (high risk), or already self-contained (easy).
  • The decision balances how easy the extraction is against the benefit of extracting it.
  • Advice:
    • pick the first couple of services toward the easy end (still contributing to the goal) to build early momentum
    • If you cannot make even the easiest work, reconsider whether microservices suit you
    • Successes then prepare you for complex, critical extractions.

3.6 Decomposition by layer

Extracting a service has sub-steps across the three tiers: UI, backend code, data.

  • UI:
    • the mapping from a microservice to a UI is often not 1:1 (chapter 14), so UI extraction can be a separate step
    • Do not ignore it: many look only at the backend benefit and end up siloed
    • The UI often lags the backend (the possibilities only appear once the services exist) but do not let it lag too much.
  • Backend code and storage must both be in scope. Example: extracting wishlist functionality, with code in the monolith and related tables in its database.

Code first

  • Extract the wishlist code into a new microservice
    • the data stays in the monolithic database for now. The most common first step because it gives more short-term benefit and the code is easier to extract than data.
  • Leaving data behind stores up pain, so it must follow
    • If the code cannot be extracted cleanly you can abort and avoid the data work; but if the code comes out and the data cannot, you are in trouble
    • So sketch how both will be extracted before you start.

Data first

  • Extract the wishlist tables first
    • Seen less often, but useful when unsure the data can be separated cleanly: you prove it can be done before the (hopefully easier) code extraction.
  • Main short-term benefit: de-risking the full extraction, forcing you to face loss of enforced data integrity and lack of transactions across the data early.

3.7 Useful decompositional patterns

Many are detailed in Newman's Monolith to Microservices (O'Reilly, 2019).

Strangler fig pattern

  • A term coined by Martin Fowler, inspired by the plant: wrap the old system with the new and let the new system take over more features incrementally.
  • Intercept calls to the monolith: if the functionality is implemented in the new architecture, redirect to the microservice; otherwise let the call continue to the monolith.
  • Often needs no change to the monolith, which is unaware it is wrapped.

Parallel run

Run the monolith's implementation and the new microservice side by side, serving the same requests and comparing results, to check the new one without risking existing behaviour. Especially useful for critical functionality (detailed later in the book, chapter 8).

Feature toggle

  • A mechanism to switch a feature on or off, or switch between two implementations
    • Useful in a migration: leave the monolith's functionality in place and toggle between it and the microservice's.
  • With the strangler fig using an HTTP proxy, the toggle can live in the proxy layer as a simple control.
  • Reference: Pete Hodgson, "Feature Toggles (aka Feature Flags)", martinfowler.com, 2017.

3.8 Data decomposition concerns

Performance

  • Relational databases are very good at joins. Splitting the database moves joins up into service code, which is unlikely to be as fast.
  • MusicCorp example:
    • extract catalog functionality (artists, tracks, albums)
    • The monolith's Albums table is referenced by the Ledger table (sales: date plus a SKU, stock keeping unit)
    • At month end finance wants a best-sellers report with names ("400 copies of Now That's What I Call Death Polka, $1,596") instead of SKUs, so a query joins Ledger to Albums.
  • After the split, the Finance service queries the Ledger for the best-selling SKUs, then calls the Catalog service for each SKU, which runs its own SELECT on Albums. The join still happens, but in the application tier
    • latency will almost certainly rise.
  • Mitigation: the report is monthly, so cache aggressively; allow bulk SKU lookups in Catalog; or cache album information locally.

Data integrity

  • With both tables in one database, a foreign key guarantees a ledger row can always reach its album, and prevents deleting a referenced album
    • Across two databases that enforcement is gone.
  • You must get used to databases no longer enforcing relationships between entities. Coping patterns:
    • a soft delete: mark the Album row deleted instead of removing it
    • copy the album name into the Ledger when a sale is made (then decide how to synchronise name changes)

Transactions

  • Splitting data loses ACID transactions (explained in chapter 6)
    • The reflex is distributed transactions, but they are complex even when done well and do not give the same guarantees (see "Database Transactions", chapter 6).
  • Preferable alternatives are sagas (chapter 6), which bring new complexity. As with integrity, accept that breaking apart databases, for good reasons, brings a new set of problems.

Tooling

  • Database refactoring tooling is limited: code has IDE refactoring and is stateless; databases have state.
  • Most schema tools use version-controlled delta scripts run in strict order, idempotently: Rails migrations, DBDeploy (a tool Newman helped create), and today Flyway or Liquibase.

Reporting database

  • Breaking apart databases hides internal storage, which makes stable interfaces (and independent deployability) possible, but it hurts legitimate needs to access data from several services, or in a database rather than via a REST API.
  • Reporting database pattern:
    • a dedicated database designed for external access
    • the microservice pushes data from its internal storage into it. It hides internal state management but still presents data as a database: ad hoc SQL, large joins, existing SQL toolchains.
  • Two key points:
    • Practise information hiding:
      • expose only the bare minimum, a subset of the service's data
      • As it is not a direct mapping, you can design a different schema tailored to consumers, even a different database technology.
    • Treat it like any other microservice endpoint: the maintainer must keep it compatible when internals change, and owns the mapping from internal state to the reporting database.

Summary points

  • Know what you want to achieve; the goal shapes the work and tells you whether you are heading the right way.
  • Migrate incrementally: change, roll out, assess, repeat; even splitting one service can be broken into small steps.
  • For more depth: Newman's Monolith to Microservices. Next: how microservices communicate.
Terms to carry forward
  • Incremental migration, premature decomposition.
  • Strangler fig, parallel run, feature toggle.
  • Code first vs data first.
  • Soft delete, SKU, delta scripts (Flyway, Liquibase).
