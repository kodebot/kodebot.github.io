Building Microservices 7: Build

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 7. Previous: Building Microservices 6: Workflow. Next: Building Microservices 8: Deployment.

Takeaways
  • Continuous integration is a practice, not a tool: integrate to mainline at least daily, have tests, and make a broken build the team's top priority.
  • Prefer trunk-based development with feature flags over long-lived feature branches, which only delay integration.
  • A build pipeline models the path to production; continuous delivery treats every check-in as a release candidate. Build the artifact once, deploy that same artifact everywhere, keep configuration outside it.
  • Mapping code to builds: one giant repo with one build is a trap; choose one repository per microservice (multirepo) or a monorepo with several builds. Newman prefers multirepo.

7.1 A brief introduction to continuous integration

  • CI
    • keeps everyone in sync by frequently checking that new code integrates. A CI server detects a commit, checks it out and verifies it (compiles, tests pass)
    • daily integration is the bare minimum.
  • It produces artifacts for further validation, built once and stored in a repository (the CI tool's or a separate system), so you confirm that the artifact you deploy is the one you tested.
  • Benefits: fast feedback (static analysis and tests), automated artifact creation, everything version controlled (including infrastructure as code), and traceability from deployed artifact to code and tests.

Are you really doing CI?

Adopting Jenkins, CircleCI or Travis is not the same as doing CI. Jez Humble's three questions:

Question Why it matters
Do you check in to mainline once per day? Frequent integration keeps future integration easy, even with short-lived branches
Do you have tests that validate your changes? Without tests you only know it compiles, not that behaviour is intact
When the build breaks, is fixing it the team's #1 priority? A red build means the last change may not have integrated; stop other check-ins, or the fix time balloons (days of a broken build)

7.2 Branching models

  • Feature branching
    • gives isolation but delays integration, so the eventual merge is more complex
    • Trunk-based development has everyone commit to the same trunk and uses feature flags to hide unfinished work
    • Newman prefers it; flags also help progressive delivery (chapter 8).
  • Evidence:
    • the 2016 State of DevOps report (DORA and Puppet) found that branches or forks living less than a day, fewer than three active branches in total, and daily merging to trunk all contribute to higher performance
    • The 2019 report extends this to open source: commit sooner and work in small batches (large "patch bombs" are slower to merge).
  • GitFlow
    • and branch-heavy flows are common in open source, where many time-poor untrusted committers need vetting
    • Typical in-house teams are tight-knit with commit rights, so what works for open source may not suit your day job.
  • Rule: "Integrate early, and integrate often." If you must branch, keep branches short.

7.3 Build pipelines and continuous delivery

  • Early CI work at Thoughtworks showed the value of stages:
    • fast, small-scoped tests first
    • slow, large-scoped tests later (no point running them if the fast ones fail). That is a build pipeline, where one deployable artifact progresses through stages, building confidence.
  • Continuous delivery (CD),
    • from Humble and Farley's book Continuous Delivery (2010): constant feedback on production readiness, treating every check-in as a release candidate
    • You model every stage, manual and automated, and know where each version stands.
  • Example (the Catalog service):
    • build-120 failed the fast tests
    • build-121 failed the performance tests
    • build-122 reached production; a version deploys only if it passes each stage.

[!note] Continuous delivery versus continuous deployment Continuous delivery treats each check-in as a release candidate and decides whether to deploy. Continuous deployment deploys automatically every check-in that passes automated checks. Deployment extends delivery: you can do delivery without deployment, not the reverse. Many want a human decision, which is compatible with delivery. Human steps after check-in are often bottlenecks (for example manual regression testing replaced by automated tests), so more automation moves you towards deployment.

  • Tooling:
    • choose a tool with CD as a first-class concept
    • hacking CI tools into CD is complex. It should model manual stages too (for example a manual UAT environment where you mark the stage passed, which then triggers the next automated stage).

Trade-offs and environments

  • Early in the pipeline you want fast feedback
    • later you want certainty, via increasingly production-like environments. Your laptop is fastest but least like production
    • a faithful production copy for every commit is slow and costly. Keep reviewing the balance.
  • Difficulty of replicating production is one reason for testing in production (smoke tests, parallel runs; chapter 8).

Artifact creation

  • Rule 1: build an artifact once and once only (rebuilding wastes time, "is bad for the planet", and a differing build flag can change behaviour).
  • Rule 2: the artifact you verify is the artifact you deploy.
  • Build it early (after compiling and fast tests) and store it in an artifact repository (Artifactory, Nexus or a container registry)
    • The same artifact (build-123) is deployed for slow tests, performance tests and production.
  • So environment-specific configuration stays outside the artifact. Example: log level DEBUG in the Slow Tests stage to diagnose failures, INFO in Performance Tests and Production.

7.4 Mapping source code and builds to microservices

One giant repo, one giant build

  • Simple:
    • one repository, one build producing several artifacts, one commit for multi-service changes
    • It suits lockstep releases, which are normally to be avoided, though it may be fine for a short time early in a project with one team.
  • Downsides:
    • a one-line change to the User service rebuilds and verifies everything (hurting cycle time, the speed from change to live)
    • it is unclear which artifacts to deploy so teams deploy everything together
    • a break blocks all other changes
    • with several teams, who owns the build? It is "the worst form of monorepo" for independently deployable services, and Newman almost only sees it in early projects.

Pattern: one repository per microservice (multirepo)

  • Each service has its own repository and a straightforward mapping from change to CI build, and ownership can change per repository
    • The cost: developers work across several repositories, and Git cannot make atomic changes across repositories.
  • Reusing code:
    • package it as a library (the Invoice and Payroll services depend on a Connection library)
    • Rolling out a library change means building a new version, bumping the dependency, and redeploying each consumer
    • The chapter 5 caveats apply: no atomic rollout, and it is harder to see which services use which version when deprecating one.
  • Changes across repositories:
    • changing the Inventory API and the Shipping client needs two commits
      • stage them (Inventory first, since client code is useless without the new API) and handle the case where one fails
    • The lack of atomic deploy is, in Newman's view, usually a symptom of boundaries in the wrong place: "If you are constantly making changes across multiple microservices, it's likely that your microservice boundaries are in the wrong place", so consider merging services
    • The pain can usefully enforce boundaries
    • Eases: IDEs that support multiple repositories, or wrapper scripts.
  • Where to use it: small or large teams alike; if you constantly change across boundaries it may not fit (but that is itself a warning sign), and code reuse is harder.

Pattern: monorepo

  • Code for several microservices (or projects) in one repository, popularised by big tech (Google is best known)
    • Main claimed benefits: atomic changes across projects, finer-grained reuse (depend on a single source file rather than a packaged library), and visibility of others' code.
  • Example: the Inventory and Shipping change fits in a single commit.

[!warning] Atomic commit is not atomic deploy Committing across services at once does not give atomic rollout. Wanting to roll out changes across services simultaneously violates independent deployability.

  • Mapping to builds:
    • start by mapping folders to builds (a change in user-service triggers the User build; changes in both folders trigger both)
    • It gets harder with a shared common folder (rebuilds everything) and overlapping folders
    • Large repos need graph-based build tools such as Bazel (an open source version of Google's internal tool); changing build systems is a major undertaking.
  • Defining ownership (Fowler's scale):
Model Meaning
Strong Owners make the changes; outsiders must ask
Weak Outsiders may change code, but owners review and accept (a pull request)
Collective Any developer can change any code
  • Collective ownership suits about 20 developers or fewer
    • beyond that, strong or weak. Monorepos need fine-grained ownership controls: Google built them on Perforce first
    • GitHub CODEOWNERS (since 2016) maps owners to directories or paths (owners are requested for review on a pull request; aim for small pull requests).
# CODEOWNERS (examples from GitHub's documentation)
# @doctocat owns files under build/logs at the repo root and below
/build/logs/ @doctocat

# @octocat owns any file in an apps directory anywhere
apps/ @octocat

# @doctocat owns /docs at the repo root
/docs/ @doctocat

  • Tooling and scale:
    • Google's monorepo took huge engineering: a graph-based build system, a distributed object linker, IDE plug-ins
    • it outgrew Perforce and built its own tool, Piper
      • When Newman worked there (2007-2008) over a hundred people maintained developer tools
      • Read Potvin and Levenberg, "Why Google Stores Billions of Lines of Code in a Single Repository" (CACM, 2016): "your organization probably isn't Google"
      • Microsoft put Windows in Git (about 270 GB working directory) and built VFS for Git (formerly GVFS) to download only needed files
    • Newman knows no team outside Microsoft using it. Lerna (from the Babel team) helps produce several versioned artifacts from one repo.
  • How "mono" is mono?
    • About 95% of Google's code was in the monorepo as of 2016
    • others scope a monorepo to one system, and some teams run a per-team monorepo (all of a team's services together), giving most benefits without the scale problems under collective ownership.
  • Where to use it:
    • large tech-focused companies (Google, Microsoft, Facebook, Twitter, Uber) that can invest heavily, and very small teams (10 to 20 developers)
    • The pain lands on organisations in the middle: enough scale to need new tooling, not enough bandwidth to build it.

Which approach would Newman use?

  • Multirepo.
    • The monorepo's main advantages (finer-grained reuse, atomic commits) do not outweigh the problems at scale: encouraging cross-service changes, confused ownership, and new tooling
    • Organisations that start with a monorepo find it hard to leave later (rapid growth, then the sunk cost fallacy)
    • Fine-grained ownership tools may change his mind; graph-based build tool adoption remains low.

Summary points

  • The ideas here (CD, trunk-based development, repository layout) matter whether or not you use microservices.
