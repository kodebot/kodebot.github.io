Building Microservices 8: Deployment

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 8. Previous: Building Microservices 7: Build. Next: Building Microservices 9: Testing.

Takeaways
  • A logical microservice becomes several instances across machines and zones, with databases that may use read replicas and shared infrastructure; topology differs per environment.
  • Five principles: isolated execution, automation, infrastructure as code, zero-downtime deployment, desired state management.
  • Options: physical machine, VM, container, application container, PaaS, FaaS (plus Wasm on the horizon). Newman's default is containers, with Kubernetes when you need orchestration, but "if it ain't broke, don't fix it" and give up as much control as you are comfortable with.
  • Progressive delivery separates deployment from release: blue-green, feature toggles, canary releases and parallel runs.

8.1 From logical to physical

  • Earlier chapters showed services logically (Invoice talks to Order)
    • Physically each service has multiple instances for load and robustness, a load balancer (for HTTP) routing requests, and instances spread over machines and data centres.
  • Cloud providers (AWS, Azure, Google) give no SLA for a single machine or a single availability zone, so deploy across multiple availability zones.
  • The database:
    • "don't share databases" still holds, yet instances of the same service share one database: the data-access logic stays inside one logical service
    • Each instance needs the same order data.
  • Database deployment:
    • Read replicas take read traffic from a primary node; writes are harder to scale (sharding adds complexity).
    • Shared infrastructure:
      • one engine and hardware can host several logically isolated databases (Invoice and Order), pooling hardware and cutting licences and management, but a failure hits several services. On-prem organisations favour this
      • public cloud teams more often run dedicated databases per service (for example AWS RDS handles backups, upgrades and multi-zone failover cheaply).

Environments

  • Each environment has a purpose:
    • some have production data, some only a few real services with fakes for the rest
    • The Catalog service's path: developer laptop, CI (fast and slow tests), preproduction (optional manual verification), then production.
  • Ideally every environment copies production, but cost forbids it; early environments favour fast feedback, later ones production-likeness.
  • Example topology:
    • laptop with one instance
    • CI with two instances on one machine (to test load balancing cheaply)
    • production with four instances over four machines in two data centres.
  • So the number of instances and configuration vary per environment, while the artifact is built once and environment-specific information stays separate (a parameter as simple as the instance count).

8.2 Principles of microservice deployment

Principle Idea
Isolated execution Instances have their own compute resources and cannot affect neighbours
Focus on automation Choose technology that allows automation; make it culture
Infrastructure as code Machine-readable configuration in source control, to recreate environments
Zero-downtime deployment Releasing a version never interrupts consumers
Desired state management A platform maintains the declared state, relaunching instances as needed

Isolated execution

  • Multiple services per host
    • looks simpler for host management (host count does not grow with services), but: monitoring is harder (service CPU or host CPU?)
    • side effects from one service's load
    • harder impact analysis of host failures
    • contradictory dependencies
    • and who configures the host (a central team, hurting team autonomy)
      • Gilt, a fashion retailer that began with a Rails monolith, hit uneven load on one service damaging neighbours
      • It undermines independent deployability.
  • Neal Ford:
    • many deployment practices optimise for scarcity of resources (buying a server took long lead times, every two to three years at some clients)
    • on-demand computing and virtualisation removed that.
  • Isolation models:
    • dedicated physical machines (best isolation, highest cost) to containers (weaker isolation, cheaper and faster to provision)
    • PaaS platforms such as Lambda or Heroku provide isolation for you
    • For most workloads containers are "good enough", Newman's default.

Focus on automation

  • More services mean more processes to configure and monitor
    • manual operations then need more people. Automate (launch a VM with code, deploy software and database changes without manual steps) and let developers self-service provision.
  • Case studies:
    • realestate.com.au (REA) front-loaded tooling work: two services in the first three months, 10 to 15 in the next three, over 70 after 18 months. Gilt went from about 10 services after a year to over 100 by 2012 and over 450 in 2014 (roughly three per developer)
    • the Financial Times has a similar ratio.

Infrastructure as code

  • Configure infrastructure with machine-readable code (Chef, Puppet, bash), bringing software-development practice (version control, testing, repeatability) to operations
    • See Kief Morris, Infrastructure as Code, 2nd ed
    • (2020).
  • Declarative tools:
    • Puppet
    • Chef
    • Ansible (from CFEngine); for cloud resources Terraform (cross-platform, Newman's preference over AWS CloudFormation/CDK) and Pulumi (normal programming languages instead of DSLs).
  • Benefits:
    • auditing (who changed what) and reproducing an environment at a point in time
    • A client rebuilding a past production system for a court case spent over three months piecing it together from emails and release notes.

Zero-downtime deployment

  • Without it you must coordinate outages with consumers
    • Sarah Wells of the Financial Times called it the single biggest improvement in delivery speed, enabling more frequent releases and releasing during working hours (fewer mistakes, more support).
  • Asynchronous, broker-backed communication makes it easy (messages wait); synchronous is harder
    • Rolling upgrades (ramp old instances down as new ones come up) suit Kubernetes, though blue-green suffices if that is all you need
    • Retrofitting is harder than designing for it.

Desired state management

  • Specify requirements (instance count, memory, CPU) and the platform maintains them: if an instance dies, it launches a replacement, even on hardware or data-centre loss
    • Examples: Kubernetes, cloud autoscaling groups, Nomad (mixed workloads such as Java apps, VMs, Hadoop jobs).
  • Anecdote: killing dev EC2 instances at day's end while an autoscaling group kept respawning them cost real money (per-hour billing). Fix: a script that disables the group on shutdown.
  • Prerequisites:
    • fully automated instance deployment and fast launch times (else keep spare capacity)
    • Adopt a platform rather than hack your own, perhaps after you already have a few services.
  • GitOps
    • (pioneered by Weaveworks) combines desired state and infrastructure as code: the desired state lives in source control and tooling (for example Flux) applies changes to the running Kubernetes system
    • A tool does not mean you embrace the ideas.

8.3 Deployment options

Option What it is
Physical machine Directly on hardware, no virtualisation
Virtual machine An instance in a VM
Container An instance as a container, perhaps orchestrated by Kubernetes
Application container Services inside a host such as Tomcat, IIS or WebLogic
PaaS Higher abstraction (Heroku, Google App Engine, AWS Beanstalk)
FaaS Instance deployed as functions (AWS Lambda, Azure Functions)
  • Physical machines:
    • rare
    • low utilisation, the temptation to pack several services per machine, and desired state or zero-downtime need a management layer. Needs a specific reason.
  • Virtual machines:
    • split a physical machine into VMs (VMware, EC2), each a full OS
    • excellent isolation, higher utilisation
      • Cost of virtualisation: the hypervisor (type 2 virtualisation: AWS, VMware, vSphere, Xen, KVM, which run on a host OS; type 1 runs on hardware) consumes CPU, I/O and memory, so there are diminishing returns, like dividers in a sock drawer taking space
      • Cloud-managed VMs are easy to automate (with autoscaling groups)
    • VMs under central ops control often are not. Netflix built much on EC2 VMs. Use when you need stricter isolation or cannot containerise.

Containers

  • The Linux kernel manages the process tree and resource limits
    • A container is an abstraction over a subtree of the process tree, sharing the host kernel, with resources allocated by the kernel
    • Lineage: Solaris Zones, OpenVZ, LXC, then Docker on top.
  • Versus VMs:
    • no hypervisor, no extra kernel
    • start in seconds rather than minutes
    • finer resource control
    • many more per host (thin dividers). Often run on EC2 VMs for the best of both.
  • Not perfect:
    • you must route traffic to containers (Docker helped; LXC did not). Isolation is weaker than VMs: early documented container breakouts
    • much improved, but treat containers as isolation for trusted software, and investigate more for untrusted code.
  • Windows containers
    • arrived with Windows Server 2016
    • OS size was an obstacle (Nano Server over 1 GB early on, versus Alpine at a few megabytes, though layer caching helps; Server Core for legacy). They offer process isolation or Hyper-V isolation (own VM; same image, chosen at launch, slower start).
  • Blurred lines: stronger isolation with container lightness: Hyper-V containers and Firecracker (a "kernel-based VM", used behind AWS Lambda).
  • Docker:
    • brought the image concept, tooling, networking help and a registry. Treat services in any language uniformly
    • replaces heavyweight Vagrant VMs locally, with the same image locally and in production. It managed one machine only
    • Docker Swarm and Swarm Mode followed, but Kubernetes won orchestration.

Application containers

  • Several services in one host such as Tomcat, IIS or WebLogic:
    • clustering and monitoring, and a single JVM's overhead for several services. Newman challenges them: they constrain technology choice and automation options
    • shared in-memory session state clustering is something to avoid
    • monitoring is insufficient
    • slow start-up
    • harder life-cycle management and analysing threads and resource use
    • cost and overhead. It again optimises for scarcity, and lacks isolation: prefer self-contained, process-per-instance services.

Platform as a Service

  • Higher abstraction:
    • give a technology artifact (WAR file, Ruby gem) and it runs and may autoscale. Best ones are hosted
    • Heroku set the benchmark and also runs databases. Trade-off: little control when it does not fit
    • "the smarter the PaaS tries to be, the more it goes wrong" (autoscaling heuristics for the average app). Growth in self-hosted PaaS stalled
    • serverless products (managed brokers, databases, storage) filled the space.

Function as a Service

  • Serverless
    • is an umbrella for technologies where servers do not matter to the user (Ken Fromm is credited with coining it, as far as Newman can tell). AWS Lambda (launched 2014) started the FaaS excitement: you deploy a function, dormant until a trigger (file, queue item, HTTP call)
    • the platform starts, runs and stops it and scales concurrency.
  • Benefits: pay only for use (good for low or unpredictable load), implicit high availability, less operational work.
  • Limitations:
    • Runtime support: Azure Functions supports the most; Google supported only Go, some Node versions and Python at the time of writing; AWS allows custom runtimes (more to maintain).
    • Resources: you control only memory, which implies CPU and I/O.
    • Duration caps: Google 9 minutes, AWS Lambda 15, Azure potentially unlimited. Long-running work is a poor fit.
    • Statelessness: chaining is awkward; Azure Durable Functions suspend and resume state, which Newman finds friendlier than AWS Step Functions (JSON configuration).
  • WebAssembly (Wasm):
    • a standard for running sandboxed programs from many languages in browsers (eBay delivered barcode scanning written in C++ this way)
    • WASI
      • extends it beyond the browser (for example CDNs such as Fastly and Cloudflare)
      • Lightweight and strongly sandboxed, it may challenge containers server-side but lacks platforms (running it inside Kubernetes containers is "somewhat pointless")
    • Nomad's pluggable drivers suit it.
  • Challenges:
    • cold starts (worst for JVM and .NET; runtimes are often kept warm, and Go, Python, Node and Ruby start fast)
    • concurrency limits and scaling that overwhelms downstream systems (Bustle's Redis).
  • Mapping to microservices:
    • Function per microservice: a sensible start; an entry point dispatches on the path (/receipt, /claim, /report for an Expenses service).
    • Function per aggregate
      • (DDD): one function per aggregate keeps lifecycle logic together
      • Keep a coarser external interface; a shared database is acceptable while one team manages it, but split data if needs diverge
      • The microservice then becomes more a logical concept than a single deployable.
    • Finer than an aggregate: Newman advises against it (it breaks aggregate integrity and drags in sagas; he abandoned a function per state transition).
  • The way forward:
    • most developers will use platforms hiding detail
    • he urges Kubernetes-bound clients to try FaaS first. The BBC runs Lambda for BBC News alongside EC2 where Lambda invocations would cost too much.

8.4 Which option is right?

Sam's really basic rules of thumb
  • If it ain't broke, don't fix it. Fashion should not drive decisions.
  • Give up as much control as you are happy with, then a little more. If a good PaaS or FaaS works, use it.
  • Containerising is not pain-free but is a good compromise between isolation cost and control, with local-development benefits. "Expect Kubernetes in your future."
  • If on public cloud and the problem fits FaaS, do that and skip Kubernetes. Do not let lock-in fear trap you (chapter 16).
  • Found a PaaS (Heroku, Zeit) that fits? Push the work to it.
  • For the rest, containerisation.

Role for Puppet, Chef and other tools

  • Their role shrank (since 2014) with containers:
    • a Dockerfile defines the same needs, and a container is rebuilt from scratch, avoiding much of the complexity of re-running tools on long-lived machines. They persist for legacy and for building clusters
    • infrastructure as code remains vital, now via Terraform or Pulumi.

8.5 Kubernetes and container orchestration

  • Why orchestrate:
    • Docker defines and runs a container on one machine
    • you need containers across machines
      • Orchestrators schedule workloads (find or reallocate resources), maintain desired state, and distribute for utilisation, latency or robustness
      • Hand-written scripts "get old very fast"
      • Mesos, Nomad, ECS and Swarm Mode offer similar
    • Kubernetes won (Docker Swarm, Rancher and CoreOS lost out).

Simplified Kubernetes concepts

  • Cluster: nodes (machines running workloads) plus a control plane.
  • Pod: one or more containers deployed together (usually one; a sidecar proxy such as Envoy in a service mesh is the rare second).
  • Service: a stable routing endpoint mapping to ephemeral pods. You do not "deploy a service"; you deploy pods that map to one.
  • Replica set: desired number of pods; usually handled via a deployment.
  • Deployment: applies changes: rolling upgrades, rollbacks, scaling.
  • To deploy: define a pod, a service, and apply changes with a deployment.

Multitenancy and federation

  • One shared cluster pools resources and cuts cost, but Kubernetes is limited as a multitenant platform
    • Options: platforms on top (Red Hat's OpenShift, with access controls but vendor abstractions), or federation (several clusters plus a layer across them), which makes pooling harder (a node belongs to one cluster) but eases upgrading clusters (move services to a new cluster rather than upgrading in place)
    • Largely a scale concern.

Background, CNCF and portability

  • Kubernetes began at Google, inspired by Borg and Omega (see "Borg, Omega, and Kubernetes", Burns et al.), but made more developer-friendly and not aimed at Borg's massive scale
    • Mesos and Nomad suit thousands of machines (Apple Siri on Mesos; Roblox on Nomad). Newman sees it both as a gift to the industry and as Google's counter to an AWS near-monopoly (AWS and Azure lead; Google Cloud is a distant third), both true.
  • The CNCF (part of the Linux Foundation) hosts and curates projects (it is compared to the Apache Software Foundation), runs events, docs, training and certification.
  • Kubernetes is not really a platform
    • teams assemble one (service mesh, brokers, log aggregation), often via a platform engineering team. This gives choice but "tyranny of choice"
    • OpenShift pre-selects. Portability is true in theory, less in practice (your custom platform must be rebuilt).

Helm, Operators, CRDs and Knative

  • Helm
    • ("the missing package manager") and Operators manage third-party applications (such as Kafka)
    • Operators focus on ongoing management, and they can be used together
      • CRDs extend the Kubernetes API (new abstractions beside pod, service and so on, integrating with the CLI and access controls)
    • Newman finds their best use unclear and the space unsettled.
  • Knative
    • brings FaaS-style workflows to Kubernetes but needs a service mesh (only Istio stable)
    • given Kubernetes and Istio's churn he advises conservative organisations to look at OpenFaaS (no mesh required) instead, and regrets that Google kept Knative out of the CNCF.
  • The future: Kubernetes will be "everywhere. You just won't know it", hidden under higher-level abstractions, though developers still must understand distributed systems.

Should you use it?

  • Running your own cluster is a significant undertaking (big on-prem users outsource it)
    • prefer fully managed (Google, Azure, AWS), but on public cloud ask whether FaaS or PaaS (Azure Web Apps, Google App Engine, Zeit, Heroku) fits better
    • Let admins and developers try it first (minikube, MicroK8s, Katacoda, CNCF training)
    • Do not adopt it "because everyone else is": with a handful of developers and few services it is overkill.

8.6 Progressive delivery

  • Frequent deployment correlates with lower change failure rates (Forsgren, Humble and Kim, Accelerate, 2018), so "go fast and break stuff" does not apply to shipping
    • Progressive delivery releases functionality to users in a controlled way, built on separating deployment from release.

[!note] Deployment versus release (Jez Humble) Deployment is installing a version into an environment (often production). Release is making the system or a feature available to users. Blue-green shows it: run the new (green) version beside the live (blue), verify, then redirect customers; a problem found before the switch hurts nobody.

  • Progressive delivery
    • was coined by James Governor (RedMonk): "continuous delivery with fine-grained control over the blast radius"
    • Adam Zimman of LaunchDarkly adds it can delegate feature control to the product owner, who must understand the mechanics.
  • Feature toggles (flags):
    • hide deployed functionality
    • used with trunk-based development, to enable on a schedule, to disable a problem feature, or per user (a beta group). Start with a configuration file
    • managed tools include LaunchDarkly and Split
    • see Pete Hodgson's "Feature Toggles".
  • Canary release:
    • named for mine canaries
    • a limited subset sees the new version, growing if healthy
      • With microservices: toggle per service, or run two versions and route in the network path
      • Newman once ramped manually over a week
    • now Spinnaker automates it from metrics.
  • Parallel run:
    • send the same request to two implementations and compare, with one the source of truth (do not send two order updates or pay an invoice twice). Newman's Monolith to Microservices (2019, ch. 3) covers it
    • GitHub's Scientist does it in-process.
  • Start by separating deployment from release and deploying safely and often, working with product owners.

Summary points

  • The principles (isolation, automation, infrastructure as code, zero downtime, desired state) outlive the current technology.
  • Understand your requirements; a simpler solution than Kubernetes may fit, and offloading work to the public cloud is fine.
  • Next chapter: testing.
