Building Microservices 9: Testing

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 9. Previous: Building Microservices 8: Deployment. Next: Building Microservices 10: From Monitoring to Observability.

Takeaways
  • Keep a pyramid of automated tests: many fast unit tests, fewer service tests (one microservice, collaborators stubbed), very few end-to-end tests.
  • End-to-end tests across microservices are flaky, slow, ownerless and anti-independent-deployability; at scale most teams remove them in favour of explicit schemas, consumer-driven contracts (CDCs) and production testing.
  • Pact is the main CDC tool; CDCs are as much a conversation between teams as a test.
  • Test in production safely (smoke tests, canaries, synthetic users) and weigh MTTR against MTBF.
  • Treat cross-functional requirements (performance, robustness) as tests too, and start early.

9.1 Types of tests

  • Brian Marick's testing quadrant
    • (as shown in Crispin and Gregory, Agile Testing): the lower half is technology facing (supports developers: unit tests, property tests such as performance), the upper half business facing (acceptance testing automated and end-to-end; exploratory testing manual, such as UAT). Most of it is preproduction validation, often a gate for deployment
    • a limitation is that it leaves out testing in production.
  • Newman advises automating repetitive testing
    • if you still do large amounts of manual testing, fix that before going far down the microservices path, since you cannot get the benefits without fast validation.

[!note] Manual exploratory testing Moving to microservices changes it little (apart from ownership if UIs split along team lines, "Toward Stream-Aligned Teams"). Tooling for visual assertions automates some checks, freeing testers for discovery: exploring as an end user and testing what is too costly to automate. This chapter mostly ignores it.

9.2 Test scope

  • Mike Cohn's test pyramid
    • (Succeeding with Agile, 2009): unit tests, service tests and UI tests. Higher up, scope and confidence grow but feedback slows and failures are harder to diagnose
    • lower down, tests run fast and pinpoint the failing line, but a single line tested tells little about the whole system.
  • The names are ambiguous ("service" especially; is a test of several classes a unit test?). Newman keeps unit and service but says end-to-end instead of UI.
  • Worked example: a helpdesk and web shop call Customer, which calls Loyalty.

Level What it covers
Unit One function or method; no microservices launched, little external file or network use. Often from TDD or property-based testing. Thousands run in under a minute; they support refactoring
Service One microservice directly, bypassing the UI, external collaborators stubbed so failure points at that service
End-to-end The whole system, often driving a GUI in a browser; high confidence, but tricky in microservices

[!note] What about integration tests? Newman avoids the term: some mean two services or a code-database binding, others mean full end-to-end tests. Map your own usage to his explicit terms.

Trade-offs

  • Balance fast feedback against confidence
    • Too slow? Replace large tests with smaller ones: when a larger test fails, write a unit test to catch it sooner
    • Bug in production? Probably a missing test.
  • Rule of thumb:
    • an order of magnitude more tests as you go down the pyramid
    • Example: a monolith with 4,000 unit, 1,000 service and 60 end-to-end tests that Newman's team cut down in large-scope tests.
  • Test snow cone (inverted pyramid): almost no small tests, all coverage in large ones: glacial runs, few builds, and a build can stay broken a long time.

9.3 Implementing service tests

  • Deploy one instance of the microservice (for example the container image built in chapter 7) and stub the downstream collaborators (Loyalty), configuring the service under test to talk to them.
  • Stub versus mock:
    • a stub returns canned responses (when asked for customer 123's balance, return 15,000) and does not care how often it is called (0, 1 or 100)
    • A mock also verifies the call was made and fails otherwise
      • it needs more smarts and makes tests brittle if overused, but is useful for expected side effects (creating a customer sets up a points balance)
    • Newman uses stubs far more
    • Gerard Meszaros calls fakes, spies, dummies, stubs and mocks Test Doubles
    • See Freeman and Pryce, Growing Object-Oriented Software, Guided by Tests.
  • A smarter stub: mountebank
    • (Brandon Byars)
    • A small appliance programmable over HTTP (written in NodeJS, which does not matter to callers): you create imposters on ports with a protocol (TCP, HTTP, HTTPS, SMTP) and canned responses, and can set expectations to act as a mock
      • one instance can stub several services
    • Capital One used it in performance tests
    • It does not stub messaging protocols (Pact may help).
  • Passing service tests do not tell you about consumers (helpdesk, web shop), hence end-to-end tests.

9.4 Implementing (those tricky) end-to-end tests

  • Deploy several microservices together and drive the UI
    • Which versions of the other services (production, or queued to go live)? Avoid duplication across services' own end-to-end tests with fan-in: a successful build of any of several pipelines triggers a shared end-to-end stage.

Disadvantages

  • Flaky and brittle tests:
    • more moving parts, so failures unrelated to the functionality (a service down, a network glitch, race conditions, timeouts)
    • Tests that people just rerun are flaky, "the enemy"
    • They breed normalisation of deviance (Diane Vaughan, on the Challenger disaster): accepting failure as normal
    • Per Fowler ("Eradicating Non-Determinism in Tests"): track them down, remove them if not fixable at once, rewrite them to avoid threads, stabilise the environment, or replace them with a smaller-scoped test.
  • Who writes them?
    • Free-for-all test explosion (snow cone) or no ownership so failures get ignored
    • Emily Bache's approach: split the suite into groups owned by different teams (still fragile: a Loyalty change can break both suites)
    • A dedicated test team is "disastrous" (distance from the code, longer cycle times)
    • If you cannot avoid a shared suite, give it joint ownership of its health; Newman thinks at a certain organisational scale you must move away from cross-team end-to-end tests.
  • How long?
    • They can take a day or more (one regression suite took six weeks)
    • Few teams curate them
    • Parallelising (Selenium Grid) is no substitute for removing tests; removal is risky and unthanked ("airport security" analogy), so it rarely happens.
  • The great pile-up:
    • long suites mean broken stages stay broken longer, changes pile in and releases get bigger and riskier
    • The right answer is to make the suite faster, not to allow check-ins on a broken build.
  • The metaversion: versioning services together invites deploying them together ("Now you have 2.1.0 problems", Brandon Byars), abandoning independent deployability, and services become coupled and tangled.
  • Lack of independent testability:
    • teams that deploy independently should test independently, with their own test environments
    • Accelerate found high performers "do most of their testing on demand, without requiring an integrated test environment".

[!question] Should you avoid end-to-end tests? They can be manageable with few microservices, but with 10 or 20 they bloat into a Cartesian-like explosion, and a shared suite undermines independent deployability. Schemas catch structural breakages; semantic breakages need something with reduced scope: contract tests.

9.5 Contract tests and consumer-driven contracts

  • Contract tests: the consuming team writes tests that describe how it expects an external service to behave. They should pass against both your stubs and the real service.
  • CDCs: the contract tests become an explicit, programmatic statement of the consumer's expectations, shared with the producer team, who run each consumer's contracts in its build against a single producer in isolation: faster and more reliable than end-to-end.
  • Example:
    • Customer has two consumers, so there is a set for the helpdesk and one for the web shop
    • Scope matches a service test (run only Customer, dependencies stubbed)
    • Good practice: people from both sides pair on the tests.
  • CDCs sit at the service-test level of the pyramid
    • a break shows which consumer is affected, then you fix it or start the breaking-change discussion (chapter 5). CDCs also make Conway's law explicit.

Pact

  • Originally built in-house at realestate.com.au, now open source; initially Ruby and HTTP only, now JVM, JavaScript, Python, .NET and also messaging.
  • Flow:
    • the consumer defines expectations in a DSL
    • a local Pact server runs them and produces a Pact file (a JSON specification). The same mock server acts as a local stub, replacing mountebank or hand-rolled stubs.
  • The producer replays the Pact file against its service
    • Because consumer and producer build separately, share the file via the CI artifact repository or the Pact Broker, which stores several versions (test against consumer-in-production and latest), records when contracts were validated, and shows which services depend on which.
  • Other options: Spring Cloud Contract, only for pure JVM.
  • It is about conversations:
    • like Agile stories as "a placeholder for a conversation", CDCs codify discussions about the API and trigger new ones when they break. They need trust and communication: with a third party you may have only limited integration tests around the untrusted component
    • for thousands of public consumers you may play the consumer yourself, and CDCs matter more.

The final word

  • Those who have run microservices at scale mostly drop end-to-end tests for explicit schemas, CDCs, in-production testing and canaries
    • See them as training wheels while you learn CDCs and improve monitoring and deployment, trading cycle time for lower risk
    • Do not ditch them without understanding what you lose.

9.6 Developer experience

  • Running many microservices locally strains the developer machine (JVM services are heavy)
    • Developing in the cloud adds latency to feedback and needs connectivity (cloud IDEs such as Cloud9, now AWS-owned, exist but are not yet the norm)
    • Newman thinks it "misses the point": a developer should run only the services they work on (say the team's five), locally, with stubs for other teams' services
    • Needing to work on hundreds of services signals a bigger problem ("Strong Versus Collective Ownership").

9.7 From preproduction to in-production testing

  • Preproduction tests model how the system behaves
    • models are imperfect, and more tests bring diminishing returns: you cannot reduce failure to zero in a distributed system. Production is "the most important location" to test.

  • Types:
    • a ping check (is the instance up) is a test
    • smoke tests at deployment, on software before release
    • canary releases
    • injecting fake user behaviour (a fake customer's order or registration) into the real system.
  • Making it safe:
    • tests must not cause instability or taint production data
    • Pings (unless the health checks become an internal denial of service), and smoke tests on deployed-but-unreleased software are safe thanks to separating deployment from release
    • Synthetic users need care (no shipping the order or taking payment); see "Semantic Monitoring".

[!note] MTTR over MTBF? Techniques such as blue-green and canary releases acknowledge you cannot catch every problem. In web operations the trade is mean time between failures (MTBF) versus mean time to repair (MTTR). Fast rollback plus good monitoring (chapter 10) can beat more functional tests; many teams build test suites and neglect monitoring and recovery. Sometimes (proving a business idea) skipping preproduction testing altogether is sensible.

9.8 Cross-functional testing

  • Nonfunctional requirements
    • (latency, user capacity, accessibility, security) are better called cross-functional requirements (CFR), Sarah Taraporewalla's term, since they emerge from cross-cutting work
    • Most can really only be met in production, but tests in the property testing quadrant show progress
    • They may be set per service (a payment service needs more durability than music recommendations, where 10 minutes of downtime is fine) and often surface as service-level objectives (SLOs) (chapter 10).
  • CFR tests follow the pyramid too:
    • a load test is end-to-end, but once a bottleneck is found, write a smaller test
    • an accessibility check on generated HTML needs no network. Review CFRs early and often.

Performance tests

  • Microservices add network calls (one database call becomes several service calls), and a slow link in a synchronous chain slows everything
    • Do not postpone performance testing until just before launch.
  • Mix isolated service tests with core journeys run at volume
    • ramp up simulated customers to see how latency varies
    • make the environment as production-like as feasible (data volume, machines) while knowing results may mislead (false negatives or positives)
      • Run a subset daily and a larger set weekly
    • the longer you wait, the harder to find the culprit commit.
  • Look at the results, with targets (your SLOs); or fail when performance drifts from one build to the next. Use the same visualisation tools as in production.

Robustness tests

  • A microservice system is as reliable as its weakest link (multiple instances behind a load balancer, circuit breakers; chapter 12)
    • Tests that recreate failures (an artificial timeout against a stub) are trickier but worthwhile, especially for shared behaviour such as mesh circuit breaking.

Summary points

  • Optimise for fast feedback and separate test types by scope.
  • Avoid end-to-end tests spanning more than one team; use CDCs as focus points for conversations.
  • Understand the trade-off between testing effort and fast detection (MTBF versus MTTR), and try testing in production.
  • Further reading: Crispin and Gregory, Agile Testing; Ham Vocke, "The Practical Test Pyramid" (martinfowler.com, 2018).
Terms to carry forward
  • Test pyramid, snow cone, Marick quadrant.
  • Unit, service and end-to-end tests; stub, mock, test double; mountebank.
