Clean Architecture 5: Object-Oriented Programming

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 5. Own-words digest with short attributed quotes. Previous: Clean Architecture 4: Structured Programming. Next: Clean Architecture 6: Functional Programming.

Takeaways
  • The popular definitions of OO fail: "data plus function", "modelling the real world", and "encapsulation, inheritance and polymorphism". Encapsulation was perfect in C and weakened by C++, Java and C#; inheritance was possible by hand in C; polymorphism was possible with pointers to functions.
  • What OO really gave us is safe and convenient polymorphism, which imposes discipline on indirect transfer of control.
  • For the architect that means dependency inversion: any source code dependency can be inverted, so the architect has absolute control over the direction of every dependency and can build plugin architectures with independently deployable and developable components.

5.1 What is OO?

  • "The basis of a good architecture is the understanding and application of the principles of object-oriented design." But what is OO?
    • "The combination of data and function"
      • is unsatisfying: it implies o.f() differs from f(o), which is absurd
      • programmers passed data structures to functions long before 1966, when Dahl and Nygaard moved the call stack frame to the heap and invented OO.
    • "A way to model the real world" is evasive: what does it mean and why would we want it? Perhaps OO is easier to understand because it is closer to the real world, but that is too loose and does not say what OO is.
    • "Encapsulation, inheritance and polymorphism": the implication is that OO is the right mix of these three, or that an OO language must support them. Martin examines each.

5.2 Encapsulation?

  • OO languages make it easy to draw a line around a cohesive set of data and functions: outside it the data is hidden and only some functions are known (private members, public member functions)
    • This idea is not unique to OO: C had perfect encapsulation
    • A C header declares the struct and functions; the implementation file defines them:
// point.h
struct Point;

struct Point* makePoint(double x, double y);

double distance(struct Point* p1, struct Point* p2);

// point.c
#include "point.h"
#include <stdlib.h>
#include <math.h>

struct Point {
    double x, y;
};

struct Point* makePoint(double x, double y) {
    struct Point* p = malloc(sizeof(struct Point));
    p->x = x;
    p->y = y;
    return p;
}

double distance(struct Point* p1, struct Point* p2) {
    double dx = p1->x - p2->x;
    double dy = p1->y - p2->y;
    return sqrt(dx * dx + dy * dy);
}
  • (The book's point.c spells the function makepoint; corrected here to match the header.) Users of point.h have no access to the members of struct Point: perfect encapsulation in a non-OO language, which C programmers did all the time.
  • Then C++ broke it. For technical reasons (the compiler needs to know the size of class instances) the member variables must be declared in the class's header:
// point.h
class Point {
public:
    Point(double x, double y);
    double distance(const Point& p) const;

private:
    double x;
    double y;
};
  • Clients now know the members exist (the compiler blocks access, but if they are renamed point.cc must be recompiled)
    • The public, private and protected keywords partially repair it, but that was a hack forced by the compiler's need to see the variables
    • Java and C# abolished the header and implementation split entirely, weakening encapsulation further (declaration and definition cannot be separated)
    • Many OO languages (Smalltalk, Python, JavaScript, Lua, Ruby) have little or no enforced encapsulation
    • OO relies on programmers being well-behaved enough not to circumvent it
    • So: no point for OO on encapsulation.

5.3 Inheritance?

  • Inheritance is simply the redeclaration of a group of variables and functions within an enclosing scope, which C programmers (and users of most languages of that era) did manually long before OO. A NamedPoint in C masquerades as a Point because its first two fields match Point's in order
    • it is a pure superset:
// namedPoint.c (excerpt)
struct NamedPoint {
    double x, y;
    char* name;
};

// main.c (excerpt)
struct NamedPoint* origin = makeNamedPoint(0.0, 0.0, "origin");
struct NamedPoint* upperRight = makeNamedPoint(1.0, 1.0, "upperRight");

printf("distance=%f\n",
    distance(
        (struct Point*) origin,
        (struct Point*) upperRight));
  • That trickery was common practice and is how C++ implements single inheritance
    • Multiple inheritance by such tricks is considerably harder, and in C you must cast (an OO language upcasts implicitly)
    • Verdict: OO made masquerading data structures significantly more convenient, but nothing completely new: no point for encapsulation and perhaps a half-point for inheritance.

5.4 Polymorphism?

  • Polymorphic behaviour existed before OO. A simple C copy program:
#include <stdio.h>

void copy() {
    int c;
    while ((c = getchar()) != EOF)
        putchar(c);
}
  • getchar() reads STDIN and putchar() writes STDOUT
    • which device? Their behaviour depends on the type of STDIN and STDOUT, as if they were Java-style interfaces with an implementation per device
    • UNIX requires every IO driver to provide five standard functions with identical signatures (open, close, read, write, seek; UNIX systems vary)
    • The FILE structure holds five pointers to functions:
struct FILE {
    void (*open)(char* name, int mode);
    void (*close)();
    int (*read)();
    void (*write)(char);
    void (*seek)(long index, int mode);
};
  • The console driver defines these functions and loads a FILE with their addresses (struct FILE console = {open, close, read, write, seek};); getchar() simply returns STDIN->read():
extern struct FILE* STDIN;

int getchar() {
    return STDIN->read();
}
  • This simple trick is the basis of all polymorphism in OO:
    • in C++ every virtual function has a pointer in a vtable, all virtual calls go through it, and derivatives' constructors load their versions into the object's vtable
    • Polymorphism is an application of pointers to functions, used since Von Neumann architectures appeared in the late 1940s: OO provided nothing new..
    • but it made polymorphism much safer and more convenient
    • Raw function pointers are dangerous: you must remember conventions (initialise the pointers, call everything through them) and a lapse gives a "devilishly hard" bug
    • OO languages eliminate those conventions and dangers, making polymorphism trivial: "OO imposes discipline on indirect transfer of control."

5.5 The power of polymorphism

  • What if a new IO device appears (handwriting recognition in, speech synthesiser out)? The copy program needs no changes, not even a recompile, because its source does not depend on the IO drivers' source
    • as long as the drivers implement the five FILE functions it works. IO devices became plugins of the copy program.
  • Why did UNIX do this? In the late 1950s programs should be device independent: many were written device-dependent (reading decks of punched cards, IBM Hollerith 80-column cards, and punching new decks), then customers moved to reels of magnetic tape, forcing large rewrites
    • The plugin architecture was invented for IO device independence and implemented in almost every OS since, but most programmers did not extend it to their own programs because function pointers were dangerous
    • OO allows the plugin architecture to be used anywhere, for anything.

5.6 Dependency inversion

  • Before safe polymorphism, a typical calling tree had main calling high-level functions, which called mid-level, which called low-level, and source code dependencies inexorably followed the flow of control (Figure 5.1): to call a function the caller had to mention the callee's module (C #include, Java import, C# using)
    • Control flow was dictated by system behaviour and source dependencies by control flow, leaving the architect few options.
  • With polymorphism (Figure 5.2) module HL1 calls F() in ML1 through an interface, which is a source code contrivance: at runtime the interface does not exist and HL1 simply calls F() in ML1 (indirectly)
    • But the source code dependency (the inheritance relationship) from ML1 to the interface I points opposite to the flow of control
    • This is dependency inversion, and its implications for the architect are "profound".
  • Because OO languages give safe, convenient polymorphism, any source code dependency, wherever it is, can be inverted by inserting an interface
    • Architects in OO systems have absolute control over the direction of all source code dependencies
      • they are not constrained to align them with the flow of control: whichever module calls and whichever is called, the dependency can point either way
    • "That is power! ..
    • what OO is really all about, at least from the architect's point of view."
  • Use it:
    • rearrange dependencies so the database and the UI depend on the business rules (Figure 5.3), not the reverse: the UI and database become plugins to the business rules, whose source never mentions the UI or the database. The business rules, UI and database can be compiled into three separate components or deployment units (jar files, DLLs, Gem files) with the same dependencies as the source
    • the business rules component does not depend on the other two.
  • So the business rules can be deployed independently of the UI and database, and changes to those need not affect the rules
    • When a component's source changes only that component is redeployed: independent deployability
    • If modules can be deployed independently they can be developed independently by different teams: independent developability.

5.7 Conclusion

  • To the software architect the answer to "what is OO?" is clear: the ability, through polymorphism, to gain absolute control over every source code dependency in the system. It lets the architect create a plugin architecture in which modules with high-level policies are independent of modules with low-level details, the details being plugins that can be deployed and developed independently.

Summary points

  • OO is not new capabilities: encapsulation was better in C, inheritance was doable by hand, polymorphism came via function pointers.
  • OO's gift is safe, convenient polymorphism and thus dependency inversion.
  • Use it to make the UI and database plugins to the business rules, for independent deployment and development.
Terms to carry forward
  • Polymorphism as pointers to functions (vtable); plugin architecture.
  • Dependency inversion; source code dependency versus flow of control.
  • Independent deployability; independent developability.
