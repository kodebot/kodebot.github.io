Clean Architecture 6: Functional Programming

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 6. Own-words digest with short attributed quotes. Previous: Clean Architecture 5: Object-Oriented Programming. Next: Clean Architecture 7: SRP, the Single Responsibility Principle.

Takeaways
  • Functional programming rests on Alonzo Church's lambda calculus (1930s); its key property is that variables do not vary (immutability).
  • All race conditions, deadlocks and concurrent update problems are due to mutable variables. Immutability removes them, but is practical only with compromises.
  • Compromises: segregate mutability (immutable components plus protected mutable ones, using transactional memory) and event sourcing (store transactions, not state).
  • The three paradigms are disciplines on direct control transfer, indirect control transfer and assignment; none added power. Software is still sequence, selection, iteration and indirection.

6.1 Squares of integers

  • The concepts predate programming itself, strongly based on Alonzo Church's lambda calculus (1930s). To explain it, take a problem: print the squares of the first 25 integers. In Java:
public class Squint {
    public static void main(String args[]) {
        for (int i = 0; i < 25; i++)
            System.out.println(i * i);
    }
}
  • In Clojure (a Lisp derivative and functional):
(println (take 25 (map (fn [x] (* x x)) (range))))
  • Annotated:
    • println prints
    • take 25 takes the first 25
    • map (fn [x] (* x x)) squares
    • (range) is the integers. In Lisp you call a function by putting it in parentheses
    • (fn [x] (* x x)) is an anonymous function computing a square. Read from the innermost call: range returns a never-ending list of integers from 0
    • map calls the squaring function on each, producing a never-ending list of squares
    • take returns a list of only the first 25
    • println prints it. Only 25 elements are created because no element of a never-ending list is evaluated until accessed. Martin does not aim to teach Clojure here.
  • The point:
    • the Java program uses a mutable variable (the loop variable i, which changes state during execution)
    • the Clojure program has none: variables like x are initialised but never modified. Hence: "Variables in functional languages do not vary."

6.2 Immutability and architecture

  • Why should an architect care? The answer is "absurdly simple":
    • all race conditions, deadlock conditions and concurrent update problems are due to mutable variables. You cannot have a race condition or concurrent update problem if no variable is ever updated, and you cannot have deadlocks without mutable locks
    • Every problem in applications with multiple threads and processors cannot happen without mutable variables.
  • Architects care about concurrency (systems must be robust across threads and processors), so the question is whether immutability is practicable. With infinite storage and infinite processor speed, yes
    • without, "a bit more nuanced": yes, if certain compromises are made.

6.3 Segregation of mutability

  • A common compromise:
    • segregate the application, or the services within it, into mutable and immutable components
    • Immutable components work in a purely functional way with no mutable variables and communicate with one or more components that are not purely functional and allow variable state to change (Figure 6.1).
  • Mutating state exposes those components to all concurrency problems, so it is common to protect the mutable variables with transactional memory: it treats variables in memory like a database treats records on disk, protecting them with a transaction- or retry-based scheme (footnote: "I know... What's a disk?").
  • A simple example is Clojure's atom:
(def counter (atom 0))  ; initialize counter to 0
(swap! counter inc)     ; safely increment counter
  • counter is an atom: a special variable whose value may mutate only under disciplined conditions enforced by swap!, which takes the atom and a function computing the new value (here inc)
    • swap! uses compare and swap: read counter and pass it to inc
    • when inc returns, lock counter and compare it to the value passed in
    • if equal, store the result and release the lock
    • otherwise release the lock and retry from the beginning.
  • Atoms suit simple applications but cannot completely safeguard against concurrent updates and deadlocks when multiple dependent variables are involved
    • more elaborate facilities exist then.
  • Well-structured applications are segregated into components that do not mutate variables and those that do, with the mutated variables protected by suitable disciplines
    • Architects would be wise to push as much processing as possible into the immutable components and drive as much code as possible out of those that must allow mutation.

6.4 Event sourcing

  • Limits of storage and processing power "have been rapidly receding": billions of instructions a second and billions of bytes of RAM
    • The more memory and speed, the less we need mutable state.
  • Example:
    • a bank maintaining account balances mutates them on each deposit or withdrawal
    • Instead store only the transactions, and compute a balance by adding all transactions for the account from the beginning of time: no mutable variables
    • It sounds absurd (transactions grow without bound; infinite resources would be needed to run forever), but perhaps we need it to work only for the application's reasonable lifetime.
  • That is event sourcing (credit:
    • Greg Young): store the transactions, not the state
    • when state is needed apply all transactions from the beginning of time. Shortcuts: compute and save the state every midnight and apply only the transactions since.
  • Storage:
    • a lot is needed, but offline storage grows so fast that "trillions of bytes" are small
    • More importantly nothing is ever deleted or updated, so applications are not CRUD but CR, and with no updates or deletions there can be no concurrent update issues
    • With enough storage and processing power applications can be entirely immutable and therefore entirely functional
    • This is exactly how your source code control system works.

6.5 Conclusion

  • Structured programming is discipline imposed upon direct transfer of control
    • object-oriented programming is discipline upon indirect transfer of control
    • functional programming is discipline upon variable assignment
      • Each took something away and none added power: "What we have learned over the last half-century is what not to do."
  • The unwelcome fact:
    • software is not a rapidly advancing technology
    • The rules are the same as in 1946, when Alan Turing wrote the very first code to execute in an electronic computer; tools and hardware changed but the essence did not
    • Software is composed of sequence, selection, iteration and indirection: "Nothing more
    • Nothing less."

Summary points

  • Immutability removes the entire class of concurrency bugs; it is feasible with segregated mutability and, where affordable, event sourcing.
  • Architects should maximise immutable components and protect the rest (transactional memory).
  • The paradigms restrict; they do not add; software's essence is unchanged.
Terms to carry forward
  • Immutability; race condition, deadlock, concurrent update.
  • Segregation of mutability; transactional memory (Clojure atom, swap!).
  • Event sourcing (CR, not CRUD).
