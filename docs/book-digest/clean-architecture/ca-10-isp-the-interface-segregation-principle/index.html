Clean Architecture 10: ISP, the Interface Segregation Principle

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 10. Own-words digest. Previous: Clean Architecture 9: LSP, the Liskov Substitution Principle. Next: Clean Architecture 11: DIP, the Dependency Inversion Principle.

Takeaways
  • ISP: do not make a user depend on operations it does not use. Segregate operations into interfaces so each user depends only on what it needs.
  • Without it, in a statically typed language a user's source depends on operations it never calls, so an unrelated change forces recompilation and redeployment.
  • It looks like a language issue (dynamic languages avoid the source dependency), but the root concern is architectural: it is harmful to depend on modules that contain more than you need.
  • Example: a system that depends on a framework bound to a database inherits the database's changes and failures.

10.1 The principle and its name

  • ISP takes its name from a diagram (Figure 10.1): several users use operations of an OPS class; User1 uses only op1, User2 only op2, User3 only op3.
  • If OPS is a class in a language like Java, User1's source inadvertently depends on op2 and op3 though it does not call them
    • So a change to op2's source in OPS forces User1 to be recompiled and redeployed, although nothing it cared about changed.
  • The fix (Figure 10.2): segregate the operations into interfaces
    • In a statically typed language such as Java, User1's source then depends on U1Ops and op1 but not on OPS, so a change to OPS that User1 does not care about does not cause it to be recompiled and redeployed.

10.2 ISP and language

  • The description depends critically on language type
    • Statically typed languages like Java force programmers to write declarations that users must import, use or otherwise include
    • those declarations in source create the dependencies that force recompilation and redeployment
      • In dynamically typed languages like Ruby and Python such declarations do not exist in source
    • they are inferred at runtime, so there are no source code dependencies to force recompilation or redeployment.
  • This is "the primary reason that dynamically typed languages create systems that are more flexible and less tightly coupled than statically typed languages"
    • It might lead you to conclude that ISP is a language issue rather than an architecture issue.

10.3 ISP and architecture

  • Looking at the root motivation reveals a deeper concern:
    • it is harmful to depend on modules that contain more than you need
    • This is true for source dependencies that force unnecessary recompilation and redeployment, and at a much higher, architectural level.
  • Example (Figure 10.3): an architect wants to include a framework F in system S; F's authors bound it to a particular database D
    • So S depends on F, which depends on D
    • If D has features F does not use (and so S does not care about), changes to those features can force the redeployment of F and therefore of S
    • Worse, a failure of one of D's features may cause failures in F and S.

10.4 Conclusion

  • "Depending on something that carries baggage that you don't need can cause you troubles that you didn't expect." The idea is explored further with the Common Reuse Principle in Chapter 13, "Component Cohesion".

Summary points

  • Users should depend only on the operations they use; segregate fat interfaces.
  • In static languages the cost is recompilation and redeployment; in all systems it is exposure to unrelated change and failure.
  • Architecturally: avoid dependencies on frameworks and modules that carry baggage you do not need.
Terms to carry forward
  • ISP; fat interface; segregated interfaces (U1Ops).
  • Static versus dynamic typing and source dependencies; baggage.
