Clean Architecture 12: Components

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 12. Own-words digest. Previous: Clean Architecture 11: DIP, the Dependency Inversion Principle. Next: Clean Architecture 13: Component Cohesion.

Takeaways
  • Components are the units of deployment: the smallest entities that can be deployed (jar, gem, DLL; in all languages, "the granule of deployment").
  • Well-designed components stay independently deployable and so independently developable, however they are finally packaged.
  • History: non-relocatable programs and library source, then relocatable binaries, the linking loader, the separate linker, and finally fast dynamic linking, which made the component plugin architecture a casual default after about 50 years.

12.1 What a component is

  • Components are the units of deployment.
    • In Java they are jar files, in Ruby gem files, in .NET DLLs
    • in compiled languages aggregations of binary files, in interpreted languages aggregations of source files. In all languages they are the granule of deployment.
  • They can be linked into a single executable, aggregated into a single archive such as a .war, or deployed independently as dynamically loaded plugins (.jar, .dll, .exe)
    • However deployed, well-designed components always retain the ability to be independently deployable and therefore independently developable.

12.2 A brief history of components

  • Early years:
    • programmers controlled the memory location and layout of programs
    • one of the first lines was the origin statement giving the load address
      • Martin's example is a PDP-8 program with a subroutine GETSTR that reads a string from the keyboard into a buffer, plus a small unit-test program
    • the *200 at the start makes the compiler generate code loaded at address 200 (octal). Programs were not relocatable.
  • Libraries were kept in source: programmers included the library functions' source with their application code and compiled it all as one program (footnote: Martin's first employer kept several dozen decks of subroutine library source on a shelf and you slapped one onto the end of your deck).
  • The problem:
    • devices were slow and memory expensive and limited, so compilers made several passes over the source and had to re-read it from slow devices each time
    • Compiling a large program could take hours, and the larger the function library the longer it took.
  • First fix:
    • compile the function library separately and load the binary at a known address (say 2000 octal), creating a symbol table for the library compiled with the application
    • To run, load the binary library first (footnote: most old machines used core memory, which survived power-off, so the library was often left loaded for days), then the application (Figure 12.1).
  • This worked while the application fitted between 0000 and 1777 octal
    • Soon applications outgrew it and had to be split into two address segments, jumping around the library (Figure 12.2)
    • As the library grew it exceeded its bounds and needed more space (near 7000 octal): fragmentation that would continue as memory grew
    • "Clearly, something had to be done."

12.3 Relocatability

  • The solution:
    • relocatable binaries. The compiler output binary code that a smart loader could place in memory
    • the code was instrumented with flags telling the loader which parts to alter for the chosen address (usually adding the start address to memory references)
      • Programmers could now tell the loader where to load the library and the application
    • the loader accepted several binary inputs and loaded them one after another, relocating as it went, so only needed functions were loaded.
  • The compiler also emitted function names as metadata:
    • a call to a library function emitted the name as an external reference, a definition as an external definition
    • the loader linked references to definitions once it knew where it had loaded them. "And the linking loader was born."

12.4 Linkers

  • The linking loader let programmers divide programs into separately compilable and loadable segments: fine for small programs with small libraries. In the late 1960s and early 1970s programs got much bigger and linking loaders became too slow: libraries lived on slow magnetic tape (even disks were slow) and the loader had to read dozens or hundreds of binary libraries to resolve references
    • loading could take more than an hour.
  • So loading and linking were separated into two phases:
    • the slow linking went into a separate application, the linker, whose output (a linked relocatable) a relocating loader could load very quickly
    • Programmers could prepare an executable with the slow linker and load it fast at any time.
  • The 1980s:
    • C and other high-level languages
    • programs of hundreds of thousands of lines were common. .c files were compiled to .o files and fed to the linker
    • compiling each module was fast, all of them took a while, and the linker more
      • Turnaround was an hour or more again
      • Through the 1960s, 1970s and 1980s every speed-up was defeated by program growth: Murphy's law of program size: "Programs will grow to fill all available compile and link time."
  • Then Moore (footnote:
    • Moore's law: computer speed, memory and density double every 18 months
    • held from the 1950s to 2000, then stopped cold for clock rates) won the late-1980s battle: disks shrank and became significantly faster, RAM so cheap that much disk data was cached, clock rates rose from 1 MHz to 100 MHz. By the mid-1990s link time was shrinking faster than programs grew, often to seconds, making a linking loader feasible again for small jobs.
  • This was the era of Active-X, shared libraries and the beginnings of .jar files: linking at load time, joining several .jar files or shared libraries in seconds. "And so the component plugin architecture was born." Today we routinely ship .jar files, DLLs or shared libraries as plugins: a Minecraft mod is a custom .jar in a folder
    • Resharper plugs into Visual Studio as DLLs.

12.5 Conclusion

  • These dynamically linked files that can be plugged together at runtime are the software components of our architectures
    • It took 50 years, but a component plugin architecture can now be the casual default rather than a herculean effort.

Summary points

  • A component is a unit of deployment; good ones are independently deployable and developable.
  • History: relocatability, linkers and faster hardware turned plug-in components from impossible to ordinary.
  • The next chapters ask how to group classes into components (cohesion) and how components relate (coupling).
Terms to carry forward
  • Component (jar, gem, DLL); granule of deployment.
  • Relocatable binary; linking loader; linker; Murphy's law of program size.
  • Component plugin architecture.
