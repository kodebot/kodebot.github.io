Clean Architecture 13: Component Cohesion

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 13. Own-words digest. Previous: Clean Architecture 12: Components. Next: Clean Architecture 14: Component Coupling.

Takeaways
  • Which classes belong in which component has usually been decided ad hoc. Three principles guide it: REP (Reuse/Release Equivalence), CCP (Common Closure) and CRP (Common Reuse).
  • REP: "The granule of reuse is the granule of release." CCP: gather what changes together; it is SRP for components. CRP: do not force users to depend on things they do not need; it is the generic form of ISP.
  • REP and CCP are inclusive (bigger components); CRP is exclusive (smaller). Architects balance the tension, and the balance shifts over time from develop-ability toward reusability.

13.1 The three principles

  • "Which classes belong in which components? This is an important decision" and has been made "in an ad hoc manner based almost entirely on context"
    • Three principles of component cohesion: REP, CCP and CRP.

13.2 REP: the Reuse/Release Equivalence Principle

  • "The granule of reuse is the granule of release." The last decade brought module management tools (Maven, Leiningen, RVM), because a vast number of reusable components and libraries exist: "the age of software reuse", fulfilling one of the oldest promises of the OO model.
  • REP seems obvious in hindsight:
    • people who want to reuse components cannot, and will not, unless they are tracked through a release process and given release numbers
    • Not only to ensure compatibility between reused components: developers need to know when new releases come and what changes they bring, and may decide, from the changes, to stay on the old release
    • So the release process must produce notifications and release documentation for informed decisions.
  • Design meaning:
    • the classes and modules in a component must form a cohesive group with an overarching theme or purpose, not a random hodgepodge. Another view: classes grouped into a component should be releasable together
    • sharing a version number, release tracking and release documentation should make sense to author and users.
  • That is "weak advice" (waving hands):
    • it is hard to explain the glue precisely
    • But violations are easy to detect because they do not "make sense": "your users will know, and they won't be impressed with your architectural skills"
    • The weakness is compensated by CCP and CRP, which strongly define REP, in a negative sense.

13.3 CCP: the Common Closure Principle

  • **Gather into components those classes that change for the same reasons and at the same times
    • Separate into different components those classes that change at different times and for different reasons.**
  • It is SRP restated for components: SRP says a class should not have multiple reasons to change; CCP says a component should not.
  • For most applications maintainability matters more than reusability
    • If code must change you want all changes in one component rather than spread over many (footnote: see "The Kitty Problem" in Chapter 27)
    • Changes confined to one component mean only that one is redeployed; components not depending on it need not be revalidated or redeployed.
  • If two classes are so tightly bound, physically or conceptually, that they always change together, they belong in the same component: it minimises the workload of releasing, revalidating and redeploying.
  • It is closely tied to OCP:
    • CCP addresses "closure" in OCP's sense
    • Because 100% closure is unattainable, closure must be strategic: design classes closed to the most common kinds of change you expect or have seen
    • CCP amplifies this by gathering into one component classes closed to the same types of change, so a requirement change has a good chance of touching a minimal number of components.
  • Similarity with SRP:
    • SRP separates methods into different classes if they change for different reasons; CCP separates classes into different components if they change for different reasons
    • The sound bite: **"Gather together those things that change at the same times and for the same reasons
    • Separate those things that change at different times or for different reasons."**

13.4 CRP: the Common Reuse Principle

  • "Don't force users of a component to depend on things they don't need." Classes and modules that tend to be reused together belong in the same component
    • Classes are seldom reused alone: reusable classes collaborate with others in the reusable abstraction, with lots of dependencies on each other
    • Example: a container class and its iterators, reused together because tightly coupled.
  • CRP also says which classes not to keep together. When one component uses another a dependency exists
    • even if it uses a single class of the used component, it still depends on the whole component. Every change to the used component will likely force changes in the using one
    • even with no changes needed, it will likely be recompiled, revalidated and redeployed, even if it does not care about the change.
  • So when you depend on a component you want to depend on every class in it: classes in a component should be inseparable (impossible to depend on some and not others), or you redeploy more than necessary and waste effort
    • Hence CRP tells more about which classes shouldn't be together: classes not tightly bound should not share a component.
  • Relation to ISP:
    • CRP is the generic version of ISP
    • ISP advises not to depend on classes with methods you do not use; CRP advises not to depend on components with classes you do not use
    • Single sound bite: "Don't depend on things you don't need."

13.5 The tension diagram

  • The three principles tend to fight each other. REP and CCP are inclusive (make components larger); CRP is exclusive (makes them smaller). Good architects resolve the tension.
  • Figure 13.1 (a tension diagram, idea credited to Tim Ottinger): the edges describe the cost of abandoning the principle on the opposite vertex.
    • An architect focused only on REP and CRP finds too many components impacted by simple changes.
    • One focused too strongly on CCP and REP generates too many unneeded releases.
  • A good architect finds a position in the triangle that meets the team's current concerns while knowing they will change: early in a project CCP is much more important than REP, since develop-ability beats reuse
    • Projects tend to start on the right-hand side (sacrificing only reuse) and slide left as the project matures and others draw from it
    • So component structure varies with time and maturity, and "has more to do with the way that project is developed and used, than with what the project actually does".

13.6 Conclusion

  • Cohesion was once seen simply as a module performing one, and only one, function
    • the three principles describe a much more complex variety. Grouping classes means weighing reusability against develop-ability and balancing with the application's needs: "nontrivial", and dynamic: the partitioning that is right today may not suit next year, so component composition will "jitter and evolve" as focus moves from develop-ability to reusability.

Summary points

  • REP: release what you reuse; components are cohesive, versioned, documented.
  • CCP: same reasons and times of change in one component (SRP for components).
  • CRP: inseparable classes only; do not drag in unneeded dependencies (ISP for components).
  • Balance the three; the balance shifts with project maturity.
Terms to carry forward
  • REP, CCP, CRP; granule of reuse and release.
  • Inclusive versus exclusive principles; cohesion tension diagram.
  • "Don't depend on things you don't need."
