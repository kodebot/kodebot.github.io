Clean Architecture 14: Component Coupling

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 14. Own-words digest. Previous: Clean Architecture 13: Component Cohesion. Next: Clean Architecture 15: What Is Architecture?.

Takeaways
  • Three principles govern relationships between components, balancing develop-ability against logical design: ADP (Acyclic Dependencies), SDP (Stable Dependencies) and SAP (Stable Abstractions).
  • ADP: no cycles in the component dependency graph; break them with DIP or a new component. The structure evolves (it "jitters") and is not designed top-down.
  • SDP: depend in the direction of stability, measured by I = Fan-out / (Fan-in + Fan-out); SAP: a component should be as abstract as it is stable (A = Na / Nc).
  • Plot components on the I/A graph; aim for the Main Sequence, avoid the Zones of Pain and Uselessness; D = |A + I - 1| measures distance. Metrics are "imperfect, at best".

14.1 The Acyclic Dependencies Principle

  • "Allow no cycles in the component dependency graph." The forces on component structure are technical, political and volatile.
  • The morning after syndrome:
    • you get things working, go home, and next morning they do not, because somebody stayed later and changed something you depend on
    • It occurs where many developers modify the same source files
      • on small projects it is minor, but as project and team grow it becomes "nightmarish": weeks may pass without a stable build as everyone keeps changing code to fit the last change
    • Two solutions evolved, both from the telecommunications industry: the weekly build and the ADP.

The weekly build

  • Common in medium-sized projects:
    • developers ignore each other for the first four days, working on private copies, then on Friday integrate and build
    • Advantage: living in an isolated world four days in five
    • Disadvantage: a large integration penalty on Friday
    • As the project grows, integration overflows into Saturday, then starts on Thursday, creeping toward mid-week
      • the duty cycle of development versus integration falls and so does efficiency, until managers move to a biweekly build, and so on
    • To stay efficient the schedule keeps lengthening, which increases project risk: integration and testing get harder and the team loses rapid feedback.

Eliminating dependency cycles

  • The solution:
    • partition the development environment into releasable components, units of work for a developer or team
    • When a component works it is released with a release number into a directory others use, and the owners keep changing a private copy while everyone else uses the released version
    • Other teams decide whether and when to adopt each new release
    • So no team is at the mercy of others; integration happens in small increments, with no point where everyone must integrate everything.
  • It works only if you manage the dependency structure: no cycles. With cycles, the morning after syndrome cannot be avoided.
  • Figure 14.1
    • (a typical component diagram): components are nodes and dependencies directed edges
    • whichever component you start from you cannot follow dependencies back to it: a directed acyclic graph (DAG).
    • A new Presenters release affects whoever depends on it (follow arrows backward): View and Main, who decide when to integrate.
    • Releasing Main affects nobody ("they don't know about Main").
    • To test Presenters you build it with the Interactors and Entities versions it uses; nothing else.
    • A whole-system release goes bottom up: Entities first, then Database and Interactors, then Presenters, View, Controllers, Authorizer, and Main last: "We know how to build the system because we understand the dependencies between its parts."

The effect of a cycle

  • A new requirement makes the User class in Entities use the Permissions class in Authorizer (Figure 14.2): a cycle
    • Database must now be compatible with Authorizer, which depends on Interactors: much harder to release
    • Entities, Authorizer and Interactors become in effect one large component: all their developers suffer the morning after syndrome because they must use exactly the same release of each other's components
    • Testing Entities now requires building and integrating Authorizer and Interactors.
  • This is why a simple unit test sometimes drags in so many libraries: cycles make components hard to isolate, unit testing and releasing become error-prone, and build issues grow geometrically with the number of modules. It can be hard to work out the build order
    • "there probably is no correct order", causing nasty problems in languages like Java that read declarations from compiled binaries.

Breaking the cycle

  • It is always possible to break a cycle and restore a DAG, by:
    1. DIP: create an interface with the methods User needs, put it in Entities, and have Authorizer inherit it: this inverts the Entities-to-Authorizer dependency (Figure 14.3).
    2. A new component that both depend on: move the classes both need into it (Figure 14.4).
  • The "jitters": the second solution means the structure is volatile under changing requirements: as an application grows the dependency structure jitters and grows, so monitor for cycles and break them, sometimes by creating new components.

Top-down design

  • "The component structure cannot be designed from the top down": it is not among the first things designed but evolves as the system grows and changes
    • This is counterintuitive:
      • large-grained groupings are expected to be high-level functional decompositions, yet component dependency diagrams have little to do with describing the application's function
      • they are "a map to the buildability and maintainability" of the application
    • With no software yet there is nothing to build or maintain, so no such map
    • As modules accumulate we need to manage dependencies to avoid the morning after syndrome, and to localise changes we attend to SRP and CCP.
  • A key concern is isolation of volatility:
    • components that change frequently and capriciously must not affect stable ones (cosmetic GUI changes should not hit business rules; report changes should not hit the highest-level policies)
    • The graph is created and moulded by architects to protect stable high-value components from volatile ones
    • As the application grows, CRP shapes components; as cycles appear, ADP is applied and the graph jitters and grows
    • Designing it before any classes would likely "fail rather badly": you would not know about common closure or reusable elements and would almost certainly create cycles.

14.2 The Stable Dependencies Principle

  • "Depend in the direction of stability."
    • Designs cannot be completely static; CCP makes components sensitive to some changes and immune to others, and some are designed to be volatile
    • A component we expect to be volatile should not be depended on by a component that is difficult to change, or it becomes hard to change too
    • It is the "perversity of software" that a module designed to be easy to change can be made hard to change by someone hanging a dependency on it, without a line of its source changing
    • SDP ensures easy-to-change modules are not depended on by harder-to-change ones.

Stability

  • Stand a penny on its side:
    • it stays that way until disturbed, yet "unstable". So stability is not directly about frequency of change: per Webster's "not easily moved", it is the amount of work required to make a change
    • the penny is unstable (little work to topple), a table is stable.
  • Many factors make a component hard to change (size, complexity, clarity) but Martin focuses on one sure way: make lots of other components depend on it
    • A component with many incoming dependencies is very stable because reconciling a change with all its dependents is a lot of work.
  • Figure 14.5: X has three dependents ("three good reasons not to change"): responsible
    • it depends on nothing so no outside influence: independent
      • Figure 14.6: Y has no dependents (irresponsible) and three dependencies (changes can come from three sources): dependent
    • very unstable.

Stability metrics

  • Fan-in:
    • incoming dependencies: the number of classes outside the component that depend on classes inside
    • Fan-out: outgoing: classes inside that depend on classes outside
    • I (Instability) = Fan-out / (Fan-in + Fan-out), in [0, 1]: I = 0 maximally stable, I = 1 maximally unstable
    • (Earlier publications called Fan-out and Fan-in Efferent and Afferent couplings, Ce and Ca: "just hubris".)
  • Example (Figure 14.7): component Cc has three outside classes depending on it (Fan-in 3) and one outside class it depends on (Fan-out 1): I = 1/4. In C++ dependencies appear as #include (easiest with one class per source file)
    • in Java count import statements and qualified names.
  • I = 1:
    • Fan-in 0 and Fan-out > 0: irresponsible and dependent, as unstable as it gets: no reason not to change, plenty of reason to
    • I = 0: Fan-in > 0 and Fan-out 0: responsible and independent, as stable as it gets.
  • SDP: the I of a component should be larger than the I of the components it depends on; I metrics should decrease in the direction of dependency.

Not all components should be stable

  • If everything were maximally stable the system would be unchangeable
    • Design so some are unstable and some stable: Figure 14.8, three components with the changeable ones on top depending on the stable one below
    • Convention: any arrow pointing up violates SDP (and ADP).
  • Figure 14.9: Flexible (designed easy to change, so unstable) has had a dependency hung on it from Stable (I much smaller): a change to Flexible now forces dealing with Stable and all its dependents
    • Suppose a class U in Stable uses class C in Flexible (Figure 14.10)
    • Fix with DIP (Figure 14.11): create an interface US in a new component UServer declaring what U needs
    • make C implement it. Both components now depend on UServer, which is very stable (I = 0), while Flexible keeps its needed instability (I = 1)
    • "all the dependencies now flow in the direction of decreasing I".
  • Abstract components:
    • a component with only an interface and no executable code looks strange but is a common and necessary tactic in statically typed languages like Java and C#: stable, so ideal targets for less stable components
    • In dynamic languages (Ruby, Python) they do not exist, nor the dependencies targeting them: dependency structures are much simpler since inversion needs no declared or inherited interfaces.

14.3 The Stable Abstractions Principle

  • "A component should be as abstract as it is stable."
  • Where does high-level policy go?
    • Some software should change rarely: high-level architecture and policy decisions. So it belongs in stable components (I = 0)
    • unstable components (I = 1) hold only volatile code. But policy in stable components is hard to change, making the architecture inflexible
    • how can a maximally stable component withstand change? Via OCP: classes flexible enough to extend without modification: abstract classes.
  • SAP
    • sets a relationship between stability and abstractness: a stable component should be abstract so stability does not prevent extension
    • an unstable component should be concrete so its instability lets the concrete code change easily. A stable component should consist of interfaces and abstract classes
    • stable and extensible components are flexible and do not over-constrain the architecture.
  • SDP + SAP = DIP for components:
    • SDP says dependencies run toward stability, SAP says stability implies abstraction, so dependencies run toward abstraction. DIP deals with classes, where there are "no shades of gray" (abstract or not)
    • SDP and SAP deal with components, which can be partially abstract and partially stable.

Measuring abstraction

  • A = Na / Nc,
    • where Nc is the number of classes in the component and Na the number of abstract classes and interfaces
    • A ranges from 0 (no abstract classes) to 1 (only abstract classes).

The Main Sequence

  • Plot A on the vertical axis and I on the horizontal (Figure 14.12)
    • The maximally stable and abstract components are at the upper left (0, 1); maximally unstable and concrete ones at the lower right (1, 0)
    • Not every component sits at a corner: for example one abstract class often derives from another, so the derivative is abstract but has a dependency, lowering its stability
    • So there is a locus of reasonable positions, found by identifying the zones of exclusion (Figure 14.13).
  • Zone of Pain, near (0, 0):
    • highly stable and concrete: rigid: cannot be extended (not abstract) and is hard to change (stable)
    • Example: a database schema, "notoriously volatile, extremely concrete, and highly depended on" (why the OO-to-database interface is so hard and schema updates painful)
    • Also concrete utility libraries (I = 1 in a sense, but nonvolatile: String is concrete yet changing it would create chaos, so it is nonvolatile)
    • Nonvolatile components are harmless there; only volatile ones are painful, so volatility could be a third axis (Figure 14.13 shows the plane where volatility = 1).
  • Zone of Uselessness, near (1, 1):
    • maximally abstract yet no dependents: useless
    • "detritus": leftover abstract classes nobody ever implemented. A component deep in this zone contains a significant fraction of them.
  • The Main Sequence
    • is the line connecting (1, 0) and (0, 1), maximally distant from both zones (Martin borrows the term from astronomy: "arrogance")
    • A component on it is neither too abstract for its stability nor too unstable for its abstractness: depended on to the extent that it is abstract and depends on others to the extent that it is concrete
    • The best positions are the endpoints; good architects put most components there, and the rest (neither perfectly abstract nor stable) do best on or near the Main Sequence.

Distance from the Main Sequence

  • D = |A + I - 1|,
    • in [0, 1] (earlier called D′): 0 means on the Main Sequence, 1 as far as possible. Compute D for each component and re-examine those not near zero
    • You can also compute the mean and variance of D (a conforming design has both near zero) and use the variance for control limits to flag exceptional components.
  • Figure 14.14, a scatterplot: most components lie along the Main Sequence, some more than one standard deviation (Z = 1) from the mean: worth a look (very abstract with few dependents, or very concrete with many). Figure 14.15, a mock-up plotting D over time for a Payroll component: strange dependencies crept in over recent releases
    • with a control threshold at D = 0.1, the R2.1 release exceeded it, so investigate.

14.4 Conclusion

  • The metrics measure how well a design conforms to a pattern of dependency and abstraction that Martin believes is "good", reflecting experience that some dependencies are good and others bad
    • "A metric is not a god; it is merely a measurement against an arbitrary standard
    • These metrics are imperfect, at best", but he hopes they help.

Summary points

  • ADP: no cycles; break with DIP or a new component; structure evolves and is not designed top-down.
  • SDP: depend toward stability (I decreases along dependencies); SAP: stable means abstract (A).
  • Aim for the Main Sequence (D near 0) and avoid the Zones of Pain (volatile, concrete, stable) and Uselessness (abstract, unused).
Terms to carry forward
  • ADP, DAG, morning after syndrome, weekly build.
  • SDP; Fan-in, Fan-out, I; SAP; A; Main Sequence; D.
  • Zone of Pain; Zone of Uselessness; abstract component.
