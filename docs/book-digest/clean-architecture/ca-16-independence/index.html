Clean Architecture 16: Independence

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 16. Own-words digest with short attributed quotes. Previous: Clean Architecture 15: What Is Architecture?. Next: Clean Architecture 17: Boundaries, Drawing Lines.

Takeaways
  • A good architecture supports use cases and operation, maintenance, development and deployment, and it does so by decoupling and leaving options open.
  • Decouple layers (UI, application-specific rules, application-independent rules, database) and use cases (vertical slices), so things that change for different reasons change independently.
  • Decoupling mode (source, deployment or service level) is an option to keep open: do not default to services; decouple to the point a service could be formed and keep components in one address space as long as possible.
  • Beware accidental duplication: similar-looking screens, queries or records often diverge; do not eliminate them knee-jerk.

16.1 What architecture must support

  • A good architecture must support: the use cases and operation, the maintenance, the development and the deployment of the system.
  • Use cases:
    • the architecture must support the intent of the system: the first concern and first priority (a shopping cart application must support shopping cart use cases)
    • But architecture has little influence on behaviour (few behavioural options to leave open)
      • the most important thing it can do is clarify and expose behaviour so the system's intent is visible at the architectural level
    • "A shopping cart application with a good architecture will look like a shopping cart application": use cases are first-class elements visible at the top level (classes, functions or modules with prominent positions and clearly descriptive names), so developers do not hunt for behaviour (Chapter 21, "Screaming Architecture").
  • Operation:
    • a more substantial, less cosmetic role: if the system must handle 100,000 customers per second, or query big data cubes in milliseconds, the architecture must support it
    • That may mean an array of little services running in parallel on many servers, a plethora of lightweight threads sharing one process's address space, a few processes in isolated address spaces, or even a simple monolith
    • Leaving that decision open is part of a good architect's job:
      • a monolith that depends on being a monolith cannot easily move to multiple processes, threads or micro-services
      • an architecture that isolates components and does not assume how they communicate can move along the spectrum as needs change.
  • Development: here Conway's law applies: "Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure." A system built by many teams with many concerns needs an architecture that lets teams act independently without interfering: partition into well-isolated, independently developable components allocated to independent teams.
  • Deployment:
    • the goal is "immediate deployment": no dozens of little configuration scripts and property tweaks, no manually created directories or files arranged just so
    • the system is immediately deployable after build, again through proper partitioning and isolation, including the master components that tie the system together and ensure each component is started, integrated and supervised.

16.2 Leaving options open

  • A good architecture balances all these concerns with a component structure that satisfies them mutually
    • That is "pretty hard": most of the time we do not know all the use cases, operational constraints, team structure or deployment needs, and they change over the life cycle: "the goals we must meet are indistinct and inconstant
    • Welcome to the real world."
  • But some principles are relatively cheap and help partition systems into well-isolated components that leave as many options open as possible, for as long as possible
    • "A good architecture makes the system easy to change, in all the ways that it must change, by leaving options open."

16.3 Decoupling layers and use cases

  • Decoupling layers:
    • the architect does not know all the use cases but does know the system's basic intent (a shopping cart, a bill of materials, order processing)
    • Apply SRP and CCP: separate what changes for different reasons and collect what changes for the same reasons, in the context of the system's intent.
    • User interfaces
      • change for reasons unrelated to business rules
      • use cases contain both, so separate the UI portion from the business rule portion so they change independently while keeping use cases visible and clear.
    • Business rules may be closely tied to the application (input field validation) or to the domain (interest on an account, counting inventory): these change at different rates for different reasons, so separate them.
    • The database, query language and schema are technical details unrelated to rules or UI and change on their own; separate them.
    • Result: decoupled horizontal layers: UI, application-specific business rules, application-independent business rules, database.
  • Decoupling use cases:
    • the use cases themselves change for different reasons: adding an order versus deleting an order almost certainly change at different rates
    • Use cases are narrow vertical slices cutting through the horizontal layers (each uses some UI, some application-specific and application-independent rules and some database)
    • So separate the UI of add-order from that of delete-order, and likewise their business rules and database, "all the way down" the vertical height
    • If you decouple what changes for different reasons, new use cases can be added without interfering with old ones, especially if each use case uses a different part of the UI and database.
  • Decoupling mode:
    • the same decoupling also helps operation: separated aspects mean high-throughput ones are likely already apart from low-throughput ones
    • with UI and database separate from the business rules they can run on different servers and the higher-bandwidth ones be replicated
      • But to take advantage the decoupling needs the right mode: components cannot depend on sharing an address space
    • they must be independent services communicating over a network
      • Many call them "services" or "micro-services" (by a vague line count), and an architecture based on services is a service-oriented architecture (SOA)
      • Martin is not saying SOA or micro-services are best: sometimes components must be separated all the way to the service level, and the decoupling mode is one of the options to leave open.
  • Independent develop-ability:
    • with strongly decoupled components team interference drops: if the business rules do not know the UI, a UI team cannot much affect a business-rules team
    • if use cases are decoupled, the addOrder team will not interfere with the deleteOrder team. The architecture supports any team organisation: feature teams, component teams, layer teams or others.
  • Independent deployability:
    • done well, you can hot-swap layers and use cases in running systems
    • adding a use case could be as simple as adding a few jar files or services and leaving the rest alone.

16.4 Duplication

  • Architects fall into a trap through fear of duplication
    • Duplication is generally bad and real duplication should be removed
    • But there are two kinds:
      • true duplication, where every change to one instance requires the same change to every duplicate
      • and false or accidental duplication: apparently duplicated code that evolves along different paths (different rates, different reasons) and "a few years" later looks very different.
  • Two use cases with very similar screen structures tempt architects to share the code
    • Is it true duplication? "Most likely it is accidental": the screens will probably diverge, and unifying them makes separating them later a challenge
    • When separating use cases vertically you will be tempted to couple them for similar screens, algorithms, queries or schemas: "Resist the temptation to commit the sin of knee-jerk elimination of duplication
    • Make sure the duplication is real."
  • Likewise when separating layers horizontally you may notice a database record's structure resembles a screen view and be tempted to pass the record up to the UI instead of creating a view model and copying the elements across
    • This is almost certainly accidental duplication: creating the view model is little effort and keeps the layers decoupled.

16.5 Decoupling modes (again)

  • Layers and use cases can be decoupled at three levels:
    • Source level:
      • control dependencies between source modules so changes in one do not force changes or recompilation of others (for example Ruby Gems). Components share one address space and communicate by simple function calls
      • a single executable is loaded: often called a monolithic structure.
    • Deployment level:
      • control dependencies between deployable units (jar files, DLLs, shared libraries) so source changes in one module do not force others to be rebuilt and redeployed
      • Many components may still share an address space and call functions
        • others live in other processes on the same processor, using interprocess communication, sockets or shared memory
      • The key point is that they are independently deployable units (jars, Gems, DLLs).
    • Service level: reduce dependencies to data structures and communicate solely through network packets, so every execution unit is entirely independent of source and binary changes to others (services or micro-services).
  • What is the best mode?
    • It is hard to know early and the optimum may change as the project matures
    • A system comfortable on one server may later need components on separate servers: source-level decoupling may suffice at first, later deployable units or services.
  • One popular solution:
    • decouple at the service level by default
    • Problems: it is expensive (development time and system resources: "dealing with service boundaries where none are needed is a waste of effort, memory, and cycles"; the last two are cheap "but the first is not") and encourages coarse-grained decoupling: "no matter how 'micro' the micro-services get, the decoupling is not likely to be fine-grained enough".
  • Martin's preference:
    • push the decoupling to the point where a service could be formed should it become necessary, but leave the components in the same address space as long as possible, keeping the service option open
      • Start with source-level separation (maybe good enough for the project's lifetime)
    • if deployment or development issues arise move some to the deployment level
    • as issues grow, carefully choose which deployable units become services and shift gradually
      • Operational needs may later decline, so what needed service-level decoupling may need only deployment or source level.
  • A good architecture lets a system be born as a monolith deployed as a single file, then grow into independently deployable units, then services or micro-services, and later reverse that progression back to a monolith
    • It protects the majority of the source code from these changes and leaves the decoupling mode open so large deployments can use one mode and small deployments another.

16.6 Conclusion

  • It is tricky, and Martin is not saying the mode change should be a trivial configuration option (though sometimes appropriate)
    • The decoupling mode is one of the things likely to change with time, and "a good architect foresees and appropriately facilitates those changes".

Summary points

  • Support use cases, operation, development, maintenance and deployment through decoupling and open options.
  • Layers (UI, app rules, domain rules, database) and use case slices are the natural decoupling axes; mind accidental duplication.
  • Keep the decoupling mode open (source, deployment, service); services only when the need is proven.
Terms to carry forward
  • Conway's law; immediate deployment; decoupling layers and use cases.
  • Accidental duplication; view model.
  • Decoupling mode: source, deployment, service.
