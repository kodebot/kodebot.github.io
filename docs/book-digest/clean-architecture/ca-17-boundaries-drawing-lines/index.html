Clean Architecture 17: Boundaries, Drawing Lines

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 17. Own-words digest with short attributed quotes. Previous: Clean Architecture 16: Independence. Next: Clean Architecture 18: Boundary Anatomy.

Takeaways
  • Software architecture is the art of drawing lines (boundaries) that separate software elements and restrict those on one side from knowing about those on the other. Early lines defer decisions and keep them from polluting the core business logic.
  • The enemy is coupling to premature decisions (frameworks, databases, web servers, utility libraries, dependency injection): decisions unrelated to the use cases.
  • Draw lines between things that matter and things that do not: business rules versus GUI and database. Dependency arrows point toward the business rules, so the UI and database are plugins.
  • Boundaries sit on an axis of change (SRP again); the arrangement applies DIP and the Stable Abstractions Principle.

17.1 Why draw lines: coupling to premature decisions

  • Boundaries separate software elements and restrict those on one side from knowing about those on the other
    • Some are drawn very early, even before any code; others much later
    • Early ones are drawn to defer decisions for as long as possible and to keep them from polluting the core business logic.
  • The architect's goal is to minimise the human resources required to build and maintain the system
    • What saps that people-power? Coupling, and especially coupling to premature decisions.
  • Premature decisions
    • are those with nothing to do with the business requirements (the use cases): frameworks, databases, web servers, utility libraries, dependency injection and the like
    • A good architecture renders these ancillary and deferrable, does not depend on them, and lets them be made "at the latest possible moment, without significant impact".

17.2 A couple of sad stories

  • Company P
    • (a warning about premature decisions)
    • In the 1980s its founders wrote a simple monolithic desktop application that grew through the 1990s into a popular desktop GUI product
    • In the late 1990s the web emerged and customers demanded a web version; P hired "a bunch of hotshot twenty-something Java programmers" to webify it.
    • They adopted a rich three-tiered "architecture" (footnote:
      • three-tier is "not an architecture
      • it's a topology", the kind of decision a good architecture defers) distributed over server farms: servers for the GUI, middleware and database. Every domain object had three instantiations (one per tier) and method invocations between tiers became serialised, marshalled objects.
    • A simple feature such as adding a field to a record meant changing the classes in all three tiers and several inter-tier messages: data travelled both ways, so four message protocols were needed, each with a sending and a receiving side: eight protocol handlers
      • In all: three executables, each with three updated business objects, four new messages and eight new handlers, plus all the instantiation, serialisation, marshalling, message building and parsing, socket communication, timeout managers and retry scenarios needed for the simplest feature.
    • During development there was no server farm:
      • they ran the three executables as three processes on one machine for years, yet kept all that machinery
      • The irony: P never sold a system that required a server farm: every deployment was a single server, still running all of it "in anticipation of a server farm that never existed"
      • The premature decision "multiplied the development effort enormously"
      • The story, Martin says, is a superposition of many places.
  • Company W (a worse fate): a local business managing fleets of company cars hired an "Architect" who wanted a full-blown, enterprise-scale service-oriented "ARCHITECTURE": a huge domain model of all the business's "objects" and a suite of services to manage them, "putting all the developers on a path to Hell".
    • Example:
      • to add a contact person's name, address and phone number to a sales record, look up the ContactService ID in the ServiceRegistry, send it a CreateContact message with dozens of required fields the programmer did not have (so fake the data), then put the new contact's ID into the sales record and send UpdateContact to the SaleRecordService
      • Testing meant starting every needed service one by one, plus the message bus and a BPel server, with propagation delays as messages bounced through queues
      • New features meant coupling across services, "the sheer volume of WSDLs" to change and the redeployments they forced: "Hell starts to seem like a nice place by comparison."
    • "There's nothing intrinsically wrong with a software system that is structured around services." The error was the premature adoption and enforcement of a suite of tools that promised SOA: a massive suite of domain object services
      • the cost: "person-hours in droves flushed down the SoA vortex".

17.3 FitNesse: an architectural success

  • Micah and Robert Martin started FitNesse in 2001:
    • a simple wiki wrapping Ward Cunningham's FIT tool for writing acceptance tests. This was before Maven "solved" the jar file problem
    • Martin insisted users download only one jar (rule: "Download and Go"), which drove many decisions.
  • Own web server:
    • one of the first decisions was to write their own web server for FitNesse's needs
    • It sounds absurd (plenty of open source servers existed in 2001) but a bare-bones server is simple and it let them postpone any web framework decision (footnote: years later they slipped the Velocity framework in).
  • Avoiding the database: they had MySQL in mind but purposely delayed it with a design making the decision irrelevant: an interface between all data accesses and the repository, an interface named WikiPage with methods to find, fetch and save pages.
    • At first the methods were stubbed in MockWikiPage; for three months they worked only on translating wiki text to HTML, which needed no storage.
    • When stubs were insufficient they made InMemoryPage, managing a hash table of pages in RAM, which let them write feature after feature for a full year: the whole first version worked (create pages, links, wiki formatting, running tests with FIT) but could not save any work.
    • For persistence they thought again of MySQL but saw it would be easy to write the hash tables to flat files: FileSystemWikiPage
      • Three months later the flat files were judged good enough and they abandoned MySQL: "We deferred that decision into nonexistence and never looked back."
    • A customer later wanted the wiki in MySQL
      • shown the WikiPage architecture, he came back a day later with the whole system working in MySQL by writing a MySqlWikiPage derivative. They bundled it for a while
      • nobody else used it, so they dropped it, as did the customer.
  • Lesson:
    • an early line between business rules and databases meant the business rules knew only simple data access methods
    • It allowed deferring the database for well over a year, trying the file system, changing direction for a better solution, and still moving in the original MySQL direction when someone wanted it
    • For 18 months there was no database, so no schema, query, server, password or connection-time issues, and all tests ran fast
    • "Drawing the boundary lines helped us delay and defer decisions, and it ultimately saved us an enormous amount of time and headaches
    • And that's what a good architecture should do."

17.4 Which lines, and when?

  • Draw lines between things that matter and things that don't.
    • The GUI does not matter to the business rules, so a line
    • the database does not matter to the GUI, so a line
    • the database does not matter to the business rules, so a line.
  • Many reject that last statement, taught that the database is inextricably connected to the business rules or even embodies them
    • Martin: misguided (a later chapter shows why): the database is a tool the business rules use indirectly
    • They need not know the schema, the query language or other details; they only need a set of functions to fetch or save data, so the database goes behind an interface.
  • Figure 17.1:
    • BusinessRules use DatabaseInterface to load and save data
    • DatabaseAccess implements the interface and directs the actual Database. (Classes are symbolic: a real system has many of each following the same pattern.)
  • Figure 17.2:
    • the boundary is drawn across the inheritance relationship, just below DatabaseInterface
    • The two arrows leaving DatabaseAccess point away from it: none of the other classes knows it exists.
  • Figure 17.3,
    • at component level: the Database component knows about BusinessRules; BusinessRules do not know about the Database
    • So the DatabaseInterface classes live in the BusinessRules component, and the DatabaseAccess classes in the Database component
    • The direction matters: the Database does not matter to the BusinessRules, but the Database cannot exist without them
    • Why? The Database component holds the code that translates the BusinessRules' calls into the database's query language, and that translation code knows about the BusinessRules.
  • So the BusinessRules could use any kind of database: Oracle, MySQL, Couch, Datomic or flat files; the decision can be deferred while you write and test business rules.

17.5 What about input and output?

  • Developers and customers confuse the GUI with the system, defining it in terms of the GUI and expecting to see it work immediately
    • They miss a critical principle: "The IO is irrelevant." Example: a video game feels dominated by screen, mouse, buttons and sounds, but behind it is a model (data structures and functions) that does not need the interface and would model all the game's events without ever displaying anything
    • The interface does not matter to the model, the business rules.
  • So again a boundary between GUI and BusinessRules (Figure 17.4), and the less relevant component depends on the more relevant one: the arrows show which component knows about, and therefore cares about, the other: the GUI cares about the BusinessRules
    • The GUI could be replaced by any other interface and the rules would not care.

17.6 Plugin architecture

  • These two decisions form a pattern for adding other components: the same pattern as systems accepting third-party plugins
    • "The history of software development technology is the story of how to conveniently create plugins to establish a scalable and maintainable system architecture." The core business rules are kept separate from, and independent of, the components that are optional or can take many forms (Figure 17.5).
  • Because the UI is a plugin, many kinds can plug in:
    • web, client/server, SOA, console or any other
    • The database as plugin can be replaced by any SQL, NoSQL or file system database
    • Replacements may not be trivial (a client-server UI after a web one may need the communications reworked), but starting from a plugin structure at least makes the change practical.

17.7 The plugin argument

  • ReSharper and Visual Studio
    • are made by completely different teams in different companies: JetBrains (Russia) and Microsoft (Redmond)
    • Which can damage the other? The dependency structure answers (Figure 17.6): ReSharper's source depends on Visual Studio's, so the ReSharper team cannot disturb the Visual Studio team, but the Visual Studio team could completely disable ReSharper.
  • That deeply asymmetric relationship is what we want in our own systems: certain modules immune to others (business rules should not break when a web page format or database schema changes)
    • A plugin architecture creates firewalls across which changes cannot propagate: if the GUI plugs in to the business rules, GUI changes cannot affect them.
  • Boundaries are drawn where there is an axis of change:
    • components on one side change at different rates and for different reasons than those on the other
    • GUIs change at different times and rates than business rules
      • business rules change at different times and for different reasons than dependency injection frameworks: so boundaries between them
    • "This is simply the Single Responsibility Principle again
    • The SRP tells us where to draw our boundaries."

17.8 Conclusion

  • To draw boundaries, first partition the system into components: some are core business rules, others are plugins with necessary functions not directly related to the core
    • Then arrange the code so the arrows between components point in one direction, toward the core business: an application of the Dependency Inversion Principle and the Stable Abstractions Principle: dependency arrows point from lower-level details to higher-level abstractions.

Summary points

  • Coupling to premature decisions is what drains effort; boundaries defer those decisions.
  • Business rules depend on nothing; the database, GUI and frameworks are plugins that depend on them.
  • Draw lines on axes of change (SRP); P and W show the cost of premature architecture, FitNesse the payoff of deferral.
Terms to carry forward
  • Boundary; premature decision; plugin architecture.
  • Axis of change; asymmetric dependency (ReSharper and Visual Studio).
  • Defer decisions (FitNesse WikiPage).
