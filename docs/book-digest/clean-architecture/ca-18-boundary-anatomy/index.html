Clean Architecture 18: Boundary Anatomy

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 18. Own-words digest. Previous: Clean Architecture 17: Boundaries, Drawing Lines. Next: Clean Architecture 19: Policy and Level.

Takeaways
  • A system's architecture is its components and the boundaries between them. At runtime a boundary crossing is a function on one side calling a function on the other, passing data; the trick is managing source code dependencies.
  • Boundaries come in increasing strength: monolith (source level), deployment components, local processes, services; threads are not boundaries.
  • Stronger boundaries are costlier to cross: function calls are cheap and chatty; OS-level crossings are moderately expensive; network services are slow (tens of milliseconds to seconds).
  • Whatever the form, the dependency rule is the same: source dependencies point toward the higher-level component; lower-level components plug in.

18.1 Boundary crossing

  • "The architecture of a system is defined by a set of software components and the boundaries that separate them." At runtime a boundary crossing is nothing more than a function on one side of the boundary calling a function on the other side and passing along some data. The trick is managing the source code dependencies: when one source module changes, others may have to change or be recompiled and redeployed, and boundaries are firewalls against that change.

18.2 The dreaded monolith

  • The simplest and most common boundary has no strict physical representation: a disciplined segregation of functions and data within a single processor and a single address space, the source-level decoupling mode
    • Deployed, it is a single executable file (a statically linked C or C++ project, a set of Java class files in an executable jar, .NET binaries in one .EXE): the "so-called monolith".
  • That the boundaries are invisible at deployment does not mean they are not present and meaningful: independently developing and marshalling the components for final assembly is "immensely valuable".
  • Such architectures almost always depend on dynamic polymorphism to manage internal dependencies (footnote: static polymorphism, generics or templates, can sometimes work in monoliths, especially in C++, but it cannot protect from recompilation and redeployment the way dynamic polymorphism can)
    • That is one reason OO became so important: without it architects must fall back on the dangerous practice of function pointers, which most find too risky, so they abandon component partitioning.
  • Figure 18.1:
    • the simplest boundary crossing is a function call from a lower-level client to a higher-level service: runtime and compile-time dependencies point the same way, toward the higher-level component. The Client calls f() on the Service passing an instance of Data (<DS> = data structure)
    • the Data definition is on the called side.
  • Figure 18.2:
    • when a high-level client must invoke a lower-level service, dynamic polymorphism inverts the dependency against the flow of control: control still crosses left to right, with the high-level Client calling f() on the lower-level ServiceImpl through the Service interface
    • but all dependencies cross right to left toward the higher-level component, and the Data definition is on the calling side.
  • Even in a statically linked monolith this disciplined partitioning greatly helps development, testing and deployment: teams work independently on their components without treading on each other, and high-level components stay independent of lower-level details.
  • Communication inside a monolith is just function calls, very fast and inexpensive, so crossings can be very chatty
    • Because deployment needs compilation and static linking, components are typically delivered as source code.

18.3 Deployment components

  • The simplest physical representation of a boundary is a dynamically linked library: a .NET DLL, Java jar, Ruby Gem or UNIX shared library: the deployment-level decoupling mode
    • Deployment involves no compilation: components arrive in binary or equivalent deployable form, and deployment is just gathering the units, for example into a WAR file or even a directory.
  • Otherwise they are the same as monoliths:
    • functions generally live in the same processor and address space, and the strategies for segregating components and managing dependencies are the same (footnote: though static polymorphism is not an option)
    • Crossings are function calls, so very inexpensive: maybe a one-time hit for dynamic linking or runtime loading, but still chatty.

18.4 Threads

  • Both monoliths and deployment components can use threads, but threads are not architectural boundaries or units of deployment: they are a way to organise the schedule and order of execution, wholly inside one component or spread across many.

18.5 Local processes

  • A much stronger physical boundary:
    • created typically from the command line or an equivalent system call, a local process runs on the same processor (or set of cores) but in a separate address space
    • memory protection generally prevents shared memory (shared partitions are often used). They usually communicate through sockets or other OS facilities such as mailboxes or message queues.
  • Each local process may be a statically linked monolith or composed of dynamically linked deployment components (several monolithic processes may compile in the same components, or share deployment components)
    • "Think of a local process as a kind of uber-component": it consists of lower-level components managing their dependencies by dynamic polymorphism.
  • The segregation strategy is the same:
    • source dependencies point the same way across the boundary, always toward the higher-level component
    • So the source of higher-level processes must not contain the names, physical addresses or registry lookup keys of lower-level processes: lower-level processes should be plugins to higher-level ones.
  • Crossing involves OS calls, data marshalling and decoding, and interprocess context switches: moderately expensive, so limit chattiness carefully.

18.6 Services

  • The strongest boundary.
    • A service is a process generally started from the command line or an equivalent system call
    • Services do not depend on their physical location: two communicating services may or may not run on the same processor or multicore, and they assume all communication is over the network.
  • Crossings are very slow compared to function calls: turnaround from tens of milliseconds to seconds. Avoid chatting where possible and deal with high latency.
  • Otherwise the same rules apply as for local processes: lower-level services plug in to higher-level ones, and the source of higher-level services must not hold specific physical knowledge (such as a URI) of any lower-level service.

18.7 Conclusion

  • Most systems other than monoliths use more than one boundary strategy: a system with service boundaries may also have local process boundaries
    • indeed "a service is often just a facade for a set of interacting local processes"
    • A service or local process is almost certainly either a monolith of source components or a set of dynamically linked deployment components
    • So a system's boundaries are often a mixture of local chatty boundaries and boundaries more concerned with latency.

Summary points

  • A crossing is a function call; control the source dependency direction (toward higher level), inverting with polymorphism when needed.
  • Strength ladder: monolith, deployment components, local process, service; threads are not boundaries.
  • Cost rises with strength: chatty and cheap inside a process, latency-conscious across a network.
Terms to carry forward
  • Boundary crossing; monolith; deployment component; local process; service.
  • Dynamic versus static polymorphism; chattiness and latency.
  • Higher-level source must not name lower-level processes or URIs.
