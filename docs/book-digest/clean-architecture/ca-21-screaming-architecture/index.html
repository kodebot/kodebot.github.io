Clean Architecture 21: Screaming Architecture

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 21. Own-words digest. Previous: Clean Architecture 20: Business Rules. Next: Clean Architecture 22: The Clean Architecture.

Takeaways
  • An architecture should scream its purpose: open the top-level directories and you should see "Health Care System", not "Rails" or "Spring/Hibernate".
  • Architectures support use cases (Ivar Jacobson's Use Case Driven Approach); they are not supplied by frameworks. Frameworks are tools, not ways of life.
  • A good architecture defers and delays decisions about frameworks, databases and web servers; the web is a delivery mechanism (an IO device), a detail.
  • Result: all use cases are testable without any framework, web server or database.

21.1 What does the architecture scream?

  • Imagine blueprints of a building
    • For a single-family home you would see a front entrance, a foyer to a living room, perhaps a dining room, a kitchen near it, a dinette and a family room: "no question" it is a home: the architecture would scream "HOME"
    • For a library: a grand entrance, check-in/out clerks, reading areas, small conference rooms, and "gallery after gallery capable of holding bookshelves": it screams "LIBRARY".
  • So what does your application's architecture scream? Looking at the top-level directory structure and the source files in the highest-level package, do they scream "Health Care System", "Accounting System" or "Inventory Management System"? Or "Rails", "Spring/Hibernate" or "ASP"?

21.2 The theme of an architecture

  • Read Ivar Jacobson's Object Oriented Software Engineering, subtitled A Use Case Driven Approach: software architectures are structures that support the use cases of the system
    • As house and library plans scream the use cases of those buildings, so should the architecture of an application.
  • "Architectures are not (or should not be) about frameworks
    • Architectures should not be supplied by frameworks
    • Frameworks are tools to be used, not architectures to be conformed to. If your architecture is based on frameworks, then it cannot be based on your use cases."

21.3 The purpose of an architecture

  • Good architectures are centred on use cases
    • so architects can safely describe the structures that support them without committing to frameworks, tools and environments. House plans: the first concern is that the house is usable, not that it is brick
    • the architect takes pains so the homeowner can choose the exterior material (brick, stone or cedar) later, after the plans ensure the use cases are met.
  • A good software architecture lets decisions about frameworks, databases, web servers and other environment and tools be deferred and delayed
    • "Frameworks are options to be left open." You should not need to decide on Rails, Spring, Hibernate, Tomcat or MySQL until much later, and it should be easy to change your mind
    • A good architecture emphasises the use cases and decouples them from peripheral concerns.

21.4 But what about the web?

  • Is the web an architecture? Does delivery over the web dictate your structure? "Of course not!" The web is a delivery mechanism, an IO device, and the architecture should treat it as one
    • Delivery over the web is a detail that should not dominate the structure; the decision to deliver over the web should itself be deferred
    • The architecture should be as ignorant as possible about how it will be delivered, so you can ship it as a console app, web app, thick client or web service without undue complication or change to the fundamental architecture.

21.5 Frameworks are tools, not ways of life

  • Frameworks can be powerful and useful, and their authors "often believe very deeply" in them: examples are told from a true believer's point of view, and other authors are disciples showing "the way", often assuming an all-encompassing, let-the-framework-do-everything position
    • "This is not the position you want to take."
  • Look at each framework with a jaded eye,
    • skeptically: "Yes, it might help, but at what cost?" Ask how you should use it and how to protect yourself from it
    • think about preserving the use-case emphasis of your architecture
    • develop a strategy that prevents the framework from taking over the architecture.

21.6 Testable architectures

  • If the architecture is about use cases and frameworks are kept at arm's length, you can unit-test all the use cases without any framework in place: no web server running, no database connected
    • Entity objects should be plain old objects with no dependencies on frameworks, databases or other complications
    • use case objects coordinate the Entities
    • and all together should be testable in situ without framework complications.

21.7 Conclusion

  • The architecture should tell readers about the system, not about the frameworks used
    • For a health care system, a new programmer's first impression of the repository should be "Oh, this is a health care system." They should be able to learn all the use cases without knowing how the system is delivered
    • If they ask, "We see some things that look like models, but where are the views and controllers?", the answer: "Oh, those are details that needn't concern us at the moment
    • We'll decide about them later."

Summary points

  • Structure by use cases and domain, not by framework.
  • Treat the web and frameworks as deferred details; keep frameworks at arm's length.
  • Use cases and Entities are testable without framework, web server or database.
Terms to carry forward
  • Screaming architecture; use case driven (Jacobson).
  • Web as delivery mechanism; frameworks are tools, not ways of life.
