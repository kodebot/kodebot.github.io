Clean Architecture 25: Layers and Boundaries

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 25. Own-words digest. Previous: Clean Architecture 24: Partial Boundaries. Next: Clean Architecture 26: The Main Component.

Takeaways
  • Systems are not just UI, business rules and database: most have more components. Finding every axis of change reveals boundaries, as the Hunt the Wumpus example shows (language, text delivery, storage, networking, even rule levels).
  • Each boundary's API is defined and owned by the user (upstream) component, implemented by the other side.
  • Data flows into multiple streams that meet at the highest-level policy and may later split again; boundaries can appear when a part becomes a service.
  • Boundaries are expensive to build and expensive to add late: watch for friction and build each at the inflection point where implementing costs less than ignoring.

25.1 Hunt the Wumpus

  • It is easy to think of systems as three components, UI, business rules, database; for simple systems that suffices but for most the number is larger
    • Take a simple computer game: the UI handles messages from the player to the game rules, which store state in some persistent data structure
    • Is that all?
  • The game is the venerable Hunt the Wumpus (1972):
    • text-based, with simple commands like GO EAST and SHOOT WEST
    • the computer reports what the player sees, smells, hears and experiences
    • the player hunts a Wumpus in a system of caverns, avoiding traps, pits and other dangers.
  • Keep the text UI but decouple it from the game rules so the product can use different languages in different markets: the rules talk to the UI through a language-independent API and the UI translates it into a human language
    • With dependencies managed properly (Figure 25.1) any number of UI components can reuse the same game rules, which neither know nor care which language is used.
  • Likewise the state may live in flash, the cloud or RAM: the rules should not know, so an API to the storage component with dependencies directed by the Dependency Rule (Figure 25.2).

25.2 Clean architecture?

  • We could apply the clean architecture here (footnote:
    • we would not for something this trivial
    • it is probably 200 lines or fewer, here a proxy for a much larger system) with use cases, boundaries, entities and data structures. But have we found all the significant boundaries?
  • Language is not the only axis of change
    • for the UI: we might also vary the mechanism that communicates the text: a normal shell window, text messages or a chat application
    • That is a potential boundary on another axis: add an API isolating language from the communications mechanism (Figure 25.3).
  • In Figure 25.3 dashed outlines mark abstract components defining an API implemented by components above or below (the Language API is implemented by English and Spanish). **GameRules communicates with Language through an API GameRules defines and Language implements
    • Language communicates with TextDelivery through an API Language defines and TextDelivery implements: "The API is defined and owned by the user, rather than by the implementer."**
  • Inside GameRules you would find polymorphic Boundary interfaces used by its code and implemented by code in Language (and the reverse), and the same inside Language with TextDelivery: in each case the API defined by the Boundary interfaces is owned by the upstream component
    • Variations such as English, SMS and CloudData are provided by polymorphic interfaces defined in the abstract API component and implemented by the concrete components.
  • Simplified (Figure 25.4):
    • oriented so all arrows point up, putting GameRules at the top as the component with the highest-level policies (footnote: arrows show source dependencies, not data flow)
      • Information flow: input comes from the user through TextDelivery (bottom left), rises through Language, getting translated into commands for GameRules
    • GameRules processes it and sends data down to DataStorage (lower right)
    • output goes back down to Language, which translates the API back into the human language and delivers it through TextDelivery.
  • So the flow of data divides into two streams:
    • the left stream communicates with the user, the right deals with persistence
    • they meet at the top at GameRules, the ultimate processor of data from both (footnote: formerly the Central Transform; Page-Jones, Practical Guide to Structured Systems Design, 2nd ed., 1988).

25.3 Crossing and splitting the streams

  • Not always two streams:
    • for multiplayer play over the net add a network component (Figure 25.5), giving three streams all controlled by GameRules
    • As systems grow the component structure may split into many streams.
  • Do all streams eventually meet in one component at the top? "If only life were so simple!" GameRules itself has levels: part deals with map mechanics (how the caverns connect, what is in each, moving the player, deciding the events the player must handle), but another set of policies is even higher level: they know the player's health and the cost or benefit of events: losing health gradually, gaining it by finding food
    • The lower-level mechanics policy declares events to this higher-level policy (FoundFood, FellInPit), which manages the player's state and eventually decides win or lose (Figure 25.6).
  • Is that an architectural boundary between MoveManagement and PlayerManagement? Add micro-services: in a massively multiplayer version MoveManagement runs on the player's computer while PlayerManagement runs on a server offering a micro-service API to all connected MoveManagement components (Figure 25.7; the Network elements are more complex than shown)
    • A full-fledged boundary exists between them.

25.4 Conclusion

  • Why extrapolate a program "which could be implemented in 200 lines of Kornshell" into all these crazy boundaries? To show that architectural boundaries exist everywhere
    • Architects must recognise when they are needed
    • fully implemented boundaries are expensive
    • but boundaries ignored are very expensive to add later, "even in the presence of comprehensive test-suites and refactoring discipline".
  • The answer is "dissatisfying"
    • Very smart people say not to anticipate abstraction: YAGNI, with real wisdom since over-engineering is often much worse than under-engineering
    • But when you truly need a boundary where none exists, adding it can be very costly and risky
    • "O Software Architect, you must see the future
    • You must guess, intelligently." Weigh costs and decide which boundaries to implement fully, partially or not at all.
  • It is not a one-time decision at the start:
    • watch
      • as the system evolves, note where boundaries may be required, and watch carefully for the first inkling of friction from a missing one
      • then weigh the cost of implementing against the cost of ignoring, and review that decision frequently
    • The goal is to implement each boundary right at the inflection point where the cost of implementing becomes less than the cost of ignoring
    • "It takes a watchful eye."

Summary points

  • Look for every axis of change (language, delivery mechanism, storage, network); each can define a boundary.
  • APIs are owned by the user component; dependencies point up toward the highest-level policy.
  • Streams meet and split; services create full boundaries. Build boundaries at the inflection point of cost.
Terms to carry forward
  • Axis of change; abstract API component; API owned by the user.
  • Streams (user, persistence, network); Central Transform.
  • Inflection point (cost of implementing versus ignoring).
