Clean Architecture 28: The Test Boundary

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 28. Own-words digest. Previous: Clean Architecture 27: Services, Great and Small. Next: Clean Architecture 29: Clean Embedded Architecture.

Takeaways
  • Tests are part of the system and participate in the architecture. Architecturally all tests are the same; they are the outermost circle, following the Dependency Rule (they depend inward; nothing depends on them), and independently deployable.
  • Tests not designed into the system are fragile (the Fragile Tests Problem) and make the system rigid.
  • Design for testability: don't depend on volatile things (GUIs). Use a testing API with "superpowers" that decouples the structure of the tests from the structure of the application; avoid structural coupling.
  • Keep dangerous testing-API parts in a separate deployable component.

28.1 Tests as system components

  • "The tests are part of the system, and they participate in the architecture just like every other part of the system does": in some ways normal, in others unique.
  • There is "a great deal of confusion about tests":
    • part of the system or not; unit versus integration, acceptance, functional
    • Cucumber, TDD
    • BDD, component tests... The book does not need to enter that debate: from an architectural point of view all tests are the same: tiny TDD tests or large FitNesse, Cucumber, SpecFlow or JBehave tests are architecturally equivalent.
  • Tests, by nature, follow the Dependency Rule:
    • very detailed and concrete, they always depend inward toward the code under test
    • "You can think of the tests as the outermost circle": nothing in the system depends on the tests.
  • Tests are independently deployable: mostly deployed in test systems rather than production, so even where independent deployment is otherwise unnecessary, tests are still independently deployed.
  • Tests are the most isolated system component:
    • not necessary for operation and no user depends on them
    • their role is to support development, not operation. Yet they are "no less a system component than any other", and "in many ways they represent the model that all other system components should follow".

28.2 Design for testability

  • Their extreme isolation and non-deployment often lead developers to think tests fall outside the system's design: "This is a catastrophic point of view." Tests not well integrated into the design tend to be fragile and make the system rigid and difficult to change.
  • The issue is coupling:
    • strongly coupled tests must change with the system, and even a trivial change to a component can break many
    • This can be acute: changes to common components can break hundreds or thousands of tests: the Fragile Tests Problem.
  • Example: a suite using the GUI to verify business rules, starting at the login screen and navigating the page structure to the rule under test: any change to the login page or navigation structure breaks a huge number of tests.
  • Fragile tests have the perverse effect of making the system rigid: developers who know simple changes cause massive failures may resist them, as in a conversation with marketing about a simple navigation change that breaks 1000 tests.
  • The solution is to design for testability. The first rule of software design (for testability or anything else) is "Don't depend on volatile things." GUIs are volatile, so test suites operating the system through the GUI must be fragile: design the system and tests so business rules can be tested without the GUI.

28.3 The testing API

  • Create a specific API the tests use to verify all the business rules
    • It should have superpowers: avoid security constraints, bypass expensive resources such as databases, and force the system into particular testable states
    • It is a superset of the interactors and interface adapters used by the user interface.
  • Its purpose is to decouple the tests from the application, which goes beyond detaching them from the UI: the goal is to decouple the structure of the tests from the structure of the application.

28.4 Structural coupling

  • Structural coupling
    • is "one of the strongest, and most insidious" forms of test coupling
    • Imagine a suite with a test class for every production class and a set of test methods for every production method: deeply coupled to the application's structure
    • When a production method or class changes, many tests must change: tests are fragile and production code is rigid.
  • The testing API's role is to hide the application's structure from the tests, so production code can be refactored and evolved without affecting the tests, and tests likewise without affecting production code. The separation of evolution is necessary because over time tests become increasingly concrete and specific while production code becomes increasingly abstract and general
    • strong structural coupling prevents or impedes that evolution and keeps production code from being as general and flexible as it could be.

28.5 Security

  • The testing API's superpowers could be dangerous in production
    • If that is a concern, keep the testing API and the dangerous parts of its implementation in a separate, independently deployable component.

28.6 Conclusion

  • "Tests are not outside the system
    • rather, they are parts of the system that must be well designed" to give the benefits of stability and regression protection. Tests not designed as part of the system are fragile and hard to maintain, and "often wind up on the maintenance room floor: discarded because they are too difficult to maintain".

Summary points

  • Tests are the outermost circle; they depend inward and deploy independently.
  • Avoid GUI-driven and structure-mirrored tests; use a testing API that hides the application's structure.
  • Keep the testing API's superpowers out of production.
Terms to carry forward
  • Fragile Tests Problem; structural coupling; testing API.
  • Tests as the outermost circle; "don't depend on volatile things".
