Clean Architecture 29: Clean Embedded Architecture

Source: James Grenning (guest chapter) in Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 29. Own-words digest. Previous: Clean Architecture 28: The Test Boundary. Next: Clean Architecture 30: The Database Is a Detail.

Takeaways
  • "Although software does not wear out, firmware and hardware become obsolete" (Doug Schmidt). Grenning adds: software can be destroyed from within by unmanaged dependencies on firmware and hardware.
  • Code is firmware because of what it depends on and how hard it is to change, not because it is stored in ROM. Stop writing so much firmware.
  • Passing the App-titude test (it works) is not enough. The target-hardware bottleneck slows teams that can test only on the target; a clean embedded architecture is a testable one.
  • Tools: a HAL (hardware abstraction layer), a PAL (processor abstraction layer), an OSAL (operating system abstraction layer), interfaces and substitutability, and no repeated conditional compilation (DRY).

29.1 Software, firmware and hardware

  • Written by James Grenning. He read "The Growing Importance of Sustaining Software for the DoD" on Doug Schmidt's blog (SEI): "Although software does not wear out, firmware and hardware become obsolete, thereby requiring software modifications." Software can have a long useful life
    • firmware becomes obsolete as hardware evolves (hardware is continually evolving; features keep adding to the software's complexity).
  • Grenning's addition: "Although software does not wear out, it can be destroyed from within by unmanaged dependencies on firmware and hardware." Embedded software is often denied a long life by being infected with dependencies on hardware.
  • Common definitions of firmware (code in non-volatile memory such as ROM, EPROM or flash; software programmed on a hardware device; software embedded in hardware; software written to ROM) are "wrong, or at least obsolete": **"It's not firmware because of where it is stored
    • rather, it is firmware because of what it depends on and how hard it is to change as hardware evolves."** Hardware evolves (look at your phone), so structure embedded code accordingly. "What we really need is less firmware and more software."
  • Non-embedded engineers write firmware too:
    • when you bury SQL in your code or spread platform dependencies through it
    • Android app developers write firmware when they do not separate business logic from the Android API.
  • Story 1:
    • in the late 1990s Grenning helped redesign a communications subsystem moving from time-division multiplexing (TDM) (state of the art in the 1950s and 1960s, widely deployed in the 1980s and 1990s) to voice over IP (VOIP)
    • Asked how a call should react, the systems engineer would disappear and return with a detailed answer from the current product's code: "The tangled legacy code was the spec for the new product!" There was no separation between TDM and the business logic of making calls: the whole product was hardware- and technology-dependent from top to bottom: it had "essentially become firmware".
  • Story 2:
    • command messages arrive over a serial port
    • a message processor/dispatcher parses and dispatches them, but it sits in the same file as the code touching the UART (the device that controls the serial port): it is "polluted with UART details" and could have been long-lived software but is firmware.
  • For engineers: "Stop writing so much firmware and give your code a chance at a long useful life."

29.2 The App-titude test

  • Why does so much potential embedded software become firmware? Emphasis falls on getting it to work, not on structuring it for a long life. Kent Beck's three activities: **
  • "First make it work"** (you are out of business if it does not); **
  • "Then make it right"** (refactor so you and others can understand and evolve it); **
  • "Then make it fast"** (refactor for needed performance)
    • Much embedded code is written for "make it work", plus an obsession with "make it fast" via micro-optimisations
    • Fred Brooks (The Mythical Man-Month): "plan to throw one away"
    • They give virtually the same advice: learn what works, then make a better solution
  • Embedded software is not special here:
    • most non-embedded apps are also built just to work. Getting an app to work is the "App-titude test"
    • programmers concerned only with that "are doing their products and employers a disservice".
  • Example:
    • one file of a small embedded system lists, in source order, interrupt handlers (ISR(TIMER1_vect), ISR(INT2_vect)), a button handler, calc_RPM, Read_RawData, Do_Average, sensor zeroing, device control, flash setup load and save, data set store and recall, bytes2float, Sensor_init and uC_Sleep
      • Grouped by concern: domain logic (calc_RPM, Do_Average, Get_Next_Measurement, Zero_Sensor_1/2)
    • hardware platform setup (the ISRs, uC_Sleep)
    • on/off button reaction
    • A/D input reading (Read_RawData)
    • persistent storage (flash setup and data set functions, bytes2float)
    • and a function that does not do what its name implies (Sensor_init).
  • Other files showed many impediments to understanding and a structure implying the code can be tested only on the embedded target
    • virtually all of it knows it is on a special microprocessor and uses "extended" C tied to a tool chain: no long life unless the product never changes hardware
    • "This application works: the engineer passed the App-titude test
    • But ..
    • can't be said to have a clean embedded architecture."

29.3 The target-hardware bottleneck

  • Embedded developers face special concerns:
    • limited memory, real-time deadlines, limited IO, unconventional user interfaces, sensors and real-world connections
      • hardware is often developed concurrently with software and firmware, so you may have no place to run the code, and the hardware has its own defects
    • "Embedded is special ..
    • but not so special that the principles in this book are not applicable."
  • The target-hardware bottleneck: if code is structured without clean architecture and can be tested only on the target, you are slowed down.

29.4 A clean embedded architecture is a testable embedded architecture

  • Layers
    • (Figure 29.1: three layers): at the bottom, the hardware, which will change with technology advances and Moore's law (parts obsolete; new parts cheaper, faster, lower power)
    • Hardware must be separated from the rest (Figure 29.2), but nothing stops hardware knowledge from polluting all the code, making it hard to change, whether for hardware changes, user requests or bug fixes.
  • Software and firmware intermingling is an anti-pattern: it resists changes, makes them dangerous (unintended consequences), needs full regression tests even for minor changes, and without externally instrumented tests leaves boring manual tests and new bug reports.
  • The hardware is a detail:
    • the software/firmware line is fuzzier than the code/hardware line (Figure 29.3)
    • an embedded developer's job is to firm it up. The boundary is the hardware abstraction layer (HAL) (Figure 29.4), long used in PCs.
    • The HAL exists for the software above it and its API is tailored to that software's needs: firmware can store bytes and arrays in flash, but the application needs to store and read name/value pairs to some persistence mechanism (flash, spinning disk, cloud or core memory: a detail).
    • An LED tied to a GPIO bit:
      • firmware or a board support package may offer Led_TurnOn(5), while the HAL offers Indicate_LowBattery(): expressing a service the application needs
        • GPIO assignments are hidden
      • "Layers may contain layers..
      • a repeating fractal pattern."
    • "Don't reveal hardware details to the user of the HAL." A successful HAL is a seam for off-target testing.
  • The processor is a detail:
    • vendor tool chains give header files and take liberties with C, adding keywords and what look like global variables for registers, IO ports, timers and interrupt controllers
    • code using them is no longer C and may not compile for another processor or even another compiler. Limit which files know about the extensions.
    • Example:
      • an ACME DSP header acmetypes.h (with _ACME_X42 and _ACME_A42 branches defining Uint_32, Int_16 and so on)
      • Do not use it directly: your types would be wrong off-target, and porting would be harder
      • Use stdint.h; if the target compiler lacks it, write one that uses acmetypes.h for target builds (typedef Uint_32 uint32_t; and so on).
    • Example:
      • a say_hi() function writing "hi" to the serial port by setting IE (interrupt enable bits) and SBUF0 (serial output buffer) and waiting on TI_0 (transmit buffer empty interrupt), even using 0b11000000 binary notation, which is not C
      • A clean embedded architecture uses such registers directly in very few places, confined to firmware; whatever knows them becomes firmware, bound to the silicon
      • Firmware may isolate them with a processor abstraction layer (PAL), so firmware above it can be tested off-target.
  • The operating system is a detail:
    • in bare-metal systems a HAL may suffice, but with an RTOS or embedded Linux or Windows, treat the OS as a detail too
    • The OS separates software from firmware (Figure 29.5), and using it directly causes problems: the supplier may be bought, royalties rise or quality falls, or your needs outgrow it, forcing syntactic and semantic changes
    • Isolate with an operating system abstraction layer (OSAL) (Figure 29.6): sometimes just renaming a function, sometimes wrapping several
    • Moving between RTOSes is painful; with an OSAL you mostly write a new OSAL to a defined interface ("This is not a trick question. I choose the latter")
    • Worried about bloat? The layer isolates the duplication of using an OS, and can give applications a common structure (message passing instead of every thread handcrafting concurrency) and test points so application code can be tested off-target and off-OS.

29.5 Programming to interfaces and substitutability

  • Beyond HAL and OSAL in each major layer (software, OS, firmware, hardware), apply the book's principles: separation of concerns, programming to interfaces, substitutability
    • Layering rests on programming to interfaces: when modules interact through an interface you can substitute one provider for another: a home-grown printf for deployment on the target is substitutable if its interface matches the standard.
  • Rule of thumb:
    • use header files as interface definitions, limited to function declarations plus the constants and struct names the functions need. Do not clutter them with data structures, constants and typedefs needed only by the implementation: it breeds unwanted dependencies
    • "Expect the implementation details to change."
  • "A clean embedded architecture is testable within the layers because modules interact through interfaces": each interface is a seam for off-target testing.

29.6 DRY conditional compilation directives

  • Embedded C and C++ often use conditional compilation for different targets or operating systems
    • Grenning recalls #ifdef BOARD_V2 appearing several thousand times in a telecom application (six thousand in the text's example): a violation of DRY (Hunt and Thomas, The Pragmatic Programmer): once is fine, six thousand an "extreme problem"
    • With a HAL, the hardware type becomes a detail hidden below it
      • the HAL provides interfaces and you connect software to hardware with the linker or runtime binding instead of conditional compilation.

29.7 Conclusion

  • Embedded developers have much to learn from outside embedded work
    • "Letting all code become firmware is not good for your product's long-term health
    • Being able to test only in the target hardware is not good for your product's long-term health
    • A clean embedded architecture is good for your product's long-term health."

Summary points

  • Software outlives hardware if it does not depend on it; firmware is defined by dependency, not storage.
  • HAL, PAL and OSAL make hardware, processor and OS details; they create off-target test seams.
  • Interfaces in headers, substitutability and one-place variation (not scattered #ifdefs).
Terms to carry forward
  • Firmware versus software; App-titude test; target-hardware bottleneck.
  • HAL, PAL, OSAL; off-target testing; DRY.
