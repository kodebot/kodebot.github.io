Clean Architecture 30: The Database Is a Detail

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 30. Own-words digest. Previous: Clean Architecture 29: Clean Embedded Architecture. Next: Clean Architecture 31: The Web Is a Detail.

Takeaways
  • "From an architectural point of view, the database is a non-entity": a detail, like a doorknob to the architecture of a home. This is not about the data model, which is architecturally significant; the database is a utility that provides access to data, a low-level mechanism.
  • Relational databases (Codd, 1970) are brilliant but still technology. Do not pass rows or tables around as objects: that couples use cases, rules and the UI to the relational structure.
  • Databases dominate because of slow disks. With RAM you would use linked lists, trees, hash tables and queues; you already reshape data into those in memory.
  • Performance is a low-level data access concern that can be fully encapsulated. Markets can still demand an RDBMS: put it beside the core behind a narrow, safe channel.

30.1 The database is not the data model

  • The database's relationship to the architecture is "rather like the relationship of a doorknob to the architecture of your home"
    • Martin knows these are "fighting words" ("I've had the fight")
    • To be clear: not the data model: the structure given to data inside the application is "highly significant"
    • **The database is not the data model
      • the database is a piece of software, a utility that provides access to the data.** To the architecture it is irrelevant: "a low-level detail, a mechanism
    • And a good architect does not allow low-level mechanisms to pollute the system architecture."

30.2 Relational databases

  • Edgar Codd
    • defined the principles of relational databases in 1970
      • by the mid-1980s the relational model was the dominant form of data storage, for good reason: "elegant, disciplined, and robust", an excellent storage and access technology
    • But "no matter how brilliant, useful, and mathematically sound a technology it is, it is still just a technology
    • And that means it's a detail."
  • Relational tables suit certain access, but "there is nothing architecturally significant about arranging data into rows within tables". The use cases should neither know nor care
    • knowledge of the tabular structure should be restricted to the lowest-level utility functions in the outer circles.
  • Many data access frameworks let database rows and tables be passed around as objects: "an architectural error": it couples the use cases, business rules and sometimes even the UI to the relational structure of the data.

30.3 Why are database systems so prevalent?

  • What explains the preeminence of Oracle, MySQL and SQL Server? "In a word: disks." The rotating magnetic disk was the mainstay of data storage for five decades
    • several generations of programmers know no other
    • Disks went from stacks of massive 48-inch platters weighing thousands of pounds and holding 20 megabytes to single 3-inch circles weighing a few grams and holding a terabyte or more
    • Throughout, one fatal trait: disks are slow.
  • Data lives in circular tracks divided into sectors (often 4K)
    • a platter has hundreds of tracks and there may be a dozen platters. To read one byte you move the head to the right track, wait for the rotation to the sector, read the whole 4K sector into RAM and index into the buffer: milliseconds, and "a millisecond is a million times longer than the cycle time of most processors" (RAM access is in nanoseconds).
  • To mitigate the delay you need indexes, caches and optimised query schemes, and a regular representation of the data for them to work with: a data access and management system, which split into two kinds:
    • File systems:
      • document based
      • natural for storing and retrieving whole documents by name
      • poor at searching content (easy to find login.c, hard and slow to find every .c file with a variable named x).
    • Database systems (RDBMS):
      • content based
      • natural for finding records by content and associating records by shared content
      • rather poor at storing and retrieving opaque documents.
  • Both organise data on disk for efficient access and each indexes and arranges it their own way; both eventually bring the data into RAM to manipulate it.

30.4 What if there were no disk?

  • Disks are "a dying breed", going the way of tape drives, floppies and CDs, replaced by RAM
    • When all your data is in RAM, will you organise it into tables with SQL, or files in a directory? "Of course not." You will use linked lists, trees, hash tables, stacks, queues and other data structures and access them with pointers or references, "because that's what programmers do".
  • In fact you already do:
    • whether the data is in a database or file system you read it into RAM and reorganise it into lists, sets, stacks, queues or trees for your convenience
    • it is unlikely you leave it as files or tables.

30.5 Details and performance

  • Hence "the database is a detail":
    • a mechanism for moving data between the surface of the disk and RAM, "a big bucket of bits where we store our data on a long-term basis"
    • We seldom use the data in that form
    • "From an architectural viewpoint, we should not care about the form that the data takes while it is on the surface of a rotating magnetic disk
    • Indeed, we should not acknowledge that the disk exists at all."
  • Performance is an architectural concern, "of course", but for data storage it can be entirely encapsulated and separated from the business rules: getting data in and out quickly is a low-level concern, solved with low-level data access mechanisms, "nothing whatsoever to do with the overall architecture".

30.6 Anecdote

  • In the late 1980s Martin led engineers at a startup building a network management system measuring the communications integrity of T1 telecommunication lines: it retrieved data from devices at the line endpoints and ran predictive algorithms to detect and report problems. On UNIX they stored data in simple random access files: no relational database was needed since the data had few content-based relationships
    • trees and linked lists in random access files were most convenient to load into RAM.
  • The marketing manager said they had to have an RDBMS:
    • "it wasn't an engineering issue, it was a marketing issue"
    • A hardware engineer took up the chant for technical reasons, holding meetings behind Martin's back and drawing a house balanced on a pole ("Would you build a house on a pole?"), implying an RDBMS keeping its tables in random access files was somehow more reliable than their files
    • Martin "fought, and fought, and fought"; the hardware developer was promoted over his head to software manager and an RDBMS was put into the system.
  • "In the end, they were absolutely right and I was wrong
    • Not for engineering reasons: I was right about that." Customers expected an RDBMS: it had become a check-box item on every purchaser's list, with no realistic use for the relational data
    • The need came from the highly effective marketing campaigns of the database vendors, who convinced executives that their corporate "data assets" needed protection and that database systems provided it
    • The same kind of marketing surrounds "enterprise" and "Service-Oriented Architecture" today.
  • What he should have done:
    • bolt an RDBMS on the side with "some narrow and safe data access channel to it", keeping the random access files in the core
    • What he did: "I quit and became a consultant."

30.7 Conclusion

  • **The data model is architecturally significant
    • the technologies and systems that move data on and off a rotating magnetic surface are not.** Relational databases, which force data into tables accessed with SQL, have much more to do with the latter
    • "The data is significant
    • The database is a detail."

Summary points

  • Separate the data model (significant) from the database (a detail).
  • Keep rows, tables and SQL in the outer circles; never pass them inward.
  • Meet market demands by plugging an RDBMS in beside the core, not at its heart.
Terms to carry forward
  • Database as a detail (the doorknob); data model versus database.
  • File system versus RDBMS; disks are slow; RAM data structures.
  • Row and table structures must not cross inward.
