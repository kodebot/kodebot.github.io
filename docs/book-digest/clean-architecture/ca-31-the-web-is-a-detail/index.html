Clean Architecture 31: The Web Is a Detail

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 31. Own-words digest. Previous: Clean Architecture 30: The Database Is a Detail. Next: Clean Architecture 32: Frameworks Are Details.

Takeaways
  • The web is just the latest oscillation between putting computing power in central servers and at the terminals; it "didn't change anything". Push such short-term swings away from the business rules.
  • The GUI is a detail; the web is a GUI; so the web is a detail. Think of the web as an IO device and keep applications device-independent.
  • Full UI abstraction is hard because the UI dance is chatty and GUI-specific, but use-case input and output data structures can be abstracted, so each use case operates the UI as a device-independent IO device.
  • "The world is full of marketing geniuses": decoupling is often very necessary.

31.1 The endless pendulum

  • "Do you remember how the web changed everything? ..
    • Actually the web didn't change anything
    • Or, at least, it shouldn't have." The web is the latest in a series of oscillations since the 1960s between all the power in central servers and all the power at the terminals.
  • Even in the last decade of the web:
    • first the thinking was that server farms held all the power with stupid browsers
    • then applets went into browsers
    • people disliked that and moved dynamic content back to servers
    • then Web 2.0 moved processing back into the browser with Ajax and JavaScript, to the point of whole huge applications executing in browsers
    • and now excitement about pulling JavaScript back into the server with Node. "(Sigh.)"
  • The oscillations did not start with the web. Before it, client-server
    • before that, central minicomputers with arrays of dumb terminals
    • before that, mainframes with smart green-screen terminals (analogous to modern browsers)
    • before that, computer rooms and punched cards
      • "We can't seem to figure out where we want the computer power." In the scope of IT history the web "didn't change anything at all"
      • As architects we look at the long term: those oscillations are short-term issues "we want to push away from the central core of our business rules".

31.2 Two cautionary stories

  • Company Q
    • built a popular personal finance system, a desktop app with a very useful GUI
    • After the web came, its next release made the GUI look and behave like a browser: Martin hated it ("What marketing genius ... ?"), apparently others did too, and after a few releases Q removed the browser-like feel and returned to a regular desktop GUI.
    • What should a Q architect have done before a marketing genius pushed the change? Decoupled the business rules from the UI. Martin does not know whether Q did
      • he would have lobbied hard to isolate the rules, "because you never know what the marketing geniuses will do next".
  • Company A's smartphone: a recent upgrade of its "operating system" (odd to say, for a phone) changed the look and feel of all applications
    • Martin does not know if it caused difficulty for app programmers, but hopes the architects of A and of the apps kept UI and business rules isolated, "because there are always marketing geniuses out there just waiting to pounce on the next little bit of coupling you create".

31.3 The upshot

  • "The GUI is a detail. The web is a GUI. So the web is a detail." As an architect, put details like that behind boundaries that keep them separate from your core business logic.
  • "The WEB is an IO device." In the 1960s we learned the value of writing device-independent applications; the motivation has not changed; "the web is not an exception".
  • The counter-argument:
    • a GUI like the web is so unique and rich (JavaScript validation, drag-and-drop Ajax calls, and "the plethora of other widgets and gadgets") that device independence looks absurd
    • "To some extent, this is true." The interaction between application and GUI is "chatty" in ways specific to the kind of GUI: the dance between a browser and a web application differs from that between a desktop GUI and its application, and abstracting that dance the way devices are abstracted in UNIX seems unlikely.
  • But another boundary can be abstracted.
    • Business logic is a suite of use cases, each performing a function for a user, describable by input data, processing and output data
    • At some point in the UI/application dance the input data is complete, allowing the use case to run; on completion the resultant data feeds back into the dance
    • The complete input data and resultant output data go into data structures used as the input and output values of a process that executes the use case
    • "With this approach, we can consider each use case to be operating the IO device of the UI in a device-independent manner."

31.4 Conclusion

  • "This kind of abstraction is not easy, and it will likely take several iterations to get just right
    • But it is possible
    • And since the world is full of marketing geniuses, it's not hard to make the case that it's often very necessary."

Summary points

  • The web is an IO device, the latest swing of the pendulum; keep it outside the business rules.
  • Do not try to abstract the chatty UI dance; abstract the use-case request and response data instead.
  • Decoupling protects against sudden UI redesigns driven by marketing.
Terms to carry forward
  • Oscillation (centralise or distribute computing power).
  • GUI as a detail; the web as an IO device; device independence.
  • Use case input and output data structures.
