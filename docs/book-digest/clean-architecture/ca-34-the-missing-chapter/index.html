Clean Architecture 34: The Missing Chapter

Source: Simon Brown (guest chapter) in Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 34. Own-words digest. Previous: Clean Architecture 33: Case Study, Video Sales. Next: Clean Architecture 35: Afterword.

Takeaways
  • Good design intentions can be destroyed "in a flash" by implementation details. Brown compares four ways to organise the same code: package by layer, by feature, ports and adapters, and his own package by component.
  • A layered architecture's acyclic graph can hide violations (a "relaxed" layered architecture). Rely on the compiler to enforce architecture rather than discipline or after-the-fact tools.
  • Overusing public turns packages into mere folders, making all four styles identical. Use access modifiers, module systems and separate source trees as decoupling modes.

34.1 The question: view order status

  • By Simon Brown
    • All the preceding advice helps design software with clear boundaries, responsibilities and controlled dependencies, but "the devil is in the implementation details, and it's really easy to fall at the last hurdle".
  • Running example:
    • an online book store with a use case letting customers view the status of their orders
    • A Java example, but the principles apply to other languages
    • Setting the Clean Architecture aside for a moment, look at several ways to organise code.

34.2 Package by layer

  • The traditional horizontal layered architecture (Figure 34.1), separating code by technical function: a layer for web, one for business logic, one for persistence. In a strict layered architecture a layer depends only on the next adjacent lower layer
    • in Java layers are packages and all dependencies point down.
  • Types:
    • OrdersController (a web controller, say Spring MVC)
    • OrdersService (interface for business logic)
    • OrdersServiceImpl (implementation; "arguably a horrible way to name a class, but ... perhaps it doesn't really matter")
    • OrdersRepository (interface for persistent order data), and JdbcOrdersRepository.
  • Martin Fowler
    • ("Presentation Domain Data Layering") calls a layered architecture a good way to get started
    • many books, tutorials and samples teach it, and it is quick to get running without much complexity. The problem: as software grows, three big buckets are not enough and you must modularise further.
  • As Uncle Bob said, a layered architecture doesn't scream anything about the business domain: two layered systems from different domains look "eerily similar: web, services, and repositories"
    • There is "another huge problem" (see 34.5).

34.3 Package by feature

  • A vertical slicing by related features, domain concepts or aggregate roots (DDD terms); typically all the types in one package named for the concept (Figure 34.2)
    • It is a simple refactoring from package by layer, and the top-level organisation now screams something about the domain (orders, not web, services and repositories)
    • It is also potentially easier to find all the code when the "view orders" use case changes (a benefit much reduced by modern IDE navigation, footnote).
  • Teams often realise horizontal layering is a problem and switch to vertical layering: "In my opinion, both are suboptimal."

34.4 Ports and adapters

  • As Uncle Bob has said
    • ports and adapters, the hexagonal architecture
    • boundaries, controllers, entities and the like aim to make business and domain code independent of technical details such as frameworks and databases
    • Code bases have an "inside" (domain) and an "outside" (infrastructure) (Figure 34.3): UIs, databases, third-party integrations
    • The outside depends on the inside, never the other way (Figure 34.4: com.mycompany.myapp.domain is the inside).
  • OrdersRepository has been renamed simply Orders: from domain-driven design, everything inside is named in the ubiquitous domain language ("we talk about 'orders' ..., not the 'orders repository'")
    • The diagram is simplified: interactors and objects to marshal data across boundaries are missing.

34.5 Package by component

  • Brown agrees with SOLID, REP, CCP, CRP and most of the book but concludes differently about code organisation
    • His career:
      • enterprise software, mostly Java, across business domains and styles (web, client-server, distributed, message-based)
      • the common theme was a traditional layered architecture
    • (Footnote: his first job in 1996 built client-server desktop apps with PowerBuilder, a 4GL; then Java client-server apps pre-JDBC with their own database connectivity and GUI toolkits on AWT.)
  • Layering problems beyond the above:
    • layers equate to Java packages, so for the controller to depend on OrdersService, that interface must be public, and likewise OrdersRepository so OrdersServiceImpl can see it
    • A strict layered architecture wants a clean acyclic dependency graph, but "we can cheat by introducing some undesirable dependencies, yet still create a nice, acyclic dependency graph".
  • The newcomer story:
    • a new hire wants to impress
      • finds OrdersController, decides the new orders page goes there, discovers OrdersRepository and injects the implementation straight into the controller
    • It works (Figure 34.5) and the arrows still point downward, but the controller is bypassing OrdersService: a relaxed layered architecture, where layers may skip adjacent neighbours
    • Sometimes intended (e.g. CQRS, with separate update and read patterns), but often undesirable, especially if the business layer ensures authorised access to individual records
    • Brown sees it often as a consultant, usually revealed when teams visualise their code base for the first time.
  • A guideline such as "web controllers should never access repositories directly" needs enforcement:
    • Discipline and code review ("we trust our developers"): fails "when budgets and deadlines start looming".
    • Static analysis
      • (NDepend, Structure101, Checkstyle) at build time, with rules like "types in **/web should not access types in **/data", run after compilation: crude, but can report violations and fail the build
      • both approaches are fallible with a longer feedback loop
      • unchecked, the code base becomes a "big ball of mud" (Foote and Yoder's paper, http://www.laputan.org/mud/).
    • Brown would "like to use the compiler to enforce my architecture if at all possible".
  • Package by component
    • (Figure 34.6) is a hybrid: bundle all responsibilities of one coarse-grained component into a single Java package, a service-centric view like micro-services
    • As ports and adapters treat the web as just another delivery mechanism, here the UI stays separate from these components
    • Business logic and persistence code are bundled into one "component".
  • Definitions differ
    • Martin: components are units of deployment, the smallest deployable entities (jar files)
    • Brown: "a grouping of related functionality behind a nice clean interface, which resides inside an execution environment like an application", from his C4 model (https://www.structurizr.com/help/c4): software systems contain containers (web apps, mobile apps, databases, file systems), containers contain components, components are implemented by classes
    • Whether a component lives in its own jar is orthogonal.
  • Benefit:
    • for anything involving orders there is one place to go, the OrdersComponent
    • inside, business logic and persistence are still separated, but as a hidden implementation detail. It resembles a separate OrdersService in a micro-services or SOA design
    • the key difference is the decoupling mode. Well-defined components in a monolith are "a stepping stone to a micro-services architecture".

34.6 The devil is in the implementation details

  • The four approaches look like different architectural styles, but "this perception starts to unravel very quickly if you get the implementation details wrong"
    • Overly liberal public is common: "in our muscle memory" (look at samples on GitHub), regardless of style
    • It ignores the language's encapsulation; "nothing preventing somebody from ..
    • instantiating a concrete implementation class directly".
  • Organisation versus encapsulation:
    • if all types are public, packages are merely folders for organisation, not encapsulation
      • you can effectively ignore them, so all four styles are exactly the same (Figure 34.7): conceptually different, syntactically identical: really "just four ways to describe a traditional horizontally layered architecture"
    • "Of course nobody would ever make all of their Java types public
    • Except when they do
    • And I've seen it."
  • Java's access modifiers are not perfect (footnote:
    • packages look hierarchical but you cannot restrict access by package/subpackage
    • hierarchy exists only in names and directories), but ignoring them "is just asking for trouble". Figure 34.8 greys out the types whose modifier can be tightened:
    • Package by layer:
      • OrdersService and OrdersRepository must be public (inbound dependencies from other packages)
      • OrdersServiceImpl and JdbcOrdersRepository can be package protected (implementation details).
    • Package by feature:
      • OrdersController is the sole entry point, so everything else can be package protected
      • caveat: nothing outside can access orders information except through the controller, "which may or may not be desirable".
    • Ports and adapters: the OrdersService and Orders interfaces are public; implementations package protected and dependency injected at runtime.
    • Package by component:
      • only the OrdersComponent interface has an inbound dependency (from the controller)
      • everything else is package protected: "The fewer public types you have, the smaller the number of potential dependencies." Nothing outside the package can use OrdersRepository directly (barring reflection, "but please don't do that!"), so the compiler enforces the principle. In .NET use internal, with a separate assembly per component.
  • All of this concerns a monolithic application in one source tree: lean on the compiler rather than self-discipline and post-compilation tooling.

34.7 Other decoupling modes

  • Module systems:
    • in Java, OSGi and the (then new) Java 9 module system let you distinguish public from published types: an Orders module with all types public but only a small subset published for external use
    • Brown hopes Java 9 modules will "spark people's interest in design thinking once again".
  • Separate source trees
    • per concern: for ports and adapters, three trees: business and domain (OrdersService, OrdersServiceImpl, Orders)
      • web (OrdersController)
      • persistence (JdbcOrdersRepository)
    • The latter two have a compile-time dependency on the domain tree, which knows nothing of them; configure with separate Maven, Gradle or MSBuild modules
    • Ideally repeat this per component, but it is idealistic: real-world performance, complexity and maintenance issues.
  • Two trees:
    • domain (the "inside") and infrastructure (the "outside"), mapping onto the common ports and adapters diagram (Figure 34.9), with a compile-time dependency from infrastructure to domain
    • It works, but beware the "Périphérique anti-pattern of ports and adapters": like the Boulevard Périphérique ring road around Paris, all infrastructure in one tree means infrastructure in one area (a web controller) can call infrastructure in another (a database repository) directly without going through the domain, especially if access modifiers are forgotten.

34.8 Conclusion: the missing advice

  • "Your best design intentions can be destroyed in a flash if you don't consider the intricacies of the implementation strategy." Think about mapping your design onto code structures, organising the code, and which decoupling modes to apply at runtime and compile time
    • Leave options open, but be pragmatic: consider team size, skill level, solution complexity, time and budget
    • Use the compiler to enforce your chosen style, and watch for coupling elsewhere, such as data models
    • "The devil is in the implementation details."

Summary points

  • Layered and feature packaging each fall short; component packaging hides persistence behind a clean interface.
  • Acyclic dependency graphs do not guarantee the intended architecture; enforce with the compiler.
  • public everywhere erases the difference between styles; use access modifiers, modules and source trees.
Terms to carry forward
  • Package by layer / feature / component; ports and adapters.
  • Relaxed layered architecture; big ball of mud; Périphérique anti-pattern.
  • Public versus published; C4 model (container, component, class).
