Clean Architecture 35: Afterword

Source: Jason Gorman (afterword, 26 January 2017) in Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017). Own-words digest. Previous: Clean Architecture 34: The Missing Chapter. Next: Clean Architecture 36: Appendix A, Architecture Archaeology.

Takeaways
  • Big Architecture (long up-front design handed from "senior" to "junior" programmers, who ignored it) was wiped out by Agile and Extreme Programming, replaced by just-enough design up front with plenty of refactoring.
  • But programmers must then think like architects: structure decides how well software can keep adapting and evolving. The result of neglect is Fragile Architecture.
  • Every design decision should leave the door open for future change, like lining up the next shot in pool. "If it costs $500 to change a line of code, change ain't happening."
  • Design is learned by practice, like riding a bicycle: analyse your code, refactor, review designs after each TDD test, review with a colleague, add a quality gate to the build pipeline, and talk about Clean Architecture and teach it.

35.1 From Big Architecture to Fragile Architecture

  • Gorman began his career in the 1990s, "when the dinosaurs of Big Architecture ruled the world": objects, components, design patterns and UML were the route to advancement
    • Projects began with long design phases with blueprints drawn by "senior" programmers for "junior" programmers to follow, "which, of course, they didn't
    • Ever."
  • He rose through inflated titles ("software architect", "lead architect", "chief architect", "Lord Architect of the Privy Council") and found himself connecting boxes with arrows and coding with PowerPoint, with barely any impact on real code
    • His realisation: "every line of code contains at least one design decision", so whoever writes code has a bigger effect on quality than "a PowerPoint jockey"
    • "I'm a programmer ..
    • the best way I've found to have a positive impact on code is to write it."
  • The Big Architecture dinosaurs, "to be found wandering the primeval plains of Big Process", were "wiped out by the asteroid of Extreme Programming"
    • Teams stopped waiting weeks or months for a document they would ignore and instead agreed a test with the customer, held a quick design session, and wrote the code
    • Just-Enough-Design-Up-Front-with-Plenty-of-Refactoring mammals replaced them: architecture became responsive
    • "Well, that was the theory, anyway."
  • The problem:
    • programmers have to be able to think like architects
    • Not all Big Architecture learning was valueless: how software is structured has a profound impact on the ability to keep adapting it, even in the short term.
  • Every design decision must leave the door open for future changes: "Like playing pool, each shot isn't just about sinking that ball
    • it's also about lining up the next shot." Writing working code that doesn't block future code is a non-trivial skill that takes years to master
    • So Big Architecture gave way to Fragile Architecture: designs that grew quickly to deliver value sooner but made sustaining that pace of innovation very difficult
    • "It's all very well talking about 'embracing change,' but if it costs $500 to change a line of code, change ain't happening."

35.2 What to do now

  • Bob Martin's original papers on OO design principles
    • changed Gorman's view of his code as a young developer
    • Having seen how code can deliver value today without blocking tomorrow's, "the onus is on you to put in the practice"
    • "Like riding a bicycle, you can't master software design just by reading about it."
  • Concrete advice:
    • Analyse your code for the problems the book highlights, then practise refactoring them away (doubly valuable if you are new to refactoring).
    • Build principles into your process: in TDD, hold a little design review after each passing test and clean up as you go ("way cheaper than fixing bad designs later").
    • Ask a colleague to review code before committing.
    • Add a code quality gate to your build pipeline "as a last line of defense against unclean architecture" (and if there is no pipeline, "maybe it's time to create one?").
    • Talk about Clean Architecture: with your team and the wider community; "quality is everybody's business", and a consensus on good versus bad architecture matters.
    • Pay it forward: most developers are not very architecture-aware (as Gorman was not 25 years ago); once you understand it, take the time to wrap someone else's head around it.
  • Technology changes continually but foundational principles rarely change: this book should stay on the shelf for years after "Lean JSON Cloud NoSQL for Dummies" ends up in a yard sale
    • "The real journey starts here."

Summary points

  • Agile removed Big Architecture, but programmers must still design for change.
  • Design skill comes from practice, review and conversation, not only reading.
  • Principles outlast technologies.
Terms to carry forward
  • Big Architecture versus Fragile Architecture.
  • Just enough design up front with plenty of refactoring.
  • Quality gate in the build pipeline.
