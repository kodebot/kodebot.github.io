Core Java 5: Inheritance

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 5. Previous: Core Java 4: Objects and Classes. Next: Core Java 6: Interfaces, Lambda Expressions and Inner Classes.

Takeaways
  • Inheritance builds a new class on an existing one with extends: the subclass reuses the superclass's methods and fields, adds its own, and can override methods. Java has single inheritance only.
  • Polymorphism and dynamic binding: a variable of the superclass type can hold any subclass object, and the JVM calls the method of the actual type at run time (the default in Java, no virtual keyword).
  • Subclass to superclass assignment is free (substitution principle); the other way needs a cast that is checked at run time, so guard it with instanceof (preferably the pattern form x instanceof Manager boss).
  • Every class extends Object; you will override equals, hashCode and toString. The equals contract is reflexive, symmetric, transitive, consistent and false for null.
  • protected means package plus subclasses. Do not call overridable methods from a constructor.

5.1 Classes, superclasses and subclasses

  • Running example:
    • managers are paid a base salary plus a bonus, employees only a salary
    • A Manager is-an Employee (the hallmark of inheritance), so reuse Employee and add the bonus.
  • Grain of salt
    • (the author): in real life an employee can become a manager, so being a manager would be a role, not a subclass
    • The book assumes two permanent kinds of people for teaching
    • Inheritance may also be less common than first envisioned, but remains powerful and indispensable.

5.1.1 Defining subclasses

public class Manager extends Employee
{
    private double bonus;
    // ...
    public void setBonus(double bonus)
    {
        this.bonus = bonus;
    }
}
  • extends derives a new class from an existing one. Terms: superclass, base class, parent class and subclass, derived class, child class.
  • Other languages: Python class Manager(Employee), C++ class Manager : public Employee. All Java inheritance is public: no private or protected inheritance as in C++.
  • "Super" does not mean better: subclasses have more functionality. The names come from set theory: the set of all employees is a superset of the set of managers.
  • Manager boss = ...; boss.setBonus(5000); works; an Employee has no setBonus. A Manager object also has getName and getHireDay automatically.
  • A Manager object has four fields: name, salary, hireDay (from the superclass) and bonus.
  • The JLS says private members "are not inherited",
    • which confuses readers: the spec uses "inherits" narrowly (the subclass cannot access them directly)
    • Each Manager object still contains the three superclass fields.
  • You only write the differences: put general methods in the superclass, specialised ones in subclasses. Moving common functionality up is routine.
  • Records cannot be extended and cannot extend another class.

5.1.2 Overriding methods

  • getSalary must return base salary plus bonus. Two wrong attempts:
public double getSalary()
{
    return salary + bonus; // won't work: salary is private to Employee
}

public double getSalary()
{
    double baseSalary = getSalary(); // still won't work: calls itself forever
    return baseSalary + bonus;
}
  • super.getSalary() calls the superclass method:
public double getSalary()
{
    double baseSalary = super.getSalary();
    return baseSalary + bonus;
}
  • super is not a reference to an object (you cannot assign it to a variable); it is a keyword telling the compiler to call the superclass method.
  • A subclass can add fields, add methods and override methods, but inheritance never takes anything away.

5.1.3 Subclass constructors

public Manager(String name, double salary, int year, int month, int day)
{
    super(name, salary, year, month, day);
    bonus = 0;
}
  • super(...) calls the superclass constructor. The subclass cannot touch private superclass fields, so it must initialise them through a constructor.
  • Before Java 25
    • super(...) had to be the first statement
    • Now code before it runs in the early execution context (chapter 4): apart from assigning uninitialised fields, you cannot access the object under construction.
  • With no explicit super(...), the superclass needs a no-argument constructor, called before the subclass constructor.
  • super has two meanings (call a superclass method, call a superclass constructor), just as this has two (reference to the implicit parameter, call another constructor of the same class).
Manager boss = new Manager("Carl Cracker", 80000, 1987, 12, 15);
boss.setBonus(5000);

var staff = new Employee[3];
staff[0] = boss;
staff[1] = new Employee("Harry Hacker", 50000, 1989, 10, 1);
staff[2] = new Employee("Tony Tester", 40000, 1990, 3, 15);

for (Employee e : staff)
{
    IO.println(e.getName() + " " + e.getSalary());
}
  • Output: Carl Cracker 85000.0, Harry Hacker 50000.0, then the third employee at 40000.0.
  • e.getSalary() picks the right method although the declared type is Employee: when e refers to a Manager, the manager's method runs
    • Polymorphism: a variable can refer to several actual types
    • Dynamic binding: automatic selection of the method at run time.
  • C++ and C# need virtual; in Java dynamic binding is the default, and you opt out with final.
  • From this chapter on, classes are in packages with mostly public methods, as in production code; main stays simple. Run with java InheritanceDemo.java.
// com/horstmann/corejava/Manager.java (Listing 5.2)
package com.horstmann.corejava;

public class Manager extends Employee
{
    private double bonus;

    public Manager(String name, double salary, int year, int month, int day)
    {
        super(name, salary, year, month, day);
        bonus = 0;
    }

    public double getSalary()
    {
        double baseSalary = super.getSalary();
        return baseSalary + bonus;
    }

    public void setBonus(double b)
    {
        bonus = b;
    }
}

5.1.4 Inheritance hierarchies

  • Inheritance can continue:
    • an Executive can extend Manager. All classes descending from a common superclass form an inheritance hierarchy
    • the path from a class up to its ancestors is its inheritance chain.
  • Sibling branches are independent: Programmer and Secretary extending Employee have nothing to do with Manager.
  • Java has no multiple inheritance (Python and C++ do); chapter 6 shows how to recover most of its benefits.

5.1.5 Polymorphism

  • The "is-a" rule:
    • every object of the subclass is an object of the superclass (every manager is an employee, not the reverse)
    • Equivalent form, the substitution principle: you can use a subclass object wherever a superclass object is expected.
Employee e;
e = new Employee(/* ... */); // Employee object expected
e = new Manager(/* ... */);  // OK, Manager can be used as well
  • Object variables are polymorphic. In staff[0] = boss; both refer to the same object, but the compiler treats staff[0] as an Employee:
boss.setBonus(5000);     // OK
staff[0].setBonus(5000); // ERROR: setBonus is not a method of Employee
  • You cannot assign a superclass reference to a subclass variable: Manager m = staff[i]; is an error, since not all employees are managers and a later m.setBonus(...) would fail.
  • Arrays are covariant.
    • Employee[] staff = managers; (where managers is a Manager[]) compiles, and both refer to the same array
    • Then staff[0] = new Employee(...) also compiles, which would smuggle an employee into the managers.
    • To prevent corruption, every array remembers its element type and checks stores. Storing an Employee in a new Manager[10] array throws ArrayStoreException.

5.1.6 Understanding method calls

For a call x.f(args) where x is declared as class C:

  1. Enumerate candidates. The compiler lists all methods named f in C and all accessible methods named f in its superclasses (private superclass methods are not accessible).
  2. Overloading resolution. It picks the unique best match for the argument types: x.f("Hello") chooses f(String) over f(int). No match, or several equally good matches after conversions, is a compile error.
  3. Now name and parameter types are known. The signature is name plus parameter types; a subclass method with the same signature as a superclass method overrides it.
  4. Return type is not part of the signature, but an override must stay compatible. A subclass may return a subtype (covariant return types): Employee.getBuddy() can be overridden as public Manager getBuddy().
  5. Static binding applies when the method is private, static, final or a constructor: the compiler knows exactly which method. Otherwise dynamic binding at run time.
  6. At run time, with actual type D (a subclass of C), the JVM calls D.f(String) if defined, otherwise searches D's superclass, and so on.
    • The search is too slow to repeat for each call, so the JVM precomputes a method table per class, built from the class file plus the superclass table
      • A call is a table lookup
      • For super.f(param) the superclass table is consulted.
Employee:
  getName()          -> Employee.getName()
  getSalary()        -> Employee.getSalary()
  getHireDay()       -> Employee.getHireDay()
  raiseSalary(double) -> Employee.raiseSalary(double)

Manager:
  getName()          -> Employee.getName()
  getSalary()        -> Manager.getSalary()
  getHireDay()       -> Employee.getHireDay()
  raiseSalary(double) -> Employee.raiseSalary(double)
  setBonus(double)   -> Manager.setBonus(double)
  • (Both tables also hold the methods inherited from Object, ignored here.)

  • At run time e.getSalary(): fetch the method table of the actual type of e, look up the defining class for getSalary(), call it.
  • Key property: extensibility without changing existing code.
    • Add an Executive class and the code calling e.getSalary() need not be recompiled
    • Executive.getSalary() is used automatically.
  • An overriding method must be at least as visible as the overridden one: if the superclass method is public, the subclass method must be public too
    • Forgetting public is a common error ("more restrictive access privilege").

5.1.7 Preventing inheritance: final classes and methods

  • A final class cannot be extended:
    • public final class Executive extends Manager
    • A final method cannot be overridden: public final String getName()
    • All methods of a final class are final, but fields are not automatically final.
  • Only one good reason:
    • keep semantics from being changed. Calendar.getTime and setTime are final (the designers own the conversion between Date and calendar state)
    • String is final, so a String reference is certainly a String.
  • Call only final or private methods from a constructor. Otherwise a subclass can override them and see a partially constructed object:
public class Employee
{
    public Employee(String name, double salary, int year, int month, int day)
    {
        this.name = name;
        this.salary = salary;
        hireDay = LocalDate.of(year, month, day);
        IO.println("Constructed " + description());
    }

    public String description()
    {
        return "An employee with a salary of " + salary;
    }
}

public class Executive extends Manager
{
    private String title;

    public Executive(String name, String title, double salary,
        int year, int month, int day)
    {
        super(name, salary, year, month, day);
        this.title = title;
    }

    public String description()
    {
        if (title.length() >= 20)
        {
            return "An executive with an impressive title";
        } else {
            return "An executive with a title of " + title;
        }
    }
}
  • Constructing an Executive calls the Manager constructor, then the Employee constructor, which calls description()
    • Polymorphism picks Executive.description() while title is still null, giving a NullPointerException.

  • C++ differs: calls inside a constructor are not polymorphic (always Employee::getDescription).
  • Since Java 21, compile with -Xlint:this-escape to be warned when a public class's constructor calls a method that is not final or private
    • (The flag name is a bit unfortunate: other ways for this to "escape" are not yet detected.)
  • Some programmers declare everything final unless polymorphism is wanted (C++ and C# default to non-polymorphic)
    • The author finds that extreme but agrees to think carefully about final methods and classes.
  • Inlining and final:
    • early Java users added final hoping to avoid dynamic binding cost
    • A non-overridden short method can be inlined (e.getName() becomes e.name), which helps because CPUs dislike branching
    • Today the JIT knows which classes override what, inlines short hot non-overridden methods, and undoes it if a loaded subclass overrides one (rare).
  • Enumerations and records are always final.

5.1.8 Casting

  • A cast converts a reference:
    • Manager boss = (Manager) staff[0];
    • The only reason is to use an object in its full capacity after its actual type was temporarily forgotten (to call setBonus on an array element).
  • Assigning a subclass reference to a superclass variable promises less, so it is allowed
    • assigning superclass to subclass promises more, so it needs a cast that is checked at run time.
  • A wrong promise (Manager boss = (Manager) staff[1]; where it is a plain employee) throws ClassCastException, ending the program if not caught. So test with instanceof first:
if (staff[i] instanceof Manager)
{
    boss = (Manager) staff[i];
    // ...
}
  • The compiler refuses casts that cannot succeed: String c = (String) staff[i]; is a compile error because String is not a subclass of Employee.
  • Rules: you can cast only within an inheritance hierarchy, and use instanceof before casting down.
  • x instanceof C is false when x is null (no exception).
  • Casting is usually not a good idea:
    • dynamic binding already picks the right getSalary
    • If you want setBonus on plain employees, ask whether the superclass design is flawed
    • Minimise casts and instanceof.
  • Java's cast resembles C's syntax but behaves like C++'s dynamic_cast, except that a failing dynamic_cast yields a null pointer instead of throwing.

5.1.9 Pattern matching for instanceof

  • Since Java 16 you can declare the variable inside the test and skip the cast:
if (staff[i] instanceof Manager boss)
{
    boss.setBonus(5000);
}
  • If staff[i] is a Manager, boss is bound to it; otherwise the test is false and the body is skipped. Prefer this over a cast.
  • A useless pattern is a compile error:
    • if (boss instanceof Employee e) when boss is a Manager
    • The equally useless boss instanceof Employee is allowed for compatibility with Java 1.0.
  • The pattern variable is usable immediately in the same expression, after &&:
if (e instanceof Executive exec && exec.getTitle().length() >= 20)
{
    // ...
}
  • It works because the right side of && runs only if the left is true
    • With || it is a compile error (e instanceof Manager exec || exec.getTitle()...), because the right side runs when the left is false, with nothing bound.
  • With the conditional operator: String title = e instanceof Executive exec ? exec.getTitle() : ""; binds exec after the ? but not after the :.
  • Pattern variables can shadow a field:
class Value
{
    private double v;

    public boolean equals(Object other)
    {
        if (other instanceof LabeledValue v)
        {
            // v is the same as other
        } else {
            // v denotes the field
        }
        return false;
    }
}
  • Record patterns (Java 21) bind variables to the components of a record:
record Point(double x, double y) { }

Point p = new Point(3, 4);
double distance = 0;
if (p instanceof Point(var a, var b))
{
    distance = Math.hypot(a, b);
}
// explicit types: p instanceof Point(double a, double b)

record Circle(Point center, double radius) { }

Circle c = new Circle(p, 2);
if (c instanceof Circle(Point(var a, var b), var r))
{
    // nested record pattern
}

// Java 22: _ marks an unmatched part
if (p instanceof Point(var a, _))
{
    distance = Math.abs(a);
}
  • These are called pattern matching because they resemble type patterns in switch (section 5.9).

5.1.10 Protected access

  • Fields are best private and methods usually public
    • a subclass cannot access private superclass fields. To restrict a member to subclasses (or let subclass methods use a superclass field), declare it protected: if Employee declares hireDay protected, Manager methods can use it.
  • In Java protected also means accessible to any class in the same package
    • An Administrator subclass in a different package can peek at hireDay of Administrator objects only, not of other Employee objects, to prevent subclassing just to gain access.
  • Use protected fields with caution: unknown subclass authors start depending on them, and you can no longer change the implementation, against encapsulation.
  • Protected methods make more sense: a tricky method can be reserved for subclasses that "know their ancestor well". Example: Object.clone (chapter 6).
  • Java's protected is a little less safe than C++'s, since the whole package gets access.

5.2 Object: the cosmic superclass

  • Every class extends Object; you never write extends Object, it is assumed when no superclass is named. Several Object methods appear only with concurrency (chapter 10).

5.2.1 Variables of type Object

Object obj = new Employee("Harry Hacker", 35000);
Employee e = (Employee) obj; // a cast is needed to use it specifically
  • Only the primitive types are not objects. All array types, of objects or primitives, are class types extending Object: obj = staff; and obj = new int[10]; are fine.
  • Many languages have a common root class (Python object, JavaScript Object); C++ classes can be unrelated.

5.2.2 The equals method

  • Object.equals tests whether two references are identical, a reasonable default (for example comparing two PrintStreams makes little sense)
    • Often you want state-based equality.
  • Example (matching name, salary and hire date; in real life compare IDs):
public class Employee
{
    // ...
    public boolean equals(Object otherObject)
    {
        // a quick test to see if the objects are identical
        if (this == otherObject)
        {
            return true;
        }

        // must return false if the explicit parameter is null
        if (otherObject == null)
        {
            return false;
        }

        // if the classes don't match, they can't be equal
        if (getClass() != otherObject.getClass())
        {
            return false;
        }

        // now we know otherObject is a non-null Employee
        Employee other = (Employee) otherObject;

        // test whether the fields have identical values
        return name.equals(other.name)
            && salary == other.salary
            && hireDay.equals(other.hireDay);
    }
}
  • getClass() returns an object's class (details later). To guard against null fields use Objects.equals(a, b): true if both null, false if only one is null, otherwise a.equals(b):
return Objects.equals(name, other.name)
    && salary == other.salary
    && Objects.equals(hireDay, other.hireDay);
  • For classes with few fields, the this == otherObject shortcut may prevent the JVM from inlining equals; consider benchmarking both.
  • In a subclass, call super.equals first (it already checked the class), then compare the new fields:
public class Manager extends Employee
{
    // ...
    public boolean equals(Object otherObject)
    {
        if (!super.equals(otherObject))
        {
            return false;
        }
        // super.equals checked that this and otherObject belong to the same class
        Manager other = (Manager) otherObject;
        return bonus == other.bonus;
    }
}
  • Records get equals automatically,
    • comparing components (two records are equal when the component values are equal)
    • double components compare with Double.equals, not ==, which matters for -0.0 and NaN.

5.2.3 Equality testing and inheritance

  • Should equals return false when classes differ (the getClass test above), or accept subclasses via instanceof? The JLS requires equals to be:
    1. Reflexive: x.equals(x) is true for non-null x.
    2. Symmetric: x.equals(y) is true if and only if y.equals(x) is.
    3. Transitive: if x.equals(y) and y.equals(z) then x.equals(z).
    4. Consistent: unchanged objects give the same result on repeated calls.
    5. x.equals(null) is false for non-null x.
  • Symmetry bites with an instanceof test. If Employee.equals uses instanceof, then e.equals(m) (employee vs manager with the same name, salary and hire date) returns true, so m.equals(e) must also be true, forcing Manager.equals to ignore manager-specific data.

  • Some argue getClass violates the substitution principle, citing AbstractSet.equals (TreeSet and HashSet should compare equal). The author's two scenarios:
    1. If subclasses can have their own notion of equality, symmetry forces the getClass test.
    2. If equality is fixed in the superclass, you can use instanceof and let different subclasses be equal (and should declare equals final).
  • For employees compared by matching fields, two managers with different bonuses must differ, so use getClass
    • If equality used an employee ID, instanceof would suit and Employee.equals should be final.
  • The standard library has over 150 equals methods using a mishmash of instanceof, getClass, catching ClassCastException, or nothing
    • The java.sql.Timestamp docs note "with some embarrassment" that it is stuck: it extends java.util.Date (whose equals uses instanceof), and no override can be both symmetric and accurate.
  • The set example is itself a cautionary tale:
Set<String> x = new HashSet<>();
x.add("Hello");
x.add("World");
Set<String> y = new TreeSet<>(String.CASE_INSENSITIVE_ORDER);
y.add("Hello");
y.add("WORLD");

x.equals(y); // false
y.equals(x); // true
  • TreeSet compares by sort order, not equals, and under case-insensitive order "World" and "WORLD" are the same.

A recipe for a good equals method:

  1. Name the explicit parameter otherObject (you will cast it to a variable called other).
  2. Test whether this == otherObject: return true;. An optimisation, worthwhile for complex state, sometimes counterproductive.
  3. if (otherObject == null) return false; (required).
  4. Compare classes. If the semantics of equals can change in subclasses use the getClass test:
if (getClass() != otherObject.getClass())
{
    return false;
}
ClassName other = (ClassName) otherObject;

If the same semantics hold for all subclasses, use instanceof (it also binds other, no cast needed):

if (!(otherObject instanceof ClassName other))
{
    return false;
}
  1. Compare the fields: == for primitives, Objects.equals for object fields:
return field1 == other.field1
    && Objects.equals(field2, other.field2)
    && /* ... */ true;
  1. In a subclass, include a call to super.equals(other).
  2. For array fields use Arrays.equals (and Arrays.deepEquals for multidimensional arrays).

A common mistake: wrong parameter type.

public class Employee
{
    public boolean equals(Employee other) // does NOT override Object.equals
    {
        return other != null
            && getClass() == other.getClass()
            && Objects.equals(name, other.name)
            && salary == other.salary
            && Objects.equals(hireDay, other.hireDay);
    }
}
  • The parameter type Employee makes this an unrelated overload of equals, not an override
    • Protect yourself with @Override: @Override public boolean equals(Object other)
    • If you write @Override public boolean equals(Employee other) the compiler reports an error because nothing is overridden.

java.util.Arrays (1.2): static boolean equals(xxx[] a, xxx[] b) (5.0) true if lengths and elements match (component type Object or any primitive). java.util.Objects (7): static boolean equals(Object a, Object b) true if both null, false if exactly one is, else a.equals(b).

5.2.4 The hashCode method

  • A hash code is an integer derived from an object, scrambled so distinct objects probably get different values
    • Examples from String (Table 5.1): "Hello" is 69609650, "Harry" is 69496448, "Hacker" is -2141031506.
  • String computes it as a rolling sum:
int hash = 0;
for (int i = 0; i < length(); i++)
{
    hash = 31 * hash + charAt(i);
}
  • Object defines a default identity hash code that depends on the JVM (from the memory address)
    • Table 5.2: the strings s and t (both "Ok", one made with new String) have the same hash code 2556 because string hashes derive from content, while sb (20526976) and tb (20527144) differ because StringBuilder has no hashCode override.
  • If you redefine equals, redefine hashCode
    • for objects that may go into a hash table (chapter 9)
    • Return an integer, possibly negative, combining field hashes so different objects scatter widely.
public int hashCode()
{
    return 7 * Objects.hashCode(name)
        + 11 * Double.hashCode(salary)
        + 13 * Objects.hashCode(hireDay);
}
  • Use null-safe Objects.hashCode (0 for null) and static Double.hashCode to avoid creating a Double.
  • If fields have small ranges you need as many distinct codes as possible
    • For dates, 7 * year + 11 * month + 13 * day collides a lot, while 31 * 12 * year + 31 * month + day is a perfect hash for a reasonable year range (the real LocalDate.hashCode handles years ±999,999,999 and is more complex).
  • Simplest: Objects.hash(name, salary, hireDay) combines all field hashes.
  • Array fields:
    • an array's own hash code ignores its elements
    • Use Arrays.hashCode (overloads for primitives and objects) or Arrays.deepHashCode
    • It works like String.hashCode ("multiply by 31 and add") with a twist: a zero-length array has hash code 1 to differ from null (0):
public static int hashCode(Object[] a)
{
    if (a == null)
    {
        return 0;
    }

    int result = 1; // starting at 1, not 0

    for (Object element : a)
    {
        result = 31 * result + (element == null ? 0 : element.hashCode());
    }

    return result;
}
  • Objects.hash calls Arrays.hashCode, so Objects.hash(x) equals 31 + x.hashCode().
  • Records get hashCode automatically, derived from component hashes. The exact algorithm is unspecified; OpenJDK combines with multiply-by-31-and-add starting at zero.
  • Contract: equals and hashCode must agree. If x.equals(y) then x.hashCode() == y.hashCode(). If equals compares IDs, hashCode must hash the IDs, not names or addresses.

java.lang.Object (1.0): int hashCode(). java.util.Objects (7): static int hash(Object... objects), static int hashCode(Object a). Wrapper classes (Integer, Long, Short, Byte, Double, Float, Character, Boolean): static int hashCode(xxx value) (8). java.util.Arrays (1.2): static int hashCode(xxx[] a) (5.0).

5.2.5 The toString method

  • toString returns a string representing the object. Convention: class name, then field values in square brackets, for example java.awt.Point[x=10,y=20].
  • Better than a hard-wired class name: getClass().getName(), so it works for subclasses:
public String toString()
{
    return getClass().getName()
        + "[name=" + name
        + ",salary=" + salary
        + ",hireDay=" + hireDay
        + "]";
}
  • A subclass calls super.toString() and adds its fields:
public class Manager extends Employee
{
    // ...
    public String toString()
    {
        return super.toString()
            + "[bonus=" + bonus
            + "]";
    }
}
  • A manager prints like Manager[name=...,salary=...,hireDay=...][bonus=...].
  • It is ubiquitous because + with a string calls toString automatically ("The current position is " + p)
    • "" + x works like x.toString() and even for primitives
    • IO.println(x) calls x.toString() too.
  • Object.toString prints the class name and hash code, so IO.println(System.err) gives java.io.PrintStream@2f6684 (the implementor did not override it).
  • Arrays inherit Object.toString
    • in an archaic format: "" + luckyNumbers gives "[I@1a46e30" ([I means int array)
    • Use Arrays.toString(luckyNumbers) ("[2, 3, 5, 7, 11, 13]") and Arrays.deepToString for arrays of arrays.
  • Great for logging:
    • IO.println("Current position = " + position);, though a logger is better (chapter 7): logger.log(INFO, "Current position = " + position);
    • Add toString to every class you write. Records already get one listing the class name and component names and values.
  • Unmodified behaviour

5.3 Generic array lists

  • C and C++ fix array sizes at compile time
    • Java lets you set the size at run time (new Employee[actualSize]), but you still cannot easily resize. ArrayList adjusts its capacity automatically.
  • ArrayList is a generic class with a type parameter in angle brackets, ArrayList<Employee>; you can use it without knowing how generics are defined (chapter 8).

5.3.1 Declaring array lists

ArrayList<Employee> staff = new ArrayList<Employee>();
var staff2 = new ArrayList<Employee>();           // with var, avoid repeating the type
ArrayList<Employee> staff3 = new ArrayList<>();   // "diamond" syntax
  • Diamond <>:
    • the compiler infers the type argument from where the new value goes (a variable, parameter or return type)
    • Do not combine var with the diamond: var elements = new ArrayList<>(); yields ArrayList<Object>.
  • Before Java 5 there were no generics:
    • ArrayList held Objects
    • Using it without <...> is a raw type, the type parameter erased
    • Vector is the older dynamic array; ArrayList is more efficient and there is no good reason to use Vector now.
  • add appends. When the internal array of references is full, the list allocates a bigger array and copies.
  • If you know the size, call staff.ensureCapacity(100) or construct with new ArrayList<>(100) so the first 100 adds do not reallocate.
  • Capacity is not size. new ArrayList<>(100) holds no elements yet; new Employee[100] has 100 usable slots. size() is the number of elements (the counterpart of a.length).
  • trimToSize() shrinks storage to the current size; use it only when no more elements will be added (adding later moves the block again).
  • C++ comparison:
    • like vector, but C++ overloads [] and copies by value (a = b copies all elements)
    • Java has no operator overloading, and a = b makes both refer to the same list.

java.util.ArrayList<E> (1.2): ArrayList<E>(), ArrayList<E>(int initialCapacity), boolean add(E obj) (always true), int size(), void ensureCapacity(int capacity), void trimToSize().

5.3.2 Accessing array list elements

  • ArrayList is a library class, not part of the language, so no []: use get and set.
staff.set(i, harry); // like a[i] = harry
Employee e = staff.get(i); // like Employee e = a[i]
  • Do not call set(i, x) until the size exceeds i:
    • with new ArrayList<Employee>(100) (capacity 100, size 0), list.set(0, x) fails
    • Use add to fill, set only to replace an existing element.
  • The raw ArrayList.get returned Object, forcing a cast (Employee) staff.get(i), and its add and set accepted any type: staff.set(i, "Harry Hacker") compiled without warning and failed only on retrieval
    • ArrayList<Employee> catches that at compile time.
  • Best of both worlds: build a list, then copy it to an array:
var list = new ArrayList<X>();
// while (...) { x = ...; list.add(x); }
var a = new X[list.size()];
list.toArray(a);
  • Insert or remove in the middle:
    • staff.add(n, e) shifts the elements at n and above up (growing if needed)
    • Employee e = staff.remove(n) shifts them down and returns the removed element. These are not efficient
    • for many elements with frequent middle changes consider a linked list (chapter 9).
  • "For each" works: for (Employee e : staff) equals an index loop with staff.get(i).
  • Listing 5.6 (ArrayListDemo.java) is the chapter 4 EmployeeDemo with ArrayList<Employee>: no array size to specify, add for any number of elements, size() instead of length, a.get(i) instead of a[i].

5.3.3 Compatibility between typed and raw array lists

  • Always use type parameters in your own code. For legacy code such as:
public class EmployeeDB
{
    public void update(ArrayList list) { /* ... */ }
    public ArrayList find(String query) {
        /* ... */ return null;
    }
}
  • Passing a typed ArrayList<Employee> to update compiles with no warning, but update might add non-Employee objects, failing later when retrieved
    • That is the pre-generics situation: the VM's integrity is not at risk, but you get no compile-time checks.
  • The reverse, ArrayList<Employee> result = employeeDB.find(query);, gives a warning (see it with -Xlint:unchecked)
    • A cast (ArrayList<Employee>) ... gives another warning, "misleading cast".
  • Reason:
    • for compatibility the compiler translates typed lists into raw ArrayList after checking the types
    • the VM has no type parameters, so (ArrayList) and (ArrayList<Employee>) carry out identical run-time checks (type erasure).
  • Study the warnings and when satisfied tag the receiving variable:
@SuppressWarnings("unchecked") ArrayList<Employee> result
    = (ArrayList<Employee>) employeeDB.find(query);

5.4 Object wrappers and autoboxing

  • Each primitive type has a wrapper class:
    • Integer, Long, Float, Double, Short, Byte, Character, Boolean (the first six extend Number)
    • Wrappers are immutable and final.
  • A type argument cannot be primitive, so there is no ArrayList<int>
    • use ArrayList<Integer>. It is far less efficient than int[] (each value is a separate object), so use it only for small collections where convenience wins.
  • Autoboxing:
    • list.add(3); becomes list.add(Integer.valueOf(3));
    • Unboxing: int n = list.get(i); becomes int n = list.get(i).intValue();
    • It also works in arithmetic: Integer n = 3; n++; unboxes, increments and boxes back
    • ("Boxing" is a metaphor borrowed from C#.)

  • They differ in identity: == on wrappers compares memory locations.
Integer a = 1000;
Integer b = 1000;
if (a == b) { /* probably false */ }
  • The spec requires some values to be wrapped into fixed shared objects: boolean, byte, char up to 127, short, and int from -128 to 127
    • With both set to 100 the comparison must succeed
    • Never rely on wrapper identity: do not compare with == and do not use wrappers as locks (chapter 10).
  • Do not use wrapper constructors (deprecated for removal): use Integer.valueOf(1000), never new Integer(1000), or autoboxing.
  • For the special values, Double.equals beats ==: 0.0 == -0.0 but Double.valueOf(-0.0).equals(Double.valueOf(0.0)) is false
    • Double.NaN != Double.NaN but Double.valueOf(Double.NaN).equals(Double.valueOf(Double.NaN)) is true. equals is an equivalence relation
    • == on doubles is not.
  • Subtleties:
    • Unboxing null throws NullPointerException: Integer n = null; IO.println(2 * n);.
    • In a conditional expression mixing Integer and Double, the Integer is unboxed, promoted to double, and boxed to Double:
Integer n = 1;
Double x = 2.0;
IO.println(true ? n : x); // prints 1.0
  • The compiler, not the VM, inserts boxing and unboxing into the bytecode.
  • Future: Java plans value types, user-defined types like primitives whose values are not stored inside objects (a Point with two doubles would be a 16-byte block you can copy but not reference), and wrappers are planned to become value classes.
  • Wrappers also host handy methods: int x = Integer.parseInt(s); is a static method, unrelated to Integer objects but placed there.
  • Constants:
    • MIN_VALUE and MAX_VALUE for integral wrappers (Integer.MIN_VALUE is -2147483648, Integer.MAX_VALUE is 2147483647)
    • For Double and Float, MIN_VALUE is the smallest positive value, so for the largest value among possibly negative inputs use -Double.MAX_VALUE (not Double.MIN_VALUE):
double largest = -Double.MAX_VALUE; // do NOT use Double.MIN_VALUE
while (in.hasNextDouble())
{
    largest = Math.max(largest, in.nextDouble());
}
  • (The book's printed snippet declares int largest = -Double.MAX_VALUE;, which does not compile; double is the intended type.)
  • Wrappers cannot make a method that modifies a numeric parameter: parameters are passed by value, and Integer is immutable, so triple(Integer x) cannot work.

5.5 Methods with a variable number of arguments

  • Varargs: String.formatted(Object... args) is called as "%d".formatted(n) or "%d %s".formatted(n, "widgets"). The ... is part of the Java code.
  • For the implementor, Object... is exactly Object[]
    • The compiler bundles the arguments into an array, autoboxing as needed: "%d %s".formatted(new Object[] { Integer.valueOf(n), "widgets" }).
  • You can define your own with any type, even primitives:
public static double max(double... values)
{
    double largest = Double.NEGATIVE_INFINITY;
    for (double v : values)
    {
        if (v > largest)
        {
            largest = v;
        }
    }
    return largest;
}

double m = max(3.1, 40.4, -5); // compiler passes new double[] { 3.1, 40.4, -5 }
  • You may pass an array instead of separate arguments, so a method whose last parameter is an array can become varargs without breaking existing callers
    • Even public static void main(String... args) is legal.

5.6 Abstract classes

  • Higher in the hierarchy, classes become more general and abstract: the ancestor is a basis for other classes rather than something you instantiate
    • Example: Person above Employee and Student, so the common getName moves up.
  • What should Person.getDescription() return when Person knows only a name? Instead of an empty string, declare it abstract, with no implementation
    • A class with an abstract method must itself be declared abstract.
public abstract class Person
{
    private String name;

    public Person(String name)
    {
        this.name = name;
    }

    public abstract String getDescription();

    public String getName()
    {
        return name;
    }
}
  • Abstract classes can have fields and concrete methods; always move common fields and methods up, abstract or not.
  • A subclass can leave some or all abstract methods undefined (then it must be abstract too) or define them all (then it is concrete)
    • A class can be declared abstract even with no abstract methods.
  • Abstract classes cannot be instantiated:
    • new Person("Vince Vu") is an error
    • You can still declare variables of the abstract type, referring to a concrete subclass object: Person p = new Student("Vince Vu", "Economics");.
  • Python uses @abstractmethod; C++ calls them pure virtual functions (= 0).
public class Student extends Person
{
    private String major;

    public Student(String name, String major)
    {
        super(name);
        this.major = major;
    }

    public String getDescription()
    {
        return "a student majoring in " + major;
    }
}

    • Employee now extends Person (description "an employee with a salary of $%.2f".formatted(salary)).
  • "Isn't that a call to an undefined method?"
    • No: p never refers to a Person object (it cannot be built) but to a concrete subclass where getDescription is defined
    • And you must declare getDescription in Person, or the compiler would not let you call it on a Person variable
    • Abstract methods appear most often inside interfaces (chapter 6).

5.7 Enumeration classes

  • An enum: public enum Size { SMALL, MEDIUM, LARGE, EXTRA_LARGE }. Qualify constants (Size.SMALL) except:

    1. inside the methods of the enumeration itself
    2. in a case of a switch whose selector is an enum (case SMALL -> "S";)
    3. after a static import: import static com.horstmann.util.Size.*; then Size s = SMALL;

  • You cannot statically import constants of an enum in the default package.

  • (The book's code line import static Size.*; is the illegal form for a default-package enum.)

  • The type from an enum declaration is a class with exactly four instances; you cannot construct more. So compare enum values with ==, never equals.

  • A trailing comma after the last constant is allowed (handy when more values will be added):

public enum Size
{
    SMALL,
    MEDIUM,
    LARGE,
    EXTRA_LARGE,
    XXL,
    // add more values here and put a comma after each
}
  • All enums are subclasses of the abstract class Enum and inherit its methods:
    • name() returns the constant's name (final); toString() returns the name by default but can be overridden.
    • valueOf is the converse: Size s = Enum.valueOf(Size.class, "SMALL");
    • values() (static, per enum) returns an array of all constants: Size[] values = Size.values();
    • ordinal() is the zero-based position: Size.MEDIUM.ordinal() is 1.
  • Enums can have constructors, fields and methods
    • The constructor runs only when the constants are created and is always private (declaring it public or protected is a syntax error)
    • When an enum has members, end the constant list with ;:
public enum Size
{
    SMALL("S"), MEDIUM("M"), LARGE("L"), EXTRA_LARGE("XL");

    private final String abbreviation;

    Size(String abbreviation) // automatically private
    {
        this.abbreviation = abbreviation;
    }

    public String getAbbreviation()
    {
        return abbreviation;
    }
}
  • You can override a method in a single constant (uncommon):
    • EXTRA_LARGE { public String toString() { return "XL"; } }; makes EXTRA_LARGE an instance of an anonymous subclass of Size
    • otherwise enums cannot be subclassed.
  • An enum with no instances (just a leading ;) cannot be instantiated: a way to mark a utility class with only static methods:
public enum FileUtils
{
    ; // No instances

    public static String extension(String filename)
    {
        int n = filename.lastIndexOf(".");
        return n >= 0 ? filename.substring(n + 1) : "";
    }
}
  • Limitation:
    • an enum constructor cannot run a switch on the instance being constructed (switch (this) is an error)
    • The cause is the implementation: each switch consults an array mapping the enum's current ordinal values to those at compile time, built only after the instances exist
    • In a regular method such a switch is fine.
  • Enum has a type parameter ignored here: Size really extends Enum<Size>, used by compareTo (chapter 6; type parameters in chapter 8).

5.8 Sealed classes

  • Unless final, anyone can subclass a class
    • For more control, take a custom JSON library: a JSON value is an array, number, string, Boolean, object or null
    • Model it with an abstract JSONValue and final subclasses (JSONArray, JSONNumber, ...)
    • Final subclasses stop further subclassing of those, but cannot stop another subclass of JSONValue.
  • Why care? Code like this assumes it knows all direct subclasses:
JSONValue v = null; // some value
if (v instanceof JSONArray a)
{
    // ...
}
else if (v instanceof JSONNumber n)
{
    // ...
}
// ... JSONString, JSONBoolean, JSONObject
else
{
    // must be JSONNull
}
  • A sealed class controls which classes may inherit from it (preview in Java 15, final in Java 17):
public abstract sealed class JSONValue
    permits JSONArray, JSONNumber, JSONString, JSONBoolean, JSONObject, JSONNull
{
    // ...
}
  • A non-permitted subclass (public class JSONComment extends JSONValue) is an error. Sealed classes model domain constraints accurately (JSON has no comments).
  • Rules for permitted subclasses:
    • They must be accessible: not private nested classes, not package-visible classes from another package.
    • Public permitted subclasses must be in the same package (or the same module if you use modules, chapter 12).
    • Without a permits clause,
      • all direct subclasses must be declared in the same file
      • Since a file has at most one public class this suits non-public subclasses, but public inner classes can work (chapter 6).
  • Compile-time exhaustiveness checking is a key motivation. With switch patterns the compiler knows no default is needed:
public String type()
{
    return switch (this)
    {
        case JSONArray _ -> "array";
        case JSONNumber _ -> "number";
        case JSONString _ -> "string";
        case JSONBoolean _ -> "boolean";
        case JSONObject _ -> "object";
        case JSONNull _ -> "null";
        // No default needed here
    };
}
  • This does not look very OO (each class could supply its own type() polymorphically, best for open-ended hierarchies), but for a fixed set of classes one method with all alternatives is often more convenient.
  • A subclass of a sealed class need not be final
    • Exhaustiveness only needs the direct subclasses, so reorganise (Figure 5.3): JSONValue permits JSONObject, JSONArray, JSONPrimitive, and JSONPrimitive is sealed again, permits JSONString, JSONNumber, JSONBoolean, JSONNull.
  • A subclass of a sealed class must declare one of sealed, final or non-sealed. non-sealed is the first Java keyword with a hyphen. sealed is a contextual keyword (still usable as an identifier: int sealed = 1;)
    • hyphenated non-sealed avoids clashes, except with subtraction (non = non-sealed;).
  • Why non-sealed? An XML Node with six direct subclasses stays sealed, but Element is opened for arbitrary subclasses:
public abstract sealed class Node permits Element, Text, Comment,
    CDATASection, EntityReference, ProcessingInstruction
{
    // ...
}

public non-sealed class Element extends Node
{
    // ...
}

public class HTMLDivElement extends Element
{
    // ...
}
  • Sealed interfaces work exactly the same way, controlling direct subtypes (interfaces are chapter 6).

5.9 Pattern matching

  • instanceof with a binding variable is convenient, but a chain of if statements must set the result in each branch. The pattern-matching switch is simpler:
Employee e = null; // some employee
String description = switch (e)
{
    case Executive exec -> "An executive with a title of " + exec.getTitle();
    case Manager _ -> "A manager who deserves a bonus";
    default -> "A lowly employee with a salary of " + e.getSalary();
};
  • Note the symmetry between e instanceof Executive exec and case Executive exec. Since Java 22 an underscore replaces an unused variable (case Manager _).
  • You generally cannot combine type patterns in one case, except when none declares a variable: case Employee _, Manager _ -> "Not an executive".
  • The expression form with no fallthrough is usually most natural; the statement and fallthrough forms also accept type patterns.
  • Java 25 primitive type patterns (preview): case byte b -> ... matches an integer from -128 to 127.

5.9.1 Null handling

  • The classic switch is null-hostile: a null selector throws NullPointerException. Add case null:
String description = switch (e)
{
    case Executive exec -> "An executive with a title of " + exec.getTitle();
    case Manager m -> "A manager who deserves a bonus";
    case null -> "No employee";
    default -> "A lowly employee with a salary of " + e.getSalary();
};
  • You can combine case null only with default:
    • case null, default -> "No free parking";
    • case _ is not allowed as a default, deliberately, so you need not remember whether it covers null.

5.9.2 Guards

  • A guard adds a condition with the restricted keyword when, and can use the pattern's variable:
case Executive exec when exec.getTitle().length() >= 20 ->
    "An executive with an impressive title";
  • If the guard fails, the next case is tried; if it throws, the switch throws. Guards shine with record patterns:
String description = switch (p)
{
    case Point(var x, var y) when x == 0 && y == 0 -> "origin";
    case Point(var x, _) when x == 0 -> "on x-axis";
    case Point(_, var y) when y == 0 -> "on y-axis";
    default -> "not on either axis";
};
  • A record pattern calls the component accessors; if a (custom) accessor throws, the switch throws a MatchException.

5.9.3 Exhaustiveness

  • A switch expression must be exhaustive: a case for every possible selector value. Ways to achieve it:
    1. cases for every instance of an enum
    2. unguarded type patterns covering every subtype of a sealed type
    3. an unguarded type pattern of the selector type
    4. a default clause
  • Guarded patterns do not count,
    • since the compiler cannot evaluate them: two Executive cases guarded by >= 20 and < 20 are not exhaustive
    • rewrite the second as an unguarded case Executive exec or add default.
  • If a sealed hierarchy or enum is later changed, a previously exhaustive switch may no longer be, and a non-matching selector throws MatchException.
  • A classic switch statement need not be exhaustive, but an enhanced switch statement must be: one with a pattern, case null, or a selector type other than a primitive, wrapper, String or enum
    • For "do nothing" add default -> {} (no fallthrough) or default: break;.
  • null is not required for exhaustiveness: an exhaustive switch without case null throws NullPointerException for a null selector.
  • This is a problem for nested records:
record Box<T>(T contents) { }

Box<Box<String>> doubleBoxed = null; // some value
String unboxed = switch (doubleBoxed)
{
    case Box(Box(String s)) -> s;
};
  • null selector: NullPointerException
    • new Box<>(new Box<>(null)): the result is null
    • But new Box<>(null) causes a MatchException: a case like "Box(b) where b == null" would be needed, but the exhaustiveness checker ignores null.

5.9.4 Dominance

  • Constant cases are disjoint, so order does not matter
    • with patterns, cases are checked in order and the first match wins. A case that can never match because of an earlier one is a compile error (the earlier case dominates it):
String description = switch (e)
{
    case Employee _ -> "A lowly employee with a salary of " + e.getSalary();
    case Manager m -> "A manager who deserves a bonus"; // ERROR: dominated
};
  • Fine points:
    • Guarded patterns are not used for dominance (the compiler cannot compare >= 20 with >= 30).
    • default does not dominate constant cases, but default dominates case null even though it does not cover it.
    • Putting default before constant cases is legal but a poor idea: always put it last.

5.9.5 Patterns and constants

  • No constants inside record patterns: case Point(0, y) is an error; use a guard: case Point(x, y) when x == 0.
  • Numeric constant patterns are allowed only when the selector is int, short, char, byte (or wrappers)
    • string constants only for a String selector. With an Object selector, case 0 and case "" are errors
    • use case Integer i when i == 0 and case String s when s.equals("null").
  • Enum constants are different: the selector type merely has to be a supertype of the enum (Object, Enum, or an interface): case DayOfWeek.FRIDAY -> "TGIF"; is fine with an Object selector.

5.9.6 Variable scope and fallthrough

(Skip if you never use fallthrough.)

  • A pattern variable's scope extends to the end of its case (guard and statements after the :), not into the next case, since execution can enter that case when the object is not a String:
switch (obj)
{
    case String s when s.length() == 0:
        IO.println("empty string"); // scope of s ends here
    default:
        IO.println(obj.toString());
}
  • You cannot fall into a type pattern that binds a variable:
    • falling from case String s when s.length() > 0: into case Integer n: would leave n unbound (error)
    • You can fall into a pattern with an unnamed variable: case String _:.
  • Since Java 1.0 a variable declared in a case body is scoped to the end of the whole switch, which was never useful: String t = s; in one case then IO.println(t) in default: is an error ("may not have been initialised").

    • Listing 5.14 (RecordPatternDemo.java) classifies a random Point as origin, on the x-axis, on the y-axis or neither using record patterns with guards.

5.10 Reflection

  • The reflection library lets programs manipulate Java code dynamically, supporting UI builders, object-relational mappers and other tools
    • A program that analyses classes is reflective
    • Uses:
    • analyse the capabilities of classes at run time
    • inspect objects at run time, for example one toString that works for all classes
    • write generic array manipulation code
    • use Method objects like function pointers in C++
  • It is powerful and complex and mainly of interest to tool builders; application programmers can skip it at first.

5.10.1 The Class class

  • The JVM keeps run-time type identification for every object (used to pick methods). You can read it through a class confusingly named Class
    • Object.getClass() returns a Class instance.
Employee e = null; // some employee
Class cl = e.getClass();
IO.println(e.getClass().getName() + " " + e.getName()); // Employee Harry Hacker, or Manager Harry Hacker for a manager
  • Class names include the package: new Date().getClass().getName() is "java.util.Date".
  • Three ways to get a Class object:
    1. getClass() on an object.
    2. Class.forName(String className): for names only known at run time; throws a checked exception if the class is not found (see 5.10.2).
    3. T.class for any type T or void: Date.class, int.class, Double[].class. A Class object really describes a type (int is not a class, but int.class exists).
String className = "java.util.Date";
Class cl = Class.forName(className);
Class cl1 = Date.class;
Class cl2 = int.class;
Class cl3 = Double[].class;
  • Class is generic (Employee.class is Class<Employee>); you can mostly ignore the parameter and use the raw type (chapter 8).
  • Odd array names: Double[].class.getName() is "[Ljava.lang.Double;" and int[].class.getName() is "[I".
  • The JVM keeps a unique Class object per type, so compare with ==: e.getClass() == Employee.class
    • Unlike e instanceof Employee, this fails for instances of subclasses such as Manager
    • It also fails for anonymous subclasses, for example an enum constant that overrides a method: Size.EXTRA_LARGE.getClass() != Size.class.
  • Constructing an instance reflectively:
var className = "java.util.Date";
// or any other name of a class with a no-arg constructor
Class cl = Class.forName(className);
Object obj = cl.getConstructor().newInstance();
  • getConstructor throws if there is no no-argument constructor (other constructors in 5.10.7).
  • The old Class.newInstance is deprecated: it rethrows constructor exceptions as they are, bypassing compile-time checking of checked exceptions, whereas Constructor.newInstance wraps them in an InvocationTargetException.
  • Class resembles C++'s type_info and Python's type: more versatile than C++, less flexible than Python (where classes can be modified after declaration).

java.lang.Class (1.0): static Class forName(String className), Constructor getConstructor(Class... parameterTypes) (1.1). java.lang.reflect.Constructor (1.1): Object newInstance(Object... initargs). java.lang.Throwable (1.0): void printStackTrace().

5.10.2 A primer on declaring exceptions

  • A failing program can "throw an exception", more flexible than terminating because a handler can catch it
    • With no handler the program terminates with a message naming the exception type (as with a null reference or out-of-bounds index)
    • Full coverage in chapter 7.
  • Unchecked exceptions
    • (bounds errors, null references): the compiler does not require handlers, since you should avoid those mistakes. Checked exceptions: the compiler checks that you are prepared for them
    • used for errors you cannot prevent, such as Class.forName with a class that may not exist.
  • Simplest strategy: add throws Exception to any method containing a statement that may throw a checked exception (and to its callers, including main):
public static void doSomethingWithClass(String name) throws Exception
{
    Class cl = Class.forName(name); // might throw an exception
    // do something with cl
}
  • If it occurs, main ends with a stack trace. The compiler complains whenever you call a method that threatens a checked exception, so you can find them easily.

5.10.3 Resources

  • Classes often have associated data:
    • images, sounds, text with message strings and button labels
    • In Java such a file is a resource
    • Example: a dialog's text read from about.txt instead of hard-coded (so the next edition's title and year are easy to change), packaged in the JAR.
  • Class helps locate resources:
    1. Get the Class object of a class with a resource (ResourceDemo.class).
    2. For methods that accept URLs (such as ImageIcon): URL url = cl.getResource("about.png");.
    3. Otherwise use getResourceAsStream for an input stream.
  • The JVM knows where a class lives and searches for the resource in the same location: if ResourceDemo is in package resources, put the icon in the same directory as its class file
    • You can also give a relative path (data/about.txt) or an absolute path (/images/about.gif).
  • Resource loading only automates finding files
    • interpreting contents is up to the program. Another common use is internationalisation: language-dependent strings in resource files, one per language (Volume II, chapter 7).
  • Listing 5.15 (ResourceDemo.java): loads an image with getClass().getResource("/images/about.gif"), reads data/about.txt and data/title.txt with getResourceAsStream(...).readAllBytes(), and shows them in a JOptionPane dialog
    • Build and run:
$ javac v1ch05/resources/ResourceDemo.java
$ jar cvfe ResourceDemo.jar v1ch05.resources.ResourceDemo \
    v1ch05/resources/*.class images/*.gif v1ch05/resources/data/*.txt
$ java -jar ResourceDemo.jar
  • Move the JAR elsewhere and rerun to confirm it reads the resources from the JAR, not the current directory.

java.lang.Class (1.0): URL getResource(String name) (1.1), InputStream getResourceAsStream(String name) (1.1): find the resource in the same place as the class; return null if not found (no exception for I/O errors).

5.10.4 Using reflection to analyse the capabilities of classes

  • In java.lang.reflect, Field, Method and Constructor describe fields, methods and constructors. All have getName()
    • Field has getType() (a Class)
    • Method and Constructor report parameter types, and Method the return type.
  • All three have getModifiers(), an int of bit flags decoded by the static methods of Modifier (isPublic, isPrivate, isFinal, ..., and Modifier.toString)
    • Alternatively accessFlags() returns a set of AccessFlag values: m.accessFlags().contains(AccessFlag.STATIC).
  • getFields, getMethods, getConstructors
    • return public members, including those of superclasses
    • getDeclaredFields, getDeclaredMethods, getDeclaredConstructors return all members declared in the class itself (private, package, protected too) but not inherited ones.
  • Listing 5.16 (ReflectionDemo.java) prompts for a class name (or reads the first argument) and prints its signature: modifiers, sealed/enum/record/interface/class, extends, interfaces, permitted subclasses, then constructors, methods and fields
    • For java.lang.Double it prints public final class java.lang.Double extends java.lang.Number { ... with constructors, methods such as public static native long doubleToRawLongBits(double);, and fields like POSITIVE_INFINITY and private final double value;.
  • Remarkable: it can analyse any class the interpreter can load, not only classes known at compile time. Chapter 6 uses it to peek inside compiler-generated inner classes.
// core of ReflectionDemo: print the fields of any class
public static void printFields(Class cl)
{
    Field[] fields = cl.getDeclaredFields();

    for (Field f : fields)
    {
        Class type = f.getType();
        String name = f.getName();
        IO.print("   ");
        String modifiers = Modifier.toString(f.getModifiers());
        if (modifiers.length() > 0)
        {
            IO.print(modifiers + " ");
        }
        IO.println(type.getName() + " " + name + ";");
    }
}

5.10.5 Using reflection to analyse objects at run time

  • To read field contents of objects not known at compile time: f.get(obj) on a Field f returns the field's current value in obj.
var harry = new Employee("Harry Hacker", 50000, 10, 1, 1989);
Class cl = harry.getClass(); // the class object representing Employee
Field f = cl.getDeclaredField("name"); // the name field of the Employee class
Object v = f.get(harry); // the String "Harry Hacker"

  • Problem: name is private, so get and set throw IllegalAccessException: Java's security mechanism lets you discover fields but not read or write them without permission.

  • Reflection respects access control by default, but setAccessible(true) on a Field, Method or Constructor overrides it: f.setAccessible(true); // now OK to call f.get(harry).

  • setAccessible belongs to AccessibleObject, the common superclass of Field, Method and Constructor. It exists for debuggers, persistent storage and similar mechanisms.

  • With Java 17 or higher,

    • setAccessible on JDK internals throws InaccessibleObjectException
    • To keep the demo running, open the java.util and java.lang packages of the java.base module to the unnamed module (details in chapter 12):
$ java --add-opens java.base/java.util=ALL-UNNAMED \
    --add-opens java.base/java.lang=ALL-UNNAMED \
    v1ch05/objectAnalyzer/ObjectAnalyzerDemo.java
  • With reflective access you can also set fields: f.set(obj, value) works even for final fields, but record components cannot be set by reflection.
  • Future libraries may use variable handles (VarHandle, like a Field bound to one class) instead
    • Obtaining one needs a Lookup object created in a module that has permission (a method calling MethodHandles.lookup() captures the caller's access rights), so one module can grant another access to private members:
public Object getFieldValue(Object obj, String fieldName, Lookup lookup)
    throws NoSuchFieldException, IllegalAccessException
{
    Class cl = obj.getClass();
    Field field = cl.getDeclaredField(fieldName);
    VarHandle handle = MethodHandles.privateLookupIn(cl, lookup)
        .unreflectVarHandle(field);
    return handle.get(obj);
}
  • A generic toString (Listing 5.17 and 5.18): ObjectAnalyzer.toString(Object) uses getDeclaredFields, setAccessible and recursion on each value.
    • Cycles of references would recurse forever, so it records visited objects (printing ... for repeats).
    • Arrays need a different approach (next section): it uses cl.isArray(), getComponentType() and Array.get.
    • It walks up superclasses (cl = cl.getSuperclass()) so inherited fields appear, skips static fields, and prints primitives directly.
  • Example: new ObjectAnalyzer().toString(squares) for an ArrayList<Integer> of the first five squares prints the elementData array (with the five Integer values then null slots), size=5 and modCount=5.
  • You can use it as public String toString() { return new ObjectAnalyzer().toString(this); }, but showing arbitrary fields needs flags that can compromise security.

5.10.6 Using reflection to write generic array code

  • The java.lang.reflect.Array class creates arrays dynamically; Arrays.copyOf uses it. A first attempt that fails:
public static Object[] badCopyOf(Object[] a, int newLength) // not useful
{
    var newArray = new Object[newLength];
    System.arraycopy(a, 0, newArray, 0, Math.min(a.length, newLength));
    return newArray;
}
  • It returns an Object[], which cannot be cast to Employee[] (a ClassCastException): a Java array remembers its element type
    • You may cast an Employee[] temporarily to Object[] and back, but an array that started as Object[] can never become Employee[].
  • The fix:
    • make a new array of the same type with Array.newInstance(componentType, newLength)
    • Get the component type via getClass(), confirm isArray(), then getComponentType() (defined only for array classes)
    • Conversely arrayType() returns the Class for C[]
    • (Why getLength is on Array but getComponentType on Class? "The distribution of the reflection methods seems a bit ad hoc.")
public static Object goodCopyOf(Object a, int newLength)
{
    Class cl = a.getClass();
    if (!cl.isArray())
    {
        return null;
    }
    Class componentType = cl.getComponentType();
    int length = Array.getLength(a);
    Object newArray = Array.newInstance(componentType, newLength);
    System.arraycopy(a, 0, newArray, 0, Math.min(length, newLength));
    return newArray;
}
  • It works for any array type including primitives:
    • int[] a = { 1, 2, 3, 4, 5 }; a = (int[]) goodCopyOf(a, 10);
    • The parameter is declared Object because an int[] converts to Object but not to Object[].
  • Listing 5.19 (CopyOfDemo.java) shows both: goodCopyOf on an int[] and a String[] works, and the cast of badCopyOf's result to String[] throws.

5.10.7 Invoking arbitrary methods and constructors

  • C and C++ have function pointers
    • Java's designers called method pointers dangerous and error-prone and prefer interfaces and lambda expressions (chapter 6). Reflection still lets you call any method.
  • Method has invoke: Object invoke(Object obj, Object... args). The first parameter is the implicit argument, the rest the explicit ones
    • for a static method the first argument is ignored (pass null).
Method m1 = Employee.class.getMethod("getName");
Method m2 = Employee.class.getMethod("raiseSalary", double.class);

String n = (String) m1.invoke(harry);
// a primitive return comes back as its wrapper: cast and unbox
Method m3 = Employee.class.getMethod("getSalary");
double s = (Double) m3.invoke(harry);
  • Getting a Method: search getDeclaredMethods(), or call getMethod(String name, Class... parameterTypes). Several methods can share a name, so give the parameter types.
  • Constructors work the same way:
Class cl = BigInteger.class;
Constructor cons = cl.getConstructor(String.class);
Object obj = cons.newInstance("11235813213455");
  • Method and Constructor extend Executable, which is sealed (Java 17), permitting exactly those two.
  • Listing 5.20 (MethodTableDemo.java) prints a table of x and f(x) for any double function, with the table code independent of the function:
double dx = (to - from) / (n - 1);
for (double x = from; x <= to; x += dx)
{
    double y = (Double) f.invoke(null, x); // null: a static method
    IO.println("%10.4f | %10.4f".formatted(x, y));
}
  • The function is chosen with Math.class.getMethod("sqrt", double.class) or this.getClass().getDeclaredMethod("square", double.class)
    • Output for sqrt starts 1.0000 | 1.0000, 2.0000 | 1.4142, 3.0000 | 1.7321.
  • Anything you can do with function pointers (C) or delegates (C#) you can do with Method objects, but it is inconvenient and error prone:
    • Wrong arguments make invoke throw.
    • Parameters and return values are Object, forcing casts, so the compiler cannot check and errors appear only in testing.
    • It is significantly slower than a direct call.
  • Use Method objects only when absolutely necessary; interfaces and lambdas are almost always better.

java.lang.reflect.Method (1.1): public Object invoke(Object obj, Object[] args): for static methods pass null as the implicit argument; pass primitives through wrappers; unwrap primitive returns.

5.11 Design hints for inheritance

  1. Place common operations and fields in the superclass. That is why name went into Person, not into both Employee and Student.
  2. Do not use protected fields. "Just in case" protected fields give little protection: the set of subclasses is unbounded (anyone can subclass and break encapsulation), and in Java all classes in the same package can access them. Protected methods can be useful to mark methods not ready for general use that subclasses should redefine.
  3. Use inheritance to model "is-a". A Contractor extending Employee with an hourlyWage would hold both a salary and an hourly wage and cause grief in paychecks and tax forms. A contractor is not a special case of an employee (fails the is-a test).

  1. Do not use inheritance unless all inherited methods make sense. class Holiday extends GregorianCalendar inherits add, which can turn a holiday into a non-holiday (christmas.add(Calendar.DAY_OF_MONTH, 12)); the set of holidays is not closed under inherited operations. The problem would not arise when extending an immutable class (no method could produce a non-holiday).
  2. Do not change expected behaviour when overriding. The substitution principle covers behaviour, not just syntax, and the compiler cannot check it. "Fixing" Holiday.add by doing nothing or throwing violates it, since this code must behave the same for GregorianCalendar and Holiday:
int d1 = x.get(Calendar.DAY_OF_MONTH);
x.add(Calendar.DAY_OF_MONTH, 1);
int d2 = x.get(Calendar.DAY_OF_MONTH);
IO.println(d2 - d1);
  • What counts as expected is debatable (some argue Manager.equals must ignore the bonus because Employee.equals does)
    • what matters is not circumventing the original design's intent.
  1. Use polymorphism, not type information. For if (x is of type 1) action1(x); else if (x is of type 2) action2(x); ask whether the actions share a concept; if so make it a method of a common superclass or interface and call x.action(). Polymorphic code is easier to maintain and extend than multiple type tests.
  2. Do not overuse reflection. Useful for systems programming, usually not for applications: it is fragile, the compiler cannot find errors, and every mistake becomes a run-time exception.

Summary points

  • extends builds subclasses; super calls up; overriding plus dynamic binding gives polymorphism; final blocks overriding and subclassing; sealed limits subclasses.
  • Cast and test with instanceof (pattern form), and prefer polymorphism.
  • Override equals (symmetric), hashCode (consistent with equals) and toString; use @Override.
  • ArrayList<E>, wrappers with autoboxing (never compare with ==), varargs, abstract classes, enums.
  • Pattern-matching switch with guards, exhaustiveness and dominance rules.
  • Reflection: Class, Field, Method, Constructor, Array, resources; powerful but fragile.

  • Override, super, covariant return type: redefining a superclass method.
  • Polymorphism, dynamic binding, method table, static binding: how calls are resolved.
  • Substitution principle, is-a rule: use a subclass wherever a superclass is expected.
  • Cast, instanceof pattern, record pattern: checked downcasting and destructuring.
  • protected: package plus subclasses.
  • equals contract, hashCode, toString: the three Object methods to override.
  • Raw type, diamond, type erasure: generics compatibility.
  • Autoboxing, wrapper class, integer cache: primitives versus objects.
  • Abstract class, enum, sealed class, non-sealed: restricted or fixed type families.
