Core Java 7: Exceptions, Assertions and Logging

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 7. Previous: Core Java 6: Interfaces, Lambda Expressions and Inner Classes. Next: Core Java 8: Generic Programming.

Takeaways
  • A method that cannot finish normally throws an exception object instead of returning an error code; control jumps to a handler, skipping everything in between.
  • All exceptions descend from Throwable: Error (JVM trouble, do not throw) and Exception, which splits into RuntimeException (a programming mistake, unchecked) and the rest (checked, the compiler forces you to handle or declare them).
  • try-with-resources closes resources automatically and records secondary failures as suppressed exceptions; prefer it to finally.
  • Good practice: throw early, catch late; wrap low-level exceptions as the cause of a higher-level one; never swallow exceptions; never show stack traces to end users.
  • Assertions (assert) are checks enabled only while testing (-ea); logging records problems for later analysis.

7.1 Dealing with errors

  • Users should never lose work to an error. When an operation fails, the program should at least:
    • notify the user
    • save all work
    • let the user exit gracefully, or return to a safe state and allow other commands
  • Difficulty:
    • the code detecting the error is usually far from the code that can restore a safe state
    • Exception handling transfers control from where the error occurred to a handler that can deal with it.
  • Kinds of problems:
    • User input errors: typos, a syntactically wrong URL that the network layer finally rejects.
    • Device errors: printer off, a page unavailable, a printer out of paper mid-job.
    • Physical limitations: full disks, out of memory.
    • Code errors: wrong results, invalid array index, missing hash table entry, popping an empty stack.
  • The traditional reaction is an error code (a -1 end-of-file marker, or null), but that fails when no value is reserved for errors (a method returning an int cannot use -1 if -1 is valid)
    • Returning null is particularly bad: the legacy File.listFiles returns null on failure, and without a check a later NullPointerException masks the original problem.
  • In Java every method has an alternative exit path:
    • it throws an object encapsulating the error. The method exits immediately without returning any value, and the exception-handling mechanism starts searching for a handler
    • execution does not resume where the method was called.
  • Favour exceptions over error codes:
    • codes are easy to forget, exceptions cannot be overlooked, and they carry more information. Legacy File.delete returns false on failure
    • Files.delete throws an exception of a type describing the problem.

7.1.1 The classification of exceptions

  • An exception object is always an instance of a class derived from Throwable. It splits at once into Error and Exception.
    • Error: internal errors and resource exhaustion in the runtime. Do not throw these; there is little to do but tell the user and try to end gracefully. They are rare.
    • Exception
      • splits again into RuntimeException and everything else. Rule: **a RuntimeException means you made a programming error
      • any other exception means something bad happened to your otherwise good program.**
  • RuntimeException examples: a bad cast, an out-of-bounds array access, a null pointer access
    • Others: reading past the end of a file, opening a missing file, finding a Class for a nonexistent name.
  • "If it is a RuntimeException, it was your fault" works well: you could have tested the index or the null.
  • Why not just check that a file exists first? It might be deleted right after the check: existence depends on the environment, not on your code.
  • The JLS calls any exception derived from Error or RuntimeException unchecked; all others are checked, and the compiler checks that you provide handlers for them.
  • The name RuntimeException is confusing (all errors happen at run time)
    • It dates from prehistoric times: the "runtime" of Oak (Java's predecessor) generated out-of-bounds and null pointer exceptions, while presumably other components produced I/O exceptions.
  • C++ comparison: C++ has logic_error (like Java's RuntimeException: logical program errors) and runtime_error (unpredictable problems: like Java's non-runtime exceptions).

7.1.2 Declaring checked exceptions

  • A method tells the compiler what can go wrong, in its header:
public FileInputStream(String name) throws FileNotFoundException
  • If it happens, no object is initialised; the runtime searches for a handler for FileNotFoundException.
  • An exception is thrown in four situations:
    1. You call a method that throws a checked exception (the FileInputStream constructor).
    2. You detect an error and throw a checked exception with throw.
    3. You make a programming error, such as a[-1] = 0 (an unchecked ArrayIndexOutOfBoundsException).
    4. An internal error occurs in the VM or runtime library.
  • For the first two you must tell users of your method. Any method that throws is a potential death trap: if no handler catches it, the thread terminates.
class MyAnimation
{
    public Image loadImage(String s) throws IOException
    {
        // ...
    }

    public Image loadImage2(String s) throws FileNotFoundException, EOFException
    {
        // ...
    }
}
  • List several checked exceptions separated by commas
    • Do not advertise Error subclasses (beyond your control) or RuntimeExceptions (void drawImage(int i) throws ArrayIndexOutOfBoundsException is bad style: fix the bug instead)
    • If you fail to declare a checked exception, the compiler gives an error.
  • Instead of declaring you may catch it, so no throws is needed.
  • Overriding rule:
    • the checked exceptions a subclass method declares cannot be more general than the superclass method's
    • More specific, or none, is fine
    • If the superclass method throws no checked exception, neither can the subclass: overriding toString must not throw checked exceptions.
  • A method declared throws IOException may throw any subclass (FileNotFoundException).
  • C++ difference:
    • C++ throw specifiers are enforced at run time (an unexpected function is called, the program ends by default), and a function with no specifier may throw anything
    • In Java a method without throws may throw no checked exceptions.

7.1.3 How to throw an exception

  • Scenario: a header promised Content-length: 1024 but end of file came after 733 characters. EOFException ("Signals that an EOF has been reached unexpectedly during input") fits:
String readData(Scanner in) throws EOFException
{
    // ...
    while (/* ... */)
    {
        if (!in.hasNextLine()) // EOF encountered
        {
            if (n < len)
            {
                throw new EOFException();
            }
        }
        // ...
    }
    return s;
}
  • A second constructor takes a message: String gripe = "Content-length: " + len + ", Received: " + n; throw new EOFException(gripe);.
  • Steps: find an appropriate exception class, make an object, throw it. The method does not return, so you need no default return value or error code.
  • C++ difference: in Java you can throw only objects of subclasses of Throwable; C++ lets you throw any type.

7.1.4 Creating exception classes

  • If no standard class fits, derive your own from Exception or a child such as IOException
    • By convention give both a default constructor and one with a detailed message (Throwable.toString includes it):
class FileFormatException extends IOException
{
    public FileFormatException() {}

    public FileFormatException(String gripe)
    {
        super(gripe);
    }
}
  • Then throw new FileFormatException(); in readData (declared throws FileFormatException).

java.lang.Throwable (1.0): Throwable(), Throwable(String message), String getMessage().

7.2 Catching exceptions

7.2.1 Catching an exception

  • An uncaught exception terminates the program and prints its type and a stack trace
    • GUI programs may catch exceptions, print the trace and return to the UI loop (keep the console visible when debugging).
  • A try/catch block:
try
{
    // code
    // more code
}
catch (ExceptionType e)
{
    // handler for this type
}
  • If the try code throws the named type or a subclass:
    • the rest of the try block is skipped, the handler runs
    • If nothing is thrown, the catch is skipped
    • If an exception of another type is thrown, the method exits immediately (hopefully a caller handles it).
public void read(String filename)
{
    try
    {
        var in = new FileInputStream(filename);
        int b;
        while ((b = in.read()) != -1)
        {
            // process input
        }
    }
    catch (IOException exception)
    {
        exception.printStackTrace();
    }
}
  • Often the best choice is to pass the exception to the caller, adding a throws clause: public void read(String filename) throws IOException
    • The compiler enforces: handle it or pass it on.
  • Rule: catch what you know how to handle, propagate what you do not. There is nothing embarrassing about the latter: better to direct an exception to a competent handler than to squelch it.
  • When overriding, you cannot add throws beyond the superclass method, so you must catch undeclared checked exceptions (overriding compareTo, which throws none, you must catch each).
  • Java 25: an unnamed variable when you do not need the exception: catch (FileNotFoundException _) { System.exit(0); }.

7.2.2 Catching multiple exceptions

  • Use a separate catch per type, more specific before more general:
try
{
    // code that might throw exceptions
}
catch (FileNotFoundException e)
{
    // emergency action for missing files
}
catch (UnknownHostException e)
{
    // emergency action for unknown hosts
}
catch (IOException e)
{
    // emergency action for all other I/O problems
}
  • Inspect with e.getMessage() (the detail message) or e.getClass().getName() (the actual type).
  • Combine types in one clause with | when the handling is the same (only for types that are not subclasses of each other):
catch (FileNotFoundException | UnknownHostException e)
{
    // emergency action for missing files and unknown hosts
}
catch (IOException e)
{
    // emergency action for all other I/O problems
}
  • With a multi-catch the variable e is implicitly final
    • the generated bytecode contains a single block for the shared clause (more efficient). Its type is not a union type (Java has none) but the least upper bound, here IOException.
  • That matters for a switch on e: cases for just the two types are not exhaustive (error). Add a default or use separate catch clauses.
  • Catch clauses ignore sealed hierarchies: with sealed abstract class DomainException extends Exception permits FatalDomainException, SurvivableDomainException {}, catching only those two subtypes is not sufficient for the compiler, even though no other checked instance can exist.

7.2.3 Rethrowing and chaining exceptions

  • Throw in a catch to change the exception type, typically to a subsystem-level type (like ServletException, since the servlet runner only needs to know the servlet failed).
try
{
    // access the database
}
catch (SQLException original)
{
    var e = new ServletException("database error", original); // original is the cause
    throw e;
}
  • Setting the original as the cause is far better
    • than copying its message
    • If the exception type has no cause constructor, call e.initCause(original)
    • Retrieve it later with Throwable original = caughtException.getCause();
    • Highly recommended: high-level exceptions without losing the details.
  • Also useful to wrap a checked exception in a runtime exception when a method may not throw checked ones. The API offers UncheckedIOException for I/O.
  • To log and rethrow unchanged:
try
{
    // access the database
}
catch (Exception e)
{
    logger.log(level, message, e);
    throw e;
}
  • The compiler tracks that e comes from the try block: if the only checked exceptions there are SQLExceptions and e is unchanged, the enclosing method may be declared throws SQLException even though e is typed Exception.

7.2.4 The finally clause

  • An exception exits the method, which is a problem if the method acquired a local resource that needs cleanup
    • Catching, cleaning up and rethrowing duplicates the cleanup
    • finally runs whether or not an exception was caught
    • (try-with-resources below is more elegant and far more common; finally is the conceptual foundation.)
var in = new FileInputStream(/* ... */);
try
{
    // 1: code that might throw exceptions
    // 2
}
catch (IOException e)
{
    // 3: show error message
    // 4
}
finally
{
    // 5
    in.close();
}
// 6
  • Three situations:
    1. No exception: points 1, 2, 5, 6.
    2. Exception caught by a catch: if the catch does not throw: 1, 3, 4, 5, 6. If the catch throws: 1, 3, 5, then the exception goes to the caller.
    3. Exception not caught: 1, then 5, then the exception goes to the caller.

  • finally can be used without catch. For clarity use two nested try blocks: the inner one only ensures the stream is closed, the outer one only reports errors
    • errors in the finally code are then also reported:
InputStream in = null; // opened elsewhere
try
{
    try
    {
        // code that might throw exceptions
    }
    finally
    {
        in.close();
    }
}
catch (IOException e)
{
    // show error message
}
  • Trap: a return in finally masks the original return value and even swallows exceptions:
public static int parseInt(String s)
{
    try
    {
        return Integer.parseInt(s);
    }
    finally
    {
        return 0; // ERROR: parseInt("42") returns 0; parseInt("zero") swallows the NumberFormatException
    }
}
  • Do not put control-flow statements (return, throw, break, continue) in finally; it is for cleaning up resources.

7.2.5 The try-with-resources statement

  • For any resource whose class implements AutoCloseable (one method void close() throws Exception; the subinterface Closeable declares close() throws IOException):
try (Resource res = /* ... */)
{
    // work with res
}
  • res.close() is called automatically on normal exit or exception:
try (var in = new Scanner(Path.of("in.txt")))
{
    while (in.hasNextLine())
    {
        String line = in.nextLine();
        // process line
    }
}
  • Several resources (closed in reverse order of opening), without hand-nesting two try/finally blocks:
try (var in = new Scanner(Path.of("in.txt"));
     var out = new PrintWriter("out.txt"))
{
    while (in.hasNextLine())
    {
        String line = in.nextLine();
        out.println(line.toUpperCase());
    }
}
  • You can use an existing effectively final variable: try (out) { ... } (uncommon; prefer closing where it was created).
  • If both the body and close throw,
    • the original exception is rethrown and exceptions from close become suppressed: added with addSuppressed and readable with getSuppressed()
    • You would not want to program that by hand.
  • A try-with-resources can have its own catch and finally, run after the resources are closed.

7.2.6 Analysing stack trace elements

  • A stack trace lists all pending method calls at a point in execution; it prints when a program ends with an uncaught exception. printStackTrace into a StringWriter gives the text:
var t = new Throwable();
var out = new StringWriter();
t.printStackTrace(new PrintWriter(out));
String description = out.toString();
  • More flexible:
    • StackWalker yields StackWalker.StackFrames: StackWalker.getInstance().forEach(frame -> /* analyse */), or lazily walker.walk(stream -> /* process */) (streams: Volume II, chapter 1). A frame gives the file name, line number, class object and method name
    • toString formats them.
  • Throwable.getStackTrace() returns StackTraceElement[], less efficient (captures the entire stack) and gives class names, not class objects.
  • Listing 7.1 (StackTraceDemo.java) walks and prints the stack inside a recursive factorial. For `factorial

  • :with two,factorial
  • :with three (each framestackTrace.StackTraceDemo.factorial(StackTraceDemo.java:20)plus...main(StackTraceDemo.java:36)), then return 1, return 2, return 6`

7.3 Tips for using exceptions

  1. Exception handling is not a replacement for a simple test. Popping an empty stack 10,000,000 times: with if (!s.empty()) s.pop(); it took 0.167 s, catching EmptyStackException took 3.629 s. Use exceptions for exceptional circumstances only.
  2. Do not micromanage. Wrapping every statement in its own try bloats the code. If the task is "pop 100 numbers and write them to a file" and nothing can fix a failure, wrap the whole task in one try with catch (IOException e) and catch (EmptyStackException e), separating normal processing from error handling.
  3. Make good use of the exception hierarchy.
    • Do not just throw Exception or RuntimeException: find a subclass or create your own.
    • Do not just catch Exception, and never catch Throwable (you might hide an OutOfMemoryError).
    • Respect the checked/unchecked difference: checked exceptions are burdensome, so do not use them for logic errors (the reflection library gets this wrong).
    • Convert to a more appropriate exception when sensible: catch NumberFormatException and set it as the cause of an IOException subclass or your subsystem exception.
  4. Do not squelch exceptions. An empty catch (Exception e) { } compiles happily and silently ignores the failure. Make an effort to handle exceptions properly.
  5. "Tough love" beats indulgence. Throwing EmptyStackException at the point of failure is better than returning null and getting a NullPointerException later.
  6. Propagating is not a sign of shame. public void readStuff(String filename) throws IOException is fine: higher-level methods are often better placed to inform the user or abandon the command.
  7. Use standard methods for null and bounds checks: Objects.requireNonNull, checkIndex, checkFromToIndex, checkFromIndexSize:
public void putData(int position, Object newValue)
{
    Objects.checkIndex(position, data.length);
    Objects.requireNonNull(newValue);
    // ...
}
  1. Do not show stack traces to end users. They can reveal implementation details such as library versions to attackers. Log the trace and show a summary message.
  • Tips 5 and 6 together: "throw early, catch late".

7.4 Using assertions

  • Assertions are a common defensive programming idiom.

7.4.1 The assertion concept

  • You rely on a property (for double y = Math.sqrt(x); you are sure x is not negative) but want to double-check so confusing NaN does not creep in
    • An explicit if (x < 0) throw new IllegalArgumentException("x < 0"); stays in production and can slow the program if there are many.
  • Assertions put checks in during testing and remove them in production. Two forms:
assert condition;
assert condition : expression;
  • Both evaluate the condition and throw AssertionError if false. In the second form the expression is turned into the message string
    • the AssertionError does not store the value, so you cannot query it (the JDK docs say that "would encourage programmers to attempt to recover from assertion failure, which defeats the purpose of the facility").
  • Examples:
    • assert x >= 0; or assert x >= 0 : x;. Unlike C's assert macro, Java does not print the failing condition automatically
    • to see it pass a string: assert x >= 0 : "x >= 0";.

7.4.2 Assertion enabling and disabling

  • Assertions are disabled by default. Enable with -enableassertions or -ea: java -enableassertions MyProgram.

  • You do not recompile to enable or disable assertions: it is a function of the class loader, which strips assertion code when disabled so it costs nothing.

  • Enable per class or package:

    • java -ea:MyClass -ea:com.mycompany.mypackage... MyProgram (the ... means the package and subpackages; -ea:... covers the unnamed package)
    • Disable with -disableassertions or -da: java -ea:... -da:MyClass MyProgram.

  • System classes (loaded by the VM, no class loader) are not affected by -ea and -da; use -enablesystemassertions (-esa).

  • You can also control it programmatically per class loader (API notes below).

  • Side-effect trap: when assertions are off the condition does not run:

File file = new File(filename);
// ...
assert file.delete(); // BAD: with assertions off the file is never deleted

boolean deletionSuccessful = file.delete();
assert deletionSuccessful;
  • The JDK source has over four hundred assertions that are commented out (some people comment them out after testing to save class file space)
    • To include them conditionally: public static final boolean ASSERTS = true; // recompile with false for production then if (ASSERTS) assert x >= 0;.

7.4.3 Using assertions for parameter checking

  • Three mechanisms for failures: throwing an exception, logging, assertions. Choosing assertions:
    • Failures are meant to be fatal and unrecoverable.
    • Checks are on only during development and testing: "wearing a life jacket when you are close to shore, and throwing it overboard once you are in the middle of the ocean."
    • So never use assertions to signal recoverable conditions or to tell the user about a problem; only to find internal program errors during testing.
  • Parameter checking depends on the documented contract. A documented sort(int[] a, int fromIndex, int toIndex) that "throws IllegalArgumentException if fromIndex > toIndex" and "ArrayIndexOutOfBoundsException if fromIndex < 0 or toIndex > a.length" must really throw those exceptions, not assert.
  • Asserting a != null is also not appropriate if the docs are silent about null: callers may assume normal return
    • If the documentation says "(must not be null)", callers are on notice and the method may start with assert a != null;.
  • That is a precondition:
    • the original method had none
    • the revised one has a single one. If the caller breaks it, all bets are off: with the assertion it sometimes throws an AssertionError and sometimes a NullPointerException, depending on class loader configuration.

7.4.4 Using assertions for documenting assumptions

  • Instead of a comment else // (i % 3 == 2), write the assumption as code:
if (i % 3 == 0)
{
    // ...
}
else if (i % 3 == 1)
{
    // ...
} else {
    assert i % 3 == 2;
    // ...
}
  • Better still, think it through: for negative i the remainders can be -1 or -2, so the real assumption is that i is not negative: assert i >= 0; before the if.
  • Assertions are a tactical tool for testing and debugging; logging is strategic, for the whole lifecycle.

java.lang.ClassLoader (1.0): void setDefaultAssertionStatus(boolean b) (1.4, for classes without an explicit setting), void setClassAssertionStatus(String className, boolean b) (the class and its inner classes), void setPackageAssertionStatus(String packageName, boolean b) (package and subpackages), void clearAssertionStatus() (removes explicit settings and disables assertions).

7.5 Logging

  • Print statements are inserted to understand troublesome code, removed, and put back for the next bug. Logging frameworks solve this.

7.5.1 Should you use the Java logging framework?

  • Java's standard framework is java.util.logging ("j.u.l.")
    • Other frameworks have more features and are common: Log4j (https://logging.apache.org/log4j/2.x) and Logback (https://logback.qos.ch).
  • To give users a choice, log through a façade that sends messages to the preferred framework: SLF4J (https://www.slf4j.org), or the JDK's basic platform logging API (JEP 264). The frontend is the API you log with
    • the backend filters, formats and stores messages and is configured by deployers (usually by files).
  • The book uses the platform logging API as frontend and java.util.logging as backend: a reasonable choice, since you can swap the backend
    • j.u.l
    • has fewer features but suffices for many uses, and its simplicity makes it less susceptible to attacks: obscure Log4j features let attackers craft inputs that caused malicious code execution when logged.
  • For JVM-level logging (such as garbage collection) use -Xlog: java -Xlog:gc=trace:file=gc.log:uptime,tid MyProgram (details in the JDK man page for java).

7.5.2 Logging 101

  • Platform loggers implement System.Logger, each with a name (often the package of the logging class):
System.Logger logger = System.getLogger("com.mycompany.myapp");
logger.log(System.Logger.Level.INFO, "Opening file " + filename);
  • The first request for a name creates the logger; later requests return the same one. The record prints with time, class and method:
Aug 04, 2025 09:53:34 AM com.mycompany.myapp.Main read
INFO: Opening file data.txt
  • To silence info messages when deployed, configure the backend with a logging.properties file:
handlers=java.util.logging.ConsoleHandler
com.mycompany.myapp.level=WARNING

$ java -Djava.util.logging.config.file=logging.properties com.mycompany.myapp.Main
  • Since INFO is below WARNING, the message no longer shows. Getting the logger and logging belong to the frontend
    • destination, formatting, filtering and configuration belong to the backend.

7.5.3 The platform logging API

  • Levels of System.Logger.Level, in decreasing severity: ERROR, WARNING, INFO, DEBUG, TRACE. Shorten with import static java.lang.System.Logger.Level.*;.
  • The message string is built even if suppressed; to avoid that cost, pass a supplier (lambda): logger.log(INFO, () -> "Opening file " + filename); computed only when actually logged.
  • Log an exception (the log includes the stack trace):
catch (IOException ex)
{
    logger.log(WARNING, "Cannot open file " + filename, ex);
}
  • Message patterns
    • use MessageFormat, not printf: logger.log(WARNING, "Cannot open file {0}", filename); with placeholders {0}, {1}
    • Escape braces with single quotes ('{', '}') and use two single quotes '' for a literal one.
  • Localisation
    • via resource bundles (Volume II): logger.log(WARNING, bundle, "file.bad", filename); or System.getLogger("com.mycompany.myapp", bundle)
    • then String parameters are keys into the bundle (Object and Supplier<String> ones are unaffected)
      • Not every combination of deferred computation, throwable, formatting and bundle is supported
    • see the API notes.

7.5.4 Logging configuration

  • The default backend is java.util.logging
    • Its default file is conf/logging.properties in the JDK; use another with -Djava.util.logging.config.file=configFile MainClass
    • Calling System.setProperty("java.util.logging.config.file", ...) in main has no effect, because the log manager is initialised during VM startup, before main.
  • Per-logger levels: com.mycompany.myapp.level=WARNING (logger name plus .level). Root level: .level=WARNING.
  • These are not system properties: -Dcom.mycompany.myapp.level=FINE does nothing; they must be in the config file.
  • Level names differ between the platform API and java.util.logging; use the latter in the file (Table 7.1):
Platform logging java.util.logging
ERROR SEVERE
WARNING WARNING
INFO INFO
DEBUG FINE
TRACE FINER
  • Logger names are hierarchical, more than packages: turning off "com.mycompany" also deactivates its child loggers.
  • Loggers do not print: handlers do, and handlers have levels too. To see DEBUG/FINE on the console set java.util.logging.ConsoleHandler.level=FINE as well.
  • Levels can be changed in a running program with jconsole (https://www.oracle.com/technical-resources/articles/java/jconsole.html#LoggingControl).
  • Java 21:
    • the system logger java.lang.Runtime logs calls to Runtime.exit (which System.exit calls), with a stack trace showing who requested termination
    • set java.lang.Runtime.level=FINE to receive it.

7.5.5 Log handlers

  • The backend is built on handlers
    • The simplest, ConsoleHandler, prints to System.err
    • Each handler has a parent to which it sends records by default
    • The standard configuration uses a ConsoleHandler with default level INFO.
  • Other handlers:
    • FileHandler (collects records in a file) and SocketHandler (sends to a host and port)
    • Add a file handler: handlers=java.util.logging.ConsoleHandler,java.util.logging.FileHandler
    • Records go to javan.log in the user's home directory (n makes it unique), formatted as XML by default:
<record>
  <date>2025-12-04T09:53:34</date>
  <millis>1407146014072</millis>
  <sequence>1</sequence>
  <logger>com.mycompany.myapp</logger>
  <level>INFO</level>
  <class>com.horstmann.corejava.Employee</class>
  <method>read</method>
  <thread>10</thread>
  <message>Opening file staff.txt</message>
</record>
  • Use a better file name pattern such as %h/myapp%u.log
    • the %u gives a unique log per run. For long-running programs turn on file rotation (myapp.log.0, myapp.log.1, ...): when a file exceeds the limit the oldest is deleted, others are renamed and a new generation 0 is created.

7.5.6 Filters and formatters

  • Besides levels, a handler can have a Filter (a functional interface): boolean isLoggable(LogRecord record)
    • install with java.util.logging.ConsoleHandler.filter=com.mycompany.myapp.MyFilter.
  • Console and file handlers emit text and XML; define your own by extending java.util.logging.Formatter and overriding String format(LogRecord record)
    • Inside, formatMessage(record) formats the message part (resource bundle lookup and parameter substitution)
    • Formats that need a head and tail (like XML) override getHead(Handler h) and getTail(Handler h)
    • Set it with java.util.logging.FileHandler.formatter=com.mycompany.myapp.MyFormatter.

7.5.7 A logging recipe

  1. For a simple application use one logger named after your main package, e.g. System.getLogger("com.mycompany.myprog"), perhaps as a static field: private static final System.Logger logger = System.getLogger("com.mycompany.myprog");.
  2. The default backend logs INFO and above to the console. To customise, prepare logging.properties:
handlers=java.util.logging.ConsoleHandler,java.util.logging.FileHandler
com.mycompany.myapp.level=FINER
java.util.logging.ConsoleHandler.level=FINE

and start with java -Djava.util.logging.config.file=logging.properties com.mycompany.myapp.Main. 3. Whenever tempted to print to the console, use a logger: logger.log(System.Logger.Level.TRACE, "File open dialog canceled");. 4. Log unexpected exceptions with context: logger.log(System.Logger.Level.WARNING, string describing context, e);.

  • Listing 7.2 (LoggingImageViewer.java) adds logging to the chapter 2 image viewer (INFO for showing the frame and exiting, TRACE for entering and leaving methods, DEBUG for file selection), and Listing 7.3 (WindowHandler extends StreamHandler) shows records in a window
    • Run with java -Djava.util.logging.config.file=v1ch07/logging/logging.properties v1ch07.logging.LoggingImageViewer.

7.6 Debugging tips

  • Best of all is a debugger (Eclipse, IntelliJ, NetBeans), but try these first:
    • Print or log values:
      • IO.println("x=" + x); or logger.log(DEBUG, "x=" + x);. Also log this: logger.log(DEBUG, "this=" + this);. Library classes override toString helpfully
      • do the same.
    • A main per class
      • with demo code: make objects, call methods, show they behave
      • For serious unit testing use JUnit (https://junit.org): run tests on every change and add a test for each bug found.
    • A logging proxy: an object of a subclass that intercepts calls, logs and delegates; works only if the class is not final. For interfaces use the proxy from chapter 6.
var generator = new Random()
{
    public double nextDouble()
    {
        double result = super.nextDouble();
        logger.log(DEBUG, "nextDouble: " + result);
        return result;
    }
};
  • Stack trace from any exception:
    • t.printStackTrace();
    • To trace and rethrow: catch (Throwable t) { t.printStackTrace(); throw t; }
    • Without any exception, insert Thread.dumpStack();
    • To capture as a string: new Throwable().printStackTrace(new PrintWriter(out)).
  • Capture the error stream:
    • errors go to System.err, so java MyProgram > errors.txt misses them
    • Use java MyProgram 2> errors.txt, or both streams with java MyProgram 1> errors.txt 2>&1 (bash and the Windows shell).
  • Log uncaught exceptions instead of printing them to System.err (confusing to users, unavailable later): Thread.setDefaultUncaughtExceptionHandler((Thread t, Throwable e) -> logger.log(TRACE, "Uncaught exception in " + t, e));.
  • Watch class loading with -verbose: lines like [0.034s][info][class,load] java.lang.Object source: jrt:/java.base; occasionally useful for class path problems.
  • -Xlint
    • makes the compiler flag questionable code (the term "lint" comes from a C tool): javac -Xlint sourceFiles reports warnings like warning: [fallthrough] possible fall-through into case. Disable categories you do not want: javac -Xlint:all,-fallthrough,-serial sourceFiles
    • list them with javac --help-lint.
  • Monitoring:
    • jconsole shows VM statistics (memory, threads, class loading) for a running program (https://www.oracle.com/technical-resources/articles/java/jconsole.html). Java Flight Recorder collects diagnostic and profiling data
    • view it with VisualVM (https://visualvm.github.io) or Java Mission Control (https://adoptium.net/jmc; tutorial at https://github.com/thegreystone/jmc-tutorial).
  • jcmd
    • is the starting point among the command-line tools (jcmd, jhsdb, jinfo, jmap, jps, jstat): jcmd lists Java processes
    • with a process ID or main class: VM.system_properties, VM.flags, VM.log output=gc.log what=gc=trace decorators=uptime,tid, Thread.print, Thread.dump_to_file -overwrite -format=json dump.json, JFR.start filename=filename, JFR.stop name=1, and help commandName.

Summary points

  • Throw exceptions instead of returning error codes; checked exceptions are declared or caught, unchecked ones signal bugs.
  • Catch specific types, put specific before general, wrap with a cause, never squelch, throw early, catch late.
  • Use try-with-resources for cleanup; finally must not change control flow.
  • Assertions are test-time checks with no side effects, never for recoverable errors or public contracts.
  • Use a logger (frontend System.Logger, backend java.util.logging), with levels, handlers, filters and formatters; log exceptions with context.
Terms to carry forward
  • Throwable, Error, Exception, RuntimeException: the exception hierarchy.
  • Checked and unchecked exception: compiler-enforced or not.
  • throws clause, throw statement: declaring and raising.
  • Cause, suppressed exception: chained and secondary exceptions.
  • try-with-resources, AutoCloseable: automatic cleanup.
  • finally: cleanup that always runs.
  • Stack trace, StackWalker: the pending calls.
  • Assertion, precondition: test-time checks and caller obligations.
  • Logger, handler, filter, formatter, level: the logging pipeline.
  • Frontend, backend, façade: log API versus log implementation.
