Core Java 10: Concurrency

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 10. Previous: Core Java 9: Collections. Next: Core Java 11: Annotations.

Takeaways
  • A thread runs a task concurrently with others. Put the task in a Runnable (or a Callable that returns a value), call start, never run, and prefer executor services over managing threads by hand.
  • Virtual threads (Java 21) are cheap threads mounted on a few carrier platform threads; use them for blocking tasks (database, web), not CPU-heavy work.
  • A thread cannot be forced to stop: interrupt() sets a flag or ends a blocking call with InterruptedException. Never swallow it; rethrow or restore the flag.
  • Future, Callable, invokeAll, invokeAny and ExecutorCompletionService coordinate result-producing tasks; structured concurrency (Java 25 preview) ties subtasks to a scope.
  • Shared mutable state needs synchronisation (later sections): races corrupt data silently.
  • Concurrent programming gets complex; for deep system-level work read Java Concurrency in Practice (Brian Goetz et al., Addison-Wesley, 2006).

Introduction

  • Multitasking
    • is the OS running several programs at once
    • Multithreading goes one level lower: one program runs several tasks concurrently, each in a thread
    • Examples: a browser downloading many images, a web server handling concurrent requests, a GUI with a separate thread gathering UI events.
  • A fair warning: concurrency "can get very complex". This chapter covers what an application programmer is likely to need.

10.1 Running threads

Steps to run a task in a separate thread:

  1. Put the task code in the run method of a Runnable (a functional interface with one method void run()), often as a lambda: Runnable r = () -> { /* task code */ };.
  2. Construct a thread: var t = new Thread(r);.
  3. Start it: t.start();.
  • Demo:
    • threads move money between random accounts of a Bank
    • Each thread loops for a number of steps: pick fromAccount and toAccount with (int) (bank.size() * Math.random()), an amount up to MAX_AMOUNT, call bank.transfer(...), then Thread.sleep((int) (DELAY * Math.random())).
  • sleep threatens InterruptedException (section 10.3.2): interruption normally requests termination, so the run method simply exits when it occurs.
  • The book uses double for balances for convenience, not for financial accuracy (real code must not). Math.random() from many threads is slightly inefficient (see 10.5.14).
  • Output interleaves two threads, e.g
    • Thread[#25,Thread-0,5,main] 179.67 from 63 to 7 Total Balance: 100000.00 then Thread[#26,Thread-1,5,main] ...
    • Lines sometimes interleave messily, showing the threads really run concurrently (here each thread has its own bank, so no interference yet).
// v1ch10/ThreadDemo.java (one of the two tasks)
Runnable task1 = () ->
{
    var bank = new Bank(NACCOUNTS, INITIAL_BALANCE);
    try
    {
        for (int i = 0; i < STEPS; i++)
        {
            int fromAccount = (int) (bank.size() * Math.random());
            int toAccount = (int) (bank.size() * Math.random());
            double amount = MAX_AMOUNT * Math.random();
            bank.transfer(fromAccount, toAccount, amount);
            Thread.sleep((int) (DELAY * Math.random()));
        }
    }
    catch (InterruptedException e)
    {
    }
};

new Thread(task1).start();
  • Do not call run directly: it executes the task in the same thread and starts nothing. Call start, which creates the new thread that executes run.
  • You can subclass Thread and override run, but this is no longer recommended: decouple the task from the mechanism of running it (there are many ways to schedule tasks).
// v1ch10/unsynch/Bank.java (unsynchronised, used in ThreadDemo)
public class Bank
{
    private final double[] accounts;

    public Bank(int n, double initialBalance)
    {
        accounts = new double[n];
        Arrays.fill(accounts, initialBalance);
    }

    public void transfer(int from, int to, double amount)
    {
        if (accounts[from] < amount)
        {
            return;
        }
        IO.print(Thread.currentThread());
        accounts[from] -= amount;
        IO.print(" %10.2f from %d to %d".formatted(amount, from, to));
        accounts[to] += amount;
        IO.println(" Total Balance: %10.2f".formatted(getTotalBalance()));
    }

    public double getTotalBalance()
    {
        double sum = 0;
        for (double a : accounts)
        {
            sum += a;
        }
        return sum;
    }

    public int size()
    {
        return accounts.length;
    }
}

java.lang.Thread (1.0): Thread(Runnable target), start() (returns at once; the new thread runs concurrently), run() (calls the target's run), static void sleep(long millis) and sleep(Duration) (19). java.lang.Runnable (1.0): void run().

10.2 Thread states

  • Six states: New, Runnable, Blocked, Waiting, Timed waiting, Terminated; getState() reports it (NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED).
  • New (10.2.1): after new Thread(r), not yet running; some bookkeeping is needed first.
  • Runnable
    • (10.2.2): after start
    • A runnable thread may or may not actually be running: with more runnable threads than processors, the thread scheduler gives each time
    • It can preempt a running thread (also certain blocked ones and those that call yield).
  • Blocked and waiting (10.2.3): inactive, executing no code, minimal resources; the scheduler reactivates them.
    • Blocked: trying to acquire an intrinsic object lock (not a java.util.concurrent Lock) held by another thread; unblocked when released and scheduled.
    • Waiting: waiting for another thread to signal a condition: Object.wait, Thread.join, or waiting on a Lock or Condition in java.util.concurrent.
    • Timed waiting: methods with a timeout (Thread.sleep, timed Object.wait, Thread.join, Lock.tryLock, Condition.await).
    • In practice the difference is rarely significant; "blocked" often means any of the three. A reactivated thread becomes runnable again.
  • Terminated (10.2.4): the run method exits normally, or an uncaught exception ends it abruptly.

java.lang.Thread (1.0): static void yield() (hint to let another thread run; static), void join(), join(long millis), join(Duration) (19; wait for the thread to terminate), Thread.State getState() (5.0), stop() (deprecated for removal; throws UnsupportedOperationException since Java 21), suspend() and resume() (removed in Java 25).

10.3 Thread properties

10.3.1 Virtual threads

  • By default a Java thread runs on a platform thread supplied by the OS
    • OSes schedule well, but platform threads are not lightweight: a few thousand CPU instructions to start and a significant amount of reserved memory, which limits how many the OS can handle.
  • Problem for a typical web application that wants vastly more concurrent requests than platform threads: the tasks are not CPU-heavy, they spend most of their time blocked on database queries or external requests.
  • One solution: non-blocking APIs with callbacks:
    • service.request(parameters, response -> process(response)); frees the thread at once
    • High throughput, but a steep cost: all logic goes into callback code instead of the familiar sequences, branches, loops and exception handling.
  • Virtual threads
    • (Java 21) are the alternative
    • A number of platform threads, the carrier threads, execute virtual threads: a virtual thread is mounted on a carrier to run, unmounted when it blocks, and remounted on any available carrier afterwards
    • Analogy to virtual memory (mapped to less RAM)
    • By default one carrier per processor; tune with the jdk.virtualThreadScheduler.parallelism VM option.
  • Use virtual threads for tasks that call blocking operations (database or web requests); do not use them for computationally intensive operations.
  • Same API as platform threads: Thread t = Thread.startVirtualThread(myRunnable);, and isVirtual() tells which kind.

java.lang.Thread (1.0): boolean isVirtual() (21), static Thread startVirtualThread(Runnable task) (21).

10.3.2 Thread interruption

  • A thread ends when run returns (a return, the last statement, or an uncaught exception). There is no way to force a thread to terminate; interrupt() requests it.
  • interrupt() sets the thread's interrupted status (a boolean flag in every thread). Each thread should occasionally check it:
while (!Thread.currentThread().isInterrupted() && moreWorkToDo)
{
    // do more work
}
  • A blocked thread cannot check the flag
    • When interrupt is called on a thread blocked in sleep or wait, the blocking call ends with InterruptedException
    • (Some blocking I/O calls cannot be interrupted; the exception comes when the I/O completes.)
  • Interrupting just grabs attention: the thread decides how to react. Some should continue, but usually it is read as a request for termination:
Runnable r = () ->
{
    try
    {
        // ...
        while (!Thread.currentThread().isInterrupted() && moreWorkToDo)
        {
            // do more work
        }
    }
    catch (InterruptedException e)
    {
        // thread was interrupted
    }
    finally
    {
        // cleanup, if required
    }
    // exiting the run method terminates the thread
};
  • If you call sleep after every iteration, do not test the flag: sleep with the status set does not sleep, it clears the status and throws InterruptedException
    • Just catch the exception:
Runnable r = () ->
{
    try
    {
        while (moreWorkToDo)
        {
            // do more work
            Thread.sleep(delay);
        }
    }
    catch (InterruptedException e)
    {
        // thread was interrupted during sleep
    }
    finally
    {
        // cleanup, if required
    }
};
  • Two similar methods:
    • the static Thread.interrupted() checks the current thread and clears the flag
    • the instance isInterrupted() checks any thread and does not change the flag.
  • Never squelch InterruptedException (catch (InterruptedException e) { // Nothing here--BAD }), or the task cannot be interrupted while sleeping. Two reasonable choices:
    1. Declare throws InterruptedException and drop the try, so the caller or ultimately run can catch it.
    2. If you cannot, restore the flag in the catch: Thread.currentThread().interrupt();, so the caller can test it.
  • The original stop method was unsafe and now throws UnsupportedOperationException.

java.lang.Thread (1.0): void interrupt() (sets the flag; if blocked, throws InterruptedException), static boolean interrupted() (current thread, resets the flag to false), boolean isInterrupted() (does not change it), static Thread currentThread().

10.3.3 Daemon threads

  • t.setDaemon(true) (before starting) makes a thread whose only role is to serve others (timer ticks, cleaning stale cache entries). When only daemon threads remain, the VM exits. All virtual threads are daemon threads
    • setDaemon(false) has no effect on them.

10.3.4 Thread names and IDs

  • Default names are like Thread-2; set one (useful in thread dumps): t.setName("Web crawler");
    • Each thread has a positive ID: long id = t.threadId(); (Java 19)
    • getId is deprecated because it is not final and could be overridden to return something else.

Thread (1.0): setName(String), getName(), long threadId() (19).

10.3.5 Handlers for uncaught exceptions

  • run cannot throw checked exceptions, but an unchecked exception can end it
    • There is no catch clause to propagate to, so just before the thread dies the exception goes to an uncaught exception handler (a Thread.UncaughtExceptionHandler with void uncaughtException(Thread t, Throwable e)).
  • Install one per thread with setUncaughtExceptionHandler, or for all threads with the static Thread.setDefaultUncaughtExceptionHandler (for example to log the exception)
    • The default default handler is null.
  • Without an installed handler, the thread's thread group acts as one
    • if the group has a parent, call the parent's uncaughtException
    • otherwise if a default handler is set, call it
    • otherwise if it is the deprecated ThreadDeath, do nothing
    • otherwise print the thread name and stack trace to System.err
  • A thread group is a collection of threads managed together; all your threads share one by default. Do not use thread groups: there are better features.
  • Executors: setting the handler on the factory has no effect; thread pools install their own handler for task exceptions.

API: Thread.setDefaultUncaughtExceptionHandler(handler), getDefaultUncaughtExceptionHandler(), setUncaughtExceptionHandler, getUncaughtExceptionHandler() (5.0; if none, the thread group); Thread.UncaughtExceptionHandler.uncaughtException(Thread t, Throwable e) (5.0); ThreadGroup.uncaughtException(Thread t, Throwable e) (parent group, else default handler, else stack trace on System.err).

10.3.6 Thread priorities

  • A thread inherits the priority of its creator
    • change it with setPriority between MIN_PRIORITY (1) and MAX_PRIORITY (10)
    • NORM_PRIORITY is 5
      • The scheduler prefers higher priority, but it is highly system-dependent: Java priorities map to host levels (Windows has seven, so some map together), and in OpenJDK on Linux priorities are ignored altogether.
  • Do not use priorities nowadays. All virtual threads have NORM_PRIORITY; changing it has no effect.

Thread (1.0): setPriority(int), MIN_PRIORITY (1), NORM_PRIORITY (5), MAX_PRIORITY (10).

10.3.7 Thread factories and builders

  • ThreadFactory has Thread newThread(Runnable r). Write your own, or since Java 21 use builders: Thread.ofPlatform() and Thread.ofVirtual().
Thread.Builder builder = Thread.ofVirtual().name("request-", 1);

Thread t = builder.unstarted(myRunnable);
builder.start(myRunnable);

ThreadFactory factory = builder.factory();
t = factory.newThread(myRunnable);

API: java.util.concurrent.ThreadFactory (5.0): Thread newThread(Runnable r). Thread (21): ofPlatform(), ofVirtual(). Thread.Builder (21): name(String prefix, long start), name(String name), factory(), unstarted(Runnable), start(Runnable), uncaughtExceptionHandler(handler).

Thread.Builder.OfPlatform (21): daemon(), daemon(boolean on), stackSize(long), group(ThreadGroup), priority(int) (not recommended).

10.4 Coordinating tasks

  • Tasks are often split into subtasks whose results combine later; the framework provides tools for that.

10.4.1 Callables and futures

  • A Runnable is an asynchronous method with no parameters and no return value. A Callable<V> returns a value and may throw:
public interface Callable<V>
{
    V call() throws Exception;
}
  • A Future<V> holds the result of an asynchronous task
    • you get one when you schedule a task. Methods: get(), get(timeout, unit), resultNow(), exceptionNow(), cancel(boolean mayInterrupt), isCancelled(), isDone(), state().
    • get() blocks until finished
      • the timed get throws TimeoutException if too slow. Both throw InterruptedException if the waiting thread is interrupted
      • if the task ended with an exception they throw ExecutionException whose cause is that exception. If finished, get returns immediately.
    • resultNow() is a non-blocking get for tasks you know succeeded; exceptionNow() retrieves the failure for tasks you know failed.
    • cancel:
      • not yet started means it never starts; in progress means it is interrupted only if mayInterrupt is true, else it runs on
      • Cancellation always needs the task's cooperation (monitor the interrupted status, 10.3.2)
      • isDone() is true when completed (success or failure) or cancelled.
    • state() returns RUNNING, SUCCESS, FAILED or CANCELLED (Future.State); call state() before resultNow() or exceptionNow().
  • FutureTask implements both Future and Runnable, so you can run it on a thread:
Callable<Integer> task = () -> 42;
var futureTask = new FutureTask<Integer>(task);
Thread.ofPlatform().start(futureTask); // futureTask is a Runnable
Integer result = futureTask.get();     // futureTask is a Future
  • More commonly you pass a Callable to an executor. For a Future of a Runnable: var futureTask = new FutureTask<Void>(myRunnable, null);.

Callable<V> (5.0): V call().

Future<V> (5.0): get(), get(long time, TimeUnit unit) (CancellationException if cancelled, ExecutionException if failed, InterruptedException, TimeoutException), resultNow() (19, IllegalStateException unless successful), exceptionNow() (19), cancel(boolean mayInterrupt), isCancelled(), isDone(), state() (19).

FutureTask<V> (5.0): FutureTask(Callable<V>), FutureTask(Runnable task, V result).

10.4.2 Executor services

  • An executor service runs a set of tasks: submit tasks, it runs them on suitable threads; wait for all, or cancel the rest.
  • Virtual-thread executors
    • just start a new virtual thread per task
    • Platform-thread executors use a thread pool to avoid costly creation: a pool thread finishes a task, takes the next, and stays alive.

Table 10.1, Executors factory methods:

Method Description
newCachedThreadPool threads created as needed; idle ones kept 60 seconds
newFixedThreadPool fixed set of threads, idle ones kept indefinitely; extra tasks queue
newSingleThreadExecutor one thread running tasks sequentially
newVirtualThreadPerTaskExecutor each task on a new virtual thread
  • Cached pool
    • for short-lived or often-blocking platform threads
    • For CPU-bound work, optimum speed is number of threads = processor cores: use a fixed pool to bound concurrency
    • A fixed pool also throttles concurrent tasks when a service handles limited clients (crude but common).
  • With virtual threads, throttle differently: a counting semaphore or a bounded queue, and move the blocking to the point of pressure:
private static final int CONCURRENT_REQUESTS = 200;
private static final Semaphore SEMAPHORE = new Semaphore(CONCURRENT_REQUESTS);

public static String get(URI uri) throws InterruptedException, IOException
{
    var request = HttpRequest.newBuilder().uri(uri).GET().build();
    SEMAPHORE.acquire();
    try
    {
        return client.send(request, HttpResponse.BodyHandlers.ofString()).body();
    }
    finally
    {
        SEMAPHORE.release();
    }
}
  • The single-thread executor helps performance analysis (compare with the pool) and debugging race conditions.
  • Most factory methods take a ThreadFactory
    • for a pool it should produce platform threads (pooling virtual threads is never useful). For customised virtual threads use newThreadPerTaskExecutor.
  • All return an ExecutorService: Future<T> submit(Callable<T>), Future<?> submit(Runnable) (get blocks then returns null), Future<T> submit(Runnable, T result).
  • close() (Java 19) stops accepting tasks and blocks until submitted tasks finish (if interrupted, the tasks are cancelled). Use try-with-resources:
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor())
{
    // ...
    Future<V> f = executor.submit(myCallable);
    // ...
} // executor.close() called here
  • Local, short-lived executors are fine (even encouraged with virtual threads). For older Java use executor.shutdown(); executor.awaitTermination(10, TimeUnit.MINUTES);.
  • Summary:
    1. Get an executor from Executors (newCachedThreadPool, newFixedThreadPool, newVirtualThreadPerTaskExecutor).
    2. submit Callable or Runnable objects.
    3. Keep the Futures to query state, get results or cancel.
    4. Shut down when you submit no more.

java.util.concurrent.Executors (5.0): newCachedThreadPool(), newFixedThreadPool(int), newSingleThreadExecutor() (each with a ThreadFactory overload), newVirtualThreadPerTaskExecutor() (21), newThreadPerTaskExecutor(ThreadFactory) (21).

ExecutorService (5.0): the three submit methods, close() (19), shutdown() (no blocking), List<Runnable> shutdownNow() (interrupts started tasks, returns unstarted ones), boolean awaitTermination(long timeout, TimeUnit unit).

10.4.3 Invoking a group of tasks

  • invokeAny
    • submits all tasks and blocks until one completes successfully, returning its result and cancelling the rest; you do not know which won (presumably the quickest)
    • If none succeeds, ExecutionException
    • Good for searches where any solution will do (for example trying different ranges to factor a large integer, as when breaking RSA).
  • invokeAll submits all, blocks until all complete, and returns a List<Future<T>> in submission order:
List<Callable<T>> tasks = new ArrayList<>(); // ...
List<Future<T>> results = executor.invokeAll(tasks);
for (Future<T> result : results)
{
    if (result.state() == Future.State.SUCCESS)
    {
        // process result.resultNow();
    } else {
        // handle result.exceptionNow();
    }
}
  • To get results in the order they finish, use an ExecutorCompletionService, which keeps a blocking queue of Futures:
var service = new ExecutorCompletionService<T>(executor);
for (Callable<T> task : tasks)
{
    service.submit(task);
}
for (int i = 0; i < tasks.size(); i++)
{
    Future<T> result = service.take();
}
  • Listing 10.3: counts how many files in a directory tree contain a word (one Callable<Long> per file, then executor.invokeAll(tasks) and summing result.get()), timing the search
    • then replace the executor with a single-thread or virtual-thread one to compare. The second part finds the first file containing the word with invokeAny.
    • Careful task design:
      • invokeAny stops at the first task that returns, so a failing search throws NoSuchElementException instead of returning false
      • and since other tasks are cancelled once one succeeds, each monitors the interrupted status and prints "Search in path canceled." so the cancellation is visible.
public static Callable<Path> searchForTask(String word, Path path)
{
    return () ->
    {
        try (var in = new Scanner(path))
        {
            while (in.hasNextLine())
            {
                if (in.nextLine().contains(word))
                {
                    return path;
                }
                if (Thread.currentThread().isInterrupted())
                {
                    IO.println("Search in " + path + " canceled.");
                    return null;
                }
            }
            throw new NoSuchElementException();
        }
    };
}

  • Structured concurrency:
    • as structured programming replaced goto with branches, loops and functions, it seeks constructs that make concurrent programs easier to reason about. Java 25 previews an API: tasks go to a StructuredTaskScope
    • join blocks until the scope shuts down according to its policy (ShutdownOnFailure and ShutdownOnSuccess policies in earlier previews; the book shows the Java 25 preview form):
// Java 25 preview API
try (var scope = StructuredTaskScope.open())
{
    Supplier<T1> f1 = scope.fork(callable1);
    Supplier<T2> f2 = scope.fork(callable2);
    scope.join();
    result = combine(f1.get(), f2.get());
}
  • join returns when all forked subtasks complete normally
    • If any fails, the others are interrupted and join throws StructuredTaskScope.FailedException with the failed subtask's exception as the cause
    • If the current thread is interrupted, started tasks are interrupted and join throws InterruptedException.
  • A joiner customises execution and gathering: this yields the first successful subtask's result:
// Java 25 preview API
try (var scope = StructuredTaskScope.open(Joiner.<T>anySuccessfulResultOrThrow()))
{
    scope.fork(callable3);
    scope.fork(callable4);
    result = scope.join();
}

  • You could do similar things with invokeAll and invokeAny, but the structured concurrency API is more convenient, less error-prone and more flexible, and thread dumps show the hierarchy of nested scopes.
// v1ch10/ExecutorDemo.java (outline of Listing 10.3)
void main() throws Exception
{
    String start = IO.readln("Enter base directory (e.g. /opt/jdk-25-src): ");
    String word = IO.readln("Enter keyword (e.g. volatile): ");

    Set<Path> files = descendants(Path.of(start));
    var tasks = new ArrayList<Callable<Long>>();
    for (Path file : files)
    {
        Callable<Long> task = () -> occurrences(word, file);
        tasks.add(task);
    }
    ExecutorService executor = Executors.newCachedThreadPool();
    // try newSingleThreadExecutor() or newVirtualThreadPerTaskExecutor() to compare
    Instant startTime = Instant.now();
    List<Future<Long>> results = executor.invokeAll(tasks);
    Instant endTime = Instant.now();
    long total = 0;
    for (Future<Long> result : results)
    {
        total += result.get();
    }
    IO.println("Occurrences of " + word + ": " + total);
    // ... then invokeAny(searchTasks) for the first file containing the word
    executor.close();
}

ExecutorCompletionService<V> (5.0): ExecutorCompletionService(Executor), Future<V> submit(Callable<V>), submit(Runnable, V result), Future<V> take() (blocks), Future<V> poll(), poll(long time, TimeUnit unit) (null if none).

10.4.4 Thread-local variables

  • Sometimes a task-specific object (a database connection) should be reachable from all collaborating methods without passing it as a parameter
    • A thread-local variable is not a real variable but an object whose get and set access a value that depends on the current thread.
public static final ThreadLocal<Connection> CONNECTION = new ThreadLocal<>();

CONNECTION.set(connect(uri, username, password)); // when the task starts

Connection connection = CONNECTION.get();           // deeper in the same thread
var result = connection.executeQuery(query);
  • Each thread gets its own connection object
    • With a thread pool, always call CONNECTION.remove(); when the task ends (normally or with an exception), so other tasks on the same thread do not see the data and it can be garbage collected.
  • InheritableThreadLocal passes values to subtasks: a new thread gets a copy of the parent's inheritable thread locals (a copy, since the child might mutate them).
  • Virtual-thread caution:
    • sharing resource-intensive objects as thread locals scales badly when there are far more virtual threads than pool threads
    • rethink the sharing strategy. Find uses with the VM flag jdk.traceVirtualThreadLocals (stack trace when a virtual thread mutates a thread local).

java.lang.ThreadLocal<T> (1.2): get() (first call without set uses the initial value), set(T), remove().

10.4.5 Scoped values

  • Scoped values (Java 25) share data by thread more efficiently than inheritable thread locals: per-thread instances passed through nested calls, but immutable with a bounded lifetime.
public static final ScopedValue<Connection> CONNECTION = ScopedValue.newInstance();

ScopedValue.where(CONNECTION, connect(uri, username, password))
    .run(() -> doWork());

public void doWork()
{
    Connection connection = CONNECTION.get();
    var result = connection.executeQuery(query);
}
  • Bind several values with repeated where. run executes in the current thread with the binding and blocks until the task returns or throws
    • afterwards the bindings are removed (thread locals must be removed manually).
  • For a task returning a value use call with ScopedValue.CallableOp (like Callable but the exception type is a generic type parameter): String result = ScopedValue.where(CONNECTION, connect(...)).call(() -> getData()); // throws SQLException.
  • Cannot be mutated,
    • but can be rebound in a nested run or call, reverting when the nested task ends. Scoped values are inherited by virtual threads created by a StructuredTaskScope (a Java 25 preview feature)
    • immutability makes this far cheaper than inheriting thread locals.

java.lang.ScopedValue<T> (25): static <T> ScopedValue<T> newInstance() (unbound), T get(), T orElse(T other), isBound(), static ScopedValue.Carrier where(ScopedValue<T> key, T value). ScopedValue.Carrier (25): where(key, value), void run(Runnable op), <R, X extends Throwable> R call(CallableOp<? extends R, X> op) (values revert to previous bindings on normal or exceptional completion).

10.4.6 The fork-join framework

  • Some applications use many mostly idle threads (a web server with a thread per connection)
    • others use one thread per processor core for heavy computation (image or video processing). Fork-join supports the latter, for tasks that decompose into subtasks:
if (problemSize < threshold)
    solve the problem directly
else
    break it into subproblems, solve each recursively, combine the results
  • Example:
    • count array elements satisfying a property by cutting the array in half
    • Extend RecursiveTask<T> (result of type T) or RecursiveAction (no result) and override compute:
class Counter extends RecursiveTask<Integer>
{
    public static final int THRESHOLD = 1000;
    private double[] values;
    private int from;
    private int to;
    private DoublePredicate filter;

    // constructor sets the fields ...

    protected Integer compute()
    {
        if (to - from < THRESHOLD)
        {
            int count = 0;
            for (int i = from; i < to; i++)
            {
                if (filter.test(values[i]))
                {
                    count++;
                }
            }
            return count;
        } else {
            int mid = from + (to - from) / 2;
            var first = new Counter(values, from, mid, filter);
            var second = new Counter(values, mid, to, filter);
            invokeAll(first, second);
            return first.join() + second.join();
        }
    }
}
  • invokeAll blocks until all subtasks complete
    • join yields the result (get also exists but can throw checked exceptions you cannot throw from compute). Listing 10.4 (ForkJoinDemo.java) counts how many of 10,000,000 random doubles exceed 0.5 with try (var pool = new ForkJoinPool()) { pool.invoke(counter); IO.println(counter.join()); }.
  • Work stealing:
    • each worker has a deque; it pushes smaller subtasks onto the head of its own deque (only it touches the head, so no locks)
    • An idle worker steals from the tail of another deque (locking needed)
    • The tail holds larger subtasks, so more time passes before the next theft, reducing contention.
  • Fork-join pools are optimised for non-blocking work; many blocking tasks can starve the pool (an advanced ForkJoinPool.ManagedBlocker exists, not discussed).

10.5 Synchronisation

  • In most real multithreaded programs several threads share access to the same data
    • If two threads call methods that modify an object's state, they can "step on each other's toes" and corrupt it
    • This is a race condition.

10.5.1 An example of a race condition

  • Now many threads share one Bank. The unsafe transfer:
public void transfer(int from, int to, double amount)
{
    // CAUTION: unsafe when called from multiple threads
    IO.print(Thread.currentThread());
    accounts[from] -= amount;
    IO.printf(" %10.2f from %d to %d", amount, from, to);
    accounts[to] += amount;
    IO.printf(" Total Balance: %10.2f%n", getTotalBalance());
}
  • Each thread (one per account, 100 threads) keeps picking a random target and amount, calls transfer, and sleeps
    • The total should stay at $100,000 because money only moves
    • The printout shows it correct for a while, then wrong: Total Balance: 99291.06, later 99979.24, and lines interleaved
    • Errors may appear quickly or take a very long time
    • "You would probably not want to deposit your hard-earned money in such a bank." (Listing 10.5, UnsynchBankDemo; it never finishes, press Ctrl+C.)

10.5.2 The race condition explained

  • The culprit:
    • accounts[to] += amount; is not atomic. It is roughly: **1
    • load accounts[to] into a register, 2
    • add amount, 3
    • store back.** If thread A does steps 1 and 2 and is preempted, thread B updates the same entry, and A then completes step 3, A wipes out B's update: the total is wrong.
  • You can see it with javap -c -v Bank:
    • the line compiles to aload_0, getfield #2, iload_2, dup2, daload, dload_3, dadd, dastore
    • The point is simply that it is several instructions and the thread can be preempted at any of them.
  • The chance on a modern multicore processor is quite high
    • the print statements interleaved with updates boost it. Even without them, many threads on a loaded machine will fail eventually, in seconds or after many hours: "few things worse in the life of a programmer than an error that only manifests itself irregularly." (There is also a slight chance of false alarms in getTotalBalance.)
  • The real problem: transfer can be preempted in the middle. If it always ran to completion before the thread lost control, the object would never be corrupted.

10.5.3 Lock objects

  • Two ways to protect a code block:
    • the synchronized keyword (which gives a lock and an associated condition) and explicit classes in java.util.concurrent
    • The book explains explicit locks first, because synchronized is easier to understand after locks and conditions.
myLock.lock(); // a ReentrantLock object
try
{
    // critical section
}
finally
{
    myLock.unlock(); // always, even if an exception is thrown
}
  • Only one thread at a time can enter the critical section
    • others calling lock are deactivated until it unlocks. unlock must be in finally, or an exception would leave other threads blocked forever.
  • No try-with-resources
    • for locks: unlock is not called close
    • (It was proposed that Lock extend AutoCloseable, but the designers felt lock usage is uncommon and should be noticeable.)
  • Protecting transfer (each Bank has its own ReentrantLock, so threads on different banks never block each other):
public class Bank
{
    private final Lock bankLock = new ReentrantLock();
    // ...
    public void transfer(int from, int to, int amount)
    {
        bankLock.lock();
        try
        {
            IO.print(Thread.currentThread());
            accounts[from] -= amount;
            IO.printf(" %10.2f from %d to %d", amount, from, to);
            accounts[to] += amount;
            IO.printf(" Total Balance: %10.2f%n", getTotalBalance());
        }
        finally
        {
            bankLock.unlock();
        }
    }
}
  • Reentrant:
    • a thread can acquire a lock it already holds
    • The lock has a hold count; transfer calls getTotalBalance, which also locks, so the count goes to 2, back to 1, then 0
    • Code under a lock can call other methods using the same lock.
  • Use a lock around any code that updates or inspects a shared object. Care: if an exception exits the section, finally unlocks, but the object may be in a damaged state.
  • ReentrantLock(boolean fair): a fair lock favours the longest-waiting thread, but fairness is a significant drag on performance, so by default locks are not fair
    • Enable it only with a specific reason, and note the thread scheduler itself may still be unfair.

java.util.concurrent.locks.Lock (5.0): lock() (blocks if owned by another thread), unlock(). ReentrantLock (5.0): ReentrantLock(), ReentrantLock(boolean fair).

10.5.4 Condition objects

  • A thread may enter a critical section and find it cannot proceed until a condition holds
    • A condition object (historically "condition variable") manages threads that hold the lock but cannot do useful work.
  • Example:
    • do not transfer from an account without enough funds
    • if (bank.getBalance(from) >= amount) bank.transfer(from, to, amount); is not safe: the thread may be deactivated between the test and the transfer, and the balance may fall
    • Protect both under the lock
    • But if the balance is too low, we must wait for another thread to deposit, while holding the lock that blocks everyone: condition objects solve this.
  • Get one from the lock: private final Condition sufficientFunds = bankLock.newCondition(); (name it for what it represents).
  • sufficientFunds.await()
    • deactivates the thread and gives up the lock, letting another thread (hopefully) increase the balance. A thread in await joins the wait set for that condition and is not made runnable when the lock frees
    • it stays out until another thread calls signalAll on the same condition.
  • signalAll
    • moves all waiting threads out of the wait set; they become runnable and compete to reacquire the lock, then continue returning from await
    • Test the condition again: signalAll only says it may now be true
    • So always:
while (!(OK to proceed))
{
    condition.await();
}
  • Someone must eventually call signalAll: a waiting thread cannot reactivate itself. If all others are blocked and the last active thread calls await, nobody is left: deadlock.
  • When to signal: whenever an object's state changes in a way that might help waiting threads (every balance change).
public void transfer(int from, int to, int amount) throws InterruptedException
{
    bankLock.lock();
    try
    {
        while (accounts[from] < amount)
        {
            sufficientFunds.await();
        }
        // transfer funds
        accounts[from] -= amount;
        accounts[to] += amount;
        sufficientFunds.signalAll();
    }
    finally
    {
        bankLock.unlock();
    }
}
  • signalAll does not immediately run a waiter
    • it only lets them compete after the current thread releases the lock. signal unblocks one random thread: more efficient but dangerous (if that thread still cannot proceed and nobody signals again, deadlock).
  • A thread may call await, signalAll or signal only if it owns the lock of that condition.
  • The synch version (Listing 10.6): total stays $100,000 forever and no account goes negative, though it runs a bit slower (bookkeeping)
    • transfer and getTotalBalance lock, size does not (the number of accounts never changes).

Lock (5.0): Condition newCondition(). java.util.concurrent.locks.Condition (5.0): await() (joins the wait set), signalAll(), signal() (one random thread).

10.5.5 Deadlocks

  • Locks and conditions cannot solve everything
    • Example: Account 1 has $200, Account 2 has $300
    • Thread 1 transfers $300 from account 1 to 2; thread 2 transfers $400 from 2 to 1
    • Both are blocked by insufficient balances: a deadlock.
  • In the demo it cannot happen because each transfer is at most $1,000 and 100 accounts hold $100,000 in total, so some account always has at least $1,000
    • Remove the limit (set NACCOUNTS to 10 and use a maximum of 2 * INITIAL_BALANCE) and it hangs quickly.
  • To diagnose: press Ctrl+\ for a thread dump (each thread's blocked location), or open jconsole's Threads panel (chapter 7).
  • Other ways to deadlock:
    • make thread i deposit into account i instead of withdrawing (all threads may overdraw the same account, leaving no replenisher: flip fromAccount and toAccount in TransferRunnable)
    • or change signalAll to signal. Scenario: account 1 has $1,990 and the rest $990
    • all threads try to move $995. Thread 1 proceeds, then calls signal, which wakes a random thread (say thread 3), which still lacks funds and awaits again
    • thread 1 then tries $997 and also awaits: all blocked. The woken thread was not the one needed (thread 2, to drain account 2).
  • Locks and conditions are challenging: you must design the program so a deadlock cannot occur.

10.5.6 The synchronized keyword

  • Recap:
    • a lock protects code so only one thread runs it at a time and manages threads entering the critical section
    • it can have conditions
    • each condition manages threads inside the section that cannot proceed.
  • Since 1.0 every object has an intrinsic lock. A synchronized method makes a thread acquire it:
public synchronized void method()
{
    // method body
}

// is equivalent to
public void method()
{
    this.intrinsicLock.lock();
    try
    {
        // method body
    }
    finally
    {
        this.intrinsicLock.unlock();
    }
}
  • The intrinsic lock has one condition:
    • wait() is intrinsicCondition.await(), notifyAll() is signalAll(), notify() is signal()
    • They are final methods of Object (hence the different Condition names).
class Bank
{
    private double[] accounts;

    public synchronized void transfer(int from, int to, int amount)
        throws InterruptedException
    {
        while (accounts[from] < amount)
        {
            wait(); // wait on the intrinsic lock's single condition
        }
        accounts[from] -= amount;
        accounts[to] += amount;
        notifyAll(); // notify all threads waiting on the condition
    }

    public synchronized double getTotalBalance() {
        /* ... */ return 0;
    }
}
  • Static synchronized methods lock the Class object (Bank.class), so no other thread can call this or any other synchronised static method of the class.
  • Limitations of intrinsic locks:
    • Before Java 25, virtual threads were pinned
      • in synchronized: a pinned thread cannot unmount from its carrier
      • Brief pinning is fine, but many blocked pinned threads hurt throughput by stopping carriers from running other virtual threads.
    • You cannot interrupt a thread waiting for an intrinsic lock (ReentrantLock.lockInterruptibly exists).
    • No timeout on acquiring an intrinsic lock.
    • A single condition per lock can be inefficient.
  • Recommendation:
    1. Avoid explicit locking when you can: use java.util.concurrent mechanisms that lock for you (for instance the blocking queue of section 10.6.1).
    2. If synchronized works, use it (less code, fewer errors), mindful that the lock is public (next section).
    3. Use Lock/Condition for virtual threads before Java 25, or when you need the extra power.
  • Since Java 25, synchronized no longer pins virtual threads
    • (native methods and foreign functions still do)
    • To see pinning, use Java Flight Recorder events VirtualThreadPinned and VirtualThreadSubmitFailed, or jcmd pid JFR.start then jcmd pid JFR.view pinned-threads
    • Before Java 25: -Djdk.tracePinnedThreads=short or full (one warning per location, with a stack trace marking <== monitors:1).

// v1ch10/synch2/Bank.java (Listing 10.7, core)
public synchronized void transfer(int from, int to, double amount)
    throws InterruptedException
{
    while (accounts[from] < amount)
    {
        wait();
    }
    accounts[from] -= amount;
    accounts[to] += amount;
    IO.println(" Total Balance: %10.2f".formatted(getTotalBalance()));
    notifyAll();
}

public synchronized double getTotalBalance()
{
    double sum = 0;
    for (double a : accounts)
    {
        sum += a;
    }
    return sum;
}

java.lang.Object (1.0): notifyAll() (unblocks threads that called wait on this object; only inside a synchronised method or block, else IllegalMonitorStateException), notify() (one random thread), wait(), wait(long millis), wait(long millis, int nanos) (nanoseconds below 1,000,000); all throw IllegalMonitorStateException if the caller does not own the lock.

10.5.7 Synchronised blocks

  • A second way to take an object's lock: synchronized (obj) { critical section }. Often an ad hoc lock object is created just to use its lock:
public class Bank
{
    private double[] accounts;
    private final Object lock = new Object();
    // ...
    public void transfer(int from, int to, double amount)
    {
        synchronized (lock) // an ad hoc lock
        {
            accounts[from] -= amount;
            accounts[to] += amount;
        }
        IO.println("...");
    }
}
  • Know your lock object. Pitfalls:
    • Do not lock on a string literal (private final String lock = "LOCK";): literals are shared, so two unrelated places may share the lock and deadlock.
    • Do not lock on primitive wrappers (new Integer(42) is deprecated, and a maintenance programmer may change it to Integer.valueOf(42); with the same magic number twice the lock is accidentally shared).
    • For a static field lock on the class:
      • synchronized (MyClass.class) { staticCounter++; } is OK
      • synchronized (getClass()) is not, because in a subclass getClass() returns a different Class object and mutual exclusion is lost.
    • You must use the same lock for all critical sections, and nobody else must use your lock.
  • Client-side locking
    • uses an object's own lock for extra atomic operations
    • Vector<Double> balances with synchronised get and set does not make transfer safe (preempted between calls)
    • Hijacking works:
public void transfer(Vector<Double> accounts, int from, int to, double amount)
{
    synchronized (accounts)
    {
        accounts.set(from, accounts.get(from) - amount);
        accounts.set(to, accounts.get(to) + amount);
    }
}
  • It depends on Vector using its intrinsic lock for all mutators, which its documentation does not promise: very fragile and not generally recommended.
  • The VM has built-in support for synchronised methods, whereas synchronised blocks compile to a lengthy bytecode sequence managing the lock.

10.5.8 The monitor concept

  • Locks and conditions are powerful but not very object-oriented. The monitor (Per Brinch Hansen and Tony Hoare, 1970s) makes multithreading safe without explicit locks. In Java terms:
    • A monitor is a class with only private fields.
    • Each object has an associated lock.
    • All methods are locked by it: calling obj.method() acquires the lock on entry and releases it on return.
    • The lock can have any number of conditions.
  • Early monitors had one condition and a neat syntax (await accounts[from] >= amount)
    • Research showed that indiscriminate retesting is inefficient, hence explicit condition variables, each managing its own set of threads.
  • Java adapted the idea loosely: every object has an intrinsic lock and an intrinsic condition (wait/notifyAll/notify). A synchronized method acts like a monitor method.
  • Java objects differ from monitors in three ways that compromise thread safety:
Monitor Java object
Fields private Fields need not be private
All methods locked Methods need not be synchronized
Lock is internal The intrinsic lock is available to clients
  • Brinch Hansen reviewed Java's primitives scathingly in "Java's Insecure Parallelism" (ACM SIGPLAN Notices 34:38-45, April 1999), calling its insecure parallelism astonishing to see taken seriously.

10.5.9 Volatile fields

  • Sometimes synchronisation seems excessive just to read or write a field. With modern hardware and compilers there is still plenty of room for error:
    • Multiple processors may hold values in registers or local caches, so threads on different processors see different values for one location.
    • Compilers reorder instructions assuming memory changes only through explicit code in the same thread, but another thread can change it.
  • Locks avoid both: compilers must flush or re-fetch registers, avoid bad reordering and issue memory fences. Details are in the Java Memory Model (JLS section 17.4).
  • Brian Goetz's synchronisation motto: if you write a variable that another thread may next read, or read one that another thread may last have written, you must use synchronisation.
  • volatile is a lock-free way to synchronise access to one field: the compiler and VM treat it as concurrently updated, so a write in one thread is visible to readers in others.
// Done.java
private volatile boolean done;

public boolean isDone()
{
    return done;
}

public void setDone()
{
    done = true;
}
  • The alternative is synchronised accessors, but they can block if another thread holds the object lock. A separate private lock works but is more trouble.
  • Volatile gives no atomicity. done = !done is read, flip, write: not guaranteed to flip.

10.5.10 Final fields

  • A field is also safe to read from multiple threads if it is final: once the constructor completes, any thread with a reference sees the initialised value.
// Bank.java
public class Bank
{
    final HashMap<String, Double> accounts;

    public Bank()
    {
        accounts = new HashMap<>();
    }
}
  • Without final, another thread might see null instead of the constructed map. The map's operations are still not thread-safe; mutation by several threads needs synchronisation.
  • Caveat: the this reference must not escape during construction (assigned to another object's field or passed to another method).
  • A properly constructed object (no escape) with all fields final can be shared without synchronisation.

10.5.11 Atomics

  • Use volatile only for plain assignment. The java.util.concurrent.atomic package gives atomic operations using machine-level instructions without locks.
  • AtomicLong.incrementAndGet atomically increments and returns the new value, even under concurrent access.
// IdGenerator.java
public static final AtomicLong nextNumber = new AtomicLong();

// in some thread
long id = nextNumber.incrementAndGet();
  • For a more complex update, set(Math.max(get(), observed)) is a race condition. Pass a lambda instead:
// Largest.java
largest.updateAndGet(x -> Math.max(x, observed));
largest.accumulateAndGet(observed, Math::max);
  • getAndUpdate and getAndAccumulate return the old value.
  • The same methods exist on AtomicInteger, AtomicIntegerArray, AtomicIntegerFieldUpdater, AtomicLongArray, AtomicLongFieldUpdater, AtomicReference, AtomicReferenceArray and AtomicReferenceFieldUpdater.
  • High contention: optimistic updates need too many retries. LongAdder and LongAccumulator fix this:
    • A LongAdder holds several summands whose sum is the value; threads update different ones and new ones appear as threads grow.
    • It suits cases where the total is needed only after all work is done. Use increment, add and sum.
    • increment does not return the old value, which would undo the gain.
// Counting.java
final var adder = new LongAdder();
executor.submit(() ->
{
    if (condition)
        adder.increment();
});
long total = adder.sum();
  • LongAccumulator generalises it: give the operation and its neutral element, call accumulate, read with get.
// Accumulating.java
final var adder = new LongAccumulator(Long::sum, 0);
adder.accumulate(value);
  • Internally it has variables a1 to an, all starting at the neutral element. accumulate(v) atomically sets one ai = ai op v; get returns a1 op a2 op ... op an.
  • The operation must be associative and commutative, since combination order is unspecified (Math.max, Math.min qualify).
  • DoubleAdder and DoubleAccumulator are the double versions.

10.5.12 On-demand initialisation

  • To initialise a structure exactly once, on first use, rely on the VM running a static initialiser exactly once (it uses a lock internally).
// OnDemandData.java
public class OnDemandData
{
    private OnDemandData()
    {
    }

    public static OnDemandData getInstance()
    {
        return Holder.INSTANCE;
    }

    private static class Holder
    {
        static final OnDemandData INSTANCE = new OnDemandData();
    }
}
  • The Holder class is initialised lazily, at most once. The constructor must not throw: the VM will not try a second time.

10.5.13 Safe publication

  • Final fields of a properly constructed object are seen by all threads
    • Non-final fields have no general guarantee: a thread holding a reference to new BankAccount(1000) might see a balance of zero.
  • A mutable class should protect its fields with a lock anyway
    • For an object that is neither thread-safe nor immutable, it must be safely published (all constructor-set fields visible)
    • That holds when the reference is stored:
    • in a static initialiser;
    • in a volatile field or AtomicReference;
    • in any field where the assignment is protected by a lock;
    • in a final field of a properly constructed object.
  • The lock case covers a Runnable or Callable that is an inner class or lambda capturing a variable (stored in a final field).
  • Storing the reference in a thread-safe structure such as a BlockingQueue or ConcurrentHashMap also publishes it safely.
  • In most reasonable circumstances nothing bad happens. If these details matter, you are on thin ice: rethink the sharing strategy.

10.5.14 Sharing with thread-local variables

  • Sometimes you avoid sharing altogether by giving each thread its own instance (see 10.4.4)
    • SimpleDateFormat is not thread-safe; sharing a static one can give garbage
    • Synchronising is expensive and creating one per use is wasteful.
// Formatting.java
public static final ThreadLocal<SimpleDateFormat> DATEFORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String dateStamp = DATEFORMAT.get().format(new Date());
  • The lambda runs the first time get is called in each thread; afterwards get returns that thread's instance.
  • Math.random and java.util.Random are thread-safe but can be inefficient with many threads on one generator
    • Use ThreadLocalRandom.current().nextInt(upperBound), which keeps the state per thread (currently in fields of the Thread object).

10.6 Thread-safe collections

  • Concurrent modification can damage a data structure: a thread preempted mid-rerouting of hash buckets lets another follow invalid links, throw exceptions or loop forever.
  • You can lock a shared structure, but it is usually easier to pick a thread-safe implementation.

10.6.1 Blocking queues

  • Many threading problems are neatly solved with queues:
    • producers insert, consumers retrieve, and the queue hands data safely between threads
    • For the bank example, transfer threads queue instructions and one thread alone touches the bank, so no synchronisation is needed.
  • A blocking queue blocks on adding to a full queue or removing from an empty one, so it balances workload automatically: a slow first stage makes the second wait
    • a fast one fills the queue until the second catches up.
Method Normal action Special circumstances
add Adds an element Throws IllegalStateException if full
element Returns the head Throws NoSuchElementException if empty
offer Adds, returns true Returns false if full
peek Returns the head Returns null if empty
poll Removes and returns the head Returns null if empty
put Adds an element Blocks if full
remove Removes and returns the head Throws NoSuchElementException if empty
take Removes and returns the head Blocks if empty
  • Three categories:
    • Use put and take when the queue manages threads.
    • add, remove, element throw on full or empty.
    • Since a queue can fill or empty at any moment, use offer, poll, peek, which return a failure indicator.
  • poll and peek return null on failure, so null elements are illegal.
  • Timeout variants:
    • q.offer(x, 100, TimeUnit.MILLISECONDS) tries up to 100 ms to insert (returns false on timeout)
    • q.poll(100, TimeUnit.MILLISECONDS) tries to remove the head (returns null on timeout). put and take are the no-timeout equivalents.
  • Implementations in java.util.concurrent:
Class Notes
LinkedBlockingQueue No upper bound by default; optional maximum capacity
LinkedBlockingDeque Double-ended version
ArrayBlockingQueue Given capacity; optional fairness (longest-waiting threads first, at a significant cost)
PriorityBlockingQueue Removes by priority, not FIFO; unbounded, but retrieval blocks when empty
TransferQueue / LinkedTransferQueue q.transfer(item) blocks until a consumer takes the item
  • Listing 10.8 (BlockingQueueDemo) searches every file under a directory for a keyword:
    • One producer thread enumerates files into an ArrayBlockingQueue<Path> of size 10. It is bounded, or the queue would swallow the whole file system.
    • 100 search threads each take a file, print matching lines (file:lineNumber:line), then take the next.
    • To finish, the enumerator puts a termination object (an empty Path) into the queue
      • A searcher that takes it puts it back for the others and stops
      • This is a "poison pill", like a "last bag" label on a baggage belt.
    • No explicit synchronisation: the queue is the synchronisation mechanism.

    • TransferQueue has transfer and timed tryTransfer.

10.6.2 Efficient maps, sets and queues

  • java.util.concurrent provides ConcurrentHashMap, ConcurrentSkipListMap, ConcurrentSkipListSet and ConcurrentLinkedQueue.
  • Their algorithms minimise contention by allowing concurrent access to different parts.
  • size is not constant time (usually needs traversal). mappingCount returns the size as a long for maps beyond two billion entries.
  • Iterators are weakly consistent:
    • they may or may not reflect later modifications, never return a value twice and never throw ConcurrentModificationException
    • A java.util iterator does throw it.
  • A concurrent hash map supports many readers and a bounded number of writers.
  • Poor hash functions put entries into few buckets
    • even String.hashCode can be attacked with crafted colliding strings. In recent Java versions buckets become trees when keys are Comparable, guaranteeing O(log n).
  • Constructors:
    • ConcurrentHashMap(), (initialCapacity), (initialCapacity, loadFactor, concurrencyLevel) (defaults 16 and 0.75; concurrency level is the estimated number of writer threads)
    • The skip-list set and map take an optional Comparator, otherwise elements or keys must be Comparable.

10.6.3 Atomic update of map entries

  • A thread-safe map does not make compound operations atomic. Counting word frequencies with get then put is wrong: another thread may update the same count between them.
// Wrong.java
Long oldValue = map.get(word);
Long newValue = oldValue == null ? 1 : oldValue + 1;
map.put(word, newValue); // ERROR--might not replace oldValue
  • Two separate concerns:
    • a plain HashMap under concurrent use can lose or loop links and be destroyed
    • a ConcurrentHashMap never corrupts its structure, but the sequence of get and put is not atomic.
  • Old fixes:
    • A replace retry loop (while (!map.replace(word, oldValue, newValue))).
    • A ConcurrentHashMap<String, AtomicLong> with putIfAbsent(word, new AtomicLong()) then get(word).incrementAndGet(), which constructs a throwaway AtomicLong every time.
  • Modern methods:
Method Behaviour
compute(key, (k, v) -> ...) Computes the new value from the key and old value (or null)
computeIfPresent Only when there is already a value
computeIfAbsent Only when there is not yet one
merge(key, initial, fn) Uses initial for a new key, otherwise fn(existing, initial); the function does not get the key 
// Counting.java
map.compute(word, (_, v) -> v == null ? 1 : v + 1);
map.computeIfAbsent(word, k -> new LongAdder()).increment();
map.merge(word, 1L, Long::sum);
  • computeIfAbsent with a LongAdder creates the counter only when needed. merge(word, 1L, Long::sum) is the most concise form.
  • No null values in a ConcurrentHashMap (null signals an absent key). If the function given to compute or merge returns null, the entry is removed.
  • The function should be quick (other updates may block while it runs) and must not update other parts of the map.
  • Listing 10.9 (ConcurrentHashMapDemo) counts words in all .java files under a directory: it submits one task per file to Executors.newVirtualThreadPerTaskExecutor(), each doing map.merge(word, 1L, Long::sum) for every token, then prints words that occur at least 10 times.

10.6.4 Bulk operations on concurrent hash maps

  • Bulk operations run safely while other threads use the map, traversing as they go
    • There is no snapshot, so treat results as an approximation unless the map is known to be stable.
  • Three kinds:
    • search applies a function until it yields a non-null result, which it returns.
    • reduce combines keys and/or values with an accumulation function.
    • forEach applies a function to all keys and/or values.
  • Four versions of each: operationKeys, operationValues, operation (keys and values) and operationEntries.
  • Each takes a parallelism threshold: above that many elements the operation is parallel. Long.MAX_VALUE forces one thread; 1 makes maximum parallelism.
// Bulk.java
String result = map.search(threshold, (k, v) -> v > 1000 ? k : null);

map.forEach(threshold, (k, v) -> IO.println(k + " -> " + v));

// transformer first, then consumer; null from transformer skips the entry
map.forEach(threshold,
    (k, v) -> v > 1000 ? k + " -> " + v : null,
    IO::println);

Long sum = map.reduceValues(threshold, Long::sum);

Integer maxlength = map.reduceKeys(threshold,
    String::length, // transformer
    Integer::max);  // accumulator

Long count = map.reduceValues(threshold,
    v -> v > 1000 ? 1L : null,
    Long::sum);
  • search returns the first match or null if every call returns null.
  • A transformer returning null filters the item out.
  • reduce returns null if the map is empty or all entries were filtered. With one element the transformed value is returned and the accumulator is not applied.
  • Specialisations with suffixes ToInt, ToLong, ToDouble need a default value and a primitive accumulator:
// Primitive.java
long sum = map.reduceValuesToLong(threshold,
    Long::longValue, // transformer to primitive
    0,               // default for empty map
    Long::sum);      // primitive accumulator
  • Unlike the object versions, one element is accumulated with the default, so the default must be the accumulator's neutral element.

10.6.5 Concurrent set views

  • There is no ConcurrentHashSet. ConcurrentHashMap.<String>newKeySet() returns a Set<K> wrapping a ConcurrentHashMap<K, Boolean> (values are all Boolean.TRUE).
  • keySet() on an existing map gives a mutable key set: removing elements removes entries
    • Adding makes no sense (no value), so use map.keySet(1L) to supply a default value for added elements.
  • Collections.newSetFromMap works too, but newKeySet is simpler and slightly more efficient.

10.6.6 Copy on write arrays

  • CopyOnWriteArrayList and CopyOnWriteArraySet: every mutator copies the underlying array.
  • Good when iterating threads greatly outnumber mutating threads. An iterator holds the old array, so it has a consistent, possibly outdated view with no synchronisation cost.

10.6.7 Parallel array algorithms

  • Arrays.parallelSort sorts primitive or object arrays (a Comparator is allowed; ranges are allowed)
    • The word parallel is in the name so callers avoid comparators with side effects.
// ParallelSort.java
var contents = Files.readString(Path.of("alice.txt"));
String[] words = contents.split("\\PL+");
Arrays.parallelSort(words);
Arrays.parallelSort(words, Comparator.comparing(String::length));
Arrays.parallelSort(words, words.length / 2, words.length); // upper half
  • Arrays.parallelSetAll(values, i -> i % 10) fills from a function of the index, for all primitive arrays and object arrays.
  • Arrays.parallelPrefix(values, (x, y) -> x * y) replaces each element with the accumulation of its prefix: [1, 1x2, 1x2x3, ...]. It parallelises like this:
    1. Join neighbouring pairs ([1, 1x2, 3, 3x4, 5, 5x6, 7, 7x8]); regions are independent.
    2. Update the marked elements by combining with elements one or two positions below.
    3. After log n steps the process is complete: a win over the linear pass when enough processors are available.

10.6.8 Older thread-safe collections

  • Vector and Hashtable were thread-safe from the start but are obsolete, replaced by ArrayList and HashMap, which are not thread-safe.
  • Make any collection thread-safe with a synchronisation wrapper, and keep no reference to the original:
// Wrappers.java
List<E> synchArrayList = Collections.synchronizedList(new ArrayList<>());
Map<K, V> synchHashMap = Collections.synchronizedMap(new HashMap<>());
  • You still need client-side locking to iterate while others may mutate
    • The same applies to a for-each loop
    • The iterator can still throw ConcurrentModificationException, and the lock makes detection reliable.
// Iterating.java
synchronized (synchHashMap)
{
    Iterator<K> iter = synchHashMap.keySet().iterator();
    while (iter.hasNext())
    {
        // ...
    }
}
  • Prefer java.util.concurrent collections: ConcurrentHashMap lets threads touching different buckets proceed without blocking each other
    • One exception: a frequently mutated array list, where a synchronised ArrayList can beat CopyOnWriteArrayList.
  • Collections offers synchronizedCollection, synchronizedList, synchronizedSet, synchronizedSortedSet, synchronizedMap and synchronizedSortedMap.

10.7 Asynchronous computations

  • So far: split a task, then wait for all pieces. Waiting is fine with virtual threads, but with platform threads a wait-free, asynchronous style gives higher throughput.

10.7.1 Completable futures

  • A Future needs get, which blocks
    • CompletableFuture implements Future and also lets you register a callback, called in some thread when the result is ready: f.thenAccept(s -> ...).
  • Some API methods already return one, such as HttpClient.sendAsync (Volume II, chapter 4):
// Fetch.java
HttpClient client = HttpClient.newHttpClient();
HttpRequest request = HttpRequest.newBuilder(URI.create(urlString)).GET().build();
CompletableFuture<HttpResponse<String>> f = client.sendAsync(
    request, BodyHandlers.ofString());
  • To make your own, call the static CompletableFuture.supplyAsync (do not submit to an executor service directly):
// ReadPage.java
public CompletableFuture<String> readPage(URI uri)
{
    return CompletableFuture.supplyAsync(() ->
    {
        try
        {
            return new String(uri.toURL().openStream().readAllBytes());
        }
        catch (IOException e)
        {
            throw new UncheckedIOException(e);
        }
    }, executor);
}
  • Without an executor the task runs on ForkJoinPool.commonPool(), which you usually do not want.
  • The first parameter is a Supplier<T>, not a Callable<T>: same shape, but a Supplier cannot throw checked exceptions. The book calls that an uninspired choice.
  • A CompletableFuture completes with a result or with an uncaught exception. whenComplete((s, t) -> ...) receives both (the missing one is null):
// Completion.java
f.whenComplete((s, t) ->
{
    if (t == null)
    {
        // process the result s
    } else {
        // process the Throwable t
    }
});
  • A CompletableFuture is called completable because you can set the completion value
    • Other libraries call it a promise and completing it "fulfilling the promise"
    • The consumer does not care how the value is set.
  • supplyAsync is one producer. Another can have several tasks race to complete one future:
// Racing.java
var f = new CompletableFuture<Integer>();
executor.execute(() ->
{
    int n = workHard(arg);
    f.complete(n);
});
executor.execute(() ->
{
    int n = workSmart(arg);
    f.complete(n);
});
executor.execute(() ->
{
    try
    {
        Thread.sleep(timeout);
        f.completeExceptionally(new TimeoutException());
    }
    catch (InterruptedException e)
    {
        f.completeExceptionally(e);
    }
});
  • complete and completeExceptionally are safe from several threads; once completed, further calls have no effect.
  • cancel does not interrupt
    • the computation (unlike a plain Future): it just completes the future exceptionally with a CancellationException
    • This also applies to futures from supplyAsync.

10.7.2 Composing completable futures

  • Non-blocking code uses callbacks. With several steps, logic is spread over callbacks ("callback hell"), and retry logic such as a mistyped login is worse still.
  • CompletableFuture lets you compose a pipeline with all the code in one place:
// Images.java
CompletableFuture<String> contents = readPage(uri);
CompletableFuture<List<URI>> imageLinks = contents.thenApply(this::getImageLinks);
  • thenApply does not block and returns another future; when the first completes, its result is fed to getImageLinks and the return becomes the final result.
  • thenApply(f)
    • takes T -> U. thenCompose(f) takes T -> CompletableFuture<U> (a function that eventually yields a U)
    • it works like thenApply but the composition completes when the returned future does.
  • Handling errors in a pipeline:
    • whenComplete sees result or exception; handle also computes a new result from either.
    • exceptionally supplies a dummy value on failure.
    • completeOnTimeout supplies a value on timeout; orTimeout fails with a TimeoutException.
// Recovery.java
CompletableFuture<List<URI>> imageLinks = readPage(uri)
    .exceptionally(ex -> "<html></html>")
    .thenApply(this::getImageLinks);

CompletableFuture<List<URI>> viaTimeout = readPage(uri)
    .completeOnTimeout("<html></html>", 30, TimeUnit.SECONDS)
    .thenApply(this::getImageLinks);

CompletableFuture<String> failing = readPage(uri).orTimeout(30, TimeUnit.SECONDS);
  • Table 10.3, adding an action to a CompletableFuture<T> (void-result methods normally end a pipeline):
Method Parameter Description
thenApply T -> U Apply a function to the result
thenAccept T -> void Like thenApply, void result
thenCompose T -> CompletableFuture<U> Invoke on the result and execute the returned future
thenRun Runnable Run it, void result
handle (T, Throwable) -> U Process result or error into a new result
whenComplete (T, Throwable) -> void Like handle, void result
exceptionally Throwable -> U Compute a result from the error
exceptionallyCompose Throwable -> CompletableFuture<U> Invoke on the exception and execute the returned future
completeOnTimeout T, long, TimeUnit Yield the given value on timeout
orTimeout long, TimeUnit Yield a TimeoutException on timeout
  • Combining two futures (Table 10.4). The first three run a CompletableFuture<T> and a CompletableFuture<U> concurrently and combine the results
    • the next three run two CompletableFuture<T> and pass on whichever finishes first (the other result is ignored).
Method Parameters Description
thenCombine CompletableFuture<U>, (T, U) -> V Execute both and combine the results
thenAcceptBoth CompletableFuture<U>, (T, U) -> void Like thenCombine, void result
runAfterBoth CompletableFuture<?>, Runnable Run after both complete
applyToEither CompletableFuture<T>, T -> V Pass the first available result to the function
acceptEither CompletableFuture<T>, T -> void Like applyToEither, void result
runAfterEither CompletableFuture<?>, Runnable Run after either completes
  • Many futures (Table 10.5), static methods:
    • allOf(CompletableFuture<?>...) completes with no result after all complete (some perhaps exceptionally).
    • anyOf(...) completes when any does, with its result or exception. It does not stop the others, and may yield an exceptional future even though others succeeded.
  • Each method also has two Async variants for the executor of the dependent completion: one with a default executor (not recommended) and one with an Executor parameter.
  • For a pipeline, start with an Async variant to set the executor, then use non-Async methods to continue with the same executor.
  • Technically these methods take CompletionStage parameters (how to compose async computations); a CompletableFuture is both a CompletionStage and a Future.
  • Listing 10.10 (CompletableFutureDemo)
    • reads a page, finds images, loads and saves them
    • All async methods return a CompletableFuture
    • A completed future provides the URI, so the pipeline looks uniform:
// CompletableFutureDemo.java (main)
CompletableFuture.completedFuture(uriToProcess)
    .thenComposeAsync(this::readPage, executor)
    .thenApply(this::getImageLinks)
    .thenCompose(this::getImages)
    .thenAccept(this::saveImages);
  • The ideal pipeline has three kinds of step:
    • an async function T -> CompletableFuture<U> → thenCompose;
    • a sync function T -> U → thenApply;
    • a final consumer with no result → thenAccept.
  • The listing's helpers:
    • readPage and getImages use supplyAsync with the executor
    • getImageLinks is a regex scan that does not block
    • saveImages writes PNG files under /tmp and shuts the executor down. It also shows an alternative start with HttpClient.sendAsync(...).thenApply(HttpResponse::body).

10.7.3 Long-running tasks in user interface callbacks

  • Threads keep programs responsive
    • In Swing, JavaFX and Android the UI is not thread-safe and all actions run on one UI thread; JavaFX and Android even throw if another thread touches the UI
    • A long task on the UI thread freezes the interface.
// Bad.java
open.addActionListener(event -> { // BAD--runs on the UI thread
    var in = new Scanner(path);
    while (in.hasNextLine())
    {
        String line = in.nextLine();
    }
});
  • Run the work in another thread (executor.execute(task)), but update the UI only on the UI thread. Each toolkit schedules a Runnable there
    • Swing uses EventQueue.invokeLater(() -> label.setText(percentage + "% complete")).
  • Helper classes handle the details: SwingWorker (Swing), Task (JavaFX), AsyncTask (Android).
  • Listing 10.11 (SwingWorkerDemo) loads a text file (try The Count of Monte Cristo from the book's gutenberg directory):
    • While loading, Open is disabled and Cancel enabled; the status bar shows a line counter; at the end the status says Done and the menu items swap back (Figure 10.6).
    • Typical background-task pattern: update progress after each work unit, then make a final UI change.
  • SwingWorker usage:
    • Override doInBackground (worker thread) for the work and call publish for progress.
    • process runs on the event dispatch thread with the published data; several publish calls may be batched into one process(List<V>).
    • done runs on the event dispatch thread when finished.
    • Each worker is used once: construct, then execute (typically on the event dispatch thread, but not required).
    • SwingWorker<T, V> implements Future<T>: T is the result, V the progress type
      • get blocks, so call it from done, not straight after execute
      • cancel makes get throw CancellationException.
  • In the example, progress is a record and the result a StringBuilder, so the worker is SwingWorker<StringBuilder, ProgressData>
    • The 1 ms Thread.sleep is only to test cancellation
    • process shows the last line number and appends all lines with one text area update (JTextArea is slow).
// ProgressData.java
private record ProgressData(int number, String line)
{
}

// TextReader.java (excerpt)
public StringBuilder doInBackground() throws IOException, InterruptedException
{
    int lineNumber = 0;
    var in = new Scanner(path);
    while (in.hasNextLine())
    {
        String line = in.nextLine();
        lineNumber++;
        text.append(line).append("\n");
        var data = new ProgressData(lineNumber, line);
        publish(data);
        Thread.sleep(1); // to test cancellation only
    }
    return text;
}

public void process(List<ProgressData> data)
{
    if (isCancelled())
        return;
    var b = new StringBuilder();
    statusLine.setText("" + data.getLast().number());
    for (ProgressData d : data)
        b.append(d.line()).append("\n");
    textArea.append(b.toString());
}
  • The full done method calls get(), sets the text and status Done, handles CancellationException (status Cancelled) and ExecutionException (shows the cause), then disables Cancel and re-enables Open
    • The worker starts in the Open item's listener.

abstract T doInBackground() The background task; returns the result
void process(List<V> data) Handle progress data on the event dispatch thread
void publish(V... data) Forward progress data to the event dispatch thread (call from doInBackground)
void execute() Schedule on a worker thread

10.8 Processes

  • To run another program, use ProcessBuilder (a more flexible replacement for Runtime.exec) and Process, which runs a command in a separate OS process and exposes its standard streams.

10.8.1 Building a process

  • Give the command as strings or a List<String>:
    • new ProcessBuilder("gcc", "myapp.c")
    • The first must be an executable, not a shell builtin: for dir on Windows use "cmd.exe", "/C", "dir".
  • The working directory defaults to the JVM's; change it with directory(path.toFile()). Configuration methods return the builder, so chain them and finish with start().
  • By default stdin, stdout and stderr are pipes:
// Streams.java
OutputStream processIn = p.getOutputStream();
InputStream processOut = p.getInputStream();
InputStream processErr = p.getErrorStream();

BufferedWriter textIn = p.outputWriter();
BufferedReader textOut = p.inputReader();
BufferedReader textErr = p.errorReader();
  • Direction is inverted: the process's input is an output stream in the JVM (you write to it); its output and error are input streams for you.
  • Redirection options:
    • inheritIO()
      • shares all three streams with the JVM (console input is forwarded, output appears in the console)
      • Or pass ProcessBuilder.Redirect.INHERIT to redirectInput, redirectOutput or redirectError.
    • Files:
      • redirectInput(inputFile).redirectOutput(outputFile).redirectError(errorFile). Output and error files are created or truncated at start
      • use Redirect.appendTo(outputFile) to append.
    • redirectErrorStream(true) merges error into output (ordering preserved), after which you can no longer call redirectError or getErrorStream.
  • Environment variables: get builder.environment() (initialised from the JVM's), then put or remove:
// Env.java
Map<String, String> env = builder.environment();
env.put("LANG", "fr_FR");
env.remove("JAVA_HOME");
Process p = builder.start();
  • Pipelines
    • (like | in a shell): ProcessBuilder.startPipeline(List.of(...)) and read the last process's output
    • The example lists unique file extensions with find | grep -o | sort | uniq
    • A Java directory walk would be more efficient (Volume II, chapter 2).
// Pipeline.java
List<Process> processes = ProcessBuilder.startPipeline(List.of(
    new ProcessBuilder("find", "/opt/jdk-25"),
    new ProcessBuilder("grep", "-o", "\\.[^./]*$"),
    new ProcessBuilder("sort"),
    new ProcessBuilder("uniq")
));
Process last = processes.getLast();
var result = new String(last.getInputStream().readAllBytes());

10.8.2 Running a process

  • Call start(), then write to input and read output/error if they are pipes.
// Ls.java
Process process = new ProcessBuilder("/bin/ls", "-l")
    .directory(Path.of("/tmp").toFile())
    .start();
try (var in = new Scanner(process.getInputStream()))
{
    while (in.hasNextLine())
        IO.println(in.nextLine());
}
  • Stream buffers are limited: do not flood the input and read output promptly; with a lot of data use separate threads to produce and consume.
  • Waiting:
    • process.waitFor() returns the exit value (0 by convention for success). waitFor(delay, TimeUnit.SECONDS) returns true if it did not time out
    • then read exitValue(), otherwise call destroyForcibly().
  • Alternatively leave it running and poll isAlive()
    • Kill with destroy or destroyForcibly: on UNIX SIGTERM versus SIGKILL (platform-dependent)
    • supportsNormalTermination() says whether destroy can end it normally.
  • process.onExit() yields a CompletableFuture<Process> for an asynchronous notification:
// Exit.java
process.onExit().thenAccept(
    p -> IO.println("Exit value: " + p.exitValue()));
  • Since Java 21 the logger named java.lang.ProcessBuilder logs processes started by Runtime.exec and ProcessBuilder at DEBUG and TRACE (pid, directory, command, stack trace; arguments only at TRACE).

10.8.3 Process handles

  • ProcessHandle describes your own child or any running process. Four ways to get one:
    • p.toHandle() for a Process;
    • ProcessHandle.of(id) for an OS process id;
    • ProcessHandle.current() for this JVM;
    • ProcessHandle.allProcesses() for a Stream<ProcessHandle> of all visible processes.
  • From a handle:
    • pid(), parent() (Optional), children(), descendants()
    • Streams from allProcesses, children and descendants are snapshots: processes may have ended or started since.
  • info() returns a ProcessHandle.Info with arguments(), command(), commandLine(), startInstant(), totalCpuDuration() and user(), all Optional because the OS may not report them.
  • Handles have isAlive, supportsNormalTermination, destroy, destroyForcibly and onExit like Process, but no waitFor.
  • Listing 10.12 (ProcessDemo) runs ls -l in /tmp, prints the child's pid and exit value, then lists the command lines of all processes whose command contains "java".

Summary points

  • Start threads with start, not run. Prefer executors and virtual threads for blocking work. Interruption is cooperative.
  • Futures and executors coordinate results; structured concurrency scopes subtasks (preview in Java 25). Thread locals and scoped values avoid sharing.
  • Shared mutable state needs locks, synchronized or volatile/atomics. Races are silent, deadlocks need careful lock ordering, and the lock object must be private and consistent.
  • Prefer thread-safe collections and blocking queues over hand-rolled locking. ConcurrentHashMap needs compute/merge for atomic updates.
  • CompletableFuture composes asynchronous pipelines; the UI thread must never run long tasks, and UI updates belong on that thread.
  • ProcessBuilder and ProcessHandle run and inspect external programs.
Terms to carry forward
  • Race condition: result depends on thread interleaving.
  • Critical section / intrinsic lock / monitor: code guarded by one lock (a monitor method-wise).
  • Deadlock: threads each wait for a lock another holds.
  • Memory visibility / volatile / memory fence: when one thread's write is seen by another.
  • Safe publication: a reference stored so that fields are fully visible.
  • Atomic / LongAdder: lock-free updates; adder splits contention across summands.
  • Blocking queue / poison pill: handoff structure that blocks, and a sentinel that ends consumers.
  • Weakly consistent iterator: tolerates concurrent modification without ConcurrentModificationException.
  • Completable future / thenCompose: composable promise; chains async steps.
  • Event dispatch thread / SwingWorker: the only thread allowed to touch Swing, and a helper for background work.
  • ProcessHandle: view of any OS process.
