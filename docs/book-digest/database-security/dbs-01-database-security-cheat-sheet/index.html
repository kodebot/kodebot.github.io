Database Security 1: The OWASP Database Security Cheat Sheet

Source: OWASP Cheat Sheet Series, "Database Security Cheat Sheet" (cheatsheetseries.owasp.org), licensed CC BY-SA 4.0 (the repository's LICENSE file). Own-words summary, much shorter than the source; as an adaptation it is shared under the same licence. Next: Database Security 2: SQL Injection Prevention and Query Parameterisation.

Takeaways
  • The sheet covers SQL databases (MySQL, PostgreSQL, MariaDB, SQL Server) for developers and administrators; non-relational stores have their own sheet.
  • Five layers: isolate the database, encrypt connections, authenticate every connection, give least-privilege permissions, and harden and back up the server.
  • Never connect a thick client directly to the database; go through an API that enforces access control.
  • Database credentials never go in source code.

1.1 Protect the backend database

  • Isolate the database from other servers and let it talk to as few hosts as possible:
    • disable TCP access and require a local socket file or named pipe where possible;
    • bind only to localhost;
    • restrict the port to specific hosts with firewall rules;
    • put the server on a dedicated internal network segment separate from the application server;
    • protect web-based admin tools (phpMyAdmin, pgAdmin) with authentication, HTTPS and network restrictions.
  • An application on an untrusted system (a thick client) must reach the database through an API that enforces access control; never connect it directly.

Transport layer protection

  • Most databases start with unencrypted network connections
    • some encrypt only the initial authentication (the sheet names SQL Server), so the rest of the traffic, with sensitive data, travels in clear text.
  • Configure the database to allow only encrypted connections
    • install a trusted certificate
    • have the client use TLS 1.2 or higher with modern ciphers (AES-GCM or ChaCha20) and verify the certificate. See the OWASP Transport Layer Security cheat sheet.

1.2 Configure secure authentication

  • Always require authentication, even for local connections.
  • Database accounts should have strong unique passwords, be used by a single application or service, and have minimum permissions.
  • Run normal account management: review accounts and permissions regularly, remove accounts when an application is decommissioned, change passwords when staff leave or compromise is suspected.
  • For SQL Server consider Windows integrated authentication, which removes the need to store credentials in the application (MySQL has a Windows native authentication plugin).

Storing credentials

  • Never in source code, especially unencrypted
    • Keep them in a configuration file outside the web root, readable only by the required users, not checked into source control, and encrypted where the platform allows (the sheet cites ASP.NET web.config encryption).

1.3 Create secure permissions

  • Apply least privilege at every available level.
  • In all environments:
    • do not use the built-in root, sa or SYS accounts, and do not grant administrative rights over the instance;
    • let the account connect only from allowed hosts (often localhost or the application server);
    • restrict it to the databases it needs; use separate databases and accounts for development, UAT and production;
    • grant only needed permissions (most applications need only SELECT, UPDATE and DELETE); the account must not own the database, because that can lead to privilege escalation;
    • avoid database links and linked servers; if required use a minimal account.
  • Security-critical applications go further: table-level, column-level and row-level permissions, and blocking access to underlying tables so all access goes through restricted views.

1.4 Configuration and hardening

  • Harden the server's operating system from a secure baseline such as the CIS Benchmarks or Microsoft Security Baselines.
  • For any database:
    • install security updates and patches;
    • run the service under a low-privilege account;
    • remove default accounts and databases;
    • keep transaction logs on a separate disk from the main database files;
    • back up regularly, with backups protected by permissions and ideally encrypted.
Product Extra hardening named by the sheet
SQL Server disable xp_cmdshell, xp_dirtree and other unneeded stored procedures; disable CLR execution; disable the SQL Browser service; disable mixed-mode authentication unless needed; remove sample Northwind and AdventureWorks databases
MySQL or MariaDB run mysql_secure_installation (removes default databases and accounts); disable the FILE privilege for all users so they cannot read or write files
PostgreSQL see the PostgreSQL server setup and operation documentation
MongoDB, Redis see the NoSQL Security cheat sheet, the MongoDB security checklist and the Redis security guide

Summary points

  • Reachability, encryption, identity, permissions, hardening: check each layer.
  • One account per application with the fewest rights; separate environments.
  • Defaults (accounts, samples, mixed-mode authentication) are the first things to remove.
Terms to carry forward
  • Least privilege: only the permissions needed for the job.
  • Thick client: software on a user's machine that talks to servers directly.
  • CIS Benchmark: a published secure-configuration baseline.
  • Linked server / database link: a database's connection to another database, a privilege-escalation risk.
  • View: a stored query used to limit what an account can see.
