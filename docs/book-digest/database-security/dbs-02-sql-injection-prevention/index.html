Database Security 2: SQL Injection Prevention and Query Parameterisation

Source: OWASP Cheat Sheet Series, "SQL Injection Prevention Cheat Sheet" and "Query Parameterization Cheat Sheet" (cheatsheetseries.owasp.org), licensed CC BY-SA 4.0 (the repository's LICENSE file). Own-words summary, much shorter than the source; code listings are not reproduced; as an adaptation it is shared under the same licence. Previous: Database Security 1: The OWASP Database Security Cheat Sheet.

Takeaways
  • SQL injection happens when untrusted data becomes part of the query's syntax. The data can come from an HTTP request, an LDAP directory, an email, a third-party API or even the database itself.
  • The fix: define the SQL structure separately from the data values and bind values through the database API (parameterised queries).
  • Table names, column names and sort direction cannot be parameters: pick them from a fixed application-owned allow-list.
  • Hardening (least privilege, views) limits damage; validation complements binding and never replaces it. Manual escaping is strongly discouraged.

2.1 The problem

  • Impact, depending on features and privileges:
    • read data
    • modify data
    • run administration operations (even shut the DBMS down)
    • read files from or write files to the DBMS file system
    • in some cases execute operating system commands.
  • It applies to ORM query languages too (JPQL in JPA, HQL in Hibernate).
  • The same controls apply whether data arrives in an HTTP request, from another service or from previously stored data.
  • Binding stops a value changing the query's syntax
    • The sheet's example: an input like tom' or '1'='1 is treated as the literal name to match
    • Binding does not decide whether the caller may access the matching account; that is access control (OWASP A01).

2.2 Primary defences

Parameterised queries

  • Write the SQL with placeholders (such as ?), then bind the values through the driver. Concatenating untrusted values into the query before preparing it defeats the protection.
  • Do it server-side
    • Many client-side libraries only build the query by string concatenation before sending raw SQL to a server, so check that parameterisation really happens on the server.
  • The query parameterisation sheet shows prepared statements for Java (built-in and JPA/Hibernate), .NET, ASP.NET, Ruby (ActiveRecord and built-in), PHP (PDO), ColdFusion, Perl (DBI) and Rust (SQLx).

Stored procedures

  • Binding the arguments of the call protects the call, not dynamic SQL built inside the procedure
    • A procedure that concatenates data into SQL text and runs it (for example with EXECUTE IMMEDIATE or exec) can still be injectable.
  • Use static SQL with parameters, or bind values in internal dynamic SQL: Oracle PL/SQL uses bind variables with EXECUTE, SQL Server uses parameterised EXEC, PostgreSQL has EXECUTE ... USING for values and format('%I', ...) for quoting identifiers
    • Quoting an identifier protects syntax but does not limit which tables the application may select.

Allow-list for structure

  • Parameter markers stand for data values, not for table names, column names or keywords such as ASC and DESC.
  • Keep these choices fixed in code
    • When users must choose, map their choice to a small set of values allowed for that query and reject everything else (for a sort direction map to the literal ASC or DESC rather than appending supplied text).

Manual escaping: strongly discouraged

  • It is error-prone:
    • escaping rules are not simple, differ between SQL dialects, and can depend on database settings (the sheet cites MySQL NO_BACKSLASH_ESCAPES)
    • Replace it with parameter binding.

2.3 Hardening (defence in depth)

  • Least privilege:
    • start from what each account needs rather than trimming a powerful default
    • Read-only functions get read-only rights on only the tables they need
    • Do not give application accounts DBA or admin rights: it is easy and "just works" but is very dangerous.
  • Minimise privileges beyond SQL injection too:
    • an attacker may simply change a parameter to a value they are not allowed but the application is
    • Also run the DBMS under a restricted operating-system account, not root or system (the sheet notes MySQL runs as system on Windows by default).
  • If an account needs only part of a table, give it a view (for example product names and prices without supplier costs) and SELECT only on that view
    • Verify your database's view privilege rules (PostgreSQL normally checks underlying table access using the view's owner)
    • Queries against views still need parameterisation.
  • If you use stored procedures everywhere, grant application accounts only the right to execute them, with no direct table rights. Rarely if ever grant create or delete rights.
  • Different accounts per application, and ideally per function: a login page needs read access to the username and password fields and no write access, while a sign-up page needs insert rights, which can only be enforced with different database users.
  • Input validation
    • complements parameter binding
    • it does not replace it. Keep binding every value even if it passes type, length or format checks, because a check safe in one dialect may be unsafe in another.

2.4 Testing and detection

  • Review query construction in application code and stored procedures: untrusted values bound rather than concatenated
    • dynamic identifiers and sort directions taken from a fixed mapping. Preparing the outer call is no evidence that a procedure's internal SQL is safe.
  • Use the OWASP Web Security Testing Guide's SQL injection tests, including blind and out-of-band techniques.

Summary points

  • Separate command from data: parameters for values, allow-lists for structure.
  • Never rely on escaping or validation alone.
  • Assume a bug will occur and limit what the application account can do.
Terms to carry forward
  • Parameterised (prepared) query: SQL with placeholders; values bound separately.
  • Bind variable: the parameter used in dynamic SQL inside a procedure.
  • Allow-list: only values you list are accepted.
  • HQL / JPQL injection: injection into an ORM's query language.
  • Blind injection: inferring data from behaviour, with no visible output.
