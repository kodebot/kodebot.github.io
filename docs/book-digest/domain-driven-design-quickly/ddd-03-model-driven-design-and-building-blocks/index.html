DDD Quickly 3: Model-driven design and its building blocks

Source: Abel Avram, Domain Driven Design Quickly (InfoQ, 2006), chapter "Model-Driven Design" up to Modules (pp. 23-41). Previous: DDD Quickly 2: The Ubiquitous Language. Next: DDD Quickly 4: Aggregates, Factories and Repositories.

The one-minute version

A good model is not enough: it must be transferred into code, and the code must stay tied to the model. So model and design are done together, developers join the modelling, and code changes are model changes. Object orientation is the natural fit. The chapter then gives the building blocks: layered architecture (isolate the domain), entities (identity), value objects (no identity, immutable), services (stateless operations), modules (cohesion and low coupling). Aggregates, factories and repositories follow in DDD Quickly 4: Aggregates, Factories and Repositories.

From model to code

  • Analysts may work with business experts for months and build a correct model
    • then developers find parts that cannot be expressed in code, so they use the model as "inspiration", add their own design, add more classes, and the divide between model and implementation widens
      • A product may work, but will it stand the test of time, be extendable and maintainable?
  • Any domain can be expressed by many models, and any model in many ways in code. An analytically correct model may break design principles or be impractical
    • choose a model that is easy and accurate to put into code.
  • The analysis-model technique (a model separate from code design, usually made by different people, ignoring software as "a confusing factor"): its problems:
    • It was not built with design principles in mind, so developers adapt it or create a separate design; the mapping is lost and analysis models are abandoned after coding starts.
    • Analysts cannot foresee defects or all the intricacies
      • they over-detail some parts and under-detail others
        • A domain-truthful model may have serious persistence or performance problems, and developers decide on their own, drifting from the model.
    • Knowledge is lost in the hand-over:
      • diagrams and writing cannot carry everything, and developers make assumptions, possibly wrong ones. Analysts hold closed meetings with lots of shared knowledge condensed into a model
      • it would be far more productive if developers joined the analyst meetings.

The better approach: closely relate domain modelling and design.

  • Build the model with an eye on software and design; include developers in the modelling
    • Tightly relating code to the model gives the code meaning and makes the model relevant
    • Developers give feedback so problems show up early.
  • Those who write code must know the model well and feel responsible for its integrity
    • A change to code implies a change to the model; otherwise they refactor until it no longer expresses the model
    • An analyst separated from implementation loses concern for its limits and produces an impractical model.
  • Anyone who contributes to the model must spend time touching the code,
    • whatever their role
    • Everyone who changes code must learn to express a model through code
    • Every developer must take part in some model discussion and have contact with domain experts.
  • If the design does not map to the model, the model is of little value and the software's correctness is suspect
    • complex mappings are hard to understand and impossible to maintain
      • "A deadly divide opens between analysis and design." Design part of the system to reflect the model in a very literal way
    • revisit the model so it is implementable more naturally while reflecting deeper domain insight
    • demand a single model that serves both and supports a fluent Ubiquitous Language. Terminology and basic assignment of responsibilities come from the model.
  • Tools: you need a language that supports a modelling paradigm, such as object-oriented programming: classes, associations, instances and messaging map directly to model objects and relationships.
  • Procedural languages offer limited support.
    • Objects can be simulated as data structures with functions added separately, but the meaning of the data exists only in the developer's head and conceptual connections cannot be encapsulated
    • Domains like mathematics model fine with procedural code (mostly computation), but complex domains are not just abstract concepts and algorithms
    • Procedural programming is not recommended for model-driven design.

The building blocks

Per the book's map: services, entities and value objects express the model; entities and value objects are maintained with aggregates; aggregates are accessed with repositories and encapsulated with factories; layered architecture isolates the domain; Smart UI is the mutually exclusive alternative (logic in the UI).

Layered architecture

Problem: a large part of an application is not about the domain: database, file and network access, user interfaces. The domain part may be small. In OO programs, UI and database code is often written into business objects, and business logic ends up in UI widgets and database scripts, because it is the quickest way to make things work. Then:

  • domain code is hard to see and think about;
  • a superficial UI change can change business logic, and a business-rule change means meticulous tracing through UI, database and other code;
  • coherent model-driven objects become impractical; automated testing is awkward;
  • a program must stay very simple or it becomes impossible to understand.

Solution: partition into layers. Each layer is cohesive and depends only on the layers below it; use standard architectural patterns for loose coupling to the layers above. Put all domain-model code in one layer, isolated from UI, application and infrastructure, so domain objects are free of displaying or storing themselves and managing application tasks, and can evolve to capture the business knowledge.

Layer Responsibility
User Interface (presentation) presenting information to the user, interpreting user commands
Application thin: coordinates application activity; no business logic; does not hold business-object state, but can hold the state of an application task's progress
Domain information about the domain; the heart of the business software; holds the state of business objects; delegates their persistence to the infrastructure
Infrastructure supporting library for all layers: communication between layers, persistence for business objects, supporting libraries for the UI
  • Without clear separation the code entangles; one simple change in one place can have unexpected effects elsewhere
    • The domain layer should focus on core domain issues, not infrastructure
    • The UI should not be tightly tied to business logic or infrastructure tasks
    • An application layer is needed in many cases as "a manager over the business logic".
  • Example (book):
    • the user asks an application service to book a flight route
    • the application tier fetches domain objects from the infrastructure and invokes methods on them (e.g. check safety margins to other booked flights)
    • once the domain objects have checked and updated their status to "decided", the application service persists them to the infrastructure.

Entities

Some objects have an identity that stays the same across the states of the software; attributes do not matter, continuity and identity do. They can outlive the system. These are Entities.

  • The in-memory reference or address is not the identity:
    • objects move out of and into memory, are serialised and sent over a network, or destroyed
    • Two weather-info objects holding the same temperature are equal and interchangeable with different references: not entities.
  • Person:
    • name, date of birth and place of birth are not unique, so none can be the identity. Objects with the same attributes must still be distinguishable
    • mistaken identity can corrupt data.
  • Bank account: the account number is enough; it stays the same whether the account is in memory, in the database, or archived.
  • Identity can be an attribute, a combination of attributes (person: name, birth date, place of birth, parents' names, current address; or the US Social Security number), an attribute created for identity, or even a behaviour
    • Two objects with different identities must be easily distinguished by the system, and two with the same identity must be treated as the same, or the entire system can become corrupted.
  • Ways to make an ID:
    • generated by a module and kept internal
    • a database primary key (retrieved with the object)
    • created by the user (the airport code, a unique international string used by travel agencies)
    • or the object's attributes plus another attribute where needed.
  • Pattern:
    • when an object is distinguished by identity, make that primary in its definition
    • keep the class simple and focused on life-cycle continuity and identity
    • define how to tell objects apart regardless of form or history
    • watch for requirements that match objects by attributes. The model must define what it means to be the same thing.
  • Entities are important and should be considered from the start of modelling; deciding whether an object needs to be one comes next.

Value objects

Should every object be an entity? No. Tracking identity has a cost: you must guarantee a unique identity per instance (deciding what makes an identity needs careful thought; a wrong decision yields objects with the same identity), and there are performance implications: if Customer is an entity, one instance per client cannot be reused for other clients' operations, so thousands of instances may degrade performance.

Example: a drawing app with a Point class. Does each point need identity or continuity? Only its coordinates matter. An object that describes aspects of a domain and has no identity is a Value Object.

  • Make only the objects that fit the entity definition entities, the rest value objects. It simplifies the design.
  • With no identity they are easily created and discarded; the garbage collector deals with unreferenced ones.
  • Highly recommended: immutable.
    • Created by a constructor, never modified
    • for a different value, create another object. Being immutable and identity-less they can be shared, with performance benefits, and they keep data integrity.
  • Why mutability breaks sharing (book example):
    • an air-booking system reuses one flight-code object for two clients booking the same flight
    • one client changes their mind, the system mutates the code, and the first client's flight code changes too.
  • Golden rule: if value objects are shareable, they must be immutable. Keep them thin and simple. Pass by value or give a copy; copying is simple and usually harmless.
  • Value objects can contain other value objects and even references to entities
    • They need not hold a long attribute list: group attributes that form a conceptual whole
    • A customer with name, street, city, state is better as Customer holding an Address object (street, city, state belong together).

Services

Some domain actions are verbs that do not belong to any object.

Nouns of the Ubiquitous Language map to objects and their verbs become behaviour, but some behaviour is important and fits no Entity or Value Object; forcing it in "would spoil the object" by making it stand for functionality that does not belong.

In OO you cannot have a free function, so it needs an object. Often it works across several objects: "transfer money from one account to another" feels misplaced in the sender and in the receiver.

  • Declare it as a Service:
    • an object with no internal state whose purpose is to provide functionality for the domain. Naming it explicitly creates a clear distinction and encapsulates a concept
    • stuffing it into an entity or value object makes it unclear what those objects stand for.
  • Services act as interfaces providing operations; common in technical frameworks, usable in the domain layer
    • A service relates to the objects the operation is performed on or for, so it becomes a connection point for many objects
    • Putting that behaviour inside domain objects creates a dense network of associations, and high coupling between many objects is a sign of poor design (hard to read, harder to change).
  • Do not replace operations that naturally belong on domain objects, and do not create a Service for every operation. Create one when the operation is an important domain concept.

Three characteristics of a Service:

  1. The operation refers to a domain concept that does not naturally belong to an Entity or Value Object.
  2. It refers to other objects in the domain.
  3. It is stateless.

Pattern: when a significant process or transformation is not a natural responsibility of an Entity or Value Object, add it as a standalone interface declared as a Service, defined in the model's language with the operation name part of the Ubiquitous Language, and stateless.

Layers: keep the domain layer isolated; it is easy to confuse services of the domain layer, infrastructure and application layer. Application and domain services are built on top of domain entities and values. If the operation conceptually belongs to the application layer, put it there; if it is about domain objects and serves a domain need, it belongs in the domain layer.

Worked example: a web reporting app. Reports come from database data and templates, rendered as an HTML page.

  • UI layer: web pages: log in, pick a report, click.
  • Application layer: thin, between UI, domain and infrastructure; uses the database for login and the domain layer to create reports.
  • Domain layer: the core: Report and Template.
  • Infrastructure layer: database and file access.
  • The user picks a report name, the reportID (a string), plus other parameters (items, time interval)
    • The domain layer creates the report from its name
    • Finding the template for a report ID fits neither Report nor Template, so create a domain-layer Service that retrieves the template by report ID, using file infrastructure to read it from disk.

Modules

Why: a big model gets hard to talk about as a whole. Modules organise related concepts and tasks to reduce complexity. It is easier to see a large model by its modules, then the relationships between them, then the details inside one.

  • Code quality:

    • aim for high cohesion and low coupling, and apply it at module level, grouping highly related classes
    • Two common kinds: communicational cohesion (parts operate on the same data) and functional cohesion (all parts work together on one well-defined task; "considered the best").

  • Modules should have well-defined interfaces used by other modules: access one interface instead of calling three objects, which reduces coupling

    • Low coupling reduces complexity and increases maintainability.

  • Pattern:

    • choose modules that tell the story of the system and contain a cohesive set of concepts
    • If coupling is still high, change the model to disentangle concepts or find an overlooked concept that would make a meaningful module
    • Aim for concepts that can be understood and reasoned about independently; refine the model until it partitions along high-level domain concepts and the code is decoupled too.

  • Module names belong to the Ubiquitous Language and should reflect domain insight.

  • Designers create modules from the outset and, once the role is decided, it stays while internals change a lot

    • Stay flexible and let modules evolve with the project
    • Module refactoring can cost more than class refactoring, but fixing a module design mistake by changing the module beats working around it.
