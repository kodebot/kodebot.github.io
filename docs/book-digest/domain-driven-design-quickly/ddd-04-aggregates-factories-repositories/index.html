DDD Quickly 4: Aggregates, Factories and Repositories

Source: Abel Avram, Domain Driven Design Quickly (InfoQ, 2006), end of chapter "Model-Driven Design": Aggregates, Factories, Repositories (pp. 42-56). Previous: DDD Quickly 3: Model-driven design and its building blocks. Next: DDD Quickly 5: Refactoring toward deeper insight.

[!abstract] The one-minute version Domain objects have a life cycle: created, used in memory, stored, retrieved, archived, deleted. Three patterns manage it:

  • Aggregate: defines ownership and boundaries; one root entity is the only thing outsiders may hold, so invariants stay enforceable.
  • Factory: encapsulates creation of complex objects and aggregates.
  • Repository: encapsulates finding and storing objects, giving the illusion of an in-memory collection.

Aggregates

Problem. A model has many associated objects forming a complex net.

Each traversable association needs a software mechanism that enforces it, and real associations end up in code and often in the database (a one-to-one customer-account link means a reference between two objects and a relationship between two tables).

The challenge is less to make a model complete and more to make it simple and understandable: eliminate or simplify relations unless they embed deep understanding of the domain.

Reduce associations:

  1. Remove associations not essential to the model (they exist in the domain but not in your model).
  2. Reduce multiplicity with a constraint: if many objects satisfy a relationship, the right constraint may leave only one.
  3. Turn bidirectional into unidirectional: each car has an engine and each engine a car; simplify to "the car has an engine".
  • One-to-many can often become an association between one object and a collection; many-to-many (mostly bidirectional) is the worst for life-cycle management.

Remaining problem. Take a banking system with customer personal data (name, address, phones, job) and account data (number, balance, operations). On archiving or deleting a customer you must remove every reference; on a change you must update it throughout and keep data integrity.

That is usually left to the database via transactions, but a carelessly designed model brings high database contention and poor performance; solve what you can in the model.

You also must enforce invariants (rules that must hold whenever data changes), hard when many objects hold references to changing data; invariants often apply to closely related objects, not discrete ones, yet cautious locking makes users interfere pointlessly and the system unusable.

Solution: Aggregates. An Aggregate is a group of associated objects treated as one unit for data changes, with a boundary separating inside from outside and one root.

  • The root is an Entity and the only object accessible from outside
    • It can reference any aggregate object, and internal objects can reference each other, but outside objects may reference only the root.
  • Entities inside the boundary have local identity, meaningful only inside the aggregate; the root has global identity and is responsible for maintaining the invariants.

How it keeps data integrity:

  • Outsiders can only change the root or ask it to act; the root changes the other objects, an operation contained and controllable inside the aggregate.
  • Delete the root from memory and the other objects go too, since nothing else references them.
  • When a change to the root indirectly affects internals, the root enforces the invariants
    • If external objects reached internal ones directly, the logic to enforce invariants would leak into external objects, which is undesirable.
  • The root may give transient references to internals for use in one operation only (the external object must not keep them), e.g. pass copies of Value Objects
    • what happens to those copies cannot hurt the aggregate.
  • Storage: if aggregate objects live in a database, only the root should be obtainable through queries; the others are reached by traversing associations.
  • Objects inside an aggregate may hold references to roots of other aggregates.

Pattern (quoted idea): cluster entities and value objects into aggregates and define a boundary around each; choose one entity as root and control all access through it; external objects hold references to the root only; because the root controls access, it "cannot be blindsided by changes to the internals", which makes enforcing all invariants practical.

Example: Customer is the root; Address and ContactInfo (home phone, work phone, fax, e-mail) are internal. If the address is needed outside, pass a copy.

Factories

Problem. Entities and aggregates are often too complex to create in the root entity's constructor, and that contradicts the domain, where things are created by other things (electronics on assembly lines): "it is like having the printer build itself".

If creation is laborious, the client needs knowledge of the object's internal structure, relationships and rules, which breaks encapsulation; if the client is in the application layer, part of the domain has moved outside and the design is messed up.

(Real-life analogy: being handed plastic, rubber, metal and silicon and told to build your own printer.) Combining creation with the object's other responsibilities gives ungainly designs.

Factory: encapsulates the knowledge needed for object creation; especially useful for aggregates: creating the root creates everything inside and enforces all invariants.

  • Creation must be atomic.

    • Half-created objects are in an undefined state
    • for an aggregate, all objects subject to invariants must be created with the root
      • Immutable value objects must have all attributes initialised to valid state
      • If an object cannot be created properly, raise an exception
    • never return an invalid value.

  • Pattern:

    • shift the responsibility of creating complex objects and aggregates to a separate object, which may have no domain responsibility but is part of the domain design
    • provide an interface that encapsulates all complex assembly and does not require the client to reference the concrete classes
    • create whole aggregates as a unit.

  • Implementation patterns come from Design Patterns by Gamma et al.: Factory Method and Abstract Factory (the book approaches them from domain modelling, not design-pattern theory).

  • Factory Method:

    • a method that contains and hides the knowledge to create another object
    • Useful when a client wants to create an object belonging to an aggregate: add a method to the aggregate root that creates it, enforces invariants and returns a reference or a copy
    • Example: a Container holds components of a type
    • The client calls createComponent(Type t); the container instantiates the concrete class based on the type, adds it to its collection, and returns a copy.

  • Dedicated Factory object

    • when construction is more complex or creates a series of objects
    • Example: a module computing the route a car can follow from departure to destination under a constraint (shortest, fastest, cheapest); routes can carry user annotations to be saved
    • RouteFactory.createRoute(constraint) builds a Route with cities, using a Route ID generator for the unique identity an entity needs.

  • Caveats:

    • a factory must violate an object's encapsulation, so do it carefully
    • When something changes that affects construction rules or invariants, update the factory
    • Factories are tightly tied to what they build: a weakness, but also a strength, since for an aggregate the creation logic belongs to none of its objects, and a Factory holds the rules and invariants while the objects stay simple.

  • Entity factories vs value-object factories: values are immutable and valid and final at creation; entities are mutable (respecting invariants when changed) and need identity.

  • Reconstitution:

    • factories also reconstitute objects that existed and were stored. That differs from creating: the object already has an identity
    • and invariant violations are handled differently: for new objects it ends in an exception, but objects recreated from a database must be repaired to remain functional, or data is lost.

  • When a plain constructor is enough:

    • construction is not complicated
    • creation involves no other objects and all attributes arrive via the constructor
    • the client cares about the implementation or wants to choose the Strategy
    • the class is the type (no hierarchy, no concrete implementations to choose from).

Repositories

Problem. A client needs references to existing objects to use them: by creating them or by traversing an association from another object (e.g. to get a value object of an aggregate you ask the root, so you need a reference to the root). Demanding that in large apps forces objects to hold references they would not otherwise keep, increasing coupling with unneeded associations.

Tempting shortcut: go to the database. Many objects (aggregate roots are entities, probably persisted) are obtainable from the database. But the database is infrastructure:

  • Clients must know how to build SQL queries and handle record sets, exposing internals
    • such code scatters across the domain, the model "has to deal with lots of infrastructure details instead of domain concepts".
  • Changing the database means changing all that scattered code.
  • A client may restore an object internal to an aggregate, breaking its encapsulation with unknown consequences.
  • If infrastructure makes access easy, developers add traversable associations (muddling the model) or pull exact data with queries, so domain logic moves into queries and client code and entities become mere data containers
    • The technical complexity swamps client code, developers "dumb down" the domain layer, the model becomes irrelevant, and the domain focus is lost.

Repository: encapsulates all the logic to obtain object references so domain objects do not deal with infrastructure to get other objects; the model regains clarity and focus.

  • It may hold references to some objects:
    • an object created is saved in it and retrieved later
    • if it does not have a requested object it fetches it from storage. It acts as storage for globally accessible objects.
  • It may include a Strategy:
    • one persistence store or another, different locations for different types
    • The domain model is decoupled from storing objects and from the persistence infrastructure.

Pattern: for each type needing global access, create an object that gives the illusion of an in-memory collection of all objects of that type, reachable through a well-known global interface.

Provide methods to add and remove (encapsulating the actual insert or delete in the store); provide methods that select by criteria and return fully instantiated objects or collections, encapsulating the storage and query technology.

Provide repositories only for aggregate roots that need direct access. Keep the client on the model; delegate storage and access.

  • The repository may contain detailed infrastructure information, but its interface stays simple and pure domain. Select an entity by passing its identity
    • other criteria from object attributes (the repository compares all objects against the set)
    • extras such as counts.
  • Example: CustomerRepository with findCustomer(string id) and addCustomer(Customer); findCustomer("C0123") returns the customer, found or reconstituted.
  • Specification: a more complex criteria object, e.g. findCustomers(Criteria c) for "customers whose name starts with 'J'" returning John (C7265), Joe (C8433), Jane (C9771).

Factory vs Repository. Both manage the life cycle of domain objects. The Factory creates objects; the Repository handles already existing ones (it may cache locally but usually reads from persistent storage).

A repository can look like a factory because it "creates" objects, but that is reconstitution, not creation from scratch. Do not mix them: the Factory creates new objects, the Repository finds existing ones.

To add a new object: create it with the Factory, then give it to the Repository to store (client: createCustomer("C0123") returns the customer; addCustomer(C0123); the repository does insertRow).

Another way to say it: Factories are "pure domain"; Repositories may link to infrastructure, e.g. the database.
