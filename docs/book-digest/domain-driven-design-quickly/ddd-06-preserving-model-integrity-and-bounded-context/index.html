DDD Quickly 6: Preserving model integrity: bounded context, continuous integration, context map

Source: Abel Avram, Domain Driven Design Quickly (InfoQ, 2006), chapter "Preserving Model Integrity", first half (pp. 67-75). Previous: DDD Quickly 5: Refactoring toward deeper insight. Next: DDD Quickly 7: Context relationship patterns and distillation.

[!abstract] The one-minute version On large projects several teams build in parallel, and one shared model falls apart. The counter-intuitive answer: deliberately divide it into several models, each with a clearly delimited Bounded Context, kept unified by Continuous Integration inside it, and related to the others through a Context Map.

The problem

  • Enterprise projects need the combined efforts of multiple teams under different management; each gets a part of one big model, and the parts are interconnected.
  • Example:
    • a team publishes a module; a developer from another team finds a missing function, adds it and checks it in
    • He does not realise it changes the model and may break functionality
    • "Everybody knows his own backyard, but other areas are not known in enough detail."
  • "It is so easy to start from a good model and progress toward an inconsistent one." The first requirement of a model is consistency: invariable terms, no contradictions
    • A model's internal consistency is called unification.
  • One unified model for the whole enterprise is an ideal that is hard to reach and sometimes not worth trying: teams need independence (no time to meet constantly on the design), and coordinating them is daunting
    • When the design evolves partially independently, model integrity is at risk.
  • The solution is the opposite of what we learned so far:
    • do not keep one big model that will fall apart later; consciously divide it into several models
    • Models well integrated can evolve independently as long as they obey the contract they are bound to
    • Each model gets a clearly delimited border and the relationships between models are defined precisely.

(The book's map of techniques: Ubiquitous Language and Bounded Context at the centre; Continuous Integration keeps a model unified; the Context Map overviews relationships; patterns such as Shared Kernel, Customer/Supplier teams, Conformist, Anticorruption Layer, Separate Ways, Open Host Service and Published Language define them; covered next.)

Bounded Context

  • Each model has a context
    • With a single model the context is implicit
    • With an application that must interact with other software (a legacy app), the new one has its own model and context, separate from the legacy one
      • they cannot be combined, mixed or confused
    • In a large enterprise application you must define the context of each model.
  • Mixing code from distinct models makes software buggy, unreliable and hard to understand; communication gets confused, and it is unclear where a model should not apply.
  • There is no formula
    • for splitting a big model: put related elements that form a natural concept together
    • A model should be small enough to be assigned to one team, so cooperation and communication are fluid
    • The context of a model is the set of conditions that make the terms in it have a specific meaning.
  • Pattern:
    • define the scope of the model and its context boundaries, then keep the model unified
    • Explicitly set the boundaries in terms of team organisation, usage in specific parts of the application, and physical manifestations such as code bases and database schemas
    • Keep the model strictly consistent within those bounds and do not be distracted by issues outside.
  • A Bounded Context is not a Module. It is the logical frame in which the model evolves; modules organise the elements of a model, so the Bounded Context encompasses the Module.
  • Benefits: everybody works freely on their own piece; each model is easier to refactor without repercussions on others; the design can be refined and distilled toward purity.
  • Price:
    • extra work to define borders and relationships
    • some translation between models
    • you cannot transfer objects between models or invoke behaviour freely across a boundary. The book judges the benefits worth it.

Example: e-commerce. Customers register (personal data including card numbers, kept in a relational database), log in, browse, order. The app must publish an event when an order is placed (someone mails the item). Also wanted: a reporting interface (status of goods, what customers want or dislike).

  • The temptation:
    • one model for all because "one big application" was requested
      • But the shop and the reporting application are not really related: separate concerns, different concepts, maybe different technologies
    • they only share the database. Make a separate model for each
    • both can evolve freely, even become separate applications (reporting may need some data the shop must store).
  • For the warehouse, a messaging system informs staff about orders
    • They use an application with item, quantity, customer address and delivery requirements
    • The shop model need not cover that domain: it sends Value Objects with the purchase information via asynchronous messaging
    • Two models developed separately; just make sure the interface between them works.

Continuous Integration

Once a Bounded Context is defined, keep it sound.

  • With several people in one context the model tends to fragment: "the bigger the team, the bigger the problem, but as few as three or four people can encounter serious problems"

    • But splitting into ever smaller contexts loses valuable integration and coherence.

  • Even inside a team, errors happen:

    • someone who does not understand the relationships between objects modifies code against the original intent
    • someone adds code duplicating existing code, or duplicates instead of changing for fear of breaking things.

  • A model is not fully defined at the start

    • it evolves from new domain insight and development feedback, so new concepts and code elements must be integrated into one unified model and implemented correctly
      • That is why Continuous Integration is necessary inside a Bounded Context.

  • Needed:

    • a procedure to merge code (the sooner the better; daily for a single small team), an automatic build, and automated tests run on each build with errors signalled
    • Errors are caught early, fixed, and the merge-build-test cycle restarts.

  • It integrates concepts in the model, then finds its way to the implementation where it is tested

    • any inconsistency in the model can be spotted in the implementation. It applies within a Bounded Context, not to relationships between neighbouring contexts.

Context Map

  • An enterprise app has several models, each with its own Bounded Context

    • It is advisable to use the context as the basis for team organisation: people in one team communicate easily and integrate model and implementation better
    • While each team works on its model, everyone should know the overall picture.

  • A Context Map is a document that outlines the different Bounded Contexts and the relationships between them: a diagram or any written document, at any level of detail, as long as everyone on the project shares and understands it.

  • Separate unified models are not enough

    • they must be integrated, because each is only part of the system and the pieces must work together. If contexts are not clearly defined they may overlap
    • if relationships are not outlined they may not work when integrated.

  • Each Bounded Context gets a name that is part of the Ubiquitous Language, which helps team communication about the whole system

    • Everyone should know each context's boundaries and the mapping between contexts and code
    • Common practice: define the contexts, create modules for each context, and use a naming convention showing which context a module belongs to.

  • Pattern groups (next note):

    • Shared Kernel and Customer-Supplier (high interaction between contexts)
    • Separate Ways (highly independent contexts)
    • Open Host Service and Anticorruption Layer (interaction with a legacy or external system).

[!note]- Terms to carry forward model integrity · unification · bounded context (vs module) · continuous integration (inside a context) · context map · translation between models · team boundaries as context boundaries.
