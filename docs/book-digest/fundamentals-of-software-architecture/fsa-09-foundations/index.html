Fundamentals of Software Architecture 9: Foundations

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 9. Previous: Fundamentals of Software Architecture 8: Component-Based Thinking. Next: Fundamentals of Software Architecture 10: Layered Architecture Style.

Takeaways
  • An architecture style describes component topology, physical architecture, deployment, communication style and data topology. A pattern is a contextualised solution; a style is more specific to architecture.
  • The Big Ball of Mud is the absence of structure: everything is coupled to everything, so change has unpredictable ripples.
  • Top-level partitioning is a key early choice: technical (layers) or domain (workflows). Neither is more correct; the industry trend is toward domain partitioning. Conway's Law links it to team structure.
  • Styles are monolithic (single deployment unit) or distributed (several units over remote protocols). Distributed styles share the eight fallacies of distributed computing, plus three more from the authors.
  • Team topologies (stream-aligned, enabling, complicated-subsystem, platform) intersect with architecture.

9.1 Styles versus patterns

An architecture's style describes five things:

Facet What the style decides Example
Component topology How components and dependencies are organised Layered: layers by technical capability; modular monolith: components by domain
Physical architecture Monolithic or distributed A modular monolith is generally monolithic with one database; event-driven is always distributed
Deployment Granularity and deployment frequency Monoliths deploy once with one relational database; microservices have automated integration, provisioning and sometimes deployment, deploy in pieces and much faster
Communication style How components talk Method calls in a monolith; REST or message queues in distributed styles
Data topology Where data lives Monolithic database for monoliths; distributed styles sometimes separate data, depending on the style's philosophy

A name is a concise way to carry all that detail, like a design pattern. But a pattern captures a contextualised solution, while a style is more specific to architecture: its topology and its assumed and default characteristics, beneficial and detrimental. Chapter 20 covers common modern patterns.

Where do architectural styles come from?
  • There is no official cabal in an ivory tower deciding new styles. They emerge from the ecosystems architects work in.
  • A clever architect combines a new capability with other things to solve a nagging problem; others copy it; once common, it gets a name.
  • Microservices is the example: new DevOps capabilities, reliable open source operating systems and domain-driven design let architects solve scalability issues. The name was a reaction to the then-common styles of large services and extensive orchestration.
  • Microservices is a label, not a description: not a commandment to build the smallest services possible.

9.2 Fundamental patterns

Some patterns recur throughout architecture history because they organise code or deployment usefully. Layers separating concerns by functionality are as old as software, and reappear in new guises (Chapter 10). Equally old is an antipattern.

Big Ball of Mud

  • Named after the antipattern defined by Brian Foote and Joseph Yoder in a 1997 paper at the Pattern Languages of Programs conference: a haphazardly structured, sprawling, sloppy, "duct-tape-and-baling-wire, spaghetti-code jungle".
  • Signs: unregulated growth and repeated expedient repair; information shared promiscuously among distant elements, often until nearly all important information is global or duplicated.
  • Today it could be a simple script whose event handlers are wired directly to database calls. Many trivial applications start like this and become unwieldy.
  • Avoid it at all costs: change becomes harder, and deployment, testability, scalability and performance all suffer, more as it grows.
  • Few architects intend it; it arises through lack of governance around code quality and structure.

  • Neal Ford's client built a Java web application as fast as possible over several years
    • The book's figure (made with the retired Eclipse plug-in XRay) shows each class as a dot on a circle's edge and each connection as a line, bolder for stronger connections
    • Changing any class makes its effects hard to predict.
  • Because everything is coupled to everything, changes ripple. At the critical point developers spend all their time chasing bugs and side effects instead of building features.

Unitary architecture

In the beginning there was only the computer, and software ran on it; the two then split as capabilities grew (mainframes separated data into its own system; PCs began as single machines, then networks made distributed systems such as client/server).

Few unitary architectures remain outside embedded and highly constrained systems, because systems add functionality and need separation of concerns to keep performance and scale.

Client/server

A two-tier (client/server) architecture splits technical functionality between frontend and backend, in several flavours:

  • Desktop and database server:
    • rich desktop UI (such as Windows) with data on a separate database server, enabled by standalone database servers reachable over standard network protocols
      • Presentation logic sits on the desktop
    • the heavy computation on the robust server.
  • Browser and web server:
    • thinner clients, wider distribution inside and outside firewalls
    • Still considered two-tier by many because the web and database servers run on one class of machine in the operations centre while the UI runs in the browser.
  • Single-page JavaScript applications: a rich client written in browser JavaScript, resembling the original desktop variant.
  • Three-tier:
    • popular in the late 1990s as application servers arrived in Java and .NET: a database tier on an industrial-strength server, an application tier on an application server, and a frontend in generated HTML and increasingly JavaScript
    • It matched network protocols such as CORBA and DCOM
    • Those capabilities now exist as tools (message queues) or patterns (event-driven).
Three-tier architectures, language design and long-term implications
  • In the 1990s, three-tier computing was "all the rage". C++ made moving objects over a network cumbersome, so Java's designers built in serialization: every Java object supports it.
  • The architectural style came and went, but the leftovers stay: almost no one uses serialization now, yet new Java features must support it for backward compatibility, greatly frustrating language designers.
  • Understanding the long-term effects of design decisions has always eluded us; favouring simple designs is a future-proofing strategy.

9.3 Architecture partitioning

The First Law applies to partitioning too. Components are a general containment mechanism, so they can be partitioned in many ways; top-level partitioning has an outsized impact.

  • Technical partitioning: the layered monolith (Chapter 10): presentation, business rules, services, persistence and so on.
  • Domain partitioning: the modular monolith, popularised by Simon Brown: a single deployment unit with a database, partitioned around domains (Chapter 11).
  • In both, each top-level layer or component likely holds further components.

Technical partitioning

  • Organises by capability:
    • all persistence code is in one layer, easy to find
    • The Model-View-Controller pattern (from Head First Design Patterns, Eric Freeman and Elisabeth Robson, O'Reilly, 2020) matches it, so many organisations default to it.
  • Conway's Law side effect: with layered architecture, companies seated backend developers together, DBAs in another department, the presentation team in another.
  • It decouples technical concerns: if the Service layer connects only to Persistence below and Business Rules above, a persistence change affects only those layers.
  • The trade-off: developers find categories of code quickly, but realistic workflows cut across layers
    • The code for CatalogCheckout appears in every layer: the domain is smeared across the technical layers.

Domain partitioning

  • A modelling technique inspired by Eric Evans's Domain-Driven Design: identify independent, decoupled domains or workflows. Microservices is based on this philosophy
    • the modular monolith is partitioned this way.
  • Each component may use a persistence library and have its own business-rules layer, but the top level revolves around domains, which better reflects the kind of change that happens most.
  • Neither is more correct.
    • The authors have observed a decided industry trend toward domain partitioning, for both monolithic and distributed architectures
    • It is one of an architect's first decisions.
Conway's Law
  • In the late 1960s Melvin Conway observed: "Organizations which design systems…are constrained to produce designs which are copies of the communication structures of these organizations."
  • Paraphrase: a design's structure replicates how its designers communicate. Partitioning people by technical capability is an artificial separation of common concerns that can hamper collaboration.
  • Inverse Conway Maneuver, coined by Jonny Leroy of Thoughtworks: evolve team and organisation structures together to promote the desired architecture. This became widely known as team topologies.

Kata: Silicon Sandwiches, partitioning

  • Domain partitioning (Figure 9-5):
    • components Purchase, Promotion, MakeOrder, ManageInventory, Recipes, Delivery and Location
    • Subcomponents inside many handle common and local variations.

  • Technical partitioning (Figure 9-6): isolates common and local parts into their own top-level partitions, Common and Local, while Purchase and Delivery handle the workflow.
Domain partitioning Technical partitioning
Top-level components by Workflows and domains Technical capability (here, customisation)
Advantages Modelled on how the business functions, not an implementation detail; easier to build cross-functional teams around domains; closer to modular monolith and microservices; message flow matches the problem domain; easy to migrate data and components to a distributed architecture Clearly separates customisation code; closer to the layered pattern

Which is better? It depends.

9.4 Monolithic versus distributed architectures

Part I classed styles as monolithic (a single deployment unit of all code) or distributed (multiple deployment units connected by remote access protocols). No scheme is perfect, but distributed styles share challenges that monoliths do not.

  • Monolithic: layered (Chapter 10), pipeline (12), microkernel (13). The modular monolith (Chapter 11) is also monolithic.
  • Distributed: service-based (14), event-driven (15), space-based (16), service-oriented (17), microservices (18).

Distributed styles are far more powerful for performance, scalability and availability, but come with trade-offs. The first group are the fallacies of distributed computing, first listed by L. Peter Deutsch and colleagues at Sun Microsystems in 1994. A fallacy is something false that someone believes. All eight still apply.

Fallacy 1: the network is reliable

  • Networks are more reliable than they were but still generally unreliable, and distributed styles rely on the network between all services.
  • Service B can be healthy yet unreachable from Service A; worse, A may ask B to process data and get no response. This is why timeouts and circuit breakers exist.
  • The more a system relies on the network (microservices notably), the more potential for unreliability.

Fallacy 2: latency is zero

  • A local call (method or function) takes nanoseconds or microseconds (t_local)
    • the same call over a remote protocol (REST, messaging, RPC) takes milliseconds (t_remote), always more.
  • Know your average round-trip latency for a RESTful call in production (60 ms? 500 ms?)
    • It decides whether a distributed architecture is feasible, given fine-grained services and heavy inter-service communication.
  • Example: at 100 ms per request, chaining calls adds 1,000 ms to a business function (ten calls).
  • The 95th to 99th percentile matters more than the average:
    • an average of 60 ms (good) with a 95th percentile of 400 ms
    • This long-tail latency kills distributed performance
    • A network administrator can usually supply latency values.

Fallacy 3: bandwidth is infinite

  • Bandwidth is rarely a concern in a monolith. Broken into services, communication uses significant bandwidth, slowing the network and hurting latency and reliability (fallacies 1 and 2).
  • Example:
    • Service A manages wish lists and needs the customer name
    • Service B manages profiles and returns 45 attributes totalling 500 KB, though A needs only the name (200 bytes)
      • At about 2,000 requests a second, that is 1 GBps of bandwidth.
  • This is stamp coupling. Passing back only the 200 bytes would use about 400 Kbps in total.
  • Ways to resolve it:
    • private RESTful API endpoints
    • field selectors in contracts
    • GraphQL to decouple contracts
    • value-driven contracts with consumer-driven contracts
    • internal messaging endpoints. Whatever the technique: transmit only the necessary data.

Fallacy 4: the network is secure

  • VPNs, trusted networks and firewalls make architects forget it is not. Every endpoint of every deployment unit must be secured against unknown or bad requests.
  • The threat surface grows by orders of magnitude from monolithic to distributed, and securing every endpoint, even between services, is one reason synchronous, highly distributed styles (microservices, service-based) tend to be slower.

Fallacy 5: the topology never changes

  • Topology means all routers, hubs, switches, firewalls, networks and appliances; it changes all the time.
  • Story:
    • Monday morning, services time out in production and nothing was deployed over the weekend
    • After hours you find a "minor" network upgrade at 2 a.m
    • invalidated the system's latency assumptions, triggering timeouts and circuit breakers.
  • Architects must stay in constant communication with operations and network administrators about what changes and when, which is neither obvious nor easy, and leads to the next fallacy.

Fallacy 6: there is only one administrator

  • A large company has dozens of network administrators. Whom do you ask about latency or topology changes?
  • It shows the complexity of distributed architecture and the coordination it needs; a monolith with one deployment unit does not.

Fallacy 7: transport cost is zero

  • Not latency (fallacy 2) but the monetary cost of a "simple RESTful call". Architects wrongly assume the infrastructure is already in place.
  • Distributed architectures cost much more, mainly for hardware, servers, gateways, firewalls, new subnets, proxies and so on.
  • Analyse current server and network topology for capacity, bandwidth, latency and security zones before starting.

Fallacy 8: the network is homogeneous

  • Most companies use network hardware from multiple vendors
    • Does Juniper Networks hardware integrate seamlessly with Cisco Systems hardware? Mostly, and standards have improved, but not every load and circumstance is tested, so packets occasionally get lost.
  • That affects reliability and the assumptions about latency and bandwidth: it ties back to every other fallacy "in an endless loop".

The other fallacies (the authors' additions)

  • Fallacy 9: versioning is easy. Services pass information in contracts; as a service evolves, fields change. Versioning the contract leads to trade-offs:
    • Version per service or for the whole system?
    • How far should versioning reach, and what portion of the architecture must support it?
    • How many versions at once? (Some teams find themselves honouring dozens.)
    • Deprecate older versions system-wide or service by service?
  • Fallacy 10: compensating updates always work.
    • In a compensating update an orchestrator makes several related services update jointly and, if they do not, issues a reversing operation to restore the earlier state
    • Architects blithely assume it works
    • What if the compensating update fails? Show the normal compensation workflow and also how to recover when the update and the compensation both (or partly) fail.
  • Fallacy 11: observability is optional (for distributed architectures).
    • Observability is the ability to observe each service's interactions with others and the ecosystem through monitors or logs
    • Logging helps in monoliths but is critical in distributed systems, whose many communication failure modes are hard to debug without full interaction logs.

9.5 Team topologies and architecture

Team Topologies by Matthew Skelton and Manuel Pais (IT Revolution Press, 2019) is very influential and defines four team types that intersect with architecture:

  • Stream-aligned teams:
    • a stream is a flow of work scoped to a business domain or capability
    • These teams focus narrowly on one line of work (a product, service or set of features) and aim to move as fast as possible because they deliver discrete value
    • The other team types exist to reduce friction for them.
  • Enabling teams:
    • bridge a capability gap, with room for research, learning and other important but not urgent tasks
    • supply knowledge and resources from specialised domains. Good ones are highly collaborative and proactive.
  • Complicated-subsystem teams: members fully understand a complex subsystem or domain and help a stream-aligned team apply it, reducing other teams' cognitive load.
  • Platform teams:
    • provide internal services and building blocks
    • Evan Botcher's definition: "a foundation of self-service APIs, tools, services, knowledge and support which are arranged as a compelling internal product", letting autonomous delivery teams ship features faster with less coordination
    • They remove needless friction while providing governance for quality and security.

Each style chapter that follows discusses the style's effect on these team types.

9.6 On to specific styles

Architects must understand many styles before they can do trade-off analysis. Each supports a different set of characteristics and has a "sweet spot" it handles best; learning the styles shows when each works best (or least worst).

Summary points

  • A style = component topology, physical architecture, deployment, communication, data topology; a pattern is a contextualised solution.
  • Avoid the Big Ball of Mud; govern code quality.
  • Choose technical or domain partitioning early; Conway's Law links it to team structure.
  • Distributed styles carry eleven fallacies; know your latency, bandwidth, security and costs.
  • Four team types shape and are shaped by architecture.
Terms to carry forward
  • Style versus pattern.
  • Big Ball of Mud.
  • Two-tier (client/server) and three-tier architecture.
  • Top-level partitioning: technical or domain.
  • Conway's Law and the Inverse Conway Maneuver.
  • Fallacies of distributed computing (1 to 8) and the authors' 9 to 11.
  • Stamp coupling; long-tail latency; circuit breaker.
  • Compensating update.
  • Stream-aligned, enabling, complicated-subsystem and platform teams.
