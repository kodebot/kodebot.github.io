Fundamentals of Software Architecture 13: Microkernel Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 13. Previous: Fundamentals of Software Architecture 12: Pipeline Architecture Style. Next: Fundamentals of Software Architecture 14: Service-Based Architecture Style.

Takeaways
  • Microkernel (plug-in) architecture: a monolith of two components, a core system (the happy path, minimal functionality to run) and plug-ins (custom, volatile, specialised processing). It removes cyclomatic complexity from the core into plug-ins.
  • A natural fit for product-based applications and any domain needing customisation (insurance rules per state, tax forms, IDEs, browsers).
  • Plug-ins connect point to point (method call) or remotely (REST, messaging). Remote access improves decoupling and scalability but makes it distributed and still one quantum.
  • Needs a registry and contracts. Risks: a volatile core and plug-in dependencies.
  • The only style that can be both domain and technically partitioned. Simplicity 4; modularity, maintainability, testability, deployability, evolvability and responsiveness 3; scalability, elasticity and fault tolerance 1; quanta 1.

13.1 Topology

The microkernel style (also the plug-in architecture) was invented decades ago and is widely used. It fits product-based applications: packaged, downloaded and installed as a single monolithic deployment, typically at the customer's site as a third-party product.

It is also used in custom business applications in domains that need customisation, for example a US insurer with unique rules per state, or an international shipper with legal and logistical variations.

It is a relatively simple monolithic architecture of two component types: a core system and plug-ins. Application logic is split between independent plug-ins and the basic core, which isolates features and gives extensibility, adaptability and custom processing logic.

13.2 Style specifics

Core system

  • Formally, the minimal functionality required to run the system. In the Eclipse IDE the core is just a basic text editor (open a file, change text, save)
    • it only becomes useful with plug-ins.
  • Another definition:
    • the happy path, a general processing flow with little or no custom processing
    • A microkernel takes the cyclomatic complexity out of the core and puts it into separate plug-ins, giving better extensibility, maintainability and testability.

Example: Going Green (the recycling application from Chapter 7) must assess each device by custom rules. Without plug-ins:

public void assessDevice(String deviceID)
{
    if (deviceID.equals("iPhone6s"))
    {
        assessiPhone6s();
    }
    else if (deviceID.equals("iPad1"))
    {
        assessiPad1();
    }
    else if (deviceID.equals("Galaxy5"))
    {
        assessGalaxy5();
    }
    else ...
    ...
}

(The listing in the book has unbalanced braces; they are balanced here.) Rather than keep all this client-specific, high-complexity logic in the core, create one plug-in per device. Adding a device is just adding a plug-in and updating the registry; the core only locates and invokes the right plug-in:

public void assessDevice(String deviceID)
{
    String plugin = pluginRegistry.get(deviceID);
    Class<?> theClass = Class.forName(plugin);
    Constructor<?> constructor = theClass.getConstructor();
    DevicePlugin devicePlugin = (DevicePlugin) constructor.newInstance();
    devicePlugin.assess();
}

All the complex rules for one device sit in one standalone plug-in the core can run generically.

Implementing the core. Depending on size and complexity it can be a layered architecture or a modular monolith (Figure 13-2), or even be split into separately deployed domain services, each with its own domain-specific plug-ins. Example: Payment Processing as the core domain service, with one plug-in per payment method (credit card, PayPal, store credit, gift card, purchase order).

The user interface. The Presentation layer can be embedded in the core or be a separate UI with the core providing backend services; a separate UI could itself be a microkernel (Figure 13-3).

Plug-in components

  • Standalone, independent components with specialised processing, extra features and custom code that extend the core
    • They isolate highly volatile code, improving maintainability and testability
    • Ideally they have no dependencies between them.
  • Communication with the core is generally point to point: the "pipe" is usually a method call or function call to the plug-in's entry-point class.
  • A plug-in is compile based or runtime based:
    • Runtime
      • plug-ins can be added or removed without redeploying the core or other plug-ins, usually managed by frameworks such as OSGi (Open Service Gateway Initiative, Java)
      • Penrose (Java)
      • Jigsaw (Java) or Prism (.NET).
    • Compile-based plug-ins are simpler to manage, but adding, changing or removing one means redeploying the whole monolith.
  • Point-to-point plug-ins can be shared libraries (JAR, DLL, Ruby Gem), package names in Java or namespaces in C#.

  • Shared libraries (Figure 13-4): each device plug-in is a JAR, DLL or Gem named after the device.
  • Package or namespace (Figure 13-5):
    • easier: one namespace or package per plug-in in the same code base or IDE project
    • The recommended semantics: app.plug-in.<domain>.<context>, for example app.plug-in.assessment.iphone6s.
    • Second node (plug-in): marks it as a plug-in that must be self-contained and separate from other plug-ins.
    • Third node: the domain (assessment), so plug-ins group by common purpose.
    • Fourth node: the specific context (iphone6s), so it is easy to find for change or test.

Remote plug-ins. Plug-ins need not be point to point: they can be reached through REST or messaging, each plug-in a standalone service (possibly a microservice in a container).

  • It sounds like it would raise scalability, but the topology is still a single architecture quantum because of the monolithic core: every request goes through the core first.
  • Benefits:
    • better decoupling, scalability and throughput
    • runtime changes without special frameworks (OSGi, Jigsaw, Prism)
    • asynchronous
      • communication that can significantly improve responsiveness
      • Going Green could fire an asynchronous assessment request and be notified through another asynchronous channel when it completes, then notify the user.
  • Trade-offs:
    • it turns the microkernel into a distributed architecture, hard to implement and deploy for most third-party on-premises products
    • more complexity and cost
    • and if a plug-in becomes unresponsive (particularly with REST) the request cannot complete, unlike a monolithic deployment.
  • Choose by the project's requirements and a careful trade-off analysis.

The spectrum of "microkern-ality"

Not all systems that support plug-ins are microkernels, but all microkernels support plug-ins. The degree of "microkern-ality" depends on how much standalone functionality exists in the core:

  • "Pure" microkernels
    • (the Eclipse IDE, linter tools) have little core functionality. A linter's core parses source code and delivers the abstract syntax tree
    • until someone writes a plug-in that uses it, it has little use.
  • A web browser supports plug-ins but is perfectly functional without them: it sits on the right.
  • Judge the volatility of the core to decide between just supporting plug-ins and a purer microkernel.

Registry

  • The core must know which plug-ins exist and how to reach them
    • A common way is a plug-in registry with each plug-in's name, data contract and remote access protocol details (if remote)
    • Example: a tax-software plug-in flagging high-risk audit items might register the service name (AuditChecker), its data contract (input and output) and the contract format (XML).
  • The registry can be a simple internal map owned by the core (key plus plug-in reference), or a registry and discovery tool embedded in or external to the core (such as Apache ZooKeeper or Consul)
    • A simple Java registry showing point-to-point, messaging and RESTful entries for an iPhone 6S:
Map<String, String> registry = new HashMap<String, String>();

static
{
    // point-to-point access example
    registry.put("iPhone6s", "Iphone6sPlugin");

    // messaging example
    registry.put("iPhone6s", "iphone6s.queue");

    // restful example
    registry.put("iPhone6s", "https://atlas:443/assess/iphone6s");
}

Contracts

  • The contract between plug-ins and core is usually standard across a domain of plug-ins and covers behaviour, input data and output data.
  • Custom contracts
    • are typical when a third party writes the plug-in and you cannot control its contract
    • Then create an adapter between the plug-in contract and your standard one so the core has no specialised code per plug-in.
  • Contracts can be XML, JSON or even objects passed between core and plug-in. Going Green's standard contract is a Java interface plus an output class:
public interface AssessmentPlugin
{
    public AssessmentOutput assess();
    public String register();
    public String deregister();
}

public class AssessmentOutput
{
    public String assessmentReport;
    public Boolean resell;
    public Double value;
    public Double resellPrice;
}

The plug-in returns:

  • a formatted report string
  • a resell flag (can the device be resold on a third-party market or safely disposed of)
  • if resellable, its calculated value and recommended resale price

Note the roles: the core does not format or understand the assessment report, it only prints or displays it.

13.3 Data topologies, cloud, risks

Data. Usually monolithic with a single (typically relational) database.

  • It is uncommon for plug-ins to connect to the shared database directly: the core passes data to each plug-in
    • The reason is decoupling: a database change should affect only the core.
  • A plug-in may have its own data store accessible only to it: for example a simple database or rules engine holding that product's assessment rules, external or embedded (in-memory or embedded database).

Cloud. Typically monolithic, so options are coarse-grained:

  1. Deploy the whole application in the cloud (cloud facilities or containers).
  2. Put only the data in the cloud and run the microkernel on-premises.
  3. Keep the core on-premises and the plug-ins in the cloud: sounds modular but hurts responsiveness, because plug-in calls are frequent and pass a fair amount of information, so the core-plug-in latency becomes undesirable overhead.

Common risks mainly come from misapplying it:

  • Volatile core.
    • The core should be as stable as possible after initial development, since the style's benefit is isolating change in plug-ins
    • A constantly changing core undermines it, usually because the architect misjudged the core's volatility and must refactor.
  • Plug-in dependencies.
    • Microkernels work best when plug-ins talk only to the core, not each other
    • Most non-microkernel plug-in systems use dependency-free plug-ins
    • Complex ones such as the Eclipse IDE sometimes build dependencies, making the core resolve transitive dependency conflicts: what if two plug-ins need different versions of the same core library? Avoid inter-plug-in dependencies when you can.

13.4 Governance

It revolves around checking that the philosophy is honoured. Common checks:

  • Volatility checks for the core: fitness functions wired to churn in version control, not a specific code check
  • Rate of change in the core
  • Contract tests, especially if some plug-ins support different versions because of gradual evolution
  • Other structural verifications for the topology

13.5 Team topology considerations

The obvious split is core versus plug-ins:

Team type Why it fits
Stream-aligned The core is a sweet spot: they build the core functionality; plug-ins may also fall to them
Enabling Extremely well suited: segregating behaviour in plug-ins allows A/B testing and other experiments
Complicated-subsystem Specialised behaviour (such as analytics) lives in plug-ins, so the core team calls out to sophisticated plug-ins
Platform Mostly operational details, as with other monoliths

13.6 Architecture characteristics ratings

  • Like layered, simplicity and overall cost are strengths and scalability, fault tolerance and elasticity weaknesses, because of monolithic deployment
    • The quantum is always 1 because every request goes through the core to reach a plug-in.
  • Otherwise they differ:
    • microkernel is the only style that can be both domain partitioned and technically partitioned
    • Most are technically partitioned, but the domain aspect arises from a strong domain-to-architecture isomorphism: problems needing different configurations per location or client fit extremely well, as do products emphasising user customisation and feature extensibility (Jira, Eclipse).
  • Testability, deployability and reliability (3 stars): functionality is isolated in plug-ins, reducing the testing scope of a change and deployment risk, particularly with runtime-based plug-ins.
  • Modularity and evolvability (3 stars):
    • functionality is added, removed and changed through self-contained plug-ins, so applications are easy to extend and teams respond faster
      • Example: when US tax law requires a new form, add it as a plug-in
    • drop one that is no longer needed.
  • Responsiveness (3 stars):
    • microkernel applications are generally small, suffer less from the Architecture Sinkhole, and can be streamlined by unplugging functionality
    • WildFly (formerly the JBoss Application Server) performs much faster with clustering, caching and messaging unplugged.

13.7 Examples and use cases

  • Software-development tools
    • are mostly microkernels: the Eclipse IDE, PMD, Jira, Jenkins
    • Web browsers (Chrome, Firefox) use it too: viewers and other plug-ins add capabilities to the core browser.
  • Tax-preparation software:
    • the US Internal Revenue Service's basic two-page 1040 form summarises everything needed to compute tax liability
    • each line (such as gross income) needs many other forms and worksheets
      • Make the 1040 the core (the driver) and each form or worksheet a plug-in, so tax-law changes stay isolated in independent plug-ins.
  • Insurance claims processing:
    • very complicated, with rules per jurisdiction (some US states allow free windshield replacement for rock damage, others do not)
    • Most applications use big rules engines (a framework or library to define rules or workflows declaratively, with visual tools or a domain-specific language), which can grow into a Big Ball of Mud where a simple rule change needs "an army of analysts, developers, and testers".
    • Put each jurisdiction's claims rules in a standalone plug-in (source code or a rules-engine instance behind the plug-in)
      • Rules and whole jurisdictions can be added, removed or changed without touching the rest
      • The core is the standard process of filing and processing a claim, which rarely changes.

It is "a case where an architecture structure (core + plug-ins) matches the common domain problem of customization", and customisation comes up a lot.

Summary points

  • Core (happy path) plus plug-ins (volatile, custom); registry and contracts connect them.
  • Point to point is simple; remote plug-ins decouple and scale better but make it distributed (still one quantum).
  • Keep the core stable and plug-ins independent.
  • Strong for product-based and customisable domains; weak on scalability, elasticity and fault tolerance.
Terms to carry forward
  • Microkernel (plug-in) architecture; core system; plug-in.
  • Compile-based versus runtime-based plug-ins; OSGi, Penrose, Jigsaw, Prism.
  • Plug-in registry; contract; adapter.
  • Spectrum of microkern-ality.
  • Volatile core; dependency-free plug-ins; transitive dependency conflicts.
