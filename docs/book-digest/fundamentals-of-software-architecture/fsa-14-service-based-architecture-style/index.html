Fundamentals of Software Architecture 14: Service-Based Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 14. Previous: Fundamentals of Software Architecture 13: Microkernel Architecture Style. Next: Fundamentals of Software Architecture 15: Event-Driven Architecture Style.

Takeaways
  • A hybrid of microservices, and one of the most pragmatic styles: distributed, but without the cost and complexity of microservices or event-driven. A separately deployed UI, coarse-grained domain services (aim for no more than about 12) and, optionally, a monolithic database.
  • Each domain service is typically layered (API facade, business, persistence) or split into subdomains. It can use ACID transactions inside one service, which microservices cannot.
  • Flexible: separate UIs, an API gateway, one or several databases. A single shared entity library is an antipattern; logically partition the database and the shared libraries instead.
  • Quanta: 1 to many. Good ratings: maintainability, testability, deployability and evolvability 4; simplicity, modularity, responsiveness, scalability and fault tolerance 3; elasticity 2; cost $$.
  • A good stepping stone to other distributed styles: "Not every portion of an application needs to be microservices."

14.1 Topology

A distributed macro-layered structure: a separately deployed user interface, separately deployed, remote, coarse-grained services, and (optionally) a monolithic database. It varies a lot (separate UIs, separate databases).

  • Services usually represent a domain or subdomain, so they are called domain services: coarse-grained portions of functionality (such as order fulfilment or order shipping), generally independent and separately deployed.
  • They deploy much like any monolith, so containerisation is not required (Docker or Kubernetes is possible).
  • With a single monolithic database, minimise the number of domain services (no more than about 12) to avoid change-control, scalability and fault-tolerance issues.
  • Each is typically a single instance
    • multiple instances for scalability, fault tolerance or throughput usually need load balancing between the UI and the service, so the UI reaches a healthy instance.
  • Access
    • is remote from the UI, typically REST
    • alternatives are messaging, RPC, an API layer with a proxy or gateway, or even SOAP
      • Usually the UI embeds the service locator pattern to reach services directly (it can also sit in an API gateway or proxy).
  • The centrally shared monolithic database lets services use SQL queries and joins as a layered monolith would
    • With so few services, exhausting database connections is rarely an issue
    • managing database changes is the challenge (see data topologies).

14.2 Style specifics

Because domain services are coarse-grained, each is typically designed as a layered service (API Facade, Business, Persistence) or partitioned into subdomains like a modular monolith (Chapter 11).

Every service needs an API access facade the UI calls, and it usually orchestrates the request.

Example, an ecommerce order: the UI sends one request; the facade inside OrderService orchestrates placing the order, generating an order ID, applying payment and updating inventory for each product.

In microservices the same request would orchestrate many separately deployed, remote single-purpose services. That difference, internal class-level orchestration versus external service orchestration, is one of the main differences between the styles.

ACID versus BASE

Coarse-grained services let a service use regular ACID transactions (commit and rollback) to keep the database consistent within it. Fine-grained microservices rely on distributed BASE transactions (basic availability, soft state, eventual consistency), which do not give the same integrity.

  • Service-based: the customer's card has expired. Payment is an atomic transaction in the same service, so it rolls back everything added so far and tells the customer.
  • Microservices:
    • OrderPlacement creates the order, generates an ID and inserts it, then remotely calls PaymentService, which fails
    • The data is now inconsistent (order inserted but not approved), and a separate compensating update (Chapter 9) must be applied to OrderPlacement.

Service design and granularity

Coarse granularity gives better data integrity and consistency, but a big trade-off: changing order placement in OrderService means testing and redeploying all the service's functionality, including payment processing, and more deployed functionality means more risk something else breaks. In microservices only the small OrderPlacement service changes, with no PaymentService testing or deployment.

User interface options

Very flexible: the single monolithic UI can be split, even down to one per domain service, which increases scalability, fault tolerance and agility.

Example: one UI for customers placing orders, separate internal UIs for order packers and for customer support.

API gateway options

Add an API layer, a reverse proxy or API gateway, between the UI and the services.

It is useful for:

  • exposing domain service functionality to external systems
  • consolidating shared cross-cutting concerns (metrics, security, auditing, service discovery) in the gateway
  • load balancing services with multiple instances

14.3 Data topologies

The style is unique among distributed architectures in effectively supporting a monolithic database, yet the database can also be split, down to one domain-scoped database per service (like microservices).

  • With several databases, make sure no other service needs that data, which would force inter-service communication
    • In this style it is usually preferable to share data rather than call another domain service.
  • A schema change to a shared table can, if mishandled, affect every domain service, making database changes costly, risky and demanding of coordination.

Entity classes. The class files for table schemas (entity objects) usually live in a shared library (a JAR or DLL) used by all services; it can also hold SQL.

  • Antipattern:
    • one shared library of all entity objects is the least effective approach
    • Any table change means changing the library, so every service changes and redeploys, whether or not it uses the table
    • Library versioning helps, but it is hard to know which services a table change affects without detailed manual analysis.

The mitigation is to logically partition the database and mirror it in separate shared libraries:

  • Figure 14-7 partitions the database into five domains:
    • common, customer, invoicing, order and tracking, with five matching libraries
    • A change to an Invoicing table affects only the services using the invoicing library, so no other service needs retesting or redeployment.
  • The common domain and common_entities_lib are used by all services, so changing them means coordinating everything
    • One mitigation: lock the common entity objects in version control and allow only the database team to change them.
To better control database changes, make the logical partitioning in the database as fine-grained as possible while keeping well-defined data domains.

14.4 Cloud, risks, governance

  • Cloud:
    • being distributed it works well in the cloud
    • Because of their large scope, domain services are typically containerised services, not serverless functions, and easily use cloud file storage, databases and messaging.
  • Risks:
    • Inter-service communication,
      • typical of microservices, is something to avoid here
      • Ideally domains are independent with coupling only at the database
      • Too much indicates mis-partitioned domains or the wrong style.
    • Too many domain services: a practical upper limit of around 12; beyond it testing, deployment, monitoring and database connections and changes suffer.
  • Governance:
    • besides the usual structural and operational checks (cyclomatic complexity, scalability, responsiveness), ensure changes do not span multiple domain services: if they do, the domain boundaries are wrong or the style is
    • Where inter-service calls are unavailable, govern the amount of communication (an OrderProcessing service might need to tell CustomerNotification to email order status), but mostly services should be independent, with orchestration at the UI or API gateway.

14.5 Team topology considerations

Domain partitioned, so it works best with teams aligned by domain (cross-functional with specialisation); technically partitioned teams (UI, backend, database) do not suit it.

Team type Fit
Stream-aligned Works well if domain boundaries line up with streams. Harder if streams cross domain service boundaries: then realign the services or choose another style
Enabling Less effective than other distributed styles because services are coarse-grained; carefully designed components inside each service raise modularity for experiments
Complicated-subsystem Use domain and subdomain modularity to focus on complicated processing independently
Platform High modularity helps them use common tools, services, APIs and tasks

14.6 Style characteristics

It is domain partitioned. In a distributed architecture the quanta count can be one or more: if all services share a database or UI there is one; both can be federated (split) to get several.

  • Going Green quanta (Figure 14-9):
    • two
    • One is customer facing: a separate customer UI, its own database, and the Quoting and Item Status services
    • The other is internal operations (receiving, assessing, recycling): separately deployed services and two UIs, but they share one database, so it is a single quantum.
  • No five-star ratings, but four stars in key areas: agility, testability, deployability (and maintainability and evolvability), which give faster time to market.
  • Fault tolerance and availability
    • are described as high: services are self-contained and, thanks to shared code and database, do not typically call each other, so if one (Going Green's Receiving) goes down, the other six are unaffected
    • (The text says four stars; the scorecard figure shows three for fault tolerance. The book prints both.)
  • Scalability 3 and elasticity 2:
    • the coarse services replicate more functionality than finer-grained styles, so it is less cost-effective and efficient with machine resources
    • Usually one instance per service unless throughput or failover needs more: in Going Green only Quoting and Item Status scale for customer volume, so the rest are single instances, which eases single in-memory caching and connection pooling.
  • Simplicity and cost
    • differentiate it from microservices, event-driven and space-based: one of the easiest and most cost-effective distributed styles
    • The trade-off: the higher the cost and complexity, the better characteristics such as scalability, elasticity and fault tolerance get.
  • Pragmatism:
    • its flexibility and many three- and four-star characteristics make it one of the most pragmatic styles
    • More powerful styles cost too much, or are not needed: "like buying a Ferrari but only using it to commute to work in rush-hour traffic".
  • A natural fit for DDD: coarse, domain-scoped services mean each domain sits in one deployed service.
  • ACID:
    • distributed styles usually rely on eventual consistency (independent updates eventually in sync) not traditional ACID (updates in one unit of work)
    • Service-based uses ACID better than any other distributed style because the transaction scope is one coarse service.
  • It gives good modularity without the complexities of granularity and service coordination (see "Choreography and Orchestration", Chapter 18).

14.7 Examples and use cases

Going Green's flow:

  1. The customer asks (website or kiosk) what GG will pay for an old device (quoting).
  2. If satisfied, they send the device (receiving).
  3. GG assesses its condition (assessment).
  4. If in good working order, GG pays (accounting); at any time the customer checks status (item status).
  5. By the assessment, GG destroys it and recycles parts, or resells it on a third-party platform such as Facebook Marketplace or eBay (recycling).
  6. GG periodically runs financial and operational reports (reporting).

  • Each domain is a separately deployed domain service. The services needing higher throughput (Quoting and ItemStatus) run multiple instances; the others one.
  • UIs are separated by domain:
    • Customer Facing, Receiving, and Recycling and Accounting
    • This gives UI fault tolerance, scalability and security (external customers have no network path to internal functions).
  • Two physical databases:
    • one external, one internal, with internal data in a separate network zone (the horizontal line)
    • This improves security-access restrictions and data protection and makes a separate quantum
    • One-way firewall access lets internal services update customer-facing information but not the reverse
    • Alternatively, use internal table mirroring and external table synchronisation.
  • The Assessment service changes constantly as products arrive, so those changes are isolated in one domain service, giving agility, testability and deployability.

Stepping stone. It makes a good migration target before other distributed styles, or when building a distributed system from scratch:

"Not every portion of an application needs to be microservices." (Mark Richards)

Starting service-based lets a team analyse the domains and decide which should become microservices. In Going Green, Recycling and Accounting need no further breakdown, but Assessment changes often and needs high agility, so it should split into one service per device type. Skipping the step and going straight to microservices would likely turn every piece into a microservice, needed or not.

Summary points

  • UI plus 12 or fewer coarse domain services, with an optional shared database.
  • ACID within a service; coarse granularity means larger deployments per change.
  • Partition the shared database and the entity libraries together; avoid one big shared library.
  • Cost-effective distribution with 3 and 4 star ratings; ideal stepping stone.
Terms to carry forward
  • Domain service; API access facade; service locator.
  • Macro-layered structure.
  • ACID versus BASE; compensating update.
  • Entity objects; shared library antipattern; logical database partitioning; common domain.
  • API gateway or reverse proxy.
  • Federated UI and database; multiple quanta.
  • Stepping-stone migration.
