Fundamentals of Software Architecture 16: Space-Based Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 16. Previous: Fundamentals of Software Architecture 15: Event-Driven Architecture Style. Next: Fundamentals of Software Architecture 17: Orchestration-Driven Service-Oriented Architecture.

Takeaways
  • Space-based architecture removes the central database from transaction processing: data lives in replicated in-memory data grids inside processing units, and updates reach the database asynchronously through data pumps.
  • It exists for extreme, variable scalability, elasticity and concurrency, where scaling web, application and database tiers only moves the bottleneck down to the database.
  • Artifacts: processing units, virtualized middleware (messaging grid, data grid, processing grid, deployment manager), data pumps, data writers, data readers.
  • Replicated caching is the default (fast, no single point of failure); distributed caching suits large or highly dynamic data. A near-cache is not recommended.
  • Main risks are data: collisions, pump bottlenecks, data loss, memory limits. Ratings: scalability, elasticity, responsiveness 5; simplicity and testability 1; cost $$$$.

16.1 The problem: the triangle of scaling limits

A typical request flows browser, web server, application server, database server. Under rising load the bottleneck appears first at the web tier, then the application tier, then the database.

  • Scaling out web servers is easy and cheap, but usually only moves the bottleneck to the application server.
  • Scaling application servers is harder and dearer, and usually moves it to the database, the hardest and costliest tier to scale.
  • The result is a triangle: widest at the web tier (easiest to scale), narrowest at the database. The database is the final limit on concurrent transactions.
  • The authors argue it is often better to solve extreme and variable scalability architecturally than to scale a database or retrofit caching onto an architecture that cannot scale.

16.2 Topology

The name comes from tuple space: multiple parallel processors communicating through shared memory. The style replaces the central database, as a synchronous constraint, with replicated in-memory data grids.

  • Application data is kept in memory and replicated among all active processing units.
  • A processing unit that updates data sends it asynchronously to the database through a data pump, usually messaging with persistent queues.
  • Processing units start and stop dynamically with load, which addresses variable scalability.
  • With no central database in normal transactional processing, the database bottleneck is gone.
Artifact Role
Processing units Contain the application functionality
Virtualized middleware Infrastructure that manages and coordinates the processing units
Messaging grid Manages input requests and session state
Data grid Synchronises and replicates data between processing units
Processing grid Orchestrates requests across multiple processing units (optional)
Deployment manager Starts and tears down processing-unit instances as load changes
Data pumps Asynchronously send updated data to the database
Data writers Perform the database updates from the pumps
Data readers Read database data and deliver it to processing units on startup

16.3 Style specifics

Processing unit

It holds the application logic (or part of it): usually web components plus backend business logic. Small applications deploy into one unit; larger ones split by functional area. A unit can also hold small single-purpose services (much like microservices) and always holds an in-memory data grid and replication engine (Hazelcast, Apache Ignite, Oracle Coherence).

Virtualized middleware

At a minimum a messaging grid, a data grid and a deployment manager; optionally a processing grid; plus anything else needed (security, metrics for observability). No single product does all of it, so it is built from third-party web servers, caches, load balancers, orchestrators and deployment managers.

Messaging grid

When a request arrives, it decides which active processing units can take it and forwards it to one. Complexity ranges from round robin to next available (tracking which unit is most available). Usually a web server with load balancing (HA Proxy, Nginx).

Data grid

Perhaps the most crucial component. In most modern implementations it lives inside the processing units as an in-memory replicated cache. Because the messaging grid can send a request to any unit, every unit's grid must hold exactly the same data. Replication is asynchronous and usually completes in under 100 ms.

Hazelcast creates a replicated map named for the data it holds; every unit needing customer profiles contains this code:

HazelcastInstance hz = Hazelcast.newHazelcastInstance();
Map<String, CustomerProfile> profileCache =
    hz.getReplicatedMap("CustomerProfile");
  • An update in any unit is replicated to all units with the same named cache
    • A unit can hold as many replicated caches as it needs, or ask another unit for data (choreography) or use the processing grid (orchestration; see Chapter 20).
  • Startup without the database:
    • while at least one instance holds the named cache, a new instance broadcasts a request through the caching provider to join
    • the first unit to connect sends it the cache data.
  • Member lists:
    • each instance holds the IP addresses and ports of all instances with the same named cache. One instance lists only itself (size:1, ver:1)
    • a second start updates both lists (size:2, ver:2)
    • a third updates all three (size:3, ver:3)
    • when instance 2 dies the product immediately updates the others (size:2, ver:4).
  • Example: instance 1 receives a bill-to address change and calls cache.put(); the grid asynchronously updates the other two caches.

Replicated versus distributed caching

Replicated: each unit holds its own in-memory grid, synchronised among all units with the same named cache. It is extremely fast and has no single point of failure (with exceptions for products that need an external controller). It fails when:

  • Data volume is high: caches above about 100 MB force so much memory per unit (a VM or container with limited memory) that elasticity and scalability suffer.
  • Updates are very frequent: the grid cannot keep up and consistency suffers (see data collisions).

Distributed: an external server or service holds a centralised cache; units access it with a proprietary protocol. Strong consistency (one copy), but remote access adds latency, and the cache server is a single point of failure (mirroring helps but risks consistency if the primary dies before data reaches the mirror).

Criteria Replicated cache Distributed cache
Optimisation Performance Consistency
Cache size Small (< 100 MB) Large (> 500 MB)
Type of data Relatively static Highly dynamic
Update frequency Relatively low High update rate
Fault tolerance High Low
  • Both models are usually applicable and different processing units may use different ones. Use distributed for a unit holding current inventory (consistency)
    • replicated for a customer profile (performance and fault tolerance)
    • reference data such as product codes suits replicated.

Near-cache considerations

A hybrid: the distributed cache is the full backing cache; each unit's in-memory grid is a front cache holding a smaller subset, with an eviction policy: most recently used, most frequently used, or random replacement (good when no analysis favours the other two).

Front caches stay in sync with the backing cache but not with each other, so units sharing a data context (a customer profile) will likely hold different data, giving inconsistent performance and responsiveness. The authors do not recommend near-cache in space-based architecture.

Processing grid

An optional middleware piece that mediates and orchestrates a request needing more than one type of processing unit (an order-processing unit and a payment unit).

Modern implementations (especially fine-grained ones) use separate fine-grained orchestration processing units, one per major workflow.

Example: an Order Placement Orchestrator coordinating Order Placement, Payment and Inventory Adjustment, with others for order returns and stock replenishment.

Deployment manager

Continually monitors response times and user loads, starting units as load rises and stopping them as it falls: critical to elasticity. Cloud infrastructure and orchestrators such as Kubernetes usually provide it.

Data pumps

A data pump sends data to another processor, which updates the database. Units never read or write the database directly, and pumps are always asynchronous, giving eventual consistency between cache and database. The unit that handled a request owns the update and must send it through the pump.

  • They are usually messaging, which gives async communication, guaranteed delivery, persistence and FIFO order, and decouples the unit from the writer so that an unavailable writer does not interrupt processing.
  • Most systems have several pumps, usually per domain or subdomain (customer, inventory), but possibly per cache type (CustomerProfile, CustomerWishlist) or per processing-unit domain.
  • Pumps have contracts (JSON schema, XML schema, an object, or a value-driven map message) with an action (add, delete, update)
    • An update normally carries only the new values: for a changed phone number, the new number, the customer ID and the action update.

Data writers

Accept pump messages and update the database; implemented as services, applications or data hubs (such as Ab Initio).

  • Domain-based writer:
    • holds the database logic for a whole domain whatever the number of pumps it reads
    • Figure 16-11 has four units and four pumps (Profile, WishList, Wallet, Preferences) but one customer data writer holding the SQL for all customer data.
  • Dedicated writers:
    • one per pump, containing only that unit's database logic (such as Wallet)
    • It creates many components but gives better scalability and agility, since unit, pump and writer align.

Data readers

Read from the database and send data to units through a reverse data pump. Invoked in only three situations:

  1. All instances of a named cache crash.
  2. All units of a named cache are redeployed.
  3. Archive data not in the replicated cache must be retrieved.

The cold-start flow (Figure 16-13):

  1. Restarting instances each try to grab a lock on the cache; the first becomes the temporary cache owner and the others wait.
  2. The owner sends a message to a queue requesting data.
  3. The data reader runs the database queries and sends the data to a different queue, the reverse data pump, which delivers it to the owner.
  4. The owner loads the cache and releases the lock; the other instances synchronise and processing begins.

Readers can be domain-based or dedicated (dedicated is more common) and are implemented like writers.

Data abstraction layer, not data access layer. Writers and readers together form a layer. With a data access layer the units are coupled to the database table structures; with a data abstraction layer they are decoupled through separate contracts.

Space-based architecture generally uses the abstraction layer, so the cache schema in a unit can differ from the database schema and incremental database changes do not necessarily affect units.

Readers and writers contain transformation logic and can buffer a database change (a column type change, a dropped column or table) until the caches are updated.

16.4 Data topologies

Units do not touch the database, so request processing is largely independent of it, giving a wide choice of database topology and type. The deciding factor is how the system uses the backing database:

  • Reporting and analytics important: a monolithic database may be better (unless done through a data mesh, where a domain-based topology may be better).
  • Throughput and domain-based consistency:
    • one monolithic database can bottleneck synchronisation, slowing it and hurting consistency
    • domain-based may sync faster if the data partitions cleanly by domain.
  • Downstream systems that use the database for further processing: a monolithic topology may fit better.

16.5 Cloud considerations

The whole system can run in the cloud or on-prem, but also both at once, unique among the styles: units and virtualized middleware in managed cloud environments while the physical databases stay on-prem.

Async pumps and eventual consistency make the cloud synchronisation effective: elastic transactional processing in the cloud; data management, reporting and analytics in secure on-prem environments. Elastic cloud services match the style's shape.

16.6 Common risks

Mostly about data, given caching and background synchronisation.

  • Frequent reads from the database.
    • Caching all transactional data prevents excess reads and writes
    • Reads should occur only for archived data (order history, past bank statements) or a cold start (no instance running)
    • If most data must be archived and fetched, or units crash or redeploy often, the style may be wrong for the problem.
  • Data synchronisation and consistency.
    • Data is always eventually consistent
    • Under very high concurrency, pump bottlenecks are common and can delay data reaching the database, which matters if downstream systems need fresh data
    • Data loss in the pump is mitigated with persisted queues and client-acknowledgment mode in writers (the message stays in the queue until the writer acknowledges, and no other writer can read it), at the cost of responsiveness and consistency (see Preventing Data Loss, Chapter 15).
  • High data volumes. All transactional memory sits in the units, so volumes must stay low as instances are added; watch cache size to avoid a unit running out of memory and crashing.
  • Data collisions (below).

Data collisions

A data collision happens in active/active replicated caching: instance A updates the data and, during replication to B, B updates the same data. It occurs when the update rate exceeds the replication latency (RL), the time to sync each same-named cache. Worked example, two instances of an order placement service holding a replicated blue-widget inventory:

  1. Both caches hold 500 units.
  2. A takes an order for 10 and sets its cache to 490.
  3. Before replication, B takes an order for 5 and sets its cache to 495.
  4. B receives A's replication and becomes 490.
  5. A receives B's replication and becomes 495.
  6. Both caches are wrong and out of sync; the correct value is 485 in each.

The collision rate, with N instances of the same named cache, UR update rate in milliseconds (squared), S cache size in rows and RL replication latency in milliseconds, is:

Collision rate = N * UR^2 / (S * RL)
Scenario UR N S (rows) RL Updates/hr Collisions/hr %
Base (Table 16-2) 20/s 5 50,000 100 ms 72,000 14.4 0.02%
Lower latency (16-3) 20/s 5 50,000 1 ms 72,000 0.1 0.0002%
Fewer instances (16-4) 20/s 2 50,000 100 ms 72,000 5.8 0.008%
Smaller cache (16-5) 20/s 5 10,000 100 ms 72,000 72.0 0.1%
  • Base: 14 colliding updates in 72,000 (0.02%), so replication is viable.
  • Collisions are proportional to N and the update rate, and inversely proportional to cache size (a smaller cache collides more).
  • RL varies with network type and physical distance and must be measured in production; 100 ms is a good planning number if unknown.
  • Compute minimum, normal and peak rates, since update rates are rarely constant over an eight-hour day.
  • The 2 instance figure is printed as 6 per hour in the prose and 5.8 in the table.

16.7 Governance

Many moving parts mean governance is critical, especially memory.

  • Memory: a continuous fitness function has each instance report its memory use periodically (one report per unit name suffices, since all instances hold the same cache), plus a second one recording instance counts, to compute total memory per unit (Figure 16-15).
  • Synchronisation time:
    • each unit streams the request ID and a timestamp of an update
    • each data writer streams the same ID and a timestamp after the database commit
    • a fitness function matches IDs and subtracts timestamps, per unit or as an overall average (Figure 16-16)
      • Trends show whether changes help and whether the business's sync goals are met.
  • Pump bottlenecks:
    • pumps are a backpressure point and database writes are slower than cache writes, so a fitness function tracks the queue depth of each pump (Figure 16-17, an Order Placement unit and its pump)
    • Deep queues raise sync time and the chance of loss and collisions.
  • Also track the frequency of database reads (requests to data readers) and measure scalability, elasticity and responsiveness, the reasons for choosing the style.

16.8 Team topologies

Technically partitioned (many artifacts per domain), so it is most effective with technically aligned teams (functionality, pumps, readers and writers, database), though domain-aligned cross-functional teams still work.

Team type Fit
Stream-aligned A domain change may touch units, pumps, readers, writers, cache contracts, orchestrators and the database; the bigger the system, the less effective
Enabling Good: pumps, readers, writers and middleware are shared or cross-cutting, so a team can experiment on one artifact
Complicated-subsystem Good: data grid and pump complexity, and collision and async sync errors in writers, are the kind of problem domain teams should not carry
Platform Good, especially if pumps and virtualized middleware count as platform

16.9 Style characteristics

  • Elasticity, scalability and performance (five stars): the driving characteristics; in-memory caching and no database constraint can serve millions of concurrent users.
  • Trade-offs: simplicity (complicated: caching, and eventual consistency of the primary store, the system of record) and testability (one star), because simulating hundreds of thousands of concurrent users is complex and costly, so most high-volume testing happens in production under real load, with risk to normal operations.
  • Cost: relatively expensive: complexity, caching product licences, and cloud and on-prem resources for the scale.
  • Technically partitioned: any domain spreads across units, pumps, readers, writers and the database.
  • Quanta: one to many.
    • The database is not part of the quantum equation (units never call it synchronously)
    • quanta follow the UI to processing-unit associations, and units that communicate synchronously (with each other or via the processing grid) share one quantum.
  • The text asks architects to avoid data loss in a crash (see Chapter 15); the fault-tolerance figure shows two stars.

16.10 Examples and use cases

Suited to spiky user or request volume, and throughput over 10,000 concurrent users.

  • Concert ticketing.
    • Volume is low until a popular concert is announced, then jumps from hundreds to thousands or tens of thousands, and tickets sell out in minutes
    • A fixed number of tickets, with seat availability updated continually and fast, makes synchronous database transactions at that rate unlikely to work
    • The deployment manager sees the surge and starts many units, or can be configured to start them shortly before tickets go on sale.
  • Online auction.
    • Like ticketing, with unpredictable bidders and concurrent bids per asking price. Units start as load rises and are destroyed as the auction winds down
    • individual units can be devoted to each auction, keeping bidding data consistent
    • async pumps send bid history, analytics and auditing data onward with little latency.

Space-based architecture is complicated but powerful: the only style that maximises responsiveness, scalability and elasticity together, a specialised style for situations that must maximise those.

Summary points

  • It removes the database from transactions: replicated in-memory grids plus asynchronous pumps.
  • Use replicated caches for small, stable data and distributed caches for large, dynamic data; avoid near-cache.
  • Collision rate = N * UR^2 / (S * RL): measure latency, size caches carefully.
  • Govern memory, sync time and pump queue depth.
  • Superb scale and elasticity, poor simplicity and testability, high cost.
Terms to carry forward

  • Data pump, data writer, data reader, reverse data pump; data abstraction layer.
