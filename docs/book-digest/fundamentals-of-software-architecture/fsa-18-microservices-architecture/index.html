Fundamentals of Software Architecture 18: Microservices Architecture

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 18. Previous: Fundamentals of Software Architecture 17: Orchestration-Driven Service-Oriented Architecture. Next: Fundamentals of Software Architecture 19: Choosing the Appropriate Architecture Style.

Takeaways
  • Microservices is a distributed, domain-partitioned style where each service is a physical bounded context (code plus its own data), favouring duplication over reuse to reach extreme decoupling ("share nothing").
  • Named early: Martin Fowler and James Lewis popularised it in a 2014 blog post. The term is "a label, not a description": too-small services produce a Big Ball of Distributed Mud (the Grains of Sand antipattern).
  • Granularity guides: purpose, transactions, choreography. Iterate; first guesses are rarely right.
  • Operational reuse via the Sidecar pattern and a service mesh; the API layer routes only, never orchestrates; avoid transactions across services (Saga if unavoidable).
  • Data: Database-per-Service, and at most five or six services sharing a database. Serverless is a deployment model of microservices, not a separate style.
  • Ratings: 5 stars for modularity, maintainability, testability, deployability, evolvability, scalability and fault tolerance; 1 for simplicity; 2 for responsiveness; cost $$$$$.

18.1 Origins and philosophy

Most styles are named after architects notice a recurring pattern. Microservices was named early: Martin Fowler and James Lewis popularised it in a famous 2014 blog post that delineated its characteristics.

  • It is heavily inspired by domain-driven design
    • the bounded context inspired it most. A bounded context is a decoupling style (see Chapter 7), hence the nickname "share nothing".
  • Example:
    • a domain CatalogCheckout with catalog items, customers and payment
    • A monolith would share classes and link databases
    • In a bounded context, internal code and schemas may be coupled to each other but never to anything outside, such as another context's database or class.
  • Reuse has a cost (First Law):
    • it usually requires more coupling, by inheritance or composition
    • An architect whose goal is high decoupling (the primary goal of microservices) favours duplication over reuse, physically modelling the bounded context as a service and its data.

18.2 Topology

Services are much smaller than in SOA (Chapter 17), event-driven (Chapter 15) or service-based (Chapter 14) architectures, and each includes everything needed to operate independently, including its database and dependencies.

  • Each service runs in its own process, in a VM or container
    • That solves a problem of multitenant hosting (an application server shared by many applications): shared infrastructure eventually becomes constrained, and isolation between applications is poor.
  • Before free open source operating systems and automated machine provisioning, a separate infrastructure per domain was impractical
    • cloud and containers now make extreme decoupling at domain and operational level affordable.
  • Performance is the usual downside: network calls are far slower than method calls and each endpoint adds security verification, so granularity needs careful thought.
  • Experienced architects advise against transactions across service boundaries; getting granularity right is the key to success.

18.3 Style specifics

Bounded context

Each service models a function, subdomain or workflow and includes everything needed: logical components and classes, database schemas and the database. In a monolith, developers commonly share a class such as Address; here the architect duplicates it rather than coupling. Microservices takes domain partitioning to the extreme and physically embodies DDD.

Granularity

Architects take micro literally, make services too small and then must add communication links back between them, negating the point: a Big Ball of Distributed Mud.

Quoting Martin Fowler, as the authors do: "The term microservice is a label, not a description." (The 2007-era dominant style, SOA, could have been called "gigantic services", which is why this was named micro.) Boundaries should capture a domain or workflow, and for tightly coupled business processes the natural boundary may be large.

Guideline Meaning
Purpose Each service should be functionally cohesive, contributing one significant behaviour for the application
Transactions Entities that must cooperate in a transaction suggest a boundary; designing to avoid distributed transactions gives better designs
Choreography If services with excellent isolation need extensive communication to work, consider bundling them into a larger service to avoid the overhead

Iterate: architects rarely find the right granularity, data dependencies and communication style on the first pass.

Data isolation

Microservices avoids all coupling, including shared schemas and databases as integration points. Beware the Entity Trap (do not just model a service per database entity).

A relational database used to be the single source of truth; now you either name one domain the source of truth and coordinate with it, or distribute information via replication or caching.

The upside: each team can choose the most appropriate database technology for its budget, structure and operational needs, and change course without affecting other teams.

API layer

Usually an API gateway between consumers (UIs or other systems) and the services: a simple reverse proxy or a gateway with cross-cutting concerns (security, naming). To stay true to the philosophy it must not act as a mediator or orchestrator: all interesting business logic stays inside a bounded context; mediators belong in technically partitioned architectures.

Keep the API layer to **request routing and cross-cutting concerns** (security, monitoring, logging). No business logic.

Operational reuse

Duplication is preferred for domain code, but some concerns benefit from coupling: monitoring, logging, circuit breakers. If each team implements monitoring independently, how do you ensure they all do, and who handles upgrades?

The Sidecar pattern answers: common operational components sit in each service as a separate component, owned by a team or a shared infrastructure team, so upgrading the monitoring tool means updating the sidecar and every service gets it.

  • With a sidecar in every service, a service mesh gives unified control: each sidecar wires into the service plane, integration software (usually a product such as Istio) that connects the sidecars with a consistent interface.
  • Each service is a node in the mesh, which forms a console for global control of monitoring levels, logging and other operational concerns (Figure 18-4).
  • Service discovery
    • adds elasticity: requests pass through a discovery tool that monitors request count and frequency and spins up service instances
    • It is often in the mesh or hosted in the API layer, giving one place for callers to find services.

Frontends

The original vision put the UI inside the bounded context, but web partitioning and other constraints make that hard. Two common styles:

  • Monolithic frontend (Figure 18-5): a single UI (rich desktop, mobile or a JavaScript web app) calling through the API layer.
  • Micro-frontends
    • (Figure 18-6): UI-level components that give a matching level of granularity and isolation in UI and backend, relating UI components to corresponding backend services
    • (The authors recommend Building Micro-Frontends, 2nd ed., by Luca Mezzalira, O'Reilly, 2025.)

Communication

The first choice is synchronous (sender waits) or asynchronous. Typical is protocol-aware heterogeneous interoperability:

  • Protocol-aware: with no central integration hub, each service must know how to call others, so architects standardise (a level of REST, message queues) and services know or discover the protocol.
  • Heterogeneous: each service may use a different technology stack (polyglot).
  • Interoperability: services call each other over the network to collaborate and exchange information, while transactional calls are discouraged.
Enforced heterogeneity

Choreography and orchestration

Choreography has no central coordinator, matching the bounded-context philosophy and the EDA communication style. Each service calls others as needed. Figure 18-7: a user asks for another user's wish list; CustomerWishList lacks some data, calls CustomerDemographics, and returns the result.

Orchestration: with no global mediator, a localised mediator (an orchestration service) coordinates several services. Figure 18-8: the user calls the ReportCustomerInformation mediator, which calls all the services needed.

  • Choreography preserves decoupling and its benefits, but makes error handling and coordination harder.
  • For a complex workflow, choreography (Figure 18-9) forces the first service called to coordinate many others: a nominally choreographed service becoming a mediator is the Front Controller pattern, and the service taking on multiple roles adds complexity.
  • Orchestration
    • for a complex process (Figure 18-10): a mediator service coordinates the workflow, creating coupling but focusing coordination in one service and leaving the others less affected
      • Domain workflows are often inherently coupled
    • the architect's job is to represent that coupling in the way that best supports both the domain and the architecture.

Transactions and Sagas

Atomicity, trivial in a monolith, becomes a problem when databases are as decoupled as the services. Transactions across services violate the decoupling principle and create the worst kind of dynamic connascence, Connascence of Values. The authors' advice: **don't.

Fix the service granularity instead**; needing transactions to wire services together is a sign the design is too granular. Exceptions exist, such as two services needing vastly different architecture characteristics (and so separate boundaries) that still need coordination.

Distributed transactions are usually handled with the Saga pattern (a saga being an epic story of a long sequence of events).

  1. A service acts as mediator: it calls each part of the transaction, records success or failure and coordinates the results.
  2. If all succeed, values in the services and their databases update.
  3. If one part fails, the mediator must ensure no part succeeds: it tells every successful participant to undo its previous request, a compensating transaction framework.
  4. Developers usually implement this by putting each request in a pending state until the mediator declares overall success.
  5. Juggling asynchronous requests gets complex when new requests depend on pending state, and compensating transactions create a lot of coordination traffic.
A few cross-service transactions are sometimes necessary; if they dominate the architecture, microservices is probably the wrong choice. The authors identify **eight transactional Saga patterns** (*Software Architecture: The Hard Parts*, O'Reilly, 2021, chapter 12).

18.4 Data topologies

Microservices is the only style that requires breaking apart data: monolithic and domain databases are not an option, because of fine granularity, the bounded context and the sheer number of services.

Why a monolithic database fails (60 services sharing one):

  • Change control: renaming a column or dropping a table requires changes to all 60 services, plus coordinated testing and release of five dozen deployables alongside the database change.
  • The bounded context disappears: it includes the database and data structures.
  • Scalability and elasticity:
    • tools autoscale service instances but few databases scale to match, causing slow responses and timeouts
    • Services also run out of database connections as instances multiply.
  • Availability: a crash, maintenance or backup takes the whole ecosystem down. A domain database topology suffers the same issues (less extreme).

The standard: Database-per-Service (Figure 18-14). Each service owns its data, as tables in a separate database or schema.

  • It preserves the bounded context and controls change: other services request data from the owner through a contract and are decoupled from the internal structure, so a database change affects only the owner, who can even switch from a relational to a document database.
  • It gives excellent scalability, elasticity, availability and fault tolerance, and makes connection management easier.
  • Drawbacks, and the exception (Figure 18-15):
    • two services may need to write the same table, or an outside service may query the database directly for performance
    • A few services can then share a database: the authors recommend no more than five or six per database or schema
    • The box around them denotes a broader bounded context: for example, payment processing split by type (credit card, gift card, PayPal, rewards points) or shipping split by method, with all still sharing data.
  • Trade-off: database changes now need coordinated changes and deployment of several services, which is riskier and less agile, with possible effects on scalability, elasticity and fault tolerance.

18.5 Cloud considerations

Microservices can run on-prem (Kubernetes, Cloud Foundry) but is so well suited to the cloud, through on-demand VMs, containers and databases, that it is sometimes called "cloud-native".

Serverless (AWS Lambda, Google and Azure cloud functions, triggered on request) is not an architectural style but a deployment model of microservices: a microservice is single-purpose, separately deployed and does one thing well, which also describes a serverless function.

Microservices can equally be containerised; most cloud vendors have adopted Kubernetes, so containers deploy as easily.

18.6 Common risks

  • Grains of Sand:
    • services that are too fine-grained
    • Mark Richards coined the name in 2016. Micro describes what the service does, not its size (see Chapter 7 of Software Architecture: The Hard Parts).
  • Too much interservice communication,
    • from workflow (choreography, or AWS Step Functions for serverless) or needing another service's data
    • It is often a result of too-fine granularity and is fixed by merging into coarser services.
  • Too much data sharing:
    • harms change control, scalability, fault tolerance and agility, the strengths of the style
    • Know when sharing is necessary and when to consolidate services instead.
  • Code reuse and shared functionality:
    • a custom library (JAR, DLL) shared between services means part of the bounded context lives in several others and a change to shared code can break services in other contexts
    • Versioning helps but adds significant complication.

18.7 Governance

Mostly about avoiding structural decay, monitoring and limiting coupling.

  • Static coupling
    • (shared custom or third-party libraries, and contracts): asynchronous communication can decouple dynamically, but the contract still couples statically
    • Use a software bill of materials, deployment scripts and dependency-management tools to see and limit shared artifacts
    • The authors cannot prescribe how much is too much; minimise it.
  • Dynamic coupling is harder to govern and needs creativity and consistency:
    • Logs:
      • each service logs its calls (target service, protocol and so on), and fitness functions analyse them
      • this requires every service to log consistently, for example through a custom library (JAR or DLL) bound at compile time.
    • Registry entries:
      • the first instance of a service registers its interservice calls, via a contract such as JSON, to a configuration server such as Apache ZooKeeper
      • architects query it for a map of all interservice calls.

18.8 Team topologies

Domain partitioned, so best with domain-aligned, cross-functional teams; technically partitioned teams (UI, backend, database) work poorly because each domain request needs much interteam communication.

Team type Fit
Stream-aligned Works well when domain boundaries align with streams; harder for streams crossing bounded contexts. Then realign bounded contexts and granularity to the streams, or pick another style
Enabling Effective with shared services for specialised or cross-cutting concerns, working independently thanks to modularity; with platform teams, can help build the sidecar components of the mesh
Complicated-subsystem Focus on complicated domain processing independent of other services
Platform Own cross-cutting operational functionality in sidecars and the service mesh, freeing stream-aligned teams

18.9 Style characteristics

  • Notably high deployability and testability: microservices could not exist without the DevOps revolution and its automation of operations.
  • Fault tolerance (5): independent, single-purpose, fine-grained services.
  • Scalability, elasticity and evolvability:
    • some of the most scalable systems ever written use microservices
    • reliance on automation and operations integration supports elasticity
    • small, decoupled deployment units support a fast rate of change.
  • Performance is often an issue:
    • many network calls, a security check at each endpoint, and data latency (multiple services means multiple database calls)
    • The patterns used to help include intelligent data caching and replication
    • Performance is also a reason to prefer choreography over orchestration: less coupling, faster communication, fewer bottlenecks.
  • Domain partitioned,
    • with the most distinct quanta of any modern architecture: it exemplifies what the quantum measure evaluates
    • Extreme decoupling creates headaches but yields great benefits when done well.

18.10 Examples and use cases

Systems with a high degree of functional and data modularity. Example: a patient medical-monitoring system reading heart rate, blood pressure and oxygen levels from patient-monitoring devices, analysing them and alerting medical staff.

  • Each vital sign is its own microservice with its own data store for readings and history.
  • Shared services: Alert Staff (alerts a nurse or doctor when a service notices a problem) and Display Vital Signs (each service asynchronously sends its latest reading to a monitor in the patient's room).
  • Exception to independence: a vital sign (heart rate) may need data from another (a sleep monitor) to analyse for warnings.
  • Fault tolerance: if one vital-sign service crashes, the others keep working, important for medical monitoring.
  • Testability: maintenance on the blood-pressure service has a small enough test scope to be sure nothing else is affected.
  • Evolvability: adding another vital-sign monitor does not affect existing services.

Further reading the authors recommend: Building Microservices, 2nd ed. (Sam Newman, 2021); Building Micro-Frontends, 2nd ed. (Luca Mezzalira, 2025); Microservices vs. Service-Oriented Architecture and Microservices AntiPatterns and Pitfalls (Mark Richards, 2016).

Summary points

  • A service is a bounded context: code plus data, duplicated rather than shared.
  • Size services by purpose, transactions and communication; iterate; avoid Grains of Sand.
  • Sidecars and the service mesh share operations; the API layer only routes.
  • Avoid cross-service transactions; use Sagas sparingly; prefer Database-per-Service.
  • Top marks for modularity, deployability, testability, evolvability, scalability and fault tolerance; poor simplicity and responsiveness; the costliest style.
Terms to carry forward
  • Bounded context; share nothing; Big Ball of Distributed Mud; Grains of Sand.
  • Entity Trap; API layer; Sidecar; service mesh; service plane; service discovery.
  • Protocol-aware heterogeneous interoperability; micro-frontends.
  • Front Controller; Saga; compensating transaction.
  • Database-per-Service; broader bounded context.
