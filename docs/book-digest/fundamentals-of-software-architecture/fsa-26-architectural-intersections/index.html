Fundamentals of Software Architecture 26: Architectural Intersections

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 26. Previous: Fundamentals of Software Architecture 25: Negotiation and Leadership Skills. Next: Fundamentals of Software Architecture 27: The Laws of Software Architecture, Revisited.

Takeaways
  • For an architecture to work it must align with the rest of its environment. The authors call these alignments the intersections of architecture: implementation, infrastructure, data topologies, engineering practices, team topologies, systems integration, the enterprise, the business environment and generative AI.
  • Implementation: the code must match the design's operational concerns, internal structure and constraints. A cache that served responsiveness crashed a scalability-driven system at about 80,000 users.
  • Infrastructure: a scalable architecture only scales if the infrastructure does; Pets.com is the cautionary tale.
  • Data: the database topology, type, structure and read/write priority must match the style.
  • Business environment: domain-to-architecture isomorphism; unknown unknowns make every architecture iterative; residuality theory is one response.
  • Generative AI: build for swappable LLMs with guardrails and evals; as an assistant it has knowledge but lacks the wisdom to decide.

26.1 The intersections

Intersection The question it asks
Implementation Is the code aligned with operational characteristics, architectural constraints and the internal structure?
Infrastructure Do infrastructure and deployment align with scalability, responsiveness, fault tolerance and availability?
Data topologies Does the data topology (monolithic, domain databases, database per service) and data type align with the style? Widely ignored
Engineering practices Does the way the team creates, maintains and tests software, including the deployment pipeline, match the style?
Team topologies Does the team structure match the architecture? If not, even simple changes are hard
Systems integration What other systems must it talk to? Ignoring this devastates maintenance, reliability, scalability, responsiveness and availability
The enterprise Does it fit the organisation's frameworks, practices, principles and standards?
The business environment Does it fit the business and problem domain? Too often ignored, so the architecture misses the business's goals
Generative AI How do LLMs affect the architecture? Increasingly important

26.2 Architecture and implementation

The First Law's answer is "it depends"; perhaps the second most common is "that's an implementation detail", often the reason an architecture fails. The source code must align with the design on three things: operational concerns, internal structure and constraints.

Operational concerns

An order-entry system must support several thousand to half a million concurrent customers. You choose microservices (by the Chapter 18 star ratings) for scalability and elasticity.

In implementation, the tightly formed bounded contexts mean Order Placement cannot read the inventory database; it must synchronously call Inventory Management for stock counts, tightly coupling the services and hurting responsiveness.

The team adds an in-memory replicated cache (Apache Ignite, Hazelcast): Inventory has a writable in-memory cache of item IDs and current counts; every Order Placement instance holds a replicated read-only copy. This decouples the services and improves responsiveness.

But after release, more instances are needed as users grow, and at about 80,000 concurrent customers the system crashes with out-of-memory conditions in all the virtual machines, since the cache memory needs are too high.

The architecture and implementation are misaligned: the architecture focused on scalability and elasticity, the implementation on responsiveness and decoupling. Both teams made good decisions, in service of different goals.

Structural integrity

Logical components form the logical architecture (Chapter 8), usually shown as directory structures or namespaces; the source structure must match it. Without guidance, knowledge and governance, developers create directories and namespaces as they please, producing architectures that are hard to maintain, test and deploy, and so less reliable and harder to evolve.

  • Tools for automated governance: ArchUnit (Java), ArchUnitNet and NetArchTest (.NET), PyTestArch (Python), TSArch (TypeScript and JavaScript).
  • Together with good architect and developer collaboration these give implementations aligned like Figure 26-3, which is far more maintainable, testable, deployable, reliable, adaptable and extensible than the Figure 26-2 tangle.

Architectural constraints

A constraint is a governing rule limiting the architecture (REST only, a specific database type) needed to reach its goals. If the implementation breaks it, the architecture fails; the architect must identify and communicate constraints.

Example: a business with a tight budget and deadline expects many structural database changes. A traditional layered architecture fits (simple, cheap, technically partitioned: database changes isolated to one layer). Constraints needed:

  • all database logic lives in the Persistence layer
  • the Presentation layer cannot access the Persistence layer directly, even for simple queries

They stop database logic spreading, so dropping a table or renaming a column touches only the Persistence layer.

Now UI developers call the database directly (faster) and backend developers put business and database logic together (easier to test): the implementation ignores the constraints, so database changes hit every layer, take too long, and the business goals are missed.

Architectural tools also govern constraints.

26.3 Architecture and infrastructure

The scope of architecture has grown. Around the mid-2000s the relationship with operations was contractual and bureaucratic: companies outsourced operations with SLAs for uptime, scale and responsiveness. Today styles like microservices freely use what used to be solely operational.

Elastic scale was once built into space-based architectures (Chapter 16); now microservices handle it less painfully through tighter collaboration between architects and DevOps.

History: how Pets.com gave us elastic scale

  • Why it matters:
    • the infrastructure facilitates operational characteristics
    • An architecture that can scale won't if the infrastructure doesn't
    • Architects and developers are often blamed for failures caused by architecture and infrastructure misalignment, usually from lack of communication with infrastructure and operations people.
  • History of DevOps:
    • operations were considered separate and often outsourced as a cost saving, so 1990s and 2000s architectures were designed defensively, assuming operations were beyond control (see Chapter 16)
    • Orchestration-driven SOA needed elaborate tooling for scale and elasticity, so architects built those capabilities into the architecture, which became far more complex
    • Microservices' creators realised operational concerns are better handled by operations, collaborated with them and laid the foundations of DevOps.
  • Cloud can still misalign.
    • Deploying services across regions or availability zones can reduce or cancel the performance and data integrity benefits of replicated and distributed caches
    • co-locating services, containers or Kubernetes Pods on one VM raises performance but hurts scalability, fault tolerance, availability and elasticity.
  • Align through close collaboration with infrastructure staff or by adopting DevOps, so everyone understands the critical operational concerns
    • only then do the "five-star" ratings materialise.

26.4 Architecture and data topologies

Often overlooked. The wrong database type or topology can negate an architecture's best characteristics: a monolithic database gives good consistency and transactions but hurts scalability and fault tolerance; distributed topologies are good for scalability and change control but can reduce data integrity, consistency and performance.

  • Database topology
    • (Chapter 15): monolithic, distributed domain-based, or database per service
    • Microservices
      • typically use database per service to keep a strict bounded context
      • otherwise controlling change is very hard and fault tolerance, scalability, elasticity, maintainability, testability and deployability suffer
    • Some styles, like service-based (Chapter 14), are more flexible.
  • Architectural characteristics:
    • every style has superpowers (4 to 5 stars) and weaknesses (1 to 2); so do database types
    • In Software Architecture: The Hard Parts the authors rated six types: relational, key-value, document, columnar, graph, NoSQL
    • Scalability and elasticity are superpowers of microservices, event-driven and space-based architectures, and also of key-value and columnar databases, which amplify them.
  • Data structure:
    • relational data (hierarchies of interdependent relationships) fits a relational database
    • key-value pairs in a relational database
      • are a misalignment, inefficient for both database and architecture
      • Data may be relational, document-based (JSON event or request payloads) or key-value, so use polyglot databases when feasible.
  • Read/write priority:
Priority Good fit
High writes over infrequent reads Columnar
High reads Key-value, document or graph
Reads and writes about equal Relational and NewSQL

Misaligning this produces poorly performing systems.

26.5 Architecture and engineering practices

In the late 20th century architects thought methodologies (Waterfall, Scrum, Extreme Programming, Lean, Crystal) did not affect architecture. Engineering advances changed that. Separate:

  • Processes: how teams are formed and managed, meetings, workflows: the mechanics of how people organise.

  • Engineering practices:

    • process-agnostic techniques and tools to develop and release software: XP, continuous integration, continuous delivery, TDD
    • Software engineering covers development plus these practices.

  • Software lacks the maturity of other engineering:

    • civil engineers predict structural change far better
    • The Achilles' heel is estimation, because traditional estimation ignores the exploratory nature and unknowns of software.

  • Iterative processes fit architecture better

    • building microservices with Waterfall creates friction. Agile shines when migrating between styles (tight feedback loops, the Strangler Pattern, feature toggles).

  • Match style and practices:

    • microservices assumes automated machine provisioning, testing and deployment
    • with an antiquated operations group, manual processes and little testing it would likely fail.

  • Neal Ford's Building Evolutionary Architectures offers architectural fitness functions to protect characteristics as change occurs (metrics, unit tests, monitors, chaos engineering) and techniques for architectures that change gracefully.

  • Example:

    • fast time to market translates to agility, a composite of maintainability, testability and deployability (Chapter 6), all influenced by engineering practices and measurable by fitness functions
      • Microservices and service-based architectures support agility, but if practices don't align, the goals are missed
    • fitness functions reveal the misalignment so the architect can realign the practices or the architecture.

26.6 Team topologies, systems integration and the enterprise

  • Team topologies.
    • Each style in Part II has a team section, because alignment is so important
    • Teams are domain partitioned (cross-functional, organised by domain, e.g. a customer-facing team from UI to database) or technically partitioned (UI, backend, shared services, database teams: a natural fit for layered; business-function and data-synchronisation teams fit space-based)
    • Misalignment means teams struggle to implement and maintain the architecture and probably miss business goals.
  • Systems integration.
    • Systems rarely live alone
    • Is the called system available? Does it scale and perform as the caller requires? Neglect gives static and dynamic coupling that cannot scale, respond or stay agile
    • Consider communication protocols, contracts, compatibility of architectural characteristics, and whether the integration preserves each system's architectural quantum.
  • The enterprise
    • (all systems and products in a company, department or division)
    • Standards on security, platforms, technologies, documentation and diagramming
    • Ignoring them usually gets a technically effective solution deemed a failed "one-off" and scrapped.

26.7 Architecture and the business environment

The business environment directly influences architecture and never stops changing: cost-cutting to survive, aggressive expansion, quarterly pivots, or stability. An effective architect understands the company's position and direction. The authors call the alignment domain-to-architecture isomorphism:

  • Severe cost-cutting companies don't match microservices or space-based (costly to create and maintain).
  • Businesses expanding aggressively by mergers and acquisitions are poorly served by monolithic styles that cannot evolve and adapt.

The big issue is unknown change. Donald Rumsfeld (former US Secretary of Defense) distinguished known knowns, known unknowns and unknown unknowns.

Systems start with known unknowns (things developers will learn about the domain and technology) but fall victim to unknown unknowns, "the nemeses of software systems", which is why all Big Design Up Front efforts suffer: you can't design for them.

Mark Richards: "All architectures become iterative because of unknown unknowns. Agile just recognizes this and does it sooner."

Evolutionary architecture and iterative architecture help, as do characteristics such as portability, scalability, evolvability and adaptability.

Residuality theory. Barry O'Reilly (complexity theory and software design), in Residues: Time, Change, and Uncertainty in Software Architecture (Leanpub, 2024), treats business change as stressors and the architectural changes as residues.

As the architect keeps applying residues, they start addressing unknown changes no one could predict, bringing the architecture to a critical state in complexity theory. "An interesting theory, one we are watching closely."

26.8 Architecture and generative AI

Written in early 2025: LLMs have entered software development and design, used in systems and by some architects to think through hard problems.

Incorporating Gen AI into an architecture

Use abstraction and modularity: swap one LLM for another quickly; allow guardrails (rails) and evaluating results (evals) from various LLMs.

Example: a job-search company uses an LLM to anonymise résumés to reduce bias. Are the results accurate? Does it remove too much, or keep demographic information? You must gather samples and metrics and compare engines; tools such as Langfuse add this observability to the architecture.

Gen AI as an architect assistant

LLMs (Copilot) can write source code for specific, deterministic problems ("C# code that generates a unique four-digit PIN with no repeating digits"). For architects, typical prompts:

  • Risk assessment: "Are there risk areas within this architecture?"
  • Risk mitigation: "How should I address this risk?"
  • Antipatterns: "Are there any common antipatterns in this architecture?"
  • Decisions: "Should I use orchestration or choreography for this workflow?"

As of early 2025 the authors hadn't had much success: asking an LLM whether microservices or space-based fits rarely if ever gives the right answer, because everything is a trade-off; LLMs understand knowledge but lack wisdom, and the context is so large it is faster to solve the problem yourself. Some tools show promise:

  • Thoughtworks Haiven can interpret an architecture diagram and describe it, saving an export to XML for prompting; users can then ask whether it sees bottlenecks or issues.
  • Other efforts translate a PlantUML diagram or a pseudolanguage description into executable ArchUnit code to govern structure.

Expect rapid change in how Gen AI assists architects.

26.9 Summary

Architecture is holistic: much more than choosing a style and starting implementation. It means aligning with the rest of the environment, using the communication and collaboration skills from Part III.

Summary points

  • Check each intersection explicitly; misalignment, not bad design, often causes failure.
  • Govern structure and constraints in code with automated tools.
  • Match infrastructure, data topology, engineering practices and team shape to the style.
  • Fit the architecture to the business's position, and accept iteration because of unknown unknowns.
  • Build AI features behind abstractions with evals; use AI to list trade-offs, not to decide.
Terms to carry forward
  • Intersections of architecture.
  • Operational concerns; structural integrity; constraints.
  • Elastic scale; DevOps; polyglot databases.
  • Domain-to-architecture isomorphism; unknown unknowns; residuality theory.
  • Guardrails, evals, observability for LLMs.
