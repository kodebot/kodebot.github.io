Google Code Review Guide 3: The Change Author's Guide

Source: Google Engineering Practices Documentation, "The CL author's guide" ("Writing good CL descriptions", "Small CLs", "How to handle reviewer comments"), licensed CC BY 3.0. Own-words summary. Previous: Google Code Review Guide 2: Navigating, Speed, Comments and Pushback.

Takeaways
  • A change description is a permanent public record: first line says what, the body says why.
  • Write small changes: one self-contained change with its tests, roughly 100 lines good and 1000 usually too large (the reviewer decides).
  • Split work by stacking, by files, or by layer and feature; keep refactoring separate; do not break the build.
  • When comments arrive: do not take it personally, fix the code rather than explain it, and discuss disagreements collaboratively.

3.1 Writing good change descriptions

  • A description records what is changing (a summary so readers need not read the whole change) and why (context and decisions not visible in the source). It becomes part of version control history and may be read by many people over the years
    • future developers search by it.
  • Code shows what the software does but often not why it exists, which matters when someone asks whether they can remove something (the guide cites Chesterton's fence).

First line

  • A short summary of specifically what the change does, a complete sentence in the imperative ("Delete the FizzBuzz RPC and replace it with the new system", not "Deleting..."), then a blank line.
  • It shows in history summaries, so it must stand alone.

Body

  • Describe the problem, why this approach is best, shortcomings, and background such as bug numbers, benchmark results and design documents.
  • Links to external resources may not stay visible to future readers (access limits, retention), so include enough context.
  • Even small changes deserve a little attention.

Bad and good examples

  • Bad: "Fix bug", "Fix build", "Add patch", "Moving code from A to B", "Phase 1", "Add convenience functions". Some of these were real descriptions.
  • Good (functionality change): the first words state the action ("RPC: Remove size limit on RPC server message freelist."), then the problem, the solution and implementation detail.
  • Good (refactoring): says what changed from the past, the implementation, that the solution is a step in a longer direction, and why.
  • Good (small change needing context): one sentence of what, then the reason (a Python 3 build rule that lets consumers depend on a rule beside the original and encourages Python 3).

Tags and generated changes

  • Tags ([tag], #tag, tag:) are optional; keep them short in the first line and move long ones to the body.
  • Descriptions of tool-generated changes should follow the same advice.
  • Re-read the description before submitting, because the change can alter during review.

3.2 Small changes

Why small

Benefit Why
Reviewed faster a reviewer finds five minutes more easily than a 30-minute block
Reviewed more thoroughly large reviews generate piles of comments and points get dropped
Fewer bugs easier to reason about the impact
Less wasted work if rejected a wrong direction found late costs a huge change
Easier to merge a long-lived change collects conflicts
Easier to design well polishing a small change is easier
Less blocking you keep coding while a self-contained part is reviewed
Simpler to roll back large changes touch files that others have since updated
  • Reviewers may reject a change only for being too large.

What is small

  • One self-contained change: one thing, usually part of a feature, with its tests.
  • Everything the reviewer needs is in the change, its description, the codebase or something already reviewed.
  • The system keeps working after it lands.
  • Not so small that its meaning is unclear: a new API should come with a usage in the same change.
  • Guide numbers:
    • about 100 lines is reasonable and 1000 usually too large
    • file count counts too (200 lines in one file may be fine, spread over 50 files too big). When in doubt, go smaller.
  • Large is acceptable for deleting a whole file (counts as one line) and for trusted automatic refactoring tools, where the reviewer verifies intent.

Splitting

  • Stacking: send one small change, then start the next on top of it.
  • By files: groups needing different reviewers (a protocol definition and its users; code and the configuration that uses it, which rolls back more easily).
  • Horizontally: shared code or stubs isolate layers (a shared signature between service and data model).
  • Vertically: independent full-stack features (multiplication and division in the guide's calculator).
  • Grid: combine both, each cell its own standalone change.
  • Refactoring separately: moving or renaming a class goes in a different change from a bug fix in it; tiny cleanups such as a local variable name can stay.
  • Keep related tests in the same change.
    • Pure refactorings should be covered too
    • Independent test work can go first (new tests for existing code, test helpers, a test framework), for example tests before a refactoring to prove behaviour is unchanged.
  • Do not break the build between dependent changes.
  • If it cannot be small:
    • rare
    • First try a refactoring-only change to prepare, and ask teammates
    • If still large, get reviewers' agreement in advance, expect a long review and write extra tests.

3.3 Handling reviewer comments

  • Do not take it personally.
    • Read critique as help for the codebase
    • ask what constructive thing the reviewer is trying to say. Never respond in anger. If a reviewer is not constructive, talk to them in person or privately, and escalate to a manager if needed.
  • Fix the code. If a reviewer does not understand something, clarify the code first, add a code comment second, and explain only in the review tool last.
  • Think collaboratively.
    • First ask whether you understand the request
    • ask for clarification if not. If you understand but disagree, avoid "No, I'm not going to do that" and instead give your reasoning, the trade-offs, and ask whether the reviewer wants to weigh them differently.
  • Share context the reviewer lacks, and reach consensus on technical facts. For stalemates see Google Code Review Guide 1: The Standard and What to Look For.

Summary points

  • Write the "why" in every description.
  • Keep each change small, tested and self-contained.
  • Respond to review by improving the code.
Terms to carry forward
  • Imperative first line: "Delete X", not "Deleting X".
  • Stacking: building a change on top of one under review.
  • Chesterton's fence: do not remove something until you know why it is there.
  • Self-contained change: complete with tests and context, keeps the system working.
