Grokking Software Architecture 3: The Principles of Sound Structure

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 3. Previous: Grokking Software Architecture 2: The Architect's Toolkit (a guide to defensible decisions). Next: Grokking Software Architecture 4: Thinking in Layers.

Takeaways
  • Code is written once, read hundreds of times. (Fowler: "Any fool can write code that a computer can understand. Good programmers write code that humans can understand.")
  • Goal: Separation of Concerns (SoC), measured by high cohesion and loose coupling; minimise the blast radius of change or failure.
  • SOLID (Robert C. Martin, "Design Principles and Design Patterns", 2000: http://objectmentor.com/resources/articles/Principles_and_Patterns.pdf) is the pre-flight checklist. Each trades a few more files or an interface for maintainability and testability.
  • Good principles are fractal: same ideas from a method to a whole system. Do not apply SOLID dogmatically (throwaway prototypes, 10-line scripts, localised performance micro-optimisations).

3.2 Separation of Concerns

A piece of code should do one thing well; its concern is singular. Junk drawer vs mechanic's toolbox: with the toolbox you grab or replace one tool without disturbing the rest. Keep database logic away from UI, business rules away from both. Test: "What is the ONE job of this code?" If the answer includes "and", split it.

3.3 Cohesion and coupling

  • Cohesion
    • = how well things inside a module fit together
    • High: a class that only calculates shipping costs (a focused paragraph)
    • Low: one that handles authentication, logging and currency formatting.
  • Coupling
    • = how much modules depend on each other
    • Loose: LEGO bricks with a standard interface (studs)
    • Tight: super-glued bricks: changing one class forces changes in five others.
  • Two design habits from functional programming keep both healthy: pure functions (result depends only on inputs, no outside state touched) and immutability (return a new instance instead of mutating)
    • Result: predictable, testable in isolation, movable (see Grokking Simplicity, Eric Normand: https://www.manning.com/books/grokking-simplicity).
  • "Simple conversation" test
    • (audit, no code changes), applied to UserReportGenerator (client) calling UserDataService (getUserName, getUserEmail, getUserOrderIds, getOrderTotal per order in a loop)
    • Ask
    • how many calls for one job?
    • is the client reaching inside the service (service.order.customer.address.zipCode)?
    • how big is the blast radius if the service changes?
    • do I follow a "secret recipe" (initialize(), addItems(), save()) copied from class to class? The workflow has leaked: an Encapsulation violation
      • A deep "interrogation" = tight coupling
  • Blast radius:
    • how far a failure or misconfiguration spreads (borrowed from safety engineering). Large radius: one component cascades into many (a major AWS outage)
    • small: contained. Minimising it is a primary goal.
  • Refactoring
    • = improving internal structure without changing external behaviour (https://martinfowler.com/books/refactoring.html)
    • Fix: the service exposes one high-level getUserSummaryData(userId); the client makes one call
    • Payoff: small blast radius (changing order-total logic touches only the service), high cohesion, lower cognitive load.

3.4 SOLID

OOP pillars refresher:

  • Encapsulation: data plus the methods managing it, internals hidden (phone casing and screen vs poking the motherboard).
  • Abstraction: expose essentials, hide detail (tap the camera button, not exposure maths).
  • Inheritance: a subclass gets parent properties and methods (Game App and Bank App from a Base App with icon and name).
  • Polymorphism: one command, each object responds its own way (the "Share" button).
  • this/self: how an object knows its own identity (editing Jim's contact, not all 500).

The running analogy is a soccer team.

S: Single Responsibility Principle

A class should have one reason to change; the class-level form of SoC, giving high cohesion. Reasons map to business areas: sales-tax rules (Finance), database persistence (Infrastructure), email format (Marketing).

  • Before:
    • Player with dribbleBall() (own abilities), determineBestPosition() (tactics), saveStatsToDatabase() (persistence). Pain: cannot unit-test tactics without a database
    • slow tests mean no tests (Fowler on unit tests: https://martinfowler.com/bliki/UnitTest.html)
    • high cognitive load (the junk drawer)
    • frequent merge conflicts in one file.
  • After:
    • Player (state and actions), TacticsEngine, PlayerRepository (saveStats)
    • Gain: a SQL Server to PostgreSQL migration touches only PlayerRepository; tactics tested with a fake repository
    • Trade-off: a few more classes for Maintainability and Testability.
  • Most common violation:
    • Manager and Helper classes that become magnets for loosely related methods
    • Test: if you can list more than one business reason for change (tax rules AND schema), it violates SRP.

O: Open/Closed Principle

Entities are open for extension, closed for modification; depend on stable abstractions. Veteran midfielder: core skills fixed, playbook extended.

  • Before:
    • Midfielder.executePlay(playName) with an if / else if chain ("DribblePastOpponent", "DefensiveFormation"...)
      • Pain: every new play edits and retests core code ("open-heart surgery")
    • the 25th else if can break the first 24
    • a 300-line method everyone fears.
  • After:
    • each play is a class with execute()
    • Midfielder.executePlay(play) checks typeof play.execute === 'function' and calls it. New play = new class
    • tiny blast radius, independently testable, LEGO baseplate
      • (JavaScript uses duck typing; Python can use Abstract Base Classes; C# and TypeScript an interface like IPlay; Java an interface like Playable.)
  • Test: "Can I add this behaviour by adding a class without touching the old code?"

L: Liskov Substitution Principle

Objects of a parent class must be replaceable by child objects without breaking the application: a child must be a true behavioural substitute.

  • Story: the coach subs in "Bob", who claims to be a midfielder but is a goalie, stays by the net, makes a diving save, gets a red card, penalty, lost game.
  • Before:
    • Goalie extends Player implements playFieldPosition() as "stays near the net, uses hands"
    • coach.directFieldPlay(new Goalie()) compiles but violates the behavioural promise. Pain: a surprise the compiler cannot catch
    • callers need if (Player is not Goalie) checks (violating OCP, a junk drawer).
  • After: Midfielder and Forward subclasses honour the field-player contract.
  • Test with contract testing: run the parent's unit tests against every subclass; a failing subclass proves a violation.
  • Contracts without keywords:
    • a contract is any behavioural promise: interfaces (pure list of capabilities)
    • abstract classes (mixed abstract "must do" and concrete "free" methods)
    • self-declared runtime contracts (e.g. a method throwing "must be implemented by subclass"). LSP applies to all.
  • Ask: "if I pass this child where the parent is expected, will it work without surprises?"

I: Interface Segregation Principle

Classes should not be forced to implement methods they do not use; interfaces small and role-focused.

  • Before:
    • one fat training interface: Midfielder implements practiceDivingSaves() and practiceHandDistribution() as throw new Error("... not implemented"). Pain: confusing boilerplate
    • runtime bombs (a generic RunTeamPractice calling every method crashes on a midfielder)
    • a "plumber signing a surgeon's contract". Also coupling: a change in an unused part forces recompile and redeploy.
  • After:
    • split by role (Midfielder: shooting, tackling; Goalie: those plus diving saves, hand distribution)
    • It is SRP at the interface level: ask "why would this interface change?" and find two reasons.
  • Test: is this class forced to implement methods irrelevant to its job?

D: Dependency Inversion Principle

(1) High-level modules should not depend on low-level modules; both depend on abstractions. (2) Abstractions should not depend on details; details depend on abstractions. The coach designs plays around abstract roles (performAction()), not concrete players.

  • Before:
    • Coach constructor does this.forward = new Forward(); this.midfielder = new Midfielder(); and executeGamePlan() calls attack() and controlMidfield()
      • Like welding the engine to the frame
      • Pain: cannot test the coach without real players
    • adding a Defender means modifying constructor and method
    • large blast radius.
  • After:
    • Forward, Midfielder, Winger all implement performAction()
    • Coach takes players in its constructor and loops player.performAction()
    • adding a Defender changes nothing in Coach
    • test with fake players.
  • DI containers: you rarely write new Winger() yourself: .NET IServiceCollection, Java Spring Boot, Python Injector wire interfaces to implementations at startup (ch. 5).
Principle Primary goals Analogy
SRP high cohesion, SoC midfielder only plays midfield
OCP loose coupling, SoC add plays to the playbook
LSP loose coupling, reliability a substitute behaves correctly
ISP high cohesion (interfaces), loose coupling only learn relevant drills
DIP loose coupling, SoC coach depends on the playbook, not players

Real-world design questions: How likely is this to change? What will others need to work with? What assumptions am I baking in? Am I coupling too much? Can I describe it without "and"? Can I add a requirement without changing this code? How would I unit test it (if "complicated", tight coupling)? Is this class forced to know things it does not need? Would a subclass surprise a caller?

3.5 In action: SRP refactor of OrderProcessor

A monolith ("single stone") is one self-contained deployable unit; OrderProcessor.process(order) is a micro-monolith: validation (items.length === 0 || total <= 0 throws), payment, inventory update, confirmation email, in one method (monolith vs microservices: ch. 12).

  • 5 steps:
    • Spark (method does too much)
    • Inquiry (is there an ADR? four reasons to change: validation rules, payment gateways, inventory logic, email templates; missing -ilities: Maintainability, Testability)
    • Sketch (Validator, Payment, Inventory, Notifier + an OrderService coordinator)
    • Options: A full refactor with DI, B break into private helper methods (readable, but does not fix SRP or testability), C do nothing (guaranteed future pain)
    • Decision: A, recorded in an ADR.
  • After:
    • OrderValidator.validate, PaymentService.processPayment (returns true), InventoryManager.updateInventory, NotificationService.sendConfirmationEmail
    • OrderService(validator, paymentService, inventoryManager, notificationService).processOrder(order) validates, then if payment succeeds updates inventory, sends the email and returns "Order processed successfully." else "Payment failed." Payoff: changing the gateway touches only PaymentService
    • each piece tested alone
    • a NotificationService bug cannot affect payment. Use IDE tools ("Extract Method", "Move to New File") to refactor safely.

3.6 Case study: taming the 35-headed Hydra

The credit-scorecard rebuild (ch. 2): 35 per-industry scorecards, many sharing sections such as Cash Flow Analysis (appearing in about a dozen). A regulator's tweak meant finding which scorecards contain it, applying the change manually to each, and praying none was missed (inconsistent scoring = compliance problem); a one-line change took 1 to 2 days.

  • Diagnosis: SoC ignored at architectural scale ("faster now" copy-paste); low maintainability and reliability; high TCO.
  • Solution: composition over duplication.
    • Composability
      • = components can be selected and assembled in combinations to meet requirements
      • Small reusable components (Header, CashFlowAnalysisComponent...) with standard contracts
    • a new scorecard needs only the unique 10%, the other 90% is tested and trusted
    • reliability through reuse (works in 12, unlikely to fail in the 13th).
  • Payoff: multi-day tasks became 15-minute changes.

3.7 Fractal architecture

A method with one job (SRP) → a class of cohesive methods (high cohesion) → a component of cohesive classes → a system of independent components. Like city planning: zoning (SoC) and roads (loose coupling) apply to a city, a block, a house. Make many small, good decisions consistently.

3.8 The Dork Side: the real story behind OOP

Kristen Nygaard and Ole-Johan Dahl developed OOP's core ideas in the 1960s with Simula, to simulate complex real-world systems (hospital patient flow, ships in a port, infection spread) defined by constant change.

They modelled the world as self-contained objects (a Patient with data and enterHospital(), seeDoctor()), and introduced classes, inheritance, virtual methods: a generic TreatmentRoom handles any patient type, and an EmergencyPatient can be added without changing it (an early OCP).

SOLID is the modern refinement.

3.9 Mission, checklist, recap

  • Structural audit
    • (no logic changes): find a 50+ line method
    • add a comment per block describing what it does
    • read only the comments: one focused story or several jobs? (Spots low cohesion, as the conversation test spots tight coupling.) An AI assistant can suggest "distinct responsibilities as comments", but you must judge its output
      • Next chapter: project organisation (layers).
  • Recap:
    • SoC is the foundation
    • high cohesion plus loose coupling
    • SOLID as pre-flight checklist (S: one reason to change; O: extend by adding code; L: true substitutes; I: small specific interfaces; D: depend on abstractions)
    • abstractions and contracts are the main route to flexibility and testability
    • minimise blast radius
    • principles are fractal.
