Grokking Software Architecture 5: Hexagonal Architecture (Ports and Adapters)

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 5. Previous: Grokking Software Architecture 4: Thinking in Layers. Next: Grokking Software Architecture 6: Reliable API Design (public contracts and synchronous communication).

Takeaways
  • Layered architecture leaves the database at the bottom as a heavy anchor ("Database Gravity"). Hexagonal applies DIP to the whole app: a protected Core with Ports (interfaces) and Adapters (implementations).
  • Golden rule: all dependencies point INWARD. Data may still flow out (save to DB) but the DB adapter references the Core's interface.
  • Payoffs: testability (core runs in "airplane mode" with fake adapters), small blast radius (a Twilio API change stays inside one adapter), reuse (driven by web, CLI, job, test).
  • Cost: the complexity tax: more files, indirection, mapping. Overkill for simple CRUD.
  • Onion, Clean (and LMAX) are "dialects of the same language".

5.2 Decoupling the core: "database gravity"

  • In layered systems everything depends downward on the database, encouraging Database-First design even with ORMs
    • Example: Order { Id, CustomerId (a foreign key, not a Customer object), TotalAmount, byte[] RowVersion (SQL concurrency token) } is an SQL table in disguise: the database dictates the architecture.
  • Signs of a leaky system:
    • business rules in SQL/stored procedures (totals, tax, discounts)
    • validation in the repository's Save() ("is user active", stock sufficient)
    • formatting in the database (concatenating names, formatting dates for the UI). Layer boundaries are only folders so it is easy to cheat
    • hexagonal makes them structural walls.
  • Mental shift:
    • think in regions (Inside / Outside) as well as layers
    • the boundary separates them. Decoupling the core = the business logic depends on nothing outside: no DB, UI, framework, API.
  • Clean-room analogy:
    • Inside = sterile lab (business logic)
    • Outside = delivery truck (database), scientists (UI), phone calls (APIs)
    • the airlock (interface): the clean room defines the rules, the outside adapts.
  • The Boundary Keeper becomes Guardian of the Airlock: you cannot leak SQL into the Core because it does not know what SQL is.

5.3 Inside, ports, adapters

  • The Inside: the Domain (entities and rules) plus the Orchestrator (use-case flow: "load the order, validate, save"; also called Application/Service layer or Use Cases).
  • Ports = interfaces:
    • Primary (driving): how the outside uses the app (IOrderService: PlaceOrder(), CancelOrder()): "here is what I can do for you".
    • Secondary (driven): what the app needs (IOrderRepository: Save(), FindById()): "here is what I need you to do for me".
  • Adapters = translators:
    • Primary adapter: takes an outside request (HTTP, CLI), converts it, calls a primary port (OrderController unpacks JSON and calls IOrderService.PlaceOrder()).
    • Secondary adapter: implements a secondary port (SqlOrderRepository turns the clean Order into SQL).
    • In DDD adapters often act as an Anti-Corruption Layer (so messy external schemas do not corrupt the core)
      • see Evans (domainlanguage.com/ddd/) and https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer.
  • It is OCP in action: add an adapter, never modify the Core. The inversion: data still flows out but the dependency points in.
  • USB analogy:
    • laptop = Core
    • USB port = Port (the strict standard, i.e. the "driver" is the interface)
    • mouse/keyboard = Adapters
    • unplug SQL, plug a file-system adapter for tests. Castle analogy: ports are the fortified gates, adapters the drawbridges
    • primary adapters rewrite the messenger's muddy note onto clean parchment (a domain object) for the King
    • swap a wooden bridge for an iron one (SQL to Mongo) and the fortress never notices. (REST vs GraphQL come in ch. 6.)
  • Four pitfalls:
    1. Leaky Port: a port using outside types (IUserRepository.Save(SqlDataReader reader)). Fix: speak the Core's language (User).
    2. Fat Adapter: business rules in the controller or repository. Adapters should be dumb translators.
    3. CRUD obsession: a port per table (ITable1Repository). Design ports around use cases (IOrderProcessing).
    4. Misplaced responsibility: transactions or retry policy inside an adapter; "must be atomic/retried" belongs inside.
    • Rule of thumb: "What should I do with this data?" = business logic (inside); "How do I fetch/store it?" = persistence (outside).

5.4 The map

Layered diagrams flow top to bottom; the hexagon flows outside-in. Centre = domain (no outward dependencies). Left (driving side): users, automated tests, external systems use a primary adapter and port.

Right (driven side): databases, email servers, payment gateways; the Core calls a secondary port that a secondary adapter implements.

Why a hexagon? Alistair Cockburn chose it only because it has enough sides (a square implies top/bottom/left/right, hence layers); future adapters (mobile app, admin CLI) fit without changing the core.

5.5 Code: the "universal power outlet" (server monitor, C#)

Goal: alert an admin on overheating, SMS in production, console in development.

  • Before:
    • ServerMonitor.CheckTemperature(int temp) hardcodes temp > 95 and new TwilioClient("API_KEY").SendSms("555-1234", ...). Pain: every test sends a real SMS (and a bill)
    • vendor lock-in.
  • After:

    • Secondary port in the Core:

      interface IAlertPort
{
    void SendAlert(string message);
}

    • Adapters (Infrastructure): TwilioAdapter(apiKey, targetPhoneNumber), ConsoleAdapter (red text, dev), KafkaAlertAdapter(IProducer) producing {Error, Timestamp} JSON to topic "server-alerts-topic" (fire and forget; first taste of Event-Driven Architecture, ch. 7).

    • The Core's socket:

      • ServerMonitor(IAlertPort alertPort)
      • CheckTemperature calls _alertPort.SendAlert($"Temp is {temp} degrees! Take cover!") when above HIGH_TEMP_THRESHOLD. It never uses new.

    • Composition Root:

      • the single entry point (Program.Main) that builds the object graph: read config, new TwilioAdapter(envApiKey, envPhoneNumber), new ServerMonitor(myAdapter), run
      • Like a general contractor who buys the bulb and hands it to the electrician
      • Swapping = one line
      • (Java/Spring does this via @Configuration.)
  • Folder layout:
    • /Core/Domain/ServerMonitor.cs, /Core/Ports/IAlertPort.cs, /Infrastructure/Adapters/{Console,Twilio,KafkaAlert}Adapter.cs, /Infrastructure/ExternalLibs/ (SDKs), Program.cs (Composition Root)
      • Infrastructure files using MyProject.Core
    • Core files never using MyProject.Infrastructure.
  • Architectural Sovereignty:
    • the business logic is "king of its own territory"
    • Drive the same Core from a web API (primary adapter 1), an admin CLI with ConsoleAdapter (2), a scheduled job with KafkaAdapter (3).
  • Why not just a Layered Factory with DIP? A factory swaps outputs, but only the hexagon decouples the inputs (drivers) too; in layered, you still bring the anchor along.
  • Boring, reliable test:
    • FakeAlertPort holds List<string> SentMessages
    • new ServerMonitor(fakePort).CheckTemperature(100)
    • assert exactly 1 message containing "Take cover!". No internet, no keys.
  • The family (history):
    • Hexagonal (2005): Alistair Cockburn: "stop building layers, start building boundaries"; article https://alistair.cockburn.us/hexagonal-architecture.
    • Onion (2008): Jeffrey Palermo: concentric circles, layers inside the core (https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1).
    • LMAX (2011): extreme speed via the Disruptor, millions of transactions per second (Fowler: https://martinfowler.com/articles/lmax.html).
    • Clean (2012): Robert C. Martin: "Use Cases", formalised Dependency Rule (https://blog.cleancoder.com/uncle-bob/2011/11/22/Clean-Architecture.html).

5.6 The Dork Side: Cockburn's hexagon

Cockburn (an original Agile Manifesto signatory) wrote it in 2005 to solve entanglement (core logic inseparable from external tech). Story (often cited as a weather-forecasting system): he could not test logic automatically because it was tangled with GUI code and a baked-in database.

Layered diagrams imply a top and bottom, a one-way street pulled by gravity. The hexagon was chosen for "enough room" for many ports (UI, DB, test harness, admin API); six is arbitrary (3, 10 or 50 ports; "Dodecahedron Architecture" is hard to draw).

He later renamed it "Ports and Adapters" because the shape distracted from the plugs.

5.7 Rescue mission: migrating legacy code

Use the Strangler Fig Pattern (https://martinfowler.com/bliki/StranglerFigApplication.html): grow new hexagonal code around the legacy system until it takes over. Steps: (1) find a seam (new feature or bug-fix area), (2) build a hexagonal outpost (new folder/project), (3) write a legacy adapter satisfying the port by calling old code or database, (4) shift more logic in until the host is unneeded.

5.8 The cost of decoupling

  • Complexity tax:
    • "Update User Email" may need 3 files in layered (Controller, Service, Repository) but 7 to 8 in hexagonal: Controller (adapter), Input Port, Command/DTO, Use Case implementation, Output Port, Persistence Adapter, Database Entity, Mapper
    • A DTO carries raw values with no logic; a Command Object is a DTO that signals a write via an Input Port (vs a read-only Query)
    • Simple CRUD with thin logic: "renting a semi-truck to pick up a gallon of milk".
  • Indirection frustration: "Go to Definition" lands on an interface; you hunt for the adapter.
  • Mapping fatigue:
    • UserEntity (DB), User (domain), UserDto (API) plus mappers (AI assistants write these well)
    • Do not retreat to leaky code for a theoretical speed gain: premature optimisation (Fowler: https://martinfowler.com/ieeeSoftware/yetOptimization.pdf).

5.9 Mission, checklist, recap

  • Mission:
    • hunt hidden dependencies in your code (new HttpClient(), fetch(), requests.get(), console.log(), File.WriteAllText(), DateTime.Now/new Date(): system time counts)
      • sketch five minutes (hexagon, leaky arrow out, add a port, add an adapter outside)
    • Practice example: a Crypto Portfolio Tracker: PortfolioManager.CalculateTotalValue(btcAmount) creates an HttpClient, calls https://api.coingecko.com/api/v3/simple/price?ids=bitcoin&vs_currencies=usd, parses JSON, multiplies
    • Pain: breaks if the internet is down, if CoinGecko changes URL or JSON, cannot unit-test without real HTTP calls (slow, flaky, rate limited)
    • Win condition: explain why hard-coding blocks testing and how a Port fixes it
    • Guided solution in Appendix A.
  • Recap:
    • hexagonal flips a vertical stack to inside vs outside
    • the Core has zero outside dependencies
    • ports are airlocks
    • adapters are outside translators
    • all dependencies point inward
    • fake adapters make tests fast
    • Cockburn created it for entanglement so an app can be driven by a user, a program or a test script
      • Next: exposing the core through public contracts (ch. 6: REST, GraphQL, design for the AI era).
