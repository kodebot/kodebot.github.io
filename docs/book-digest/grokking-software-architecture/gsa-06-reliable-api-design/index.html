Grokking Software Architecture 6: Reliable API Design (public contracts and synchronous communication)

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 6. Previous: Grokking Software Architecture 5: Hexagonal Architecture (Ports and Adapters). Next: Grokking Software Architecture 7: Event-Driven Architecture (temporal decoupling and async communication).

Takeaways
  • An API is a binding public contract, not a list of URLs. Once published it is "forever": breaking it breaks apps, partners and agents.
  • Crossing the network boundary turns a fast, reliable in-memory call into a slow, fallible request.
  • Statelessness lets any server handle any request (scale). Idempotency makes retries safe: REST builds it into verbs, GraphQL needs an idempotency key.
  • REST (cacheable, universal, over-fetches) vs GraphQL (precise, flexible, harder to cache); BFF to serve both.
  • AI agents are API consumers: naming is prompt engineering; spec = UI for the robot.
  • Hidden traps: N+1 queries, API sprawl, debugging "magic" ORMs, chained sync dependencies (distributed monolith).

6.2 Client-server model

Workload split between Client (initiates) and Server (holds resources, fulfils). Old model: a dumb terminal plus a mainframe. Now the network boundary separates device code from data-centre code; treat each crossing as a potential failure point (latency, risk, complexity).

  • Client ("Asker"): presentation, interaction, input validation (browsers, mobile apps, IoT, desktop apps, other servers, AI agents): knows what it wants, not how.
  • Server ("Doer"): business logic, data storage, security, integrity; treats all clients equally per the contract.
  • Request-response cycle (synchronous, client always initiates, "boomerang"): (1) request (GET /user/123), (2) processing, (3) response (200 OK {"name":"Archie"}), (4) rendering.
  • Communication vs flow:
    • the handshake is synchronous, but the work can be asynchronous: close the loop early with a receipt (202 Accepted) and deliver results by callback or polling
    • Otherwise you create a blocking chain / "temporal chain" leading to a distributed monolith (ch. 7).
  • Statelessness:
    • the server retains no memory of previous interactions; each request carries all needed context (who and what)
    • Amnesiac bartender analogy: you must say "I'm Archie (Token #123), I had a Lager, another please"
    • Accepted because it lets 50 bartenders serve interchangeably (scale).
  • Thin client
    • (server-side rendering): secure (logic on server), easy to update, consistent on cheap devices
    • but laggy round-trips, useless offline. Thick client (SPA/mobile): snappy, instant validation, offline
    • but duplicated logic and outdated app versions
      • Defensible decision: thick for UX, critical rules on the server (client: "is email format valid (has @)?"; server: "is this email allowed to register?").
  • Why split: Scale (1,000,000 users: add servers behind the scenes, horizontal scaling, no huge executable to redownload) and Specialisation (frontend and backend teams work independently; the API contract is what they agree on).

6.3 API as a public contract

An API is a formal agreement of what requests are possible, data formats (JSON) and responses; once published it cannot change without breaking dependents. Internally an IDE refactors everything; over a network you cannot force teams or phones to update. Styles (REST, GraphQL) are concrete implementations of the contract idea.

  • Restaurant analogy:
    • kitchen = Core (hot, chaotic)
    • customer = client
    • menu = API. Swap chef, stoves, building
    • if "Burger" still arrives, nobody cares. "You cannot order a Shoe" = 404 Not Found.
  • Four clauses:
    1. Endpoint (address): GET /api/v1/orders/123; moving it without a redirect breaks the contract.
    2. Headers (metadata): Authorization, Content-Type: application/json (the bouncer at the club).
    3. Request/response bodies (data structures): the IKEA box promising 32 screws; changing or omitting fields collapses the integration.
    4. Status codes (result): 200 OK, 400 Bad Request; a crash returned as 200 OK with an error message is lying (the waiter's thumbs-up and empty plate).
  • Overarching wrapper: idempotency.
    • Doing the same action many times has the same effect as once
    • the first request changes state, identical repeats are no-ops returning the same success. Protects from being charged twice when a connection drops before the reply.
  • Breaking changes:
    • renaming userId to user_id crashes mobile, blanks the frontend, fails partners
    • Forbidden: removing or renaming a field, changing a data type (ID 123 to "123"), adding a required parameter
    • Allowed: adding an optional parameter or a response field.
  • Hyrum's Law
    • (Hyrum Wright; https://www.hyrumslaw.com): "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviours of your system will be depended on by somebody." E.g
    • a user list never documented as sorted came back alphabetically for two years; a database switch randomised it and broke a client
    • The real contract is how production behaves.
  • Versioning is the escape hatch: run /api/v1/orders and /api/v2/orders side by side (print a new menu rather than replacing the burger).
  • Date-based versioning (the Stripe model):
    • one endpoint (POST /v1/charges) and a release-date header
    • the core always uses the latest domain models
    • a gateway or middleware chain applies backward-compatibility transformations for older dates (e.g. 2022-08-01)
      • Pros: incremental non-breaking updates, no forced migrations
      • Cons: high server-side complexity
      • Default to URI path versioning
    • consider dates for high-value public financial/SaaS platforms.

6.4 REST or GraphQL

  • REST
    • (Representational State Transfer; Roy Fielding, 2000 dissertation): resources as nouns with standard URLs; simplicity and cacheability
    • Vending machine: press B4 (GET /products/123) and get the whole bag
    • Over-fetching: you want the price, you get id, name, price, calories, ingredients, manufacturer (5 KB for 4 bytes)
    • Mitigation: field filtering GET /products/123?fields=name,price.
  • Idempotency in verbs:
    • GET /orders/1 idempotent
    • PUT /orders/1 idempotent (set Shipped ten times, still Shipped)
    • DELETE /orders/1 idempotent
    • POST /orders NOT idempotent (ten clicks, ten charges). Practices: enforce PUT for updates (a phone on bad Wi-Fi cannot safely retry a POST update)
    • "POST-to-PUT promotion" for payments: PUT /payments/{transaction_id} as an upsert (create if absent; if the retry finds identical data do nothing and return success)
    • a retry hitting an idempotent PUT or DELETE should return 200 OK or 204 No Content, not an error.
  • GraphQL:
    • developed by Facebook in 2012, open-sourced 2015, built because complex mobile apps on slow 3G crashed with heavy REST
    • Data as a graph crawled in one request
    • Personal shopper: you send a shopping list
    • Example: query { chipItem: product(id:"123"){ name } sodaItem: product(id:"456"){ price } } returns exactly those two fields
    • Pros: flexible, precise; cons: complex server, harder to cache (every request differs).
  • GraphQL and idempotency:
    • almost all requests are HTTP POST, losing REST's verb safety. Queries are naturally idempotent
    • mutations
      • (processPayment(amount: 50)) are dangerous on retry
      • Fix: the client generates a UUID idempotency key (processPayment(amount: 50.00, idempotencyKey: "a1b2c3d4-...") { status transactionId })
    • the server checks "processed this key recently?" and either processes and stores it, or returns a copy of the original success.
  • Reality check:
    • public APIs are overwhelmingly REST (standardisation)
    • GraphQL grows in internal APIs (Meta, Shopify, GitHub) via zero over-fetching, no chattiness (one round trip), client-driven shaping, selective field resolution
      • gRPC (Google): binary Protocol Buffers, great for backend-to-backend microservices, no native browser support so not for public web APIs (grpc.io).
  • Decision with the 5-step process
    • (Chip Inventory API): consumers: Scenario A public API for third-party grocery stores
    • Scenario B warehouse workers with terrible Wi-Fi. Sketch: REST = three chatty arrows (/products/123, /inventory/123, /locations/123)
    • GraphQL = one arrow.
    • ADR 006: API style for Public Partner Gateway
      • (Accepted): decide REST Level 2 (verbs)
      • Rationale: compatibility (lower "time to first Hello World"), cacheability (CDNs), tooling (OpenAPI/Swagger)
      • Consequences: accept chattiness, keep resources granular; future: a dedicated GraphQL adapter (BFF) for the warehouse team if performance blocks.
  • Backends for Frontends (BFF):
    • a dedicated single-purpose API per UI (Sam Newman: https://samnewman.io/patterns/architectural/bff/). Mobile BFF strips heavy data and stitches several domain responses
    • Web BFF serves rich data. Core API = "general access"
    • BFFs = "frontend performance" (SRP; a tailored suit instead of a poncho).

6.5 Designing for the AI agent

AI agents (LLMs) read API docs, choose a tool and execute. "Dumb genius" paradox: great reasoning, poor context. Vague slang or internal acronyms cause hallucination.

  • Cost of context:
    • a limited context window
    • every JSON character costs tokens
      • A 50 KB response when only an email was needed wastes money and can push instructions out of memory
      • Prefer granularity (getUserEmail) over convenience (getAllUserData)
      • Illustrative maths: a bloated 50 KB response might cost $0.01 per call
    • at 1,000 calls a day, over $3,650 a year (the book's own illustration). Counter-risk: hundreds of tiny endpoints = API sprawl (6.8.2).
  • Naming is prompt engineering; your schema is the system prompt.
    • Hazard: /update_status with status: 0 could be hallucinated as "banned" when it means "admin"
    • Cryptic { "f_id": 101, "t": 4, "val": "x99" } vs declarative { "flaggedCommentId": 101, "reasonType": "Spam", "moderatorNote": "x99" } (string enums are self-documenting).
  • Rule: treat the OpenAPI/Swagger spec as the UI for the robot.
    • C# XML comments can carry rules of engagement: /// USE THIS ENDPOINT whenever the user asks "How much is shipping?" Do NOT use this for digital items (ebooks), as they have free shipping. on [HttpPost("calculate-shipping")] decimal GetShipping(...)
    • The book generates OpenAPI specs first, then server stubs and AI tool definitions from the same source of truth.
  • An API gateway in front of the contract does rate limiting and security (ch. 11).

6.7 Code: a clean endpoint (C#)

The Controller is a Translator: converts HTTP/JSON into class calls, hands work to a Service, translates the answer back. MVC (Model = data/the burger, View = UI/the plate, Controller = coordinator/the waiter); in JSON APIs there is no View but the Controller remains.

[ApiController][Route("api/orders")]
public class OrderController : ControllerBase {
  private readonly IOrderService _service;                 // the Core
  public OrderController(IOrderService service) {
      _service = service;
  }
  [HttpGet("{id}")]
  public async Task<IActionResult> GetOrder(int id) {
    var order = await _service.GetOrderById(id);           // 1 translate to domain intent
    if (order == null) return NotFound($"Order {id} not found.");  // 2 implicit contract
    return Ok(order);                                      // 3 translate to HTTP response
  } }

Knows routes and status codes but no SQL or business rules. Swap it for a console app calling the same _service to get a CLI. In hexagonal terms this is a primary adapter and the service interface is the port.

6.8 Hidden costs of abstraction

  • N+1 query problem:
    • 1 query for a parent list (latest 50 orders) plus N queries for a child per parent = 51 database calls for one screen
    • In REST/ORM it hides behind lazy loading (order.User.Name in a loop; db.Orders.Take(50).ToList())
    • Fix: eager loading (db.Orders.Include(o => o.User).Take(50).ToList() does a JOIN)
    • In GraphQL it happens by design (the user resolver runs 50 times for orders { user { name } })
    • Fix: DataLoader (Facebook): collect the 50 IDs for a few milliseconds, fire one batch SELECT Id, Name FROM Users WHERE ID IN (1,...,50), map back
    • ORM = Object-Relational Mapper (details in ch. 8).
  • API sprawl:
    • an endpoint per tiny request (/api/user-summary, /api/user-summary-with-phone, /api/mobile-user) gives 400 endpoints in two years, none deletable
      • Fix: ruthless generalisation: one endpoint with ?fields=phone,summary
    • prune like a garden.
  • Debugging hell:
    • "magic" ORMs (Entity Framework, Prisma) hide SQL until a timeout, deadlock or a 400-line generated query
    • "You cannot debug what you cannot see, and you cannot debug what you do not know." Learning SQL is not optional: at least INDEX, JOIN, execution plans.
  • Chained dependencies (distributed monolith):
    • Order API calls Inventory, Payment, Shipping synchronously: latency adds (3 x 200 ms = 600 ms plus network), and availability is limited by the worst service (Shipping down = no orders despite stock and a valid card)
    • Fix: do stock and payment synchronously, queue "Print Label" asynchronously (ch. 7).

6.9 The Dork Side: the accidental genius of REST

1990s enterprise systems used SOAP and CORBA with heavy XML/WSDL contracts, while the World Wide Web was already scaling exponentially.

Roy Fielding's 2000 PhD dissertation "Architectural Styles and the Design of Network-based Software Architectures" (https://roy.gbiv.com/pubs/dissertation/fielding_dissertation.pdf) described why the web works; he was simultaneously co-authoring HTTP/1.1 (RFC 2616) (https://datatracker.ietf.org/doc/html/rfc2616).

REST is an architectural style, not a protocol.

  • Constraints:
    • client-server
    • statelessness
    • cacheability (responses must say whether reusable)
    • uniform interface (same URIs and verbs). ("State Transfer": the server forgets; the representation of state is transferred to the client.)
  • HATEOAS
    • (Hypermedia as the Engine of Application State): responses include links for the only valid next steps: { "orderId":123, "status":"shipped", "links":[{"rel":"self","href":"/api/v1/orders/123"},{"rel":"cancel","href":"/api/v1/orders/123/cancel"}] }
    • when the cancel link is missing the Cancel button disappears.
  • Richardson Maturity Model
    • (Leonard Richardson; https://martinfowler.com/articles/richardsonMaturityModel.html): grades how RESTful an API is, from the "Swamp" of chaotic commands up to Level 3 hypermedia
    • Purists demand Level 3; Level 2 (verbs) is usually good enough
    • Respect Fielding's physics: statelessness and cacheability.

6.10 Mission, checklist, recap

  • Function-mindset anti-pattern:
    • GET /api/getMyThings and POST /api/saveThing returning ["Buy milk","Walk the dog","Call Mom"]
    • Critique:
      • verbs in URLs (HTTP already has verbs)
      • no identity (cannot delete one safely)
      • no extensibility (adding a "Done" checkbox means changing strings to objects, breaking clients)
    • Exercise: refactor POST /api/changeUserAddress, GET /api/data/user_info returning a raw string into a RESTful contract: identify the noun, standardise verbs, use an extensible JSON object (guided solution in Appendix A).
  • Recap:
    • client = asker, server = doer
    • sync communication can trigger async flow
    • stateless = amnesia
    • idempotency is the safety switch
    • an API is a binding contract
    • four REST pillars (client-server, statelessness, cacheability, uniform interface)
    • REST = vending machine, GraphQL = personal shopper
    • for AI: granularity, descriptive naming, strict versioning
    • the Controller is a translator, not a decision maker.
