Grokking Software Architecture 7: Event-Driven Architecture (temporal decoupling and async communication)

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 7. Previous: Grokking Software Architecture 6: Reliable API Design (public contracts and synchronous communication). Next: Grokking Software Architecture 8: The Database as an Architectural Pillar.

Takeaways
  • Temporal coupling (sender and receiver must both be up at the same instant) makes synchronous chains brittle: a distributed monolith. EDA breaks it with a broker between producer and consumer.
  • Command (imperative, one-to-one, "do this") vs Event (past tense fact, one-to-many, "this happened"). Pub/Sub lets you add consumers without touching the producer (OCP).
  • The price is eventual consistency (you become an AP system); fix the "panic gap" with an optimistic UI.
  • Delivery is at-least-once; make consumers idempotent. Use ACKs, a Dead Letter Queue, prefetch limits, a Correlation ID, and the Outbox for atomic save and publish.
  • AI agents are just slow consumers: never call an LLM synchronously in a controller.

7.1 Temporal coupling

Order API calls Inventory, which calls Payment, which calls Shipping: if Shipping is down the user cannot buy, though stock and card are fine. Temporal coupling = components depend on time: both sides must be online and responsive at the same moment.

Phone call (both on the line) vs text message (read later). The domino effect is typical of orchestration (a central conductor); choreography (ch. 12) lets services react independently. Fix: stop asking "can you do this right now?" and say "here is what happened; deal with it when you can".

7.2 Core components and pub/sub

An async API with a status receipt still has a synchronous technical loop; a Message Broker removes it (services need not be online together).

  • Producer (publisher): creates the message and moves on, indifferent to listeners (radio DJ, e.g. "Order Placed", "User Registered").
  • Broker: reliable post office: receives, persists, routes by label without opening the letter (mailroom clerk): RabbitMQ, Apache Kafka, Azure Service Bus, AWS SNS/SQS.
  • Consumer (subscriber): reactive, wakes when a message arrives (the doorbell), rather than polling.
Broker Vibe Best for Trade-off
RabbitMQ (Swiss Army knife; https://www.rabbitmq.com/getstarted.html) smart broker, dumb consumer complex routing, flexible fan-out, multiple protocols (AMQP, MQTT) very low latency but not Kafka-level scale; more ops
Apache Kafka (firehose; https://kafka.apache.org/quickstart) dumb broker, smart consumer massive scale, replayable history, stream processing huge throughput but higher latency from batching; high operational complexity
AWS SQS/SNS (serverless) "set it and forget it" zero-management teams; SQS queues, SNS fan-out easy scaling and no maintenance, but vendor lock-in and higher cost at scale
Azure Service Bus (enterprise; https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-messaging-overview) RabbitMQ's corporate cousin sessions (FIFO), transactions, duplicate detection rich features and Azure integration, but higher latency than raw open source

Tip: start with your cloud's managed service; self-host RabbitMQ or Kafka only for ultra-complex routing or massive replay with a platform team (most use MSK, Confluent Cloud, WarpStream).

  • Command ("the message"):
    • tells a specific service to act
    • imperative names (PlaceOrder, SendEmail, ChargeCreditCard)
    • one-to-one
    • you expect it to happen ("Waiter, bring me this burger"). Event ("the fact"): announces something that already happened
    • past tense (OrderPlaced, EmailSent, CreditCardCharged)
    • one-to-many broadcast
    • zero expectations. Use commands for a specific outcome (high coupling), events to decouple. Events make strict transactions hard ("you cannot roll back a sent email", ch. 12).
  • Pub/Sub:
    • publishers categorise messages into topics without knowing receivers
    • subscribers choose topics. Flow: Order Service saves the order and publishes OrderPlaced
    • Shipping prints a label
    • Rewards adds points
    • Analytics updates the dashboard
      • Rewards and Analytics were added without touching Order Service code (OCP), unlike hardcoded HTTP calls
      • Cost: instant consistency
      • (Read models and polyglot persistence: ch. 8; sagas and the transactional outbox: ch. 12.)

7.3 Eventual consistency

After placing an order the Recent Orders page may show shipping "Pending" or nothing. You traded immediate consistency for availability: from ACID to BASE ("Basically Available", eventually consistent; ch. 8).

  • Reality is eventually consistent:
    • a cheque is reconciled days later
    • you see the sun as it was 8 minutes ago
      • Eventual consistency: if no new updates, eventually all reads return the last value (Werner Vogels: https://www.allthingsdistributed.com/2008/12/eventually_consistent.html).
  • Coffee shop:
    • synchronous = the cashier makes your latte before the next order (100% consistent, 0% scalable)
    • eventual = write your name on a cup, take the next order, the barista calls your name in 3 minutes (higher latency for you, massive scalability)
      • See Hohpe, "Your Coffee Shop Doesn't Use Two-Phase Commit" (https://www.enterpriseintegrationpatterns.com/docs/IEEE_Software_Design_2PC.pdf).
  • Design rule: identify what needs immediate consistency (no negative checking balance) vs what tolerates eventual (total likes). "Most of your system can be eventually consistent."
  • Panic gap = read-your-writes problem:
    • user buys a $5,000 laptop, redirected to "My Orders", sees "No Orders Found" and refreshes 50 times
    • Fix: client-side intelligence (optimistic UI): show a "Processing..." placeholder from the user's intent ("We received your request").
  • CAP link:
    • distributed (P) + keep accepting orders when Shipping is down (A) = you sacrifice C
    • explain it as "we chose a system that never goes down over one that is always perfect".
  • AI agents are just slow consumers.
    • Mistake: Controller calls OpenAI synchronously, 20 s spinner, 504 Gateway Timeout, user clicks again, two LLM calls. Instead: TicketCreated event
    • SupportBot consumer pulls the text, awaits the LLM, saves the draft
    • publishes TicketDrafted. The Web API returns 202 Accepted. "Never block a human while a robot thinks: put the LLM behind a queue."
  • CAP revisited ("2 of 3" is mostly a lie):
    • CAP prohibits only perfect availability and consistency during partitions. Single region: partitions rare (design CA)
    • multi-region: P mandatory
      • Latency is a partition (a time bound on communication): if network latency exceeds your timeout you must make a partition decision (cancel checkout = choose C; accept and charge later = choose A)
      • PACELC (Daniel Abadi, 2012: https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf): if Partition, trade A vs C
    • Else (healthy) trade Latency vs Consistency
      • Modern designs use an explicit partition mode (an ATM that lets you withdraw only $200 offline) and compensation (a saga fixes it after healing)
      • Design for recovery with a compensating transaction
      • Brewer, "CAP Twelve Years Later": https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/.

7.4 The event lifecycle

Published (created), Persisted (on disk), Consumed (read by a worker), Acknowledged (complete); it can span seconds to days without loss. (Reactive Manifesto: Responsive, Resilient, Elastic, Message Driven: https://www.reactivemanifesto.org.)

  • Queue vs topic:
    • Queue = point-to-point load balancing (bank teller line): one consumer from a pool takes each message (image resizing, order processing)
    • Topic = pub/sub fan-out (radio station): every subscriber gets a copy (OrderPlaced to Shipping, Email, Analytics).
  • Four operational realities:
    1. Partitioning: topics are split into partitions; events with the same partition key (customer_id, order_id) go to the same partition, processed in order by one consumer.
    2. Ordering: global ordering is an "expensive illusion"; only within a partition. OrderPlaced and OrderCancelled on different partitions may arrive reversed: include sequence numbers or timestamps and handle out-of-order events.
    3. Delivery semantics: at-most-once (may lose), at-least-once (industry baseline; duplicates possible), exactly-once (complex, expensive, specialised brokers). Rule: default to at-least-once and make the consumer idempotent by checking a tracking table of processed event IDs.
    4. Push vs pull and backpressure: push can choke a slow consumer; pull lets unread events buffer safely in the durable partition (Black Friday: 100,000 events/s).
  • Four stages of flow:
    • Publication: the broker's tiny ACK means the producer is done
    • Enqueue: persisted to disk
    • Consumption: the message is locked but not deleted
    • Acknowledgment:
      • only on success does the consumer ACK
      • crash before ACK and the broker requeues (at-least-once). Danger: label printed but crash before ACK = a second label (fix with idempotency)
  • Dead Letter Queue (DLQ):
    • a message may fail forever because of a poison pill (bad data, e.g. Order ID -1) or broken infrastructure (firewall rule, expired password)
    • Endless redelivery is the "spawn kill" infinite death loop
    • Brokers have MaxDeliveryCount (3 or 5): after that the message moves to the DLQ ("poison queue") for human inspection; fix the bug and requeue
    • Configure it, do not hand-write loops: "RetryPolicy": { "MaxDeliveryCount": 5, "BackoffStrategy": "Exponential" /* 1s, 2s, 4s, 8s */, "DeadLetteringOnExpiration": true }
    • **Never set it to infinity
    • Monitor the DLQ**: a growing pile means a bug, config or permissions issue.
  • Fan-out storm:
    • a major tour ticket sale at midnight: 100,000 "Buy" clicks x 10 consumers = 1,000,000 background processes
    • the database exceeds connection limits or lock contention (many processes fighting for the same seat)
      • Three fixes: prefetch limits (throttling/QoS): cap unacknowledged messages per consumer ("take only 10 at a time")
    • stagger producers (batches of 50, sleep 500 ms: better 5 minutes to send than crash the DB in 5 seconds)
    • stateless horizontal scaling (spin up 500 identical consumers; ch. 9).

7.5 Code: the event (C# POCO)

An event class is a payload with no logic ("the envelope, not the postman"). Rules: past-tense name (OrderPlaced not CreateOrder), schema version property, immutability (init setters).

public record OrderPlaced : IEvent {
  public Guid EventId { get; init; } = Guid.NewGuid();     // for idempotent consumers
  public string SchemaVersion { get; init; } = "1.0";      // contract evolution
  public Guid CorrelationId { get; init; }                 // the thread across services
  public Guid OrderId { get; init; }
  public Guid UserId { get; init; }
  public decimal TotalAmount { get; init; }
  public DateTime OccurredOn { get; init; } = DateTime.UtcNow; }

Keep it minimal (not the whole customer profile; consumers look up). Broker serialises to JSON. C# record = immutable with value equality. Never put business logic (CalculateTax()) in an event.

  • Duplicate detection:
    • use the broker's built-in feature (Azure Service Bus, RabbitMQ): it tracks message IDs and drops repeats within a time window
    • don't spend your "complexity budget" re-implementing it.
  • The atomicity question (dual write):
    • saving the order and publishing the event are two actions
    • DB save succeeds then the network drops = shipping never notified
    • publish first then DB fails = a phantom order. Fix: Transactional Outbox Pattern (ch. 12).
  • Marker interface IEvent: Task PublishAsync<T>(T @event) where T : IEvent; stops you publishing a Customer or string.
  • Correlation ID:
    • GUID generated when the user clicks "Buy", passed API to database to event to queue to consumer
    • without it logs are noise, with it you filter the whole request across ten servers (replaces the stack trace).
  • Where EDA lives in a repo:
    • shared contracts project (Core.Shared/Contracts, containing OrderPlaced.cs, referenced by both sides)
    • an IEventPublisher interface instead of HttpClient
    • handlers/consumers
      • folders: public class ShippingLabelPrinter : IConsumer<OrderPlaced> replaces the Controller action. In hexagonal terms: IEventPublisher is an outbound port in the Core
      • RabbitMQPublisher or ServiceBusPublisher is an infrastructure adapter. Companion repo has a full example

7.6 The Dork Side: Apollo 13 and logs

April 13, 1970. The root cause was technical debt: years earlier the Service Module heater spec changed from 28 V to 65 V; the thermostat switches in Oxygen Tank No. 2 were not updated and melted shut in a pre-flight test.

At 55 hours (200,000 miles out) Jack Swigert stirred the oxygen tanks; wires sparked, the tank exploded. Houston telemetry ("logs"): Main Bus B Undervolt, Cryo Pressure Decreasing, Fuel Cells 1 and 3 falling. Engineers first assumed an instrumentation error (denial).

Sy Liebergot (EECOM) correlated the oxygen pressure drop rate with the fuel-cell power loss: one bug (oxygen fed the fuel cells) and told Flight Director Gene Kranz the ship was "bleeding to death": he trusted the event stream.

  • The hotfix:
    • the Lunar Module (designed for 2 men for 2 days, now 3 for 4) had rising CO2; the Command Module used square scrubber canisters, the Lunar Module round
    • Houston built an adapter from hoses, socks, duct tape and flight manuals and read instructions over the radio (the "mailbox" rig): ugly "duct tape code" that respected production constraints
    • (The book frames the square/round mismatch as an ISP violation.)
  • Legacy:
    • telemetry is truth (observability; https://copyconstruct.medium.com/monitoring-in-the-time-of-cloud-native-c87c7a5bfa3e)
    • correlation IDs matter
    • redundancy is life (the Lunar Module as backup server; in EDA the queue holds messages if the database dies).

7.7 Mission, checklist, recap

  • Mission: Toxicity Filter.
    • Console app simulating an LLM that takes 3 s: event CommentPosted (CorrelationId, CommentText)
    • broker = System.Threading.Channels
    • producer prints "HTTP 200 OK" instantly
    • consumer waits 3 s (Thread.Sleep(3000)), analyses, prints result and "ACK sent". Acceptance: no blocking
    • a visible 3 s gap
    • the same CorrelationId in both logs
      • Target output: [T+00s] [Producer] [ID: 8f42a...] Comment 'Your code smells' dropped in channel. ..
      • [T+03s] [AI Consumer] Analysis Complete: TOXICITY DETECTED! Banning User. (guided solution in Appendix A).
  • Checklist:
    • sync vs async (phone vs text)
    • temporal decoupling
    • producer-broker-consumer roles
    • eventual consistency and CAP
    • three golden rules of event design (past tense, flat structure, immutability)
    • ACK
    • DLQ and monitoring
    • correlation ID.
  • Recap:
    • EDA = broadcasting past-tense events instead of commands
    • the broker is the shock absorber
    • stop fighting the time gap and design for eventual consistency
    • PACELC
    • ACKs and DLQs
    • structured logging and correlation IDs are survival
    • mental shift from "command and control" to choreography.
