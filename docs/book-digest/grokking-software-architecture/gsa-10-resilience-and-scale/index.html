Grokking Software Architecture 10: Architecting for Resilience and Scale

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 10. Previous: Grokking Software Architecture 9: Architecting for the Cloud (pets for cattle, concrete for code). Next: Grokking Software Architecture 11: Foundational Security Architecture.

Takeaways
  • The Happy Path is a lie: in the cloud, hardware breaks daily, networks fail, APIs go down. Failure is statistically guaranteed; design to survive it.
  • Client-side shock absorbers: timeout (escape hatch), retry with exponential backoff (second chance), fallback (plan B), circuit breaker (fire alarm), bulkhead (watertight compartments).
  • Keep resilience out of business logic with decorators/annotations (Polly, Resilience4j, tenacity).
  • Scale up (bigger box, ceiling, single point of failure) vs scale out (more boxes, needs statelessness, load balancer). Scale is a business decision (money).
  • Cache before you scale out. Avoid L1/L2 caching unless you must.
  • Ariane 5 ($370M): blind code reuse and redundancy without diversity are not resilience.

10.1 Designing for failure

New developers try to prevent failure; seniors survive it. Two failure kinds:

Kind Examples Response
Transient network blips, socket timeouts, HTTP 503 retry with exponential backoff
Non-transient 400 Bad Request, 401/403, corrupt "poison pill" messages fail fast or send to a DLQ; retrying wastes compute and clogs queues

Resilience = accept that micro-failures happen and stop them taking down the application (a localised failure, not a total one). Replace the old try/catch + log + 500 page.

Restaurant analogy: the bad waiter stares at the chef forever (you wait 3 hours); the resilient waiter waits two minutes, then says "out of steak, but the chef can do chicken now". Three patterns: timeouts, retries, fallbacks.

Rate limiting vs these patterns: timeouts, retries and breakers protect you as a client; rate limiting protects you as a server (at the API gateway; ch. 11).

Timeouts (the escape hatch)

  • Many libraries wait indefinitely by default
    • 1,000 users on a hung dependency exhaust your memory "just waiting"
    • A timeout is a hard limit: "abort after X seconds"
    • Assume every network call will hang; timeout every one.
  • Two timeouts:
    • connection (the handshake; e.g. 2 s: a healthy server answers instantly, otherwise fail fast) and read (waiting for the payload; e.g. 8 s)
    • Python requests: timeout=(2, 8).
  • Where numbers come from:
    • monitoring baselines and the provider's SLA
    • If 99% of healthy requests finish under 2 s, a 2 s connection timeout is defensible
    • An SLA is a formal, contractual standard of service (uptime such as 99.9%, and for architects the latency guarantee: "95% under 500 ms")
    • Triggered timeouts become evidence for vendor accountability.
  • Timeouts alone leave the user without their order; give the network a polite second chance.

Retries (the second chance)

  • Many failures are one-millisecond blips (a 503 can be a router hiccup). But retrying 50 times a second DDoSes your own partner.
  • Exponential backoff:
    • multiply the delay after each failure (1 s, 2 s, 4 s, 8 s)
    • Popularised by Metcalfe and Boggs's 1976 Ethernet paper (http://www.bitsavers.org/pdf/xerox/parc/techReports/CSL-75-7_Ethernet_Distributed_Packet_Switching_for_Local_Computer_Networks.pdf).
  • Warning: retrying a payment can double-charge; generate an idempotency key in the business layer and pass it on every attempt (see 10.3).

Fallbacks (plan B)

  • A fallback is a pre-programmed alternative when the primary fails: default data, a cached response, a simplified rule (graceful degradation).
  • Examples:
    • Netflix cannot reach the AI recommender → hardcoded Top 10 Global Hits
    • shipping calculator down → flat $5 shipping (a deliberate trade-off: lose a few dollars to save a $100 sale).

10.2 The circuit breaker pattern

Timeouts and retries don't help when a dependency is down for an hour: every checkout blocks a thread for 10 s, threads and memory run out, and the failure cascades upstream. Like a household breaker that trips to stop a fire.

A circuit breaker is a protective proxy around external calls: if failures cross a threshold it trips (opens), blocks further requests, and returns a fast error or a fallback; the dependency gets breathing room.

State Behaviour
Closed normal; requests flow; failures are counted (electrical "closed" = wire connected, a common confusion)
Open tripped (e.g. 5 failures in a row, or 50% failures over 30 s); calls fail immediately, saving memory, user time and the struggling API
Half-open after a cooldown (e.g. 60 s) one test request goes through: success → closed; failure → open and the timer restarts

Result: self-healing. Formalised by Michael Nygard, Release It! (2007): https://pragprog.com/titles/mnee2/release-it-second-edition/.

Bulkhead pattern (breaker's partner: the breaker prevents the fire, the bulkhead prevents the flood). Partition threads, memory or DB connections into isolated compartments.

With 100 threads, a slow Payment API could occupy all of them and block even the homepage; give 80 to general traffic and 20 to payments: checkout breaks but browsing continues.

Implementation is complex (custom thread pools); see https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead.

10.3 In practice: the resilience decorator

Hand-written while loops, counters and sleep() inside business code violate Separation of Concerns: fetching a user is business, surviving the network is infrastructure. Use language features (decorators, attributes, annotations): Polly (C#), Resilience4j (Java), tenacity (Python).

The fragile way (Listing 10.1): requests.post("https://api.FlakyPayments.com/charge", json={"amount": amount, "order_id": "12345"}) then raise_for_status(). Four production failures:

  1. Infinite hang (no timeout; requests has none by default).
  2. One-strike out (no retries; a blip is a fatal 500).
  3. Missing plan B (an hour of downtime means unhandled exceptions; no queue).
  4. Double charge (no idempotency key).

It also violates SoC, testability, coupling, encapsulation, abstraction, and every SOLID principle (SRP, OCP, LSP, IoC, DIP), and fails the four architect roles (Boundary Keeper: HTTP in domain logic; Risk Scout: assumed the happy path; Explainer-in-Chief: a risky call looks safe; Scribe: magic string "12345", no timeouts documented).

The resilient way (Listing 10.2, Python)

import requests, uuid, os
from enum import Enum
import pybreaker
from tenacity import retry, stop_after_attempt, wait_exponential

db_breaker = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)   # trips after 5 failures; OPEN for 30 s

class OrderStatus(Enum):                                              # domain vocabulary, no magic strings
    PENDING_PAYMENT = "PENDING_PAYMENT"; PAID = "PAID"; FAILED = "FAILED"

class PaymentService:                                                 # infrastructure layer
    def __init__(self, base_url): self.base_url = base_url           # injected config
    @db_breaker
    @retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10), reraise=True)
    def charge_credit_card(self, amount, order_id, idempotency_key):
        response = requests.post(f"{self.base_url}/charge",
            json={"amount": amount, "order_id": order_id},
            headers={"Idempotency-Key": idempotency_key},
            timeout=(2, 8))                                          # escape hatch
        response.raise_for_status()
        return response.json()

def process_checkout(user_cart):                                      # business layer with fallback
    try:
        api_url = os.getenv("PAYMENT_API_URL", "https://api.flakypayments.com")
        order_key = str(uuid.uuid4())                                 # generated ONCE, outside the retry loop
        PaymentService(base_url=api_url).charge_credit_card(user_cart.total_amount, user_cart.order_id, order_key)
    except requests.exceptions.RequestException:                      # specific, never a naked Exception
        send_to_async_queue({"order_id": user_cart.order_id, "amount": user_cart.total_amount,
                             "status": OrderStatus.PENDING_PAYMENT.value})

Why each choice:

  • reraise=True surfaces the real network error instead of tenacity's generic RetryError.
  • The idempotency key is generated in the business layer; created inside the retried function, each attempt would get a new key and charge again.
  • Catch specific exceptions (RequestException); a naked except Exception would swallow unrelated bugs.
  • When the breaker is OPEN, charge_credit_card() raises pybreaker.CircuitBreakerError without touching the network, so Plan B runs.
  • "Don't leak the loop": the decorator handles retries, but the business layer must catch the final failure.
  • The env-var URL allows sandbox/staging swaps without touching the service. (In real code the enum, service and controller live in separate files.)

Payoff: survives blips, preserves transaction intent, protects the infrastructure; policy is declared in plain English at the top of the function (Explainer-in-Chief) and documented (Scribe).

Sidecars vs decorators: a service mesh (Linkerd, Istio, Envoy sidecar proxies) can do transparent network retries, circuit breaking (ejecting failing nodes), connection pooling, mTLS. Use application code for domain-aware fallbacks (a cached value, a queued order); a proxy can retry a packet but only your code knows the business plan B.

Caveat on payment fallbacks: queuing unauthorised card charges for later creates financial liability (delayed declines), locks inventory, and risks false confirmations. Don't implement it alone: present the business with synchronous fail-fast (reject checkout, protect inventory) vs asynchronous order capture (PENDING_PAYMENT with an inventory lock timeout).

Architecture as a financial record (the Scribe role): timestamped logs of triggered timeouts and breakers are evidence:

  • Service credits: timeouts prove individual SLA breaches; breakers prove systemic outages.
  • The "wait-tax" audit: hanging requests burn CPU and memory; hard limits and fallbacks avoid scaling out just to hold a backlog.
  • Vendor accountability:
    • a 2.0 s timeout against a promised 0.5 s is an exhibit
    • The author's team once proved a provider's repeated SLA latency breaches over 5 days (slow network caused backup retries and data-transfer overages) and received over $10,000 in service credits.
  • Needs observability (Datadog, Splunk, New Relic, Prometheus + Grafana; ch. 14).

10.4 Scalability

Scalability = handling increasing workloads by adding resources (e.g. 10 users a minute to 10,000 a second after an influencer tweet).

  • A business decision:
    • each extra "nine" (99.9% to 99.99%) raises cost, complexity and maintenance exponentially
    • The architect presents the trade-off ("$5,000 a month extra to survive a 10,000 users/second spike: worth it?") and aligns
    • Over-engineering a 500-employee HR tool is an architectural failure.
  • Scale up (vertical):
    • one more powerful worker (a $20/month 2 GB server to a $400/month 64 GB, 16-core server). Pro: easy, no code change. Con: hard physical ceiling
    • single point of failure.
  • Scale out (horizontal):
    • more identical smaller servers behind a load balancer
    • Pro: practically infinite and resilient (a crashed server is skipped)
    • Con: complexity: servers must hold no local state (a cart on Server A empties when the next click hits B) so session state lives in an external store or cache.
  • Resilience at the data layer (the availability ceiling):
    • Replication (primary/replica) with automated failover that promotes a replica.
    • Multi-region read replicas for global scale and region outages; offloads reads.
    • Replication is not a backup: a destructive query propagates to every replica. Use the 3-2-1 rule: 3 copies, 2 storage types, 1 offsite/cross-region immutable snapshot.
    • RPO
      • (Recovery Point Objective: minutes of data loss tolerable) and RTO (Recovery Time Objective: restore time). RPO = 0 and RTO = 0 cost exponentially more
      • match the business's willingness to pay.

10.5 Basic performance tuning: don't compute what you can remember

Before scaling out, ask "are we doing unnecessary work?" A "Top 10 Bestsellers of the Week" join run 5,000 times for 5,000 visitors is wasteful: run it once, cache in Redis for five minutes; two servers may then suffice.

  • Multi-level caching (L1/L2): L1 = local in-process memory (a sticky note on the desk); L2 = shared distributed cache like Redis (a whiteboard). Naming comes from CPU caches.
  • Trap: cache invalidation ("only two hard things: cache invalidation and naming things"): a profile picture update must reach the database, L2 and every server's L1, or users see flickering stale data.
  • Use L1 only when:
    • data is practically immutable (US states, ZIP codes, historic tax rates)
    • you need microsecond latency (high-frequency trading, real-time game routing)
    • you pay heavy network egress (a 5 MB file read from Redis 10,000 times a minute).
  • Tip: a single L2 cache first; L1 early is premature optimisation until metrics prove latency or cost hurt.

10.6 The Dork Side: the $370 million overflow (Ariane 5)

4 June 1996: the European Space Agency's uncrewed Ariane 5 (four scientific satellites) veered 90 degrees 37 seconds after liftoff (about 2.5 miles up); aerodynamic stress ripped off the boosters, triggering self-destruct: $370 million and a decade of research. Cause: software.

  • The bug:
    • horizontal velocity stored as a 64-bit float was converted to a 16-bit signed integer (max 32,767)
    • Ariane 5 was faster, the value overflowed, an unhandled exception crashed the navigation computer
      • (An unsigned 16-bit, max 65,535, would also have been exceeded a fraction of a second later.)
  • Lesson 1: context is everything (blind reuse).
    • The failing function (Inertial Reference System alignment) only needs to run on the launchpad
    • On Ariane 4 a hack kept it running 50 seconds after liftoff (restarting after a late hold took 45 minutes); Ariane 4 could not reach the limit in that window
    • It was copied into Ariane 5 with no simulation against the new flight profile
    • "Proven" only in the environment where it was tested.
  • Lesson 2: redundancy is not resilience.
    • A fully independent backup computer ran the same software
    • it hit the same line 0.05 seconds later and crashed identically. True resilience requires diversity: a backup database running the same bad SQL does not help
    • a real fallback does something different (cached result, graceful degradation).
  • Convenience trap:
    • code left running purely for human convenience destroyed a rocket
      • "Writing or leaving code in production simply to make your own life easier is architectural malpractice." Every running line, thread, connection or task is a liability
    • turn off what serves no purpose in that context.
  • Report: Ariane 501 Inquiry Board (Prof. J. L. Lions, 19 July 1996): https://www-users.math.umn.edu/~arnold/disasters/ariane5rep.html.

10.7 Mission, checklist, recap

Mission: Protecting Shop-Zilla on Black Friday. FlakyPayments fails ~30% of requests; successes take 8 s instead of 1 s.

Decide: (1) a timeout (assume 99% of healthy requests finish under 2 s; 8 s is too long to hold a thread); (2) retry count and backoff multiplier; (3) circuit breaker failure threshold (e.g. 10 in a row) and cooldown before half-open; (4) the fallback: what to show the user and how to capture the order data to charge later.

No single right numbers, but defensible ones.

Recap: Happy Path is an illusion; timeouts prevent thread exhaustion; retries with backoff; the breaker fails fast and probes; fallbacks degrade gracefully; bulkheads isolate resources; decorators keep SoC; architecture is a financial record; scale up vs out; cache before scaling; Ariane 5.
