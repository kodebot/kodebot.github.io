Grokking Software Architecture 13: Architecting for the Delivery Lifecycle (CI/CD)

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 13. Previous: Grokking Software Architecture 12: The Great Debate: Monoliths vs Microservices. Next: Grokking Software Architecture 14: Architecting for Quality and Observability.

Takeaways
  • Deployability is a first-class -ility. A 40-step manual checklist at 2 a.m. is an architecture problem, not an IT problem.
  • Traffic-shifting strategies: rolling, blue-green, canary. Feature flags separate deployment (engineering) from release (product).
  • Governance as code: architectural fitness functions (NetArchTest, ArchUnit) as blocking CI gates; ratchet old debt.
  • Change data shape with Expand/Contract; beware data divergence on rollback.
  • Build one immutable image and promote it; consider testing in production vs a staging tier.
  • DORA metrics score the architecture. Knight Capital lost $440M in 45 minutes to a manual deployment.

13.2 Designing for deployability

A system that cannot be deployed "at 2 p.m. on a Tuesday without anyone breaking a sweat" has boundaries that are not as decoupled as you think (Humble and Farley, Continuous Delivery; Fowler: https://martinfowler.com/bliki/ContinuousDelivery.html).

  • Monolith: one artifact; but across 20 nodes behind a load balancer the pipeline must run rolling upgrades (drain connection pools, verify health checks, update target groups).
  • Microservices: the pipeline must also coordinate independent schedules, backward-compatible API contracts (ch. 6) and ensure shipping v2.4 cannot take down checkout.

13.3 Deployment strategies

Big Bang (recreate): stop v1, show a maintenance page, upload v2, pray. Two hours dark to change a button colour violates SLAs.

Rolling updates (assembly line)

Replace instances one by one or in small batches: drain, upgrade, health-check, return to the load balancer.

  • Pro: cheap; no parallel environment.
  • Con: dual-version problem: v1 and v2 serve the same pool; one refresh may hit v1 then v2, so schema changes cannot be dropped blindly (see Expand/Contract).

Blue-green (parallel worlds)

Blue = live (100% of traffic); Green = an identical isolated copy running the new code. Run end-to-end, load and security tests on Green, then flip one routing setting at the gateway or load balancer.

  • Pro: zero downtime, no version mixing, near-instant rollback (flip back).
  • Con: two full environments (the "Infrastructure Premium").
  • Data-divergence trap: orders written to Green in the five live minutes are trapped in Green's database if you roll back to Blue; you need a synchronisation strategy.

Canary (early warning)

Named for miners' canaries. Send a tiny slice (e.g. 2%) of real traffic to the new version, watch error rates and checkout completion, then dial up (10%, 25%, 50%...) or tear down (https://martinfowler.com/bliki/CanaryRelease.html).

  • Pro: minimal blast radius using real behaviour.
  • Con:
    • operational complexity
    • needs session affinity (no hopping between canary and main mid-session)
    • both versions write to the shared database, so data divergence needs Expand/Contract.

Deployment vs release: feature flags

  • Deployment = moving binaries to production (engineering concern).
  • Release = making a feature visible (product concern).
  • A feature flag (toggle) changes the runtime path without redeploying:
    if (_featureManager.IsEnabled("EnterpriseDiscountV2")) return CalculateEnterpriseDiscount(order);
else return CalculateLegacyDiscount(order);
  • Dark launch: ship with the flag off; enable for QA/audit accounts only; marketing flips it later with no pipeline run (Separation of Concerns).
  • Flag debt: forgotten toggles create dead paths (the Knight Capital cause). Govern with:
    • Expiry metadata: owner, creation date, expires: "2026-10-01"; a CI fitness function fails the build past expiry.
    • Telemetry-driven stale audits: LaunchDarkly, Unleash; a flag 100% true or false for 14 days is stale and auto-ticketed.
    • AST linters such as Uber's Piranha remove the dead branch and open a PR.

Trade-off matrix

Strategy Infra cost Rollback speed Dual-version risk Operational complexity
Big Bang low very slow none very low
Rolling low moderate high medium
Blue-green high (double footprint) instantaneous none (but see data divergence) medium
Canary low-medium fast controlled high

AWS comparison: https://docs.aws.amazon.com/whitepapers/latest/overview-deployment-options/overview-deployment-options.html.

13.4 Architecture governance: automated guardrails

AI risk (Jekyll and Hyde): an AI assistant writes syntactically fine code but takes the path of least resistance, leaking boundaries ("accidental arsonist"), 10 times faster. Tired human reviewers miss structural leaks (a query creeping into a controller). Blog: https://blogs.realworldbooks.academy/the-accidental-architecture-crisis.

Fitness functions as unit tests (ch. 4): NetArchTest (.NET), ArchUnit (Java/TypeScript) parse compiled code into a graph. Two rules:

  1. Domain layer must not depend on Infrastructure.
  2. Controllers must be named *Controller and live in the Presentation namespace.
[Fact] public void DomainLayer_ShouldNot_DependOn_InfrastructureLayer() {
  var result = Types.InAssembly(typeof(Domain.Order).Assembly)
      .That().ResideInNamespace("ShopZilla.OrderService.Domain")
      .ShouldNot().HaveDependencyOn("ShopZilla.OrderService.Infrastructure").GetResult();
  Assert.True(result.IsSuccessful, "Data Isolation Error: Core Domain cannot depend on Infrastructure!"); }

The build goes red and deployment halts.

Expand/Contract (parallel change)

Swapping binaries takes milliseconds; changing data shape is "remodelling a house during a dinner party". Never run a raw ALTER TABLE ... DROP COLUMN on a live database.

Rename customer_phone to phone_mobile:

  1. Expand: add the new empty column beside the old; old code still works.
  2. Transition: write both (INSERT INTO orders (id, customer_phone, phone_mobile) VALUES (101, '555-0199', '555-0199')), backfill history. Use deterministic write ordering or optimistic locks so a v1 container does not overwrite a migrated row.
  3. Contract: when analytics show 100% of instances use the new schema, release the cleanup that removes legacy code and drops the old column.

Talk: Pramod Sadalage (https://www.youtube.com/watch?v=emgBzHZJwN4). Your service boundaries decide the pain: a shared multi-service database needs cross-team orchestration; strict database isolation keeps it contained.

Preventing data divergence (survival guide)

  • Golden rule: never let two concurrent versions make incompatible structural mutations on one schema.
  • Automate with Expand/Contract, abandon destructive scripts.
  • Inversion toggle:
    • a runtime flag, separate from delivery switches, forcing the app to stop writing the new format and revert to legacy when you roll back
    • otherwise the old version chokes on new rows.
  • Deployment circuit breakers: trip when DB latency crosses the SLA during backfills or index builds (ch. 10).
  • Graceful degradation: drop to read-only mode or serve cached responses during migration locks.

Common pitfalls with guardrails

  • "Perfect architecture" trap: don't enforce everything on day one; start with one critical rule.
  • "Silent killer" gate: warnings that do not fail the build are ignored; guardrails must block.
  • No on-ramp:
    • use a ratchet gate. If the legacy code has 85 violations, set the ceiling at 85
    • an 86th fails
    • if someone fixes down to 78, the baseline becomes 78. Pair with the Boy Scout Rule (leave code cleaner than you found it).
  • (Strangler Fig appears for the third time, ch. 5, 12.) Reference: Ford, Parsons, Kua, Building Evolutionary Architectures.

13.5 The CI/CD pipeline: conveyor belt of truth

  1. Commit trigger: a human or AI pushes; a webhook starts an ephemeral cloud runner (ch. 9).
  2. Guardrail gauntlet (CI): linting and formatting; unit and integration tests; fitness functions (an unauthorised Domain-to-Presentation dependency crashes the pipeline here).
  3. Assembly: build an immutable container image, tag it uniquely, store it in a private registry.
  4. Zero-downtime landing (CD): per the chosen strategy (e.g. blue-green: start Green, watch health, flip routing).

Roll forward vs rollback

  • Rollback: re-point routing to the previous stable image (instant; risks dual-version and data divergence, reconcile data from the failure window).
  • Roll forward: hotfix goes through the full pipeline (v2.1 over faulty v2.0).
  • Warning:
    • roll forward only works if MTTR is low
    • The true lead time includes:
      • diagnosis and triage
      • build and automated verification
      • artifact baking and supply-chain tagging (SBOM, vulnerability scan)
      • governance gates (approvals)
      • cluster promotion and health probes
    • If this takes 45 minutes, users suffer 45 minutes; in finance or medical systems, instant rollback stays the default.

13.6 Code: GitHub Actions pipeline

name: Order Service Lifecycle Pipeline
on: { push: { branches: ["main"] }, pull_request: { branches: ["main"] } }     # A: trigger on commit/PR
jobs:
  verify-and-build:
    runs-on: ubuntu-latest                                                      # B: ephemeral "cattle" runner
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '10.0.x' }
      - run: dotnet restore
      - run: dotnet test --no-restore --configuration Release                  # C: governance gate (unit + fitness tests)
      - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: docker/login-action@v3
        with: { registry: registry.shopzilla.com,
                username: ${{ secrets.REGISTRY_USERNAME }}, password: ${{ secrets.REGISTRY_PASSWORD }} }  # D: secrets from the vault
      - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: docker/build-push-action@v5
        with: { context: ., file: ./ShopZilla.OrderService/Dockerfile, push: true,
                tags: "registry.shopzilla.com/order-service:latest, registry.shopzilla.com/order-service:${{ github.sha }}" }  # E
  • A: the pipeline runs on every commit or PR to main.
  • B: a fresh runner used for ~60 seconds then destroyed (cattle, ch. 9).
  • C: dotnet test also runs the architecture rules; a breach breaks the chain.
  • D: no hardcoded credentials (ch. 11).
  • E: double tagging: latest for convenience, ${{ github.sha }} as the traceable fingerprint of the commit.
  • Takeaway: look at the shape (clean environment, automated boundaries, immutable artifact, safe push), not the YAML syntax.

13.7 Environment promotion as architectural confidence

Environment promotion: the single immutable artifact, compiled once, is promoted through a chain of environments by its SHA. Never build a "similar" container per environment (configuration drift).

  1. Local sandbox: fluid; proves intent, not survival in a network ("works on my machine").
  2. Dev environment: shared cloud, closer to production.
  3. Pre-production gateway: staging or testing in production.

The staging dilemma: a permanent physical clone of production is "often a well-intentioned lie": data drifts, sizes mismatch for cost, simulated load never matches real human traffic; systems pass staging then die at real scale. You "pick your pain": pay to maintain staging, or invest in testing in production:

  • Dark launch to live servers behind isolated routing.
  • Canary to ~1% of real sessions while watching dashboards.
  • Expand/Contract schemas and inversion flags as safety latches.

When to keep staging: compliance (banking, medical privacy) that legally mandates a partition between unreleased code and real user records; heavily coupled shared databases or legacy mainframes that cannot be isolated by toggles.

When to promote straight to production (all four prerequisites):

  1. High-confidence automated testing (unit, integration, contract, fitness functions).
  2. Strict service decoupling (bounded contexts).
  3. Ephemeral preview environments (IaC).
  4. Fine-grained production routing controls (dark launch, inversion flags, canary proxies).

Rule of thumb: if you cannot isolate a failure to a single-digit percentage of users within milliseconds, keep staging; if you can, production is the final validation loop.

13.8 DORA metrics: the architecture's report card

DORA (DevOps Research and Assessment) shows you need not trade speed for stability (GitLab guide: https://docs.gitlab.com/user/analytics/dora_metrics).

Axis Metric What it reveals
Velocity Deployment frequency tangled monolith = once a quarter; decoupled services = many times a day
Velocity Lead time for changes commit to production: manual provisioning = weeks; pipeline-gated containers = minutes
Stability Change failure rate % of deployments needing intervention; symptom of poor testability (fix with fitness functions)
Stability Time to restore service (MTTR) hidden dependency webs = hours; routing logic and runtime toggles = seconds

13.9 The Dork Side: Knight Capital's $440M deployment error

1 August 2012: Knight Capital, the largest US equities trader (17% of NYSE volume), was functionally bankrupt by the afternoon.

  • Setup:
    • for the NYSE Retail Liquidity Program (live Aug 1) Knight upgraded its SMARS trading software (it splits big orders into small ones for the best price). Engineers repurposed an old dormant flag, PowerPeg, whose code (an old strategy that bought stock without checking total volume) sat untested for years
    • they left the dead code rather than delete it.
  • Deployment: an admin manually copied files to 8 servers; on July 31 he updated servers 1 to 7 and forgot server 8. No automated verification caught it.
  • 9:30 a.m. open: server 8 ran old code that interpreted the new data through the resurrected PowerPeg logic and began buying and selling millions of shares a second.
  • The fatal response: with no observability or fleet-state check, they uninstalled the new software from servers 1 to 7 so all eight ran the old logic and the losses accelerated.
  • 10:15 a.m.: shut down after 45 minutes; $440 million unauthorised losses; capital gone.

What was violated

  • Primary root cause: no deployment verification (nodes' build tag checks would have blocked the rollout).
  • Manual "ClickOps": automated build and deploy of one immutable image to the whole fleet makes a forgotten node impossible.
  • Blind rollback instead of routing: blue-green would have let them flip back to untouched Blue in a fraction of a second.
  • Zombie code: dead flags must be pruned and guarded (fitness functions and expiry).

Defending -ilities against "ship by Friday": (1) reframe technical risk as financial and operational risk (use Knight Capital); (2) use the Tradeoff Triangle: skipping gates means accepting a higher change-failure rate and longer MTTR; (3) write an ADR recording the business's explicit risk acceptance.
