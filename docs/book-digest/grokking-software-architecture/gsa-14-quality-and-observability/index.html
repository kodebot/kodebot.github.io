Grokking Software Architecture 14: Architecting for Quality and Observability

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 14. Previous: Grokking Software Architecture 13: Architecting for the Delivery Lifecycle (CI/CD). Next: Grokking Software Architecture 15: Communicating and Planning Architecture.

Takeaways
  • In production you cannot attach a debugger. You need testability (verify before deploy) and observability (infer internal state from emitted telemetry).
  • Inversion of Control makes testing possible: a boundary is "only as real as your ability to mock it".
  • Observability = logs (why), metrics (how: the Four Golden Signals), traces (where). Use OpenTelemetry.
  • Structured JSON logs plus MDC (thread-local context) keep business code clean.
  • LLM-ops adds token cost, time-to-first-token, drift and evaluation telemetry.
  • Avoid the Dashboard Illusion, Log Bombing and Observability as an Afterthought.
  • Nagios lesson: outside-in checks give the Green Light Lie.

14.2 Testability: IoC makes testing possible

Testing an aircraft wing: bolt it on a half-built plane in a thunderstorm, or put it in a wind tunnel. Most code is welded to live databases, real payment gateways and the system clock, so tests fail when a remote API is down or at 11:59 p.m. vs 12:00 a.m.

  • If a class does new FlakyPaymentAdapter() in its constructor it is physically coupled to the internet.
  • With IoC, the class demands an interface
    • production's DI container supplies the real adapter and tests pass a MockPaymentAdapter that succeeds or fails instantly, no network.
  • "An architectural boundary is only as real as your ability to mock it."

14.3 Observability: runtime insight

Observability = determining internal health, bottlenecks and execution state from the data an app outputs (logs, metrics, traces). Monitoring (outside-in) asks "is the server up?"; observability answers "why is this tenant's payment stalling on a nested lookup five layers down?" (Majors, Fong-Jones, Miranda, Observability Engineering).

The three-tier telemetry stack

  1. SDK instrumentation layer: language libraries (Logback/SLF4J for Java, Serilog for .NET, Winston or Pino for Node.js) capture side effects, timings, thread context.
  2. Collector or gateway (or sidecar agent): buffers, batches and filters before shipping.
  3. Centralised storage and analytics sinks: Elasticsearch, Datadog, Prometheus, Splunk.

OpenTelemetry (OTel): vendor-neutral CNCF standard (APIs, SDKs, tooling) so you can swap back-end providers with a config change (https://opentelemetry.io/docs/).

Pillar 1: structured semantic logging

Prose logs (logger.info("Order processed successfully for user " + userId)) are an anti-pattern: aggregators struggle to parse them and refactors break them. Emit machine-readable JSON with typed metadata:

{ "timestamp": "2026-05-30T07:57:34Z", "level": "INFO", "message": "Order processed successfully",
  "service": "order-service",
  "context": { "orderId": "ord_99812", "customerId": "cust_4412", "tenantId": "tenant_enterprise_beta" } }

You can filter a billion logs down to one customer's order quickly.

Pillar 2: metrics and the Four Golden Signals

Metrics are numerical aggregations over time: infrastructure vitals (CPU, memory, network I/O) and application vitals:

Signal Meaning
Latency time to serve a request; track p99 tail latency (the threshold below which 99% of requests fall, i.e. the slowest 1%'s experience), not the flat average
Traffic demand: requests per second, concurrent actions
Errors failure rate: HTTP 5xx or caught exceptions
Saturation how close resources are to capacity: queues, heaps, thread pools. Pool of 50 DB connections at 100% means request 51 waits, latency spikes, then times out

Limit: aggregates tell you the system suffers (p99 8.5 s, errors +4%) but not who or what: 10,000 healthy users hide one tenant locking the thread pool. You need traces.

Pillar 3: traces

A trace links all hops of one request. A unique trace ID (correlation ID) is injected into headers or event metadata at the edge, carrying across boundaries, threads and queues into an end-to-end tree. Standard header spec: W3C Trace Context (https://www.w3.org/TR/trace-context/).

Model observability (LLM-ops)

Classic observability asks if the server is up; model observability asks if the intelligence is correct, cost-effective and safe. Four data classes:

  1. Token diagnostics and economic guardrails: track prompt_tokens and completion_tokens in real time; a recursive agent loop can burn thousands of dollars an hour, so telemetry must trigger circuit breakers over tenant budgets or depth limits.
  2. Semantic latency and the "reasoning gap": measure Time-to-First-Token (TTFT) separately from total generation time; trace streaming chunks.
  3. Guardrails, toxicity and semantic drift: log prompt and completion embeddings; vector distance reveals semantic drift. Add a human-in-the-loop hook that logs the full chain of thought when a guardrail (e.g. prompt-injection catch) fires.
  4. Automated evaluation frameworks: RAGAS (grades accuracy and relevance), LangSmith (traces reasoning chains) act like fitness functions, failing the pipeline on hallucination or low faithfulness. They are heuristic and evolving: early indicators, not proof.

14.4 Instrumentation logging

Visibility erodes one uninstrumented endpoint at a time ("we'll add logging later").

Mapped Diagnostic Context (MDC)

Passing a TelemetryContext into every port, entity method and repository violates Separation of Concerns. MDC (pioneered by Ceki Gülcü in Java's log4j) tags a thread with context in thread-local storage; the logging framework stamps it on every downstream log from that thread.

  • Equivalents: AsyncLocal (.NET), AsyncLocalStorage (Node.js), contextvars (Python).
  • Thread-local storage = per-thread private variable ("sandbox"; writes invisible to other threads).
  • Steps
    1. Entry: at the edge (middleware or controller) MDC.put("tenantId", ...), MDC.put("orderId", ...). In production use a decorator, AOP aspect or middleware, not manual puts in service logic.
    2. Deep stack: controller, application service, domain aggregate and repository know nothing about MDC.
    3. Enriched log: five layers down logger.debug("Executing relational record lookup") is output as JSON with tenantId and orderId.
    4. Cleanup: when the request ends the map is emptied (no leaks or contamination).
  • Legacy tip: add a single Servlet filter, HTTP interceptor or gateway middleware at the edge to upgrade an old codebase's logs without changing signatures.

Case study: the high-volume breaking client

One tenant created vastly more records than any other; screens hung for seconds, pipelines crawled, while infrastructure dashboards looked fine. 5 Whys with the Four Golden Signals:

Why Finding (tool)
1. Why slow for one client? p99 latency spike on one API endpoint (request telemetry)
2. Why that endpoint? not CPU: stalled waiting on a repository lookup (custom telemetry logs)
3. Why was the query slow? excessive disk reads loading deeply nested relational tables (database performance insights)
4. Why this client? cloned their data to staging: tens of thousands of deeply nested records, a non-standard usage
5. Root cause? single-tier caching and connection-pool assumptions overwhelmed; pool saturation hit 100%
  • Three tools: database query and performance insights; Application Insights request telemetry and live metrics; custom telemetry debug logs.
  • Remedy:
    • because queries sat behind clean interfaces (ch. 3, 5) the data-access strategy changed without touching the domain
    • an in-memory L1 cache with a shared L2 (Redis) (ch. 8, 10) kept redundant reads off the database.
  • Afterwards:
    • rich logging, duration metrics, tenant-scoped tracing and query hooks became first-class for critical paths, enforced with fitness functions (ArchUnit, NetArchTest) asserting new endpoints, services and repositories must inject loggers and bind MDC hooks
    • run in CI (ch. 13).

14.5 Three observability anti-patterns

Anti-pattern What goes wrong Instead
Dashboard Illusion a wall of green aggregate gauges (CPU, memory, error rate fine) hides one tenant's collapse add tenant- and transaction-scoped telemetry; aggregates say all is fine, instrumentation logs say where
Log Bombing logging everything (every assignment, function entry, status) buries the needle and costs storage and I/O log contextually; dynamic levels; sampling; volumetric alarms
Observability as an afterthought retrofitting at 2 a.m. mid-incident is stressful and too late for the data you need ship telemetry with the feature: duration metrics, tenant-scoped trace IDs, query hooks

Common root cause: treating observability as something the system provides automatically.

Defensive volume management

  • Log contextually: log boundary entries (hitting the database), failures and unusual states; let a correct repetitive loop work in silence.
  • Dynamic log levels: keep WARN/ERROR normally; flip one component to DEBUG at runtime with no redeploy.
  • Event sampling: in a batch of 100,000 card payments log the first, then ~1% (every 100th).
  • Volumetric alarms: a "water meter": 50 logs/s on a normal Thursday jumping to 5,000/s signals a code emergency (an infinite loop repeating one error).

When to log

Do log Don't log
Boundary crossings (database, external API) Tight loops (inside a foreach over thousands of rows)
State and lifecycle transitions (OrderPlaced, PaymentSettled, AccountLocked) Method entry/exit tracing (use trace spans)
Failures and anomalies (exceptions, fallbacks, unexpected data) Happy-path noise ("iteration 42 successful")
Security audit milestones (auth attempts, escalations, denials) Secrets and PII (passwords, tokens, card PANs, health records; violates ch. 11)

14.7 Code: instrumented service and telemetry tests (Java)

Outbound port (decoupled boundary, also the ideal measuring point):

public interface PaymentPort {
    boolean process(double amount);
}

"Measure at the boundaries": because network calls sit behind ports, metrics collectors can wrap them with a decorator or proxy (p99 dependency latency, error rate) without touching domain rules; and the trace ID is read from MDC and injected into HTTP or queue headers before the adapter ships the payload.

Instrumented service (constructor injection, MDC bound for the request):

public boolean checkout(String orderId, double amount) {
  try (var context = MDC.putCloseable("orderId", orderId)) {         // thread-local, auto-cleaned
    logger.info("Executing transaction payment processing phase");
    boolean ok = paymentPort.process(amount);
    if (!ok) {
        logger.error("Payment transaction rejected by outbound payment port provider");
        return false;
    }
    logger.info("Transaction payment processed successfully"); return true; } }

Every log in the block and down the call stack carries orderId; operators query one order's story across services.

Test doubles

  • Pattern A: lambda stub.
    • PaymentPort inlinePaymentStub = amount -> true; (a Java functional interface)
    • new OrderService(stub).checkout("ord_99812", 150.00) asserts true. Passive: cannot count calls.
  • Pattern B: Mockito mock.
    • mock(PaymentPort.class); when(mock.process(anyDouble())).thenReturn(true); then verify(mockPaymentPort, times(1)).process(150.00)
    • Mockito generates a dynamic proxy recording who called, when and with what.
Property Stub (A) Mock framework (B)
Setup extremely low medium
State assertions manual dynamic
Behavioural verification no yes (times(x))
Telemetry assertions hard easy
Best for trivial happy paths complex structural constraints
  • Audit-driven verification: a stub would absorb a duplicated payment and stay green; Mockito's verify fails the CI build before a customer is double-charged.
  • Telemetry quality gate: an interceptor port asserts MDC.get("orderId") equals "ord_99812" mid-call and assertNull(MDC.get("orderId")) after, catching a dropped MDC block or a leaked context.
  • Summary: IoC and observability are two sides of one coin: testable boundaries make good measuring points.

14.8 The Dork Side: Nagios and the fallacy of outside-in monitoring

Early-2000s Nagios dominated server rooms. Apps were mute black boxes, so a supervisor ran external checks every few minutes: ICMP ping, TCP port check (80/443), remote shell (df -h, uptime). Green if ping returns, the socket opens and disk is under (say) 90%; red triggers email or pager.

  • Vulnerability 1: the Green Light Lie.
    • A memory leak or race deadlocks the DB connection pool
    • every worker freezes
    • requests stall 2 minutes then 500. Nagios stays green: kernel running, NIC answers ping in 4 ms, port 443 accepts a handshake, and frozen threads drop CPU to 2%. Dashboards say healthy
    • customers see 100% downtime.
  • Vulnerability 2: blunt thresholds and alert fatigue. A rotating log disk at 91% is normal but wakes someone at 3 a.m.; engineers learn to ignore alerts and miss real failures.
  • Cloud friction
    • Auto-scaling: 50 containers appear and vanish in 30 minutes; static host lists alarm on decommissioning.
    • War-room silos: DBAs say disk I/O is fine, network says switches are up, developers say CPU is low: finger-pointing without trace context.
    • Reinvention:
      • CNCF championed Prometheus (multi-dimensional metrics)
      • Grafana
      • OpenTelemetry, plus Datadog and Honeycomb: the application reports on itself. Nagios evolved too (cloud discovery, REST automation, container monitoring, Nagios Log Server).
  • Modern repeats: external /healthz pings, container liveness probes checking socket handshakes, or high-level cloud CPU gauges.
  • Inside-out flip (using the case study):
    • contextual awareness via MDC tenantId
    • multi-plane correlation of logs, application behaviour and database metrics (e.g. Azure Performance Insights)
    • data-driven architecture, showing where time goes per transaction
  • Cornerstone lesson: build clean boundaries with IoC so the system is testable, embed inside-out observability from day one, and let telemetry (not guesses) guide the trade-offs.

14.9 Mission, checklist, recap

Mission: instrument a legacy InventoryService endpoint. A high-volume tenant sees very long load screens; hardware metrics are fine; no logs, no correlation, SQL inside the endpoint handler. Document:

  1. Multi-layer map: query analysers, request telemetry, application metrics to find where time is lost per block.
  2. Controlled replication: capture and replicate the tenant's data safely; use Dependency Inversion to separate endpoint code from infrastructure for local benchmarking.
  3. Thread-context instrumentation: the exact MDC keys bound on every nested loop.
  4. Strategic remedy: options (query optimisation, indexing, caching redesign) with trade-offs and a metrics-driven defence of one. (Guided solution in Appendix A.) Next: communicating and planning architecture (ch. 15).

Recap: testability is structural; the boundary rule; three pillars; Golden Signals; data-driven architecture; three anti-patterns; MDC; flip the polling paradigm.
