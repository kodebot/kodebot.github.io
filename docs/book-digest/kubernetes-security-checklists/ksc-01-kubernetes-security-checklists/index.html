Kubernetes Security Checklists 1: Cluster Operator and Application Developer Checklists

Source: Kubernetes documentation, "Security Checklist" and "Application Security Checklist" (kubernetes.io, Kubernetes project, content licensed CC BY 4.0). Own-words summary. The OWASP Kubernetes Security Cheat Sheet is queued separately and not covered here. Related reading list item 16.

Takeaways
  • Both checklists say they are a first step, not a guarantee: items may be too strict or too lax for you, and the order is not a priority order.
  • For cluster operators, the big areas are authentication and authorisation, network security, pod security, secrets, images and admission controllers.
  • For developers: your own ServiceAccount, a restricted securityContext, minimal RBAC, NetworkPolicies and scanned, signed images.
  • Defaults often favour convenience: many managed clusters expose the API server publicly, and the kubelet's default settings are overly permissive without a config file.

1.1 The cluster operator checklist

Authentication and authorisation

  • Do not use the system:masters group for user or component authentication after bootstrapping, and do not run kube-controller-manager as it
    • Reserve it as a break-glass mechanism, not an admin user.
  • Run kube-controller-manager with --use-service-account-credentials.
  • Protect the root certificate (an offline CA or a managed online CA with effective access control); give intermediate and leaf certificates expiries no more than 3 years ahead.
  • Review access periodically, no more than 24 months apart; follow the RBAC good practices.

Network security

  • Use CNI plugins that support network policies
    • apply ingress and egress policies to all workloads, starting with a default deny policy in each namespace so no workload is missed (an allow-list approach).
  • Use a service mesh to encrypt in-cluster traffic if the CNI does not provide encryption in transit.
  • Do not expose the API server, kubelet API or etcd publicly. Use mutual TLS for etcd with a CA unique to etcd; consider a bastion host for the API server.
  • Filter workloads' access to the cloud metadata API (169.254.169.254) because it can leak information.
  • Restrict LoadBalancer and ExternalIPs use (the checklist cites CVE-2020-8554 and the DenyServiceExternalIPs admission controller).

Pod security

  • Grant RBAC rights to create, update, patch and delete workloads only when necessary
    • RBAC cannot restrict what is inside a Pod spec, so without admission controls, the right to create pods can give unrestricted access to schedulable nodes.
  • Apply and enforce the Pod Security Standards (privileged, baseline, restricted) in each namespace via Pod Security admission, which has warn, audit and enforce modes so you can tighten gradually
    • It replaces the removed PodSecurityPolicy.
  • Set a memory limit no higher than the request (a higher limit can expose the node to out-of-memory problems)
    • a CPU limit may suit sensitive workloads but throttles usage and can disturb autoscaling.
  • Seccomp
    • restricts the system calls a process may make (Linux only; since Kubernetes 1.27 RuntimeDefault can be the default profile)
    • AppArmor and SELinux provide mandatory access control through profiles or labels (Linux only, distribution-dependent).

Logs, placement, secrets, images, admission

Area Items
Logs and auditing audit logs, if enabled, are protected from general access
Pod placement place pods by sensitivity tier; run sensitive apps on isolated nodes or sandboxed runtimes (node selectors, PodTolerationRestriction, RuntimeClass)
Secrets no confidential data in ConfigMaps; encryption at rest for the Secret API; consider injecting from third-party stores (Secrets Store CSI Driver); do not mount service account tokens that pods do not need (automountServiceAccountToken: false); use bound, time-limited service account tokens; mount secrets as files rather than environment variables, which are more prone to leaking in crash dumps
Images only what the program needs (no shells or debug tools in production images; use ephemeral debug containers); run as an unprivileged user (USER, runAsUser); refer to images by sha256 digest not tag, or verify signatures at deploy time; scan during build and deployment
Admission controllers enable an appropriate set, secure the webhooks themselves
  • Admission controllers mentioned:
    • those on by default (CertificateApproval, CertificateSigning, CertificateSubjectRestriction, LimitRanger, MutatingAdmissionWebhook, PodSecurity, ResourceQuota, ValidatingAdmissionWebhook)
    • recommended but off by default (DenyServiceExternalIPs, NodeRestriction, which limits a kubelet to its own pods and node)
    • and optional ones (AlwaysPullImages, ImagePolicyWebhook).

1.2 The application developer checklist

Assumes the developer is a cluster user working with namespaced objects.

Area Items
Design follow sound security principles; set resource requests and limits (memory limit: this list says equal to or greater than the request, while the cluster operator list says equal to or lower, so decide which you follow; CPU limit for sensitive workloads)
Service account do not use the default ServiceAccount; one per workload or microservice; automountServiceAccountToken: false unless the pod needs the API
Pod securityContext runAsNonRoot: true; a less privileged runAsUser and runAsGroup with matching file permissions; optional fsGroup for persistent volumes; deploy into a namespace that enforces a Pod Security Standard (document or add defence in depth if you do not control that)
Container securityContext allowPrivilegeEscalation: false; readOnlyRootFilesystem: true; privileged: false; drop all capabilities and add back only what is needed
RBAC create, patch, update, delete only if necessary; do not grant rights to create or update roles (privilege escalation); review bindings to system:unauthenticated; patch on a Namespace can let users relabel it and widen attack surface
Images scan before deploying; verify signatures
Network policies allow only expected ingress and egress; check whether the cluster actually enforces NetworkPolicy
  • Advanced:
    • seccomp, AppArmor and SELinux settings per container
    • runtime classes for different isolation (gVisor, kata-containers; confidential virtual machines in high-trust settings).

Summary points

  • Defaults are not hardened: deny by default and open what you need.
  • Pod creation rights are powerful; admission controls and Pod Security Standards close the gap.
  • Treat images like code: minimal, pinned by digest, scanned, signed.
Terms to carry forward
  • Pod Security Standards: privileged, baseline and restricted policies for pods.
  • Network policy: a namespaced allow-list of pod traffic.
  • Admission controller: a gate on API requests before objects are stored.
  • Seccomp, AppArmor, SELinux: Linux kernel mechanisms limiting what processes can do.
  • Bound service account token: a time-limited token for a pod.
  • Break-glass: emergency-only use of a powerful identity.
