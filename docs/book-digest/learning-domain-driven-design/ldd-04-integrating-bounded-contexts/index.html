Learning DDD 4: Integrating Bounded Contexts

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 4. Previous: Learning DDD 3: Managing Domain Complexity. Next: Learning DDD 5: Implementing Simple Business Logic.

Takeaways
  • Bounded contexts evolve independently but must integrate; the touchpoints are contracts, and the integration language must be chosen.
  • The patterns follow how teams collaborate: cooperation (partnership, shared kernel), customer-supplier (conformist, anticorruption layer, open-host service) and separate ways.
  • Shared kernel is a pragmatic exception justified when duplication costs more than coordination; never use separate ways for a core subdomain.
  • A context map plots contexts and their integrations, showing design, communication patterns and organisational issues; maintain it as a shared effort.

Why integration

  • A boundary divides responsibility between languages
    • One context can model the same entity for a different problem from another
    • They evolve and are implemented independently, but they are not independent: components must interact to meet system goals.
  • Touchpoints are called contracts
    • They result from model and language differences, affect more than one party so must be defined and coordinated, and raise the question of which language is used for integration.
  • Patterns are grouped by the nature of collaboration between teams:
Group When
Cooperation Teams with well-established communication
Customer-supplier One side provides a service, power is imbalanced
Separate ways Teams unwilling or unable to collaborate

Cooperation

  • For contexts built by one team, or by teams with dependent goals (each succeeds only if the other does). The key criterion is the quality of communication and collaboration.

Partnership

  • Integration is coordinated ad hoc: one team tells the other about an API change and the second adapts. No drama or conflicts (Figure 4-1).
  • Coordination is two-way: neither dictates the contract language; both find the best solution and cooperate on integration issues; neither blocks the other.
  • Needs well-established collaboration practices, high commitment, frequent synchronisation, and continuous integration to shorten the feedback loop
    • Possibly a poor fit for geographically distributed teams.

Shared kernel

  • Sometimes the same model, or part of it, is implemented in several bounded contexts. It must be designed for the needs of all of them and kept consistent.
  • Example:
    • an enterprise permissions model
    • Permissions are granted directly or inherited from organisational units, any context may modify the authorisation model, and changes must affect all contexts using it (Figure 4-2).
  • Shared scope:
    • the overlapping model couples lifecycles
    • a change hits all contexts immediately. Keep it small, ideally only integration contracts and data structures passed across boundaries.
  • Implementation: a change to the source is immediately reflected everywhere.
    • Mono-repository: the same source files referenced by several contexts.
    • Otherwise: a dedicated project used as a linked library.
    • Either way, each change triggers integration tests for all affected contexts. Not propagating changes leads to stale implementations, data corruption or runtime issues.
  • When to use:
    • only when the cost of duplication is higher than the cost of coordination, which depends on volatility: the more a model changes the higher integration costs
    • So it is naturally applied to core subdomains.
  • It contradicts "one team per bounded context" when different teams are involved (the overlap is developed by several teams). Hence it must be justified as a pragmatic exception.
  • Common use cases:
    • Communication or collaboration problems that block a partnership (geography, organisational politics)
      • Without coordination you get integration issues, desynchronised models and arguments about whose is better
      • Small scope limits cascading changes, and per-change tests catch problems early.
    • Gradual modernisation of a legacy system (temporary): a shared codebase as an intermediate step towards bounded contexts.
    • Same team owning the contexts: ad hoc partnership can "wash out" boundaries over time; a shared kernel explicitly defines integration contracts.

Customer-supplier

  • One context, the supplier, provides a service to its customers. The supplier is upstream, the consumer downstream (Figure 4-3).
  • Unlike cooperation, both teams can succeed independently, so there is usually an imbalance of power: either side may dictate the contract. Three patterns follow.

Conformist

  • Power favours upstream, which has no motivation to support its clients: it offers a contract based on its own model, take it or leave it
    • Causes: an external provider or organisational politics.
  • If downstream can accept that model, the relationship is conformist: it conforms to upstream's model (Figure 4-4).
  • Justified because the contract is an industry standard or well-established model, or good enough for downstream's needs.

Anticorruption layer

  • Power still favours upstream, but downstream will not conform. It translates the upstream model into one tailored to itself through an anticorruption layer (Figure 4-5).
  • Use it when conforming is not desirable or worth the effort:
    • the downstream context contains a core subdomain (conforming might impede modelling);
    • the upstream model is inefficient or inconvenient: "if a bounded context conforms to a mess, it risks becoming a mess itself" (typical for legacy systems);
    • the supplier's contract changes often: changes affect only the translation mechanism.
  • It also isolates the consumer from foreign concepts, simplifying its language and model. Chapter 9 covers implementations.

Open-host service

  • Power favours the consumers; the supplier wants to protect them and serve well.
  • Upstream decouples its implementation model from the public interface, so each evolves at its own pace (Figure 4-6).
  • The public interface does not follow the supplier's ubiquitous language: it exposes a protocol convenient for consumers in an integration-oriented language, the published language.
  • It is the reverse of the anticorruption layer: the supplier does the translation of its internal model.
  • Upstream can evolve its implementation freely as long as it can still translate to the published language
    • It can also expose several versions of the published language so consumers migrate gradually (Figure 4-7).

Separate ways

  • Not collaborating at all, because teams are unwilling or unable. Reasons:
    • Communication issues: size or politics make collaboration hard; it may be cheaper to duplicate functionality in several contexts.
    • Generic subdomains:
      • if a generic solution is easy to integrate, integrate it locally in each context. Example: a logging framework
      • exposing it as a service would cost more than duplicating it.
    • Model differences: models so different that conforming is impossible and an anticorruption layer costs more than duplicating.
Never for core subdomains

Separate ways should be avoided when integrating core subdomains: duplicating them defeats the strategy of implementing them in the most effective and optimised way.

Context map

  • A context map is a visual representation of the system's bounded contexts and their integrations (Figure 4-8). It gives insight into:
    • High-level design: components and the models they implement.
    • Communication patterns: which teams collaborate, and which prefer "less intimate" patterns (anticorruption layer, separate ways).
    • Organisational issues: what does it mean if all of one upstream team's consumers build an anticorruption layer, or all separate-ways cases cluster around one team?
  • Maintenance:
    • introduce it from the start and update as contexts change
    • Since it holds information from several teams, maintain it as a shared effort: each team updates its own integrations
    • It can be managed as code with a tool such as Context Mapper.
  • Limitations:
    • hard to chart when a context spans several subdomains, since several patterns can be at play (Figure 4-9: a partnership and an anticorruption layer between two contexts)
    • Even within one subdomain, different modules may need different integration strategies.

Conclusion

Pattern Summary
Partnership Contexts integrated in an ad hoc manner
Shared kernel Limited overlapping model belonging to all participating contexts
Conformist Consumer conforms to the provider's model
Anticorruption layer Consumer translates the provider's model into its own
Open-host service Provider implements a published language optimised for consumers
Separate ways Cheaper to duplicate than to collaborate and integrate

Exercises

  1. Which integration pattern should never be used for a core subdomain? Shared kernel / open-host service / anticorruption layer / separate ways.
  2. Which downstream subdomain is more likely to implement an anticorruption layer? Core / supporting / generic.
  3. Which upstream subdomain is more likely to implement an open-host service (select all)? Core / supporting / generic.
  4. Which integration pattern in a sense violates ownership boundaries? Partnership / shared kernel / separate ways / none.
Answers (book appendix B)
  1. D: duplicating a core subdomain thwarts its future evolution; changes must be coordinated across copies.
  2. A: an anticorruption layer protects the downstream model, especially a core one.
  3. A: an open-host service protects consumers from changes in upstream, especially a volatile core.
  4. B: shared kernel lets teams co-evolve part of a model; an exception, to be used sparingly and justified.

Summary points

  • Contexts evolve independently but integrate through contracts.
  • Choose the pattern from team collaboration and power balance, and from subdomain type (core: no separate ways, anticorruption layer likely).
  • Use a context map, maintained by all teams.
Terms to carry forward
  • Upstream / downstream: supplier and consumer.
  • Partnership / shared kernel: cooperation patterns.
  • Conformist / anticorruption layer / open-host service: customer-supplier patterns.
  • Published language: integration-oriented protocol of an open-host service.
  • Separate ways: duplicate instead of integrate.
  • Context map: diagram of contexts and integrations.
