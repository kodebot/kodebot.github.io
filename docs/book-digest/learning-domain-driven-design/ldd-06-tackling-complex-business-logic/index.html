Learning DDD 6: Tackling Complex Business Logic

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 6. Previous: Learning DDD 5: Implementing Simple Business Logic. Next: Learning DDD 7: Modeling the Dimension of Time.

Takeaways
  • The domain model pattern (Fowler) handles complex logic: state transitions, business rules and invariants that must always hold. Its building blocks are value objects, aggregates (with entities, commands and domain events) and domain services.
  • Value objects are identified by their values, immutable, carry behaviour, and replace primitive obsession; use them whenever you can (especially for money).
  • An aggregate is a consistency and transaction boundary: only its own commands change state, one aggregate per transaction, referenced by ID elsewhere, kept as small as strong consistency allows, with a single aggregate root.
  • Domain events announce what happened (past tense); domain services host stateless logic spanning aggregates.
  • These patterns reduce degrees of freedom, that is complexity. Use for core subdomains.

History

  • The domain model pattern comes from Fowler's PoEAA, which ended: "Eric Evans is currently writing a book on building Domain Models", that is Evans's Domain-Driven Design: Tackling Complexity in the Heart of Software.
  • Evans's patterns (aggregate, value objects, repositories and others) are often called tactical DDD. To avoid implying that DDD requires them, the author uses Fowler's term: the pattern is domain model
    • aggregates and value objects are its building blocks.

Domain model

  • For complex business logic: not CRUD but complicated state transitions, business rules and invariants (rules protected at all times).
  • Help desk example (support ticket lifecycle):
    • Customers open tickets; customer and agent append messages; the ticket tracks the correspondence.
    • Priority: low, medium, high, urgent. An agent must offer a solution within an SLA based on priority.
    • If the agent does not reply within the SLA, the customer can escalate to the agent's manager. Escalation reduces the agent's response time limit by 33%.
    • If the agent has not opened an escalated ticket within 50% of the response time limit, it is reassigned automatically.
    • Tickets auto-close if the customer does not answer the agent's questions within seven days.
    • Escalated tickets cannot be closed automatically or by the agent, only by the customer or the agent's manager.
    • A customer can reopen a closed ticket only if it was closed in the past seven days.
  • An entangled net of rules. Implemented with active records it is easy to duplicate logic and corrupt state.

Implementation

  • A domain model is an object model of the domain incorporating behaviour and data
    • Building blocks: aggregates, value objects, domain events, domain services
    • All put business logic first
    • (Samples are OOP, but the concepts also apply to functional programming.)
  • Complexity:
    • the logic is already complex, so objects must add no accidental complexity: no infrastructure or technology concerns (no DB or external calls)
    • Use plain old objects (POCOs in .NET, POJOs in Java, POPOs in Python).
  • Ubiquitous language: emphasis on business logic makes the code "speak" the language and follow the experts' mental models.

Building blocks

Value object

  • Identified by the composition of its values: a Color of red, green and blue. Change a field and it is a new colour; same values means same colour, so no ID field is needed.
// Color.cs
class Color
{
    int _red;
    int _green;
    int _blue;
}
  • A ColorId (Figure 6-1) is redundant and creates bugs: two rows with the same RGB but different ids.
  • Primitive obsession
    • code smell: representing domain concepts with strings, integers or dictionaries
    • In a Person class (id, names, landline, mobile, email, heightMetric, countryCode) values are strings assigned by convention, so the class must validate everything: validation duplicates and is hard to enforce before use, worse as others evolve the code.
// Person.cs (primitive obsession)
class Person
{
    private int _id;
    private string _firstName;
    private string _lastName;
    private string _landlinePhone;
    private string _mobilePhone;
    private string _email;
    private int _heightMetric;
    private string _countryCode;

    public Person(/* ... */)
    {
    }
}

var dave = new Person(
    id: 30217,
    firstName: "Dave",
    lastName: "Ancelovici",
    landlinePhone: "023745001",
    mobilePhone: "0873712503",
    email: "dave@learning-ddd.com",
    heightMetric: 180,
    countryCode: "BG");
  • With value objects the intent is clear even with short names, and validation lives in the value objects:
// Person.cs (value objects)
class Person
{
    private PersonId _id;
    private Name _name;
    private PhoneNumber _landline;
    private PhoneNumber _mobile;
    private EmailAddress _email;
    private Height _height;
    private CountryCode _country;

    public Person(/* ... */)
    {
    }
}

var dave = new Person(
    id: new PersonId(30217),
    name: new Name("Dave", "Ancelovici"),
    landline: PhoneNumber.Parse("023745001"),
    mobile: PhoneNumber.Parse("0873712503"),
    email: EmailAddress.Parse("dave@learning-ddd.com"),
    height: Height.FromMetric(180),
    country: CountryCode.Parse("BG"));
  • Value objects shine when they centralise business logic that manipulates the values: cohesive, easy to test, and they express domain concepts.
// Examples of value object behaviour
var heightMetric = Height.Metric(180);
var heightImperial = Height.Imperial(5, 3);

var string1 = heightMetric.ToString();                   // "180cm"
var string2 = heightImperial.ToString();                 // "5 feet 3 inches"
var string3 = heightMetric.ToImperial().ToString();      // "5 feet 11 inches"
var firstIsHigher = heightMetric > heightImperial;       // true

var phone = PhoneNumber.Parse("+359877123503");
var country = phone.Country;                             // "BG"
var phoneType = phone.PhoneType;                         // "MOBILE"
var isValid = PhoneNumber.IsValid("+972120266680");      // false

var red = Color.FromRGB(255, 0, 0);
var green = Color.Green;
var yellow = red.MixWith(green);
var yellowString = yellow.ToString();                    // "#FFFF00"
  • They eliminate conventions ("this string is an email, that one a phone number").

Implementation

  • A field change means a different value, so value objects are immutable: MixWith returns a new instance.
// Color.cs
public class Color
{
    public readonly byte Red;
    public readonly byte Green;
    public readonly byte Blue;

    public Color(byte r, byte g, byte b)
    {
        this.Red = r;
        this.Green = g;
        this.Blue = b;
    }

    public Color MixWith(Color other)
    {
        return new Color(
            r: (byte) Math.Min(this.Red + other.Red, 255),
            g: (byte) Math.Min(this.Green + other.Green, 255),
            b: (byte) Math.Min(this.Blue + other.Blue, 255)
        );
    }
}
  • Equality is by value, so override equality properly (C#):
// Color.cs (equality)
public class Color
{
    public override bool Equals(object obj)
    {
        var other = obj as Color;
        return other != null &&
            this.Red == other.Red &&
            this.Green == other.Green &&
            this.Blue == other.Blue;
    }

    public static bool operator ==(Color lhs, Color rhs)
    {
        if (Object.ReferenceEquals(lhs, null))
        {
            return Object.ReferenceEquals(rhs, null);
        }
        return lhs.Equals(rhs);
    }

    public static bool operator !=(Color lhs, Color rhs)
    {
        return !(lhs == rhs);
    }

    public override int GetHashCode()
    {
        return ToString().GetHashCode();
    }
}
  • In C# 9.0 the record type has value-based equality and needs no overrides.
  • The core library string is a value object in .NET and Java: immutable, every operation returns a new instance, with rich behaviour (trim, concatenate, replace, substring).

When to use value objects

  • Whenever you can. More expressive, centralises logic, and is safer: immutable so side-effect free and thread safe.
  • Rule of thumb: use them for elements that describe properties of other objects, especially entity properties (ids, names, phone numbers, email, statuses, passwords).
  • Especially for money: primitives scatter money logic and cause rounding and precision bugs.

Entities

  • The opposite of a value object: needs an explicit identification field. A Person with only a Name is suboptimal because namesakes exist.
// Person.cs (entity)
class Person
{
    public readonly PersonId Id;
    public Name Name { get; set; }

    public Person(PersonId id, Name name)
    {
        this.Id = id;
        this.Name = name;
    }
}
  • PersonId is itself a value object over any suitable type (GUID, number, string, a domain value such as a Social Security number)
    • It must be unique per instance (Figure 6-2) and, with rare exceptions, immutable for the entity's life.
  • Entities are mutable and expected to change; value objects describe an entity's properties.
  • "Entity" is not in the domain model's building-block list on purpose: entities are implemented only inside aggregates.

Aggregates

  • An aggregate is an entity (explicit id, mutable state) but much more: its goal is to protect the consistency of its data.

Consistency enforcement

  • Mutable state can be corrupted in many ways, so the aggregate draws a clear boundary: it is a consistency enforcement boundary
    • Its logic validates all incoming changes against its rules.
  • Implementation: only the aggregate's own logic modifies its state. External processes and objects may only read; changes go through its public interface.
  • State-modifying methods are commands. Two styles:
// Ticket.cs (method style)
public class Ticket
{
    public void AddMessage(UserId from, string body)
    {
        var message = new Message(from, body);
        _messages.Append(message);
    }
}

// Ticket.cs (command object style)
public class Ticket
{
    public void Execute(AddMessage cmd)
    {
        var message = new Message(cmd.from, cmd.body);
        _messages.Append(message);
    }
}
  • Style is preference; the author prefers explicit command structures passed polymorphically to Execute.
  • The public interface validates input and enforces all rules and invariants, so all business logic for the aggregate lives in the aggregate
    • That keeps the application layer (service layer) simple: load the state, execute the action, persist, return the result
    • (Footnote: it implements transaction scripts and must be atomic.)
// Application layer
public ExecutionResult Escalate(TicketId id, EscalationReason reason)
{
    try
    {
        var ticket = _ticketRepository.Load(id);
        var cmd = new Escalate(reason);
        ticket.Execute(cmd);
        _ticketRepository.Save(ticket);
        return ExecutionResult.Success();
    }
    catch (ConcurrencyException ex)
    {
        return ExecutionResult.Error(ex);
    }
}
  • The concurrency check (the catch) is vital:
    • concurrent updates must not blindly overwrite earlier commits
    • The second process is told its state is out of date and retries
    • The database must support concurrency management; simplest is a version field incremented per update.
// Ticket.cs
class Ticket
{
    TicketId _id;
    int _version;
}

-- optimistic concurrency on commit
UPDATE tickets
SET ticket_status = @new_status,
    agg_version = agg_version + 1
WHERE ticket_id = @id AND agg_version = @expected_version;
  • The update applies changes and bumps the version only if the current version equals the one read. It can be done outside a relational database
    • document databases suit aggregates, but concurrency management must be supported.

Transaction boundary

  • The aggregate is also the transaction boundary: all its changes commit atomically (all or none).
  • No operation may assume a multi-aggregate transaction: one aggregate per database transaction. This forces careful boundary design
    • Needing to commit several aggregates signals wrong boundaries.

Hierarchy of entities

  • Sometimes several objects must share a transactional boundary (modified together, or one's rules depend on the other's state)
    • Design follows the domain: an aggregate is a hierarchy of entities sharing transactional consistency (Figure 6-3), containing entities and value objects bound by the domain's logic
    • Hence the name: it aggregates them.
  • Rule spanning entities: if an agent did not open an escalated ticket within 50% of the response time limit, reassign it:
// Ticket.cs
public class Ticket
{
    List<Message> _messages;

    public void Execute(EvaluateAutomaticActions cmd)
    {
        if (this.IsEscalated && this.RemainingTimePercentage < 0.5 &&
            GetUnreadMessagesCount(for: AssignedAgent) > 0)
        {
            _agent = AssignNewAgent();
        }
    }

    public int GetUnreadMessagesCount(UserId id)
    {
        return _messages.Where(x => x.To == id && !x.WasRead).Count();
    }
}
  • It checks escalation, remaining time (under 50%) and unread messages for the agent, against strongly consistent data that cannot change after the checks, since the changes are one atomic transaction.

Referencing other aggregates

  • All objects share one transaction, so large aggregates hurt performance and scalability
    • Use consistency as the guide:
      • only data that logic needs strongly consistent belongs inside
      • eventually consistent data lives outside, for example in another aggregate (Figure 6-4)
    • Rule: keep aggregates as small as possible.
// Ticket.cs (references)
public class Ticket
{
    private UserId _customer;
    private List<ProductId> _products;
    private UserId _assignedAgent;
    private List<Message> _messages;
}
  • Messages are inside; customer, products and agent are referenced by ID to make clear they are outside and each aggregate has its own transaction boundary.
  • Test for membership: could the logic lead to an invalid state if it worked on eventually consistent data? If read acknowledgements arrived late, many tickets would be needlessly reassigned (corrupt state), so the messages belong inside.

The aggregate root

  • Only one entity is the public interface: the aggregate root (Figure 6-5). A message can be marked read, but only through Ticket:
// Ticket.cs
public class Ticket
{
    List<Message> _messages;

    public void Execute(AcknowledgeMessage cmd)
    {
        var message = _messages.Where(x => x.Id == cmd.id).First();
        message.WasRead = true;
    }
}

Domain events

  • Besides the root's interface, the outer world hears about aggregates through domain events: messages describing a significant event that has occurred (ticket assigned, ticket escalated, message received)
    • Names are in the past tense.
  • They carry all the data about the event, for example (JSON):
{
    "ticket-id": "c9d286ff-3bca-4f57-94d4-4d4e490867d1",
    "event-id": 146,
    "event-type": "ticket-escalated",
    "escalation-reason": "missed-sla",
    "escalation-time": 1628970815
}
  • Events are part of the aggregate's public interface. The aggregate publishes them
    • other processes, aggregates or external systems subscribe (Figure 6-6). Chapter 9 covers reliable publishing.
// Ticket.cs (publishing an event)
public class Ticket
{
    private List<DomainEvent> _domainEvents;

    public void Execute(RequestEscalation cmd)
    {
        if (!this.IsEscalated && this.RemainingTimePercentage <= 0)
        {
            this.IsEscalated = true;
            var escalatedEvent = new TicketEscalated(_id, cmd.Reason);
            _domainEvents.Append(escalatedEvent);
        }
    }
}

Ubiquitous language

  • Aggregate name, data members, actions and events all use the bounded context's language
    • Evans: the code must be based on the language developers use with one another and with domain experts.

Domain services

  • Logic that fits no aggregate or value object, or concerns several aggregates, becomes a domain service: a stateless object hosting business logic, usually orchestrating calls to components for a calculation or analysis.
  • Example: the response time frame depends on the ticket (priority, escalation), the department's SLA policy and the agent's work schedule (shifts):
// ResponseTimeFrameCalculationService.cs
public class ResponseTimeFrameCalculationService
{
    public ResponseTimeframe CalculateAgentResponseDeadline(UserId agentId,
        Priority priority, bool escalated, DateTime startTime)
    {
        var policy = _departmentRepository.GetDepartmentPolicy(agentId);
        var maxProcTime = policy.GetMaxResponseTimeFor(priority);

        if (escalated)
        {
            maxProcTime = maxProcTime * policy.EscalationFactor;
        }

        var shifts = _departmentRepository.GetUpcomingShifts(agentId,
            startTime, startTime.Add(policy.MaxAgentResponseTime));

        return CalculateTargetTime(maxProcTime, shifts);
    }
}
  • Domain services coordinate several aggregates but are not a loophole: still one aggregate instance modified per transaction
    • they suit calculation logic reading several aggregates.
  • They have nothing to do with microservices, SOA or other uses of "service".

Managing complexity

  • Goldratt (The Choice): complexity is the difficulty of controlling and predicting behaviour, reflected in degrees of freedom: the data points needed to describe a state.
  • Two classes:
    • ClassA has five independent properties: five degrees of freedom
    • ClassB has five variables but B and C derive from A (value / 2, value / 3) and E from D (value * 2): two degrees of freedom
    • ClassA is harder to control and predict, so ClassB's invariants reduce complexity.
// ClassA.cs
public class ClassA
{
    public int A { get; set; }
    public int B { get; set; }
    public int C { get; set; }
    public int D { get; set; }
    public int E { get; set; }
}

// ClassB.cs
public class ClassB
{
    private int _a, _d;

    public int A
    {
        get => _a;
        set
        {
            _a = value;
            B = value / 2;
            C = value / 3;
        }
    }

    public int B { get; private set; }

    public int C { get; private set; }

    public int D
    {
        get => _d;
        set
        {
            _d = value;
            E = value * 2;
        }
    }

    public int E { get; private set; }
}
  • Value objects and aggregates encapsulate invariants, reducing degrees of freedom: their logic sits within their boundaries and state changes only through their own methods.
  • Since the pattern is for complex logic, it targets core subdomains.

Conclusion

Building block Summary
Value object Identified only by values, immutable, models data and behaviour
Aggregate Hierarchy of entities sharing a transactional boundary; strongly consistent data; modified only through commands; committed atomically; publishes domain events
Domain service Stateless object hosting logic belonging to no aggregate or value object
  • Because state cannot be changed from outside, business logic is not duplicated in the application layer. Next: event sourcing, making time part of the model.

Exercises

  1. True statement: value objects hold only data / only behaviour / are immutable / their state can change.
  2. Guiding principle for aggregate boundaries: only one entity / as small as possible while keeping consistency requirements / as wide as possible / depends.
  3. Why one aggregate instance per transaction? Performance / correct transactional boundaries / no such requirement / databases without multirecord transactions.
  4. Relationships between building blocks (select all): value objects describe entities' properties / value objects emit domain events / an aggregate contains one or more entities.
  5. Active records versus aggregates: active records hold only data / an aggregate encapsulates all its business logic, but logic manipulating an active record can sit outside / aggregates hold only data / an aggregate contains active records.
Answers (book appendix B)
  1. C: value objects are immutable and can hold data and behaviour.
  2. B: as small as possible while keeping consistency requirements.
  3. B: one aggregate per transaction is another way to ensure all strongly consistent information sits inside the boundary.
  4. A and C: value objects describe entities' properties; an aggregate contains one or more entities.
  5. B: both can have behaviour, but the aggregate enforces that all related behaviour lives in its boundary.

Summary points

  • Domain model for complex logic, built from value objects, aggregates and domain services.
  • Aggregates: commands in, events out, one root, one transaction, small, referenced by ID, versioned for concurrency.
  • Invariants cut degrees of freedom and so complexity.
Terms to carry forward
  • Value object / entity: identified by values and immutable / identified by id and mutable.
  • Aggregate / aggregate root: consistency and transaction boundary / its only public entry point.
  • Command / domain event: state-modifying call / past-tense fact it publishes.
  • Domain service: stateless logic spanning aggregates.
  • Invariant: rule that must always hold.
  • Primitive obsession: using primitives for domain concepts.
  • Degrees of freedom: data points describing a state.
