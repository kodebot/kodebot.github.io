Learning DDD 9: Communication Patterns

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 9. Previous: Learning DDD 8: Architectural Patterns. Next: Learning DDD 10: Design Heuristics.

Takeaways
  • These patterns organise communication across components: cross-context model translation, publishing aggregate events reliably, and processes spanning aggregates.
  • Model translation (for an anticorruption layer or open-host service) is stateless (proxy, API gateway, message proxy) or stateful (aggregating or unifying data, with its own storage).
  • Publishing an event from the aggregate or after the commit is unsafe; the outbox commits state and events atomically and a relay publishes them (at-least-once).
  • A saga is a long-running process matching events to commands with compensations; a process manager holds state and decides next steps (if-else means process manager).
  • Only data inside an aggregate is strongly consistent; do not use sagas to patch bad boundaries.

Scope of the chapter

  • Beyond one component: patterns that facilitate cross-bounded-context communication, work around aggregate limitations and orchestrate business processes across components.

Model translation

  • Recap (chapter 4): with cooperating teams, partnership coordinates protocols ad hoc, and shared kernel co-evolves a limited model, for example integration contracts in a co-owned repository.
  • In customer-supplier, if downstream cannot conform, models must be translated:
    • downstream adapts the upstream model with an anticorruption layer (ACL);
    • upstream protects consumers with an open-host service (OHS) and an integration-specific published language.
  • The logic is similar, so the chapter does not distinguish them
    • Translation is stateless (on the fly for incoming OHS or outgoing ACL requests) or stateful (complex, needs a database).

Stateless model translation

  • The owner of the translation (OHS upstream, ACL downstream) implements a proxy that intercepts incoming and outgoing requests and maps the source model to the target model (Figure 9-1)
    • The form depends on sync or async communication.

Synchronous

  • Typically embed the transformation in the context's codebase (Figure 9-2): an OHS translates to the public language when processing incoming requests; an ACL when calling upstream.
  • Or offload to an API gateway: open source (Kong, KrakenD) or managed (AWS API Gateway, Google Apigee, Azure API Management).
    • For an OHS the gateway converts the internal model into the published language and eases serving multiple API versions (Figure 9-3).
    • An ACL built on a gateway can serve several downstream contexts, acting as an integration-specific context (Figure 9-4)
      • Such contexts, mainly transforming models for others, are interchange contexts.

Asynchronous

  • A message proxy:
    • an intermediary subscribing to the source context's messages, transforming them and forwarding them to the target (Figure 9-5)
    • It can also filter out irrelevant messages to reduce noise.
  • Essential for an open-host service:
    • a common mistake is exposing domain events as they are, which leaks the implementation model
    • Intercept and convert them into the published language (Figure 9-6)
    • This also separates private events (internal) from public events (integration); chapter 15 expands.

Stateful model translation

  • For bigger transformations: aggregating source data or unifying several sources.

Aggregating incoming data

  • Batching requests (sync or async) for performance (Figure 9-7), or combining several fine-grained messages into one (Figure 9-8).
  • This cannot be done by an API gateway: it needs tracking, so the translation needs its own persistent storage (Figure 9-9).
  • Off-the-shelf options: stream-processing platforms (Kafka, AWS Kinesis) or batching tools (Apache NiFi, AWS Glue, Spark).

Unifying multiple sources

  • A context may process data from several sources, including other contexts. Typical: backend for frontend (Richardson), where the UI combines data from several services.
  • Or a context with complex logic over data from many contexts: front it with an anticorruption layer that aggregates all sources, decoupling integration complexity from business logic (Figure 9-10).

Integrating aggregates

  • Aggregates communicate by publishing domain events (chapter 6). How to publish to a message bus? First, two mistakes.

Mistake 1: publishing from the aggregate

// Campaign.cs (wrong)
public class Campaign
{
    List<DomainEvent> _events;
    IMessageBus _messageBus;

    public void Deactivate(string reason)
    {
        foreach (var l in _locations.Values())
        {
            l.Deactivate();
        }

        IsActive = false;

        var newEvent = new CampaignDeactivated(_id, reason);
        _events.Append(newEvent);
        _messageBus.Publish(newEvent);
    }
}
  • Two problems: the event is dispatched before the new state is committed (a subscriber may be told of a deactivation the state contradicts), and if the transaction fails (race condition, later logic making it invalid, database problem) the event is already published and cannot be retracted.

Mistake 2: publishing from the application layer after commit

// ManagementAPI.cs (still wrong)
public class ManagementAPI
{
    private readonly IMessageBus _messageBus;
    private readonly ICampaignRepository _repository;

    public ExecutionResult DeactivateCampaign(CampaignId id, string reason)
    {
        try
        {
            var campaign = _repository.Load(id);
            campaign.Deactivate(reason);
            _repository.CommitChanges(campaign);

            var events = campaign.GetUnpublishedEvents();
            foreach (IDomainEvent e in events)
            {
                _messageBus.Publish(e);
            }
            campaign.ClearUnpublishedEvents();
        }
        catch (Exception ex)
        {
            // handle
        }
    }
}
  • Events go out only after a successful commit, but the bus may be down, or the server may crash after commit and before publishing: the database is committed and the events are never published.

Outbox

  1. Commit the updated aggregate state and the new domain events in the same atomic transaction.
  2. A message relay fetches newly committed events.
  3. The relay publishes them to the bus.
  4. On success it marks them published or deletes them.

  • Relational database: use a dedicated outbox table and commit both tables atomically (Figure 9-12).
  • NoSQL without multi-document transactions: embed outgoing events in the aggregate's record:
{
    "campaign-id": "364b33c3-2171-446d-b652-8e5a7b2be1af",
    "state": {
        "name": "Autumn 2017",
        "publishing-state": "DEACTIVATED",
        "ad-locations": []
    },
    "outbox": [
        {
            "campaign-id": "364b33c3-2171-446d-b652-8e5a7b2be1af",
            "type": "campaign-deactivated",
            "reason": "Goals met",
            "published": false
        }
    ]
}
  • Fetching unpublished events:
    • Pull, polling publisher: the relay queries continuously; use proper indexes to limit load.
    • Push, transaction log tailing: the database notifies the relay (some relational databases expose record changes by tailing the log; some NoSQL stores expose streams, for example AWS DynamoDB Streams).
  • Guarantee: at-least-once delivery. If the relay fails after publishing but before marking, the message is published again next time (so consumers must handle duplicates).

Saga

  • Aggregates limit each transaction to one instance, but some business processes span aggregates.
  • Example:
    • when an advertising campaign is activated, submit its materials to the publisher
    • on confirmation set the publishing state to Published, on rejection mark it Rejected. Two different entities, possibly different bounded contexts: merging them into one aggregate would be overkill, so use a saga.
  • A saga is a long-running business process:
    • long in terms of transactions (may run from seconds to years), not necessarily time
    • It spans several transactions handled by any component emitting events and responding to commands
    • It listens to events, issues commands, and when a step fails it issues compensating actions to keep the state consistent.
  • It listens to CampaignActivated (Campaign) and PublishingConfirmed, PublishingRejected (AdPublishing context)
    • it runs SubmitAdvertisement on AdPublishing and TrackPublishingConfirmation, TrackPublishingRejection on Campaign. TrackPublishingRejection is the compensating action that makes sure the campaign is not listed as active (Figure 9-13).
// CampaignPublishingSaga.cs (simple, stateless)
public class CampaignPublishingSaga
{
    private readonly ICampaignRepository _repository;
    private readonly IPublishingServiceClient _publishingService;

    public void Process(CampaignActivated @event)
    {
        var campaign = _repository.Load(@event.CampaignId);
        var advertisingMaterials = campaign.GenerateAdvertisingMaterials();
        _publishingService.SubmitAdvertisement(@event.CampaignId,
            advertisingMaterials);
    }

    public void Process(PublishingConfirmed @event)
    {
        var campaign = _repository.Load(@event.CampaignId);
        campaign.TrackPublishingConfirmation(@event.ConfirmationId);
        _repository.CommitChanges(campaign);
    }

    public void Process(PublishingRejected @event)
    {
        var campaign = _repository.Load(@event.CampaignId);
        campaign.TrackPublishingRejection(@event.RejectionReason);
        _repository.CommitChanges(campaign);
    }
}

  • This saga is stateless and relies on the messaging infrastructure
    • Stateful sagas (for example tracking executed operations to issue compensations) can be event-sourced aggregates persisting the full history of received events and issued commands, with command execution moved out of the saga and run asynchronously like outbox event dispatching:
// CampaignPublishingSaga.cs (stateful, commands as events)
public class CampaignPublishingSaga
{
    private readonly ICampaignRepository _repository;
    private readonly IList<IDomainEvent> _events;

    public void Process(CampaignActivated activated)
    {
        var campaign = _repository.Load(activated.CampaignId);
        var advertisingMaterials = campaign.GenerateAdvertisingMaterials();
        var commandIssuedEvent = new CommandIssuedEvent(
            target: Target.PublishingService,
            command: new SubmitAdvertisementCommand(activated.CampaignId,
                advertisingMaterials));

        _events.Append(activated);
        _events.Append(commandIssuedEvent);
    }

    public void Process(PublishingConfirmed confirmed)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            target: Target.CampaignAggregate,
            command: new TrackConfirmation(confirmed.CampaignId,
                confirmed.ConfirmationId));

        _events.Append(confirmed);
        _events.Append(commandIssuedEvent);
    }

    public void Process(PublishingRejected rejected)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            target: Target.CampaignAggregate,
            command: new TrackRejection(rejected.CampaignId,
                rejected.RejectionReason));

        _events.Append(rejected);
        _events.Append(commandIssuedEvent);
    }
}
  • The outbox relay executes the commands on the relevant endpoints for each CommandIssuedEvent
    • Separating the state transition from command execution makes commands run reliably even if the process fails at any stage.

Consistency

  • A saga orchestrates a multi-component transaction, but components are eventually consistent
    • no two transactions are atomic. Principle: **only data within an aggregate's boundary is strongly consistent
    • everything outside is eventually consistent.** Do not abuse sagas to compensate for wrong aggregate boundaries: operations that must be strongly consistent belong in one aggregate.
  • Sagas are often confused with the process manager.

Process manager

  • A saga manages a simple linear flow, strictly matching events to commands: CampaignActivated to PublishingService.SubmitAdvertisement, PublishingConfirmed to Campaign.TrackConfirmation, PublishingRejected to Campaign.TrackRejection.
  • A process manager (Hohpe and Woolf, Enterprise Integration Patterns, 2003) implements a business-logic-based process: a central processing unit that maintains the state of the sequence and decides the next steps (Figure 9-14).
  • Rule of thumb: a saga with if-else branches is probably a process manager.
  • Instantiation:
    • a saga starts implicitly when an event (such as CampaignActivated) is observed
    • A process manager is bound to no single event, being a coherent multi-step process, so it must be instantiated explicitly.
  • Business trip booking:
    • the routing algorithm picks the most cost-effective flight route and asks the employee to approve
    • if the employee prefers another route the manager must approve
    • after the flight is booked, book one of the preapproved hotels
    • if no hotel is available, cancel the flight tickets. No central entity triggers it: the booking is the process (Figure 9-15).

  • Process managers are often aggregates (state-based or event-sourced), with explicit ID and persistent state, subscribed to workflow events and emitting CommandIssuedEvent for the outbox relay to execute:
// BookingProcessManager.cs
public class BookingProcessManager
{
    private readonly IList<IDomainEvent> _events;
    private BookingId _id;
    private Destination _destination;
    private TripDefinition _parameters;
    private EmployeeId _traveler;
    private Route _route;
    private IList<Route> _rejectedRoutes;
    private IRoutingService _routing;

    public void Initialize(Destination destination,
        TripDefinition parameters,
        EmployeeId traveler)
    {
        _destination = destination;
        _parameters = parameters;
        _traveler = traveler;
        _route = _routing.Calculate(destination, parameters);

        var routeGenerated = new RouteGeneratedEvent(
            BookingId: _id,
            Route: _route);

        var commandIssuedEvent = new CommandIssuedEvent(
            command: new RequestEmployeeApproval(_traveler, _route));

        _events.Append(routeGenerated);
        _events.Append(commandIssuedEvent);
    }

    public void Process(RouteConfirmed confirmed)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            command: new BookFlights(_route, _parameters));

        _events.Append(confirmed);
        _events.Append(commandIssuedEvent);
    }

    public void Process(RouteRejected rejected)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            command: new RequestRerouting(_traveler, _route));

        _events.Append(rejected);
        _events.Append(commandIssuedEvent);
    }

    public void Process(ReroutingConfirmed confirmed)
    {
        _rejectedRoutes.Append(_route);
        _route = _routing.CalculateAltRoute(_destination,
            _parameters, _rejectedRoutes);
        var routeGenerated = new RouteGeneratedEvent(
            BookingId: _id,
            Route: _route);

        var commandIssuedEvent = new CommandIssuedEvent(
            command: new RequestEmployeeApproval(_traveler, _route));

        _events.Append(confirmed);
        _events.Append(routeGenerated);
        _events.Append(commandIssuedEvent);
    }

    public void Process(FlightBooked booked)
    {
        var commandIssuedEvent = new CommandIssuedEvent(
            command: new BookHotel(_destination, _parameters));

        _events.Append(booked);
        _events.Append(commandIssuedEvent);
    }
}
Book typos

The printed Campaign loop uses for (l in ...), ManagementAPI uses repository.Load without the underscore and messageBus.publish, and ReroutingConfirmed uses bare route, destination, parameters; the notes show the evident intent.

Conclusion

Pattern Purpose
Stateless model translation Proxy, API gateway or message proxy for ACL and OHS, on the fly
Stateful model translation Aggregate or unify data, needs its own storage
Outbox Reliably publish an aggregate's domain events (never lost despite failures)
Saga Simple cross-component process matching events to commands, with compensations
Process manager Complex business process with state and decisions

Exercises

  1. Which integration pattern requires model transformation logic (select all)? Conformist / anticorruption layer / open-host service.
  2. Goal of the outbox: decouple messaging infrastructure from business logic / reliably publish messages / support event-sourced domain models.
  3. Other use cases for the outbox besides publishing to a bus? Yes / No.
  4. Saga versus process manager (select all): a process manager needs explicit instantiation while a saga runs when a relevant event is published / a process manager never persists state / a saga needs its components to be event-sourced / a process manager suits complex workflows.
Answers (book appendix B)
  1. B and C: the ACL transforms the upstream model for the downstream; the OHS transforms the internal model for consumers.
  2. B: reliably publish messages.
  3. A (yes): the outbox can drive asynchronous execution, for example sending email.
  4. A and D: a process manager needs explicit instantiation and suits complex workflows; a saga runs on a relevant event and suits simpler processes.

Summary points

  • Translate models in a proxy, gateway or message proxy; use state only when aggregating or unifying.
  • Outbox for reliable publishing; remember at-least-once delivery.
  • Saga for linear event-to-command flows; process manager for stateful, branching processes.
  • Respect strong consistency inside aggregates, eventual outside.
Terms to carry forward
  • Interchange context: context that mainly translates models.
  • API gateway / message proxy: translation components for sync and async.
  • Outbox / message relay: atomic commit of state and events, plus publisher.
  • Polling publisher / log tailing: pull and push ways to fetch unpublished events.
  • Saga / compensating action: event-to-command process, undo step.
  • Process manager: stateful, explicitly instantiated, decides next steps.
