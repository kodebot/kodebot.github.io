Learning DDD 11: Evolving Design Decisions

Source: Vlad Khononov, Learning DDD (O'Reilly, 2021), ch. 11. Previous: Learning DDD 10: Design Heuristics. Next: Learning DDD 12: EventStorming.

Takeaways
  • Design decisions must evolve with four vectors of change: business domain, organisational structure, domain knowledge and growth.
  • Subdomains morph (core to generic, generic to core, supporting to generic or core, and back); each change affects integration patterns, implementation strategy and tactical design.
  • The signal is pain: the existing technical design cannot support current needs. Migrate transaction script to active record to domain model to event-sourced domain model step by step.
  • Organisational change moves integration: partnership to customer-supplier to separate ways; more teams mean narrower contexts.
  • Domain knowledge grows (and decays): start wide, narrow later. Growth creates a big ball of mud unless you remove accidental complexity in subdomains, contexts and aggregates.

Why evolve

  • Companies must continually change, even reinvent themselves
    • Unmanaged change turns even a sophisticated design into a maintenance nightmare
    • Four common vectors: business domain, organisational structure, domain knowledge, growth.

Changes in domains

  • Recap:
    • core (done differently from competitors for advantage), supporting (done differently but no edge), generic (all companies do it the same way)
    • The type affects how to draw context boundaries, how to integrate contexts and which logic patterns to use
    • Subdomains can morph as the organisation evolves.

Change Example (online retailer BuyIT)
Core to generic BuyIT built an innovative algorithm to optimise courier delivery routes and charged lower fees. DeliverIT then offers path optimisation as a service ("solved" the travelling salesman problem), more advanced and far cheaper. It is now off the shelf for all competitors: a commodity.
Generic to core BuyIT used an off-the-shelf inventory system, but business intelligence showed poor demand predictions (stock-outs of popular products, warehouse space wasted on unpopular ones). It builds its own system with better predictions that competitors "stuck" with the generic one cannot match. Real-life textbook case: Amazon reinvented its physical infrastructure management and turned it into AWS.
Supporting to generic A marketing vendor and contract management system, simple CRUD. Years later an open source contract management tool arrives with more features (OCR, full-text search) that were always low priority on the backlog. BuyIT drops its own and integrates the open source one.
Supporting to core The company finds a way to optimise the supporting logic to cut costs or earn more. Symptom: increasing complexity of the business logic. If extra complexity does not affect profit it is accidental business complexity; if it enhances profitability, the subdomain is becoming core.
Core to supporting The complexity is not justified (not profitable); the organisation cuts it to the minimum logic that supports other subdomains.
Generic to supporting The integration cost of the open source solution does not justify the benefits, so BuyIT goes back to its in-house system: generic became supporting.

Strategic design concerns

  • A subdomain type change directly affects its bounded context and strategic decisions (chapter 4): cores protect their models with anticorruption layers and protect consumers with published languages (OHS).
  • Separate ways
    • is acceptable for supporting and generic subdomains
    • If the subdomain becomes core, duplicating it across teams is unacceptable: teams must integrate, and a customer-supplier relationship fits since only one team implements a core.
  • Implementation strategy:
    • supporting can be outsourced or used as "training wheels" for new hires
    • core must be in-house, close to the sources of domain knowledge. When supporting turns core, bring it in-house
    • when core turns supporting, you can outsource to free R&D for the cores.

Tactical design concerns

  • The main indicator is the inability of the existing technical design to support current business needs
    • Supporting subdomains use transaction script or active record, which fit complex rules and invariants badly
    • As rules accumulate, adding features gets painful: use the pain as a call to reassess the domain and design.
  • Changing the implementation strategy is normal:
    • you cannot foresee how a business evolves, and applying the most elaborate patterns everywhere is wasteful
    • If decisions were conscious, migrating between patterns is not that troublesome.

Transaction script to active record

  • Both are procedural scripts
    • active record adds structures that encapsulate mapping to storage. When data handling gets hard, find complicated data structures and encapsulate them as active records instead of direct database access.

Active record to domain model

  • When logic over active records gets complex and you see inconsistencies and duplication:
    1. Identify value objects (immutable structures), and move their related logic into them.
    2. Look for transactional boundaries. Make setters private so only the object modifies its state; the compilation errors reveal where external components control state. Refactor that logic inside.
    3. Look at hierarchies needing strongly consistent rule checks: candidate aggregates. Find the smallest transaction boundaries (smallest data to keep consistent), decompose along them, reference external aggregates by ID only.
    4. For each aggregate identify the root and make the other internal methods private.
// Before: Player and ApplyBonus (external logic changes the state)
public class Player
{
    public Guid Id { get; set; }
    public int Points { get; set; }
}

public class ApplyBonus
{
    public void Execute(Guid playerId, byte percentage)
    {
        var player = _repository.Load(playerId);
        player.Points *= 1 + percentage / 100.0;
        _repository.Save(player);
    }
}

// Step 1: private setters (this will not compile; the errors show who mutates state)
public class Player
{
    public Guid Id { get; private set; }
    public int Points { get; private set; }
}

// Step 2: the logic moves inside the object
public class Player
{
    public Guid Id { get; private set; }
    public int Points { get; private set; }

    public void ApplyBonus(int percentage)
    {
        this.Points *= 1 + percentage / 100.0;
    }
}

Domain model to event-sourced domain model

  • With sound aggregate boundaries, model the domain events that represent each aggregate's lifecycle
    • The hard part: the history of existing aggregates: migrating "timeless" state
    • The fine-grained history is gone, so either generate past events on a best-effort basis or model migration events.

Modelling migration events

  • Acknowledge the missing knowledge explicitly with a migration event that initialises each stream:
{
    "lead-id": 12,
    "event-id": 0,
    "event-type": "migrated-from-legacy",
    "first-name": "Shauna",
    "last-name": "Mercia",
    "phone-number": "555-4753",
    "status": "converted",
    "last-contacted-on": "2020-05-27T12:02:12.51Z",
    "order-placed-on": "2020-05-27T12:02:12.51Z",
    "converted-on": "2020-05-27T12:38:44.12Z",
    "followup-on": null
}
  • Advantage: no one can assume the stream holds every past event. Disadvantage: legacy traces remain forever; with CQRS projections must always handle migration events.

Organisational changes

  • Team structure changes communication and thus integration
    • A growing development centre (Figure 11-2): since one team owns a context, new teams can force a wide context to split into narrower ones.
  • Development centres in different places: shifting work may hurt collaboration, so integration evolves:
    • Partnership to customer-supplier: partnership assumes strong communication; moving a context to a distant centre erodes it.
    • Customer-supplier to separate ways: with severe communication problems (distance or politics) integration issues multiply, and at some point duplicating functionality is cheaper than "chasing one another's tails".

Domain knowledge

  • DDD's core tenet: domain knowledge is essential, and hardest to get for core subdomains (complex, changing). Modelling is ongoing; models improve with knowledge.
  • Complexity is often implicit:
    • initial simplicity is deceptive
    • edge cases, invariants and rules appear, sometimes forcing a rebuild from the ground up, including context boundaries and aggregates.
  • Strategic heuristic:
    • design boundaries according to the level of domain knowledge. Where logic is unclear and changing, use broader boundaries
    • as knowledge stabilises, decompose into narrower contexts or microservices (chapter 14).
  • Use new knowledge to make the design more resilient
    • But knowledge can be lost: stale documentation, departing designers, ad hoc additions until the codebase is a legacy system
    • Prevent it proactively; an effective recovery tool is the EventStorming workshop (next chapter).

Growth

  • Growth shows a healthy system, but its dark side is the big ball of mud:

"A big ball of mud is a haphazardly structured, sprawling, sloppy, duct-tape-and-baling-wire, spaghetti-code jungle. These systems show unmistakable signs of unregulated growth, and repeated, expedient repair." Brian Foote and Joseph Yoder (PLoP '97).

  • It results from extending functionality without re-evaluating design decisions
    • Growth blows up boundaries, and many DDD tools are about boundaries: subdomains (business building blocks), bounded contexts (models), value objects (immutability), aggregates (consistency).
  • Principle:
    • identify and eliminate accidental complexity (from outdated design decisions) and manage essential complexity (inherent in the domain) with DDD
    • Follow the DDD order: subdomains, then contexts, then aggregates.

Subdomains

  • Aim for useful boundaries, not perfect ones
    • Growth blurs them, so revisit using the coherent use cases heuristic (use cases working on the same data) to see where to split a subdomain (Figure 11-3).
  • Finding finer subdomains of different types is an important insight for managing essential complexity
    • Especially for core subdomains: distil them as much as possible so effort goes where strategy matters.

Bounded contexts

  • Over time contexts lose focus and accumulate logic for different problems (accidental complexity). Revisit boundaries and look to extract laser-focused contexts.
  • Growth can expose design problems: contexts becoming "chatty", unable to finish an operation without calling another, signal an ineffective model: redesign boundaries to give contexts more autonomy.

Aggregates

  • Principle:
    • keep aggregates as small as possible, with only what the business requires to be strongly consistent. It is "convenient" to distribute new features among existing aggregates
    • data that need not be strongly consistent for all the logic is accidental complexity.
  • Extracting functionality into a dedicated aggregate simplifies the original and perhaps the whole context, and often reveals a hidden model that should become its own bounded context.

Conclusion

  • "The only constant in life is change" (Heraclitus). Treat change as first-class in design.
  • Keep decisions aligned with the current domain and subdomains; act on organisational change in integration; keep using new domain knowledge; manage growth:
    • expand a subdomain: look for finer-grained subdomains;
    • do not let a context become a "jack of all trades";
    • keep aggregates as small as possible (use strongly consistent data as the test).
  • Continuously check boundaries for growth-driven complexity; remove accidental complexity and use DDD for the essential.

Exercises

  1. Organisational growth often causes which integration change? Partnership to customer-supplier / anticorruption layer to open-host service / conformist to shared kernel / open-host service to shared kernel.
  2. Integration moves from conformist to separate ways; what can you deduce (select all)? The teams struggled to cooperate / the duplicated functionality is supporting or generic / it is a core subdomain.
  3. Indicators that a supporting subdomain should become core (select all): easier to evolve the model / painful to evolve the model / changes at a higher frequency.
  4. A new business opportunity causes (select all): supporting to core / supporting to generic / generic to core / generic to supporting.
  5. What strategy change could turn one of WolfDesk's generic subdomains into core? Managed fraud service / building its own compute platform, like Amazon / outsourced agents.
Answers (book appendix B)
  1. A: partnership to customer-supplier (teams find ad hoc integration harder as the organisation grows).
  2. A and B: teams struggled to cooperate (duplication is cheaper than collaboration), and separate ways suits supporting and generic subdomains.
  3. B and C: a supporting subdomain turning core makes new requirements harder and more frequent.
  4. A and C: supporting or generic turning core implies increased advantage: a new business opportunity.
  5. B: new data centres around the world would take considerable effort and give an advantage over rivals.

Summary points

  • Re-check subdomain types, team structure, domain knowledge and growth regularly.
  • Pain in the design is the signal to migrate patterns step by step.
  • For events from legacy state: generate past events (testable, lossy) or migration event (honest, permanent).
Terms to carry forward
  • Subdomain morphing: change of type over time.
  • Accidental versus essential complexity: from outdated design versus inherent to the domain.
  • Migration event: single event initialising a stream from legacy state.
  • Chatty contexts: sign of ineffective boundaries.
  • Big ball of mud: unregulated growth.
