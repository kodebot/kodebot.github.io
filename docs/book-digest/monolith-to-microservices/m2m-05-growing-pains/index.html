Monolith to Microservices 5: Growing Pains

Source: Sam Newman, Monolith to Microservices (O'Reilly, 2019), chapter 5. Previous: Monolith to Microservices 4: Decomposing the Database. Next: Monolith to Microservices 6: Closing Words.

Takeaways
  • Different problems appear at ten services than at hundreds. Think of microservices as turning a dial, not flipping a switch: each turn brings new pain points that need new skills, techniques or tools.
  • Ten pains: ownership at scale, breaking changes, reporting, monitoring and troubleshooting, local developer experience, running too many things, end-to-end testing, global versus local optimisation, robustness and resiliency, orphaned services.
  • Do first: log aggregation (before you start), then correlation IDs, tracing and synthetic transactions; stop accidental breaking changes; give reporting its own database.
  • Use strong ownership at scale, consumer-driven contracts and progressive delivery instead of huge end-to-end suites, and a service registry against orphans.
  • Do not fix problems you will never have: build feedback mechanisms and watch for the warning signs.

5.1 More services, more pain

  • When problems appear depends on service interaction complexity, organisation size, number of services, technology, latency and uptime needs
    • "Services" means logical services (each may run as several instances).
  • Figure 5-1 maps the pains against service growth ("deeply unscientific", anecdotal)
    • A more coupled architecture brings robustness, testing and tracing problems earlier
    • Use the map as an indicator and build feedback mechanisms to look for the signs.

5.2 Ownership at scale

  • Types of ownership (Martin Fowler's, applied to services; about making code changes, not deployments or support):
Type Meaning
Strong every service has owners; outsiders submit changes (a pull request) and owners decide
Weak most services have owners but anyone can change anything directly, expecting to talk to the owner first
Collective no one owns anything; anyone changes anything
  • Signs:
    • collective ownership at scale
    • A fintech grew from 30 to 40 developers to over 100 with no ownership ("people know what is right"), ending with no clear architecture vision and a tangled distributed monolith, nicknamed "colander architecture" (people punched holes by exposing data or making point-to-point calls)
    • Detangling a distributed monolith costs far more than a monolith.
  • When: about 20 co-located developers can use collective ownership. It needs time for consensus, which fast hiring or distribution destroys.
  • Solution:
    • strong code ownership is almost universal in large multi-team microservice organisations (over about 100 developers)
    • Each team practises collective ownership locally and sets its own rules for a good change
    • It also supports product-oriented, domain-focused teams with embedded product owners.

5.3 Breaking changes

  • A service's contract is not just the data returned but the expected behaviour, explicit or not. Independent deployability needs you not to break consumers.
  • Signs:
    • production outages from new versions breaking compatibility (catastrophic without fast rollback; usually visible quickly unless the changed part is rarely used)
    • people orchestrating lock-step releases (occasionally fine within a team, a problem if common).
  • When: a fairly early pain, especially when more than one team is involved; within a team developers know both sides.
  • Newman's rules ("Don't break contracts. See rule 1." and then the real ones):
    1. Eliminate accidental breaking changes. An explicit schema detects structural breaks quickly (a method that took two integers now takes one) and makes developers pause; protolock forbids incompatible protocol buffer changes. Schema-less JSON is the default and explicit JSON schemas are rarely used; developers curse formal schemas until they have faced breakage, and typed formats can also deserialise faster. Semantic breaks (a method that adds now multiplies) are best caught by tests. Make contract changes obvious: avoid technology that magically serialises data or generates schemas from code. Making a contract hard to change beats constantly breaking consumers.
    2. Think twice before a breaking change. Prefer expansion changes (add methods, resources or topics; keep the old).
    3. Give consumers time to migrate. Two ways: run two versions of the service (Figure 5-2; more infrastructure, data compatibility, bug fixes in both so branching; only for short periods) or, preferred, one version supporting both contracts (Figure 5-3, for example two APIs on different ports; more complexity inside the service but no coexisting versions). Some teams still support three or more old contracts years later because external consumers cannot change. A lock-step release is possible within one team but should not be a habit.
  • Changes are easier inside a team; breaking APIs exposed to third parties is painful. Treat consumers like customers and keep on good terms.
Get this sorted, fast

Organisations with growing numbers of microservices eventually nearly eliminate accidental breaks and manage purposeful ones, or the impact makes the architecture untenable. Small microservice organisations that do not sort this out will probably not last to become large ones.

5.4 Reporting

  • A monolith's single database is a ready-made schema for stakeholders' reports (maybe on a read replica; Figure 5-4)
    • With microservices the data is spread over isolated schemas, so cross-data reporting is harder.
  • When:
    • it bites early, often discovered halfway through because reporting is outside normal software development ("out of sight, out of mind")
    • If you already report from a data warehouse or lake, just have the services copy data to it.
  • Solution:
    • stakeholders have SQL tool chains tied to the old schema, so provide a single database for reporting, separated from the services' databases and designed for reporting (possibly matching the old schema to limit impact)
    • Services push data into it (Figure 5-5) using Chapter 4 techniques: change data capture, views across schemas, programmatic copying in the services, or intermediaries listening to events
    • See Chapter 5 of Building Microservices.

5.5 Monitoring and troubleshooting

  • The epigraph (from the Honest Status Page account): "We replaced our monolith with microservices so that every outage could be more like a murder mystery."
  • A monolith is mostly all up or all down
    • with tens or hundreds of processes you must detect a single failing instance, and decide whether one process at 100% CPU merits waking someone at 3 a.m.
  • When:
    • hard to predict; perhaps the first production failure, a couple of services, or 20 or more
    • Signs: unexplained production issues, alerts when the system seems healthy, difficulty answering "is everything OK?"
    • Prioritise basic improvements ahead of time.
  • Log aggregation:
    • forward all logs to a central searchable place (ELK stack: Elasticsearch, Logstash or Fluentd, Kibana; Newman's favourite is Humio)
    • some can alert. Do this first, before implementing a microservice architecture: it is useful immediately and a test of whether your organisation can change operations
    • if it struggles, microservices are probably a step too far.
  • Tracing:
    • Generate a correlation ID for every inbound call (ideally by an API gateway or service mesh), pass it on (HTTP header or message field), and log with it in a standard place so you can query all logs for one chain (Figure 5-6)
      • Correlation IDs also help manage sagas.
    • Log aggregation batches logs, so it cannot give accurate timing: use a distributed tracing system such as Jaeger (Figure 5-7)
      • The more latency sensitive you are, the sooner
      • If correlation IDs are in place you already have the hooks; a service mesh can handle inbound and outbound tracing, though not inside services.
  • Test in production:
    • keep getting feedback after deployment, as later changes can break things
    • Synthetic transactions inject fake user behaviour and alert on deviation
    • At Atomist a scripted fake-customer enrolment (authorising GitHub and Slack) caught problems such as GitHub rate limits before real users did
      • accounts were controlled and cleaned up afterwards
    • Start from existing end-to-end tests reworked for production, but beware side effects (a company accidentally ordered 200 washing machines to its head office).
  • Toward observability:
    • traditional monitoring handles known causes (disk space, an unresponsive instance, a latency spike)
      • Complex systems fail in ways you cannot predict, so gather lots of information (tracing, logs) and be able to ask open-ended questions after the fact
    • expect to be surprised
    • use toolchains that allow ad hoc queries. Recommended: Cindy Sridharan, Distributed Systems Observability (O'Reilly, 2018).

5.6 Local developer experience

  • With many services, running them all locally stops scaling (four or five JVM services on a laptop, not twenty)
    • Signs: slower local builds and runs, requests for bigger machines (only buys time).
  • When:
    • depends on the number and footprint of services (Go, Node or Python may go further than the JVM). Teams with collective ownership of several services suffer more
    • teams with strong ownership of few focus on their own and stub the rest.
  • Solutions:
    • stub the services you do not run, or point at instances elsewhere
    • A fully remote setup brings connectivity needs, slower feedback and resource cost
    • Telepresence gives a hybrid local and remote workflow for Kubernetes; Azure's cloud functions can run locally against remote resources
    • Watch developer experience as the count grows, with feedback mechanisms and continued investment.

5.7 Running too many things

  • More services and instances mean more to deploy, configure and manage. Desired state management (specify how many instances where, and keep it so) becomes essential
    • manual processes and traditional configuration tools (Chef, Puppet) strain. Signs: growing time on deployments and their troubleshooting
    • more operations staff
    • mistakes from manual steps. It is a matter of scale.
  • Solutions:
    • high automation with developer self-service provisioning and automatic desired-state management
      • Kubernetes is the tool of choice (needs containers) but is not developer-friendly alone
    • higher-level abstractions are emerging (larger organisations often use packaged versions such as Red Hat OpenShift)
    • public clouds offer managed Kubernetes. Newman likes Function-as-a-Service (serverless) and is serverless-first on a public cloud, using other options only when it does not fit.
Do not reach for Kubernetes too early

It is not a prerequisite. Wait until you have enough processes that your current approach strains; five microservices may be fine with what you have. Do not adopt it just because everyone else does (the same as microservices).

5.8 End-to-end testing

  • Wider test scope gives more confidence but slower runs and harder diagnosis
    • With microservices the scope is huge: many services deployed and configured, plus false negatives from environment problems (dying instances, time-outs).
  • Signs:
    • the suite grows (teams unsure what is covered add scenarios "just in case"), failures not pointing to code issues (people re-run), time growing, pressure for more testers or a separate test team
    • When: it sneaks up, worst with cross-team user journeys.
  • Solutions:
    • Limit the scope of tests spanning services and keep them inside one team.
    • Consumer-driven contracts
      • (the consumer writes an executable specification the provider must pass; Pact) in place of cross-service tests
      • some teams have huge success, others struggle
      • Newman calls it a poorly underused practice.
    • Automated release remediation and progressive delivery:
      • roll out in stages (canary), define thresholds such as 95th percentile latency and error rates, continue only if met, otherwise roll back automatically (Netflix built Spinnaker). Not a replacement for testing but a place to spend effort
      • even manually controlled progressive delivery is a big step up.
    • Continually refine quality feedback cycles: people with context should add tests where defects rise and also remove tests that duplicate coverage, balancing fast feedback with safety.

5.9 Global versus local optimisation

  • Teams with local decision-making can each choose sensibly yet collectively inefficiently: Invoicing picks Oracle, Notifications MongoDB, Fulfillment PostgreSQL
    • Do you want skills and licences for three similar databases?
  • Signs:
    • discovering by accident (a lunch comment) that several teams solved the same problem differently. REA (Australian real estate) found many ways to deploy
    • moving between teams was hard and duplicated effort justified a common approach. When: over time in multi-team organisations with freedom, often after rapid scaling
    • collective ownership forces consistency (if you want it, you must solve this).
  • Solutions:
    • the irreversible and reversible decisions spectrum (Figure 5-8, from Chapter 2): the higher the cost of change, the broader the consensus
      • teams need to understand the bigger picture and have a network to raise issues
    • A technical cross-cutting group with a technical leader from each team (chaired by the CTO or chief architect) works both ways
    • An informal option is Monzo's "proposals": free-form documents published to a shared space with a Slack alert, open to change
    • Balance autonomy against consistency and keep gathering information to adjust it.

5.10 Robustness and resiliency

  • Packets get lost, calls time out, machines die; rare events become common as services multiply
    • They mostly appear in production
    • When: as services and calls grow, with cascading failures and back pressure more likely when interconnected.
  • Solutions:
    • for each call ask how it might fail and what to do if it does
    • isolate services (asynchronous communication avoids temporal coupling)
    • sensible time-outs and circuit breakers to fail fast and avoid back pressure
    • multiple copies and desired state management for dying instances
      • Resiliency is a way of working: document production issues and what you learned so they do not recur
      • Further reading: Building Microservices chapter 11 and Release It! (Michael Nygard, Pragmatic Bookshelf, 2018).

5.11 Orphaned services

  • Many organisations still struggle to know what they have, where it is and who owns it
    • Stable services running for years unchanged are what independent deployability promises, but if no one owns them they are orphaned
      • people fear changing them (like servers found walled up in old offices) and some teams could not find the source code
    • When: after long use, when collective memory fades.
  • Solutions:
    • a hypothesis, untested: collective ownership may reduce it (mechanisms to move between services, limited technology choice, common tooling), unless practices changed since the service was last touched
    • In-house service registries crawl source repositories for metadata files, merged with service discovery data (Consul, etcd)
    • The Financial Times Biz Ops tool (Figure 5-9; several hundred services; a graph database also covering networks and file servers) computes a System Operability Score (Figure 5-10: registry information supplied, health checks present)
    • Then bring orphans in line: assign to a team (strong ownership) or raise work items (collective).

Summary points

  • Watch for these pains and build feedback to see them, but do not solve problems you will never have.
  • Early moves: log aggregation, correlation IDs, contract discipline, a reporting database.
  • Later: ownership, platform, testing strategy, cross-team governance, registries.
