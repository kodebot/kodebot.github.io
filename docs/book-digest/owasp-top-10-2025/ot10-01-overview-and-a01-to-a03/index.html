OWASP Top 10:2025 1: Overview and A01 to A03

Source: OWASP Foundation, "OWASP Top 10:2025" (owasp.org/Top10/2025), the introduction and categories A01 to A03. The owasp.org page footer states a Creative Commons Attribution 3.0 Unported licence. Own-words summary, much shorter than the source. Next: OWASP Top 10:2025 2: A04 to A06.

Takeaways
  • The Top 10 is an awareness document ranked from contributed testing data plus a community survey, grouping many weaknesses (CWEs) into root-cause categories.
  • 2025 changes: two new categories (A03 Software Supply Chain Failures, A10 Mishandling of Exceptional Conditions) and one consolidation (SSRF folded into A01).
  • Broken access control is still number one: every application tested had some form of it.
  • Misconfiguration jumped to #2; supply chain failures have the fewest recorded occurrences but the highest average exploit and impact scores.

1.1 How the list is built

  • Data-informed, not blindly data-driven:
    • 12 categories ranked from contributed data
    • two more promoted from a community survey, because test data looks at the past and tools take years to detect new risks.
  • Prevalence, not frequency: it counts how many applications have at least one instance of a weakness, not how many instances (manual testers report a flaw once, scanners report every instance).
  • Root cause over symptom
    • where possible, with CWEs capped at 40 per category (A01 has 40; A03 and A09 have 5)
    • The 2025 data had 589 CWEs to analyse (about 30 in 2017, almost 400 in 2021).
  • Why categories instead of a top 10 CWE list: not every CWE exists in every language or framework, and common vulnerabilities (injection, cross-site scripting, hard-coded passwords) have several CWEs.

1.2 A01:2025 Broken Access Control (#1)

  • What:
    • access control makes sure users cannot act outside their intended permissions. 100% of tested applications had some form of it
    • the category has the most occurrences in the data. SSRF (CWE-918) is now part of it.
  • Typical failures:
    • Not denying by default (least privilege).
    • Bypassing checks by changing a URL, parameter or request (force browsing, parameter tampering).
    • Insecure direct object references: viewing or editing another account by changing its identifier.
    • APIs missing checks on POST, PUT and DELETE.
    • Elevation of privilege; tampered or replayed tokens (for example a JWT) or cookies.
    • CORS misconfiguration letting untrusted origins call the API.
  • Prevent:
    • Enforce access control in trusted server-side code only; deny by default except for public resources.
    • Implement it once and reuse it; enforce record ownership in the model; keep business limits in domain models.
    • Remove directory listing, .git folders and backups from web roots.
    • Log failures and alert on repeats; rate-limit APIs.
    • Invalidate server sessions on logout; keep stateless JWTs short-lived and use refresh tokens with OAuth revocation if longer.
    • Test access control in unit and integration tests.
  • Example: an application that hides the admin page in front-end JavaScript only is still open to a direct command-line request to the URL.

1.3 A02:2025 Security Misconfiguration (#2, up from #5)

  • What:
    • a system, application or cloud service is set up insecurely
    • Every tested application showed some misconfiguration, and the trend grows as more behaviour moves into configuration
    • XML external entity (XXE) handling is a notable CWE.
  • You may be vulnerable if:
    • hardening is missing anywhere in the stack
    • unnecessary ports, services, accounts or sample apps are enabled
    • default accounts keep default passwords
    • error pages show stack traces
    • security headers are absent or weak
    • backward compatibility overrides secure settings
    • cloud storage permissions are open.
  • Prevent:
    • A repeatable, automated hardening process; dev, QA and production configured alike with different credentials.
    • A minimal platform without unused features, components or samples.
    • Review configuration with each patch cycle, including cloud storage permissions.
    • Segmentation (containers, security groups); security headers; a central error handler as a backstop.
    • Automated verification of settings in every environment (manual at least yearly if not automated).
    • Federation, short-lived credentials or platform roles instead of static keys in code, configs or pipelines.
  • Examples:
    • a sample admin console left on the server with default credentials
    • directory listing exposing compiled classes that reveal a flaw
    • a cloud provider default that shares storage openly.

1.4 A03:2025 Software Supply Chain Failures (#3, new scope)

  • What:
    • breakdowns or compromises in building, distributing or updating software, often through vulnerable or malicious third-party code, tools or dependencies
    • It expands "vulnerable and outdated components" to the whole ecosystem of dependencies, build systems and distribution
    • Half of the survey respondents ranked it first
    • Few CVEs map to it, but it has the highest average incidence rate (5.19%, as reported) and the highest average exploit and impact scores.
  • You are likely vulnerable if you do not track versions of every component (including transitive ones), run unsupported software, skip regular scanning, lack change tracking across your supply chain (IDEs and extensions, repositories, registries, build artefacts), have not hardened each part, have no separation of duties, use untrusted sources, patch slowly (monthly or quarterly under change control), or run a CI/CD pipeline weaker than what it deploys.
  • Prevent:
    • A patch management process and a central SBOM (software bill of materials) covering transitive dependencies.
    • Remove unused dependencies and features; continuously inventory versions (OWASP Dependency-Track, Dependency-Check, retire.js) and watch CVE, NVD and OSV.
    • Get components only from trusted sources over secure links; prefer signed packages; choose versions deliberately; replace unmaintained libraries or use a virtual patch.
    • Roll out updates in stages or as canaries in case a trusted vendor is compromised.
    • Track changes to CI/CD settings, repositories, sandboxes, IDEs, SBOM tooling, logging, SaaS integrations, artefact repositories and container registries.
    • Harden each system with MFA and locked-down IAM: the code repository (no secrets, protected branches), developer workstations, build servers (separation of duties, signed builds, environment-scoped secrets, tamper-evident logs), artefacts (provenance, signing, time stamps, promote rather than rebuild, immutable builds) and infrastructure as code.

Summary points

  • Access control belongs on the server, deny by default.
  • Harden and verify configuration automatically.
  • Treat the supply chain, including your own pipeline, as part of the attack surface.
Terms to carry forward
  • CWE: Common Weakness Enumeration, a catalogue of weakness types.
  • SSRF: server-side request forgery.
  • SBOM: software bill of materials.
  • IDOR: insecure direct object reference.
  • Transitive dependency: a dependency of a dependency.
