OWASP Top 10:2025 3: A07 to A10

Source: OWASP Foundation, "OWASP Top 10:2025" (owasp.org/Top10/2025), categories A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures and A10 Mishandling of Exceptional Conditions; the owasp.org page footer states a Creative Commons Attribution 3.0 Unported licence. Own-words summary. Previous: OWASP Top 10:2025 2: A04 to A06.

Takeaways
  • Authentication failures: stop credential stuffing and weak passwords with MFA, breached-password checks, no defaults, safe sessions; use a trusted authentication system.
  • Integrity failures: verify signatures on software, updates and serialised data; secure the pipeline.
  • Logging and alerting failures: logging without alerting is of minimal value; log security events, protect the logs, alert and rehearse the response.
  • Mishandling of exceptional conditions (new): handle errors where they occur, fail closed, roll back whole transactions, and limit resources.

3.1 A07:2025 Authentication Failures (#7)

  • What:
    • an attacker tricks the system into accepting an invalid user
    • Standard authentication frameworks seem to be helping, but the rank is unchanged
    • Notable CWEs: hard-coded passwords and credentials, improper authentication, session fixation, improper certificate validation.
  • Weak spots:
    • Credential stuffing (breached username and password lists) and password spraying with predictable variants (Password1!, Password2!...); brute force not blocked.
    • Default, weak or well-known passwords; accepting already-breached passwords.
    • Knowledge-based recovery questions, which cannot be made safe.
    • Plain text, encrypted or weakly hashed password stores.
    • Missing or ineffective MFA and weak fallbacks.
    • Session identifiers exposed in URLs or hidden fields, reused after login, or not invalidated at logout or idle time.
    • Not checking the scope and audience of credentials.
  • Prevent:
    • Enforce MFA; encourage password managers; ship no default credentials.
    • Check new passwords against the worst-passwords list and breached-credential lists (for example haveibeenpwned.com).
    • Follow NIST 800-63b section 5.1.1 for memorised secrets; do not force periodic rotation unless a breach is suspected, then reset immediately.
    • Use the same message for every outcome to resist account enumeration ("Invalid username or password").
    • Delay or limit failed attempts without creating a denial-of-service; log failures and alert.
    • Use a server-side session manager that issues a new high-entropy ID after login, keeps it in a secure cookie not the URL, and invalidates it on logout, idle and absolute timeouts.
    • Prefer a well-tested authentication system over building your own; for JWTs validate aud, iss and scopes.

3.2 A08:2025 Software or Data Integrity Failures (#8)

  • What:
    • code and infrastructure treat untrusted code or data as trusted
    • It works at a lower level than the supply-chain category: trust boundaries and integrity of software, code and data artefacts.
  • Examples:
    • plugins, libraries or modules from untrusted sources, repositories or CDNs
    • a CI/CD pipeline that pulls code or artefacts without verifying a signature
    • auto-update that downloads updates without integrity checks, so an attacker could push their own update to every installation
    • insecure deserialisation of data an attacker can see and modify.
  • Prevent:
    • Digital signatures to verify source and integrity.
    • Consume only trusted repositories (an internal vetted repository for higher risk).
    • Review code and configuration changes; segregate and control access in CI/CD.
    • Never use unsigned or unencrypted serialised data from untrusted clients without an integrity check or signature, to detect tampering and replay.

3.3 A09:2025 Security Logging and Alerting Failures (#9)

  • What:
    • without logging and monitoring, attacks cannot be detected; without alerting, response is slow
    • The word "alerting" was added to stress action on logs
    • The category is hard to test and always under-represented in data (723 CVEs), but voted up by the community three times.
  • Problems:
    • logins, failed logins and high-value transactions not logged (or only successes)
    • unclear or missing warnings
    • unprotected log integrity
    • logs not monitored or only stored locally
    • no alert thresholds or escalation
    • scans by tools such as Burp or ZAP do not trigger alerts
    • no near-real-time detection
    • log data visible to users or attackers, or containing personal or health data
    • log injection through unencoded data
    • missing error handling so a problem is never logged
    • outdated alert use cases.
  • Prevent:
    • Log login, access control and server-side validation failures with enough user context and retain them long enough for forensics
      • log every security control, success or failure, in a format log tools can consume.
    • Encode log data to prevent injection into logging systems.
    • Give transactions an audit trail with integrity controls (for example append-only tables); roll back errors and fail closed.
    • Alert on suspicious behaviour
      • build use cases and playbooks with a security operations team
      • add honeytokens (fake users or data) so any access gives a near-false-positive-free alert
      • optionally use behaviour analysis.
    • Adopt an incident response plan such as NIST 800-61r2 or later and teach developers what attacks look like.

3.4 A10:2025 Mishandling of Exceptional Conditions (new)

  • What:
    • programs fail to prevent, detect or respond to unusual situations (24 CWEs: improper error handling, logic errors, failing open and related cases)
    • Causes include poor input validation, error handling placed late and high up instead of where the error occurs, unexpected memory, privilege or network states, inconsistent or missing exception handling
    • "Any time an application is unsure of its next instruction" an exceptional condition has been mishandled.
  • Consequences: logic bugs, overflows, race conditions, fraudulent transactions, and state, resource, timing, authentication or authorisation problems, which hit confidentiality, integrity and availability.
  • Prevent:
    • Expect the worst: catch errors where they occur and do something meaningful: tell the user clearly, log, and alert if warranted; keep a global exception handler as a backstop.
    • Watch for repeated errors that may indicate an attack.
    • Roll back every part of a failed transaction and restart (fail closed); recovering half-way often creates unrecoverable mistakes.
    • Apply rate limits, quotas and throttling; "nothing in information technology should be limitless" (lack of limits causes resilience problems, brute-force success and large cloud bills).
    • Consider reporting identical repeated errors as statistics, without disturbing automated monitoring.

Summary points

  • MFA plus breached-password checks plus a trusted session manager beat custom authentication.
  • Verify what you run, update and deserialise.
  • Alerts, not just logs; failed operations must fail closed.
Terms to carry forward
  • Credential stuffing / password spraying: reusing breached credentials, or trying variants of them.
  • Account enumeration: learning which accounts exist from differing messages.
  • Insecure deserialisation: rebuilding objects from attacker-controlled data.
  • Honeytoken: a decoy credential or record that alerts when touched.
  • Fail closed: on error, deny and roll back.
