Podman for DevOps 2: Comparing Podman and Docker

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 2. Previous: Podman for DevOps 1: Introduction to container technology. Next: Podman for DevOps 3: Running the first container.

Takeaways
  • Docker is daemon-centric: the CLI and REST API talk to a long-running dockerd, which uses containerd and runc. If the daemon stops, containers suffer.
  • Podman is daemonless: the podman binary is both CLI and engine, using fork/exec. Conmon (one small monitor per container) sits between Podman and the OCI runtime, so containers survive after Podman exits.
  • Podman is built from community libraries: libpod, containers/image, containers/storage, Buildah, Netavark, Conmon, and the crun or runc runtimes.
  • Rootless containers use a user namespace with a UID map; the CLI is Docker-compatible (alias docker=podman).
  • Podman adds pods and Kubernetes or systemd generation; both tools use OCI images and runtimes.

The chapter compares the two engines architecturally and by usage. If you have little Docker experience you can skip it and come back later. No setup is needed; to replay the examples you need Podman (installed in chapter 3) and Docker.

2.1 Docker container daemon architecture

  • Docker appeared in 2013. It used LXC as its runtime, then replaced it with its own libcontainer.
  • Three pillars: the Docker daemon, the REST API and the CLI (Figure 2.1: client or remote API in, daemon out to registries and containers).
  • The daemon is the most critical piece and must always run; "otherwise, your beloved containers will not survive for long".

The Docker daemon

A daemon is a background process providing services. The Docker daemon:

  • listens for Docker API requests
  • handles, manages and checks running containers
  • manages images, networks and storage volumes
  • interacts with external or remote registries

Interacting with the daemon

  • Through the Unix socket /var/run/docker.sock. Depending on the distribution, give non-root users permission or add them to the docker group. Permissions on Fedora 40:
# ls -la /var/run/docker.sock
srw-rw----. 1 root docker 0 Aug 25 12:48 /var/run/docker.sock
  • No other authentication by default. Do not expose the daemon to untrusted networks: access to the socket is equivalent to passwordless root on the host.

The Docker REST API

Anything the CLI does is available: list, create, inspect, get logs, export, start or stop, kill, rename, pause containers. List cached images over the socket with curl:

# curl --unix-socket /var/run/docker.sock \
    http://localhost/v1.41/images/json | jq

Docker client commands

The CLI has over 30 commands. The most common:

Command Purpose
build build an image from a Dockerfile
cp copy files between container and local filesystem
exec run a command in a running container
images list images
inspect low-level information on Docker objects
kill, stop, start, restart, rm control containers
load, save load an image from or save it to a tar archive
login log in to a registry
logs fetch a container's logs
ps list running containers
pull, push pull from or push to a registry
rmi remove images
run run a command in a new container
create create a container without starting it
tag create a TARGET_IMAGE tag referring to SOURCE_IMAGE

The client instructs the daemon, so the daemon must be running before using the client or API.

Docker images

  • Docker's image format packages binary data and metadata as a template for containers. Since version 1.12 Docker adopted an image spec that evolved into the OCI Image Format Specification.
  • The first spec already had: a list of layers, creation date, operating system, CPU architecture, and configuration parameters for the runtime.
  • A layer is a set of filesystem changes; it holds no environment variables or default arguments (those live in the image manifest).
  • Layers are merged into one view, usually by a union filesystem; a running container gets a read/write ephemeral layer lost on destruction.

Docker registries

  • A registry holds image metadata and layers for many daemons. The daemon is an HTTP API client of the registry.
  • Docker Hub is the preconfigured default (SaaS by the Docker company). Quay.io is a free SaaS alternative hosted by Red Hat. An on-premises registry is one command:
$ docker run -d -p 5000:5000 --restart=always --name registry registry:2

More: https://docs.docker.com/registry/deploying/.

What a running Docker architecture looks like

  • The daemon (dockerd) is accompanied by containerd, which decouples container management (kernel interaction included) from the daemon, follows the OCI standard and uses runc (Figure 2.2).
# systemctl status docker
● docker.service - Docker Application Container Engine
   Active: active (running) since Tue 2024-09-03 20:01:46 UTC; 4min 0s ago
   Main PID: 3970 (dockerd)
   CGroup: /system.slice/docker.service
           └─3970 /usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock
  • containerd.service runs with one child, containerd-shim-runc-v2, matching Figure 2.2. docker ps then lists the container (the example runs centos/httpd-24-centos7:latest).
  • Chain: a container started through runc, managed by the containerd service, configured through the Docker daemon.

containerd architecture (Figures 2.3 and 2.4)

  • Two subsystems: the bundle service (extracts bundles from disk images) and the runtime service (executes bundles to create containers).
  • Modules linking subsystems:
Module Role
Executor implements the container runtime (the Runtimes block)
Supervisor monitors and reports container state
Snapshot manages filesystem snapshots
Events collects and consumes events
Metrics exports metrics through the metrics API
  • Flow: pull metadata and content through a distribution controller; unpack with the bundle controller into snapshots that compose bundles; run the bundle through the runtime controller.

2.2 Podman daemonless architecture

  • Podman = POD MANager: a daemonless engine managing containers, images, storage volumes and network resources. After installation there is no service to start.
  • The podman binary is both CLI and container engine that orchestrates the runtime.

Podman commands and REST API

Curated list: https://docs.podman.io/en/latest/Commands.html. Common commands (a Docker-compatible CLI):

Command Purpose
build build from a Containerfile or Dockerfile
cp, exec, events, images, inspect, kill, load, login, logs, ps, pull, push, restart, rm, rmi, run, save, start, stop, tag as in Docker
generate generate Kubernetes YAML or systemd units
pod manage pods
system disk usage, container migration, REST API services, storage management, pruning
unshare run a command in a modified user namespace
volume list, prune, create, inspect volumes
  • No daemon on a socket is needed. You can optionally run a Podman service on a Unix socket for the native REST API:
$ podman system service --time 0 unix://tmp/podman.sock
  • Default sockets: unix://run/podman/podman.sock for rootful services; unix://run/user/<UID>/podman/podman.sock for non-root.
$ curl --unix-socket /tmp/podman.sock \
    http://d/v3.0.0/libpod/images/json | jq .

OpenAPI docs: https://docs.podman.io/en/latest/_static/api.html. (jq pretty-prints the JSON.) The REST API and systemd socket activation return in chapter 3.

Podman building blocks

Podman follows open standards, relying on community projects:

Block Component
Container life cycle the libpod library (https://github.com/containers/podman/tree/main/libpod)
Container runtime OCI-compliant runtimes, crun and runc
Image management containers/image Go libraries, used by engines and registries (https://github.com/containers/container-libs/tree/main/image)
Storage containers/storage Go library: layers, images, volumes (https://github.com/containers/container-libs/tree/main/storage)
Image builds Buildah, a tool and library (https://github.com/containers/buildah)
Runtime monitoring Conmon, shared with CRI-O (https://github.com/containers/conmon)
Networking Netavark, Rust-based stack

Netavark: introduced in Podman 4.0 with CNI as the new default; CNI deprecated in 5.0. The default network uses the bridge driver; bridge, macvlan and ipvlan are supported; plugins via the plugin API (https://github.com/containers/netavark/blob/main/plugin-API.md).

The libpod library

Written in Go; the key to Podman's birth; implements the engine's high-level functions. Scope:

  • Image formats (OCI and Docker): authenticate, pull, store layers and metadata, build, push.
  • Container life cycle: create, run, stop, kill, resume, delete, exec in running containers, logging.
  • Containers and pods: pods are sandboxed container groups sharing namespaces (UTS, IPC, network, and optionally PID) and managed together.
  • Rootless containers and pods with no privilege escalation.
  • Resource isolation through cgroups, with CLI options for memory and CPU reservation or storage read/write rate limits.
  • A Docker-compatible CLI, and a Docker-compatible REST API on local Unix sockets (not enabled by default) covering everything the CLI does.

libpod calls runtimes, Conmon, containers/storage, containers/image, Buildah and Netavark.

The runc and crun OCI runtimes

  • The engine orchestrates; the runtime acts. Standard: the OCI Runtime Specification (https://github.com/opencontainers/runtime-spec; lifecycle doc: https://github.com/opencontainers/runtime-spec/blob/master/runtime.md).
  • runc (https://github.com/opencontainers/runc) is the most widely adopted; born 2015 when Docker spun out its plumbing. It includes libcontainer, a Go package that creates containers with namespaces, cgroups, capabilities and filesystem access controls (a former independent Docker project).
  • libcontainer bootstraps a container from namespace isolation to running the binary as PID 1. The runtime calls it to:
    • consume the mount point and metadata from Podman
    • start the isolated process using the clone() and unshare() syscalls
    • set up cgroup reservations
    • set up SELinux, seccomp and AppArmor rules
  • It also initialises namespaces and file descriptors, creates the rootFS and bind mounts, exports logs, manages seccomp, SELinux and AppArmor, and creates and maps users and groups.
  • Namespace creation happens in the nsexec() function of the nsenter package: C code embedded in Go through cgo (https://github.com/opencontainers/runc/blob/master/libcontainer/nsenter/nsexec.c). Interface methods: https://github.com/opencontainers/runc/blob/master/libcontainer/container_linux.go.
  • crun (https://github.com/containers/crun) is a fast, low-memory OCI runtime written in C, usable as a library. runc and crun are interchangeable; neither is for manual use.
crun advantage Detail
Smaller binary about 50 times smaller than runc
Faster quicker at instrumenting the container under the same conditions
Less memory under half of runc's; helps with massive deployments and IoT; allows very low limits (4 MB and possibly less)
  • Why crun became Podman's default on Fedora: Fedora 31 (2019) defaulted to cgroup v2 (https://www.redhat.com/sysadmin/fedora-31-control-group-v2); runc could not manage it yet; crun could (v1 and v2), so the switch was nearly seamless. runc gained support from v1.0.0-rc93. (Chapter 1 gave Fedora 33; the two chapters differ.)
  • Switch runtimes with a flag:
$ podman --runtime /usr/bin/runc run --rm fedora echo "Hello World"
$ podman --runtime /usr/bin/crun run --rm fedora echo "Hello World"
  • Both support eBPF (user-defined programs run in a sandbox VM in the kernel, no kernel recompile; used for networking, security, observability, tracing) and CRIU (Checkpoint Restore in Userspace: freeze a running container, save its state to disk, resume later).

Conmon

Which process launches the runtime, and what monitors the container? Conmon (https://github.com/containers/conmon) sits between the engine and the runtime; one instance per container. Order seen with a tracing tool (Figure 2.5):

  1. The engine runs Conmon, which detaches and daemonises itself.
  2. Conmon runs the runtime instance, which starts the container and exits.
  3. Conmon keeps running as the monitoring interface while the engine process has exited.

Three nginx containers show three Conmon processes:

# for i in {1..3}; do podman run -d --rm docker.io/library/nginx; done
# ps aux | grep conmon
root 4272 ... /usr/bin/conmon --api-version 1 -c 775cb306... -u 775cb306... -r /usr/bin/crun [..omitted output]
root 4341 ... /usr/bin/conmon --api-version 1 -c 5abde0da... -u 5abde0da... -r /usr/bin/crun [..omitted output]
root 4409 ... /usr/bin/conmon --api-version 1 -c 9cd5e446... -u 9cd5e446... -r /usr/bin/crun [..omitted output]
  • Even after Podman exits you can attach to the container through Conmon; Conmon sends logs to files or the systemd journal. It is lightweight, written in C, with Go bindings to pass config between manager and runtime. It acts as a small dedicated daemon for each container.

Rootless containers

  • Standard users run their own containers, with better isolation, and the fork/exec daemonless approach makes it easy:
$ podman run -d --rm docker.io/library/nginx
  • Podman creates a user namespace and maps UIDs with a uid_map file (see man user_namespaces), so container root maps to an ordinary host user.
  • Storage is under the user's home, usually $HOME/.local/share/containers/storage.
  • Networking for rootless containers differs from rootful; chapter 10 compares them.

OCI images

Podman and containers/image implement the OCI Image Format Specification (https://github.com/opencontainers/image-spec). An OCI image is:

  • a manifest
  • an optional image index
  • an image layout
  • one or more filesystem layer changeset archives
  • an image configuration document (layer order, arguments, environment)
  • a conversion document (how translation occurs)
  • an Artifacts Guidance document (packaging content other than images)
  • a named descriptor (type, metadata, content address)
Element What it is
Manifest content-addressable; image layers and config for one architecture and OS (Linux x86_64); https://github.com/opencontainers/image-spec/blob/main/manifest.md
Image index list of manifests for different architectures (amd64, arm64, 386) and OSes, with annotations; .../image-index.md
Image layout directory structure of blobs; locations of manifests, the image index (JSON) and configuration; index.json references the manifest blob; .../image-layout.md
Filesystem layers tar archives (gzip or zstd) applied in order as changesets; Podman uses overlayfs as its graph driver; .../layer.md
Image configuration layer composition and execution parameters (entry points, volumes, arguments, environment) plus metadata; immutable: changing it creates a derived image; .../config.md

2.3 The main differences between Docker and Podman

Docker Podman
Architecture daemon-centric daemonless: binary is CLI and engine, with Conmon orchestrating and monitoring the runtime
Default runtime runc crun in most distributions
Rootless added recently; was first in Podman first engine with it
Pods create a container, then attach others to its network namespace native pods: podman pod create, then podman run --pod
Kubernetes none built in podman generate kube makes Kubernetes YAML for a running container
systemd external podlet generates a systemd unit from a podman run command (as the book states it)
  • Runtime defaults by distribution: Fedora and RHEL 9: crun; the conservative RHEL 8: runc with crun optional; RHEL 10 ships only crun, considered stable and production-ready. The book skips a performance comparison.
  • CLI similarity: Docker was born 2013, Podman 2017 (4 years later). Podman kept the look and feel; early claims: alias docker=podman works for existing scripts, and a package places a fake docker under /usr/bin pointing to Podman. Docker-built images are OCI compatible. Table 2.1 compares commands (attach, build, commit, cp, create, diff, events, exec, export, history, images, import, info, inspect, kill, load, login, logs...) with Podman extras such as auto-update, container, generate, healthcheck, image, init.
  • Pod example:
$ podman pod create --name mypod
$ podman run --pod mypod -d docker.io/library/nginx
  • Real-world adoption: the OpenStack project adopted Podman as the default manager for its containerised services when deployed with TripleO, orchestrated by systemd on control plane and compute nodes.

Running a container

Docker: client to daemon to runtime (Figure 2.7). Podman talks directly to the registry, storage, and the kernel through the runtime (a process, not a daemon), with Conmon in between (Figure 2.8). Core difference: daemon-centric versus fork/exec.

Concerns Docker users raised about the daemon:

  • a single point of failure
  • resource consumption
  • poor rootless support because of per-user Docker and containerd daemons

For the end user the command is nearly identical, and options stay as close as possible to Docker's:

$ docker run -d --rm docker.io/library/nginx
$ podman run -d --rm docker.io/library/nginx

Summary points

The chapter compared architectures and usage and showed the community projects behind Podman (OCI specs, runc, crun). The authors say the book is not a debate on whether Podman beats Docker and that everyone should be grateful to Docker for bringing containers to the masses. Understanding internals pays off in troubleshooting and performance tuning.
