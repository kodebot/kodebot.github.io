Podman for DevOps 5: Implementing storage for the container's data

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 5. Previous: Podman for DevOps 4: Managing running containers. Next: Podman for DevOps 6: Meet Buildah, building containers from scratch.

Takeaways
  • Two kinds of storage: underlying container storage (images and root filesystems, handled by containers/storage with the overlay driver) and external storage that persists application data.
  • Layout under graphRoot: overlay-images (metadata), overlay-layers (archives), overlay (unpacked layers with diff, lower, merged, work, link). A running container's writes land in a temporary upperdir/diff.
  • Copy files with podman cp or podman mount; persist an edited container into a new image with podman commit.
  • Bind mounts (-v, --mount) need existing host paths and hide what is underneath; volumes are engine-managed (podman volume ...), anonymous or named, with plugin drivers (e.g. NFS), build-time VOLUME, --volumes-from.
  • SELinux: mislabelled mounts give 403; fix with :z (shared) or :Z (private, MCS categories). Also tmpfs, image and devpts mounts.

5.1 Why does storage matter for containers?

Two kinds of storage:

  • external storage attached to running containers so data survives restarts

  • underlying storage for container root filesystems and images

  • Containers are stateless, ephemeral, often read-only, built to scale horizontally (launch another container instead of adding CPU or RAM to one), like the public-cloud model. Exceptions exist: a container that cannot scale out, or copies that must share configuration, cache or data.

  • Car-sharing analogy: you unpack your stuff when you get in and pack it when you leave; you attach storage to a container for writing data and detach it when it stops so a new container can use it.

  • Three-tier example: the web tier needs a cache, rendered pages, runtime images; the backend needs configuration and synchronisation data; the database needs data storage. Developers must plan where storage attaches and what features the app needs.

  • Orchestration: storage must be elastic like Kubernetes, ideally software-defined storage that developers and containers consume self-service. Local storage (this book's topic) is not enough there, since containers must move between hosts.

  • A stable, performant underlying store gives correct management of containers and image root filesystems.

5.2 Containers' storage features

Container storage vs CSI:

  • Container storage (earlier "underlying container storage") handles container images on copy-on-write (COW) filesystems until the engine runs them.
  • Container Storage Interface (CSI), with an orchestrator such as Kubernetes, supplies the block or file storage containers write data to.

containers/storage (https://github.com/containers/storage) is a Podman-era innovation: a shared method for accessing container storage on a host. With Docker you had to pass through the daemon, which hid storage from users and administrators; now several tools (Podman, Buildah, Skopeo, CRI-O) can analyse and manage it at the same time. Configuration: /etc/containers/storage.conf.

Storage driver

  • Supported COW drivers: overlay, vfs, btrfs, zfs (also called graph drivers, since most organise layers in a graph). On Fedora 40 with Podman 5.2.2 the default is overlay.
  • OverlayFS has been in the kernel since 3.18, usually enabled by default and activated dynamically on mount. It overlays directory trees, storing only differences but showing the latest squashed tree. In containers, read-only layers stack until the running container's last read-write layer is created as an overlay.

Anatomy of the overlay store (worked example)

Pull an image (with no other images present, to match layers):

# podman pull docker.io/library/httpd:latest
Copying blob 6bd9d3710aae done
Copying blob 4f4fb700ef54 skipped: already exists
...
Copying config 1bcf11fa15 done
Writing manifest to image destination
1bcf11fa154f23987201bd92a75bf75e3507fc49f415d5dfe35887d1be3fd596

Find the store with podman info (or podman info --format json | jq .store):

# podman info | grep -A17 "store:"
store:
  configFile: /usr/share/containers/storage.conf
  graphDriverName: overlay
  graphOptions:
    overlay.mountopt: nodev,metacopy=on
  graphRoot: /var/lib/containers/storage
  graphStatus:
    Backing Filesystem: btrfs
    Supports d_type: "true"
    Using metacopy: "true"
  runRoot: /run/containers/storage
  volumePath: /var/lib/containers/storage/volumes
  • graphRoot: /var/lib/containers/storage (rootless: $HOME/.local/share/containers/storage).
# cd /var/lib/containers/storage && ls
db.sql defaultNetworkBackend libpod overlay overlay-containers overlay-images overlay-layers secrets storage.lock tmp userns.lock volumes
Directory Contents
overlay-images image metadata; the ID directory holds the manifest describing the layers
overlay-layers archives for every layer of every image (*.tar-split.gz, layers.json)
overlay the unpacked layers

Inside each layer directory in overlay/:

Entry Role
diff the layer's changes (upper layer of the overlay)
lower all lower-layer mounts, ordered uppermost to lowermost
merged where the overlay is mounted
work internal operations
link a unique string identifying the layer
  • The l directory holds symbolic links with unique short strings pointing to each layer's diff; the lower file references lower layers through them.
  • Verification chain: the image manifest lists layer digests (e.g. sha256:a480a496..., size 29126289); search overlay-layers/layers.json (unindented, so pipe through jq) for that compressed-diff-digest to get the layer ID (98b5f35e..., diff-size 77832192). SHA-256 is used for integrity checks; Podman developers are working towards other algorithms such as SHA-512.
  • The first (root) layer has no lower file; the overlay creates a dummy empty directory instead.
  • A diff layer is the actual host directory holding the filesystem changes of one image or container layer.

What happens when a container runs:

# podman run -d docker.io/library/httpd:latest
# podman exec -ti 9f84f1cbadf2... /bin/bash
root@9f84f1cbadf2:/usr/local/apache2# echo "this is my NOT persistent data" > tempfile.txt
root@9f84f1cbadf2:/usr/local/apache2# mount | grep overlay
overlay on / type overlay (rw,relatime,context="system_u:object_r:container_file_t:s0:c560,c898",lowerdir=/var/lib/containers/storage/overlay/l/RGJRWXLMSBUBJF4VR3RDLGFXP2:...:/var/lib/containers/storage/overlay/l/43LDU3L34EOOEP5NFGNDBLNNNV,upperdir=/var/lib/containers/storage/overlay/88633bde45bb.../diff,workdir=/var/lib/containers/storage/overlay/88633bde45bb.../work,redirect_dir=on,uuid=on,metacopy=on)

(Rootless: run the mount check inside podman unshare.) The mount line gives lowerdir (layers separated by colons) and the upperdir, where the new file lives:

# ls -la /var/lib/containers/storage/overlay/88633bde45bb.../diff/usr/local/apache2/
-rw-r--r--. 1 root root 31 Oct 19 14:05 tempfile.txt
# cat .../diff/usr/local/apache2/tempfile.txt
this is my NOT persistent data

The data is on the host but in a temporary layer removed with the container.

The storage.conf file

  • It holds containers/storage configuration: driver options and the default paths for internal directories.
  • graphroot (root path): persistent location for downloaded image layers, local image metadata and diff layers.
  • runroot: temporary, volatile data of active containers: state files, lock files, the merged mount points. Often on a memory-backed filesystem (tmpfs), so it is fast and cleared on reboot.
  • A container's folder under runroot holds PID files, logs and files Podman mounts into the container:
# ls -l /run/containers/storage/overlay-containers/9f84f1cbadf2.../userdata/
conmon.pid  hostname  hosts  oci-log  pidfile  resolv.conf  run

5.3 Copying files in and out of a container

Two methods: podman cp, or mounting the container filesystem.

podman cp

$ podman run -d --name alpine_cp_test alpine sleep 1000
$ podman cp alpine_cp_test:/etc/os-release /tmp        # container to host
$ cat /tmp/os-release
NAME="Alpine Linux"
ID=alpine
VERSION_ID=3.20.3
PRETTY_NAME="Alpine Linux v3.20"
$ podman cp /tmp/build_folder alpine_cp_test:/          # host to container (whole folder)

Check with podman exec ... ls. It also copies between containers.

Interacting with overlayfs

$ podman unshare                          # root shell in a user namespace with UID 0, GID 0
# cd $(podman mount alpine_cp_test)       # changes to MergedDir

MergedDir merges LowerDir and UpperDir; from there copy files in either direction. The same logic works for rootful containers. Copying out is mostly for troubleshooting; copying in suits testing secrets or config.

Persisting changes with podman commit

Copying in is not a way to customise permanently: immutability means persistent changes go through an image rebuild. When you must keep the change without a build, podman commit turns a container into a new image. (Dockerfile steps can be seen as a series of commits.)

$ echo "Hello World!" > /tmp/index.html
$ podman run --name custom_nginx -d -p \
    8080:80 docker.io/library/nginx
$ podman cp /tmp/index.html \
    custom_nginx:/usr/share/nginx/html/
$ curl localhost:8080
Hello World!
$ podman commit -p custom_nginx hello-world-nginx
$ podman stop custom_nginx && podman rm custom_nginx
$ podman run -d -p 8080:80 --name hello_world \
    localhost/hello-world-nginx
  • commit adds one new layer; all other layers are shared with the existing nginx image, so no extra storage beyond that layer. (-p pauses the container during the commit.)

5.4 Attaching host storage to a container

  • Containers are ephemeral objects built on a stateful image; if a container crashes or is removed its data is lost, so data needs a separate location mounted into the container, preserved on removal and reusable.
  • Secrets and config files: baking certificates or keys into an image is bad practice, since rotating one means rebuilding the whole image; likewise any config change. The OCI specs support volumes and bind mounts.

Bind mounts

A bind mount (Linux man pages) remounts part of the filesystem hierarchy elsewhere:

$ sudo mount --bind /etc /mnt
$ sudo umount /mnt

Podman has two options:

-v / --volume --mount
Syntax compact /HOST_DIR:/CONTAINER_DIR[:options] verbose type=TYPE,source=HOST_DIR,destination=CONTAINER_DIR (src and dst as short forms)
Types bind or volume bind, volume, tmpfs, image, devpts
Read-only -v /host_files:/mnt:ro --mount type=bind,src=/host_files,dst=/mnt,ro=true
Notes statistically more used clearer and more expressive 
$ podman run -v /host_files:/mnt docker.io/library/nginx
$ podman run --mount type=bind,src=/host_files,dst=/mnt docker.io/library/nginx

Other options: man podman-run. Limitations: the host path must exist with proper permissions before the run, and a bind mount obscures whatever is already at the container mount point.

Volumes

A volume is a directory created and managed by the engine and mounted at a path in the container. podman volume lists, inspects, creates and removes them.

Anonymous volume (a single argument, the container path):

$ podman run -d -p 8080:80 --name nginx_volume1 -v /usr/share/nginx/html docker.io/library/nginx
$ podman inspect nginx_volume1
"Mounts": [
  {
    "Type": "volume",
    "Name": "2ed93716b7ad7370...",
    "Source": "/home/packt/.local/share/containers/storage/volumes/2ed93716.../_data",
    "Destination": "/usr/share/nginx/html",
    "Driver": "local",
    "Options": ["nosuid", "nodev", "rbind"],
    "RW": true,
    "Propagation": "rprivate"
  }
]
$ podman volume ls
DRIVER  VOLUME NAME
local   2ed93716b7ad73706df5c6f56bda262920accec59e7b6642d36f938e936d36d9
$ podman volume inspect $ID | grep Mountpoint
  • An empty volume is populated with the content of the target mount point (50x.html, index.html). The volume survives the container and can be reused. Popular images already declare volumes for config and data.

Named volume:

$ podman run -d -p 8080:80 --name nginx_volume2 -v nginx_vol:/usr/share/nginx/html docker.io/library/nginx
  • Default volume paths: rootless <USER_HOME>/.local/share/containers/storage/volumes; rootful /var/lib/containers/storage/volumes. podman volume mount and podman volume unmount give access to a volume's files.
  • Remove:
$ podman volume rm nginx_vol            # only if no container uses it
$ podman volume rm --force nginx_vol    # also removes containers using it
$ podman volume prune                   # all unused volumes
  • Monitor accumulation: volumes use disk space; some images create volumes that are not always removed with the container.

Pre-populating a volume:

$ podman volume create custom_nginx
$ podman unshare
# podman volume mount custom_nginx
/home/packt/.local/share/containers/storage/volumes/custom_nginx/_data
# echo "Hello World!" >> /home/packt/.local/share/containers/storage/volumes/custom_nginx/_data/index.html
$ podman run -d -p 8080:80 --name nginx_volume3 -v custom_nginx:/usr/share/nginx/html docker.io/library/nginx
$ curl localhost:8080
Hello World!

(The book writes podman create volume in the prose and podman volume create in the commands.) A non-empty volume obscures the target directory's contents.

--mount for volumes:

$ podman run -d -p 8080:80 --name nginx_volume4 --mount type=volume,src=custom_nginx,dst=/usr/share/nginx/html docker.io/library/nginx

Volume drivers

  • All of the above use the local driver. Other drivers are configured in /usr/share/containers/containers.conf, section [engine.volume_plugins], as plugin name plus file or socket path (vendor plugins, usually unnecessary).
  • The local driver can also mount NFS shares: an NFS-backed volume for MongoDB's /data/db (needs a configured NFS server reachable from the host; not available for rootless):
$ sudo podman volume create --driver local --opt type=nfs --opt o=addr=nfs-host.example.com,rw,context="system_u:object_r:container_file_t:s0" --opt device=:/opt/nfs-export nfs-volume
$ sudo podman run -d -v nfs-volume:/data/db docker.io/library/mongo

Volumes in builds

The Dockerfile VOLUME directive defines which directory becomes an anonymous volume. It is metadata only: the volume is created at runtime.

FROM docker.io/library/nginx:latest
VOLUME /usr/share/nginx/html

$ podman build -t my_nginx .
$ podman run -d --name volumes_from_build my_nginx
$ podman inspect volumes_from_build --format "{{ .Mounts }}"
  • Podman auto-creates and mounts it. Unnamed volumes are normally removed with the container that created them.
  • The official mongo image defines two volumes (/data/configdb, /data/db); the same applies to PostgreSQL, MariaDB, MySQL.
  • --image-volume chooses how predefined volumes mount: default bind, or tmpfs, or ignore: $ podman run -d --image-volume tmpfs docker.io/library/mongo. (Chapter 6 covers builds.)

Mounting volumes across containers

$ podman run -d --name mongodb01 docker.io/library/mongo
$ podman run -it --volumes-from=mongodb01 docker.io/library/fedora
[root@c10420016687 /]# ls -al /data
drwxr-xr-x. 2 999 999 4096 Sep 20 22:20 configdb
drwxr-xr-x. 4 999 999 4096 Oct 17 15:36 db

If you stop and remove mongodb01, the volumes stay mounted in the Fedora container. Same permissions as the source by default; add rw or ro: --volumes-from=mongodb01,ro.

SELinux considerations for mounts

  • SELinux applies labels (stored as extended attributes) recursively to define a context; see it with ls -alZ:
$ ls -alZ /etc/passwd
-rw-r--r--. 1 root root system_u:object_r:passwd_file_t:s0 2965 Jul 28 21:00 /etc/passwd
  • Container processes run as container_t and have read/write on container_file_t, read/execute on container_share_t. By default also /etc read-only and /usr read/execute; resources under /var/lib/containers/overlay/ are container_share_t.
  • A mislabelled mount runs without complaint but is inaccessible:
$ mkdir ~/custom_docroot
$ echo "Hello World!" > ~/custom_docroot/index.html
$ podman run -d --name custom_nginx -p 8080:80 \
    -v ~/custom_docroot:/usr/share/nginx/html \
    docker.io/library/nginx
$ curl localhost:8080
403 Forbidden  (nginx/1.21.3)

Two fixes:

  1. Permissive mode (not good practice; only when you can't troubleshoot): $ sudo setenforce 0. Permissive is not disabling: SELinux still logs AVC denials; switching permissive/enforcing needs no reboot, while disabling does. Per container: --security-opt label=disable.
  2. Relabel (preferred) with the :z and :Z suffixes (volumes and bind mounts):
Suffix Effect
:z relabel so all containers can read and write
:Z relabel so only this container can read and write

(Equivalent --mount forms: relabel=shared and relabel=private.) Be careful on system-critical directories such as /etc or /home: relabelling can block host processes.

$ podman run -d --name custom_nginx -p 8080:80 \
    -v ~/custom_docroot:/usr/share/nginx/html:z docker.io/library/nginx
$ ls -alZ ~/custom_docroot
drwxrwxr-x. 2 packt packt system_u:object_r:container_file_t:s0 4096 Oct 16 15:53 .
  • MLS and MCS: the trailing s0 is a Multi-Level Security sensitivity level; every process at s0 can read and write, so a malicious container on the same host could steal or overwrite data. Multi-Category Security adds plaintext categories; objects are accessible only to processes with the same categories. Container processes get categories of the pattern cXXX,cYYY (random integers).
  • :Z applies MCS categories to the mount: system_u:object_r:container_file_t:s0:c16,c898. Run a second container with :Z on the same directory (custom_nginx2 on port 8081): it works, but the first now returns 403 because the directory was relabelled with a new category pair.
  • The examples use bind mounts but apply to volumes too; do not use :z and :Z with volumes, since Podman handles their labelling automatically.

5.5 Attaching other types of storage

tmpfs

  • tmpfs is a virtual-memory filesystem: contents live in RAM, with faster I/O, discarded when the container stops. Use it for non-persistent data (e.g. cache) to avoid cluttering disks.
$ podman run -d -p 8080:80 \
    --name tmpfs_example1 \
    --mount type=tmpfs,tmpfs-size=512M,destination=/tmp \
    docker.io/library/httpd
$ podman exec -it tmpfs_example1 mount | grep '\/tmp'
tmpfs on /tmp type tmpfs (rw,nosuid,nodev,relatime,context="system_u:object_r:container_file_t:s0:c375,c804",size=524288k,uid=1000,gid=1000,inode64

$ podman run -d -p 8080:80 \
    --name tmpfs_example2 \
    --tmpfs /tmp:rw,size=524288k,mode=1777 \
    docker.io/library/httpd
  • Both give a 512 MB tmpfs at /tmp (the second: read/write, permissions 1777). Default options: rw, noexec, nosuid, nodev. SELinux MCS labelling is automatic, so other containers cannot read the memory.

Images

An OCI image can be attached at runtime (troubleshooting, borrowing binaries from a foreign image, security scans). An extra overlay is created, so even rw never alters the original image, only the upper overlay.

$ podman run -it \
    --mount type=image,src=docker.io/library/busybox,dst=/mnt,rw=true \
    alpine

The image must be pulled first (podman pull); unlike podman run, mounting does not fetch a missing image.

devpts

Attaches a pseudo-terminal slave (PTS) to a container; introduced in Podman 2.1.0 for containers that mount the host /dev/ yet still need a terminal (/dev gives direct access to physical or virtual devices):

$ sudo podman run -it \
    -v /dev/:/dev:rslave \
    --mount type=devpts,destination=/dev/pts \
    docker.io/library/fedora
[root@034c8a61a4fc /]# dnf install -y toolbox
# mount | grep '\/dev\/pts'
devpts on /dev/pts type devpts (rw,nosuid,noexec,relatime,seclabel,gid=5,mode=620,ptmxmode=000)
devpts on /dev/pts type devpts (rw,nosuid,noexec,relatime,context="system_u:object_r:container_file_t:s0:c299,c741",gid=5,mode=620,ptmxmode=666)

The container has an extra non-isolated devpts on /dev/pts.

Why storage matters (single-host and orchestrated); storage features and drivers with a focus on overlayfs; copying files and committing; bind mounts, volumes, tmpfs, images and devpts, and SELinux isolation of storage between containers on a host.
