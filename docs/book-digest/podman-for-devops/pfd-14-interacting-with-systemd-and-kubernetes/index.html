Podman for DevOps 14: Interacting with systemd and Kubernetes

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 14. Previous: Podman for DevOps 13: Docker migration tips and tricks. Next: Podman for DevOps 15: Managing containers, Kubernetes and AI workloads from a graphical interface.

Takeaways
  • podman generate systemd is deprecated (static units go stale). Use Quadlets: declarative .container files that systemd's generator turns into services at runtime; podlet converts a podman run command into one.
  • Put Quadlets in /etc/containers/systemd/, add [Unit] Requires= for ordering and [Install] WantedBy= for boot, then systemctl daemon-reload. podman secret holds secrets (plain text on disk).
  • podman kube generate turns containers, Pods and volumes into Kubernetes YAML (Pod, Service of type NodePort, PersistentVolumeClaim); podman kube play runs YAML in Podman (--down to remove).
  • Single Pod (shared 127.0.0.1) is simple but not the Kubernetes pattern; multiple Pods on a network, where the Pod name is the service name (aardvark-dns), replace Docker Compose and stay portable.
  • Test the full manifest (Pods, Services, PVCs) on minikube with kubectl create -f.

14.1 Setting up the host prerequisites

  • Containers can be managed like any other service through systemd and systemctl. systemd is the system and service manager, the first process on boot (PID 1), an init system that brings up and maintains userspace services; each logged-in user gets separate instances. It starts services with a dependency system between units; there are 11 unit types. Fedora 40+ runs it by default:
# systemctl is-system-running
running
# systemctl list-units --type=service | head

(systemd's internals need the Linux manual.)

14.2 Integrating containers into systemd via Quadlets

  • Deprecated: podman generate systemd produced unit files, but static unit generation was brittle: best practices evolved each release and users didn't regenerate their files, missing bug fixes and performance updates.
  • Quadlets (recommended): describe a container in a declarative format similar to systemd configuration files; systemd uses a generator to create the units at runtime. The easiest way to write one is podlet, which takes a podman run command and outputs Quadlet format.
  • Example: a Git service with Gitea (repository with web UI) and MariaDB (database for Gitea).

Secrets

# export MARIADB_PASSWORD=my-secret-pw
# podman secret create MARIADB_PASSWORD --env MARIADB_PASSWORD
cb5eab6a00d2b69635a314188
# podman secret ls
ID                         NAME              DRIVER  CREATED         UPDATED
cb5eab6a00d2b69635a314188  MARIADB_PASSWORD  file    18 seconds ago  18 seconds ago
# podman secret inspect cb5eab6a00d2b69635a314188      # driver file, path /var/lib/containers/storage/secrets/filedriver
# cat /var/lib/containers/storage/secrets/filedriver/secretsdata.json
{ "cb5eab6a00d2b69635a314188": "bXktc2VjcmV0LXB3" }
# ls -l /var/lib/containers/storage/secrets/filedriver/secretsdata.json
-rw-------. 1 root root 53 Aug 7 15:18 ...

podman secret create stores the secret in plain text (JSON with the ID and the Base64 value; decoding gives my-secret-pw). Good enough here because the containers run as root and the file has root-only permissions.

MariaDB first (the dependency), run standalone to check

# mkdir -p /opt/var/lib/mariadb
# podman run -d --network host --name mariadb -v \
    /opt/var/lib/mariadb:/var/lib/mysql:Z -e \
    MARIADB_DATABASE=gitea -e MARIADB_USER=gitea -e \
    MARIADB_RANDOM_ROOT_PASSWORD=true \
    --secret=MARIADB_PASSWORD,type=env docker.io/mariadb:latest

Detached; name mariadb; host network for simplicity (could be restricted); local directory mapped with :Z for SELinux; environment variables, with the password via --secret. Check with podman ps. Install and run podlet:

# dnf install -y podlet          # podlet-0.3.0 on Fedora 40
# podlet podman run -d --network host --name mariadb -v /opt/var/lib/mariadb:/var/lib/mysql:Z -e MARIADB_DATABASE=gitea -e MARIADB_USER=gitea -e MARIADB_RANDOM_ROOT_PASSWORD=true --secret=MARIADB_PASSWORD,type=env docker.io/mariadb:latest
# mariadb.container
[Container]
ContainerName=mariadb
Environment=MARIADB_DATABASE=gitea MARIADB_USER=gitea MARIADB_RANDOM_ROOT_PASSWORD=true
Image=docker.io/mariadb:latest
Network=host
Secret=MARIADB_PASSWORD,type=env
Volume=/opt/var/lib/mariadb:/var/lib/mysql:Z

Just put podlet in front of the podman run command.

Gitea

# mkdir -p /opt/var/lib/gitea/data
# podman run -d --network host --name gitea \
    -v /opt/var/lib/gitea/data:/data:Z \
    docker.io/gitea/gitea:latest
# podman logs gitea       # "Starting Gitea ... Listen: http://0.0.0.0:3000" (Gitea 1.24.4)

Browse to http://localhost:3000 and complete the install page (database type, address, user and password; Figures 14.1 and 14.2). Then generate the Quadlet files into the systemd directory (the book's second command uses gitea/gitea:latest-rootless; its redirection to the file is cut in the printed text):

# podlet podman run -d --network host --name mariadb -v /opt/var/lib/mariadb:/var/lib/mysql:Z -e MARIADB_DATABASE=gitea -e MARIADB_USER=gitea -e MARIADB_RANDOM_ROOT_PASSWORD=true --secret=MARIADB_PASSWORD,type=env docker.io/mariadb:latest > /etc/containers/systemd/mariadb.container
# podlet podman run -d --network host --name gitea -v /opt/var/lib/gitea/data:/data:Z docker.io/gitea/gitea:latest-rootless > /etc/containers/systemd/gitea.container

Edit the Gitea file to order startup with Requires so systemd starts MariaDB first:

# gitea.container
[Unit]
Requires=mariadb.container

[Container]
ContainerName=gitea
Image=docker.io/gitea/gitea:latest-rootless
Network=host
Volume=/opt/var/lib/gitea/data:/data:Z

Stop the standalone containers (data persists in the mapped volumes), reload systemd, start by unit:

# podman stop mariadb gitea
# systemctl daemon-reload
# systemctl start mariadb
# systemctl status mariadb
Loaded: loaded (/etc/containers/systemd/mariadb.container; generated)
Active: active (running) since Thu 2025-08-07 16:11:15 UTC
# systemctl start gitea

The status shows the unit as generated from the .container file. Start at boot by adding to both files:

[Install]
# Start by default on boot
WantedBy=multi-user.target default.target

podman quadlet inspects and manages Quadlets without digging through /etc/ or /run/; podman quadlet -v lists, verbosely, all files the systemd generator processed.

14.3 Generating Kubernetes YAML resources

  • Kubernetes is the de facto standard for multi-node orchestration: Pods scheduled across nodes by load, labels, capabilities, hardware (GPUs). A Pod is a group of containers sharing network, IPC and optionally PID namespaces (a sandbox), started, stopped and paused together.
  • Podman reads the configuration of containers or Pods and generates API-compliant Pod resources, plus Service and PersistentVolumeClaim (PVC) resources for ports and volumes. Use them in Podman itself (an alternative to Compose) or apply them to a cluster.
  • Kubernetes runs workloads as Deployments, StatefulSets, DaemonSets, Jobs, CronJobs; a Pod is the minimal unit in all of them, so a generated Pod can be adapted into a Deployment (replicas and rollouts) or a DaemonSet (one Pod per node).

Generate a Pod from a running container

$ podman kube generate [options] {CONTAINER|POD|VOLUME}

Options: -s, --service (also generate Services), -f, --filename (write to a file; default stdout).

$ podman run -d -p 8080:80 --name nginx docker.io/library/nginx
$ podman kube generate nginx
# Created with podman-5.2.5
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: "2025-08-07T16:19:45Z"
  labels:
    app: nginx-pod
  name: nginx-pod
spec:
  containers:
    - args:
        - nginx
        - -g
        - daemon off;
      image: docker.io/library/nginx:latest
      name: nginx
      ports:
        - containerPort: 80
          hostPort: 8080

(The printed YAML has lost its indentation; restored here.) Every Kubernetes resource has at least four fields:

Field Meaning
apiVersion API schema version (Pod is v1, the core API)
kind resource kind (Pod)
metadata name, namespace, labels, annotations, plus runtime values (creationTimestamp, resourceVersion, uid)
spec the specification; for a Pod, the containers with arguments, volumes, ports, security contexts

A fifth status field appears at runtime. The ports entry (containerPort: 80, hostPort: 8080) is used later by podman kube play. Save with podman kube generate nginx -f nginx-pod.yaml, or apply straight to a cluster: podman kube generate nginx | kubectl create -f -.

Pods and Services

  • Pod IPs are on the cluster's software-defined network and not routed externally; a Service gives a stable name and IP, balancing replicas. Cluster DNS is CoreDNS (started with the control plane; resolves internal names and forwards external ones).
  • Service types: ClusterIP (default; IP local to the cluster), NodePort (NAT maps the service VIP and port to a port on the worker nodes, 30000 or higher, for external access), LoadBalancer (cloud provider balances ingress). Podman generates NodePort Services and doesn't support LoadBalancer (it is a single-node engine). podman kube generate is meant as a starting point you extend.
$ podman kube generate -s nginx
apiVersion: v1
kind: Service
metadata:
  labels:
    app: nginxpod
  name: nginx_pod
spec:
  ports:
    - name: "80"
      nodePort: 30582
      port: 80
      targetPort: 80
  selector:
    app: nginxpod
  type: NodePort
---
apiVersion: v1
kind: Pod
metadata:
  labels:
    app: nginxpod
  name: nginx_pod
spec:
  containers:
    - args: [nginx, -g, daemon off;]
      image: docker.io/library/nginx:latest
      name: nginx
      ports:
        - containerPort: 80
          hostPort: 8080
      securityContext:
        capabilities:
          drop:
            - CAP_MKNOD
            - CAP_NET_RAW
            - CAP_AUDIT_WRITE

(The book's example output carries an older "podman-4.0.0-rc4" banner.) The selector matches Pods labelled app: nginxpod; in a cluster the Service gets an internal non-routed VIP, and a DNAT rule forwards traffic on port 30582 on every node to the service IP. Container port 80 maps to node port 30582. The point: port a workload to Kubernetes with little effort.

Composite application in a single Pod

Advantages: the Pod is one unit and resource sharing is simple. Scripts and YAML: https://github.com/PacktPublishing/Podman-for-DevOps-Second-Edition/tree/main/Chapter14/kube. Examples are rootless but apply to rootful too.

$ for vol in dbvol wpvol; do podman volume create $vol; done
$ podman pod create --name wordpress-pod -p 8080:80
$ podman create \
    --pod wordpress-pod --name db \
    -v dbvol:/var/lib/mysql \
    -e MYSQL_ROOT_PASSWORD=myrootpasswd \
    -e MYSQL_DATABASE=wordpress \
    -e MYSQL_USER=wordpress \
    -e MYSQL_PASSWORD=wordpress \
    docker.io/library/mysql
$ podman create \
    --pod wordpress-pod --name wordpress \
    -v wpvol:/var/www/html \
    -e WORDPRESS_DB_HOST=127.0.0.1 \
    -e WORDPRESS_DB_USER=wordpress \
    -e WORDPRESS_DB_PASSWORD=wordpress \
    -e WORDPRESS_DB_NAME=wordpress \
    docker.io/library/wordpress
$ podman pod start wordpress-pod
$ podman ps              # infra + db + wordpress; http://localhost:8080 shows the WordPress setup (Figure 14.3)

WORDPRESS_DB_HOST=127.0.0.1 because both containers share the Pod's network namespace.

The infra container

$ podman kube generate wordpress-pod \
    -f wordpress-single-pod.yaml

The generated Pod (condensed; the printed listing shows only the wordpress container although the Pod holds both, and notes the env and volumes are preserved):

apiVersion: v1
kind: Pod
metadata:
  labels:
    app: wordpress-pod
  name: wordpress-pod
spec:
  containers:
    - args:
        - apache2-foreground
      env:
        - name: WORDPRESS_DB_HOST
          value: 127.0.0.1
        - name: WORDPRESS_DB_PASSWORD
          value: wordpress
        - name: WORDPRESS_DB_NAME
          value: wordpress
        - name: WORDPRESS_DB_USER
          value: wordpress
      image: docker.io/library/wordpress:latest
      name: wordpress
      ports:
        - containerPort: 80
          hostPort: 8080
      volumeMounts:
        - mountPath: /var/www/html
          name: wpvol-pvc
  volumes:
    - name: wpvol-pvc
      persistentVolumeClaim:
        claimName: wpvol
  • Volumes map to PVC objects. A PVC claims a storage volume of given capacity and access modes; the bound storage is a PersistentVolume (PV), created manually or automatically by a StorageClass using a CSI-compliant driver. This decouples requesting from provisioning, making storage more portable.
  • PVCs are not exported by default: name the volumes: podman kube generate wordpress-pod wpvol dbvol. A PVC looks like:
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  annotations:
    volume.podman.io/driver: local
  name: dbvol
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
status: {}

PVC definitions are needed to recreate the app in Kubernetes but not in Podman (a missing volume is created empty). Export everything: $ podman kube generate -s wordpress-pod wpvol dbvol.

Single Pod: pros and cons. Pro: one network namespace, no dedicated Podman network. Con: it doesn't reflect the Kubernetes pattern: you would normally split WordPress and MySQL into separate Pods with their own Services, for independent management and updates.

Composite application with multiple Pods

The Podman community's view: standardise on Kubernetes YAML for complex workloads. This approach can fully replace Docker Compose while giving Kubernetes portability. Clean up the previous Pod and volumes first (see the repository's AdditionalMaterial).

$ podman network create kubenet
$ for vol in wpvol dbvol; do podman volume create $vol; done
$ podman pod create -p 3306:3306 \
    --network kubenet \
    --name mysql-pod
$ podman create --name db \
    --pod mysql-pod \
    -v dbvol:/var/lib/mysql \
    -e MYSQL_ROOT_PASSWORD=myrootpasswd \
    -e MYSQL_DATABASE=wordpress \
    -e MYSQL_USER=wordpress \
    -e MYSQL_PASSWORD=wordpress \
    docker.io/library/mysql
$ podman pod create -p 8080:80 \
    --network kubenet \
    --name wordpress-pod
$ podman create --name wordpress \
    --pod wordpress-pod \
    -v wpvol:/var/www/html \
    -e WORDPRESS_DB_HOST=mysql-pod \
    -e WORDPRESS_DB_USER=wordpress \
    -e WORDPRESS_DB_PASSWORD=wordpress \
    -e WORDPRESS_DB_NAME=wordpress \
    docker.io/library/wordpress
$ podman pod start mysql-pod && podman pod start wordpress-pod

Key: WORDPRESS_DB_HOST=mysql-pod. The Pod's name acts as the service name, resolved by the network's DNS (aardvark-dns): a perfect Compose replacement. The 3306 mapping lets a client reach MySQL and supplies the port for the later Service.

$ podman kube generate \
    -f wordpress-multi-pod-basic.yaml \
    wordpress-pod \
    mysql-pod

The file holds just the two Pod resources (wordpress-pod with WORDPRESS_DB_HOST: mysql-pod, hostPort: 8080, volume wpvol-pvc; mysql-pod with args: [mysqld], hostPort: 3306, volume dbvol-pvc; both with restartPolicy: Never and a securityContext dropping CAP_MKNOD, CAP_NET_RAW, CAP_AUDIT_WRITE). Source: https://github.com/PacktPublishing/Podman-for-DevOps-Second-Edition/blob/main/Chapter14/kube/wordpress-multi-pod-basic.yaml. It is enough to recreate the app on Podman from scratch; version it in Git. The full export adds Services and PVCs (for Kubernetes):

$ podman kube generate -s \
    -f wordpress-multi-pod-full.yaml \
    wordpress-pod \
    mysql-pod \
    dbvol \
    wpvol

(Full file: .../Chapter14/kube/wordpress-multi-pod-full.yaml.)

14.4 Running Kubernetes resource files in Podman

podman kube play runs the manifests (an easy interface for complex stacks):

$ podman kube play wordpress-single-pod.yaml
$ podman pod ps
POD ID        NAME           STATUS   CREATED         INFRA ID      # OF CONTAINERS
5f8ecfe66acd  wordpress-pod  Running  4 minutes ago   46b4bdfe6a08  3
$ podman ps            # infra (podman-pause) + wordpress-pod-db + wordpress-pod-wordpress
$ podman volume ls     # dbvol, wpvol created

Clean up with --down (stops and removes the Pods):

$ podman kube play --down wordpress-single-pod.yaml

Volumes are not removed by default (safe against data loss); use podman volume prune for unused ones. Multi-Pod run needs the network named explicitly, since the Kubernetes YAML has no Podman network info:

$ podman kube play --network kubenet \
    wordpress-multi-pod-basic.yaml
$ podman pod ps         # mysql-pod and wordpress-pod, 2 containers each (counting infra)
$ podman ps --format "{{.Image }} {{.Names}}"

DNS: Podman 4+ uses aardvark-dns for custom networks (Podman 3 used dnsmasq). Rootless records: /run/user/<UID>/containers/networks/aardvark-dns/<NETWORK_NAME>:

$ cat /run/user/1000/containers/networks/aardvark-dns/kubenet
10.89.0.1
0c52ee13... 10.89.0.4 wordpress-pod,0c52ee133f0f
71c93fa6... 10.89.0.5 mysql-pod,71c93fa6080b

Name resolution works at the Pod level, not the container level, because the Pod initialised the namespaces: a Pod name is a service name in Podman. Generated Kubernetes manifests thus make a portable replacement for Docker Compose.

14.5 Testing the results in Kubernetes

Use minikube (lowercase) for a local all-in-one cluster on Linux, Windows or macOS: a VM via host virtualisation (KVM, VirtualBox, Hyper-V, Parallels, VMware) or a control plane in a container (Docker or Podman); add-ons for ingress, service meshes, registries, logging. An alternative is KinD (Kubernetes in Docker, https://kind.sigs.k8s.io/), not covered. Skip this setup if you already have a cluster.

$ curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
$ sudo install minikube-linux-amd64 /usr/local/bin/minikube

KVM driver:

$ sudo dnf install @virtualization
$ sudo systemctl enable --now libvirtd
$ sudo usermod -aG libvirt $(whoami)           # needs a new login
$ minikube config set driver kvm2

Podman driver: the cluster must run in a rootful container, so the user needs passwordless sudo for Podman (sudo visudo, add <username> ALL=(ALL) NOPASSWD: /usr/bin/podman), then:

$ minikube config set driver podman

(If the host is a KVM VM with Podman installed, minikube picks the podman driver automatically.) Install kubectl:

$ version=$(curl -L -s https://dl.k8s.io/release/stable.txt)
$ curl -LO "https://dl.k8s.io/release/${version}/bin/linux/amd64/kubectl"
$ sudo install -o root -g root \
    -m 0755 kubectl \
    /usr/local/bin/kubectl

Start minikube with the CRI-O runtime:

$ minikube start --driver=kvm2 --container-runtime=cri-o
$ minikube start --driver=podman --container-runtime=cri-o
$ kubectl get pods -A       # coredns, etcd, kube-apiserver, kube-controller-manager, kube-proxy, kube-scheduler, storage-provisioner all Running

(--driver is optional if already configured. Wait if some are ContainerCreating. With the Podman driver an extra kindnet Pod handles CNI networking.)

Running the generated files in Kubernetes

Services provide name resolution and internal load balancing; PVCs request storage. In minikube automatic provisioning uses the minikube-hostpath StorageClass (local directories bind-mounted into containers).

$ kubectl create -f wordpress-multi-pod-full.yaml      # default namespace
$ kubectl get pods
mysql-pod      1/1  Running
wordpress-pod  1/1  Running
$ kubectl get svc
kubernetes     ClusterIP  10.96.0.1      <none>  443/TCP
mysql-pod      NodePort   10.108.34.77   <none>  3306:30284/TCP
wordpress-pod  NodePort   10.96.63.142   <none>  80:30408/TCP
$ kubectl get endpoints          # mysql-pod 10.244.0.5:3306, wordpress-pod 10.244.0.6:80
$ kubectl get pvc                # dbvol and wpvol Bound, 1Gi RWO, storageclass standard
$ kubectl get pv                 # two dynamically provisioned PVs (Reclaim Delete)
  • Services are NodePort (30000 or higher). Pods are matched to Services by label selector; matching Pods become the service's endpoints. PVs remain while PVCs exist, even if Pods are recreated. (The kubernetes service is for internal API access; ignore it.)
  • minikube has no ingress controller by default (minikube addons enable ingress adds one), so test via NodePort at the minikube IP:
$ minikube ip
10.88.0.6
# browse http://10.88.0.6:30408   -> WordPress first setup screen
$ kubectl delete -f wordpress-multi-pod-full.yaml      # removes all resources, including generated PVs

Summary points

Containerised services under systemd with Quadlets (the book's summary still speaks of "generating systemd unit files"), generating Kubernetes resources with single-Pod and multi-Pod approaches (the latter a Kubernetes-compliant Compose alternative), and testing on Podman and minikube.
