Principles and Patterns for Distributed Application Architecture 3: Patterns of Distributed Application Architecture

Source: Jonas Bonér, Principles and Patterns for Distributed Application Architecture (O'Reilly, 2025), chapter 3. Previous: Principles and Patterns for Distributed Application Architecture 2: Principles of Distributed Application Architecture. Next: Principles and Patterns for Distributed Application Architecture 4: Designing Distributed Applications.

Takeaways
  • Twenty patterns, best practices and techniques for elastic, resilient, high-performing, predictable, maintainable distributed applications; the author says they compose, so "the sum is greater than the parts".
  • Data and state: partition state, communicate facts (immutable events), isolate mutations, localize state, log events (event sourcing), untangle reads and writes (CQRS).
  • Flow and communication: coordinate dataflow (backpressure), go async, leverage location transparency, observe dynamics.
  • Consistency: minimize consistency (ACID 2.0, causal consistency), compose sagas instead of distributed transactions.
  • Resilience: guard connections (timeouts, retries, circuit breakers), model with actors, supervise subordinates, protect critical data, detect failure, replicate for resilience, gossip for convergence, seek consensus.

The chapter opens: "How can we put these principles into practice?" It dives into twenty patterns; some are "probably more best practices and techniques", but all are called patterns for simplicity.

3.1 Partition state

Divide state into smaller chunks to leverage parallelism of the system.

  • Distributed applications run in parallel on computers that do not share memory, bringing coordination and concurrency control to the multimachine level
    • handling state as a monolith becomes inefficient and often impossible.
  • Partitioning also helps scalability (each node stores and processes only a finite dataset; a network of them handles larger problems) and fault tolerance (failures are isolated to partitions, using bulkheads).
  • Split the monolithic state into smaller partitions managed mostly independently, ideally as "embarrassingly parallel" tasks.
  • Some datasets partition naturally (accounts, purchase orders, devices, user sessions); others need care over how to divide and what partition key to use.
  • For an aggregated view across partitions: event sourcing (components subscribe to the event stream and build their own aggregated model) and/or CQRS to create aggregated read projections (joins) in your database of choice.
  • The sacrifice is consistency:
    • independent partitions go against the coordination needed for guarantees across partition boundaries such as atomicity and isolation
    • It is an explicit trade-off of performance, scalability and fault tolerance against consistency and simplicity.

3.2 Communicate facts

Choose immutable event streams over mutable state.

  • Mutable state
    • is not stable through time: it holds only the current value and evolves by destructive in-place updates
    • Most languages treat value and identity as the same thing, so identity cannot evolve without changing the value, forcing mutexes and similar guards.
  • Concurrent updates are a "notorious source of data corruption"
    • Techniques exist (mutexes, barriers, fork-join; coroutines, actors, futures/promises) but are complex, easy to get wrong as code evolves, and need coordination that caps performance and scalability (Amdahl's law and USL)
    • Destructive mistakes lose data that is expensive to detect and recover.
  • Instead use immutable values representing facts, shareable as local or distributed events without locks or transactions.
  • A fact is immutable and represents something that already happened, which cannot be changed or retracted
    • Knowledge is cumulative: gain it by receiving facts or deriving them, and invalidate old knowledge by adding new facts that refute it
    • Facts are never deleted, only made irrelevant.
  • Facts stored as events in causal order represent a component's full history of state changes (event sourcing) while serving low-latency reads from memory (a pattern called memory image).
  • Share facts by publishing them to the component's event stream, which others (components, databases, subsystems) subscribe to for communication, integration and replication
    • Implementations: event-sourcing libraries (Akka, Axon), message brokers (Kafka, Pulsar), optimised append-only storage, or regular databases.
  • The stream must be append-only, made of immutable events, with no writable side channels, a single producer, and zero to many consumers
    • Reading from a cursor/index allows replay on failure or network problems and supports at-least-once or exactly-once delivery (usually with deduplication).

3.3 Isolate mutations

Contain and isolate mutable state using bulkheads.

  • When you must use mutable state, never share it:
    • contain it with its behaviour in isolated, partitioned compartments separated by bulkheads, a shared-nothing architecture
    • That contains failure, limits its scope, localises it and avoids escalation to cascading failures
    • Validation errors are not failures but part of the normal interaction protocol of a stateful component.
  • Bulkheads are easiest to install with asynchronous messaging, which adds a protocol boundary isolating components in time and space, enables observing fluctuating demand (avoiding flooding a bulkhead) and gives a unit of replication.
  • Use mutable state only for local computation inside the consistency boundary, invisible to the world
    • When processing is done, create an immutable value for the result (a fact) and publish it.
  • Bulkheaded components should ideally use single-threaded execution, like Akka actors, avoiding deadlocks, race conditions and corruption.
  • Others rely on stable immutable values
    • each component internally keeps the benefits of mutability (familiarity, simple coding, efficiency), strong consistency and less contention through the single writer principle.

3.4 Coordinate dataflow

Orchestrate a continuous steady flow of information.

  • Think in terms of dataflow: how data flows through the system, what behaviour it triggers and how components are causally related. This focuses on behaviour, not structure.
  • Orchestrate workflow and integration by letting components subscribe to each other's event streams and consume published facts on demand.
  • Consumers control their rate of consumption,
    • which may be decoupled from the production rate
    • A consumer that controls its own rate cannot be overwhelmed
    • This is one reason architectures use message queues: they absorb extra load so consumers drain it at leisure.
  • The poison pill pattern gracefully shuts down a service by sending a special message saying no more will come.
  • A consumer controlling its rate plus an out-of-band mechanism to halt production gives flow control, which must be managed end to end with every participant cooperating.
  • Backpressure
    • forces the producer to slow when the consumer cannot keep up, usually through a backchannel upstream on which downstream components signal to slow down or speed up (Figure 3-1)
    • All parties must speak the same protocol.
  • Another scheme: a queue between producer and consumer, reacting to its utilisation by giving the consumer more resources or slowing or degrading the producer.
  • Take particular care at the edges, where components meet each other or third-party systems
    • protocols for graceful degradation and flow control lower the likelihood of failure and give control when it strikes.

3.5 Localize state

Take ownership of data by co-locating state and processing.

  • In data-intensive use cases, co-locate state and processing for locality of reference and a single source of truth, giving low latency, high throughput and more even workloads.
  • Locality of reference has two types: temporal (reuse specific data) and spatial (keep data close in space).
  • Three ways:
    1. Move the processing to the state: cluster sharding (on the key of the partitioned dataset) of in-memory data, running business logic in-process on each shard and avoiding read and write contention. Ideally the in-memory data is the single source of truth, mapped strongly consistently to storage (event sourcing and memory image).
    2. Move the state to the processing: replicate data to all nodes where logic runs (including the edge), with eventually consistent convergence (CRDTs with gossip), or use distributed stream processing with pipelines across nodes. This gives high availability without extra storage infrastructure and keeps data consistent across components, nodes, data centres and clients where strong consistency is not required.
    3. Combine both inside the consistency boundary of mobile, self-contained, autonomous, location-transparent components (actors), physically co-located with the end user. Such a component can lose its backend connection and keep serving, the local-first software design.
  • Co-location is different from, and complementary to, caching
    • Caching keeps read-only copies close to the processing context, useful for read-heavy cases, but adds complexity staying in sync with the master, so cached data cannot be the single source of truth.

3.6 Go async

Embrace asynchronous messaging and nonblocking execution.

  • An idle component should not hold resources (thread, socket, file)
    • Asynchronous nonblocking execution and I/O use resources efficiently and minimise contention on shared resources, one of the biggest barriers to elasticity, scalability, low latency and throughput.
  • Example:
    • a service making 10 requests of 100 ms each to 10 other services. Sequentially the total is about 1 second (Figure 3-2)
    • asynchronously it is about 100 ms (Figure 3-3), an order of magnitude difference.
  • A blocking call ties up a thread, a limited resource, so it cannot do other work
    • Nonblocking calls free the thread (via async callback or message), improving cost, energy and performance (Figure 3-4).
  • All parts of the request chain must participate, from dispatch through service implementation to data storage and back, within a service boundary as much as between services and clients.
  • An asynchronous boundary between components decouples them in time (concurrency) and space (distribution, mobility, location transparency, elasticity, resilience via bulkheading)
    • Aids: event-driven design, actors, message queues, distributed stream-processing products.

3.7 Observe dynamics

Understand your system by looking at its dynamics.

  • Distributed systems are complex and issues have many sources (networking, resources, third parties)
    • without observability root causes are hard to find. It improves reliability and user experience and reduces MTTR.
  • Observability is about answering "how is your system doing?" now and historically. It comprises application metrics, network metrics, health reports, logs and traces, in three categories:
Category What and example
Logs Structured logs per service with context (user ID, request ID) to track user flows; on failure, the error and its context
Metrics Request latency, success rates, error counts; alert if latency exceeds a threshold
Traces Distributed tracing connecting requests across services, showing where delay occurs
  • Centralise the data in a cloud observability platform to derive synthetic metrics and alerts.
  • Observe the communication tissue, not only applications:
    • consumers, producers, exchanges and queue sizes reveal bottlenecks and misbehaving components, and the evolution of the consumed message rate shows what is running behind
    • This drives elasticity decisions.
  • Watch out for: data overload (alert fatigue; focus on essential signals), incomplete traces (missing spans hide dependencies), and latency and cost of telemetry (use sampling or prioritise critical data).

3.8 Leverage location transparency

One communication abstraction across all dimensions of scale.

  • Elastic systems must adapt to demand
    • Key insight: we are all doing distributed computing, even on one node (CPUs communicating over the Intel QuickPath Interconnect, QPI) or a cluster, so there is little conceptual difference between scaling vertically on multicore and horizontally on a cluster.
  • The traditional way uses different tools for each level (callbacks within a core, threads and locks across cores, pub/sub across nodes and clouds): semantic mismatches, hard-coded communication style and topology.
  • Instead unify all communication through asynchronous messaging: one programming model and semantics across scale, "from core to socket, from socket to CPU, from CPU to container, from container to server, from server to rack, from rack to data center, from data center to region, from region to multi-cloud, and from multi-cloud to global edge"
    • Asynchronous messaging is the only semantically equivalent way.
  • Location transparency
    • is decoupling in space plus decoupling runtime instances from their references
    • It is often mistaken for "transparent distributed computing" but is the opposite: it embraces the network's constraints (partial failure, network splits, dropped messages) as first-class.
  • It differs from transparent remoting or distributed objects, which Martin Fowler said "sucks like an inverted hurricane": they hide the network and make everything look local, but local and distributed communication have vastly different semantics and failure modes
    • RPC, EJBs, CORBA and distributed transactions are named as leaky abstractions.
  • If components support location transparency and mobility and local communication is only an optimisation, you need no static topology or deployment model up front
    • operations and the runtime can decide.
  • Asynchronous message passing also shifts focus from low-level plumbing to workflow, communication patterns and collaboration.

3.9 Log events

Make the event log the backbone for durability, communication and integration.

  • Disk was expensive, which is why most SQL databases update in place
    • Jim Gray (Turing Award winner) is quoted: "Update-in-place strikes many systems designers as a cardinal sin: it violates traditional accounting practices that have been observed for hundreds of years." Still, CRUD was born.
  • Disk is now cheap, so there is little reason to use update-in-place for a system of record. We can store everything ever created
    • "CRUD has been distilled to CR": create new facts, read from any point in history.
  • This is guidance, not a rule: legal (data retention laws) or moral (account deletion requests) requirements may require physical deletion.
  • An event log stores facts in causal order:
    • not a database of current state but of everything that ever happened
    • Time is a natural index for replay for debugging, auditing, replication and failover
    • Pat Helland: "The truth is the log
    • The database is a cache of a subset of the log."
  • Event sourcing
    • captures state changes triggered by commands as new events stored in arrival order, such as OrderCreated, PaymentAuthorized or PaymentDeclined
    • The log is an explicit transaction log available for querying, auditing and replay from any time, a "bulletproof failover mechanism and audit log".
  • Benefits:
    • an always up-to-date in-memory snapshot (memory image), a fully durable in-memory database per component
    • entities sharded across the cluster with commands routed to shards (Akka)
      • in Akka entities can also have multiple live instances with primary-primary replication and CRDTs merging concurrent writes, enabling multi-region and multi-cloud
    • no object-relational impedance mismatch: use any domain data structures
      • master data sits on disk in append-only format, giving the single writer principle and "mechanical sympathy" (a quote long attributed to Jackie Stewart)
  • Combine with CQRS for the query and consistency problems
    • Each event-sourced entity publishes an event stream (usually through a message broker) that many parties subscribe to: a query-optimised database, services coordinating workflow, and audit or replication infrastructure.

3.10 Untangle reads and writes

Scale your reads separately from your writes for better resilience and scalability.

  • CQRS (command query responsibility segregation), coined by Greg Young, separates the write model from the read model so each can use different techniques.
  • The read model is better defined as anything that depends on data written by the write model: query models, but also other readers on the event stream (services performing a side effect, downstream systems)
    • That broader view underpins reliably orchestrating workflow across services.
  • It helps each service own its data. Example: OrderService needs product information from InventoryService
    • instead of asking each time, it keeps its own read-only copy updated in real time by subscribing to InventoryService's events (Figure 3-6).
  • Two advantages:
    • Resilience:
      • temporal decoupling of writes from the actions taken in response (index updates, stream processing, side effects, cross-service work)
      • the services need not be available at the same time, which avoids retries and allows eventual consistency.
    • Scalability:
      • scale reads and writes independently. A read-mostly system may run tens or hundreds of query nodes with three to five write nodes for availability
      • a write-mostly system (probably sharded) the opposite.
  • Multiple read models (views),
    • for example SQL or NoSQL for queries, a search database, a time-series database, and stream processing for trends
    • A new model can be added at any time by replaying the event log: with the log as the single source of truth you can produce any view (polyglot persistence).
  • CQRS is a general design pattern usable with almost any persistence, but fits event sourcing; each can be used without the other.
  • Trade-offs:
    • CQRS with event sourcing forces you to face the essential complexity head on; for an MVP, prototype or throwaway you may do better starting with CRUD and a monolith.
    • Write and read sides take time to become consistent, "often only a matter of milliseconds to a few seconds", which can have a big design impact.
    • To mitigate, write the event and update the read model in the same database transaction, but only within a single service (not across services, so each owns its data), and with care because it can create performance and availability problems and reduce CQRS's value.
  • Embrace reality: the world is seldom strongly consistent, so relaxing consistency raises headroom for resilience, performance and elasticity.

3.11 Minimize consistency

Batter the consistency mechanisms down to a minimum.

  • James Hamilton: "The first principle of successful scalability is to batter the consistency mechanisms down to a minimum."
  • ACID 2.0, a term coined by Pat Helland, summarises principles for eventually consistent protocol design:
    • Associative: grouping and batching of messages does not matter
    • Commutative: ordering does not matter
    • Idempotent: duplication does not matter
    • Distributed: the environment where it applies
  • Eventual consistency raises the ceiling on scalability, availability and reduced coupling, but sometimes gives up too much business semantics
    • Then use causal consistency: what humans find intuitive, scalable and available, and (per the chapter) proven the best achievable in an always-available system.
  • Implement causal consistency with logical time (vector clocks, CRDTs, event logging) rather than wall-clock timestamps, which suffer clock skew and cross-node coordination problems.

3.12 Compose sagas

Manage long-running business transactions with sagas.

  • Transactions are fine within well-defined consistency boundaries (a service, entity or actor) using a SQL database, distributed SQL or event sourcing
    • What is problematic is extending transactional semantics across services.
  • Transactions try to maintain the illusion of a single, globally strongly consistent present, magnified in distributed transactions (XA, two-phase commit)
    • Pat Helland: "Developers simply do not implement large scalable applications assuming distributed transactions." If elasticity, scalability and availability do not matter, 2PC is available.
  • The saga pattern is a failure-management alternative for long-running business transactions using compensating actions. Hector Garcia-Molina defined it in 1987 to shorten the time a database holds locks
    • it was not made for distributed systems but suits them.
  • One long distributed transaction is a composition of quick local transactional steps, each paired with a compensating action (reversing in business semantics, not necessarily resetting state) so the whole can be reversed on failure
    • Ideally steps are commutative so they can run in parallel.
  • A saga is usually run by a coordinator, a single centralised FSM made durable, preferably through event logging so it can be replayed on failure.
  • It is eventually consistent, event based and fits asynchronous decoupled components (Figure 3-7).
  • Limit:
    • sagas give atomicity but not isolation
    • concurrent sagas can affect each other. If that is unacceptable, avoid spanning multiple consistency boundaries or use another pattern.

3.13 Guard connections

Ensure graceful degradation.

  • Quote from George Candea and Armando Fox ("Recursive Restartability"): components should be able to deny service for any request, and apps must be designed to "take No for an answer" and decide whether to give up, wait and retry, or reduce fidelity.
  • You may be at the mercy of systems that do not offer asynchronous nonblocking APIs or take part in backpressure
    • to be safe you must protect yourself against crashes and spikes and keep providing at least a degraded service.
  • Little's law,
    • L = λ × W, so W = L / λ: W is mean response time (time in the queue), L is mean queue length, λ is the effective arrival rate (Figure 3-8)
    • You can measure but not control the arrival rate, but you can control the queue length, and so the response time.
  • Ways to control queue length:
    • Drop messages and make the producer retry after a timeout (load shedding)
    • Block the producer or throw exceptions (for synchronous calls); not both
    • Flow control by negotiation (backpressure)
    • Circuit breaker
  • Timeouts
    • are essential: they bound waiting
    • if no response arrives the request is assumed failed, so the system can log, fail gracefully or trigger alternatives. Without them one stalled request can block resources and cascade.
  • Retries help with transient issues, but must be managed so they do not overwhelm services: a maximum retry limit, exponential backoff, and idempotent operations so duplicates do not corrupt data.
  • A circuit breaker is an FSM with three states:
    1. Closed (default): all requests pass.
    2. Open: after a failure or a number of failures it trips, lets nothing through and fails fast, shielding the component; some implementations register a fallback for graceful degradation.
    3. Half-open: after a timeout it tries to reset; if the next request fails it returns to open and resets the timeout, if it succeeds it returns to closed (Figure 3-9).

3.14 Model with actors

Model distribution, autonomy, bulkheading, mobility and location transparency with actors.

  • Carl Hewitt invented the actor model in 1973,
    • "well ahead of his time": a computational model embracing nondeterminism, assuming all communication is asynchronous
    • That enables concurrency and, with long-lived stable addresses to stateful isolated autonomous actors, decoupling in time and space, so service distribution, location transparency and mobility.
  • The author says multicore, cloud and edge, IoT and mobile have caught up with it, and that he created Akka to put the actor model in every developer's hands.
  • An actor combines processing, storage and communication in one bulkheaded, autonomous, mobile, location-transparent unit.
  • Actors communicate by asynchronous message passing
    • Each has a mailbox (a local dedicated queue, messages processed in arrival order) and a serialisable, mobile reference (ActorRef in Akka, PID in Erlang) decoupled from the runtime instance
    • The sender need not know where the actor is or whether it is running (recovering, updating or relocating).
  • An actor is single-threaded, multiplexed on a thread pool, so it is a natural consistency boundary: mutable state inside is safe without locks, races or deadlocks
    • Concurrency comes from running many actors ("actors always come in systems")
    • They are very light: in Akka you can run millions of actors on a single GB of RAM.
  • Three axioms: on receiving a message an actor can
    • create new actors,
    • send a message to an actor it has a reference to,
    • designate how it handles the next message, so behaviour changes at runtime, making finite-state machines easy
  • Actors are natural bulkheads:
    • one failing does not affect others
    • with no blocking calls there is no cascading failure
    • failures are contained and reified as messages sent to whoever registered interest, so actors can supervise each other.
  • They embody most principles and many patterns here: asynchronous communication, location transparency, autonomy, decoupling, virtual addressing, localised state, consistency boundary, isolated mutations, bulkheading, mobility, decentralisation, message-driven design.
  • Akka layers higher-level patterns on top: replication, sharding, cluster membership, leader election, flow control, stream processing, event sourcing, CQRS, sagas and more.

3.15 Supervise subordinates

Build self-healing systems using supervisor hierarchies.

  • If components are bulkheads with asynchronous boundaries and failures are reified as messages, systems can heal themselves without human intervention
    • Supervisor hierarchies formalise this, used successfully in actor languages and platforms (Erlang invented it, and Akka uses it).
  • Parents supervise the life cycle of subordinates.
    • A subordinate never manages its own failure: it crashes and notifies its parent
    • This is the fail fast philosophy, also "let it crash" or "crash-only software".
  • The supervisor chooses a strategy: resume or restart the subordinate, delegate its work, or escalate to its own supervisor.
  • Figure 3-11 example:
    • a child raises an exception, which is captured and reified as a failure message sent asynchronously to its supervisor. The supervisor decides it is beyond its responsibility and escalates
    • the top-level supervisor restarts the whole chain of failed components recursively, restoring a healthy hierarchy: "self-healing in action".
  • Paired with location transparency, failures are just events, so the same failure-management model scales across nodes, regions or clouds with the same semantics.
  • Failures must be:
    • contained (no cascading)
    • reified as immutable values (facts)
    • signalled asynchronously
    • observed by one to N healthy components
    • managed safely outside the failed context.
  • Vending machine example
    • (Figures 3-12 to 3-14): on the happy path the customer inserts enough coins and gets coffee, and a short payment returns "insert more coins"
    • If the machine is out of beans, telling only the customer is of little use; better to notify the service technician
    • Lesson: define who is responsible for managing a failure versus who merely benefits from knowing it happened.
  • In software, validation errors ("insert more coins") go to the user, who can fix them
    • internal component errors have little value to the user. If each failure is a message, other components (the supervisor) subscribe and act from a safe, separate runtime context, for example restarting or relocating the component.

3.16 Protect critical data

Always protect your critical data from failure and uncertainty.

  • Almost all failures relate to state or data:
    • inconsistent (covered elsewhere)
    • partial (only some of the data you need)
    • corrupted (on the wire or disk)
    • lost (on the wire or disk)
    • duplicated (retransmission after failure).
  • "Out of the Tar Pit" (the page text spells the authors Ben Mosely and Peter Marks) defines two types of state and two types of complexity:
Term Meaning
Input data Essential if it must be referred to in the future (critical, protect at all costs); non-essential if only temporary
Derived data Not essential; can always be derived from input data
Essential complexity Addresses the essence of the problem
Accidental complexity All the rest (infrastructure, performance, elasticity, resilience)
  • The paper's ideal system has three layers (Figure 3-15):
    1. Essential state: the foundation, self-contained, holds essential input data, references nothing else.
    2. Essential logic: the heart, the "business logic"; depends on essential state and nothing else.
    3. Accidental state and control: least important for data; control is the order of things; changes here can never affect essential logic or state, but can be affected by them.
  • In practice use supervisor hierarchies to create a hierarchy of dependency with protective layers: the error kernel pattern (credited to Roland Kuhn's Reactive Design Patterns), an onion-like design.
    • Instead of scattering critical state across services, define a minimal error kernel holding the "not recomputable" input data you cannot lose
      • push risky behaviour out to the leaves of the process tree.
    • The kernel never does dangerous operations itself:
      • it never talks to external resources and never takes user input directly, always delegating to a subordinate
      • So when it receives a message you can assume correctness and safety.
  • It builds on: partition state, communicate facts, isolate mutations, go async, bulkheads, detect failure, guard connections, model with actors, supervise subordinates.

3.17 Detect failure

Employ failure detection for more resilient systems.

  • A distributed system is discrete parts bridged by an unreliable network
    • accurately detecting that a peer is down is important but there is no perfect failure detector
      • Failure detection was introduced in 1996 by Tushar Deepak Chandra and Sam Toueg ("Unreliable Failure Detectors for Reliable Distributed Systems")
    • it is "almost like science mixed with art": educated guesses.
  • Things that can go wrong even with a healthy peer:
    • the request is dropped
    • the response is dropped
    • the request is not successfully executed
    • the request is queued
    • the receiver is struggling with load or garbage collection
    • network congestion delays the request or response.
  • A detector has two properties on two axes, completeness and accuracy:
Property Meaning
Strong completeness Every crashed process is eventually suspected by every correct process ("everyone knows")
Weak completeness Every crashed process is eventually suspected by some correct process ("someone knows")
Strong accuracy No correct process is ever suspected ("no false positives")
Weak accuracy Some correct process is never suspected ("some false positives")
  • Ideally both strong, but every guarantee has a cost: how many false positives can you accept, how fast must detection be? Lower detection latency causes more false positives, for example during a garbage-collection pause.
  • Phi accrual failure detector
    • (Naohiro Hayashibara and colleagues), used in Akka: the suspicion level is a value phi on a scale dynamically adjusted to network conditions, using heartbeat history statistics, and decoupling monitoring from interpretation
    • It never answers yes or no, only a likelihood
    • phi = -log10(1 - F(timeSinceLastHeartbeat)), where F is the cumulative distribution function of a normal distribution with mean and standard deviation estimated from historical heartbeat inter-arrival times (Figure 3-17).
  • SWIM
    • (Das and colleagues, 2002): separates cluster dissemination from heartbeats and adds a quarantine for suspected nodes, marking them faulty after a grace period
    • It combines failure detection with group-membership dissemination and uses delegated heartbeats to bridge network splits, where a node unreachable from one node may be reachable from others:
    1. Node N1 picks a random member N2 and sends PING(N2).
    2. Either N2 replies ACK(N2), or there is a timeout.
    3. On timeout, N1 sends PING(N2) requests to a set of random members RN.
    4. Each RN pings N2; on ACK(N2), RN forwards it to N1.
  • Good failure detection lets the system reroute requests, restart processes or reallocate resources
    • without it a slow or unreachable component may be treated as operational, causing delays, resource lockups or inconsistencies.

3.18 Replicate for resilience

Replicate data for resilience, elasticity and performance.

  • Replication: sharing data between multiple discrete parties (services, nodes, data centres) while ensuring consistency, to raise availability, resilience and elasticity.
Choice Options
Synchronous vs asynchronous Synchronous writes the primary and replica together, strongly consistent. Asynchronous decouples writing from sending to replicas, enabling asynchronous I/O and messaging, batching, and decoupling in space and time for availability, resilience, scalability and elasticity.
Push vs pull Push: continuously send data to replicas as written. Pull (passive): replicas fetch at their convenience, from the primary or from peers; works well with timeout-based caches.
  • Sharding
    • splits a large dataset into shards across servers
    • each holds a subset and can operate independently, improving scalability and performance and allowing horizontal scaling (elasticity).
  • Example:
    • a user dataset indexed by user name, sharded across four nodes, each holding part of the keyspace (Figure 3-19)
    • For redundancy, replicate each partition to at least one other shard node so each holds its own data plus backups of others' (Figure 3-20).
  • Four replication strategies:
    • Primary-replica (active-passive): one primary serves reads and writes; two or more replicas serve only reads; the primary replicates each write (Figure 3-21).
    • Primary-primary
      • (active-active, multi-master): two or more primaries serve reads and writes concurrently, always "hot", replicating bidirectionally
        • The key is conflicting concurrent updates to the same record (Figure 3-22)
        • Options: last write wins (brute force, possible data loss, no application help)
      • store tuples of both writes so the client reconciles on read (leaks complexity to the application)
      • CRDTs (automatic intelligent merging that understands application semantics, guaranteed to converge, but the application must model data as CRDTs; the approach Akka takes).
    • Buddy replication: each instance picks one or more buddies and replicates only to them, often in gossip-based systems (Figure 3-23).
    • Quorum replication: an update completes only after a quorum of copies processed it; better balance of consistency with availability, scalability and performance.
  • Do not replicate everything everywhere; decide the guarantees per dataset.
  • Gifford's parameters (1979): N = nodes storing replicas; W = replicas that must acknowledge an update before it completes; R = replicas contacted for a read.
    • W + R > N and W > N/2: strong consistency.
    • W + R <= N: eventual consistency; risk of reading nodes not yet updated (quorum reads help).
    • W < (N + 1)/2: conflicting writes possible if write sets do not overlap.
  • Ryan Barrett's talk "Transactions Across Datacenters" compares replication and consensus strategies (Figure 3-24)
    • Not covered here: hinted handoff, strict and sloppy quorum, anti-entropy using Merkle trees, read repair.

3.19 Gossip for convergence

Use epidemic gossiping for elastic cluster membership and data convergence.

  • The industry moves towards decentralisation: masterless peer-to-peer meshes that distribute logic and data together. Listed advantages:
    • scalability (distribute data and work across nodes)
    • resilience and high availability (no single point of failure)
    • performance (less bottleneck, more parallelism)
    • data locality (closer to where data is made or used, lower latency)
    • security and privacy (breaching many nodes is harder; data can stay in a region for compliance)
    • cost optimisation
    • reduced vendor lock-in (open source, standard interfaces, multi-cloud and edge)
  • The key problem is making many nodes act as one and disseminating information automatically
    • Many systems use gossip (epidemic) protocols: information spreads randomly between pairs of nodes until it reaches the whole network, like gossip or a virus.
  • Two classes: anti-entropy (gossip until superseded by newer information; reliable sharing) and rumour-mongering (gossip for long enough that all nodes very likely have it).
  • Key features:
    • decentralisation (no central authority)
    • scalability (probabilistic, evenly spread load)
    • fault tolerance (redundant dissemination survives node failures)
    • convergence (nodes eventually agree; exact guarantees depend on the implementation).
  • Gossip makes these easy:
    • Cluster membership: gossip the membership so nodes join, leave or go temporarily unavailable seamlessly (Akka uses push/pull gossip).
    • Failure detection: gossip heartbeats at a set cadence.
    • Leader election:
      • gossip who is leader
      • In Akka the leader is not elected but decided deterministically, the first node in a sorted ring, after cluster convergence (a gossip is seen where all nodes are in the "seen set").
  • Peer-to-peer systems rely on a semantic-free index:
    • each data item has a key
    • each node takes an identifier from the same hash space and stores a subset of keys, giving a distributed hash table (DHT). Chord (Stoica, Morris, Karger, Kaashoek and Balakrishnan, 2001) arranges nodes in a node ring and guarantees finding data in O(log N) jumps (Figure 3-25).
  • Consistent hashing
    • (Karger and colleagues) spreads K objects across N buckets (about K/N each) and, when N changes, moves only about K/N objects, using a base hash function such as SHA-1
    • hash(key) = P in 0..m-1, on a ring where key is the bucket ID, P the position on the ring and m the ring size
    • Buckets and incoming request keys are hashed with the same function onto the ring.
  • Buckets are replicated to more than one node so requests can go to a replica if nodes are lost
    • Reading from several replicas allows stronger consistency: usually a quorum read with an odd replication factor (3, 5 or 7) (Figure 3-26).
  • Gossip can be inefficient with many nodes
    • mitigations are separating failure-detection heartbeats from data dissemination (as in SWIM) and push/pull gossip (Khambatti and colleagues, 2003).
  • Used successfully in Amazon's Dynamo, Apache Cassandra and Akka Cluster (Akka uses Dynamo-style gossiping, biased gossip, push/pull gossip, CRDTs for gossip state and leader election).

3.20 Seek consensus

Leverage consensus algorithms for coordination and consensus.

  • Sometimes you need strongly consistent consensus across components.
  • The FLP impossibility result (Fischer, Lynch and Paterson, 1985): in a fully asynchronous system where at least one process can fail, a deterministic consensus algorithm is impossible (it cannot always terminate)
    • It rests on worst-case scheduling, rare in practice except in adversarial cases such as a targeted denial-of-service attack.
  • Four properties a consensus protocol needs:
Property Meaning
Termination Every process eventually decides a value V
Validity If a process decides V, some process proposed V
Integrity No process decides twice
Agreement No two correct processes decide differently
  • Paxos
    • and Raft are designed with FLP in mind and work in practice
    • Others: Zab (used by Zookeeper) and Viewstamped Replication (predates Paxos, similar to Raft in some ways).
    • Paxos (Leslie Lamport): phases with quorum-based voting; progress even if some processes fail or messages are delayed.
    • Raft (Diego Ongaro and John Ousterhout): simpler and easier to implement; leader election, log replication, strong leader.
  • Two categories:
    • Single-value consensus (agree on one value, often database transaction metadata; binary consensus limits it to {0,1}): Paxos.
    • Multivalued consensus (agree on a growing sequence of values, with optimisations and reconfiguration support): Multi-Paxos and Raft.
  • Raft works in a cluster with one leader and followers. The leader manages the replicated log of commands; followers passively replicate and respond.
    • Leader election: a server hearing nothing from a leader within a timeout becomes a candidate and requests votes; a majority makes it leader (Figure 3-27).
    • Log replication:
      • the leader appends each command to its log and replicates to followers
      • once a majority acknowledge, the entry is committed, applied to its state machine, and followers are told to apply it.
    • Safety: all servers eventually agree on the same entries in the same order even through crashes; leaders commit only entries safely replicated to a majority.
    • It also supports dynamic reconfiguration and log compaction.
  • Why it matters:
    • nodes must agree to avoid conflicts. Example: two users simultaneously try to withdraw the last $100 from the same account on different nodes
    • a protocol like Raft agrees which transaction comes first so the balance is updated consistently and double spending is prevented.

Summary points

  • Treat state as partitioned, immutable facts and event logs; keep mutation inside bulkheaded consistency boundaries.
  • Communicate asynchronously with flow control and location transparency; observe dynamics.
  • Use CQRS, minimal consistency, causal consistency and sagas instead of distributed transactions.
  • Build resilience with guarded connections, actors, supervisor hierarchies, error kernels, failure detection, replication, gossip and, where required, consensus.
Terms to carry forward
  • Fact / event log / event sourcing: immutable events as the source of truth.
  • CQRS: separate write and read models.
  • Backpressure: consumer-driven flow control.
  • Saga: local steps with compensating actions.
  • Circuit breaker: closed, open, half-open FSM.
  • Actor / supervisor hierarchy / error kernel: isolated unit, parent-managed failure, minimal protected core.
  • Phi accrual / SWIM: failure detection approaches.
  • N, W, R: replica count, write acknowledgements, read contacts.
  • Consistent hashing / Chord: balanced key placement and ring lookup.
  • FLP / Paxos / Raft: consensus impossibility and practical protocols.
