Software Architecture Patterns 3: Layered Architecture

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), chapter 3. Previous: Software Architecture Patterns 2: Architectural Structures and Styles. Next: Software Architecture Patterns 4: Microkernel Architecture.

Takeaways
  • The chapter's first sentence calls the layered architecture "otherwise known as the n-tier architecture": in this book the two names are one style.
  • It is the most common style and the de facto standard for most applications, because it matches traditional IT teams organised by technical area (presentation, back end, database).
  • Layers are horizontal; most have four (presentation, business, persistence, database), smaller ones three, larger ones five or more.
  • Closed layers give layers of isolation: a change in one layer generally does not touch the others. An open layer may be bypassed.
  • Watch for the architecture sinkhole anti-pattern. Avoid the style when you need scalability, elasticity, fault tolerance or performance, or when changes are mostly domain-level.

3.1 Description

  • Components sit in horizontal layers, each with one role (presentation logic, business logic, persistence logic).
  • Most layered architectures have four standard layers: presentation, business, persistence, database.
    • Sometimes business and persistence merge into one business layer, particularly when persistence logic such as SQL is embedded in business components.
    • Smaller applications may have three layers; larger, more complex ones five or more.
  • Each layer is an abstraction around the work needed to satisfy a request:
    • the presentation layer handles all user interface and browser communication, and does not need to know how customer data is fetched
    • the business layer executes the business rules
      • it does not care how data is formatted for the screen or where it comes from, only that it gets data from the persistence layer, applies logic (calculating or aggregating) and passes the result up
  • Layers appear as a namespace, package or directory structure
    • Customer functionality is app.business.customer in the business layer and app.presentation.customer in the presentation layer.
    • The second node is the layer, the third is the domain component.
    • The third node (customer) repeats in every layer, which marks a technically partitioned architecture: the domain is spread across all layers.
  • The strength is separation of concerns: each layer's components deal only with that layer's logic.
    • This makes it easy to build roles-and-responsibilities models, and to develop, test, govern and maintain, when well-defined interfaces and contracts sit between layers.

3.2 Key concepts

Closed layers and layers of isolation

  • A closed layer:
    • a request must pass through the layer directly below it to reach the next one
    • A request from the presentation layer goes through the business layer, then the persistence layer, then the database layer.
  • Why not let the presentation layer read the database directly, which is faster? The answer is layers of isolation:
    • a change in one layer generally does not affect components in other layers
    • if presentation could reach the persistence layer, a change to SQL would hit both the business and presentation layers, giving a tightly coupled, brittle application that is hard and expensive to change
  • Each layer is independent, with little or no knowledge of the others' inner workings.
    • Example: converting the presentation framework from angular.js to react.js leaves the business layer unaffected, provided the contracts (the model) between presentation and business stay the same.
    • Example: replacing a relational database with a NoSQL database should affect only the persistence layer, if designed correctly.

Open layers

  • Sometimes a layer should be open: requests may bypass it and go straight to the layer below.
  • The chapter's example is a shared services layer (data and string utilities, auditing, logging) used by business-layer components.
    • A separate layer is a good idea because it architecturally restricts access to those services to the business layer
      • Without it, nothing stops the presentation layer using them, and the restriction is hard to govern.
    • The services layer sits below the business layer, but the business layer should not have to go through it to reach persistence. The age-old fix is to mark the services layer open.
  • Open and closed layers define the relationship between layers and request flows, and tell designers and developers the access restrictions.
  • Failing to document which layers are open or closed, and why, usually gives tightly coupled, brittle architectures that are very hard to test, maintain and deploy.

3.3 Example: retrieving customer information

A business user asks for one customer's details, which consist of customer data and order data.

  1. The customer screen accepts the request and later displays the result. It does not know where the data is, how it is retrieved or how many tables are queried.
  2. It forwards the request to the customer delegate (presentation layer), which knows which business-layer modules can process the request, how to reach them and what data they need (the contract).
  3. The customer object (business layer) aggregates all the information the request needs.
  4. It calls the customer DAO (data access object) for customer data and the order DAO for order data, both in the persistence layer.
  5. The DAOs run SQL and pass the data back up to the customer object, which aggregates it and passes it to the customer delegate, then the customer screen.

3.4 Considerations and analysis

The layered style is well understood and general purpose, a good starting point for most applications, particularly when you are unsure which style fits.

The architecture sinkhole anti-pattern

  • Requests flow through several layers as simple pass-through processing with little or no logic in each.
  • Example:
    • presentation passes a customer request to business, which passes it to persistence, which makes a simple SQL call
    • the data returns up the stack with no aggregation, calculation or transformation.
  • Every layered architecture has some such requests. What matters is the percentage.
    • The 80-20 rule is a good guide: about 20% pass-through and 80% with business logic is typical.
    • If the ratio is reversed and most requests are pass-through, consider making some layers open, remembering this is faster but makes change harder to control because layer isolation is lost.

  • The chapter says the style is as viable today as when introduced
    • Domain-driven design offers a domain perspective, but technically partitioned styles such as layered are still sometimes more suitable.

When to consider this style

  • Tight budget or time:
    • it is generally monolithic, so it avoids the complexity of remote access, contract management and the fallacies of distributed computing
    • Most developers and architects already know it.
  • Most changes isolated to specific layers: business-rule-only changes, user-interface look and feel, migration to a new UI framework, even migration to a new type of database.
  • Technically partitioned teams
    • (UI developers, back-end developers, shared-services teams, database teams): the team structure matches the layers
    • The chapter names this alignment Conway's Law.

When not to consider this style

There are "even more reasons" not to use it:

  1. High operational concerns: scalability, elasticity, fault tolerance, performance.
    • It tends towards a monolith and is generally hard to scale.
    • It can sometimes scale by splitting layers into separate physical deployments or running instances on multiple virtual machines, but this is expensive and inefficient because 100% of the functionality must scale.
    • It is not very fault tolerant: a fatal crash anywhere brings down all functionality.
  2. Most changes are domain-level rather than technical.
    • Example: adding an expiration date to "My Movie List" in a movie streaming application (movies queued to watch later).
    • It needs a database schema change, then SQL in the persistence layer, then business rules and contracts (how long before expiry, what to do when a movie expires), then the presentation layer to show the date beside each movie.
    • Every layer changes; with technically partitioned teams this can mean coordinating the UI, back-end and database teams, which hurts agility and costs time and effort.
  3. Cross-functional domain teams (one team with UI, back-end and database skills per domain): a technical structure does not match a domain team structure.

Summary points

  • Layered = n-tier in this book; four typical layers, technically partitioned.
  • Closed layers isolate change; open layers (for example a shared services layer) allow bypass; document which is which.
  • Strengths: simplicity, low cost, familiarity, fit with technically organised teams.
  • Weak points: scalability, fault tolerance, agility and extensibility, and domain-wide changes that touch every layer.
Terms to carry forward
  • Closed layer / open layer: a request must pass through / may bypass the layer.
  • Layers of isolation: a change in one layer does not affect others.
  • Architecture sinkhole: requests that are pure pass-through in several layers.
  • 80-20 rule: about 20% pass-through requests is typical.
  • DAO: data access object.
  • Conway's Law (as the chapter uses it): team structure aligned with architecture structure.
