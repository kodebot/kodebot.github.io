Software Architecture Patterns 4: Microkernel Architecture

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), chapter 4. Previous: Software Architecture Patterns 3: Layered Architecture. Next: Software Architecture Patterns 5: Event-Driven Architecture.

Takeaways
  • A core system plus independent plug-in modules: functionality is added as extensions without touching the core, which is why it is also called a plug-in architecture.
  • A natural fit for product-based applications, common in internal business applications, and implemented by many operating systems (hence the name).
  • A plug-in registry tells the core which plug-ins exist and how to reach them. Plug-ins can be libraries, packages in one codebase, or remote services; only the last makes it distributed.
  • It can be technically partitioned (plug-ins as adapters or configuration) or domain partitioned (plug-ins add functionality).
  • Weak points: the core is a bottleneck, so scalability, elasticity and fault tolerance are poor.

4.1 Topology

  • Two component types: a core system and plug-in modules.
  • Application logic is divided between independent plug-ins and the basic core, giving extensibility, flexibility and isolation of features and custom processing.
  • The core can be minimal (older IDEs such as Eclipse) or more full featured (web browsers such as Chrome); either way it is extended by separate plug-ins.
  • Plug-in modules are standalone, independent components holding specialised processing, extra features, adapter logic or custom code.
    • They should be independent of each other and not depend on other plug-ins to work.
    • Keep communication between plug-ins to a minimum to avoid confusing dependency issues.

The plug-in registry

  • The core must know which plug-ins are available and how to reach them
    • One common way is a plug-in registry holding each plug-in's name, contract details and remote access protocol details (depending on how it connects).
  • Example: a tax-software plug-in that flags items as a high audit risk might have a registry entry with the service name AuditChecker, the contract (input and output data) and the contract format (XML).
  • When contracts and the access protocol are standard across the system, the registry may hold only the plug-in name and an interface name for invoking it.

Connecting plug-ins

  1. Separate libraries or modules (JAR and DLL files) connected point-to-point, such as a method call through an interface.
    • Managed by frameworks such as OSGi (Open Service Gateway Initiative), Java Modularity, Jigsaw, Penrose and Prism, or .NET environments.
    • Deployment is then a monolithic (single deployment) architecture.
    • A common technique is dropping a file in a directory and restarting the application; some frameworks support adding or changing plug-ins at runtime without a restart.
  2. A single consolidated codebase, manifested as a namespace or package structure.
    • Example:
      • an electronics-recycling application with a plug-in assessing a specific device, namespaced app.plugin.assessment.iphone12
      • The second node marks it as a plug-in, so its code stays separate from the core.
  3. Remote services, accessed from the core through REST or messaging interfaces.
    • The architecture is then distributed.
    • All requests still go through the core, but runtime deployment of plug-ins is easier, and scalability and responsiveness may improve when several plug-ins serve one business request.

4.2 Examples

  • Eclipse IDE: the basic download is little more than a fancy editor; plug-ins make it a highly customisable development tool.
  • Internet browsers: viewers and other plug-ins add capabilities the basic browser (the core) lacks.
  • Developer and pipeline tools such as PMD, Jira and Jenkins are implemented with microkernel architecture.
  • Business applications too: tax software, electronics recycling, insurance.

Insurance claims processing

  • Claims software is very complicated because each jurisdiction (for example a US state) has different rules
    • some allow a free windshield replacement for rock damage, others do not. That creates "an almost infinite set of conditions".
  • Most claims applications use large, complex rules engines, which can become a big ball of mud: changing one rule affects others, or needs an army of analysts, developers and testers for a simple change.
  • The microkernel answer (Figure 4-2):
    • the core holds the basic claim-processing logic, which rarely changes, with no jurisdiction processing
    • plug-ins hold each jurisdiction's rules.
    • The figure shows New Hampshire, Texas, Georgia, California, New York and Massachusetts rules.
    • Plug-ins can be custom source code or separate rules-engine instances.
    • Jurisdiction rules can be added, removed and changed with little or no effect on the core or other plug-ins.

4.3 Considerations and analysis

  • Very flexible, varies greatly in granularity. It can be the overarching architecture or be embedded inside another style: a particular event processor, domain service or even a microservice can use it while other services are built differently.
  • Evolutionary design and incremental development: produce a minimal core with the primary functionality and add features over time without significant changes to the core.
  • Either partitioning, depending on use:
    • plug-ins as adapters or specific configuration: technically partitioned
    • plug-ins as extensions or additional functionality: more domain partitioned

When to consider this style

  • A starting point for a product-based application, or a custom application with planned extensions, particularly when you release features over time or control which users get which features.
  • Applications or products with multiple configurations per client environment or deployment model
    • Example: an application deployable on any cloud, with plug-ins acting as adapters for each vendor's services while the core stays agnostic of the cloud.
  • Like layered, it is relatively simple and cost-effective, a good choice under tight budget and time.

When not to consider this style

  • All requests go through the core,
    • whether plug-ins are remote or point-to-point, so the core is the main bottleneck: not suited to highly scalable and elastic systems
    • Fault tolerance is also poor because the core is the single entry point.
  • A goal of the style is to reduce change in the core and push volatility out to plug-ins, which are self-contained and easier to test and change
    • If most changes are in the core and plug-ins are not holding extra functionality, it is likely a poor match.

Summary points

  • Minimal or full-featured core plus independent plug-ins behind a contract; a registry locates them.
  • Monolithic when plug-ins are libraries or packages; distributed when plug-ins are remote services.
  • Good for products and planned extensions; poor for scale and fault tolerance because every request passes through the core.
  • Technically or domain partitioned, depending on what plug-ins do.
Terms to carry forward
  • Core system: the minimal (or fuller) base the plug-ins extend.
  • Plug-in module: standalone component with extra or specialised functionality.
  • Plug-in registry: the core's record of each plug-in's name, contract and access protocol.
  • OSGi: Open Service Gateway Initiative, a framework for managing plug-in modules.
  • Product-based application: packaged software released in versions, such as a downloadable third-party product.
