Software Architecture Patterns 7: Space-Based Architecture

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), chapter 7. Previous: Software Architecture Patterns 6: Microservices Architecture. Next: Software Architecture Patterns A: Style Analysis Summary.

Takeaways
  • Built for extreme scalability and concurrency and for elastic systems with variable, unpredictable user volumes.
  • It removes the database from transactional processing: data lives in replicated in-memory data grids inside the processing units, and is synchronised to a database asynchronously through data pumps.
  • Virtualized middleware manages the complexity: messaging grid, data grid, processing grid (optional) and deployment manager.
  • Complex and expensive, so not a general-purpose style; large data volumes, tight budgets and high consistency needs rule it out.
  • Technically partitioned. Top ratings for scalability and performance; low simplicity and agility.

7.1 The problem it solves

  • A typical web request flows from browser to web server, then application server, then database server
    • This is fine for few users, but as load grows bottlenecks appear first at the web server, then the application server, then the database.
  • The usual answer is to scale out web servers:
    • relatively easy and inexpensive, but it usually just moves the bottleneck to the application servers
    • Scaling those is more complex and costly and moves the bottleneck down to the database, which is hardest and most expensive to scale.
  • The result is a triangle: widest at the web servers (easiest to scale), narrowest at the database (hardest).
  • In any high-volume application with an extremely large concurrent user load, the database is usually the final limit on concurrent transactions
    • Caching, scaling and sharding products help, but scaling for extreme loads is "a very difficult proposition" at the database.
  • Space-based architecture is designed for these high scalability and concurrency problems, and for elastic systems with variable and unpredictable concurrent users.

7.2 Topology and components

  • The style removes the database from transactional processing, hence the name
    • It takes its name from the computer-science term tuple space: multiple parallel processors with shared memory.
  • High scalability comes from replacing the database with replicated in-memory data grids during transactional processing
    • Data is kept in memory, replicated among all active processing units, and synchronised with a background database asynchronously through data pumps.
  • Processing units
    • start and stop dynamically as load rises and falls, which handles variable scalability
    • With no database in transactional processing, the bottleneck is removed, giving "near-infinite scalability within the application".

Processing unit

  • What the style calls a service. It holds the business functionality and ranges from a single-purpose function to the whole application.
  • Each contains business logic, an in-memory data grid with transactional data, and optionally web-based components.
  • Units may communicate directly with each other or through the processing grid of the virtualized middleware.

Virtualized middleware

The middleware manages request and session handling, data synchronisation, communication and orchestration between processing units, and the dynamic starting and stopping of units for elasticity. It has four main components:

Component Job
Messaging grid Manages input request and session information. It finds which active processing units can take a request and forwards it to one. Its complexity ranges from a simple round-robin algorithm to a next-available algorithm that tracks which unit is processing which request. Typically implemented by a traditional web server.
Data grid "Perhaps the most important and crucial component". It works with each unit's data-replication engine to replicate updates between units. Because the messaging grid can send a request to any unit, every unit must hold exactly the same data. Typically implemented with caching products such as Hazelcast, Apache Ignite and Oracle Coherence; synchronisation is usually asynchronous behind the scenes.
Processing grid (optional) Manages distributed processing for requests needing coordination or orchestration between processing-unit types. Orchestration can run through the grid or directly between units in a choreographed fashion.
Deployment manager Starts and stops processing units based on load, continually monitoring response times and user loads; critical for variable scalability. Usually implemented with container orchestration such as Kubernetes.

Data pumps, writers and readers

  • A data pump asynchronously sends updates to a database. It is typically implemented with persistent queues using messaging or streaming.
  • Data writers
    • listen asynchronously for those updates and update the database
    • They range from application-level custom writers or data hubs to dedicated writers per processing-unit type.
  • On a cold start after a crash or deployment, data readers use a reverse data pump to fetch data from the database into a processing unit
    • Once at least one unit with the same in-memory grid is populated, further units can start and be populated without going to the database.

7.3 Examples

The chapter calls it "very complicated and specialized", used mainly for high-volume, highly elastic systems needing very fast performance.

  • Concert ticketing.
    • When tickets for a favourite band's show go on sale, concurrency jumps from a few dozen to tens of thousands within seconds, all wanting the same seats
    • continuous database reads and writes "simply isn't feasible".
  • Online auctions and bidding. Sellers do not know how many will bid, and bidding gets "fast and furious" near the end, then falls to a minimum before the cycle repeats.
  • High-volume social media.
    • Hundreds of thousands, even millions, of posts, likes, dislikes and responses within seconds
    • the database gets in the way regardless of elasticity, so removing it from transactions and persisting eventually is one possible solution.

7.4 Considerations and analysis

  • A complex and expensive style, so not suitable as a general-purpose architecture like the others in the report; it is for high scalability, elasticity and performance.
  • Unique deployment model: the whole architecture can be cloud only, on prem only, or split.
    • The split model suits cloud-based processing where the data must stay on prem: data writers and readers sit on prem with the database, and asynchronous data pumps send data from cloud processing units to them.
  • It is technically partitioned:
    • domain functionality is spread across processing units, in-memory grids, data pumps, writers and readers
    • A domain change, particularly one involving data, usually affects all of these.

When to consider this style

  • Very high concurrent scalability or elasticity: processing tens of thousands of concurrent requests or more is a big challenge with a database, and this style takes the database out of the equation.
  • Very high performance and responsiveness: it relies on in-memory caching, so data update and retrieval are usually measured in nanoseconds, which the chapter calls the most responsive and highest-performing of all the styles in the report.

When not to consider this style

  • Large data volumes. All transactional data sits in memory, so data size is a limit. The chapter's image: "a 45-terabyte relational database" cannot fit in memory.
  • Tight budget and time:
    • it is technically complex
    • Reproducing very high user loads in a test environment is expensive and slow, so testing scalability is hard, and agility is fairly low.
  • High data consistency: it is always eventually consistent, and updates to the in-memory grids may take a long time to reach the database.

Summary points

  • Processing units with replicated in-memory data grids replace the database in transactional processing; data pumps persist updates asynchronously.
  • Virtualized middleware (messaging grid, data grid, processing grid, deployment manager) manages routing, replication, orchestration and elasticity.
  • Right for extreme, elastic concurrency (ticketing, auctions, social media); wrong for big data volumes, tight budgets or high consistency.
Terms to carry forward
  • Tuple space: multiple parallel processors with shared memory; the origin of the style's name.
  • Processing unit: the style's service: logic plus in-memory data grid (plus optional web components).
  • Virtualized middleware: messaging grid, data grid, processing grid, deployment manager.
  • Data pump / data writer / data reader: asynchronous persistence and cold-start reload.
  • Elastic system: variable and unpredictable concurrent user volume.
