Software Architecture Patterns A: Style Analysis Summary

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), appendix A. Previous: Software Architecture Patterns 7: Space-Based Architecture.

Takeaways
  • Figure A-1 puts the architecture-characteristic scores of all five styles in one chart, one dot for not well supported up to five dots for well supported.
  • If scalability is your main concern, the event-driven, microservices and space-based styles are probably good choices; if you choose layered, deployment, performance and scalability may be risk areas.
  • The chart helps, but choose by analysing the whole environment: infrastructure support, developer skill set, budget, deadlines and application size.
  • Once an architecture is in place it is very hard and expensive to change, so choosing the style is critical.

A.2 How the appendix says to use it

  1. Find your primary architecture concern (for example scalability) and read across the chart.
    • Scalability points to event-driven, microservices and space-based.
  2. For a style you already chose, read down its column for risk areas.
    • Layered: scalability, performance and deployment.
  3. Then go beyond the chart and analyse:
    • infrastructure support
    • developer skill set
    • project budget and deadlines
    • application size

Summary points

  • One chart compares five styles on eight rows; the per-chapter charts agree with it.
  • Match the style to your top concern, then check the risks in its column and the wider environment.
Terms to carry forward
  • T / D / D/T: technical, domain, or either partitioning.
  • Rating scale: one dot not well supported, five dots well supported.
