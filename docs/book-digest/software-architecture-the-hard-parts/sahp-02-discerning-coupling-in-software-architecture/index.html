Software Architecture: The Hard Parts 2: Discerning Coupling in Software Architecture

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 2. Previous: Software Architecture: The Hard Parts 1: What Happens When There Are No "Best Practices"?. Next: Software Architecture: The Hard Parts 3: Architectural Modularity.

Takeaways
  • Coupling is not inherently bad ("the dosage alone makes the poison", Paracelsus); advice to "decouple everything" gives no guidance for building useful systems.
  • Trade-off analysis in three steps: find what is entangled, analyse how it is coupled, assess the impact of change on interdependent parts.
  • An architecture quantum is an independently deployable artifact with high functional cohesion, high static coupling and synchronous dynamic coupling.
  • Static coupling is how things are wired (dependencies, database, broker); a shared database or orchestrator collapses many services into one quantum.
  • Dynamic coupling is how quanta communicate at runtime, in three interlocking forces: communication, consistency, coordination; their 8 combinations give the saga pattern names in Table 2-1.

2.1 Why coupling needs untangling

  • Opening scene:
    • Penultimate's architects debate sagas, orchestration, ESBs versus Kafka ("an apples-to-oranges comparison") and decoupling. Logan: if everything were decoupled "nothing can communicate with anything else"
    • coupling is not bad, architects must know how to apply it appropriately.
  • Architects struggle with granularity and communication decisions because no universal guides exist
    • Generic advice says "decouple" but not how to do it while still building useful systems.
  • Why did complexity ramp up with microservices when distributed systems date from the last century? Because of the bounded context: transactionality became a first-class architectural concern. Earlier, event handlers usually connected to one relational database, which handled integrity and transactions
    • moving the database inside the service boundary moves data concerns into architecture concerns.
  • Trade-off frameworks such as ATAM (Architecture Trade-off Analysis Method) exist but "lack focus on real problems architects face on a daily basis".
  • Entanglement is like a braid (Figure 2-1): individual strands are hard to see. The first step is to untangle the dimensions of the problem.
  • Definition: two parts of a software system are coupled if a change in one might cause a change in the other.
  • The framework, simple in steps with hard parts "in the details":
    1. Find what parts are entangled together.
    2. Analyse how they are coupled to one another.
    3. Assess trade-offs by determining the impact of change on interdependent systems.
  • The worked problem, close to generic for microservices:
    • how do architects determine the size and communication styles of microservices? Too-small services create transactional and orchestration issues
    • too-large services create scale and distribution issues.

2.2 Architecture quantum

  • Name origin:
    • Latin quantus, "how great" or "how many"
    • the legal profession used it for the required or allowed amount (damages)
    • it appears in topology
    • singular quantum, plural quanta (like datum/data).
  • Definition:
    • an architecture quantum is an independently deployable artifact with high functional cohesion, high static coupling and synchronous dynamic coupling
    • A common example is a well-formed microservice within a workflow.
  • Static coupling
    • is how static dependencies resolve through contracts: operating system, frameworks, libraries (including transitive dependencies) and any other operational requirement for the quantum to operate. Dynamic coupling is how quanta communicate at runtime, synchronously or asynchronously
    • its fitness functions must be continuous, typically via monitors.
  • The difference:
    • static coupling describes how services are wired together (operational dependencies)
    • dynamic coupling describes how services call one another at runtime (communication dependencies). Example: a service must contain its database (static)
    • it may call other services in a workflow (dynamic), but neither needs the other present to function apart from that runtime workflow.

Independently deployable

  • Each quantum is a separate deployable unit. A monolith is by definition one quantum.
  • Three uses of the boundary:
    1. A common language for architects (coupling), developers (scope of behaviour) and operations (deployable characteristics).
    2. It captures one of the forces (static coupling) architects weigh when choosing service granularity: release cadence, other services affected, engineering practices (Chapter 7).
    3. It forces inclusion of common coupling points such as databases and user interfaces. A system with a shared database fails the independent-deployment criterion unless the database deploys in lockstep with the application. Many distributed systems that would otherwise be several quanta fail here.

High functional cohesion

  • The proximity of related elements (classes, components, services)
    • It overlaps with the bounded context in domain-driven design: behaviour and data implementing a particular domain workflow.
  • A giant monolith qualifies for independent deployability but is almost certainly not functionally cohesive; the larger the monolith, the less likely it is.
  • In microservices each service ideally models a single domain or workflow. Cohesion here is about how independent one service is from another, not how they interact.

High static coupling

  • Elements inside the quantum are tightly wired, which is an aspect of contracts: REST and SOAP formats, but also method signatures and operational dependencies such as IP addresses or URLs (Chapter 13).
  • Quantum counts by topology:
    • Monolithic styles are always one quantum (Figure 2-2). A single deployment unit with a single database cannot exceed one quantum; the database is the usual single coupling point.
    • Service-based architecture
      • (Figure 2-3) stays at one quantum because of its single relational database
      • The authors define it here as a specific hybrid style: separately deployed user interface, separately deployed remote coarse-grained services, and a monolithic database
      • It avoids database separation, and services follow the bounded-context principles of microservices
      • It is a common target when restructuring monoliths, decomposing without disrupting existing schemas and integration points (Chapter 5).
    • Mediated event-driven architecture
      • (Figure 2-4) is always one quantum: the database plus the Request Orchestrator
      • "any holistic coupling point necessary for the architecture to function forms an architecture quantum around it".
    • Broker event-driven architecture
      • (Figure 2-5, no central mediator) is also one quantum when all services share a relational database
      • The static question: "Is this dependency of the architecture necessary to bootstrap this service?" Services that rely on services that use the database join its quantum.
    • Event-driven with two data stores
      • and no static dependencies between the sets of services (Figure 2-6) gives multiple quanta
      • each can run in a production-like ecosystem though not take part in every workflow.
    • Microservices (Figure 2-7) can each form their own quantum, with each service (as a bounded context) able to have its own architecture characteristics, such as scalability or security.
    • A tightly coupled user interface (Figure 2-8) reduces it to one quantum: most UIs will not operate if parts of the back end are unavailable, and it is hard to give services different operational characteristics if they all share one UI (especially with synchronous calls).
    • Micro-frontends (Figure 2-9): service-emitted UI elements on a shared canvas with loosely coupled, event-based communication; each service plus its UI component forms a quantum.
    • A shared database between two systems (Figure 2-10) couples them into one quantum.
  • The operating system, data store, message broker, container orchestration and every other operational dependency are static coupling points, using the strictest possible contracts.
  • Practical use: architects draw a static quantum diagram of how legacy systems are wired to see what a change affects and how to decouple.

2.3 Dynamic quantum coupling

Three interlocking forces form a multidimensional decision space:

Force Question
Communication Synchronous or asynchronous?
Consistency Does the workflow need atomicity, or can it use eventual consistency?
Coordination Does the workflow use an orchestrator, or do services choreograph?

  • Communication.
    • Synchronous (Figure 2-11): the requestor waits for the receiver's response, for example over gRPC, blocking until a value, status or error comes back.
    • Asynchronous
      • (Figure 2-12): the caller posts a message (usually via a message queue) and, once acknowledged, returns to work
      • a reply queue can asynchronously return a result. Queues create diagram noise, so many architects omit them, which still implies asynchronous messaging
      • queues are not required.
    • The choice affects synchronisation, error handling, transactionality, scalability and performance.
  • Consistency.
    • Strictness of transactional integrity: atomic (all-or-nothing, consistent during the request) at one end, degrees of eventual consistency at the other
    • Transactionality across services is "one of the most difficult problems to model", so the general advice is to avoid cross-service transactions (Chapters 6, 9, 10, 12).
  • Coordination.
    • How much coordination the workflow needs: orchestration or choreography (Chapter 11). A single service replying to a request needs no special consideration
    • the more complex the workflow, the greater the need.
  • The forces cannot be chosen in isolation
    • each has a "gravitation effect" on the others. Example: transactionality is easier in synchronous architectures with mediation, while higher scale is possible with eventually consistent asynchronous choreographed systems.

The eight combinations (Table 2-1)

Letter codes: s/a communication, a/e consistency, o/c coordination.

Pattern name Communication Consistency Coordination Coupling
Epic Saga (sao) synchronous atomic orchestrated very high
Phone Tag Saga (sac) synchronous atomic choreographed high
Fairy Tale Saga (seo) synchronous eventual orchestrated high
Time Travel Saga (sec) synchronous eventual choreographed medium
Fantasy Fiction Saga (aao) asynchronous atomic orchestrated high
Horror Story (aac) asynchronous atomic choreographed medium
Parallel Saga (aeo) asynchronous eventual orchestrated low
Anthology Saga (aec) asynchronous eventual choreographed very low

  • Part I focuses on static coupling and the dimensions (data ownership, transactionality, granularity)
    • Part II ("Putting Things Back Together") focuses on dynamic coupling and communication patterns, entangling the dimensions again in Chapter 12.

2.4 Sysops Squad saga: understanding quanta

  • Addison to Austen:
    • the quantum "basically defines a DDD bounded context in architectural terms". The authors do not reuse "bounded context" because it has a specific DDD definition and overloading it would force constant differentiation
    • the first part (cohesion and independent deployment) matches a bounded-context service, but the quantum goes further by typing coupling.
  • Static coupling
    • is "how things are wired together"
    • Test: what wiring would you need to bootstrap this service from scratch? Not just Java, Postgres and Docker but Spring Boot and 15 to 20 frameworks and libraries (visible in the Maven POM) and the event broker
    • The presence of the broker is static; calling another service through it is dynamic.
  • Use:
    • a defensive static quantum diagram per service for reliability and risk analysis ("if we change a service, what must be tested?") and to show how teams impact each other. No open-source tool exists for their mix of architecture
    • the platform team is automating it from container manifests, POM files, NPM dependencies and other dependency tools, plus service observability log files that build a call graph.
  • Dynamic coupling
    • concerns synchronous versus asynchronous calls and their effect on performance, scale, elasticity and reliability. Reminder: scalability is supporting many concurrent users
    • elasticity is supporting a burst of requests in a short time.
  • Example:
    • Ticketing operates at 10 times the elastic scale of Assignment. A synchronous call makes the whole workflow bog down waiting for the slower service
    • an asynchronous call through a queue buffer lets them run independently.
  • Takeaway: the quantum defines the scope of architecture characteristics, but the call type can temporarily entangle two services.

Summary points

  • Untangle forces, then analyse coupling and the impact of change.
  • Quantum = independent deployability + functional cohesion + static coupling + synchronous dynamic coupling; a shared database, orchestrator or UI can merge quanta.
  • Dynamic coupling has three forces (communication, consistency, coordination) giving eight named patterns.
Terms to carry forward
  • Architecture quantum / quanta: independently deployable, functionally cohesive, with static and dynamic coupling.
  • Static coupling: operational wiring needed to bootstrap.
  • Dynamic coupling: runtime communication between quanta.
  • Communication, consistency, coordination: the three dynamic forces.
  • Service-based architecture (as defined here): separate UI, coarse-grained services, monolithic database.
  • Micro-frontend: UI elements emitted by the services themselves.
