Software Architecture: The Hard Parts 4: Architectural Decomposition

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 4. Previous: Software Architecture: The Hard Parts 3: Architectural Modularity. Next: Software Architecture: The Hard Parts 5: Component-Based Decomposition Patterns.

Takeaways
  • Modularity is the why of breaking up a monolith; decomposition is the how.
  • Eating the elephant "one bite at a time" is the Elephant Migration Anti-Pattern: an unstructured approach that tends to produce a big ball of distributed mud (a distributed monolith).
  • Two approaches: component-based decomposition (refactor and extract well-defined components) and tactical forking (clone the monolith and delete what each team does not need).
  • The choice follows the structure of the codebase: first decide whether it is decomposable at all, then whether components exist.
  • Coupling metrics help: afferent and efferent coupling, abstractness, instability and distance from the main sequence.

4.1 Choosing an approach

  • Addison and Austen want to start with reporting, the knowledge base or surveys
    • Addison notes that making reporting a service does not solve the data problem; a separate reporting database with data pumps might be needed, "too big of a bite"
    • Logan calls bite-by-bite the Elephant Migration Anti-Pattern: it "may seem like a good approach at the start" but usually becomes a big ball of distributed mud, "what some people also call a distributed monolith"
    • Take a holistic view and use tactical forking or component-based decomposition.
  • Component-based decomposition: an extraction approach applying refactoring patterns that refine and extract components (the logical building blocks) into a distributed architecture incrementally and in a controlled fashion.
  • Tactical forking: replicate the application and chip away at the unwanted parts to form services, "similar to the way a sculptor creates a beautiful work of art from a block of granite or marble".
  • The deciding factor is how well the existing code is structured: are there clear components and boundaries, or a big ball of mud? The flowchart (Figure 4-1):
    1. Is the codebase decomposable?
    2. If yes, is it largely an unstructured mess with no definable components? Then tactical forking.
    3. If files are structured into well-defined (even loosely defined) components, use component-based decomposition (patterns in Chapter 5).

4.2 Is the codebase decomposable?

  • A codebase without internal structure is the Big Ball of Mud anti-pattern, coined by Brian Foote in an essay of the same name in 1999
    • Example: a complex web application with event handlers wired directly to database calls and no modularity
    • Architects rarely make patterns for these systems because architecture concerns internal structure and these lack it.
  • Without governance, many systems degrade this way. Step one in any restructuring is to understand the internal structure and ask: is this codebase salvageable? No single measure decides it
    • architects judge, using coupling metrics for macro characteristics.

Afferent and efferent coupling

  • Edward Yourdon and Larry Constantine (Structured Design, 1979) defined afferent coupling (incoming connections to a code artifact: component, class, function) and efferent coupling (outgoing connections to other artifacts).
  • Why it matters:
    • when deconstructing a monolith you find shared classes such as Address
    • reuse is encouraged in a monolith, but now you must see how many other parts of the system use the shared asset.
  • Many platforms have tools showing a matrix of class and component relationships
    • the example (Figure 4-2) is an Eclipse plug-in visualising JDepend output with per-package coupling analysis.

Abstractness and instability

  • Robert Martin created derived metrics for a C++ book in the late 1990s, applicable to any object-oriented language.
  • Abstractness (Equation 4-1):
    • A = sum(ma) / (sum(mc) + sum(ma)), where ma are abstract elements (interfaces, abstract classes) and mc concrete elements. Abstract elements help developers understand overall function
    • a codebase with one main() method and 10,000 lines scores near zero and is hard to understand.
  • Instability (Equation 4-2): I = Ce / (Ce + Ca), Ce efferent and Ca afferent coupling. High instability means the code breaks more easily when changed because of high coupling.
    • Example: with Ca = 2, Ce = 0 gives instability 0; Ce = 3 gives 3/5.
    • It reflects how many changes might be forced by changes to related components
      • Near 1: highly unstable
      • Near 0: either stable (mostly abstract elements) or rigid (mostly concrete)
      • The trade-off for high stability is lack of reuse: if every component is self-contained, duplication is likely.
  • Look at I and A together, which leads to the main sequence.

Distance from the main sequence

  • Equation 4-3: D = |A + I - 1|. It imagines an ideal relationship between abstractness and instability; components near the line have a healthy mix (Figure 4-3).
  • Plot a candidate component and measure its distance from the line.
    • Upper right: the zone of uselessness: too abstract, hard to use.
    • Lower left: the zone of pain: too much implementation, too little abstraction, brittle and hard to maintain (Figure 4-4).
  • Implication:
    • like moving a large structure on a poor foundation, restructuring a poorly structured application is risky
    • improving internal structure first eases the move. If many components lie in the zones of uselessness or pain, perhaps "it is not a good use of time" to repair the internal structure.

4.3 Component-based decomposition

  • The authors' experience:
    • most difficulty migrating monoliths to microservices comes from poorly defined architectural components
    • A component here has a well-defined role and responsibility and a well-defined set of operations, usually a namespace or directory
    • In Figure 4-5 the directory penultimate/ss/ticket/assign is the component Ticket Assign with namespace penultimate.ss.ticket.assign.
Build services from components

When breaking monolithic applications into distributed architectures, build services from components, not individual classes.

  • The Chapter 5 patterns refactor source code into well-defined components that can become services
    • They essentially migrate a monolith to a service-based architecture: a hybrid of microservices where the application splits into domain services, coarse-grained, separately deployed services containing all business logic for a domain.
  • Service-based is a fine final target or stepping stone:
    • as a stepping stone it shows which domains need finer granularity (Chapter 7) and which can stay coarse
    • it does not require breaking the database, so you can do domain and functional partitioning before database decomposition (Chapter 6)
    • it needs no operational automation or containerisation; each domain service can use the original deployment artifact (EAR, WAR, assembly)
    • the move is technical: it generally does not involve business stakeholders or change IT organisation structure or the testing and deployment environments
Consider service-based first

When migrating monoliths to microservices, consider moving to service-based architecture first as a stepping stone.

4.4 Tactical forking

  • Named by Fausto De La Torre as a pragmatic approach for restructuring big balls of mud.
  • Usual thinking is extraction (Figure 4-6):
    • developers constantly meet strands of coupling and find more and more of the monolith must come along
    • Deletion (Figure 4-7) removes unneeded code and leaves dependencies intact, avoiding the unravelling.
  • The pattern (Figures 4-8 to 4-11), with two teams making two services (one for the hexagon and square domain, one for the circle domain):
    1. Start with the monolith of several domain behaviours and little internal organisation.
    2. Clone the entire monolith; each team gets a copy.
    3. Each team deletes the code it does not need; in a tightly coupled codebase this is easier than extracting many dependencies. Once functionality is isolated, delete any code that does not break anything.
    4. Teams keep refactoring to remove unwanted code; at the end two coarse-grained services remain, preserving the coarse structure.

Trade-offs
Benefits Teams start immediately with virtually no up-front analysis. Deleting is easier than extracting from a chaotic codebase, because unneeded code is verified by compilation or simple testing.
Shortcomings The services likely keep a lot of latent leftover code. Unless more work is done, code inside the new services is no better than the chaotic monolith, just less of it. Naming of shared code and shared component files may become inconsistent, making common code hard to identify and keep consistent.
  • The name is apt: a tactical, not strategic, approach for quickly migrating important or critical systems, albeit in an unstructured way.

4.5 Sysops Squad saga: choosing a decomposition approach

  • They analyse the application with abstractness and instability: most code lies along the main sequence, with a few outliers, so decomposition is feasible.
  • Austen likes tactical forking (the sculptor removing marble that should not be there)
    • Addison objects:
      • duplicate code and shared functionality (logging, security, persistence-layer database calls) and the problems are maintainability, testability and reliability
      • applying the same change to several services "would be a nightmare"
    • Since component boundaries are good, Austen agrees to the slower component-based approach.

ADR: Migration using the component-based decomposition approach

  • Context: break the monolith into separately deployed services; the two approaches considered were tactical forking and component-based decomposition.
  • Decision: use component-based decomposition, because:
    • the application has well-defined component boundaries
    • it reduces the chance of maintaining duplicate code in each service
    • tactical forking would need service boundaries defined up front (to know how many forks to create)
      • with component-based decomposition the service definitions emerge through component grouping
    • given the reliability, availability, scalability and workflow problems, it is a safer, more controlled, incremental migration
  • Consequences:
    • it will likely take longer than tactical forking
    • developers work collaboratively to identify shared functionality, component boundaries and domain boundaries
      • tactical forking would split the team into smaller teams per fork and increase coordination

Summary points

  • Check decomposability first (coupling metrics, distance from the main sequence), then choose by structure.
  • Component-based decomposition builds service-based architecture first; tactical forking suits balls of mud at the cost of duplicated, unimproved code.
  • Avoid ad hoc bite-by-bite migration.
Terms to carry forward
  • Elephant Migration Anti-Pattern: unstructured piecemeal migration leading to distributed mud.
  • Afferent / efferent coupling: incoming / outgoing connections.
  • Abstractness, instability, distance from the main sequence.
  • Zone of uselessness / zone of pain.
  • Tactical forking: clone and delete.
  • Component-based decomposition: refactor components, then extract services.
