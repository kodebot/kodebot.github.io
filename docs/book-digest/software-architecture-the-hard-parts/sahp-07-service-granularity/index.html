Software Architecture: The Hard Parts 7: Service Granularity

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 7. Previous: Software Architecture: The Hard Parts 6: Pulling Apart Operational Data. Next: Software Architecture: The Hard Parts 8: Reuse Patterns.

Takeaways
  • Modularity is breaking a system into parts; granularity is the size of those parts. Most distributed-system problems are about granularity, not modularity.
  • Granularity is not classes or lines of code but what the service does. Measure it with statements and public interfaces or operations, which are still partly subjective but the best objective proxies the authors have.
  • Replace opinion ("single responsibility", "micro means small") with trade-off analysis between six disintegrators and four integrators.
  • Teams over-focus on disintegrators and forget the integrators; the right size is an equilibrium between them.
  • Put each trade-off to the business as a plain choice (for example time-to-market versus data integrity), and record the outcome in an ADR.

7.1 The scene

  • Taylen (tech lead) wants every domain service split smaller:
    • "micro means small", justified by the single-responsibility principle
    • Logan (the consulting architect) answers that not every part of an application has to be microservices, calling that one of the biggest pitfalls of the style.
  • Test case:
    • a customer notification service (SMS, email, postal letter): one service or three? Taylen says three, Addison says one, Austen would toss a coin. Logan: remove opinion and gut feeling
    • use granularity disintegrators and integrators.

7.2 Modularity versus granularity

  • The dictionary definitions look alike, so people conflate the terms
    • In the book's usage, modularity is breaking systems into separate parts (chapter 3) and granularity is the size of those parts.
  • Why measure by statements:
    • every developer has a different style, so class counts and lines of code are poor metrics
    • a statement (a single complete action in source, ended by a semicolon or newline) at least measures what the service does (chapter 4).
  • A second metric is the number of public interfaces or operations a service exposes.
  • Two opposing forces (Figure 7-1): disintegrators answer "when should I consider breaking apart a service?", integrators answer "when should I consider putting services back together?".

7.3 Granularity disintegrators

Driver Question Reason for applying it (Table 7-2)
Service scope and function Is the service doing too many unrelated things? Single-purpose services with tight cohesion
Code volatility Are changes isolated to one part of the service? Agility: smaller testing scope, lower deployment risk
Scalability and throughput Do parts need to scale differently? Lower cost, faster responsiveness
Fault tolerance Do errors in one part cause critical functions to fail? Better overall uptime
Security Do some parts need a higher security level? Better access control for certain functions
Extensibility Does the service keep adding new contexts? Agility: easier to add functionality

Service scope and function

  • Two dimensions: cohesion (how the operations interrelate) and size (statements and public entry points).
  • The notification service has relatively strong cohesion (everything is "notifying the customer"), so splitting into SMS, email and letter services is not justified by scope alone
    • "single purpose" is a matter of opinion.
  • A service holding customer profile, customer preferences and website comments has weak cohesion (a broad "customer" scope) and is a good candidate to split into three.
  • Related to Robert C
    • Martin's single-responsibility principle (SOLID), originally about classes and later extended to components and services
    • A microservice is defined as a single-purpose, separately deployed unit that does one thing really well, which tempts developers to go as small as possible without asking why
    • Cohesion metrics such as LCOM exist, but for services the question stays subjective: is "notify the customer" one thing, or is "notify by email" one thing? So use the other drivers too.

Code volatility

  • Volatility-based decomposition:
    • split on how often code changes, measurable from version control
    • Notification example: SMS changes about every six months, email about every six months, postal letter weekly.
  • As one service, every letter change means testing and redeploying SMS and email too (a bigger testing scope and higher deployment risk, and possibly SMS and email unavailable during deployment)
    • Splitting into Electronic Notification and Postal Letter Notification isolates the frequent change.

Scalability and throughput

  • Measured demand:
    • SMS 220,000 per minute, email 500 per minute, postal letter 1 per minute
    • As one service, email and letter must scale to meet SMS, which hurts cost and elasticity (mean time to startup)
    • Three services scale independently.

Fault tolerance

  • If email repeatedly crashes (out of memory), a combined service takes SMS and letters down with it; three services contain the failure.
  • Why three and not "email versus the rest" even though only email is unstable: the leftover SMS-plus-letter service would be weakly cohesive and hard to name
    • The book's test names: Other Notification Service, Non-Email Service and SMS-Letter Service are all poor; Email, SMS and Letter are good
    • A service that is hard to name is doing multiple things (scope driver)
    • When splitting for any driver, check that strong cohesion can be formed with the leftover functionality. The volatility split into two worked because email and SMS are both "electronic".

Security

  • Securing sensitive data (for example PCI data in a separate schema or region) must also cover how the data is accessed, not just where it is stored.
  • A Customer Profile Service that also does credit-card maintenance exposes card functionality to anyone entering the service for something else, even through different API entry points
    • Splitting gives the card operations a single-purpose service with tighter access control.

Extensibility

  • A payment service that handles credit cards, gift cards and PayPal must be retested and redeployed in full every time a method is added (reward points, store credit, ApplePay, SamsungPay)
    • Separate services per method mean only the new service is developed, tested and deployed.
  • Advice:
    • apply this driver only if the extension is planned, desired or part of the normal domain
    • Payment types are likely to keep growing; notification methods probably will not
    • Since guessing is hard, wait until a pattern or confirmed growth establishes it.

7.4 Granularity integrators

Driver Question Reason (Table 7-3)
Database transactions Is an ACID transaction needed between the services? Data integrity and consistency
Workflow and choreography Do the services need to talk to one another? Fault tolerance, performance and reliability
Shared code Do the services share code? Maintainability
Data relationships Can the data be split as well as the service? Data integrity and correctness

Database transactions

  • A Customer Profile Service and a Password Service give good access control to password operations (change, reset, sign-in lookup) since access is at service level.
  • But registering a customer needs both inserts:
    • the Profile Service inserts and commits, then calls the Password Service, which inserts and commits
    • If the second fails, the first is already committed: no ACID transaction, inconsistent data, and complex, error-prone compensation (see chapter 12 sagas).
  • If a single-unit-of-work transaction is required by the business, consolidate the services.

Workflow and choreography

  • Services talking to each other is interservice (east-west) communication. As services get smaller, it grows, with three costs:
    • Fault tolerance:
      • with A calling B and C, B calling C, D calling E and E calling C, a failure of C leaves all of them nonoperational (transitive dependency)
      • Splitting for fault tolerance gains nothing if the services are tightly dependent.
    • Performance and responsiveness:
      • a customer service split into five, retrieved through one choreographed request, costs five hops
      • at 300 ms of network and security latency each, that is 1,500 ms of added latency. Chapter 11 offers orchestration as an alternative.
    • Reliability and data integrity:
      • adding a customer across five services where A, B and C commit and D fails leaves committed partial data that may already have been read or broadcast
      • it needs compensating transactions or a stored state to restart.
  • Rule of thumb for performance:
    • look at the percentage of requests needing inter-service workflow and their criticality. 30% workflow and 70% atomic may be fine to keep separate
    • reversed, consider merging
    • if a critical, fast-response request is in the 30%, merge even then. There is more leeway for backend work where no user waits.

Shared code

  • Shared code (logging, security, utilities, formatters and so on) usually lives in a library bound at compile time (a JAR, GEM or DLL); chapter 8 covers reuse patterns.
  • If five services share a library of domain functionality, a change eventually forces all of them to be changed, tested and deployed together (eventually, because versioning can defer it)
    • Consolidating avoids multiple deployments and services out of sync on library versions.
  • Infrastructure cross-cutting code (logging, auditing, authentication, authorization, monitoring) is not a reason to merge services or go back to a monolith.
  • Three guidelines for treating shared code as an integrator:
    • Specific shared domain functionality:
      • consider it when the shared share is relatively high
      • the example is shared code over 40% of the collective codebase for profile, preference and comment functions, so nearly half the code would live in a library used only by those three services.
    • Frequent shared code changes: frequent library changes mean frequent coordinated deployments even if versioning helps.
    • Defects that cannot be versioned: when a defect or business-rule change must reach all services at once, and this happens often, consider merging.

Data relationships

  • This integrator assumes the data of a split service is not shared but formed into bounded contexts for change control and availability.
  • Table 7-1 maps functions A, B and C to tables 1 to 6 (owner means writes; access means read-only)
    • If the service splits and Service B owns table 3 but needs table 5 (owned by C), while C needs table 3, neither may query the other's table, because a column removal in table 3 would break C
    • They must call each other back and forth, so merge them to avoid the latency, fault-tolerance and scalability costs.
  • It is the integrator with the fewest trade-offs, because reorganising table relationships for the sake of splitting a service is seldom feasible (chapter 6 covers breaking up data).

7.5 Finding the right balance

  • The secret is understanding both sets of drivers and analysing the trade-offs, collaborating with business stakeholders, not deciding alone.
  • Turn a pair of drivers into a trade-off statement for the product owner or sponsor. The book gives three examples:
    • Isolate frequent code changes (agility, faster time-to-market) versus keep a database transaction (data integrity). The sponsor prefers integrity and keeps one service for now.
    • Keep the service together for a transaction versus separate sensitive functionality for security
      • The sponsor, whose CIO has been through rough security situations, keeps the services separate and works on mitigating consistency problems.
    • Split payment for extensibility versus avoid the extra workflow that hurts responsiveness when several payment types are used
      • The sponsor expects only two or three more payment types over a couple of years and chooses responsiveness, since the customer waits for the order ID.

7.6 Sysops Squad saga: ticket assignment granularity

  • Two components: assignment (picks the expert by skill, location and availability) and routing (finds the expert, sends the ticket to the mobile app, notifies by SMS).
  • Taylen argues for separate services:
    • assignment algorithms are complex and change two to three times a month (volatility-based decomposition)
    • Skyler argues they are one function
    • Addison finds the common ground: they are two activities tightly bound synchronously, so if routing cannot find the expert it must tell assignment to pick another, which would mean heavy coordination.
  • Addison frames the trade-off:
    • isolating assignment for change control versus one service for performance, error handling and workflow control. Taylen agrees to the single service
    • to keep the code isolated, the single service gets three architectural components (assignment, routing, shared code) in separate namespaces.
ADR: consolidated service for ticket assignment and routing
  • Decision: one consolidated service. Reasons: tickets are routed immediately once assigned; both functions scale the same (no throughput difference or back-pressure need); neither fault tolerance nor scale is a driver; separate services would add workflow with performance, fault-tolerance and reliability risk.
  • Consequences: assignment changes (frequent) and routing changes (infrequent) both require testing and deployment of both functions, so testing scope and deployment risk grow.

7.7 Sysops Squad saga: customer registration granularity

  • Registration collects profile, credit card, password with security question, and covered products. Three options (Figure 7-19): one customer service
    • four services (profile, credit card, password, supported product)
    • or two (profile with products, and a secure service for card and password).
  • The product owner Parker requires all or nothing:
    • never a customer without a credit card or password record
    • The security expert Sam wants separate secured services
    • The card and password data are already tokenised and encrypted, and the team uses the Tortoise security libraries at the API layer and within each service through the service mesh (a double check).
  • The trade-off (transactionality versus security) resolves in favour of one customer service, since the all-or-nothing rule is absolute and the security risk is mitigated by library use
    • The book draws the lesson that security can be controlled by design (a custom library) rather than by architecture (separate deployment units)
    • Austen facilitated the discussion rather than controlling it.
ADR: consolidated service for customer-related functionality
  • Decision: one consolidated service for profile, credit card, password and supported products. Registration and unsubscribe need one atomic unit of work, which separate services cannot give; the Tortoise library in the API gateway and service mesh mitigates the access risk.
  • Consequences: Tortoise is required in both places; any change to profile, card, password or products widens the testing scope and deployment risk; everything scales as one unit.

Summary

  • Granularity is decided by weighing disintegrators against integrators, with measurements (statements, change rates, throughput, request mix) and conversations with the business, not by "micro means small".
  • Next: how to reuse code across services (chapter 8) and, in Part II, how to put data and workflows back together.
Terms to carry forward
  • Granularity vs modularity: the size of the parts vs breaking into parts.
  • Granularity disintegrator / integrator: a driver to split a service or to merge services.
  • Cohesion: how the operations in a service interrelate.
  • Volatility-based decomposition: splitting by rate of code change.
  • East-west communication: interservice calls.
  • Statement count, public interfaces: the size metrics.
  • Trade-off statement: a question put to the business that sets one driver against another.
