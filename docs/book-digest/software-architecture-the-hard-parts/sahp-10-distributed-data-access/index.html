Software Architecture: The Hard Parts 10: Distributed Data Access

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 10. Previous: Software Architecture: The Hard Parts 9: Data Ownership and Distributed Transactions. Next: Software Architecture: The Hard Parts 11: Managing Distributed Workflows.

Takeaways
  • When data is split, a service that needs data it does not own (outside its bounded context) cannot just join a table. The chapter gives four read-access patterns: Interservice Communication, Column Schema Replication, Replicated Caching, Data Domain.
  • None is free: simple and common (interservice) is slow and couples availability; replicated columns and caches are fast but need synchronisation; a shared data domain is the fastest and most consistent but widens the bounded context.
  • "If an architect thinks they have discovered something that isn't a trade-off, they just haven't identified the trade-off yet" (the first law of software architecture, from Fundamentals of Software Architecture).
  • Measure before choosing: data volume, instance counts and update rate decided the Sysops Squad choice.

10.1 The scene

  • The expert-profile table is owned by the User Management Service, but Ticket Assignment queries it constantly
    • Taylen cannot rewrite the assignment algorithms to read less, and says messaging would be "the same thing" as REST (you still wait)
    • Taylen wants the table in the ticketing data domain; Addison asks Logan for options.
  • In a monolith one SQL join gets everything; across schemas and services, reads become hard.
  • Example used throughout: a Wishlist Service (customer ID, item ID, date added) must display the item description (item_desc), but that column lives in the Product table owned by the Catalog Service.

10.2 Interservice communication pattern

  • By far the most common pattern: ask the owner through a remote access protocol (the Wishlist Service sends a list of item IDs to the Catalog Service and gets descriptions back).
  • Three kinds of added latency per request:
    • Network latency: usually about 30 to 300 ms.
    • Security latency: extra authorisation on the endpoint, about 20 to 400 ms.
    • Data latency: the owner needs an additional database call instead of a join, about 10 to 50 ms.
    • Together, up to about one second just to fetch descriptions (the authors' ranges).
  • Service coupling: if Catalog is unavailable, so is Wishlist (semantic and static coupling), and as Wishlist scales, so must Catalog.

Advantages Disadvantages
Simplicity Network, data and security latency (performance)
No data volume issues Scalability and throughput issues
No fault tolerance (availability issues)
Requires contracts between services

10.3 Column schema replication pattern

  • The needed column (item_desc) is copied into the Wishlist table, so Wishlist reads it with an ordinary query or join.
  • Problems:
    • Synchronisation and consistency:
      • whenever a product is created, removed or its description changes, Catalog must tell Wishlist (and any other copy-holder), usually through queues, topics or event streams
      • Asynchronous is preferred unless immediate transactional sync is needed (better responsiveness, less availability dependency).
    • Ownership governance: the replica lives in another service's table, so that service can update it even though it does not own it.
  • Services remain coupled through the synchronisation, but the reader gets performance, fault tolerance and scalability that interservice communication lacked.
  • The authors caution against it for the Wishlist/Catalog case, but it may fit data aggregation, reporting, or cases where other patterns fail because of large data volumes, high responsiveness needs or high fault tolerance needs.
Advantages Disadvantages
Good data access performance Data consistency issues
No scalability or throughput issues Data ownership issues
No fault-tolerance issues Data synchronisation is required
No service dependencies

10.4 Replicated caching pattern

  • Caching is usually seen as a responsiveness tool (dozens of milliseconds down to a couple of nanoseconds)
    • Here it is also a sharing tool: replicated in-memory caches hold the data in each service and keep it continuously synchronised.
  • Compare the caching models:
    • Single in-memory cache: each service has its own, unsynchronised, so useless for sharing.
    • Distributed cache:
      • data sits in an external caching server reached over a proprietary protocol. Weaknesses for this purpose: the fault-tolerance dependency just moves to the cache server
      • other services can update the shared data, breaking ownership and risking inconsistency with the owning database
      • and remote access adds latency.
    • Replicated cache:
      • no external dependency
      • each instance holds the same data and an update is propagated asynchronously behind the scenes to the others. Not every caching product supports it
      • ones that do include Hazelcast, Apache Ignite and Oracle Coherence.

  • Applied:
    • the Catalog Service owns an in-memory cache of product descriptions (it is the only one that can modify it) and the Wishlist Service holds a read-only replica. No calls are needed
    • Catalog's updates reach the Wishlist cache automatically.
  • Advantages: responsiveness (fastest possible access), fault tolerance (Wishlist keeps working if Catalog goes down, and caches reconnect when it returns) and scalability (Wishlist scales independently).
  • The four trade-offs:
    • Startup dependency:
      • Catalog populates the cache, so it must be running when the first Wishlist instance starts
      • otherwise that instance waits. Other instances can start from a peer's cache, and once loaded the owner can come and go.
    • Data volume: feasibility drops quickly past about 500 MB, and every instance holds its own copy (500 MB and 5 instances means 2.5 GB). Analyse cache size times instance count.
    • Update rate: if data changes too quickly the caches cannot stay in sync (inventory counts); it suits relatively static data such as product descriptions.
    • Configuration and setup:
      • services find each other through TCP/IP broadcasts and lookups
      • a broad range slows the socket handshake, and cloud and containerised environments make this hard because IP addresses are dynamic and not under your control.

Advantages Disadvantages
Good data access performance Cloud and containerised configuration can be hard
No scalability or throughput issues Not good for high data volumes
Good level of fault tolerance Not good for high update rates
Data remains consistent Initial service startup dependency
Data ownership is preserved

10.5 Data domain pattern

  • The chapter 9 shared data domain also works for reads:
    • put the Wishlist and Product tables in one shared schema, so Wishlist gets descriptions with a simple SQL join
    • The tables then belong to neither service but to a broader bounded context.
  • When it makes sense: interservice communication is ruled out by Catalog's reliability and latency, column replication by the need for high consistency, and replicated cache by data volume.
  • Benefits: services fully decoupled (no availability, responsiveness, throughput or scalability problems), data consistency and integrity very high (nothing to transfer or synchronise; foreign keys, views, stored procedures and triggers can exist in the domain, which is itself a reason to choose it), and no contract is needed since the table schema is the contract.
  • That last point is also a trade-off:
    • contracts act as an abstraction layer over the table schema in the other patterns, keeping schema changes inside a tight bounded context
    • Here a table change may force several services to change.
  • Other costs: ownership governance, and data access security: Wishlist sees all data in the domain, which is fine here but not where a service should not see certain data (a tighter, contract-based bounded context can prevent that).
Advantages Disadvantages
Good data access performance Broader bounded context to manage data changes
No scalability or throughput issues Data ownership governance
No fault tolerance issues Data access security
No service dependency
Data remains consistent

10.6 Sysops Squad saga: data access for ticket assignment

  • Ticket Assignment needs expert skills, service-location zones and standard schedule from the expert-profile table (the live location feed comes from elsewhere).
  • Ruled out:
    • service consolidation (different domains) and the data domain (Ticket Assignment already connects to the ticketing schema and cannot connect to a second; and the domains should not merge)
    • Left: interservice communication or replicated caching.
  • Sizing: 900 experts at about 1.3 KB each is roughly 1,200 KB; relatively static; at most 2 User Management and 4 Ticket Assignment instances at peak, so little total memory.
  • Hypothesis-based trade-off analysis:
    • the first trade-off Taylen finds is the startup dependency (User Management must start first)
    • Addison's counterpoint: with remote calls the assignment service stops whenever User Management is down, while with the cache it is independent once loaded, so the cache is more fault tolerant overall.
  • Sydney raises the next one:
    • which caching product, and nobody on the team has done replicated caching, so there is risk
    • Taylen volunteers for research and proofs of concept; Addison investigates licensing cost and technical limits such as availability-zone crossovers and firewalls
    • Logan approves.

ADR: in-memory replicated caching for expert profile data
  • Decision: replicated caching between User Management and Ticket Assignment, with User Management as sole writer. A common data domain is rejected because Ticket Assignment cannot connect to a second schema and the domains should not be combined; the cache fixes the performance and fault-tolerance issues of interservice communication.
  • Consequences: at least one User Management instance must run when the first Ticket Assignment instance starts; licensing costs for the caching product.

Summary

  • Choose a read pattern from the data's size, change rate, consistency need and the cost of coupling availability, then record the choice in an ADR.
  • Next: managing workflows across services, orchestration versus choreography (chapter 11).
Terms to carry forward
  • Interservice communication, column schema replication, replicated caching, data domain: the four read-access patterns.
  • Network, security and data latency.
  • Single in-memory, distributed, replicated cache.
  • Startup dependency of a replicated cache.
  • First law of software architecture: everything is a trade-off.
