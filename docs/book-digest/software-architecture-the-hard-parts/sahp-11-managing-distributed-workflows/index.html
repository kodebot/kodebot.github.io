Software Architecture: The Hard Parts 11: Managing Distributed Workflows

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 11. Previous: Software Architecture: The Hard Parts 10: Distributed Data Access. Next: Software Architecture: The Hard Parts 12: Transactional Sagas.

Takeaways
  • This chapter covers the coordination force of dynamic quantum coupling (with communication and consistency, chapter 2): combining services to do domain work.
  • Two coordination patterns: orchestration (an orchestrator, also called a mediator, manages the workflow) and choreography (no central coordinator; services react to each other).
  • Choreography looks simpler on the happy path; the difficulty lies in boundary and error conditions, which add communication links. Orchestration costs responsiveness, scale and a single point of failure, but gives centralised workflow, error handling, recoverability and state.
  • Semantic coupling (the inherent workflow in the problem domain) cannot be reduced by implementation, only made worse. Model the workflow's semantics as closely as possible.
  • "Never use absolutes when talking about architecture, except when talking about absolutes."

11.1 The scene

  • Austen wants an ADR saying "only choreography, to keep things decoupled"
    • Logan objects: "always" is tricky, and a mentor's maxim is never use absolutes when talking about architecture, except when talking about absolutes
    • How to decide between the communication patterns is the chapter's question.
  • The chapter realises the dynamic-coupling patterns named in chapter 2 (the eight sagas)
    • the book says its named patterns touch only some of the many possible permutations, so an architect should understand the forces.

11.2 Orchestration communication style

  • An orchestrator (mediator) manages workflow state, optional behaviour, error handling, notification and other workflow maintenance, named for the conductor of an orchestra.
  • Domain services keep their own bounded context, data and behaviour
    • the orchestrator holds no domain behaviour beyond the workflow it mediates. Microservices use one orchestrator per workflow, not a global component such as an enterprise service bus (ESB), which would be an undesirable coupling point.
  • Useful for complex workflows with alternate paths and error conditions, not just the happy path.
  • Example (Penultimate Electronics sells a device online):
    • The Place Order request goes to the Order Placement Orchestrator, which calls the Order Placement Service synchronously (records the order, returns status), then the Payment Service, then the Fulfillment Service asynchronously (no strict timing dependency; if fulfilment happens a few times a day, a synchronous call is overhead), then the Email Service.
    • Payment rejected (for example an expired card): the Payment Service tells the orchestrator, which asynchronously asks Email to notify the customer and updates Order Placement, which still thinks the order is active.
    • Back order:
      • Fulfillment reports the item is out of stock
      • the orchestrator must refund the payment (which is why many online services charge at shipment, not order time) and update the order state.
  • Each service keeps its own transactional state here, modelling the Fairy Tale Saga(seo) pattern (chapter 12).
  • Note: even elaborate error scenarios needed no new communication paths beyond those of the normal workflow, unlike choreography.

Advantages Disadvantages
Centralised workflow: a unified component for state and behaviour as complexity rises Responsiveness: all communication goes through the mediator, a potential throughput bottleneck
Error handling: a state owner for the workflow Fault tolerance: a potential single point of failure for the workflow (redundancy adds complexity)
Recoverability: the orchestrator can retry after a short outage Scalability: more coordination points means less parallelism; choreography-based sagas (Time Travel(sec), Anthology(aec)) scale higher
State management: workflow state is queryable Service coupling: higher coupling between orchestrator and domain components, sometimes necessary

11.3 Choreography communication style

  • No central coordination; like dance partners, the moves are planned beforehand by the choreographer (architect) but carried out without a coordinator.
  • The same purchase:
    • the request goes to the first service in the chain (Order Placement), which asynchronously calls Payment, which messages Fulfillment, which messages Email
    • Fewer services (no orchestrator) and a simple chain of messages, but the difficulties are in boundary and error conditions.
    • Payment fails: Payment messages Email and Order Placement instead of Fulfillment. One new link; not too complex.
    • Back order:
      • many steps have already completed
      • each service has its own transaction (the Anthology Saga(aec) pattern), so on error each must issue compensating messages. Fulfillment broadcasts an event that Email, Payment and Order Placement subscribe to.
  • The initial workflow looked simpler than the orchestrated one, but error cases keep adding complexity: each error scenario forces new links between domain services that the happy path did not need.

Semantic versus implementation coupling

  • Every workflow has semantic coupling:
    • the inherent coupling of the problem domain (assigning a ticket means: client requests, skills matched, then cross-referenced with schedules and locations)
    • The way the architect models it is implementation coupling.
  • Semantic coupling is mandated by domain requirements
    • no cleverness reduces it, though implementation choices can increase it. Architects may still push back on impractical business semantics.
An architect can never reduce semantic coupling via implementation, but they can make it worse.
  • Example:
    • a technically partitioned (layered) monolith smears a domain concept like Catalog Checkout across the layers, while a domain-partitioned (modular) monolith keeps it in one component and its database
    • Aligning the architecture with the domain keeps the implementation's complexity similar to the workflow's
    • Extra layers (for example database-connection-pooling cost savings, a trade-off sometimes worth it) add implementation complexity on top of the semantic complexity.
  • Lesson of the last decade, in the authors' words:
    • model the workflow's semantics as closely as possible with the implementation
    • More steps in the workflow mean more potential error and optional paths, so more need for coordination.

Workflow state management in choreography

  • Workflows carry transient state (what executed, what is left, order, errors, retries). An orchestrator is the obvious owner; choreography has none. Three common options:
Option How Advantages Disadvantages
Front Controller The first service (Order Placement) owns workflow state besides domain behaviour; others call back to update it A pseudo-orchestrator inside choreography; order state trivial to query More workflow state in a domain service; more communication overhead; worse performance and scale from chatter
Stateless choreography No transient state; query each service and build a snapshot on demand High performance and scale; extremely decoupled State must be built on the fly; complexity rises swiftly with workflow complexity (trades performance for workflow control)
Stamp coupling Workflow state is carried in the message contract; each service updates its part and passes it on No extra queries to a state owner; no front controller Larger contracts; no just-in-time status query
  • Stamp coupling is a partial solution: there is still no single place to ask the state of an ongoing workflow (chapter 13 discusses contracts and workflow coupling).

Advantages of choreography Disadvantages of choreography
Responsiveness: fewer choke points, more parallelism Distributed workflow: no owner, so error and boundary management is harder
Scalability: no coordination points, more independent scaling State management: no central state holder
Fault tolerance: no single orchestrator; multiple instances Error handling: services need more workflow knowledge
Service decoupling: no orchestrator Recoverability: no one to attempt retries and remediation

11.4 Trade-offs between orchestration and choreography

  • State owner and coupling:
    • state lives either in a mediator or in a front controller
    • Removing the mediator forces more service-to-service communication, which can be a fine trade for a workflow that needs high scale and has few error conditions
    • As workflow complexity rises, the need for an orchestrator rises proportionally (Figure 11-14), and the more semantic complexity, the more useful an orchestrator.
  • Sweet spot for choreography:
    • workflows that need responsiveness and scalability and either lack complex error scenarios or have infrequent ones. Used by Phone Tag(sac), Time Travel(sec) and Anthology(aec)
    • mixed with other forces it can reach the Horror Story(aac).
  • Orchestration
    • is best for complex workflows with boundary and error conditions: less scale, but far less complexity
    • Used by Epic(sao), Fairy Tale(seo), Fantasy Fiction(aao) and Parallel(aeo).
  • Next force: how coordination intersects with consistency (chapter 12).

11.5 Sysops Squad saga: managing workflows

  • The primary ticket workflow spans four services
    • Customer-facing: the customer submits a ticket via the Ticket Management Service and gets a number
    • Background: Ticket Assignment finds the expert and routes the ticket to the expert's mobile device
    • the Notification Service tells the customer the expert is coming
    • the expert marks the ticket complete (sent to Ticket Management)
    • Ticket Management tells the Survey Service to invite the customer to a survey.
  • Austen prefers choreography, Addison orchestration. Logan: no obvious winner, so model likely scenarios and see how each reacts. The team builds a table:
    • Lost or misrouted tickets (a business priority): orchestration, for control of the workflow.
    • Status of a ticket at any moment
      • (a business request): both work
      • Orchestrator state is queryable, but choreography can query each service or use stamp coupling
      • "This isn't a zero-sum game", so both get credit.
    • Cancellation and reassignment
      • (customer cancels; expert unavailable, connection lost, delayed at a customer site): error handling, orchestration
      • "Complex workflows must go somewhere, either in an orchestrator or scattered through services."
Concern Orchestration Choreography
Workflow control yes
State query yes yes
Error handling yes
ADR: use orchestration for the primary ticket workflow
  • Context: the workflow needs easy tracking of lost or mistracked messages, excellent error handling and ticket status tracking; either style would work.
  • Decision: orchestration, based on the trade-offs above.
  • Consequences: a single orchestrator may cause scalability issues for the ticketing workflow; reconsider if scalability requirements change.

Summary

  • Pick the coordination style by workflow complexity, error frequency and the need for state and scale; never by a rule like "always choreography".
  • Next: consistency, the transactional sagas that tie communication, consistency and coordination together (chapter 12).
Terms to carry forward
  • Orchestration, orchestrator (mediator), choreography.
  • Dynamic quantum coupling: communication, consistency and coordination.
  • Semantic coupling vs implementation coupling.
  • Happy path vs error and boundary conditions.
  • Front Controller, stateless choreography, stamp coupling.
  • Technical vs domain partitioning.
  • Compensating message: a message that reverses an earlier step's effect.
