Software Architecture: The Hard Parts 12: Transactional Sagas

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 12. Previous: Software Architecture: The Hard Parts 11: Managing Distributed Workflows. Next: Software Architecture: The Hard Parts 13: Contracts.

Takeaways
  • Eight saga patterns come from three binary dimensions: communication (synchronous or asynchronous), consistency (atomic or eventual), coordination (orchestrated or choreographed). Each has named ratings for coupling, complexity, responsiveness and scale.
  • The "traditional" Epic Saga(sao) (sync, atomic, orchestrated) is the most coupled and scales worst; it uses compensating updates, which have no isolation, can cause side effects and can fail.
  • The best general trade-offs are usually Fairy Tale(seo) and Parallel(aeo) (orchestrated, eventual) and, for simple high-throughput flows, Anthology(aec). Horror Story(aac) (async, atomic, choreographed) is the worst combination.
  • Instead of compensating, manage saga state with a finite state machine, retries and escalation: better responsiveness, at the cost of temporarily out-of-sync data.
  • Sagas are not framework features: they must be designed, coded and maintained, so document them (for example with annotations and a small tool).

12.1 The scene

  • Austen's ticket workflow (asynchronous communication, atomic transactions, choreography) is called a "horror story" by Addison. Logan: it is the Horror Story saga pattern, really an anti-pattern
    • there are eight generic saga patterns, each with a different balance of trade-offs.
  • History:
    • the saga concept predates microservices, originally limiting the scope of database locks in early distributed systems
    • the book says the paper widely assumed to have coined it is from the 1987 ACM conference proceedings
      • Chris Richardson (Microservices Patterns, Manning, and his website's "Saga Pattern" section) describes it for microservices as a sequence of local transactions, each publishing an event that triggers the next
    • on failure the saga issues compensating updates to undo prior changes. That is only one of the eight types (chapter 2).
  • Because distributed transactions lack atomicity, what makes sagas interesting is when problems occur.

Anthology Saga(aec) Asynchronous Eventual Choreographed
  • The names are whimsical
    • the superscript lists the three dimensions in alphabetical order (communication, consistency, coordination) as a memory aid, so the book wants no memorisation test.
  • Each is shown as a 3D intersection of the three forces and as an isomorphic diagram (generic services, only the differentiating features). All have legitimate uses.

Epic Saga(sao)

  • The "traditional" saga, also called the orchestrated saga
    • It mimics a monolith: a monolith added to the dimensional diagram would be the origin (0, 0, 0)
    • An orchestrator coordinates updates to three services expected to succeed or fail together.
  • The authors warn that a pattern names a commonality, not a solvability: moving transactions into the distributed world is not an incremental change, and the difficulty grows with the semantic coupling of the problem
    • Such transactions limit database choice and have "legendary failure modes".
  • A common implementation uses compensating transactions:
    • a compensating update reverses a write done by another service (reverses an update, reinserts a deleted row, deletes an inserted row)
    • The mediator monitors success and, if a call fails, asks the others to undo.
  • Advantage:
    • familiar monolith-like transactional behaviour, with a clear workflow owner. Disadvantages: orchestration plus transactionality hurts performance, scale and elasticity (timing bottlenecks)
    • failure modes and boundary conditions abound.
  • Ratings:
    • coupling very high, complexity low (synchronous calls avoid race conditions and deadlocks), responsiveness/availability low (fails if any service is down), scale/elasticity very low. Many default to it because it feels familiar and stakeholders demand synchronised state
    • other patterns often fit better.

Phone Tag Saga(sac)

  • Like Epic but choreographed
    • named for the children's telephone game. With no orchestrator, the first service becomes the coordination point (the front controller)
    • on error each service sends compensating requests back along the chain
      • Logic to coordinate atomicity must live somewhere, so services carry workflow context, error handling and routing, and for a complex workflow the front controller becomes as complex as a mediator.
  • On the happy path the last service can return the result, so throughput can beat Epic; error paths are slower because each service unwinds the chain.
  • Fairly rare:
    • choreography is usually paired with asynchronicity
    • Synchronous calls prevent race conditions, and if errors are easy to resolve or services are idempotent with retries, it can scale beyond Epic.
  • Ratings:
    • coupling high, complexity high (rising with workflow complexity; stamp coupling is an alternative), responsiveness low, scale low
    • Better for simple workflows without common errors.

Fairy Tale Saga(seo)

  • A happy, easy-to-follow story
    • Eventual consistency removes the atomic requirement: if a service is down, a change can be cached until it returns
    • The orchestrator coordinates requests, responses and error handling, but each domain service owns its own transaction
      • the orchestrator can send compensating calls without being inside a transaction.
  • "Much more attractive", common in microservices: a mediator eases workflows, synchronous is the easier choice, and eventual consistency removes the hardest error-handling challenge.
  • Ratings: coupling high (two of three forces maximised, but transactionality gone), complexity very low, responsiveness medium, scale high.

Time Travel Saga(sec)

  • Synchronous, eventual, choreographed:
    • no mediator, each service accepts a request, acts and forwards it
    • It can implement Chain of Responsibility or Pipes and Filters: any one-way series of steps
    • "Time Travel" because everything is decoupled in time: consistency arrives gradually.
  • Strong for fire-and-forget workflows such as data ingestion and bulk transactions
    • weak for complex error handling, which each service must solve itself. Only asynchrony (Anthology) would scale better
    • extra effort is needed to synchronise data.
  • Ratings:
    • coupling medium, complexity low, responsiveness medium, scale high
    • An on-ramp to Anthology: synchronous is easier to reason about, implement and debug, so if scale suffices stay here.

Fantasy Fiction Saga(aao)

  • Like Epic but asynchronous
    • it seems a way to speed up an Epic, but asynchrony adds layers of complexity in the mediator. Example: transaction Alpha is pending, Beta starts, then Gamma depends on Alpha's pending outcome: the mediator must track all pending transactions, with possible deadlocks and race conditions.
  • Ratings:
    • coupling high (extreme, with out-of-order problems), complexity high, responsiveness low (extremely bad if a service is unavailable), scale low ("high scale is virtually impossible in transaction systems"). More popular than it should be
    • Parallel Saga is usually the better option.

Horror Story(aac)

  • Atomic consistency (the strictest) with asynchronous communication and choreography (the loosest): no mediator manages transactional consistency across async calls
    • Each service must track undo information for several pending transactions, possibly out of order, and coordinate in error cases (if Alpha's call fails while Beta is pending, services must reverse the firing order, undoing elements potentially out of order).
  • Typically the result of an architect starting from Epic, seeing slow performance and adding asynchrony and choreography without considering the entangled dimensions
    • Anthology (no holistic transactions) is the better move.
  • Ratings: coupling medium (not the worst; Epic is), complexity very high (the worst), responsiveness low (heavy interservice chatter), scale medium.

Parallel Saga(aeo)

  • Epic with two restrictions relaxed:
    • asynchronous and eventual. A mediator makes it suitable for complex workflows
    • services own their transactions
    • on error the mediator sends asynchronous compensating messages (retries, data synchronisation, other remediation)
      • Costs: more burden on the mediator, and async timing issues (race conditions, deadlocks, queue reliability).
  • Ratings:
    • coupling low, complexity low, responsiveness high, scale high (isolating transactions at domain level lets the system scale around domain concepts; some public-facing services need scale, back-office ones need security)
    • "An attractive set of trade-offs for many scenarios, especially with complex workflows that need high scale."

Anthology Saga(aec)

  • The opposite of Epic:
    • asynchronous, eventual, choreographed, using message queues without orchestration
    • The least coupled pattern, with the highest throughput, scale and elasticity, but each service carries workflow context and error handling
    • Works for simple, mostly linear workflows; prohibitively hard for complex or critical ones (stamp coupling can carry workflow state)
    • A Pipes and Filters architecture would fit exactly.
  • Ratings: coupling very low, complexity high, responsiveness high, scale very high.

12.3 State management and eventual consistency

  • Instead of compensating updates, an orchestrator can manage saga state with a finite state machine, always knowing the saga's current state and eventually correcting errors through retries or automated or manual action.
  • Example (Fairy Tale implementation of ticket completion):
    • the Survey Service is down, so no compensating update; the saga state becomes NO_SURVEY and a success response goes to the expert (step 7)
    • The Ticket Orchestrator Service then retries and analyses the error behind the scenes and, if it cannot resolve it, sends it to an administrator or supervisor
    • The expert is not concerned that the survey was not sent.

Saga state machines

  • A state machine describes all possible paths: a start state, transition states and the actions that occur on a transition. The new-ticket saga:
    • START:
      • customer submits a ticket
      • support plan and data are validated
      • the row is inserted
      • state becomes CREATED and the customer is notified. Errors here prevent the saga from starting.
    • CREATED: assign to an available expert (held until one is free) then ASSIGNED.
    • ASSIGNED: route to the expert; stays until routing succeeds and the expert acknowledges, then ACCEPTED.
    • ACCEPTED: either COMPLETED (expert marks complete) or REASSIGN (wrongly assigned or expert cannot finish).
    • REASSIGN: find another expert (waits if none) then back to ASSIGNED.
    • COMPLETED: send the survey and go to CLOSED, or NO_SURVEY if the survey service errs.
    • NO_SURVEY: keep retrying until the survey is sent, then CLOSED.

Initiating state Transition state Transaction action
START CREATED Assign ticket to expert
CREATED ASSIGNED Route ticket to assigned expert
ASSIGNED ACCEPTED Expert fixes problem
ACCEPTED COMPLETED Send customer survey
ACCEPTED REASSIGN Reassign to a different expert
REASSIGN ASSIGNED Route ticket to assigned expert
COMPLETED CLOSED Ticket saga done
COMPLETED NO_SURVEY Send customer survey
NO_SURVEY CLOSED Ticket saga done
  • Developers can implement such a table as transition triggers and error handling in an orchestrator (or in the services if choreographed). Compensating updates versus state management depends on the situation and a responsiveness versus consistency trade-off
    • either way the transaction's state should be known and managed.
Advantages of state management Disadvantages
Good responsiveness Data may be out of sync when errors occur
Less impact on the end user for errors Eventual consistency may take some time

12.4 Techniques for managing sagas

  • Distributed transactions cannot be "dropped in" like an ACID transaction manager; they are designed, coded and maintained by developers and architects.
  • A useful technique:
    • annotations (Java) or custom attributes (C#)
    • They hold no functionality but document and associate services with sagas
    • The sagas are listed in one Transaction enum:
// Saga.java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Saga {
    public Transaction[] value();

    public enum Transaction {
        NEW_TICKET,
        CANCEL_TICKET,
        NEW_CUSTOMER,
        UNSUBSCRIBE,
        NEW_SUPPORT_CONTRACT
    }
}

// Saga.cs
[AttributeUsage(AttributeTargets.Class)]
class Saga : System.Attribute
{
    public Transaction[] transaction;

    public enum Transaction
    {
        NEW_TICKET,
        CANCEL_TICKET,
        NEW_CUSTOMER,
        UNSUBSCRIBE,
        NEW_SUPPORT_CONTRACT
    };
}

// SurveyServiceAPI.java and TicketServiceAPI.java
@ServiceEntrypoint
@Saga(Transaction.NEW_TICKET)
public class SurveyServiceAPI
{
    ...
}

@ServiceEntrypoint
@Saga({Transaction.NEW_TICKET, Transaction.CANCEL_TICKET})
public class TicketServiceAPI
{
    ...
}
  • This shows the Survey Service in the NEW_TICKET saga and the Ticket Service in two
    • It defines the testing scope for a change and which services a change might impact
    • A simple CLI that walks the code base (finding classes with @ServiceEntrypoint and checking @Saga) can answer, even for a business analyst:
$ ./sagatool.sh NEW_TICKET -services
-> Ticket Service
-> Assignment Service
-> Routing Service
-> Survey Service

12.5 Sysops Squad saga: atomic transactions and compensating updates

  • Logan walks through ticket completion as an Epic Saga:
    • the expert marks the ticket complete on the mobile app
    • the Ticket Orchestrator calls the Ticket Service synchronously (updates and commits), which asynchronously sends analytics data to a queue for the Analytics Service and acknowledges
    • the orchestrator then calls the Survey Service synchronously (inserts a survey row, emails the survey and acknowledges), then answers the expert, who can take the next ticket.
  • Problems with compensating updates:
    • User coupled to the business process:
      • if the Survey Service is down, a compensating update reverts the ticket to in-progress and the expert gets an error and must retry
      • Why should the expert care about the survey? (In the monolith it all ran in one transaction, which Addison always thought odd.)
    • No isolation, so side effects:
      • the Analytics Service already processed the completed ticket's data, so reversing the ticket does not reverse that
      • Telling Analytics to ignore it needs complex code and timing logic, and downstream actions may already have occurred: "turtles all the way down".
    • Compensation can fail:
      • if the compensating update to the Ticket Service errors, the ticket stays "complete"
      • retrying gives "already marked as complete" and confusion about what to tell the expert. Logan: developers' confusion is often a good check on an incomplete architecture.
    • Responsiveness: the user waits until all corrective action is done (asynchronous compensation via Parallel or Anthology helps).

Advantages Disadvantages
All data restored to prior state No transaction isolation
Allows retries and restart Side effects may occur on compensation
Compensation may fail
Poor responsiveness for the end user
  • Further challenges raised by the team: a service cannot perform a rollback (what if it cannot undo?), and whether to lock participating services during the workflow (blocking other requests guarantees validity but destroys performance and scale; worse with asynchronous calls).
  • Logan's observation:
    • transactions make participants "stop their individual worlds and synchronise"; easy in a monolith with a relational database, so overused there
    • Much of the real world is not transactional (Gregor Hohpe's essay "Starbucks Does Not Use Two-Phase Commit")
    • The broader the transaction scope, the worse it gets.
  • Alternative:
    • a Fairy Tale or Parallel Saga with asynchronous eventual consistency and state management, so errors are handled behind the scenes, the user is less affected and responsiveness is better
    • If atomicity is a problem, look at those patterns.

Summary

  • Choose the saga pattern by naming which of communication, consistency and coordination the business really needs, then read its ratings
    • Avoid distributed atomic transactions unless they are essential, and make state visible.
  • Next: contracts between services, and how they influence coupling and workflows (chapter 13).
Terms to carry forward
  • Saga (local transactions plus compensating updates); the eight patterns and their superscript codes.
  • Compensating update, side effect, compensation failure.
  • Front controller, stamp coupling, idempotence.
  • Saga state machine: START, CREATED, ASSIGNED, ACCEPTED, REASSIGN, COMPLETED, NO_SURVEY, CLOSED.
  • Isomorphic diagram, chain of responsibility, pipes and filters.
  • Atomic vs eventual consistency as the dimension that most affects complexity.
