Software Architecture: The Hard Parts 13: Contracts

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 13. Previous: Software Architecture: The Hard Parts 12: Transactional Sagas. Next: Software Architecture: The Hard Parts 14: Managing Analytical Data.

Takeaways
  • A contract is "the format used by parts of an architecture to convey information or dependencies": integration points, library and framework dependencies, caches, any wiring between parts. It is an extra dimension that cuts across communication, consistency and coordination.
  • Contracts run on a spectrum from strict (a remote method call, gRPC) to loose (name-value pairs). Decide the type first (an architecture decision), then implement it (gRPC is "an implementation, not an architecture").
  • Strict gives fidelity, build-time checks and documentation but tight coupling; loose gives decoupling and evolvability but needs contract management. Consumer-driven contracts give loose coupling with governed fidelity, if the team is mature.
  • Stamp coupling (passing a large structure when each service uses a small part) is often an accidental anti-pattern (brittleness, bandwidth) but is useful for carrying workflow state in choreography.

13.1 The scene

  • Sydney:

    • then implementation is left to the developers as long as it passes the fitness functions.
  • Chapter 2's three forces (communication, consistency, coordination) are joined by contracts, which affect all of them equally, like time orthogonal to three spatial dimensions.
  • The dictionary meaning (an enforceable agreement) is widened here to cover all the techniques that wire parts together, including transitive dependencies, internal and external integration points, and caches
    • Common formats: SOAP, REST, gRPC, XML-RPC.

13.2 Strict versus loose contracts

  • Contracts are a spectrum:

  • A strict contract requires adherence to names, types, ordering and all other details, with no ambiguity
    • The strictest: a remote method call such as Java RMI, mimicking an internal call
    • Many strict formats mimic method semantics (RPC variants); gRPC is a popular remote invocation framework that defaults to strict contracts.
  • Architects like them because they model internal method-call semantics, but they make integration brittle: contracts are glue that is both used by many parts and (if they change often) a source of ripples, the combination chapter 8 warned about
    • Use strict contracts only when advantageous.
  • Even JSON can carry a schema, making it strict:
{
    "$schema": "http://json-schema.org/draft-04/schema#",
    "properties": {
        "acct": {"type": "number"},
        "cusip": {"type": "string"},
        "shares": {"type": "number", "minimum": 100}
    },
    "required": ["acct", "cusip", "shares"]
}
  • Looser formats:
    • REST models resources, not method endpoints, so adding engine details to an airplane resource does not break a seat query
    • GraphQL gives read-only aggregated data instead of costly orchestration calls across services. Two Profile views:
# Customer Wishlist's view
type Profile {
    name: String
}

# Customer Profile's own view
type Profile {
    name: String
    addr1: String
    addr2: String
    country: String
    . . .
}
  • The Wishlist knows a customer only by an identifier and needs only the name from Profile
    • Specifying every field "just in case" is stamp coupling, an anti-pattern in most cases: it introduces breaking changes where they are not needed
    • Keep contracts at a "need to know" level, a balance between semantic coupling and needless fragility.
  • The loosest contracts are name-value pairs (YAML, JSON), raw facts with no metadata or type information:
{
    "name": "Mark",
    "status": "active",
    "joined": "2003"
}
  • They allow extremely decoupled systems (a goal of microservices) but trade away contract certainty, verification and add application logic; contract fitness functions address it.

Trade-offs

Strict contracts: advantages Strict contracts: disadvantages
Guaranteed contract fidelity (schema verification of values, types, metadata) Tight coupling: if two services share a strict contract and it changes, both change
Versioned (supports two endpoints that accept different values; gradual change with some past versions) Versioned: precision, but an integration nightmare without a deprecation strategy or with too many versions
Easier to verify at build time (schema tools check integration points)
Better documentation (distinct parameters and types)
Loose contracts: advantages Loose contracts: disadvantages
Highly decoupled: the most flexibility for microservices Contract management: misspelled names, missing pairs, deficiencies a schema would catch
Easier to evolve: little or no schema (semantic coupling still needs coordination; implementation cannot reduce it) Requires fitness functions: teams often use consumer-driven contracts so loose contracts still carry enough information

13.3 Contracts in microservices

  • Two services with independent transactionality share domain information (a Customer Address)
    • Option 1: same technology stack and a strict typed contract (RMI, or gRPC) with high fidelity, but tight coupling against the microservices aspiration.
  • Option 2:
    • each service has its own internal Customer (its bounded context) and passes name-value pairs in JSON
    • Benefits:
      • each team can evolve its representation aggressively
      • implementation decoupling (one team can switch platforms without affecting the other, since all platforms can produce and consume name-value pairs, "the lingua franca of integration architecture")
    • Downside: fidelity: how do you know developers pass the right number and type of parameters? Fix with JSON schema overlays or consumer-driven contracts.

Consumer-driven contracts

  • Normally a provider decides what to emit (a push model)
    • A consumer-driven contract inverts it into a pull model: each consumer composes a contract of the items it needs and passes it to the provider, who includes it in its build and keeps the contract tests green at all times.
  • Several consumer teams with overlapping needs each give their contract to the provider, and the tests run in the provider's CI or deployment pipeline. Each team can specify strictness as it likes while fidelity is enforced during the build
    • tools automate the checks.

Advantages Disadvantages
Loose coupling between services (name-value pairs, the loosest possible) Requires engineering maturity: it works only when teams run CI with contract tests and do not ignore failures, otherwise integration points stay broken
Variability in strictness: fitness functions can check more than schemas (for example acceptable value ranges, not just numeric type) Two interlocking mechanisms rather than one: name-value pairs plus consumer-driven contracts
Evolvable: implementation details can change without breaking the semantics passed
  • The choice comes down to team maturity and decoupling against complexity plus certainty with stricter contracts.

13.4 Stamp coupling

  • Stamp coupling:
    • passing a large data structure between services where each interacts with only a small part. Common with industry-standard document formats, typically XML
    • the book's example is the global travel-industry XML itinerary, passed around with each system updating its own section.
  • It is often an accidental anti-pattern: over-specified contracts or too much bandwidth for mundane calls.

Over-coupling

  • Wishlist needs only a name from Profile (looked up by unique ID), but the architect couples to Profile's whole structure, perhaps to future-proof
    • Result: brittleness: if Profile changes a field Wishlist does not care about, such as state, the contract still breaks.

Bandwidth

  • One of the fallacies of distributed computing is that bandwidth is infinite
    • in a monolith natural barriers hide the cumulative size of calls. The example: 2,000 requests per second with a 500 KB payload is 1,000,000 KB per second
    • with only the name (200 bytes) it is a reasonable 400 KB (the book's figures, per second).

Stamp coupling for workflow management

  • For choreographed workflows that are also complex (scale pushes against orchestration), include workflow status and transactional state in the contract
    • Each service updates its part and the state, then passes it on; at the end the receiver reads the contract for success or failure, status and error messages
    • For transactional consistency, services rebroadcast the contract to previously visited services to restore atomic consistency.
  • It raises coupling above nominal, but "the semantic coupling must go somewhere", and choreography can improve throughput and scalability.
Advantages Disadvantages
Allows complex workflows within choreographed solutions Creates (sometimes artificially) high coupling between collaborators
Can create bandwidth issues at high scale

ADR: loose contract for the Sysops Squad expert mobile application
  • Context: the app is deployed through a public app store, which delays contract updates.
  • Decision: a loose name-value pair contract between the orchestrator and the app, with an extension mechanism for temporary short-term flexibility.
  • Consequences: revisit if the store allows faster or continuous deployment; more contract validation logic must live in the orchestrator and the app.

Summary

  • Choose strictness by how often the information changes and by whether the parties change together
    • verify loose contracts with consumer-driven contract tests
    • use stamp coupling deliberately (workflow state) and avoid it by accident (over-specified or large payloads).
