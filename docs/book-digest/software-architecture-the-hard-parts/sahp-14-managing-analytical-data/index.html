Software Architecture: The Hard Parts 14: Managing Analytical Data

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 14. Previous: Software Architecture: The Hard Parts 13: Contracts. Next: Software Architecture: The Hard Parts 15: Build Your Own Trade-Off Analysis.

Takeaways
  • Operational data (transactions) and analytical data (reports, aggregations, machine learning) have different purposes and need different shapes. Three architectures for analytical data: data warehouse, data lake, data mesh.
  • The data warehouse extracts, transforms into a single (star) schema and loads, centralising data and technically partitioning it; it fails on brittle integration, split domain knowledge, complexity and limited value.
  • The data lake inverts it (load and transform on demand): less up-front work, but discovery is hard, PII risk rises and it is still technically partitioned.
  • Data mesh (a sociotechnical approach, Zhamak Dehghani) aligns analytical data ownership with business domains. Its core architectural element is the data product quantum (DPQ), a cooperative quantum beside each service, always asynchronous and eventually consistent with it.
  • The chapter also shows the book's method applied to a new capability: understand it through trade-offs.

14.1 The scene

  • Dana (data architect) asks how analytical data will be handled once the operational databases are split into small parts: reporting and analytics need the data glued back together, and the company wants better predictive planning with data science and statistics
    • Logan: a data warehouse solved consolidation but had many issues.
  • Operational data has been the book's focus; analytical data now.

14.2 Previous approaches

The data warehouse

  • History:
    • monolithic applications held code and data on one system
    • client/server separated application and data processing, giving better transactional management and the ability to use historical data for analytics. The Data Warehouse pattern was an early attempt to provide queryable analytical data: operational and analytical formats do not fit each other, and aggregations and calculations are expensive on a relational database already under transactional load.
  • The pattern's characteristics:
    • Data extracted from many sources: querying all operational databases for reports was impractical, so data is extracted into one large store.
    • Transformed to a single schema:
      • operational schemas are built around transactions (OLTP, chapter 1)
      • analytics wants large-volume reporting and aggregation. Most warehouses used a star schema (dimensional modelling), denormalised for speed and simpler queries.
    • Loaded into the warehouse:
      • regular extract, transform, load, using database replication or specialised tools
      • any schema change in an operational system must be mirrored in the transformed schema, so change coordination is hard.
    • Analysis done on the warehouse: storage and compute were massive, offloading the heavy work.
    • Used by data analysts: building reports needs domain understanding, so domain expertise must exist in both the operational and analytical systems.
    • BI reports and dashboards as the output, with a SQL-ish interface for DBAs (one reason for the transformation step).
The star schema

It separates facts (the organisation's quantifiable data; for the Sysops Squad: hourly rate, time to repair, distance to client) from dimensions (descriptive attributes: squad member specialities, names, store locations), hence "dimensional models". It is purposely denormalised: simpler queries and business logic (fewer complex joins), faster queries and aggregations, data cubes and multidimensional queries. Most star schemas become incredibly complex.

  • The warehouse is a good example of technical partitioning: data is transformed into a schema that suits queries but loses the domain partitioning, which must be re-created in queries, requiring highly trained specialists.

  • Failings:
    • Integration brittleness: transforming during ingestion couples the warehouse schema to the semantics of the domain; a domain change means a schema change and an import-logic change.
    • Extreme partitioning of domain knowledge: architects, developers, DBAs and data scientists have partly overlapping expertise and must coordinate on every data change.
    • Complexity: an alternate schema, plus ingestion and transformation, is a separate ecosystem yet tightly coupled to the domains.
    • Limited functionality for the intended purpose: most warehouses failed to deliver value commensurate with the cost (large infrastructure before the cloud; requested reports the warehouse could not give).
    • Synchronisation creates bottlenecks: converging many data streams, sometimes affecting operational systems despite the wish for decoupling.
    • Operational versus analytical contract differences (chapter 13): the pipelines transform as well as ingest, adding contractual brittleness.

Centralised consolidation of data Extreme partitioning of domain knowledge
Dedicated analytics silo provides isolation Integration brittleness

  • Logan: the warehouse fit older monolithic architectures better than modern distributed ones, and the team has many more machine learning cases to support.

The data lake

  • A reaction to the warehouse's cost and failures
    • it keeps the centralised model and pipelines but inverts transform-and-load into load-and-transform: do no up-front transformation, give users data in its native form, and transform only on demand (reactive instead of proactive work)
    • Observations behind it: prebuilt warehouse schemas often did not suit the reports requested, and many ML models work better with data closer to its raw form
    • Domain experts had endured data stripped of domain context only to need domain knowledge to craft queries.
  • Characteristics: data extracted from many sources, less transformed (often stored raw, perhaps snapshots dumped as files), loaded into the lake (often cloud) with regular dumps, and used by data scientists who discover data and do the needed aggregation and composition.
  • Martin Fowler's 2015 blog post on the Data Lake pattern (the chapter's footnote: https://martinfowler.com/bliki/DataLake.html) influenced the discussion
    • Logan recalls the question "how do we manage reporting in architectures like microservices?" and the lake as an early answer.
  • Problems:
    • Difficult discovery of the proper assets: understanding of data relationships evaporates, so domain experts must still help.
    • PII and other sensitive data:
      • combining pieces of information can reveal private facts
      • many countries restrict not just private information but data that can be combined to identify people. Dumping unstructured data risks exposure, and domain experts must reanalyse the lake to avoid it.
    • Still technically, not domain, partitioned: both warehouse and lake have separate ingestion, transformation, loading and serving partitions and separate data from its context (such as PII), against the trend towards domain partitioning (as in microservices, which keep data inside the service boundary).
    • Brittleness and pathological coupling of pipelines remain (some transformation and cleansing still occur)
      • integrity and quality testing is pushed downstream, recreating bottlenecks
      • batch nature and technical partitioning cause stale data unless upstream changes are coordinated, or pipelines break.
Advantages Disadvantages
Less structured than a warehouse Sometimes difficult to understand relationships
Less up-front transformation Requires ad hoc transformations
Better suited to distributed architectures

14.3 The data mesh

  • Dehghani and others derived the Data Mesh from domain-oriented decoupling in microservices, service mesh and sidecars (chapter 8), applied to analytical data with modifications
    • The split between operational and analytical data is another orthogonal coupling, but more complex than operational coupling.
  • Definition: data mesh is a sociotechnical approach to sharing, accessing and managing analytical data in a decentralised fashion, serving reporting, ML training and insight generation, by aligning the architecture and ownership of the data with business domains and enabling peer-to-peer consumption.

Four principles

  • Domain ownership of data: owned and shared by the domains most familiar with it (those originating it or its first-class consumers), accessed peer to peer without a central lake or warehouse and without a dedicated data team.
  • Data as a product:
    • data is served as a product to avoid silos
    • organisational roles and success metrics make domains share data in a way that delights consumers. This introduces the data product quantum, serving discoverable, understandable, timely, secure, high-quality data.
  • Self-serve data platform: capabilities for data product developers and consumers, including declarative creation of data products, search and browse discoverability, and emerging graphs such as lineage and knowledge graphs.
  • Computational federated governance:
    • organisation-wide requirements (compliance, security, privacy, quality, interoperability) are met across all domains through a federated decision model of domain data product owners
    • policies are automated and embedded as code in each data product, through a platform-supplied sidecar in each DPQ that stores and executes policies at the point of access (read or write).

  • The book defers the wider topic to Zhamak Dehghani's Data Mesh (O'Reilly); this chapter covers the data product quantum.

Data product quantum (DPQ)

  • As in a service mesh, a team builds a DPQ adjacent to, but coupled with, its service
    • Service Alpha holds behaviour and operational data; its DPQ holds code and data as the interface to the analytics and reporting side
    • The DPQ is operationally independent but highly coupled to its service.
  • Types:
    • Source-aligned (native) DPQ: provides analytical data for its collaborating quantum, typically a microservice.
    • Aggregate DPQ: aggregates data from several inputs, synchronously or asynchronously (some aggregations are fine asynchronously; others need synchronous queries to a source-aligned DPQ).
    • Fit-for-purpose DPQ: custom-made for a need such as reporting, BI or machine learning.
  • Each domain contributing to analysis has a DPQ owned by the domain team that implements the service
    • It overlaps the information in the database and may interact asynchronously with domain behaviour.
  • A cooperative quantum is operationally separate, communicates with its cooperator asynchronously with eventual consistency, has tight contract coupling with its cooperator and generally looser contract coupling with the analytics quantum (the part responsible for reports, analysis and BI)
    • They are two sides of the data: operational in the quantum, analytical in the DPQ
    • The analytics quantum has static coupling to the DPQs it needs, calling them synchronously or asynchronously (some DPQs expose a SQL interface for synchronous queries, other needs aggregate across DPQs).

Data mesh, coupling and quantum

  • Analytical reporting is probably required, so the DPQ and its communication belong to the static coupling of the quantum (a service plane must exist in microservices, a message broker if messaging is used)
    • Like a sidecar it should be orthogonal to implementation changes in the service and keep its own contract with the data plane.
  • Dynamic coupling:
    • the data sidecar should always use a pattern with both eventual consistency and asynchronicity, that is Parallel Saga(aeo) or Anthology Saga(aec) (chapter 12)
    • It should never include a transactional requirement to keep operational and analytical data in sync, which would defeat the point, and communication to the data plane should generally be asynchronous to protect the service's operational characteristics.

When to use it

Advantages Disadvantages
Highly suitable for microservices architectures Requires contract coordination with the data product quantum
Follows modern architecture principles and engineering practices Requires asynchronous communication and eventual consistency
Excellent decoupling of analytical and operational data
Carefully formed contracts allow loosely coupled evolution of analytical capabilities
  • Most suitable for modern distributed architectures with well-contained transactionality and good isolation between services
    • domain teams decide the amount, cadence, quality and transparency of the data
      • Harder where analytical and operational data must stay in sync at all times (a daunting challenge in distributed architectures)
    • supporting eventual consistency, perhaps with strict contracts, avoids many difficulties.
  • The authors present data mesh as an example of incremental evolution in the ecosystem: new capabilities resolve old problems such as the artificial separation of domain from data.

14.4 Sysops Squad saga: data mesh

  • Goal:
    • become data-driven in expert supply planning (skill-set demand by location and time, to help recruitment and training)
    • Each new service already includes a DPQ run by its domain team, built out gradually
    • The data mesh platform team supplies self-serve capabilities (find and connect to data products, create new ones) and monitors the mesh for downtime and policy incompatibility
    • A global federated governance group (domain data product owners with security, legal, risk and compliance experts and platform owners) standardises data-sharing contracts, asynchronous transport and access control
      • the platform team uniformly upgrades the DPQ sidecars.
  • The Tickets DPQ is its own quantum, aggregating ticket views. For supply planning the team takes the Tickets DPQ (long-term view of tickets raised and resolved), the User Maintenance DPQ (daily snapshots of expert profiles) and the Survey DPQ (customer survey log) and adds a new Experts Supply DPQ that takes asynchronous input from the three
    • its first product, supply recommendations, uses an ML model trained on that data and yields daily recommendations.
  • Concern: incomplete data for a period skews trend analysis. Dana: no data for a day is better than incomplete data; an empty day can be exempted if it is rare.

ADR: ensure Expert Supply DPQ sources supply an entire day's data or none
  • Context: the Experts Supply DPQ analyses trends over time periods; incomplete days skew the results.
  • Decision: each source delivers complete daily snapshots or nothing for that day, so data scientists can exempt the day; contracts between the feeds and the DPQ are loosely coupled to avoid brittleness.
  • Consequences: if too many days are exempt (availability or other problems) trend accuracy suffers.
  • Fitness functions: (1) complete daily snapshot: check message timestamps on arrival; given typical volume, a gap over one minute marks the day exempt. (2) A consumer-driven contract fitness function for the Ticket DPQ and the Experts Supply DPQ so internal evolution of the Ticket domain does not break supply planning.

Summary

  • Choose the analytical architecture by how well it respects domain boundaries: warehouse and lake centralise and technically partition data
    • the mesh keeps analytical data with its domain behind contracts and asynchronous eventual consistency.
  • Next: how to apply the trade-off method yourself (chapter 15).
Terms to carry forward
  • Data warehouse, data lake, data mesh; ETL vs load-and-transform.
  • Star schema, facts, dimensions; OLTP vs analytical use.
  • Data product quantum (DPQ): source-aligned, aggregate, fit-for-purpose.
  • Cooperative quantum; analytics quantum.
  • Four data mesh principles: domain ownership, data as a product, self-serve platform, computational federated governance.
  • PII risk of combined data.
