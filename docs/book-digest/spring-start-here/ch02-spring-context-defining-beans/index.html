Book digests/Spring Start Here

Ch 2: The Spring context, defining beans

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 2 (pp. 23-52). Previous: Ch 1: Spring in the real world. Book projects: ssh_ch2_ex1 to ssh_ch2_ex6.

Takeaways
  • Spring can only manage objects it knows about.
  • The context is a place in your app's memory holding the objects Spring manages; each such object is a bean.
  • Three ways to put a bean in:
  1. @Bean methods: full control over creation.
  2. Stereotype annotations like @Component: least code.
  3. registerBean(): programmatic, for conditional logic.

  • Definition (book): a bean is an object instance that has been added to the Spring context; once there, Spring manages it entirely and can connect framework capabilities to it.
  • Not every object must be a bean. Only the ones Spring needs to "know" so it can attach features to them. (Illustrative: a short-lived StringBuilder inside a method stays plain.)
  • By default Spring knows none of your objects.

2.1 Setup: the skeleton project (ssh_ch2_ex1)

The book's running example is a Parrot class with a name (any class works; Foo is fine).

public class Parrot {
    private String name;
    // getters and setters omitted
}

Maven pom.xml dependency (Java 25 LTS, Spring 7.0.1 in the book):

<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-context</artifactId>
  <version>7.0.1</version>
</dependency>
  • Spring is modular:
    • add only the parts you use. spring-context is enough here. All Spring dependencies live in the org.springframework group
    • look them up in the Spring reference, no need to memorise.
  • Creating the context:
var context = new AnnotationConfigApplicationContext();

AnnotationConfigApplicationContext is the implementation for annotation-based config (the most common). The book advises not to dive into the context class hierarchy yet: you would lose the essentials.

  • Java 25 note: the book's listings alternate between public static void main(String[] args) and the Java 25 shorthand static void main().

2.2 Way 1: the @Bean annotation

Three steps:

Step 1, config class (a special class telling Spring what to do, e.g. create beans, enable features):

@Configuration
public class ProjectConfig { }

Step 2, @Bean method (ssh_ch2_ex2):

@Configuration
public class ProjectConfig {
    @Bean
    Parrot parrot() {
        var p = new Parrot();
        p.setName("Koko");
        return p;
    }
}
  • Naming convention:
    • the method name is a noun, not a verb, because the method represents the object
    • It also becomes the bean name ("parrot")
    • Do not confuse the bean name ("parrot") with the parrot's name attribute ("Koko"); the latter means nothing to Spring.

Step 3, start the context with it, then fetch the bean:

var context = new AnnotationConfigApplicationContext(ProjectConfig.class);
Parrot p = context.getBean(Parrot.class);   // no cast needed
System.out.println(p.getName());            // Koko
  • getBean(Type) looks up by type. If no bean of that type exists, Spring throws.

Any object can be a bean

@Bean String hello() {
    return "Hello";
}
@Bean Integer ten() {
    return 10;
}

// Usage
context.getBean(String.class);   // Hello
context.getBean(Integer.class);  // 10

Prints Koko, Hello, 10. The type is irrelevant to Spring. (Real apps rarely register a String or Integer; this just proves the point.)

Several beans of the same type (ssh_ch2_ex3)

@Bean Parrot parrot1() {
    var p = new Parrot();
    p.setName("Koko");
    return p;
}
@Bean Parrot parrot2() {
    var p = new Parrot();
    p.setName("Miki");
    return p;
}
@Bean Parrot parrot3() {
    var p = new Parrot();
    p.setName("Riki");
    return p;
}

  • Asking by type alone fails with: NoUniqueBeanDefinitionException: No qualifying bean of type 'main.Parrot' available: expected single matching bean but found 3: parrot1,parrot2,parrot3. Spring cannot guess which you mean.
  • Fix 1, by name:
    • context.getBean("parrot2", Parrot.class) returns Miki
    • The bean name defaults to the @Bean method name (this is why the exception message lists parrot1,parrot2,parrot3).
  • Fix 2, @Primary (ssh_ch2_ex4): Spring's default choice when several beans match and no name is given. Only one bean per type may be primary.
@Bean
@Primary
Parrot parrot2() {
    var p = new Parrot();
    p.setName("Miki");
    return p;
}

2.3 Way 2: stereotype annotations (ssh_ch2_ex5)

Annotate the class, and Spring creates the instance itself. @Component is the most basic stereotype annotation (others come later).

@Component
public class Parrot {
    private String name;
    public String getName() {
        return name;
    }
    public void setName(String name) {
        this.name = name;
    }
}

// ProjectConfig.java
@Configuration
@ComponentScan(basePackages = "com.example.beans")
public class ProjectConfig { }
  • Gotcha: @Component alone does nothing. By default Spring does not scan for stereotype annotations; @ComponentScan with the package(s) switches that on.
  • The config class is still needed but has no bean methods. You can mix @Bean and stereotypes in one app (later chapters).
  • Fetching works the same; but note the result:
Parrot p = context.getBean(Parrot.class);
System.out.println(p);            // default toString, proves the bean exists
System.out.println(p.getName());  // null: Spring only calls the constructor, it did not set a name

@PostConstruct: act right after creation

With @Component you lose the chance to configure the instance (no method body like @Bean). @PostConstruct is the fix: Spring calls that method right after the constructor finishes.

@Component
public class Parrot {
    private String name;
    @PostConstruct
    public void init() {
        this.name = "Kiki";
    }
}

Prints Kiki. The annotation comes from Jakarta EE, not Spring, so it needs an explicit dependency (APIs removed from the JDK must be added back):

<dependency>
  <groupId>jakarta.annotation</groupId>
  <artifactId>jakarta.annotation-api</artifactId>
  <version>2.1.1</version>
</dependency>

@PreDestroy is the mirror: runs just before Spring closes and clears the context (also from JSR-250). The author advises avoiding it for anything important, because Spring may fail to clear the context and never call it. Example risk: closing a database connection in it.

@Bean vs stereotype: when to use which (the book's table 2.1)

@Bean Stereotype (@Component)
Control over creation Full: you build and configure the object in the method body Only after Spring creates it (e.g. via @PostConstruct)
Instances per class As many as you like One
Which classes Any, even library or JDK types (String, Integer) Only classes you own (you must edit the class to annotate it)
Boilerplate A method per bean None

Rule of thumb from the book: use stereotype annotations as much as possible (less code); use @Bean only when you cannot (e.g. a library class you cannot annotate, or you need several instances or custom setup).

2.4 Way 3: programmatic, registerBean() (ssh_ch2_ex6)

Available from Spring 5 (book's claim). Use it when @Bean and stereotypes are not enough, typically conditional registration, which annotations cannot express:

if (condition) {
    registerBean(b1);
} else {
    registerBean(b2);
}

Book scenario: an app reads parrots, some green and some orange, and registers only the green ones.

Signature:

<T> void registerBean(
    String beanName,                         // null if you don't need a name
    Class<T> beanClass,                      // e.g. Parrot.class
    Supplier<T> supplier,                    // returns the instance to add
    BeanDefinitionCustomizer... customizers  // optional, e.g. make it primary
);
  • Supplier is the functional interface from java.util.function: returns a value, takes no parameters.
  • BeanDefinitionCustomizer configures bean characteristics; varargs, so it can be omitted.

Example: empty @Configuration class, Parrot is a plain POJO with no annotations:

var context = new AnnotationConfigApplicationContext(ProjectConfig.class);

Parrot x = new Parrot();
x.setName("Kiki");
Supplier<Parrot> parrotSupplier = () -> x;

context.registerBean("parrot1", Parrot.class, parrotSupplier);

Parrot p = context.getBean(Parrot.class);
System.out.println(p.getName());   // Kiki

Making it primary via a customizer:

context.registerBean("parrot1", Parrot.class, parrotSupplier,
        bc -> bc.setPrimary(true));

Historical note (book): early Spring configured everything in XML; this book uses only modern approaches.

Decision guide: which way?

Chapter summary (book)

  • The context (IoC container) manages objects wired into Spring features (DI, transactions, security, testing); these objects are beans.
  • Three ways in: @Bean, stereotype annotations such as @Component, registerBean().
  • @Bean = full control, good for third-party classes and advanced config. Stereotypes = preferred for your own classes (less boilerplate).
  • Several beans of one type need a name or @Primary to disambiguate.
  • Lifecycle callbacks such as @PostConstruct customise initialisation after creation.
  • Defining beans correctly is the foundation for the next chapters.

Terms to carry forward
