Book digests/Spring Start Here

Ch 3: The Spring context, wiring beans

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 3. Previous: Ch 2: The Spring context, defining beans. Book projects: ssh_ch3_ex1 to ssh_ch3_ex9.

Takeaways
  • Objects rarely work alone: a Person has a Parrot.
  • Instead of fetching beans with getBean(), you let Spring hand each bean its collaborators.
  • That is dependency injection (DI), an application of IoC.
  • You can link beans by wiring (inside @Bean methods) or by autowiring (@Autowired).
  • Prefer constructor injection.
  • When several beans match, pick with @Primary or @Qualifier.
  • Parameter name vs bean name: injection is by type; the parameter name only matters as a fallback when several beans of that type exist (then parrot2 picks the bean named parrot2). With one bean the name is irrelevant; prefer an explicit @Qualifier.

  • Chapters 2 and 3 use toy classes (parrots, persons) on purpose, to focus on syntax. From chapter 4 the class design gets closer to real projects.
  • Has-A relationship: Person holds a Parrot field. Both are beans; the task is to set that field.

3.1 Linking beans defined with @Bean

Use this when you cannot edit the class (JDK or library types). Two steps each time: (1) define both beans, (2) link them.

Step 1 (ssh_ch3_ex1), two beans, no link yet:

// Parrot.java
public class Parrot {
    private String name;
    // getters, setters
    @Override public String toString() {
        return "Parrot : " + name;
    }
}

// Person.java
public class Person {
    private String name;
    private Parrot parrot;
    // getters, setters
}

// ProjectConfig.java
@Configuration
public class ProjectConfig {
    @Bean public Parrot parrot() {
        Parrot p = new Parrot();
        p.setName("Koko");
        return p;
    }
    @Bean public Person person() {
        Person p = new Person();
        p.setName("Ella");
        return p;
    }
}

// Usage
var context = new AnnotationConfigApplicationContext(ProjectConfig.class);
Person person = context.getBean(Person.class);
Parrot parrot = context.getBean(Parrot.class);
System.out.println("Person's name: " + person.getName());      // Ella
System.out.println("Parrot's name: " + parrot.getName());      // Koko
System.out.println("Person's parrot: " + person.getParrot());  // null  <- not linked

3.1.1 Wiring by calling the other @Bean method (ssh_ch3_ex2)

@Bean
public Person person() {
    Person p = new Person();
    p.setName("Ella");
    p.setParrot(parrot());   // direct call
    return p;
}

Output: Person's parrot: Parrot : Koko.

The classic question: does this create two Parrots? No. Spring controls how @Bean methods are called (it intercepts them; chapter 6 explains how). A call to parrot() from another @Bean method means "give me the parrot bean".

Proof: add a constructor that prints, run again, and the message appears once.

public Parrot() {
    System.out.println("Parrot created");
}

Parrot created
Person's name: Ella
Person's parrot: Parrot : Koko

3.1.2 Wiring by method parameter (ssh_ch3_ex3)

Add a parameter of the needed type and Spring injects the bean from its context.

@Bean
public Person person(Parrot parrot) {   // Spring injects the parrot bean here
    Person p = new Person();
    p.setName("Ella");
    p.setParrot(parrot);
    return p;
}
  • Works whether the parrot bean came from a @Bean method or a stereotype annotation like @Component; that flexibility is a plus over the direct call.
  • Does the parameter name have to match the bean method name? Only when there is more than one bean of that type.
    • Spring matches by type first. With one Parrot bean, Person person(Parrot parrot) works whatever the parameter is called (parrot, p, bird).
    • With several Parrot beans (say parrot1() and parrot2()), Spring falls back to the parameter name: a parameter called parrot2 gets the bean named parrot2 (a @Bean method's name is the bean's name by default). This is the book's figure 3.12 point.
    • If the name matches no bean and there is no @Primary or @Qualifier, startup fails because Spring cannot choose (section 3.4).
    • Safer: don't depend on the name; use @Qualifier("parrot2"), which survives renaming the parameter. (Not from the book: the name fallback also needs the parameter names kept in the compiled class, the -parameters compiler flag, which Spring Boot's build plugins set by default.)
  • Author's view: which one developers pick is mostly taste; know both, you will meet both.
  • DI defined (book): the framework sets a value into a field or parameter. It is an application of IoC, because the framework (a dependency) controls the app.

3.2 @Autowired

You mark the dependency in the class that needs it, so the relationship is visible right where it is used. Three places to put it. Examples use @Component beans, the common real-world combo.

Style How Notes
Field injection @Autowired on the field fine in demos and tests; the field cannot be final
Constructor injection @Autowired on the constructor (optional if there is one constructor) field can be final; easy to test
Setter injection @Autowired on the setter rare, found in old apps; field cannot be final; harder to test

3.2.1 On the field (ssh_ch3_ex4)

// Parrot.java
@Component
public class Parrot {
    private String name = "Koko";
    // getters, setters, toString
}

// Person.java
@Component
public class Person {
    private String name = "Ella";
    @Autowired
    private Parrot parrot;
    // getters, setters
}

// ProjectConfig.java
@Configuration
@ComponentScan(basePackages = "com.example.beans")
public class ProjectConfig { }

Output: Person's name: Ella / Person's parrot: Parrot : Koko.

Why avoid it in production code:

  • You cannot make the field final, so nobody can guarantee immutability:
    @Autowired
private final Parrot parrot;   // does not compile: final field has no initial value
  • It is harder to set the dependency yourself, which makes unit tests awkward (chapter 15).
  • Still common in demos, proofs of concept and tests, so you must read it.

3.2.2 On the constructor (ssh_ch3_ex5), the recommended way

@Component
public class Person {
    private String name = "Ella";
    private final Parrot parrot;

    @Autowired
    public Person(Parrot parrot) {
        this.parrot = parrot;
    }
}
  • Field can be final; tests can pass any Parrot straight to the constructor.
  • Since Spring 4.3, @Autowired is optional when the class has one constructor.

3.2.3 On the setter (ssh_ch3_ex6)

@Autowired
public void setParrot(Parrot parrot) {
    this.parrot = parrot;
}
  • Rare: harder to read, no final, no testing benefit. The author has seen it only in a couple of old apps.

3.3 Circular dependencies (ssh_ch3_ex7)

Bean A needs bean B to be created, and B needs A. Spring is deadlocked.

// Person.java
@Component
public class Person {
    private final Parrot parrot;
    @Autowired public Person(Parrot parrot) {
        this.parrot = parrot;
    }
}

// Parrot.java
public class Parrot {
    private String name = "Koko";
    private final Person person;
    @Autowired public Parrot(Person person) {
        this.person = person;
    }
}

Startup fails:

Caused by: org.springframework.beans.factory.BeanCurrentlyInCreationException:
Error creating bean with name 'parrot': Requested bean is currently in creation:
Is there an unresolvable circular reference?
  • The author's claim: nearly every Spring developer has created one by mistake.
  • It signals bad class design. The fix is to rewrite so the two classes do not depend on each other for creation; read the exception, it names the classes involved.

3.4 Choosing among several beans of one type

Three cases when you inject a Parrot and several exist:

  1. One bean is @Primary (chapter 2): Spring injects it.
  2. You pick explicitly with @Qualifier.
  3. Neither: exception, because Spring cannot choose.

Parameter injection (ssh_ch3_ex8):

@Bean public Parrot parrot1() {
    Parrot p = new Parrot();
    p.setName("Koko");
    return p;
}
@Bean public Parrot parrot2() {
    Parrot p = new Parrot();
    p.setName("Miki");
    return p;
}

@Bean
public Person person(@Qualifier("parrot2") Parrot parrot2) {
    Person p = new Person();
    p.setName("Ella");
    p.setParrot(parrot2);
    return p;
}

Output: Person's parrot: Parrot : Miki. The book's figure 3.12 also states that naming the parameter like the bean (parrot2) lets Spring pick it; the code uses @Qualifier explicitly, which is the unambiguous form.

@Autowired constructor (ssh_ch3_ex9), Parrot has no annotation; both beans come from @Bean methods, Person is a @Component:

// Person.java
@Component
public class Person {
    private String name = "Ella";
    private final Parrot parrot;
    public Person(@Qualifier("parrot2") Parrot parrot2) {
        this.parrot = parrot2;
    }
}

// ProjectConfig.java
@Configuration
@ComponentScan(basePackages = "com.example.beans")
public class ProjectConfig {
    @Bean public Parrot parrot1() { ... "Koko" ... }
    @Bean public Parrot parrot2() { ... "Miki" ... }
}

Output: Person's parrot: Parrot : Miki.

Author's wrap-up: you will use constructor injection most of the time; knowing why the other options exist lets you debug a strange context "without panic (and without blaming the parrot)".

Chapter summary (book)

  • Beans collaborate; Spring manages the links through DI.
  • In config classes: call one @Bean method from another, or inject through method parameters.
  • DI implements IoC: objects receive dependencies instead of creating them.
  • @Autowired works on field, constructor and setter. Constructor injection is preferred (immutability, readability, testability).
  • Circular dependencies are a design problem: refactor.
  • Several beans of one type need extra information (@Primary or @Qualifier).
  • Wiring by method parameter is by type. The parameter name only has to match the @Bean method (bean) name when several beans of that type exist and you rely on the name to choose; with a single bean it need not match, and @Qualifier is the explicit alternative.
