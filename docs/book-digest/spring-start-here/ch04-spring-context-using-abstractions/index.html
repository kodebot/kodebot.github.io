Ch 4: The Spring context, using abstractions

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 4. Previous: Ch 3: The Spring context, wiring beans. Book projects: ssh_ch4_ex1 to ssh_ch4_ex7.

Takeaways
  • Real objects depend on other objects (controller → service → repository).
  • If each points at a concrete class, changing one forces changes in its users.
  • An interface says what is needed; an implementing class says how.
  • Spring's DI then supplies the right implementation at runtime.
  • This chapter is the first realistic example (comments on tasks) and the first to decide which objects are beans and how to choose between several implementations.

4.1 Interfaces as contracts

  • Interface = the "what"; implementing class = the "how".
  • Author's anecdote:
    • as a child he asked his dad for a knife to open a radio case
    • his dad said use a screwdriver. Lesson: ask for what you need, not for a solution. Interfaces are how objects ask for what they need.
  • Ride-sharing analogy: the customer requests a trip (the interface), not a specific car or driver. Any driver with a car can answer, so customer and driver stay decoupled.

Decoupling example: DeliveryDetailsPrinter and sorting

Printing package details sorted by destination address. If the printer holds SorterByAddress directly, switching to "sort by sender" means editing the printer as well. The printer decides both what it needs and which implementation, which is the problem.

public interface Sorter {
  void sortDetails();
}

Now the printer depends on Sorter; any implementation can satisfy it and the printer never changes.

4.1.2 The scenario

A team task-management app. A user publishes a comment on a task; the app stores it (e.g. in a database) and emails a configured address.

4.1.3 Plain Java, no framework (ssh_ch4_ex1)

Naming conventions the author uses:

  • Service: object that implements a use case; name ends in "Service" (CommentService). He recommends chapter 2 of Robert C. Martin's Clean Code (Pearson, 2008) for naming.
  • Repository (also called DAO, data access object): talks to the database (CommentRepository).
  • Proxy: talks to something outside the app (CommentNotificationProxy).
  • Model: a POJO (plain object with no dependencies, described only by attributes and methods) that carries data (Comment with author and text).

Storing and notifying are two different responsibilities, so two objects, each hidden behind an interface.

Green = beans (annotated classes), white = interfaces, amber = plain data object (details in 4.2.1). Packages: model, repositories, proxies, services.

public class Comment {
    private String author;
    private String text;
    // getters, setters
}

// CommentRepository.java
public interface CommentRepository {
    void storeComment(Comment comment);
}

// DBCommentRepository.java
public class DBCommentRepository implements CommentRepository {
    @Override
    public void storeComment(Comment comment) {
      System.out.println("Storing comment: " + comment.getText());  // simulated
    }
}

// CommentNotificationProxy.java
public interface CommentNotificationProxy {
    void sendComment(Comment comment);
}

// EmailCommentNotificationProxy.java
public class EmailCommentNotificationProxy implements CommentNotificationProxy {
    @Override
    public void sendComment(Comment comment) {
      System.out.println("Sending notification for comment: " + comment.getText());
    }
}

// CommentService.java
public class CommentService {
    private final CommentRepository commentRepository;
    private final CommentNotificationProxy commentNotificationProxy;

    public CommentService(CommentRepository commentRepository,
                          CommentNotificationProxy commentNotificationProxy) {
        this.commentRepository = commentRepository;
        this.commentNotificationProxy = commentNotificationProxy;
    }

    public void publishComment(Comment comment) {
      commentRepository.storeComment(comment);
      commentNotificationProxy.sendComment(comment);
    }
}

// Main.java
public class Main {
    static void main() {
      var commentRepository = new DBCommentRepository();
      var commentNotificationProxy = new EmailCommentNotificationProxy();
      var commentService = new CommentService(commentRepository, commentNotificationProxy);

      var comment = new Comment();
      comment.setAuthor("Laurentiu");
      comment.setText("Demo comment");
      commentService.publishComment(comment);
    }
}

Sending notification for comment: Demo comment

Note Main creates every object and wires them by hand. Spring will remove that.

4.2 DI with abstractions

4.2.1 Which objects belong in the Spring context? (ssh_ch4_ex2)

  • Test: Does this object need to be managed by the framework? Here the only Spring feature in use is DI, so an object becomes a bean if it has an injected dependency or is a dependency itself.
  • CommentService (has two dependencies), DBCommentRepository and EmailCommentNotificationProxy (both are dependencies): beans.
  • Comment has no dependencies and is no one's dependency: not a bean
    • Adding it would be over-engineering: more complexity and less performance, for no framework benefit
    • (A question the author gets often in courses.)
  • Never put a stereotype annotation on an interface or abstract class. Spring cannot instantiate it; it compiles but is useless and counts as bad practice.
// DBCommentRepository.java
@Component
public class DBCommentRepository implements CommentRepository { ... }

// EmailCommentNotificationProxy.java
@Component
public class EmailCommentNotificationProxy implements CommentNotificationProxy { ... }

// CommentService.java
@Component
public class CommentService {
    private final CommentRepository commentRepository;
    private final CommentNotificationProxy commentNotificationProxy;
    // one constructor, so @Autowired is optional (needed if there were several)
    public CommentService(CommentRepository commentRepository,
                          CommentNotificationProxy commentNotificationProxy) { ... }
    public void publishComment(Comment comment) { ... }
}

// ProjectConfiguration.java
@Configuration
@ComponentScan(basePackages = {"com.example.proxies", "com.example.repositories", "com.example.services"})
public class ProjectConfiguration { }

The model package is left out of the scan because it contains no annotated classes.

var context = new AnnotationConfigApplicationContext(ProjectConfiguration.class);
var comment = new Comment();
comment.setAuthor("Laurentiu");
comment.setText("Demo comment");
var commentService = context.getBean(CommentService.class);
commentService.publishComment(comment);

Same output as before. Spring sees interface-typed constructor parameters and finds beans whose classes implement those interfaces. With three classes the saving is small; with many classes, letting Spring create and connect objects removes boilerplate.

Other DI styles work the same with abstractions (sidebar):

  • Field injection (ssh_ch4_ex3): @Autowired private CommentRepository commentRepository; and likewise for the proxy; fields are no longer final. Demo only; prefer the constructor.
  • @Bean parameters (ssh_ch4_ex4): no @Component, no @ComponentScan:
    @Configuration
public class ProjectConfiguration {
    @Bean public CommentRepository commentRepository() {
        return new DBCommentRepository();
    }
    @Bean public CommentNotificationProxy commentNotificationProxy() {
        return new EmailCommentNotificationProxy();
    }
    @Bean public CommentService commentService(CommentRepository commentRepository,
                                               CommentNotificationProxy commentNotificationProxy) {
        return new CommentService(commentRepository, commentNotificationProxy);
    }
}

4.2.2 Several implementations of one abstraction

Add a second implementation (ssh_ch4_ex5, starting from ex2):

@Component
public class CommentPushNotificationProxy implements CommentNotificationProxy {
    @Override
    public void sendComment(Comment comment) {
      System.out.println("Sending push notification for comment: " + comment.getText());
    }
}

Run as is and it fails:

NoUniqueBeanDefinitionException: No qualifying bean of type 'proxies.CommentNotificationProxy'
available: expected single matching bean but found 2:
commentPushNotificationProxy,emailCommentNotificationProxy

Fix 1: @Primary (the default choice):

@Component
@Primary
public class CommentPushNotificationProxy implements CommentNotificationProxy { ... }

Output: Sending push notification for comment: Demo comment.

  • "Why keep both if Spring injects only one?" A dependency of yours may already provide an implementation of an interface, but not one that suits your app
    • You write your own and mark it @Primary so Spring injects yours.

Fix 2: @Qualifier (ssh_ch4_ex6): when different objects need different implementations (email here, push there). Name each implementation, then name the one you want at the injection point:

@Component @Qualifier("PUSH")  public class CommentPushNotificationProxy  implements CommentNotificationProxy { ... }
@Component @Qualifier("EMAIL") public class EmailCommentNotificationProxy implements CommentNotificationProxy { ... }

// CommentService.java
@Component
public class CommentService {
    private final CommentRepository commentRepository;
    private final CommentNotificationProxy commentNotificationProxy;
    public CommentService(CommentRepository commentRepository,
                          @Qualifier("PUSH") CommentNotificationProxy commentNotificationProxy) { ... }
}

Output: Sending push notification for comment: Demo comment.

4.3 Say the responsibility: @Service and @Repository (ssh_ch4_ex7)

@Component is generic. Developers usually mark known roles explicitly. All three are stereotype annotations: Spring creates and registers an instance of the annotated class.

  • @Service: object that implements use cases.
  • @Repository: object that manages data persistence.
  • @Component: anything else with no dedicated annotation (e.g. the proxy).
// CommentService.java
@Service
public class CommentService { ... }

// DBCommentRepository.java
@Repository
public class DBCommentRepository implements CommentRepository { ... }

The benefit is readability: the role of each class is visible to anyone reading it. Next chapter: how Spring creates and manages these objects through their life cycle.

Chapter summary (book)

  • Decoupling = classes do not depend on specific implementations, so the app is easier to change, extend and maintain.
  • Interfaces define the contract. With DI on an interface, Spring finds a bean implementing it.
  • Stereotype annotations go on classes Spring should create, never on interfaces.
  • Several beans for one interface: @Primary (default) or @Qualifier (by name).
  • @Service for service logic, @Repository for data access; they make roles explicit.
