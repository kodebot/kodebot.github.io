Ch 6: Using aspects with Spring AOP

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 6. Previous: Ch 5: The Spring context, bean scopes and life cycle. Book projects: ssh_ch6_ex1 to ssh_ch6_ex7. Last chapter of part 1 (fundamentals).

Takeaways
  • An aspect lets Spring intercept a method call and run extra logic (logging, security checks, timing, transactions) without cluttering the method.
  • Spring does it by handing you a proxy instead of the real bean.
  • Setup is four steps: enable, write an @Aspect class (and make it a bean), pick an advice annotation with a pointcut expression, write the logic.
  • Use sparingly: aspects hide code, so hide only what is irrelevant.

6.1 Why aspects, and how they work

  • A method often does more than its job:
    • logging, security, transactions, auditing, timing
    • Mixed in, it gets hard to read
    • Aspects move that logic aside (the book's figure: a developer, Jane, with logging lines tangled into business code; Count Dracula shows her aspects).
  • Called aspect-oriented programming (AOP). Author's caveat, quoting Peter Parker's uncle: "With great power comes great responsibility".
  • Why learn it: Spring builds major features on aspects: transactions and security (later chapters). Knowing it saves debugging time.

Terminology (what you define when designing an aspect):

  • Aspect: the code Spring runs when specific methods are called.
  • Advice: when to run it (before, after, around the call).
  • Pointcut: which methods to intercept.
  • Join point: the event that triggers the aspect; in Spring it is always a method call.
  • Target object: the bean whose method is intercepted. It must be a bean, or Spring cannot intercept it.

Weaving: Spring wraps the target in a proxy and exposes the proxy instead of the real bean. Whether you call getBean() or use DI, you get the proxy. The proxy applies the aspect logic, then delegates to the real method.

6.2 Implementing aspects

Scenario: new regulations require logging when each use case starts and ends.

6.2.1 A simple aspect (ssh_ch6_ex1)

Extra Maven dependency next to spring-context:

<dependency>
   <groupId>org.springframework</groupId>
   <artifactId>spring-aspects</artifactId>
   <version>7.0.1</version>
</dependency>

Model and service (the service uses a real logger, not System.out):

// Comment.java
public class Comment {
    private String text;
    private String author;
    // getters, setters
}

// CommentService.java
@Service
public class CommentService {
    private final Logger logger = Logger.getLogger(CommentService.class.getName());
    public void publishComment(Comment comment) {
      logger.info("Publishing comment:" + comment.getText());
    }
}
  • Real apps use a logging framework, not System.out: Log4j, Logback, or the JDK's java.util.logging (used here to avoid extra dependencies)
    • They work with or without Spring
    • The author points to chapter 4 of his book Troubleshooting Java, 2nd ed
    • (Manning, 2025) for logs as a troubleshooting technique.
  • The logger name is usually the class name so you can see where a message came from.
@Configuration
@ComponentScan(basePackages = "com.example.services")
public class ProjectConfig { }

// Usage
var c = new AnnotationConfigApplicationContext(ProjectConfig.class);
var service = c.getBean(CommentService.class);
Comment comment = new Comment();
comment.setText("Demo comment");
comment.setAuthor("Natasha");
service.publishComment(comment);

Output before the aspect:

INFO: Publishing comment:Demo comment

Four steps to add an aspect:

Step 1: enable aspects. Spring features you must switch on use annotations starting with Enable:

@Configuration
@ComponentScan(basePackages = "com.example.services")
@EnableAspectJAutoProxy
public class ProjectConfig { }

Step 2: aspect class, and make it a bean.

@Aspect
public class LoggingAspect {
  public void log() { /* later */ }
}

// Bean methods
@Bean
public LoggingAspect aspect() {
    return new LoggingAspect();
}
  • @Aspect is not a stereotype annotation. It does not create a bean. Forgetting to add a bean is a common mistake that frustrates many people.

Step 3: advice annotation and pointcut.

@Aspect
public class LoggingAspect {
    @Around("execution(* com.example.services.*.*(..))")
    public void log(ProceedingJoinPoint joinPoint) throws Throwable {
      joinPoint.proceed();
    }
}

The string is AspectJ pointcut language. You do not need to memorise it:

  • The author looks it up in the docs or asks an AI assistant (he names Junie, ChatGPT, Claude, Codex).
  • Keep expressions simple; complex ones are best avoided.
Part of execution(* com.example.services.*.*(..)) Meaning
* (first) any return type
com.example.services the package
* (second) any class
* (third) any method name
(..) any parameters

Meaning: intercept any method in any class of the services package, any return type, any name, any parameters. ProceedingJoinPoint represents the intercepted method; its main use is deciding when to delegate.

Step 4: logic.

@Aspect
public class LoggingAspect {
    private final Logger logger = Logger.getLogger(LoggingAspect.class.getName());

    @Around("execution(* com.example.services.*.*(..))")
    public void log(ProceedingJoinPoint joinPoint) throws Throwable {
        logger.info("Method will execute");
        joinPoint.proceed();                     // calls the intercepted method
        logger.info("Method executed");
    }
}

Output:

INFO: Method will execute
INFO: Publishing comment:Demo comment
INFO: Method executed

  • proceed() calls the real method
    • If you do not call it, the method never runs and the caller does not know
    • That is how a security aspect can block a call (authorization rules fail: do not delegate).
  • proceed() throws Throwable because it propagates whatever the method throws. The example just rethrows; you can wrap it in try/catch/finally.

6.2.2 Reading and altering parameters and return value (ssh_ch6_ex2, ex3)

The service now returns a value:

public String publishComment(Comment comment) {
  logger.info("Publishing comment:" + comment.getText());
  return "SUCCESS";
}

From the join point you can read the method name and arguments:

String methodName = joinPoint.getSignature().getName();
Object[] arguments = joinPoint.getArgs();

The aspect must now return what the method returned:

@Around("execution(* com.example.services.*.*(..))")
public Object log(ProceedingJoinPoint joinPoint) throws Throwable {
    String methodName = joinPoint.getSignature().getName();
    Object[] arguments = joinPoint.getArgs();
    logger.info("Method " + methodName + " with parameters " + Arrays.asList(arguments) + " will execute");
    Object returnedByMethod = joinPoint.proceed();
    logger.info("Method executed and returned " + returnedByMethod);
    return returnedByMethod;
}

INFO: Method publishComment with parameters [com.example.model.Comment@3f1d2e23] will execute
INFO: Publishing comment:Demo comment
INFO: Method executed and returned SUCCESS
INFO: SUCCESS          <- printed by main()

An aspect can also: change the arguments, change the returned value, throw an exception to the caller, or catch an exception from the method. ssh_ch6_ex3:

Comment comment = new Comment();
comment.setText("Some other text!");
Object[] newArguments = {comment};
Object returnedByMethod = joinPoint.proceed(newArguments);   // different argument sent on
logger.info("Method executed and returned " + returnedByMethod);
return "FAILED";                                             // caller gets something else

INFO: Publishing comment:Some other text!     <- the method saw the replaced argument
INFO: Method executed and returned SUCCESS    <- what the method returned
INFO: FAILED                                  <- what main() received

Warnings (repeated twice in the book):

  • Aspects are so powerful they can hide relevant code and make the app harder to maintain
    • only hide irrelevant, easily implied lines. Think of the next maintainer: they should be able to tell what is happening.
  • Altering parameters and results is legitimately used, e.g. by Spring's transaction support.
  • Author's advice: learn how something works before using it; developers who skip this introduce bugs, vulnerabilities and performance problems.

6.2.3 Intercepting annotated methods (ssh_ch6_ex4)

Mark target methods with your own annotation so you avoid complex expressions.

@Retention(RetentionPolicy.RUNTIME)   // required: by default annotations are not visible at runtime
@Target(ElementType.METHOD)           // restrict it to methods
public @interface ToLog { }

// CommentService.java
@Service
public class CommentService {
    public void publishComment(Comment comment) { ... }
    @ToLog
    public void deleteComment(Comment comment)  { ... }
    public void editComment(Comment comment)    { ... }
}

@Around("@annotation(ToLog)")      // any method annotated with @ToLog
public Object log(ProceedingJoinPoint joinPoint) throws Throwable { /* same logic */ }

Only deleteComment() is intercepted. Annotations arrived in Java 5 and are the de facto way to configure frameworks.

6.2.4 Other advice annotations (ssh_ch6_ex5)

@Around is the most used because it covers every case, but prefer the simplest tool that suffices. The other four are less powerful; their methods get no ProceedingJoinPoint and cannot decide when to delegate.

  • @Before: runs before the method.
  • @AfterReturning: after a successful return; can receive the returned value. Not called if the method throws.
  • @AfterThrowing: if the method throws; can receive the exception.
  • @After: after the method, success or exception.
@Aspect
public class LoggingAspect {
    @AfterReturning(value = "@annotation(ToLog)", returning = "returnedValue")
    public void log(Object returnedValue) {            // parameter name must equal `returning`
      logger.info("Method executed and returned " + returnedValue);
    }
}

6.3 The aspect execution chain

A method can be intercepted by several aspects (e.g. SecurityAspect and LoggingAspect). Order matters: if Security runs first and sometimes does not delegate, Logging never sees those calls. If you want to log security failures, Logging must run first.

  • By default Spring does not guarantee the order. Put @Order(n) on the aspect class: smaller number runs earlier; equal numbers leave the order undefined.
  • Both aspects must be beans.

ssh_ch6_ex6 (no order): both aspects use @Around(value = "@annotation(ToLog)"), call proceed(), and log before/after.

@Bean public LoggingAspect loggingAspect() {
    return new LoggingAspect();
}
@Bean public SecurityAspect securityAspect() {
    return new SecurityAspect();
}

Logging Aspect: Calling the intercepted method
Security Aspect: Calling the intercepted method
Publishing comment:Demo comment
Security Aspect: Method executed and returned SUCCESS
Logging Aspect: Method executed and returned SUCCESS

The chain unwinds in reverse on the way back, like nested calls.

ssh_ch6_ex7 (with @Order):

@Aspect @Order(1) public class SecurityAspect { ... }
@Aspect @Order(2) public class LoggingAspect  { ... }

Security Aspect: Calling the intercepted method
Logging Aspect: Calling the intercepted method
Publishing comment:Demo comment
Logging Aspect: Method executed and returned SUCCESS
Security Aspect: Method executed and returned SUCCESS

Closing remark: this completes the core techniques (create and manage objects, wire them, scope them, separate cross-cutting concerns). Part 2 moves to real applications with Spring Boot.

Chapter summary (book)

  • An aspect intercepts a method and runs logic before, after or instead of it, decoupling that logic from the business code.
  • It can be dangerous: over-engineering with aspects makes the app less maintainable.
  • Aspects underpin transactions and method security.
  • Define one with @Aspect and also add a bean of its type.
  • Pointcut expressions go in the advice annotations: @Around, @Before, @After, @AfterThrowing, @AfterReturning; @Around is the most common and powerful.
  • Several aspects on one method form a chain; set the order with @Order.
