Book digests/Spring Start Here

Ch 8: Implementing web apps with Spring Boot and Spring MVC

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 8. Previous: Ch 7: Understanding Spring Boot and Spring MVC. Book projects: ssh_ch8_ex1 to ssh_ch8_ex6.

Takeaways
  • Real pages are dynamic: same page, different data per request (a shop cart).
  • The controller puts data in a Model; a template engine (Thymeleaf) renders it in the view.
  • Clients send data with request parameters (optional, small) or path variables (mandatory, one or two).
  • A request is identified by path + HTTP method: GET reads, POST adds, PUT/PATCH change, DELETE removes.
  • Use @GetMapping / @PostMapping.

8.1 Dynamic views

Example from the book: manning.com/cart shows different products for different users, and a different list after you add one. Same page, different response data.

Spring MVC flow with a dynamic view (only step 4 changes from chapter 7):

  1. Client sends the HTTP request.
  2. Dispatcher servlet uses handler mapping to find the action.
  3. It calls the controller action.
  4. The action returns the view name and sends data to the view.
  5. The response goes back to the client.

Thymeleaf (ssh_ch8_ex1)

A template engine is a library that makes it easy to take the data a controller sends and display it. Thymeleaf is the book's choice: simpler than others, and templates are just HTML files. Alternatives: Mustache, FreeMarker, JSP.

<dependency>
   <groupId>org.springframework.boot</groupId>
   <artifactId>spring-boot-starter-thymeleaf</artifactId>
</dependency>
<dependency>
   <groupId>org.springframework.boot</groupId>
   <artifactId>spring-boot-starter-webmvc</artifactId>
</dependency>

Controller: a Model parameter holds named values (key, value) added with addAttribute().

@Controller
public class MainController {
    @RequestMapping("/home")
    public String home(Model page) {
      page.addAttribute("username", "Katy");
      page.addAttribute("color", "red");
      return "home.html";
    }
}

View: put it in resources/templates, not resources/static (that was for static pages). The xmlns:th attribute works like a Java import and enables the th: prefix; ${key} reads a Model attribute.

<!DOCTYPE html>
<html lang="en" xmlns:th="http://www.thymeleaf.org">
  <head>
    <meta charset="UTF-8">
    <title>Home Page</title>
  </head>
  <body>
    <h1>Welcome
    <span th:style="'color:' + ${color}"
          th:text="${username}"></span>!</h1>
  </body>
</html>

Result: "Welcome Katy!" with the name in red.

FAQ from the book: typing localhost:8080 alone gives HTTP 404 because path / has no action. Map one with @RequestMapping if you want something there.

8.1.1 Getting data from the client

Use cases: an order (products), a forum post, login credentials, a contact form. Four ways in an HTTP request:

  • Request parameter (query parameter): key-value pairs appended to the URI. Small data.
  • Request header: like parameters but sent in the HTTP header, not the URI; also small data.
  • Path variable: value placed in the path; small data; use for mandatory values.
  • Request body: larger data (a string, even binary like a file). Covered in chapter 10 (REST).

8.1.2 Query string parameters (ssh_ch8_ex2, ex3)

Use when the data is small (the book says the query limit is about 2,000 characters) or optional. Classic example: search and filter (a product table filtered by name, price, brand in any combination; the client sends only the criteria chosen).

@Controller
public class MainController {
    @RequestMapping("/home")
    public String home(@RequestParam String color, Model page) {
      page.addAttribute("username", "Katy");
      page.addAttribute("color", color);
      return "home.html";
    }
}

@RequestParam reads the HTTP parameter with the same name as the method parameter. Syntax: ? after the path, pairs key=value, separated by &:

http://localhost:8080/home?color=blue
http://localhost:8080/home?color=blue&name=Jane

Two optional parameters (ssh_ch8_ex3):

@RequestMapping("/home")
public String home(
    @RequestParam(required = false) String name,
    @RequestParam(required = false) String color,
    Model page) {
  page.addAttribute("username", name);
  page.addAttribute("color", color);
  return "home.html";
}

A request parameter is mandatory by default. If missing, the server answers HTTP 400 Bad Request. Make it optional with required = false. (The book's note says "optional attribute" but the code uses required.)

8.1.3 Path variables (ssh_ch8_ex4)

?color=blue   (request parameter)
/home/blue    (path variable: position, no key)

@RequestMapping("/home/{color}")
public String home(@PathVariable String color, Model page) {
  page.addAttribute("username", "Katy");
  page.addAttribute("color", color);
  return "home.html";
}

Try /home/blue, /home/red, /home/green.

Request parameters Path variables
Optional values fine do not use
How many avoid more than 3; beyond that use the request body never more than 3, ideally 2
Readability some find the query expression harder easier to read
Other easier to bookmark and for search engines to index public pages

Author's rule: path variables only for mandatory values (one or two that are the core of the result); request parameters for optional ones or when there are more than two values.

8.2 GET and POST

  • An HTTP request is identified by path and method (verb). So far we used GET by default, which only retrieves data without changing it.
  • Never use an HTTP method against its purpose (e.g. a GET that changes data): possible technically, "a bad, bad choice".
  • Same path with different methods can map to different actions.
Method Client's intention
GET retrieve data
POST add new data
PUT change a record
PATCH partially change a record
DELETE delete data

The PUT / PATCH distinction (replace everything vs part) is good practice but not always made in production apps.

Scenario: products list (ssh_ch8_ex5)

Show all products and add one through an HTML form. View = GET, add = POST. Dependencies: Thymeleaf and web starter (this listing uses spring-boot-starter-web; earlier chapters used spring-boot-starter-webmvc; the project is typed sq-ch8-ex5 in the book).

public class Product {
    private String name;
    private double price;
    // getters, setters
}

// ProductService.java
@Service
public class ProductService {
    private List<Product> products = new ArrayList<>();
    public void addProduct(Product p) {
        products.add(p);
    }
    public List<Product> findAll() {
        return products;
    }
}

The book's own warning: this is a simplification. A singleton bean (chapter 5) with a mutable list, in a multi-threaded web app, causes race conditions when clients add products at once. Later chapters swap the list for a database. "Singleton beans aren't thread-safe!"

Controller, first with @RequestMapping:

@Controller
public class ProductsController {
     private final ProductService productService;
     public ProductsController(ProductService productService) {
         this.productService = productService;
     }

     @RequestMapping("/products")
     public String viewProducts(Model model) {
       var products = productService.findAll();
       model.addAttribute("products", products);
       return "products.html";
     }

     @RequestMapping(path = "/products", method = RequestMethod.POST)
     public String addProduct(@RequestParam String name, @RequestParam double price, Model model) {
       Product p = new Product();
       p.setName(name);
       p.setPrice(price);
       productService.addProduct(p);
       var products = productService.findAll();
       model.addAttribute("products", products);
       return "products.html";
     }
}
  • @RequestMapping without method matches all methods, so developers prefer dedicated annotations:
@GetMapping("/products")    // GET
public String viewProducts(Model model) { ... }

@PostMapping("/products")   // POST
public String addProduct(@RequestParam String name, @RequestParam double price, Model model) { ... }

View products.html (in resources/templates): table with th:each, then a form:

<h1>Products</h1>
<h2>View products</h2>
<table>
    <tr>
         <th>PRODUCT NAME</th>
         <th>PRODUCT PRICE</th>
    </tr>
    <tr th:each="p: ${products}" >
         <td th:text="${p.name}"></td>
         <td th:text="${p.price}"></td>
    </tr>
</table>

<h2>Add a product</h2>
<form action="/products" method="post">
   Name: <input type="text" name="name"><br />
   Price: <input type="number" step="any" name="price"><br />
   <button type="submit">Add product</button>
</form>

The form posts name and price as request parameters. Open http://localhost:8080/products.

Shortcut (ssh_ch8_ex6): use the model class itself as the parameter. Spring matches request parameter names to attribute names and builds it; the class needs a default constructor.

@PostMapping("/products")
public String addProduct(Product p, Model model) {
    productService.addProduct(p);
    var products = productService.findAll();
    model.addAttribute("products", products);
    return "products.html";
}

The author's tip: Spring hides a lot of code. When you meet syntax you do not understand, look up the framework specification instead of guessing.

Browser HTML forms directly support only GET and POST (the summary notes other methods like DELETE or PUT need another approach).

Chapter summary (book)

  • Dynamic views display different content per request; the controller sends the variable data.
  • Template engines (Thymeleaf; alternatives Mustache, FreeMarker, JSP) make this easy.
  • Clients send data via request parameters or path variables, read with @RequestParam / @PathVariable. Request parameters can be optional; path variables only for mandatory data.
  • Path plus HTTP method identify a request: GET retrieve, POST add, PUT replace, PATCH partial change, DELETE remove.
