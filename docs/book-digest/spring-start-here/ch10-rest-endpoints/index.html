Ch 10: Implementing REST endpoints

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 10. Previous: Ch 9: Using the Spring web scopes. Book projects: ssh_ch10_ex1 to ssh_ch10_ex7, ssh_ch10_openapi. Appendices C (HTTP) and D (JSON) support this chapter.

Takeaways

  • A REST endpoint is a controller action mapped to an HTTP method and path, but it returns data instead of a view name.

  • Use @RestController (= @Controller + @ResponseBody).

  • Returned objects become JSON by default.

  • Control status and headers with ResponseEntity.

  • Handle exceptions centrally with @RestControllerAdvice + @ExceptionHandler.

  • Read large client data with @RequestBody.

  • The author's warning: today AI tools generate many REST services, but you must check them; wrong request/response shapes cause functional bugs and security vulnerabilities.

10.1 Why REST

REST (representational state transfer) services are among the most common ways two apps communicate: web client to backend, mobile app to backend, even backend to backend. You expose functionality as endpoints; since it is a service reached over a web protocol, it is a web service.

Same Spring MVC mechanism as chapter 7, with one change: the dispatcher servlet is told not to look for a view, so the view resolver disappears and the returned data goes straight into the HTTP response.

Problems REST calls can bring (always ask what happens if a call fails, whether data could become inconsistent, and how to show an error):

  • An endpoint that takes long may time out and break communication.
  • Sending a lot of data in one call can time out; more than a few megabytes is usually the wrong choice.
  • Too many concurrent calls can overload the backend.
  • The network is never 100% reliable; any call may fail.

For API design best practices the author recommends API Design Patterns by J. J. Geewax (Manning, 2021).

10.2 First endpoints

Dependency is the same web starter:

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-webmvc</artifactId>
</dependency>

ssh_ch10_ex1: @ResponseBody says the method's return value is the response body, not a view name.

@Controller
public class HelloController {
    @GetMapping("/hello")
    @ResponseBody
    public String hello() {
        return "Hello!";
    }
}

Repeating it per method is duplication (/ciao too), so use @RestController (ssh_ch10_ex2):

@RestController
public class HelloController {
    @GetMapping("/hello") public String hello() {
        return "Hello!";
    }
    @GetMapping("/ciao")  public String ciao() {
        return "Ciao!";
    }
}

If you use neither @ResponseBody nor @RestController, the dispatcher servlet assumes the returned string is a view name and looks for that view.

Testing endpoints: two tools every developer should know

  • Postman (GUI): https://www.postman.com/. Choose the method, enter the URI, press Send; shows status, time, size, body, headers. Add parameters, headers or body as needed.
  • cURL (command line; useful over SSH on a VM or in batch scripts): https://curl.se/
curl http://localhost:8080/hello          # GET is the default, prints: Hello!
curl -X GET http://localhost:8080/hello   # -X names the method explicitly
curl -v http://localhost:8080/hello       # -v shows request, response status, headers, body

Verbose output shows > GET /hello HTTP/1.1, < HTTP/1.1 200, Content-Type: text/plain;charset=UTF-8, Content-Length: 6, then body Hello!.

10.3 Managing the HTTP response

The response carries headers (short values), a body (larger data) and a status (short result code).

Part of ResponseEntity Holds
Status (.status()) 200 OK, 202 Accepted, 400 Bad Request, 404, 500
Headers (.header()) short values, e.g. continent: Europe
Body (.body()) the data, as JSON by default, e.g. { "name": "France" }

Spring's defaults: 200 if no exception, 404 for a missing resource, 400 for a request it could not understand, 500 for a server exception.

10.3.1 Objects as the body (ssh_ch10_ex3)

Return an object and Spring turns it into a string, JSON by default (JSON basics in Appendix D). An object that models data exchanged between two apps is a DTO (data transfer object).

public class Country {
    private String name;
    private int population;     // millions

    public static Country of(String name, int population) {
        Country country = new Country();
        country.setName(name);
        country.setPopulation(population);
        return country;
    }
    // getters, setters
}

Author's note: since Java 16 you can use records (concise immutable data carriers). He strongly advocates immutability at application boundaries and recommends records for HTTP request and response bodies unless something prevents it.

@RestController
public class CountryController {
    @GetMapping("/france")
    public Country france() {
        return Country.of("France", 67);
    }

    @GetMapping("/all")
    public List<Country> countries() {
      return List.of(Country.of("France", 67), Country.of("Spain", 47));
    }
}

{
  "name": "France",
  "population": 67
}

[
  { "name": "France", "population": 67 },
  {
    "name": "Spain",
    "population": 47
  }
]

Lists use brackets; objects use curly braces separated by commas. JSON is the near-universal choice; XML or YAML are possible by plugging in a custom converter, but the author skips that as rarely needed.

10.3.2 Status and headers with ResponseEntity (ssh_ch10_ex4)

Spring defaults:

  • 200 OK: no exception on the server.
  • 404 Not Found: resource does not exist.
  • 400 Bad Request: part of the request could not be matched to what the server expected.
  • 500 Server Error: an exception on the server; usually the client can do nothing, someone must fix the backend.

For a custom status or headers return a ResponseEntity:

@GetMapping("/france")
public ResponseEntity<Country> france() {
  Country c = Country.of("France", 67);
  return ResponseEntity
          .status(HttpStatus.ACCEPTED)                  // 202 Accepted
          .header("continent", "Europe")
          .header("capital", "Paris")
          .header("favorite_food", "cheese and wine")
          .body(c);
}

In Postman: status shows 202 Accepted, the JSON body is intact, and the three headers are in the Headers tab.

10.3.3 Exceptions at the endpoint level

Exceptions often signal business situations: a payment endpoint throws when the account has too little money, and the client should learn the specific reason.

Approach 1: catch in the controller (ssh_ch10_ex5).

// NotEnoughMoneyException.java
public class NotEnoughMoneyException extends RuntimeException { }

// PaymentService.java
@Service
public class PaymentService {
    public PaymentDetails processPayment() {   // test stub
        throw new NotEnoughMoneyException();
    }
}

// PaymentDetails.java
public class PaymentDetails {
    private double amount;
    /* getters, setters */
}

// ErrorDetails.java
public class ErrorDetails {
    private String message;
    /* getters, setters */
}

// PaymentController.java
@RestController
public class PaymentController {
    private final PaymentService paymentService;
    public PaymentController(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    @PostMapping("/payment")
    public ResponseEntity<?> makePayment() {
      try {
        PaymentDetails paymentDetails = paymentService.processPayment();
        return ResponseEntity.status(HttpStatus.ACCEPTED).body(paymentDetails);
      } catch (NotEnoughMoneyException e) {
        ErrorDetails errorDetails = new ErrorDetails();
        errorDetails.setMessage("Not enough money to make the payment.");
        return ResponseEntity.badRequest().body(errorDetails);
      }
    }
}

POST to /payment returns 400 Bad Request with the error message in the body. It works but couples exception logic to one action and duplicates when many endpoints need it.

Approach 2 (the author's preference): a REST controller advice (ssh_ch10_ex6). It is an aspect that intercepts exceptions thrown by controller actions (compare chapter 6). The controller only handles the happy path:

@PostMapping("/payment")
public ResponseEntity<PaymentDetails> makePayment() {
    PaymentDetails paymentDetails = paymentService.processPayment();
    return ResponseEntity.status(HttpStatus.ACCEPTED).body(paymentDetails);
}

// ExceptionControllerAdvice.java
@RestControllerAdvice
public class ExceptionControllerAdvice {
    @ExceptionHandler(NotEnoughMoneyException.class)
    public ResponseEntity<ErrorDetails> exceptionNotEnoughMoneyHandler() {
      ErrorDetails errorDetails = new ErrorDetails();
      errorDetails.setMessage("Not enough money to make the payment.");
      return ResponseEntity.badRequest().body(errorDetails);
    }
}

  • The advice method is an exception handler; @ExceptionHandler says which exception triggers it.
  • Need details of the exception? Add a parameter of the handled exception type to the handler method; Spring passes the instance in.

Sidebar: contract-first with OpenAPI (ssh_ch10_openapi)

Many projects describe the API first in a specification language (method, path, variables, request and response bodies), then generate part of the implementation.

  • Benefits: consistency across the project; the contract is easier to share between teams and technologies than Java code; documentation is generated automatically.
  • Out of scope for the book. For more: Designing APIs with Swagger and OpenAPI by Joshua S. Ponelat and Lukas L. Rosenstock (Manning, 2022).

Dependency and generator plugin (partial, from the book):

<dependency>
   <groupId>org.springdoc</groupId>
   <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
   <version>2.8.5</version>
</dependency>

<plugin>
  <groupId>org.openapitools</groupId>
  <artifactId>openapi-generator-maven-plugin</artifactId>
  <version>7.11.0</version>
  <executions>
     <execution>
         <goals><goal>generate</goal></goals>
         <configuration>
           <inputSpec>${project.basedir}/src/main/resources/openapi.yml</inputSpec>
         </configuration>
     </execution>
  </executions>
</plugin>

Contract (openapi.yml):

openapi: 3.0.3
info:
  title: Payment API
  description: API for processing payments
  version: 1.0.0
paths:
  /payment:                        # endpoint path
    post:                          # HTTP method
       summary: Make a payment
       operationId: makePayment    # name of the generated Java method
       requestBody:
         description: Payment details
         required: true
         content:
           application/json:
             schema:
               $ref: '#/components/schemas/PaymentDetails'
       responses:
         '200':
           description: Payment processed successfully
           content:
             application/json:
               schema:
                 $ref: '#/components/schemas/PaymentDetails'
components:
  schemas:
    PaymentDetails:
       type: object
       properties:
         amount:
           type: number
           format: double
           example: 100.50

Building generates classes; you implement the generated interface:

@RestController
public class PaymentController implements PaymentApi {
    @Override
    public ResponseEntity<PaymentDetails> makePayment(PaymentDetails paymentDetails) {
        // business logic here
    }
}

AI-assisted tip (author): generate the API contract separately from the implementation. Have an AI tool draft the OpenAPI file, review the YAML carefully, then build to generate Java, then implement the logic. One concern at a time, and design problems show up earlier.

10.4 Request body (ssh_ch10_ex7)

Use the request body for larger data. The author's rule of thumb: anything over 50 to 100 characters. Annotate the action parameter with @RequestBody. Spring assumes JSON and decodes it into the parameter type; if it cannot, the response is 400 Bad Request.

@RestController
public class PaymentController {
  private static Logger logger = Logger.getLogger(PaymentController.class.getName());

  @PostMapping("/payment")
  public ResponseEntity<PaymentDetails> makePayment(@RequestBody PaymentDetails paymentDetails) {
      logger.info("Received payment " + paymentDetails.getAmount());
      return ResponseEntity.status(HttpStatus.ACCEPTED).body(paymentDetails);
  }
}

Postman: pick POST, body type raw JSON, e.g. {"amount": 1000}. cURL:

curl -v -X POST http://127.0.0.1:8080/payment -d '{"amount": 1000}' -H "Content-Type: application/json"

Can an HTTP GET have a request body? Before 2014 the HTTP spec did not allow it, so no client or server did. The spec changed in 2014 and now allows it, which still confuses readers of old articles.

It is not recommended, and many tools block it on purpose: GET was designed to be cacheable, safe, and identified only by the URL. The book cites section 4.3.1 of RFC 7231: https://tools.ietf.org/html/rfc7231#page-24.

Chapter summary (book)

  • REST services are a simple way for two apps to communicate.
  • Spring MVC supports REST endpoints: use @ResponseBody on the method or @RestController on the class. Otherwise the dispatcher servlet looks for a view.
  • A method can return the body and rely on default statuses; use ResponseEntity to control status and headers.
  • Exceptions can be handled in the action (couples logic to that action, risks duplication) or in a REST controller advice class.
  • An endpoint gets data from the client through request parameters, path variables, or the HTTP request body (@RequestBody).
