Ch 13: Using transactions in Spring apps

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 13. Previous: Ch 12: Using data sources in Spring apps. Book projects: ssh_ch13_ex1, ssh_ch13_ex2. Builds on aspects from Ch 6: Using aspects with Spring AOP.

Takeaways
  • A transaction groups data-changing operations so they all succeed or none apply (atomicity).
  • Success ends in a commit (changes persisted); a failure ends in a rollback (data restored to the start).
  • In Spring you just put @Transactional on a method; behind it is an aspect that starts the transaction and rolls back on a runtime exception.
  • Two traps: the exception must be thrown out of the method, and checked exceptions do not roll back by default.

13.1 Why transactions

Example: an e-wallet. A transfer has two steps: (1) withdraw from the source account, (2) deposit into the destination. John sends $100 to Jane (John 1000, Jane 500). If step 2 fails after step 1, John has 900 and Jane still 500: $100 vanished. If step 2 is retried wrongly and applied twice, money appears from nowhere. Both are data inconsistencies, serious in real systems.

  • Commit: the successful end of a transaction: the changes of all its mutable operations are stored.
  • Rollback: the transaction ends by restoring the data to how it looked at the start.
  • Start a transaction before step 1 and close it after step 2. If both succeed: commit. If step 2 fails: rollback undoes step 1.

Transactions treat related data changes as one unit of work, an essential pillar of every application framework.

13.2 How Spring does it

A Spring AOP aspect lies behind transactions. You mark a method with @Transactional; Spring configures the aspect (you do not write it) and applies transaction logic around the method.

  • Spring rolls back when the method throws a runtime exception
    • Emphasis on throws: students often think any runtime exception inside the method is enough
    • If the method catches it and does not rethrow, the aspect never sees it and commits
    • When you handle an exception in a transactional method, know that the transaction will not roll back.
  • Checked exceptions
    • (those you must handle or declare with throws): no rollback by default
    • They are controlled scenarios the developer is expected to manage, not data-corrupting surprises
    • If you want rollback for them, @Transactional has attributes to name the exceptions
    • The author's advice: keep it simple and use the default unless needed.

public class Account {
    private long id;
    private String name;
    private BigDecimal amount;
    // getters, setters

Repository with JdbcTemplate: find an account, change its amount, list all.

@Repository
public class AccountRepository {
    private final JdbcTemplate jdbc;
    public AccountRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public Account findAccountById(long id) {
      String sql = "SELECT * FROM account WHERE id = ?";
      return jdbc.queryForObject(sql, new AccountRowMapper(), id);
    }
    public void changeAmount(long id, BigDecimal amount) {
      String sql = "UPDATE account SET amount = ? WHERE id = ?";
      jdbc.update(sql, amount, id);
    }
    public List<Account> findAllAccounts() {
      String sql = "SELECT * FROM account";
      return jdbc.query(sql, new AccountRowMapper());
    }
}

// AccountRowMapper.java
public class AccountRowMapper implements RowMapper<Account> {
    @Override
    public Account mapRow(ResultSet resultSet, int i) throws SQLException {
      Account a = new Account();
      a.setId(resultSet.getInt("id"));
      a.setName(resultSet.getString("name"));
      a.setAmount(resultSet.getBigDecimal("amount"));
      return a;
    }
}

Service: the two changeAmount calls are the mutable operations; without a transaction a failure between them corrupts the data. One annotation fixes it:

@Service
public class TransferService {
    private final AccountRepository accountRepository;
    public TransferService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Transactional
    public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {
      Account sender = accountRepository.findAccountById(idSender);
      Account receiver = accountRepository.findAccountById(idReceiver);

      BigDecimal senderNewAmount = sender.getAmount().subtract(amount);
      BigDecimal receiverNewAmount = receiver.getAmount().add(amount);

      accountRepository.changeAmount(idSender, senderNewAmount);
      accountRepository.changeAmount(idReceiver, receiverNewAmount);
    }

    public List<Account> getAllAccounts() {
        return accountRepository.findAllAccounts();
    }
}

@Transactional on the class: applies to all methods and is common in real apps (a service's methods are use cases, which generally should all be transactional). If both class and method carry it, the method's configuration overrides the class's.

@Service
@Transactional
public class TransferService { ... }

Controller and DTO (TransferRequest models the request body; objects that model data moved between two apps are DTOs):

// AccountController.java
@RestController
public class AccountController {
    private final TransferService transferService;
    public AccountController(TransferService transferService) {
        this.transferService = transferService;
    }

    @PostMapping("/transfer")
    public void transferMoney(@RequestBody TransferRequest request) {
      transferService.transferMoney(request.getSenderAccountId(), request.getReceiverAccountId(), request.getAmount());
    }

    @GetMapping("/accounts")
    public List<Account> getAllAccounts() {
        return transferService.getAllAccounts();
    }
}

// TransferRequest.java
public class TransferRequest {
    private long senderAccountId;
    private long receiverAccountId;
    private BigDecimal amount;
    // getters, setters
}

Prove the rollback (ssh_ch13_ex2)

The author's rule: never trust something works until you test it; untested, a feature is in a "Schrödinger state": it both works and does not. So the copy project adds one line at the end of the service method:

@Transactional
public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {
    ...
    accountRepository.changeAmount(idSender, senderNewAmount);
    accountRepository.changeAmount(idReceiver, receiverNewAmount);
    throw new RuntimeException("Oh no! Something went wrong!");
}

The transfer call now returns HTTP 500 and the stack trace shows java.lang.RuntimeException: Oh no! Something went wrong!. But GET /accounts still shows 1000 and 1000: both updates ran, then the aspect saw the runtime exception and rolled back.

Out of scope but important to study next (the book's note): transaction isolation levels, optimistic vs pessimistic locking, distributed transactions. For continuing on persistence: Java Persistence with Spring Data and Hibernate by Cătălin Tudose (Manning, 2023).

Chapter summary (book)

  • A transaction is a set of data-changing operations that run together or not at all. Almost any real use case should be transactional.
  • If any operation fails the app restores the data (rollback); if all succeed, the transaction commits.
  • In Spring use @Transactional on a method (or class).
  • A Spring aspect intercepts annotated methods: it starts the transaction, rolls back on an exception, and commits (persists the method's changes) if none is thrown.
