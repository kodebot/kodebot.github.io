Ch 14: Implementing data persistence with Spring Data

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 14. Previous: Ch 13: Using transactions in Spring apps. Book project: ssh_ch14_ex1. Last chapter of part 2.

Takeaways
  • Spring Data lets you write repository interfaces and have Spring supply the implementation at runtime.
  • It is an umbrella project with one module (and one Maven dependency) per persistence technology: JDBC, JPA/Hibernate, MongoDB, Redis...
  • You extend a contract (CrudRepository for basic CRUD), add custom operations with @Query (preferred) or by method name, and inject the repository like any bean.

14.1 What Spring Data is

  • The persistence layer is the part of the app that talks to the database.
  • Persistence technologies include JDBC (so far in the book), ORM frameworks such as Hibernate, and NoSQL technologies such as MongoDB
    • Each has its own abstractions and class design; even one technology has several ways in (JDBC: JdbcTemplate, or the JDK's Statement, PreparedStatement, ResultSet)
    • Variety means complexity.
  • Spring Data
    • gives a common set of abstractions over all of them, and provides the implementations
    • You write less code, so the app is quicker to build and easier to understand and maintain.
  • Knowing JDBC from earlier chapters is enough to start.

14.2 How it works

  • "Spring Data" is shorthand for the project's modules. There is no single Spring Data dependency
    • each module is separate: Spring Data JDBC (JDBC straight to the DBMS), Spring Data Mongo, and so on. Full list: https://spring.io/projects/spring-data.
  • Interview tip (book):
    • do not call one module simply "Spring Data" (many call Spring Data JPA that, because it is the only one they used)
    • It can look like you do not know it is an umbrella
    • Name the module: Spring Data JPA, MongoDB, Redis.

Contracts you extend:

  • Repository: the most abstract; a marker interface with no methods. Extending it just makes Spring Data recognise your interface.
  • CrudRepository: the simplest contract with operations: create, retrieve, update, delete.
  • PagingAndSortingRepository: extends CrudRepository, adds sorting and retrieving records in pages.
  • Technology-specific ones: JpaRepository (Spring Data JPA; adds operations specific to JPA implementations such as Hibernate, "more particular" than PagingAndSortingRepository) and MongoRepository (Spring Data Mongo).

Don't confuse the @Repository annotation (stereotype that makes a class a bean) with the Spring Data Repository interface.

Why several nested interfaces and not one fat one? Interface segregation: take only what you need. If you only need CRUD, extend CrudRepository and do not get paging and sorting operations, so the app stays simpler. Spring adds a bean implementing your interface to the context; inject it anywhere.

Model: mark the primary key with @Id (Spring Data needs to know it for operations like finding by id). Use BigDecimal for money.

public class Account {
    @Id
    private long id;
    private String name;
    private BigDecimal amount;
    // getters, setters
}

Repository: an interface with two generic types: the model class (entity) and the primary key type.

public interface AccountRepository extends CrudRepository<Account, Long> {
}

You inherit getting by primary key, getting all records, deleting, and so on.

Custom operations

Spring Data can derive the query from the method name:

public interface AccountRepository extends CrudRepository<Account, Long> {
    List<Account> findAccountsByName(String name);
}
  • find means SELECT; the word after it says what; By starts the condition (WHERE). findByName would work too, since the repository is for Account.

Why the author prefers @Query over name derivation:

  • Complex queries make names too long to read.
  • A careless rename silently changes behaviour (not every app is well tested).
  • You must learn Spring Data's naming rules; you already know SQL, so that rule set has little value.
  • Slower startup: names are translated to queries at boot.
  • (Chapter summary: an invalid derived name makes the app fail at startup.)
public interface AccountRepository extends CrudRepository<Account, Long> {
    @Query("SELECT * FROM account WHERE name = :name")
    List<Account> findAccountsByName(String name);
}
  • :name matches the method parameter name. Common mistake: a space between : and the name makes the query impossible to parse; keep them together.
  • With @Query, the method name no longer matters.

Queries that change data (UPDATE, INSERT, DELETE) also need @Modifying:

public interface AccountRepository extends CrudRepository<Account, Long> {
    @Query("SELECT * FROM account WHERE name = :name")
    List<Account> findAccountsByName(String name);

    @Modifying
    @Query("UPDATE account SET amount = :amount WHERE id = :id")
    void changeAmount(long id, BigDecimal amount);
}

Service, controller

Constructor injection gives you a bean implementing the interface even though you only wrote the interface. @Transactional still wraps the use case (Ch 13: Using transactions in Spring apps). findById() comes from CrudRepository and returns an Optional:

// TransferService.java
@Service
public class TransferService {
    private final AccountRepository accountRepository;
    public TransferService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Transactional
    public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {
      Account sender = accountRepository.findById(idSender)
            .orElseThrow(() -> new AccountNotFoundException());
      Account receiver = accountRepository.findById(idReceiver)
            .orElseThrow(() -> new AccountNotFoundException());

      BigDecimal senderNewAmount = sender.getAmount().subtract(amount);
      BigDecimal receiverNewAmount = receiver.getAmount().add(amount);

      accountRepository.changeAmount(idSender, senderNewAmount);
      accountRepository.changeAmount(idReceiver, receiverNewAmount);
    }

    public Iterable<Account> getAllAccounts() {   // inherited
        return accountRepository.findAll();
    }
    public List<Account> findAccountsByName(String name) {
        return accountRepository.findAccountsByName(name);
    }
}

// AccountNotFoundException.java
public class AccountNotFoundException extends RuntimeException { }

// AccountController.java
@RestController
public class AccountController {
    private final TransferService transferService;
    public AccountController(TransferService transferService) {
        this.transferService = transferService;
    }

    @PostMapping("/transfer")
    public void transferMoney(@RequestBody TransferRequest request) {
      transferService.transferMoney(request.getSenderAccountId(), request.getReceiverAccountId(), request.getAmount());
    }

    @GetMapping("/accounts")
    public Iterable<Account> getAllAccounts(@RequestParam(required = false) String name) {
      if (name == null) {
          return transferService.getAllAccounts();
      } else {
          return transferService.findAccountsByName(name);
      }
    }
}

// TransferRequest.java
public class TransferRequest {
    private long senderAccountId;
    private long receiverAccountId;
    private BigDecimal amount;
    // getters, setters
}

Closing note: Spring Data does not make the persistence layer unimportant or exempt you from understanding data access; it gives a cleaner, faster way to build it.

Chapter summary (book)

  • Spring Data gives common abstractions over different persistence technologies.
  • Repositories are interfaces extending contracts: Repository (no operations), CrudRepository (CRUD), PagingAndSortingRepository (pagination and sorting).
  • Choose the Spring Data module for your technology (JDBC, MongoDB...).
  • Repositories inherit the contract's operations and can define custom ones.
  • @Query states the query explicitly; otherwise Spring Data derives it from the method name, which needs the naming rules and fails at startup on invalid names.
  • Operations that change data (INSERT, UPDATE, DELETE) must be annotated with @Modifying.
  • Prefer @Query for complex operations: derived names get long, hard to maintain, slow to process at startup, and break easily in refactoring.
