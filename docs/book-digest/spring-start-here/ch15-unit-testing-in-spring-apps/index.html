Ch 15: Unit testing in Spring apps

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 15. Previous: Ch 14: Implementing data persistence with Spring Data. Uses the money transfer service from ssh_ch14_ex1 (test classes TransferServiceUnitTests, TransferServiceWithAnnotationsUnitTests) and the login controller from ssh_ch9_ex1. First chapter of part 3 (testing).

Takeaways
  • A test is a small piece of code that checks a capability still works.
  • Unit tests check one isolated piece of logic; integration tests (next chapter) check components working together.
  • A unit test has three parts: assumptions (inputs and controlled dependencies), call, validations.
  • You replace dependencies with mocks (Mockito) so the test targets only the logic under test.
  • Test happy flows and exception flows.

Why test (15.1)

  • A test protects ongoing change: you can rerun it any time, it documents the use case (read the steps to see its purpose), and it gives early feedback.
  • Why would working code stop working?
    • Because you keep changing the source to fix bugs and add features
    • Re-running tests to confirm existing behaviour still works is regression testing.
  • Tests do not show their value in the short term, which is why many developers skip them; they are invaluable long term.
  • Real example (the book):
    • the troubled 2013 launch of Healthcare.gov
    • A government investigation found required end-to-end testing was not completed and components with known defects were released; many users could not use the site
    • Lesson: tests protect business value (report: https://www.gao.gov/assets/gao-15-238.pdf).
  • Testing is huge; for more the author recommends JUnit in Action by Cătălin Tudose (Manning, 2020).

Continuous integration (CI): teams run tests automatically as part of the build. A CI tool (Jenkins, GitLab Actions, GitHub Actions) builds, tests and sometimes installs the app on every change and notifies developers when something breaks.

  • Testability and maintainability help each other: design for testability and the app is more maintainable.
  • You test a method's logic across several scenarios (behaviours for different inputs): one test method per scenario, in a test class under the Maven test folder.
  • Even a small method has many scenarios, which is another reason to keep methods small: big methods with many parameters doing several things make relevant scenarios hard to find and reduce testability.

15.2 Unit tests in Spring apps

Unit tests are short, fast, focus on one flow, and eliminate all dependencies of the logic under test. When one fails you know exactly where the problem is.

Analogy: a dashboard indicator. A car that will not start could be out of fuel or a dead battery; the fuel light tells you which.

Subject under test (chapter 14's service)

@Transactional
public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {
    Account sender = accountRepository.findById(idSender)
      .orElseThrow(() -> new AccountNotFoundException());
    Account receiver = accountRepository.findById(idReceiver)
      .orElseThrow(() -> new AccountNotFoundException());

    BigDecimal senderNewAmount = sender.getAmount().subtract(amount);
    BigDecimal receiverNewAmount = receiver.getAmount().add(amount);

    accountRepository.changeAmount(idSender, senderNewAmount);
    accountRepository.changeAmount(idReceiver, receiverNewAmount);
}

Happy flow = an execution with no errors or exceptions, as expected. It is the first test you write.

The three parts of a test

  1. Assumptions (given, arrange): inputs and how mocks behave, e.g. given(repo.findById(1L)).willReturn(Optional.of(sender)).
  2. Call (when, act): run the method under test, e.g. transferService.transferMoney(1L, 2L, amount).
  3. Validations (then, assert): what must have happened, e.g. verify(repo).changeAmount(...), assertEquals, assertThrows.

Same idea under three names: assumptions / call / validations = arrange / act / assert = given / when / then. A unit test isolates ONE piece of logic, runs fast, and points straight at the broken code.

  1. Assumptions: choose inputs and control dependencies so the logic takes the flow you want. Dependencies are anything the method uses but does not create: its parameters, and objects it uses.
  2. Call/execution: run the tested logic.
  3. Validations: state what must happen under those conditions.

Naming: also "arrange, act, assert" or "given, when, then". Same idea.

Mocks

The method's flow depends on AccountRepository.findById(), but a unit test must not call the real one. A mock is a fake object whose behaviour you control. Replace the repository with a mock and you can force every flow.

Mockito (usually used with JUnit) provides mock(). Create objects before each test with @BeforeEach:

public class TransferServiceUnitTests {
    private AccountRepository accountRepository;
    private TransferService transferService;

    @BeforeEach
    void setUp() {
      accountRepository = mock(AccountRepository.class);
      transferService = new TransferService(accountRepository);
    }
}

Control the mock with given(...).willReturn(...). Call the method. Then verify() that the mock was called as expected. (In real apps, add @DisplayName to describe the scenario; the book drops it in later listings to save space.)

@Test
@DisplayName("""
   GIVEN a valid sender and receiver account
   WHEN transferMoney is called
   THEN the amounts are updated for both accounts
   """)
public void transferMoneyHappyFlow() {
   Account sender = new Account();
   sender.setId(1L);
   sender.setAmount(new BigDecimal("1000"));
   Account receiver = new Account();
   receiver.setId(2L);
   receiver.setAmount(new BigDecimal("1000"));

   given(accountRepository.findById(1L)).willReturn(Optional.of(sender));
   given(accountRepository.findById(2L)).willReturn(Optional.of(receiver));

   transferService.transferMoney(1L, 2L, new BigDecimal("100"));

   verify(accountRepository).changeAmount(1L, new BigDecimal("900"));
   verify(accountRepository).changeAmount(2L, new BigDecimal("1100"));
}

Run it from the IDE (right-click the test class, Run): green means pass, red or yellow means failure.

Annotation style (the author's preference, not necessarily more common):

@ExtendWith(MockitoExtension.class)          // enables @Mock and @InjectMocks
public class TransferServiceWithAnnotationsUnitTests {
    @Mock
    private AccountRepository accountRepository;       // framework creates the mock

    @InjectMocks
    private TransferService transferService;           // creates the tested object, injects the mocks

    @Test
    public void moneyTransferHappyFlow() {
      Account sender = new Account();
      sender.setId(1);
      sender.setAmount(new BigDecimal(1000));
      Account destination = new Account();
      destination.setId(2);
      destination.setAmount(new BigDecimal(1000));

      given(accountRepository.findById(sender.getId())).willReturn(Optional.of(sender));
      given(accountRepository.findById(destination.getId())).willReturn(Optional.of(destination));

      transferService.transferMoney(1, 2, new BigDecimal(100));

      verify(accountRepository).changeAmount(1, new BigDecimal(900));
      verify(accountRepository).changeAmount(2, new BigDecimal(1100));
    }
}

Exception flow

Test the case where something goes wrong. assertThrows() checks the expected exception; verify(..., never()) proves the method did not do something. Together they check both the reported outcome and the absence of an invalid state change (a method might throw the right exception but already have caused a side effect).

@Test
public void moneyTransferDestinationAccountNotFoundFlow() {
  Account sender = new Account();
  sender.setId(1);
  sender.setAmount(new BigDecimal(1000));

  given(accountRepository.findById(1L)).willReturn(Optional.of(sender));
  given(accountRepository.findById(2L)).willReturn(Optional.empty());     // destination not found

  assertThrows(AccountNotFoundException.class,
      () -> transferService.transferMoney(1, 2, new BigDecimal(100)));

  verify(accountRepository, never()).changeAmount(anyLong(), any());      // nothing was changed
}

Testing a returned value

The login controller action from chapter 9:

@PostMapping("/")
public String loginPost(@RequestParam String username, @RequestParam String password, Model model) {
  loginProcessor.setUsername(username);
  loginProcessor.setPassword(password);
  boolean loggedIn = loginProcessor.login();
  if (loggedIn) {
      model.addAttribute("message", "You are now logged in.");
  } else {
      model.addAttribute("message", "Login failed!");
  }
  return "login.html";
}

Same three steps. Mock the Model and LoginProcessor; make login() return true; check the returned string with assertEquals and the model attribute with verify:

@ExtendWith(MockitoExtension.class)
class LoginControllerUnitTests {
    @Mock private Model model;
    @Mock private LoginProcessor loginProcessor;
    @InjectMocks private LoginController loginController;

    @Test
    public void loginPostTestSuccess() {
      given(loginProcessor.login()).willReturn(true);

      String result = loginController.loginPost("username", "password", model);

      assertEquals("login.html", result);
      verify(model).addAttribute("message", "You are now logged in.");
    }

    @Test
    public void loginPostTestFailure() {
      given(loginProcessor.login()).willReturn(false);

      String result = loginController.loginPost("username", "password", model);

      assertEquals("login.html", result);
      verify(model).addAttribute("message", "Login failed!");
    }
}

Controlling inputs and mock behaviour lets you test other scenarios (here, failed login).

Where unit tests stop

They are fast, focused, easy to read and are the first safety net. But in Spring, logic depends on framework-provided pieces too: beans, configuration properties, repositories, transactions, security rules, HTTP clients. So also add Spring-based tests where behaviour depends on wiring: integration tests, next chapter.

Chapter summary (book)

  • A test validates logic; it ensures later changes do not break existing capabilities, and it documents.
  • Unit test: isolated logic, fast, points to the problem. Integration test: interaction between two or more components; components can work alone and fail together.
  • Mocks replace components you do not want to test, so the test focuses on specific interactions.
  • Three parts: assumptions (inputs and mock behaviour), call/execution (call the method under test), validations (verify the way the tested method behaved).
