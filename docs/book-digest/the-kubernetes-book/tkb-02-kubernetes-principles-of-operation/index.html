The Kubernetes Book 2: Kubernetes Principles of Operation

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 2. Previous: The Kubernetes Book 1: Kubernetes Primer. Next: The Kubernetes Book 3: Getting Kubernetes.

Takeaways
  • A cluster is control plane nodes (the brains: API server, scheduler, cluster store, controllers) plus worker nodes (run your apps: kubelet, runtime, kube-proxy).
  • Kubernetes works declaratively: you post desired state as YAML, controllers reconcile observed state to match it, continuously.
  • Apps are wrapped in Pods; Pods are wrapped in Deployments (self-healing, scaling, rollouts).
  • Pods are mortal and immutable: replaced, never patched, each time with a new ID and IP.
  • Services give groups of Pods a stable name, IP and port, and load balance to healthy Pods.

2.1 Kubernetes from 40K feet

Kubernetes is both a cluster and an orchestrator.

Cluster

  • One or more nodes providing CPU, memory and other resources for apps.
  • Two node types: control plane and worker.
  • Both can be physical servers, VMs or cloud instances, on ARM or AMD64/x86-64.
  • Control plane nodes must be Linux; workers can be Linux or Windows.
  • Every cluster needs at least one control plane node; use three or five for high availability (HA).
  • Every control plane node runs every control plane service: API server, scheduler, and the controllers behind self-healing, autoscaling and rollouts.
  • Figure 2.1: a cluster of three control plane nodes and three workers.
  • Dev and test often run user apps on control plane nodes; many production setups restrict apps to workers so the control plane can focus on cluster operations.

Orchestrator

A system that deploys and manages apps. Kubernetes:

  • spreads apps across nodes and failure zones for performance and availability
  • fixes things when they break
  • scales when demand changes
  • manages rollouts and rollbacks

2.2 Control plane and worker nodes

Mixed Linux and Windows workers

  • Almost all cloud-native apps are Linux apps and need Linux workers.
  • Cloud-native Windows apps need one or more Windows workers.
  • One cluster can mix both; Kubernetes schedules each app to the right node type.

The control plane

  • System services that expose the API, schedule apps, implement self-healing, manage scaling and more.
  • Simplest cluster: one control plane node, for labs and testing.
  • Production: three or five nodes, spread across availability zones (Figure 2.2).
  • Most clusters run every control plane service on every control plane node.

The API server

  • The front end of Kubernetes; every command and request goes through it, even internal control plane traffic.
  • Exposes a RESTful API over HTTPS; every request is authenticated and authorised.
  • Deploying or updating an app:
    1. Describe the app in a YAML configuration file.
    2. Post the file to the API server.
    3. The request is authenticated and authorised.
    4. The app definition is persisted in the cluster store.
    5. The app's containers are scheduled to nodes.

The cluster store

  • Holds the desired state of all apps and cluster components; the only stateful part of the control plane.
  • Based on the etcd distributed database; most clusters run an etcd replica on every control plane node.
  • Large, high-change clusters may run a separate etcd cluster for performance.
  • HA is not backup. You still need a way to recover the store.
  • etcd prefers an odd number of replicas to avoid split brain: replicas cannot communicate and cannot tell whether they hold a quorum (majority).
Cluster Nodes After a network partition
A 4 2 + 2: neither side has a majority (split brain)
B 3 Node A knows it lacks a majority; Nodes B and C know they have one (no split brain)
  • On split brain, etcd goes read-only: apps keep working, but Kubernetes cannot scale or update them.
  • Write consistency is vital: concurrent writes to the same item can corrupt it. etcd uses the Raft consensus algorithm to prevent this.

Controllers and the controller manager

  • Controllers implement much of the cluster intelligence. Each runs as a process on the control plane. Common ones:
    • Deployment controller
    • StatefulSet controller
    • ReplicaSet controller
  • All run as background watch loops, reconciling observed state with desired state.
  • Example: ask for three replicas and a controller ensures three healthy replicas exist, acting if not.
  • The controller manager spawns and manages the individual controllers.

The scheduler

Watches the API server for new work and assigns it to healthy workers:

  1. Watch the API server for new tasks.
  2. Identify capable nodes.
  3. Assign tasks to nodes.
  • Identifying capable nodes uses predicate checks, filtering and ranking.
    • Checks: taints, affinity and anti-affinity rules, network port availability, available CPU and memory.
    • Incapable nodes are ignored.
    • Rankings: already has the image, available CPU and memory, number of tasks running. Each earns points; the highest score wins.
  • No suitable node: the task is marked pending.
  • With node autoscaling configured, a pending task triggers a cluster autoscaling event that adds a node, and the scheduler assigns the task there.

The cloud controller manager

  • On a public cloud (AWS, Azure, GCP, Civo Cloud) the cluster runs a cloud controller manager integrating with cloud instances, load balancers and storage.
  • Example: an app asks for a load balancer, and it provisions a cloud load balancer and connects it to the app.

Control plane summary

  • Brains of Kubernetes: API server, scheduler, cluster store, controllers.
  • Three or five nodes for HA; a separate etcd cluster for large busy clusters.
  • All communication passes through the API server.

Worker nodes

Run business apps. Three main components:

Component Role
Kubelet Main agent; watches the API server for tasks, tells the runtime to execute them, reports status. If a task will not run, it reports to the API server and lets the control plane decide.
Runtime Executes tasks: pulls images, starts and stops containers. Most new clusters pre-install containerd.
Kube-proxy Implements cluster networking and load balances traffic to tasks on the node.
  • Docker as a runtime is no longer supported; Red Hat OpenShift uses CRI-O; many others exist, each with pros and cons.
  • Chapter 9 (Wasm) uses different runtimes.

2.3 Packaging apps for Kubernetes

Kubernetes runs containers, VMs, Wasm apps and more, but all must be wrapped in Pods.

Courier analogy

  • A courier ships books, clothes, food and electricals if you use its approved packaging and labels. It handles planes, trucks, hand-offs, tracking, delivery details and proof of delivery.
  • Likewise, wrap a workload in a Pod and Kubernetes handles node choice, networking, volumes, and lets you query and change the app.
  • Extras like insurance, refrigeration, signatures and express delivery map to controllers: health, autoscaling and more.

Example flow

  1. Write the app.
  2. Containerise it.
  3. Push it to a registry.
  4. Wrap it in a Pod.
  5. Usually wrap the Pod in a higher-level controller (for example a Deployment).

Two things to know:

  • Apps need wrapping in Pods to run.
  • Pods get wrapped in higher-level controllers for advanced features.

Object nesting

Layer What it adds
Container Wraps the app and provides dependencies
Pod Wraps the container so it runs on Kubernetes
Deployment Wraps the Pod; adds self-healing, scaling and more

You post the Deployment YAML to the API server as the app's desired state.

2.4 The declarative model and desired state

Three principles:

Term Meaning
Desired state What you want
Observed state What you have (also called actual or current state)
Reconciliation Keeping observed state in sync with desired state

How it works

  1. Describe desired state in a YAML manifest.
  2. Post it to the API server (most commonly with kubectl).
  3. Kubernetes records it in the cluster store as a record of intent.
  4. A controller notices observed state differs from the new desired state.
  5. The controller makes the changes needed to reconcile (schedule Pods, pull images, start containers, attach networks, start processes).
  6. It keeps running in the background to reconcile future differences.
  • Desired state covers images, replica counts, network ports and more.
  • Manifests are authenticated and authorised on the way in.

Declarative vs imperative

Model Description
Imperative Complex scripts of platform-specific commands to reach an end state
Declarative A simple, platform-agnostic description of the end state
  • Kubernetes supports both but prefers declarative: it works with version control and enables self-healing, autoscaling and rolling updates.

Examples

  • Node failure: you asked for 10 replicas; a node running two fails; observed state drops to 8; a controller schedules 2 new replicas.
  • App update: change the image version in the YAML and post it; the controller replaces old-version replicas with new-version ones.
  • Imperatively you would script, monitor and health-check the whole update; declaratively you change one line of YAML.

2.5 Pods

  • The atomic unit of scheduling in VMware is the VM; in Kubernetes it is the Pod.
  • All workload types need wrapping in Pods.

Pods and containers

  • Simplest case: one container per Pod, so people use "Pod" and "container" interchangeably.
  • Multi-container uses:
    • service meshes
    • helper services that initialise environments
    • apps with tightly coupled helpers such as log scrapers
  • A sidecar is a helper container in the same Pod as the main container.
    • In Figure 2.8 the service-mesh sidecar encrypts network traffic and provides telemetry.
    • This keeps the main app simple, following the single responsibility principle.

Pod anatomy

  • A Pod is a shared execution environment: network stack, volumes, shared memory and more.
  • Single-container Pod: the container has it to itself. Multi-container Pod: containers share it.
  • Figure 2.9: both containers share the Pod IP.
Container Address
Main app 10.0.10.15:8080
Sidecar 10.0.10.15:5005
  • Containers in the same Pod talk to each other over the Pod's localhost.
  • Choose multi-container Pods for tightly coupled components needing shared memory or storage; otherwise use single-container Pods loosely coupled over the network.

Pod scheduling

  • Containers in one Pod are always scheduled to one node: Kubernetes schedules Pods, and sharing memory, networking and volumes across nodes is hard.
  • Starting a Pod is atomic: it is ready only when all containers are running (two containers, one started: not ready).

Pods as the unit of scaling

  • Scale up by adding Pods, down by deleting Pods. Never scale by adding containers to existing Pods.

Pod lifecycle

  • Pods are mortal: created, live, die. A replacement is always new, with a new ID and new IP.
  • So design apps loosely coupled and immune to individual Pod failure.

Pod immutability

  • Pods are immutable: never change a running Pod; replace it with a new one.
  • Never log on to a Pod and change it. "Updating Pods" always means delete and replace.
  • A mindset shift that fits modern tooling and GitOps workflows.

2.6 Deployments

  • You almost always deploy Pods via higher-level controllers: Deployments, StatefulSets, DaemonSets.
  • All are control plane watch loops reconciling observed with desired state.
  • Deployments add self-healing, scaling, rolling updates and versioned rollbacks to stateless apps.

2.7 Service objects and stable networking

  • Failed Pods managed by a controller are replaced with new IDs and new IPs
    • The same happens in rollouts (old Pods replaced by new IPs), scale-up (new Pods with new IPs) and scale-down (Pods deleted).
  • This IP churn makes Pods unreliable to connect to directly.
  • A Service (capital S: a Kubernetes API resource) provides a reliable name and IP and load balances to Pods (Figure 2.11).
Side What it provides
Front end Stable DNS name, IP address and network port (never change)
Back end Uses labels to load balance across a dynamic set of Pods
  • Services keep a list of healthy Pods as scaling, rollouts and failures change membership, so traffic only reaches active healthy Pods.

Summary points

  • Control plane nodes host the intelligence: API server, scheduler, cluster store, controllers; production uses three or five.
  • Worker nodes run apps via kubelet (watches API server, reports status), a runtime (start and stop containers and Wasm apps) and kube-proxy (networking).
  • Declarative is preferred; controllers reconcile observed state to desired state.
  • Pods run workloads, Deployments add self-healing, scaling and rollouts, Services add reliable networking and basic load balancing.
Terms to carry forward
  • Control plane / worker node: brains vs app-running nodes.
  • API server: the HTTPS REST front end for everything.
  • Cluster store (etcd): stateful desired-state database; Raft; odd replicas.
  • Split brain: partition where no side is sure of quorum; etcd goes read-only.
  • Controller / controller manager: watch loops that reconcile state.
  • Scheduler: filters and ranks nodes, assigns tasks; pending if none fit.
  • Cloud controller manager: integrates cloud load balancers, instances, storage.
  • Kubelet / runtime / kube-proxy: worker agent, container executor, networking.
  • Desired / observed state, reconciliation, record of intent.
  • Pod, sidecar, Deployment, Service; IP churn.
