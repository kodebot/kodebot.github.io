The Kubernetes Book 5: Virtual Clusters with Namespaces

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 5. Previous: The Kubernetes Book 4: Working with Pods. Next: The Kubernetes Book 6: Kubernetes Deployments.

Takeaways
  • Namespaces divide one cluster into virtual clusters; they are not Linux kernel namespaces.
  • They give soft isolation and soft multi-tenancy: separate quotas, users, RBAC and policies, but a compromised workload can still affect other Namespaces.
  • Strong isolation between tenants needs separate clusters on their own hardware.
  • Most objects are namespaced; Nodes and PersistentVolumes are cluster-scoped. New objects land in default unless told otherwise.
  • Set the Namespace per command (-n), in the manifest (metadata.namespace), or in your kubeconfig context.

5.1 Intro to Namespaces

Namespace type Partitions Into
Linux kernel namespaces Operating systems Virtual operating systems called containers
Kubernetes Namespaces Kubernetes clusters Virtual clusters called Namespaces
  • The book capitalises "Namespace" for the Kubernetes API resource.
  • Namespaces provide soft isolation and soft multi-tenancy
    • Example: separate Namespaces for dev, test and qa, each with its own quotas and policies
    • But a compromised workload in one can easily impact others.
  • kubectl api-resources shows which objects are namespaced
    • Non-namespaced objects such as Nodes and PersistentVolumes are cluster-scoped and cannot be deployed to a Namespace.
kubectl api-resources

NAME                    SHORTNAMES   ...   NAMESPACED   KIND
nodes                   no                 false        Node
persistentvolumeclaims  pvc                true         PersistentVolumeClaim
persistentvolumes       pv                 false        PersistentVolume
pods                    po                 true         Pod
podtemplates                               true         PodTemplate
replicationcontrollers  rc                 true         ReplicationController
resourcequotas          quota              true         ResourceQuota
secrets                                    true         Secret
serviceaccounts         sa                 true         ServiceAccount
services                svc                true         Service
<Snip>
  • Unless you say otherwise, objects go to the default Namespace.

5.2 Namespace use cases

  • Namespaces let multiple tenants share a cluster. "Tenant" is loose: applications, teams, departments, even external customers.
  • Most common: tenants within one organisation. Example production split matching the org chart:
    • finance for Finance apps
    • hr for HR apps
    • corporate-ops for Corporate apps
  • Each Namespace can have its own users, permissions, resource quotas and policies.
  • External tenants are less common because soft isolation cannot stop a compromised workload escaping to other Namespaces
    • The most common strong-isolation approach at the time of writing: each tenant on its own cluster and hardware.
  • Figure 5.1: a single cluster with two Namespaces shares nodes and control plane (compromise spreads), versus two separate clusters on dedicated hardware.
Approach Pros Cons
Namespaces Lightweight, easy to manage Soft isolation only
Multiple clusters Strong isolation Higher cost, more management overhead

5.4 Creating and managing Namespaces

Clone the repo, switch to the 2025 branch and run commands from the namespaces directory:

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025
  • Namespaces are first-class resources in the core v1 API group: stable, long-standing, manageable imperatively and declaratively.

Imperative:

kubectl create ns hydra

namespace/hydra created

Declarative, shield-ns.yml:

kind: Namespace
apiVersion: v1
metadata:
  name: shield
  labels:
    env: marvel

$ kubectl apply -f shield-ns.yml
namespace/shield created

$ kubectl get ns
NAME     STATUS   AGE
<Snip>
hydra    Active   49s
shield   Active   3s

(The book jokes that Shield and Hydra, bitter enemies in the Marvel Cinematic Universe, should not share a cluster separated only by Namespaces.) Delete hydra:

kubectl delete ns hydra

namespace "hydra" deleted

Configure kubectl for a specific Namespace

Adding -n everywhere is painful; set it on your kubeconfig context instead:

kubectl config set-context --current --namespace shield

Context "tkb" modified.

All future kubectl get commands now target shield (empty at this point).

5.5 Deploying objects to Namespaces

  • Most objects are namespaced; new ones go to default unless told otherwise.
  • Two ways to target a Namespace:
    • Imperatively: add -n or --namespace to commands.
    • Declaratively: set metadata.namespace in the manifest.

app.yml in the namespaces folder defines a ServiceAccount, a Service and a Pod, all targeting shield:

apiVersion: v1
kind: ServiceAccount
metadata:
  namespace: shield     # Namespace
  name: default
---
apiVersion: v1
kind: Service
metadata:
  namespace: shield     # Namespace
  name: the-bus
spec:
  type: LoadBalancer
  ports:
  - port: 8080
    targetPort: 8080
  selector:
    env: marvel
---
apiVersion: v1
kind: Pod
metadata:
  namespace: shield     # Namespace
  name: triskelion
# <Snip>

kubectl apply -f app.yml

serviceaccount/default configured
service/the-bus configured
pod/triskelion created

(A warning about a missing ServiceAccount annotation is harmless.) Verify (no -n shield needed if your context is set):

$ kubectl get pods -n shield
NAME         READY   STATUS    RESTARTS   AGE
triskelion   1/1     Running   0          48s

$ kubectl get svc -n shield
NAME      TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)          AGE
the-bus   LoadBalancer   10.43.30.174   localhost     8080:31112/TCP   52s

Connect to the EXTERNAL-IP on port 8080. Some Docker Desktop clusters wrongly show a 172 address; use localhost:8080 instead.

curl localhost:8080

<!DOCTYPE html>
<html>
<head>
<title>AOS</title>
<Snip>

Connecting works exactly as for an app in the default Namespace.

Clean up

Deleting the Namespace deletes everything in it (Pod, Service and ServiceAccount), possibly taking a few seconds:

kubectl delete ns shield

namespace "shield" deleted

Reset the context, otherwise future commands target the deleted Namespace and return nothing:

kubectl config set-context --current --namespace default

Context "tkb" modified.

Summary points

  • Namespaces divide a cluster for resource and accounting purposes; each can have its own users, RBAC rules and quotas, with policies applied selectively.
  • They are not a strong isolation boundary, so they do not give hard multi-tenancy.
  • Without a Namespace at deploy time, objects go to default.
Terms to carry forward
  • Namespace: a virtual cluster inside a cluster (not a kernel namespace).
  • Soft isolation / multi-tenancy: separation by policy and quota, not a security boundary.
  • Cluster-scoped: not namespaced (Nodes, PersistentVolumes).
  • default, kube-system, kube-public, kube-node-lease: pre-created Namespaces.
  • Tenant: an app, team, department or customer sharing a cluster.
  • kubeconfig context Namespace: default Namespace for kubectl.
