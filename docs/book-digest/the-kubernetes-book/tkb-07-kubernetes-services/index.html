The Kubernetes Book 7: Kubernetes Services

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 7. Previous: The Kubernetes Book 6: Kubernetes Deployments. Next: The Kubernetes Book 8: Ingress.

Takeaways
  • Pods are ephemeral and unreliable, so never connect to them directly; connect through a Service.
  • A Service has a front end (DNS name, IP, port that never change) and a back end (a label selector sending traffic to healthy matching Pods).
  • An EndpointSlice, created automatically per Service, tracks the healthy matching Pods.
  • Three main types stack: ClusterIP (internal), NodePort (adds a port on every node), LoadBalancer (adds a cloud load balancer).
  • Create Services declaratively from YAML; kubectl expose is the imperative shortcut.

7.1 Service theory

Kubernetes deletes Pods on:

  • scale-downs
  • rolling updates
  • rollbacks
  • node maintenance or evictions
  • failures

So apps cannot rely on a Pod being there. A Service sits in front of one or more identical Pods and exposes them through a reliable DNS name, IP address and port. (Capital "S": it is a Kubernetes API resource.)

Figure 7.1: a client reaches a Service called app1 by name or IP, and the Service forwards to the Pods behind it.

Part What it is
Front end DNS name, IP and port that Kubernetes guarantees never change
Back end A label selector that sends traffic to healthy Pods with matching labels
  • In Figure 7.1 the client sends traffic to app1:8080 or 10.99.11.23:8080 and it reaches a Pod with the project=tkb label.
  • Services track the list of healthy Pods, so scaling, rollouts, rollbacks and even failures never leave the Service with a stale list.

Labels and loose coupling

  • Services use the same labels and selectors technology that tells Deployments which Pods they manage.
  • Figure 7.2: a Service selecting project=tkb and zone=prod. It sends to Pods A, B and D (all labels present; D's extra labels do not matter) but not to Pod C (missing one label).

A Deployment creating Pods with those labels, and a Service selecting them (both in one file, separated by ---):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: tkb-2024
spec:
  replicas: 10
  # <Snip>
  template:
    metadata:
      labels:
        project: tkb      # create Pods
        zone: prod        # with these labels
    spec:
      containers:
      # <Snip>
---
apiVersion: v1
kind: Service
metadata:
  name: tkb
spec:
  ports:
  - port: 8080
  selector:
    project: tkb          # send to Pods
    zone: prod            # with these labels

Behind the scenes with EndpointSlices

  1. Creating a Service makes the EndpointSlice controller create an associated EndpointSlice.
  2. Kubernetes watches for Pods matching the selector; new matches are added, deleted Pods are removed.
  3. An app sends traffic to the Service name; its container resolves the name to the Service IP through cluster DNS.
  4. The container sends to the Service IP, and the Service forwards to one Pod in the EndpointSlice.

Older Kubernetes used Endpoints objects; they are functionally identical, but EndpointSlices perform better on large busy clusters.

Service types

Type Builds on Purpose
ClusterIP (base) Reliable endpoint (name, IP, port) on the internal Pod network
NodePort ClusterIP Lets external clients connect through a port on every cluster node
LoadBalancer NodePort and ClusterIP Integrates with cloud load balancers for simple internet access

ClusterIP: access from inside the cluster

  • The default type. Name and IP are programmed into the internal network fabric.
    • The IP is routable only on the internal Pod network.
    • The name is registered automatically with the cluster's internal DNS.
    • All containers are pre-programmed to use cluster DNS.
  • Example: an app skippy; create a ClusterIP Service skippy, and every app on the cluster can reach it by that name.
  • ClusterIP Services are not routable and need the cluster DNS, so they do not work from outside the cluster. (Chapter 10 covers service discovery in depth.)

NodePort: access from outside the cluster

Adds a dedicated port, the NodePort, on every node.

apiVersion: v1
kind: Service
metadata:
  name: skippy           # registered with the internal cluster DNS (ClusterIP)
spec:
  type: NodePort         # Service type
  ports:
  - port: 8080           # internal ClusterIP port
    targetPort: 9000     # application port in the container
    nodePort: 30050      # external port on every cluster node (NodePort)
  selector:
    app: hello-world
  • This creates the usual ClusterIP Service and also publishes port 30050 on every node, mapped to the ClusterIP.
  • Figure 7.3 flow:
    1. An external client hits any node on the NodePort.
    2. The node forwards to the Service's ClusterIP.
    3. The Service picks a Pod from the always-current EndpointSlice list.
    4. The request is forwarded to the chosen Pod.
  • The Service does simple round-robin load balancing, so later requests probably reach other Pods.
  • Two significant limitations:
    • Ports are in the high range 30000 to 32767.
    • Clients must know node names or IPs and whether nodes are healthy.

So most people use LoadBalancer Services.

LoadBalancer: access via cloud load balancers

  • The easiest way to expose services externally: a NodePort Service fronted by a highly available cloud load balancer with a publicly resolvable DNS name and a low port number (Figure 7.4).
  • Flow: client, load balancer, NodePort on a healthy node, internal ClusterIP Service, Pod chosen from the EndpointSlice.
apiVersion: v1
kind: Service
metadata:
  name: lb               # registered with cluster DNS
spec:
  type: LoadBalancer
  ports:
  - port: 8080           # load balancer port
    targetPort: 9000     # application port inside the container
  selector:
    project: tkb

It listens on 8080 and maps to port 9000 on Pods labelled project=tkb, creating the NodePort and ClusterIP constructs automatically.

Summary of Service theory

  • Services give Pods a reliable endpoint; the front end is stable for the Service's whole life; the back end load balances over a dynamic Pod set matched by labels.
  • ClusterIP is default and internal; NodePort and LoadBalancer give external endpoints.
  • LoadBalancer creates a cloud load balancer and all the mappings to the Pods.

7.2 Hands-on with Services

  • Declarative (YAML) is preferred, but the imperative commands are useful to know.
  • You need the book's repo and a cluster from chapter 3.
    • Cloud cluster: Kubernetes provisions an internet-facing load balancer and gives public IPs or DNS names.
    • Local (Docker Desktop): same experience using localhost.
git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025
cd TKB/services

Deploy the sample app svc-test (a Deployment of ten Pods, a web app on port 8080, label chapter=services):

$ kubectl apply -f deploy.yml
deployment.apps/svc-test created

$ kubectl get deploy svc-test
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
svc-test   10/10   10           10          24s

Working with Services imperatively

kubectl expose inspects the running Deployment and creates IP, label selector, DNS records and port mappings.

$ kubectl expose deployment svc-test --type=LoadBalancer
service/svc-test exposed

$ kubectl get svc -o wide
NAME         TYPE           CLUSTER-IP     EXTERNAL-IP     PORT(S)          SELECTOR
kubernetes   ClusterIP      10.96.0.1      <none>          443/TCP          <none>
svc-test     LoadBalancer   10.10.19.33    212.2.245.220   8080:31755/TCP   chapter=services

(On a cloud the EXTERNAL-IP may take a minute to populate.) Reading the output:

Item Meaning
kubernetes line System Service exposing the Kubernetes API to all Pods and containers
Name Same as the Deployment (svc-test)
TYPE LoadBalancer; EXTERNAL-IP is localhost on local clusters (ignore a wrong 172 address on Docker Desktop)
CLUSTER-IP Internal IP, routable only on the internal network
PORT(S) Load balancer port 8080 and NodePort 31755; by default the LB port matches the app port; NodePort is random in 30000 to 32767
SELECTOR Matches the Pod labels
  • It inspected the Deployment to get the right port mapping (app on 8080) and selector (chapter=services on all 10 Pods).
  • It also created the ClusterIP and NodePort constructs: LoadBalancer builds on NodePort, which builds on ClusterIP (Figure 7.5, service stacking).

Line Meaning
Endpoints Healthy matching Pods from the Service's EndpointSlice
Session Affinity Session stickiness. Default None sends a client's connections to different Pods. ClientIP pins a client to one Pod, but needing it is an anti-pattern: microservices should be designed for process disposability so clients can use any Pod.
External Traffic Policy Cluster (default): balance across Pods on all nodes but obscure source IPs. Local: only Pods on the node the traffic arrives on, preserving source IPs.

Dual-stack clusters may also list IPv6 addresses. Browse to EXTERNAL-IP:8080 to confirm. The path: LoadBalancer on 8080, NodePort on each node, ClusterIP on 8080, Pod on 8080.

Clean up before the declarative version:

$ kubectl delete svc svc-test
service "svc-test" deleted

The declarative way

# lb.yml
kind: Service
apiVersion: v1
metadata:
  name: svc-lb
spec:
  type: LoadBalancer
  ports:
  - port: 9000          # load balancer port
    targetPort: 8080    # application port inside the container
  selector:
    chapter: services
  • metadata names the Service svc-lb and registers it with internal cluster DNS; custom labels and annotations go here too.
  • spec defines front end (port 9000) and back end (Pods labelled chapter=services, port 8080).
$ kubectl apply -f lb.yml
service/svc-lb created

Inspecting Services

$ kubectl get svc svc-lb
NAME     TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)
svc-lb   LoadBalancer   10.43.191.202   212.2.247.202   9000:30202/TCP
  • On a cloud, EXTERNAL-IP shows <pending> while the load balancer is provisioned; keep re-running the command.
  • Locally use localhost on port 9000 (ignore a 172 address on Docker Desktop). Browse to confirm the app.

Clean up

Deleting a Service automatically deletes its Endpoints and EndpointSlices.

$ kubectl delete -f deploy.yml -f lb.yml
deployment.apps "svc-lb" deleted
service "svc-lb" deleted

(The book's output prints deployment.apps "svc-lb" although the Deployment is svc-test; shown as printed.)

Summary points

  • Services give Pods reliable networking: a stable front end and a label-selected back end of healthy Pods.
  • ClusterIP is internal, NodePort exposes a port on every node, LoadBalancer integrates with cloud load balancers.
  • Services are first-class API objects; manage them declaratively through version-controlled YAML.
Terms to carry forward
  • Service front end / back end: stable name, IP, port / label selector over healthy Pods.
  • EndpointSlice: auto-created list of healthy Pods for a Service (replaced Endpoints).
  • ClusterIP / NodePort / LoadBalancer: stacked Service types.
  • port / targetPort / nodePort: Service port, container port, port on every node.
  • Session affinity: None or ClientIP stickiness (anti-pattern).
  • External Traffic Policy: Cluster or Local.
  • kubectl expose: imperative Service creation.
