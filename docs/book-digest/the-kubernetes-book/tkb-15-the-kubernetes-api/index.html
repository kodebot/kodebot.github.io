The Kubernetes Book 15: The Kubernetes API

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 15. Previous: The Kubernetes Book 14: API Security and RBAC. Next: The Kubernetes Book 16: Threat Modeling Kubernetes.

Takeaways
  • Kubernetes is API-centric: all resources are defined in the API and every request, from kubectl, kubelets or control plane services, goes through the API server, a RESTful HTTPS interface.
  • Objects are serialised (JSON to external clients, Protobuf between internal components) for transit and for the cluster store.
  • The API is split into the core group (/api/v1, no group name) and named groups (/apis/<group>/<version>/); REST paths follow GVR (group, version, resource).
  • New resources go alpha, beta, GA; beta gets a 9-month window; GA deprecations are served for 12 months or three releases (whichever is longest).
  • CustomResourceDefinitions (CRDs) extend the API with resources that behave like native ones; a custom controller is what makes them do anything.

The chapter uses lots of jargon on purpose and recommends doing the hands-on parts. Terminology: Pods, Services and others are resources in the API and objects when deployed; the book uses the terms interchangeably.

15.1 Kubernetes API big picture

  • All resources are defined in the API
    • all configuration and querying go through the API server. Admins and clients create, read, update and delete objects, usually with kubectl, but also from code or API testing tools.
  • Whatever the source, requests go to the API server, are authenticated and authorised, and a create request persists the object definition in the cluster store in serialised form and schedules it
    • (Figure 15.1.)

JSON serialisation

  • Serialisation converts an object into a string or byte stream for sending over a network or persisting; deserialisation reverses it.
  • Kubernetes serialises Pods, Services and so on as JSON and sends them over HTTP, in both directions:
    • clients like kubectl serialise objects when posting
    • the API server serialises responses
    • objects are also serialised for storage in the cluster store
  • Two schemas:
    • JSON and Protobuf
    • Protobuf is faster, more efficient and scales better but is harder to inspect and troubleshoot
    • At the time of writing: JSON with external clients, Protobuf between internal components.
  • Clients state supported schemas in the Content-Type header (for example Content-Type: application/json), and Kubernetes replies in kind.

  • Resources have configurable properties (a Pod: metadata, restart policy, service account name, runtime class, containers, volumes; a USB cable: type, length, colour).
  • Deploying a Pod means sending YAML to the API server

15.2 The API server

  • Exposes the API over a RESTful HTTPS interface, commonly on port 443 or 6443 (configurable).
$ kubectl cluster-info
Kubernetes control plane is running at https://kubernetes.docker.internal:6443
  • Like Grand Central station: everything talks via REST calls to it:
    • all kubectl commands
    • kubelets watching for tasks and reporting status
    • control plane services sharing data and status
  • It is a control plane service, which some clusters run as Pods in kube-system. If you build your own cluster, make the control plane highly available and fast
    • with hosted Kubernetes the provider manages and hides it.
  • Its main job is exposing the API inside and outside the cluster; it uses TLS and the same authN and authZ for internal and external requests.
  • RESTful means a modern web API accepting CRUD-style requests via standard HTTP methods (POST, GET, PUT, PATCH, DELETE).
K8s CRUD verb HTTP method kubectl example
create POST kubectl create -f <filename>
get, list, watch GET kubectl get pods
update PUT / PATCH kubectl edit deployment <name>
delete DELETE kubectl delete ingress <name>

Names do not always match: kubectl edit uses the update verb and the HTTP PATCH method.

A word on REST and RESTful

  • REST = REpresentational State Transfer, the industry standard for web APIs; systems using it, like Kubernetes, are called RESTful.
  • A REST request is a verb (maps to an HTTP method) and a path (URI to a resource). "Verb" is used loosely for CRUD operations and HTTP methods: an action.
  • kubectl converts a command to a REST request:
$ kubectl get pods --namespace shield

GET /api/v1/namespaces/shield/pods

A word on CRUD

CRUD = Create, Read, Update, Delete, implemented through HTTP methods. Creating via kubectl apply -f ns.json uses POST (hence "POSTing a configuration"). ns.json (folder api) defines Namespace shield:

{
  "kind": "Namespace",
  "apiVersion": "v1",
  "metadata": {
    "name": "shield",
    "labels": {
      "chapter": "api"
    }
  }
}

A simplified request header (body is the JSON file):

POST https://<api-server>/api/v1/namespaces
Content-Type: application/json
Accept: application/json

A successful response (the book prints a 200 here):

HTTP/1.1 200 (OK)
Content-Type: application/json
{
  <payload>
}

15.4 The API

  • The API is where all resources are defined: large, modular and RESTful.
  • Early on it was monolithic with all resources in one global namespace
    • as Kubernetes grew it was split into named groups (sub-groups). (Figure 15.3: simplified view with four of many groups.)
  • Two kinds: the core group and the named groups.

The core API group

  • Holds the original objects: Pods, Nodes, Services, Secrets, ServiceAccounts, found under /api/v1.
Resource REST path
Pods /api/v1/namespaces/{namespace}/pods/
Services /api/v1/namespaces/{namespace}/services/
Nodes /api/v1/nodes/
Namespaces /api/v1/namespaces/
  • Namespaced objects have longer paths
    • (two extra segments ../namespaces/{namespace}/...): GET /api/v1/namespaces/shield/pods/
    • Non-namespaced objects such as nodes are short: GET /api/v1/nodes/.
  • Read requests return 200 OK or 401 Unauthorized (as the book states).
  • GVR (group, version, resource) helps remember path structure (Figure 15.4: path to v1 StorageClasses in the storage.k8s.io group).
  • Expect no new resources in the core group.

Named API groups

  • All new resources go here
    • each group is a collection of related resources: apps has Deployments, StatefulSets, DaemonSets
    • networking.k8s.io has Ingresses, IngressClasses, NetworkPolicies.
  • Exceptions are older resources predating groups: Pods and Services are in the core group. Invented today, Services would probably be in networking.k8s.io and Pods in apps.
  • Paths start /apis/{group-name}/{version}/:
Resource Path
Ingress /apis/networking.k8s.io/v1/namespaces/{namespace}/ingresses/
ClusterRole /apis/rbac.authorization.k8s.io/v1/clusterroles/
StorageClass /apis/storage.k8s.io/v1/storageclasses/
  • Named-group paths start /apis (plural) with a group name
    • the core group starts /api (singular) with none. The core group is sometimes written "" because originally "everything was just in the API".
  • Splitting makes the API more scalable and easier to navigate and extend.

Alpha, beta and stable

New resources enter as alpha, progress through beta and graduate to GA (also called stable).

Stage Meaning Notes
Alpha Experimental ("hairy and scary") Bugs, features dropped without warning, big changes; disabled by default on most clusters
Beta Pre-release Close to the final design, minor changes expected at GA; enabled by default on most clusters; occasionally seen in production, but that is not a recommendation
GA Stable, production-ready Strong long-term commitment

Naming for a hypothetical resource tkb in the apps group:

  • alpha: /apis/apps/v1alpha1/tkb, /apis/apps/v1alpha2/tkb
  • beta: /apis/apps/v1beta1/tkb, /apis/apps/v1beta2/tkb
  • GA v1, and v2 goes through the same incubation: /apis/apps/v2alpha1/tkb, /apis/apps/v2beta1/tkb, /apis/apps/v2/tkb

Real stable paths: /apis/networking.k8s.io/v1/ingresses, /apis/batch/v1/cronjobs, /apis/autoscaling/v2/horizontalpodautoscalers. You can deploy through one API (for example v1beta2) and later manage the object through a newer one (v1).

Resource deprecation

At the time of writing:

  • Beta: a 9-month window to release a newer beta or graduate to GA, to stop resources stagnating (Ingress stayed in beta for over 15 releases).
  • GA:
    • long-lived
    • When deprecated, still served and supported for 12 months or three releases, whichever is longest, then removed
    • A stable resource is only deprecated after a newer stable version exists (v1 only after v2 ships).

Deploying a deprecated resource in recent versions:

  1. Returns a deprecation warning on the CLI.
  2. Adds a k8s.io/deprecated:true annotation to the audit record.
  3. Sets the apiserver_requested_deprecated_apis gauge metric.

The audit record and metric help you find deprecated API use when planning upgrades.

Extending the API

  • Kubernetes has built-in controllers for built-in resources, but you can add your own resources and controllers
    • Network and storage vendors use this to expose advanced features (snapshot schedules, IP address management)
    • Example: volumes appear via CSI drivers, Pods consume them via StorageClasses and PVCs, while snapshot scheduling is a custom resource with a custom controller, all managed with kubectl and YAML.
  • Pattern:
    1. Create your custom resource.
    2. Write and deploy your custom controller.
  • A CustomResourceDefinition (CRD) creates new resources that look and feel native, with their own REST paths
    • crd.yml (folder api) defines a cluster-scoped resource books in group nigelpoulton.com, served at v1:
# crd.yml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: books.nigelpoulton.com
spec:
  group: nigelpoulton.com        # API sub-group (a.k.a. "named API group")
  scope: Cluster                 # can be "Namespaced" or "Cluster"
  names:
    plural: books                # all resources need a plural and singular name
    singular: book               # singular names are used on the CLI and in command output
    kind: Book                   # kind property used in YAML files
    shortNames:
    - bk                         # short name usable by kubectl
  versions:                      # resources can be served by multiple API versions
  - name: v1
    served: true                 # if false, "v1" will not be served
    storage: true                # store instances of the object as this version
    schema:                      # this block defines the resource's properties
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
<Snip>

Summary points

  • Kubernetes is API-driven; the API is served by the API server, a control plane service that must be highly available and high-performance.
  • The API is resource-based and RESTful, accepting CRUD operations via POST, GET, PUT, PATCH and DELETE; divided into the core group (/api/v1) and named groups (/apis/...).
  • "Resource" is the API definition
    • "object" is a running instance (the book: "The Pod resource exists in the core API group, and there are five Pod objects running in the default Namespace").
  • Alpha, beta, GA lifecycle; GA deprecation guarantees at least 12 months or three versions.
  • The API is becoming the de facto cloud API; CRDs let third parties add resources that feel native.
Terms to carry forward
  • Serialisation / Protobuf / JSON / Content-Type.
  • REST, RESTful, CRUD, verb.
  • API server, kubectl proxy.
  • Core group /api/v1 vs named groups /apis/<group>/<version>; GVR.
  • Alpha, beta, GA; deprecation windows.
  • CRD, custom resource, custom controller.
  • Resource vs object.
