The Kubernetes Book 16: Threat Modeling Kubernetes

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 16. Previous: The Kubernetes Book 15: The Kubernetes API. Next: The Kubernetes Book 17: Real-World Kubernetes Security.

Takeaways
  • Threat modelling identifies vulnerabilities so you can prevent and mitigate them; the chapter applies STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
  • No model covers every threat, one threat often leads to another, and one threat has several mitigations: defence in depth is the key tactic.
  • Spoofing: protect the CA behind mTLS; set automountServiceAccountToken: false where a Pod does not need the API server.
  • Information disclosure: encrypt Secrets with KMS v2 envelope encryption so a node snapshot is not enough to read them.
  • Elevation of privilege: run non-root, drop capabilities, filter syscalls (seccomp), use MAC (AppArmor, SELinux), block privilege escalation, and enforce with Pod Security Admission.

16.1 Threat modeling

  • Threat modelling is the process of identifying vulnerabilities so you can put measures in place to prevent and mitigate them.
  • STRIDE defines six threat categories:
    • Spoofing
    • Tampering
    • Repudiation
    • Information disclosure
    • Denial of service
    • Elevation of privilege
  • STRIDE is structured but "no model guarantees to cover all threats". For each category the chapter gives a description and some Kubernetes-specific angles
    • the aim is ideas, not completeness.

16.2 Spoofing

Spoofing is pretending to be somebody else to gain extra privileges.

Securing communications with the API server

  • Kubernetes has many components (API server, controller manager, scheduler, cluster store, kubelet, container runtime), each with its own privileges
    • Even with least privilege, spoofing any of them causes problems.
  • All components authenticate with cryptographically signed certificates (mTLS), and Kubernetes rotates certificates automatically. Caveats:
    • A typical install auto-generates a self-signed CA that issues all component certificates: better than nothing, not enough for production alone.
    • mTLS is only as secure as the CA: compromising the CA can defeat the whole mTLS layer, so keep it secure.
  • Good practice: certificates from the internal CA are used and trusted only inside the cluster.
    • Approve certificate signing requests carefully.
    • Never add the Kubernetes CA as a trusted CA for systems outside the cluster.
  • Use two trusted key pairs for the API server:
    • one authenticating internal systems (issued by the cluster's self-signed CA)
    • one authenticating external systems (trust one or more third-party CAs)

Securing Pod communications

  • A Pod can spoof another Pod. Every Pod has a ServiceAccount giving it an identity, via a service account token mounted automatically as a Secret.
  • That token allows access to the API server, and most Pods do not need that, so set automountServiceAccountToken: false for those that do not:
apiVersion: v1
kind: Pod
metadata:
  name: service-account-example-pod
spec:
  serviceAccountName: some-service-account
  automountServiceAccountToken: false     # this line
# <Snip>

If a Pod does need the API server, consider the non-default expirationSeconds and audience settings. This example (inspired by the official docs) expires the token after one hour and restricts it to the vault audience, in a projected volume:

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - image: nginx
    name: nginx
    volumeMounts:
    - mountPath: /var/run/secrets/tokens
      name: vault-token
  serviceAccountName: my-pod
  volumes:
  - name: vault-token
    projected:
      sources:
      - serviceAccountToken:
          path: vault-token
          expirationSeconds: 3600    # this line
          audience: vault            # and this one

16.3 Tampering

Tampering is changing something maliciously to cause:

  • Denial of service: make the resource unusable.
  • Elevation of privilege: gain extra privileges.

It is hard to avoid, so a common countermeasure is to make it obvious (the book's analogy: tamper-proof seals on medication).

Tampering with Kubernetes components

Targets:

  • etcd
  • configuration files for the API server, controller manager, scheduler, etcd and kubelet
  • container runtime binaries
  • container images
  • Kubernetes binaries

Tampering happens in transit (over the network) or at rest (in memory or on disk).

  • In transit: TLS has built-in integrity guarantees that warn you of tampering.
  • At rest: recommendations (not exhaustive):
    • restrict access to servers running Kubernetes components, especially the control plane
    • restrict access to repositories storing Kubernetes configuration files
    • do remote bootstrapping only over SSH (and protect the keys)
    • always run SHA-2 checksums on downloads
    • restrict access to your image registry and its repositories
  • Also configure auditing and alerting on important binaries and config files
    • Example using the Linux audit daemon to watch the docker binary and attempts to change its file attributes:
$ auditctl -w /usr/bin/docker -p wxa -k audit-docker

(The chapter refers back to this example under repudiation.)

Tampering with applications

  • Make live Pod filesystems read-only in the securityContext: readOnlyRootFilesystem: true for the root filesystem, and allowedHostPaths for others
    • Here anything mounted below /test is read-only:
apiVersion: v1
kind: Pod
metadata:
  name: readonly-test
spec:
  securityContext:
    readOnlyRootFilesystem: true     # read-only root filesystem
    allowedHostPaths:                # make anything below
    - pathPrefix: "/test"            # this mount point
      readOnly: true                 # read-only
# <Snip>

16.4 Repudiation

  • Repudiation creates doubt about something; non-repudiation provides proof. In security: proving certain individuals did certain things.
  • Non-repudiation covers: what, when, who, where, why and how happened. The last two are hardest and usually need correlating several events over time.
  • API server audit events help (auditing may need enabling). An example event:
{
  "kind": "Event",
  "apiVersion": "audit.k8s.io/v1",
  "metadata": { "creationTimestamp": "2022-11-11T10:10:00Z" },
  "level": "Metadata",
  "timestamp": "2022-11-11T10:10:00Z",
  "auditID": "7e0cbccf-8d8a-4f5f-aefb-60b8af2d2ad5",
  "stage": "RequestReceived",
  "requestURI": "/api/v1/namespaces/default/persistentvolumeclaims",
  "verb": "list",
  "user": {
    "username": "fname.lname@example.com",
    "groups": [ "system:authenticated" ]
  },
  "sourceIPs": [ "123.45.67.123" ],
  "objectRef": {
    "resource": "persistentvolumeclaims",
    "namespace": "default",
    "apiVersion": "v1"
  },
  "requestReceivedTimestamp": "2022-11-11T10:10:00.123456Z",
  "stageTimestamp": "2022-11-11T10:10:00.123456Z"
}
  • Audit more than the API server: container runtimes, kubelets, applications and non-Kubernetes infrastructure such as network firewalls.
  • With several sources you need a central, secure log store, commonly fed by an agent on every node deployed as a DaemonSet
    • If the store is not secure, the logs can themselves be repudiated.
  • To prove tampering with binaries and config files, use an audit daemon watching writes on control plane and worker nodes
    • With the earlier docker rule, docker run generates an event like this (as printed, trimmed):
type=SYSCALL msg=audit(1234567890.123:12345): arch=abc123 syscall=59 success=yes \

uid=0 gid=0 euid=0 suid=0 fsuid=0 egid=0 sgid=0 fsgid=0 tty=pts0 ses=1 comm="docker" \
exe="/usr/bin/docker" subj=system_u:object_r:container_runtime_exec_t:s0 \

Combined and correlated with Kubernetes audit logs, these give "a comprehensive and trustworthy picture that cannot be repudiated".

16.5 Information disclosure

Information disclosure is leaking sensitive data (hacked data stores, APIs that expose too much).

Protecting cluster data

  • The whole cluster configuration lives in the cluster store (etcd): network and storage config, passwords, the cluster CA. It is a prime target.
  • At minimum limit and audit access to nodes hosting the cluster store; node access can bypass some security layers.
  • Secret encryption arrived in Kubernetes 1.7 but is not on by default, and the data encryption key (DEK) sits on the same node as the Secret, so node access bypasses it (worst on etcd nodes).
  • KMS v1 (beta in 1.11) stored key encryption keys (KEK) outside the cluster. KEKs encrypt and decrypt DEKs; this is envelope encryption.
  • KMS v2 (redesigned, GA since 1.29) improves on it:
    • a new DEK for every write, encrypted at rest with the KEK
    • cache size limited only by control plane node resources, so earlier DEKs are cached in memory for speed
    • zero-downtime re-encryption after key rotation, with no API server downtime or Pod restarts
  • KMS plugins run on control plane nodes and talk to the API server over Unix sockets, then to an external KMS provider that encrypts and decrypts DEKs.
  • Result: attackers must compromise both the control plane and the external KMS; a control plane snapshot is not enough to read a Secret.

  • Consider storing KEKs in Hardware Security Modules (HSM) or cloud Key Management Stores
    • Follow "trust but verify": check the encryption works and plan for a lost KEK or lost connectivity to the KMS.

Protecting data in Pods

  • Secrets
    • are the preferred way to store sensitive data such as passwords
    • Example: a front-end container reading an encrypted database can have the decryption key mounted as a Secret, far better than a plain-text file or environment variable.
  • Data in Persistent Volumes and ConfigMaps, if encrypted, should have its keys in Secrets.
  • Remember the caveats above about where Secret encryption keys live: "locking the house but leaving the keys in the door".

16.6 Denial of service

Denial of service (DoS) makes something unavailable. A well-known form is overload. Example: overloading the API server halts cluster operations (even internal systems use it).

Protecting cluster resources

  • Replicate essential services for HA:
    • multiple control plane nodes, replicated across availability zones, so one zone's network DoS cannot take down the whole control plane
    • Same for worker nodes, letting the scheduler spread apps across zones.
  • Set limits for:
    • memory
    • CPU
    • storage
  • Limit Kubernetes objects per Namespace (ReplicaSets, Pods, Services, Secrets, ConfigMaps). This ResourceQuota caps Pods in Namespace skippy at 100:
apiVersion: v1
kind: ResourceQuota
metadata:
  name: pod-quota
  namespace: skippy
spec:
  hard:
    pods: "100"
  • podPidsLimit
    • caps the processes a Pod can create
    • Against a fork bomb, the Pod is confined and cannot exhaust the node's PID range (kubelet included); Kubernetes normally restarts a Pod that exhausts it
    • Setting the right value needs an estimate of how many Pods run per node, or you over- or under-allocate.

Protecting the API server

It exposes a RESTful interface over a TCP socket, a target for botnet DoS. Helpful measures:

  • HA control plane: several API server replicas across nodes and zones
  • monitoring and alerting on request rates with sane thresholds
  • firewalls limiting exposure to the internet
  • Safeguard high-privilege accounts: an attacker may spoof a user or control plane service to overload it, despite strong RBAC.

Protecting the cluster store

  • Run an HA etcd cluster of 3 or 5 nodes.
  • Monitor and alert on etcd requests (log entries are a good start).
  • Isolate etcd at the network level so only control plane members reach it.
  • Default installs put etcd on the control plane servers (fine for dev and test)
    • large production clusters should consider a dedicated etcd cluster for performance and resilience. etcd is the most common choking point for large clusters, and a poorly performing etcd can be as bad as one under DoS.

Protecting application components

  • Most Pods expose a network service, so anyone on the network can DoS them. Use Pod resource limits, plus:
    • Network Policies limiting Pod-to-Pod and Pod-to-external communication
    • mutual TLS and API token authentication, rejecting unauthenticated requests
    • application-layer authorisation with least privilege, for defence in depth

16.7 Elevation of privilege

Privilege escalation is gaining higher access than granted, to cause damage or gain unauthorised access.

Protecting the API server

Authorisation modes (run several at once, for example RBAC plus Node):

Mode What it does Caveat
RBAC Restricts API operations to subsets of users (regular accounts or system services); every request is authenticated then authorised. Example: authN proves it is Mia; authZ decides whether Mia can create Pods.
Webhook Offloads authorisation to an external REST policy engine You must build and maintain it, and it becomes a single point of failure for every API request, so vet it rigorously
Node Authorises API requests made by kubelets (Nodes), which differ from users' requests

Protecting Pods

Four techniques (a Pod is only an execution environment for containers; the terms are often used interchangeably):

  1. Prevent processes running as root.
  2. Drop capabilities.
  3. Filter syscalls.
  4. Prevent privilege escalation.

Do not run processes as root

  • Root is UID 0, the most powerful Linux user
    • Running app processes as root grants full access to the container, and a container's root sometimes has unrestricted root access to the host.
  • Force a non-root user with runAsUser, one of many PodSecurityContext (spec.securityContext) settings. This runs all containers in the Pod as UID 1000:
apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  securityContext:        # applies to all containers in this Pod
    runAsUser: 1000       # non-root user
  containers:
  - name: demo
    image: example.io/simple:1.0
  • Two Pods with the same UID share a security context and possibly resources. Fine for replicas of one Pod
    • otherwise risky: two containers with R/W access to one volume can corrupt data, and a compromised container can tamper with data it should not reach.
  • Set runAsUser per container instead; it overrides the Pod level. Here the demo container runs as 2000 and other containers in the Pod use 1000:
apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  securityContext:        # applies to all containers in this Pod
    runAsUser: 1000       # non-root user
  containers:
  - name: demo
    image: example.io/simple:1.0
    securityContext:
      runAsUser: 2000     # overrides the Pod-level setting
  • Other ways around UID clashes: user namespaces (a process is UID 0 inside the container but UID 1000, say, on the host; check support in your Kubernetes version and runtime) and maintaining a map of UID usage.

Capability dropping

  • Root's power is a combination of many small privileges called capabilities. Examples: SYS_TIME sets the system clock
    • NET_ADMIN does network operations such as changing routes and interfaces. Root holds all of them.
  • Capabilities let you grant the exact set a process needs. There are over 30, so runtimes ship sensible defaults, often not good enough for production.
  • Find the minimum set:
    • run the app in test with all capabilities dropped, read the logs of missing permissions, map them to capabilities, add them to the Pod spec, and repeat until it runs
    • Caveats:
    • extensive testing is needed per app, or a production edge case can crash it
    • every application revision needs the same testing, so you need test procedures and release processes that handle it
  • Kubernetes uses your runtime's default set (for example containerd's); override it in securityContext:
apiVersion: v1
kind: Pod
metadata:
  name: capability-test
spec:
  containers:
  - name: demo
    image: example.io/simple:1.0
    securityContext:
      capabilities:
        add: ["NET_ADMIN", "CHOWN"]

Filter syscalls (seccomp)

  • seccomp
    • (secure computing) filters syscalls (how an app asks the kernel to do something) rather than capabilities
    • Apply least privilege: only the syscalls a container needs
    • It went GA in Kubernetes 1.19.
Profile Behaviour
Non-blocking Allows the Pod but records every syscall to an audit log; use extensively in dev and test, then build a custom profile from the log
Blocking Blocks all syscalls: extremely secure, but the Pod can do nothing useful
Runtime Default Uses the container runtime's profile, a balance of usable and secure, thoroughly tested; a common place to start
Custom Allows only the syscalls the app needs and blocks everything else; preferred for security. Danger: edge cases missed in testing can fail in production when an uncaptured syscall is needed

Mandatory Access Controls

  • Beyond seccomp and capabilities, MAC systems such as AppArmor and SELinux (Linux-only) are configured at node level and applied to Pods through Pod Security Contexts
    • They control how processes interact with system resources and are hard to configure, though tools can generate profiles from audit logs.
  • They are mandatory once enabled, unlike seccomp and capabilities, which are voluntary.
  • Some runtimes apply a default SELinux profile to all containers; override it in the Pod's securityContext.
  • Caution: powerful, and they can stop apps working if misconfigured, so test extensively first.

Prevent privilege escalation by containers

  • A Linux process is created when a parent clones itself and loads new instructions into the child
    • By default a child may claim more privileges than its parent, usually a bad idea, especially for containers whose security configuration is defined against the initial configuration.
  • Block it per container:
apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  containers:
  - name: demo
    image: example.io/simple:1.0
    securityContext:
      allowPrivilegeEscalation: false     # this line

Standardising Pod security with PSS and PSA

Two technologies work together: you choose the PSS policies and PSA enforces them.

  • Pod Security Standards (PSS): policies specifying required Pod security settings.
  • Pod Security Admission (PSA): enforces one or more PSS policies when Pods are created.

Pod Security Standards

Every cluster gets three community-maintained policies:

Policy Meaning
Privileged Wide-open allow-all
Baseline Sensible defaults; more secure than privileged, less than restricted
Restricted The gold standard of current best practice; very strict, many Pods will fail it

At the time of writing you cannot modify these, import others or create your own.

Pod Security Admission

  • Works per Namespace and is a validating admission controller, so it cannot modify Pods and has no effect on running Pods.
  • Three modes:
Mode Behaviour
Warn Allows violating Pods, issues a user-facing warning
Audit Allows violating Pods, logs an audit event
Enforce Rejects violating Pods
  • Good practice:
    • give every Namespace at least baseline in warn or audit to see which Pods fail and why
    • then enforce baseline and warn and audit on restricted. A Namespace with no Pod Security configuration is a gap: attach a policy soon, even if only warn and audit.
  • Label format <prefix>/<mode>: <policy>, prefix always pod-security.kubernetes.io, mode warn, audit or enforce, policy privileged, baseline or restricted. Example (baseline, warn):
pod-security.kubernetes.io/warn: baseline

PSA examples

Steps:

  1. Create Namespace psa-test.
  2. Label it to enforce baseline.
  3. Try a privileged container (fails).
  4. Fix the Pod so it conforms (works).
  5. Test the effect of switching to restricted.
  6. Switch to restricted.
  7. Check the impact on existing Pods.

Needs kubectl, a cluster and the book's repo; run from the psa directory:

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025

$ kubectl create ns psa-test

$ kubectl label --overwrite ns psa-test \
    pod-security.kubernetes.io/enforce=baseline

$ kubectl describe ns psa-test
Name:         psa-test
Labels:       kubernetes.io/metadata.name=psa-test
              pod-security.kubernetes.io/enforce=baseline     # label correctly applied
Annotations:  <none>
Status:       Active

psa-pod.yml violates baseline with a privileged container:

# psa-pod.yml
apiVersion: v1
kind: Pod
metadata:
  name: psa-pod
  namespace: psa-test        # deploy to the new psa-test Namespace
spec:
  containers:
  - name: psa-ctr
    image: nginx
    securityContext:
      privileged: true       # violates the baseline policy

$ kubectl apply -f psa-pod.yml
Error from server (Forbidden): error when creating "psa-pod.yml": pods "psa-pod" is
forbidden: violates PodSecurity "baseline:latest": privileged (container "psa-ctr"
must not set securityContext.privileged=true)

Change privileged to false:

# psa-pod.yml (edited)
apiVersion: v1
kind: Pod
# <Snip>
spec:
  containers:
  - name: psa-ctr
    image: nginx
    securityContext:
      privileged: false      # changed from true to false

$ kubectl apply -f psa-pod.yml
pod/psa-pod created

Test the impact of restricted without applying it, using --dry-run=server:

$ kubectl label --dry-run=server --overwrite ns psa-test \
    pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "psa-test" violate the new PodSecurity enforce
level "restricted:latest"
Warning: psa-pod: allowPrivilegeEscalation != false, unrestricted capabilities,
runAsNonRoot != true, seccompProfile
<Snip>

psa-pod fails four requirements:

  • allowPrivilegeEscalation is not false
  • it runs unrestricted capabilities
  • runAsNonRoot is not true
  • it fails the seccompProfile test

Apply it for real and check the existing Pod:

$ kubectl label --overwrite ns psa-test \
    pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "psa-test" violate the new PodSecurity enforce level
"restricted:latest"
Warning: psa-pod: allowPrivilegeEscalation != false, unrestricted capabilities,
runAsNonRoot != true, seccompProfile
namespace/psa-test labeled

$ kubectl get pods --namespace psa-test
NAME      READY   STATUS    RESTARTS   AGE
psa-pod   1/1     Running   0          3m9s

Same warning, but the Pod keeps running: PSA is an admission controller, so it acts only when Pods are created or modified. Multiple policies and modes can combine on one Namespace, a common pattern: enforce baseline, warn and audit on restricted, to prepare for restricted:

$ kubectl label --overwrite ns psa-test \
    pod-security.kubernetes.io/enforce=baseline \
    pod-security.kubernetes.io/warn=restricted \
    pod-security.kubernetes.io/audit=restricted

Verify with kubectl describe ns psa-test.

Alternatives to Pod Security Admission

PSS and PSA are limited: validating only, and no custom or imported policies. Third-party options include:

  • OPA Gatekeeper
  • Kubewarden
  • Kyverno

16.8 Towards a more secure Kubernetes

Kubernetes is on a continual journey towards better security:

  • v1.26: all binary artifacts and container images used to build clusters are cryptographically signed.
  • An official feed of publicly announced CVEs; since v1.27 a JSON and RSS feed refreshes when a new CVE is announced.
  • v1.27: containers inherit a default seccomp profile from the runtime; this needs --seccomp-default on every kubelet.
  • Many clouds offer confidential computing (confidential VMs and containers) that Kubernetes can use to encrypt memory for container workloads (data in use)
    • some offer it in hosted Kubernetes.
  • A third-party security audit of Kubernetes, published April 2023 on Kubernetes 1.24, the second after the original in 2019.
  • The Cloud Native Security Whitepaper is recommended for a holistic view.

Summary points

  • STRIDE structures threat modelling of Kubernetes into six categories; one threat can lead to another and several mitigations can address one threat, so use defence in depth.
  • Pod Security Admission is the preferred way to implement Pod security defaults.
  • The next chapter covers best practices and lessons from running Kubernetes in production.
Terms to carry forward
  • STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege.
  • mTLS / CA: component authentication and the single point it depends on.
  • Non-repudiation / audit events: proof of what, when, who, where, why, how.
  • DEK / KEK / envelope encryption / KMS v2: per-write data key wrapped by an external key.
  • ResourceQuota / podPidsLimit: caps on objects and processes.
  • Capabilities, seccomp, MAC (AppArmor, SELinux): privilege splitting, syscall filter, mandatory controls.
  • allowPrivilegeEscalation: false.
  • PSS (Privileged, Baseline, Restricted) / PSA (warn, audit, enforce).
  • OPA Gatekeeper, Kubewarden, Kyverno: third-party policy engines.
