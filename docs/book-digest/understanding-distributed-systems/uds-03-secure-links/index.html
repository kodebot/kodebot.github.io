Understanding Distributed Systems 3: Secure links

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 3. Previous: Understanding Distributed Systems 2: Reliable links. Next: Understanding Distributed Systems 4: Discovery.

[!abstract] The one-minute version TCP bytes travel in the clear, so a middleman can read or alter them. TLS (RFC 8446 for TLS 1.3: https://datatracker.ietf.org/doc/html/rfc8446) runs on top of TCP and adds encryption, authentication and integrity, so protocols like HTTP can use it. Use it for all communication, even inside your own network.

3.1 Encryption

Data between client and server is obfuscated so only the two processes can read it.

  • On connection open the parties negotiate a shared secret using asymmetric encryption: each generates a key pair (private and public) and they exchange public keys
    • mathematical properties of the pairs let both derive the same secret (primer: https://blog.cloudflare.com/a-relatively-easy-to-understand-primer-on-elliptic-curve-cryptography/)
      • The shared secret is never sent over the wire.
  • Asymmetric encryption is slow and expensive, so it is used only to create the shared key
    • After that symmetric encryption (fast, cheap) is used
    • The shared key is renegotiated periodically to limit how much data could be deciphered if it were broken.
  • Encrypting in-flight data costs CPU, but it is negligible:
    • modern processors have dedicated cryptographic instructions
    • So use TLS for all communications, even those not on the public internet.

3.2 Authentication

Encryption hides data, but the client must still know it is talking to the real server (and the server may want to verify the client).

  • TLS authenticates with digital signatures based on asymmetric cryptography (https://en.wikipedia.org/wiki/Digital_signature). The server has a key pair and shares its public key

    • it signs messages with its private key
    • the client uses the public key to verify the signature.

  • Problem:

    • how does the client know the public key is authentic? Hence certificates, which prove ownership of a public key
    • A certificate holds the owner's information, expiration date, public key, and a digital signature of the third party that issued it
    • The issuer is a certificate authority (CA), itself represented by a certificate, forming a chain that ends at a root CA, which self-signs its certificate.

  • For a device to trust a certificate, the certificate or one of its ancestors must be in the client's trusted store

    • Trusted root CAs such as Let's Encrypt (https://letsencrypt.org/) are normally included by the OS vendor.

  • At connection time

    • the server sends the full chain, from its own certificate up to the root
    • The client scans the chain until it finds a certificate it trusts, then verifies the certificates in reverse order from that point: checking things like expiration date and that the signature was really made by the issuing CA
    • If verification reaches the server's own certificate without error, the path is verified and the server is authenticated.

  • Most common mistake: letting a certificate expire.

    • The client cannot verify the identity, opening a connection fails, and the whole application can go down
    • Automation to monitor and auto-renew certificates before expiry is well worth it.

3.3 Integrity

  • Even obfuscated data can be tampered with (e.g. random bits swapped)
    • TLS computes a message digest with a secure hash function to produce a message authentication code (HMAC) (RFC 2104: https://datatracker.ietf.org/doc/html/rfc2104)
    • The receiver recomputes the digest and compares it with the one in the message; on mismatch the message was corrupted or tampered with and is dropped.
  • The HMAC also protects against corruption, not only tampering
    • Why, if TCP guarantees integrity? TCP's checksum is not 100% reliable: it fails to detect errors for roughly 1 in 16 million to 10 billion packets
    • with 1 KB packets, that is once per 16 GB to 10 TB transmitted (source cited: "When the CRC and TCP checksum disagree", https://dl.acm.org/doi/10.1145/347057.347561).

3.4 Handshake

When a TLS connection opens, a handshake happens:

  1. The parties agree on a cipher suite: the key exchange algorithm (to make shared secrets), the signature algorithm (to sign certificates), the symmetric encryption algorithm (for application data) and the HMAC algorithm (integrity and authenticity of application data).
  2. They use the key exchange algorithm to create the shared secret, which the symmetric algorithm then uses to encrypt the channel.
  3. The client verifies the server's certificate; on success it can send encrypted application data. The server can optionally also verify a client certificate.

The steps need not happen in this order: implementations optimise to cut round trips. The handshake typically takes 2 round trips with TLS 1.2 and just one with TLS 1.3. Bottom line: a new connection is not free, so put servers geographically close and reuse connections when possible.
