Understanding Distributed Systems 5: APIs

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 5 (end of Part I). Previous: Understanding Distributed Systems 4: Discovery. Next: Understanding Distributed Systems 6 and 7: Part II intro, system models, failure detection (Part II, coordination).

[!abstract] The one-minute version A server's API is an adapter that turns messages from the link into calls on its business logic. This chapter walks through designing a RESTful HTTP API: model resources with URLs, pick request methods (know which are safe and idempotent), return correct status codes, describe it with an IDL (OpenAPI), evolve it without breaking clients, and make requests idempotent so clients can retry safely after timeouts.

Communication styles

  • Direct:
    • client talks straight to the server; both must be up for it to succeed
    • Indirect: through a broker (messaging): sender writes to a message channel, the receiver reads from it later
    • Indirect fits when the "both up" guarantee is not needed or is hard to get (chapter 23).
  • This chapter: direct request-response, "like a function call but across process boundaries and over the network".
  • Messages are serialised in a language-agnostic format.
    • The choice sets serialisation speed, human readability and how hard evolution is
      • JSON (https://www.ecma-international.org/publications-and-standards/standards/ecma-404/) is self-describing and readable but verbose and costly to parse
    • Protocol Buffers (https://developers.google.com/protocol-buffers) is leaner and faster but not human-readable.
  • Synchronous:
    • the client blocks waiting for the response (inefficient, blocks threads)
    • Asynchronous: the outbound adapter invokes a callback on response
    • JavaScript, C# and Go hide callbacks with async/await.
  • Technologies:
    • HTTP and gRPC (https://grpc.io/). Internal server-to-server APIs usually use a high-performance RPC framework like gRPC
    • public external APIs tend to use HTTP because browsers easily make HTTP calls from JavaScript.
  • REST
    • (Fielding's dissertation: https://www.ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm) is a set of principles for elegant, scalable HTTP APIs
    • an API following them is RESTful
      • Among them: requests are stateless (each carries everything needed), and responses are labelled cacheable or non-cacheable (a cacheable response can be reused for an equivalent later request).

5.1 HTTP

  • A request-response protocol (https://en.wikipedia.org/wiki/Hypertext_Transfer_Protocol): the client sends a request to the server's API endpoint, the server replies

    • An HTTP 1.1 message is text: a start line (request: what it is for; response: success or failure), headers (key-value metadata) and an optional body.

  • Stateless: everything the server needs is in the request. Uses TCP for reliability; over TLS it is HTTPS.

  • HTTP 1.1

    • keeps the connection open by default, but a new request cannot be issued until the previous response arrives: head-of-line (HOL) blocking
    • A browser fetching several images downloads them one at a time
    • Pipelining (https://en.wikipedia.org/wiki/HTTP_pipelining) is allowed for some requests but still suffers HOL blocking (one slow response blocks those after it)
    • The usual fix, more connections, costs memory and sockets.

  • HTTP/2

    • (RFC 7540: https://tools.ietf.org/html/rfc7540): built to fix 1.1's limits
    • binary, and multiplexes concurrent request-response transactions (streams) on one connection. In early 2020 about half the most-visited sites used it.

  • HTTP/3:

    • based on UDP with its own transport protocol to address TCP's shortcomings: with HTTP/2 a packet loss on the TCP connection blocks all streams (HOL), with HTTP/3 only one stream is interrupted
    • (References: https://www.youtube.com/watch?v=rlN4F1oyaRM, https://blog.cloudflare.com/http-3-vs-http-2/)

  • The book illustrates with HTTP 1.1.

5.2 Resources

Example: a product-catalogue service (customers browse; admins create, update, delete). An HTTP server hosts resources (a document, image, collection of resources: physical or abstract). A URL identifies a resource by its location.

  • https://www.example.com/products?sort=price: protocol, hostname, resource name, query string (extra parameters affecting handling, here the sort order)
    • Without the query string it is the /products endpoint.
  • URLs model relationships: /products/42 (product 42 in the collection), /products/42/reviews. The more nesting, the more complex the API.
  • Resources are serialised in message bodies. The client states its preferred representation in headers
    • the server picks the best (content negotiation: https://developer.mozilla.org/en-US/docs/Web/HTTP/Content_negotiation). JSON represents non-binary resources:
{
  "id": 42,
  "category": "Laptop",
  "price": 999
}

5.3 Request methods

CRUD via request methods, the "verb" applied to a resource:

  • POST /products: create a product, return the new resource's URL
  • GET /products: list (query string filters, paginates, sorts)
  • GET /products/42: retrieve product 42
  • PUT /products/42: update product 42
  • DELETE /products/42: delete product 42

Safe: no visible side effects, can be cached. Idempotent: running it many times has the same end result as once (crucial, see 5.7).

Method Safe Idempotent
POST No No
GET Yes Yes
PUT No Yes
DELETE No Yes

5.4 Response status codes

(Reference list: https://httpstatuses.com/)

  • 200 to 299 success (200 OK: request succeeded, body has the resource).
  • 300 to 399 redirection (301 Moved Permanently: new URL in the Location header).
  • 400 to 499 client errors:
    • usually fail the same way on retry because the fault is the client's, so do not retry
    • 400 Bad Request (input validation failed), 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but not allowed), 404 Not Found.
  • 500 to 599 server errors:
    • the cause may be temporary, so retry is OK
    • 500 Internal Server Error, 502 Bad Gateway (a gateway or proxy got an invalid response from a downstream server), 503 Service Unavailable (temporary overload or scheduled maintenance).
  • (Footnote) Upstream/downstream: if service A calls B, B is a downstream dependency of A and A is upstream of B; no industry consensus, other texts may reverse it.

5.5 OpenAPI

The HTTP adapter implements the service interface, e.g.:

interface CatalogService
{
    List<Product> GetProducts(...);
    Product GetProduct(...);
    void AddProduct(...);
    void DeleteProduct(...);
    void UpdateProduct(...)
}

GET /products makes the adapter call GetProducts(...) and convert the result to an HTTP response.

An interface definition language (IDL) is a language-independent API definition from which you generate server-side boilerplate adapters and client SDKs in the languages you want. OpenAPI (https://swagger.io/specification/, evolved from Swagger) is one of the most popular IDLs for RESTful HTTP APIs: a YAML document with endpoints, methods, status codes and the JSON schema of resources:

openapi: 3.0.0
info:
  version: "1.0.0"
  title: Catalog Service API
paths:
  /products:
    get:
      summary: List products
      parameters:
        - in: query
          name: sort
          required: false
          schema:
            type: string
      responses:
        "200":
          description: list of products in catalog
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/ProductItem"
        "400":
          description: bad input
components:
  schemas:
    ProductItem:
      type: object
      required:
        - id
        - name
        - category
      properties:
        id:
          type: number
        name:
          type: string
        category:
          type: string

From this a tool generates documentation, boilerplate adapters and client SDKs.

5.6 Evolution

An API starts as a well-designed interface (or should) and must change for new use cases. Avoid breaking changes that force all clients to change at once, some of which you do not control.

  • Endpoint level: renaming /products to /new-products, or making an optional query parameter mandatory, breaks old clients.
  • Message level:
    • changing a schema incompatibly, e.g. category from string to number, makes old deserialisation blow up
    • the same holds for Protocol Buffers (reference: https://martin.kleppmann.com/2012/12/05/schema-evolution-in-avro-protocol-buffers-thrift.html).
  • Version REST APIs
    • to allow breaking changes, e.g
    • a version prefix /v1/products/
    • Rule of thumb: evolve backward-compatibly unless there is a very good reason. Backward-compatible APIs are not elegant but they are practical.

5.7 Idempotency

Problem: when a request times out the client does not know whether the server received it (the server may have processed it and crashed before replying). The fix is to retry. Methods such as PUT and DELETE are inherently idempotent (RFC 7231 section 4.2.2: https://datatracker.ietf.org/doc/html/rfc7231#section-4.2.2): the same PUT twice has the same effect as once.

But POST is not. A timed-out POST that created a product, retried, makes two products. Client-side reconciliation (find and remove duplicates) pushes complexity onto every client. Better: make the server treat the request as idempotent.

  • Decorate the request with an idempotency key, a unique identifier such as a UUID, often in a header (Stripe's API uses Idempotency-Key: https://stripe.com/blog/idempotency)
    • The server stores every request ID it has seen in a database
    • on a new request it checks
    • if absent it records the ID and executes. IDs need not be kept forever
    • purge after some time.
  • The tricky part:
    • if the server records the ID and crashes before executing, every retry is wrongly ignored
    • So handle the request atomically: either process it and store the ID, or do neither.
  • If the IDs and resources live in the same database, wrap both in one ACID transaction (see https://brandur.org/http-transactions, https://brandur.org/idempotency-keys)
    • If handling needs external calls to other services, it needs coordination: section 13.2 (sagas).
  • What to return for a duplicate?
    • Not an "already exists" error (the client would need special handling vs. the first 201 Created)
    • ideally return the same response as the very first request.
  • Multi-client scenario:
    • A creates a product but never gets the reply
    • B deletes it
    • A retries. Returning the original creation response is less surprising than an odd error about a deleted resource. "When in doubt," follow the principle of least astonishment.
  • Payoff: an idempotent API makes clients robust: requests can be retried on failure with no edge-case worries (also see https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

Summary (the author's)

Communicating over networks is what makes a system distributed. It is easy to ignore the "leaking" complexity because languages and frameworks make a remote API look like a local function call.

The author learned the lesson after days chasing odd degradations that turned out to be exhausted socket pools or routers dropping packets.

Things that can go wrong: socket pools exhausted, TLS certificates expire, DNS servers unavailable, routers congested and dropping packets, non-idempotent requests causing unexpected states.

"The only universal truth is that the fastest, safest, most secure, and reliable network call is the one you don't have to make."
