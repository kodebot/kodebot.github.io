Understanding Distributed Systems 8: Time

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 8. Previous: Understanding Distributed Systems 6 and 7: Part II intro, system models, failure detection. Next: Understanding Distributed Systems 9: Leader election.

The one-minute version

Time matters for TTLs, timeouts and, above all, ordering events. A single-threaded program runs operations one after another; a distributed system has no shared global clock and processes run concurrently. Physical clocks drift and get corrected by jumps, so they cannot reliably order events across nodes. Logical clocks track causality instead: a Lamport clock (smaller timestamp is consistent with happened-before) and a vector clock (can tell happened-before from concurrent).

8.1 Physical clocks

  • A process has a wall-time clock, most commonly a vibrating quartz crystal: cheap, not very accurate

    • Manufacturing differences and temperature make one run slightly faster or slower than another
    • The rate is clock drift; the difference between two clocks at a point in time is clock skew.

  • Quartz clocks must be synced periodically with machines that have higher-accuracy clocks like atomic clocks (time from quantum-mechanical properties of atoms, far more expensive, accurate to 1 second in 3 million years; https://en.wikipedia.org/wiki/Atomic_clock).

  • Sync uses a protocol; the challenge is the network's unpredictable latency

    • The most common is NTP (RFC 5905: https://datatracker.ietf.org/doc/html/rfc5905): the client estimates clock skew from a server timestamp corrected by the estimated network latency, then adjusts its clock
    • That makes the clock jump forward or backward, which breaks timestamp comparison: an operation that ran after another could get an earlier timestamp because the clock jumped back between them.

  • Monotonic clock:

    • offered by most OSs, unaffected by jumps: it measures seconds elapsed since an arbitrary point (e.g. boot) and only moves forward
      • Good for elapsed time between two timestamps on the same node
    • useless for comparing different nodes.

  • Since wall clocks cannot be perfectly synchronised, do not rely on them to order operations across nodes

    • New angle: in a single-threaded process one of two operations must come first
    • That happened-before relationship is a causal bond: the first can have side effects that affect the second
    • Build a clock that captures causality rather than physical time: a logical clock.

8.2 Logical clocks

A logical clock measures time in logical operations, not wall-clock time. The simplest is a counter incremented before each operation: operations on one process get distinct, ordered timestamps.

Across processes: sending an email creates a synchronisation point. Whatever you did before sending (drinking coffee) must have happened before what your friend did after receiving it. So when one process sends a message to another, the sender's earlier operations happened before the receiver's later ones.

Lamport clock (Lamport's paper "Time, Clocks, and the Ordering of Events in a Distributed System": http://lamport.azurewebsites.net/pubs/time-clocks.pdf). Each process has a local counter:

  1. Initialised to 0.
  2. Increment by 1 before an operation.
  3. Sending: increment by 1 and send a copy of the counter in the message.
  4. Receiving: set the counter to the maximum of the received and local counter, then increment by 1.
  • It assumes crash-stop; crash-recovery can be supported by e.g. persisting the clock's state on disk.
  • Guarantee: if O1 happened-before O2, then ts(O1) < ts(O2). (Book example: D happened-before F with timestamps 4 and 5.)
  • Limitations:
    • unrelated operations can share a timestamp (A and E both equal 1)
    • To get a strict total order, break ties arbitrarily, e.g
    • by process ID (then E's timestamp exceeds A's)
    • Even so, timestamp order does not imply causality: E did not happen-before C even though the timestamps seem to say so
    • To guarantee that, use a vector clock.

8.3 Vector clocks

A vector clock guarantees that if one timestamp is less than another, the former must have happened-before the latter (paper: https://fileadmin.cs.lth.se/cs/Personal/Amr_Ergawy/dist-algos-papers/4.pdf).

  • It is an array of counters, one per process, each process holding its own copy
    • Three processes P1, P2, P3: each keeps [C_P1, C_P2, C_P3]; the first counter belongs to P1, and so on
    • (Real implementations use a dictionary rather than an array.)

Rules:

  1. Initially all counters are 0.
  2. On an operation, the process increments its own counter.
  3. On sending, increment its own counter and send a copy of the array.
  4. On receiving, merge the array with the local one by element-wise maximum, then increment its own counter.

Comparison (partial order: in a total order every pair is comparable; in a partial order some pairs are not).

Given timestamps T1 (of O1) and T2 (of O2): if every counter in T1 is <= the matching counter in T2 and at least one is strictly <, then O1 happened-before O2 (book: B happened-before C in its Figure 8.2).

If neither happened-before the other, the timestamps cannot be ordered and the operations are concurrent (E and C in the figure).

Illustration of the rule (my own numbers, not from the book): [2,1,0] vs [3,1,0]: all counters <=, one strictly <, so the first happened-before the second. [2,0,0] vs [1,1,0]: each is larger somewhere, so they are concurrent.

  • Drawback:
    • storage per process grows linearly with the number of processes, a problem for apps with many clients
    • Other clocks fix this, such as dotted version vectors ("Why Logical Clocks are Easy": https://queue.acm.org/detail.cfm?id=291775).

Takeaway. Logical clocks may feel abstract; the book returns to practical uses later. In general physical clocks cannot accurately derive the order of events on different processes. Sometimes they are good enough, e.g. timestamping logs used only for debugging.
