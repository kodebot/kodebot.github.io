Understanding Distributed Systems 12: Transactions

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 12. Previous: Understanding Distributed Systems 11: Coordination avoidance. Next: Understanding Distributed Systems 13: Asynchronous transactions.

[!abstract] The one-minute version A transaction makes a group of operations look like one atomic operation: all succeed or none do (https://en.wikipedia.org/wiki/Transaction_processing). Inside one relational database that is easy. When data lives in several data stores (common in microservices, each with its own store) you need a distributed transaction, which is much harder. The chapter covers ACID, isolation (race conditions, serializability, and the concurrency control protocols 2PL, OCC, MVCC), atomicity (write-ahead log, two-phase commit) and NewSQL (Spanner).

12.1 ACID

Money transfer: if the withdrawal succeeds but the deposit fails, the funds must go back. So both steps are wrapped in an inseparable unit of change. In a relational database a transaction is a group of operations with the ACID guarantees:

  • Atomicity:
    • no partial failures
    • All operations complete or none do
    • A failed transaction's changes must be undone, whether the transaction itself failed (e.g. divide by zero) or the database crashed midway.
  • Consistency:
    • application-level invariants must always hold
    • a transaction moves the database from a correct state to another correct state
      • The developer defines how (transfer invariant: the total across accounts is unchanged; money is not created or destroyed)
      • Confusingly, this "C" has nothing to do with the consistency models discussed earlier
    • per Joe Hellerstein it "was tossed in to make the acronym work" (http://www.bailis.org/blog/when-is-acid-acid-rarely/). The book ignores it for the rest of the chapter.
  • Isolation: a transaction appears to run as if no other transaction is executing; concurrent execution causes no race conditions.
  • Durability:
    • once committed, changes are on durable storage and survive a crash
    • Persisting to disk is not the whole story: replication is needed to survive storage failures (chapter 10).

Transactions spare developers a whole range of failure scenarios. To understand distributed ones, first see how a centralised database does it.

12.2 Isolation

The easiest isolation: run transactions serially (e.g. a global lock), but that is extremely inefficient, so transactions run concurrently, and concurrent access to the same data produces race conditions:

  • Dirty write: overwriting a value written by a transaction that has not committed.
  • Dirty read: observing a write from a transaction that has not completed.
  • Fuzzy read (non-repeatable read): reading an object twice and seeing different values because another transaction updated it between the reads.
  • Phantom read:
    • reading a group of objects matching a condition while another transaction adds, updates or deletes matching objects
    • E.g
    • one transaction sums all employees' salaries while another deletes some records: the final sum is wrong at commit.

An isolation level protects against one or more of these and provides an abstraction for reasoning about concurrency. Stronger = more protection but less performance. An isolation level is defined by which race conditions it forbids.

  • Serializability
    • is the only level that isolates against all race conditions: executing a group of transactions has the same side effects as running them serially in some order
    • With concurrent X and Y where X commits first, a serializable system guarantees they appear as X then Y or Y then X (even if Y committed after!).
  • Strict serializability adds a real-time requirement: serializability combined with linearizability's real-time guarantee, so when a transaction completes its side effects are immediately visible to all future transactions.
  • (Strict) serializability is slow: it requires coordination, creating contention
    • a transaction may wait for others or even abort because it can no longer be part of a serializable execution
    • Since not every app needs it, data stores offer weaker levels
    • Rule of thumb: consciously choose the level and understand its implications, or the store decides silently: PostgreSQL's default is read committed (https://www.postgresql.org/docs/12/transaction-iso.html)
    • If in doubt, choose strict serializability.
  • More levels and races exist than the ones shown
    • Jepsen is a good formal reference (https://jepsen.io/consistency), and vendors' docs "don't always match" the formal definitions (https://jepsen.io/analyses).

12.2.1 Concurrency control

Given serializability, the challenge is maximising concurrency while preserving the appearance of serial execution. A concurrency control protocol defines the strategy; two categories guarantee serializability: pessimistic and optimistic.

Pessimistic: two-phase locking (2PL) (https://en.wikipedia.org/wiki/Two-phase_locking).

  • Locks block other transactions from accessing an object
    • Two kinds:
      • a read lock can be shared by many read-only transactions but blocks anyone wanting a write lock
      • a write lock is held by one transaction and blocks all others (read or write)
    • A lock manager tracks the locks granted, who holds them, and who waits.
  • Two phases:
    • an expanding phase (only acquire locks) and a shrinking phase (only release)
    • Obeying that rule provably guarantees (strict) serializability
    • In practice locks are released only when the transaction completes (strict 2PL), so data written by uncommitted X stays locked and Y cannot read it and be forced to abort if X aborts (cascading abort, wasted work).
  • Deadlock: X waits for a lock Y holds while Y waits for one X holds. General fix: detect deadlocks after they occur and abort a victim transaction, then restart it.

Optimistic: optimistic concurrency control (OCC) (https://www.eecs.harvard.edu/~htk/publication/1981-tods-kung-robinson.pdf).

  • Run transactions without blocking, assuming conflicts are rare and transactions short-lived
    • A transaction writes to a local workspace, not the data store
    • At commit the store checks whether the workspace conflicts with other running transactions' workspaces, using a timestamp per transaction that fixes its serialisation order
    • Success: the workspace is copied into the store
    • Failure: abort and restart.
  • OCC still uses physical locks (latches) briefly on internal shared structures (e.g. when validating), unrelated to 2PL's logical locks.
  • When:
    • optimistic avoids lock and deadlock overhead, so it suits read-heavy workloads or occasionally conflicting writes
    • pessimistic is more efficient for conflict-heavy workloads (no wasted work).

Neither is good for read-only transactions: in 2PL (the book writes "2PC" here, a slip for 2PL) a reader may wait long for a shared lock; in OCC it may abort because a value it read was overwritten. Read-only transactions greatly outnumber writes, so ideally they never block or abort.

Multi-version concurrency control (MVCC) (https://en.wikipedia.org/wiki/Multiversion_concurrency_control) delivers that by keeping older versions. A write creates a new version; a read sees the newest version that existed when the transaction started.

So a read-only transaction reads an immutable, consistent snapshot without blocking or aborting. For write transactions MVCC falls back to 2PL or OCC. Since most transactions are read-only, it brings major performance gains: MVCC is the most widely used scheme today.

  • MVCC + 2PL example:
    • a write transaction uses 2PL on everything it reads or writes
    • at commit the transaction manager gives it a unique commit timestamp TC_i, assigned to all new versions
      • One commit at a time, so a read-only transaction whose start timestamp TS_j >= TC_i sees all of that transaction's changes (it reads only the newest committed version with timestamp <= TS_j).
  • The book glosses over the implementation details
    • you are unlikely to implement these yourself, but the data stores you depend on do, so know the trade-offs
      • For depth it recommends Andy Pavlo's database systems course: https://15445.courses.cs.cmu.edu/fall2019/.

A limited OCC you should know how to implement (per object): give each object a version number incremented on every update.

A transaction reads a value, computes locally, then updates conditionally on the version being unchanged, atomically with compare-and-swap (supported by many stores; same trick as the lease fix in section 9.2).

Read version 42 and update only if still 42: if so, write and set 43; otherwise abort and restart.

12.3 Atomicity

A transaction either commits after all its operations or aborts after some; on abort every change must be undone (rolled back).

  • To guarantee atomicity and durability the store writes every change to a write-ahead log (WAL) persisted on disk before applying it
    • Each entry records the transaction ID, the object ID, and the old and new value
    • Usually the log is never read; on abort or crash it has enough information to redo and undo changes
    • (Details are outside the book; see any database textbook.)
  • Limit:
    • WAL recovery only works within a single data store
    • If the two bank accounts are in different banks with separate stores, running two separate transactions is unsafe: if the second fails, the system is inconsistent
    • We need both commit or both fail without side effects.

12.3.1 Two-phase commit (2PC)

(https://en.wikipedia.org/wiki/Two-phase_commit_protocol) A protocol for atomic commits across multiple processes. A coordinator (e.g. the client app that started the transaction) orchestrates the participants. Two phases: prepare and commit.

  1. The coordinator sends prepare: "are you ready to commit?"
  2. If all participants say ready, it sends commit to all. If any says it cannot, or does not respond promptly, it sends abort to all.

Two points of no return:

  • A participant that replies ready must commit later no matter what, and cannot progress until the coordinator says commit or abort
    • If the coordinator crashes, the participant is stuck.
  • Once the coordinator decides to commit or abort after hearing from all participants, it cannot change its mind and must see it through
    • if a participant is down it keeps retrying until it succeeds.

Reputation: "mixed" (see "It's Time to Move on from Two Phase Commit": http://dbmsmusings.blogspot.com/2019/01/its-time-to-move-on-from-two-phase.html).

It is slow (multiple round trips); if the coordinator or a participant fails, all processes in the transaction block until it returns; and participants must implement the protocol: you cannot just take two different stores and expect them to cooperate.

  • You can make it resilient by replicating each process's state: e.g. replicate the coordinator with Raft to survive coordinator failures; participants can be replicated too.
  • Atomic commit is a form of consensus called uniform consensus:
    • all processes, even the faulty ones, must agree on a value, whereas general consensus (section 10.2) only needs the non-faulty ones to agree
    • So uniform consensus is harder (https://infoscience.epfl.ch/record/88273/files/CBS04.pdf?version=1), but general consensus can replicate each process's state to make the protocol robust.

12.4 NewSQL

History: the first large-scale data stores of the late 2000s were called NoSQL: focused entirely on scalability, lacking guarantees like ACID transactions. That has been changing as distributed stores add features only traditional databases had: NewSQL.

Google Spanner (https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf), arguably the most successful NewSQL store:

  • Data (key-value pairs) is split into partitions for scale; each partition is replicated across nodes in different data centres using state machine replication (Paxos).
  • In each replication group a leader handles a client write for that partition: it replicates across a majority, then applies
    • The leader is also the lock manager and implements 2PL to isolate transactions on that partition.
  • Transactions spanning partitions use 2PC.
    • The client initiates; one of the involved group leaders coordinates, the other group leaders are participants
    • The coordinator logs the transaction state in a local WAL replicated across its group, so if the coordinator crashes another node in the group is elected and resumes coordinating
    • Each participant logs its state in its own replicated log, so a failed participant is replaced the same way.
  • Isolation:
    • MVCC combined with 2PL: read-only transactions are lock-free and see a consistent snapshot
    • write transactions use 2PL to create new versions, guaranteeing strict serializability.
  • Timestamps
    • (needed for MVCC) are easy on one machine, hard when clocks are not synchronised
    • A central timestamp service would be a scalability bottleneck
    • So Spanner uses physical clocks that return an uncertainty interval [t_earliest, t_latest] that includes the measurement error, where t_earliest <= t_real <= t_latest: a node does not know the real time but knows (with very high probability) that it is within the interval.
  • When a transaction commits it gets t_latest of the interval from the coordinator's clock, but before committing and releasing locks it waits for the uncertainty period (t_latest - t_earliest)
    • That wait guarantees any transaction starting after it committed will see its changes
    • The challenge is a small interval: Spanner deploys GPS and atomic clocks in every data centre and syncs the nodes' quartz clocks to them frequently (uncertainty is generally less than 10 ms).
  • CockroachDB (https://www.cockroachlabs.com/), inspired by Spanner, instead uses hybrid logical clocks (a physical plus a logical timestamp; paper: https://cse.buffalo.edu/tech-reports/2014-04.pdf).
