Understanding Distributed Systems 13: Asynchronous transactions

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 13 (end of Part II). Previous: Understanding Distributed Systems 12: Transactions. Next: Understanding Distributed Systems 14 and 15: Part III intro, HTTP caching, CDNs (Part III, scalability).

[!abstract] The one-minute version 2PC is a synchronous, blocking protocol: if the coordinator or any participant is slow or down, the transaction stalls, and participants hold locks meanwhile. That is unacceptable for long-running transactions (hours or days) or across organisations that will not let others block them. Asynchronous transactions use persistent messages that are processed exactly once (a cashier's check, in the real world). They are atomic but not isolated. Two implementations: the outbox pattern (replicate data to another store) and sagas (multi-step workflows with compensating transactions).

Why 2PC does not fit

  • 2PC is usually combined with a blocking concurrency control protocol like 2PL, so participants hold locks while waiting for the coordinator, blocking other transactions on the same objects.
  • Its assumptions:
    • coordinator and participants are available, and the transaction is short-lived
    • Participant availability can be improved with state machine replication; you cannot fix transactions that take hours or days by nature
    • And participants in different organisations may not want to grant each other the power to block their systems for transactions they do not control.

Real-world model: fund transfer between banks via a cashier's check. The issuing bank deducts the funds, the check is physically carried to the other bank and deposited. For it to work the check cannot be lost or deposited twice.

Neither bank waited on the other, so it is an asynchronous (non-blocking) atomic transaction. The price: source and destination are inconsistent while the check is in transit, so such transactions are atomic but not isolated.

Generalise: a check is just a message. Use persistent messages sent over the network, guaranteed to be processed exactly once.

13.1 Outbox pattern

Scenario: a product catalogue service backed by a relational database wants advanced full-text search. Relational databases offer basic full-text search, but a dedicated service such as Elasticsearch (https://www.elastic.co/elasticsearch/) is needed for advanced cases.

A common modern pattern is to replicate the same data to different stores tailored to different use cases (https://queue.acm.org/detail.cfm?id=3321612).

  • On every add, change or delete the service must update both the database and the search service
    • Updating the DB then the search service and crashing in between leaves the system inconsistent
    • they need transactional treatment.
  • 2PC is a poor fit:
    • the database supports the X/Open XA 2PC standard (https://pubs.opengroup.org/onlinepubs/009680699/toc.pdf), but the search service does not
    • we would have to implement the protocol for it, and we do not want the catalogue service to block if search is briefly unavailable
      • Temporary inconsistency is acceptable: eventual consistency is enough.

Solution: send a persistent message to the search service whenever a product changes. One implementation:

  1. In the same local ACID transaction as the product change, append the message to a dedicated outbox table. Because the relational database is ACID, the message is appended if and only if the transaction commits (https://microservices.io/patterns/data/transactional-outbox.html).
  2. A dedicated relay process monitors the outbox table. On a new message it sends it to the destination (the search service) and deletes it only after receiving a delivery acknowledgement.
  3. Duplicates are possible: if the relay crashes after sending but before deleting, it resends on restart. To process exactly once, give each message an idempotency key so the destination de-duplicates (chapter 5.7).
  4. In practice the relay does not send directly to the destination: it forwards to a message channel such as Kafka (https://kafka.apache.org) or Azure Event Hubs (https://azure.microsoft.com/en-gb/services/event-hubs/) that delivers to one or more destinations in the order appended (chapter 23). Example open-source relay: Debezium (https://debezium.io/).
  5. Conceptually this is like state machine replication: the state is the catalogue's products, and replication runs through a log of operations (the outbox table).

13.2 Sagas

Scenario: a travel booking service must atomically book a flight through one service and a hotel through another. Either request can fail; if one succeeds and the other fails, the first must be cancelled. Booking a trip thus needs several steps, some only needed on failure, so the simple outbox solution does not suffice.

Saga ("Sagas": https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf): a distributed transaction composed of local transactions T1, T2, ..., Tn, where each Ti has a compensating local transaction Ci that undoes its changes. The saga guarantees either all local transactions succeed or, on failure, the compensating transactions undo the partial execution: atomicity.

Another view: each Ti assumes all the others will succeed: a likely but still a guess. When it is wrong, a mistake was made and an "apology" is issued in the form of compensations Ci, like an overbooked flight in the real world ("Building on Quicksand": https://dsf.berkeley.edu/cs286/papers/quicksand-cidr2009.pdf).

Implementation with an orchestrator (the transaction coordinator) that manages local transactions across the participants. Here the travel service is the coordinator; the flight and hotel services are participants. The saga has three local transactions: T1 books a flight, T2 books a hotel, C1 cancels the flight booked by T1. Workflow:

  1. The coordinator sends the booking request T1 to the flight service. If it fails, no harm: mark the transaction aborted.
  2. If T1 succeeds, send T2 to the hotel service. If it succeeds, the transaction is successful: done.
  3. If the hotel booking fails, the transaction must abort: the coordinator sends C1 to the flight service to cancel. Without it, the transaction stays inconsistent and atomicity breaks.
  • The coordinator can talk to participants asynchronously via message channels to tolerate temporary failures.
  • Because the transaction has several steps and the coordinator can fail at any time, it must persist the transaction's state as it advances: model it as a state machine and durably checkpoint the state on each transition
    • After a crash, or when another process is elected coordinator, it resumes from the last checkpoint (see "Clarifying the Saga pattern": http://web.archive.org/web/20161205130022/http://kellabyte.com:80/2012/05/30/clarifying-the-saga-pattern).
  • Caveat:
    • if the coordinator crashes after sending a request but before backing up its state, it resends on restart
    • a timed-out request is retried too. So participants must de-duplicate messages and be idempotent.
  • You need not build orchestration engines yourself: AWS Step Functions (https://aws.amazon.com/step-functions/) and Azure Durable Functions (https://docs.microsoft.com/en-us/azure/azure-functions/durable/) provide managed workflows.

13.3 Isolation

We left 2PC's blocking behind but sacrificed isolation.

It can be worked around, e.g. with semantic locks ("Semantic ACID properties in multidatabases...": https://dl.acm.org/doi/10.5555/284472.284478): any data the saga modifies is marked with a dirty flag, cleared only at the end of the transaction.

Another transaction that touches a dirty record can fail and roll back, or wait until the flag is cleared.

Part II summary (the author's)

Entire textbook chapters, even books, exist on these topics. You may never implement something like state machine replication from scratch, but seeing it once makes you a better "user" of the abstractions it provides. Two crucial insights:

  1. Failures are unavoidable in distributed systems. What makes coordination algorithms complex is that they must tolerate failures: imagine how much simpler Raft would be with a reliable network and processes that could not crash. Fault tolerance matters at every level, hence Part IV.
  2. Coordination is expensive: it adds complexity and hurts scalability and performance. Reduce it by:
    • keeping coordination off the critical path (as chain replication does);
    • proceeding without coordination and "apologising" when an inconsistency is detected (as sagas do);
    • using protocols that guarantee some form of consistency without coordination, like CRDTs.
