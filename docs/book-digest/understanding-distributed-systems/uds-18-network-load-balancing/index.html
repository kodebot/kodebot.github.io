Understanding Distributed Systems 18: Network load balancing

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 18. Previous: Understanding Distributed Systems 17: File storage. Next: Understanding Distributed Systems 19: Data storage.

[!abstract] The one-minute version With a single application server, Cruder will eventually fall over. Run several servers behind a load balancer: two servers should have twice the capacity (scaling out). This works because Cruder is stateless: state lives in the database and file store. A load balancer also raises availability (it drops faulty servers). It needs a routing algorithm, service discovery and health checks, and can run at the DNS, transport (L4) or application (L7) layer, or inside clients as a sidecar.

Why it works

  • Scaling a stateless application takes little effort, assuming its dependencies scale too
    • Scaling a stateful service (a data store) is much harder: it must replicate state, which needs coordination, adds complexity and can become a bottleneck (next chapter)
    • Rule of thumb: keep apps stateless by pushing state to third-party services built by teams with years of experience.
  • Benefits:
    • clients are decoupled from servers and need not know individual addresses, so servers can be added or removed transparently
    • redundant servers are interchangeable, so the balancer can detect faulty ones and remove them, raising availability.
  • Availability maths.
    • Availability is the percentage of time the system can serve requests, equivalently the probability a request succeeds. The app is unavailable only if all servers are down
    • with N servers the probability is the product of their failure rates
    • availability is 1 minus that (AWS Well-Architected, Availability: https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html).
    • Two servers at 99% each: 1 - (0.01 x 0.01) = 0.9999 = 99.99%. "The nines of independent servers sum up" (growing servers linearly grows availability exponentially).
    • Only theoretical:
      • the balancer does not remove faulty servers immediately, and the formula assumes independent failures
      • When a faulty server leaves the pool, the survivors may not sustain the extra load and degrade.

Load balancing algorithms

  • Routing can be round-robin, consistent hashing, or based on server load.
  • Balancing by load is harder than it looks.
    • The balancer might sample a load endpoint (e.g. CPU usage) on each server, caching answers because constant querying is costly
    • Delayed metrics cause surprises: a server that just joined reports load 0 and is hammered until the next sample, then reports overloaded and gets nothing: it alternates between very busy and idle.
  • Randomly distributing requests without looking at load balances better than that
    • Combine load with randomness: pick two servers at random and send the request to the less loaded one: "the power of two random choices" (https://brooker.co.za/blog/2012/01/17/two-random.html), which "works remarkably well in practice".

Service discovery

How the balancer learns its pool. Naive: a static config file of IPs, painful to keep current.

Better: a fault-tolerant coordination service (etcd, ZooKeeper) holds the list: a new server registers with a TTL; when it unregisters or the TTL expires (it stopped renewing) it leaves the pool.

Dynamic pools are the basis of cloud autoscaling (spin servers up and down by load: https://docs.microsoft.com/en-us/azure/architecture/best-practices/auto-scaling).

Health checks

Detect when a server can no longer serve and must leave the pool. (Reference: https://aws.amazon.com/builders-library/implementing-health-checks/)

  • Passive: the balancer observes real traffic: unreachable server, timeout, or a non-retriable status such as 503, then it removes the server.
  • Active:
    • servers expose a health endpoint polled periodically: 200 OK if they can serve, 5xx if overloaded
    • a timeout also counts as an error
      • The handler can simply return 200 (a degraded server will mostly time out) or compare local metrics (CPU, free memory, concurrent requests) with thresholds.
  • "Here be dragons":
    • a misconfigured threshold or a bug can make all servers fail the check
    • a naive balancer would empty the pool and take the app down
      • A "smart enough" one notices that a large fraction is unhealthy, treats the checks as unreliable and ignores them, sending requests to any server.
  • Zero-downtime updates:
    • during a rollout a rolling subset reports unavailable so the balancer stops sending them requests
    • in-flight requests finish (drain) before the servers restart on the new version. Same mechanism lets you restart any server harmlessly.
  • Watchdog for gray failures:
    • e.g. a rare memory leak shrinks free memory, the server swaps heavily and degrades
    • eventually most servers suffer. Rather than build complex recovery, a background watchdog thread monitors a metric (available physical memory)
    • when it breaches a threshold for some time, the server deliberately crashes or restarts
      • That lets the system self-heal and buys operators time to find the cause
      • The watchdog must be well tested and monitored (a bug could cause endless restarts), but the author finds it "uncanny how this simple pattern can make an application a lot more robust to gray failures".

18.1 DNS load balancing

Put the servers' public IPs in the app's DNS record and let clients pick one (round-robin DNS: https://en.wikipedia.org/wiki/Round-robin_DNS).

Not resilient: a dead server's IP keeps being served, and even reconfiguring the record takes time to reach clients because DNS entries are cached (chapter 4). The practical use: distributing traffic between data centres in different regions (global DNS load balancing, as for CDNs).

18.2 Transport layer (L4) load balancing

Operates at the TCP level (layer 4 of the OSI model); all client-server traffic flows through it.

  • A network load balancer has network cards mapped to one or more virtual IP (VIP) addresses; each VIP maps to a server pool. Clients see only the VIP.
  • On a new TCP connection to the VIP the balancer picks a server and shuffles packets for that connection both ways
    • Because all traffic passes through it, it can detect unavailable servers (e.g. passive checks) and remove them.
  • A connection is identified by the tuple (source IP/port, destination IP/port)
    • a hash (e.g. consistent hashing) assigns tuples to servers with minimal disruption when the pool changes (talk: https://www.youtube.com/watch?v=woaGu3kJ-xk).
  • It translates addresses (NAT:
    • https://en.wikipedia.org/wiki/Network_address_translation): outbound, the packet's source becomes the balancer's address and destination the server's
    • replies are translated back toward the client.
  • Responses are usually bigger than requests, so servers can bypass the balancer with direct server return (https://blog.envoyproxy.io/introduction-to-modern-network-load-balancing-and-proxying-a57f6ff80236), greatly reducing its load.
  • Built from commodity machines, scaled out with Anycast (https://en.wikipedia.org/wiki/Anycast) and ECMP (https://en.wikipedia.org/wiki/Equal-cost_multi-path_routing): instances announce the same Anycast VIP with identical BGP weight to the edge routers
    • with equal weights, routers use equal-cost multi-path routing (consistent hashing) so a connection's packets generally reach the same instance.
  • Managed options: AWS Network Load Balancer (https://aws.amazon.com/elasticloadbalancing/network-load-balancer/), Azure Load Balancer (https://azure.microsoft.com/en-us/services/load-balancer/).
  • Limit: fast, but it just moves bytes without knowing what they mean, so it does not support features needing higher protocols like terminating TLS.

18.3 Application layer (L7) load balancing

An HTTP reverse proxy (layer 7) that distributes requests over a pool: it receives an HTTP request, inspects it, forwards it to a backend. Two TCP connections exist: client to balancer, balancer to server.

  • It can de-multiplex individual HTTP requests sharing one TCP connection, important with HTTP/2, where many concurrent streams share a connection and some connections cost much more than others.
  • It can rate-limit by HTTP headers, terminate TLS, and keep requests of one logical session on one server (sticky sessions): e.g
    • identify the session by cookie and map it to a server with consistent hashing, so servers cache session data in memory
    • Caveat: sticky sessions can create hotspots (sessions differ in cost).
  • L7 behind L4: L7 balancers have more features but lower throughput, so L4 balancers are better against certain DDoS attacks like SYN floods (an attacker rapidly opens TCP connections without finishing them).
  • A dedicated balancer is a single point of dependency:
    • if it goes down, so does the app
    • When clients are internal, delegate balancing to them with the sidecar pattern: all a client's traffic goes through a co-located proxy process (the sidecar) that acts as an L7 balancer, and can also rate-limit, authenticate and monitor
    • This is the service mesh (https://blog.envoyproxy.io/service-mesh-data-plane-vs-control-plane-2774e720f7fc), popular with microservices among hundreds of services
      • common sidecars: NGINX, HAProxy, Envoy.
  • Pros:
    • no dedicated balancer to scale and maintain
    • Cons: much more complexity: you need a control plane to manage all the sidecars (see "Service Mesh Wars, Goodbye Istio": https://blog.polymatic.systems/service-mesh-wars-goodbye-istio-b047d9e533c7).
