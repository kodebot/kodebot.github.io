Understanding Distributed Systems 20: Caching

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 20. Previous: Understanding Distributed Systems 19: Data storage. Next: Understanding Distributed Systems 21: Microservices.

[!abstract] The one-minute version If a big share of requests to the data store hits a small pool of frequently accessed entries, put a cache in front. A cache is a high-speed layer that temporarily buffers responses from an origin; its state is disposable (rebuildable from the origin), so it gives only best-effort guarantees. It pays off only with a high hit ratio. It is an optimisation: if the origin cannot survive without it, you do not have a scalable architecture.

  • Hit ratio (share of requests served from the cache) depends on: the universe of cachable objects (fewer is better), the likelihood of repeated access (higher is better), and the cache size (larger is better).
  • Rule of thumb: the higher up the call stack you cache, the more downstream resources you save (why client-side HTTP caching came first).
  • Caching is an optimisation: if the access pattern suddenly changes (misses) or the cache is unavailable, the app must not fall over; becoming slower is okay.

20.1 Policies

On a miss the object comes from the origin in one of two ways:

  • Side cache: after an "object-not-found" from the cache, the application requests it from the origin and updates the cache. The app treats the cache as a key-value store.
  • Inline cache: the cache talks to the origin on the app's behalf; the app only ever touches the cache (HTTP caching is an example).

Eviction policy: a limited-capacity cache must evict entries to make room; which one depends on the policy and access pattern, e.g. least recently used (LRU).

Expiration policy: e.g. a TTL; an object older than its TTL expires and can be evicted. Longer expiry = higher hit ratio but more chance of stale, inconsistent data. Expiry can be deferred to the next request, which is better: if the origin is temporarily down, returning an expired object beats returning an error.

A TTL is a workaround for cache invalidation, "very hard to implement in practice" (https://en.wikipedia.org/wiki/Cache_coherence): if you cache a database query result, any change to any of the possibly thousands of records it touched would have to invalidate it.

20.2 Local cache

The simplest cache is co-located with the client: an in-memory hash table or an embeddable key-value store like RocksDB (http://rocksdb.org/).

  • Each client cache is independent, so objects are duplicated: if every client has a 1 GB cache the total effective size is still 1 GB however many clients exist
    • Clients may see different versions of an object.
  • More clients mean more requests to the origin, worse when clients restart or new ones come online with empty caches: a thundering herd, a spike on the origin
    • The same happens when an unseen object suddenly becomes popular.
  • Mitigation: coalesce requests: at most one outstanding request per client per object.

20.3 External cache

A service dedicated to caching, typically in memory, shared across clients: Redis (https://redis.io/) or Memcached (https://memcached.org/), also managed on AWS and Azure. It fixes local-cache drawbacks at the cost of complexity and money.

  • Unlike a local cache it can scale throughput and size by replication and partitioning: Redis can automatically partition data across nodes and replicate each partition leader-follower (https://redis.io/topics/cluster-tutorial).
  • Shared, so there is a single version of each object (if not replicated), fewer consistency problems, and origin requests do not grow with the number of clients.
  • But
    • the load just shifts to the cache, which must be scaled out eventually
    • When rebalancing, move or drop as little data as possible (hit ratio must not collapse): consistent hashing or similar helps.
  • Costs: another service to operate; higher latency than a local cache (a network call).
  • If the external cache is down?
    • Bypassing it and hitting the origin seems fine, but the origin may not withstand a sudden surge: the outage can cascade and take the origin down too
    • Defence: an in-process cache in front of the external one, and an origin prepared to shed requests (see the resiliency part)
    • Remember: the system must survive without the cache, only slower.
