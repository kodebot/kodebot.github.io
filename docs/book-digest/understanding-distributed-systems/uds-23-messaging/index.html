Understanding Distributed Systems 23: Messaging

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 23 (end of Part III). Previous: Understanding Distributed Systems 22: Control planes and data planes. Next: Understanding Distributed Systems 24: Part IV intro and common failure causes (Part IV, resiliency).

Takeaways
  • A message channel (broker) decouples a producer from a consumer: the consumer can be down, load spikes are smoothed, consumers scale out behind it.
  • There is no exactly-once delivery. Get exactly-once processing with at-least-once delivery + idempotent messages + delete after processing.
  • Cap retries and park failures in a dead letter channel. Watch for backlogs (bimodal behaviour) and isolate poisonous sources.
  • Part III summary: scale with functional decomposition, partitioning, replication, using a few managed services.

Why a channel

Cruder lets users upload a video and encode it in many formats. The gateway uploads to a file store (S3) and asks an encoding service to process it. Encoding takes minutes, so the gateway should not wait; but fire-and-forget loses the request if the encoder instance crashes.

Messaging (introduced in chapter 5) is indirect communication: a producer writes a message to a channel (message broker), which delivers it to a consumer. The channel is a temporary buffer; sending does not need the receiver online (asynchronous).

A message has a header (metadata such as a unique ID) and a body. It is a command (an operation for the receiver to invoke) or an event (something of interest happened).

Services use inbound adapters (consumers, part of the API surface) and outbound adapters to talk to channels.

In the example the gateway writes a message with a link to the uploaded file and replies 202 Accepted (accepted, not completed). The message is deleted from the channel only after successful processing, so a failed one is retried.

Benefits:

  • producer can send while the consumer is temporarily unavailable;
  • requests are load-balanced across consumer instances (easy scale-out);
  • the consumer reads at its own pace, so the channel smooths load spikes;
  • batching: fetch up to N messages per read; worse per-message latency, dramatically better throughput ("a no brainer" when latency allows).

Costs: the broker is yet another service to run, and the extra hop adds latency, more with a large backlog. Always a trade-off.

Channel types: point-to-point (each message to exactly one consumer instance) vs publish-subscribe (each instance gets a copy).

Messaging styles

  • One-way: producer writes to a point-to-point channel expecting a consumer to process it eventually (the video example).
  • Request-response:
    • like direct request-response but both messages flow through channels. The consumer has a point-to-point request channel
    • each producer has its own response channel. The producer tags a request with a request ID and a reference to its response channel
    • the consumer replies there with the same request ID.
  • Broadcast: producer writes to a publish-subscribe channel to notify all consumers of an event (e.g. the outbox pattern, section 13.1).

23.1 Guarantees

Brokers (AWS SQS https://aws.amazon.com/sqs/, Kafka) make different trade-offs. Surprise: some, like SQS standard queues (https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html), give no strong ordering.

Why: a broker must scale horizontally, so it is distributed, and ordering across nodes needs coordination.

Kafka partitions a channel into sub-channels by partition key; each partition fits one broker process so ordering within it is trivial, and only one consumer may read a given sub-channel to preserve order end to end (the competing consumer pattern, implemented with leader election).

All of chapter 16's caveats apply: a hot partition may outpace its consumer, forcing rebalancing by adding partitions, which can degrade the broker while messages shuffle.

Other broker trade-offs: delivery guarantees (at-most-once, at-least-once), durability, latency, standards (AMQP: https://en.wikipedia.org/wiki/Advanced_Message_Queuing_Protocol), competing consumers, limits such as maximum message size.

Assumptions used below (like SQS and Azure Queue Storage, https://azure.microsoft.com/en-us/services/storage/queues/):

  • channels are point-to-point with many producers and consumers;
  • delivery is at least once;
  • while an instance processes a message it stays in the channel but is hidden from others for a visibility timeout
    • if the instance crashes, the timeout expires and another instance sees it
    • on success the consumer deletes it.

23.2 Exactly-once processing

  • Delete before processing: a crash after deleting loses the message for good.
  • Delete after processing: a crash after processing but before deleting means the message is read again.
  • Hence there is no exactly-once message delivery (https://bravenewgeek.com/you-cannot-have-exactly-once-delivery-redux/)
    • Best a consumer can do: simulate exactly-once processing by requiring idempotent messages and deleting only after processing.

23.3 Failures

If processing a message always fails, the visibility timeout keeps redelivering it forever. So limit the number of reads: the broker stamps a delivery counter (or the consumer implements it).

At the maximum, do not delete without processing (data loss); instead move it to a dead letter channel, which parks messages retried too often. They no longer pollute the main channel; a human inspects them, fixes the cause, and moves them back for reprocessing.

23.4 Backlogs

A broker makes the system robust to outages: producers keep writing while the consumer is degraded. As long as arrival rate <= deletion rate all is well; otherwise a backlog builds, giving bimodal behaviour (normal mode vs degraded mode); the longer it grows, the more time or resources to drain. Causes:

  • more producers or higher throughput than the consumer can handle;
  • consumer degradation (slower processing, lower deletion rate);
  • the consumer fails a fraction of messages, which are re-picked until they reach the dead letter channel, wasting resources and delaying healthy messages.

Detect by measuring the average time a message waits before first being read: the broker timestamps the write and the consumer compares it with the read time. Different physical clocks (section 8.1) make it imprecise but a good early warning.

23.5 Fault isolation

A single producer emitting poisonous messages (fail repeatedly) degrades the consumer and can create a backlog, since each is processed several times before the dead letter channel.

If messages carry a source identifier, the consumer can treat them differently: e.g. move a failing user's messages to a low-priority channel (read less often) without processing them on the main channel, isolating the damage one bad user can do.

Part III summary (the author's)

  • Scalability rests on three orthogonal patterns: functional decomposition (separate services with well-defined responsibilities), partitioning, replication.
  • A small set of managed services builds a surprisingly large range of apps
    • the attraction is that someone else gets paged (Part V: maintaining a service is no small feat). Know how to: run instances in the cloud (EC2) and load-balance them (ELB)
    • keep apps stateless with a file store (S3), a key-value/document store (DynamoDB) and a messaging service (SQS, Kinesis). These are reasonable defaults
    • once you have a scalable core, add caching (managed Redis/Memcached) or CDNs.
