Understanding Distributed Systems 28: Upstream resiliency (and Part V intro)

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 28 and the Part V introduction. Previous: Understanding Distributed Systems 27: Downstream resiliency. Next: Understanding Distributed Systems 29: Testing.

Takeaways

  • Load shedding: reject excess requests with 503 based on local state.
  • Load leveling: put a message channel in front; the service consumes at its own pace.
  • Rate limiting: reject over-quota requests with 429, based on global state, per user, API key or IP.
  • Constant work: do the same amount of work under any load; worst case equals average case.
  • None of these add capacity; combine with autoscaling (https://en.wikipedia.org/wiki/Autoscaling).

28.1 Load shedding

A server cannot control how many requests arrive. The OS keeps a per-port connection queue that rejects new connections once full, but typically under extreme load the server crawls to a halt first (out of memory, threads, sockets or files), response times climb and it becomes unavailable.

  • At capacity it should reject excess requests so resources go to the ones already in progress (https://aws.amazon.com/builders-library/using-load-shedding-to-avoid-overload).
  • Implementation: a counter of concurrent requests (increment on arrival, decrement on response) compared with a threshold approximating capacity.
  • On overload, fail fast with 503 Service Unavailable.
  • Which to reject: not necessarily arbitrary ones. Reject only low-priority requests, or the oldest first (they will time out and be retried soon, so handling them is a waste).
  • Limit:
    • rejection is not free (the server may still pay for opening a TLS connection and reading the request)
    • If load keeps growing, the cost of rejecting eventually degrades the server.

28.2 Load leveling

When clients do not expect a prompt response, put a messaging channel between clients and service. It decouples load from capacity so the service works at its own pace and smooths short-lived spikes. If the service never catches up, a large backlog builds (chapter 23).

  • Shedding and leveling protect a service
    • they do not handle more load. To do that, scale out, hence the combination with autoscaling that detects a hot service and adds capacity.

28.3 Rate limiting (throttling)

Reject a request when a quota is exceeded. A service can have several quotas (requests or bytes per interval), typically per user, API key or IP.

  • Example: quota 10 requests/s per API key; a key averaging 12/s gets about 2/s rejected.
  • Return a distinct error so the sender knows it is a quota: HTTP 429 Too Many Requests, with details on which quota was exhausted and by how much, and optionally a Retry-After header saying how long to wait.
  • Benefits:
    • stops non-malicious users monopolising the service by mistake
    • guards against client bugs that repeatedly hit a service
    • enforces pricing tiers (more use, more pay, so costs are offloaded to users).
  • DDoS:
    • only partial protection
    • Throttled clients can keep hammering after a 429, and rate-limiting is not free (to limit by API key you must open a TLS connection and read part of the request)
    • It reduces impact only
    • Economies of scale are the only true protection: many services behind one large gateway that rejects traffic upstream, its cost amortised across them.
  • vs load shedding:
    • shedding uses a process's local state (its concurrent requests)
    • rate limiting uses global state (e.g. requests for an API key across all instances), so it needs coordination.

28.3.1 Single-process implementation

Quota example: 2 requests per minute per API key.

  • Naive:
    • a doubly-linked list per key of the last N request timestamps
    • append on arrival, periodically purge entries older than a minute, compare list length with the quota. Memory grows with the number of requests per key.
  • Bucketing: divide time into fixed buckets (e.g. 1 minute), each a counter; a request at 12:00:18 increments bucket "12:00". Storage no longer grows with request count.
  • Sliding window:
    • window length = the quota's time unit (1 minute)
    • It can overlap several buckets, so the count is a weighted sum of the bucket counters, each weighted by its overlap with the window
    • An approximation, improved with finer buckets (30 s rather than 1 min).
  • Store only buckets the window can overlap: with 1-minute window and buckets, at most 2. So two counters per API key, far less than a list per key.

28.3.2 Distributed implementation

With many processes, the quota applies to the total across instances, so a shared data store holds the counters (two integers per key).

  • Fetch-update-write per request loses updates if two processes race, so it would need a transaction: correct but slow and expensive (data store must scale linearly with requests) and the store becomes a hard dependency.
  • Better: a single atomic get-and-increment (most stores offer it) or emulate with compare-and-swap: much faster than transactions.
  • Better still: batch bucket updates in memory and flush asynchronously to the store: less accurate shared state, but far fewer requests to the store.
  • If the store is down
    • (CAP essence: sacrifice consistency or availability): rejecting requests just because rate-limiting state is unreachable could harm the business, so keep serving based on the last state read
    • This is static stability (chapter 22).

28.4 Constant work

When overload, config changes or faults make an app behave differently it is multi-modal: modes may trigger rare bugs, clash with happy-path assumptions, and invalidate operators' mental model. Rule of thumb: minimise the number of modes.

  • Example:
    • data planes prefer simple key-value stores over relational databases for predictable performance: a relational DB has hidden optimisations so the same query may perform differently from run to run (https://blog.nelhage.com/post/some-opinionated-sql-takes/)
    • a dumb KV store behaves predictably.
  • Overload makes systems slower exactly when worst
    • Ideal:
      • worst case equals average case: the constant work pattern (https://aws.amazon.com/builders-library/reliability-and-constant-work/): the same work under high load as under average load
      • any variation under stress should be the system performing better
    • Such a system is antifragile, which differs from resilient (keeps operating under extreme load, while antifragile does better).
  • Application (chapter 22):
    • a config store (control plane) holds per-user settings such as the gateway's rate-limit quotas
    • Sending each change separately makes data-plane work proportional to the number of changes
    • If many settings change at once (a business decision changes quotas), every data-plane instance gets a flood of update messages.
  • Fix:
    • the control plane periodically dumps all users' settings (changed or not) to a file store (Azure Storage, S3)
    • data plane instances periodically read the dump in bulk. Work is constant however many settings change.
  • Extreme form:
    • pre-allocate empty config slots for the maximum number of users, so work stays stable as users grow and you can stress-test the real behaviour
    • It caps users, but a limit exists anyway
    • Typical of cellular architectures (26.2): fixed maximum cell size, scale out by adding cells.
  • Benefits:
    • reliable and predictable updates
    • far simpler to implement than a delta-only mechanism
    • self-healing: a corrupted dump is fixed by the next one, a faulty update is reverted by creating a new dump and waiting, whereas individual updates need complex data-plane logic to heal.
  • Cost: constant work is more expensive than the necessary work, but often worth it for reliability and simplicity.

Part IV summary

  • More components or operations means more failures; eventually anything that can happen will ("cruel math", the author's team's joke).
  • Production engineers worry more about tolerating failures than scaling further: once the architecture handles current load, faults are the main concern until the next scalability bottleneck.
  • Failures are inevitable; when you cannot design a failure mode away (e.g. with constant work), reduce the blast radius and stop cracks propagating between components.

Part V: Maintainability (introduction)

"Everyone knows that debugging is twice as hard as writing a program in the first place. So if you're as clever as you can be when you write it, how will you ever debug it?" (Brian Kernighan)

  • Most of software's cost is after initial development (fixing bugs, adding features, operating), so make systems easy to modify, extend and operate.
  • Testing
    • (unit, integration, end-to-end) is the minimum to change a system without fear
    • Then changes must be released safely without hurting availability
    • Operators must monitor health, investigate degradations and restore service, which requires changing behaviour without code changes (feature flags, scaling by config).
  • Historically
    • developers, testers (QA) and operators were separate teams handing work over
    • being phased out. Now developers commonly test and operate what they write, needing an end-to-end view of the lifecycle.
  • Roadmap:
    • ch. 29 testing (unit, integration, end-to-end, formal verification)
    • ch. 30 continuous delivery and deployment
    • ch. 31 monitoring (metrics, SLIs, dashboards, SLOs)
    • ch. 32 observability (logs, traces)
    • ch. 33 manageability (change behaviour without code).
