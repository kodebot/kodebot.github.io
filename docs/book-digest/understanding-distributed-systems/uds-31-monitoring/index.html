Understanding Distributed Systems 31: Monitoring

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 31. Previous: Understanding Distributed Systems 30: Continuous delivery and deployment. Next: Understanding Distributed Systems 32-34: Observability, manageability, final words.

Takeaways
  • Monitoring detects user-impacting failures, alerts humans and gives dashboards. Black-box shows symptoms; white-box finds root causes.
  • Metrics are time series, pre-aggregated to be cheap. SLIs (good events / total events) quantify service level; SLOs set the acceptable range; the leftover is the error budget.
  • Alert on SLO burn rate, not raw CPU. Use percentiles, not averages.
  • Healthy on-call: actionable alerts, mitigate first, postmortem later.

Black-box vs white-box

Early monitoring only said whether a service was up (black-box). Later developers instrumented apps to report whether features worked (white-box), popularised by Etsy's statsd (https://codeascraft.com/2011/02/15/measure-anything-measure-everything/). Black-box finds symptoms; white-box helps find the root cause.

  • Black-box main use:
    • monitor external dependencies (third-party APIs) and how users perceive the service from outside, via synthetics: scripts that periodically send test requests to the public endpoints from the same regions as users, timing them and checking success (https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Synthetics_Canaries.html)
    • They catch connectivity issues and problems in rarely used APIs.
  • Example: if a service's DNS server is down, synthetics cannot resolve the IP, yet the service itself thinks all is fine and just receives fewer requests.

31.1 Metrics

A metric is a time series of samples (a float and a timestamp) of resource usage (CPU) or behaviour (failed requests). Often tagged with labels (key-value pairs: region, data centre, cluster, node), so you can slice and dice without creating a metric per combination; but each distinct label combination is a separate metric, so tagging yields huge numbers of metrics to store and process.

  • A service should at least emit:
    • load (request throughput)
    • internal state (in-memory cache size)
    • dependencies' availability and performance (data store response time). This needs explicit code and deliberate effort.
  • Example handler (get_resource(id): check in-process cache, else repository, then store) raises many questions: valid id? cache hit? age of the cached entry? did the remote call fail or time out and how long did it take? cache size? total handler time?

Event-based approach: on failure the handler sends an event (e.g. {"failureCount": 1, "serviceRegion": "EastUs2", "timestamp": 1614438079}) to a local telemetry agent, which batches and emits to a remote telemetry service persisting event logs (e.g. Azure Monitor log-based metrics: https://docs.microsoft.com/en-us/azure/azure-monitor/app/pre-aggregated-metrics-log-metrics#log-based-metrics).

Expensive: telemetry load grows with events, and aggregating at query time (failures in North Europe over a month) may mean fetching and aggregating trillions of events.

Pre-aggregation: since metrics are time series, pre-aggregate samples over fixed periods (1 min, 5 min, 1 h) as sum, average or percentiles.

  • At ingestion with a 1-hour sum you get one failureCount per serviceRegion with one sample per hour (00:00 -> 561, 01:00 -> 42, 02:00 -> 61).
  • Create multiple pre-aggregates with different periods and pick the best at query time (CloudWatch pre-aggregates on ingestion: https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch_concepts.html).
  • Further:
    • client-side pre-aggregation in the agent cuts bandwidth, compute and storage
    • Cost: you cannot re-aggregate after ingestion (an hourly metric cannot later become 5-minute) without the original events.
  • Metrics are mainly for alerting and visualisation, so they are stored pre-aggregated in a time-series store (e.g. Druid: http://static.druid.io/docs/druid.pdf).

31.2 Service-level indicators (SLIs)

Not every metric deserves an alert (no 3 a.m. page for a memory spike minutes ago). An SLI is a metric measuring one aspect of the level of service users get (response time, error rate, throughput), typically aggregated over a rolling window with a summary statistic (average or percentile).

  • Best defined as a ratio of good events over total events: 0 = completely broken, 1 = working as expected; this also simplifies alert configuration.
  • Common SLIs: response time (fraction of requests faster than a threshold); availability (successful requests over total).
  • Where to measure:
    • service, load balancer or client? Pick what best represents user experience
    • the client is most meaningful since it includes delays across the whole request path.
  • How to measure:
    • response times follow a right-skewed, long-tailed distribution (https://igor.io/latency/), affected by network delays, page faults, context switching
    • The average hides this: 99 requests at 1 s and one at 10 minutes give an average of nearly 7 s although 99% took 1 s.
  • Percentiles
    • are better: the 99th percentile of 1 s means 99% of requests took at most 1 s. The upper ones (99th, 99.9th) are long-tail latencies
    • they hit the most important users (those making the most requests have the most chances to see them).
  • Revenue: Akamai study, a 100 ms delay in load time can cut conversion by 7% (https://www.akamai.com/newsroom/press-release/akamai-releases-spring-2017-state-of-online-retail-performance-report).
  • Capacity impact via Little's Law
    • (average items in system = arrival rate x average time in system; https://robertovitillo.com/back-of-the-envelope-estimation-hacks/): a service using ~2K threads for 10K req/s has a 200 ms average per request
    • If 1% of requests suddenly take 20 s (congested switch, relaxed timeouts), another 2K threads are needed: thread count must double.
  • Keeping tail latency in check improves resiliency and cuts operational cost, and improving the worst case also improves the average.

31.3 Service-level objectives (SLOs)

An SLO defines the range of acceptable values for an SLI at which the service is healthy; it sets users' expectations. A service-level agreement (SLA) is a contract on what happens when an SLO is missed, usually financial.

  • Example: 99% of calls to endpoint X complete under 200 ms, over a rolling 1 week. Equivalently up to 1% may be slower: the error budget (failures that can be tolerated).
  • Uses:
    • alerting, and prioritising repair work: e.g
    • when the budget is exhausted, repairs beat new features until the SLO is restored
    • An incident's importance = fraction of budget burned (20% matters more than 1%).
  • Window size: short windows force quick action on fixes; long windows suit long-term investment decisions: have several SLOs with different windows.
  • How strict:
    • too lenient misses user pain
    • too strict wastes effort on micro-optimisation with diminishing returns
      • 100% is impossible, and even then users' last-mile connection is outside your control
      • Start comfortable and tighten as confidence grows
    • do not just pick today's achievable numbers
    • work backward from what users care about. Above 3 nines is very costly with diminishing returns.
  • Keep as few SLOs as possible and review them: if a user-facing issue generated many support tickets but no SLO moved, SLOs are too relaxed or miss that use case.
  • Agree SLOs with stakeholders:
    • engineers (achievable without excessive toil) and product managers (guarantee good UX)
    • From Google's SRE book: "if you can't ever win a conversation about priorities by quoting a particular SLO, it's probably not worth having that SLO" (https://sre.google/sre-book/service-level-objectives/).
  • Over-reliance:
    • users may depend on actual behaviour rather than the documented SLA
    • Periodic controlled failures in production (chaos testing) (https://en.wikipedia.org/wiki/Chaos_engineering) show dependencies cope with the target service level, and validate resiliency mechanisms.

31.4 Alerts

Alerting triggers an action when a condition occurs (e.g. a metric crosses a threshold): from automation (restart an instance) to ringing an on-call human.

  • It must be actionable:
    • no digging in dashboards to judge impact or urgency. A CPU spike alert is not (impact unclear)
    • an SLO is a good candidate as it quantifies user impact
    • alert when a large fraction of the error budget is consumed.
  • Precision vs recall:
    • precision = significant events (real issues) / total alerts
    • recall = fraction of significant events that triggered an alert. Low precision = noisy, not actionable
    • low recall = misses outages. Improving one usually lowers the other.
  • Naive example:
    • availability SLO 99% over 30 days; alert if availability falls below 99% within 1 hour
    • Budget spent when it fires = 1 hour / 30 days = 0.14%
    • Systems are never 100% healthy, so that is not useful: high recall, low precision.
  • Raising the required duration improves precision but delays detection in a real outage
    • Better: alert on burn rate = % of error budget consumed / % of SLO window elapsed: burn rate 1 exhausts the budget in exactly 30 days
    • 2 in 15
    • 3 in 10.
  • Improve recall
    • with multiple alerts at different thresholds: burn rate below 2 = low-severity, check in working hours
    • above 10 = automated call to an engineer. See the SRE workbook (https://sre.google/workbook/alerting-on-slos/).
  • Most alerts should be SLO-based, but some target known failure modes not yet fixed: e.g
    • a known memory leak, temporarily mitigated by an alert that triggers an automated restart when an instance runs out of memory.

31.5 Dashboards

Metrics also power real-time dashboards; they easily become a dumping ground of forgotten, confusing charts. First pick the audience and what they look for, then work backward to charts and metrics (https://aws.amazon.com/builders-library/building-dashboards-for-operational-visibility).

Dashboard Audience and purpose Content
SLO stakeholders across the org; during incidents quantifies user impact the SLOs
Public API operators; finds problematic paths during an incident per endpoint: requests received or messages pulled, request size, auth issues; handling duration, dependencies' availability and response time; counts per response type, response size
Service the owning team; first entry point when debugging, needs deep internals knowledge service-specific metrics plus upstream (load balancers, queues) and downstream (data stores) dependencies; operators then drill down by segmenting, then raw logs and traces

31.5.1 Best practices

  • Define dashboards and charts in a domain-specific language and version-control them like code, so they update in the same PR as the code and stay in sync across environments (pre-prod and prod)
    • manual updates are error-prone.
  • Most important charts at the top (dashboards render top to bottom). Use a default timezone like UTC so people in different places talk about the same data.
  • Same time resolution and range
    • across a dashboard to correlate anomalies: 1-hour range, 1-minute resolution for an ongoing incident
    • 1-year range, 1-day resolution for capacity planning.
  • Few data points and metrics per chart
    • (slow to render, hard to read). Only metrics with similar ranges share a chart, or the largest hides the rest: put 10th percentile, average and 90th percentile in one chart
    • 0.1th, 99.9th percentile, min and max in another.
  • Annotate
    • charts: a description with links to runbooks, related dashboards, escalation contacts
    • a horizontal line per alert threshold
    • a vertical line per relevant deployment.
  • A metric emitted only on error leaves gaps and raises doubt whether the service stopped emitting. Emit 0 when no error and 1 when there is one.

31.6 Being on call

A healthy rotation needs services built for reliability and operability from the start. Making developers operate what they build gives them the incentive to cut operational toil and puts the people who know the architecture and its limits on call.

  • On call is stressful (even without call-outs, the loss of freedom causes anxiety), so it should be compensated and the engineer should not be expected to progress feature work
    • they are interrupted anyway, so give them free rein to improve the on-call experience (revise dashboards, improve resiliency).
  • Alerts must be actionable:
    • link to dashboards and a runbook of actions (automate what you can: "machines are good at following instructions")
    • Unless it was a false positive, communicate every action in a shared channel (global chat), so others can chime in, track progress and hand over easily.
  • Mitigate first, fix root cause later. Bad release? Roll back. Cannot cope with unchanged load? Scale out.
  • Then find the root cause and prevent recurrence, spending more time the greater the SLO impact
    • Incidents burning a significant fraction of the error budget need a formal postmortem with repair items
    • Ideally the team agrees that if the error budget is burned or alerts spiral, everyone stops feature work until a healthy rotation is restored
    • See the SRE books (https://sre.google/books/).
