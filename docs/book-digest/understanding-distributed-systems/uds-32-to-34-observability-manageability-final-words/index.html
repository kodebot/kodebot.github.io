Understanding Distributed Systems 32-34: Observability, manageability, final words

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 32, 33, 34. Previous: Understanding Distributed Systems 31: Monitoring.

Takeaways
  • Observability = tools giving granular insight into production to understand emergent behaviour and validate hypotheses fast. A superset of monitoring: monitoring spots symptoms, observability explains causes.
  • Telemetry: metrics (monitoring; high throughput, low dimensionality), event logs and traces (debugging; high dimensionality, lower throughput). Metrics and traces are derived views of event logs.
  • Manageability: change behaviour without code changes: externalised, dynamically reloaded configuration and feature toggles.

Ch. 32 Observability

A distributed system is never 100% healthy: something is always failing. Relaxed consistency and resiliency mechanisms (rate limiting, retries, circuit breakers) tolerate many failures but add complexity, making emergent behaviours harder to predict.

  • Humans still debug root causes:
    • form a hypothesis and validate it
    • Example: response-time variance has crept up for weeks; correlated with rising traffic, the operator hypothesises the service nears a resource limit
    • Metrics and charts alone cannot validate this.
  • A good platform minimises time to validate hypotheses, which needs granular events with rich context because you cannot know in advance what will be useful.
  • Stores:
    • metrics go to time-series stores with high throughput but poor high-dimensionality
    • event logs and traces go to stores handling high-dimensional data (e.g. Azure Data Explorer: https://azure.microsoft.com/mediahandler/files/resourcefiles/azure-data-explorer/Azure_Data_Explorer_white_paper.pdf) but poor high throughput.

32.1 Logs

A log is an immutable list of time-stamped events. Format: free-form text, or structured (JSON, or binary like Protobuf) as a bag of key-value pairs, e.g. {"failureCount": 1, "serviceRegion": "EastUs2", "timestamp": 1614438079}.

Sources: your services and dependencies (brokers, proxies, data stores). Typically written to disk files, shipped asynchronously by an agent to a log collector (ELK stack: https://www.elastic.co/what-is/elk-stack, or AWS CloudWatch logs).

  • Strengths:
    • a wealth of detail if instrumented
    • great for tracing a symptom back to a root cause (an instance crash) and for long-tail behaviour invisible in averages and percentiles (why a specific request failed).
  • Weaknesses:
    • easy to emit (that is the only advantage)
    • Overhead if misused, especially blocking, non-async writes
    • A full disk loses logs at best and at worst breaks the instance
    • Expensive to ingest, process and store, even binary structured logs (high dimensionality)
    • Low signal-to-noise (fine-grained, service-specific).

Best practices:

  • One event per work unit (a request or a message pulled from a queue), built by passing a context object through the code path.
  • The event holds: who created it, what for, success or failure, measurements (durations), and every network call instrumented (response time, status code).
  • Sanitise sensitive data (users' personal data) that developers should not see.
  • It minimises but does not remove joins: to correlate caller and callee events, every event includes the request (or message) ID.

Controlling cost:

  • Log levels (debug, info, warning, error) with a dynamic knob: raise verbosity to investigate, lower to save.
  • Sampling (e.g. log every nth event; https://www.honeycomb.io/blog/dynamic-sampling-by-example/), with priority: sample failed requests more than successful ones.
  • More nodes mean more volume, and a bad commit can cause excessive logging, so log collectors must rate limit.
  • In-memory aggregates (metrics) emitted instead of raw logs: cheaper, but you lose drill-down.

32.2 Traces

Tracing captures the whole lifespan of a request across services. A trace is a list of causally related spans; a span is a time interval for a logical operation or work unit, with key-value pairs.

  • Each request gets a unique trace ID, propagated at every fork (thread to thread, and caller to callee over the network, e.g. via HTTP headers)
    • Each stage is a span event carrying the trace ID.
  • On completion a span goes to a collector, which stitches spans into a trace: Zipkin (https://zipkin.io/), AWS X-Ray (https://aws.amazon.com/xray/).
  • Uses:
    • debug issues of specific requests (e.g. from support tickets)
    • rare issues hitting few requests
    • issues across a large group with something in common (slow requests on a subset of instances)
    • find end-to-end bottlenecks
    • resource attribution (which users hit which downstream services in what proportion, for rate limiting or billing).
  • Hard to retrofit:
    • every component on the path must propagate the trace context, including third-party frameworks, libraries and services
    • The service mesh pattern can help retrofit it.

32.3 Putting it together

Event logs are fine-grained and service-specific: one event covers one service's work unit, so it tells little about the whole request flow or a service's overall health. Metrics and traces are derived views built from event logs:

  • a metric = time series of summary statistics from aggregating counters or observations over many events (emit counters in events and let the backend roll them up at ingestion, as some collectors do);
  • a trace = all events of one request's lifecycle aggregated into an ordered list (emit span events, backend assembles).

Ch. 33 Manageability

Operators need to change behaviour without code changes: releasing (chapter 30) or changing configuration.

  • Settings affect behaviour (max internal cache size) or hold secrets (credentials)
    • They vary by environment and can be sensitive, so do not hard-code: keep them in a dedicated store such as AWS AppConfig (https://docs.aws.amazon.com/appconfig/; background: https://www.allthingsdistributed.com/2021/08/continuous-configuration-on-aws.html) or Azure App Configuration (https://azure.microsoft.com/en-us/services/app-configuration/).
  • Option 1: the CD pipeline reads config at deploy and passes it via environment variables; drawback: changes require redeploying.
  • Option 2:
    • the app periodically re-reads config at run time and applies changes
    • e.g. an HTTP handler whose constructor depends on a setting must be re-created when the setting changes.
  • With dynamic config, ship a build with a feature disabled, then enable it for a fraction of instances or users to build confidence before full rollout (feature toggles), or run A/B tests (https://en.wikipedia.org/wiki/A/B_testing).

Part V summary (the author's advice)

  • Most time goes to maintenance: fixing bugs, adding features, operating production.
  • To become a better system designer, embrace maintenance and make systems easy to modify, extend and operate; you gain a "sixth sense" for critiquing others' designs.
  • Learn from production: be on call for your services, join as many post-mortems as you can and ask how each incident could have been avoided: worth more long term than reading about the latest architectural trends.

Ch. 34 Final words (recommended next steps)

  • Best way to keep learning: design, build and maintain large-scale systems (some of the best-paid jobs, high demand).
  • Second best:
    • industry papers
      • Start with "Windows Azure Storage: A Highly Available Cloud Storage Service with Strong Consistency" (https://sigops.org/s/conferences/sosp/2011/current/2011-Cascais/printable/11-calder.pdf): Azure storage is a core building block under many Microsoft products
    • strong consistency was a key decision that eases application developers' work
    • it touches many concepts in this book. Then "Azure Data Explorer" (the cloud-native event store built on Azure storage; link above): shows how large systems compose.
  • New to reading papers:
    • Keshav's three-pass approach, "How to Read a Paper" (https://web.stanford.edu/class/ee384m/Handouts/HowtoReadPaper.pdf). Follow references down the rabbit hole
    • the book's references are "side quests".
  • Books:
    • Martin Kleppmann, Designing Data-Intensive Applications ("a must-read": https://www.amazon.com/dp/1449373321)
    • Alex Xu, System Design Interview for case studies (https://www.amazon.co.uk/dp/B08CMF2CQF).
