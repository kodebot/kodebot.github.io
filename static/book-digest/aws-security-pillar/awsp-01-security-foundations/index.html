AWS Security Pillar 1: Security Foundations

Source: AWS Well-Architected Framework, Security Pillar (Amazon Web Services; the PDF is stamped 2026, the page text says "Publication date: November 6, 2024"). Own-words summary, much shorter than the source. Next: AWS Security Pillar 2: Identity Management.

Takeaways
  • The pillar has seven design principles and seven areas; this note covers the principles, the shared responsibility model, governance, and the SEC01 best practices.
  • Security in the cloud is split: AWS secures the cloud itself, you secure what you put in it, and how much is yours depends on the service (EC2 leaves you the OS; S3 does not).
  • Governance works in layers: the shared responsibility model, then platform-wide guardrails, then product-team controls.
  • SEC01 has eight practices. The two rated high risk first: separate workloads by account and secure the root user.

1.1 Why this pillar, and its status

  • It is one of six pillars (operational excellence, security, reliability, performance efficiency, cost optimisation, sustainability) and is aimed at CTOs, CISOs, architects, developers and operations teams.
  • It gives guidance and links, not implementation detail or architecture patterns.
  • AWS now labels the standalone paper "historical reference" and says current guidance lives in the main Framework. The practice wording below follows the 2026 PDF.

1.2 The seven design principles

Principle What it asks for Example
Strong identity foundation least privilege, separation of duties, no reliance on long-term static credentials people sign in through a central identity provider instead of using IAM users
Maintain traceability monitor, alert and audit actions in real time CloudTrail on in every account
Security at all layers defence in depth from network edge to code WAF at the edge, security groups on instances, input validation in the app
Automate best practices controls defined as code in version-controlled templates a CloudFormation template that every new account receives
Protect data in transit and at rest classify data, then encrypt, tokenise or restrict S3 objects encrypted with a KMS key
Keep people away from data reduce direct access and manual handling engineers use a pipeline, not a shell, to change production
Prepare for security events policies, simulations, automated tooling a practised incident runbook

1.4 Shared responsibility

  • AWS (security of the cloud): the hardware, software, networking and facilities that run the services.
  • Customer (security in the cloud): set by the services chosen.
    • EC2 is infrastructure as a service, so you manage the guest OS, patches, installed software and the security group firewall.
    • S3 and DynamoDB are abstracted: AWS runs the OS and platform; you manage data, classification, encryption options and IAM permissions.
  • Controls come in three kinds:
    • Inherited: fully from AWS (physical and environmental controls).
    • Shared: both sides, in different scopes (patching, configuration management, training).
    • Customer specific: only you (for example zoning data into specific security environments).
  • Patching of managed services:
    • Single-tenant (RDS, ElastiCache, OpenSearch): AWS builds and releases patches; you choose maintenance windows and apply them.
    • Multi-tenant (S3, DynamoDB, ElastiCache Serverless): AWS applies patches; you read each service's maintenance documentation.

1.5 Governance

  • Foundation: the shared responsibility model. AWS Artifact gives on-demand access to AWS security and compliance reports.
  • Middle layer: platform-wide capability, where most control objectives are met.
    • Account vending, IAM Identity Center, common detective controls.
    • Service control policies (SCPs) in AWS Organizations as security invariants, applied across accounts (for example, only allowed Regions; detective controls cannot be switched off).
    • Codified checks: AWS Config rules and pipeline checks.
  • Top layer: product teams implement controls in their own applications (input validation, identity passed correctly between microservices) while inheriting from the middle layer.
  • Risk reasoning: judge risk by likelihood and consequence (the inherent risk), choose a control objective that lowers either, then look at the residual risk with the control in place.

1.6 Account management and separation

  • Treat an AWS account as a hard boundary. Group accounts by function, compliance need or shared controls, not by mirroring the org chart.
  • Three jobs for AWS Organizations:
    • Manage accounts centrally: create accounts and group them into OUs.
    • Set controls centrally: SCPs allow or deny services, Regions and actions for all users and roles below an OU.
    • Configure services centrally: org-wide CloudTrail, aggregated AWS Config, CloudFormation StackSets.
  • Use delegated administration (GuardDuty, Security Hub, Config) so security tooling lives outside the billing and management account.
  • AWS Control Tower adds a landing zone, mandatory and optional controls, and an Account Factory.

1.7 SEC01 best practices

SEC01-BP01 Separate workloads using accounts (risk: high)

  • Anti-patterns: unrelated workloads with different data sensitivity in one account; a poorly designed OU structure.
  • Benefit: a smaller blast radius if one workload is accessed by mistake, plus central governance.
  • Steps:
    1. Design the OU structure around business needs, data sensitivity and workload structure; good use of inheritance means fewer policies.
    2. Build a landing zone (custom or Control Tower).
    3. Establish guardrails from the landing zone.
    4. Restrict access to newly added Regions.
    5. Consider StackSets to push IAM policies, roles and groups from an approved template.

SEC01-BP02 Secure the account root user and its properties (risk: high)

  • The root user has full access and in some cases cannot be limited by policy; use it only for the few tasks that need it.
  • Anti-patterns: routine root use; untested recovery plans; forgetting that account recovery depends on the root email, phone, DNS and mail servers.
  • Preventative controls:
    • Accurate contact details; a corporate-domain distribution list as the root email; a dedicated, unshared phone number.
    • No root access keys (CIS 1.4); if they exist, move to role credentials and delete them.
    • For member accounts under Organizations, consider whether you need root credentials at all, and apply guardrails that disallow root access keys and root actions.
    • Where credentials exist: a complex password, MFA (CIS 1.5), hardware MFA preferred (CIS 1.6), more than one MFA device (up to 8; adding a second turns off the lost-device recovery flow).
    • Store the password somewhere that does not need the same AWS account (avoid circular dependency).
  • Detective controls: alarm on root use (CIS 1.7); GuardDuty reports a RootCredentialUsage finding.
  • Operational guidance: a two-person rule over credentials and MFA; organisation, not an individual, owns the email and phone; test root access periodically before an emergency.

SEC01-BP03 Identify and validate control objectives (risk: high)

  • Derive control objectives from compliance requirements and your threat model, then validate the controls continuously and keep evidence for auditors.
  • Frameworks named: SOC 2, HITRUST, PCI-DSS, ISO 27001, NIST SP 800-53.
  • Enforce with SCPs, resource policies and trust policies
    • detect with AWS Config rules (move to enforcement once confident)
    • start from Security Hub CSPM standards (AWS Foundational Security Best Practices, CIS AWS Foundations Benchmark) and add Config conformance packs where needed.

SEC01-BP04 Stay up to date with threats and recommendations (risk: high)

  • Follow MITRE ATT&CK, the CVE list, the OWASP Top 10 and AWS Security Bulletins.
  • Prefer services that update themselves: GuardDuty (threat intelligence), Inspector (CVE database), WAF and Shield Advanced (managed rule groups).
  • Pair with an operational-excellence fleet management and patching strategy.

SEC01-BP05 Reduce security management scope (risk: medium)

  • Choosing a managed service moves some controls to AWS. Hosting a database on a VM leaves you the largest share.
  • Examples: RDS instead of a self-run database; EKS or ECS for containers; serverless.
  • Weigh the saved security work in total cost of ownership; use AWS Artifact reports as audit evidence.
  • You still own update timing for managed services (RDS version, Lambda runtime); AWS Health helps track it.

SEC01-BP06 Automate deployment of standard security controls (risk: medium)

  • Define standard controls as infrastructure-as-code, keep them in version control, test in CI/CD, and deploy automatically.
  • Anti-pattern: changing standard controls by hand in the console.
  • Steps: a template repository, pipelines that test for misconfiguration, a catalogue of standard templates for teams, backup and recovery for the control configuration itself.

SEC01-BP07 Identify threats and prioritise mitigations using a threat model (risk: high)

  • Keep a living register of threats and mitigations; revisit it as the workload and landscape change.
  • The pillar suggests starting with Shostack's four questions (Threat Modeling: Designing for Security is queued for digest):
    1. What are we working on? (a data flow diagram plus written assumptions)
    2. What can go wrong?
    3. What are we going to do about it?
    4. Did we do a good job?
  • Prioritise threats, then choose prevent, detect and respond mitigations.

SEC01-BP08 Evaluate and implement new security services and features regularly (risk: low)

  • Subscribe to AWS blogs, bulletins and the features-update SNS topic; attend AWS events; use your account team (and a TAM under Enterprise Support).

Summary points

  • Know which half of the shared model you hold for each service you pick.
  • Accounts are the strongest isolation boundary; use Organizations and SCPs to apply guardrails by inheritance.
  • Lock down the root user first, then automate everything else as code.
Terms to carry forward
  • Security invariant: a control applied across many accounts, usually through an SCP.
  • SCP: service control policy; limits what accounts in an OU may do, even for admins.
  • Landing zone: the starting multi-account environment created by Control Tower or built by hand.
  • Inherent and residual risk: risk before and after a control.
  • AWS Artifact: AWS's portal for compliance reports.
