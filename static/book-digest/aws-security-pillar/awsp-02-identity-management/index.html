AWS Security Pillar 2: Identity Management

Source: AWS Well-Architected Framework, Security Pillar, "Identity and access management", SEC02. Own-words summary, much shorter than the source. Previous: AWS Security Pillar 1: Security Foundations. Next: AWS Security Pillar 3: Permissions Management.

Takeaways
  • Two kinds of identity need managing: human (workforce, third parties, application users) and machine (workloads, tools, devices).
  • Aim for no long-term credentials: federate people, give workloads IAM roles, and treat IAM users and access keys as the exception.
  • Where a secret must exist, apply remove, replace, rotate and keep it in a secrets service, never in code.
  • Five of the six practices are rated high risk if missing; groups and attributes (SEC02-BP06) are medium.

2.1 Two kinds of identity

Kind Who How they reach AWS
Workforce admins, developers, operators central identity provider, then temporary credentials
Third parties contractors, vendors, SaaS partners cross-account roles, resource-based policies
Application users customers using web or mobile apps Amazon Cognito user and identity pools
Machines EC2, Lambda, IoT devices, on-premises systems IAM roles and temporary credentials

2.2 SEC02-BP01 Use strong sign-in mechanisms (risk: high)

  • Require MFA for human identities and workloads (IAM best practice), a minimum password length and complexity, and let users change their own passwords.
  • Give each person an individual identity, not shared credentials, so activity is auditable.
  • Anti-pattern: no strong password policy.
  • Set exact values from company policy or a standard such as NIST 800-63.

2.3 SEC02-BP02 Use temporary credentials (risk: high)

  • Long-term access keys exist only for IAM users and the root user. Federation or assuming a role always yields temporary credentials, even for the console.
  • Anti-pattern: developers use long-term access keys from IAM users instead of getting temporary credentials from the command line.
  • Workforce: federate to a central identity provider (IAM Identity Center or direct federation); few cases still need IAM users.
  • Third parties: cross-account roles and resource-based policies; Cognito's OAuth 2.0 client-credentials grant for B2B partners.
  • Application users: Cognito identity pools give temporary credentials; define a separate low-privilege role for guests.
  • Machines: roles for EC2, Lambda execution roles, the IoT Core credential provider, IAM Roles Anywhere for systems outside AWS.
  • When long-term keys are unavoidable:
    • Grant highly restricted permissions (specific actions, resources, conditions).
    • Consider letting the IAM user only call AssumeRole for one role.
    • Limit source IP addresses in the role trust policy.
    • Alert on misuse with CloudWatch Logs metric filters.
    • Add permission boundaries, which complement coarse SCPs with fine-grained limits.

2.4 SEC02-BP03 Store and use secrets securely (risk: high)

  • A workload proves its identity to databases and third parties with API keys, passwords and OAuth tokens. Use a purpose-built service to store, manage and rotate them.
  • Anti-patterns: not rotating; long-term credentials in source code or config files; unencrypted storage at rest.
  • The approach is remove, replace, rotate:
    1. Remove credentials the workload no longer needs.
    2. Replace long-term credentials with temporary ones (IAM roles for EC2 and Lambda, IAM Roles Anywhere or Systems Manager Hybrid Activations outside AWS, Cognito identity pools for mobile).
    3. Rotate what remains using AWS Secrets Manager, retrieved at runtime.
  • Find hard-coded secrets by scanning repositories (the pillar names Amazon CodeGuru, filtering on Type=Secrets).

2.5 SEC02-BP04 Rely on a centralised identity provider (risk: high)

  • Manage workforce identities in one place so you can create, assign, revoke and audit access from a single location.
  • Anti-pattern: separate user accounts per application with no federation or single sign-on.
  • Workforce:
    • IAM Identity Center for single sign-on across the accounts in your organisation, or direct IAM federation into each account
    • then remove IAM users replaced by federated identities.
  • Application users: Amazon Cognito (OpenID Connect and OAuth; Amplify libraries for custom apps).

2.6 SEC02-BP05 Audit and rotate credentials periodically (risk: high)

  • Anti-patterns: not auditing credential use; unnecessary long-term credentials; never rotating them.
  • Audit:
    • remove leavers and unused cross-account roles
    • use credential reports and IAM Access Analyzer
    • alarm on specific API calls with CloudWatch
    • GuardDuty flags unexpected credential use.
  • Rotate: when temporary credentials are impossible, rotate keys on a schedule and automate where possible (Secrets Manager rotation).

2.7 SEC02-BP06 Employ user groups and attributes (risk: medium)

  • Define permissions by group (the function someone performs) and attributes (department, project, location), so there are fewer, simpler policies.
  • Anti-patterns: copying permissions per person; groups too broad (over-permissive) or too narrow (duplicated, confusing membership).
  • Decide where groups live (identity provider, IAM Identity Center, IAM groups). With IAM Identity Center, attach permission sets to groups
    • if the external provider supports SCIM, turn on automatic provisioning so groups and memberships sync.

Summary points

  • Everyone and everything gets an individual identity with MFA where a person is involved.
  • Prefer federation and roles over IAM users; prefer no secret over a rotated secret.
  • Audit identities on a schedule: people leave, roles go stale.
Terms to carry forward
  • Federation: signing in through an external identity provider and receiving temporary AWS credentials.
  • IAM Identity Center: AWS's single sign-on service for multiple accounts.
  • IAM Roles Anywhere: temporary credentials for workloads outside AWS.
  • Remove, replace, rotate: the order of work for any secret.
  • SCIM: protocol that syncs users and groups between an identity provider and a service.
