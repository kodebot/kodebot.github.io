AWS Security Pillar 5: Infrastructure Protection

Source: AWS Well-Architected Framework, Security Pillar, "Infrastructure protection", SEC05 (network) and SEC06 (compute). Own-words summary, much shorter than the source. Previous: AWS Security Pillar 4: Detection. Next: AWS Security Pillar 6: Data Protection.

Takeaways
  • Defence in depth on the network: layers by data sensitivity, then traffic controls inside each layer, then inspection, all deployed as code.
  • Compute is protected by hardened, verified images, scanning and patching by automation, and no interactive access where a runbook will do.
  • Seven practices: SEC05-BP01 and BP02 and SEC06-BP01 and BP02 are high risk; the rest are medium.

5.1 SEC05: network protection

SEC05-BP01 Create network layers (risk: high)

  • Group components by function, data sensitivity and behaviour; separate what needs internet access (public web endpoints) from what is internal only (databases).
  • Anti-patterns: everything in one VPC or subnet; layers drawn with no thought for data sensitivity.
  • Steps:
    • Put public endpoints behind load balancers or proxies, and consider managed edge services (CloudFront, API Gateway, Elastic Load Balancing, Amplify) to shift controls to AWS.
    • Run EC2, Fargate and Lambda in private subnets matched to the groups.
    • For managed services (DynamoDB, Kinesis, SQS) use VPC endpoints as the default path over private IP addresses.

SEC05-BP02 Control traffic flow within your network layers (risk: high)

  • Restrict each layer to the flows the workload needs. Start with north-south (internet or external systems to your environment), then east-west (between your components).
  • Anti-pattern: a perimeter-only approach that controls traffic at the edge and nowhere else.
  • Steps:
    • map the required flows
    • apply several controls for inbound and outbound traffic (security groups, route tables)
    • use firewalls for fine-grained control (Route 53 Resolver DNS Firewall, AWS Network Firewall, AWS WAF) and AWS Firewall Manager to manage rules centrally.

SEC05-BP03 Implement inspection-based protection (risk: medium)

  • Put inspection points between layers to confirm traffic matches expected patterns, and analyse flows and metadata.
  • Anti-pattern: rules that only look at ports and protocols.
  • Options:
    • a central inspection VPC or per-VPC inspection
    • inline with AWS Network Firewall or a third-party appliance behind a Gateway Load Balancer
    • out of band with VPC Traffic Mirroring (EventBridge plus Lambda can switch mirroring on for new resources)
    • and web-traffic protection with WAF.

SEC05-BP04 Automate network protection (risk: medium)

  • Use infrastructure as code and CI/CD so changes are tracked, quick to deploy and drift is detectable.
  • Anti-pattern: each workload team defines its whole network stack and protections alone.
  • Steps:
    • decide what is central and what teams own
    • use separate test and production network accounts
    • keep central templates in a repository distinct from workload repositories
    • build pipelines with misconfiguration tests.

5.2 SEC06: compute protection

SEC06-BP01 Perform vulnerability management (risk: high)

  • Scan and patch code, dependencies and infrastructure often.
  • Anti-patterns: no programme; patching with no regard to severity or risk; running software past vendor end of life.
  • Steps:
    • understand the shared model
    • configure scanning (Amazon Inspector covers instances, containers and functions for vulnerabilities and unintended network exposure)
    • define identification, prioritisation and remediation timelines by severity
    • automate OS and application patching with a patch management service.

SEC06-BP02 Provision compute from hardened images (risk: high)

  • Fewer opportunities for unintended access come from hardened images
    • Acquire container images and libraries only from trusted registries, verify signatures, and keep your own private registries for trusted artefacts.
  • Anti-pattern: trusting registries but not verifying signatures.
  • Per compute type:
    • OS: hardened AMIs built from trusted base images with EC2 Image Builder.
    • Containers: follow container best practice and scan images in the pipeline and regularly in the repository (ECR image scanning).
    • Lambda: use layers to separate function code from shared libraries and turn on code signing.

SEC06-BP03 Reduce manual management and interactive access (risk: medium)

  • Automate deployment, configuration, maintenance and investigation. Allow manual access only for emergencies or safe sandbox environments.
  • Anti-patterns: SSH or RDP into EC2; individual user logins on instances; sharing a password or private key.
  • Steps:
    1. Install and start SSM Agent (check your base AMI).
    2. Give instance profile roles the AmazonSSMManagedInstanceCore policy.
    3. Disable SSH, RDP and similar services (user data or custom AMIs).
    4. Make sure security groups do not allow port 22 or 3389, and alert on mistakes (AWS Config).
    5. Write Systems Manager automations, runbooks and run commands; control who may run them with IAM; test in non-production and invoke them instead of logging in.

SEC06-BP04 Validate software integrity (risk: medium)

  • Use cryptographic verification and signing on OS images, container images and code artefacts.
  • Anti-pattern: trusting a reputable vendor website and ignoring certificate or signature validation.
  • A hash or digest shows the payload was not tampered with but does not prove who produced it
    • provenance needs a certificate from a trusted authority signing the artefact. Check whether a provider publishes a public key, and build signature checks into image acquisition and hardening.

SEC06-BP05 Automate compute protection (risk: medium)

  • Anti-pattern: immutable infrastructure with no way to patch or replace it.
  • Steps:
    • build compliant hardened AMIs automatically (CIS Benchmarks or STIG)
    • automate configuration management (AWS Config, Security Hub CSPM)
    • automate patching or replacing instances (Systems Manager Patch Manager)
    • automate scanning for CVEs.

Summary points

  • Place the workload in layers, restrict traffic in each, inspect between them, and define it all as code.
  • Build images once, verify them, and replace instead of logging in.
  • A matching hash is not proof of origin.
Terms to carry forward
  • North-south and east-west traffic: into and out of the environment versus between its components.
  • VPC endpoint: private access to an AWS service from inside a VPC.
  • Gateway Load Balancer (GWLB): routes traffic through third-party inspection appliances.
  • Hardened image: a base image reduced and configured to benchmark standards (CIS, STIG).
  • Provenance: proof of where an artefact came from.
