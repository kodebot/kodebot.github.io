AWS Security Pillar 6: Data Protection

Source: AWS Well-Architected Framework, Security Pillar, "Data protection", SEC07 (classification), SEC08 (at rest) and SEC09 (in transit). Own-words summary, much shorter than the source. Previous: AWS Security Pillar 5: Infrastructure Protection. Next: AWS Security Pillar 7: Incident Response.

Takeaways
  • You cannot protect data you have not classified. Classification drives isolation, encryption, retention and who may read it.
  • Different data deserves different controls; one level for everything wastes effort and leaves the sensitive items under-protected.
  • At rest: encrypt by default, guard the keys. In transit: current TLS, managed certificates, authenticated calls.
  • Eleven practices; classification, lifecycle, key management, encryption at rest, access control, certificate management and encryption in transit are rated high risk.

6.1 SEC07: data classification

SEC07-BP01 Understand your data classification scheme (risk: high)

  • Know what data the workload handles, its handling requirements, who owns it, where it is stored, and the legal and compliance rules that apply.
  • Anti-pattern: no formal policy defining sensitivity levels and their handling.
  • Steps:
    • learn the organisation's scheme
    • identify sensitive data types
    • record them in a data catalogue
    • tag data with its sensitivity (AWS Organizations tag policies can enforce tagging standards).

SEC07-BP02 Apply data protection controls based on data sensitivity (risk: high)

  • Anti-pattern: the same controls for all data, which over-provisions for some and under-protects others.
  • Steps:
    • set isolation boundaries per level
    • decide access, encryption, auditing and retention controls per class
    • reduce sensitivity where possible (tokenisation or anonymisation)
    • verify with automated testing and monitoring.

SEC07-BP03 Automate identification and classification (risk: medium)

  • Anti-pattern: relying on manual identification, which is error-prone.
  • Run an initial scan, or sample if a full scan is too costly
    • Amazon Macie can run broad, sampled discovery across S3 buckets, then deeper discovery jobs; other stores can be exported to S3 to be scanned
    • Apply the SEC07-BP02 controls to what is found, and keep scanning for unexpected sensitive data.

SEC07-BP04 Define scalable data lifecycle management (risk: high)

  • Anti-pattern: one-size-fits-all lifecycle handling.
  • Define how data is handled on entry, transformation and destruction: retention periods, access, auditing and provenance
    • Implement retention and automated destruction that match legal, regulatory and organisational needs, review as rules change, and use AWS Config to find resources without automated lifecycle management.

6.2 SEC08: protecting data at rest

SEC08-BP01 Implement secure key management (risk: high)

  • Key management covers storage, rotation, access control and monitoring of key material.
  • Anti-patterns: people handling unencrypted key material; inventing custom cryptographic algorithms; overly broad key permissions.
  • Choose AWS owned or managed keys (no key policies to maintain) or customer managed keys in KMS. The default key store balances agility, security, data sovereignty and availability
    • custom key stores with CloudHSM or an external key store suit special cases.
  • Check how each service integrates with KMS. Example: EC2 uses encrypted EBS volumes, and snapshots from them should also be encrypted with a customer managed key.

SEC08-BP02 Enforce encryption at rest (risk: high)

  • Anti-patterns: not using encrypt-by-default; overly permissive decryption access; not monitoring key use.
  • Configure default encryption for new EBS volumes; copy AMIs with encryption on (root volumes and snapshots follow); turn on RDS encryption for clusters and snapshots.
  • Use KMS key policies that limit access by data class. Example from the source: one key for production data and another for development or test data
    • if production must decrypt development artefacts, adjust the development key's policy to allow the production account.

SEC08-BP03 Automate data at rest protection (risk: medium)

  • Anti-patterns: not enabling encryption defaults where supported; planning only for operational events and ignoring security events.
  • Capture storage settings (such as S3 encryption) in infrastructure-as-code, check templates in the pipeline with CloudFormation Guard, run AWS Config rules in proactive mode before creation, monitor drift with Config, remediate automatically, and let IAM Access Analyzer flag permissions that can be reduced
    • Use backups (the pillar points to the reliability pillar) because recovery matters for security events too.

SEC08-BP04 Enforce access control (risk: high)

  • Anti-patterns: mixing data of different sensitivity; over-permissive decryption-key permissions; misclassifying data.
  • Steps:
    • least privilege for users, services and KMS key policies
    • separate accounts per classification level managed through Organizations
    • review S3 bucket and object permissions regularly, avoid public readable or writable buckets, detect them with Config, serve public content through CloudFront, and verify buckets that must be private block public access.

6.3 SEC09: protecting data in transit

SEC09-BP01 Implement secure key and certificate management (risk: high)

  • Anti-patterns: manual certificate deployment or renewal; not thinking through the CA hierarchy for a private CA; self-signed certificates on public resources.
  • Use AWS Certificate Manager (ACM) for publicly trusted TLS certificates on web servers and load balancers
    • AWS Private CA for your own hierarchy or exportable certificates
    • AWS IoT Core for certificates at device scale
    • native mutual TLS on API Gateway or Application Load Balancer. Rely on ACM managed renewal.

SEC09-BP02 Enforce encryption in transit (risk: high)

  • Use only encrypted protocols for sensitive data leaving your VPC.
  • Anti-pattern: deprecated SSL and TLS versions and cipher suites (for example SSL 3.0).
  • Examples:
    • a security group that allows only HTTPS to a load balancer or instance
    • HTTPS on CloudFront with a suitable security profile
    • an IPsec VPN for point-to-point or network-to-network links
    • strongest supported cipher policy on an HTTPS listener
    • require SSL or TLS in Redshift
    • check each service's documentation.

SEC09-BP03 Authenticate network communications (risk: low)

  • Use protocols that verify identity (TLS, IPsec) between services, applications and users.
  • Anti-patterns: unencrypted or unauthenticated flows inside the workload; reusing credentials across entities; relying on network controls alone for access control.
  • Steps:
    • document and diagram your data flows (the same diagram helps threat modelling) and check against runtime behaviour
    • add network controls aligned to the flows (security groups, AWS PrivateLink) as one layer, not the only one
    • authenticate the calls themselves.

Summary points

  • Classify first; everything else follows from the class.
  • Keep the keys safer than the data: narrow key policies, separate keys per environment, no custom crypto.
  • Automate certificates and encryption defaults so nobody has to remember them.
Terms to carry forward
  • Data catalogue: single view of where data lives and how sensitive it is.
  • Tokenisation: replacing a sensitive value with a stand-in.
  • KMS, CloudHSM: key management service and hardware security module.
  • ACM and Private CA: public and private certificate authorities.
  • mTLS: both ends present certificates.
  • PrivateLink: private connectivity to services without public internet.
