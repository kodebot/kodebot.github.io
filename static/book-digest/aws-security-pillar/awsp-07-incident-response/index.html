AWS Security Pillar 7: Incident Response

Source: AWS Well-Architected Framework, Security Pillar, "Incident response", SEC10. Own-words summary, much shorter than the source. Previous: AWS Security Pillar 6: Data Protection. Next: AWS Security Pillar 8: Application Security.

Takeaways
  • Cloud incident response has three aspects: preparation, operations, post-incident activity. Operations follow the NIST phases: detect, analyse, contain, eradicate, recover.
  • Prepare people, process and technology together; a programme missing one is not complete.
  • Cloud-specific design goals: respond where the data is, keep evidence in a dedicated account, redeploy to fix, automate repeatable triage, and learn.
  • Eight practices: the first two (people and plan) are high risk; forensic setup, playbooks, access, tools, simulations and learning are medium.

7.1 Cloud response design goals

Goal Meaning
Establish response objectives agree the aim with stakeholders, legal and leadership (contain, restore, preserve evidence and so on)
Respond using the cloud do response work in the cloud, where the event and data are
Know what you have preserve logs, resources and snapshots by copying them into a central response account; use tags and retention enforcement
Use redeployment if the cause is misconfiguration, redeploy the correct configuration; after a suspected compromise, verify the root cause is mitigated first
Automate where possible script triage of repeated events; keep humans for unique, complex or sensitive cases
Choose scalable solutions detection and response must scale as the environment does
Learn and improve find gaps with simulations and fix them
  • The response tooling should arrive through a deployment pipeline, not be left static, because static tools create extra risk.
  • Reference guide named by the pillar: NIST SP 800-61, Computer Security Incident Handling Guide.

7.2 SEC10-BP01 Identify key personnel and external resources (risk: high)

  • Keep a current list of internal and external people, their roles, legal obligations and contact details.
  • Anti-pattern: not maintaining that list.
  • Steps:
    • set up an incident management solution (for example Incident Manager in the Security Tooling account)
    • give each contact at least two channels (SMS, phone, email)
    • define escalation by role, not by individual, and include people who inform external parties.

7.3 SEC10-BP02 Develop incident management plans (risk: high)

  • The incident response plan is the first document and the foundation of the programme. Update, iterate and test it regularly.
  • Steps:
    1. Define roles and responsibilities with representatives from HR, the executive team, legal, and application owners and developers.
    2. Draw a RACI (responsible, accountable, consulted, informed) chart so communication is direct and leadership at each stage is clear.
    3. Involve application owners and developers; build relationships and rehearse with them before an incident.
    4. Involve trusted partners or external experts.
    5. Align with local regulations and compliance requirements.
    6. Practise the plan regularly with every defined role.

7.4 SEC10-BP03 Prepare forensic capabilities (risk: medium)

  • Traditional forensics concepts apply on AWS. Build the account structure first.
  • Security OU: a log archive account (aggregated logs, limited permissions) and a security tools account (delegated administrator for security services).
  • Forensics OU:
    • a single forensics account, or one per Region you operate in
    • Per-Region accounts let you block resource creation elsewhere, reducing the chance of evidence being copied to an unintended Region.

7.5 SEC10-BP04 Develop and test security incident response playbooks (risk: medium)

  • Playbooks give prescriptive steps, simplify response and reduce human error. Write them per scenario.
  • A playbook holds:
    • Overview: the risk or scenario and its goal.
    • Prerequisites: logs, detection and automation needed; the expected notification.
    • Communication and escalation: who is involved, contacts, responsibilities.
    • Response steps by phase: detect (how), analyse (scope of impact), contain (limit scope), eradicate (remove the threat), recover (return to production), including queries and code to run.
    • Expected outcomes: what running those steps should produce.

7.6 SEC10-BP05 Pre-provision access (risk: medium)

  • Responders need the right access in place before the incident to cut time from investigation to recovery.
  • Anti-patterns: using the root account for response; altering existing accounts; editing IAM permissions directly to give just-in-time elevation.
  • Preferred model:
    • federation plus temporary escalation
    • The responder requests a higher-privilege role, an approver approves, temporary credentials are issued, and they expire so a new request is needed
    • Implement with AWS Security Token Service and session policies to scope access.
  • Plan for when federation is unavailable (compromised identity provider, broken federation, a DDoS-type event): see AWS Security Pillar 3: Permissions Management on emergency access.

7.7 SEC10-BP06 Pre-deploy tools (risk: medium)

  • Make sure security staff have tools ready, deployed through the same automation as everything else (identity, network security, data protection and monitoring can all be automated through APIs).
  • Steps:
    • configure logging for response (AWS Security Pillar 4: Detection)
    • turn on detection and response services
    • adopt a tagging strategy (purpose, owner, environment, data type) so responders can learn context quickly.

7.8 SEC10-BP07 Run simulations (risk: medium)

  • Simulations (game days) use realistic scenarios that mimic a threat actor's tactics, techniques and procedures to exercise the response.
  • Steps:
    1. Define the scenario and objectives, with leadership acceptance.
    2. Identify stakeholders: at least facilitators and participants; legal, communications or executives where relevant.
    3. Build and test the scenario, redefining it where parts are infeasible.
    4. Facilitate it, matching the style (paper-based or highly technical) to the objectives.
    5. Write an after-action report covering what went well, what to improve and gaps, so progress can be tracked.

7.9 SEC10-BP08 Establish a framework for learning from incidents (risk: medium)

  • A lessons-learned framework and root cause analysis improve response and help prevent recurrence.
  • Questions to ask:
    • What was the incident, when and how was it first identified, and which systems alerted?
    • Which systems, services and data were involved and what specifically happened?
    • What worked well, what did not, and which process or procedure failed to scale?
    • What can be improved for people (were the right people reachable?), process and technology?
  • Assign ownership for the improvements; this links to the blameless review practices in the SRE sources queued in the reading list.

Summary points

  • Contacts, roles and a RACI chart come before tools.
  • Keep evidence in dedicated accounts and redeploy known-good configuration.
  • Test the plan with simulations, then write the after-action report.
Terms to carry forward
  • NIST phases: detect, analyse, contain, eradicate, recover.
  • RACI: responsible, accountable, consulted, informed.
  • Playbook: step-by-step response for one scenario.
  • Game day: a simulated incident exercise.
  • After-action report (AAR): written findings after a simulation.
  • Just-in-time (temporary) elevation: a time-limited, approved grant of higher privilege.
