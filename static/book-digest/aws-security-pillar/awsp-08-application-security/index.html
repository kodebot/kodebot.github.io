AWS Security Pillar 8: Application Security

Source: AWS Well-Architected Framework, Security Pillar, "Application security", SEC11, and the conclusion. Own-words summary, much shorter than the source. Previous: AWS Security Pillar 7: Incident Response.

Takeaways
  • Application security is built into how software is delivered: trained people, reviewed code, automated tests, a controlled package source, programmatic signed deployment and a secure pipeline.
  • The pipeline is itself a production system to protect: least-privilege roles, tests builders cannot skip, input validation.
  • Penetration testing and code review catch what automation misses; automated tests catch what people forget.
  • Make security ownership part of each builder team, with the security team validating rather than deciding alone.
  • Eight practices: penetration testing, programmatic deployment and pipeline assessment are high risk; training, automated testing, code review and central packages are medium; the ownership programme is low.

8.1 SEC11-BP01 Train for application security (risk: medium)

  • Train teams in secure development and operation so issues are prevented, detected and fixed earlier. Cover threat modelling, secure coding practices and secure configuration services
    • make training self-service and gather feedback.
  • Anti-patterns:
    • considering security only at the review stage
    • leaving every security decision to a central team
    • not explaining how SDLC decisions relate to the overall security picture.
  • Steps:
    • assess skill gaps (surveys, code reviews, discussions)
    • plan topics (threat modelling, secure coding, security testing, secure deployment) using resources such as the Threat Modeling Workshop and AWS training
    • schedule regular hands-on sessions
    • define the security review process and each party's responsibility.

8.2 SEC11-BP02 Automate testing throughout the development and release lifecycle (risk: medium)

  • Anti-patterns: test cases and results not shared; testing only just before release; automating tests whose requirements change often.
  • Use consistent IDE, code review and CI/CD tooling with security tests. Decide where to block the pipeline and where to only notify.
  • Tools the pillar mentions: Automated Security Helper (open-source scanner), Amazon Q Developer in the IDE, Amazon CodeGuru Security on commit, Amazon Inspector for Lambda code.
  • Track findings in a ticketing system, link each finding to remediation guidance, and analyse results regularly to choose the next automation and training.

8.3 SEC11-BP03 Perform regular penetration testing (risk: high)

  • A penetration test finds issues automation and manual review cannot, and shows how well your detective controls work
    • It tries to make the software behave unexpectedly, such as exposing protected data or granting wider permissions than intended.
  • Anti-patterns: testing only for known or common issues; testing without third-party tools and libraries; checking package security but not the business logic.
  • Steps:
    • scope with a structured process based on the threat model
    • test when change is minimal but there is time to fix
    • train builders to read findings
    • automate repeatable tests
    • analyse findings for systemic issues to feed more automation and education.

8.4 SEC11-BP04 Conduct code reviews (risk: medium)

  • Review by someone other than the author for quality, vulnerabilities and standards. Use automated tools to assist.
  • Anti-patterns: no review before deployment; the same person writes and reviews; no tooling.
  • Steps:
    • define when reviews happen (before merging to main or before production) and who takes part (team, senior developers, security experts)
    • choose and integrate tools (GitHub pull requests, CodeGuru Security) with enforced minimum reviewers and approval rules
    • keep a checklist of what to review. See Google Code Review Guide: contents for Google's review practice.

8.5 SEC11-BP05 Centralise services for packages and dependencies (risk: medium)

  • Give teams one place to obtain packages so they can be validated first and analysed across the organisation.
  • Anti-patterns: pulling from arbitrary internet repositories; not testing new packages before offering them.
  • Steps:
    • a logically central repository in every development environment
    • access provided at account vending
    • automated package testing before publication
    • metrics on common packages, languages and busy teams
    • a request and feedback mechanism
    • regular scans for newly found issues.

8.6 SEC11-BP06 Deploy software programmatically (risk: high)

  • Anti-patterns: manual production deployment; hand-editing software per environment.
  • Steps:
    • separate accounts per environment with restricted human access to production
    • a CI/CD pipeline (CodeBuild, CodePipeline) that builds, tests and deploys
    • sign and verify packages (AWS Signer or KMS) after testing.

8.7 SEC11-BP07 Regularly assess security properties of the pipelines (risk: high)

  • Apply the pillar to pipelines, especially the separation of permissions.
  • Anti-patterns: security tests builders can bypass; overly broad pipeline permissions; pipelines that do not validate inputs.
  • Start from the AWS Deployment Pipelines Reference Architecture
    • generate least-privilege pipeline policies with IAM Access Analyzer
    • monitor pipelines and alert on abnormal activity (EventBridge to Lambda or SNS).

8.8 SEC11-BP08 Build a program that embeds security ownership in workload teams (risk: low)

  • Builders make security decisions; the security team validates them in review. This speeds delivery and builds an ownership culture.
  • Anti-patterns: all design decisions left to security; requirements addressed late; no feedback from builders or security staff.
  • Steps:
    • train builders first
    • create a community and onboarding
    • name the programme (Guardians, Champions, Advocates are common)
    • choose a model (train builders, embed security engineers, or affinity roles)
    • find sponsors
    • track participants, review times and feedback.

8.9 The pillar's conclusion

  • Security is an ongoing effort, and incidents are chances to improve the architecture.
  • Defence in depth means strong identity controls, automated responses to security events, protection of infrastructure at several levels, and well-classified, encrypted data.

Summary points

  • Pipelines, packages and people are the three levers of application security.
  • Sign what you deploy, and secure the pipeline that deploys it.
  • Embed ownership in teams; let the security team verify rather than decide alone.
Terms to carry forward
  • SDLC: software development lifecycle.
  • Blocking vs notifying gate: whether a failed security check stops the pipeline.
  • Penetration test: authorised attempt to make the software misbehave.
  • Security champion: a builder who owns security within a team.
  • Package signing: cryptographic proof that an artefact was approved.
