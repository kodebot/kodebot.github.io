Azure Security 2: Identity, Network, Data and Secrets Best Practices

Source: Microsoft Learn, Azure security fundamentals articles: "Azure identity management and access control security best practices", "Azure network security best practices", "Azure data security and encryption best practices" and "Best practices for protecting secrets", learn.microsoft.com. Microsoft content, own-words summary, much shorter than the source. Previous: Azure Security 1: The Microsoft Cloud Security Benchmark and Secure Future Initiative. Next: Azure Security 3: The Azure SQL Security Checklist and Well-Architected Security Principles.

Takeaways
  • Identity is the primary perimeter (Zero Trust): one Entra directory, MFA, Conditional Access, RBAC, and Privileged Identity Management for admin roles.
  • Network: segment, avoid broad allow rules, disable direct RDP and SSH from the internet, reach PaaS through Private Link, protect against DDoS.
  • Data and keys: encrypt at rest and in transit, use Key Vault, and on suspected key compromise rotate before disabling.
  • Secrets: never hard-code, scan for them, store in Key Vault, use managed identities, rotate, log access.
  • Compare with AWS Security Pillar 2: Identity Management, AWS Security Pillar 5: Infrastructure Protection and AWS Security Pillar 6: Data Protection.

2.1 Identity management and access control

  • The articles align with Zero Trust:
    • identity is the primary security perimeter because network perimeters are porous (BYOD devices and cloud apps)
    • Microsoft Entra ID is the identity and access service.
  • Twelve practices:
    1. Treat identity as the primary perimeter; centre controls and detections on user and service identities.
    2. Centralise identity management:
      • one Entra directory as the authoritative source;
      • synchronise on-premises directories with Entra Connect, but do not synchronise highly privileged on-premises accounts (Domain Admins, Enterprise Admins), using OU or attribute filtering, so attackers cannot pivot from cloud to on-premises;
      • turn on password hash synchronisation (it also lets Identity Protection detect leaked credentials), even as a backup if you use federation;
      • use Entra ID for new applications (Entra B2B for guests and partners; Entra External ID for customer sign-up and sign-in).
    3. Manage connected tenants (security needs visibility across them).
    4. Enable single sign-on.
    5. Turn on Conditional Access: policies by group, location and app sensitivity; block legacy authentication protocols, which attackers use for password spray.
    6. Plan routine improvements, using Identity Secure Score to rank them.
    7. Enable password management: self-service password reset, monitor registration, extend cloud password policies on-premises with Entra password protection.
    8. Enforce multifactor verification for users.
    9. Use role-based access control: for example give security teams the Security Reader role at an appropriate management-group scope; use built-in roles before custom ones.
    10. Lower exposure of privileged accounts:
      • turn on Privileged Identity Management (time-limited elevation and notifications);
      • keep critical admin accounts as managed Entra accounts, not consumer accounts;
      • define at least two emergency (break-glass) access accounts, not tied to individuals, with a documented process;
      • make critical admin accounts passwordless (preferred) or MFA;
      • deprovision admin accounts when staff leave;
      • test admin accounts with realistic attack simulations.
    11. Control where resources are created.
    12. Use Entra ID for storage authentication; actively monitor for suspicious sign-ins (untraceable attempts, brute force, many locations, infected devices, suspicious IP addresses).

2.2 Network security

  • Centralise
    • core network functions (ExpressRoute, virtual network and subnet provisioning, IP addressing) and governance of security elements such as network virtual appliances
    • use a common set of tools for visibility.
  • Segment subnets:
    • use CIDR subnetting inside the private address space, put access controls between subnets, and never allow broad ranges (such as 0.0.0.0 to 255.255.255.255), which give a false sense of security and are found by red teams
    • make troubleshooting procedures forbid such rules.
  • Zero Trust: assume an attacker can compromise one endpoint inside the trusted boundary and spread, so do not rely on a trusted network.
  • Control routing: default system routes let VMs in a virtual network talk to each other and out to the internet; use user-defined routes to send traffic through a security appliance.
  • Virtual network appliances (from partners) add firewalling, intrusion detection and prevention, application control, anomaly detection, web filtering, anti-malware and botnet protection above what security groups give.
  • Perimeter networks (DMZ) concentrate access control, monitoring and logging at the edge, with DDoS protection, IDS/IPS, firewall policies and web filtering.
  • DDoS protection: enable it on virtual networks with public resources; choose Network Protection (many public IPs) or IP Protection (few); layer with a web application firewall.
  • Avoid internet exposure for hybrid links:
    • site-to-site VPN runs over the internet (the page cites a bandwidth of about 1.25 Gbps)
    • ExpressRoute is a dedicated link that avoids the public internet.
  • Disable direct RDP and SSH from the internet,
    • because brute-force attacks turn a compromised VM into a launch point
    • use other access options (for example point-to-site VPN for one user, site-to-site VPN for a network, ExpressRoute).
  • Use Private Link
    • so PaaS services (Storage, SQL Database) are reached through a private endpoint in your virtual network
    • traffic stays on the Microsoft backbone and public exposure is no longer needed.
  • Also: load balancing (Application Gateway with TLS termination, external and internal load balancers, Traffic Manager) for availability.

2.3 Data security and encryption

  • Choose a key management solution, with keys outside the data they protect.
  • Secure workstations: use privileged access workstations for sensitive tasks, and enforce endpoint protection wherever data is consumed.
  • At rest:
    • encrypt at host for VMs
    • encrypt before writing sensitive data
    • know key rotation behaviour (rotating a key encryption key re-wraps the data encryption keys without re-encrypting the data, and both old and new versions must remain available)
    • if a customer-managed key may be compromised, rotate and reconfigure dependent services before disabling or deleting the old key
    • use RSA-OAEP-256 for key wrapping (plain RSA-OAEP uses SHA-1 and is legacy).
  • In transit:
    • site-to-site VPN for multiple on-premises workstations
    • point-to-site VPN for one
    • ExpressRoute for large data sets, with application-level TLS on top if desired
    • HTTPS for storage access.
  • In use:
    • confidential computing protects data while processed, so you need not fully trust app vendors, hardware vendors or infrastructure providers
    • scenarios include preventing unauthorised access, meeting regulations, trusted multi-party collaboration and isolated processing.
  • Protect email, documents and sensitive data with classification and labelling.

2.4 Protecting secrets

Area Practice
Discovery audit for passwords, API keys, connection strings; do not hard-code secrets; scan code (Azure DevOps credential scanner, GitHub secret scanning)
Storage Azure Key Vault with envelope encryption; encrypt in transit; restrict access with firewalls and network security groups
Access managed identities for applications; least-privilege Azure RBAC on secrets
Lifecycle rotate regularly; distribute secrets safely and include recovery in disaster recovery plans
Monitoring log access with Key Vault logging, Azure Monitor or Event Grid
  • The article closes with a long list of service-specific guidance (App Service Key Vault references, Pipelines, Data Factory, Cosmos DB customer-managed keys and so on).

Summary points

  • Strong identity (MFA, Conditional Access, PIM) before anything else.
  • Close the doors (no public RDP or SSH, Private Link) and segment the rest.
  • Keys and secrets live in Key Vault; applications use managed identities.
Terms to carry forward
  • Entra ID: Microsoft's cloud identity service (formerly Azure Active Directory).
  • Conditional Access: policy-based sign-in decisions.
  • PIM: Privileged Identity Management, just-in-time elevation.
  • Private Link / private endpoint: private access to PaaS services.
  • Key Vault, managed identity: key and secret store; credential-free identity for apps.
  • Confidential computing: protecting data in use.
