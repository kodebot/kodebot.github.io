Azure Security 3: The Azure SQL Security Checklist and Well-Architected Security Principles

Source: Microsoft Learn, "Azure database security checklist" (page dated 2026-07-24) and "Security design principles" (Azure Well-Architected Framework), learn.microsoft.com. Microsoft content, own-words summary, much shorter than the source. Previous: Azure Security 2: Identity, Network, Data and Secrets Best Practices.

Takeaways
  • The database checklist groups Azure SQL Database and Managed Instance controls into protect data, control access, monitor proactively, and data integrity.
  • Built-in protections include TLS 1.2 or higher, transparent data encryption on by default, Entra authentication, firewall rules and Private Link, auditing and Defender for SQL.
  • The Well-Architected security pillar is built on Zero Trust (verify explicitly, least privilege, assume breach) and the CIA triad.
  • Only the opening sections of the pillar's integrity and availability guidance were read for this note.

3.1 Azure database security checklist

  • Azure SQL Database and Managed Instance include built-in controls to limit access, protect data and monitor threats: IP and virtual network firewall rules, Entra authentication, TLS, authorisation, encryption at rest and in transit, auditing and threat detection
    • The checklist is meant to be used after the Azure SQL Database security best practices article.
Group Control What it does
Protect data TLS encrypts data in motion; Azure SQL requires TLS 1.2 or higher
Transparent Data Encryption (TDE) encrypts data and log files at rest; on by default for new databases; bring your own key through Key Vault
Always Encrypted encrypts inside the client application so keys never reach the database engine, separating data owners from data managers
Column-level encryption symmetric encryption of specific columns
Control access Entra authentication centralised identity with single sign-on; SQL authentication with strong passwords is the alternative
Authorisation least-privilege role-based access
Network server-level and database-level IP firewall rules; virtual network service endpoints; Private Link with a private IP address in your network
Row-level security limits rows by user identity, role or execution context
Dynamic data masking masks sensitive data for non-privileged users without changing it
Data discovery and classification identifies and labels sensitive data
Monitor Auditing writes events to Storage, Log Analytics or Event Hubs
Defender for SQL detects anomalous activity including SQL injection, brute-force attacks and vulnerability exploits
Vulnerability assessment finds, tracks and helps fix database weaknesses; risk reports for compliance
Defender for Cloud central monitoring, with recommendations from the cloud security benchmark
Integrity Ledger tamper-evident, immutable record of transactions
  • Compare with the vendor-neutral guidance in Database Security 1: The OWASP Database Security Cheat Sheet: the same layers (network, transport, authentication, permissions, hardening) appear as Azure features.
  • Next steps named: configure firewall rules, protect data with encryption, enable auditing, enable Defender for SQL, review the best practices.

3.2 Well-Architected security design principles

  • A Well-Architected workload "must be built with a zero-trust approach" and resilient to attacks, balancing confidentiality, integrity and availability with business goals
    • Questions to ask: do defensive investments cost attackers meaningful effort and friction
    • will controls limit the blast radius
    • do you know what the workload is worth to an attacker
    • can you detect, respond and recover quickly?
  • Zero Trust compass:
    • Verify explicitly: only trusted identities, performing allowed actions, from expected locations.
    • Use least-privilege access: the right identities, permissions, duration and assets.
    • Assume breach: design compensating controls that limit damage if a defence fails.
  • Security is recurring, not one-off; security and reliability can pull in opposite directions because security design can add points of failure.

Plan your security readiness

  • Use segmentation for boundaries in the environment, processes and team structure
    • build skills with role-based security training
    • have an incident response plan using an industry framework (preparedness, detection, containment, mitigation, post-incident)
    • know compliance requirements
    • define team-level security standards across the lifecycle
    • align incident response with the organisation's security operations centre.

Design to protect confidentiality

  • Approaches paired with the Zero Trust principle each serves:
    • strong access controls on a need-to-know basis (least privilege);
    • classify data by type, sensitivity and risk (verify explicitly);
    • encrypt at rest, in transit and during processing by confidentiality level (assume breach);
    • guard against exploits that expose information (verify explicitly);
    • guard against data exfiltration, malicious or accidental (assume breach);
    • keep the confidentiality level as data flows through components;
    • maintain an audit trail of all access (assume breach).

Design to protect integrity

  • Prevent tampering with business logic, flows, deployment processes, data and lower layers such as the operating system and boot sequence, because lack of integrity can lead to breaches of confidentiality and availability
    • Start with strong authentication and authorisation, minimising access by privilege, scope and time
    • The rest of the integrity and availability sections were not read for this note.

Summary points

  • For Azure SQL: encrypt (TLS, TDE, Always Encrypted), restrict (Entra, firewall, Private Link, RLS, masking), watch (auditing, Defender), verify (ledger).
  • Design from Zero Trust: verify explicitly, least privilege, assume breach.
Terms to carry forward
  • TDE: transparent data encryption at rest.
  • Always Encrypted: client-side encryption keeping keys from the database engine.
  • Row-level security / dynamic data masking: row filtering and display masking.
  • Ledger: tamper-evident transaction history.
  • CIA triad: confidentiality, integrity, availability.
