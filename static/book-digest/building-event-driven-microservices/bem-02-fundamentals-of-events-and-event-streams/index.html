Building Event-Driven Microservices 2: Fundamentals of Events and Event Streams

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 2. Previous: Building Event-Driven Microservices 1: Why Event-Driven Microservices. Next: Building Event-Driven Microservices 3: Fundamentals of Event-Driven Microservices.

Takeaways
  • An event is a recording of something that happened in the business, and it is the single source of truth. Events are immutable: correct them by publishing a new event.
  • An event stream is a durable, append-only, immutable log, partitioned, ordered per partition, indexed by offset, replayable, and able to keep events indefinitely.
  • Three delivery models: ephemeral messaging (at most once, not stored), queues (consumed and removed), event streams (retained, replayable): streams are the backbone of data communication.
  • Events are unkeyed, keyed or entity events. Keys give data locality; entity events carry full state (event-carried state transfer, ECST).
  • Kappa architecture (the stream is the only record) is preferred over lambda (stream plus a historical store).

2.1 What is an event?

  • Anything that happened within the scope of the business communication structure: receiving an invoice, booking a room, requesting a coffee, hiring an employee, finishing some code
    • Like an application log, but also the single source of truth, so it must contain everything needed to describe what happened.
  • Immutable: once published it cannot be modified. Mutating data already read by consumers is useless since they cannot easily be told; instead publish a corrective event.
  • Schemas: well-defined field names, types and defaults (Chapter 4).
  • The author avoids the word message:
    • it suggests a private note to a specific person that may be deleted after reading
    • Events are more like a post on a message board: public to anyone with access, readable many times, not deleted because it is old
    • "All messages are events, but not all events are messages"; the book uses event and record.

2.2 What is an event stream?

  • A durable and append-only immutable log:
    • producers append at the tail, consumers start at the head and read at their own pace
    • A timestamped sequence of business facts for a domain.
  • Properties:
Property Meaning
Immutability contents, offset position, timestamp and metadata cannot change; you only add events
Partitioned supports massive data sets; instances of a service consume partitions in parallel
Indexed each event gets an immutable index (offset) uniquely identifying it
Ordered records in a partition are served in publication order
Durability and replayability consume now or later; new and existing consumers can replay, given enough storage; not deleted on read or lack of consumers
Indefinite storage retain as long as needed; no forced expiry
  • Figure 2-1:
    • a stream with three partitions and a service with two instances
    • instance 0 consumes partition 0, instance 1 consumes partitions 1 and 2. Events were just appended at offset 5 (partition 0) and 7 (partition 1)
    • instance 1 is at offset 4 and has 5, 6 and 7 to process. A new consumer from the head must process everything to catch up.
  • Streams live on an event broker
    • Apache Kafka is the de facto standard. A topic is where events are written
    • the broker handles replication, rebalancing, client connections and access control.

2.3 Three ways to communicate: ephemeral, queue, stream

  • Ephemeral messaging
    • (Figure 2-2): a channel carries a message from a producer to current subscribers only
      • nothing is stored and messages are discarded if there is a failure or no subscriber (at-most-once; NATS.io Core, not JetStream)
    • A late subscriber gets only later messages
    • Good for low-overhead direct service-to-service communication where some loss is tolerable (Tinder uses NATS for update notifications: a missed push matters little)
    • It lacks the retention, durability and replayability needed for data products.
  • Queues
    • (Figure 2-3): a durable sequence of records awaiting processing
      • consumers compete first-come first-served, acknowledge per record, and the broker then typically deletes the record (unlike streams, which use partition-exclusive subscriptions and strict ordering)
    • RabbitMQ and Apache ActiveMQ support AMQP and MQTT
    • Typical use: a work queue
    • Usually at-least-once (a failed subscriber means reprocessing)
    • Queues can order by priority since they are not strict FIFO.
    • For several independent consumers: a per-consumer queue or a durable event stream.
    • Modern queue brokers
      • use an exchange that copies a record to each subscribed queue (Figure 2-4)
      • Some (Solace, RabbitMQ Streams) support replay and infinite retention
      • Queue TTLs were historically short, which fed the false notion that brokers cannot retain data; RabbitMQ and ActiveMQ allow unlimited TTL
      • Queues are good input buffers for parallelisable work where order does not matter, and consumers scale by registering more consumers.
  • Queues via Apache Kafka (KIP-932): new since the first edition (early access in Kafka 4.0). Using a stream as a queue had problems:
    • one consumer per partition in a consumer group;
    • head-of-line blocking (one slow record stalls the partition);
    • no per-record retry or failure marking (you acknowledge or redo a whole batch).
    • A share group (a KafkaShareConsumer) treats the topic's log like a queue: multiple instances per partition
      • individual acknowledgement
      • retries until a maximum (default 5) or success
      • processing time-outs that release records to other instances, and rewindable progress (data is not deleted after processing). It lets you use queue semantics without a dedicated queue broker.

2.4 The structure of an event

  • A record has a header, a key and a value (Figure 2-5 shows an ecommerce order with the items bought and total cost).
    • Header (record properties): metadata about the event, often broker-specific: datetimes, tracking IDs, user-defined key-value pairs that do not belong in the value.
    • Key (optional): usually routes the event to a partition so all records of one key are colocated; may represent a unique entity.
    • Value: the bulk of the data; if the key is a table's primary key, the value is the other fields.
  • Queues and ephemeral systems use similar but different conventions (routing keys, binding keys).
  • Unkeyed events
    • (Figure 2-6): no key, independent, no special routing
    • Often raw measurements: a camera photographing a car running a red light
    • It could have been keyed by camera ID, but this device records only in its own format; adding a key needs extra processing and a new stream.
  • Keyed events
    • (Figures 2-7, 2-8): a non-null key set by the producer, immutable once written; for the camera, the licence plate
    • All events with the same key go to one partition (data locality), so consumers can divide work per partition knowing key-based work reads one partition
    • FAST 321 has at least two red-light events.
  • Entity events:
    • represent a unique thing, keyed by its unique ID, describing its properties and state at a point in time (also state events)
    • Examples: Car, Driver, Tire, Intersection (Figure 2-9)
    • Like a database row: a primary key and current data, valid until it changes
    • Repaint the car blue and a new event carries the updated colour and datetime and all unchanged data too (Figure 2-10), which enables powerful things (Chapter 5)
    • The same key goes to the same partition (Figure 2-11: red then blue event for FAST 321); the producer appends a full entity event whenever the entity is created, updated or deleted.
    • Entity events enable event-carried state transfer (ECST): the entity's state travels in the event to all consumers, who can materialise it into their bounded context.

2.5 Repartitioning and copartitioning

  • Repartitioning
    • (Figure 2-12): a service reads one stream and writes another with a different key, key-to-partition mapping and/or partition count (two partitions to four)
    • It lets you join, group and aggregate streams of different partitioning
    • It may introduce out-of-order data (see "Multiple producers to multiple partitions", later).
  • Copartitioning
    • (Figure 2-13): two streams are copartitioned when they have the same key, same key-to-partition mapping strategy and same partition count
    • Required for primary-key joins, aggregations and reduce operations, assigning the same keyed data to the same instance
    • Instance 0 reads partition 0 of both streams, so all events with key A go to instance 0, key D to instance 1.

2.6 Aggregating and materialising state

  • Aggregation:
    • consume two or more events and combine into one result; a primary way to generate state from events
    • It needs durable state (so progress survives failure; Chapter 8)
    • Keyed events make it easy: one key is one partition
    • Reading several topics requires them to be partitioned identically, else repartition
    • Simple example (Figure 2-14): sum the traffic fines issued to a driver
    • Complex ones use several streams, event types and internal state machines.
  • Materialisation:
    • a projection of a stream into a table
    • Apply entity events in order, upserting each so the latest event per key is represented (Figure 2-15: FAST 321 and SJFH 372 hold their newest values)
    • The reverse also works: publish every table update as an entity event (Figure 2-16: BB upserted twice and DD once give three upsert events).
  • Stream-table duality:
    • a stream can be represented by a table and a table by a stream
    • this is fundamental to sharing state between services with no coupling. A relational table's insert, update and delete commands can be played from an immutable log (MySQL's binary log) to reconstruct it.
  • Deleting events and compaction:
    • you cannot delete a record like a table row because immutability is the point
    • Publish a tombstone: a keyed event with a null value (a Kafka convention)
    • It signals consumers the key's data is deleted, and enables compaction.
    • Compaction
      • is an asynchronous broker process keeping only the most recent event per key (Figure 2-17); older events are removed and the rest compacted into smaller files
      • It reduces disk and the events needed to reach current state, at the cost of losing part of the history
      • The tombstone itself is kept briefly (Kafka default 24 hours).
    • Guarantees: a minimum compaction lag (Kafka: min.compaction.lag.ms; for example 24 hours or 7 days so consumers read first), offsets unchanged (gaps appear; reading a removed offset errors), and consistency (a consumer from the start builds the same table as one running since the beginning).
    • Caution: manual deletion tools can have unexpected results because consumers' derived state is not fixed; preventing bad data is essential (Chapter 18).

2.7 Kappa and lambda architectures

  • Kappa
    • (Jay Kreps, co-creator of Apache Kafka and co-founder of Confluent, 2014): event streams are the sole record of current and historical data
    • Consumers start at the beginning and reach the head (Figure 2-18); no secondary store
    • Possible only with modern brokers and cheap cloud storage, no longer limited by mandatory TTLs
    • Services materialise their own state from the streams: simple code, no extra permissions.
    • Trade-offs:
      • each service builds its own state, so a large data set with few partitions can take hours or days (hydration time)
      • Mitigate with snapshots or backups of materialised state (Kafka Streams, Apache Flink, Spark Structured Streaming provide them)
      • Kappa gives one guarantee: the stream is the single source of truth.
// Example 2-1: joins with Kafka Streams
StreamsBuilder builder = new StreamsBuilder();

// Materializes the tables from the source Kafka topics
KTable products = builder.table("products");
KTable productReviews = builder.table("product_reviews");

// Join events on the primary key, apply business logic as needed
KTable productsWithReviews = products.join(productReviews, businessLogic(..), ...);
builder.build();

-- Example 2-2: joins with Flink SQL
CREATE TABLE PRODUCTS (
    product_id BIGINT,
    name VARCHAR,
    brand VARCHAR,
    description VARCHAR,
    timestamp TIMESTAMP(3),
    PRIMARY KEY (product_id) NOT ENFORCED,
) WITH (
    'connector' = 'kafka',
    'topic' = 'products',
    'format' = 'protobuf',
    'properties.bootstrap.servers' = 'localhost:9092',
    'properties.group.id' = 'foobar'
);

CREATE TABLE PRODUCT_REVIEWS (
    product_id BIGINT,
    reviews VARCHAR,
    timestamp TIMESTAMP(3),
    PRIMARY KEY (product_id) NOT ENFORCED,
) WITH (
    'connector' = 'kafka',
    'topic' = 'product_reviews',
    'format' = 'protobuf',
    'properties.bootstrap.servers' = 'localhost:9092',
    'properties.group.id' = 'foobar'
);

CREATE TABLE PRODUCTS_WITH_REVIEWS AS
SELECT *
FROM PRODUCTS
INNER JOIN PRODUCT_REVIEWS
ON PRODUCTS.product_id = PRODUCT_REVIEWS.product_id;
  • A KTable is a stream materialised into a table using ECST
    • both examples do a non-windowed inner join on the primary key into a denormalised, enriched table with a few lines of code (Part III goes deeper).
  • Lambda:
    • an event stream for real time plus a secondary repository for history; consumers load history first, then switch to the stream
    • It rests on the outdated idea that streams cannot hold events indefinitely
    • The book includes it for historical context, not as an endorsement.
    • Version 1
      • (Figure 2-19): stream and history built independently
      • often the history is just the source system's internal database, an antipattern that loads the producer
        • The producer writes both and not atomically, so an intermittent failure leaves them diverged
      • a stream-only consumer then differs from a new consumer built from history, hard to trace since stream data expires in days.
    • Version 2 (Figure 2-20): history built from the stream by a secondary process; resembles kappa with an awkward split.
    • Obstacles:
      • the producer maintains extra code
      • the consumer maintains two code paths and must switch without missing or duplicating data
      • results may not converge
      • data models must evolve in sync in two places
      • merging lambda data sets is nearly impossible (two streams need one reconciliation, kappa avoids crossover, lambda needs four).
    • Verdict: too difficult at scale and puts the onus of data access on the consumer; kappa is simpler.

2.8 Event data definitions and schemas

  • Event data is both long-term, implementation-agnostic storage and the communication mechanism, so producers and consumers need a common understanding: consumers should interpret an event without asking the producer's owner
    • It is analogous to an API definition for request-response services.
  • Schema technologies such as Apache Avro and Google's Protobuf provide an evolution framework (safe changes without downstream code changes) and generated typed classes for business logic (Chapter 4).

2.9 Powering microservices with the event broker

  • A cluster of distributed brokers provides:
    • scalability (add brokers for production, consumption, storage)
    • durability (replication)
    • high availability (clients reconnect to other nodes) and high performance (hundreds of thousands of reads or writes a second).

Selecting an event broker

  • Kafka is the book's example; consider factors rather than comparing products:
    • Support tooling (Chapter 19): browse records and schemas; quotas, access control and topic management; monitoring, throughput and lag.
    • Hosted services: exist? buy or host? monitoring, scaling, disaster recovery, replication, multizone? lock-in? professional support?
    • Client libraries and processing frameworks: your languages, ability to build missing ones, common frameworks or roll-your-own.
    • Community support: online help, maturity, use across organisations, attracting and exciting employees.
    • Indefinite and tiered storage:
      • store events forever with older segments on slower, cheaper storage
      • Tiered storage keeps a fast tier on broker memory or SSD and a cheaper tier in a large-scale store (Amazon S3, Google Cloud Storage, Azure Storage), moved asynchronously but still replayable through the consumer API
      • Ask: automatic? movable by usage? seamless retrieval?

Summary points

  • Streams give durable, replayable, scalable access: every consumer gets an identical copy if it reads as written.
  • Consumers no longer query the producer, removing point-to-point connections; they materialise and aggregate their own state.
  • The broker is the single source of truth for all data; local copies serve business logic.
