Building Event-Driven Microservices 3: Fundamentals of Event-Driven Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 3. Previous: Building Event-Driven Microservices 2: Fundamentals of Events and Event Streams. Next: Building Event-Driven Microservices 4: Schemas and Data Contracts.

Takeaways
  • An event-driven microservice is an ordinary application that is driven by events: it reads from streams, does work, and outputs events, API calls or other work. Idle without events (or a timer).
  • Four ways to build one: a basic producer/consumer, a stream-processing framework, a streaming SQL query, and connectors for legacy systems.
  • Every microservice has shared responsibilities: boundaries, scalability, state, stream progress, failure recovery, the single writer per stream principle, keys and partitioning, and schemas.
  • Keep services small enough for one person to hold in their head, and do not maximise the count. Budget for the microservice tax.
  • Containers dominate; microVMs offer stronger isolation. Service contracts still matter for request-response APIs, alongside data contracts for streams.

3.1 The basics

  • It needs the same compute, storage and network as any application, plus source storage, build and deploy tools, monitoring and logging.
  • Event-driven means events drive the business logic, as water turns a mill wheel (Figure 3-1). Work happens only when events arrive (or a timer expires, which is also an event).
  • A consumer reads events and tracks its own offset (position from the start of the stream) so many consumers progress independently
    • A consumer group presents several instances as one logical entity and allows horizontal scaling (Figure 3-2)
    • When an instance joins, partitions are redistributed (rebalancing); instances receive events only from their partitions
    • Local state may also need rebalancing (Chapter 8).

3.2 The basic producer/consumer

  • You write the operations that stitch the business logic together (Chapter 11)
    • Example 3-1 consumes events from the topic input_topic, tallies a sum per key and emits the total to a new stream when it exceeds 1000
    • Steps
    • create the KafkaConsumer (plain-text keys, JSON values),
    • create the KafkaProducer,
    • a state store (here an in-memory dictionary),
    • the endless polling loop,
    • poll a batch,
    • process per partition,
    • update the sum,
    • check the threshold,
    • write to key_sums,
    • flush
# Example 3-1: a basic producer consumer application that tallies a sum per key
# and emits it if the sum is greater than 1000
from kafka import KafkaConsumer, KafkaProducer
import json
import time

# 1) Initialize Kafka consumer
consumer = KafkaConsumer(
    'input_topic',
    bootstrap_servers=['localhost:9092'],
    value_deserializer=lambda x: json.loads(x.decode('utf-8')),
    key_deserializer=lambda x: x.decode('utf-8'),
    group_id='ch03_python_example_consumer_group_name',
    auto_offset_reset='earliest'
)

# 2) Initialize Kafka producer
producer = KafkaProducer(
    bootstrap_servers=['localhost:9092'],
    value_serializer=lambda x: json.dumps(x).encode('utf-8'),
    key_serializer=lambda x: x.encode('utf-8')
)

# 3) The state store is a simple dictionary
key_sums = {}

# 4) Polling loop
while True:
    # 5) Poll for new events
    event_batch = consumer.poll(timeout_ms=1000)

    # 6) Process each partition's events
    for partition_batch in event_batch.values():
        for event in partition_batch:
            key = event.key
            number = event.value['number']

            # 7) Update sum for this key
            if key not in key_sums:
                key_sums[key] = 0
            key_sums[key] += number

            # 8) Check if sum exceeds 1000
            if key_sums[key] > 1000:
                # Prepare and send new event
                output_event = {
                    'key': key,
                    'total_sum': key_sums[key]
                }
                # 9) Write to topic named "key_sums"
                producer.send('key_sums', key=key, value=output_event)
                # 10) Flushes the events to the broker
                producer.flush()
  • In real use pick a state store suited to the case instead of a dictionary: an RDBMS, a managed key-value store, graph or document store.
  • The example shows what nearly all event-driven microservices share: consumers, producers, state stores and a continual loop driven by arriving events, with business logic embedded in the loop.

3.3 The stream-processing microservice

  • Built on a stream-processing framework:
    • Apache Kafka Streams, Apache Flink, Apache Spark (the first edition also cited Storm and Samza, now less common)
    • They integrate tightly with the broker and give higher-level constructs (join streams and materialised tables easily).
  • Difference from a basic consumer: a framework needs a separate cluster (Flink, Spark: their own proprietary clusters for state, scaling, durability and routing) or a tight tie to a broker (Kafka Streams relies on the Kafka cluster for durable state, repartitioning and scaling).
  • Tip: frameworks often use a MapReduce, functional style: declare map, reduce, aggregate, join and filter. Chapters 12 and 13 cover them.
  • The Flink Java example (reproduced as printed): filter sales of 100 or more, join with payments on order_id, write to the topic PaymentsInnerJoinOrders:
// Flink table API example (reproduced as printed, abbreviated in the book)

// 1) TableEnvironment manages table access for the Flink application
TableEnvironment tableEnv =
    TableEnvironment.create(EnvironmentSettings.inStreamingMode());

// 2) Create the output table for joined results
tableEnv.executeSql(
    "CREATE TABLE PaymentsInnerJoinOrders (" +
    " order_id STRING," +
    " /* Add all columns you want to output here */" +
    ") WITH (" +
    " 'connector' = 'kafka'," +
    " 'topic' = 'PaymentsInnerJoinOrders'," +
    " 'properties.bootstrap.servers' = 'localhost:9092',"
    ")"
);

// Payments and Sales table definitions removed for brevity

// 3) Reference the Sales and Payments tables
Table sales = tableEnv.from("Sales");
Table payments = tableEnv.from("Payments");

// 4) Perform inner join between Sales and Payments tables on order_id
Table result = sales
    .filter { sale -> sale.total >= 100 }
    .join(payments)
    .where($("Sales.order_id")
        .isEqual($("Payment.order_id")))
    // 5) Declare your output schema in the JoinFunction
    .apply(new JoinFunction<> ...);

// 6) Insert the joined results into the output Kafka topic
result.executeInsert("PaymentsInnerJoinOrders");
  • Walk-through:
    • the tableEnv connection
    • declare the output table (once)
    • reference the Sales and Payments tables, which are materialised streams
    • declare the transformations: filter out sales.total < 100, then join
    • a placeholder where you merge matching events and declare the output schema, part of the data contract (Chapter 4)
    • write to the output table and Flink commits to the topic
  • These few lines also handle fault tolerance, load balancing, in-order processing and big-data scale, and can join streams and tables partitioned and keyed differently.
  • Frameworks need more upfront investment in supporting architecture and often support limited languages (Python and the JVM mostly); SQL variants are growing fastest.

3.4 The streaming SQL query

  • "Should my microservice just be a SQL query?" SQL's declarative nature (state the result, not how) suits streams, and managed streaming SQL services are growing.
-- The same application in Flink SQL; assume the tables have already been declared
INSERT INTO PaymentsInnerJoinOrders
SELECT *
FROM Sales s
INNER JOIN Payment p
ON s.order_id = p.order_id;
  • A streaming query is a long-running process that continually executes the logic, scaling up and down like any microservice (Chapter 14).
  • Streaming SQL is not standardised and depends on the framework; it needs robust lower-level APIs beyond toys. Flink has four layers, each depending on the ones below (Figure 3-3): SQL (high-level language)
    • Table API (declarative DSL)
    • DataStream (core APIs) and stateful stream processing (low-level building block of streams, state and event time).
  • Tip: look for chances to use streaming SQL; it can save a lot of time. Check what each framework supports.

3.5 The legacy application

  • Old but important systems, rarely changed, often gatekeepers to business data siloed in their database or files, not written for event-driven processing and unlikely to change.
  • Integrate them with connectors (Figure 3-4):
    • read events from a source system or database, convert to events and write to a stream
    • also read from a stream, convert and write to a legacy API or database. This gets value from streams without redesigning the whole system (Chapter 6).

3.6 Topologies

  • Microservice topology:
    • the event-driven logic internal to one service: transformation, storage, production of events
    • Figure 3-5: ingest stream A into a data store (materialise), ingest stream B, filter and transform, join on the materialised state, output to a new stream.
  • Business topology:
    • one level out: the microservices, event streams and APIs fulfilling complex business functions
    • an arbitrary grouping (a team, department, or superset of functions)
      • Microservices implement the bounded contexts and event streams share cross-context domain data
      • Figure 3-6: microservice 1 turns stream A into B
    • microservices 2 and 3 consume B
    • 2 acts strictly as a consumer and exposes a REST API for synchronous access
    • 3 transforms and outputs stream C. New services and streams are added asynchronously coupled. It does not show the inner workings of a service.

3.7 Responsibilities of an event-driven microservice

Responsibility Meaning
Service boundaries and scope enforce well-defined boundaries; mapping services to bounded contexts avoids ambiguity in multi-service workflows
Scalability scale horizontally (instances) or vertically (power); frameworks with built-in scaling are appealing; compute can be per service or a shared pool
State management solely responsible for creates, reads, updates and deletes of its store, including disk exhaustion and untested changes (Chapter 8)
Keep track of stream progress for example Kafka's consumer group per logical service; a consumer may manually set or store offsets (to replay)
Failure recovery return to a healthy state; resume from the last good offsets, which may cause duplicate processing and duplicate state updates; snapshots, restoration from streams and replay (Chapter 8)
The single writer per stream principle each event stream has one and only one producing microservice, the owner of each event; a known source of truth and traceable lineage; enforce with access control (Chapter 19)
Event keys and partitioning choose the output key and partition; same key usually same partition, with round-robin, random or custom strategies possible
Event schemas and data contracts define content with Avro, Protobuf or JSON schema (for example whether product_id is a string or an integer) for clear, healthy streams (Chapter 4)

3.8 How small should a microservice be?

  • The goal is not as many as possible ("you'd probably end up writing a blog about how you made 1,000 microservices and everything was awful")
    • Every service has overhead, yet avoid a monolith's pains.
  • Rules of thumb:
    • manageable by one team (two pizzas is an unreliable guide, "depending on how hungry your developers are")
    • one developer can hold the whole space of duties in their head
    • a newcomer learns what it does and how in a day or two. The real concern is that it serves a bounded context and a business need
    • size is secondary, and services at the upper end are fine if you can name the business concern, boundaries and a mental list of what it should and should not do.
  • Quick tips:
    • Build only as many services as necessary; more is not better.
    • One person should understand the whole service.
    • The team owns the service and its output event streams.
    • Add functionality to an existing service first; it saves per-application overhead.
    • Build modular components, so a module can later become its own service.

3.9 Managing microservices at scale

  • Each service needs compute, data stores, configuration and environment variables, and the owning team must be able to deploy it, so streamline DevOps
    • Containerisation, container management and infrastructure as code (IaC) are key (Docker, Kubernetes, Terraform; Chapter 19).
  • Containers:
    • package an application with its dependencies and share the host kernel: cheap, fast to start, consistent across environments. Trade-offs: the application must run on the host OS (a specialised OS needs an independent host)
    • security, because a kernel vulnerability puts every container on the host at risk, which matters in shared-tenancy clouds.
  • Virtual machines:
    • full isolation with their own OS and virtualised hardware
    • more secure but costlier, slower to start, larger
      • MicroVMs (Google's gVisor, Amazon's Firecracker, Kata Containers) have low overhead, start in under a second and give hardware-level isolation for multitenant services
      • Five years after the first edition, VMs of either kind are still rarer than containers, whose isolation and security have improved
    • use containers unless you have strict isolation requirements.
  • Container management systems (CMS):
    • Kubernetes, Docker Engine, Amazon ECS, Nomad control deployment, resource allocation and compute integration
      • Services must scale vertically and horizontally
      • Deploy each microservice as a single unit: often one executable in one container
    • complex ones need several containers and external stores, which a Kubernetes pod deploys and reverts as one action
    • one-off operations such as database migrations can run during deployment. VM management is more limited (Kubernetes and Docker Engine support gVisor and Kata; AWS supports Firecracker).

The microservice tax

  • The sum of financial, manpower and opportunity costs of the tools, platforms and components of a microservice architecture: running the event broker, CMS, deployment pipelines, monitoring and logging. Paid centrally it gives a unified, scalable framework
    • paid independently per team it gives overhead, duplicate solutions, fragmented tooling and unsustainable growth.
  • Also lost productivity while developers learn asynchrony, failure recovery and modularisation (especially juniors); resources and AI copilots help.
  • It is one of the biggest impediments to starting
    • Small organisations may do better with a modular monolith, expanding when scaling and growth demand
    • It is not all-or-nothing: invest incrementally
    • Self-hosted, hosted and fully managed options exist, and cloud services (managed CMS, brokers, monitoring, data catalogues, pipelines) have improved greatly since 2020 and make it easier to experiment before committing.

3.10 Service contracts

  • Service contracts set clear microservice boundaries and are critical for documentation, API management and knowing what you may access. OpenAPI and Swagger are the most popular.
  • A contract establishes:
    • service APIs (names, parameters, return types, protocols)
    • code generation (stubs)
    • documentation generated with the code so it matches
    • namespacing
    • versioning and change history
    • ownership
    • service-level objectives or agreements (the owner is responsible; an SRE may keep instances running), and breaking change management (mark APIs deprecated).
  • Event-driven services differ:
    • communication is via streams, not point-to-point, so many of these ideas do not apply
    • the next chapter covers data contracts. Services that offer both request-response APIs and event streams need both service contracts and data contracts.

Summary points

  • Microservices are applications driven by events; they may be written in many languages, though frameworks limit the choices.
  • They own their code, state and runtime properties and are deployed in containers or VMs managed by a CMS.
  • Pay the microservice tax incrementally, reuse what you have first, and get one service running before iterating.
