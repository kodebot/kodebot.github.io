Building Event-Driven Microservices 6: Integrating Event-Driven Architectures with Existing Systems

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 6. Previous: Building Event-Driven Microservices 5: Designing Events. Next: Building Event-Driven Microservices 7: Denormalization and Eventification.

Takeaways
  • Data liberation publishes cross-domain data from existing stores to event streams, making the stream the single source of truth and ending point-to-point coupling.
  • Never dual write to a store and a stream: no atomic commit exists across them.
  • Three patterns: query-based, log-based (change-data capture, CDC) and outbox table. CDC (for example Debezium) is the usual tool; the outbox gives the strongest isolation and schema guarantees.
  • Snapshot first, then capture live changes; avoid table locks.
  • CDC frameworks are a bootstrap, not the destination: move active products toward native event production.

6.1 What is data liberation?

  • Data liberation
    • is identifying and publishing cross-domain data sets to event streams, part of a migration strategy
    • Point-to-point dependencies (three services querying a legacy system directly, Figure 6-1) show what to liberate
    • Afterwards systems couple only on event streams (Figure 6-2).
  • Sinking is the reverse: events are written into an existing store when a legacy application cannot read streams.

The dual write antipattern

  • A service writes to two independent stores (a state store and an event stream); a simple transaction cannot cover both (Figure 6-3)
    • Commit to one may succeed while the other fails (invalid schema, service permanently moved, long outage)
    • Retries run out, and the data permanently diverges.
  • Two-phase commit (2PC) is not supported by many data stores or brokers; Kafka's 2PC project was in progress at publication.

The three liberation patterns

  • Liberated data must be the entire data set and stay up to date with inserts, updates and deletes:
    • Query-based: query the store; any store works.
    • Log-based: follow the append-only log; only for stores that keep one.
    • Outbox table-based: write to a table used as an output queue; another process publishes then deletes the entries; needs transactions and a queue-like table.
  • Common to all: emit in sorted timestamp order using the source record's most recent updated_at in the event header, so the stream is timestamped by when it occurred, not when it was published (Chapter 9).
  • Frameworks: Kafka Connect (Kafka only), Debezium, Apache NiFi: many off-the-shelf connectors, custom connectors possible, scalable, Confluent schema registry integration (customisable for others).

6.2 Change-data capture

  • Relies on the store's immutable log (MySQL binary log, PostgreSQL write-ahead log), which records a write before applying it so a crash can be replayed
    • CDC tails the log, converts each change (record creation, deletion, update, plus data set and schema changes) into events and writes them to a stream
    • Some stores (MongoDB Change Streams, Couchbase's replication protocol) expose event APIs instead.
  • The log seldom holds the whole history, and not every store has a log or an off-the-shelf connector; it fits mostly relational databases such as MySQL and PostgreSQL.
  • Figure 6-4: a MySQL binary log; a Kafka Connect service running a Debezium connector parses it into events; an event router emits each to a stream per source table.
  • CDC gives every change (no missed transitions)
    • Configuration chooses fields (filter out internals) and metadata (serverId, transactionId), and often uses before/after fields (Chapter 5)
    • Checkpoint progress; recovery gives at-least-once production, fine for entity data because updating entity data is idempotent
    • Debezium is the most popular, supporting many stores and producing to Kafka and Apache Pulsar.

Snapshotting the initial data set

  • The log keeps only a short window (for example several GB)
    • Snapshotting (bootstrapping) loads all current data into the stream from the store itself: query, copy, convert and write every entity, resource-intensive
    • Ensure overlap between snapshot and log so no record is missed when switching to live CDC.
  • It usually needs a consistent set of data, so it may lock the table for hours. Options: snapshot from a read-only replica
    • or Debezium's non-locking incremental snapshot, based on Netflix's DBLog paper (Andreakis and Papapanagiotou): watermarks interleave log events with selected rows, selects run in chunks with progress tracked (pause and resume), no locks, minimal source impact
      • A snapshot row is discarded if a newer log record for the key was already written
    • then CDC tails the log indefinitely.

Benefits and drawbacks of log-based CDC

  • Benefits:
    • Delete tracking (deletions become tombstones).
    • Minimal effect on performance for log-based stores (change tables such as SQL Server's cost by volume).
    • Low latency.
    • Non-blocking snapshots.
  • Drawbacks:
    • Exposure of internal data models through the changelog.
    • Denormalisation outside the store: highly normalised streams force downstream joins (Chapter 7).
    • Brittle dependency between source and event schema (a type change may break consumers).

6.3 Liberating data with a polling query

  • Query, convert to events, write; use Kafka Connect or Debezium rather than rolling your own
    • It uses only the store's query API (no log)
    • Two stages: the initial snapshot (as above, with no log to switch to) and the incremental phase.
  • Needs a record of what changed:
    • an updated_at or modified_at column is the high-water mark
    • iteration n+1 selects records after n. The Kafka Connect JDBC connector modes (quoted from its documentation): incrementing (a strictly incrementing column; detects only new rows, not modifications or deletions)
      • timestamp (detects new and modified rows; values monotonically incrementing, not necessarily unique)
      • timestamp+incrementing (two columns; a globally unique ID gives each row a unique stream offset). Schemas are inferred from query results by frameworks
    • if you roll your own, you generate them. If the source model changes, the event schema may too.
  • Locking tables is heavy in polling. A dated process: CDC is far more common now, and polling is for stores and APIs with no log access.

Incremental updating steps

  1. Ensure the field exists (a timestamp or auto-incrementing ID, populated by the store); without it incremental updates are impossible.
  2. Choose the polling frequency: higher means lower latency but more load; the interval must allow a query to finish, or race conditions let older data overwrite newer.
  3. Do one bulk load of all existing data before enabling incremental updates.
  • Benefits:
    • customisability
    • independent polling periods (tight SLAs get frequent queries)
    • isolation of the internal model via views or materialised views. Caution: the liberated data becomes the single source of truth, so consider whether concealed data should be liberated or the source refactored (common with legacy systems where business and entity data are intertwined).
  • Drawbacks:
    • required updated-at timestamp
    • detects only soft deletes (an is_deleted column)
    • brittle schema dependency (more likely when liberation is separate from the store's codebase)
    • may miss intermediate values (several changes between polls show as one)
    • consumes production resources (a read replica helps at extra cost)
    • query performance varies with data size (worst case all data changes each time, causing races)
    • transactional inconsistencies (a record may reference one not yet captured).

6.4 Transactional outbox tables

  • A dedicated table buffering data bound for the stream. When the internal model updates, select only the data to expose and write it to the outbox
    • a separate asynchronous process (such as a CDC connector) reads the outbox and writes to the stream (Figure 6-5)
      • The store's transactions make the outbox a write-ahead log: the internal update and outbox write succeed or fail together
      • After commit to the stream, delete the outbox record
    • failures keep records without loss. At-least-once delivery.
  • Example 6-1 (Python, MySQL): update EcomItem's price, select the name and price, insert into EcomItem_Outbox, commit atomically, roll back on error (the book's example connection used a literal user and a placeholder password; omitted here):
# Example 6-1: atomic update of the internal model and the transactional outbox
try:
    conn = mysql.connector.connect(host='localhost',
                                   database='python_db',
                                   user='<user>',
                                   password='<password>')
    conn.autocommit = False
    cursor = conn.cursor()

    # 1) Update the internal domain model
    internal_model_update = """
    Update EcomItem
    set price = 1299.99
    where id = 4291"""
    cursor.execute(internal_model_update)

    # 2) Select data from the internal domain model to write to the outbox
    internal_sub_model_query = """
    Select name, price
    from EcomItem
    where id = 4291"""
    cursor.execute(internal_sub_model_query)
    name_and_price = cursor.fetchone()

    if name_and_price is None:
        raise Exception("Unexpected missing record. Can't get name_and_price")

    # 3) Insert the selected data into the outbox
    outbox_insert = """INSERT INTO EcomItem_Outbox (id, name, price)
    VALUES (4291, %s, %s)"""

    # Pass the name and price in to replace the query wildcards
    cursor.execute(outbox_insert, name_and_price)

    # Commit the internal and outbox updates atomically
    conn.commit()

except mysql.connector.Error as error:
    # Revert changes due to exceptions
    conn.rollback()

finally:
    # Close the database connection
    if conn.is_connected():
        cursor.close()
        conn.close()
  • Table 6-1 (outbox definition):
    • id INT NOT NULL, name VARCHAR(255), price DECIMAL(13,2) NOT NULL, Datetime defaulting to CURRENT_TIMESTAMP, ordering_id INT NOT NULL AUTO_INCREMENT. NOT NULL makes an insert fail unless the mandatory event fields are present
    • the default timestamp may populate event metadata.
  • Tip:
    • the outbox schema and event schema must map 1:1
    • validate them with predeployment scripts. The outbox is relatively invasive: it needs changes to the store or application layer and their owners' involvement.
  • Built-in change-data tables (SQL Server) can be read with the query-based pattern via Kafka Connect or Debezium.
  • Outbox records need a strict ordering identifier so intermediate states emit in order
    • alternatively upsert by primary key and forgo intermediate states (overwritten ones are never emitted).
  • Performance: the extra load may be unnoticeable for small stores but expensive for large ones with many tables; weigh against a reactive strategy (parsing CDC logs).

Isolating internal data models

  • The outbox need not map 1:1 with the internal domain: normalised tables built for relational operations suit consumers poorly, and exposing them as separate streams forces every downstream team to reconstruct the domain. Warning: exposing the internal data model is an antipattern
    • consumers should only see public data contracts (Chapter 4).
  • Options:
    • denormalise on insert so the outbox mirrors the public contract (extra performance and storage), or keep 1:1 streams and denormalise with a downstream processor (Chapter 7)
    • Teams often cite lack of resources, but the cost is paid either upstream once or by every consumer downstream
    • Isolation keeps services changing only for new business requirements.

Ensuring schema compatibility

  • Serialise before writing
    • (Figure 6-6): a failure rolls back the internal changes, so outbox and tables stay in sync
    • This is the strongest guarantee (the stream is a first-class citizen), and permits a single outbox with serialised content and an output_stream routing column (Figure 6-7)
    • Cost: serialisation overhead, and a failed serialisation stops the business process.
  • Serialise after writing
    • (Figure 6-8): independent outboxes per model mapped to each stream's public schema
    • the publisher serialises later (Figure 6-9, User and Account outboxes). A failure means the already committed transaction put incompatible data in the outbox and may not be reversible: expect many unserialisable events, manual salvage (even downtime), and events published out of order.
  • Benefits of outbox:
    • multi-language support
    • exactly-once outbox semantics (atomic creation, so no changes missed if in a transaction)
    • early schema enforcement
    • internal model isolation
    • denormalisation.
  • Drawbacks:
    • the database must support transactions
    • application code changes
    • business process performance impact (and failed transactions can block operations)
    • data store performance impact from many writes, reads and deletes.
  • Note: balance costs; some organisations parse CDC logs and leave cleanup downstream, but producer savings are "often dwarfed by the expenses incurred at the consumer side".

6.5 Capturing change-data using triggers

  • Older databases used triggers to build audit tables
    • an AFTER trigger on INSERT, UPDATE or DELETE writes a row to a change-data table, and if it fails the original command fails (atomic). Figure 6-10: user upserts captured with the insertion time and an auto-incrementing sequence ID for the publisher.
  • Validation against the event schema during a trigger is generally not possible: triggers run inside the database, with limited languages (PostgreSQL allows C, Python and Perl user-defined functions; many databases do not), and each trigger fires independently with real overhead
    • Figure 6-11: validate and serialise after the fact; failures need error handling, likely human
    • The change-data table is the bridge between internal and output schemas, so keep it in sync with the event schema and compare them in testing.
  • Triggers can work well in legacy systems (old technology, stable load, schemas unlikely to change)
    • Warning: avoid triggers whenever possible in favour of a designated CDC system (overhead and management complexity across dozens or hundreds of tables).
  • Benefits: supported by most relational databases; low overhead and easy maintenance for small, infrequently updated sets; customisable logic (expose only some fields).
  • Drawbacks:
    • inline performance overhead
    • change management complexity (code and data set changes may need trigger changes that get overlooked)
    • poor scaling (triggers scale linearly with data sets)
    • after-the-fact schema enforcement leaves unpublishable events in the table.
  • Tip: where triggers can run validation code (Python in PostgreSQL), you cut downstream risk at some cost.

6.6 Data definition changes under capture

  • Data definition
    • is the formal description of a data set (a table in DDL: names, types, indices)
    • Adding, deleting or renaming columns, changing types and defaults are valid but can break liberated streams.
  • Get deeply integrated with the source's change management:
    • Observe data store pull requests for code touching captured stores.
    • Build integration tests that pull the event schema and compare it to the store's schema, notifying the developer in development.
    • Establish deployment validations by adding those tests to the pipeline (validate or override before deploying).
  • You are bridging two independent systems at a gap where team boundaries tend to lie
    • Tip: with an outbox the populating code lives in the same codebase, so breaking changes show as compile and test errors before production.

6.7 Compromises for data liberation

  • The liberated stream must eventually and accurately reflect the source
    • ECST consumers materialise it back into a table copy. Legacy systems restore from their own backups, snapshots and logs, so a restore may not match one built from the stream.
  • Ideal (Figure 6-12):
    • publish to the stream first, then read it back to build internal state: a single source of truth (the producer's materialisation converges with consumers') and failure recovery from the stream (rewind and replay)
    • Downsides: increased latency (network round trips), unsuitable for complex multistep transactions needing IDs and values from earlier steps (largely limited to basic upserts), and refactoring that legacy systems often cannot afford.
  • Compromise:
    • unidirectional event-driven architecture (the legacy system does not read back)
    • keep the internal data set synchronised with the stream through strictly controlled publishing
    • the stream is eventually consistent with the source (Figure 6-13).

6.8 Sinking event data to data stores

  • Sinking:
    • consume events and insert them into a store, via a centralised framework or a standalone microservice. Works for entity, keyed and unkeyed events
    • tracks its own offsets and runs independently and invisibly to the destination application.
  • Uses:
    • replace point-to-point couplings between legacy systems (liberate from the source, sink to the destination)
    • batch big-data analysis via a distributed filesystem (HDFS, then Amazon S3, Azure Blob Storage, Google Cloud Storage) and table formats such as Apache Iceberg and Delta Lake.
  • Kafka Connect gives simple configuration on shared infrastructure; standalone microservice sinks are managed independently.

6.9 Impacts of sinking and sourcing on a business

  • A centralised framework is low-overhead and one team can serve many, best in large organisations with data in many stores
    • teams configure connectors without operational duties. Two traps:
    1. Shared responsibility: the framework team owns connector stability, but the source team may add or remove fields or change data volume and break connectors, which only the framework team notices: cross-team dependencies scale linearly.
    2. Over-reliance: systems stay ignorant of events and requisition new sources and sinks instead of refactoring; organisations get complacent.
  • Warning: CDC tools are not the final destination; they bootstrap. The broker is only as good as the quality and reliability of its data.
  • Counterintuitively, minimise CDC framework use and have teams implement their own change-data capture (the outbox pattern) despite extra up-front work: teams own publishing, no cross-team dependencies, and an "event-first" mind-set (data out there, not just data in here)
    • Use connectors for maintenance-only or resource-limited products
    • for new and active products, produce natively and schedule refactoring. Weigh each strategy's trade-offs
    • the data communication layer is only as good as its data.

Summary points

  • Data liberation creates a clean, consistent single source of truth, decoupling access from production and storage, and promoting new products.
  • Spectrum: careful integration (events emitted as written, maybe produced first, producers protecting consumers) to highly reactive (frameworks pull from datasets or CDC logs, broken schemas, exposed internals), which is unsustainable.
  • Culture decides success: data owners must produce clean, reliable streams; capture mechanisms are not the final destination.
Terms to carry forward

  • Query-based, log-based (CDC), outbox; snapshot; high-water mark; soft delete.
