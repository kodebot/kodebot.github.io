Building Event-Driven Microservices 7: Denormalization and Eventification

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 7 (portions appeared in Building an Event-Driven Data Mesh, O'Reilly 2023). Previous: Building Event-Driven Microservices 6: Integrating Event-Driven Architectures with Existing Systems. Next: Building Event-Driven Microservices 8: Stateful Event-Driven Microservices.

Takeaways
  • Streams sourced from relational tables (especially via CDC) are normalised; every consumer would repeat the same expensive, error-prone foreign-key joins.
  • Eventification denormalises and remodels those streams once, upstream, so consumers get easy-to-use events and couple on a public data contract.
  • Do it at the transactional outbox (inside the source transaction) or in a dedicated service (streaming SQL or a framework), ideally owned by the team that owns the source data.
  • Include commonly used data; leave out data that is large or changes frequently.
  • Choose Type 1 (overwrite) or Type 2 (append) handling for slowly changing dimensions.

7.1 The problem and the example

  • Relational databases resolve relationships at query time with all data available
    • Event-driven microservices work best when the data is in the event
    • Streaming joins are more complex than joins on static data and are slower and more expensive (Chapters 12 to 14).
  • Eventification
    • is an implementation pattern for denormalising and remodelling highly relational streams into forms suited to event-driven consumers, reducing the repetitive, error-prone, expensive denormalisation every consumer would do
    • Denormalising in a stream is harder than in tables, so decide carefully what goes in.
  • The example is an ecommerce marketplace (think Amazon, eBay, Alibaba, Etsy, Shopify):
    • Item (item_id 4291, name "Mirage Block Set", price 1299.99, merchant_id 4, updated_at) has a foreign key to Merchant (merchant_id 4, "Devin's Trading Cards", premium_partner true).
    • Item shares its primary key item_id with Inventory (quantity_in_stock 3).
    • premium_partner marks a paid premium experience (better advertising, placement and search; video, extra pictures, bundles, AI-generated custom deals)
      • Most services need Item and Merchant for branding and premium treatment.
  • Without eventification (Figure 7-1) each consumer repeats the same join. Downsides:
    • Repeated processing: duplicate code and similar resource use per client; costly at scale with partitioned streams.
    • Significant client code constraints:
      • scalable streaming joins are mostly JVM-based (Kafka Streams, Flink, Spark), some Python and SQL
      • no first-class support for Go, JavaScript, Ruby, Rust. A dedicated relational database per service may not suit its other needs.
  • Solution: denormalise the merchant into an Enriched_Item (Inventory left out for now).
  • Factors:
    • Consumption patterns: ease of use is the chief goal; foreign-key denormalisation is often a top requirement.
    • Degree of denormalisation: depends on use cases, size and change frequency.
    • Keys for joining related streams: choose event keys that make joins easy (Inventory and Item share a primary key).
    • Structuring the external data model: convert and standardise data and conceal parts of the internal model, so consumers couple only on a public contract.
  • Two implementation places: within the source database (transactional outbox) or external, with a dedicated service.
  • Warning: some companies denormalise in their data lake: slow, expensive, and it makes consumers responsible for denormalising and standardising, which hurts data quality.

7.2 Where to eventify

At the transactional outbox

  • Select internal model data and denormalise it before writing to the outbox
    • Example 7-1 (based on Example 6-1) joins Item and Merchant inside one transaction and writes Enriched_Item_Outbox:
# Example 7-1: eventification and denormalisation prior to writing event data to the outbox for event 4291
try:
    # Stubbing out example code to save some space
    conn = ...
    cursor = conn.cursor()
    internal_model_update = ...

    # Commit the internal model updates
    cursor.execute(internal_model_update)

    # Select fields from the internal model and denormalize
    # by joining against the Merchant table
    internal_model_query = """
    select i.name, i.price, m.name as merchant_name, m.premium_partner
    from Item as i, Merchant as m,
    join on i.merchant_id = Merchant.id
    where i.id = 4291"""

    cursor.execute(internal_sub_model_query)
    result = cursor.fetchone()

    # Create the insert statement for the outbox table
    outbox_insert = """
    INSERT INTO
    Enriched_Item_Outbox (id, name, price, merchant_name, premium_partner)
    VALUES (4291, %s, %s, %s, %s)"""

    cursor.execute(outbox_insert, result)
    # Commit the internal and outbox updates atomically
    conn.commit()

except mysql.connector.Error as error:
    # Revert changes due to exceptions
    conn.rollback()

finally:
    # Close the database connection
    if conn.is_connected():
        cursor.close()
        conn.close()
  • The listing is reproduced as printed
    • its SQL has a stray comma and the query and execute variable names differ (internal_model_query versus internal_sub_model_query), which the book leaves as it is.
  • The internal relational model stays encapsulated; the outbox offers a model suited to consumers.
  • Catch:
    • when Merchant data changes (a merchant pays for premium status), every previously created Enriched_Item must be updated too, or the stream is permanently inaccurate
    • Whenever you denormalise (outbox or dedicated service) you must update the event whenever any included field changes.
  • An outbox decouples internal and external models at low overhead
    • It is not always possible: stores without transactions, frozen legacy systems, and strict performance requirements rule it out.

In a dedicated service

  • A purpose-built microservice or streaming SQL application outside the source joins the normalised CDC streams into one enriched stream (Figure 7-2) using Kafka Streams, Flink or Spark.
  • Example 7-2 (Flink SQL):
-- Example 7-2: a Flink SQL version of an eventification service for Item and Merchant
SELECT *
FROM Item
INNER JOIN Merchant
ON Item.merchant_id = Merchant.id
  • Tip:
    • windowing can limit materialised data size and improve performance
    • SQL is common, easy to read, and makes smuggled business logic easy to spot
    • The purpose is simple denormalisation, not business logic, filters or application-specific logic.
  • Warning: handle out-of-order data (Flink uses watermarks, Chapter 9; check others' documentation).
  • Advantages: reduced demand on the database, scales independently of it, simplifies source application logic.
  • Challenges:
    • synchronising changes to tables, connectors and the eventification service
    • few robust stream-joiner frameworks (JVM or SQL)
    • ownership arguments (the best owner is the team that owns the source data).
  • Wherever you denormalise (inside the database, a dedicated service, or the consumer), make data easy to understand, use well-defined schemas, and reduce the chance of misinterpretation.

7.3 What should go in the event, and what should stay out?

  • Balance consumer needs, update frequency, data size and total load.
  • Frequency:
    • every inventory change (sale, return, shipment; a Black Friday "door crasher") would trigger a join and re-emission of the Item
    • Consumers that ignore quantity still process inconsequential updates, at cost for producer and consumer
    • The Inventory producer could emit periodically (for example every 5 or 30 seconds), trading latency for fewer updates.
  • Size: a Reviews table of the top 100 reviews per Item rarely changes, but joining it re-emits the whole payload on every Item or Reviews update, burdening consumers that never use it.
  • Both: high rate of change times large size compounds load on the broker, the eventification process and consumers: "very expensive".
  • Rule of thumb:
    • avoid joining in data that changes frequently or is large
    • let consumers integrate it themselves. Figure 7-3: Enriched_Item includes the commonly used data, omits Reviews (size) and Inventory (frequency). No magic cut-off exists
    • these are heuristics.

7.4 Slowly changing dimensions

  • Many Items belong to one Merchant, whose name or location rarely changes but could at any moment
    • This is a slowly changing dimension (SCD): usually static, changes unpredictably (a term from data analytics, useful here).
  • Relational databases normalise it into its own table and update one row
    • Event streams resemble the document model: if you denormalise Merchant data into millions of Items, you must update all those events when it changes
    • Of at least eight SCD subtypes, Type 1 and Type 2 matter most for event streams.

Type 1: overwrite with the new value

  • Only the most recent value is kept. Example 7-3 (Devin's Trading Cards, premium_partner: false) then Example 7-4 (true, new updated_at) as a new entity event overwriting the old:
{
    "name": "Devin's Trading Cards",
    "premium_partner": false,
    "updated_at": "2011-08-10 13:22:09"
}

{
    "name": "Devin's Trading Cards",
    "premium_partner": true,
    "updated_at": "2019-08-12 19:00:27"
}
  • The broker can compact away the old event; retaining longer is optional but Type 1 does not model a change history.

Type 2: append the new value

  • The changed value is appended to the state and emitted as a new event, so the consumer sees current and previous versions and can reconstruct the entity at a point in time: one service reacts to premium_partner true while analytics track premium status over time
    • The producer must track what it has already written
    • Example 7-5 (with version IDs):
[
    {
        "name": "Devin's Trading Cards",
        "premium_partner": false,
        "updated_at": "2011-08-10 13:22:09",
        "version": "0"
    },
    {
        "name": "Devin's Trading Cards",
        "premium_partner": true,
        "updated_at": "2019-08-12 19:00:27",
        "version": "1"
    }
]
  • The default is usually Type 1: publish the latest data and let the stream hold prior values; the consumer opts in to keeping previous values in its own store.
  • Type 2
    • forces the consumer to consider the dimension changes: joins give different results depending on the point in time represented, and a consumer wanting only the latest must select it explicitly
    • More verbose and more overhead, but it reduces the chance a consumer overlooks the history.

Summary points

  • Many source structures convert poorly to events; relational models (especially via CDC) cause tight coupling, repetitive and expensive joins, and overly complex microservices.
  • Eventification (outbox or standalone application) also decouples internal from external models. **Limit it to simplifying formats through joins and standardisation
    • custom consumer business logic belongs downstream.**
  • Event size and update frequency are the main factors; be careful adding information that is rarely used, very large, or causes a high update rate.
Terms to carry forward
  • Eventification; enriched event; foreign-key join.
  • Slowly changing dimension; Type 1 (overwrite), Type 2 (append).
