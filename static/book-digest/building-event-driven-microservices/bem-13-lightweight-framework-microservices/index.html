Building Event-Driven Microservices 13: Lightweight Framework Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 13. Previous: Building Event-Driven Microservices 12: Heavyweight Framework Microservices. Next: Building Event-Driven Microservices 14: Streaming SQL.

Takeaways
  • Lightweight frameworks need no dedicated cluster: they rely on the event broker and the container management system (CMS) to scale, keep state and recover.
  • Apache Kafka Streams is effectively the only widely used one (it is part of Apache Kafka); Apache Samza and the Python Faust framework have faded.
  • They offer much of what heavyweight frameworks do (declarative topologies, table materialisation, primary and foreign-key joins, groupings, windows, aggregations) that a basic producer/consumer lacks.
  • Shuffling goes through internal event streams in the broker; state sits in internal stores backed by changelogs. Scaling needs no restart but has a rematerialisation pause, reduced by hot replicas.

13.1 What lightweight frameworks are

  • Unlike heavyweight frameworks they do not require a dedicated processing and resource management cluster
    • they use the event broker and the CMS to scale, manage state and recover from failures.
  • History:
    • the first edition identified only Apache Kafka Streams and Apache Samza
    • Kafka Streams remains the only one in widespread use, as a core component of Apache Kafka
    • Samza's use and release cadence have diminished; the author would not start a new project with it over Kafka Streams
    • Others have faded too, such as the open source BSD-licensed Python Faust framework: not that nobody uses them, but the critical social mass to keep up with broker changes has gone
    • Building a full-featured, durable, reliable and scalable framework is hard, and with other off-the-shelf options it is hard to rally enough developers and users.
  • The chapter leans on Kafka Streams, which is perhaps the only one still in the toolkit in another five years thanks to its embedding in Kafka.

13.2 Example: joining products with brand data on a foreign key

  • Connectors pull brand and product data from an ecommerce database into two streams (Figure 13-1). Product holds what it is, a text description, price and a foreign key to the brand (brandId)
    • brand holds the official name and a logo link for advertising.
  • Kafka Streams joins them on brandId to produce an EnrichedProduct stream by denormalising with brand data (Example 13-1, slightly abbreviated):
// Example 13-1: a Kafka Streams microservice joining and enriching Product with Brand data
public Topology buildTopology(Properties envProps) {
    // Configuration code not shown for brevity
    // 1) Create the Kafka topic Serializer/Deserializers, aka Serdes
    BrandSerde brandSerde = new BrandSerde(...);
    ProductSerde productSerde = new ProductSerde(...);
    EnrichedProductSerde enrichedProductSerde = new EnrichedProductSerde(...);

    // 2) Create the stream builder
    KStreamBuilder builder = new KStreamBuilder();

    // 3) Declare two KTables
    KTable<Long, Brand> brandTable =
        builder.table(Serdes.Long(), brandSerde, "brand-topic");
    KTable<Long, Product> productTable =
        builder.table(Serdes.Long(), productSerde, "product-topic");

    // 4) Declare the join, providing the joiner function
    productTable
        .join(brandTable, Product::getBrandId, new ProductToBrandJoiner())
        // 5) Convert back to a stream and write to the output
        .toStream()
        .to("enriched-product-topic",
            Produced.with(Serdes.Long(), enrichedProductSerde));

    // 6) Build and return the declared streaming topology
    return builder.build();
}

// Example 13-2: the ProductToBrandJoiner used to populate the enriched item
public class ProductToBrandJoiner implements
    ValueJoiner<Product, Brand, EnrichedProduct> {

    public EnrichedProduct apply(Product p, Brand b) {
        return EnrichedProduct
            .newBuilder()
            .setId(p.getId())
            .setName(p.getName())
            .setDescription(p.getDescription())
            .setPrice(p.getPrice())
            .setBrandName(b.getBrandName())
            .setBrandLogoURI(b.getBrandLogoURI())
            .build();
    }
}
  • Steps:
    • Serdes (serialiser and deserialiser) convert Kafka byte arrays into Avro, Protobuf or JSON Schema objects mapped to plain Java objects
    • the stream builder declares the topology
    • two KTables materialise brand-topic and product-topic
    • a table-to-table join with a ValueJoiner (ProductToBrandJoiner) saying how to merge the entities
    • convert back to a stream and write to enriched-product-topic
    • build the topology, which the calling class sets up to begin streaming. See the official documentation for foreign-key joins
  • Lightweight frameworks give stream-processing features comparable to heavyweight ones for those who want the advanced features without running their own clusters: declarative topologies, table materialisation, primary and foreign-key joins, groupings, windowing and aggregations, all missing from a basic producer/consumer.

13.3 Under the hood

  • Defined by a lightweight deployment model:
    • deploy like any event-driven application using native CMS functions, changing parallelism by adding or removing instances. No secondary cluster (as with Flink or Spark) for durable state, recovery or scalability
    • they rely mainly on the event broker, and to a lesser extent the CMS.

Event shuffling and repartitioning

  • Shuffling relies on internal event streams hosted by the broker: the producer writes events to their partitions through an internal stream, consumed by downstream instances of the same application
    • Key-based operations (joins, groupByKey with reduce or aggregate) need same-key data on one instance, so events pass through an internal stream with each key in a single partition (see "Copartitioning Event Streams").
  • The internal stream acts like the external shuffle service described for heavyweight frameworks (Figure 13-2)
    • each repartition stage uses its own dedicated internal stream, hosted by the same broker.
  • Caution: internal streams are private; no other microservice uses them. Do not couple microservices on internal streams.
  • Because in-flight events are durably retained in the broker, the application scales dynamically. The trade-off is increased latency, unavoidable because there are no other shuffle options
    • Kafka Streams is bound entirely to Apache Kafka.

State and changelogs

  • In-memory and disk-based key-value stores
    • are most common, since the domain-specific language (DSL) is based on manipulating and storing keys and values
    • By default: internal state stores backed by changelog streams in the broker (see Chapter 8).
  • Tip: since every lightweight application is independent, one can request instances with very fast local disk while another asks for very large, slower drives.
  • You can extend them to plug in other storage by implementing the storage interface (for example the Kafka Streams StateStore interface), allowing external stores or alternative storage and query models: for example Amazon DynamoDB instead of an internal key-value store.

Scaling and recovering from failures

  • Scaling and failure recovery are very similar:
    • adding an instance (intentionally, or a recovering one) needs partition and state assignment
    • removing one needs reassigning partitions and state to a live instance.
  • Main benefit:
    • dynamic scaling, no restart to change parallelism, though processing may pause for consumer group rebalancing and rematerialisation from the changelog
    • Figure 13-3: assigned input partitions (including internal streams) are rebalanced and state is restored from changelogs before work continues.

State assignment

  • An instance with new internal state must load the changelog before processing new events, like loading a checkpoint in heavyweight systems.
    • Operator state (<partitionId, offset> for all partitions, input and internal) is stored in the application's consumer group.
    • Keyed state (<key, state>) is stored in each state store's changelog.
  • During the state restoration phase all internal state must be loaded before new events
    • processing earlier risks nondeterministic results. Once every store is restored, consumption of input and internal streams resumes.

State replication and hot replicas

  • A hot replica (see Chapter 8) is a copy of a state store materialised from the changelog: a standby fallback for a failed primary, and a way to scale down gracefully: on termination and rebalance, partitions are assigned to use the replica's state without interruption
    • Cost: additional disk and processor usage.
  • Scaling up currently looks like:
    • start an instance
    • join the consumer group and rebalance
    • pause while state is materialised from the changelog (can take time)
    • resume
      • An option: populate a replica of the state on the new instance, wait until it catches up to the head of the changelog, then rebalance to give it ownership of the input partitions
      • This reduces outages and needs extra bandwidth only from the broker
    • it is under development for Kafka Streams.

Summary points

  • Lightweight frameworks need no independent cluster; they rely on the broker and CMS for scaling, shuffling and durability.
  • Kafka Streams relies extensively on broker integration and is the most popular lightweight framework in use
    • Apache Samza's popularity, use and project activity have dwindled since the first edition.
Terms to carry forward
  • Lightweight framework; Kafka Streams; KTable; Serde; ValueJoiner.
  • Internal (repartition) stream; changelog; state restoration phase; hot replica.
