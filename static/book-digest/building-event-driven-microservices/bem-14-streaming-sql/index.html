Building Event-Driven Microservices 14: Streaming SQL

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 14. Previous: Building Event-Driven Microservices 13: Lightweight Framework Microservices. Next: Building Event-Driven Microservices 15: Microservices Using Functions as a Service.

Takeaways
  • Streaming SQL is a declarative way to build microservice-like queries: say what the result should be and the engine does the work. It is usually a layer on a full-featured framework (Flink SQL, Spark SQL).
  • A continuous query runs indefinitely, applying the logic to each arriving event. Streams are declared as tables first: upsert, append-only or retraction.
  • No ANSI or other standard for streaming SQL: dialects differ in syntax and semantics.
  • Run it from a CLI, embedded in an application, a notebook, or a SQL gateway; use it as a sidecar and extend it with user-defined functions (UDFs).

14.1 The continuous query

  • Streaming SQL is a handy way to reduce the overhead of getting started with stream processing for anyone who knows SQL
    • It is most commonly a layer over a full-featured streaming framework (as in "The Streaming SQL Query"): Flink SQL and Spark SQL (with structured streaming)
    • The principles are largely the same across engines; this chapter covers only those two Apache projects.
  • There is no definitive streaming SQL standard (ANSI or otherwise): "a bit of a wild west" of dialects whose syntax and semantics differ, though not wildly, with plenty of documentation.
  • Streams-as-tables
    • is the basic abstraction
    • Figure 14-1: a query filters out events with a value less than or equal to 5 and passes the rest to the next stage (another query, a table materialisation, or an output stream).
  • A streaming query runs indefinitely, applying the logic to each event as received
    • a conventional query operates on the data present when run and terminates after iterating over its bounded data set. Both operate on tables, so the figure omits the necessary step of declaring a table on top of the stream.

14.2 Turning streams into tables

  • Three table types:
    • Upsert tables:
      • require a primary key
      • each event is an upsert or a delete, so a new record of a key overwrites the old one. Identical to a materialised table ("Materializing State from Entity Events").
    • Append-only tables:
      • no primary key
      • every record is inserted, keeping the complete history
      • records are immutable and cannot be deleted, like the append-only log behind the stream.
    • Retraction tables:
      • a more advanced type not in every framework
      • supports inserts, updates and deletions with the entire row acting as the key: insert with +I["Gary", 123] and remove with +D["Gary", 123]. They mainly reflect results of upstream computations, such as emitting from a Flink dynamic table.
  • Warning:
    • check that your framework supports at least both append-only and upsert tables
    • some support only append-only, significantly limiting what you can do. Most tables declared from streams are upsert or append-only.

14.3 Example: enriching data with Flink SQL

  • Declare a table over the Kafka topic Photographs:
CREATE TABLE Photographs (
    id BIGINT PRIMARY KEY NOT ENFORCED,
    photographer_id BIGINT NOT NULL,
    camera_id BIGINT NOT NULL,
    photo_url STRING NOT NULL,
    height INT,
    width INT
) WITH (
    'connector' = 'upsert-kafka',
    'topic' = 'Photographs',
    'key.format' = 'raw',
    'value.format' = 'json',
    'properties.bootstrap.servers' = 'broker.url:9092',
    'properties.group.id' = 'Photographs_group_id'
);
  • The framework registers the table's metadata in a metadata catalogue so other streaming SQL engines can query it, and uses the upsert-kafka connector to generate the materialised table (new events overwrite old values of the same key). Tip: the primary key is NOT ENFORCED because the table does not own the data
    • the producer service enforces the key.
  • Catalogue compatibility varies:
    • Flink supports several catalogue types (JDBC-based and Apache Hive)
    • Spark has an in-memory (local) catalogue and Hive
      • In production you likely need Hive or a Hive-compatible catalogue for durable metadata
      • Note: Hive is an older part of Apache Hadoop
    • you may use another data catalogue that implements the Hive API, a useful standard interface.
  • A second table, Photographers, uses the avro-confluent value format and a schema registry URL (Chapter 4), deserialising Avro with the registry's schema:
CREATE TABLE Photographers (
    kafka_key_id BIGINT PRIMARY KEY NOT ENFORCED,
    first_name STRING,
    last_name STRING,
    signup_date TIMESTAMP WITH TIME ZONE
) WITH (
    'connector' = 'upsert-kafka',
    'topic' = 'Photographers',
    'properties.bootstrap.servers' = 'broker.url:9092',
    'properties.group.id' = 'Photographers_group_id',
    'key.format' = 'raw',
    'key.fields' = 'kafka_key_id',
    -- Schema registry URL for deserializing the Avro value
    'value.avro-confluent.url' = 'http://schema.registry.url:8082',
    'value.format' = 'avro-confluent',
    'value.fields-include' = 'EXCEPT_KEY'
);
  • The output table (abbreviated in the book) and the join on the photographer_id foreign key:
CREATE TABLE Enriched_Photographs (
    id BIGINT PRIMARY KEY NOT ENFORCED,
    photographer_id BIGINT NOT NULL,
    camera_id BIGINT NOT NULL,
    photo_url STRING NOT NULL,
    height INT,
    width INT,
    first_name STRING,
    last_name STRING
) WITH (
    -- Omitting some of the table details for brevity.
    'connector' = 'upsert-kafka',
    'topic' = 'Enriched_Photographs',
    ...
);

INSERT INTO Enriched_Photographs
SELECT pics.id,
       pics.photographer_id,
       pics.camera_id,
       pics.photo_url,
       pics.height,
       pics.width,
       people.first_name,
       people.last_name
FROM Photographs AS pics
INNER JOIN Photographers AS people
WHERE pics.photographer_id = people.kafka_key_id;
  • The listings are as printed, except that a trailing comma in the Photographers options and in the select list is removed
    • The results are one row per photograph, emitted to the Enriched_Photographs topic
    • Photograph and photographer data is retained indefinitely within the Flink job, mirroring the key-space of the source topics
      • a tombstone on either source deletes the corresponding photographs and propagates to Enriched_Photographs.

14.4 Executing streaming SQL

  • Command-line interface (CLI):
    • in Flink SQL and Spark SQL, mostly for testing and local development (you could plug it into production, security issues notwithstanding)
    • Run ./bin/sql-client.sh (Flink) or ./bin/spark-sql (Spark) and type queries:
$ ./bin/sql-client.sh
Flink SQL> SELECT *
> FROM Photographers
> WHERE first_name = 'Adam'
> AND last_name = 'Bellemare';
  • A streaming query needs the CLI to remain running
    • terminating the CLI terminates the job (you could run it in a container like any microservice, but better production options follow).
  • Embedded in the application:
    • put SQL in native code, limited to the framework's languages (Java, Python and so on) but with much less code since most logic is embedded SQL
    • a templated code generator can produce boilerplate and dependencies. It fits microservice deployment pipelines, testing, scaling and monitoring:
// Create the Flink table environment
TableEnvironment tableEnv = TableEnvironment.create(...);
// Specify the external Hive catalog and choose the database
tableEnv.useCatalog("hive_ext");
tableEnv.useDatabase("photo_db");

// Create the Photographs table using SQL DDL
// The table metadata is written into the Hive catalog
tableEnv.executeSql(
    "CREATE TABLE Photographs (id BIGINT ...) WITH (...)");

// Query the Photographs table using SQL
tableEnv.executeSql(
    "SELECT * FROM Photographs WHERE first_name = 'Alice'");
  • Notebook:
    • an interactive browser-based device combining executable code, rich text, equations and visualisations
    • popular with data analysts, scientists and engineers, then in production pipelines. Free open source examples: Apache Zeppelin and Jupyter.
    • Benefits:
      • interactive development in small cells with immediate results
      • visualisations and documentation (Markdown, LaTeX)
      • container-like isolation (code, environment details, even data)
      • multi-language (Python, Java, Scala, R)
      • shareable like any file. Tip: notebooks are not only for SQL.
    • Interpreters connect a notebook to the engine (for example the Zeppelin interpreter for Flink); install separately or integrated.
    • Drawbacks:
      • version control complexity (large, binary-ish files; plugins such as Jupyter's nbdime or Jupytext help)
      • performance limitations at scale
      • testing limitations (extract business-critical logic into a dedicated project with unit and integration tests)
      • promotion limitations (hard to promote, roll back and manage permissions across environments).
    • Warning:
      • notebooks suit exploration and analysis
      • for production create a dedicated microservice and port the code. Stripped-down notebook-like hosted options (no download, a single language) are mostly a GUI to submit code to a SQL gateway.
  • SQL gateway:
    • a service letting multiple clients run SQL concurrently and remotely
    • each job runs in its own session using the processing cluster (Figure 14-2: one client submits a job, another checks the status of an existing one)
      • Examples: Spark distributed SQL engine and Flink's SQL gateway
      • Main benefit: no application to build
    • even the CLI can submit jobs. Ideal for simple, stable queries such as joiner services denormalising relational data.

14.5 SQL as a sidecar

  • SQL can provide sidecar capabilities (Chapter 11) for work too hard in the microservice, such as joins and complex aggregations that basic producer/consumer frameworks lack
    • Figure 14-3: a hybrid app where a SQL query materialises and joins Enriched_Photographs with a Cameras topic and writes a combined event to a new topic for the downstream microservice, named Private_Stream_F2AZ (a private placeholder name): purpose-built for that microservice, with the SQL joiner and microservice in one bounded context, private to the outside.
  • Best of both worlds: use any libraries, languages and frameworks compatible with basic consuming and producing, while joins, windowing, aggregations and complex event-driven state machines are offloaded to the SQL engine.
  • Warning: when terminating the microservice, terminate the SQL job too so no zombie processes remain; keep the two tightly coupled through their life cycle.

14.6 User-defined functions (UDFs)

  • A UDF is a custom function for operations hard to express in SQL, written in the framework's native language and called inline (Flink and Spark both support them)
    • Example: a Flink scalar UDF appending _modified to a string:
import org.apache.flink.table.functions.ScalarFunction;

public class AppendModifiedUDF extends ScalarFunction {
    public String eval(String input) {
        if (input == null) {
            return null;
        }
        // Append '_modified' to the input string
        return input + "_modified";
    }
}
  • Three main types by records in versus out:
    • one in, one out
    • many in, one aggregated out
    • one in, many out. UDFs can modify values, build aggregations, calculate complex state machines, and call external systems (third-party services, GenAI models).

Summary points

  • Streaming SQL makes stream processing more accessible by treating streams as tables with a continuous query
    • the stream-to-table step is critical. Upsert and append-only tables serve different needs.
  • Execution options (CLI, embedded, notebook, gateway) fit different stages from local development to production; UDFs extend SQL with custom logic.
  • While streaming SQL commonly comes with a serverless framework, it is not the only serverless option: functions as a service follows.
Terms to carry forward
  • Continuous query; upsert, append-only, retraction tables; metadata catalogue (Hive).
  • SQL gateway; SQL sidecar; UDF.
