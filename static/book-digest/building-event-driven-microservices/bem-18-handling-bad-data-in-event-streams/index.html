Building Event-Driven Microservices 18: Handling Bad Data in Event Streams

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 18. Previous: Building Event-Driven Microservices 17: Integrating Event-Driven and Request-Response Microservices. Next: Building Event-Driven Microservices 19: Supportive Tooling.

Takeaways
  • Bad data does not conform to what is expected (an email with no @, a card expiry with MM/YYYY swapped to YYYY/MM) or is malformed or corrupted. Event streams are immutable, so you cannot edit it after the fact (outside expiry or compaction).
  • Three strategies, in order: prevention (schemas, testing, validation; fail fast and gracefully), event design (corrections that overwrite bad data), and rewind, rebuild and retry as a last resort.
  • There are eight types of bad data. Schemas cover types 1 to 5, data quality rules and producer tests cover 6, and testing covers 7 and 8.
  • State events can be fixed once and compacted; delta events cannot, so fixes are build-forward or a rebuild.
  • Use dead-letter queues sparingly.

18.1 The eight types of bad data

  • Bad data can come from many places; a recurring reason appears across the types (revisited in the prevention sections: no schema, validation or tests at the producer).
    1. Corrupted data (Figure 18-1): indecipherable, so the consumer cannot tell what the event was. Relatively rare; caused by faulty serialisers that convert objects to byte arrays.
    2. Event has no schema (Figure 18-2): events sent without a schema; without types, names, requirements, limitations or structure it is impossible to tell good from bad, and interpretation falls to consumers.
    3. Event has an invalid schema (Figure 18-3): the purported schema cannot be applied. Example: with the Confluent Schema Registry the event's SchemaId does not correspond to a valid schema; you deleted it, or the serialiser inserted the wrong ID (perhaps from a staging or testing registry).
    4. Incompatible schema evolution (Figure 18-4): technically deserialisable but it cannot be converted to the consumer's schema; usually the source made a breaking evolution and consumers were not updated.
    5. Logically invalid value in a field (Figure 18-5): a value that should never occur, such as an array of integers for first_name or a null in a non-nullable field. Arises with implicit conventions instead of a well-defined schema, or with incomplete, old or homemade serialisation libraries that ignore parts of the protocol.
    6. Logically valid but semantically incorrect (Figure 18-6): trickier. A serialisable string first_name of Robert'); DROP TABLE Students; -- is valid for the field but not plausibly a first name (sanitise inputs; not only user data causes this). An order with a negative cost may be a bug in production, a semantic change in the schema definition, or something worse. Prone: services that parse NGINX server logs or customer-submitted YAML or XML inventory files; malformed sources such as concatenated phone numbers with varying spaces, dashes and symbols.
    7. Missing events: nothing produced when there should have been. Fairly easy to prevent by testing, but high impact if only some data is missing, as with event sourcing.
    8. Events that should not have been produced: bugs in producer code; a service fails, comes back and repeats from its last known good state, creating duplicates (Figure 18-7): a delta (add 1 to a sum) corrupts an aggregation; an analytics event (which ads a user clicked) inflates engagement; an order with its own order_id may ship and bill twice. Idempotent production (the Kafka idempotent producer) fences out duplicates from intermittent failures and retries, but not duplicates that are logically indistinguishable from other events.

18.2 Preventing bad data with schemas, validation and tests

  • Prevention is the number one approach: far easier than fixing later ("it cannot be overstated"; far less effort and cost than any other strategy).
  • Schemas (types 1 to 5):
    • Avro, Protobuf or JSON Schema (Confluent Schema Registry and similar support these) make events easy to create, test, validate and evolve
      • they significantly reduce incident rates and let consumers use data instead of best-effort parsing
    • JSON is a common but poor choice: no enforced types, mandatory or optional fields, defaults or evolution
    • Implicit schemas, historical conventions and tribal knowledge cannot provide data integrity: be strict, and let CI/CD pipelines validate schema, data and evolution before deploying, so no bad data reaches production streams.
  • Data quality rules (type 6):
    • schemas enforce types (no Strings in Integer fields) but not semantics
    • Options: producer unit tests (throw if malformed, such as a phone number over X digits) and data contracts with data quality rules
    • A Confluent rule for a US Social Security number enforcing exactly nine characters, applied at serialisation (mode: WRITE):
{
    "schema": "...",
    "ruleSet": {
        "domainRules": [
            {
                "name": "checkSsnLen",
                "kind": "CONDITION",
                "type": "CEL",
                "mode": "WRITE",
                "expr": "size(message.ssn) == 9"
            }
        ]
    }
}
  • If message.ssn is not exactly nine characters, the serialiser throws and the record is not written
    • You can then terminate the producer, skip the record, or send it to a dead-letter queue (DLQ)
    • If it is an integer, you could also require it be positive; if a string, contain only digits.
  • Approach DLQs with caution:
    • shunting data aside means dealing with it later (repair and resend)
      • They work best when each event is completely independent, with no relation to others and no ordering requirement
    • otherwise you risk an error-free but incomplete stream causing its own miscalculations. A DLQ is a last-ditch effort
    • test and foolproof producer logic to publish correctly the first time.
  • Testing (types 7 and 8):
    • write unit and integration tests for serialisers and deserialisers (validate schemas against the production schema registry), data validation rules and business logic
    • run producer tests in CI/CD before production (Chapter 20).

18.3 Event design and fixing bad data

  • State events
    • carry the whole fact about an entity (Order, Product, Customer, Shipment), like table rows with schema, types and defaults
    • Delta events describe changes and need aggregating a sequence to get current state (Figure 18-8)
    • State events enable ECST, materialised into consumers' own stores (Figure 18-9), with a new event for key A upserted over the old (Figure 18-10).
  • State events benefit from compaction:
    • the compactor deletes events with newer values of the same key without affecting materialisation
    • With deltas this is impossible: every delta is needed
    • Compaction is critical for deleting bad, private and sensitive data from the stream.

Fix it once and fix it right with state events

  • Publish a new event with the correct data; it propagates to all consumers and compaction eventually removes the old bad records.
  • Consumers must still deal with side effects of earlier bad data: if they made business decisions on it they must undo them or compensate (Chapter 10), exactly as with bad data in a non-event-driven system.
  • With connectors (Chapter 6), just fix the data in the source database (Figure 18-11): the CDC connector takes it from the database log, packages it and publishes to the compacted output topic
    • A Kafka Streams app on compacted state topics always gets the eventually correct state event and publishes corrected events downstream (Figure 18-12)
    • If it gets bad data itself (a bad evolution, corrupted data) it can log an error, divert to a DLQ and continue.
  • FTP example
    • (Figure 18-13): an external partner drops a daily XML export of total product inventory in an FTP directory
      • a listener trigger starts a short job (AWS Lambda or another FaaS, Chapter 15) that parses it into inventory state events keyed on productId, rather than an idle full-time streaming job
    • If the partner cannot commit to a schema you face frequent break-fix (they re-create files, you change parsing): a chronic source of bad data
    • Tip: get partners to comply with a basic schema, providing SDKs or validation tools.
  • State events are easy to fix, compactable, map to database tables, store only what you need, and let you infer deltas at any point if stored.

Build forward: undo bad deltas with new deltas

  • Deltas (and commands) cannot be compacted, updated or deleted, and every delta is relative to the previous one: a bad delta moves you to a bad state
    • Two strategies: build forward (undo bad deltas with new ones; challenging and error-prone) or rewind, rebuild and retry (filter bad data out, restore consumers from snapshots or the source streams; labour-intensive and error-prone).
  • Warning: deltas have no mechanism for purging data under legal obligations such as the GDPR right to be forgotten; make sure delta streams contain no sensitive information.
  • Build forward needs all bad events identified and results remediated: undo events (consumers must apply them correctly; risk of bad data in the undo itself, such as duplicates) or a compensation ("The Compensation Workflow Pattern").
  • Deltas tightly couple event models to consumer logic:
    • one way to compute correct state, an infinite number of ways to compute incorrect state, some terminal ("a package, once sent, can't be unsent, nor can a car crushed into a cube be un-cubed")
    • Undo events must restore the good state without overshooting to another bad one, requiring audits of each consumer's code and deployed state, so it is feasible mainly with one tightly coupled consumer under the same team.

18.4 The last resort: rewind, rebuild and retry

  • Applies to any topic with bad data (delta, state, hybrid or other): expensive, risky, labour-intensive and easy to get wrong.
  • From an external source
    • (for example an NGINX or gateway server whose log rows a connector parses into events): find the cause: say a new logging configuration changed the format but the parser was not updated in lockstep (more reason for testing)
    • The logfile remains the replayable truth but every parsed event after that point is malformed and has propagated downstream
    • If the parser used schemas and data quality checks, it could have shunted bad data to a DLQ, protecting consumers but delaying them
      • repair means updating the parser and reprocessing the logs, and consumers resume (the data being late).
    • Tip:
      • prevention would have stopped it
      • A stream already contaminated cannot be compacted (not a keyed entity stream) or edited: purge and rebuild it from the original logs
      • This is not a normal state of affairs: treat it as an incident-worthy event with notes, a postmortem and actionable follow-ups.
    • Consumers in a bad state
      • must be stopped, reset or restored, then consume the new stream
      • From the beginning is easiest: rebuild event by event, re-emitting outputs (maybe wanted, maybe muted until a logical condition such as a datetime)
      • Offsets from the old stream are useless since the new stream's offsets do not correspond
      • From a snapshot or savepoint
        • needs planning ahead (not done if producers skipped schemas): see "Recovery using snapshots or checkpoints"
        • it matches a known good datetime, so start processing from an event timestamp earlier than the snapshot's latest to avoid missing events, and keep processing idempotent or you will get another bad data scenario.
  • From the topic as the only source:
    • if state events, publish good data over bad
    • If it is a sequence of measurements (clickstream analytics written verbatim to a stream through a gateway with no unit and validation tests, no schema, no data quality rules), the only option is to reprocess the bad topic into a new good topic: write a stream processor (streaming SQL works well) to identify and repair the bad data into a new stream
    • This assumes all needed data is in the event; otherwise it is permanently lost (acceptable for lossy data, critical for others)
    • Then port the producer (fix the root cause or it recurs) and migrate consumers (another intensive operation, particularly if repair changed event ordering and offsets; may need a total reset to the beginning or a snapshot).

Summary points

  • Data is immutable once written, so dealing with bad data afterwards is hard.
  • First, prevent: well-defined schemas, schema validation, data quality checks and testing are the most cost-effective and important strategy.
  • Second, event design:
    • state events let you republish the same key with updated data
    • the broker compacts away incorrect, redacted and deleted data (such as for GDPR and CCPA)
    • fix it once at the source and propagate to every subscriber with little extra effort.
  • Third, rewind, rebuild and retry: pause consumers and producers, fix and rewrite data to a new stream, migrate everyone; expensive and complex, avoid if possible.
  • The most successful organisations integrate prevention and good event design into normal development
    • the least successful have no standards, schemas, testing or validation and "pay a heavy price".
Terms to carry forward
  • Bad data types 1 to 8; data quality rule; dead-letter queue; idempotent producer.
  • Build forward; rewind, rebuild, retry; savepoint.
