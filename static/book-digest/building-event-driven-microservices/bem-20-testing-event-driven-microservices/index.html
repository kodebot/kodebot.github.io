Building Event-Driven Microservices 20: Testing Event-Driven Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 20. Previous: Building Event-Driven Microservices 19: Supportive Tooling. Next: Building Event-Driven Microservices 21: Deploying Event-Driven Microservices.

Takeaways
  • Event-driven microservices are small and purpose-built, so relatively easy to test: event streams, queues and APIs are inputs, state is local to the service, outputs are events. The chapter is a companion to general testing books, covering what is specific to event-driven systems.
  • Unit tests (stateless and stateful functions, boundaries and nulls), topology tests (no broker needed), and schema evolution tests against the registry.
  • Integration tests come in local, remote and hybrid forms; containers (Testcontainers) are the most common local route.
  • Remote environments: temporary single-tenant (best), durable multitenant (worst), or production (careful). Populate streams with production copies, curated events or generated events (or a hybrid).
  • Invest in tooling to create, populate and tear down environments: it also prepares you for disaster recovery.

20.1 General principles and unit tests

  • Functional testing
    • (unit, integration, system, regression) checks the service does what it should and does not do what it should not
    • Nonfunctional testing (performance, load, stress, recovery) checks behaviour under environmental scenarios
    • Consult other sources for language-specific frameworks and testing best practices.
  • Unit tests
    • exercise the smallest pieces of code and are the foundation for larger tests. Event-driven microservices apply transformations, aggregations, mappings and reductions
    • test each stage so the data in and out meet expectations.

Stateless functions

  • Easy to test independently. A MapReduce-style topology (for example Kafka Streams):
myInputStream
    .filter(myFilterFunction)
    .map(myMapFunction)
    .to(outputStream);
  • At least two unit tests (one per function). The filter has several conditions:
public boolean myFilterFunction(String eventKey, MyEventValue value) {
    if (value.type == 7 && value.modifier.equals("valid")) {
        return true;
    } else if (value.type > 3 && value.type < 6) {
        return true;
    } else {
        return false;
    }
}
  • Test the three happy paths:
    • type == 7 && modifier equals "valid"
    • type == 4
    • type == 5 (4 and 5 are the boundaries of the true range; you do not test every value inside). Test false cases at boundaries: type != 7 with "valid"
    • type == 7 with a modifier that is not valid
    • type <= 3
    • type >= 6. And null-pointer exceptions: value == null, value.modifier == null (especially with optional or nullable fields).
  • Tests give security that code changes do not violate expected outputs. Tip: test boundary conditions so a change that breaks the original constraints fails the tests.

Stateful functions

  • More complicated:
    • computed state varies with input events and time, so you need durable state for the test cycle (a mocked or temporary data store)
    • Example, summing values per key in a basic producer/consumer:
public Long addValueToAggregation(String key, Long eventValue) {
    // The data store is provided by the unit-test framework
    Long storedValue = datastore.getOrElse(key, 0L);
    // Sum the values and load them back into the state store
    Long sum = storedValue + eventValue;
    datastore.upsert(key, sum);
    return sum;
}
  • Mock and inject the store, or use a local version of the real store (closer to integration testing). Consider what the store must do and how it relates to the runtime one
    • mocks avoid spinning up, purging and shutting down a full store per unit test.

20.2 Testing the full topology

  • Topology testing
    • (see "Microservice Topology") exercises the entire business logic
    • full-featured frameworks typically give a local test mode (or community options), with no event broker needed:
    • Apache Spark: third-party StreamingSuiteBase and spark-fast-tests, plus the built-in ContinuousMemoryStream for fine-grained input and output control.
    • Apache Flink: MiniClusterWithClientResource, a local embedded mini cluster.
    • Kafka Streams: TopologyTestDriver, which mocks the framework without an event broker.
  • You control event production in code, including timestamp and partition: events with specific values
    • out of order
    • invalid timestamps
    • invalid data, to exercise corner cases, time-based aggregations, event scheduling and stateful functions.
  • Example topology:
    • myInputStream.map(myMapFunction).groupByKey().reduce(myReduceFunction): unit tests cover the functions
    • topology testing checks the results of map, groupByKey and reduce together.
  • Example 20-1, a simplified Kafka Streams test (the topology builder normally lives in the main code):
// The object that drives the topology, injects events, and consumes the output
private TopologyTestDriver testDriver;
private TestInputTopic<String, Long> inputTopic;
private TestOutputTopic<String, Long> outputTopic;
private Serde<String> stringSerde = new Serdes.StringSerde();
private Serde<Long> longSerde = new Serdes.LongSerde();

// This function would actually be in the main code body, not in the test code.
public Topology buildMyTopology(String inputStream, String outputStream) {
    StreamsBuilder sb = new StreamsBuilder(...);

    // 1) Build the topology
    sb
        .stream(inputStream, Consumed.with(stringSerde, longSerde))
        .map(myMapFunction)
        .groupByKey()
        .reduce(myReduceFunction,
            Materialized.with(stringSerde, longSerde))
        .to(outputStream, Produced.with(stringSerde, longSerde));

    return sb.build();
}

@Before
public void setup() {
    Topology topology = buildMyTopology("input", "output");

    // 2) Setup test driver
    Properties props = new Properties();
    testDriver = new TopologyTestDriver(topology, props);

    // 3) Setup the test topics to input and output data
    inputTopic = testDriver
        .createInputTopic("input",
            stringSerde.serializer(),
            longSerde.serializer());
    outputTopic = testDriver
        .createOutputTopic("output",
            stringSerde.deserializer(),
            longSerde.deserializer());
}

@After
public void tearDown() {
    testDriver.close();
}

@Test
public void shouldSumToThree() {
    // 4) Write data into the input topic
    inputTopic.pipeInput("a", 1L);
    inputTopic.pipeInput("a", 2L);

    // 5) Assert that the outputs are exactly what we expect them to be
    assertThat(outputTopic.readKeyValue(), equalTo(new KeyValue<>("a", 3L)));

    // 6) And make sure that there isn't anything else extra in the topic
    assertThat(outputTopic.isEmpty(), is(true));
}
  • (Variable and method names are tidied from the printed listing, which mixes input and inputTopic.) The driver executes the topology (2), plugs in the input and output topics (3), you pipe data in (4), validate the output (5) and confirm there are no side effects or errant events (6).

20.3 Testing schema evolution and compatibility

  • Validate a candidate schema against the one in the schema registry and compare against your schema evolution rules before deploying
    • Example (Confluent Schema Registry): register the initial User schema (Example 20-2) against a subject (the acceptable schemas inside a Kafka topic; my_user_subject, Example 20-3 via a curl POST)
    • the candidate drops age (Example 20-4)
    • a compatibility query (Example 20-5) passes the candidate to the registry's compatibility endpoint and reads is_compatible with jq.
{
    "type": "record",
    "name": "User",
    "namespace": "com.example",
    "fields": [
        {"name": "id", "type": "string"},
        {"name": "name", "type": "string"},
        {
          "name": "age",
          "type": "int"
        }
    ]
}

{
    "type": "record",
    "name": "User",
    "namespace": "com.example",
    "fields": [
        {"name": "id", "type": "string"},
        {
          "name": "name",
          "type": "string"
        }
    ]
}

# Example 20-5: validate that the updated User schema can be deployed
ORIGINAL_USER_SCHEMA=...  # As shown above

curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
    --data "{\"schema\": $ORIGINAL_USER_SCHEMA}" \
    "www.mySR.com/subjects/my_user_subject/versions"

CANDIDATE_USER_SCHEMA=...  # As shown above
COMPATIBILITY_RESPONSE=$(
    curl -s -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
        --data "{\"schema\": $CANDIDATE_USER_SCHEMA}" \
        "www.mySR.com/compatibility/subjects/my_user_subject/versions/latest")

# Extract the 'is_compatible' boolean from the response
IS_COMPATIBLE=$(echo "$COMPATIBILITY_RESPONSE" | jq -r '.is_compatible')

if [ "$IS_COMPATIBLE" = "true" ]; then
    echo "The new schema is compatible, you can deploy it!"
elif [ "$IS_COMPATIBLE" = "false" ]; then
    echo "The new schema is not compatible, don't deploy it!"
else
    echo "Error: Could not determine compatibility!"
    echo "Unexpected response from Schema Registry."
    echo "Don't deploy the schema!"
    exit 1
fi
  • (The book's script prints tick and cross symbols; they are replaced by plain text here.) The default evolution mode is BACKWARD (you can delete fields and add optional fields), so this example is compatible and can deploy. This is one example for the Confluent registry
    • consult your registry's documentation.

20.4 Integration testing

  • Focus on emulating event-stream inputs and direct request inputs; from simple smoke tests to suites across hundreds or thousands of input and output combinations
    • The goal: the service performs as expected on its inputs and produces events and query responses as expected
    • Note: integration tests may include more than one microservice (tightly coupled in one bounded context), but each extra service adds complexity and the chance of omitted cases.
  • Three variations: local (a local replica of production), remote (a separate staging, QA or even production environment) and hybrid (some parts local, some remote, such as a laptop container against remote stores and brokers).
  • Questions throughout: What is the goal (does it run, a smoke test with production data, complex multi-service workflows)? Must it restart from the beginning of the input streams (full data loss, reprocessing) or restore from a snapshot or checkpoint? What data decides success (hand-crafted, generated, real production, how much)? Any performance, load, throughput or scaling requirements? How to lower the barrier so each microservice does not need a custom harness?

Local integration testing

  • A local copy of production:
    • at minimum an event broker, a schema registry, the microservice's data stores, the service itself and any processing frameworks (heavyweight framework or FaaS)
    • containerisation, logging and the CMS are not strictly needed
      • You control each system independently and can script production-like scenarios: intermittent failures, out-of-order events, network loss
    • test the framework integration with your logic
    • test horizontal scaling, especially copartitioning and state
    • and test event-driven and request-response logic together (treat the API as another source of events).
  • Options by component:
    • Event broker:
      • create and delete streams
      • selective event ordering for time-based logic, out-of-order events and upstream producer failures
      • modify partition counts
      • induce broker failures and recovery
      • induce stream availability failures.
    • Schema registry: publish evolution-compatible schemas and use them to produce input events; induce failures and recovery.
    • Data stores: change table schemas and stored procedures (if applicable); rebuild internal state when the instance count changes; induce failures.
    • Processing framework:
      • shuffling via internal streams (lightweight) or the shuffle mechanism (heavyweight) for copartitioning and data locality
      • checkpointing, failures and recovery
      • inducing a worker failure (heavyweight).
    • Application:
      • scale the instance count (dynamically if supported) and verify rebalancing
      • state restored from checkpoints or changelogs with data locality preserved
      • external state access unaffected, and request-response access unaffected.
  • Two ways to run local tests:
    • embedded libraries in your code (narrow) or a local environment of components, most commonly containers, controlled from test scripts
    • plus hosted or SaaS options.

Within the runtime of your test code

  • Narrowest option: the test code starts and controls the full event broker and schema registry with the service under test. Example 20-6 (pseudocode):
// Start the broker and the schema registry, both of which run on the JVM
broker.start(brokerUrl, brokerPort, ...);
schemaRegistry.start(schemaRegistryUrl, srPort, ...);

// The first instance of the microservice
topologyOne.start(brokerUrl, schemaRegistryUrl,
    inputStreamOne, inputStreamTwo, ...);

// A second instance of the same microservice
topologyTwo.start(brokerUrl, schemaRegistryUrl,
    inputStreamOne, inputStreamTwo, ...);

// Publish some test data to input stream 1
producer.publish(inputStreamOne, ...);
// Publish some test data to input stream 2
producer.publish(inputStreamTwo, ...);
// Wait a short amount of time. Not the best way to do it, but you get the idea
Thread.sleep(5000);

// Now mimic topologyOne failing
topologyOne.stop();

// Check the output of the output topic. Is it as expected?
event = consumer.consume(outputTopic, ...);

// Shut down the remaining components if no more testing is to be done
topologyTwo.stop();
schemaRegistry.stop();
broker.stop();

// Validate the consumer output
return event.equals(...);
  • Beyond topology tests it can run multiple topology instances, exercise consumer group rebalancing and partition assignment, validate joins, groupBy and aggregations, test scaling up and down, and inject faults. Warning: this works only because Kafka and the Confluent Schema Registry are Java applications that can run beside another Java app
    • it is limited to Java (and Scala and Kotlin).

With containers

  • The easiest, most common and most flexible
    • approach: plug any containerised service into your test workflow (with overhead to create, manage and destroy)
    • Testcontainers (open source) composes and manages containers from test code, for many languages (Java, Go, .NET, Python, Rust, Ruby, and more)
    • Example 20-7 starts a Confluent Kafka broker, a PostgreSQL with pgvector, and a HashiCorp Vault:
KafkaContainer kafka = new KafkaContainer(
    DockerImageName.parse("confluentinc/cp-kafka:8.0.0"));
kafka.start();

PostgreSQLContainer<?> pgvector =
    new PostgreSQLContainer<>("pgvector/pgvector:pg16");
pgvector.start();

public static VaultContainer<?> vaultContainer =
    new VaultContainer<>("hashicorp/vault:1.20.0")
        .withVaultToken(VAULT_TOKEN)
        .withInitCommand(
            "secrets enable transit",
            "write -f transit/keys/my-key",
            "kv put secret/mysecret1 top_secret=mountains",
            "kv put secret/mysecret2 secret_one=dogs secret_two=bananas"
        );
  • You can also create containers outside the test code (Docker and Kubernetes offer guides)
    • Apache Kafka, Apache Pulsar and Confluent Platform ship off-the-shelf Docker containers
    • Tip: pin specific software versions to match production, or run against newer versions to find upgrade problems early
    • You can bundle all dependencies in one container shared across the organisation: more production-like but more complicated and opaque
      • an open source contribution model lets colleagues contribute fixes.
  • Figure 20-1:
    • a lightweight-framework example: the schema registry, broker and topics live in the container, and the microservice instance runs outside and references their addresses from its test config
    • This is probably the most common option today.

Hosted, managed and SaaS services

  • Remotely hosted FaaS and SaaS add complications. Some managed services have open source options (Kafka, Flink, Spark)
    • most remote FaaS and SaaS do not: Microsoft Event Hubs, Google PubSub and Amazon Kinesis are proprietary. Use emulators: Google PubSub has one
    • LocalStack provides an open source Kinesis (and other Amazon services)
    • Azure Event Hubs has no emulator
      • (its clients can use Apache Kafka instead, though not every feature is supported)
      • Google Cloud, AWS Lambda and Azure functions can be tested locally
    • OpenWhisk, OpenFaaS and Kubeless provide similar mechanisms.
  • Heavyweight framework
    • environments: install and configure the framework, submit the processing job to the framework, await output on the output streams
    • a typical single-container setup runs the resource manager and worker instances beside the broker and other dependencies (Figure 20-2, containerised for distribution among developers).
  • Tip:
    • keep testing, development, staging and production separate
    • use access controls so services cannot accidentally contaminate others' streams. Fully managed, FaaS and SaaS options are much more common than in the first edition
    • many organisations host nothing and use providers' environments for development, testing and staging, sometimes with no emulator.

20.5 Testing with fully remote cloud services

  • Prerequisites:
    • the service has an account, credentials and permissions
    • creates and populates event streams and other data stores
    • cleans up and deletes its resources after the test (or failure). Most of the work is here
    • the hardest parts are clean-up and not breaking someone else's test environment: credentials and strict permissions help
      • Warning: invest in service accounts, credentials and permissions for multitenant test environments: easier, safer, more reliable, less break-fix, and it tests the permissions needed for production.
  • Three ways: a temporary single-tenant environment, a durable multitenant environment, or production.

Temporary single-tenant environment

  • Use IaC ("Infrastructure as Code for Clusters and Services") to generate temporary environments: your own temporary Kafka cluster on dedicated hardware, or an API request to a SaaS (such as Confluent) for a Kafka environment
    • A new environment has no streams or events, so your script populates them
      • scripted testing regularly exercises creating and deleting brokers and compute environments, and any special data or configuration is codified in the scripts (crafted data lives in test code, not a customised environment)
    • Tip: mirror production partition counts so copartitioning and repartitioning logic is properly tested.
  • Populate streams from:
    • Production events:
      • copy using the replication tooling (specific streams, events, offset ranges, time ranges). Warning: consider load on production
      • throttle large copies. Advantages: data accurately reflects production
      • copy as many or few events as needed
      • full isolation from other services under test. Disadvantages: may affect production performance without broker quotas
      • may need substantial data (long-lived entities in compacted streams)
      • sensitive information
      • your service cannot decrypt encrypted production data (it is not a production service and should not have production keys)
      • streamline the copying. Common for load testing: SLOs, throughput, request latency, scaling, failure recovery.
    • A curated testing source:
      • specially crafted events representing a range for a stream, usually produced by the service owner, kept as JSON, XML or YAML files in the code repository
      • consumers load them into their own (or a mocked) broker. Advantages: anyone can use them
      • owners know the data best
      • data is validated during parsing and population. Disadvantages: complexity of parsing and populating
      • shifting file-format standards (competing standards in large organisations)
      • may not exercise joins, aggregations or repartitions
      • becomes stale and orphaned as people move on
      • hand-edited events can introduce errors. Like documentation, they decay and lose trust.
    • Programmatically generated events:
      • generate from your input schemas pulled from the schema registry (latest or mixed old and new). Advantages: specific values and relationships to exercise all logic
      • total isolation
      • third-party tools (Confluent Avro tools)
      • no production impact
      • fuzzing for boundary conditions and malformed fields
      • failing to generate under the latest schema is an early warning that your code needs changing. Disadvantages: duplicated efforts across services
      • stale scripts under schema evolution
      • not accurate to production distribution (key skew)
      • a join needs related events in two streams
        • Tip: a hybrid: a small, carefully curated set of core entity events plus generated data for the rest
        • Sample production data to make sure generated events match real schemas, ranges and relationships.

Durable multitenant environment

  • A single shared environment with pooled streams populated with a production subset or crafted data
    • Advantages: easy to start, isolated from production
    • Disadvantages: a tragedy of the commons (fragmented, abandoned streams; unclear which are valid input versus leftover output)
    • services may produce incompatible events during their own testing and break downstream consumers
    • systems under test are not isolated (simultaneous large performance tests affect each other)
    • data goes stale
    • may not represent production's range.
  • Warning:
    • the worst option for usability: the broker becomes a dumping ground of confusing streams and broken data
    • The core problem is individual carelessness (developers pollute their own output streams), growing with service and team count
    • Mitigate with careful curation, strict naming conventions and restricted writes, but it is hard to scale.

Testing in production

  • Spin up the service, consume production input streams, apply business logic and write to a temporary test output stream: isolation is crucial when a previous version of the same service runs beside it ("absolutely certain you aren't writing to the production output event streams")
    • Advantages: complete production events
    • uses the production security model (access control and encryption)
    • excellent for smoke tests with current data
    • no separate environment to maintain. Disadvantages: uses production resources (affects SLOs; not for load and performance testing)
    • you must clean up created streams, consumer groups, permissions and state stores
    • you need tooling to tell test services and streams from production ones (metadata tagging helps a lot). Works best for smaller teams and low-utilisation clusters
    • most organisations use dedicated QA or testing environments and copy production data.

Choosing a strategy

  • Microservice modularity means you need not pick one strategy for everything
    • Supportive tooling for creating and tearing down dedicated brokers and for copying events between brokers largely determines your options.
  • With little or no tooling you end up with one shared test broker with a hodgepodge of streams: suffixes like -testing-01, -testing-02, -testing-02-final, -testing-02-final-v2
    • unreliable data
    • tribal knowledge
    • higher costs for a continuously available cluster that hosts large data and performance tests.
  • With proper investment each service can bring up its own environment, populate streams, copy some production data, run in a near-production setting and tear down afterwards (no leftover artefacts)
    • The overhead is not trivial, but unlocks multicluster benefits, redundancy and disaster recovery (Chapter 19)
    • A shared cluster can still work with diligent housekeeping, clean and reliable source streams, deleting abandoned artefacts
      • access controls so only owners populate data
      • coordinated performance tests, and incremental adoption of tooling for dedicated clusters, SaaS environments and cross-broker replication.

Summary points

  • Streams can be populated by copying production, curating data sets and generating from schemas
    • each has pros and cons and all rely on supportive tooling to create, populate and manage streams.
  • Building the test environment is a collaborative effort:
    • invest in tooling for a common platform
    • programmatic creation of environments (including event stream population) cuts the setup overhead.
  • A shared test environment is typical when tooling investment is low, at the cost of managing data, validity and ownership
    • disposable environments are preferable (isolation, fewer multitenancy issues), need more tooling investment, but save time and effort and better prepare the organisation for disaster recovery.
Terms to carry forward
  • Unit, topology, integration tests; TopologyTestDriver; Testcontainers; emulator (LocalStack).
  • Local, remote, hybrid integration; temporary single-tenant versus durable multitenant environments.
  • Curated, generated, production-copied test data; BACKWARD compatibility check.
