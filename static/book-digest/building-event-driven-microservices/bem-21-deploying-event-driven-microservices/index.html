Building Event-Driven Microservices 21: Deploying Event-Driven Microservices

Source: Adam Bellemare, Building Event-Driven Microservices, 2nd edition (O'Reilly, 2025), chapter 21. Previous: Building Event-Driven Microservices 20: Testing Event-Driven Microservices. Next: Building Event-Driven Microservices 22: Conclusion.

Takeaways
  • Deploying microservices is harder than one monolithic deployment; with many services, standardise and streamline deployment and give teams autonomy over it, backed by supportive tooling.
  • Principles: team autonomy, a standard process, supportive tooling, reprocessing impacts, SLAs (worst-case state rebuild), minimal dependent changes, negotiate breaking changes. A service that regularly forces others to deploy with it may have ill-defined bounded contexts.
  • CI builds and validates; continuous delivery keeps it deployable; continuous deployment automates release (hard for stateful services).
  • Patterns: basic full-stop, rolling update (strict prerequisites), breaking schema change (three variants, plus historical data migration), and blue-green (careful with a shared output stream).

21.1 Principles of deployment

  • An organisation with a few dozen services can use a few custom processes, but any organisation seriously invested in microservices, event-driven or not, must standardise and streamline deployment.
  • Principles:
    • Give teams deployment autonomy: control their own testing and deployment and deploy at their discretion.
    • Standardised deployment process: consistent across services; a new service starts with a process already available, usually via a continuous integration framework.
    • Supportive tooling: reset consumer group offsets, purge state stores, check and update schema evolution, delete internal streams; enables automation and autonomy.
    • Consider event-stream reprocessing impacts:
      • reconsuming input can take long, leaving stale results for downstream consumers
      • the service may then emit a large volume of output causing load downstream
      • very large streams and streams with many consumers see surges
      • consider side effects (for example resending multiple years of promotional emails).
    • Adhere to SLAs: rebuilding state stores can cause significant downtime; account for the worst-case rebuild when setting SLAs.
    • Minimise dependent service changes:
      • deployments may force other services to change APIs or data models (REST API, domain schema)
      • these violate the other team's autonomy to deploy only when business requirements demand.
    • Negotiate breaking changes with downstream consumers:
      • a breaking schema change may need new streams and a renegotiated data contract
      • hold the discussions before deployment and have a consumer migration plan.
  • Warning:
    • make microservices independently deployable
    • If a deployment regularly needs other services to synchronise theirs, their bounded contexts may be ill-defined and should be reviewed (exception: a few tightly coupled services in one bounded context built to be codependent, typically owned by one team).

21.2 Architectural components

  • Two main roles: the systems that build and deploy the code, and the compute resources that run the services.

CI, delivery and deployment

  • Build, test and deploy as code changes are committed: part of the microservice tax; owners decide when, where and how to deploy.
    • Continuous integration (CI):
      • automating the integration of changes from multiple contributors into one project
        • the team integrates at its own discretion, reducing the time from writing code to seeing it in production
      • CI frameworks execute processes on merge to the main (or any) branch: build, unit tests, integration tests, code style validation, schema evolution validation, linting
      • The output is a ready-to-deploy container or virtual machine.
    • Continuous delivery: keeping the codebase deployable; the CI pipeline validates the build, but the deployment is not automated and needs manual intervention.
    • Continuous deployment: automated deployment: a committed change propagates through CI, reaches a deliverable state and is automatically deployed to production, a tight loop with short turnaround.
  • Warning:
    • continuous deployment is difficult in practice, especially for stateful services (deployments may need state store rebuilds and stream reprocessing)
    • weigh the impact before choosing automatic or manual deployment.

Container management and commodity hardware

  • The CMS manages, deploys and controls resource use of containers (see "Managing Containers and Virtual Machines"). The container built in CI is stored in a repository, awaiting CMS deployment instructions
    • CI to CMS integration (usually provided by the CMS) is essential.
  • Many event-driven microservices need no specialised hardware:
    • commodity hardware is inexpensive, reliable enough and supports horizontal scaling (add or remove hardware from pools; recover by spinning up instances on the next available server)
    • Create special pools for services needing dedicated graphics cards, very fast storage or high parallelism.

21.3 The basic full-stop deployment pattern

  • The basis of all other patterns (Figure 21-1, a CI pipeline showing continuous delivery versus continuous deployment); add steps as needed.
    1. Commit code: the usual trigger, often via webhooks or other hooks.
    2. Execute automated unit and integration tests: integration tests may need their own transient environments populated with data ("Local Integration Testing"). Tip: independent integration environments avoid multitenancy issues (resource contention, contaminated sources, version mismatches).
    3. Run predeployment validation tests: detect problems before release: event stream validation (existence and configuration of input and output streams; missing streams can be created; read and write permissions) and schema validation (input and output schemas follow evolution rules, validated against the schema registry). Tip: keep the event schemas your code is written against in the service's repository; after compatibility validation use a code generator to produce structs or classes.
    4. Deployment: stop the deployed service before deploying the new one:
      • Stop instances and clean up:
        • stop the instances
        • perform state store and consumer group resets
        • delete internal streams
          • If rebuilding state would be expensive on failure, instead leave state, consumer group and internal topics alone and deploy as a new parallel service (quick rollback, more complex).
      • Deploy:
        • deploy the containerised code and start the required instances
        • wait for them to boot and signal readiness before moving on
        • on failure abandon and deploy the previous working version.
    5. Run post-deployment validation tests: the service operates normally, consumer lag returns to normal, no logging errors, endpoints work.
  • Warning: consider the impact on all dependent services: SLAs, downtime, catch-up time, output event load, new streams, breaking schema changes; communicate with their owners.

21.4 The rolling update pattern

  • Keep the service running while updating individual instances. Prerequisites: no breaking changes to state stores
    • none to the internal microservice topology (especially for lightweight frameworks)
    • none to internal event schemas
    • no replaying of input event streams.
  • Works well for: new fields in input streams to integrate; consuming from new streams; bug fixes that do not need rewinding and reprocessing.
  • Warning: inadvertently altering the internal topology is one of the most common mistakes; it is a breaking change and needs a full application reset, not a rolling update.
  • Only step 4 changes:
    • instead of stopping all instances, one at a time is stopped, updated and started, so old and new instances run together with old and new logic at once
    • Benefit: processing continues with no downtime
    • Drawback: the prerequisites limit it to specific scenarios.

21.5 The breaking schema change pattern

  • Breaking changes are inevitable as an organisation grows:
    • a fundamental shift in the business domain, or a fix for a poorly defined schema ("Negotiating a Breaking Schema Change" covers negotiation; this covers deployment)
    • Downstream consumers are the number one concern. Two options: write new events to the same stream or to a new stream.
  • Variant 1: write breaking events to the same old stream.
    • Simplest for the producer: update the schema and redeploy (Figure 21-2)
    • only new events use the new schema, the old ones stay. No reprocessing or reconstruction under old schemas
    • consumers must handle both
      • Hopefully they throw exceptions on new events if not updated, preventing erroneous progress, but they may silently fail, discard the new events, or worst of all incorrectly deserialise them into bad data.
  • Variant 2: write breaking events to a new stream.
    • The service produces new events only to a dedicated new stream (Figure 21-3): a breaking change for all existing consumers, each notified and coordinated
    • a big bang that is risky without testing. Warning: producer owners must extensively test the new schema
    • if events fail to be created or consumers cannot read them you get multiple service outages.
    • Often required when business changes force consumers to adopt the new schema in their data models
      • Example: deprecating Account and re-creating it as BuyerAccount and SellerAccount (a regulatory compliance model that separates accounts by function, where the old model allowed both buying and selling).
    • Biggest risk:
      • consumers do not notice the old stream is no longer active, producing stale data and increasingly inaccurate computations
      • track all consumers with read access and notify them.
  • Variant 3: write both old and new events in parallel
    • to their own streams (Figure 21-4)
    • may not be possible for all use cases
      • Mark the old stream deprecated, encourage (and maybe chronically nag) consumers to migrate, then remove the old stream or archive it
      • Assumptions: the producer can write both, with the data to create both formats (some remodelling cannot map to both)
    • and consumers can keep consuming two definitions without inconsistency (small changes like a type expansion may not matter, major ones likely will).
    • Benefit: consumers must deliberately swap streams, a guard against variant 1's silent failures and bad decoding.
    • Caution:
      • the migration may never finish, leaving similar-yet-different streams in use indefinitely
      • new services may subscribe to the old stream. Use metadata tagging to mark streams deprecated and keep migration windows small.
    • Works best for minor changes where both formats keep integrity: for example changing a field from Integer to String is breaking but both can be output (String is a superset of Integer).
    • Warning: avoid prolonged dual production: it is a temporary solution that becomes permanent without a tight schedule of deprecation, consumer migration and eventual deletion or archiving.
    • Two dedicated services
      • (Figure 21-5): a second microservice produces the new schema while the old one keeps the old
      • when everyone migrates you simply turn off the old service (no patch and redeploy to stop old production)
        • Drawback: you must clone and manage a copy of the service
        • Warning: the offsets in the new stream will not match the old stream's (late-arriving events and repartitioning change order; intermittent failures create duplicates)
        • New questions: how to manage offsets
      • do migrating consumers reprocess from the beginning
      • what about historical data?

Reprocessing historical data for breaking schema changes

  • The foundational question:
    • will you populate the new stream with historical data? Often writing new data in the new format suffices, particularly for time-limited streams (24 hours of data) or unimportant history
    • Tip: the schema may change so much that old and new formats cannot coexist: more common than it seems when a business updates its model, expands products or takes new customers.
  • For entity streams (see "Entity Events") and other infinite-duration data you will likely need to migrate history: present and future consumers need a reliable source of truth, and converting once in one place reduces consumer complexity and the chance each introduces bad data (Chapter 18), worse with popular data
    • Two ways:
    • From the producer's internal state stores:
      • iterate the internal database and produce the historical entities in the new schema to the new stream, a one-time process before consumers read from it (so they can rebuild their stores)
      • natively, or via a new snapshot with a connector (Chapter 6).
    • From upstream event streams:
      • rewind the producer's input offsets and reprocess, producing history in the new schema
      • the producer may use several input streams and the broker for its own durable state (lightweight framework, Chapter 13).
  • Decide which streams to re-create:
    • entities almost always
    • time-based events (past interactions) are rarely candidates. Rebuilding is only part of it: you must still help consumers migrate, manage deprecation and eventual archival or deletion.
  • Biggest risk:
    • consumers fail to migrate and cannot fall back to the old source as with eventual migration
    • Reduce it with integration testing, preferably in programmatically generated environments and source data: register producer and consumers together to rehearse the migration
    • Note: synchronised migrations are uncommon; core entities usually have stable domain models, but when major breaking changes occur one may be unavoidable.

21.6 The blue-green deployment pattern

  • Goal:
    • zero downtime while deploying new functionality
    • mostly used in request-response deployments so request handling continues during the update (Figure 21-6)
      • A full copy of the new service (blue) runs in parallel with the old (green)
    • blue has a fully isolated external data store, its own consumer group and its own IP addresses
      • It consumes input until monitoring shows it has caught up to green, then traffic starts to move.
  • A router in front sends a few requests to blue and the rest to green
    • if there are no failures it routes more to blue and less to green (watch for scaling issues), until all traffic is on blue. Green is then turned off or left idle for a cooldown
    • if an error appears the router reroutes traffic back to green to restore SLOs.
  • Note:
    • integrate monitoring and alerting (resource metrics, consumer group lag, autoscaling triggers, system alerts) into the pattern
    • It suits services needing minimal downtime (customer experiences, around-the-clock services), but with event streams beware asynchronous materialisation and computation and multiple consumer groups.
  • Warning:
    • be cautious about blue-green writing to a common output stream: two independent instances may overwrite each other's work or create duplicate events
    • prefer a rolling update or full-stop deployment there.

Summary points

  • Streamlined deployment means paying the microservice tax in deployment and monitoring systems; delegate deployment to owning teams with supportive tooling.
  • CI pipelines set up and run tests, validate builds and prepare containers; the CMS manages deployment into compute clusters, resources and scaling.
  • Full-stop is simplest but can cause significant downtime and may not fit SLAs; the other patterns each have benefits and drawbacks and are a starting point, not a comprehensive list.
Terms to carry forward
  • CI, continuous delivery, continuous deployment; full-stop, rolling update, blue-green.
  • Breaking schema change variants 1 to 3; dual production; historical data migration.
  • Predeployment validation; post-deployment validation.
