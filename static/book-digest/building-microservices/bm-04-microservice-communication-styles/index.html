Building Microservices 4: Microservice Communication Styles

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 4. Previous: Building Microservices 3: Splitting the Monolith. Next: Building Microservices 5: Implementing Microservice Communication.

Takeaways
  • Decide the style of communication first, and the technology second. Teams often pick technology before asking what kind of interaction they want.
  • Inter-process calls differ from in-process calls in performance, changing interfaces and error handling; do not hide the network from developers.
  • Two axes: synchronous blocking vs asynchronous nonblocking, and request-response vs event-driven (plus common data). A system usually mixes them.
  • Request-response fits when you need a result. Event-driven inverts responsibility: the emitter does not know who listens, so coupling is lower. Common data suits bulk data and legacy interoperability.
  • Asynchronous and event-driven styles add real complexity (retries, dead letters, correlation); start small.

4.1 From in-process to inter-process

Calls across a network are very different from calls within a process. Thinking "an object calling an object" gets you into trouble.

Performance

  • In-process calls can be inlined by the compiler or runtime
    • round-tripping a packet in a data centre is measured in milliseconds. A thousand in-process calls are fine
    • a thousand network calls between two services probably not, so APIs may need rethinking.
  • In-process parameters are pointers
    • Across a network the data is serialised, sent and deserialised, so you must care about payload size: send less (good for information hiding), pick more efficient serialisation, or pass a reference to a file.
  • Abstractions that hide the network call from developers hide too much: surprise bottlenecks follow.

Changing interfaces

  • In-process, caller and callee ship together (an IDE refactoring updates both), so a change is atomic
    • Between microservices they are separately deployable, so a backward-incompatible change needs a lockstep deployment or a phased rollout of the new contract.

Error handling

  • In-process errors are mostly deterministic:
    • expected and handled, or catastrophic and propagated
    • In a distributed system many errors are outside your control: timeouts, unavailable services, dropped networks, containers killed for memory, "bits of your data center can catch fire".
  • Tanenbaum and van Steen (Distributed Systems) give five failure modes (simplified):
Failure Meaning
Crash Fine until the server crashed: reboot
Omission You sent something and got no response (or an expected stream of events just stops)
Timing Something happened too late, or too early
Response A response arrived but looks wrong (missing needed information)
Arbitrary (Byzantine) Something is wrong but participants cannot agree whether or why
  • Many are transient
    • others need a human. So a rich set of error semantics lets clients act: HTTP's 4xx are request errors (is there point retrying a 404?)
    • 5xx relate to downstream issues, some temporary (503 may be worth a retry; 501 probably not)
      • Whatever the protocol, rich semantics make compensating actions easier and systems more robust.

4.2 Technology for IPC: so many choices

  • People gravitate to familiar or fashionable technology and buy into its ideas and constraints
    • Examples of mismatch: Angular or React for a plain website, or Kafka for request-response (it was designed for event-based interactions).
  • So describe the style first, then filter technology (Newman's model; chapter 5 covers technology).

4.3 Styles of microservice communication

Style Definition
Synchronous blocking A service calls another and blocks waiting for the response
Asynchronous nonblocking The caller carries on processing whether or not the call is received
Request-response A service asks another to do something and expects a response with the result
Event-driven Services emit events; others consume and react; the emitter is unaware which services, if any, consume them
Common data Services collaborate through a shared data source (not often seen as a communication style)

  • Newman starts by choosing request-response or event-driven for the situation
    • With request-response he still chooses sync or async; with event-driven he is limited to nonblocking asynchronous options
    • Reliability, latency, volume, security and scale also matter.
  • Mix and match
    • is the norm
    • one microservice can use several styles (an Order service with a request-response API that places or changes orders and fires events when they change).

4.4 Pattern: synchronous blocking

  • A service calls a downstream one and blocks until it completes, often waiting for a response (so nearly always also request-response)
    • Example: Order Processor tells Loyalty to add points.
  • Advantages:
    • simple and familiar: it reads like a script, like a SQL query or an HTTP request
    • Sticking with the familiar can make sense when moving from a monolith with so much else new.
  • Disadvantages:
    • Temporal coupling (chapter 2): Loyalty must be reachable, else Order Processor must choose a compensating action (retry now, buffer and retry later, or give up).
    • The coupling is two-way and between specific instances: the response travels back over the same connection, so if the caller's instance died, the response is lost.
    • Slow downstream or network means the caller is blocked, so slowness propagates: more vulnerable to cascading failures than async.
  • Where to use it:
    • fine for simple architectures
    • Problems appear with chains of calls: Order Processor → Payment → Fraud Detection → Customer
    • Any service or hop failing fails the whole operation, and each service holds an open connection waiting (risking running out of connections and congestion).
  • Fix by restructuring:
    • move Fraud Detection out of the purchase flow into the background, updating customer records that payment checks earlier
    • This shortens the chain, improves latency, removes a critical-path dependency
    • Or use nonblocking interactions without changing the workflow.

4.5 Pattern: asynchronous nonblocking

Sending a call does not block the caller. Three common styles: common data, request-response, event-driven.

  • Advantages:
    • sender and receiver are temporally decoupled (the receiver need not be reachable when called) and it suits long-running work
    • Example:
      • Order Processor tells Warehouse to dispatch a package (finding, packing, pickup may take hours or days)
      • Warehouse calls back with progress, a form of asynchronous request-response
    • A blocking call held open for hours or days is not feasible.
  • Disadvantages: complexity and choice; several styles, bewildering technology, and a different mental model that offers many ways to get into trouble.

[!note] async/await and "asynchronous" that is still blocking async/await lets you work with an asynchronous source (such as exchange rates arriving via a broker, a Promise that resolves later) in a blocking, synchronous style: await blocks until the value is fulfilled, so process(latestRate) does not run before it resolves. From your code's point of view it is a synchronous, blocking interaction. (The book's JavaScript example omits error handling.)

  • Where to use it: long-running processes and long call chains you cannot restructure.

4.6 Pattern: communication through common data

  • One service puts data in a defined location and others use it later; fundamentally asynchronous
    • Example: the New Product Importer writes a file read by Inventory and Catalog
    • It is probably the most common IPC pattern, yet often not recognised because it is so indirect.
  • Implementation:
    • needs a persistent store
    • a filesystem often suffices (or a robust distributed memory store). Consumers need their own way to notice new data, commonly polling.
  • Data lake vs data warehouse sit at opposite coupling ends:
    • in a data lake sources upload raw data in any format and consumers must know how to process it
    • a data warehouse is a structured store, so producers must know its structure and update if it changes incompatibly.
  • Both assume one-way flow, easier to reason about
    • A shared database with several readers and writers is the problematic form (common coupling, chapter 2; Order Processor and Warehouse updating one record).
  • Advantages: simple, uses commonly understood technology (file or database), interoperable with older systems (mainframes, COTS products), good for large volumes.
  • Disadvantages:
    • polling or timed jobs mean it is not for low latency (you can add a notification call, or use streaming such as Kafka for near real-time)
    • the common store is a coupling source and its robustness is yours to worry about.
  • Where to use it: interoperability with systems restricted in technology (a mainframe may not talk gRPC or Kafka or Redis, but can read a file), and sharing large volumes (multigigabyte files, millions of rows).

4.7 Pattern: request-response communication

  • A service sends a request and expects a response with the result; implementable synchronously or asynchronously.
  • Examples:
    • Chart (best-selling CDs by genre) asks Inventory for stock levels
    • Order Processor asks Warehouse to reserve stock and needs success before taking payment (if stock cannot be reserved, payment is cancelled). Useful where calls must complete in a given order.

[!note] Commands versus requests Some say "command" for asynchronous request-response. Newman prefers request: a command implies a directive that must be obeyed, whereas a request can be rejected. A microservice should judge each request by its own internal logic and reject it if it violates that logic.

Synchronous vs asynchronous implementation

  • Synchronous: a connection to the downstream service stays open while it responds; the responder needs to know nothing about the requester, and trouble comes if the connection dies.
  • Asynchronous (via a message broker):
    • the request sits in a queue that Inventory consumes when able
    • Inventory then sends the response to another queue that Order Processor reads. The responder must know (or be told) where to send the response.
    • Queues buffer requests so the service is not overwhelmed (depending on the queue absorbing them).
    • To relate the response to the original request (it may return to a different instance, much later), store the request's state in a database so any instance can reload it.
  • All request-response needs timeouts so nothing waits forever (chapter 12).

[!note] Parallel versus sequential calls Checking a price with three stockists: sequential calls cost the sum of latencies (1 s each is 3 s); parallel calls cost the slowest (about 1 s). Reactive extensions and async/await help run calls in parallel.

  • Where to use it:
    • whenever you need the result before continuing, or want to know a call failed so you can compensate (for example retry)
    • Then choose sync or async with the trade-offs above.

4.8 Pattern: event-driven communication

  • A service emits events that other services may or may not receive
    • Inherently asynchronous
    • An event is a statement of something that has occurred, nearly always inside the emitter's world; the emitter has no knowledge of other services' intent and may not know they exist.
  • Example: Warehouse emits events about packing an order; Notifications emails the customer and Inventory updates stock.
  • It inverts responsibility:
    • in request-response, Warehouse would tell Notifications to send emails and need to know which events matter
    • With events, that responsibility moves into Notifications
    • The intent is the opposite of a request: the emitter leaves it to recipients
    • Coupling drops sharply (less domain coupling)
    • It mirrors autonomous teams (chapter 15) and spreads "smarts" more evenly; compare choreography and orchestration in chapter 6.

[!note] Events and messages An event is a fact (something happened, with detail). A message is what you send over an asynchronous mechanism such as a broker. "The message is the medium; the event is the payload." A request can also be a message payload (asynchronous request-response).

Implementation

Two aspects: a way to emit events and a way for consumers to find out.

  • Message brokers
    • (RabbitMQ) usually do both: producers publish; the broker handles subscriptions and can track what consumers have seen
    • Scalable and resilient but at a cost: another system to run, test against and staff
    • Newman is "a fan".
  • Beware middleware smarts: vendors bundle more and more (the enterprise service bus). "Keep your middleware dumb, and keep the smarts in the endpoints."
  • Atom
    • (a REST-compliant feed specification): publish feeds over HTTP and have consumers poll
    • It reuses libraries and HTTP scales, but is poor at low latency, and consumers must track what they have seen and manage polling
    • People then spend ages rebuilding broker features (for example competing consumers, where workers compete for messages and two must not process the same one; a broker's standard queue handles it, Atom needs shared state)
    • If you have a good broker, use it; if not, try Atom but beware the sunk cost fallacy.
  • Payload encoding is the same question as for synchronous calls: if you are happy with JSON, keep it.

What's in an event?

Example: Customer emits "new customer registered"; Loyalty creates an account, Notifications sends a welcome email.

  • Just an ID:
    • Loyalty has enough, but Notifications needs an email and name, so it calls back to Customer
    • Downsides: extra domain coupling, and a barrage of requests on Customer if many consumers all call back.
  • Fully detailed events (Newman's preference):
    • put in everything you would be happy sharing via an API; Notifications can act without ever knowing Customer exists
    • Events can double as a historical record (auditing, even reconstituting an entity: event sourcing)
    • Downsides:
    • Size:
      • Kafka's default maximum message is 1 MB
      • RabbitMQ's theoretical limit is 512 MB (down from 2 GB) though performance suffers. For large data use a hybrid: some data in the event, the rest looked up.
    • Visibility:
      • Loyalty receives an email address it does not need
      • To limit exposure of PII or card data, send two event types (one with PII, one without), but then managing visibility and guaranteeing both fire is hard (what if the service dies between them?).
    • Contract:
      • event content becomes part of your contract
      • removing a field can break others. Information hiding still applies. Rule: put information in an event only if you would share it over a request-response API.

  • Where to use it:
    • when information wants to be broadcast and you are happy to invert intent; when loose coupling matters most
    • Newman gravitates to it almost by default, admitting a bias from past bad experiences with overly coupled systems ("fighting the last battle")
    • He sees far more teams replacing request-response with event-driven than the reverse
    • If unsure, start with one event.

4.9 Proceed with caution

  • Event-driven architectures can be more decoupled and scalable, but cost complexity: for long-running async request-response, does the response return to the same node? If that node is down, or if not, where is state stored? It is a different way of thinking for programmers used to in-process calls.
  • Cautionary tale (a bank pricing system, 2006):
    • market events produced a list of items to reprice, put on a message queue, consumed by a pool of pricing workers using the competing consumers pattern
    • After a release the workers kept dying:
      • a bug crashed a worker on a certain request type
      • on a transacted queue the worker's lock timed out and the request went back on the queue, where another worker picked it up and died
    • Martin Fowler calls this a catastrophic failover
    • They had set no maximum retry limit
    • Fixes: the bug fix, a maximum retry, and a message hospital (dead letter queue) with a UI to view and replay failed messages.
  • So adopt eagerly only with good monitoring and consider correlation IDs (chapter 10). Recommended: Hohpe and Woolf, Enterprise Integration Patterns (2003).
  • Synchronous calls are not exempt:
    • on a timeout, did the request get lost, or the response? If you retry and the original got through, what then? The answer is idempotency (chapter 12)
    • Those headaches are just more familiar.

Summary points

  • There is rarely one right option; weigh synchronous vs asynchronous and event-driven vs request-response for your context.
  • Newman's bias is towards asynchronous, event-driven collaboration (from experience and an aversion to coupling), with significant complexity attached.
  • Next: implementation, starting with communication technology.
Terms to carry forward
  • Synchronous blocking, asynchronous nonblocking, request-response, event-driven, common data.
  • Temporal coupling, cascading failure, compensating action.
  • Message broker, dead letter queue (message hospital), competing consumers.
  • Fully detailed event, event sourcing, correlation ID.
  • Five failure modes (crash, omission, timing, response, arbitrary).
