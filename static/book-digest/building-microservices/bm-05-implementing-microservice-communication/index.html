Building Microservices 5: Implementing Microservice Communication

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 5. Previous: Building Microservices 4: Microservice Communication Styles. Next: Building Microservices 6: Workflow.

Takeaways
  • Pick technology from the communication style you want. Favour options that make backward-compatible change easy, keep the interface explicit, stay technology agnostic, are simple for consumers and hide internals.
  • Four families: RPC (gRPC is Newman's pick), REST over HTTP (a sensible default, great at the perimeter), GraphQL (aggregation for clients) and message brokers (queues, topics, Kafka).
  • Use explicit schemas and compare versions in CI to catch structural breakages; only tests catch semantic ones.
  • Avoid breaking changes (expansion, tolerant reader); if unavoidable, emulate the old interface (expand and contract) rather than lockstep or coexisting versions.
  • API gateways guard north-south traffic, service meshes handle east-west; keep both free of business logic ("dumb pipes").

5.1 Looking for the ideal technology

  • Make backward compatibility easy: adding a field must not break clients, and you want feedback on compatibility before production.
  • Make the interface explicit: consumers see what is exposed, and maintainers see what must stay intact. Use an explicit schema plus documentation.
  • Keep APIs technology agnostic: do not let integration technology dictate the stack (a ".NET shop" today may not be one in five years).
  • Make the service simple for consumers: freedom of technology, though client libraries ease adoption at the cost of coupling.
  • Hide internal detail: exposed internals bind consumers, raise the cost of change and breed technical debt.

5.2 Technology choices

Family What it is
RPC Local method calls executed on a remote process (SOAP, gRPC)
REST Resources (Customer, Order) accessed with a common set of verbs
GraphQL Client-defined queries fetching from several services and filtering the result
Message brokers Middleware for asynchronous communication via queues or topics

Remote procedure calls

  • Most need an explicit schema, the IDL (SOAP calls its schema WSDL)
    • Schemas let you generate client and server stubs for different stacks (a Java SOAP server with a .NET client)
    • Java RMI skips the IDL (Java types are the definition) but requires both sides to use Java.
  • RPC implies a serialisation protocol (gRPC uses protocol buffers) and sometimes a network protocol (TCP guarantees delivery; UDP is lighter). Clients need the schema out of band
    • Avro RPC can send the schema with the payload.
  • Challenges:
    • Technology coupling: RMI ties client and server to the JVM. Thrift, gRPC and SOAP interoperate.
    • Local calls are not remote calls:
      • marshalling cost, network time, and the first fallacy of distributed computing, "the network is reliable"
      • Developers may make remote calls without knowing.
    • Brittleness:
      • with RMI, adding a createCustomer(String emailAddress) overload means regenerating stubs
      • removing an unused age field breaks consumers' deserialisation. Binary stub generation forces lockstep releases, and types become expand-only.
  • Where to use it:
    • Newman likes RPC; gRPC (built on HTTP/2, with tools like Protolock) tops his list when you control both ends and want synchronous request-response
    • RMI and SOAP he avoids
    • With many unknown consumers, REST fits better.
// CustomerRemote.java
import java.rmi.Remote;
import java.rmi.RemoteException;

public interface CustomerRemote extends Remote
{
    public Customer findCustomer(String id) throws RemoteException;

    public Customer createCustomer(
        String firstname, String surname, String emailAddress)
        throws RemoteException;
}

REST

  • An architectural style inspired by the web
    • The key concept is the resource (a Customer) with representations (JSON) that are fully decoupled from internal storage; clients ask to change it and the server may decline
    • See the Richardson Maturity Model for REST styles.
  • REST over HTTP:
    • the verbs have agreed meanings (GET retrieves idempotently, POST creates), replacing many createCustomer/editCustomer methods
    • HTTP also brings caching proxies (Varnish), load balancers (mod_proxy), monitoring and security controls (basic auth to client certificates), if used well
    • SOAP rides HTTP but ignores verbs and error codes; gRPC exploits HTTP/2 multiplexing but is not REST.
  • HATEOAS
    • (hypermedia as the engine of application state): clients follow links instead of knowing URIs, like a human finding the shopping cart however its look changes
    • Clients must understand the semantics of the link relations (artist, instantpurchase) but not the URIs.
<!-- album listing with hypermedia controls -->
<album>
  <name>Give Blood</name>
  <link rel="/artist" href="/artist/theBrakes" />
  <description>
    Awesome, short, brutish, funny and loud. Must buy!
  </description>
  <link rel="/instantpurchase" href="/instantPurchase/1234" />
</album>
  • Challenges:
    • historically no client code generation (so people ship client libraries)
    • OpenAPI (from Swagger) now allows it, though Newman rarely sees it used. Payloads are bigger than Thrift's, HTTP/TCP overhead hurts low latency (HTTP/3 uses QUIC), and HATEOAS can be chatty (start by navigating controls, optimise later).
  • Where to use it:
    • a sensible default for synchronous request-response; excels at large-scale caching and external or client-facing APIs
    • Newman has seen little evidence HATEOAS pays off between microservices
    • It is poor for asynchronous interaction.

GraphQL

  • Lets a client define a query to avoid several requests. Example: a mobile screen needs a few customer fields and the date, value and shipped status of the last five orders
    • one query replaces two calls that return unneeded data.
  • A microservice exposes a GraphQL endpoint with a schema and query builder.
  • Challenges:
    • Dynamic queries can load the server heavily, like expensive SQL but without a query planner; throttling across several services is hard.
    • Caching is more complex than REST headers and CDNs; IDs per resource and client caches (Apollo) are workarounds.
    • Writes fit worse, so teams use GraphQL for reads and REST for writes.
    • It encourages seeing services as wrappers over databases (compare OData); do not couple to the datastores.
  • Where to use it:
    • at the perimeter, for GUIs, mobile and some external APIs (GitHub)
    • It is a call aggregation and filtering mechanism, not a replacement for service-to-service calls
    • An alternative is the BFF pattern (chapter 14).

Message brokers

  • Intermediaries (middleware) between processes. A message can carry a request, response or event; the sender gives it to the broker with routing information.
  • Queues
    • are point to point
    • topics
      • let many consumers subscribe, each receiving a copy
      • A consumer may be a consumer group (several instances of one service): only one member receives each message, which is competing consumers and distributes load (Figure 5-1)
      • With topics, several groups each get a copy and one instance per group sees it (Figure 5-2)
      • A queue looks like a topic with one group, but the sender knows the destination of a queue message
      • Topics suit events
    • queues suit request-response (guidance, not rule).

  • Guaranteed delivery:
    • the broker holds messages durably until delivered, so a downed consumer is not the sender's problem (unlike a failed HTTP call)
    • It needs a clustered broker run correctly (RabbitMQ needs low-latency links between nodes or data can be lost), and you must trust it
    • Meanings vary: read the docs.
  • Other characteristics:
    • Ordering: often guaranteed but scoped (Kafka only within a partition); consumers may defer out-of-order messages.
    • Transactions: Kafka writes to several topics in one transaction; JMS offers read transactions.
    • Exactly once delivery is controversial. Build consumers to tolerate duplicates, for example by checking a message ID and ignoring repeats.
  • Choices: RabbitMQ, ActiveMQ, Kafka; cloud options such as AWS SQS (the second AWS product, 2006), SNS and Kinesis.
  • Kafka
    • stands out for: very large scale (built at LinkedIn; one expert saw 50,000 producers and consumers on a cluster), message permanence (retained for a configurable period, even forever, so consumers can reingest and new ones catch up) and built-in stream processing (KSQL, like a materialised view over topics)
    • Newman recommends Stopford's Designing Event-Driven Systems and Kafka: The Definitive Guide.

5.3 Serialisation formats

  • Textual:
    • JSON has largely replaced XML, mainly because browsers consume it, though compressed sizes rarely differ much and schemas were dropped in the rush
    • Avro uses JSON to define a schema-based format and can ship the schema with the payload
    • Newman still likes XML (XPath, CSS selectors) over JSONPath.
  • Binary:
    • protocol buffers (the most popular), Simple Binary Encoding, Cap'n Proto, FlatBuffers. Benchmarks may not match your usage, so measure yourself
    • most systems gain more by sending less data or skipping the call.

5.4 Schemas

  • Schema type follows the format: XSD for XML, JSON Schema for JSON; SOAP needs WSDL and gRPC needs a protocol buffer spec.
  • Newman favours explicit schemas for two reasons: they make the endpoint explicit (and reduce documentation), and they catch accidental breakage.
Breakage Meaning Caught by
Structural Fields or methods removed, new required fields added Schema comparison
Semantic Same structure, changed behaviour (the calculate method now multiplies rather than adds) Testing
  • The analogy is static versus dynamic typing:
    • without an explicit schema you still have an implicit one in your consumer code
    • The case against schemas ("more work, little value") is partly a failure of imagination and tooling
    • When one team owns both sides he is more relaxed.

5.5 Handling change between microservices

"How do you handle versioning?" is really about contract changes.

Avoiding breaking changes

  • Expansion changes: add, never remove (a new dateOfBirth field).
  • Tolerant reader:
    • pick only the fields you need and ignore the rest
    • The Email service needs firstname, lastname, email but not telephoneNumber; if the customer is restructured (a naming wrapper), XPath still finds the fields
    • This is Martin Fowler's term and reflects Postel's law: "Be conservative in what you do, be liberal in what you accept from others."
  • Right technology: protocol buffers' field numbers let new fields pass unnoticed; Avro ships schemas; HATEOAS goes furthest.
  • Explicit interface:
    • an explicit schema makes information hiding boundaries explicit ("what's exposed in the schema is by definition not hidden")
    • REST schemas are rare but OpenAPI and JSON Schema are growing
    • For events, AsyncAPI and CloudEvents (a CNCF specification, supported by Azure Event Grid) are emerging.
  • Semantic versioning:
    • MAJOR.MINOR.PATCH (major = incompatible, minor = backward-compatible features, patch = fixes)
    • A helpdesk built on Customer 1.2.0 should survive 1.3.0, may need 1.2.0 or later, and expect changes at 2.0.0
    • Newman has not seen it used enough in distributed systems.
  • Catch accidental breaks early:
    • compare schemas in CI and fail the build on incompatibility
    • Tools:
      • Protolock (protocol buffers)
      • json-schema-diff-validator
      • openapi-diff (three tools share the name; the Azure one passes or fails on compatibility), and the open-source Confluent Schema Registry (JSON Schema, Avro, protobuf; needs Kafka to run)
    • For semantic breaks, use consumer-driven contract tests (Pact), and run tests with each supported client library.
<!-- Customer response, then restructured -->
<customer>
  <firstname>Sam</firstname>
  <lastname>Newman</lastname>
  <email>sam@magpiebrain.com</email>
  <telephoneNumber>555-1234-5678</telephoneNumber>
</customer>

Managing breaking changes

Option Verdict
Lockstep deployment Defeats independent deployability; acceptable rarely, within one team, but a one-off can become business as usual and lead to a distributed monolith
Coexist incompatible versions Netflix uses it sparingly; costs: fix bugs in two services (branching), routing smarts in middleware or nginx scripts, shared persistent state. Fine for minutes or hours (canary release)
Emulate the old interface Newman's preference: one running service exposes old and new endpoints
  • Emulate and expand and contract:
    • expand to support old and new, then contract by removing the old once consumers move
    • Route with version headers or URI versions (/v1/customer/, /v2/customer/); for protocol buffers use namespaces (v1.createCustomer)
    • When Newman's team coexisted three versions, they transformed V1 requests to V2 and V2 to V3 internally, to delineate retired code.
  • The social contract:
    • agree up front how the need is raised, how teams agree the change, who updates consumers, and how long they have
    • Be consumer-first
    • Sometimes consumers cannot change (Netflix set-top boxes); the decision can be financial.
  • Tracking usage: log each endpoint and identify clients (a user-agent identifier or API gateway keys).
  • Extreme measures:
    • a company that simply switched off old interfaces after a generous one year
    • another added a growing sleep to an old library until teams migrated. Only after other efforts, and Newman would still track who is affected.

5.6 DRY and code reuse

  • DRY means avoiding duplicated behaviour and knowledge, not just code. Sharing in a microservice world is trickier.
  • Libraries:
    • shared code that leaks across service boundaries couples them (a common domain-objects library at one client forced all services to update and queues to be drained)
    • Logging libraries are fine
    • realestate.com.au copies a service template rather than sharing it
    • You cannot update all uses at once (each service packages and redeploys its own copy), so accept several versions
      • if you need exact simultaneity, use a dedicated microservice instead.
  • Client libraries:
    • if the same people write server and client, server logic leaks into the client and cohesion suffers (Newman did this)
    • The AWS SDK model is good: written by others, and clients choose when to upgrade
    • Netflix's client libraries handle discovery, failure modes and logging (reliability at scale) but caused coupling
    • Separate transport code from service-specific code, decide whether use is mandatory, and let clients control upgrades.

5.7 Service discovery

Two parts: a way for an instance to register ("I'm here!") and a way to find it, ideally coping with instances created and destroyed constantly.

  • DNS:
    • a name such as accounts.musiccorp.net, or a template like <servicename>-<environment>.musiccorp.net
    • Widely supported, but updating entries for disposable hosts is painful (Route 53 helps) and TTL caching (even in the JVM) leaves stale entries
    • Point DNS at a load balancer rather than DNS round-robin, which hides sick hosts from the client.
  • ZooKeeper:
    • from Hadoop
    • a hierarchical namespace with watches, running as at least three nodes
    • configuration, leader election and naming. Newman would now avoid it for registration.
  • Consul:
    • configuration plus discovery, an HTTP interface, a built-in DNS server serving SRV records (IP and port)
    • health checks
    • consul-template (update config files, for example a HAProxy pool) and integration with Vault (secrets).
  • etcd and Kubernetes: Kubernetes services select pods by metadata; often enough, though a mixed environment may still want Consul.
  • Rolling your own: Newman used AWS instance tags (service, environment, version) queried via API; today it would be "a much worse wheel".
  • Don't forget the humans: expose the same information to people.

5.8 Service meshes and API gateways

  • North-south
    • traffic crosses the perimeter
    • east-west stays inside. An API gateway handles north-south
    • a service mesh handles east-west. Both act as proxies for generic behaviour with no tie to any one microservice's logic.

API gateways

  • Mostly reverse proxies adding API keys, logging, rate limiting and developer portals
    • The hype came from the "API economy"; many firms bought features they never needed
    • Usually it only fronts the organisation's own GUI clients (Kubernetes needs something at the edge since it routes only inside the cluster), so a third-party-oriented gateway is overkill.
  • Where to use them:
    • be clear what you want
    • for Kubernetes a focused product such as Ambassador (or your own reverse proxy)
    • possibly more than one gateway. Newman reports more mis-selling in this space than any other.
  • What to avoid:
    • Call aggregation drifts into business logic: use GraphQL, a BFF, or a modelled saga (chapter 6).
    • Protocol rewriting ("any SOAP API into REST") pushes smarts into the pipe.
    • Smart gateways break "dumb pipes, smart endpoints" and add handoffs: a central team changes your gateway via tickets.
    • Proxying all east-west calls adds a network hop.

Service meshes

  • Push common inter-service functions (mutual TLS, correlation IDs, discovery, load balancing) into the mesh, avoiding shared libraries and versions, and working across languages (Netflix once mandated JVM to JVM)
    • Changes roll out without rebuilding services.
  • How they work:
    • a proxy runs beside each instance (on Kubernetes, in the same pod), so a call from Order Processor to Payment goes via local proxies, limiting remote hops
    • the Envoy proxy underlies Istio and Ambassador. A control plane changes proxy behaviour, distributes certificates and collects data.
  • Smart pipes? No: only generic behaviour such as timeouts, which teams can set self-service (in Istio via the service definition).
  • Do you need one?
    • The space was unstable (Linkerd rebuilt from v1 to v2; Istio took years to 1.0). Newman's old advice was "if you can afford to wait six months, wait"
    • it has since matured. Options are limited off Kubernetes, and they add complexity (hard to justify for five microservices)
    • switching is painful. Monzo relied on Linkerd v1, then moved to an in-house Envoy-based mesh.
  • Other protocols: meshes mainly handle HTTP; Kafka traffic bypasses the mesh.

5.9 Documenting services

  • Schemas show structure, not behaviour, so documentation is still needed (more so without schemas)
    • OpenAPI also drives portals (open-source ones are basic; Ambassador's Developer Portal auto-discovers endpoints)
    • For events: AsyncAPI (adapted from OpenAPI) and CloudEvents (more integration, historically JSON only, protobuf support restored).
  • Self-describing system:
    • UDDI was heavyweight
    • Fowler's humane registry is a lightweight alternative (a wiki)
      • Combine health checks, correlation IDs, Consul, OpenAPI and CloudEvents into dashboards, crawling repositories for metadata files
      • The Financial Times Biz Ops (on a graph database) calculates a System Operability Score
    • Spotify's Backstage and Ambassador's Service Catalog are open-source options.

Summary points

  • Let the problem and the style guide the technology; use schemas for explicit contracts and to catch accidental breaks.
  • Prefer backward-compatible changes; when breaking, give consumers time and avoid lockstep.
  • Surface information to humans with a humane registry.
