Building Microservices 6: Workflow

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 6. Previous: Building Microservices 5: Implementing Microservice Communication. Next: Building Microservices 7: Build.

Takeaways
  • Splitting data across services loses atomicity: each service can use ACID locally, but the operation as a whole is no longer one transaction.
  • Distributed transactions (two-phase commit) are mostly distributed locking; they add latency, lose isolation and fail in messy ways. Newman says avoid them.
  • A saga models a long-lived business process as independent local transactions, with compensating transactions for rollback and a choice of backward or forward recovery.
  • Two implementation styles: orchestrated (central coordinator, visible, more coupled) and choreographed (events, loosely coupled, harder to follow). One team owning the saga: orchestration is fine; several teams: prefer choreography.
  • Sagas handle business failures, not technical ones; use correlation IDs to track state.

6.1 Database transactions

  • A transaction treats several changes as a single unit and gives a way to clean up on error. Typically this is an ACID transaction:
Property Guarantee
Atomicity All operations complete or all fail, as if nothing happened
Consistency The database is left in a valid state
Isolation Concurrent transactions do not see each other's interim changes
Durability Completed changes survive a system failure
  • Not every database offers ACID (MongoDB supported it only on a single document for years; multidocument ACID arrived in 4.0 per the book's footnote)
    • For depth Newman recommends Kleppmann's Designing Data-Intensive Applications
    • This chapter focuses on atomicity, the first thing lost when functionality splits.

Still ACID, but lacking atomicity

  • A service can still use ACID inside its own database
    • only the scope shrinks
      • Example: onboarding a customer ends by changing customer 2346's status from PENDING to VERIFIED and deleting the row from PendingEnrollments
      • In one database that is a single transaction
    • across the Customer and Enrollments services it is two independent transactions.
  • You could sequence them (delete only if the update worked), but you must then handle the delete failing yourself
    • Reordering steps is useful (it returns with sagas), but the operation's atomicity is lost.

6.2 Distributed transactions: two-phase commit

  • 2PC has a voting phase and a commit phase, run by a central coordinator.
    • Voting: the coordinator asks workers whether a change can be made (set status to VERIFIED; remove the pending row). Any "no" aborts everything.
    • A "yes" is a guarantee to make the change later, so the worker typically locks the record so nothing invalidates it.
    • Commit: if all agreed, changes are applied and locks released; otherwise a rollback message lets workers release locks.
  • Problems:
    • Commits do not land simultaneously, so a window exists where A has changed but B has not. Isolation is lost.
    • At heart it is coordinating distributed locks, hard to manage and deadlock-prone.
    • Failure modes abound (a worker votes yes then does not answer the commit), some needing a manual fix by an operator.
    • More participants and more latency mean more trouble: 2PC is only suitable for short-lived operations, since resources stay locked for the duration.

Just say no

  • Newman strongly advises against distributed transactions across microservices. Alternatives:
    • Do not split state that must stay atomic: keep it in one database and one service (or the monolith) and split elsewhere first.
    • If you must split, or the operation takes minutes, days or months, use a saga.

6.3 Sagas

  • A saga coordinates several state changes without locking resources for long, by modelling the steps as discrete, independently executable activities
    • It also forces you to model business processes explicitly.
  • Origin:
    • Hector Garcia-Molina and Kenneth Salem, "Sagas", ACM SIGMOD Record 16(3), 1987, about long-lived transactions (LLTs)
    • Mapping an LLT to one database transaction would lock rows or tables for a long time
    • Break it into a sequence of shorter transactions, each touching part of the data, so there is far less contention
    • The model works equally across services.
A saga is not atomic

  • Example:
    • MusicCorp order fulfilment as one saga, each step a different service
    • inside the Warehouse, reserving stock is a local ACID transaction writing a row to its Reservation table.

Failure modes

  • Backward recovery: revert and clean up (a rollback) using compensating actions for already-committed transactions.
  • Forward recovery: carry on from the failure point by retrying, which requires persisting enough information.
  • Expect backward, forward or a mix, depending on the process.
  • Sagas recover from business failures (insufficient funds), not technical failures (payment gateway timeout or a 500). They assume reliable components
    • see chapter 12 and Friedrichsen's "The Limits of the Saga Pattern".

Saga rollbacks

  • Suppose the item cannot be found when packaging, and you decide to cancel the whole order (not offer back-order)
    • Payment was taken and points awarded in earlier, already committed transactions, so there is no simple rollback.
  • You run a compensating transaction for each committed step
    • It is a semantic rollback: the original did happen, and you add a new transaction reverting its effect
    • You cannot unsend an email, so the compensation sends a second email saying the order was cancelled.
  • Keeping a record of the aborted order is appropriate and useful.

Reordering steps to reduce rollbacks

  • Award loyalty points only at dispatch rather than earlier, so a packaging failure has no points to undo
    • Pull likely failures earlier and push hard-to-undo steps later, so some compensations need not exist.

Mixing fail-backward and fail-forward

  • Once payment is taken and the item packed, only dispatch remains. If the carrier has no room, rolling back the order would be odd: retry (perhaps next day), then involve a human.

6.4 Implementing sagas

Style Idea Typical interaction
Orchestrated A central orchestrator defines order and triggers compensation: command and control Request-response
Choreographed Responsibility distributed across services: "trust but verify" Events

Orchestrated sagas

  • Order Processor
    • acts as orchestrator: it knows which services are needed, decides when to call them and what to do on failure
    • The process is explicit in one place, easing onboarding and understanding.
  • Downsides:
    • Domain coupling: the orchestrator must know every service.
    • Anaemic services:
      • logic gets absorbed by the orchestrator
      • Services should still own local state and behaviour ("their own local state machines")
      • Note the maxim: "If logic has a place where it can be centralized, it will become centralized!"
    • Mitigate by using different orchestrators for different flows (Order Processor, Returns, Goods Receiving), all reusing Warehouse functionality.
BPM tools

Choreographed sagas

  • Services react to events
    • When Warehouse gets Order Placed it reserves stock and fires an event; failure raises something like Insufficient Stock
    • When Payment Gateway fires Payment Taken, Loyalty awards points while Warehouse dispatches in parallel.
  • A message broker with a topic handles broadcast; a Recommendation service could also listen to Order Placed.
  • Pros: no service knows about another (far less domain coupling); no place for logic to centralise.
  • Cons: the process is not explicit (you rebuild it by reading each service) and you lack a view of a saga's state, needed for compensation.
  • Fix:
    • put a unique correlation ID for the saga in every event, and have a service consume all events to project a view of each order's state (and possibly act to resolve issues)
    • Newman considers correlation IDs essential here (chapter 10).

Mixing styles

  • You can mix styles by process or inside one saga (an orchestrated flow inside the Warehouse boundary, within a larger choreographed saga). Whatever you do, keep a clear way to see saga state and completed activities
    • Garcia-Molina and colleagues also studied nested sagas (1991).
  • Tracing calls: correlation IDs and log aggregation (chapter 10) help with either style.

Orchestration or choreography?

  • Newman finds the extra tracking complexity of choreography "almost always" outweighed by looser coupling, but this reflects his taste for events.
  • Rule of thumb:
    • One team owns the whole saga: orchestration is fine (the coupling is manageable inside a team).
    • Several teams involved: prefer choreography, to distribute responsibility and let teams work in isolation.
  • Orchestration leans on request-response, choreography on events (a tendency, not a rule). If event-driven design confuses you, choreography may not suit.

6.5 Sagas versus distributed transactions

  • Pat Helland ("Life Beyond Distributed Transactions: An Apostate's Opinion", acmqueue, 2016) notes that a single node's failure stalls commit in most distributed transaction systems, so the larger the system, the likelier it is down: like an aircraft that needs all engines, adding an engine reduces availability.
  • Modelling processes as sagas avoids many of these problems and makes the process a first-class concept.

Summary points

  • Workflows come down to explicitly modelling the business process, which fits microservice boundaries drawn around the business domain.
  • Next reading: Hohpe and Woolf's Enterprise Integration Patterns and Bernd Ruecker's Practical Process Automation (O'Reilly, 2021; orchestration-focused).
