Building Microservices 10: From Monitoring to Observability

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 10. Previous: Building Microservices 9: Testing. Next: Building Microservices 11: Security.

Takeaways
  • A monolith has one obvious place to look when something breaks; a microservice system has many suspects ("every outage could be more like a murder mystery"). You need aggregation, tools to slice and dice, and a different mindset.
  • Monitoring is an activity; observability is a property: how well you can understand internal state from external outputs, including by asking questions you did not anticipate.
  • Build, in order: log aggregation (a prerequisite, with correlation IDs from day one), metrics aggregation (mind cardinality), then distributed tracing.
  • Define health with SLOs, SLIs and error budgets; alert sparingly (alert fatigue); use semantic monitoring and synthetic transactions.
  • Pick democratic, integrable, contextual, real-time tools that fit your scale, and remember the expert is still the human.

10.1 Disruption, panic and confusion

  • Picture a Friday afternoon:
    • the site misbehaves, social media is ablaze. In a monolith: slow? the monolith
    • errors? the monolith
    • CPU at 100%? the monolith. With microservices there are multiple servers, log files and network latency spots, so the failure surface is larger.
  • Three needs:
    • monitor the small things and aggregate to see the whole
    • have tools to slice and dice data
    • and think differently about system health, including testing in production.

How the problem grows

Stage What you watch and how
One service, one server Host metrics (CPU, memory), the service's logs (read locally), and external response time or a health check endpoint
One service, many servers Same, but aggregate and drill down: is high CPU on all hosts (the service) or one (the host)? SSH multiplexers can grep logs for a while; capture response times at the load balancer and at the service; defining "healthy" matters because the load balancer removes unhealthy nodes
Many services, many servers Thousands of log lines across hosts: is a server or the system at fault, and how to trace an error deep in a call chain? Needs aggregated logs and metrics and a mindset shift from static monitoring to observability and testing in production

10.2 Observability versus monitoring

  • Observability
    • is the extent to which you can understand the system's internal state from its external outputs
    • it needs a holistic view (a system, not disparate entities). Highly observable systems let you "ask questions of your production system that you never would have thought to ask".
  • Monitoring
    • is something you do
    • traditional monitoring predicts failures and defines alerts, which breaks down as systems distribute. So monitoring is an activity, observability a property.

The pillars of observability? Not so fast

  • The "three pillars" are metrics, logs and distributed tracing (New Relic added events: MELT)
    • Newman moved away from it as reductive: it fixes on implementation instead of the outcome, the categories overlap (metrics in a logfile; traces built from log lines), and cynically it sells several tools.
  • Treat any output as an event and project from the event stream a trace (given correlation), a searchable index or aggregations
    • Think about outputs you can interrogate, not tool categories.

Building blocks

  • Log aggregation,
    • metrics aggregation
    • distributed tracing
    • "are you doing OK?" (SLAs, SLOs and error budgets)
    • alerting
    • semantic monitoring and testing in production.

10.3 Log aggregation

  • Logging into machines or using SSH multiplexers does not scale
    • Use a subsystem that collects logs centrally: services log to the local filesystem, a local daemon forwards to a store operators can query
    • Your services stay unaware of it (no special API), but you must understand the failure modes of log shipping, where logs can be lost.
  • Newman's nearest thing to one-size-fits-all advice:
    • log aggregation is a prerequisite for microservices
    • It is highly valuable, easy relative to other pain, and a test of readiness: if you cannot do it, you will struggle with the rest.

[!warning] Before anything else Get a log aggregation tool running before building out the architecture.

Common format

  • Pick one standard format (date, time, service name, level in consistent places)
    • Avoid reformatting in forwarding agents (computationally expensive; Newman has seen it cause CPU production issues): change the format at the source, and use agents only for legacy or third-party software
    • No industry standard has emerged; most variants extend the Apache or nginx access log format.
  • Simple text lines put the data in fixed columns
    • but a customer ID that sits in different positions is hard to find, so consider structured JSON lines (harder for humans to read raw).
15-02-2020 16:00:58 Order INFO [abc-123] Customer 2112 has placed order 988827
15-02-2020 16:01:01 Payment INFO [abc-123] Payment $20.99 for 988827 by cust 2112

Correlating log lines

  • Example:
    • signing a customer up for the streaming service: UI click
    • Gateway
    • Streaming, which calls Payment
    • Customer and Email. If only Payment logs an odd error you cannot see it in context.
  • Use a correlation ID:
    • generated for the first call (in the Gateway) and passed to every subsequent call, written in a fixed place in each log line, so you can extract everything for a request
    • Every service must pass it on, so standardise and enforce
    • It also supports tooling for event storms, odd corner cases and costly transactions.
  • Hard to retrofit, so add them early; logs can take you far before you need a tracing tool.
15-02-2020 16:01:01 Gateway INFO [abc-123] Signup for streaming
15-02-2020 16:01:02 Streaming INFO [abc-123] Cust 773 signs up ...
15-02-2020 16:01:03 Customer INFO [abc-123] Streaming package added ...
15-02-2020 16:01:03 Email INFO [abc-123] Send streaming welcome ...
15-02-2020 16:01:03 Payment ERROR [abc-123] ValidatePayment ...

Timing

  • Timestamps are written on each machine, and clocks drift (clock skew)
    • NTP reduces but does not eliminate skew, so even a second can reorder a close sequence. So logs give neither fully accurate timing nor causality.
  • Leslie Lamport's logical clocks
    • ("Time, Clocks, and the Ordering of Events in a Distributed System", CACM 1978) use counters to order calls
    • Newman would rather use distributed tracing, which fixes both.

Implementations

  • Open source:
    • Fluentd forwarding to Elasticsearch, with Kibana. Costs: running Elasticsearch
    • it is billed as a database but is a search index (a projection of the source of truth), with data-loss problems found by Kyle Kingsbury's Jepsen analyses of versions 1.1.0 and 1.5.0, so keep the ability to re-index original logs
      • And Elastic changed the licence of Elasticsearch and Kibana from Apache 2.0 to the SSPL, angering many contributors
    • AWS committed to an open source fork.
  • Commercial:
    • Splunk (valuable but "eye-wateringly expensive")
    • Humio (Newman's favourite; built for efficient ingestion rather than indexing)
    • Datadog, and cloud tools such as CloudWatch (AWS) and Application Insights (Azure).

Shortcomings

  • Clock skew limits ordering and latency analysis.
  • Volume:
    • lots of data means hardware and fee costs
    • indexing is expensive as it grows (one team's Elasticsearch cluster handled only six weeks of logs for one product), pushing you to log less.
  • Sensitive data:
    • logs can hold valuable information, forcing access limits (complicating collective ownership) and making them an attack target
    • consider not logging some data ("if you don't store data, it can't be stolen").

10.4 Metrics aggregation

  • Raw numbers are hard to judge ("50 4XX errors per second:
    • bad?")
    • you need history to see patterns. New instances come and go, so collection must be easy, with metadata to aggregate for the whole system, per service or per instance.
  • Capacity planning: with on-demand IaaS, scaling takes minutes, so understanding trends keeps infrastructure just enough.
  • Resolution:
    • keep, say, 10-second samples for the last 30 minutes, and hourly averages for last month
    • Aggregating old data loses information, and you must guess in advance what to lose.
  • Standard metrics tools suit trends and simple failures but restrict the questions you can ask.

Low versus high cardinality

  • Cardinality
    • is roughly how many fields you can query in a data point (service name, customer ID, request ID, build number, product ID, OS, cloud provider...)
    • Time-series stores struggle as it grows.
  • Charity Majors (Honeycomb):
    • a metric is a number with tags, and "storing a tag is expensive"
    • Prometheus was built for low-cardinality data and its docs warn against labels such as user IDs or email addresses.
  • High-cardinality systems let you ask unplanned questions; they are very hard to retrofit.
  • Implementations:
    • Prometheus is now the popular open source choice (replacing Graphite, recommended in the first edition)
    • For high cardinality, Newman strongly suggests Honeycomb or Lightstep (often seen as tracing tools).

[!warning] Monitoring and observability systems are production systems Log aggregators, tracers and alerting tools are mission-critical and need the same diligence, and can be attack vectors: the SolarWinds supply chain attack (used by 425 of the US Fortune 500) reached networks including the US Treasury's.

10.5 Distributed tracing

  • Aggregation alone lacks the relationships between services
    • Correlation IDs in logs are a start, but need custom tooling to visualise
    • Distributed tracing works broadly the same everywhere: local activity in a thread is a span, spans share a unique identifier and go to a central collector that builds a trace (Figure 10-7 shows one in Honeycomb).
  • In the OpenTracing API a span has start and end times, associated logs and key-value pairs for querying (customer ID, order ID, hostname, build number).
  • Sampling:
    • collecting everything affects the system
    • Google's Dapper (the inspiration for most tools) sampled randomly and aggressively; Jaeger keeps 1 in 1,000 by default
    • Honeycomb and Lightstep sample dynamically: keep every error, but perhaps only 1 in 100 similar successes.
  • Implementing:
    • capture spans inside services (libraries and frameworks often support OpenTracing or OpenTelemetry already; instrument your own code too), send them (usually via a local forwarding agent that can buffer, change sampling and add tags), and run a collector
    • Jaeger is the popular open source choice; Lightstep and Honeycomb commercially
    • Choose something committed to OpenTelemetry, an open API from OpenTracing and OpenCensus with broad support, offering portability across vendors.

10.6 Are we doing OK?

  • "Up or down" means little in a distributed system: if one instance is unreachable, or Returns is reachable but half its functionality needs the troubled Inventory service, is it healthy? Like a beehive, one sick bee does not mean a sick hive
    • Metrics such as CPU are "one step removed" from "is the system working?".
  • Concepts from site reliability engineering (SRE):
Term Meaning
SLA (service-level agreement) Agreement between builders and users with consequences; usually the bare minimum. Example: AWS EC2 promises best-effort 90% instance uptime per hour and just stops charging for that hour if missed (real performance is far higher)
SLO (service-level objective) What a team signs up to provide (uptime, response times); meeting all teams' SLOs should exceed the SLAs, but SLOs may also be aspirational or internal
SLI (service-level indicator) A measure of something the software does (response time, a customer registered, an error, an order placed), used to check SLOs
Error budget How much error is acceptable: a 99.9% quarterly availability SLO allows about 2 hours 11 minutes of downtime
  • Error budgets inform risk: well under budget, perhaps roll out a service in a new language; over budget, focus on reliability. They give teams "breathing room to try new things".

10.7 Alerting

  • With microservices something is often going wrong; decide which problems should alert a human and how. Key question: "Should this problem cause someone to be woken up at 3 a.m.?"
  • Google example:
    • servers in a Mountain View lobby had hard drives attached with Velcro, because drives fail so often they are simply swapped
    • a drive failure is routine, handled in working hours.
  • Alert fatigue:
    • at Three Mile Island (1979) operators were overwhelmed by alerts and could not see the fundamental problem (operator Craig Faust: "I would have liked to have thrown away the alarm panel")
    • The 737 Max crashes (346 deaths) involved confusing multiple alerts, per the NTSB report
    • Too many alerts exceed "available mental resources".
  • Newman uses alert rather than alarm; the two are treated as equivalent. EEMUA's criteria for a good alert (via Steven Shorrock's "Alarm Design: From Nuclear Power to WebOps"):
Quality Meaning
Relevant Of value
Unique Not duplicating another
Timely Early enough to use
Prioritized Enough information to order them
Understandable Clear and readable
Diagnostic Clear what is wrong
Advisory Tells the operator what to do
Focusing Draws attention to the most important issues

10.8 Semantic monitoring

  • Define a model of acceptable system semantics and ask "is the system behaving the way we expect?" For MusicCorp: new customers can register
    • at least $20,000 of products sold per hour at peak
    • orders ship at a normal rate. These greatly exceed SLAs and help identify SLOs. Agreeing the model is hard and belongs with the product owner
    • operators must make sure the discussion happens.
  • Two ways to check: real user monitoring and synthetic transactions.
  • Real user monitoring:
    • compare real production behaviour with the model
    • Business data (sales) is often locked in a database, so expose "business" metrics to production tooling (if you can emit CPU rate to a metrics store, record a sale too)
    • It is noisy and tells you only what already happened.

10.9 Testing in production

  • Charity Majors:
    • "Not testing in prod is like not practicing with the full orchestra because your solo sounded fine at home." Many people fear it yet already do it
    • All forms are a kind of monitoring.
Technique Summary
Synthetic transactions Inject fake user behaviour with known inputs and outputs (create a customer, check it exists) regularly
A/B testing Two versions of a function shown to different users; compare which performs better (two registration forms)
Canary release Small share of users sees the new version, increased if it works
Parallel run Both implementations run on each request; the user sees one; compare results
Smoke tests After deployment but before release; from a simple "is it up" to full synthetic transactions
Chaos engineering Inject faults (Netflix's Chaos Monkey turns off production VMs); chapter 12
  • Synthetic transactions in practice (2005):
    • a Thoughtworks team building a pricing system for an investment bank (about five services, one on a grid scavenging cycles from roughly 250 desktops) ran Nagios every minute to insert a fake event into a queue, priced in a "junk" book
    • if no repricing appeared in time, an issue was raised. Newman finds it a far better indicator than low-level metrics, though you still need those to diagnose.
  • Implementing:
    • reuse a subset of your end-to-end tests (chapter 9)
    • Watch data requirements (fake users with known data) and side effects: a friend's ecommerce company ran its tests against production ordering and a large number of washing machines arrived at head office.

10.10 Standardisation and tool selection

  • Standardise
    • observability: log format, one place for metrics, standard metric names (not ResponseTime in one service and RspTimeSecs in another)
    • Make the right thing easy through a platform with building blocks (the platform team, chapter 15).
  • The space will churn (Honeycomb and Lightstep lead). Criteria:
Criterion Meaning
Democratic Usable by everyone, not only expert operators; affordable beyond critical production, and used in dev and test too
Easy to integrate Open standards (OpenTracing, OpenTelemetry) ease integration and switching vendors
Provide context Temporal (versus a minute, day or month ago), relative (versus other things), relational (what depends on this), proportional (how bad, who is impacted), per a Lightstep post
Real-time Seconds, not minutes or hours
Suitable for your scale Do not copy Google: Ben Sigelman says tools scaling to 5 billion RPCs per second are "profoundly feature poor"; at 5 million you can afford more

The expert in the machine

  • Vendors keep claiming ML will detect and diagnose problems automatically; Newman is dubious
    • Example: a European data science startup found clusters of patients in bed-monitor data, but only a clinician knew the cluster meant sicker patients
    • Likewise tools may say "something looks odd", but acting on it needs expertise
    • "The expert in the system is, and will remain for some time, a human." Do not make experts fight poor tools.

10.11 Getting started

  • Capture host metrics (CPU, I/O) and link each instance to its host
    • capture response times for service interfaces and log all downstream calls
    • correlation IDs from the start
    • log major business process steps
    • have basic log and metric aggregation.
  • Hesitate over a dedicated tracing tool if you must host it yourself (a managed service is easier). Create synthetic transactions for key operations.
  • Then make sure you can ask questions and say with confidence the system works for users.

Summary points

  • Shift from passive monitoring to actively making the system observable, from static dashboards to dynamic slicing and dicing.
  • Start with log aggregation and correlation IDs; add tracing when needed.
  • Move health from binary to nuanced; alert on SLOs rather than every small problem.
  • "Get good at handling the unknown." Reading: Majors, Fong-Jones and Miranda, Observability Engineering (O'Reilly, 2022)
    • Google's Site Reliability Engineering (2016) and The Site Reliability Workbook (2018).
Terms to carry forward
  • Observability, monitoring, event, MELT.
  • Log aggregation, correlation ID, clock skew, structured logging.
  • Cardinality, span, trace, collector, sampling, OpenTelemetry.
  • SLA, SLO, SLI, error budget.
  • Alert fatigue, semantic monitoring, real user monitoring, synthetic transaction, chaos engineering.
