Building Microservices 11: Security

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 11. Previous: Building Microservices 10: From Monitoring to Observability. Next: Building Microservices 12: Resiliency.

Takeaways
  • Microservices widen the attack surface (more data on networks, more infrastructure) but give more room to defend in depth and limit the blast radius.
  • Security is a mix of principles (least privilege, defence in depth, automation, built into delivery) and the NIST five functions: identify, protect, detect, respond, recover.
  • Foundations: manage credentials and secrets (rotate, revoke, limit scope), patch all layers, keep tested backups separate from production, and be able to rebuild automatically.
  • Choose a trust model (implicit versus zero trust), protect data in transit (server and client identity, visibility, manipulation) and at rest, and be frugal with data.
  • Authentication via SSO (OpenID Connect), authorise in the owning microservice (avoid the confused deputy), passing identity with JWTs.

11.1 Core principles

  • Newman is not a security expert ("a conscious incompetent") but argues developers need grounding, as they now do for testing and data. The dichotomy: more exposure, but more defences.
  • Security is only as strong as the weakest part: do not harden the front door and leave the back door open.

Principle of least privilege

  • Grant the minimum access needed, for the shortest time needed
    • A microservice with read-only database access limits an attacker to read-only access to that database; an expired credential is useless
    • It extends to which services may talk to which.

Defence in depth

  • Multiple layers, like Dover Castle (on a hill, two walls, a keep)
    • Microservices offer more places to protect: small, limited-scope services, different network segments, network protections at more points, and varied technology so a single zero-day does not hit everything.
Types of security controls
  • Preventative: stop an attack (storing secrets securely, encryption at rest and in transit, authentication and authorisation).
  • Detective: reveal an attack (application firewalls, intrusion detection).
  • Responsive: help during and after (automated rebuild, working backups, a communications plan).

You need a combination, with several of each. (Newman could not find the original source of this categorisation.)

Automation and delivery

  • Automation copes with many moving parts, reduces human error and variability, eases least privilege (specific privileges per script), and helps revoke and rotate keys.
  • Build security into delivery,
    • not as an afterthought ("Do you want fries with that?", Jonny Schneider on usability)
    • Developers need general awareness, specialists should embed in teams when needed ("Enabling Teams"), and tooling should help
    • Automated tools: OWASP ZAP (recreates attacks), Brakeman (Ruby static analysis), Snyk (vulnerable dependencies)
    • Put them in CI; they find only local issues, not systemic ones.

11.2 The five functions of cybersecurity (NIST)

Function Meaning Microservice angle
Identify Who the attackers are, what they want, where you are weakest Threat modelling from the outside in; look holistically, not at one or two services; an external party helps
Protect Defend key assets Most of the chapter: wider surface, more options
Detect Know if an attack happened More networks and machines; use chapter 10 techniques plus intrusion detection (container tools such as Aqua)
Respond Act on a breach Scope the breach; PII triggers privacy notification; the GDPR requires reporting personal data breaches to authorities within 72 hours (tell people earlier if you can); a blame culture hurts learning
Recover Restore and learn More parts to recover; automation and backups help
  • Threat modelling story:
    • a company argued over CCTV in reception after an intruder reached the corporate network, while a faulty front-door lock left the door unlocked in the mornings for years
    • Humans are bad at understanding risk and fixate on technology they know (JWTs, mutual TLS)
    • See Adam Shostack, Threat Modeling: Designing for Security (2014).

11.3 Foundations of application security

Credentials

  • Microservices mean many more credentials (services, machines, databases), tempting "lazy" broad shared ones. Two areas: user credentials and secrets
    • for both consider rotation, revocation and limiting scope.
  • User credentials:
    • Verizon's 2020 Data Breach Investigations Report found credential theft in 80% of hacking-related breaches
    • Advice (via Troy Hunt, from NIST and the UK NCSC): use password managers, long passwords, no complex rules, and no mandated regular changes
    • Cloud API keys matter too:
      • Code Spaces went out of business after an attacker destroyed everything, backups included, in one AWS account
      • another client lost over $10,000 to bitcoin mining on stolen keys (bots scan for credentials).

Secrets

  • Examples: TLS certificates, SSH keys, public/private API keypairs, database credentials. Lifecycle:
Stage Question
Creation How is it made?
Distribution How does it reach only the right place?
Storage Only authorised access?
Monitoring Do we know how it is used?
Rotation Can we change it safely?
  • Tools:
    • Kubernetes secrets (basic, stored in plain text; acceptable depending on your threat model)
    • HashiCorp Vault (open source; distributes secrets, generates time-limited credentials for databases and clouds, works with consul-template to update config files)
    • AWS Secrets Manager and Azure Key Vault (or run Vault yourself on the cloud with an encrypted backend).
  • Rotation:
    • limits an attacker's window (a keypair changed weekly gives one week)
    • Example: time-limited AWS keys generated on the fly, valid under an hour, so one checked into public GitHub is useless once expired
    • It can cause incidents when you do not know what uses a credential, so limit scope and automate.
  • Revocation:
    • if you know a credential leaked, revoke and regenerate automatically
    • services must re-read secrets (or be rolling-restarted). If you already rotate regularly, emergency revocation is likely covered.
  • Scanning for keys: private keys leak through commits; GitHub scans some; git-secrets (as a commit hook) and gitleaks scan before commit.
  • Limiting scope:
    • a shared Inventory login gives an attacker read/write
    • the Debezium process (feeding Kafka for ETL) gets a read-only login
      • Better: each instance its own credentials, so you can rotate or revoke one, trace a leak, and spot which instance ran an expensive query
    • needs automation (Vault).

Patching

  • Equifax (2017): an Apache Struts vulnerability, with a patch available for months, exposed data on over 160 million people and cost a $700 million settlement.
  • Layers needing patches:
    • hardware and OS, container runtime, Kubernetes and your code
    • A managed Kubernetes cluster reduces what you own
    • Containers are immutable but include an OS and base images (backdoors? six months of unapplied OS patches), so use tools like Aqua
    • Use Snyk or GitHub code scanning for third-party dependencies, which can send pull requests and fail the build.

Backups

  • "Like flossing": more say they do it than do
    • Replication and reliable disks tempt people to skip them, but a wiped Cassandra cluster or a deleting bug still happens
    • Automated deployment means you back up state (databases, perhaps logs), not whole machines (block-level clones are near instant).
  • Avoid the Schrödinger backup: a backup that may or may not be one until you restore it; restore regularly (for example build performance-test data from production backups).
  • Keep backups isolated from core systems: Code Spaces kept them in the compromised account. Use a separate account, maybe another region or provider.

Rebuild

  • After an attack, rebuild and remove the attacker's access
    • A rootkit once altered ls and ps; it was found by checking hashes against official packages, and the server had to be reinstalled
    • Routine rebuilds plus credential rotation limit persistent attackers.
  • Needs good automation and backup restoration
    • make rebuild the same as every deployment (container deploys do this). Caveat: can you rebuild the platform (the Kubernetes cluster) itself?

11.4 Implicit trust versus zero trust

  • Implicit trust: anything inside the perimeter is trusted. Common, often unconsciously; once an attacker is inside they can read, change or impersonate.
  • Zero trust
    • ("perimeterless computing"): assume you are already compromised ("the call is coming from inside the house"): assess every inbound call, store data and keys safely, and encrypt sensitive data in transit inside the system
    • It is a mindset, not a product; Jan Schaumann notes you can even allow connections to internal services from the internet since the internal network is treated as untrusted
    • It needs constant investment.
  • It is a spectrum:
    • be driven by your threat model
    • MedicalCo
      • classified data as Public, Private (logged-in users, such as insurance plan) or Secret (health data) and ran services in matching zones: a service runs in the zone of its most sensitive data
      • services reach down into no more secure zones, but services in secure zones may call less secure ones
    • The public zone is nearer implicit trust, the secret zone zero trust (a zoned approach is still defence in depth).

11.5 Securing data

Data in transit: four concerns

Concern Meaning and solution (HTTP example)
Server identity Is it really the server? HTTPS (HTTP with TLS) validates a certificate; also fine for SOAP or gRPC over HTTPS. (SSL was replaced by TLS but the name lingers)
Client identity Authenticate the calling service (shared secret, client certificate); do not make a central call per request (latency). Newman would not check client identity without server identity: mutual authentication, via mutual TLS, common in zero trust; Vault eases certificates and service meshes are partly adopted for this
Visibility TLS hides data from intermediaries, but also stops proxies like Squid or Varnish caching
Manipulation TLS also prevents tampering; or sign open data with an HMAC (hash sent with the data)

Data at rest

  • Breaches often involve unencrypted data or a flawed mechanism.
  • Go with the well known:
    • use tested implementations, never your own algorithm
    • use salted password hashing (not encryption, which can be reversed with the key)
    • badly implemented encryption can be worse than none.
  • Pick your targets: encrypting everything is simple but costly (CPU, logs, schema migrations needing decrypt-migrate-encrypt); finer-grained services let you encrypt specific tables.
  • Be frugal:
    • store only what you need
    • Mask the end of IP addresses; keep an age range and postcode rather than full details
    • Unstored data cannot be stolen or requested
    • The German Datensparsamkeit (from German privacy law) means storing only what business operations or law require.
  • It's all about the keys:
    • do not keep the key beside the data
    • Use a security appliance or key vault (Vault); database features such as SQL Server's Transparent Data Encryption need scrutiny of key handling
    • "Encrypt data when you first see it
    • Only decrypt on demand."
  • Encrypt backups too.

11.6 Authentication and authorisation

  • Authentication
    • confirms a party is who it says (the principal)
    • authorisation maps a principal to allowed actions. Users should not log in separately to each service: single sign-on (SSO).
  • Service-to-service: mutual TLS, or API keys used to hash a request.
  • Human authentication:
    • multifactor authentication (MFA) (2FA is a subset): SMS codes, email magic links, apps such as Authy, hardware keys (YubiKey), biometrics
    • Treat MFA as a must for key services and sensitive access such as source code.

Single sign-on implementations

  • A principal is sent to an identity provider (maybe with MFA), which tells the service provider who they are
    • the system decides what they may do. The provider can be external (Google offers an OpenID Connect provider) or internal, linked to a directory service (LDAP, Active Directory)
    • Okta is a hosted SAML provider that links to company directories.
  • SAML is SOAP-based and complex, and has fallen from favour; OpenID Connect (an implementation of OAuth 2.0, using simpler REST calls) is now dominant.

The SSO gateway

  • Rather than each service handling the handshake (duplication, shared library coupling, mixed stacks), a gateway proxy does it once
    • Downstream services need principal information: HTTP headers (Shibboleth with Apache and SAML) or a JWT.
  • Cautions:
    • harder to reason about a service in isolation (let developers run services behind a gateway)
    • a false sense of security (defence in depth: perimeter, subnet, firewall, machine, OS, hardware)
    • gateways accumulate functionality, becoming a coupling point with a larger attack surface.

Fine-grained authorisation

  • A gateway can do coarse-grained checks (only logged-in users reach the helpdesk; role STAFF). Finer decisions belong in the service: a CALL_CENTER principal sees customer data except payment details and issues capped refunds
    • CALL_CENTER_TEAM_LEADER larger ones.
  • Avoid roles like CALL_CENTER_50_DOLLAR_REFUND: service-specific behaviour then lives in a directory run by someone else. Favour coarse roles modelled on how your organisation works.

The confused deputy problem

  • An upstream party tricks an intermediate into doing something it should not
    • Example: a logged-in customer clicks /orderStatus/12345; the browser UI calls the Web Shop (a BFF; chapter 14), which asks Order and Shipping
    • Calls are authenticated, but the customer could guess other order IDs: authenticated yet not authorised
    • Who checks that user A may see A's order?
  • Centralised, upstream authorisation (in the gateway or Web Shop) implies implicit trust, makes the gateway know downstream functionality, and ties deployment to gateway configuration, undermining independent deployability.
  • Decentralised authorisation: the Order service decides, which needs the user's identity: a plain username header can be forged, hence JWTs (older approaches included nested SAML assertions).

JSON Web Tokens

  • A JWT holds claims in a string that can be signed (tamper-proof) and optionally encrypted, expire, and travel in many protocols (the HTTP Authorization header)
    • It has three dot-separated parts: header (signing algorithm), payload (JSON claims; standard public claims such as exp are honoured by libraries; do not reuse those names), and signature (integrity and, with a private key, origin).
{
  "sub": "123",
  "name": "Sam Newman",
  "exp": 1606741736,
  "groups": "admin, beta"
}
  • Using tokens:
    • after login a session token (likely OAuth) lives on the client
    • each request hits the gateway, which generates a JWT valid for that request and passes it downstream
    • services verify the signature and read claims. Per-request JWTs are common (short validity, easier key changes, and clients are unaffected). It beats nested SAML assertions.
  • Challenges:
    • Keys: verifying needs a public key out of band; handle changes (Vault can supply and rotate).
    • Expiry:
      • long asynchronous processes (days of order fulfilment) clash with short tokens
      • teams use special longer-lived scoped tokens or stop using the token at some point (no settled answer).
    • Size: one music-rights domain might need up to 10,000 entries per track; use a simple token for most, plus a data store lookup for the rare complex case.

Summary points

  • Build security with a holistic view and threat modelling; use a mix of controls and a multifaceted approach.
  • Finer-grained services let you reduce the impact of a breach and trade overhead against data sensitivity.
