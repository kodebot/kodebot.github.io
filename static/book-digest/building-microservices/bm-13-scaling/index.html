Building Microservices 13: Scaling

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 13. Previous: Building Microservices 12: Resiliency. Next: Building Microservices 14: User Interfaces.

Takeaways
  • Scale for performance (load, latency) or robustness. Four axes: vertical, horizontal duplication, data partitioning, functional decomposition; you may combine them.
  • Try the cheap, low-risk ones first (vertical, horizontal); decomposition is the biggest change, so exhaust the others before it unless you have other reasons.
  • Caching helps performance, scale and robustness, but cache in as few places as possible; choose an invalidation scheme (TTL, conditional GET, notification, write-through, write-behind).
  • Autoscale for failure first, then load; scale down cautiously.
  • Start small, measure, experiment; needing to re-architect for scale "is a sign of success".

13.1 The four axes of scaling

The Scale Cube (Abbott and Fisher, The Art of Scalability, 2nd ed., 2015) has three axes: functional decomposition, horizontal duplication, data partitioning. Newman adds a fourth, vertical scaling. Running example: FoodCo (anonymised), a food delivery firm struggling with write contention on its primary database.

Vertical scaling

  • Get a bigger machine
    • Quick and low-risk on virtualised or cloud infrastructure (an AWS u-24tb1.metal has 24 TB of memory)
      • resizing a VM or renting a bigger instance needs few code changes (perhaps runtime memory flags)
    • It can also make other scaling easier (a bigger database host can hold new services' databases).
  • Historically it meant buying hardware with long lead times and oversizing. If you would have to buy new kit, Newman skips to horizontal duplication.
  • Limits:
    • CPUs now gain cores, not clock speed, and software often cannot use them (4 to 8 cores may give little)
    • it does little for robustness (a down machine is down)
    • cost rises faster than capacity. FoodCo had already upgraded the database several times and it would not last given growth.

Horizontal duplication

  • Duplicate part of the system and distribute the work. Often tried early: run several copies of the monolith.
  • Implementations:
    • Load balancer across instances (here Catalog); detects and removes bad nodes; mostly software and often client side; part of the service's logical boundary.
    • Competing consumers (Hohpe and Woolf): song uploads queue jobs and several Song Transcoder instances consume; add instances for throughput.
    • Read replicas: FoodCo offloaded read-heavy traffic from the primary, with routing internal to the microservice, freeing the primary for writes.
  • Benefits: application rarely changes; the next step if vertical is unavailable.
  • Limits:
    • more infrastructure and cost
    • a "blunt instrument" (copies of a whole monolith though only part is stressed)
    • you depend on the distribution mechanism. Needing sticky sessions (same user, same replica) causes other problems: avoid.

Data partitioning

  • Apply a function to a key to choose a partition (shard)
    • Example: family names A to M to one database and N to Z to another (identical schemas, different rows)
    • It can be done at the database (if natively supported) or microservice instance level (via a proxy; good with in-memory caches, scales both tiers)
    • Consumers should not see it.
  • Also common:
    • geographic partitioning
    • FoodCo rejected per-country partitions: expansion would mean a new partition for every country, raising the cost of entering markets
    • Cassandra partitions reads and writes across a "ring", and Kafka partitions topics.
  • Benefits:
    • scales transactional workloads and writes
    • smaller maintenance impact (per-partition updates, off-peak by region)
    • data residency (EU data stays in the EU)
    • combines with duplication.
  • Limits:
    • Robustness: a failed partition fails its share (one of four = 25% of requests), so combine with duplication.
    • Choosing the key:
      • surname is poor: Chinese surnames number under about 4,000, and the top 100 cover over 80% of people, skewed to N to Z in Mandarin
      • A unique customer ID distributes evenly and survives name changes.
    • Changing scheme: adding nodes is easy (Cassandra rebalances; Kafka adds partitions but existing messages stay), but fixing a bad scheme hurts (one client took production offline for three days).
    • Cross-shard queries (customers over 18) need querying every shard and joining, or an alternative read store, often asynchronous with cached results (Mongo uses map/reduce).
  • Write scaling is where databases differ most
    • changing technology is common (a bigger box meanwhile). See Sadalage and Fowler, NoSQL Distilled (2012). It mostly changes data, code lightly.

Functional decomposition

  • Extract functionality so it scales independently (the Order service from MusicCorp's system)
    • the canonical microservice move (chapter 3). FoodCo's path: vertical exhausted, duplication used, partitioning discounted, so it moves deliveries and menus out first, which also lets a growing delivery team own them.
  • Benefits:
    • rightsize infrastructure (switch off rarely used parts, small machines for light loads, more for constrained ones)
    • cost control (why SaaS providers use it)
    • room for different technologies
    • organisational scaling (chapter 15). Not robust by itself, but allows partial failure tolerance.
  • Limits:
    • complex, no short-term benefit, the largest code impact (frontend and backend, plus data), and more services to run and make robust
    • Newman exhausts other options first, unless other drivers exist (FoodCo wants to grow its team and countries).

13.2 Combining models

  • Scale along several axes:
    • extract Order, then duplicate it, then partition it by geography with duplication within each group
    • Scaling on one axis eases others: decomposing Order lets you duplicate or partition it alone, not the whole monolith
    • The goal is not all axes, but knowing the trade-offs.

13.3 Start small

  • Knuth:
    • "premature optimization is the root of all evil (or at least most of it)". Optimise for real need
    • scaling one part adds new moving parts and new fragility (Order on its own infrastructure is another service to keep available).
  • Experiment scientifically: use automated load tests for a baseline, recreate the bottleneck, change, observe.

[!note] CQRS and event sourcing CQRS (Command Query Responsibility Segregation) uses separate models for reads and writes, deployable separately and scaled independently; often paired with event sourcing (derive entity state from its event history). Like read replicas in the application tier, but "a complex pattern to execute well"; if only read-constrained, try a read replica first. Both change how developers think. They are an internal implementation detail of a service and should be invisible to consumers.

13.4 Caching

  • Store a previous result for reuse. Example: Recommendation keeps a local copy of stock levels from Inventory (the origin): a cache hit or a cache miss (fetch from the origin)
    • entries need invalidation.
  • Why cache:
    • Performance: avoids network hops and recomputation (an expensive top-sellers-by-genre join).
    • Scale: diverts reads from a contended origin (read replicas are a cache with automatic invalidation).
    • Robustness:
      • a local cache can serve if the origin is down, if you do not evict stale data automatically: you favour availability over consistency
      • The Guardian crawled the live site periodically into a static fallback version.

Where to cache

Example: Sales records item IDs and timestamps; the top ten best sellers need album names from Catalog.

Location What it is Trade-offs
Client-side Data cached outside the origin (an in-memory ID-to-name map in Sales; store only the fields you need) Avoids the network call; good for latency and robustness. But limited invalidation options and inconsistency between clients (Sales, Recommendation, Promotions)
Shared client-side One Redis or memcached for several clients Consistent, fewer copies (memory is scarce), but a round trip; blurs the client/server line
Server-side Catalog caches for its consumers (in memory, a reverse proxy, a hidden Redis, read replicas) Invisible to consumers, easier sophisticated invalidation (write-through), consistent view; but a round trip remains, so less for latency and robustness
Request cache Cache the top ten result itself Fastest; but only that request benefits

Invalidation

"There are only two hard things in Computer Science: cache invalidation and naming things." (Phil Karlton)

  • Time to live (TTL):
    • valid for a duration (5 minutes) via HTTP Cache-Control or timestamps via Expires; the origin can hint (shorter for fast-selling items)
    • Simple but blunt: data can be stale for 4 minutes 59 seconds
    • Start with one TTL per resource type.
  • Conditional GETs:
    • an ETag identifies a resource version; send If-None-Match: <etag>
    • The server returns 304 Not Modified or 200 with the new version and ETag
    • It still makes a request, so it saves regeneration cost, not round trips (useful when building the response is expensive).
  • Notification-based:
    • the origin emits events (Inventory's Stock Change) so subscribers invalidate
    • Narrows the stale window and is elegant but more complex (a broker fits)
    • Use a heartbeat event to know the mechanism is alive; decide whether notifications carry the state or just "changed" (size and sensitivity, as in chapter 4).
  • Write-through: update the cache with the origin; practical server-side (same transaction), vague elsewhere; nearly removes staleness.
  • Write-behind: write the cache first, the origin later: faster but risks data loss and blurs the source of truth; rare in microservices.

[!warning] The golden rule of caching Be careful about caching in too many places. Inventory caching with a 1 minute TTL and Recommendation caching with 1 minute can leave data up to 2 minutes old while it looks like 1. "The ideal number of places to cache is zero." Treat caching as a performance optimisation and cache in as few places as possible.

  • Freshness versus optimisation:
    • cutting a TTL from 5 minutes to 1 shrinks staleness to a fifth but means five times the origin calls
    • Sometimes it is safest to turn off a feature if a cache fails.
  • Cache poisoning (AdvertCorp again):
    • a bug skipped overriding cache headers on some proxied legacy pages that carried Expires: Never
    • Squid and browsers (and CDNs, ISPs) cached them, and only changing the URLs fixed it, since browser caches cannot be cleared. Understand the full path of cached data.

13.5 Autoscaling

  • With automated provisioning and deployment you can scale automatically: predictively (known trends, such as instances up at 8:45 and down at 17:15) or reactively (load or failure)
    • Know how fast you can scale: if you get two minutes' notice but need ten to scale, hold spare capacity
    • Load tests validate rules.
  • A news site suits both:
    • daily and weekend patterns plus unpredictable spikes
    • In practice autoscaling is used more for failures (AWS "at least five instances": the whack-a-mole during maintenance)
    • Autoscale for failure first, and scale down cautiously: more power than needed beats too little.

13.6 Starting again

  • The first architecture may not suit later volumes
    • Gilt's Rails monolith worked for two years, then needed redesign
    • Do not build for massive scale at the start
      • you may not know what to build or whether it will succeed (Eric Ries spent six months on a product nobody downloaded; a 404 link would have taught the same)
    • "The need to change our systems to deal with scale isn't a sign of failure
    • It is a sign of success."

Summary points

  • Know what you need: techniques that improve latency may not help volume.
  • Many forms of scaling add complexity, so be targeted and avoid premature optimisation.
  • Next: the user interface.
