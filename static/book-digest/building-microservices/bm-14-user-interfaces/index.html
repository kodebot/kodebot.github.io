Building Microservices 14: User Interfaces

Source: Sam Newman, Building Microservices, 2nd ed. (O'Reilly, 2021), ch. 14. Previous: Building Microservices 13: Scaling. Next: Building Microservices 15: Organizational Structures.

Takeaways
  • The UI is where microservice capabilities are woven together; think digital, not web versus mobile.
  • Prefer stream-aligned teams owning UI and services end to end over a dedicated frontend team; solve the usual reasons (scarce specialists, consistency, SPAs) differently.
  • Patterns: monolithic frontend, micro frontends (page-based, widget-based), central aggregating gateway, backend for frontend (BFF), with GraphQL as an implementation option.
  • Newman's defaults: page-based for websites, widget-based micro frontends for SPAs, a BFF per experience when mobile or third parties need tailored calls.

14.1 Toward digital

  • Web and mobile are no longer treated separately:
    • you cannot predict how customers will interact, which drives granular APIs
    • Microservice capabilities are combined to curate experiences on desktop, mobile, wearables or in a physical store.
  • Two sides: who owns what, and how to implement.

14.2 Ownership models

  • A layered organisation (frontend team, backend team, data team) means adding one control needs three teams and hand-offs
    • Newman prefers the UI broken apart and owned by teams that also own the server-side functionality: faster changes and direct contact with end users (backend teams lose track of who the user is)
    • Yet dedicated frontend teams remain the commoner pattern.

Why dedicated frontend teams exist

Driver Answer
Scarce specialists Embed them or use enabling teams; share skills via communities of practice (DBAs, operations and testers followed the same path, and specialists get time for hard problems)
Consistency Specialists across teams, a living style guide, shared components; the Financial Times Origami enabling team builds web components with the design team. Consistency is not universal: Amazon and AWS accept inconsistent UIs for team autonomy ("speed of delivery trumps consistency")
Technical challenges Single-page applications (SPAs) (Angular, React, Vue) are hard to split, which micro frontends address
  • Stream-aligned teams
    • (Skelton and Pais, Team Topologies, 2019): aligned to a single valuable stream of work, delivering "without requiring hand-offs to other teams": full stack teams, not full stack developers
    • FinanceCo (a European fintech): most teams ship customer-facing software with customer-oriented KPIs, so the impact of a change is clear.
  • Users see "a single pane of glass" and do not care whether the UI is modular.

14.3 Pattern: monolithic frontend

  • All UI state and behaviour live in the UI, which calls microservices for data (an Album details screen pulls the album and track listing from the Album service and offers from Promotions, returning JSON)
    • Typical of monolithic SPAs with a dedicated frontend team
    • Binary protocols suit native or thick clients, not browsers.
  • Downsides:
    • drives (or is driven by) a dedicated frontend team
    • contention if several teams share it
    • little scope to tailor responses per device (a phone needing 10 of 100 order fields). It suits a single team owning UI and services
    • with several teams, resist it as it leads to a layered architecture.

14.4 Pattern: micro frontends

  • "An architectural style where independently deliverable frontend applications are composed into a greater whole" (Cam Jackson, martinfowler.com, 2019). Microservices give backend independent deployability
    • micro frontends give it for the frontend, which is essential for stream-aligned teams that own UI and services (stock, purchase flow and customer profile teams each changing their part).
  • Two techniques:
    • widget-based and page-based decomposition
    • Limit: cross-cutting capabilities (type-ahead recommendations while searching) do not fit a widget or page, so you fall back to API calls.

[!note] Self-contained systems (SCS) An SCS is an autonomous web application with no shared UI, owned by one team, asynchronous communication where possible, no shared business code. Newman agrees with many ideas (especially single-team ownership) but finds it overly prescriptive ("autonomous web application" rules out a native iOS app using gRPC) and focused on activity over principles; he would rather focus on stream-aligned teams and let architecture follow.

14.5 Pattern: page-based decomposition

  • The UI is several web pages, served by different services (/albums/ from the Albums service, /artists/ from Artists) stitched by common navigation
    • services may call others (Inventory for stock). The owning team renders full UI end to end.
  • It is the classic web:
    • URLs, links, bookmarks, back and forward. No fancy JavaScript or iFrames
    • adapt per device with progressive enhancement. It is Newman's default for a website
    • many UIs that suit it are shoehorned into SPAs.

14.6 Pattern: widget-based decomposition

  • A screen holds widgets changeable independently (basket and recommendations on MusicCorp; the Recommendations widget cycles a carousel and adds to a wishlist, calling the Recommendations and Wishlist services), within a container application (core navigation, which widgets)
    • Spotify uses it heavily.
  • Implementation: HTML fragments via server or client templating for simple widgets; for complex ones, avoid clashes. Not iFrames (sizing and communication problems).
  • Dependencies:
    • widgets share a page, so conflicts matter (React v16 versus v15), but it eases incremental upgrades. The cost is duplication and page weight (CNN's page was 7.9 MB, more than Alpine Linux's 5 MB)
    • put automated page-weight checks in place.
  • Communication: the chart widget emits a custom Album Selected event; recommendations and album details subscribe: event-driven interaction inside the browser.

[!note] Web components The Web Component Standard (sandboxing HTML, CSS and JavaScript) seemed the obvious fit but took long to settle and be supported; Newman has met no organisation serving them from microservices, and is "not holding my breath".

  • When to use:
    • it lets several stream-aligned teams contribute to one UI, more flexibly than pages, and enabling teams can supply reusable widgets
    • When building an SPA, micro frontends are his default
    • Concerns: separate bundling (one-off) and payload size.

14.7 Constraints

  • Devices impose constraints:
    • browsers, screen resolution
    • screen readers and keyboard navigation for accessibility (legal duties exist, such as the UK Equality Act 2010, s. 20), and on mobile bandwidth, battery, one-handed use, no right-click
    • SMS interfaces in the global south.
  • A common response is call filtering and aggregation to strip unneeded data and combine calls.

14.8 Pattern: central aggregating gateway

  • A gateway between UIs and microservices that filters and aggregates for all UIs. Without it, a "recent orders" screen calls Customer (pulling all fields for a few) and Order separately
    • the gateway makes one call, combines and discards extra data, and can batch lookups, cutting bandwidth and latency.
  • Problems:
    • Ownership: it ends up with a dedicated team (a siloed layered architecture) and becomes a bottleneck; a frontend team may lack the backend skills.
    • Different UIs: mobile and web want different data and calls, so the gateway bloats and many teams change one deployable.
    • Multiple concerns: buy a product for generic needs (API keys, authentication, routing) but do not put aggregation in it: you work in its DSL, bake smarts into a third party, and aggregation may really be domain functionality for a service.
  • When to use: acceptable if one team owns UI and services, and keep it limited.

14.9 Pattern: backend for frontend (BFF)

  • A BFF is single-purpose, built for one UI, so it avoids being a shared bottleneck and coupling to the UI is acceptable: "the UI is actually split into two parts", one on the device and one on the server, owned by the same team
    • Used well at SoundCloud and REA.
  • How many?
    • The preferred model is one BFF per client type (REA: separate BFFs for iOS and Android, run by separate teams)
    • Variation: SoundCloud shared one BFF between its Android and iOS Listener apps, though its engineers might reconsider (the "mobile team" was really two)
    • Stewart Gleadow's guideline: "one experience, one BFF"; align with team boundaries (Conway's law).
  • Reuse:
    • duplication across BFFs is easier to spot than in clients (common server stack), but merging them recreates the central gateway. Newman tolerates duplication across services
    • options are a shared library (cheap, risky coupling) or a new microservice (good for domain logic)
      • Example: the wishlist (Customer holds the wishlist, Catalog name and price, Inventory stock) needed by both BFFs becomes a Wishlist service
    • the rule of thumb is to abstract on the third use.
  • Beyond mobile:
    • web BFFs help with server-side templating and with caching aggregated calls (a reverse proxy in front)
    • BFFs also work for third parties (royalty reporting, set-top boxes): breaking changes for one party do not affect others.
  • When to use:
    • for a web-only app only if server-side aggregation is significant
    • as soon as mobile or third-party needs arise, consider a BFF per client from the start, especially when UI and service teams are separated.

14.10 GraphQL

  • A query language where clients ask for exactly the fields they want (and nested data, saving round trips), requiring explicit types
    • A server-side resolver maps queries to microservice calls, so GraphQL can implement an aggregating gateway or BFF and client query changes need no server change (unless new types or fields are required)
    • Align multiple GraphQL backends with team boundaries (it then acts as a BFF)
    • Chapter 5 gives the concerns.
{
  order(id: 123) {
    date
    total
    status
    delivery {
      company
      driver
      duedate
    }
  }
}

14.11 A hybrid approach

  • Mix: widget-based for the website, a BFF for mobile. Keep cohesion: ordering or customer-detail logic stays in the owning services, not smeared across intermediate layers.

Summary points

  • Decomposition need not stop at the server, and dedicated frontend teams are not inevitable.
  • Next: organisational structures.
Terms to carry forward
  • Stream-aligned team, enabling team, SPA.
  • Monolithic frontend, micro frontend, page-based and widget-based decomposition.
  • Self-contained system, aggregating gateway, BFF, GraphQL resolver.
