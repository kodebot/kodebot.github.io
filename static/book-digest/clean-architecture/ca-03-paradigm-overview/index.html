Clean Architecture 3: Paradigm Overview

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 3. Own-words digest. Previous: Clean Architecture 2: A Tale of Two Values. Next: Clean Architecture 4: Structured Programming.

Takeaways
  • Three programming paradigms exist: structured, object-oriented and functional.
  • Each removes a capability and none adds one: structured programming disciplines direct transfer of control, object-oriented programming indirect transfer of control, functional programming assignment.
  • All three were discovered between 1958 and 1968; Martin expects no more negative paradigms.
  • Architecture connects to all three: polymorphism crosses architectural boundaries, functional programming disciplines data location and access, and structured programming is the algorithmic foundation of modules.

3.1 The three paradigms

  • Structured programming:
    • the first paradigm adopted (not the first invented), discovered by Edsger Wybe Dijkstra in 1968
    • He showed that unrestrained jumps (goto) harm program structure and replaced them with the familiar if/then/else and do/while/until constructs
    • Summary: structured programming imposes discipline on direct transfer of control.
  • Object-oriented programming:
    • the second paradigm adopted but actually discovered two years earlier, in 1966, by Ole Johan Dahl and Kristen Nygaard
    • They noticed that the function call stack frame in ALGOL could be moved to a heap, so local variables declared by a function could exist long after it returned
    • The function became a constructor for a class, locals became instance variables and nested functions became methods
      • this led inevitably to polymorphism through the disciplined use of function pointers
    • Summary: object-oriented programming imposes discipline on indirect transfer of control.
  • Functional programming:
    • the third, only recently adopted, yet the first invented: it predates programming itself
    • It comes from Alonzo Church, who in 1936 invented lambda calculus (written "l-calculus" in the page text) while pursuing the same mathematical problem that motivated Alan Turing at the time
    • Lambda calculus underlies LISP, invented in 1958 by John McCarthy
    • A foundational notion is immutability: the values of symbols do not change, so a functional language effectively has no assignment statement (most do offer some means to alter a variable, under strict discipline)
    • Summary: functional programming imposes discipline upon assignment.

3.2 Food for thought

  • The pattern is deliberate:
    • each paradigm removes capabilities from the programmer and none adds any
    • Each imposes extra discipline that is negative in intent: the paradigms tell us what not to do more than what to do.
  • Together they remove goto statements, function pointers and assignment
    • Is anything left to take away? Probably not, so these are likely the only three negative paradigms, supported by the fact that they were all discovered within ten years (1958 to 1968) and no new paradigms have been added in the decades since.

3.3 Conclusion: why this matters to architecture

  • "Everything." Martin's mapping to architecture's three big concerns:
    • Polymorphism is the mechanism to cross architectural boundaries (separation of components).
    • Functional programming imposes discipline on the location of and access to data (data management).
    • Structured programming is the algorithmic foundation of modules (function).

Summary points

  • Structured, object-oriented and functional programming each take away a power: direct jumps, unmanaged indirect calls, and unrestricted assignment.
  • The next three chapters take each paradigm in turn and tie it to architecture.
Terms to carry forward
  • Structured / object-oriented / functional programming; goto; polymorphism; immutability.
  • Each paradigm removes a capability (discipline, not new power).
