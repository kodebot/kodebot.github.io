Clean Architecture 7: SRP, the Single Responsibility Principle

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 7. Own-words digest with short attributed quotes. Previous: Clean Architecture 6: Functional Programming. Next: Clean Architecture 8: OCP, the Open-Closed Principle.

Takeaways
  • SRP is not "every module does one thing" (that rule, "a function should do one, and only one, thing", is a different, low-level rule). The principle is: a module should be responsible to one, and only one, actor.
  • An actor is a group of people (users or stakeholders) who require the same change; a module is a source file or a cohesive set of functions and data structures.
  • Symptoms of violation: accidental duplication and merges. Solution: separate code that different actors depend on (data structure plus separate classes, optionally a Facade).
  • SRP reappears at larger scales as the Common Closure Principle (components) and the Axis of Change that drives architectural boundaries.

7.1 What SRP means

  • Of the SOLID principles SRP may be the least well understood, probably because its name is inappropriate: programmers hear it and assume every module should do just one thing
    • There is such a principle (a function should do one thing; used when refactoring large functions into smaller ones, at the lowest levels) but it is not SRP.
  • Historical wording:
    • "A module should have one, and only one, reason to change." Software changes to satisfy users and stakeholders: those are the "reason to change"
    • Rephrased: "A module should be responsible to one, and only one, user or stakeholder." But "user" and "stakeholder" are not quite right: several people may want the same change, so Martin refers to the group as an actor
    • Final form: "A module should be responsible to one, and only one, actor."
  • Module:
    • the simplest definition is a source file
    • where code is not in source files it is a cohesive set of functions and data structures. "Cohesive" implies the SRP: cohesion is the force that binds together the code responsible to a single actor.
  • The best way to understand it is through the symptoms of violation.

7.2 Symptom 1: accidental duplication

  • Martin's favourite example:
    • the Employee class of a payroll application with three methods: calculatePay(), reportHours() and save() (Figure 7.1)
    • It violates SRP because the methods are responsible to three very different actors:
    • calculatePay(): specified by the accounting department, reporting to the CFO.
    • reportHours(): specified and used by human resources, reporting to the COO.
    • save(): specified by the database administrators (DBAs), reporting to the CTO.
  • Putting them in one class couples the actors to each other, so what the CFO's team does can affect something the COO's team depends on.
  • Example:
    • calculatePay() and reportHours() share an algorithm for non-overtime hours, which careful, non-duplicating developers put in regularHours() (Figure 7.2)
      • The CFO's team decides the calculation needs a tweak
    • HR does not want it (they use non-overtime hours for another purpose)
      • A developer sees regularHours() called by calculatePay() but does not notice reportHours() also calls it, makes and tests the change
    • the CFO's team validates it and it deploys. HR keeps using reportHours() reports that are now wrong
    • when found, the COO is "livid because the bad data has cost his budget millions of dollars".
  • "We've all seen things like this happen": the problems come from putting code that different actors depend on in close proximity
    • The SRP says to separate the code that different actors depend on.

7.3 Symptom 2: merges

  • Merges are common in source files with many methods, especially if they serve different actors
    • Example: the CTO's DBAs decide on a schema change to the Employee table, while the COO's HR clerks need a change to the hours report format
    • Two developers, possibly on different teams, check out Employee and their changes collide: a merge
    • Merges are risky ("no tool can deal with every merge case"); here the merge puts the CTO and the COO at risk, and possibly the CFO.
  • Many other symptoms exist but all involve several people changing the same source file for different reasons. The cure is again to separate code that supports different actors.

7.4 Solutions

  • Many solutions exist; each moves functions into different classes.
    • Separate the data from the functions
      • (Figure 7.3): the three classes (pay calculation, hour reporting, saving) share access to EmployeeData, a simple data structure with no methods
      • Each class holds only the code for its function and the three are not allowed to know about each other, so accidental duplication is avoided.
    • Downside:
      • developers must instantiate and track three classes
      • A common remedy is the Facade pattern (Figure 7.4): an EmployeeFacade with very little code that instantiates and delegates to the classes.
    • Some prefer to keep the most important business rules closer to the data: keep the most important method in the original Employee class and use that class as a Facade for the lesser functions (Figure 7.5).
  • Objection:
    • "every class would contain just one function"
    • Not so: calculating pay, generating a report or saving likely needs many functions, so each class has many private methods
    • Each such class is a scope: outside it no one knows the private members exist.

7.5 Conclusion

  • SRP is about functions and classes, but returns in different forms at two more levels: at the component level as the Common Closure Principle
    • at the architectural level as the Axis of Change responsible for creating architectural boundaries.

Summary points

  • One actor per module; cohesion binds the code that answers to one actor.
  • Violations show up as accidental duplication (shared code changed for one actor, breaking another) and merges.
  • Separate by actor (data plus classes, Facade); the same idea scales to components and architecture.
Terms to carry forward
  • SRP: one, and only one, actor.
  • Accidental duplication; merge conflicts; Facade.
  • Common Closure Principle; Axis of Change.
