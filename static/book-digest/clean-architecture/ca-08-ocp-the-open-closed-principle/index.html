Clean Architecture 8: OCP, the Open-Closed Principle

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 8. Own-words digest with short attributed quotes. Previous: Clean Architecture 7: SRP, the Single Responsibility Principle. Next: Clean Architecture 9: LSP, the Liskov Substitution Principle.

Takeaways
  • OCP (coined by Bertrand Meyer, 1988): "A software artifact should be open for extension but closed for modification." Extending behaviour should not require modifying the artifact.
  • It is "the most fundamental reason that we study software architecture": if simple requirement extensions force massive changes, the architecture has failed.
  • At the architectural level it works by SRP (separate things that change for different reasons) plus DIP (organise dependencies properly) into a hierarchy of components where higher-level components are protected from changes in lower-level ones.
  • Directional control (interfaces that invert dependencies) and information hiding (no transitive dependencies) shape the dependencies.

8.1 The principle

  • OCP was coined in 1988 by Bertrand Meyer (Object Oriented Software Construction, Prentice Hall, 1988, p. 23): "A software artifact should be open for extension but closed for modification." The behaviour of an artifact ought to be extendable without having to modify that artifact.
  • This is "the most fundamental reason that we study software architecture": if simple extensions to the requirements force massive changes, the architects have engaged in "a spectacular failure".
  • Most students see OCP as guiding class and module design, but it takes on greater significance at the level of architectural components.

8.2 A thought experiment

  • A system shows a financial summary on a web page:
    • scrollable, negatives in red
    • Stakeholders ask for the same information as a report for a black-and-white printer: properly paginated with page headers, footers and column labels, negatives in parentheses
    • Some new code is needed, but how much old code must change? A good architecture reduces changes "to the barest minimum
    • Ideally, zero."
  • How: properly separate the things that change for different reasons (SRP), then organise the dependencies between them properly (DIP).
  • Applying SRP (Figure 8.1): an analysis procedure inspects the financial data and produces reportable data, formatted by two reporter processes
    • The insight: generating the report involves two separate responsibilities, the calculation of the reported data and the presentation into web- and printer-friendly form.
  • Then organise source code dependencies so a change to one responsibility does not change the other and behaviour can be extended without undue modification
    • Do it by partitioning the processes into classes and the classes into components (the double lines in Figure 8.2): the Controller (upper left), the Interactor (upper right), the Database (lower right) and four components for the Presenters and Views (lower left)
    • Notation: <I> interfaces, <DS> data structures, open arrowheads using relationships, closed arrowheads implements or inheritance.
  • Notice:
    • all dependencies are source code dependencies: an arrow from class A to class B means A's source mentions B but B mentions nothing of A
    • For instance FinancialDataMapper knows FinancialDataGateway through an implements relationship, while the gateway knows nothing of the mapper.
  • Also each double line is crossed in one direction only, so all component relationships are unidirectional (Figure 8.3), and the arrows point toward the components we want to protect from change.

8.3 Protecting components

  • The rule: if component A should be protected from changes in component B, then component B should depend on component A.
    • Protect the Controller from changes in the Presenters; protect the Presenters from changes in the Views; protect the Interactor from changes in "well, anything".
    • The Interactor best conforms to OCP:
      • changes to the Database, the Controller, the Presenters or the Views have no impact on it. It holds this privileged position because it contains the business rules, the application's highest-level policies
      • all the other components handle peripheral concerns while the Interactor handles the central one.
    • The Controller is peripheral to the Interactor yet central to the Presenters and Views; the Presenters are peripheral to the Controller but central to the Views.
  • This creates a hierarchy of protection based on "level":
    • Interactors are the highest-level concept and the most protected
    • Views are among the lowest and the least protected
    • Presenters sit above Views but below the Controller and Interactor.
  • This is OCP at the architectural level: architects separate functionality based on how, why and when it changes, then organise it into a hierarchy of components in which higher-level components are protected from changes made to lower-level ones.

8.4 Directional control and information hiding

  • Much of the complexity in the class diagram exists to make the component dependencies point in the correct direction. For example the FinancialDataGateway interface between the FinancialReportGenerator and the FinancialDataMapper exists to invert the dependency that would otherwise point from the Interactor component to the Database component
    • likewise the FinancialReportPresenter interface and the two View interfaces.
  • Information hiding:
    • the FinancialReportRequester interface protects the FinancialReportController from knowing too much about the Interactor's internals
    • Without it the Controller would have transitive dependencies on the FinancialEntities
    • Transitive dependencies violate the general principle that software entities should not depend on things they do not directly use (met again in the Interface Segregation Principle and the Common Reuse Principle).
  • So although the first priority is to protect the Interactor from changes to the Controller, we also protect the Controller from changes to the Interactor by hiding the Interactor's internals.

8.5 Conclusion

  • OCP is "one of the driving forces behind the architecture of systems": the goal is a system easy to extend without a high impact of change, accomplished by partitioning into components and arranging them in a dependency hierarchy that protects higher-level components from changes in lower-level ones.

Summary points

  • Open for extension, closed for modification; failing it means requirement extensions force massive change.
  • Get there with SRP (separate reasons to change) and DIP (dependencies point toward the components to protect).
  • Level equals protection: business rules (Interactor) at the top; details (Views, Database) below.
Terms to carry forward
  • OCP; component hierarchy of protection; level.
  • Directional control (dependency inversion by interface); information hiding (no transitive dependency).
