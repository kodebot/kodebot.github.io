Clean Architecture 9: LSP, the Liskov Substitution Principle

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 9. Own-words digest with short attributed quotes. Previous: Clean Architecture 8: OCP, the Open-Closed Principle. Next: Clean Architecture 10: ISP, the Interface Segregation Principle.

Takeaways
  • LSP (Barbara Liskov, 1988): subtypes must be substitutable: programs written against the base type must behave the same when given any subtype.
  • Classic violation: the square/rectangle problem (a Square cannot honour a Rectangle's independent width and height).
  • LSP has grown from guiding inheritance to a principle about interfaces and implementations of any form (interfaces, duck-typed classes, REST services).
  • At the architecture level a violation (taxi dispatch services with non-uniform REST interfaces) forces special-case mechanisms that pollute the system.

9.1 The principle

  • In 1988 Barbara Liskov wrote this as a way of defining subtypes: "If for each object o1 of type S there is an object o2 of type T such that for all programs P defined in terms of T, the behavior of P is unchanged when o1 is substituted for o2 then S is a subtype of T." (Barbara Liskov, "Data Abstraction and Hierarchy", SIGPLAN Notices 23, 5, May 1988.) This is the Liskov Substitution Principle (LSP).

9.2 Guiding the use of inheritance

  • Conforming example
    • (Figure 9.1): a class License has a method calcFee(), called by the Billing application
    • Two "subtypes", PersonalLicense and BusinessLicense, use different fee algorithms
    • It conforms to LSP because Billing's behaviour does not depend in any way on which subtype it uses; both are substitutable for License.

9.3 The square/rectangle problem

  • The canonical violation, "famed (or infamous)" (Figure 9.2)
    • Square is not a proper subtype of Rectangle because a Rectangle's height and width are independently mutable while a Square's must change together
    • A user who believes it has a Rectangle can be confused:
Rectangle r = ...;

r.setW(5);
r.setH(2);
assert(r.area() == 10);
  • If the ... produced a Square, the assertion fails
    • The only defence is to add mechanisms to the user (such as an if) that detect whether the Rectangle is really a Square
    • Since the user's behaviour now depends on the types it uses, those types are not substitutable.

9.4 LSP and architecture

  • In the early years of the object-oriented revolution LSP guided the use of inheritance
    • Over the years it morphed into a broader principle of software design about interfaces and implementations
    • The interface may be a Java-style interface implemented by several classes
    • several Ruby classes sharing method signatures
    • or a set of services answering the same REST interface. LSP applies wherever users depend on well-defined interfaces and on the substitutability of their implementations.
  • The best way to understand it architecturally is to see what happens when it is violated.

9.5 Example LSP violation: the taxi aggregator

  • We build an aggregator for many taxi dispatch services:
    • customers use the website to find the most appropriate taxi regardless of company
    • once they choose, the system dispatches the taxi via a RESTful service
      • The URI of the dispatch service is part of the driver database record
      • For driver Bob it might be purplecab.com/driver/Bob
    • the system appends dispatch information and sends it with a PUT:
purplecab.com/driver/Bob
    /pickupAddress/24 Maple St.
    /pickupTime/153
    /destination/ORD
  • So all companies' dispatch services must conform to the same REST interface, treating pickupAddress, pickupTime and destination identically.
  • Now Acme (the largest taxi company in the area; its CEO's ex-wife is our CEO's new wife) hired programmers who did not read the spec carefully and abbreviated destination to dest
    • The architecture needs a special case: Acme dispatch requests must be built by different rules
    • The simplest way is an if in the module building the command:
if (driver.getDispatchUri().startsWith("acme.com")) ...
  • "No architect worth his or her salt would allow such a construction": putting "acme" in the code creates opportunities for "all kinds of horrible and mysterious errors, not to mention security breaches"
    • If Acme bought Purple Taxi and kept the separate brands and websites but unified the systems, would we add another if for "purple"?
  • The architect must insulate the system by creating a dispatch command creation module driven by a configuration database keyed by the dispatch URI:
URI Dispatch format
Acme.com /pickupAddress/%s/pickupTime/%s/dest/%s
*.* /pickupAddress/%s/pickupTime/%s/destination/%s
  • So the architect has to add "a significant and complex mechanism" because the RESTful services' interfaces are not substitutable.

9.6 Conclusion

  • LSP can, and should, be extended to the level of architecture: a simple violation of substitutability can pollute a system's architecture with a significant amount of extra mechanism.

Summary points

  • Substitutability: users must not need to know which implementation they hold.
  • It applies to class hierarchies, interfaces and service contracts alike.
  • A non-substitutable service forces special cases and configuration machinery into the architecture.
Terms to carry forward
  • LSP; subtype and substitutability.
  • Square/rectangle problem; non-substitutable interface (the Acme dest field).
