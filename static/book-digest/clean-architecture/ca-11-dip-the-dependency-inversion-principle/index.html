Clean Architecture 11: DIP, the Dependency Inversion Principle

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 11. Own-words digest. Previous: Clean Architecture 10: ISP, the Interface Segregation Principle. Next: Clean Architecture 12: Components.

Takeaways
  • DIP: the most flexible systems have source code dependencies that refer only to abstractions, not concretions.
  • It is not absolute: depend freely on stable concretions (platform facilities such as Java's String); avoid depending on volatile concrete modules, the ones you are actively developing.
  • Interfaces are less volatile than implementations. Practices: refer to abstract interfaces, do not derive from or override volatile concrete classes, and never name anything concrete and volatile.
  • Create volatile objects through an Abstract Factory; gather unavoidable concrete dependencies into concrete components such as main. The curved boundary line and the one-way dependencies lead to the Dependency Rule.

11.1 The principle

  • DIP says the most flexible systems are those in which source code dependencies refer only to abstractions, not to concretions.
    • In a statically typed language like Java, use, import and include statements should refer only to source modules containing interfaces, abstract classes or other abstract declarations
      • nothing concrete should be depended on.
    • The same applies to dynamically typed languages like Ruby and Python, but it is harder to define a concrete module: it is any module in which the called functions are implemented.
  • Treating this as an absolute rule is unrealistic:
    • systems must depend on many concrete facilities
    • Java's String is concrete and cannot, and should not, be made abstract
    • But String is very stable: changes are rare and tightly controlled, so nobody worries about "frequent and capricious changes"
    • We tend to ignore the stable background of operating system and platform facilities and tolerate those dependencies because we can rely on them not to change.
  • It is the volatile concrete elements we avoid depending on: the modules we are actively developing and which change frequently.

11.2 Stable abstractions

  • Every change to an abstract interface corresponds to a change to its concrete implementations
    • changes to implementations do not always, or even usually, require changes to the interfaces they implement
    • So interfaces are less volatile than implementations
    • Good designers work hard to reduce the volatility of interfaces: add functionality to implementations without changing interfaces ("Software Design 101").
  • Therefore stable architectures avoid depending on volatile concretions and favour stable abstract interfaces, which boils down to four practices:
    1. Don't refer to volatile concrete classes; refer to abstract interfaces. This applies in every language. It puts severe constraints on object creation and generally enforces Abstract Factories.
    2. Don't derive from volatile concrete classes. In statically typed languages inheritance is the strongest and most rigid source relationship, so use it with great care; in dynamic languages it is less of a problem but still a dependency.
    3. Don't override concrete functions. Concrete functions often require source dependencies; overriding them does not eliminate those dependencies but inherits them. To manage them, make the function abstract and create multiple implementations.
    4. Never mention the name of anything concrete and volatile. (A restatement of the principle.)

11.3 Factories

  • To comply, creating volatile concrete objects needs special handling, because in virtually all languages creating an object requires a source dependency on its concrete definition
    • In most OO languages such as Java the answer is an Abstract Factory.
  • Figure 11.1: the Application uses ConcreteImpl through the Service interface
    • But it must create ConcreteImpl instances; to avoid a source dependency it calls the makeSvc method of the ServiceFactory interface
    • ServiceFactoryImpl, which derives from ServiceFactory, implements it: it instantiates ConcreteImpl and returns it as a Service.
  • The curved line in the figure is an architectural boundary separating the abstract from the concrete: all source dependencies cross it in the same direction, toward the abstract side
    • It divides the system into two components: the abstract component with all the high-level business rules, and the concrete component with all the implementation details those rules manipulate.
  • The flow of control crosses the line in the opposite direction to the source dependencies: they are inverted against the flow of control, "which is why we refer to this principle as Dependency Inversion".

11.4 Concrete components

  • The concrete component in Figure 11.1 contains a single dependency (the factory implementation naming ConcreteImpl), so it violates DIP
    • That is typical: DIP violations cannot be entirely removed, but can be gathered into a small number of concrete components and kept separate from the rest of the system.
  • Most systems have at least one such component, often called main because it contains the main function (the function the OS invokes at startup). In Figure 11.1, main would instantiate ServiceFactoryImpl and put that instance in a global variable of type ServiceFactory
    • the Application then accesses the factory through that global.

11.5 Conclusion

  • DIP will "show up again and again" as the most visible organising principle in the architecture diagrams
    • The curved line of Figure 11.1 becomes the architectural boundaries of later chapters, and the rule that dependencies cross it in one direction, toward more abstract entities, becomes the Dependency Rule.

Summary points

  • Depend on abstractions; tolerate stable concretions; avoid volatile ones.
  • Four practices: no references to, derivation from or overriding of volatile concretions; never name them.
  • Abstract Factory plus a small concrete main component keep dependencies pointing at the abstractions.
Terms to carry forward
  • DIP; abstraction versus concretion; volatile versus stable.
  • Abstract Factory; concrete component (main); architectural boundary.
  • Preview: the Dependency Rule.
