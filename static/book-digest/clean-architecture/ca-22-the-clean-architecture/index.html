Clean Architecture 22: The Clean Architecture

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 22. Own-words digest. Previous: Clean Architecture 21: Screaming Architecture. Next: Clean Architecture 23: Presenters and Humble Objects.

Takeaways
  • Hexagonal (Ports and Adapters), DCI, BCE and the Clean Architecture share one goal: separation of concerns by layers, with at least one layer for business rules and one for interfaces.
  • They yield systems that are independent of frameworks, testable, independent of the UI, database and any external agency.
  • The Dependency Rule: source code dependencies must point only inward, toward higher-level policies. Nothing in an inner circle may know anything about an outer circle: not a name, not a data format.
  • Layers: Entities, Use Cases, Interface Adapters, Frameworks and Drivers. Cross boundaries with dependency inversion and simple data structures.

22.1 A family of architectures

  • Over several decades many ideas about system architecture appeared:
    • Hexagonal Architecture (also Ports and Adapters), developed by Alistair Cockburn and adopted by Steve Freeman and Nat Pryce in Growing Object Oriented Software with Tests.
    • DCI from James Coplien and Trygve Reenskaug.
    • BCE, introduced by Ivar Jacobson in Object Oriented Software Engineering: A Use-Case Driven Approach.
  • They vary in detail but are "very similar": the same objective, separation of concerns, achieved by dividing software into layers, each with at least one layer for business rules and another for user and system interfaces.
  • Each produces systems that are:
    • Independent of frameworks: the architecture does not rely on a library of feature-laden software, so you use frameworks as tools rather than cramming the system into their limited constraints.
    • Testable: business rules can be tested without the UI, database, web server or any other external element.
    • Independent of the UI: the UI can change easily without changing the rest (a web UI replaced by a console UI without touching the business rules).
    • Independent of the database: swap Oracle or SQL Server for Mongo, BigTable, CouchDB or something else; the rules are not bound to it.
    • Independent of any external agency: the business rules "don't know anything at all about the interfaces to the outside world".
  • Figure 22.1 integrates these architectures into a single actionable idea.

22.2 The Dependency Rule

  • The concentric circles of Figure 22.1 represent areas of software: the further in, the higher level; outer circles are mechanisms, inner circles are policies.
  • The overriding rule: "Source code dependencies must point only inward, toward higher-level policies."
  • Nothing in an inner circle can know anything about something in an outer circle. In particular, the name of something declared in an outer circle must not be mentioned by code in an inner circle (functions, classes, variables or any named software entity)
    • Likewise data formats declared in an outer circle should not be used by an inner circle, especially if generated by a framework in an outer circle: "We don't want anything in an outer circle to impact the inner circles."

22.3 The layers

  • Entities:
    • encapsulate enterprise-wide Critical Business Rules
    • An entity can be an object with methods or a set of data structures and functions: it does not matter as long as many applications in the enterprise can use them
    • With no enterprise and just one application, the entities are that application's business objects: the most general, high-level rules, least likely to change when something external changes (page navigation or security should not affect them; "no operational change to any particular application should affect the entity layer").
  • Use cases:
    • application-specific business rules: they encapsulate and implement all the system's use cases, orchestrating the flow of data to and from the entities and directing them to use their critical rules to reach the use case's goals. Changes here should not affect the entities, nor should the layer be affected by the database, UI or common frameworks
    • but changes to how the application operates will affect it (if a use case's details change, some code here changes).
  • Interface adapters:
    • a set of adapters that convert data from the format most convenient for use cases and entities to the format most convenient for an external agency such as the database or the web
      • The whole MVC of a GUI lives here: presenters, views and controllers
    • the models are likely just data structures passed from controllers to use cases and back to presenters and views
      • Data is also converted here to the form suited to the persistence framework
    • no code inward of this circle knows anything about the database:
      • if it is SQL, all SQL is restricted to this layer, specifically the database-related parts
      • Any adapter converting data from an external service form to the internal one also lives here.
  • Frameworks and drivers:
    • the outermost layer: frameworks and tools such as the database and the web framework
    • You write little code here beyond glue to the next circle in
    • "This is where all the details go
    • **The web is a detail
    • The database is a detail.** We keep these things on the outside where they can do little harm."

22.4 Only four circles?

  • The circles are schematic:
    • you may need more
    • no rule requires exactly four
      • But the Dependency Rule always applies: source dependencies always point inward. Moving inward, abstraction and policy increase: the outermost circle is low-level concrete detail
    • the innermost is the most general and highest level.

22.5 Crossing boundaries

  • At the lower right of Figure 22.1: controllers and presenters communicating with use cases
    • The flow of control begins in the controller, moves through the use case and ends in the presenter, while the source dependencies each point inward toward the use cases
    • This apparent contradiction is resolved with the Dependency Inversion Principle: in Java, arrange interfaces and inheritance so source dependencies oppose the flow of control at the right points.
  • Example:
    • a use case must call the presenter, but a direct call would violate the rule (no outer-circle name in an inner circle)
    • So the use case calls an interface in the inner circle (the "use case output port" in the figure) and the presenter in the outer circle implements it
    • The same technique crosses all boundaries, using dynamic polymorphism to make source dependencies oppose control flow so the Dependency Rule holds whichever way control travels.

22.6 Which data crosses the boundaries

  • Typically simple data structures:
    • basic structs, simple data transfer objects, plain function arguments, a hashmap or a constructed object
    • What matters is that isolated, simple data structures cross: "We don't want to cheat and pass Entity objects or database rows", nor structures with any dependency that violates the rule.
  • Example:
    • many database frameworks return a convenient "row structure" for a query
    • do not pass it inward, because that forces an inner circle to know about an outer one. "When we pass data across a boundary, it is always in the form that is most convenient for the inner circle."

22.7 A typical scenario

  • Figure 22.2: a web-based Java system with a database.
    1. The web server gathers input and hands it to the Controller.
    2. The Controller packages it into a plain old Java object and passes it through the InputBoundary to the UseCaseInteractor.
    3. The Interactor interprets the data and controls the dance of the Entities, using the DataAccessInterface to bring the Entities' data into memory from the Database.
    4. When done, the Interactor gathers data from the Entities and builds OutputData (another plain old Java object), passed through the OutputBoundary interface to the Presenter.
    5. The Presenter repackages the OutputData into a ViewModel (yet another plain old Java object) of mostly Strings and flags the View uses: where OutputData holds Date or Currency objects the Presenter loads already formatted Strings; button and menu item names and flags telling whether they are grey also go in the ViewModel.
    6. The View has almost nothing left to do but move the data from the ViewModel into the HTML page.
  • All dependencies cross the boundary lines pointing inward, following the Dependency Rule.

22.8 Conclusion

  • Conforming to these simple rules "is not difficult, and it will save you a lot of headaches"
    • Separating the software into layers and following the Dependency Rule gives a system that is intrinsically testable, and when external parts (the database, the web framework) become obsolete you can replace them with a minimum of fuss.

Summary points

  • Many layered architectures share the same aims; the clean architecture unifies them.
  • Dependencies point only inward; inner circles know nothing of outer names or formats.
  • Cross boundaries with interfaces (dependency inversion) and simple data in the inner circle's preferred form.
Terms to carry forward
  • Dependency Rule; Entities, Use Cases, Interface Adapters, Frameworks and Drivers.
  • Input and output boundary (ports); Presenter, ViewModel; DTO.
  • Hexagonal architecture (Ports and Adapters), DCI, BCE.
