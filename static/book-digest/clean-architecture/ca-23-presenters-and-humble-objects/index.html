Clean Architecture 23: Presenters and Humble Objects

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 23. Own-words digest. Previous: Clean Architecture 22: The Clean Architecture. Next: Clean Architecture 24: Partial Boundaries.

Takeaways
  • The Humble Object pattern splits behaviour into a humble module (hard to test, stripped to its barest essence) and a testable one holding everything else.
  • Presenters and Views are the classic split: the Presenter formats data into a View Model; the View just moves it to the screen.
  • Testability is an attribute of good architecture, and the humble/testable split often defines an architectural boundary: Presenter/View, database gateways, data mappers (so-called ORMs), service listeners.
  • Boundary crossings use simple data structures; using the pattern at boundaries vastly increases testability.

23.1 The Humble Object pattern

  • Presenters (Chapter 22) are a form of the Humble Object pattern, which helps identify and protect architectural boundaries
    • the clean architecture of the last chapter "was full of Humble Object implementations".
  • The pattern (footnote:
    • xUnit Patterns, Meszaros, Addison-Wesley, 2007, p
      1. was originally identified to help unit testers separate hard-to-test behaviours from easy-to-test ones
    • Split the behaviours into two modules or classes:
      • the humble one contains the hard-to-test behaviours stripped down to their barest essence
      • the other contains all the testable behaviours stripped out of the humble object.
  • Example:
    • GUIs are hard to unit test because it is very difficult to write tests that see the screen and check the right elements are displayed
    • But most GUI behaviour is in fact easy to test
    • So split it into a Presenter and a View.

23.2 Presenters and views

  • The View is the humble object, hard to test; its code is kept as simple as possible: it moves data into the GUI but does not process it.
  • The Presenter is the testable object:
    • it accepts data from the application and formats it for presentation so the View can simply move it to the screen. If the application wants a date shown, it hands the Presenter a Date object
    • the Presenter formats it into a string and puts it in a simple data structure, the View Model, where the View finds it.
  • Money:
    • the application might pass a Currency object
    • the Presenter formats it with appropriate decimal places and currency markers into a string in the View Model
    • if a negative value should be red, a simple boolean flag in the View Model is set.
  • Buttons:
    • each has a name that is a string in the View Model, placed by the Presenter
    • if a button should be grey, the Presenter sets a boolean
      • Menu item names, and the names of every radio button, check box and text field, are likewise loaded into strings and booleans
    • tables of numbers become tables of properly formatted strings.
  • "Anything and everything that appears on the screen, and that the application has some kind of control over, is represented in the View Model as a string, a boolean or an enum
    • Nothing is left for the View to do other than to load the data from the View Model into the screen
    • Thus the View is humble."

23.3 Testing and architecture

  • "It has long been known that testability is an attribute of good architectures." The Humble Object pattern is a good example: separating behaviours into testable and non-testable parts often defines an architectural boundary
    • The Presenter/View boundary is one, "but there are many others".

23.4 Database gateways

  • Between the use case interactors and the database sit the database gateways (footnote: Patterns of Enterprise Application Architecture, Martin Fowler et al., Addison-Wesley, 2003, p. 466)
    • They are polymorphic interfaces with a method for every create, read, update or delete operation the application performs on the database
    • Example: to know the last names of all users who logged in yesterday, UserGateway has a method getLastNamesOfUsersWhoLoggedInAfter taking a Date and returning a list of last names.
  • No SQL in the use cases layer:
    • use gateway interfaces, implemented by classes in the database layer
    • That implementation is the humble object: it simply uses SQL (or whatever the database interface is) to fetch what each method needs
    • The interactors are not humble (they encapsulate application-specific business rules) but are testable, since the gateways can be replaced with stubs and test doubles.

23.5 Data mappers

  • In which layer do ORMs like Hibernate belong? First:
    • "There is no such thing as an object relational mapper (ORM)." Objects are not data structures, at least from their users' point of view: the users cannot see the data (it is private) and see only public methods
      • an object is a set of operations
    • A data structure is a set of public data variables with no implied behaviour
    • ORMs are better named "data mappers": they load data into data structures from relational tables.
  • They belong in the database layer, and form another Humble Object boundary between the gateway interfaces and the database.

23.5.1 Service listeners

  • What about services:
    • if your application talks to other services or provides services, does the pattern create a service boundary? "Of course!" The application loads data into simple data structures and passes them across the boundary to modules that format the data and send it to external services
    • On input, service listeners receive data from the service interface and format it into a simple data structure the application can use, which is then passed across the service boundary.

23.6 Conclusion

  • At each architectural boundary the Humble Object pattern is likely "lurking somewhere nearby"
    • Communication across the boundary will almost always use some kind of simple data structure, and the boundary frequently divides something hard to test from something easy to test
    • Using the pattern at architectural boundaries vastly increases the testability of the entire system.

Summary points

  • Strip hard-to-test code to a humble object; put the logic in a testable partner.
  • Presenter plus View Model plus humble View; gateways, data mappers and service listeners follow the same shape.
  • The boundary between humble and testable is often an architectural boundary.
Terms to carry forward
  • Humble Object; Presenter, View, View Model.
  • Database gateway; data mapper (not an "ORM"); service listener.
  • Test double.
