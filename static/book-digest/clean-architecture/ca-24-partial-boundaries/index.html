Clean Architecture 24: Partial Boundaries

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 24. Own-words digest. Previous: Clean Architecture 23: Presenters and Humble Objects. Next: Clean Architecture 25: Layers and Boundaries.

Takeaways
  • Full-fledged boundaries are expensive (reciprocal polymorphic interfaces, input and output data structures, dependency management for independently compilable and deployable components), and costly to maintain.
  • An architect may judge the cost too high yet want to hold a place for a boundary: a partial boundary, which some Agile folk frown on as breaking YAGNI ("You Aren't Going to Need It").
  • Three ways: skip the last step (do the work but keep one component), a one-dimensional boundary (Strategy pattern), and a Facade.
  • All can degrade if the full boundary never arrives; deciding where boundaries might be and how fully to build them is the architect's job.

24.1 Why partial boundaries

  • Full boundaries require reciprocal polymorphic Boundary interfaces, input and output data structures, and all the dependency management to isolate the two sides into independently compilable and deployable components: "a lot of work", and a lot of work to maintain.
  • A good architect may decide the expense is too high but still want to hold a place for such a boundary in case it is needed later
    • This anticipatory design is often frowned upon in the Agile community as a violation of YAGNI
    • Architects sometimes think "Yeah, but I might": then they may implement a partial boundary.

24.2 Skip the last step

  • Do all the work needed to create independently compilable and deployable components, then keep them together in the same component: the reciprocal interfaces and input/output data structures exist, all set up, but everything is compiled and deployed as one component.
  • It needs the same amount of code and preparatory design as a full boundary but not the administration of multiple components: no version number tracking or release management burden: "That difference should not be taken lightly."
  • This was the early strategy behind FitNesse: its web server component was designed to be separable from the wiki and testing part, so other web applications might reuse it, yet users should not need two downloads (the goal "download and go": one jar, no hunting for jars or version compatibility).
  • It also shows the danger:
    • over time, as it became clear no separate web component would be needed, the separation weakened and dependencies started to cross the line in the wrong direction
    • "nowadays, it would be something of a chore to re-separate them."

24.3 One-dimensional boundaries

  • A full boundary uses reciprocal interfaces to isolate in both directions, which is expensive in setup and maintenance
    • A simpler structure that holds the place for later extension (Figure 24.1) is the traditional Strategy pattern: a ServiceBoundary interface used by clients and implemented by ServiceImpl classes.
  • It sets the stage for a future boundary:
    • the dependency inversion needed to isolate the Client from ServiceImpl is in place
    • But the separation degrades rapidly, as the "nasty dotted arrow" shows: without reciprocal interfaces nothing prevents a backchannel except the diligence and discipline of developers and architects.

24.4 Facades

  • Even simpler is the Facade pattern (Figure 24.2): even the dependency inversion is sacrificed
    • The boundary is simply the Facade class, which lists all the services as methods and forwards the calls to classes the client is not supposed to access.
  • But the Client then has a transitive dependency on all those service classes: in static languages a change to one service class's source forces the Client to recompile
    • and backchannels are easy to create.

24.5 Conclusion

  • These are three simple ways to partially implement a boundary
    • there are "of course, many others", offered as examples. Each has its own costs and benefits, is appropriate in some contexts as a placeholder for an eventual full boundary, and can degrade if that boundary never materialises.
  • "It is one of the functions of an architect to decide where an architectural boundary might one day exist, and whether to fully or partially implement that boundary."

Summary points

  • Full boundaries cost a lot; partial ones are cheaper placeholders.
  • Skip the last step, Strategy (one-way) and Facade trade protection for effort.
  • Partial boundaries erode without discipline; choose them deliberately.
Terms to carry forward
  • Partial boundary; YAGNI; anticipatory design.
  • Skip the last step; Strategy pattern; Facade pattern; backchannel.
