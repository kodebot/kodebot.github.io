Clean Architecture 26: The Main Component

Source: Robert C. Martin, Clean Architecture: A Craftsman's Guide to Software Structure and Design (Pearson, 2017), chapter 26. Own-words digest with short excerpts. Previous: Clean Architecture 25: Layers and Boundaries. Next: Clean Architecture 27: Services, Great and Small.

Takeaways
  • Every system has at least one component that creates, coordinates and oversees the others: Main.
  • Main is the ultimate detail: the lowest-level policy and initial entry point, depended on by nothing but the operating system. It builds the factories, strategies and global facilities, injects dependencies, then hands control to the high-level policy.
  • Think of Main as a plugin: you can have many Mains, one per configuration (Dev, Test, Production; per country, jurisdiction or customer).

26.1 The ultimate detail

  • "In every system, there is at least one component that creates, coordinates, and oversees the others. I call this component Main."
  • Main is **the ultimate detail:
    • the lowest-level policy**
    • It is the initial entry point of the system; nothing, other than the operating system, depends on it
    • Its job is to create all the Factories, Strategies and other global facilities, and then hand control over to the high-level abstract portions.
  • This is where dependencies should be injected by a Dependency Injection framework
    • once injected into Main, Main distributes them normally, without using the framework. "Think of Main as the dirtiest of all the dirty components."

26.2 The Hunt the Wumpus Main

  • Martin shows the Main of a recent Hunt the Wumpus (shortened here).
    • It loads up all the strings the main body of the code should not know about: arrays of cave environments ("bright", "humid", "creepy", "foggy", "dreadful" ...)
      • shapes ("round", "square", "craggy" ...)
      • cavern types ("cavern", "room", "catacomb", "tunnel" ...) and adornments ("smelling of sulfur", "with bones scattered around", "that fills you with dread" ...).
    • main uses an HtwFactory to create the game and passes the class name htw.game.HuntTheWumpusFacade, "because that class is even dirtier than Main", so that changes in that class do not make Main recompile or redeploy:
public static void main(String[] args) throws IOException {
    game = HtwFactory.makeGame("htw.game.HuntTheWumpusFacade",
        new Main());
    createMap();
    BufferedReader br =
        new BufferedReader(new InputStreamReader(System.in));
    game.makeRestCommand().execute();
    while (true) {
        System.out.println(game.getPlayerCavern());
        System.out.println("Health: " + hitPoints + " arrows: " +
            game.getQuiver());
        HuntTheWumpus.Command c = game.makeRestCommand();
        System.out.println(">");
        String command = br.readLine();
        if (command.equalsIgnoreCase("e"))
            c = game.makeMoveCommand(EAST);
        // ... west, north, south, rest, and shoot commands (sw, se, sn, ss) elided ...
        else if (command.equalsIgnoreCase("q"))
            return;

        c.execute();
    }
}
  • main also creates the input stream and holds the main loop, interpreting simple input commands (e, w, n, s to move, r to rest, sw, se, sn, ss to shoot, q to quit) and deferring all processing to higher-level components.
  • Finally main creates the map:
    • a random number of caverns (10 to 39), each given a generated name, connected north, south, east or west by chance
    • the player's cavern, the Wumpus, three bat caverns and three pit caverns are placed in random distinct caverns
    • the quiver is set to 5 arrows.
  • "The point is that Main is a dirty low-level module in the outermost circle of the clean architecture
    • It loads everything up for the high level system, and then hands control over to it."

26.3 Conclusion: Main as a plugin

  • "Think of Main as a plugin to the application": it sets up the initial conditions and configurations, gathers all the outside resources, and hands control to the application's high-level policy. As a plugin
    • there can be many Main components: one for Dev, another for Test, another for Production; one per country
    • jurisdiction or customer.
  • "When you think about Main as a plugin component, sitting behind an architectural boundary, the problem of configuration becomes a lot easier to solve."

Summary points

  • Main is the dirtiest, lowest-level component: entry point, factories, dependency injection, configuration.
  • Everything else depends inward; nothing depends on Main.
  • Multiple Mains give you per-environment or per-customer configuration.
Terms to carry forward
  • Main (the ultimate detail); Dependency Injection in Main only.
  • Main as a plugin; many Mains (Dev, Test, Production).
