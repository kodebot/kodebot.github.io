Core Java 4: Objects and Classes

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 4. Previous: Core Java 3: Fundamental Programming Structures in Java. Next: Core Java 5: Inheritance.

Takeaways
  • OOP puts data first: a program is a set of objects, each exposing behaviour and hiding implementation (encapsulation). Procedural code puts algorithms first.
  • A class is a cookie cutter and objects are the cookies. Objects have behaviour (methods), state (instance fields) and identity.
  • An object variable holds a reference, not the object; two variables can refer to the same object, and any variable can be null.
  • Make instance fields private, expose methods. Never return a reference to a mutable field; prefer immutable types such as LocalDate.
  • Classes relate by dependence (uses-a), aggregation (has-a) and inheritance (is-a); minimise coupling.
  • static fields and methods belong to the class, not to objects.

4.1 Introduction to object-oriented programming

  • OOP
    • is the dominant paradigm, replacing the "structured" or procedural style of the 1970s
    • An OO program is made of objects, each with a specific functionality exposed to users and a hidden implementation
    • Many come "off the shelf" from a library; as long as one meets your specification you do not care how it works.
  • Procedural programming
    • designs procedures (algorithms) first and then the data structures to suit them
    • Niklaus Wirth, designer of Pascal, titled his 1976 book Algorithms + Data Structures = Programs, with algorithms first
    • OOP reverses the order: data first, then the algorithms.
  • Objects suit larger problems. A simple web browser might need 2,000 procedures all touching a set of global data
    • in OO style it might be 100 classes with about 20 methods each (Figure 4.1).
    • It is easier to grasp and to debug: if one object's data is in a bad state, search the 20 methods that could touch it, not 2,000 procedures.

4.1.1 Classes

  • A class specifies how objects are made: classes are cookie cutters, objects are the cookies. Constructing an object makes an instance of the class.
  • The standard library has thousands of classes (user interfaces, dates, networking), but you still write your own for your problem domain.
  • Encapsulation (also called information hiding) means combining data and behaviour in one package and hiding implementation details from users.
    • The data bits are the instance fields; the procedures are the methods.
    • The values of an object's instance fields are its current state; a method call may change the state.
  • The key to encapsulation:
    • methods never directly access instance fields of another class
    • programs interact with object data only through methods. That gives the "black box" behaviour behind reuse and reliability.
    • A class may completely change how it stores data; if the methods stay the same, no other object knows or cares.
  • Classes can be built by extending other classes (inheritance, chapter 5)
    • Java has a "cosmic superclass" Object that all classes extend
    • An extending class gets all the properties and methods of the parent and adds new ones.

4.1.2 Objects

Three key characteristics:

Characteristic Question it answers
Behaviour What can you do with this object, i.e. which methods can you call?
State How does the object react when you call those methods?
Identity How is it distinguished from other objects with the same behaviour and state?
  • All instances of a class share behaviour (the methods you can call).
  • State may change over time but not spontaneously: a state change must result from method calls. If an object changes without a method call on it, someone broke encapsulation.
  • State alone does not describe an object because each has a distinct identity: two orders are different even if they request identical items
    • Instances always differ in identity and usually in state.
  • The three influence each other: an order that is "shipped" or "paid" may reject adding or removing items; an "empty" order must not allow itself to be shipped.

4.1.3 Identifying classes

  • Procedural design starts at the top with main. OO design has no top: identify your classes, then add methods to each.
  • Rule of thumb: nouns in the problem analysis become classes, verbs become methods.
    • Order-processing nouns: Item, Order, Shipping address, Payment, Account.
    • Verbs: items are added to orders; orders are shipped or cancelled; payments are applied to orders.
  • For each verb, decide which object has major responsibility
    • When an item is added to an order, the Order is in charge because it knows how it stores and sorts items, so add is a method of Order taking an Item parameter.
  • The noun-and-verb rule is only a heuristic; experience tells you which nouns and verbs matter.

4.1.4 Relationships between classes

Relationship Meaning Example
Dependence ("uses-a") A class depends on another if its methods use or manipulate objects of that class Order uses Account to check credit status; Item does not depend on Account
Aggregation ("has-a") Objects of A contain objects of B An Order contains Item objects
Inheritance ("is-a") A more specialised class extends a more general one RushOrder extends Order with priority handling and a different shipping charge method; adding items and billing are inherited
  • Minimise dependencies. If class A does not know B exists, it is unaffected by changes to B, so changes to B cannot introduce bugs in A. This is minimising coupling.
  • Some methodologists prefer the more general "association", but for programmers "has-a" is concrete, and the standard notation for associations is less clear.
  • Many programmers draw UML (Unified Modeling Language) class diagrams: classes as rectangles, relationships as arrows with adornments (Table 4.1 gives the connector styles the book uses for inheritance, interface implementation, dependency and aggregation).

4.2 Using predefined classes

  • The Math class only encapsulates functionality; it has no data, so there are no objects to make. A more typical class is Date.

4.2.1 Objects and object variables

  • You construct objects and give them an initial state, then apply methods. A constructor is a special method that constructs and initialises objects
    • it has the same name as the class and is used with the new operator:
new Date()                       // current date and time
IO.println(new Date());          // pass it on
String s = new Date().toString();
Date rightNow = new Date();      // keep it in a variable
  • Why a class for dates and not a built-in type as in Visual Basic (#12/31/1999#)? Locales differ (month/day/year versus day/month/year)
    • With a class, design is offloaded to a library designer and other programmers can replace or enhance it
    • (Proof: the Java date library started muddled and was redesigned twice.)
  • Object variable versus object:
Date startTime;          // startTime doesn't refer to any object
s = startTime.toString(); // compile-time error: not yet initialised
startTime = new Date();  // refer to a new object
startTime = rightNow;    // or to an existing object: both refer to the same one

  • An object variable does not contain an object; it refers to one.
    • The value of new is itself a reference
    • Date startTime = new Date(); has two parts: new Date() makes the object and yields a reference, then the reference is stored in the variable.
  • Set a variable to null to say it refers to no object, and test before using: if (startTime != null) IO.println(startTime); (more in 4.3.5).
  • C++ comparison: a Java object variable is like a C++ pointer (Date* rightNow), not a C++ reference (Date&): C++ references cannot be null or reassigned.
    • The usual pointer dangers vanish: using an uninitialised variable gives a reliable runtime error, and the garbage collector handles memory.

4.2.2 The LocalDate class

  • Date represents a point in time as milliseconds from the epoch, 00:00:00 UTC, 1 January 1970 (UTC is for practical purposes GMT)
    • It is poor for human calendar information such as "December 31, 1999", a Gregorian calendar notion (Chinese or Hebrew lunar calendars describe the same moment differently, as would "your customers from Mars").
    • Recommended reading from the book: Calendrical Calculations by Nachum Dershowitz and Edward M. Reingold (Cambridge University Press, 4th ed., 2018).
  • The designers separated keeping time from naming points in time: Date for a point in time, LocalDate for familiar calendar dates
    • Using different classes for different concepts is good OO design. A far more robust date and time library exists (Volume II, chapter 6).
  • LocalDate objects are built with static factory methods, not constructors:
LocalDate today = LocalDate.now();
LocalDate newYearsEve = LocalDate.of(1999, 12, 31);

int year = newYearsEve.getYear();          // 1999
int month = newYearsEve.getMonthValue();   // 12
int day = newYearsEve.getDayOfMonth();     // 31

LocalDate aThousandDaysLater = newYearsEve.plusDays(1000);
year = aThousandDaysLater.getYear();       // 2002
month = aThousandDaysLater.getMonthValue(); // 9
day = aThousandDaysLater.getDayOfMonth();  // 26
  • The getters seem pointless for a date you just built, but they matter for computed dates.
  • LocalDate encapsulates its fields; you cannot know its internal representation, and need not.
  • Date.getDay, getMonth and getYear exist but are deprecated: a method is deprecated when the designer realises it should never have been introduced
    • They were tagged when calendar classes arrived in Java 1.1
    • Avoid them (compiler warnings, possible removal).
  • The JDK's jdeprscan tool checks code for deprecated API use (https://docs.oracle.com/en/java/javase/25/docs/specs/man/jdeprscan.html).

4.2.3 Mutator and accessor methods

  • newYearsEve.plusDays(1000) yields a new LocalDate; the original is unchanged. plusDays does not mutate its object (like String.toUpperCase).
  • The older GregorianCalendar class, in contrast, has a mutator:
GregorianCalendar someDay = new GregorianCalendar(1999, 11, 31); // months run 0 to 11
someDay.add(Calendar.DAY_OF_MONTH, 1000);
year = someDay.get(Calendar.YEAR);          // 2002
month = someDay.get(Calendar.MONTH) + 1;    // 9
day = someDay.get(Calendar.DAY_OF_MONTH);   // 26
  • After add, someDay is no longer new year's eve, hence the name. Methods that only read state are accessor methods (LocalDate.getYear, GregorianCalendar.get).
  • C++ marks accessors with a const suffix; Java has no special syntax to tell accessors from mutators.

Listing 4.1, CalendarDemo.java, prints this month's calendar with today marked *. The steps:

  1. LocalDate date = LocalDate.now();, capture month and today (day of month).
  2. Set date to the first of the month with date.minusDays(today - 1), get date.getDayOfWeek() (a DayOfWeek object) and its getValue(): 1 is Monday, 7 is Sunday, so the weekend is at the end.
  3. Print the header Mon Tue Wed Thu Fri Sat Sun and indent the first line with for (int i = 1; i < value; i++).
  4. Loop while (date.getMonthValue() == month): print "%3d".formatted(date.getDayOfMonth()), add * if it is today, else a space, advance with date.plusDays(1), and print a newline when the next day is Monday.
  5. We stop when the month changes, so we need not know whether a month has 31, 30, 29 or 28 days.
// CalendarDemo.java
void main()
{
    LocalDate date = LocalDate.now();
    int month = date.getMonthValue();
    int today = date.getDayOfMonth();

    date = date.minusDays(today - 1); // set to start of month
    DayOfWeek weekday = date.getDayOfWeek();
    int value = weekday.getValue(); // 1 = Monday, ..., 7 = Sunday

    IO.println("Mon Tue Wed Thu Fri Sat Sun");
    for (int i = 1; i < value; i++)
    {
        IO.print("    ");
    }
    while (date.getMonthValue() == month)
    {
        IO.print("%3d".formatted(date.getDayOfMonth()));
        if (date.getDayOfMonth() == today)
        {
            IO.print("*");
        } else {
            IO.print(" ");
        }
        date = date.plusDays(1);
        if (date.getDayOfWeek().getValue() == 1)
        {
            IO.println();
        }
    }
    if (date.getDayOfWeek().getValue() != 1)
    {
        IO.println();
    }
}
  • (The book's printed listing indents with a single space per day; four spaces align the columns with the header.)
  • The point: you use a class through its interface (plusDays, getDayOfWeek) and handle weekday and month-length complexity without knowing the implementation.

java.time.LocalDate (8): static now(), static of(int year, int month, int day), getYear(), getMonthValue(), getDayOfMonth(), getDayOfWeek() (returns DayOfWeek; call getValue() for 1 to 7), plusDays(int n), minusDays(int n).

4.3 Defining your own classes

  • "Workhorse classes" typically have no main; they have instance fields and methods. A complete program combines several source files, one having main.

4.3.1 An Employee class

class ClassName
{
    // field1, field2, ...
    // constructor1, constructor2, ...
    // method1, method2, ...
}

// Employee.java (simplified payroll class)
class Employee
{
    // instance fields
    private String name;
    private double salary;
    private LocalDate hireDay;

    // constructor
    Employee(String n, double s, int year, int month, int day)
    {
        name = n;
        salary = s;
        hireDay = LocalDate.of(year, month, day);
    }

    // a method
    String getName()
    {
        return name;
    }

    // more methods ...
}

Listing 4.2, EmployeeDemo.java: fills an Employee[] of three objects (Carl Cracker 75000, hired 1987-12-15; Harry Hacker 50000, 1989-10-01; Tony Tester 40000, 1990-03-15), raises each salary by 5% with raiseSalary, then prints name, salary and hire day via getName, getSalary, getHireDay.

// Employee.java (full class used by the demo)
class Employee
{
    private String name;
    private double salary;
    private LocalDate hireDay;

    Employee(String n, double s, int year, int month, int day)
    {
        name = n;
        salary = s;
        hireDay = LocalDate.of(year, month, day);
    }

    String getName()
    {
        return name;
    }

    double getSalary()
    {
        return salary;
    }

    LocalDate getHireDay()
    {
        return hireDay;
    }

    void raiseSalary(double byPercent)
    {
        double raise = salary * byPercent / 100;
        salary += raise;
    }
}

// EmployeeDemo.java
void main()
{
    // fill the staff array with three Employee objects
    Employee[] staff = new Employee[3];

    staff[0] = new Employee("Carl Cracker", 75000, 1987, 12, 15);
    staff[1] = new Employee("Harry Hacker", 50000, 1989, 10, 1);
    staff[2] = new Employee("Tony Tester", 40000, 1990, 3, 15);

    // raise everyone's salary by 5%
    for (Employee e : staff)
    {
        e.raiseSalary(5);
    }

    // print out information about all Employee objects
    for (Employee e : staff)
    {
        IO.println("name=" + e.getName() + ",salary=" + e.getSalary()
            + ",hireDay=" + e.getHireDay());
    }
}

4.3.2 Dissecting the Employee class

  • One constructor and four methods: Employee(String, double, int, int, int), getName(), getSalary(), getHireDay(), raiseSalary(double byPercent).
  • It models a business entity with state (name, salary) that can change on a raise, and could be specialised into managers and executives.
  • The author admits it is not perfect, and lists open design questions:
    • Should the name be a string or a Name class (first, last, middle initial)?
    • Is double right for a salary?
    • Why pass year, month and day instead of a LocalDate?
    • Would immutable state be better?
    • Are separate manager and executive classes a good idea (next chapter)?
  • It is kept because it is a familiar context for exploring features. Access levels (public classes and methods) are discussed later; default access is enough for now.
  • private fields:
    • only methods of Employee can read or write them
    • You could omit private, but that is "a very bad idea": other code will exploit the access "when you least expect it", destroying encapsulation
    • Make all instance fields private.
  • Fields can themselves be objects: name and hireDay are references to String and LocalDate.

4.3.3 First steps with constructors

  • A constructor runs when you construct an object and gives the fields their initial state: new Employee("James Bond", 100000, 1950, 1, 1) sets name, salary and hireDay (1 January 1950).
  • A constructor can only be called with new. You cannot reset an existing object: james.Employee("James Bond", 250000, 1950, 1, 1) is a compile error.
  • Constructor rules:
    • same name as the class
    • a class can have more than one constructor
    • zero, one or more parameters
    • no return value
    • always called with new
  • Python needs no new (but all Python objects live on the heap); C++ can build on the stack (Employee number007(...)) or heap (new Employee(...)).
  • Classic bug: shadowing a field with a local variable.
Employee(String n, double s, int year, int month, int day)
{
    String name = n;   // ERROR: declares a local variable, the field is untouched
    double salary = s; // ERROR
    // ...
}
  • The locals name and salary shadow the fields and live only inside the constructor
    • It comes from typing faster than thinking, out of habit of writing the type
    • Never name a local the same as an instance field.

4.3.4 Declaring local variables with var

  • var harry = new Employee("Harry Hacker", 50000, 1989, 10, 1); avoids repeating the type.
  • The book uses var when the type is obvious from the right-hand side without knowledge of the API, and never with numeric types (so you need not tell 0, 0L and 0.0 apart).
  • var is only for local variables inside methods; parameters and fields must have declared types.
  • A style guide for var: https://openjdk.org/projects/amber/guides/lvti-style-guide.

4.3.5 Working with null references

  • An object variable holds a reference or null. Null is convenient for an unknown name or hire date, but applying a method to null throws NullPointerException:
LocalDate rightNow = null;
String s = rightNow.toString(); // NullPointerException
  • An uncaught exception terminates the program
    • Normally you do not catch these; you rely on programmers not causing them
    • The stack trace shows the line, and since Java 14 the message names which variable or method returned null (for e.getHireDay().toString(), whether e was null or getHireDay returned null).
  • Be explicit about which fields may be null
    • In Employee, name and hireDay should not be (salary is primitive, never null)
    • hireDay is non-null because it is built with LocalDate.of, but name is null if the constructor gets a null n.
  • Two remedies:
// "permissive": turn null into a sensible value
name = Objects.requireNonNullElse(n, "unknown");

// "tough love": reject it
name = Objects.requireNonNull(n, "The name cannot be null");
  • Tough love throws NullPointerException at the faulty call, with two benefits: the report describes the problem and pinpoints the location
    • otherwise the exception would appear elsewhere with no easy trace to the bad argument.
  • Whenever a parameter is an object reference, ask whether you intend to model "present or absent". If not, prefer throwing an exception.

4.3.6 Implicit and explicit parameters

void raiseSalary(double byPercent)
{
    double raise = salary * byPercent / 100;
    salary += raise;
}
  • number007.raiseSalary(5) runs double raise = number007.salary * 5 / 100; number007.salary += raise;.
  • The call has two arguments:
    • the implicit argument (the Employee before the method name) and the explicit argument (the 5)
    • The declaration lists a parameter only for the explicit one.
  • Every method has an implicit parameter named this, set to the implicit argument
    • this.salary is the same as salary and some programmers write it to distinguish fields from locals.
  • "Implicit/explicit" is the author's useful terminology, not official; the Java Language Specification says "the object for which the method was invoked".
  • Early OOP described objects as sending messages; the object receiving is the receiver. In Java, sending a message is invoking a method.

4.3.7 Benefits of encapsulation

  • getName, getSalary, getHireDay are field accessors. Why not make the fields public?
    • Control and safety: salary only changes in raiseSalary, so if it is wrong, that is the only method to debug. With a public field the culprit could be anywhere.
  • To get and set a field, provide a private field, an accessor and a mutator. More tedious, but:
    1. You can change the internal representation without touching other code. If the name is stored as firstName and lastName, getName returns firstName + " " + lastName and the rest of the program never notices.
    2. Mutators can validate, for example setSalary can reject a negative salary; direct assignment does not.
  • Danger: accessors that return references to mutable objects. The earlier edition returned a Date from getHireDay:
class Employee
{
    private Date hireDay;
    // ...
    Date getHireDay()
    {
        return hireDay; // BAD
    }
}
  • Date has a mutator setTime, so rogue code can change the employee's private state:
Employee harry = null; // assume an existing employee
Date d = harry.getHireDay();
double tenYearsInMilliseconds = 10 * 365.25 * 24 * 60 * 60 * 1000;
d.setTime(d.getTime() - (long) tenYearsInMilliseconds);
// Harry has just been given ten years of added seniority

  • Both d and harry.hireDay refer to the same object, so mutating d changes the private state. Chapter 6 shows the fix of cloning before returning
    • a better fix is immutable objects such as LocalDate instead of Date.

4.3.8 Class-based access privileges

  • A method can access the private data of all objects of its class, not only the object it was called on:
class Employee
{
    // ...
    public boolean equals(Employee other)
    {
        return id == other.id;
    }
}
  • harry.equals(boss) reads the private id of both; legal because boss is also an Employee.

4.3.9 Private methods

  • Public data is dangerous, but methods are different: helper methods that are too tied to the implementation, or need a special calling order, should be private.
  • A private method can be dropped or changed when the data representation changes, because the class designers know nothing else uses it; a non-private method cannot simply be dropped.

4.3.10 Final instance fields

  • A final instance field must be set by the end of every constructor and can never change afterwards: private final String name; (no setName exists).
  • Most useful for primitive or immutable types (a class is immutable if none of its methods mutate its objects; String is immutable).
  • For mutable classes final can mislead: private final StringBuilder evaluations; (set in the constructor with new StringBuilder()) only means the reference never changes, while the object can be mutated:
void giveGoldStar()
{
    evaluations.append(LocalDate.now() + ": Gold star!\n");
}
  • A final field can be null: name = n != null && n.length() == 0 ? null : n;, but then it can never become non-null.

4.4 Static fields and methods

  • Some data live outside objects, and some methods are not invoked on objects.

4.4.1 Static fields

  • A static field has one copy for the whole class; it is not part of any object. It exists even with no objects.
  • Example: unique employee IDs. Each object has its own id; one shared nextId:
class Employee
{
    private static int nextId = 1;

    private int id;
    // ...
}
  • With 1,000 Employee objects there are 1,000 id fields but one nextId. In the constructor:
id = nextId;
nextId++;
  • For harry that is harry.id = Employee.nextId; Employee.nextId++;.
  • Pitfall: if you declare something static that should be an instance field, the compiler will not warn you.

  • Conceptually a static field belongs to the class, but you may write Employee.nextId, e.nextId (for any Employee e), and inside the class nextId, this.nextId or Employee.nextId.

  • Pay attention to every static declaration: static variables are uncommon and deserve close scrutiny. Static constants are different and stand out by their ALL_CAPS names.

4.4.2 Static constants

  • Static variables are rare, static constants are common. Math declares one:
public class Math
{
    // ...
    public static final double PI = 3.14159265358979323846;
    // ...
}
  • Use it as Math.PI. Without static, PI would be an instance field: you would need a Math object, and each would have its own copy.
  • System.out is another static constant (public static final PrintStream out). Fields should be private, but public constants (final fields) are fine
    • because out is final, System.out = new PrintStream(...) is an error.
    • Yet System.setOut can change it, because setOut is a native method and native methods can bypass Java's access control: a very unusual workaround not to imitate.
  • For thirty years System.out.println was the way to print, but it is hard to explain to beginners: why a public field, why not uppercase OUT, why native methods to change it? So Java 25 introduced IO.println.

4.4.3 Static methods

  • A static method does not operate on objects: Math.pow(x, a) has no implicit parameter. Think of them as methods without a this parameter.
  • A static method of Employee cannot access the instance field id, but it can access static fields:
static int advanceId()
{
    int r = nextId; // obtain next available id
    nextId++;
    return r;
}

int n = Employee.advanceId();
  • Without static you would need an Employee reference to call it.
  • You may call a static method through an object (harry.advanceId()), but that is confusing because the method never looks at harry
    • Use the class name. IDEs suggest a refactoring otherwise.
  • Use static methods when:
    1. the method needs no object state because all it needs comes as explicit parameters (Math.pow)
    2. the method only needs static fields (Employee.advanceId)
  • Other languages call these class fields and class methods.
  • The odd name has a history:
    • in C, static first marked local variables that survive block exit (the variable "stays"), then global functions and variables hidden from other files (reused to avoid a new keyword)
    • C++ reused it a third, unrelated time for members belonging to a class rather than an object, which is the Java meaning.

4.4.4 Factory methods

  • A common use of static methods is factory methods that construct objects, such as LocalDate.now, LocalDate.of, and for NumberFormat:
NumberFormat currencyFormatter = NumberFormat.getCurrencyInstance();
NumberFormat percentFormatter = NumberFormat.getPercentInstance();
double x = 0.1;
IO.println(currencyFormatter.format(x)); // $0.10
IO.println(percentFormatter.format(x));  // 10%

Three reasons to prefer a factory method to a constructor:

  1. Constructors cannot be named: the name is always the class name, but you want two different names for the currency and percent instances.
  2. A constructor cannot vary the type of the object. The factory methods actually return DecimalFormat, a more specialised subclass of NumberFormat (chapter 5).
  3. A constructor always builds a new object; a factory can share instances. For example Set.of() returns the same empty set each time.

4.4.5 The main method

  • Static methods can be called with no objects, so main was traditionally static: when a program starts there are no objects yet, and main constructs what is needed.
class Application
{
    public static void main(String[] args)
    {
        // construct objects here
    }
}
  • As of Java 25, main need not be public or static, or take String[] args. The launcher's rules:
    1. If several main methods exist, static main is preferred over instance methods.
    2. Methods with a String[] parameter are preferred over those with none.
    3. Private main methods are not considered.
    4. If main is not static, the class needs a non-private no-argument constructor; the launcher builds an instance and calls main on it.
  • Also as of Java 25, main need not be declared inside a class
    • A source file with methods outside any class is a compact compilation unit, which implicitly declares a class named after the file (usually the file name without extension, so Application.java gives Application; technically host-dependent)
    • Top-level variables and methods become instance fields and methods of that class.
void main()
{
    // top level method
}

int counter = 0; // instance field

void work()
{
    counter++;
}
  • You cannot declare a constructor in an implicit class (its name is not reliable), and it makes no sense to implicitly declare classes you want to use from other classes, since you need a reliable name
    • The practical use is a class with a main launched as a source file.
  • In the previous section's EmployeeDemo.java the Employee class sat in the same compact unit and is technically an inner class of the implicit EmployeeDemo class (chapter 6)
    • This lets the book show different Employee variants.
  • Every class can have a main method,
    • handy for demo code
    • if the class is part of another program its main does not run. For Employee without a no-argument constructor, main must be static:
class Employee
{
    // ...
    static void main() // runs demo
    {
        var e = new Employee("Harry", 50000);
        IO.println(e.getName() + " " + e.getSalary());
    }
}
  • Run it with java Employee.java.

Listing 4.3, StaticDemo.java: creates Employee("Tom", 40000), ("Dick", 60000), ("Harry", 65000), prints name, id and salary for each, then calls Employee.advanceId() and prints Next issued id= plus the result.

// Employee.java (Listing 4.4)

{
    private static int nextId = 1;

    private String name;
    private double salary;
    private int id;

    Employee(String n, double s)
    {
        name = n;
        salary = s;
        id = advanceId();
    }

    String getName()
    {
        return name;
    }

    double getSalary()
    {
        return salary;
    }

    int getId()
    {
        return id;
    }

    void raiseSalary(double byPercent)
    {
        double raise = salary * byPercent / 100;
        salary += raise;
    }

    static int advanceId()
    {
        int r = nextId; // obtain next available id
        nextId++;
        return r;
    }

    static void main() // runs demo
    {
        var e = new Employee("Harry", 50000);
        IO.println(e.getName() + " " + e.getSalary());
    }
}

java.util.Objects (7): requireNonNull(obj), requireNonNull(obj, message), requireNonNull(obj, Supplier<String>) (8) throw NullPointerException (chapter 6 covers suppliers, chapter 8 the <T> syntax); requireNonNullElse(obj, defaultObj) (9) and requireNonNullElseGet(obj, Supplier) (9) return obj, or the default if obj is null.

4.5 Method parameters

  • Call by value:
    • the method gets just the value the caller provides
    • Call by reference: the method gets the location of the caller's variable, so it can modify that variable
    • (Call by name is mostly of historical interest, from Algol.)
  • Java always uses call by value: a method gets a copy of every argument and cannot modify the caller's variables.
double percent = 10;
harry.raiseSalary(percent); // percent is still 10 afterwards
  • A method that tries to triple a number parameter fails:
void tripleValue(double x) // doesn't work
{
    x = 3 * x;
}
  • x starts as a copy of percent (10), becomes 30, then is discarded; percent stays 10.
  • Two kinds of parameter: primitive types and object references. A method cannot change a primitive parameter, but object parameters work differently:
void tripleSalary(Employee x) // works
{
    x.raiseSalary(200);
}

harry = new Employee(/* ... */);
tripleSalary(harry);
  • x is initialised with a copy of the reference held in harry
    • raiseSalary runs on the object both refer to, so its salary rises by 200 percent
    • x is then discarded while harry still refers to the changed object.
  • Java does not use call by reference for objects, despite claims by some programmers (and "even some book authors"). Counter-example, a swap that does not work:
void swap(Employee x, Employee y) // doesn't work
{
    Employee temp = x;
    x = y;
    y = temp;
}

var a = new Employee("Alice", 70000);
var b = new Employee("Bob", 60000);
swap(a, b);
// a still refers to Alice, b still to Bob

  • x and y are copies of the references; swapping the copies has no lasting effect.
  • Object references are passed by value. Summary of what a method can do:
    1. It cannot modify a parameter of a primitive type.
    2. It can change the state of an object parameter.
    3. It cannot make an object parameter refer to a new object.
  • Listing 4.5 (ParamDemo.java) demonstrates all three, with outputs:
    • tripleValue: Before percent=10.0, end of method x=30.0, After percent=10.0.
    • tripleSalary: Before salary=50000.0, end of method salary=150000.0, After salary=150000.0.
    • swap: Before a=Alice, b=Bob; end of method x=Bob, y=Alice; After a=Alice, b=Bob.
  • Other languages: C++ tags reference parameters with & (void tripleValue(double& x)); C# uses ref (bidirectional), in or out.

4.6 Object construction

4.6.1 Overloading

  • Overloading: several methods with the same name but different parameters, for example new StringBuilder() and new StringBuilder("To do:\n").
  • The compiler picks by matching parameter types with argument types (overloading resolution). It is a compile error if nothing matches, or if no match is better than all others.
  • Any method can be overloaded, not only constructors
    • A method is fully described by its signature: name plus parameter types
    • String has six public indexOf methods: indexOf(int), indexOf(int, int), indexOf(int, int, int), indexOf(String), indexOf(String, int), indexOf(String, int, int).
  • The return type is not part of the signature: two methods with the same name and parameter types but different return types are not allowed.
  • Trap:
    • new StringBuilder('\n') does not make a builder holding a newline
    • The int constructor sets a preallocated capacity, and the char converts to an int (not to a String), so you get an empty builder with capacity 10
    • Be careful with overloading when argument types do not match exactly.

4.6.2 Default field initialisation

  • A field not set in a constructor gets a default: numbers 0, boolean false, object references null.
  • Relying on defaults is considered poor practice (initialisation hidden from readers).
  • Fields get defaults; local variables do not: locals must always be set explicitly.
  • For Employee, unset name and hireDay would be null, and harry.getHireDay().getYear() would throw if the hire day were null.

4.6.3 The constructor with no arguments

Employee()
{
    name = "";
    salary = 0;
    hireDay = LocalDate.now();
}
  • If a class has no constructors at all, you get a free no-argument constructor that sets fields to defaults (0, false, null).
  • If a class has at least one constructor but no no-argument one, new Employee() is illegal. To allow it, write one, which can be empty: ClassName() { }.
  • No destructors in Java
    • (C++ has them for cleanup)
    • Garbage collection reclaims memory
    • For other resources (files, handles), the old Object.finalize is deprecated for removal because you cannot know when it runs
    • Instead supply a close method to call when done; chapter 7 shows how to call it automatically.

4.6.4 Explicit field initialisation

  • Make sure every field gets something meaningful whichever constructor runs. You can assign in the declaration, before the constructor body executes:
class Employee
{
    private String name = "";
    // ...
}
  • Useful when all constructors need the same value. The initial value need not be a constant; it can be a method call:
class Employee
{
    private static int nextId;
    private int id = advanceId();
    // ...
    private static int advanceId()
    {
        int r = nextId;
        nextId++;
        return r;
    }
}

4.6.5 Parameter names

  • Single-letter names (n, s) force readers to read the code to learn what they mean. Better options:
    • an a prefix: Employee(String aName, double aSalary)
    • same name as the field, using this. for the field, since parameters shadow fields:
Employee(String name, double salary)
{
    this.name = name;
    this.salary = salary;
}
  • Prefixing fields with _, m or x (_salary, mSalary) exists but is not common in Java.

4.6.6 Calling another constructor

  • Besides referring to the implicit parameter, this(...) calls another constructor of the same class, removing duplicate construction code:
Employee(double s)
{
    // calls Employee(String, double)
    this("Employee #" + nextId, s);
    nextId++;
}
  • new Employee(60000) runs Employee(double), which calls Employee(String, double).
  • Before Java 25 the this(...) call had to be the first statement; that restriction is gone, but code before it runs in the early construction context, where you may not:
    • read any instance variable
    • write an instance variable that has an explicit initialisation
    • invoke any method on this
    • pass this to other methods
  • So no code can observe a partially constructed object. A useful thing to do there is validate or normalise parameters:
Employee(double s)
{
    if (s < 0)
    {
        s = 0; // Cannot have negative salary
    }
    this("Employee #" + nextId, s);
    nextId++;
}

4.6.7 Initialisation blocks

  • A third way to initialise fields: an initialisation block (arbitrary code in the class body) that runs whenever an object is constructed, before the constructor body, whichever constructor is used:
class Employee
{
    private static int nextId;

    private int id;
    private String name;
    private double salary;

    // object initialisation block
    {
        id = nextId;
        nextId++;
    }

    Employee(String n, double s)
    {
        name = n;
        salary = s;
    }

    Employee()
    {
        name = "";
        salary = 0;
    }
}
  • Never necessary and not common; a constructor is usually clearer.
  • You may set fields in a block before they are declared, but not read fields initialised later (JLS section 8.3.3 at https://docs.oracle.com/javase/specs)
    • The rules baffled the compiler implementors, early Java versions had subtle bugs, so always put initialisation blocks after the field definitions.

What happens, in order, when a constructor is called:

  1. All instance fields are set to their default values (0, false, null).
  2. Field initialisers and initialisation blocks run, in the order they appear in the class.
  3. The body of the constructor runs.
  4. If the constructor calls another constructor, that body runs as well.

4.6.8 Static initialisation

  • A static field is initialised by a value in its declaration (private static int nextId = 1;) or a static initialisation block, for complex setup
    • Example: start IDs at a random integer below 10,000:
private static RandomGenerator generator = RandomGenerator.getDefault();

// static initialisation block
static
{
    nextId = generator.nextInt(10000);
}
  • Static initialisation happens when the class is first loaded; static fields default to 0, false or null; initialisers and static blocks run in order of appearance.
  • History:
    • up to Java 6 a "Hello, World" program needed no main: a static block printed it when the class loaded, then the launcher complained that main was missing
    • Since Java 7 the launcher checks for main first.
  • Cycles in static initialisation:
class Config
{
    static final Config DEFAULT = new Config();
    String get(String key) {
        /* ... */ return null;
    }

    Config()
    {
        // read configuration
        Logger.DEFAULT.log("Config read successfully");
    }
}

class Logger
{
    static final Logger DEFAULT
        = new Logger(Config.DEFAULT.get("logger.default.file"));
    void log(String message) { /* ... */ }
}
  • The first use of Logger triggers its static initialisation, which builds Config
    • the Config constructor calls Logger.DEFAULT.log while Logger.DEFAULT is still unset, so a NullPointerException occurs, causing a fatal ExceptionInInitializerError. Rare, but hard to debug.
  • Listing 4.6 (ConstructorDemo.java) combines overloaded constructors, this(...), a no-argument constructor, an object initialisation block, a static initialisation block and field initialisation
    • Its nextId starts at generator.nextInt(10000).
  • Random numbers: RandomGenerator (JDK 17, package java.util.random) improves on the classic Random (1.0), which has a short period of 2^48 after which state repeats.
    • Rule of thumb: to generate n numbers the period should be at least n squared, so Random is unsuitable beyond 2^24 numbers (about 17 million). Prefer newer algorithms.
    • RandomGenerator is an interface (chapter 6); the default works for most purposes.

java.util.random.RandomGenerator (17): int nextInt(int n) (0 to n-1), static RandomGenerator of(String name) (the algorithm "L64X128MixRandom" suits most applications), static RandomGenerator getDefault() (a strong generator with 64 or more state bits). java.util.Random (1.0): static Random from(RandomGenerator) (19) wraps a generator so legacy code can use strong generators.

4.7 Records

  • Sometimes data is just data and hiding gets in the way
    • A Point with x and y as a class needs private final fields, a constructor and getters, but would you ever change a point's implementation? A point in the plane is its two coordinates.
  • Records (preview in JDK 14, final in JDK 16) define such classes concisely.

4.7.1 The record concept

  • A record is a class whose state is immutable and publicly readable.
record Point(double x, double y) { }
  • This generates private final fields x and y (the record's components), the constructor Point(double x, double y) and public accessors x() and y() (not getX; it is legal in Java to have a field and a method with the same name).
var p = new Point(3, 4);
IO.println(p.x() + " " + p.y());
  • Records skip the get convention because it is messy (is for booleans, capitalisation, fields x and X). Legacy classes are usually mutable and so not candidates anyway.
  • Every record also gets toString, equals and hashCode automatically (chapter 5).
  • You can add methods, even redefine generated ones with the same signature (a bad idea, for example x() returning 2 * x), and static fields and methods
    • You cannot add instance fields:
record Point(double x, double y)
{
    // double z;  // ERROR: no extra instance fields
    double distanceFromOrigin()
    {
        return Math.hypot(x, y);
    }

    static Point ORIGIN = new Point(0, 0);

    static double distance(Point p, Point q)
    {
        return Math.hypot(p.x - q.x, p.y - q.y);
    }
}
  • Fields are automatically final, but may reference mutable objects:
record PointInTime(double x, double y, Date when) { }

var pt = new PointInTime(0, 0, new Date());
pt.when().setTime(0); // the record instance has changed
  • If you want immutable records, do not use mutable field types.
  • A record can be declared inside another class (chapter 6)
    • the enclosing class can then use p.x instead of p.x(). This also holds for any record in a compact compilation unit, since it is nested in the implicit class.
  • When to use:
    • a record for immutable data completely represented by a set of variables
    • a class for mutable data or representation that may evolve. Records are easier to read, more efficient and safer in concurrent programs.

4.7.2 Constructors: canonical, compact and custom

  • The generated constructor that sets all fields is the canonical constructor.
  • To validate or normalise its parameters, use the compact form (no parameter list):
record Range(int from, int to)
{
    Range // compact form, normalising parameters
    {
        if (from > to) // swap the bounds
        {
            int temp = from;
            from = to;
            to = temp;
        }
    }
}
  • A compact body is the prelude to the canonical constructor: it changes the parameter variables before they are assigned to this.from and this.to
    • You cannot read or modify the instance fields in it
    • A validating version simply throws IllegalArgumentException when from > to.
  • Custom constructors must ultimately call the canonical one: Point() { this(0, 0); }. As in 4.6.6, Java 25 allows code in the early construction context before that call.
  • Writing the canonical constructor yourself is legal but very uncommon; a compact constructor does the same with less work.
  • Listing 4.7 (RecordDemo.java) shows a Point with a custom constructor, method, static field and method
    • a Range with a compact constructor (new Range(4, 3) becomes 3 to 4)
    • and a mutable PointInTime where pt.when().setTime(0) changes the record's printed value.

4.8 Packages

  • A package groups classes: for organising work and separating your code from libraries by others.

4.8.1 Encapsulation

  • Like private, packages encapsulate, but encapsulation is the default: only classes declared public can be used from other packages, and only public methods called from other packages
    • A class or method that is not public is visible only inside its own package.
public class Employee
{
    private String name;
    private double salary;
    private LocalDate hireDay;

    public Employee(String name, double salary, int year, int month, int day)
    {
        // ...
    }

    public String getName()
    {
        // ...
    }
}

4.8.2 Package names

  • Packages keep class names unique: two programmers can both write an Employee class if the packages differ.
  • To guarantee a unique package name, use your internet domain name reversed, then subpackages per project: horstmann.com becomes com.horstmann, then com.horstmann.corejava, giving the qualified name com.horstmann.corejava.Employee.
  • To the compiler nested packages have no relationship: java.util and java.util.random are independent collections.

4.8.3 Class importation

  • A class can use all classes of its own package and all public classes of other packages, by qualified name (java.time.LocalDate today = java.time.LocalDate.now();) or by import:
import java.time.*;        // all classes of the package
import java.time.LocalDate; // one class
  • Imports go at the top of the file, below any package statement. java.time.* is less tedious and has no effect on code size
    • explicit imports tell readers exactly which classes are used.
  • The * imports a single package: import java.* or import java.*.* does not import everything with that prefix.
  • java.lang never needs importing.
  • IDEs can organise imports (expand java.util.* into specific imports, remove unused ones); learn how in yours.
  • Name conflicts:
    • both java.util and java.sql have a Date
    • Importing both with * and then using Date is a compile error
    • Add a specific import (import java.util.Date;) or, if you need both, use full names:
var startTime = new java.util.Date();
var today = new java.sql.Date(/* ... */);
  • Locating classes in packages is the compiler's job; bytecode always uses full package names. The import is only a convenience for short names.
  • Not #include:
    • C and C++ need #include because the compiler looks only at the current source file
    • the Java compiler consults other source and class files itself. In C++ the analogs of package and import are namespace and using.

4.8.4 Module imports

  • Packages can be grouped into modules (chapter 12). As of Java 25 you can import all packages of a module: import module java.xml; (the java.xml module is for XML processing).

  • The most useful module for general programming is java.base (includes java.lang, java.util, java.io and over thirty other packages): import module java.base; lets you use LocalDate and Date without qualification.

  • In a compact source file java.base is imported automatically, so if you only use its packages you need no import statements.

  • Two packages in an imported module can contain the same class name (java.net.Proxy and java.lang.reflect.Proxy): import the one you need or use the qualified name.

4.8.5 Static imports

  • import static imports static methods and fields, not just classes:
import static java.lang.System.*;

err.println("Goodbye, World!"); // System.err
exit(0);                        // System.exit
  • Import a single member with import static java.lang.System.exit;.
  • Abbreviating System.err or System.exit makes code less clear, but sqrt(pow(x, 2) + pow(y, 2)) is clearer than Math.sqrt(Math.pow(x, 2) + Math.pow(y, 2)).
  • You can import enum constants too:
import java.time.DayOfWeek;
import static java.time.DayOfWeek.*;

DayOfWeek w = FRIDAY; // same as DayOfWeek.FRIDAY

4.8.6 Adding a class to a package

  • Put package com.horstmann.corejava; at the top of the source file, before the class definitions
    • With no package statement the classes are in the unnamed package (all earlier examples)
    • The implicit class of a compact compilation unit is always in the unnamed package.
  • Source files must sit in a subdirectory matching the package name (com/horstmann/corejava on Unix, com\horstmann\corejava on Windows).

  • Run java PackageDemo.java from the base directory; the compiler finds com/horstmann/corejava/Employee.java automatically.
// PackageDemo.java (Listing 4.8, unnamed package)
import com.horstmann.corejava.Employee;
// the Employee class is defined in that package

void main()
{
    // because of the import statement, we don't have to use
    // com.horstmann.corejava.Employee here
    var harry = new Employee("Harry Hacker", 50000, 1989, 10, 1);

    harry.raiseSalary(5);

    IO.println("name=" + harry.getName() + ",salary=" + harry.getSalary());
}

// com/horstmann/corejava/Employee.java (Listing 4.9)
package com.horstmann.corejava;
// the classes in this file are part of this package

import module java.base;
// import statements come after the package statement

/**
 * This class is almost identical to the initial Employee class, but it is inside
 * a package. Note that the class and its methods are public.
 */
public class Employee
{
    private String name;
    private double salary;
    private LocalDate hireDay;

    public Employee(String name, double salary, int year, int month, int day)
    {
        this.name = name;
        this.salary = salary;
        hireDay = LocalDate.of(year, month, day);
    }

    public String getName()
    {
        return name;
    }

    public double getSalary()
    {
        return salary;
    }

    public LocalDate getHireDay()
    {
        return hireDay;
    }

    public void raiseSalary(double byPercent)
    {
        double raise = salary * byPercent / 100;
        salary += raise;
    }
}
  • (A comment in the book's printed PackageDemo mentions a "static import statement" for IO.println; none is needed in Java 25 because IO is available, as the code above shows.)

4.8.7 Compiling with packages

  • Outside demos the unnamed package is not common. Source tree with two packages:
    • com/horstmann/corejava/Employee.java and com/mycompany/MyProgram.java
  • Start from the base directory (the one containing com): java com/mycompany/MyProgram.java.
  • For larger programs, compile first: javac com/mycompany/MyProgram.java puts a .class file beside each source (IDEs and build tools usually use a separate output tree). Then run:
$ javac com/mycompany/MyProgram.java
$ java com.mycompany.MyProgram
  • javac works on files (slashes, .java extension); the JVM loads a class (dots).
  • The compiler does not check that the directory layout matches the package statement
    • A source with package com.mycompany; compiles even outside com/mycompany, but the program will not run until the class files are in the right place, because the JVM cannot find classes whose packages do not match directories.

4.8.8 Package access

  • public features are usable by any class; private only by the defining class. With neither modifier, a feature is accessible to all methods of the same package (package access).
  • For classes this is a reasonable default (the non-public Employee of Listing 4.2 is visible only inside its unnamed package)
    • For variables it was an unfortunate choice: a forgotten private silently breaks encapsulation.
  • Real example from the JDK source:
    • in java.awt.Window, String warningString; is not private, so any class of java.awt could set it to "Trust me!"
    • After more than twenty years it is still not private, and about half of the newer fields are not either.
  • Packages are not closed:
    • anyone can add classes to one
    • In early Java you could smuggle a class into java.awt by starting it with package java.awt; and placing the class file under java/awt, then modify the warning string (Figure 4.9).
  • Since version 1.2 the class loader refuses user classes whose package starts with java.
    • Your own packages get no such protection
    • A now-obsolete mechanism let a JAR declare packages sealed; today use modules (chapter 12).

4.8.9 The class path

  • Class files live in subdirectories matching the package, or in a JAR file (a compressed archive of class files and subdirectories, in ZIP format, so any ZIP tool can open it)
    • Third-party libraries usually arrive as JARs (creating your own is in 4.9.1).
  • To share classes among programs:
    1. Put class files in a base directory for the package tree: Employee.class must be in /home/user/classdir/com/horstmann/corejava.
    2. Put JAR files in a directory such as /home/user/archives.
    3. Set the class path, the collection of all locations that may contain class files.
  • Separator: colon on Unix, semicolon on Windows; . is the current directory:
/home/user/classdir:.:/home/user/archives/archive.jar
c:\classdir;.;c:\archives\archive.jar
  • A wildcard includes all JAR files (not .class files) of a directory: /home/user/archives/'*' (escape * on Unix to stop the shell expanding it) or c:\archives\*.
  • The Java API is always searched, so do not list it.
  • Trap:
    • javac always looks in the current directory, but the java launcher looks there only if . is on the class path
    • With no class path set the default is ., but if you set one and forget ., programs compile but will not run.

  • To find com.horstmann.corejava.Employee the JVM first checks the Java API, then the class path: /home/user/classdir/com/horstmann/corejava/Employee.class, then the same relative path from the current directory, then inside archive.jar.
  • The compiler has a harder job.
    • For an unqualified name like Employee it must find the package, using the imports
    • With import java.util.*; and import com.horstmann.corejava.*; it tries java.lang.Employee (always imported), java.util.Employee, com.horstmann.corejava.Employee and Employee in the current package, searching each on the class path.
    • More than one match is a compile error (qualified names are unique, so import order does not matter).
    • The compiler also recompiles a source file newer than its class file. Only public classes can be imported from other packages, and a file holds one public class named like the file, so the compiler easily locates them
      • for non-public classes of the current package it searches all source files of the package.

4.8.10 Setting the class path

  • IDEs and build tools manage the class path, but know how to set it by hand for troubleshooting
    • Preferred: the -classpath option (or -cp, or --class-path), on one line (put long ones in a script):
$ java -classpath /home/user/classdir:.:/home/user/archives/archive.jar MyProg
  • Alternative: the CLASSPATH environment variable (export CLASSPATH=... in bash, set CLASSPATH=... on Windows), lasting until the shell exits.
  • JShell: use CLASSPATH=archive.jar jshell; jshell --class-path=archive.jar gives no autocomplete for classes in the JAR (https://bugs.openjdk.org/browse/JDK-8177650).
  • Do not set CLASSPATH permanently:
    • people forget the global setting
    • The cautionary tale: Apple's QuickTime installer on Windows set it globally to one JAR without including ., so "countless Java programmers" saw programs that compiled but failed to run.
  • Also bad (and obsolete since Java 9): dropping JARs in jre/lib/ext; forgotten classes got loaded from there.
  • Classes can also load from the module path (chapter 12).

4.9 JAR files

  • Give users one file instead of a directory tree. A JAR (Java archive) holds class files and other files (images, sounds) in ZIP compression.

4.9.1 Creating JAR files

  • The jar tool (in $JAVA_HOME/bin): jar cvf jarFileName file1 file2 ..., for example jar cvf CalculatorClasses.jar *.class icon.png.

Table 4.2, jar options (like tar):

Option Meaning
c Create a new or empty archive and add files (directories processed recursively)
C Temporarily change directory, e.g. jar cvf jarFileName.jar -C classes *.class
e Create an entry point in the manifest (4.9.3)
f Take the JAR file name as the next argument; without it, output goes to stdout (create) or input comes from stdin (extract, list)
i Create an index file for faster lookup in large archives
m Add a manifest (a description of contents and origin; there is a default, supply your own to authenticate contents)
M Do not create a manifest file
t Display the table of contents
u Update an existing JAR
v Verbose output
x Extract files (all, or those named)
0 Store without ZIP compression

4.9.2 The manifest

  • Every JAR has a manifest META-INF/MANIFEST.MF. The minimum is Manifest-Version: 1.0.
  • Entries are grouped in sections separated by blank lines: the first, the main section, covers the whole JAR; later ones start with a Name: entry for a file, package or URL.
  • Make a JAR with your own manifest: jar cfm MyArchive.jar manifest.mf com/mycompany/mypkg/*.class. Update one: jar ufm MyArchive.jar manifest-additions.mf.
  • Format reference: https://docs.oracle.com/en/java/javase/25/docs/specs/jar/jar.html.

4.9.3 Executable JAR files

  • Name the entry point with the e option, or put Main-Class: com.mycompany.mypkg.MainAppClass in the manifest (no .class extension):
$ jar cvfe MyProgram.jar com.mycompany.mypkg.MainAppClass files-to-add
$ java -jar MyProgram.jar
  • The manifest's last line must end with a newline, otherwise it is not read correctly (a common error is a file containing only the Main-Class line without a terminator).
  • Double-clicking: on Windows the runtime installer associates .jar with javaw -jar (no shell window); macOS recognises .jar files too.
  • A JAR does not feel like a native app
    • On Windows, wrappers turn a JAR into an .exe that finds the JVM: Launch4J (https://launch4j.sourceforge.net) and IzPack (https://github.com/izpack/izpack).

4.9.4 Multi-release JAR files

  • Modules and strong encapsulation removed some internal APIs, so library providers may need different code per Java version
    • A multi-release JAR puts version-specific classes in META-INF/versions/<N>, with the manifest line Multi-Release: true.
  • Example:
    • a legacy Application.class may use com.sun.javafx.css.CssParser, while the Java 9 version uses javafx.css.CssParser. Java 8 ignores the versions directory and loads the legacy classes
    • Java 9 and later use the newer ones.
  • Add versioned classes:
    • jar uf MyProgram.jar --release 9 Application.class
    • From scratch: jar cf MyProgram.jar -C bin/8 . --release 9 -C bin/9 Application.class
    • Compile per release with javac -d bin/8 --release 8 ... (-d creates the directory).
  • The JDK ships symbol files for two prior API versions (in Java 21 you can compile with --release 21, 20 or 19).
  • Purpose is limited:
    • the same version of a program or library working on several JDKs, with the same public API in every release
    • If you add functionality or change an API, ship a new JAR version.
  • javap is not retrofitted: javap -classpath MyProgram.jar Application.class shows the base version
    • for a newer one use javap -classpath MyProgram.jar\!/META-INF/versions/9/Application.class.

4.9.5 A note about command-line options

  • JDK commands traditionally used a single dash and multi-letter names (java -jar, javac -Xlint:fallthrough -classpath)
    • The odd one out was jar, which follows tar style with no dashes.
  • JEP 293
    • (https://openjdk.org/jeps/293) moves toward the Linux style of double dashes for long options and single-letter shortcuts (ls --human-readable or ls -h), from Java 9
    • So --version replaces -version, --class-path replaces -classpath, and --module-path has the shortcut -p (chapter 12).
  • Arguments to -- options are separated by whitespace or = (--class-path=/home/user/classdir); the = form helps when passing options through tools that cannot handle whitespace.
  • JDK_JAVA_OPTIONS passes options to the java launcher: export JDK_JAVA_OPTIONS='--class-path /home/user/classdir -enableassertions'.
  • JEP 293 says single-letter flags can be grouped (jar -cv -f myapp.jar -m MANIFEST.MF *.class), but that does not currently work for jar, while the old jar -cvfm myapp.jar MANIFEST.MF *.class works though it should not
    • Stick to the classic tar-style options for jar.
  • Also unsupported: attaching an argument directly (javac -doutputdir), which would invite conflicts with legacy options (what if the directory is named eprecation?).

4.10 Documentation comments

  • The JDK's javadoc generates HTML documentation from source
    • The online API docs from chapter 3 are exactly javadoc run on the standard library
    • Keeping docs in the source file avoids code and comments drifting apart.

4.10.1 Comment insertion

  • javadoc extracts information for: modules, packages, public classes and interfaces, public and protected fields, public and protected constructors and methods (protected in chapter 5, interfaces in chapter 6, modules in chapter 12).
  • Place a /** ... */ comment immediately above each member. It contains free-form text followed by tags starting with @ (@since, @param).
  • The first sentence should be a summary; javadoc builds summary pages from them.
  • Block tags start a line with @. Inline tags use braces: {@tagname contents} (@code, @link). HTML such as <em> or <ul> passes through.
  • Since Java 23
    • you can write JavaDoc in Markdown, with /// in front of each line instead of /** */
    • it follows CommonMark plus GitHub Flavored Markdown tables. Not yet common
    • details in JEP 467 (https://openjdk.org/jeps/467).

4.10.2 Class comments

  • Place after any imports, directly before the class. The leading * on each line is optional (IDEs add them):
/**
 * A {@code Card} object represents a playing card, such
 * as "Queen of Hearts". A card has a suit (Diamond, Heart,
 * Spade or Club) and a value (1 = Ace, 2 ... 10, 11 = Jack,
 * 12 = Queen, 13 = King).
 */
public class Card
{
    // ...
}

4.10.3 Method comments

  • Immediately before the method, with extra tags:
    • @param variable description: one entry per parameter; keep all @param tags together.
    • @return description: a "returns" section.
    • @throws class description: exceptions the method may throw (chapter 7).
/**
 * Raises the salary of an employee.
 * @param byPercent the percentage by which to raise the salary (e.g., 10 means 10%)
 * @return the amount of the raise
 */
public double raiseSalary(double byPercent)
{
    double raise = salary * byPercent / 100;
    salary += raise;
    return raise;
}
  • When description and return value are identical, use the inline {@return ...} (Java 16): /** {@return the name of the employee} */ gives the description "Returns the name of the employee." plus a "Returns" section.
  • {@inheritDoc} copies the documentation from the superclass or interface method (chapters 5 and 6).

4.10.4 Field comments

  • Only public fields need documentation, generally static constants:
/**
 * The "Hearts" card suit
 */
public static final int HEARTS = 1;

4.10.5 Package comments

  • Class, method and variable comments go in the source
    • For a package, add a file in the package directory: a Java file package-info.java (an initial /** */ comment followed by the package statement, with nothing else) or an HTML file package.html (text between <body> tags is extracted).

4.10.6 HTML markup

  • Use <em>, <strong>, <ul>/<li>, <img .../>.
  • For monospaced code use {@code ...} instead of <code>: no need to escape < and &. For unescaped < or & in the plain font use @literal{...}.
  • Multi-line code: <pre>{@code ... }</pre>, or since Java 18 {@snippet : ... }; braces must match and /* */ comments are not allowed inside.

4.10.7 Links

  • @see reference adds a hyperlink in "see also". References: package.class#member label, <a href="...">label</a>, or "text".
    • @see com.horstmann.corejava.Employee#raiseSalary(double) links to a method; the package, or package and class, may be omitted to mean the current ones.
    • Use #, not a period, between class and member (javadoc is not as clever as the compiler).
    • A constructor is named <init>: @see com.horstmann.corejava.Employee#<init>().
    • An optional label becomes the link anchor; < means you give an HTML link, " means plain text. Several @see tags are allowed but must be kept together.
  • {@link package.class#member}
    • links anywhere in a comment (same reference rules)
    • use @linkplain for the plain font. In a snippet put @link in a comment: IO.println(); // @link substring=println target=java.lang.IO#println().
  • Since Java 20 level 2 and 3 headings get automatic ids (<h2>General Principles</h2> becomes general-principles-heading), linkable with two # symbols: {@link com.horstmann.corejava.Employee##general-principles-heading}.
  • Files such as images go in a doc-files subdirectory next to the source; javadoc copies it: <img src="doc-files/uml.png" alt="UML diagram"/>.

4.10.8 General comments

  • @since text (for example @since 1.7.1).
  • Class tags: @author name (repeatable; version control tracks authorship better) and @version text.
  • {@value optionalFormat constantFieldReference} inserts a constant's value, with a printf-style format since Java 20: {@value %X Integer#MAX_VALUE} gives 7FFFFFFF.
  • @deprecated goes with the @Deprecated annotation and explains when and why, with alternatives.
  • {@index entry} adds an entry to the generated index.

4.10.9 Code snippets

  • Snippets (Java 18) import presumably tested, current code from files, to avoid stale documentation:
{@snippet file=EmployeeDemo.java}
{@snippet class=com.horstmann.corejava.EmployeeDemo.java}
  • Files go in the package's snippet-files subdirectory. To copy a named region of a file, mark it in the source with comments // @start region=default-employee and // @end.
  • Decorations live in comments, so the source still compiles and runs:
    • highlight: // @highlight substring=new or // @highlight regex=get[A-Z][a-z]+ (the book's example spells it @hightlight once, a typo)
    • replace: // @replace regex=([^)]+) replacement="(..., ...)" turns new Employee("Fred", 100000) into new Employee(..., ...)
    • link: // @link substring=Card target=com.horstmann.games#Card.<init>()

4.10.10 Comment extraction

  1. Change to the directory containing the sources (for nested packages like com.horstmann.corejava, the directory containing com, also where an overview.html lives).
  2. Run javadoc -d docDirectory nameOfPackage (or several packages), or for the unnamed package javadoc -d docDirectory *.java. Do not omit -d: HTML would land in the current directory, which gets messy.
  • Useful options:
    • -author and -version (those tags are omitted by default)
    • -link to link standard classes, e.g. javadoc -link https://docs.oracle.com/en/java/javase/25/docs/api *.java
    • -linksource (source converted to HTML with line numbers, names become links)
    • -overview filename for an overview comment (text between <body> tags, shown under "Overview").
  • More at https://docs.oracle.com/en/java/javase/25/javadoc/index.html.

4.11 Class design hints

  1. Always keep data private. Doing otherwise violates encapsulation. Representation changes more often than usage, so private data confines changes and makes bugs easier to find.
  2. Always initialise data. Java initialises fields but not locals; do not rely on defaults, set values explicitly in declarations or in all constructors.
  3. Do not use too many basic types in a class. Replace related primitives with a class: street, city, state, zip in Customer become an Address class, which copes with changes such as international addresses.
  4. Not all fields need individual accessors and mutators. You may need salary both ways, but never the hire date after construction, and some fields (an array of state abbreviations in Address) nobody should get or set.
  5. Break up classes with too many responsibilities. "Too many" is subjective; if there is an obvious way to split one complicated class into two simpler ones, do it, but ten one-method classes is overkill.
    • Bad design: CardDeck with int[] value and int[] suit plus shuffle, getTopValue, getTopSuit, draw mixes two concepts, a deck and a card.
    • Better: a Card class (simple enough to be a record) and an enum for suits, with CardDeck holding Card[]:
public class CardDeck
{
    private Card[] cards;

    public CardDeck() { /* ... */ }
    public void shuffle() { /* ... */ }
    public Card getTop() {
        /* ... */ return null;
    }
    public void draw() { /* ... */ }
}

public enum Suit { DIAMONDS, HEARTS, SPADES, CLUBS }

public record Card(int value, Suit suit) { }

  1. Make class and method names reflect responsibilities. A class name should be a noun (Order), a noun with an adjective (RushOrder) or a gerund (BillingAddress). Dubious library example: Date, which describes time. Accessors start with get (getSalary), mutators with set (setSalary).
  2. Prefer immutable classes. LocalDate and the other java.time classes are immutable: methods like plusDays return new objects.
    • Mutation is a problem under concurrency: two threads updating an object at once give unpredictable results. Immutable objects can be shared safely among threads.
    • Easy for value-like classes (a string, a point in time): computations yield new values.
    • Not everything should be immutable: raiseSalary returning a new Employee would be strange.

Summary points

  • OOP makes data primary; classes encapsulate state and behaviour; objects have behaviour, state and identity.
  • Object variables hold references; null needs care; Objects.requireNonNull fails fast.
  • Parameters are passed by value, references included.
  • Constructors can be overloaded, chain with this(...), and run after field initialisers and initialisation blocks; static initialisation happens at class load.
  • Records give immutable, concise data carriers; compact constructors validate.
  • Packages organise code and give default encapsulation; the class path (or module path) tells the JVM where to look; JARs bundle classes; javadoc documents public API.
  • Design hints: private data, initialise, group primitives into classes, single responsibility, immutable where possible.
Terms to carry forward
  • Encapsulation, instance field, method, state, identity: the core OOP vocabulary.
  • Object variable, reference, null: variables refer to objects.
  • Mutator, accessor, immutable: whether a method changes state.
  • Implicit parameter (this), explicit parameter: the receiver and the arguments.
  • Static field, static method, static constant, factory method: class-level members.
  • Call by value: Java copies arguments, including references.
  • Overloading, signature: same name, different parameter types.
  • Canonical, compact constructor: record constructors.
  • Package, import, unnamed package, module import: organising and referring to classes.
  • Class path, JAR, manifest: how classes are found and packaged.
  • Javadoc, @param, @return, {@code}, {@snippet}: API documentation.
  • Compact compilation unit: Java 25 source with top-level methods.
