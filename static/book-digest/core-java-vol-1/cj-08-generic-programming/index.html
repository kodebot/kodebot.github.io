Core Java 8: Generic Programming

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 8. Previous: Core Java 7: Exceptions, Assertions and Logging. Next: Core Java 9: Collections.

Takeaways
  • Generics give classes and methods type parameters, replacing the old Object plus cast approach: code is easier to read and errors become compile-time errors, not run-time ClassCastExceptions.
  • Using generic classes is easy; writing them is hard. Use the knowledge mainly to understand and troubleshoot.
  • The JVM has no generic types: the compiler erases type parameters to their bounds (or Object), inserts casts, and creates bridge methods to keep polymorphism. That explains most limitations.
  • Pair<Manager> is not a subtype of Pair<Employee>. Wildcards (? extends T to read, ? super T to write) restore flexibility safely.
  • Limits: no primitive type arguments, no new T() or new T[n], no instanceof Pair<String>, no generic exceptions, no arrays of parameterised types.

8.1 Type parameters

  • Generic programming means writing code reusable for many types. ArrayList is one example: you do not write separate classes for String and File collections.

8.1.1 The advantage of generic programming

  • Before generics, reuse used inheritance: ArrayList held Object references.
public class ArrayList // before generic classes
{
    private Object[] elementData;
    // ...
    public Object get(int i) { /* ... */ }
    public void add(Object o) { /* ... */ }
}
  • Two problems: a cast is needed on every read (String filename = (String) files.get(i);), and no error checking: files.add(Path.of("...")) and files.add(new File("...")) both compile and the failure appears later as a ClassCastException.
  • With a type parameter:
    • var files = new ArrayList<String>();, or ArrayList<String> files = new ArrayList<>(); (diamond; the type is inferred from the variable)
    • No cast on get; files.add(new File("...")) does not compile
    • "A compiler error is much better than a class cast exception at runtime."

8.1.2 Who wants to be a generic programmer?

  • Using ArrayList<String> is as easy as using String[]
    • Implementing generic classes is hard: users will plug in all kinds of classes and expect everything to work without odd restrictions or confusing errors, so you must anticipate uses.
  • Example: addAll should accept an ArrayList<Manager> into an ArrayList<Employee> but not the reverse. The designers invented the wildcard type to allow one and forbid the other.
  • Three skill levels:
    • just use generic classes like ArrayList
    • understand enough to decode confusing error messages when mixing generic classes and solve them systematically instead of by "random tinkering"
    • implement your own generic classes and methods. The author expects most readers to use the knowledge for troubleshooting and curiosity

8.1.3 Defining a simple generic class

  • A generic class has one or more type variables, written in angle brackets after the class name:
public class Pair<T>
{
    private T first;
    private T second;

    public Pair() {
        first = null;
        second = null;
    }
    public Pair(T first, T second) {
        this.first = first;
        this.second = second;
    }

    public T getFirst() {
        return first;
    }
    public T getSecond() {
        return second;
    }

    public void setFirst(T newValue) {
        first = newValue;
    }
    public void setSecond(T newValue) {
        second = newValue;
    }
}
  • (Why not an immutable record? The class is mutable on purpose, for reasons that appear soon.)
  • Several variables are allowed:
    • public class Pair<T, U> { ... }
    • Use short uppercase letters: E for collection elements, K and V for key and value, T (and neighbours U, S) for "any type".
  • Instantiate
    • by substituting types: Pair<String> acts like an ordinary class with constructors Pair<String>() and Pair<String>(String, String) and methods String getFirst(), void setFirst(String) and so on
    • A generic class is a factory for ordinary classes.
  • Listing 8.1 (PairDemo1.java): minmax(String[] a) scans an array and returns a Pair<String> holding the min and max (for "Mary had a little lamb": min is a, max is little).

8.1.4 Generic methods

  • A single method can have type parameters, between the modifiers and the return type, and may live in an ordinary class or a generic one:
public static <T> T getMiddle(T... a)
{
    return a[a.length / 2];
}
  • Usually no type argument is supplied:
    • getMiddle("John", "Q.", "Public") infers T = String
    • When you must, put it before the method name after a dot: Collections.<String>emptySet(), or this.<String>getMiddle("John", "Q.", "Public").
    • C++ puts type arguments after the name, causing parsing ambiguities (g(f<a,b>(c)) could be a call with f<a,b>(c) or two boolean comparisons).
  • Inference sometimes fails
    • with a cryptic message. double middle = getMiddle(3.14, 1729, 0); makes the compiler look for a common type of double and int arguments and find Number plus the generic Comparable, producing a long "inferred type does not conform to upper bound(s)" error
    • the fix is to write all arguments as double.
  • Peter von der Ahé's trick
    • to see an inferred type: deliberately cause an error
    • Assigning getMiddle("Hello", 0, null) to a LocalDate yields an error listing the inferred type (Object & Serializable & Comparable<...> & Constable & ConstantDesc): you can assign it to any of those.
  • Inference can be slow: List.of(...) with hundreds of new Pair<>("John", "Smith") takes the compiler a long time; help it with List.<Pair<String>>of(...).

8.1.5 Bounds for type variables

  • To compute the smallest element of any array, T must have a compareTo. Bound it:
<T extends Comparable> T min(T[] a)
{
    if (a == null || a.length == 0)
    {
        return null;
    }
    T smallest = a[0];
    for (int i = 1; i < a.length; i++)
    {
        if (smallest.compareTo(a[i]) > 0)
        {
            smallest = a[i];
        }
    }
    return smallest;
}
  • Comparable is itself generic (ignore the warnings for now; section 8.4 does it properly). Now calling it with a Rectangle[] (not Comparable) is a compile error.
  • Why extends for an interface?
    • <T extends BoundingType> means "subtype of", and both can be classes or interfaces
    • extends approximates subtyping and the designers did not want a new keyword.
  • Multiple bounds with &: T extends Comparable & Serializable (commas separate type variables). At most one bound can be a class, and it must be first.
  • Listing 8.2 (PairDemo2.java): a generic <T extends Comparable> Pair<T> minmax(T[] a) applied to four birthdays (Hopper, Lovelace, von Neumann, Zuse): min is 1815-12-10, max is 1910-06-22.

8.1.6 Generic exceptions

  • A throws clause may use a type variable:
interface Task<T extends Throwable>
{
    void run() throws T;
}

<T extends Throwable> void repeat(Task<T> t, int n) throws T
{
    for (int i = 0; i < n; i++)
    {
        t.run();
    }
}
  • repeat(() -> Thread.sleep(100), 10) throws the same checked InterruptedException
    • If the lambda throws both InterruptedException and IOException, T is inferred as the least upper bound Exception (the union is not a Java type).
  • You cannot use a type variable in a catch:
    • catch (T e) is an error
    • You can neither throw nor catch objects of a generic class, and a generic class cannot even extend Throwable: public class Problem<T> extends Exception does not compile.

8.2 Generic code and the virtual machine

  • The VM has no objects of generic types, only ordinary classes
    • (An early generics implementation could even compile to class files running on 1.0 VMs.) The compiler erases type parameters.

8.2.1 Type erasure

  • Every generic type gets a raw type: the generic name with parameters removed; type variables are replaced by their bounding types, or Object if unbounded. The raw Pair:
public class Pair
{
    private Object first;
    private Object second;

    public Pair(Object first, Object second) { /* ... */ }
    public Object getFirst() {
        return first;
    }
    public void setFirst(Object newValue) {
        first = newValue;
    }
    // ...
}
  • Pair<String>, Pair<LocalDate> and so on all become the raw Pair. Erasure is efficient but only works because all type arguments are reference types.
    • C++ generates separate code per type argument; C# is a middle way (one implementation for all reference types, separate ones for value types).
    • Planned: value types in Java as type parameters, with an optimised memory layout, so one day ArrayList<int> could be backed by an int[].
  • The raw type uses the first bound
    • For class Interval<T extends Comparable & Serializable> implements Serializable the raw type has Comparable lower, upper
    • Swap the bounds (T extends Serializable & Comparable) and T becomes Serializable, with casts to Comparable inserted where needed.

8.2.2 Translating generic expressions

  • When the erased return type differs from the use, the compiler inserts casts
    • Employee buddy = buddies.getFirst(); (with Pair<Employee> buddies) becomes two VM instructions: call the raw Pair.getFirst, then cast the returned Object to Employee
    • The same happens when accessing a generic field (buddies.first).

8.2.3 Translating generic methods

  • A generic method looks like a family but after erasure only one remains: <T extends Comparable> T min(T[] a) becomes Comparable min(Comparable[] a).
  • Bridge methods preserve polymorphism. A subclass overriding a generic method:
class DateInterval extends Pair<LocalDate>
{
    public void setSecond(LocalDate second)
    {
        if (second.compareTo(getFirst()) >= 0)
        {
            super.setSecond(second);
        }
    }
}
  • After erasure DateInterval has setSecond(LocalDate) and the inherited setSecond(Object) from Pair, which look unrelated
    • But Pair<LocalDate> pair = interval; pair.setSecond(aDate); must call DateInterval.setSecond
    • The compiler generates a bridge method in DateInterval:
public void setSecond(Object second)
{
    setSecond((LocalDate) second);
}
  • Trace of pair.setSecond(aDate): the declared type Pair<LocalDate> has only setSecond(Object)
    • the VM calls it on the DateInterval
    • that is the synthesised bridge, which calls setSecond(LocalDate).
  • Bridges can be stranger:
    • if DateInterval overrides getSecond with return type LocalDate, the class has two getSecond methods, LocalDate getSecond() and a bridge Object getSecond()
    • You cannot write this in Java (same parameter list) but the VM identifies methods by parameter types and return type, so it is fine.
  • Bridges are not only for generics:
    • covariant return types need them too
    • Employee.clone() returning Employee also gets a synthesised bridge Object clone() overriding Object.clone.

Remember:

  1. There are no generics in the virtual machine, only ordinary classes and methods.
  2. All type parameters are replaced by their bounds.
  3. Bridge methods are synthesised to preserve polymorphism.
  4. Casts are inserted as necessary to preserve type safety.

8.2.4 Calling legacy code

  • A design goal was interoperability with legacy code
    • Example: Swing's JSlider.setLabelTable(Dictionary table) uses a raw Dictionary (generified in Java 5 but JSlider never updated).
  • Populate with a generic type, then pass it, getting a warning: the compiler cannot know whether setLabelTable will, say, replace keys with strings:
Dictionary<Integer, Component> labelTable = new Hashtable<>();
labelTable.put(0, new JLabel(new ImageIcon("nine.png")));
labelTable.put(20, new JLabel(new ImageIcon("ten.png")));
slider.setLabelTable(labelTable); // warning
  • Ask what the legacy code will really do (JSlider only reads), then the warning can be ignored. The reverse (a raw return assigned to a generic variable, Dictionary<Integer, Component> labelTable = slider.getLabelTable();) also warns
    • verify the contents, knowing there is never an absolute guarantee but things are no worse than before generics (worst case an exception).
  • Silence it with @SuppressWarnings("unchecked") on a local variable declaration or a whole method (which turns off the check for all its code).

8.3 Inheritance rules for generic types

  • Pair<Manager> is not a subtype of Pair<Employee>,
    • even though Manager extends Employee
    • Pair<Employee> buddies = new Pair<Manager>(ceo, cfo); is illegal
    • In general there is no relationship between Pair<S> and Pair<T> whatever S and T are.
  • Necessary for type safety: if it were allowed, employeeBuddies.setFirst(lowlyEmployee) would put a lowly employee in what is really a Pair<Manager>.

  • Arrays differ: Employee[] employeeBuddies = managerBuddies; is allowed, protected by ArrayStoreException at run time (chapter 5).
  • Raw types:
    • you can always convert a parameterised type to its raw type (Pair<Employee> is a subtype of raw Pair), needed for legacy code
    • You can then cause a type error with only a compile-time warning (rawBuddies.setFirst(new File("..."))), but VM security is not at stake: reading it later as a Manager throws ClassCastException.
  • Generic classes extend generic classes as usual: ArrayList<T> implements List<T>, so an ArrayList<Manager> converts to List<Manager>, but not to ArrayList<Employee> or List<Employee>.

8.4 Wildcard types

  • A rigid generic type system is unpleasant; the designers added the wildcard type as a safe escape hatch.

8.4.1 The wildcard concept

  • Pair<? extends Employee> denotes any Pair whose type parameter is a subclass of Employee: Pair<Manager> yes, Pair<String> no.
  • void printBuddies(Pair<Employee> p) cannot take a Pair<Manager>. Use void printBuddies(Pair<? extends Employee> p): Pair<Manager> is a subtype of Pair<? extends Employee>.
  • Can wildcards corrupt? No:
var managerBuddies = new Pair<Manager>(ceo, cfo);
Pair<? extends Employee> wildcardBuddies = managerBuddies; // OK
wildcardBuddies.setFirst(lowlyEmployee); // compile-time error
  • The methods look like ? extends Employee getFirst() and void setFirst(? extends Employee)
    • For setFirst the compiler knows the parameter is some specific subtype but not which, so it rejects every argument except null (even a Manager)
    • getFirst works: it returns some subtype of Employee, safe to assign to an Employee.
  • This distinguishes safe accessors from unsafe mutators.

8.4.2 Supertype bounds for wildcards

  • ? super Executive:
    • all supertypes of Executive
    • Behaviour is opposite: you can supply arguments to methods but cannot usefully use return values
    • Pair<? super Executive> has void setFirst(? super Executive) and ? super Executive getFirst().
    • The unknown type is one of Object, Employee, Manager, Executive (more with interfaces). setFirst cannot take an Employee or Object (it might really be Manager), but can take an Executive
      • getFirst can only be assigned to an Object.
void minmaxTitle(Executive[] a, Pair<? super Executive> result)
{
    if (a.length == 0)
    {
        return;
    }
    Executive smallest = a[0];
    Executive largest = a[0];
    for (int i = 1; i < a.length; i++)
    {
        if (smallest.getTitle().length() > a[i].getTitle().length())
        {
            smallest = a[i];
        }
        if (largest.getTitle().length() < a[i].getTitle().length())
        {
            largest = a[i];
        }
    }
    result.setFirst(smallest);
    result.setSecond(largest);
}
  • This accepts a Pair<Executive>, Pair<Manager>, Pair<Employee> or Pair<Object>.
  • Rule of thumb: ? super wildcards let you write to a generic object; ? extends wildcards let you read from one. (PECS, the book's wording above.)

  • Comparable<? super T>:
    • <T extends Comparable<T>> Pair<T> minmax(T[] a) fails for LocalDate, which implements Comparable<ChronoLocalDate> (through ChronoLocalDate) not Comparable<LocalDate>
    • The fix:
<T extends Comparable<? super T>> Pair<T> minmax(T[] a)
  • compareTo(? super T) may take a T or a supertype of T, and passing a T is always safe. It looks intimidating, but its purpose is to remove unnecessary restrictions on callers
    • application programmers can gloss over it, library programmers must get used to wildcards "or your users will curse you and throw random casts at their code".
  • Functional interface parameters: default boolean removeIf(Predicate<? super E> filter) lets you pass a Predicate<Object> to an ArrayList<Employee>:
ArrayList<Employee> staff = new ArrayList<>();
Predicate<Object> oddHashCode = obj -> obj.hashCode() % 2 != 0;
staff.removeIf(oddHashCode);

8.4.3 Unbounded wildcards

  • Pair<?>
    • looks like raw Pair but is very different: methods are ? getFirst() and void setFirst(?)
    • The result of getFirst can only go to an Object; setFirst can never be called, not even with an Object (only setFirst(null))
    • Raw Pair accepts any Object.
  • Useful for simple operations that never need the actual type:
boolean hasNulls(Pair<?> p)
{
    return p.getFirst() == null || p.getSecond() == null;
}
  • A generic <T> boolean hasNulls(Pair<T> p) would work too, but the wildcard version reads better.

8.4.4 Wildcard capture

  • swap(Pair<?> p) cannot hold a temporary, since ? is not a type: ? t = p.getFirst(); is an error. Use a generic helper whose type variable captures the wildcard:
<T> void swapHelper(Pair<T> p)
{
    T t = p.getFirst();
    p.setFirst(p.getSecond());
    p.setSecond(t);
}

void swap(Pair<?> p)
{
    swapHelper(p);
}
  • T is unknown but definite, so swapHelper makes sense
    • Here a generic swap would have worked, but when a wildcard arises mid-computation capture is unavoidable, as in maxminTitle(Executive[] a, Pair<? super Executive> result) { minmaxTitle(a, result); swap(result); }.
  • Capture is only legal when the compiler can guarantee one definite type: the T in ArrayList<Pair<T>> can never capture the wildcard in ArrayList<Pair<?>> (each element may have a different type for ?).
  • Listing 8.3 (PairDemo3.java) gathers printBuddies (Pair<? extends Employee>), minmaxTitle, maxminTitle, hasNulls and swap together, using Executives (CEO Gus Greedy and Senior Associate Vice President Sue Striver).

8.5 Restrictions and limitations

  • Most are consequences of type erasure.

8.5.1 Type parameters cannot be instantiated with primitive types

  • No Pair<double>, only Pair<Double>:
    • after erasure the fields are Object and cannot hold a double. Annoying but consistent with the separate status of the eight primitive types
    • write separate classes and methods when wrappers will not do.

8.5.2 Casts only work with raw types

  • The VM only knows raw types, so type inquiries return raw types:
Pair<String> p = (Pair<String>) obj; // warning: only tests that obj is some Pair
Pair<T> q = (Pair<T>) obj;           // only checks for a raw Pair
T t = (T) obj;                       // does nothing at run time
  • The casts compile with warnings, but the instanceof tests are compile-time errors: obj instanceof Pair<String> p, obj instanceof Pair<T> p, obj instanceof T.
  • Why casts are needed:
    • <T> T defaultValue(Class<T> cl) returning "" fails ("result type is T but "" is a String"), so return (T) "";
    • Primitives need two or three casts: return (T) (Integer) 0; and return (T) (Character) (char) 0;.

8.5.3 You cannot create arrays of parameterised types

  • var table = new Pair<String>[10]; is an error
    • After erasure it is Pair[], convertible to Object[]
      • objarray[0] = new Pair<Employee>(); would pass the array-store check but still be a type error, so such arrays are outlawed
    • Only creation is banned: you can declare a variable Pair<String>[].
  • A cast of a wildcard array, var table = (Pair<String>[]) new Pair<?>[10];, is not safe: storing a Pair<Employee> then using a String method on getFirst() gives a ClassCastException.
  • Collect parameterised objects in an ArrayList: ArrayList<Pair<String>> is safe and effective.

8.5.4 Varargs warnings

  • Generic varargs create arrays of generic types, which the rules otherwise forbid:
<E> void addAll(Collection<E> coll, E... elements)
{
    for (E element : elements)
    {
        coll.add(element);
    }
}

Collection<Pair<String>> table = new ArrayList<>();
addAll(table, pair1, pair2); // warning at the call site
  • The rules are relaxed to a warning at the call site (suppress with @SuppressWarnings("unchecked") at the caller), plus a "possible heap pollution" warning at the declaration
    • To avoid both, annotate the method with @SafeVarargs, promising that it does not write to the parameter array nor pass it to others who might:
@SafeVarargs
static <E> void addAll(Collection<E> coll, E... elements)
  • @SafeVarargs works only on constructors and methods that are static, final or private (others could be overridden).
  • It can defeat the no-generic-arrays rule:
    • @SafeVarargs static <E> E[] array(E... array) { return array; } then Pair<String>[] table = array(pair1, pair2);
    • Hidden danger: Object[] objarray = table; objarray[0] = new Pair<Employee>(); runs without ArrayStoreException (the store checks only the erased type), and the exception appears later.

8.5.5 Generic varargs do not spread primitive arrays

  • A reference array passes as if spread: String[] moreStrings = new String[] { "Mary", "had", "a", "little", "lamb" }; addAll(strings, moreStrings); is the same as listing the elements.

  • The elements are not really spread: the converse holds. Individually listed arguments are gathered into an array; a supplied array is passed directly.

  • Primitive arrays do not spread: Collection<Integer> numbers = ...; int[] moreNumbers = { 11, 12, 13, 14, 15 }; addAll(numbers, moreNumbers); is an error (no valid E; an int[] is not an Integer[]).

  • Insidious case:

    • List.of(E... elements)
    • List.of(moreStrings) gives a list of 5 elements, but List.of(moreNumbers) gives a List<int[]> with a single element (the whole array), because E cannot match int and instead matches the array type int[].

8.5.6 You cannot instantiate type variables

  • new T(...) is illegal: <T> Pair<T> makePair() { return new Pair<T>(new T(), new T()); } (erasure would make it new Object()).
  • Modern workaround: let the caller supply a constructor expression via a Supplier<T>:
<T> Pair<T> makePair(Supplier<T> constr)
{
    return new Pair<>(constr.get(), constr.get());
}

Pair<String> p = makePair(String::new);
  • Reflection workaround: you cannot write T.class.getConstructor().newInstance() (T.class would erase to Object.class); the API must receive a Class object:
<T> Pair<T> makePair(Class<T> cl) throws ReflectiveOperationException
{
    Constructor<T> constr = cl.getConstructor();
    return new Pair<>(constr.newInstance(), constr.newInstance());
}

Pair<String> p = Pair.makePair(String.class);
  • It throws ReflectiveOperationException because the class may lack a no-argument constructor
    • Class is generic: String.class is the sole instance of Class<String>, so the method infers Pair<String>.
  • Varargs workaround
    • (confusing API): a varargs parameter that exists only to give the component type: <T> Pair<T> makePair(T... dummy), called as Pair<String> names = makePair(); (an empty String[] supplies the type)
    • Users must be told to call it with no arguments.

8.5.7 You cannot construct a generic array

  • T[] mm = new T[2]; is an error: an array carries a type used for store checks, and that type is erased (it would always build Comparable[2]).
  • If the array is only a private field, declare the erased element type and cast on reads:
public class ArrayList<E>
{
    private Object[] elements;
    // ...
    @SuppressWarnings("unchecked")
    public E get(int n)
    {
        return (E) elements[n];
    }

    public void set(int n, E e)
    {
        elements[n] = e; // no cast needed
    }
}
  • That does not work when returning a T[]: var result = new Comparable[2]; return (T[]) result; compiles with a warning, and String[] names = minmax("Tom", "Dick", "Harry"); compiles with none, but throws ClassCastException after the call.
  • Best fix: ask for an array constructor expression: String[] names = minmax(String[]::new, "Tom", "Dick", "Harry"); with
<T extends Comparable> T[] minmax(IntFunction<T[]> constr, T... a)
{
    T[] result = constr.apply(2);
    // ...
    return result;
}
  • Old-fashioned: var result = (T[]) Array.newInstance(a.getClass().getComponentType(), 2);.
  • ArrayList.toArray lacks the component type, so it has two variants: Object[] toArray() and T[] toArray(T[] result) (uses the array if large enough, otherwise builds a new one of the same component type).

8.5.8 Type variables are not valid in static contexts of generic classes

  • No static fields or methods using the class's type variable:
public class Singleton<T>
{
    private static T singleInstance; // ERROR

    public static T getSingleInstance() // ERROR
    {
        // construct a new instance of T if null
        return singleInstance;
    }
}
  • It could never work: after erasure there is one Singleton class and one singleInstance field, not one per Singleton<Random> or Singleton<JFileChooser>.

8.5.9 You can defeat checked exception checking

  • A bedrock rule is that checked exceptions need handlers, but generics can defeat it:
class Sneaky
{
    @SuppressWarnings("unchecked")
    static <T extends Throwable> void throwAs(Throwable t) throws T
    {
        throw (T) t;
    }
}
  • Sneaky.<RuntimeException>throwAs(e); makes the compiler believe e becomes unchecked, but it stays checked: the cast (T) t does nothing at run time
    • A plain throw (RuntimeException) t; would fail with ClassCastException.
  • Use: Runnable.run cannot throw checked exceptions. An adapter lets a task throw anything:
class Sneaky
{
    interface Runnable
    {
        void run() throws Exception;
    }

    static java.lang.Runnable asRunnable(Sneaky.Runnable task)
    {
        return () ->
        {
            try
            {
                task.run();
            }
            catch (Exception e)
            {
                Sneaky.<RuntimeException>throwAs(e);
            }
        };
    }
}
  • The demo thread sleeps (Thread.sleep throws InterruptedException, no catch needed), prints "Hello, World!" and throws new Exception("Check this out!"), which appears as a stack trace.
  • Remarkable:
    • no wrapping into an unchecked exception
    • the checked exception is simply rethrown. "Using generic classes and erasure, we were able to defeat an essential part of the Java type system."

8.5.10 Beware of clashes after erasure

  • Method clash: public boolean equals(T value) in Pair<T>: its erasure equals(Object) clashes with Object.equals. Rename the method.
  • Interface rule from the generics spec: a class or type variable may not be a subtype of two different parameterisations of the same interface:
class Employee implements Comparable<Employee> { /* ... */ }
class Manager extends Employee implements Comparable<Manager> { /* ... */ } // ERROR
  • The non-generic version (raw Comparable twice) is legal
    • The reason is synthesised bridge methods: Comparable<X> gets a bridge public int compareTo(Object other) { return compareTo((X) other); }, and you cannot have two such methods for different X.

8.5.11 Type inference in generic record patterns is limited

  • A generic record record Pair<T>(T first, T second) {} works in patterns, with the type argument inferred:
var p = new Pair<String>("Hello", "World");
String content = switch (p)
{
    case Pair(var a, var b) -> a + " " + b.toUpperCase();
};
  • Explicit forms: case Pair<String>(var a, var b), case Pair(String a, String b), case Pair<String>(String a, String b).
  • Exhaustiveness with generics needs work from the compiler. With a sealed hierarchy:
sealed interface JSONPrimitive<T> {}
record JSONNumber(double value) implements JSONPrimitive<Double> {}
record JSONBoolean(boolean value) implements JSONPrimitive<Boolean> {}
record JSONString(String value) implements JSONPrimitive<String> {}

<T> double toNumber(JSONPrimitive<T> v)
{
    return switch (v)
    {
        case JSONNumber(var n) -> n;
        case JSONBoolean(var b) -> b ? 1 : 0;
        case JSONString(var s) ->
        {
            try
            {
                yield Double.parseDouble(s);
            }
            catch (NumberFormatException ex)
            {
                yield Double.NaN;
            }
        }
    };
}
  • It is exhaustive: the compiler knows there are only three implementors.
  • Summing a pair of primitives with Pair<? extends JSONPrimitive<?>> is not exhaustive: sum(Pair.of(new JSONNumber(42), new JSONString("Fred"))) is possible
    • You could add the other six combinations throwing exceptions, but that is a run-time check
    • To accept only homogeneous pairs at compile time:
<T extends JSONPrimitive<U>, U> Object sum(Pair<T> pair)
{
    return switch (pair)
    {
        case Pair(JSONNumber(var left), JSONNumber(var right)) -> left + right;
        case Pair(JSONBoolean(var left), JSONBoolean(var right)) -> left | right;
        case Pair(JSONString(var left), JSONString(var right)) -> left.concat(right);
        default -> throw new AssertionError(); // Java cannot tell this will not happen
    };
}
  • The mixed call no longer compiles, but the default is still required: the type system cannot prove the components share a type
    • Explicit type arguments (case Pair<JSONNumber>(JSONNumber(var left), ...)) fail with "unsafe casts" because the compiler cannot prove the cast from Pair<T> to Pair<JSONNumber> safe.

8.6 Reflection and generics

  • Reflection on generic objects shows little about type parameters (erased), but the declarations themselves survive in some places.

8.6.1 The generic Class class

  • String.class is the sole object of Class<String>
    • The parameter makes Class<T> methods more precise: T cast(Object obj), T[] getEnumConstants(), Class<? super T> getSuperclass(), Constructor<T> getConstructor(Class<?>... parameterTypes), Constructor<T> getDeclaredConstructor(...).
  • getConstructor returns Constructor<T>, so no cast is needed: Class<T> cl = ...; T noArgInstance = cl.getConstructor().newInstance();.
  • cast returns the object typed as T if it is a subtype, else throws ClassCastException; getEnumConstants returns null if the class is not an enum.

java.lang.Class<T> (1.0): T cast(Object obj) (null passes), T[] getEnumConstants() (5.0), Class<? super T> getSuperclass(), Constructor<T> getConstructor(Class... parameterTypes) and getDeclaredConstructor(...) (1.1).

8.6.2 Using Class<T> parameters for type matching

public static <T> Pair<T> makePair(Class<T> c) throws ReflectiveOperationException
{
    Constructor<T> constr = c.getConstructor();
    return new Pair<>(constr.newInstance(), constr.newInstance());
}
  • makePair(String.class): String.class is a Class<String>, so T matches String and the result is a Pair<String>.

8.6.3 Generic type information in the virtual machine

  • Erased classes keep a faint memory of their generic origin: raw Pair knows it came from Pair<T> (but an object cannot tell whether it was a Pair<String> or a Pair<Employee>)
    • For Comparable min(Comparable[] a) erased from <T extends Comparable<? super T>> T min(T[] a), reflection can show the type parameter T, its generic bound, the wildcard, the wildcard's supertype bound and the generic array parameter
    • Everything the implementor declared can be reconstructed, but not how parameters were resolved for a call or object.
  • The java.lang.reflect.Type interface expresses declarations. Its subtypes:
    • Class: concrete types
    • TypeVariable: T extends Comparable<? super T>
    • WildcardType: ? super T
    • ParameterizedType: Comparable<? super T>
    • GenericArrayType: T[]
  • The last four are interfaces (the VM supplies implementing classes).

  • Listings 8.4 and 8.5 (GenericReflectionDemo and Printer) print what reflection finds
    • For Pair the report is class com.horstmann.corejava.Pair<T> extends java.lang.Object followed by public T getFirst(), public T getSecond(), public void setFirst(T), public void setSecond(T)
    • For java.util.Collections it shows signatures such as public static <T extends java.lang.Object & java.lang.Comparable<? super T>> T min(java.util.Collection<? extends T>).
  • Printer.printType is a chain of instanceof patterns over Class<?>, TypeVariable<?>, WildcardType, ParameterizedType and GenericArrayType, printing bounds with getBounds, getUpperBounds, getLowerBounds, getActualTypeArguments, getRawType.

8.6.4 Type literals

  • To drive behaviour by a generic type (a persistence mechanism saving ArrayList<Integer> differently from ArrayList<String>), erasure is a problem since both are raw ArrayList
    • A type literal captures a Type via an anonymous subclass:
var type = new TypeLiteral<ArrayList<Integer>>() { }; // note the {}

class TypeLiteral<T>
{
    private Type type;

    public TypeLiteral()
    {
        Type parentType = getClass().getGenericSuperclass();
        if (parentType instanceof ParameterizedType paramType)
        {
            type = paramType.getActualTypeArguments()[0];
        } else {
            throw new UnsupportedOperationException("Construct as new TypeLiteral<...>(){}");
        }
    }
}
  • The generic superclass of the anonymous subclass survives in the VM
    • You cannot get a generic type from an object (erased), but the generic types of fields and method parameters survive
    • Injection frameworks like CDI and Guice use type literals to inject generic types.
  • Listing 8.6 (TypeLiterals.java): a Formatter keeps Map<TypeLiteral<?>, Function<?, String>> rules, then formatFields(obj) walks the object's fields, looks up each field's getGenericType() and applies the matching rule: an ArrayList<Integer> is joined with spaces, an ArrayList<Character> is joined into a quoted string, other lists use toString
    • For the sample (nums 42 and 1729, chars 'H' and 'i', strings "Hello" and "World") the result is nums=42 1729, chars="Hi", strings=[Hello, World].

java.lang.Class<T> (generic reflection): TypeVariable[] getTypeParameters() (5.0), Type getGenericSuperclass() (5.0), Type[] getGenericInterfaces() (5.0). java.lang.reflect.Method (1.1): getTypeParameters(), Type getGenericReturnType(), Type[] getGenericParameterTypes().

TypeVariable (5.0): getName(), Type[] getBounds(). WildcardType (5.0): Type[] getUpperBounds(), Type[] getLowerBounds(). ParameterizedType (5.0): Type getRawType(), Type[] getActualTypeArguments(), Type getOwnerType() (null for top-level).

GenericArrayType (5.0): Type getGenericComponentType().

  • You now know how to use generics, write your own, and, importantly, decipher generic declarations in the API docs and error messages.

Summary points

  • Type parameters make code safer and cleaner; generic classes and methods can have bounds (extends, &).
  • Erasure: no generics in the VM, bounds replace type variables, casts and bridge methods are added.
  • No subtype relation between different parameterisations; use ? extends to read and ? super to write; capture wildcards with helper methods.
  • Restrictions: no primitives as type arguments, no new T, no new T[], no instanceof with parameterised types, no static type variables, no generic exceptions, no arrays of parameterised types, beware of erasure clashes.
  • Work-arounds: Supplier<T>, Class<T>, IntFunction<T[]>, @SafeVarargs, type literals.
Terms to carry forward
  • Type variable, type parameter, diamond: T, <T>, <>.
  • Bound (extends, &): restricting a type variable.
  • Raw type, type erasure: the generic type without parameters.
  • Bridge method: compiler-made method preserving polymorphism.
  • Wildcard (?, ? extends, ? super), wildcard capture: flexible generic types.
  • Unchecked warning, @SuppressWarnings, @SafeVarargs: managing generics warnings.
  • Heap pollution: a variable pointing to an object of the wrong generic type.
  • Type, TypeVariable, ParameterizedType: reflection of generic declarations.
  • Type literal: capturing a generic type with an anonymous subclass.
