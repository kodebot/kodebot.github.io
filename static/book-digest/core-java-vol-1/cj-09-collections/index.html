Core Java 9: Collections

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 9. Previous: Core Java 8: Generic Programming. Next: Core Java 10: Concurrency.

Takeaways
  • The Java Collections Framework separates interfaces from implementations: hold the reference in an interface type (Queue, List, Set, Map) and name the concrete class only at construction.
  • Two roots: Collection (add, iterator) and Map (put, get). A List is ordered with index access, a Set rejects duplicates, a Queue or Deque is for first-in first-out or both ends.
  • Iterators sit between elements; next returns and passes over an element; remove removes the last returned element and cannot be called twice in a row.
  • Pick the structure by cost: ArrayList (fast index access), LinkedList (cheap insert and remove through an iterator, never use indexes), HashSet/HashMap (fast lookup, no order), TreeSet/TreeMap (sorted), ArrayDeque, PriorityQueue.
  • Changing a collection while another iterator reads it throws ConcurrentModificationException.

9.1 The Java Collections Framework

  • The original Java shipped only Vector, Stack, Hashtable, BitSet and the Enumeration interface: wise, because a comprehensive library takes time and skill
    • Java 1.2 added a full framework, balancing: small and easy to learn, without the complexity of C++'s STL yet with the benefit of generic algorithms, and fitting the legacy classes
    • It has some idiosyncratic decisions.

9.1.1 Separating collection interfaces and implementation

  • A queue interface lets you add at the tail, remove at the head and ask the size ("first in, first out"):
public interface Queue<E> // a simplified form of the interface in the Java API
{
    void add(E e);
    E remove();
    int size();
}
  • Two common implementations: a circular array (ArrayDeque) and a linked list (LinkedList), each a class implementing Queue.
  • Use the concrete class only when constructing; hold the reference as the interface type:
Queue<Customer> expressLane = new ArrayDeque<>(100);
expressLane.add(new Customer("Harry"));

// change your mind in one place
Queue<Customer> expressLane2 = new LinkedList<>();
  • Another reason: both classes have non-queue methods, and using one by accident is a compile error through a Queue variable.
  • The interface says nothing about efficiency
    • A circular array is more memory-efficient but has finite capacity and reallocates; measurements show ArrayDeque generally beats LinkedList (less impact on the garbage collector)
    • When ArrayDeque appeared in Java 6, code using Queue swapped by changing one line.

9.1.2 The Collection interface

  • The root interface has two fundamental methods:
public interface Collection<E>
{
    boolean add(E element);
    Iterator<E> iterator();
    // ...
}
  • add returns true if the collection changed, false otherwise (adding a duplicate to a set has no effect). iterator returns an object to visit the elements.

9.1.3 Iterators

public interface Iterator<E>
{
    boolean hasNext();
    E next();
    default void remove();
    default void forEachRemaining(Consumer<? super E> action);
}
  • Call hasNext before next; at the end next throws NoSuchElementException.
Collection<String> coll = new ArrayList<>(); // ...
Iterator<String> iter = coll.iterator();
while (iter.hasNext())
{
    String element = iter.next();
    // do something with element
}
  • The "for each" loop is the compiler's translation into this iterator loop and works for any Iterable (an interface with Iterator<E> iterator())
    • Collection extends Iterable.
  • Instead of a loop: coll.forEach(element -> ...) or iter.forEachRemaining(element -> ...).
  • Order depends on the collection:
    • ArrayList goes from index 0
    • a HashSet gives an essentially random order. All elements are visited, but assume nothing about order (fine for totals or counting).
  • The designers did not reuse Enumeration (nextElement, hasMoreElements) because they disliked the cumbersome names.
  • Conceptual difference from C++ STL:
    • STL iterators are modelled on array indexes (look up and advance separately)
    • Java iterators sit between elements: next jumps over the next element and returns it; lookup and advance are coupled
    • Analogy: Iterator.next is like InputStream.read, consuming what it returns.

  • remove removes the element last returned by next.
    • To remove the first element: iter.next(); iter.remove();
    • Calling remove without a preceding next throws IllegalStateException, so two adjacent removals need a next between them:
iter.remove();
iter.next();
iter.remove(); // OK
// iter.remove(); iter.remove();  // ERROR

9.1.4 Generic utility methods

  • Interfaces are generic, so you can write methods for any collection:
public static <E> boolean contains(Collection<E> c, Object obj)
{
    for (E element : c)
    {
        if (element.equals(obj))
        {
            return true;
        }
    }
    return false;
}
  • Collection<E> already declares: int size(), boolean isEmpty(), boolean contains(Object), boolean containsAll(Collection<?>), boolean add(E), boolean addAll(Collection<? extends E>), boolean remove(Object), boolean removeAll(Collection<?>), boolean retainAll(Collection<?>), void clear(), Object[] toArray(), T[] toArray(T[] a).
  • It redeclares equals and hashCode only as a place for documentation. Set and List mandate specific equals behaviour
    • others inherit Object.equals or compare elements (then hashCode must be overridden too).
  • Pre-generics compatibility: contains and remove take an Object, and containsAll, removeAll, retainAll take Collection<?>, so type errors may go undetected: Collection<Path> paths = ...; paths.remove("/tmp"); compiles but can have no effect.
  • AbstractCollection
    • leaves size and iterator abstract and implements the routine methods in terms of them (isEmpty is size() == 0, contains loops through the iterator)
    • concrete classes extend it and may override for speed. A bit outdated, since default methods did not exist then
    • some were added: three for streams (Volume II), toArray (section 9.6.6) and default boolean removeIf(Predicate<? super E> filter).

java.util.Collection<E> (1.2): iterator(), size(), isEmpty(), contains(Object), containsAll(Collection<?>), add(E) (true if changed), addAll(Collection<? extends E>), remove(Object), removeAll(Collection<?>), removeIf(Predicate<? super E>) (8), clear(), retainAll(Collection<?>), Object[] toArray(), <T> T[] toArray(IntFunction<T[]> generator) (11; typically T[]::new).

java.util.Iterator<E> (1.2): hasNext(), next(), remove() (must follow a visit; throws IllegalStateException if the collection was modified since; may throw UnsupportedOperationException by default), forEachRemaining(Consumer<? super E>) (8).

9.2 Interfaces in the Collections Framework

  • Two fundamental interfaces: Collection (insert with boolean add(E element), read with an iterator) and Map (key/value pairs: V put(K key, V value) and V get(Object key)).
  • A List is ordered: elements are added at a position and reached by an iterator (sequential) or an integer index (random access):
void add(int index, E element)
E remove(int index)
E get(int index)
E set(int index, E element)
  • Trap with List<Integer>: two remove methods, remove(int index) and remove(Integer o). A parameter of type int picks the index version with no boxing and no warning:
List<Integer> ids = new ArrayList<>();
int id = 0;
if (id == 0)
{
    ids.remove(id); // removes index 0, not the element with value 0
}
  • List.equals: the other object must be a list of the same size with equal corresponding elements.
  • A design flaw:
    • two ordered collections with different trade-offs (array-backed has fast random access; linked has slow), so ideally two interfaces
    • Java 1.4 added the tagging interface RandomAccess (no methods) to test: if (c instanceof RandomAccess) { /* random traversal */ } else { /* sequential traversal */ }.
  • Set
    • has the same methods as Collection but tighter behaviour: add rejects duplicates
    • equals means the same elements in any order
    • hashCode matches
      • A separate interface lets methods accept only sets and means equals can check the argument is a Set, not just any Collection
      • Lists are equal with the same elements in the same order.
  • SortedSet and SortedMap
    • expose the comparator and subset views (section 9.5.3). NavigableSet and NavigableMap add finding the next or previous element
    • TreeSet and TreeMap implement them (efficient in trees).
  • Java 21 SequencedCollection<E>
    • gives uniform access to first and last elements and reverse traversal: getFirst(), getLast(), addFirst(e), addLast(e), removeFirst(), removeLast(), reversed()
    • Before, lists, sets and deques each had different methods
    • SequencedSet returns SequencedSet from reversed; SequencedMap has analogous methods.

9.3.1 Linked lists

  • Removing or inserting in the middle of an array is expensive (everything beyond moves)
    • A linked list stores each object in a separate link holding a reference to the next; in Java all linked lists are doubly linked (each link also points to its predecessor)
    • Removing in the middle updates only the neighbouring links.

var staff = new LinkedList<String>();
staff.add("Amy");
staff.add("Bob");
staff.add("Carl");
Iterator<String> iter = staff.iterator();
String first = iter.next();  // Amy
String second = iter.next(); // Bob
iter.remove();               // removes the last visited element (Bob)
  • A linked list is ordered by position, but add appends to the end
    • Position-dependent add is the job of an iterator (it describes positions), only meaningful for ordered collections, so Iterator has no add
    • The subinterface ListIterator adds it:
interface ListIterator<E> extends Iterator<E>
{
    void add(E element); // no boolean: it always modifies the list
    boolean hasPrevious();
    E previous();
    // ...
}
  • previous returns the object it skipped, like next
    • Get one with staff.listIterator()
    • add inserts before the iterator position: skipping the first element and adding "Juliet" puts her before Bob.
ListIterator<String> iter = staff.listIterator();
iter.next(); // skip past first element
iter.add("Juliet");
  • Several add calls go in order before the iterator position
    • A fresh iterator makes the new element the first; past the last element it becomes the tail
    • With n elements there are n + 1 insertion spots, for three elements: |ABC, A|BC, AB|C, ABC|.
  • remove is not the Backspace key:
    • right after next it removes the element on the left, but right after previous it removes the one on the right, and you cannot call it twice in a row. add depends only on position
    • remove depends on iterator state.
  • set replaces the last element returned by next or previous: String oldValue = iter.next(); iter.set(newValue);.
  • ConcurrentModificationException: an iterator detects when its collection was modified by another iterator or a collection method:
List<String> list = new LinkedList<>(); // ...
ListIterator<String> iter1 = list.listIterator();
ListIterator<String> iter2 = list.listIterator();
iter1.next();
iter1.remove();
iter2.next(); // throws ConcurrentModificationException
  • Rule: attach as many iterators as you like if all are readers, or one that both reads and writes.
  • How:
    • the collection counts mutating (structural) operations
    • each iterator keeps its own count and compares at the start of each method. Exception: set is not a structural modification, so several iterators may call set (needed by algorithms in Collections).
  • Other Collection methods come from AbstractCollection: toString gives [A, B, C] (handy for debugging), contains("Harry") checks presence.
  • Linked lists do not support fast random access,
    • yet LinkedList.get(n) exists (starting from the end if n >= size() / 2)
    • Never step through a linked list with get(i): for (int i = 0; i < list.size(); i++) ... list.get(i) is "staggeringly inefficient" (each lookup restarts, nothing is cached)
    • If you use get, you probably chose the wrong structure.
  • nextIndex() and previousIndex() (one less) are efficient for LinkedList iterators; list.listIterator(n) returns an iterator just before index n but is inefficient.
  • The only reason to use a linked list is cheap insertion and removal in the middle
    • For a handful of elements just use an ArrayList
    • Stay away from all index-based methods on linked lists; for random access use an array or ArrayList.
  • Listing 9.1 (LinkedListDemo.java) merges two lists with iterators, removes every second element of one, and tests removeAll
    • tracing it with iterator-position diagrams like |ACE |BDFG helps. It prints the merged list [Amy, Bob, Carl, Doug, Erica, Frances, Gloria], then the second list after removals [Bob, Frances], then a.removeAll(b) leaves [Amy, Carl, Doug, Erica, Gloria].
// merge the elements from b into a
ListIterator<String> aIter = a.listIterator();
Iterator<String> bIter = b.iterator();

while (bIter.hasNext())
{
    if (aIter.hasNext())
    {
        aIter.next();
    }
    aIter.add(bIter.next());
}

9.3.2 Array lists

  • List offers sequential (iterator) and random access (get, set); the latter suits arrays, not linked lists. ArrayList wraps a dynamically reallocated array.
  • Vector
    • (Java 1.0) is similar but all its methods are synchronised, wasteful when used from one thread (the common case)
    • ArrayList methods are not synchronised, and chapter 10 has better thread-safe choices. No reason to use Vector except for ancient APIs.

9.3.3 Hash sets

  • With a list you must visit elements to find one. If you do not care about order, a hash table finds elements fast, but you give up control of order.
  • A hash table computes an integer hash code for each object from its instance fields, ideally differing for different data
    • Examples (Table 9.2): "Lee" is 76268, "lee" is 107020, "eel" is 100300
    • For your own classes you implement hashCode (chapter 5) compatible with equals
    • It must be fast and depend only on the object's own state.
  • In Java a hash table is an array of linked lists called buckets
    • The bucket index is the hash code modulo the number of buckets: hash code 76268 with 128 buckets goes to bucket 108 (76268 % 128)
    • An occupied bucket is a hash collision: compare the new object with those already in the bucket
    • With a random spread and enough buckets few comparisons are needed.

  • In HashMap, a bucket turns into a balanced binary tree when it exceeds a threshold, protecting performance against poor hash functions or malicious inputs flooding with identical hash codes
    • Prefer keys that implement Comparable so poorly distributed hash codes cannot hurt.
  • Rehashing: when too full, a bigger table is built and all elements reinserted. The load factor (default 0.75) decides: above 75% full, double the buckets. Usually leave it.
  • Set the initial bucket count to expected elements divided by the load factor, or since Java 19 use HashSet<String> strings = HashSet.newHashSet(expectedElementCount);
    • Bucket counts are powers of 2 (default 16; supplied values round up), though some researchers favour primes.
  • A set is a collection without duplicates; HashSet.add first looks for the object and adds only if absent, and contains checks one bucket only
    • Its iterator visits buckets in turn, so order looks random
    • Use it only when order does not matter.
  • Listing 9.2 (SetDemo.java) reads words and compares HashSet with TreeSet: e.g
    • java v1ch09.set.SetDemo gutenberg/alice30.txt
    • Alice in Wonderland has 28,195 words, 5,909 unique, appearing in random order in the hash set.
  • Do not mutate set elements in a way that changes their hash code: the element ends up in the wrong bucket.
var rects = new HashSet<Rectangle>();
var rect = new Rectangle(5, 10, 20, 30);
rects.add(rect);
rect.setLocation(0, 0);
// rects is now [java.awt.Rectangle[x=0,y=0,width=20,height=30]]
rects.remove(new Rectangle(0, 0, 20, 30)); // returns false: not found, not removed

java.util.HashSet<E> (1.2): HashSet(), HashSet(Collection<? extends E>), HashSet(int initialCapacity), HashSet(int initialCapacity, float loadFactor) (rehashed when size/capacity exceeds the load factor), static <E> HashSet<E> newHashSet(int numMappings) (19). Object.hashCode (1.0): equal objects must return identical hash codes.

9.3.4 Tree sets

  • A TreeSet is a sorted collection:
    • insert in any order, iterate in sorted order
    • Sorting is by a tree (red-black tree in the current implementation; see Cormen, Leiserson, Rivest and Stein, Introduction to Algorithms, MIT Press, 2022)
    • Every added element lands in its sorted position, so the iterator always visits in order.
var sorter = new TreeSet<String>();
sorter.add("Bob");
sorter.add("Amy");
sorter.add("Carl");
for (String s : sorter)
{
    IO.println(s); // Amy, Bob, Carl
}
  • Adding to a tree is slower than to a hash table but much faster than checking duplicates in an array or list: about log2 n comparisons (about 10 for 1,000 elements).
  • Elements must be comparable: implement Comparable or supply a Comparator at construction.
  • Cost:
    • running SetDemo on The Count of Monte Cristo (466,300 words, each inserted 100 times), the TreeSet was almost 4 times slower
    • Without a need for sorting, do not pay for it
    • Also a comparison function must tell objects apart with complete precision, whereas a hash function only needs to scramble reasonably.
  • Example:
    • a set of rectangles with a Comparator<Rectangle>
    • Comparing by area fails (different rectangles can share an area and you want both)
    • The comparator must be compatible with equals: zero only for equal elements
    • A valid order exists (lexicographic on coordinates) but is cumbersome; the hash function is already defined.
  • Incompatible comparators break set equality.
    • var commands = new TreeSet<String>(String.CASE_INSENSITIVE_ORDER); then commands.add("QUIT"); commands.add("quit"); // not added, but now equals is not symmetric: commands.equals(Set.of("quit")) is true while Set.of("quit").equals(commands) is false (the tree set uses the comparator, the other uses String.equals)
    • Better: use the natural order and only insert lowercase strings.
  • TreeSet implements NavigableSet (adjacent-element methods).
  • Listing 9.3 (TreeSetDemo.java): Item is a record implementing Comparable<Item> by partNumber. One tree set sorts by part number (Toaster 1234, Widget 4562, Router 9912)
    • a second uses new TreeSet<Item>(Comparator.comparing(Item::description)), giving Router, Toaster, Widget.

java.util.TreeSet<E> (1.2): TreeSet(), TreeSet(Comparator<? super E>), TreeSet(Collection<? extends E>), TreeSet(SortedSet<E>) (same ordering). java.util.SortedSet<E> (1.2): Comparator<? super E> comparator() (null if natural order), first(), last().

java.util.NavigableSet<E> (6): higher(value) and lower(value) (strictly greater or less, or null), ceiling(value) and floor(value) (greater or equal, less or equal), pollFirst() and pollLast() (remove and return smallest or largest, null if empty).

9.3.5 Queues and deques

  • A queue adds at the tail and removes from the head efficiently
    • A deque (double-ended queue) adds and removes at both ends, not in the middle
    • Deque is implemented by ArrayDeque and LinkedList, both growing as needed (bounded queues are in chapter 10).
  • In Java 21 getFirst, getLast, addFirst, addLast, removeFirst, removeLast moved from Deque to SequencedCollection, which List and Set also extend.
Operation Throws on failure Returns special value
add at tail add (IllegalStateException if full) offer (false if full)
remove head remove (NoSuchElementException if empty) poll (null if empty)
look at head element (NoSuchElementException) peek (null)

Queue<E> (5.0) has add, offer, remove, poll, element, peek as in the table. SequencedCollection<E> (21): addFirst, addLast (IllegalStateException if full), removeFirst, removeLast, getFirst, getLast (all NoSuchElementException if empty).

Deque<E> (6): offerFirst, offerLast (false if full), pollFirst, pollLast, peekFirst, peekLast (null if empty). ArrayDeque<E> (6): ArrayDeque(), ArrayDeque(int initialCapacity) (unbounded, default capacity 16).

9.3.6 Priority queues

  • A priority queue retrieves elements in sorted order after arbitrary insertion: remove returns the smallest current element
    • It does not keep everything sorted, so iteration is not in sorted order.
  • It uses a heap:
    • a self-organising binary tree where add and remove make the smallest element gravitate to the root without sorting everything
    • Like TreeSet, elements are Comparable or you pass a Comparator.
  • Typical use: job scheduling (priority 1 is "highest", so remove yields the minimum).
  • Listing 9.4 (PriorityQueueDemo.java): adds four birthdays (Hopper 1906, Lovelace 1815, von Neumann 1903, Zuse 1910)
    • iterating shows an unsorted heap order, while repeated remove yields 1815-12-10, 1903-12-03, 1906-12-09, 1910-06-22.

java.util.PriorityQueue (5.0): PriorityQueue(), PriorityQueue(int initialCapacity), PriorityQueue(int initialCapacity, Comparator<? super E> c).

9.4 Maps

  • A set finds an element only if you already have an exact copy
    • Usually you have key information and want the associated element: a map stores key/value pairs (employee ID to Employee).

9.4.1 Basic map operations

  • Two general-purpose implementations, HashMap and TreeMap. Hashing and comparison apply to keys only, not values. Hashing is usually a bit faster
    • prefer it unless you need keys sorted.
var staff = new HashMap<String, Employee>(); // HashMap implements Map
var harry = new Employee("Harry Hacker");
staff.put("987-98-9996", harry);

var id = "987-98-9996";
Employee e = staff.get(id); // gets harry
  • get takes an Object
    • for historical reasons: long numericId = ...; staff.get(numericId); compiles but never finds anything. Missing key returns null
    • use getOrDefault: int score = scores.getOrDefault(id, 0);.
  • Keys are unique: a second put with the same key replaces the value and returns the old value. remove removes by key; size counts entries.
  • Easiest iteration: forEach with a lambda over key and value: scores.forEach((k, v) -> IO.println("key=" + k + ", value=" + v));.
  • Listing 9.5 (MapDemo.java): a HashMap<String, LocalDate> of birthdays: print all, remove Konrad Zuse, replace Ada Lovelace's date (1815-12-10), look up, iterate with forEach
    • (The book's first put of Ada Lovelace uses 1915, later corrected to 1815.)

java.util.Map<K, V> (1.2): V get(Object key) (null if absent; may forbid null keys), default V getOrDefault(Object key, V defaultValue), V put(K, V) (returns the old value or null), void putAll(Map<? extends K, ? extends V>), boolean containsKey(Object), containsValue(Object), default void forEach(BiConsumer<? super K, ? super V>) (8).

9.4.2 Updating map entries

  • The tricky part is the first occurrence of a key. counts.put(word, counts.get(word) + 1); throws NullPointerException the first time. Remedies:
    • counts.put(word, counts.getOrDefault(word, 0) + 1);
    • counts.putIfAbsent(word, 0); counts.put(word, counts.get(word) + 1);
    • best, merge: counts.merge(word, 1, Integer::sum); (associates the word with 1 if absent, else combines the old value and 1)
  • A set per key (a book index): computeIfAbsent builds the TreeSet only when missing and returns the value so you can chain:
var index = new TreeMap<String, TreeSet<Integer>>();
index.computeIfAbsent(term, _ -> new TreeSet<>()).add(pageNumber);
  • putIfAbsent returns the previous value or null, not useful for chaining.
  • Do not use TreeSet::new
    • here: the function gets the key k as an argument
    • with Map<Integer, ArrayList<String>>, map.computeIfAbsent(n, ArrayList::new) calls ArrayList(int capacity), allocating huge lists for large n.
  • Null handling is inconsistent: getOrDefault treats a null value as a real value (counts.put("C++", null); counts.getOrDefault("C++", -1) yields null), but putIfAbsent treats null as absent (counts.putIfAbsent("C++", 1) puts 1).

java.util.Map<K, V> update methods (8): merge(key, value, remappingFunction) (non-null old value: apply function to old and value; a null result removes the key; otherwise associate value), compute(key, remappingFunction), computeIfPresent(key, remappingFunction), computeIfAbsent(key, mappingFunction), replaceAll(function) (a null result removes the key), putIfAbsent(key, value) (returns null if it was absent or null).

9.4.3 Map views

  • A map is not a collection in Java, but it gives views (objects implementing Collection or a subinterface): Set<K> keySet()
    • Collection<V> values() (not a set)
    • Set<Map.Entry<K, V>> entrySet(). They are backed by the map; keySet is not a HashSet or TreeSet.
for (Map.Entry<String, Integer> entry : counts.entrySet())
{
    String k = entry.getKey();
    Integer v = entry.getValue();
    entry.setValue(v + 1); // same as counts.put(k, v + 1)
}
  • Map.Entry objects are live: setValue updates the map, and map changes are reflected
    • To detach, use Map.Entry.copyOf(entry); create standalone pairs with Map.entry(key, value) (Java has no Pair class)
    • Shorten with var (for (var entry : map.entrySet())) or map.forEach((k, v) -> { ... }).
  • Removing through the key-set iterator removes the key and its value
    • you cannot add to the key set or entry set view (UnsupportedOperationException): adding a key without a value makes no sense.

java.util.Map (1.2): Set<Map.Entry<K, V>> entrySet(), Set<K> keySet(), Collection<V> values() (elements may be removed, not added). Map.Entry<K, V> (1.2): getKey(), getValue(), V setValue(V) (returns old), static copyOf(entry) (17; not live).

9.4.4 Weak hash maps

  • If the last reference to a key vanishes, the value is unreachable, yet the pair stays because the map keeps its buckets alive
    • The garbage collector cannot remove it
    • Remove unused values yourself from long-lived maps, or use WeakHashMap, which removes entries when the only reference to the key is the map's own.
  • How:
    • it holds keys by WeakReference. The GC reclaims an object reachable only through weak references but puts the weak reference into a queue
    • the map checks that queue periodically and removes the matching entries.

9.4.5 Linked hash sets and maps

  • LinkedHashSet and LinkedHashMap remember insertion order by joining entries in a doubly linked list (avoiding a hash table's random order): with four puts, keySet().iterator() and values().iterator() list them in insertion order (the book's example: Amy Lee, Harry Hacker, Gary Cooper, Francesca Cruz).
  • Access order:
    • construct LinkedHashMap<K, V>(initialCapacity, loadFactor, true)
    • Each get or put moves the entry to the end of the list (the bucket does not change), so the first entries are least recently used: the basis of an LRU cache.
  • Automate eviction by overriding protected boolean removeEldestEntry(Map.Entry<K, V> eldest) (called after adding; return true to remove the eldest):
var cache = new LinkedHashMap<K, V>(128, 0.75F, true)
{
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest)
    {
        return size() > 100; // keep at most 100 elements
    }
};
  • You can inspect eldest (for example a timestamp). It runs only once per new entry, so it does not clear all old ones
    • you may modify the map inside it, but then return false. For an LRU set, see 9.5.4.

9.4.6 Enumeration sets and maps

  • EnumSet is a set of enum values stored as a sequence of bits. It has no public constructors; use factories:
enum Weekday { MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY, SATURDAY, SUNDAY };
EnumSet<Weekday> always = EnumSet.allOf(Weekday.class);
EnumSet<Weekday> never = EnumSet.noneOf(Weekday.class);
EnumSet<Weekday> workday = EnumSet.range(Weekday.MONDAY, Weekday.FRIDAY);
EnumSet<Weekday> mwf = EnumSet.of(Weekday.MONDAY, Weekday.WEDNESDAY, Weekday.FRIDAY);
  • EnumMap has enum keys, implemented as an array of values: var personInCharge = new EnumMap<Weekday, Employee>(Weekday.class);.
  • The odd type parameter E extends Enum<E> just means "E is an enumerated type" (Weekday extends Enum<Weekday>).
  • Neither is a SequencedSet or SequencedMap, nor NavigableSet: not for any fundamental reason, but the Java team saw no use case worth the effort.

9.4.7 Identity hash maps

  • IdentityHashMap
    • hashes keys with System.identityHashCode (the address-based code Object.hashCode uses) and compares with ==, so equal-content objects are distinct
    • Useful for object traversal algorithms such as serialisation, tracking which objects were visited.
  • Java 20 fixed a subtle bug
    • (https://bugs.openjdk.org/browse/JDK-8284901) introduced in Java 8: remove(Object key, Object value) and replace(K key, V oldValue, V newValue) wrongly used equals instead of ==
    • These are used in concurrent algorithms
    • Lesson: update to the latest Java version.

API notes: WeakHashMap (1.2): constructors with capacity and load factor.

LinkedHashSet (1.4) and LinkedHashMap (1.4): (), (int initialCapacity), (int, float loadFactor), and for the map (int, float, boolean accessOrder) (true = access order); protected boolean removeEldestEntry(Map.Entry<K, V> eldest) (default false).

EnumSet<E extends Enum<E>> (5.0): allOf, noneOf, range(from, to), of(...) (non-null), copyOf(EnumSet) and copyOf(Collection) (the collection must be an EnumSet or nonempty). EnumMap<K extends Enum<K>, V> (5.0): EnumMap(Class<K> keyType).

IdentityHashMap (1.4): (), (int expectedMaxSize) (capacity the smallest power of 2 above 1.5 times that; default expected size 21). System.identityHashCode(Object) (1.1).

9.5 Copies and views

  • The many interfaces and abstract classes do not tell the whole story: views give other objects implementing Collection or Map. keySet does not create a set filled with the keys
    • it returns a set object whose methods operate on the original map.

9.5.1 Small collections

  • Static factories create unmodifiable collections:
List<String> names = List.of("Peter", "Paul", "Mary");
Set<Integer> numbers = Set.of(2, 3, 5);
Map<String, Integer> scores = Map.of("Peter", 2, "Paul", 3, "Mary", 5);
  • An array of objects works too:
    • List.of(namesArray)
    • A primitive array gives a list with one element, the array: List<int[]> arrays = List.of(numbersArray); (no convenience method for a list of wrapped elements).
  • No null elements, keys or values, and no duplicate set elements or map keys: Set.of(13, null) and Map.of("Peter", 4, "Peter", 2) are errors.
  • Iteration order is deliberately scrambled
    • with a seed randomised at each VM start: two jshell runs show [Peter, Mary, Paul] then [Paul, Mary, Peter]. Do not write programs that assume any order
    • assuming implementation details never change makes useful changes hard for the framework implementors.
  • List and Set have eleven of overloads (zero to ten arguments) plus a varargs one (specialisations for efficiency)
    • Map cannot use varargs (alternating key and value types): use ofEntries with entry(...) (import static java.util.Map.*;): Map<String, Integer> scores = ofEntries(entry("Peter", 2), entry("Paul", 3), entry("Mary", 5));.
  • These objects are unmodifiable: mutators throw UnsupportedOperationException. For a mutable copy: var names = new ArrayList<>(List.of("Peter", "Paul", "Mary"));.
  • Collections.nCopies(n, anObject) gives an immutable list that appears to hold n copies, stored once: List<String> settings = Collections.nCopies(100, "DEFAULT");.
  • Collections (utility class) is not Collection (interface). Java has no Pair class, and some use Map.Entry as a "poor man's pair".

9.5.2 Unmodifiable copies and views

  • Copies:
    • Set.copyOf(names) and List.copyOf(names) make an unmodifiable copy (later changes to the original do not affect it)
    • nulls give NullPointerException. If the original is already an unmodifiable collection of the right type, copyOf returns the same object.
  • Views:
    • Collections.unmodifiableCollection, unmodifiableList, unmodifiableSet, unmodifiableSortedSet, unmodifiableNavigableSet, unmodifiableMap, unmodifiableSortedMap, unmodifiableNavigableMap
    • They add a run-time check to an existing collection, and reflect changes to the original (the difference from a copy).
var staff = new LinkedList<String>();
// ...
lookAt(Collections.unmodifiableList(staff)); // lookAt may read but not change
  • Mutators throw UnsupportedOperationException. The collection itself is not immutable (you can still change it through staff, and mutate the elements).
  • Views wrap the interface, so interface-only methods are reachable (addFirst of LinkedList is not).
  • equals and hashCode trap:
    • unmodifiableCollection (and synchronizedCollection, checkedCollection) returns a collection with Object's identity equals and hashCode, since equality is not well defined at the Collection level
    • Prefer unmodifiableSet and unmodifiableList:
var names = Set.of("Peter", "Paul", "Mary");
Collections.unmodifiableCollection(names).equals(names); // false
Collections.unmodifiableSet(names).equals(names);        // true

9.5.3 Subranges

  • subList(from, to) is a view (first index inclusive, second exclusive, like substring): List<Employee> group2 = staff.subList(10, 20); and group2.clear(); removes those elements from staff.
  • Sorted sets and maps use sort order: SortedSet<E> subSet(E from, E to), headSet(E to), tailSet(E from) (elements at least from and strictly less than to), and SortedMap<K, V> subMap(from, to), headMap(to), tailMap(from).
  • NavigableSet lets you choose inclusivity: subSet(from, fromInclusive, to, toInclusive), headSet(to, toInclusive), tailSet(from, fromInclusive).

9.5.4 Sets from Boolean-valued maps

  • Want a set with a map's features (an LRU cache)? LinkedHashSet lacks it. Wrap a LinkedHashMap<String, Boolean> with Collections.newSetFromMap:
Set<String> cache = Collections.newSetFromMap(new LinkedHashMap<String, Boolean>()
{
    protected boolean removeEldestEntry(Map.Entry<String, Boolean> eldest)
    {
        return size() > 100;
    }
});
  • Adding e puts key e with Boolean.TRUE
    • going over 100 drops the oldest. Pass an empty map and keep no reference to it
    • all changes should go through the set. Also useful with WeakHashMap
    • with a ConcurrentHashMap use newKeySet (chapter 10).

9.5.5 Reversed views

  • reversed() on SequencedCollection and SequencedSet iterates in reverse: for (String element : collection.reversed()) { ... }
    • For a SequencedMap it views the map with keys in reverse.

9.5.6 Checked views

  • A debugging aid for heap pollution (chapter 8): through a raw reference you can smuggle a wrong type in, failing only later at a cast:
var strings = new ArrayList<String>();
ArrayList rawList = strings; // warning only
rawList.add(new Date());     // now strings contains a Date
  • List<String> safeStrings = Collections.checkedList(strings, String.class); makes add check the class and throw ClassCastException right at the faulty call
    • Limited by what the VM can check: an ArrayList<Pair<String>> cannot be protected from a Pair<Date> (one raw Pair class).

9.5.7 Synchronized views

  • Collections used by several threads must not be damaged (adding while another thread rehashes would be disastrous)
    • Instead of thread-safe classes, the designers use views: var map = Collections.synchronizedMap(new HashMap<String, Employee>()); makes get, put and the rest synchronised, each call completing before another thread's call starts (details in chapter 10).

9.5.8 A note on optional operations

  • A view often has restrictions:

    • read-only, fixed size, or removal without insertion (as with a key view)
    • A restricted view throws UnsupportedOperationException for an inappropriate operation.

  • Many methods in the collection and iterator interfaces are "optional operations", which conflicts with the idea of an interface (a better design would be separate interfaces for read-only views and fixed-size views, but that would have tripled the number of interfaces, which the designers found unacceptable).

  • Should you use optional methods in your own designs? The author thinks not. Collection library designers face a "particularly brutal" set of conflicting requirements (easy to learn, convenient, completely generic, idiot-proof, and as efficient as hand-coded algorithms), which you rarely face.

java.util.List (1.2): of(...) overloads from zero to ten elements plus of(E... elements) (9; unmodifiable, no nulls), copyOf(Collection<? extends E>) (10). Set: the same.

Map: of(...) with up to ten key/value pairs (9), entry(k, v) (9), ofEntries(Map.Entry...) (9), copyOf(Map) (10).

Collections (1.2): newSetFromMap(Map<E, Boolean>) (6), the unmodifiable views (unmodifiableCollection, unmodifiableList, unmodifiableSet, unmodifiableSortedSet, unmodifiableNavigableSet (8), unmodifiableMap, unmodifiableSortedMap, unmodifiableNavigableMap (8) and the Java 21 sequenced ones), the synchronised views (synchronizedCollection, synchronizedList, synchronizedSet, synchronizedSortedSet, synchronizedNavigableSet, synchronizedMap, synchronizedSortedMap, synchronizedNavigableMap), the checked views (checkedCollection, checkedList, checkedSet, checkedSortedSet, checkedNavigableSet, checkedMap, checkedSortedMap, checkedNavigableMap, checkedQueue), nCopies(n, value), singletonList, singleton, and emptyList, emptySet, emptySortedSet, emptyNavigableSet, emptyMap, emptySortedMap, emptyNavigableMap, emptyEnumeration, emptyIterator, emptyListIterator.

Arrays.asList(E... array) (1.2): a list view of an array that is modifiable but not resizable.

Subrange methods: List.subList(firstIncluded, firstExcluded); SortedSet.subSet/headSet/tailSet; NavigableSet versions with inclusive flags; SortedMap.subMap/headMap/tailMap; NavigableMap versions with flags. reversed() on SequencedCollection, SequencedSet, SequencedMap (21).

9.6 Algorithms

  • Beyond the classes, the framework provides algorithms, and shows how to write your own.

9.6.1 Why generic algorithms?

  • Finding the maximum differs by container:
    • an array loop with indexes, an ArrayList loop with get(i), a LinkedList loop with an iterator
    • They are tedious and a bit error-prone (off-by-one? empty or one-element containers?), and you do not want separate max(ArrayList) and max(LinkedList) methods.
  • Find the minimal collection interface that can do the job efficiently. Computing a maximum needs only iteration, not random access, so accept a Collection:
public static <T extends Comparable> T max(Collection<T> elements)
{
    if (elements.isEmpty())
    {
        throw new NoSuchElementException();
    }
    Iterator<T> iter = elements.iterator();
    T largest = iter.next();
    while (iter.hasNext())
    {
        T next = iter.next();
        if (largest.compareTo(next) < 0)
        {
            largest = next;
        }
    }
    return largest;
}
  • Arrays are not collections, so they need a separate static <T extends Comparable> T max(T[] a). The C++ library has dozens of algorithms
    • Java's Collections and Arrays classes give the basics (sorting, binary search, simple utilities)
    • others are in the streams library (Volume II): largest = coll.stream().max(Comparator.naturalOrder()).get();.

9.6.2 Sorting and shuffling

  • Collections.sort(staff) sorts a List of Comparable elements
    • with another order, pass a comparator (or use List.sort): Collections.sort(staff, Comparator.comparingDouble(Employee::getSalary));.
  • Descending:
    • Comparator.reverseOrder() returns a comparator that returns b.compareTo(a)
    • Collections.sort(staff, Comparator.comparingDouble(Employee::getSalary).reversed()); sorts by descending salary.
  • How it sorts: random access in a linked list is slow (a merge sort could sort links efficiently), but the implementation dumps the elements into an array, sorts it, and copies back.
  • The algorithm is a bit slower than QuickSort but stable: it does not reorder equal elements. Sort by name then by salary and employees with equal salary keep their name order.
  • Which lists can you pass?
    • The documentation says modifiable (supports set) but need not be resizable (supports add and remove): an unmodifiableList cannot be sorted
    • Arrays.sort(staff) and Arrays.sort(staff, comparator) work for arrays.
  • Collections.shuffle(cards, RandomGenerator.getDefault()) randomly permutes a list (a list without RandomAccess is copied to an array, shuffled and copied back).
  • Listing 9.6 (ShuffleDemo.java): a list of 1 to 49, shuffled, then numbers.subList(0, 6) sorted and printed (a lottery draw).

Collections (1.2): static <T extends Comparable<? super T>> void sort(List<T>) (stable, O(n log n)), shuffle(List<?>), shuffle(List<?>, Random), shuffle(List<?>, RandomGenerator) (21; O(n a(n)) where a(n) is the average access time). List<E> (1.2): default void sort(Comparator<? super T>) (8). Comparator<T> (1.2): static reverseOrder() (8), default reversed() (8).

9.6.3 Binary search

  • On a sorted array, look at the middle element and keep searching one half: for 1,024 elements about 10 steps, versus an average of 512 (present) or 1,024 (absent) for a linear search.
  • Collections.binarySearch(elements, target) (or with a comparator) needs a sorted List, else the answer is wrong.
i = Collections.binarySearch(elements, target);
i = Collections.binarySearch(elements, target, comparator);
if (i < 0)
{
    elements.add(-i - 1, target); // keep the list sorted
}
  • A non-negative result is the matching index. A negative result means absent; the insertion point is -i - 1 (not -i, because 0 would be ambiguous).
  • Binary search needs random access: without RandomAccess it falls back to a linear-cost iterative search. Arrays has binary search for primitive and object arrays.

Collections (1.2): binarySearch(List<T>, T key) and with a Comparator (O(a(n) log n); negative i means insert at -i - 1). Arrays (1.2): binarySearch(T[] a, T key) and binarySearch(T[] a, int start, int end, T key) (6), also with a comparator; a negative result r means insert at -r - 1; component types Object or any primitive.

9.6.4 Simple algorithms

  • Collections has simple algorithms (max, copy, fill, reverse). They help the reader: a loop must be deciphered, a call states intent.
// loop: what does it do?
for (int i = 0; i < words.size(); i++)
{
    if (words.get(i).equals("C++"))
    {
        words.set(i, "Java");
    }
}

// call: obvious
Collections.replaceAll(words, "C++", "Java");
  • Collection.removeIf and List.replaceAll take lambdas:
words.removeIf(w -> w.length() <= 3);
words.replaceAll(String::toLowerCase);
  • The removeIf predicate should look only at the element being decided,
    • not at the collection, or behaviour is implementation-dependent: ArrayList.removeIf makes two passes (find all, then remove), others remove as found
    • For new ArrayList<>(List.of("Ada", "C++", "Java")), words.removeIf(w -> w.length() == words.size()) leaves ["Java"] (both 3-letter words marked first), but with a LinkedList or HashSet only one three-letter word is removed, because after the first removal the size is 2
    • The developers did not think of an efficient one-pass algorithm for array lists in time and then kept the old behaviour for compatibility (https://bugs.openjdk.org/browse/JDK-8143577).

Collections (1.2): min, max (with or without a comparator), copy(List<? super T> to, List<T> from) (target at least as long), fill(List, value), addAll(Collection<? super T>, T... values) (5.0), replaceAll(List<T>, oldValue, newValue) (1.4), indexOfSubList(l, s) and lastIndexOfSubList(l, s) (1.4; for [s, t, a, r] and [t, a, r] both return 1), swap(List, i, j) (1.4), reverse(List) (O(n); [t, a, r] becomes [r, a, t]), rotate(List, d) (1.4; index i moves to (i + d) % size, so [t, a, r] rotated by 2 is [a, r, t]), frequency(Collection, Object) (5.0), disjoint(c1, c2) (5.0).

Collection.removeIf(Predicate<? super E>) (8), List.replaceAll(UnaryOperator<E>) (8).

9.6.5 Bulk operations

  • coll1.removeAll(coll2) removes elements present in coll2; coll1.retainAll(coll2) keeps only those present in both. Intersection of two sets without a loop:
var result = new HashSet<String>(firstSet); // every collection has a copy constructor
result.retainAll(secondSet);
  • Apply bulk operations to views: terminate employees by ID with staffMap.keySet().removeAll(terminatedIDs); (the key set is a view, so the entries vanish from the map).
  • With subrange views: relocated.addAll(staff.subList(0, 10)); and staff.subList(0, 10).clear();.

9.6.6 Converting between collections and arrays

  • Array to collection: List<String> staff = List.of(names);.
  • Collection to array:
    • Object[] names = staff.toArray(); returns an Object[], and (String[]) staff.toArray() is an error
    • Pass an array constructor expression: String[] values = staff.toArray(String[]::new);
    • Before JDK 11: staff.toArray(new String[0]) (a new array of the same type, or the passed one if long enough: staff.toArray(new String[staff.size()])).

9.6.7 Writing your own algorithms

  • Work with interfaces, not concrete classes,
    • for parameters and results. processItems(ArrayList<Item> items) forces callers to repackage
    • ask for the most general interface that does the job: a List if order matters, a Collection<Item> otherwise, or better an Iterable<Item> (one method iterator, used by the enhanced for behind the scenes; Collection extends it).
  • For return types, public ArrayList<Item> lookupItems(...) over-promises; return a List, so you can later return List.of() for empty or singleton results.
  • Why does the API not follow this everywhere? Timing: JComboBox(Object[] items) and JComboBox(Vector<?> items) come from Swing, created before the Collections Framework.

9.7 Legacy collections

  • Container classes from the first release, integrated into the framework later (Figure 9.12).
  • Hashtable: like HashMap but synchronised (as Vector is). Use HashMap unless you need legacy compatibility; for concurrency use ConcurrentHashMap (chapter 10).
  • Enumeration
    • (hasMoreElements, nextElement, and since 9 asIterator()): analogous to Iterator
    • To collect one: ArrayList<String> loggerNames = Collections.list(LogManager.getLoggerNames()); or LogManager.getLoggerNames().asIterator().forEachRemaining(n -> { ... });
    • For legacy methods that need an enumeration: new SequenceInputStream(Collections.enumeration(streams)).
    • C++ often passes iterators as parameters; Java programmers rarely do. Pass the collection: recipients can get the iterator and have all the collection methods.

9.7.3 Property maps

  • Properties
    • is a map with three traits: keys and values are strings, it can easily load from and save to a file, and it has a secondary table of defaults
    • Good for configuration options.
var settings = new Properties();
settings.setProperty("width", "600.0");
settings.setProperty("filename", "/home/cay/books/corejava/code/v1ch09/raven.html");
String filename = settings.getProperty("filename");
  • It implements Map<Object, Object> for historical reasons, so get and put accept any object: stick to getProperty and setProperty.
  • Save and load:
var out = new FileWriter("program.properties");
settings.store(out, "Program Properties");

var in = new FileReader("program.properties");
settings.load(in);
  • The saved file starts with #Program Properties and a timestamp comment, then lines like top=227.0, width=423.0.
  • With streams the archaic ISO 8859-1 encoding is used (characters above U+00FF become Unicode escapes)
    • use readers and writers for UTF-8. Before Java 18 set StandardCharsets.UTF_8 explicitly.
  • Defaults, two mechanisms: per call, settings.getProperty("filename", ""); or a secondary map in the constructor:
var defaultSettings = new Properties();
defaultSettings.setProperty("width", "600");
defaultSettings.setProperty("height", "400");
defaultSettings.setProperty("filename", "");
var settings = new Properties(defaultSettings);
  • The companion code stores and reloads the image viewer's frame position, size and last file in ~/.corejava/ImageViewer.properties.
  • Properties are flat. A fake hierarchy with keys like window.main.color has no support from the class; for complex configuration use Preferences (Volume II, chapter 10).

java.util.Properties (1.0): Properties(), Properties(Properties defaults), String getProperty(String key) (falls back to defaults, else null), getProperty(key, defaultValue), Object setProperty(String, String) (returns the old value), Set<String> stringPropertyNames() (6; includes defaults), void load(Reader) (6), void store(Writer out, String header) (6).

9.7.4 System properties

  • System.getProperties() describes system information
    • System.getProperty("user.home") reads one. java.version gives a string like "21.0.1" (but "1.8.0" up to Java 8): the Java 9 numbering change broke tools
    • read JEP 322 (https://openjdk.org/jeps/322) if you parse versions.
  • Print all:
    • java -XshowSettings:properties
    • Set with -D: java -Duser.language=fr -Duser.country=CA MyProgram (never change java.version)
    • In jshell use -R: jshell -R-Duser.language=fr -R-Duser.country=CA
    • Numeric or Boolean values: Boolean.getBoolean, Integer.getInteger("java.specification.version"), Long.getLong.
  • Always-present properties include java.version, java.vendor, java.home, java.class.path, java.library.path, java.class.version, the java.specification.* and java.vm.* families, os.name, os.version, os.arch, file.separator, path.separator, line.separator, java.io.tmpdir, user.name, user.home, user.dir, native.encoding, stdout.encoding, stderr.encoding.

9.7.5 Stacks

  • The Stack class (push, pop, peek; do not pop or peek an empty stack) extends Vector, which is unsatisfactory: you can insert and remove anywhere, not just at the top
    • (Prefer a Deque such as ArrayDeque for stack use.)

9.7.6 Bit sets

  • BitSet
    • stores bits packed into long words, far more efficient than a boolean[], with get(i), set(i), clear(i) instead of masking
    • It can model a set of nonnegative integers with an upper bound (bit i on means i is in the set), more efficient than Set<Integer> when the bound is modest and the set is dense.
  • BitSet API (1.0): BitSet(int initialCapacity), cardinality() (1.4; number of set bits), length() (1.2; highest set bit plus 1), size() (bits currently available, not the number of elements), get, set, clear, and, or, xor, andNot, IntStream stream() (8).
  • Sieve of Eratosthenes
    • (Listing 9.7, plus the C++ in Listing 9.8): count primes from 2 to 2,000,000 by turning all bits on, then clearing multiples of each prime
      • 148,933 primes. It is a poor prime finder and a poor benchmark (mostly bit operations), but a tradition
      • Timings (Intel i7-1165G7, 32 GB, Ubuntu 24.04): **C++ (g++ 11.4.0) 70 ms
    • Java 25 20 ms**. Java beat C++ in the last ten editions
    • with C++ optimisation raised, C++ reaches 16 ms, which Java would match only if the program ran long enough to trigger the HotSpot JIT.
void main()
{
    int n = 2000000;
    var bitSet = new BitSet(n + 1);
    int i;
    for (i = 2; i <= n; i++)
    {
        bitSet.set(i);
    }
    i = 2;
    while (i * i <= n)
    {
        if (bitSet.get(i))
        {
            int k = i * i;
            while (k <= n)
            {
                bitSet.clear(k);
                k += i;
            }
        }
        i++;
    }
    IO.println(bitSet.cardinality() + " primes");
}

Summary points

  • Hold collections through interfaces
    • pick ArrayList, LinkedList, HashSet, TreeSet, ArrayDeque, PriorityQueue, HashMap, TreeMap, LinkedHashMap, EnumSet, EnumMap by the cost profile you need.
  • Iterators sit between elements; avoid changing a collection while another iterator reads it.
  • Hash collections need consistent equals and hashCode; sorted ones need a comparator compatible with equals.
  • Map has merge, computeIfAbsent, getOrDefault, views (keySet, values, entrySet).
  • Views (unmodifiable, subrange, reversed, checked, synchronised) wrap rather than copy; List.of, Set.of, Map.of give unmodifiable, unordered-in-effect small collections.
  • Use Collections and Arrays algorithms (sort, binarySearch, shuffle) and write your own against the most general interface.
  • Avoid legacy Vector, Hashtable, Stack; Properties and BitSet still have uses.
Terms to carry forward
  • Collection, List, Set, Queue, Deque, Map: the core interfaces.
  • Iterator, ListIterator, fail-fast: traversal and ConcurrentModificationException.
  • Hash code, bucket, collision, load factor, rehash: hash table vocabulary.
  • Red-black tree, heap: TreeSet and PriorityQueue structures.
  • View, backed collection: a window onto another collection.
  • Unmodifiable, immutable, stable sort: change and ordering guarantees.
  • Weak reference: reference that does not keep an object alive.
  • Property map, bit set: Properties and BitSet.
  • RandomAccess, SequencedCollection: efficiency tag and Java 21 first/last access.
