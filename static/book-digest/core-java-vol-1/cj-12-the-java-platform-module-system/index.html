Core Java 12: The Java Platform Module System

Source: Cay S. Horstmann, Core Java, Volume I: Fundamentals, 14th ed. (Pearson, 2025), ch. 12. Previous: Core Java 11: Annotations. Next: Core Java 13: Appendix, Java Keywords.

Takeaways
  • A module is a set of packages plus a descriptor (module-info.java) that lists what it exports and what it requires. The compiler and the VM enforce both.
  • Two gains: strong encapsulation (unexported packages are unreachable) and reliable configuration (no duplicate or missing classes). No versioning support.
  • Reflection is restricted too: use opens for libraries that need private access (JPA, JSON-B).
  • Migration: a JAR on the module path becomes an automatic module; code on the class path lives in the unnamed module. Migrate bottom-up.
  • Services use provides ... with and uses. The JDK tools jdeps, jlink and jmod analyse, trim and package modules.

12.1 The module concept

  • Classes give encapsulation through private
    • packages give the next level (package access). In large systems that is not enough: any public feature is accessible everywhere, so you cannot reason about the impact of changing it.
  • The JDK faced this over twenty years
    • CORBA (org.omg.corba) shipped until Java 10; from Java 11 you add the JARs yourself
    • And java.awt.DataFlavor is used in the implementation of SOAP, so even AWT cannot simply be dropped.
  • OSGi and similar systems were judged unsuitable. The Java Platform Module System (Java 9) is part of the language and VM, modularised the Java API, and can be used for your own code.
  • A module consists of:
    • a collection of packages;
    • optional resources and other files such as native libraries;
    • a list of accessible packages;
    • a list of modules it depends on.
  • The platform enforces both at compile time and in the VM.
  • Advantages over JARs on the class path:
    • Strong encapsulation: you control which packages are accessible.
    • Reliable configuration: no duplicate or missing classes.
  • Not addressed: versions. You cannot say which version is required or use several versions of a module in one program; use other mechanisms.

12.2 Naming modules

  • A module is a collection of packages whose names need not be related (java.sql holds java.sql and javax.sql). A module name may equal a package name.
  • Names use letters, digits, underscores and periods. There is no hierarchy: com.horstmann and com.horstmann.corejava are unrelated.
  • For shared modules use globally unique reverse domain names
    • Easiest: name it after the top-level package (SLF4J: module org.slf4j with packages org.slf4j, org.slf4j.spi, org.slf4j.event, org.slf4j.helpers).
  • A package can belong to only one module; unique module names with matching package prefixes make package names unique.
  • Application modules may use short names. The book uses library-style names such as com.horstmann.util and program names such as v1ch12.hellomod.
  • When referring to a package you do not give the module name.

12.3 The modular "Hello, World!" program

  • The class must be in a named package (the unnamed package cannot be in a module).
// com/horstmann/hello/HelloWorld.java
package com.horstmann.hello;

public class HelloWorld
{
    public static void main(String[] args)
    {
        IO.println("Hello, Modular World!");
    }
}
  • Add a module declaration in module-info.java in the base directory (named after the module by convention):
v1ch12.hellomod/
├ module-info.java
└ com/horstmann/hello/HelloWorld.java

// module-info.java
module v1ch12.hellomod
{
}
  • It is empty: the module offers nothing and needs nothing.
$ javac v1ch12.hellomod/module-info.java \
    v1ch12.hellomod/com/horstmann/hello/HelloWorld.java
$ java --module-path v1ch12.hellomod \
    --module v1ch12.hellomod/com.horstmann.hello.HelloWorld
$ java -p v1ch12.hellomod -m v1ch12.hellomod/com.horstmann.hello.HelloWorld
  • module, requires, exports and the rest are restricted keywords, meaningful only in module declarations
    • module-info compiles to module-info.class
    • It cannot be a class name (hyphen).
  • The module path is like the class path but holds modules. The main class is given as modulename/classname. -p and -m are the short options.
  • You get the warning module name component v1ch12 should avoid terminal digits (to discourage version numbers in names)
    • Ignore it or annotate the module (the annotation needs target ElementType.MODULE):
// module-info.java
@SuppressWarnings("module")
module v1ch12.hellomod
{
}

12.4 Requiring modules

  • A program using JOptionPane fails to compile: package javax.swing is not visible (declared in module java.desktop, but module v1ch12.requiremod does not read it).
// module-info.java
module v1ch12.requiremod
{
    requires java.desktop;
}
  • Modules must be explicit about requirements, so the VM can verify them before starting
    • The earlier example needed none because java.lang and java.io are in java.base, required by default.
  • java.desktop itself requires java.datatransfer, java.prefs and java.xml
    • The module graph has modules as nodes and requires (or the implied java.base) as edges
    • No cycles are allowed.
  • requires is not transitive by default: java.desktop requires java.prefs, which requires java.xml, but that gives java.desktop no right to use java.xml unless it declares it
    • (See 12.11 for relaxing this.)
  • Module M reads N if:
    • M requires N;
    • M requires a module that transitively requires N;
    • N is M itself or java.base.

12.5 Exporting packages

  • Requiring a module does not make all its packages available. A module lists accessible packages with exports:
// module-info.java of java.xml (extract)
module java.xml
{
    exports javax.xml;
    exports javax.xml.catalog;
    exports javax.xml.datatype;
    exports javax.xml.namespace;
    exports javax.xml.parsers;
}
  • Hidden packages (such as jdk.xml.internal) are simply not exported.
  • For an exported package, its public and protected types and their public and protected members are accessible outside (protected, as always, only to subclasses and the same package).
  • An unexported package is inaccessible outside its module, unlike before modules, when sun.misc.BASE64Encoder or com.sun.rowset.CachedRowSetImpl could be used although they were not public API. Some programs stop running under Java 9
    • nobody ever promised those APIs.
  • Example: module com.horstmann.greet exports package com.horstmann.greet but not com.horstmann.greet.internal.
// Greeter.java
package com.horstmann.greet;

public interface Greeter
{
    static Greeter newInstance()
    {
        return new com.horstmann.greet.internal.GreeterImpl();
    }

    String greet(String subject);
}

// GreeterImpl.java
package com.horstmann.greet.internal;

import com.horstmann.greet.Greeter;

public class GreeterImpl implements Greeter
{
    public String greet(String subject)
    {
        return "Hello, " + subject + "!";
    }
}

// module-info.java of com.horstmann.greet
module com.horstmann.greet
{
    exports com.horstmann.greet;
}

// module-info.java of v1ch12.exportedpkg
module v1ch12.exportedpkg
{
    requires com.horstmann.greet;
}
  • exports takes a package name, requires takes a module name.
  • The application calls Greeter.newInstance() and prints greeter.greet("Modular World").
$ javac com.horstmann.greet/module-info.java \
    com.horstmann.greet/com/horstmann/greet/Greeter.java \
    com.horstmann.greet/com/horstmann/greet/internal/GreeterImpl.java
$ javac -p com.horstmann.greet v1ch12.exportedpkg/module-info.java \
    v1ch12.exportedpkg/com/horstmann/hello/HelloWorld.java
$ java -p v1ch12.exportedpkg:com.horstmann.greet \
    -m v1ch12.exportedpkg/com.horstmann.hello.HelloWorld
  • The implementation is hidden; clients use an interface and a factory method.
  • Windows cmd: quote v1ch12.exportedpkg:com.horstmann.greet (the colon is special) and use ^ instead of \ for continued lines.
  • Eclipse: one project per module; in the dependent project's properties (Projects tab) add the required module to the module path (Figure 12.2).
  • A module is not a scope: two packages of the same name cannot exist in different modules, even hidden ones.

12.6 Modular JARs

  • Deploy a module as a JAR with module-info.class in the root: a modular JAR. Compile with -d to a separate directory and use jar -C to change into it:
$ javac -d modules/com.horstmann.greet \
    com.horstmann.greet/module-info.java \
    com.horstmann.greet/com/horstmann/greet/internal/GreeterImpl.java \
    com.horstmann.greet/com/horstmann/greet/Greeter.java
$ jar -c -v -f com.horstmann.greet.jar -C modules/com.horstmann.greet .
  • With Maven, Ant or Gradle, keep building as usual: a JAR containing module-info.class is a modular JAR. Put it on the module path to load it.
  • Split packages (one package across several JARs) are not possible with modules (probably never a good idea).
  • A main class can be set as in regular JARs, and the launcher names only the module:
$ javac -p com.horstmann.greet.jar -d modules/v1ch12.exportedpkg \
    v1ch12.exportedpkg/module-info.java \
    v1ch12.exportedpkg/com/horstmann/hello/HelloWorld.java
$ jar -c -v -f v1ch12.exportedpkg.jar -e com.horstmann.hello.HelloWorld \
    -C modules/v1ch12.exportedpkg .
$ java -p com.horstmann.greet.jar:v1ch12.exportedpkg.jar -m v1ch12.exportedpkg
  • Versions: --module-version 1.0 (and put it in the file name). The system does not use it to resolve modules, but tools can query it:
// Version.java
Optional<String> version = Greeter.class.getModule().getDescriptor().rawVersion();

$ jar -c -v -f com.horstmann.greet-1.0.jar --module-version 1.0 -C com.horstmann.greet .
  • The module analogue of a class loader is a layer
    • JDK and application modules go in the boot layer
    • Other modules can be loaded through the layer API (not covered), which can consider versions; application server developers are expected to use it.
  • JShell: put the JAR on the module path and add --add-modules:
$ jshell --module-path com.horstmann.greet-1.0.jar --add-modules com.horstmann.greet

12.7 Modules and reflective access

  • Encapsulation also binds reflection:
    • reflective access to non-public members of a class in a module fails
    • Libraries that rely on it include JPA-style object-relational mappers and XML/JSON binders such as JAXB and JSON-B.
  • Example:
    • the chapter 5 ObjectAnalyzer goes into module com.horstmann.util
    • a module v1ch12.openpkg has a Country class with private name and area and a Demo that analyses new Country("Belgium", 30510).
  • Running it fails with InaccessibleObjectException: Unable to make field private java.lang.String com.horstmann.places.Country.name accessible: module v1ch12.openpkg does not "opens com.horstmann.places" to module com.horstmann.util.
  • Fix with opens, which allows reflective access to all instances of classes in the package:
// module-info.java
module v1ch12.openpkg
{
    requires com.horstmann.util;
    opens com.horstmann.places;
}
  • An open module grants runtime access to all packages (as if each were both exported and opened), while compile-time access is only to exported packages: compile-time safety with classic permissive runtime behaviour.
// module-info.java
open module v1ch12.openpkg
{
    requires com.horstmann.util;
}
  • Resources
    • (loaded with Class.getResourceAsStream or Module.getResourceAsStream): if a resource sits in a directory matching a package in a module, the package must be opened to the caller
    • Resources in other directories, class files and the manifest can be read by anyone.
  • JSON-B example:
    • download jakarta.json-api-2.1.2.jar, jakarta.json.bind-api-3.0.0.jar, parsson-1.1.4.jar and yasson-3.0.3.jar from Maven Central, put them on the module path and run com.horstmann.places.Demo in v1ch12.openpkg2
    • Once the package is opened, conversion to JSON succeeds.
  • Future libraries may use VarHandle instead of reflection
    • The library needs a Lookup created in the module allowed to access the field (any method there calls MethodHandles.lookup()), which lets one module give another access to private members
    • The open question is how to grant that with minimal hassle.
// FieldReader.java
public Object getFieldValue(Object obj, String fieldName, Lookup lookup)
    throws NoSuchFieldException, IllegalAccessException
{
    Class<?> cl = obj.getClass();
    Field field = cl.getDeclaredField(fieldName);
    VarHandle handle = MethodHandles.privateLookupIn(cl, lookup)
        .unreflectVarHandle(field);
    return handle.get(obj);
}

12.8 Automatic modules

  • Real projects use third-party libraries, and you may not wait for everyone to modularise. Two mechanisms bridge the gap: automatic modules and the unnamed module.
  • A JAR without module-info.class placed on the module path is an automatic module:
    • it implicitly requires all other modules;
    • all its packages are exported and opened;
    • if its manifest META-INF/MANIFEST.MF has Automatic-Module-Name, that is the module name;
    • otherwise the name comes from the JAR file name, dropping a trailing version and replacing runs of non-alphanumeric characters with a dot.
  • So its packages behave as if on the class path; the module path is used so other modules can declare a dependency on it.
  • Example:
    • Apache Commons CSV (https://commons.apache.org/proper/commons-csv)
    • commons-csv-1.9.0.jar becomes commons.csv (version dropped, - becomes .)
    • Version 1.10.0 sets Automatic-Module-Name: org.apache.commons.csv, a name the maintainers control; eventually the JAR should get a real module-info, and dependants keep working.
  • The migration is "a great social experiment": check whether a JAR is modular or at least names its module, and be ready to update the name later.
// CSVDemo.java
package com.horstmann.places;

import java.io.*;
import org.apache.commons.csv.*;

public class CSVDemo
{
    public static void main(String[] args) throws IOException
    {
        var in = new FileReader("countries.csv");
        Iterable<CSVRecord> records = CSVFormat.EXCEL.withDelimiter(';')
            .withHeader().parse(in);
        for (CSVRecord record : records)
        {
            String name = record.get("Name");
            double area = Double.parseDouble(record.get("Area"));
            IO.println(name + " has area " + area);
        }
    }
}

// module-info.java (1.9.0, name from file name)
@SuppressWarnings("module")
module v1ch12.automod
{
    requires commons.csv;
}

// module-info.java (1.10.0, name from the manifest)
module v1ch12.automod
{
    requires org.apache.commons.csv;
}

$ javac -p v1ch12.automod:jars/commons-csv-1.10.0.jar \
    v1ch12.automod/com/horstmann/places/CSVDemo.java \
    v1ch12.automod/module-info.java
$ java -p v1ch12.automod:jars/commons-csv-1.10.0.jar \
    -m v1ch12.automod/com.horstmann.places.CSVDemo
  • The book's companion module is referred to as v2ch9.automod in the text (the listing uses v1ch12.automod).

12.9 The unnamed module

  • Any class not on the module path is in the unnamed module (technically several, acting as one)
    • Like an automatic module it can access all other modules and all its packages are exported and opened.
  • But no explicit module can access it (an explicit module has a module-info.class on the module path): explicit modules stay free of "class path hell".
  • Put commons-csv on the class path and the program above will not start: Error occurred during initialization of boot layer: java.lang.module.FindException: Module commons.csv not found, required by v1ch12.automod.
$ java --module-path v1ch12.automod \
    --class-path jars/commons-csv-1.10.0.jar \
    -m v1ch12.automod/com.horstmann.places.CSVDemo
  • Migration is bottom-up:
    1. The Java platform itself is modularised.
    2. Libraries are modularised (automatic or explicit modules).
    3. Once all libraries are modular, turn your application into a module.
  • Automatic modules can read the unnamed module, so their own dependencies can stay on the class path.

Kind Where Reads Exports and opens Reachable by explicit modules
Explicit Module path, with module-info.class What it requires What it declares Yes, if required
Automatic Module path, plain JAR All modules (and the unnamed module) All packages Yes, by its name
Unnamed Class path All modules All packages No

12.10 Command-line flags for migration

  • Even without modules of your own, you meet the modularised platform: your class-path code is in the unnamed module but talks to the JDK.
  • Compile-time encapsulation
    • is strict from Java 11
    • runtime access was allowed (with a console warning for the first offence) until Java 16, when reflective access at runtime is also enforced. Java 9 to 16 had --illegal-access:
Setting Behaviour
--illegal-access=permit Java 9 default: message for the first illegal access
--illegal-access=warn Message for each illegal access
--illegal-access=debug Message and stack trace for each
--illegal-access=deny Java 16 default: deny all
  • The flag is unusable from Java 17.
  • --add-exports
    • and --add-opens adjust legacy apps
    • Best remedy is to change the code (for com.sun.rowset.CachedRowSetImpl, use a RowSetProvider since Java 7), but without the source:
$ java --add-exports java.sql.rowset/com.sun.rowset=ALL_UNNAMED -jar MyApp.jar
$ java --add-opens java.base/java.lang=ALL-UNNAMED -jar MyApp.jar
  • The second is for libraries that call the protected ClassLoader.defineClass through reflection. Reflection inside the unnamed module is fine
    • non-public members of platform classes are not reachable.
  • Too many flags make a "command line from hell". Put them in option files with @: java @options1 @options2 -jar MyProg.java.
  • Option file syntax:
    • separate options with spaces, tabs or newlines;
    • double-quote arguments containing spaces ("Program Files");
    • a line ending in \ merges with the next;
    • backslashes must be escaped (C:\\Users\\Fred);
    • comment lines start with #.

12.11 Transitive and static requirements

  • requires transitive:
    • tedious if every user must declare indirect needs
    • java.desktop requires java.prefs (internal only), and transitive for java.datatransfer and java.xml, whose classes appear in its public API (Toolkit.getSystemClipboard(), XMLDecoder(InputSource)).
// module-info.java of java.desktop (extract)
module java.desktop
{
    requires java.prefs;
    requires transitive java.datatransfer;
    requires transitive java.xml;
}
  • Any module requiring java.desktop now automatically requires those two.
  • Some say always use requires transitive when a package appears in the public API, but the language does not require it. java.sql has requires transitive java.logging for one method (Driver.parentLogger returns a java.util.logging.Logger)
    • non-transitive would have been fine, and only users of that method would need java.logging.
  • A strong use is an aggregator module:
    • no packages, only transitive requirements
    • java.se is one: requires transitive java.compiler, java.datatransfer, java.desktop, ..., java.sql, java.sql.rowset, java.xml, java.xml.crypto
    • Requiring java.se gives all Java SE modules.
  • requires static (uncommon): the module must be present at compile time but is optional at runtime. Two uses:
    • an annotation processed at compile time from another module;
    • using a class if available, else falling back:
// Optional dependency
try
{
    new oracle.jdbc.driver.OracleDriver();
}
catch (NoClassDefFoundError er)
{
    // do something else
}

12.12 Importing modules

  • From chapter 4: import module java.desktop; imports all packages of the module (more than fifty, including java.awt and javax.swing).
  • In a compact compilation unit, java.base is imported automatically. Before Java 25 JShell imported an ad hoc set; now it imports java.base.
  • Many imports make name clashes likelier. Several examples import java.base and java.desktop, each with a List class; add import java.util.List; to settle it.
  • import module java.se; imports the whole Java API, but only in a modular program whose module requires java.se. It does not work in a compact compilation unit.

12.13 Qualified exporting and opening

  • A qualified export limits an export to named modules. java.base contains:
// module-info.java of java.base (extract)
exports sun.net to
    java.net.http,
    jdk.naming.dns;
  • Others cannot use the package
    • Excessive qualified exports signal a poor structure, but arise when modularising existing code (sun.net sits in java.base because that is where it is mostly needed, and the designers did not want java.base bigger or the internal package public)
    • A new project can design a better API.
  • opens can be qualified too, so the places package opens only to the util module:
// module-info.java
module v1ch12.openpkg
{
    requires com.horstmann.util;
    opens com.horstmann.places to com.horstmann.util;
}

12.14 Service loading

  • ServiceLoader (chapter 6) matches service interfaces with implementations, and modules make it easier.
  • A service interface and an implementation:
// GreeterService.java
public interface GreeterService
{
    String greet(String subject);

    Locale getLocale();
}

// FrenchGreeter.java
public class FrenchGreeter implements GreeterService
{
    public String greet(String subject)
    {
        return "Bonjour " + subject;
    }

    public Locale getLocale()
    {
        return Locale.FRENCH;
    }
}
  • The consumer picks among all offered implementations using its own criteria:
// Chooser.java
ServiceLoader<GreeterService> greeterLoader = ServiceLoader.load(GreeterService.class);
GreeterService chosenGreeter;
for (GreeterService greeter : greeterLoader)
{
    if (matches(greeter))
        chosenGreeter = greeter;
}
  • Before, implementations were advertised in text files under META-INF/services. Now use the descriptors:
    • A provider module adds provides ... with ..., listing the interface (defined in any module) and implementation classes (in this module).
    • A consumer module adds uses.
    • ServiceLoader.load then loads the providers even from inaccessible packages.
// module-info.java of jdk.security.auth (extract)
module jdk.security.auth
{
    provides javax.security.auth.spi.LoginModule with
        com.sun.security.auth.module.Krb5LoginModule,
        com.sun.security.auth.module.UnixLoginModule,
        com.sun.security.auth.module.JndiLoginModule,
        com.sun.security.auth.module.KeyStoreLoginModule,
        com.sun.security.auth.module.LdapLoginModule,
        com.sun.security.auth.module.NTLoginModule;
}

// module-info.java of java.base (extract)
module java.base
{
    uses javax.security.auth.spi.LoginModule;
}
  • The book's example:
    • module com.horstmann.greetsvc exports com.horstmann.greetsvc but not the package com.horstmann.greetsvc.internal that holds the French and German greeters
    • provides names classes in the unexported package (FrenchGreeter and GermanGreeterFactory):
// module-info.java of com.horstmann.greetsvc
module com.horstmann.greetsvc
{
    exports com.horstmann.greetsvc;

    provides com.horstmann.greetsvc.GreeterService with
        com.horstmann.greetsvc.internal.FrenchGreeter,
        com.horstmann.greetsvc.internal.GermanGreeterFactory;
}

// module-info.java of v1ch12.useservice
module v1ch12.useservice
{
    requires com.horstmann.greetsvc;
    uses com.horstmann.greetsvc.GreeterService;
}
  • HelloWorld loads the service, takes the desired language from the first argument (default "de"), keeps the greeter whose getLocale().getLanguage() matches, and prints either No suitable greeter. or its greeting for "Modular World".
  • With provides and uses, the consumer can use the module-private implementation classes.
  • The GermanGreeterFactory name hints that a provider factory (a provider() method) may stand in for a class (chapter 6) (unverified for this listing).
$ javac com.horstmann.greetsvc/module-info.java \
    com.horstmann.greetsvc/com/horstmann/greetsvc/GreeterService.java \
    com.horstmann.greetsvc/com/horstmann/greetsvc/internal/*.java
$ javac -p com.horstmann.greetsvc \
    v1ch12.useservice/com/horstmann/hello/HelloWorld.java \
    v1ch12.useservice/module-info.java
$ java -p com.horstmann.greetsvc:v1ch12.useservice \
    -m v1ch12.useservice/com.horstmann.hello.HelloWorld

12.15 Tools for working with modules

  • jdeps analyses the dependencies of JARs. To modularise JUnit 4: jdeps -s junit-4.12.jar hamcrest-core-1.3.jar (-s = summary):
hamcrest-core-1.3.jar -> java.base
junit-4.12.jar -> hamcrest-core-1.3.jar
junit-4.12.jar -> java.base
junit-4.12.jar -> java.management
  • Without -s you get the summary plus a package-to-package/module mapping; with -v a class-level mapping.
  • --generate-module-info writes module-info files for the analysed modules. -dotoutput produces a graph in the dot language, rendered with dot -Tpng:
$ jdeps --generate-module-info /tmp/junit junit-4.12.jar hamcrest-core-1.3.jar
$ jdeps -s -dotoutput /tmp/junit junit-4.12.jar hamcrest-core-1.3.jar
$ dot -Tpng /tmp/junit/summary.dot > /tmp/junit/summary.png
  • jlink builds an application that runs without a separate Java runtime, far smaller than the whole JDK. Name the modules and an output directory:
$ jlink --module-path com.horstmann.greet.jar:v1ch12.exportedpkg.jar:$JAVA_HOME/jmods \
    --add-modules v1ch12.exportedpkg --output /tmp/hello
$ bin/java -m v1ch12.exportedpkg
$ bin/java --list-modules

v1ch12.exportedpkg
com.horstmann.greet
java.base@25
  • The bin directory has a java executable
    • jlink bundles the minimal set of modules, in a runtime image file lib/modules: 29 MB here against 133 MB for all JDK modules, and 55 MB for the whole application
    • You still need file sets per platform and launch scripts.
  • Inspect the image with jimage; the format is internal to the JVM and not meant for other tools.
  • jmod
    • builds and inspects the .jmod files in the JDK's jmods directory (one per module; there is no rt.jar)
    • They are ZIP files with classes, native libraries, commands, headers, configuration and legal notices, useful only for linking (building runtime images)
    • You only need to produce them to bundle binary files with your modules.

  • The end of Volume I:
    • fundamentals and the standard library parts needed for most projects
    • Volume II covers streams, file I/O, networking, security, internationalisation, user interfaces and graphics.

Summary points

  • A module = packages + module-info with requires, exports, opens, provides, uses; the compiler and VM enforce it.
  • Strong encapsulation hides internals; reliable configuration replaces class-path guesswork. No version management.
  • Migrate bottom-up with automatic modules and the unnamed module; use --add-exports and --add-opens for legacy code.
  • Use jdeps, jlink, jmod for analysis and minimal runtime images.
Terms to carry forward
  • Module / module-info.java: packages plus descriptor of requirements and exports.
  • requires / requires transitive / requires static: dependency, implied dependency, compile-time only.
  • exports / opens: compile-time visibility versus reflective access; both can be qualified with to.
  • Modular JAR: JAR with module-info.class in its root.
  • Automatic module / unnamed module: plain JAR on the module path, and anything on the class path.
  • Layer: module-level class loader analogue; the boot layer holds JDK and app modules.
  • provides ... with / uses: module-level service loading.
  • Aggregator module: only transitive requirements (java.se).
  • jdeps / jlink / jmod: analyse dependencies, build a runtime image, build JMOD files.
