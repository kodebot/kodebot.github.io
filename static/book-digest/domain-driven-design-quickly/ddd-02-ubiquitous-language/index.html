DDD Quickly 2: The Ubiquitous Language

Source: Abel Avram, Domain Driven Design Quickly (InfoQ, 2006), chapter "The Ubiquitous Language" (pp. 13-22). Previous: DDD Quickly 1: Preface, introduction and what DDD is. Next: DDD Quickly 3: Model-driven design and its building blocks. The concept is Eric Evans'.

[!abstract] The one-minute version Developers and domain experts speak different languages, and translating between them loses knowledge. DDD's core answer: base a shared language on the model and use it everywhere: speech, writing, diagrams, and code. That is why it is called ubiquitous. A change in the language is a change to the model.

The need for a common language

  • Building the model needs software specialists and domain experts, but there is a fundamental communication barrier.
  • Developers think in classes, methods, algorithms, patterns, inheritance, polymorphism; they match every real-life concept to a programming artifact. "Developers will be developers."
  • Domain experts
    • know nothing of libraries, frameworks, persistence, sometimes not even databases
    • They know their area: planes, routes, altitudes, longitudes and latitudes, deviations from the normal route, trajectories, in their own jargon.
  • If one side says something the other misunderstands, "what are the chances for the project to succeed?" A project has serious problems when the team does not share a language for the domain.
  • Day-to-day terminology is disconnected from the terminology in the code (the most important product)
    • Even one person speaks differently than they write, so the most incisive expressions of the domain emerge in transient form and never get captured in the code or even in writing.
  • Translation (developers explaining patterns in layman's terms; experts inventing new jargon) harms the knowledge-building process
    • Each dialect serves only its own side, so none can be the common language.
  • Which language? The developers'? The experts'? Something in between?

The DDD answer

Use the model as the backbone of a language. Ask the team to use it consistently in all communications and in the code. Speech, writing and diagrams all carry the same words.

  • The language connects all parts of the design. Large designs take weeks or months to take shape
    • the team discovers wrong concepts and new elements, which is impossible without a common language.
  • It does not appear overnight: find the key concepts and give them words; some are easy to spot, some are hard.
  • Iron out difficulties by experimenting with alternative expressions, which reflect alternative models. Then refactor the code, renaming classes, methods and modules to conform to the new model
    • Resolve confusion in conversation as we do for ordinary words.
  • Model and language are strongly interconnected: a change in the language should become a change to the model.
  • Domain experts should object
    • to awkward or inadequate terms and structures
    • If they cannot understand something in the model or language, something is probably wrong with it
    • Developers should watch for ambiguity or inconsistency in the design.

Creating it: the air-traffic dialog

The book gives a dialog between a developer and an expert. The words that become the language:

  1. Expert: air traffic is made of planes; each takes off from a departure place and lands at a destination place.
  2. Developer: can pilots choose any air path? Expert: no, they receive a route and stay on it as closely as possible.
  3. Developer: a route is a 3D path, a series of 3D points. Expert: no, the route is the projection on the ground of the expected air path; it goes through a series of points determined by latitude and longitude.
  4. Developer: call each point a fix (a fixed point on Earth's surface), described by 2D points; departure and destination are just fixes, not separate concepts.
  5. Developer: can the plane fly as high or low as it likes? Expert: no, the altitude is in the flight plan, which also holds the route, cruise altitude, cruise speed, type of airplane, even crew members.
  6. Developer: the flight plan is important: add it to the model.
  7. Developer: we do not actually care about the plane (colour, Boeing or Airbus); we track and measure the flight. Change the model.
  • The team slowly builds a language from the boldface words, and the language changes the model.
  • Real dialogs are far more verbose
    • people talk indirectly, give too much detail, choose wrong concepts
      • Everyone should be aware of the need for a common language, stay on essentials, use their own jargon as little as possible, and use the Ubiquitous Language.
  • Implement the main concepts in code:
    • a Route class and a Fix class (Fix could inherit from a 2DPoint class or contain one; decided later)
    • This maps model to code and language to code, making the code readable and faithful to the model, which pays off when the model grows and changes could have undesirable consequences.

What to build the language with

  • UML
    • is a great tool for a few classes and relationships: easy to follow, and the diagram changes with the idea
    • But diagrams "grow like mushrooms after a nice summer rain": hundreds of classes on a sheet "as long as Mississippi" are hard even for specialists and hopeless for domain experts, even in medium projects
    • UML expresses classes, attributes and relationships but not behaviour and constraints (these end up as notes), so it cannot convey the meaning of concepts or what objects do
    • Other tools must add that.
  • Documents:
    • make small diagrams, each a subset of the model, plus text explaining behaviour and constraints
    • Each is a "spotlight" on one important aspect of the domain
    • They may be hand-drawn: that signals they are temporary, which is true since the model changes a lot early on.
  • Do not try one big diagram of the whole model: almost impossible to assemble, and so cluttered it conveys less than the small ones.
  • Be wary of long documents: slow to write, obsolete before finished, must stay in sync with the model. Old documents with the wrong language are not helpful.
  • Code:
    • advocated by the XP community
    • Well-written code is communicative, but is a method name as clear as its body? Do variable names and structure tell the whole story? "Code which functionally does the right thing does not necessarily express the right thing
    • Writing a model in code is very difficult."
  • Whatever the tools: the design team of architects, developers and domain experts needs a language that unifies their actions, helps create the model and expresses it in code.

[!note]- Terms to carry forward Ubiquitous Language · domain jargon vs technical jargon · model as backbone of the language · spotlight diagrams · fix, route, flight plan (the air-traffic vocabulary).
