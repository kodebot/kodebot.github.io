DDD Quickly 5: Refactoring toward deeper insight

Source: Abel Avram, Domain Driven Design Quickly (InfoQ, 2006), chapter "Refactoring Toward Deeper Insight" (pp. 57-66). Previous: DDD Quickly 4: Aggregates, Factories and Repositories. Next: DDD Quickly 6: Preserving model integrity: bounded context, continuous integration, context map.

[!abstract] The one-minute version A first model is always shallow. Keep refining it as you learn: the model and the code improve through small refactorings and occasional breakthroughs, usually triggered by making an implicit concept explicit. Beyond classes, three useful explicit concepts are Constraint (an invariant), Process (a Service, maybe a Strategy) and Specification (a yes/no rule as an object). Keep the design flexible; a stiff design resists refactoring.

Continuous refactoring

  • Designing without a model produces software untrue to its domain

    • modelling without feedback from design and without developers produces a model that implementers do not understand and that may not suit the technology.

  • So from time to time stop and look at the code

    • Refactoring is redesigning code to make it better without changing application behaviour, in small, controllable steps, with care
    • Automated tests help ensure nothing broke.

  • Technical refactoring deals with code quality and has patterns and tools; without the tools it can be very difficult.

  • Refactoring toward deeper insight

    • is motivated by new understanding of the domain: something gets clearer or a relationship is discovered
    • It belongs in the design too
    • Code should be expressive: readable, telling what it does and why, so it captures the substance of the model.

  • The second kind cannot be organised as patterns:

    • model complexity and variety defeat a mechanistic approach
    • "A good model is the result of deep thinking, insight, experience, and flair."

  • The beginner's rule is a trap:

    • read the specification, nouns become classes, verbs become methods. That is a simplification and gives a shallow model. All models lack depth at first
    • refactor toward deeper insight.

  • The design must be flexible. "A stiff design resists refactoring"; code not built for flexibility fights you at every change, and things that should be easy take a long time.

  • Proven building blocks plus a consistent language bring sanity

    • the challenge left is finding an incisive model: one that "sloughs off the superficial and captures the essential" (a deep model), capturing subtle concerns of domain experts and driving a practical design, in tune with how experts think and responsive to users' needs.

  • Sophisticated domain models are seldom developed except by iterative refactoring with close involvement of domain experts and developers keen to learn the domain.

Bring key concepts into light

Refactoring happens in small steps. Sometimes many small changes add little value, and sometimes a few make a big difference: a Breakthrough.

  • Start with a coarse, shallow model; refine with deeper knowledge, add concepts and abstractions, refactor the design; each refinement adds clarity and sets up a breakthrough.
  • A breakthrough often changes the way we see the model: great progress, but potentially a large refactoring (time and resources never enough) and risky because ample refactoring may change behaviour.
  • Make implicit concepts explicit.
    • Talking with experts, some concepts enter the Ubiquitous Language and some go unnoticed; those are implicit concepts used to explain concepts already in the model
    • Some turn out to play a key role: create classes and relationships for them
    • Implicit domain concepts should not stay implicit.

How to find implicit concepts

  1. Listen to the language. Early on the language may carry little or misused information; as the Ubiquitous Language grows, key concepts enter it. That is where to look.
  2. Awkwardness in the design. A set of relationships making the computation path hard to follow, or a procedure doing something complicated: likely a missing concept. Without it, other objects replace its function and get fat with behaviour that does not belong to them, hurting clarity. Make it explicit, simplify, make the design "suppler".
  3. Contradictions. One expert contradicting another, or one requirement another. Many are not real: different views of the same thing, or imprecise explanations. Reconcile them; it sometimes reveals important concepts, and at least keeps things clear.
  4. Domain literature. Books on almost any topic hold domain knowledge, though usually no model; process, distil and refine it.

Three concepts worth making explicit

Constraint: a simple way to express an invariant; whatever happens to the data, the invariant holds. The book's Bookshelf example (capacity 20): the rule is content.size() <= capacity.

public class Bookshelf {
       private int capacity = 20;
       private Collection content;

       public void add(Book book) {
                 if(content.size() + 1 <= capacity) {
                        content.add(book);
                 } else {
                 throw new IllegalOperationException(
                 "The bookshelf has reached its limit.");
                 }
       }
}

Refactor: extract the constraint into a method so everyone sees add() is subject to it, with room to grow if it gets more complex.

public class Bookshelf {
       private int capacity = 20;
       private Collection content;

       public void add(Book book) {
               if(isSpaceAvailable()) {
                       content.add(book);
               } else {
               throw new IllegalOperationException(
                       "The bookshelf has reached its limit.");
               }
       }

       private boolean isSpaceAvailable() {
               return content.size() < capacity;
       }
}

(The two versions use <= over size()+1 and < over size(); equivalent.)

Process: usually code as procedures, but in an OO language choose an object for it and give it behaviour. The best way is a Service. If there are several ways to carry it out, encapsulate the algorithm in an object and use a Strategy. Not every process needs to be explicit: make it explicit when the Ubiquitous Language specifically mentions it.

Specification: an object used to test whether an object satisfies criteria.

  • Business rules in the domain layer usually live inside the entities and value objects they apply to
    • Some are yes/no questions built from Boolean operations: e.g
    • is this customer eligible for a credit? It could be isEligible() on Customer, but evaluating it means verifying credentials, checking past debts payment, outstanding balances, etc
    • Such rules grow large and complex and bloat the object until it no longer serves its purpose
    • Tempting move: shove the rule up to the application layer
    • The right move: refactor.
  • Encapsulate the rule in its own object, the Specification of the Customer, and keep it in the domain layer. It holds Boolean methods, each a small test
    • together they answer the question. If the rule is not in one Specification, its code spreads over several objects and becomes inconsistent.
  • Uses: test whether objects fulfil a need or are ready for a purpose; select an object from a collection; a condition during creation of an object.
  • Combine simple specifications into a composite:
Customer customer =
    customerRepository.findCustomer(customerIdentiy);
...
Specification customerEligibleForRefund = new
Specification(
       new CustomerPaidHisDebtsInThePast(),
       new CustomerHasNoOutstandingBalances());

if(customerEligibleForRefund.isSatisfiedBy(customer))
{
      refundService.issueRefundTo(customer);
}

Simple rules are easier to test, and reading this code tells you what "eligible for a refund" means.
