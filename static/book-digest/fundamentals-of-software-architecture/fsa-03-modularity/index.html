Fundamentals of Software Architecture 3: Modularity

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd ed. (O'Reilly, 2025), ch. 3. Previous: Fundamentals of Software Architecture 2: Architectural Thinking. Next: Fundamentals of Software Architecture 4: Architectural Characteristics Defined.

Takeaways
  • Modularity means breaking a system into logically related groups of code; granularity is how big the pieces are. "Embrace modularity, but beware of granularity."
  • Good modularity is an implicit architecture characteristic: no requirement asks for it, yet sustainable code bases need it, and it takes constant energy against entropy.
  • Three tools measure it: cohesion (how related a module's parts are), coupling (afferent and efferent, plus Instability, Abstractness and Distance from the Main Sequence) and connascence (a precise vocabulary for kinds of coupling).
  • Most metrics are blunt and need interpretation; LCOM finds only structural lack of cohesion, not whether pieces fit logically.
  • Architects usually call modules components.

3.1 Why modularity matters

Glenford Myers (Composite/Structured Design, 1978) is quoted: 95% of the words written about software architecture extol modularity and little is said about how to achieve it.

  • Every platform groups related code into modules, yet the concept is slippery: web definitions are inconsistent, some contradictory. So the book supplies its own.
  • Metrics, fitness functions and visualisations all rely on modularity and related concepts.
  • Modularity is an organising principle
    • Software systems tend toward entropy (disorder), and as in physics, energy must be added to preserve order
    • Structural soundness "won't happen by accident".
  • Preserving good modularity is an implicit architecture characteristic: virtually no project requirement explicitly asks for it.

3.2 Modularity versus granularity

The two terms are often used interchangeably but differ:

  • Modularity: breaking systems into smaller pieces, for example moving from a monolith (such as a traditional n-tiered layered architecture) to a highly distributed style like microservices.
  • Granularity: the size of those pieces, how big a part or service should be.

Granularity is where trouble starts. It couples services or components to one another and creates complex, hard-to-maintain antipatterns:

  • Spaghetti Architecture
  • Distributed Monoliths
  • the "famous" Big Ball of Distributed Mud

The way to avoid them is to pay attention to granularity and the overall coupling between services and components.

3.3 Defining modularity

  • Merriam-Webster: a module is "each of a set of standardized parts or independent units that can be used to construct a more complex structure".
  • The book uses modularity for a logical grouping of related code: a group of classes in an object-oriented language or of functions in a structured or functional one.
  • Example: the com.mycompany.customer Java package should contain customer-related things. Mechanisms: package in Java, namespace in .NET.
  • It is a logical, not necessarily physical, separation
    • Lumping many classes into one monolithic application is convenient, but the coupling that loose partitioning encourages impedes breaking the monolith apart later.
  • Architects must know how developers package code: if several packages are tightly coupled, reusing one for related work gets harder.

Sidebar: modular reuse before classes

  • March 1968:
    • Edsger Dijkstra's "Go To Statement Considered Harmful" appeared in Communications of the ACM
    • He attacked GOTO because nonlinear leaping makes reasoning and debugging difficult.
  • It helped usher in structured programming in the mid-1970s (Pascal, C).
  • Developers then found languages lacked a good way to group like things, so a short era of modular languages began in the mid-1980s: Modula (Niklaus Wirth, creator of Pascal) and Ada.
  • Object-oriented languages soon took over, but designers kept modules as packages and namespaces
    • Java still supports modular, object-oriented and functional paradigms, each with its own scoping rules and quirks.

Namespaces

  • A namespace gives software assets fully qualified names to separate them. The everyday example is the internet's unique global identifiers tied to IP addresses.
  • Most languages use their modularity mechanism as a namespace
    • sometimes the module structure is reflected physically (Java package structures must match the directory structure of the class files).

Sidebar: a language with no name conflicts, Java 1.0

  • The original designers knew name clashes well
    • Their hack: the package namespace, plus a rule that the physical directory structure must match the package name
    • A catalogue order and an installation order, both called order, no longer clash, because filesystems do not allow two same-named files in one directory.
  • The original classpath held only directories.
  • It proved cumbersome for big projects, and reusable assets had to be "exploded" into the directory structure. Java 2 (1.2) added JAR files that act as a directory on the classpath.
  • For a decade developers fought to get the classpath right, since two JARs could again create conflicting names: hence many war stories about debugging class loaders.

3.4 Measuring modularity

Researchers have created language-agnostic metrics. The chapter focuses on three concepts: cohesion, coupling and connascence.

Cohesion

Cohesion is the extent to which a module's parts belong in the same module: how related they are. An ideal module has everything packaged together; splitting it would need coupling through calls between modules. Larry Constantine (Structured Design) is quoted: dividing a cohesive module "would only result in increased coupling and decreased readability".

The range, best to worst:

Type Meaning
Functional Every part is related, and the module contains everything essential to function
Sequential Two modules interact: one's output is the other's input
Communicational Two modules form a chain, each operating on information or contributing to output (one adds a record to the database, the other emails based on it)
Procedural Two modules must execute code in a particular order
Temporal Related by timing, such as unrelated initialisation tasks at system startup
Logical Data is related logically, not functionally (a module converting text, serialised objects or streams to another format; the StringUtils package of unrelated static methods on String)
Coincidental Elements are unrelated apart from sharing a source file: the worst form

Cohesion is less precise than coupling: the degree is often at the architect's discretion. Take a Customer Maintenance module with these operations:

Customer Maintenance
  add customer
  update customer
  get customer
  notify customer
  get customer orders
  cancel customer orders

Should the last two live in a separate Order Maintenance module? As always, it depends:

  • Are they the only two Order Maintenance operations? If so, collapse them back.
  • Will Customer Maintenance grow much larger? Then extract behaviour into another module.
  • Does Order Maintenance need so much customer knowledge that separating needs heavy coupling? (Constantine's quote again.)

This is the trade-off analysis at the heart of the job.

LCOM

  • Computer scientists gave a structural cohesion metric: Lack of Cohesion in Methods (LCOM), from Chidamber and Kemerer's Object-Oriented Metrics Suite (which also includes Cyclomatic Complexity and coupling metrics).
  • Version 1:
    • LCOM = |P| - |Q| if |P| > |Q|, otherwise 0
    • P increases by 1 for each method that does not access a given shared field; Q decreases by 1 for methods that do
    • A second variant (LCOM96B, 1996) is more elaborate, and the authors skip its variables.
  • Plain-language version: the sum of sets of methods not shared via sharing fields. It exposes incidental coupling within classes.
  • Example: a class with private fields a and b, where many methods touch only a and many only b, scores a high LCOM: a significant lack of cohesion.

  • Class X: low LCOM, good structural cohesion.
  • Class Y: each field and method pair could live in its own class without changing behaviour.
  • Class Z: mixed; the last field and method pair could be refactored into its own class.
  • Use:
    • restructuring, migrating or understanding a code base
    • shared utility classes are a common headache when moving architectures, and LCOM can find classes that were incidentally coupled and should never have been one.
  • Limit: it finds only structural lack of cohesion and cannot tell whether pieces fit logically. This reflects the Second Law: why is more important than how.

Coupling

Coupling analysis is better, partly because method calls and returns form a call graph that can be analysed mathematically (graph theory). Edward Yourdon and Larry Constantine's Structured Design: Fundamentals of a Discipline of Computer Program and Systems Design (Prentice-Hall, 1979) defined afferent and efferent coupling.

  • Afferent coupling (Ca): the number of incoming connections to a code artifact (component, class, function).
  • Efferent coupling (Ce): the outgoing connections to other artifacts.
  • Tools exist for virtually every platform.

Why such similar names? Yourdon and Constantine borrowed from mathematics and favoured symmetry over clarity; "incoming" and "outgoing" would have been clearer. Mnemonics: a comes before e as incoming comes before outgoing; the e in efferent matches the e in exit.

Core metrics (Robert C. Martin)

Derived from coupling, for most object-oriented languages:

Abstractness:  A = Σma / (Σmc + Σma)
Instability:   I = Ce / (Ce + Ca)
Distance from the Main Sequence:  D = |A + I - 1|
  • Abstractness: the ratio of abstract artifacts (abstract classes, interfaces; ma) to all artifacts (mc is the concrete ones).
    • One end: no abstractions, such as one huge main() of 5,000 lines: the numerator is 1, the denominator 5,000, so A is almost 0.
    • The other end: too many abstractions, hard to follow. The authors cite AbstractSingletonProxyFactoryBean as an example of layered abstraction and an ambiguous name.
  • Instability:
    • the ratio of efferent coupling to total coupling
    • It measures volatility
    • A class that calls many others to delegate work is highly susceptible to breakage when any of them changes.
  • Distance from the Main Sequence:
    • one of the few holistic structural metrics
    • Both A and I fall between 0 and 1 (except in extreme cases), so plotting them gives a graph with an ideal line, the main sequence.

  • Classes near the line have a healthy mix of the two competing concerns; the closer, the better balanced.
  • Zone of Uselessness (upper right): too abstract, hard to use.
  • Zone of Pain (lower left): too much implementation and too little abstraction; brittle and hard to maintain.
  • Tools on many platforms compute these to help architects learn a code base, prepare a migration or assess technical debt.
The limitations of metrics
  • Code-level tools are "extremely blunt" compared with other engineering disciplines.
  • Cyclomatic Complexity cannot tell essential complexity (the problem is complex) from accidental complexity (the code is more complex than needed).
  • Almost every code-level metric needs interpretation, but baselines for critical ones help architects judge which kind they see; fitness-function tests come later in the book.

Structured Design (1979) predates object-oriented languages and covers function-based coupling types that are outdated now, so object orientation added connascence.

Connascence

Meilir Page-Jones (What Every Programmer Should Know about Object-Oriented Design, Dorset House, 1996) gave a more precise language for coupling in object-oriented code. It is not a metric like afferent and efferent coupling.

  • Two components are connascent if a change in one requires the other to change to keep the system correct.
  • Two kinds: static (source-code level, how components are coupled by afferent or efferent coupling) and dynamic (runtime).

Static connascence

Type Components must agree on... Example from the chapter
Name the name of an entity Method names and parameters: the most common and most desirable coupling, since refactoring tools make system-wide renames trivial
Type the type of an entity Typed variables and parameters in statically typed languages; also selective typing in dynamic ones (Clojure Spec)
Meaning (or Convention) the meaning of values Hardcoded numbers instead of constants, such as int TRUE = 1; int FALSE = 0;: flipping the values would be a disaster
Position the order of values Parameter order
Algorithm a particular algorithm A security hash that must produce identical results on client and server to authenticate the user

Figure 3-5 ranks the types by strength, weakest first. Refactoring should go toward the weaker end (up the list):

  1. Name
  2. Type
  3. Meaning
  4. Algorithm
  5. Position
  6. Execution
  7. Timing
  8. Value
  9. Identity

Connascence of Position, concretely: with void updateSeat(String name, String seatLocation), the call below has the right types but the wrong semantics.

updateSeat("14D", "Ford, N");

Dynamic connascence

Type Meaning Example
Execution Order of execution matters See the email code below
Timing Timing of execution matters A race condition between two threads
Values Several values must change together Four points defining a rectangle; or one value updated across separate databases, where all change together or none do
Identity Components reference the same entity Two components sharing and updating a distributed queue

Connascence of Execution fails because properties must be set in a specific order (the subject is set after send()):

email = new Email();
email.setRecipient("foo@example.com");
email.setSender("me@me.com");
email.send();
email.setSubject("whoops");

Connascence properties

  • Strength:
    • how easily a developer can refactor the coupling
    • Prefer static to dynamic: source analysis finds it and tools make improving it trivial
    • Example: refactor Connascence of Meaning to Name by replacing a magic value with a named constant.
  • Locality:
    • how close modules are in the code base. Connascence that signals bad coupling across distance is fine nearby
    • two classes in the same module with Connascence of Meaning do less harm than two in different modules.
    • Same advice as the DDD bounded context: limit implementation coupling to as narrow a scope as practical (see Chapter 7). Strength and locality should be considered together.
  • Degree: the size of the impact of a change: a few classes or many. High dynamic connascence is tolerable with few modules, but code bases grow.

Page-Jones's three guidelines:

  1. Minimise overall connascence by breaking the system into encapsulated elements.
  2. Minimise any remaining connascence that crosses encapsulation boundaries.
  3. Maximise connascence within encapsulation boundaries.

Jim Weirich, who repopularised the concept ("Connascence Examined", Emerging Technologies for the Enterprise, 2012), offers two rules:

  • Rule of Degree: convert strong forms of connascence into weaker forms.
  • Rule of Locality: as the distance between software elements increases, use weaker forms.

Why learn it: precise vocabulary, like design patterns. Saying "we need a Singleton service" beats "a service with only one instance". In review, "You have Connascence of Meaning; refactor it to Connascence of Name" beats "don't add a magic string constant mid-method; extract it".

3.5 From modules to components

The book uses module as the generic name for a bundle of related code; most architects call modules components, the key building blocks of software architecture. Chapter 8 derives components from problem domains, but architectural characteristics and their scope come first.

Summary points

  • Modularity is the logical grouping of related code; granularity is the size of the pieces and the source of trouble.
  • Maintaining modularity takes constant effort; it is an implicit characteristic.
  • Cohesion (functional best, coincidental worst), LCOM, coupling (Ca, Ce, Instability, Abstractness, Distance) and connascence each describe a different angle.
  • All metrics need interpretation.
Terms to carry forward
  • Modularity versus granularity: breaking apart versus size of the parts.
  • Spaghetti Architecture, Distributed Monolith, Big Ball of Distributed Mud: antipatterns from coupling driven by granularity.
  • Cohesion types: functional, sequential, communicational, procedural, temporal, logical, coincidental.
  • LCOM: Lack of Cohesion in Methods; finds structural, incidental coupling in classes.
  • Afferent (Ca) and efferent (Ce) coupling: incoming and outgoing connections.
  • Abstractness, Instability, Distance from the Main Sequence: Robert C. Martin's derived metrics.
  • Zone of Pain and Zone of Uselessness: too concrete versus too abstract.
  • Connascence: a vocabulary for coupling; static or dynamic; strength, locality, degree.
  • Essential versus accidental complexity.
