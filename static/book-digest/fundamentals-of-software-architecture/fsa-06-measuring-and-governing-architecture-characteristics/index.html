Fundamentals of Software Architecture 6: Measuring and Governing Architecture Characteristics

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 6. Previous: Fundamentals of Software Architecture 5: Identifying Architectural Characteristics. Next: Fundamentals of Software Architecture 7: The Scope of Architectural Characteristics.

Takeaways
  • Characteristics are hard to define because they are not physics, have wildly varying definitions and are often composite. Decomposing them into measurable parts fixes all three.
  • Measure operational (response time, scalability models), structural (Cyclomatic Complexity) and process (code coverage, deployment success) aspects. Every metric needs interpretation.
  • Governance means steering what developers do. Fitness functions automate it: any mechanism giving an objective integrity assessment of a characteristic.
  • Examples: a cycle test with JDepend, a Distance from the Main Sequence threshold, ArchUnit and NetArchTest layer rules, and Netflix's Chaos Monkey family.
  • Fitness functions are a checklist for important-but-not-urgent concerns, not heavyweight governance.

6.1 Why measuring is hard

Architects deal with a huge range of characteristics: operational (performance, elasticity, scalability) mixed with structural (modularity, deployability). Three reasons they struggle to define them:

  • They are not physics. Many terms are vague: how do you design for agility, or "wicked fast" performance? Industry views differ, sometimes legitimately and sometimes by accident.
  • Wildly varying definitions. Even inside one organisation, departments disagree on critical characteristics such as performance, so no proper conversation is possible until developers, architects and operations unify.
  • Too composite. Many are collections of smaller ones (agility breaks into modularity, deployability, testability).

Decomposing composites into parts with objective definitions solves all three. When an organisation agrees on standard, concrete definitions it creates a ubiquitous language around architecture and can unpack composites into measurable features.

6.2 Operational measures

Many characteristics have obvious direct measures, yet with nuance.

  • If a team measures only the average response time, what if a boundary condition makes 1% of requests take 10 times longer? With enough traffic the outliers may not show
    • Also track maximum response times.
  • High-level teams base definitions on statistical analysis, not hard numbers
    • Example: a video streaming service measures scale over time, builds statistical models and raises alarms when real-time metrics leave the prediction
    • A miss means either the model is wrong or something is amiss; teams want to know both.
  • What teams measure evolves with tools, targets and devices
    • Recently many teams set performance budgets for first contentful paint and first CPU idle, which say much about mobile page performance.
The many flavours of performance
  • Performance has multiple definitions: general request and response time, or budgets for specific parts of an application.
  • Organisations have researched user behaviour and found the optimum first-page render (first visible progress in a browser or mobile device) is a fraction of a second, whereas most applications are in the double-digit range.
  • Some metrics affect design: forward-thinking organisations set K-weight budgets for page downloads, a maximum number of bytes of libraries and frameworks per page, because only so many bytes can cross a network at once, especially on mobile in low-bandwidth areas.

6.3 Structural measures

Internal structure such as modularity is an implicit characteristic. No comprehensive metrics for architecture quality exist yet, but tools address narrow dimensions of code structure. One is complexity, measured by Cyclomatic Complexity.

Cyclomatic Complexity

  • Cyclomatic Complexity (CC)
    • was designed by Thomas McCabe Sr
    • in 1976 as an objective measure of code complexity at function, class or application level
    • It applies graph theory to decision points that create different execution paths.
  • No decisions (if statements) gives CC = 1; one conditional gives CC = 2, since there are two paths.
  • For one function: CC = E - N + 2, where N is nodes (lines of code) and E is edges (possible decisions).

Example 6-1 (as printed in the book) has a CC of 3 (3 - 2 + 2):

public void decision(int c1, int c2)
{
    if (c1 < 100)
        return 0;
    else if (c1 + C2 > 500)
        return 1;
    else
        return -1;
}

  • The 2 in the formula simplifies a single function
    • For fan-out calls to other methods (connected components in graph theory) the general form is CC = E - N + 2P, where P is the number of connected components.
  • Overly complex code is a code smell that harms modularity, testability, deployability and more. Unwatched, growing complexity dominates a code base.
  • CC shows how blunt architects' metrics are:
    • it cannot tell essential complexity (a complicated problem) from accidental complexity (a poor design)
    • It is useful for assessing code from developers or generative AI, which tends to solve problems by brute force and add accidental complexity.
What is a good value for Cyclomatic Complexity?
  • It depends on the problem domain: an algorithmically complex problem yields complex functions. Watch whether complexity comes from the domain or poor coding, and whether the code is partitioned badly (could a large method split into well-factored ones?).
  • Industry thresholds say under 10 is acceptable; the authors find that very high and prefer under 5, signalling cohesive, well-factored code.
  • The Java tool Crap4J combines CC and code coverage: past a CC of 50, no coverage rescues the code.
  • Neal Ford's most terrifying artefact: one C function, the heart of a commercial package, with a CC over 800, over 4,000 lines and liberal GOTOs to escape deeply nested loops.
  • TDD tends to produce smaller, less complex methods: write a simple test, then the least code to pass it, which encourages well-factored, cohesive methods with low CC.

6.4 Process measures

Some characteristics overlap with the development process. Agility is composite: testability, deployability and more.

  • Testability is measurable with code-coverage tools (percentage of code the tests execute), but a code base can have 100% coverage with poor assertions that give no confidence.
  • Deployability metrics: percentage of successful deployments, how long deployments take, and issues raised by deployments. Each team chooses measures that fit its goals.
  • Process can shape structure:
    • if ease of deployment and testability are priorities, the architect emphasises modularity and isolation, a characteristic driving a structural decision
    • Anything in a project can become an architectural characteristic if it meets the three criteria.

6.5 Governance and fitness functions

Once characteristics are chosen, how do you ensure developers respect them under schedule pressure? Modularity is a classic important but not urgent concern.

Governance comes from the Greek kubernan, "to steer". It covers any part of the development process architects want to influence; ensuring software quality falls under it.

  • The drive for automation from Extreme Programming created continuous integration, which led to automation in operations (DevOps), and this chain continues through to architectural governance.
  • Building Evolutionary Architectures (O'Reilly, 2022, Neal Ford et al.) describes fitness functions to automate governance.

What a fitness function is

  • "Evolutionary" in that title comes from evolutionary computing, not biology
    • Co-author Dr Rebecca Parsons worked with tools such as genetic algorithms, which are guided by an objective measure of the quality of the result: a fitness function.
  • Example:
    • the travelling salesperson problem (shortest route through a list of cities)
    • A genetic algorithm could use one fitness function for route length, another for cost and another for time away.
  • An architectural fitness function is any mechanism that provides an objective integrity assessment of some architecture characteristic or combination of them.
  • It is not a new framework to download but a new perspective on existing tools. It overlaps chaos engineering, metrics, monitors and unit-testing libraries.

Cyclic dependencies

  • Modularity is implicit, so architects prioritise it, but tools work against it: in a Java or .NET IDE, referencing a class not yet imported brings an auto-import dialog that programmers reflexively accept
    • Arbitrary imports between components damage modularity.
  • Cyclic dependencies are a damaging antipattern: each component references the others, so you cannot reuse one without bringing the rest, and the architecture drifts toward the Big Ball of Mud.

  • Code reviews help but come too late: a week of rampant imports has already done serious damage.
  • The solution is a fitness function in the continuous build. Example 6-2 uses JDepend, which understands Java packages and fails the test if it finds a cycle:
public class CycleTest
{
    private JDepend jdepend;

    @BeforeEach
    void init()
    {
        jdepend = new JDepend();
        jdepend.addDirectory("/path/to/project/persistence/classes");
        jdepend.addDirectory("/path/to/project/web/classes");
        jdepend.addDirectory("/path/to/project/thirdpartyjars");
    }

    @Test
    void testAllPackages()
    {
        Collection packages = jdepend.analyze();
        assertEquals("Cycles exist", false, jdepend.containsCycles());
    }
}

It guards a practice that is important but not urgent: it matters to architects but has little effect on day-to-day coding.

Distance from the Main Sequence

The metric from Chapter 3 can also be verified. Example 6-3 sets a threshold and fails any package outside it (ArchUnit can build similar tests):

@Test
void AllPackages()
{
    double ideal = 0.0;
    double tolerance = 0.5; // project-dependent
    Collection packages = jdepend.analyze();
    Iterator iter = packages.iterator();
    while (iter.hasNext())
    {
        JavaPackage p = (JavaPackage) iter.next();
        assertEquals("Distance exceeded: " + p.getName(), ideal, p.distance(), tolerance);
    }
}
Architects must ensure developers understand the purpose of a fitness function before imposing it on them.

The intent is not for architects in an ivory tower to write esoteric rules; it is automated governance that protects code quality, built together with developers.

ArchUnit and NetArchTest

ArchUnit is a Java testing framework inspired by and using parts of the JUnit ecosystem, with predefined governance rules as unit tests and the ability to write modularity tests. Take the layered architecture of Figure 6-4 (Chapter 10 covers its motivations and trade-offs):

Some developers do not grasp why the layers exist, or adopt "better to ask forgiveness than permission" for a local concern such as performance; that erodes the architecture's long-term health. Example 6-4 states the allowed relationships and verifies them:

layeredArchitecture()
    .layer("Controller").definedBy("..controller..")
    .layer("Service").definedBy("..service..")
    .layer("Persistence").definedBy("..persistence..")
    .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
    .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
    .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Service")

The .NET equivalent is NetArchTest. Example 6-5 checks that presentation classes do not depend on the data layer:

// Classes in the presentation should not directly reference repositories
var result = Types.InCurrentDomain()
    .That()
    .ResideInNamespace("NetArchTest.SampleLibrary.Presentation")
    .ShouldNot()
    .HaveDependencyOn("NetArchTest.SampleLibrary.Data")
    .GetResult()
    .IsSuccessful;

Gaming the metric. Once developers learn how compliance is measured they may code to the metric. Example: unit tests with no assertions merely "touch" the code to inflate coverage. A governance rule (via ArchUnit) can require every unit test to have at least one assertion. Dedicated rule-breakers will find a way, but this prevents accidental lapses.

Chaos engineering at Netflix

  • When Netflix moved operations to Amazon's cloud, architects lost control of operations and worried about operational defects. That spawned chaos engineering.
  • The Chaos Monkey is a production fitness function that simulates general chaos to see how well the system endures it.

  • Latency was a problem with some AWS instances, so Chaos Monkey simulated high latency; later a specialised Latency Monkey was created.
  • Chaos Kong simulates a whole Amazon datacentre failing, helping Netflix avoid such outages for real.
  • Conformity Monkey: enforces governance rules in production (example: each service must respond without errors for all requests).
  • Security Monkey: checks each service for well-known defects such as ports that should not be active and configuration errors.
  • Janitor Monkey:
    • looks for instances nothing routes to any more. Developers migrate to newer services and leave old ones running with no collaborators
    • since cloud instances cost money, it removes the orphans.
  • The perspective shift:
    • it is not whether something will break but when
    • Anticipating and testing for breakage makes systems more robust
    • See Chaos Engineering (Casey Rosenthal and Nora Jones, O'Reilly, 2020).

The checklist perspective

Atul Gawande's The Checklist Manifesto (Metropolitan, 2009) describes how pilots and surgeons (sometimes legally) use checklists. They are not forgetful: when you do a highly detailed job repeatedly, details slip, and a succinct checklist is an effective reminder.

Fitness functions are the same: not a heavyweight governance mechanism, but a way to express and automatically verify important architectural principles. Developers know not to release insecure code, but that competes with dozens of other priorities; tools like the Security Monkey build the check into the substrate of the architecture.

Summary points

  • Decompose composites into objectively defined, measurable parts.
  • Operational, structural and process measures all need interpretation (averages hide outliers, CC cannot separate essential from accidental complexity, coverage can be gamed).
  • Governance steers; fitness functions automate it for important-but-not-urgent concerns.
  • Cycle tests, main-sequence thresholds, ArchUnit and NetArchTest, and chaos engineering are examples; build them with developers.
Terms to carry forward
  • Ubiquitous language (for characteristics): agreed, concrete definitions.
  • Performance budget, K-weight budget, first contentful paint.
  • Cyclomatic Complexity: E - N + 2 (or E - N + 2P); under 5 preferred, under 10 acceptable.
  • Essential versus accidental complexity.
  • Governance and fitness function.
  • Cyclic dependencies and Big Ball of Mud.
  • JDepend, ArchUnit, NetArchTest.
  • Chaos engineering: Chaos Monkey, Latency Monkey, Chaos Kong, Conformity, Security and Janitor Monkeys.
