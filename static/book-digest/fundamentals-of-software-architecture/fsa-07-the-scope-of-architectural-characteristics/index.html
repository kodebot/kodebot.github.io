Fundamentals of Software Architecture 7: The Scope of Architectural Characteristics

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 7. Previous: Fundamentals of Software Architecture 6: Measuring and Governing Architecture Characteristics. Next: Fundamentals of Software Architecture 8: Component-Based Thinking.

Takeaways
  • Older frameworks assumed one set of characteristics for the whole system. Modern architectures such as microservices have different characteristics per service, so scope matters.
  • The authors' scope measure is the architecture quantum: an independently deployable unit with high functional cohesion, low external implementation static coupling and synchronous communication to other quanta.
  • Coupling has four kinds: semantic, implementation, static and dynamic. Two services sharing a coupling point (a database, a component) are in the same quantum.
  • Scoping drives the style choice: monolith or distributed, then persistence, then communication style.
  • Worked kata: Going Green splits into three quanta from three clusters of characteristics. The cloud adds scoping questions of its own.

7.1 Why scope matters

  • Many outdated frameworks had a fatal flaw:
    • they assumed one set of characteristics for the whole system
    • That is sometimes still true, but microservices and similar styles hold different characteristics at service and system levels.
  • Scope helps choose the architecture style used as a starting point.
  • While writing Building Evolutionary Architectures the authors needed a measure of the structural evolvability of styles
    • The code-level metrics in Chapter 6 reveal low-level detail but cannot evaluate dependencies outside the code base, such as databases, that affect many operational characteristics.
  • Example: no effort making a code base performant or elastic succeeds if the database does not match those characteristics.
  • Finding no good measure of scope, they made one: the architecture quantum.

7.2 Architecture quanta and granularity

Component-level coupling is not the only thing binding software together. Business concepts bind parts semantically, creating functional cohesion. To design, analyse and evolve software, consider all coupling points that could break.

Plurals for Latin-derived technical terms

Quantum is Latin, so the plural is quanta, like data. The Chicago Manual of Style (18th edition, 2024, p. 336) notes data is now commonly treated as a mass noun with a singular verb.

Where the term comes from. In physics a quantum is the smallest possible amount of something (usually energy); the Latin means "how great" or "how much". In general use it means a "small, unbreakable thing", the sense used here.

An informal definition: "the smallest part of the system that runs independently". Microservices often form quanta: a service runs independently with its own data and other dependencies.

An architecture quantum establishes the scope for a set of architectural characteristics and has four features:

  • Independent deployment from other parts of the architecture.
  • High functional cohesion.
  • Low external implementation static coupling.
  • Synchronous communication with other quanta.

Establishes the scope for characteristics

It is a boundary for a set of characteristics, particularly operational ones. Being independently deployable with high functional cohesion, it gives a useful measure of architecture modularity.

Independently deployable

A quantum includes everything it needs to function. If an application uses a database, the database is part of the quantum, because the system will not work without it.

  • Virtually every legacy system deployed with a single database is, by definition, a quantum of one.
  • In microservices each service has its own database (part of the bounded-context philosophy, Chapter 18), which creates multiple quanta, each with its own scope of characteristics.

High functional cohesion

  • Cohesion is how unified the code is in purpose. A Customer component with properties and methods all about the Customer entity has high cohesion
    • a Utility component with random methods does not.
  • High functional cohesion means a quantum does something purposeful.
  • It matters little in a monolith with a single database, where cohesion is essentially the whole system
    • In distributed architectures (event-driven, microservices) architects design each service around a single workflow, a bounded context, so it has high functional cohesion.
Domain-driven design's bounded context
  • Eric Evans's Domain-Driven Design (Addison-Wesley Professional, 2003) has deeply influenced architectural thinking. DDD is a modelling technique for decomposing complex problem domains in an organised way.
  • A bounded context is where everything related to a portion of the domain is visible internally but opaque to other bounded contexts.
  • Before DDD, architects sought to reuse code across common entities organisation-wide, but shared artifacts cause tight coupling, harder coordination and more complexity.
  • So instead of one Customer class for the whole organisation, each problem domain has its own Customer class and reconciles differences at the communication points between domains.

Four kinds of coupling

Coupling What it describes Example
Semantic The natural coupling of the problem being solved An order-processing application inherently involves inventory, catalogues, carts, customers and sales. A domain change means changing requirements, and no architecture pattern prevents that from rippling out
Implementation How the team decides to implement dependencies One database or split for scalability and availability? Monolith or distributed? These barely change semantic coupling but greatly affect architectural decisions
Static The "wiring": how services depend on one another. Two services are in the same quantum if they depend on the same coupling point Catalog and Shipping both depend on a shared address component, so they share a quantum. Several services using the same relational database also share one
Dynamic The forces when quanta communicate while running Services talking to form workflows; trade-offs in Chapter 15

A simple test: two things are coupled if changing one might break the other. Static coupling defines the scope of dependencies.

Low external implementation static coupling

  • Implementation coupling between quanta should be low, derived from DDD's low coupling between bounded contexts
    • Quanta are the operational building blocks one level of abstraction above components and often overlap service boundaries.
  • Tight coupling is desirable when high cohesion is required, such as inside a service or subsystem.
  • An architecture is brittle when one implementation change causes unexpected side effects that break seemingly unrelated things
    • Example: an architect renames a service call field from State to StateCode, expecting one caller to be affected, and many other dependencies break.
Higher coupling is allowed for narrower scopes; the broader the scope, the looser the coupling should be.

Synchronous communication

Communication is dynamic coupling. It concerns operational characteristics because they often determine timing and blocking in distributed architectures.

  • Example:
    • in microservices, when an auction ends the Auction service sends payment information synchronously to the Payment service, which can handle only one payment every 500 ms
    • When many auctions end at once, the first call works, then calls fail: Payment is not as scalable as Auction.
  • With asynchronous communication (a message queue) the queue buffers: it holds pending messages until the receiver is ready
    • It will still overflow if Auction keeps sending more than Payment can handle, but bursts are absorbed.
  • Synchronous communication is unforgiving in distributed architectures, especially when parts have different characteristics. Chapter 15 covers communication types.

In modern systems, architects define characteristics at the quantum level, not the system level.

7.3 The impact of scoping

Scope helps determine service boundaries. Figure 7-1 is the whole decision tree and Figures 7-2 to 7-4 detail its steps:

  1. Choose the style (Figure 7-2). From characteristics and domain analysis, decide whether the system succeeds with one set of characteristics or needs several groups. One set allows a monolith, which reduces later choices. Several groups point to a distributed architecture.
  2. Determine quantum boundaries (Figure 7-3) for a distributed architecture (granularity guidelines in Chapter 18).
  3. Determine persistence (Figure 7-4). A monolith generally takes a single monolithic database, developed and deployed in lockstep; the architect then picks the monolithic style. Distributed architectures use a single database (common in event-driven) or partition the data along service granularity (microservices).
  4. Determine the communication style between quanta: synchronous or asynchronous (Chapter 15). In some systems, choosing synchronous communication can change the quantum boundaries set by static coupling; the two types of coupling interact often.

7.4 Kata: Going Green

The problem. Going Green (GG) recycles and resells old electronics such as cell phones through public kiosks and a website, both running the same system.

  • A user uploads the device's model number and condition, and GG bids.
  • If the user accepts, they deposit it in a kiosk or, via the website, GG sends a box to mail it.
  • On receipt GG assesses the device and pays the user.
  • GG then estimates the value and either recycles or resells it.
  • The system also produces reports and analytics.

Three clusters appear in the characteristics analysis:

  • Customer facing (quote, status): scalability, availability, agility.
  • Electronic item assessment: maintainability, deployability, testability (which make up the composite agility).
  • Recycling, reporting and accounting: security, data integrity, auditability.

Why assessment is separate. GG's business is reselling the highest-value used electronics, and new models arrive constantly. The faster GG updates its assessments, the more newer (more valuable) devices it can resell: a business driver intersecting an architectural concern.

Could one system meet all eight characteristics? Possibly, but with difficulty, because they counteract one another: fast deployability is harder when you also prioritise back-office auditability, and the UI needs a vastly different level of scalability from the rest.

Use the clusters to separate quanta. In Figure 7-7 the dotted lines are the quanta. Using characteristic scope as a guide to service granularity is a good first step toward the most beneficial trade-offs (Chapter 18).

  • Quantum 1: Quote service and Item Status service, with their database.
  • Quantum 2: Assessment service, with its own database.
  • Quantum 3: Receiving, Recycling, Accounting and Reporting services, sharing one database.

7.5 Scoping and the cloud

Cloud-based resources complicate scoping because they encapsulate many operational characteristics. At least two scenarios:

  • Using the cloud to host containers:
    • the cloud acts as an alternate operations centre running and orchestrating containers
    • Consider the characteristics of the containers and the constraints of the orchestration tool (for example Kubernetes).
  • Using provider resources as system components:
    • applications are pieced together from the provider's building blocks (triggered functions, databases)
    • Look at the capabilities the provider advertises, and hopefully maintains, to see how to build suitable capabilities.

Many things now cloud configuration settings, such as elasticity, were hard-won by the previous generation working on physical systems. Those concerns are easier now, but new trade-offs appear: provider availability and heightened security concerns. The details change a lot; the job of analysing trade-offs stays constant.

Summary points

  • Scope matters: characteristics belong to quanta, not always the whole system.
  • A quantum is independently deployable (with its data), highly cohesive, loosely coupled externally and mindful of synchronous communication.
  • Use four coupling types to find quanta; a shared database or component joins quanta.
  • Scoping steers monolith versus distributed, persistence and communication choices; clusters of characteristics suggest quanta.
Terms to carry forward
  • Architecture quantum (plural quanta): independently deployable unit with high functional cohesion, low external implementation static coupling and synchronous communication.
  • Semantic, implementation, static and dynamic coupling.
  • Brittle architecture: one change breaks seemingly unrelated things.
  • Bounded context: DDD unit visible inside, opaque outside.
  • Quantum of one: a system with a single shared database.
  • Characteristic clusters: groups that guide quantum boundaries.
