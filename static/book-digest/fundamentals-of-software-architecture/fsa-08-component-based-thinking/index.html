Fundamentals of Software Architecture 8: Component-Based Thinking

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 8. Previous: Fundamentals of Software Architecture 7: The Scope of Architectural Characteristics. Next: Fundamentals of Software Architecture 9: Foundations.

Takeaways
  • Component-based thinking sees a system as logical components interacting to perform business functions. The architect "sees" the system at this level, not the class level.
  • A component is usually a namespace or directory; the leaf nodes of the directory tree are the components. A logical architecture (components and their interactions) is independent of the physical one (services, UIs, databases).
  • Build the logical architecture iteratively: identify core components, assign user stories, analyse roles and responsibilities, analyse characteristics, restructure, and repeat.
  • Start from the Workflow or Actor/Action approach; avoid the Entity Trap (Order Manager style components).
  • Manage coupling: afferent and efferent counts, temporal coupling, and the Law of Demeter (limit knowledge, which redistributes rather than removes coupling).

8.1 Defining logical components

Chapter 3 introduced a module as a collection of related code. Here the focus is its architectural form: logical components, the building blocks of a system. Identifying and managing them is part of architectural thinking, hence component-based thinking: seeing the structure as a set of logical components interacting to perform business functions.

The analogy is a house floor plan:

  • A typical Western floor plan has rooms (kitchen, bedrooms, bathrooms, living room, office), each with a purpose; these are the house's components.
  • The major functions a system performs are its components: managing inventory, shipping orders, processing payments. Each contains the source code for that business function.

Logical components usually appear as a namespace or directory structure holding the source code. The leaf nodes of the tree are the components and the higher nodes are the system's domains and subdomains.

  • order_entry/ordering/payment is the Payment Processing component.
  • order_entry/processing/fulfillment is the Order Fulfillment component.
  • Other leaves shown: validation, order_history and shipment.

Analysing a system's directories or namespaces reveals its logical architecture.

8.2 Logical versus physical architecture

A logical architecture is a system's logical components and how they interact. It usually shows actors and may show a repository (not a database) to clarify where data is used or transferred. It typically does not show user interfaces, databases or services; its components should match the directory structure and namespaces.

A physical architecture includes physical artifacts: services, user interfaces, databases. It should closely represent one or more of the styles in Part II (microservices, layered, event-driven and so on).

Do not skip the logical architecture. Many architects go straight to physical, which the authors advise against:

  • A physical architecture does not always show where the functionality is and how it fits together; payment processing may be spread across several services.
  • It gives development teams no guidance on building a monolithic or distributed system or organising code, leading to unstructured architectures that are hard to maintain, test and deploy.

A logical architecture is generally independent of the physical one: it focuses on what the system does, how functionality is demarcated and how parts interact. The architect may not yet know whether the components go into one deployment unit or separate services.

8.3 Creating a logical architecture

Identifying components works best as an iterative process: produce candidates, then refine them through a feedback loop that essentially never stops.

  1. Identify the initial core components.
  2. Assign user stories or requirements to them.
  3. Analyse roles and responsibilities to check the stories belong.
  4. Analyse architectural characteristics to see if components should be split or combined.
  5. Restructure (optionally refine) and repeat.

The cycle works for greenfield systems and whenever a feature is added or changed. Example: letting order-entry users pick up items at a store instead of shipping requires scheduling code and changes to ordering, which may mean new components, changed ones or both.

Identifying core components

  • A common mistake is spending too much effort getting the initial components perfect
    • Make a "best guess" from the core functionality and refine
    • It is better to iterate while you learn than to try to be perfect when you know least.
  • Often the architect needs few or none of the requirements to start: the initial components come from major user actions or the main processing workflows.
  • Think of initial components as empty buckets: placeholders whose names suggest a role until user stories fill them.

Three common approaches (the first two are useful; the third is an antipattern):

The Workflow approach

Use the major happy-path workflows (or the main request-processing workflow). Order-entry example, one component per step:

Workflow step Component
User browses the catalogue Item Browser
User places an order Order Placement
User pays Order Payment
Email order details Customer Notification
Prepare the order Order Fulfillment
Ship the order Order Shipment
Email that it shipped Customer Notification
Track shipment Order Tracking

Not every step yields a new component (steps 4 and 7 share Customer Notification). Model the major workflows, not all of them: the rest will evolve.

The Actor/Action approach

Useful with several actors. Identify each actor's major actions; the system is always an actor too, doing automated work such as billing and replenishing stock. Order-entry example:

Actor Action Component
Customer Search for items Item Search
Customer View item details Item Details
Customer Place an order Order Placement
Customer Cancel an order Order Cancel
Customer Register as new customer Customer Registration
Customer Update customer information Customer Profile
Order packer Select the box size Order Fulfillment
Order packer Mark ready for shipment Order Fulfillment
Order packer Ship the order Order Shipment
System Adjust inventory Inventory Management
System Order more stock Supplier Ordering
System Apply payment Order Payment

It usually produces more components than the Workflow approach, but both identify initial components and how they communicate before detailed requirements exist.

The Entity Trap

Starting from entities (Customer, Item, Order) and creating Customer Manager, Item Manager and Order Manager components. Three reasons to avoid it:

  • Ambiguous names.
    • "What does Order Manager do?" "It manages orders." Compare Validate Order
    • Suffixes such as Manager, Supervisor, Controller, Handler, Engine or Processor are a sign you are in the trap.
  • Dumping grounds. Every bit of order functionality (validation, placement, history, fulfilment, shipping, tracking) lands in one component, like the "kitchen sink" utility classes everyone has written.
  • Too coarse-grained. Components do too much, so they are hard to maintain, test and deploy, and so not very reliable.

If a system truly is entity based and does only CRUD (create, read, update, delete), it needs a CRUD framework, tool or no-code/low-code environment, not an architecture.

Assigning user stories to components

An iterative step that starts filling the buckets (stories are never fully known up front). Three stories and four existing components (Order Placement, Order Fulfillment, Order Shipment, Inventory Management):

User story Component
Customer: validate my order is complete and correct Order Placement
Order preparer: know what box size to use Order Fulfillment
Customer: receive an email each time the order status changes Customer Notification (new)

The third has no good home: Placement, Fulfillment and Shipment could each send mail, but the code lives in one directory, and copying it into three components is a bad idea. So the architect defines a new component, and the other three must communicate with it.

Analysing roles and responsibilities

Check cohesion: how, and how much, a component's operations interrelate. Components can grow too big even when all their operations relate.

Example: eight requirements assigned to Order Placement (validate the order, display the cart, determine the shipping address, collect payment information, generate an order ID, apply payment, adjust inventory counts, email an order summary). Its role-and-responsibility statement reads as a long chain of "and", "also", "in addition", with commas.

  • A test for too much responsibility: look for conjunctive phrases such as and, also, in addition, as well as, and excessive commas.
  • The code would sit in one directory or namespace (such as com/app/order/placement), too much for one place.

Analysing architectural characteristics

Characteristics such as scalability, reliability, availability, fault tolerance, elasticity and agility may influence component size.

  • Breaking up a large component makes each part easier to maintain and test (agility) and gives better scalability, elasticity and fault tolerance.
  • Example: if one part handles hundreds of concurrent users and another only a few, a purely functional design might assign one user-interaction component, but characteristics suggest subdividing.
  • Because the architect must know the characteristics first, logical architecture work usually follows the characteristics analysis.

Restructuring components

  • Feedback is critical
    • Iterate on component designs with developers: edge cases and discoveries cannot all be foreseen, and deeper building gives a more nuanced understanding of where behaviour belongs.
  • Expect to restructure often, in greenfield systems and any under frequent maintenance.

8.4 Component coupling

Components are coupled when they communicate or when a change to one might impact another. The more coupled, the harder to maintain and test.

  • Coupling needs no direct communication (Figure 8-11): Order Placement and Order Shipment are coupled "because a change in one impacts the other, even though they aren't communicating".

Static coupling

Components communicate synchronously. Two types:

  • Afferent coupling (CA; incoming, fan-in):
    • how many components depend on the target
    • Customer Notification is called by Order Placement and Order Shipment, so its afferent coupling level is 2.
  • Efferent coupling (CE; outgoing, fan-out): how many components the target depends on. Order Placement depends on Order Fulfillment, so its efferent coupling is 1.

Temporal coupling

  • Nonstatic dependencies, usually based on timing or transactions (single units of work). Example: Order Placement must be invoked before Order Shipment, so they are temporally coupled.
  • It is hard to detect with current tooling; usually found through design documents or error conditions.

The Law of Demeter

Loose coupling makes a system more maintainable, easier to test, less risky to deploy and more reliable (changes hit fewer components). One technique is the Law of Demeter, or Principle of Least Knowledge: a component or service should have limited knowledge of other components or services.

  • Greek myth: Demeter produced all the grain for the world but had no idea what people did with it. She was effectively decoupled from the world.
  • Example (Figure 8-14):
    • after accepting an order, Order Placement tells Inventory Management to decrement stock
    • if stock is low it also tells Supplier Ordering to order more and Item Pricing to adjust the price
    • finally it tells Email Notification to email the customer. It does not do those jobs, but it knows they must happen, and more knowledge means tighter coupling.

  • Adding a component between Order Placement and Inventory Management to hide that inventory must be decremented would not reduce Order Placement's outgoing coupling, so that point stays.
  • But the knowledge that low supply means "order more stock and adjust the price" can move into Inventory Management (Figure 8-15), reducing Order Placement's coupling.
  • Catch: this also raises Inventory Management's coupling. The Law of Demeter does not necessarily reduce system-wide coupling; it redistributes it.

8.5 Case study: Going, Going, Gone

If a team has no special constraints and wants a general-purpose decomposition, the Actor/Action approach works well. GGG has three roles: the bidder, the auctioneer and the system.

Role Main actions
Bidder View live video stream; view live bid stream; place a bid
Auctioneer Enter live bids into the system; receive online bids; mark item as sold
System Start auction; make payment; track bidder activity

The components:

  • Video Streamer: streams a live auction to users.
  • Bid Streamer: streams bids as they occur. Both streamers give bidders a read-only view.
  • Bid Capture: captures bids from the auctioneer and bidders.
  • Bid Tracker: tracks bids and is the system of record.
  • Auction Session: starts an auction; when a bidder wins and the item ends, triggers payment and resolution, including telling bidders the next item.
  • Payment: a third-party processor for credit card payments.

Apply the characteristics. Bid Capture handling both auctioneer and bidders makes functional sense, but the auctioneer does not need the scalability or elasticity of bidders, who may number in the thousands. Conversely the auctioneer needs more reliability (no dropped connections) and availability: a bidder failing to log in is bad for business, but the same for the auctioneer is disastrous.

Split it. Bid Capture becomes Bid Capture and Auctioneer Capture, with links from Auctioneer Capture to Bid Streamer (to show online bidders live bids) and to Bid Tracker. Bid Tracker now unifies two very different streams: the auctioneer's single stream and the many bidder streams.

This is unlikely to be the final design (registration, payment administration and more remain), but it is a good starting point. There is not one "true design": assess trade-offs as objectively as possible and choose the least worst set.

Summary points

  • Components are the building blocks; logical architecture comes before physical.
  • Iterate: identify, assign stories, check cohesion, apply characteristics, restructure.
  • Workflow and Actor/Action work; the Entity Trap does not.
  • Count afferent and efferent coupling, watch temporal coupling, and use the Law of Demeter knowing it only redistributes coupling.
Terms to carry forward
  • Component-based thinking; logical component (namespace or directory).
  • Logical versus physical architecture.
  • Empty buckets: initial components before stories are assigned.
  • Workflow, Actor/Action, Entity Trap.
  • Conjunctive phrases test for too much responsibility.
  • Afferent (CA) and efferent (CE) coupling; temporal coupling.
  • Law of Demeter (Principle of Least Knowledge).
  • System of record: the authoritative store (Bid Tracker in GGG).
