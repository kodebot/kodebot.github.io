Fundamentals of Software Architecture 10: Layered Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 10. Previous: Fundamentals of Software Architecture 9: Foundations. Next: Fundamentals of Software Architecture 11: The Modular Monolith Architecture Style.

Takeaways
  • Layered (n-tiered) is one of the most common styles and the de facto standard for many legacy applications because it is simple, familiar and cheap. "Just start coding" usually ends up here.
  • Most have four layers (Presentation, Business, Persistence, Database); the physical deployment has three variants.
  • It is technically partitioned, so a domain such as "customer" is smeared across every layer, which fits DDD poorly.
  • Closed layers give layers of isolation; open layers (for example a Services layer) are added deliberately. Watch for the Architecture Sinkhole antipattern (the 80-20 rule).
  • Strengths: cost and simplicity. Weak on everything else as it grows: 1 star for modularity, maintainability, deployability, evolvability, scalability, elasticity, fault tolerance; testability 2; responsiveness 3. Quanta = 1.

10.1 Topology

Components sit in logical horizontal layers, each with a specific role (such as presentation or business logic).

  • No rule fixes the number or types of layers, but most have four: Presentation, Business, Persistence, Database.
  • Some merge Business and Persistence, especially when persistence logic (SQL or HSQL) is embedded in Business components. Small applications may have three layers
    • large, complex ones five or more.

Three physical (deployment) variants:

  1. Presentation, Business and Persistence in one deployment unit, with the Database as a separate external database or filesystem.
  2. Presentation in its own unit, Business and Persistence combined in a second, and the Database external.
  3. All four layers in one deployment, including the database. Useful for small applications with an embedded or in-memory database, such as mobile apps. Many on-premises products ship this way.

Responsibilities. Each layer abstracts part of the work for a business request:

  • The Presentation layer handles UI and browser communication. It only needs to display customer data in a format, not know how to get it.
  • The Business layer runs business rules
    • It does not care how data is formatted for the screen or where it comes from: it gets data from Persistence, applies logic (calculate, aggregate) and passes it up.
  • This separation of concerns makes role-and-responsibility models easy, and lets developers use their technical specialism (presentation or persistence logic)
    • The cost is a lack of overall holistic agility: the whole system's ability to respond quickly to change.

Technically partitioned. As Chapter 9 showed, components are split by technical role, not domain. Any business domain (customer, say) is spread through the Presentation, Business, Rules, Services and Database layers, making changes to it hard. So a DDD approach does not fit the style well.

10.2 Style specifics

Layers of isolation

A layer is closed or open. If closed, a request moving down cannot skip a layer: Presentation goes to Business, then Persistence, then Database.

  • For a simple retrieval it would be faster for Presentation to read the database directly (the early-2000s Fast-Lane Reader pattern), but that needs Business and Persistence to be open.
  • Which is better? The answer is layers of isolation:
    • changes in one layer generally do not affect others as long as the contracts between layers stay unchanged
    • Each layer knows little of the others' internals.
  • To support this, layers on the major request flow must be closed
    • If Presentation reaches Persistence directly, a Persistence change hits both Business and Presentation: tightly coupled, "very brittle", and hard and expensive to change.
  • Isolation also lets any layer be replaced without affecting the others (given well-defined contracts and the Business Delegate pattern, which reduces coupling between business services and the UI by acting as an adapter)
    • Example: swap the old UI framework for a new one inside Presentation.

Adding layers

Sometimes a layer should be open. Suppose the Business layer has shared objects (date and string utilities, auditing, logging) and you decide Presentation may not use them.

  • Figure 10-4:

    • Presentation can reach the Business layer, so it can reach the shared objects, which is hard to govern.
  • Figure 10-5: add a Services layer holding the shared objects. Business is closed, so Presentation is architecturally barred from them.
  • Mark the new Services layer open, otherwise Business would have to go through it to reach Persistence. Open lets Business use it (solid arrow) or bypass it (dotted arrow).
  • Document which layers are open or closed, and why. Failing to do so usually yields tightly coupled, brittle architectures hard to test, maintain and deploy.

Architecture Sinkhole antipattern

Every layered architecture has some requests that are simply passed layer to layer with no business logic.

  • Example:
    • Presentation asks for a customer's name and address, Business passes it to Rules, which passes it to Persistence, which makes a simple SQL call
    • The data returns up the stack with no aggregation, calculation, rules or transformation.
  • The cost is unnecessary object instantiation and processing, draining memory and performance.
  • Measure the percentage of requests like this. The 80-20 rule is a good guide: 20% sinkholes is acceptable; 80% is a sign layered is the wrong style for the domain.
  • Another fix is to make all layers open, accepting that change becomes harder to manage.

10.3 Data topologies, cloud, risks

  • Data:
    • traditionally a monolithic system with a single monolithic database
    • The shared Persistence layer often maps object hierarchies between object-oriented languages and the set-based relational world.
  • Cloud:
    • because the style is monolithic and partitioned into layers, cloud options are limited to deploying one or more layers with a cloud provider
    • The technical partitioning suits separated deployments, but latency between on-premises servers and the cloud can bite because workflows usually pass through most layers.
  • Common risks:
    • no fault tolerance: monolithic deployment and no modularity mean one small out-of-memory condition crashes the whole application
    • Availability suffers from a high mean time to recover (MTTR): startup takes about 2 minutes for small applications to 15 minutes or more for large ones.

10.4 Governance

Excellent news: the style is so common that the authors of the original structural testing tools built them for it. The Chapter 6 fitness function was created for it (Example 10-1):

layeredArchitecture()
    .layer("Controller").definedBy("..controller..")
    .layer("Service").definedBy("..service..")
    .layer("Persistence").definedBy("..persistence..")
    .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
    .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
    .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Service")
  • The architect names the layers after packages (in ArchUnit syntax two periods either side of a package name indicate its ownership), then defines the allowed communication, governing the open and closed layers.
  • Fitness function libraries support layered architecture extremely well, automating governance of the layer relationships during implementation.

10.5 Team topology considerations

Unlike some styles, layered is generally independent of team topologies and works with any configuration:

Team type Why it fits
Stream-aligned The architecture is small and self-contained and represents a single journey through the system; teams own the flow through every layer
Enabling Highly modular by technical concern: specialists can experiment with one or more layers (a new UI library in Presentation) without affecting the rest
Complicated-subsystem Each layer does one specific task: Persistence is a hook for a team needing operational data for analytics, without touching the layers stream-aligned teams own
Platform Many tools exist, but as with monoliths in general it becomes unwieldy as it grows: strain on database connections, memory, performance, concurrent users, making the platform team's work increasingly difficult

10.6 Style characteristics

A one-star rating means the characteristic is not well supported; five stars means it is one of the style's strongest features. Definitions are in Chapter 4.

  • Cost and simplicity
    • are the primary strengths: monolithic, simpler and easier to understand than distributed styles, and cheap to build and maintain
    • But ratings diminish quickly as the code base grows.
  • Deployability (1 star)
    • is low because deployments are high risk, infrequent and ceremonial
    • A three-line change to a class means redeploying the whole unit, so database, configuration or other changes can sneak in beside it, and it is bundled with dozens of other changes.
  • Testability (2 stars)
    • is low because developers will not run the whole regression suite for three lines (if they have one)
    • It earns two stars, not one, because you can mock or stub components or a whole layer.
  • The engineering characteristics all start well but degrade as the code base grows.
  • Elasticity and scalability (1 star)
    • come from monolithic deployment and lack of modularity
    • You can make some functions scale more, but it needs complex techniques (multithreading, internal messaging, parallel processing) the style suits poorly
    • The architecture quantum is always 1 (monolithic UI, database and backend), so it scales only to a point.
  • Responsiveness (3 stars): achievable by careful design and improved with caching and multithreading, but held back by no inherent parallel processing, closed layering and the Architecture Sinkhole.

10.7 When to use and when not to use

  • Use
    • it for small, simple applications or websites
    • as a starting point under very tight budget and time constraints
    • and when architects are still deciding whether a more complex style is needed but must begin development. It is probably one of the lowest-cost styles.
  • When doing so, minimise code reuse and keep object hierarchies shallow to preserve modularity and ease a later move to another style.
  • Do not use it for large applications and systems: maintainability, agility, testability and deployability suffer as it grows, so more modular styles suit them better.

10.8 Examples and use cases

Operating systems (Linux, Windows) use layers for separation of concerns:

  • Hardware: CPU, memory, I/O devices.
  • Kernel: hardware abstraction, memory management, process scheduling.
  • System Call Interface: interacts with the kernel to provide system services.
  • User: applications and utilities.

The networking OSI model and the internet's TCP/IP:

  • Physical: physically transmits data.
  • Data Link: error detection and frame synchronisation.
  • Network: routing (for example IP).
  • Transport: reliable transmission (for example TCP).
  • Application: services such as email (SMTP), file transfer (FTP) and web browsing (HTTP).

Any architecture that values separation of concerns, maintainability and independent layer development benefits. It is also common for teams optimising feasibility: can we deliver the stated scope in the time and with the resources available? An investor-funded organisation that must ship fast often chooses it, even if parts are rewritten later.

Summary points

  • Four logical layers; three deployment variants; technically partitioned; quanta = 1.
  • Keep layers on the main flow closed for isolation; add open layers deliberately and document them.
  • Beware the Architecture Sinkhole; apply the 80-20 rule.
  • Cheap and simple, but modularity, deployability, scalability and fault tolerance rate 1 star and degrade as it grows.
Terms to carry forward
  • Layered (n-tiered) architecture; technical partitioning.
  • Closed and open layers; layers of isolation.
  • Fast-Lane Reader pattern; Business Delegate pattern.
  • Architecture Sinkhole antipattern; 80-20 rule.
  • Architecture by Implication and Accidental Architecture antipatterns.
  • MTTR (mean time to recover).
  • Star ratings scorecard (Chapter 4 definitions).
