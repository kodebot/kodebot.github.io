Fundamentals of Software Architecture 11: The Modular Monolith Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 11. Previous: Fundamentals of Software Architecture 10: Layered Architecture Style. Next: Fundamentals of Software Architecture 12: Pipeline Architecture Style.

Takeaways
  • A single deployment unit (WAR, EAR, .NET assembly) with functionality grouped by domain: a domain-partitioned monolith. New in this edition because DDD and domain partitioning made it popular.
  • Domains or subdomains are modules, organised either as a monolithic structure (one code base, split by directory or namespace) or a modular structure (each module its own artifact, such as a JAR or DLL, combined at deployment).
  • Module communication is "never a good thing" but sometimes necessary: use peer-to-peer calls or a mediator. Too much reuse or communication turns it into a Big Ball of Mud (or DLL/JAR Hell).
  • Governance with fitness functions: check modules exist, limit coupling points, forbid specific module dependencies.
  • Strengths: cost, simplicity, modularity. Deployability and testability get 2 stars (slightly better than layered). Scalability, elasticity and fault tolerance get 1. Quanta = 1.

11.1 Topology

It is a monolithic architecture: deployed as one unit (a WAR file, a single .NET assembly, an EAR file on the Java platform, and so on). Because it is domain partitioned, its shape is a single deployment unit with functionality grouped by domain area.

Contrast with layered. In a layered architecture components are organised by technical capability, so customer-profile presentation logic might live at com.app.presentation.customer.profile: the third node is the technical layer.

In a modular monolith the same component is com.app.customer.profile: the third node is the domain. A complex component may split by technical concern after the domain, such as com.app.customer.profile.presentation or com.app.customer.profile.business.

11.2 Style specifics

Domains (or subdomains) are called modules. Two ways to organise them:

Monolithic structure

  • All modules live in one source-code repository and deploy together. Each module is a separate high-level directory holding its components and subdomains (Figure 11-2).
  • Example namespaces for an order-entry system:
com.orderentry.orderplacement
com.orderentry.inventorymanagement
com.orderentry.paymentprocessing
com.orderentry.notification
com.orderentry.fulfillment
com.orderentry.shipping
  • Pro: the simplest option; all code in one place, so easier to maintain, test and deploy.
  • Con:
    • it needs strict governance to keep module boundaries
    • Developers tend to reuse too much code across modules and allow too much communication between them, which can turn it into an unstructured Big Ball of Mud.

Modular structure

  • Each module is a self-contained artifact (JAR, DLL) and the modules are assembled into one deployment unit at deployment time (Figure 11-3, JARs on the Java platform).
  • Pros:
    • teams can work on separate modules, often in their own repository
    • it suits largely independent modules and large, complex systems where each module needs different expertise or business knowledge
    • developers are less apt to over-reuse code or over-communicate
    • cleaner boundaries and separation of concerns.
  • Con: it loses effectiveness when dependent modules need to communicate. Then the monolithic structure is more effective.

Module communication

"Communication between modules is never a good thing in this architectural style", but is often necessary. In Figure 11-2, OrderPlacement must talk to InventoryManagement (adjust stock and perhaps order more) and to PaymentProcessing (apply payment). Two options:

Peer-to-peer. A class in one module instantiates a class in another and calls its methods (Figure 11-4).

  • In the monolithic structure it is too convenient to instantiate any class in another module, an easy path from well structured to Big Ball of Mud (Figure 9-1).
  • In the modular structure the other module's classes sit in external artifacts, so the module will not compile without them: a compile-time dependency
    • The usual fix is a shared interface class in a separately shared JAR or DLL so each module compiles independently
    • Too much communication still ends in DLL Hell (or JAR Hell on Java).

Mediator. A mediator component forms an abstraction layer between modules, acting as an orchestrator that accepts requests and delivers them to the right module (Figure 11-5).

  • It decouples modules, but each module is now coupled to the mediator: coupling is simplified, not removed.
  • The mediator, not the dependent modules, needs an API or interface to invoke the other modules' functionality.

11.3 Data topologies

  • Deployed as one unit, it usually has a monolithic database. A single database reduces inter-module communication because the data is shared.
  • If modules are independent and perform specific functions they can also have their own databases with contextual data, even though the architecture is monolithic.

11.4 Cloud considerations

It can be deployed in the cloud (especially small systems), but its monolithic nature makes it less able to use on-demand provisioning. Smaller systems can still use cloud services such as file storage, databases and messaging.

11.5 Common risks

  • It can get too big to maintain, test and deploy. Monoliths are not bad in themselves; "too big" varies by system. Warning signs:
    • changes take too long
    • changing one area unexpectedly breaks others
    • team members get in each other's way
    • startup takes too long
  • Going overboard with code reuse blurs module boundaries and leads to the unstructured monolith: so interdependent it cannot be unravelled.
  • Too much inter-module communication.
    • Some is normal in a complex workflow, but too much suggests the domains were ill-defined
    • rethink them to fit complex workflows and interdependencies.

11.6 Governance

The primary artifact is the module, usually shown by directory, namespace or package. So the first automated governance is to define the modules and ensure compliance. Tools: ArchUnit (Java), ArchUnitNet and NetArchTest (.NET), PyTestArch (Python), TSArch (TypeScript and JavaScript).

Example 11-1 (pseudocode) checks that all source falls under a defined module namespace:

# The following namespaces represent the modules in the system
LIST module_list = {
    com.orderentry.orderplacement,
    com.orderentry.inventorymanagement,
    com.orderentry.paymentprocessing,
    com.orderentry.notification,
    com.orderentry.fulfillment,
    com.orderentry.shipping
}

# Get the list of namespaces in the system
LIST namespace_list = get_all_namespaces(root_directory)

# Make sure all the namespaces start with one of the listed modules
FOREACH namespace IN namespace_list
{
    IF NOT namespace.starts_with(module_list)
    {
        send_alert(namespace)
    }
}

A developer who adds a high-level namespace or directory outside the defined modules gets an alert. This works well for the monolithic structure; it is harder for the modular structure, because code may not share one repository. There each module is tested separately (Example 11-2, as printed):

# Get the list of namespaces in the system
LIST namespace_list = get_all_namespaces(root_directory)

# Make sure all the namespaces start with com.orderentry.inventorymanagement
FOREACH namespace IN namespace_list
{
    IF NOT namepace.starts_with("com.orderentry.inventorymanagement")
    {
        send_alert(namespace)
    }
}

Limit communication. "Too much" is subjective, but architects should minimise interdependencies. Example 11-3 (as printed in the book) alerts when a module exceeds five coupling points:

# Walk the directory structure, gathering modules and the source code files
# contained within those modules
LIST module_list = {
    com.orderentry.orderplacement,
    com.orderentry.inventorymanagement,
    com.orderentry.paymentprocessing,
    com.orderentry.notification,
    com.orderentry.fulfillment,
    com.orderentry.shipping
}

MAP module_source_file_map
FOREACH module IN module_list
{
    LIST source_file_list = get_source_files(module)
    ADD module, source_file_list TO module_source_file_map
}

# Determine how many references exist for each source file and send an alert if
# the system's total dependency count is greater than 5
FOREACH module, source_file_list IN module_source_file_map
{
    FOREACH source_file IN source_file_list
    {
        incoming count = used_by_other_module(source_file, module_source_file_map)
        {
            outgoing_count = uses_other_module(source_file)
            {
                total_count = incoming count + outgoing count
            }
            IF total_count > 5
            {
                send_alert(module, total_count)
            }
        }
    }
}

Forbid specific dependencies. For example, in Figure 11-2 OrderPlacement should not talk to Shipping. Example 11-4 (ArchUnit):

public void order_placement_cannot_access_shipping()
{
    noClasses().that()
        .resideInAPackage("..com.orderentry.orderplacement..")
        .should().accessClassesThat()
        .resideInAPackage("..com.orderentry.shipping..")
        .check(myClasses);
}

11.7 Team topology considerations

Domain partitioning works best when teams are also aligned by domain (cross-functional teams with specialisation), who can take a requirement from presentation logic to database. Teams organised by technical category (UI, backend, database) do not suit it: domain requirements then need much communication and collaboration, which is often difficult.

Team type Why it fits
Stream-aligned Own the flow end to end, matching the monolithic, self-contained shape
Enabling High modularity and separation of concerns: specialists experiment by adding modules with minimal impact on existing ones
Complicated-subsystem Each module performs a specific domain role (such as PaymentProcessing), so people can focus on complicated processing independently
Platform Common tools, services, APIs and tasks fit the high modularity

11.8 Style characteristics

It is a domain-partitioned architecture with a monolithic deployment, so the architecture quantum is typically 1.

  • Overall cost, simplicity and modularity
    • are the main strengths: none of distributed styles' complexity, simpler to understand, low cost to build and maintain
    • modularity comes from separating concerns between modules.
  • Deployability and testability (2 stars) rate slightly higher than layered because of the modularity, but it is still a monolith, so ceremony, risk, deployment frequency and completeness of testing hold the scores down.
  • Elasticity and scalability (1 star)
    • from monolithic deployment
    • Scaling some functions needs very complex techniques (multithreading, internal messaging, parallel processing) that suit it poorly.
  • Fault tolerance (1 star): one out-of-memory condition crashes the whole unit; availability suffers from a high MTTR, with startup usually measured in minutes.

11.9 When to use and when not to use

Use it:

  • under tight budget and time constraints (simple and low cost)
  • when starting a new system, or when direction is still unclear: it is often more effective to begin with a modular monolith and later move to service-based (Chapter 14) or microservices (Chapter 18) than to jump straight to a distributed style
  • for domain-focused teams (cross-functional with specialisation), each owning a module end to end with minimal coordination
  • when most changes are domain based (for example, adding expiration dates to items in a wishlist)
  • for teams practising DDD

Do not use it:

  • when a system needs high scalability, elasticity, availability, fault tolerance, responsiveness or performance
  • when most changes are technically oriented, such as continually replacing the UI or database technology
    • Because the architecture is domain partitioned, such changes hit every module and need heavy coordination between domain teams
    • layered (Chapter 10) is much better then.

11.10 Example: EasyMeals

A new delivery-based neighbourhood restaurant for busy working people: customers order dinner online and get it at the door within an hour. It is small and local, with low scalability and responsiveness needs and a limited budget, so the modular monolith suits it.

The modules, with namespaces com.easymeals.<module>: placeorder, payment, prepareorder, delivery, recipes, inventory. Customers reach PlaceOrder and PaymentProcessing through a dedicated user interface.

Module Role Components (namespaces)
PlaceOrder View the menu, select items, add name, address and payment information, submit the order menu, shoppingcart, customerdata, paymentdata, checkout
PaymentProcessing Apply payment (credit cards, debit cards, PayPal). Modularity makes it easy to add another type such as loyalty points creditcard, debitcard, paypal
PrepareOrder After payment, PlaceOrder talks to it; shows the whole order to the kitchen, who mark it ready for delivery displayorder, ready
Delivery Assign a delivery person and address; they mark it delivered and record issues (an aggressive dog, a customer not home) assign, issues, complete
Recipes Cooks and management add menu items and maintain ingredients and measurements view, maintenance
IngredientsInventory Ensure enough ingredients for the menu; a more complex module with an AI component that forecasts sales to automate weekly procurement maintenance, forecasting, ordering, suppliers, invoices

A module is made up of one to many components (Chapter 8). The simplicity and modularity make it relatively easy to find and change code to fix a bug or add a feature.

Summary points

  • One deployment unit, domain-partitioned modules; namespace com.app.<domain>.<component>.
  • Monolithic structure (simple, needs governance) versus modular structure (cleaner boundaries, weak when modules must communicate).
  • Communicate by peer-to-peer or mediator; keep it minimal; govern with fitness functions.
  • Great start for new systems and domain-focused teams; poor for operational characteristics or technical-change-heavy work.
Terms to carry forward
  • Modular monolith; domain-partitioned; module.
  • Monolithic structure versus modular structure (JAR or DLL per module).
  • Peer-to-peer versus mediator communication.
  • DLL Hell and JAR Hell.
  • Unstructured monolith.
  • Module governance fitness functions (ArchUnit, ArchUnitNet, NetArchTest, PyTestArch, TSArch).
