Fundamentals of Software Architecture 12: Pipeline Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 12. Previous: Fundamentals of Software Architecture 11: The Modular Monolith Architecture Style. Next: Fundamentals of Software Architecture 13: Microkernel Architecture Style.

Takeaways
  • Pipes and filters: filters hold the functionality, pipes carry data one way, usually point to point. It is the principle behind Unix shells (Bash, Zsh) and echoes MapReduce and functional programming.
  • Four filter types: producer (start), transformer (map), tester (reduce-like check or switch) and consumer (end). Filters are stateless, self-contained and do one task.
  • Usually monolithic; each filter can be deployed as a service to go distributed. It suits the cloud (for example AWS Step Functions with a lambda per filter).
  • Risks: overloaded filters, bidirectional communication, hard error handling, and contract changes between filters. Govern with tags (annotations or attributes).
  • Ratings: technically partitioned, quanta 1; simplicity 4; testability, evolvability and responsiveness 3; modularity, maintainability and deployability 2; scalability, elasticity and fault tolerance 1.

12.1 Topology

The pipeline architecture (pipes and filters) is one of the fundamental styles: it follows as soon as developers split functionality into discrete parts.

Most know it as the principle behind Unix shells (Bash, Zsh); functional programmers see parallels in language constructs, and tools using the MapReduce model follow the same basic topology. The chapter's examples are low level, but it also works for higher-level business applications.

  • Two component types: filters hold the system functionality and perform a specific business function; pipes transfer data to the next filter(s).
  • Pipes form one-way, usually point-to-point communication.
  • The isomorphic shape: a single deployment unit, with functionality in filters connected by unidirectional pipes.

12.2 Style specifics

Most implementations are monolithic, but each filter (or set of filters) can be deployed as a service, giving a distributed architecture with synchronous or asynchronous remote calls. Either way there are only two architectural components, filters and pipes.

Filters

  • Self-contained and independent of other filters; generally stateless; should do one task only. Composite tasks are handled by a sequence of filters.
  • A filter may be several class files, so it is a component (Chapter 8); even a single-class filter is a component.

Four types:

Type Role Examples
Producer The starting point, outbound only; sometimes called the source A user interface; an external request to the system
Transformer Accepts input, optionally transforms some or all of it, forwards to the outbound pipe. Functional programmers see map Enhance data, transform data, perform a calculation
Tester Accepts input, tests it against one or more criteria, optionally produces output. Similar to reduce Check all data is valid; act as a switch ("don't forward to the next filter if the order amount is under five dollars")
Consumer The termination point Persist the final result to a database or show it on a UI screen

Compositional reuse. The unidirectional simplicity of pipes and filters encourages reuse, as shell users know. The "More Shell, Less Egg" blog tells how Donald Knuth was asked for a program to read a text file, find the n most frequent words and print them sorted by frequency.

He wrote over 10 pages of Pascal, designing and documenting a new algorithm. Doug McIlroy answered with a shell script small enough for a social media post:

tr -cs A-Za-z '\n' |
tr A-Z a-z |
sort |
uniq -c |
sort -rn |
sed ${1}q

Even Unix shell designers are often surprised at the inventive uses developers find for such composites.

Pipes

  • The communication channel between filters: typically unidirectional and point to point, from one source to another.
  • The payload can be any data format, but architects favour smaller amounts of data for performance.
  • If a filter or group is a separate service, the pipe is a one-way remote call (REST, messaging, streaming or another protocol).
  • In either topology pipes can be synchronous or asynchronous; in monolithic deployments asynchronous communication uses threads or embedded messaging.

12.3 Data topologies

Most are monoliths with a single monolithic database, but it varies from a single database to one per filter.

Figure 12-2 is a pipeline for a typical continuous fitness function running in production that analyses an operational characteristic such as responsiveness or scalability:

  1. Capture Raw Data loads a separate database of raw data.
  2. It sends the raw data through a pipe to Time Series Selector, which reads configuration (such as the period to analyse) from a separate database.
  3. The transformed data goes through a pipe to Trend Analyzer, which analyses it and stores analytics in another database.
  4. The analytics go through a final pipe to Graphing Tool, which ends the pipeline by generating a graphical report.

12.4 Cloud considerations

  • A good fit for the cloud: high modularity and separate filter types. Most pipelines are not overly complex, so they also deploy fine as a monolith with all filters in one unit.
  • Filters also work as distributed functions
    • On AWS the pipeline can be an AWS Step Function with each filter a separate lambda
    • Step Functions offer two workflows: Standard (each step executes exactly once) and Express (each step can execute more than once); the style works with both.
  • Other options: serverless functions, containerised functions, or one service containing all four filter components.

The Figure 12-2 example as a Step Function:

{
    "Comment": "Measure and analyze scalability trends.",
    "StartAt": "Capture Raw Data",
    "States": {
        "Capture Raw Data": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:account_id:function:raw_data_capture",
            "Next": "Time Series Selector"
        },
        "Time Series Selector": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:account_id:function:time_series_selector",
            "Next": "Trend Analyzer"
        },
        "Trend Analyzer": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:account_id:function:trend_analyzer",
            "Next": "Graphing Tool"
        },
        "Graphing Tool": {
            "Type": "Task",
            "Resource": "arn:aws:lambda:region:account_id:function:graphing_tool",
            "End": true
        }
    }
}

12.5 Common risks

  • Overloaded filters. The aim is single-purpose filters; the most common risk is giving a filter too much responsibility. Governance (below) helps.
  • Bidirectional communication.
    • Pipes are meant to be unidirectional to keep a clean separation of concerns
    • If you need it, either pipeline is the wrong style or the filters are too complex and the functionality is not demarcated correctly.
  • Error handling. Once started, it is hard to decide how to exit and recover. Identify the possible fatal error conditions before defining the architecture.
  • Contracts between filters. Each pipe has a contract (data and possibly types). Changing one needs strict governance and testing so receiving filters do not break.

12.6 Governance

Operational characteristics (responsiveness, scalability, availability) are governed per use case. Structurally, architects use the role and responsibility of each filter type. It is easy to overload filters and turn the pipeline into an unstructured monolith.

It is hard to write a fitness function that checks a producer is truly the start of the pipeline or that a tester really performs a conditional check. One technique is tags: annotations in Java, custom attributes in C#. They do no work; they give metadata. Tagging a filter's starting class tells developers what type it is, helping prevent overloading or functions that do not fit the type.

Java tag for the four filter types:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Filter
{
    public FilterType[] value();

    public enum FilterType
    {
        PRODUCER,
        TESTER,
        TRANSFORMER,
        CONSUMER
    }
}

C# custom attribute:

[System.AttributeUsage(System.AttributeTargets.Class)]
class Filter : System.Attribute
{
    public FilterType[] filterType;

    public enum FilterType
    {
        PRODUCER,
        TESTER,
        TRANSFORMER,
        CONSUMER
    };
}

A filter can be several class files (the Trend Analyzer, say), so a second tag marks the class that is the filter's entry point:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface FilterEntrypoint {}

[System.AttributeUsage(System.AttributeTargets.Class)]
class FilterEntrypoint : System.Attribute {}

Developers then tag the entry-point class with its type. For the Trend Analyzer transformation filter:

@FilterEntrypoint
@Filter(FilterType.TRANSFORMER)
public class TrendAnalyzerFilter
{
    ...
}

[FilterEntrypoint]
[Filter(FilterType.TRANSFORMER)]
class TrendAnalyzerFilter
{
    ...
}

This will not stop every developer making a transformer do testing logic (a tester's job), but it gives additional context.

12.7 Team topology considerations

Generally independent of team topologies; works with any configuration:

Team type Why it fits
Stream-aligned Small, self-contained, a single flow through the system; teams own it start to end
Enabling Highly modular: add filters without affecting the flow. Example: add a transformer after Time Series Selector to try an alternative trend analysis on the same data as Trend Analyzer
Complicated-subsystem Each filter does one specific task; unidirectional hand-offs let members focus narrowly on one filter's complexity
Platform High modularity lets them use common tools, services, APIs and tasks

12.8 Style characteristics

It is technically partitioned (logic split by filter type) and usually monolithic, so the architecture quantum is 1.

  • Cost, simplicity, modularity
    • are the strengths: no distributed-style complexity, easy to understand, low cost
    • Modularity comes from separating concerns by filter type: any filter can be modified or replaced without affecting the others (in the Kafka example the Duration Calculator can change its calculation without touching any other filter).
  • Deployability and testability
    • are only average but slightly above layered because of filter modularity
    • It is still typically monolithic, so ceremony, risk, deployment frequency and completeness of testing still hurt.
  • Elasticity and scalability (1 star)
    • from monolithic deployment
    • A distributed version with asynchronous communication improves them significantly, at a cost to overall cost and simplicity.
  • Fault tolerance (1 star):
    • an out-of-memory condition in one part crashes the whole unit
    • availability suffers from high MTTR, startup in minutes. Going distributed with asynchronous communication improves it too, again paying in cost and complexity.
  • "One of the classic trade-offs": most low operational scores can be raised by making each filter a deployment unit with pipes as remote calls, but that hurts simplicity and cost.

12.9 When to use and when not to use

  • Use it for systems of any complexity with distinct, ordered, deterministic one-way processing steps, and for tight time frames and budgets.
  • Do not use it when you need high scalability, elasticity or fault tolerance (a distributed approach mitigates this), or for back-and-forth communication between filters (pipes are unidirectional).
  • It can handle nondeterministic workflows with many tester filters, but that overcomplicates the style and hurts maintainability, testability, deployability and reliability
    • Event-driven architecture (Chapter 15) suits nondeterministic workflows far better.
  • Where it appears: electronic data interchange (EDI) tools (document-to-document transformations), database ETL (extract, transform, load) tools, and orchestrators and mediators such as Apache Camel.

12.10 Example: service telemetry through Kafka

Service telemetry is streamed from services to Apache Kafka (Figure 12-4):

  1. Service Info Capture (producer) subscribes to the Kafka topic and receives service information. It only knows how to connect to a topic and receive streaming data.
  2. It passes data to the Duration filter (tester), which only qualifies data: is it about the duration in milliseconds of a service request?
  3. If yes, it goes to the Duration Calculator (transformer). If not, it goes to the Uptime tester, which checks whether it is an uptime metric. If it is not, the pipeline ends: the data is of no interest to this flow.
  4. If it is, the Uptime Calculator computes the uptime metrics and passes the modified data to Database Output (consumer), which persists it in MongoDB.

It shows how extensible the style is: a new tester filter could be added after the Uptime filter to feed a new metric such as database connection wait time. Technically partitioned filters give good modularity even in a monolith; it fits a workflow-based, step-by-step approach to processing data. Next comes another monolithic style with good modularity through plug-ins: the microkernel.

Summary points

  • Pipes carry data one way between single-purpose, stateless filters (producer, transformer, tester, consumer).
  • Monolithic by default; distributed (for example Step Functions) improves scale and fault tolerance at a cost in simplicity.
  • Watch for overloaded filters, two-way pipes, hard error recovery and contract changes; tag filters to govern roles.
  • Ratings: simple (4) but low on scalability, elasticity and fault tolerance.
Terms to carry forward
  • Pipeline (pipes and filters) architecture; producer, transformer, tester, consumer.
  • Compositional reuse.
  • Filter entry-point tag (annotation or attribute).
  • AWS Step Functions: Standard and Express workflows.
  • Error-handling and contract risks.
  • Deterministic one-way processing.
