Fundamentals of Software Architecture 15: Event-Driven Architecture Style

Source: Mark Richards and Neal Ford, Fundamentals of Software Architecture, 2nd edition (O'Reilly, 2025), chapter 15. Previous: Fundamentals of Software Architecture 14: Service-Based Architecture Style. Next: Fundamentals of Software Architecture 16: Space-Based Architecture Style.

Takeaways
  • EDA is a distributed, asynchronous, decoupled style: processors trigger and respond to events (fire and forget). The authors argue it is a style, not just a pattern.
  • Four topology components: initiating event, event broker, event processor, derived event. A poison event (an endless loop of derived events) is the classic hazard.
  • An event says something has happened and is broadcast; a message is a command to one receiver. Payloads are data-based (fast, but stamp coupling and contract pain) or key-based (simple, but needs database reads). Avoid anemic events and the Swarm of Gnats.
  • Error handling, data loss and request-reply have named patterns (Workflow Event, Event Forwarding, correlation ID).
  • Two topologies: choreographed (broadcast) and mediated (control). Three database topologies: monolithic, domain, dedicated.
  • Strengths: responsiveness 5, evolvability 5, fault tolerance 5, scalability 4. Weak: simplicity 2 and testability 2. Cost $$$; quanta 1 to many.

15.1 Request-based versus event-based

Most applications are request based. A request orchestrator (usually a UI, but possibly an API layer, orchestration services, an event hub, an event bus or an integration hub) directs a request, deterministically and synchronously, to request processors that read and update a database.

Example: a customer asks for the order history of the past six months. That is a data-driven, deterministic request in a context, not something the system must react to.

An event-based model reacts to an event by acting. Example: submitting an online auction bid is not a request but an event that occurs after the asking price is announced; the system responds by comparing it with simultaneous bids and finding the highest bidder.

15.2 Topology

EDA uses asynchronous fire-and-forget communication. Four primary components:

  • Initiating event: starts the flow, simple (a bid) or complex (updating a health-benefits system when an employee marries). It goes to an event channel in the event broker.
  • Event broker:
    • usually federated (several domain-based clustered instances), each holding all event channels (queues and topics) for its domain's flow
    • Because of the decoupled, broadcast nature it uses topics, topic exchanges (AMQP) or streams with publish and subscribe.
  • Event processor (usually just a service): one accepts the initiating event, does its task and advertises what it did through a derived event.
  • Derived event: other processors respond to it and emit their own, until all processors are idle and all derived events processed.

Worked example: retail order entry

  1. Order Placement receives the initiating event (place order), inserts the order, returns an order ID, and emits order placed.
  2. Three processors react in parallel: Notification (emails the order details), Payment (charges the card) and Inventory (adjusts stock).
  3. Notification emits email sent, which nobody listens to: typical of EDA and a sign of extensibility, because future processors can respond without changing the system.
  4. Inventory emits inventory updated; Warehouse responds, managing stock between warehouses and reordering when low. When restocked it emits stock replenished, which Inventory handles. Inventory does not then emit an "inventory adjusted" event: that would create a poison event.
  5. Payment emits payment applied or payment denied. Notification listens for the denial and emails the customer to update their card or choose another method.
  6. Order Fulfillment listens for payment applied (picking and packing: where the item is, what box size) and emits order fulfilled.
  7. Notification and Shipping both respond: Notification tells the customer it is ready, Shipping picks a method, ships and emits order shipped, which Notification also uses to say it is on its way.
A **poison event** is a derived event that keeps being triggered and responded to in a continuous loop between services. They happen often in EDA, so be careful.

The relay race. Think of a relay: a runner runs a stretch, hands off the baton and is done. Likewise, once a processor hands off an event it is free to react to other events, and each processor scales independently for load or backlogs.

15.3 Style specifics

Events versus messages

Event Message
Meaning Something has already happened: "I just placed an order" A command or query: "apply the payment for this order"
Response Typically none required Usually a response
Receivers Broadcast to many processors Almost always one processor
Pattern Publish and subscribe (one to many) Point to point (one to one)
Channel A topic, stream or notification service A queue or messaging service

EDA mostly uses events, sometimes messages (requesting data, request-reply), and the mediated topology uses messages to control order. The authors' quiz:

  • "Adventurous Air Flight 6557, turn left, heading 230 degrees": a message (command, one target, even if others hear it).
  • "In other news, a cold front has moved into the area": an event (broadcast, already happened, no reply expected).
  • "OK, class, turn to page 145 in your workbooks": a message, even though broadcast: broadcasting a command over publish and subscribe does not make it an event.
  • "Hi, everyone! Sorry I'm late for the meeting": an event (already happened, broadcast, no reply).

Derived events

They are essential and a processor can trigger more than one. Charging a credit card (Figure 15-3) involves a Fraud Detection processor and a Credit Limit processor, both driven by one creditcard charged event:

  • Fraud Detection: one derived event if fraud is detected, another if not (both needed, since different processors act on each).
  • Credit Limit: limit okay (the payload may carry the credit left), limit warning (card near its limit; Notification may warn the customer) and fatal limit exceeded (of interest to Notification, Decline Purchase and perhaps an Extend Credit Limit marketing processor).
  • Beware the Swarm of Gnats antipattern: too many fine-grained events.

Triggering extensible events

  • It is usually good practice for each processor to advertise what it did, even if nobody cares yet. An extensible derived event is a built-in "hook".
  • Example (Figure 15-5):
    • Notification emails a customer and emits email sent
    • Nobody listens, so it disappears (or is ignored in streaming)
    • That is not waste: if the business later wants to analyse emails, add an Email Analyzer processor with minimal effort and no changes to other processors, because the information is already in email sent.

Asynchronous capabilities

EDA relies mainly on asynchronous communication for fire-and-forget and request-reply, which can greatly raise responsiveness.

  • A user posts a product review
    • The comment service takes 3,000 ms to validate (unacceptable words, abusive text such as "slow thinker", and a context check that it is about the product).
  • Synchronous REST: 50 ms network latency in, 3,000 ms to validate and post, 50 ms back: 3,100 ms from the user's view.
  • Asynchronous messaging: the user waits 25 ms for acceptance. The system still takes 25 + 3,000 = 3,025 ms to post, but the user sees only 25 ms.
  • Caveat:
    • synchronously the user is guaranteed the comment posted
    • asynchronously it is only acknowledged. If it contains profanity and is rejected, the system can notify a registered user by message.
  • Responsiveness is not performance.
    • Responsiveness is the time to get information back to the user; performance is the time to insert the comment end to end
    • The asynchronous path did nothing to optimise the comment service
    • Optimising it (running parsers in parallel, caching) while still synchronous would address performance
    • "When the user doesn't need any information back, why make them wait?"
  • Error handling is the big problem of asynchronous communication; see the Workflow Event pattern below.

Dynamic Quantum Entanglement antipattern. Synchronous communication between two quanta makes them depend on each other, so they become one quantum. Asynchronous communication detangles them.

  • Figure 15-7:
    • Portfolio Management sends a trade order synchronously to Trade Order (compliance checks, creating the order) and must block for a confirmation number
      • They are one quantum, and characteristics now live between them: if Trade Order is down or slow, Portfolio Management is too
    • if Portfolio Management scales, Trade Order must as well.
  • Figure 15-8:
    • send the order through a queue and receive the confirmation number on a separate asynchronous channel. They are now two quanta
    • Portfolio Management can still issue orders when Trade Order is unavailable.

Broadcast capabilities

EDA can broadcast events without knowing who receives them or what they do, dynamically decoupling processors. It underlies patterns such as eventual consistency and complex event processing (CEP).

Example: each new ticker price on the stock market may drive trade analytics or buying and selling. The publisher simply broadcasts the price: semantic decoupling, one processor having no knowledge of or dependency on another's actions.

Event payload

The information in an event is its payload, from a key-value pair to everything downstream needs. The two basic types are data-based and key-based.

Data-based payloads send all the information needed. Example (Figure 15-10): Order Placement inserts the order (the system of record) and broadcasts order_placed with all details (45 attributes, 500 KB). Payment uses the order ID, customer information and total; Inventory Management uses the item ID and quantity.

  • Advantages:
    • consumers do not query the database, which improves performance, responsiveness and scalability
    • the publisher does not know who needs what, so including everything guarantees it
    • some processors may not even have database access in strict bounded contexts.
  • Disadvantage 1: data consistency.
    • Multiple systems of record
    • If a customer orders 100 items by mistake or uses a wrong address and corrects it at once, the database holds the new values but older events may still carry the old ones
    • Event timing is hard to control, so newer values may even be processed before older values and be overlaid.
  • Disadvantage 2: contract management and versioning.
    • With 45 attributes the event needs a contract (JSON? XML? strict with a schema such as a JSON schema, GraphQL spec or class definition, or loose with name-value pairs?), each forming tight static coupling
    • Versioning (for example a vendor MIME type in event headers) needs every processor to follow the same logic under strong governance, and version communication and deprecation are very hard in a decoupled asynchronous style: data-based payloads are "somewhat fragile".
  • Disadvantage 3: stamp coupling.
    • Processors share a data structure but use different parts. In Figure 15-11 Order Placement sends 45 attributes (500 KB) but Inventory needs only item_id and quantity (30 bytes)
    • removing an address-line attribute would still affect Inventory.
  • Bandwidth.
    • At 500 orders per second, sending the 500 KB event to Inventory takes 250,000 KB/s
    • sending the 30 bytes needed takes 15 KB/s. Bandwidth is not infinite (the third fallacy) and in the cloud it is expensive.
  • Consumer-driven contracts (a contract per consumer with only its data) are hard in EDA, because broadcast means you cannot always know who responds.

Key-based payloads carry only a key (an order ID or customer ID), so responders query the database. Example event body:

{
    "order_id": "123"
}
  • Disadvantages:
    • every responder must query the database (Payment for order information, Inventory for item ID and quantity), which hurts responsiveness, performance and scalability and can overwhelm the database
    • it is a challenge when the data lies in another processor's bounded context.
  • Advantages:
    • better consistency and integrity (a single system of record, so changes during processing are easy)
    • the contract is so simple it is usually loose, schema-less JSON or XML, avoiding versioning and deprecation issues
    • no stamp coupling and minimal bandwidth, so faster on the network and broker.

Trade-off summary (Table 15-1). It is not all or nothing: each event can use a different payload.

Criteria Data-based Key-based
Performance and scalability Good Bad
Contract management Bad Good
Stamp coupling Bad Good
Bandwidth utilisation Bad Good
Restricted database access Good Bad
Overall system fragility Bad Good

The core trade-off: scalability and performance versus contract management and bandwidth. Extreme scale suggests data-based; frequently changing data suggests key-based.

Anemic events

An anemic event is a derived event whose payload lacks enough information or context for the receiver to decide anything.

  • Example (Figure 15-13):
    • a customer updates their profile and Customer Profile emits profile_updated with only the customer ID. Service 1 does not know what changed
    • Service 2 does not know if it needs to act
    • Service 3 does not know the prior values. Querying the database cannot tell them.
  • Fix: include the updated information and the prior values, which most databases do not keep.
  • It sits on a spectrum of payload granularity:
    • far left is key-based (fine for create or delete, poor for update), far right is data-based (all data whether needed or not: stamp coupling)
    • The profile update belongs in between.

The Swarm of Gnats antipattern

Anemic events concern the granularity of the payload; the Swarm of Gnats concerns the granularity of the events themselves: too many derived events from one processor.

  • Too coarse (Figure 15-14):
    • Payment applied, then Fraud Detection emits one fraud_checked event
    • Credit Card Locking, Customer Notify and Purchase Profile all must respond and read the payload to decide
    • If no fraud was detected, only Purchase Profile needed to act: wasted bandwidth and processing.
  • Better (Figure 15-15): two derived events, fraud_detected and no_fraud_detected, so each processor decides from the event itself.
  • Too fine (Figure 15-16):
    • a customer who moved updates bill-to address, ship-to address and phone number
    • Customer Profile emits a separate event for each change, saturating the system and making event flows hard to understand.
  • Fix (Figure 15-17): bundle the changes into a single profile_updated derived event with the before and after data of all fields.
  • Guidance: focus on the outcome of the processing or state change.

Error handling: the Workflow Event pattern

A pattern of reactive architecture that addresses both resiliency and responsiveness via delegation, containment and repair using a workflow delegate.

  1. An event processor sends data through a channel to the event consumer.
  2. On an error the consumer immediately delegates it to the Workflow Processor and moves on to the next message, so responsiveness is unchanged (trying to diagnose the error would delay everything waiting).
  3. The workflow processor tries to work out what is wrong (a static, deterministic error, or ML or AI anomaly analysis), programmatically repairs the data and sends it back to the originating queue as a new message.
  4. If it cannot, it sends it to another queue read by a dashboard for a knowledgeable person, who fixes it manually and resubmits it (usually through a reply-to header).

Example. A trading advisor batches trade orders (a basket) and asynchronously sends them to a broker on the other side of the country. The contract is ACCOUNT(String),SIDE(String),SYMBOL(String),SHARES(Long):

12654A87FR4,BUY,AAPL,1254
87R54E3068U,BUY,AAPL,3122
6R4NB7609JJ,BUY,AAPL,5433
2WE35HF6DHF,BUY,AAPL,8756 SHARES
764980974R2,BUY,AAPL,1211
1533G658HD8,BUY,AAPL,2654

The fourth line has "SHARES" after the number. Without error handling the TradePlacement service throws, and with no user to tell it can only log:

Exception in thread "main" java.lang.NumberFormatException:
For input string: "8756 SHARES"
    at java.lang.NumberFormatException.forInputString(NumberFormatException.java:65)
    at java.lang.Long.parseLong(Long.java:589)
    at java.lang.Long.<init>(Long.java:965)
    at trading.TradePlacement.execute(TradePlacement.java:23)
    at trading.TradePlacement.main(TradePlacement.java:29)

With the pattern, TradePlacement delegates the error to the Trade Placement Error service and continues:

Trade Placed: 12654A87FR4,BUY,AAPL,1254
Trade Placed: 87R54E3068U,BUY,AAPL,3122
Trade Placed: 6R4NB7609JJ,BUY,AAPL,5433
Error Placing Trade: "2WE35HF6DHF,BUY,AAPL,8756 SHARES"
Sending to trade error processor <-- delegate the error fixing and move on
Trade Placed: 764980974R2,BUY,AAPL,1211
...

The workflow delegate strips "SHARES" and resubmits:

Received Trade Order Error: 2WE35HF6DHF,BUY,AAPL,8756 SHARES
Trade fixed: 2WE35HF6DHF,BUY,AAPL,8756
Resubmitting Trade For Re-Processing

...
trade placed: 1533G658HD8,BUY,AAPL,2654
trade placed: 2WE35HF6DHF,BUY,AAPL,8756 <-- this was the original trade in error

Consequence: out-of-order processing. Resubmitted messages are processed out of sequence, but trades in one account must be in order (a SELL for IBM before a BUY for AAPL in the same account).

Fix: the TradePlacement service queues and stores the brokerage account number of the erroneous trade, holds later trades for that account in a temporary FIFO queue, and de-queues and processes them in order once the bad trade is fixed.

Preventing data loss

Asynchronous communication risks a dropped or never-delivered event or message. Most EDA use AMQP (brokers: Amazon SNS, RabbitMQ, Solace, Azure Event Hubs): events go to an exchange, which forwards via binding rules to a queue per subscribing processor.

These brokers can use the Event Forwarding pattern. The Jakarta Messaging API (formerly JMS) uses topics rather than that two-step process but can use the pattern with durable subscribers (the topic keeps the event until the subscriber is back).

Kafka event streaming prevents loss differently (see its documentation).

Three places data can be lost (processor A publishes, broker queues, processor B stores in a database):

Loss point Fix
A crashes before the broker acknowledges, or the broker acknowledges then crashes before another processor accepts it Persistent message queues (guaranteed delivery: stored in memory and also persisted to disk or a database) plus synchronous send (A blocks until the broker confirms persistence)
B de-queues the event then crashes before processing Client acknowledge mode: the event stays in the queue, tagged with the client ID so no other consumer reads it (the default auto acknowledge removes it immediately)
B cannot persist to the database (data error) ACID transaction commit; then last participant support (LPS) removes the event from the persisted queue, acknowledging that processing completed and the data is persisted

Request-reply processing

When a processor needs an immediate answer (for example a confirmation ID before triggering an event), EDA uses request-reply (pseudosynchronous) messaging: each channel has a request queue and a reply queue. The producer sends to the request queue, returns control, does other work, then waits on the reply queue; the consumer processes and replies.

Correlation ID technique (most common).

  1. The producer sends to the request queue and records the message ID (124); its CID is null.
  2. It does a blocking wait on the reply queue with a message selector: CID equals 124. The reply queue holds ID 855 (CID 120) and ID 856 (CID 122): neither is picked up.
  3. The consumer receives message 124 and processes it.
  4. It builds a reply and sets its CID to the original message ID (124).
  5. It sends the reply (new ID 857) to the reply queue.
  6. The producer receives it because the CID matches its selector.

Temporary queue technique. The producer creates a temporary queue (or the broker does) and sends the request with its name in the reply-to header; it blocks on that queue (no selector needed, since only its reply arrives); the consumer replies to it; the producer deletes the queue.

Simpler, but the broker must create and delete a queue per request, which can significantly slow the broker at high volume and concurrency. The authors usually recommend the correlation ID technique.

15.4 Mediated event-driven architecture

So far: choreographed EDA (processors broadcast, many respond). For more control use the mediator topology: an initiating event, an event queue, an event mediator, event channels and event processors. It typically uses messages (commands such as ship_order), not events.

  • The mediator accepts the initiating event, knows the steps, generates derived messages and sends them point to point to dedicated queues
    • Processors listen, process and (usually) respond to the mediator
    • they do not advertise what they did.
  • Most implementations use several mediators, one per domain or group of events (a customer mediator for registrations and profile updates; an order mediator for carts and checkout)
    • This avoids a single point of failure and raises throughput.
  • Choosing a mediator by complexity:
    • Apache Camel, Mule ESB, Spring Integration for simple error handling and orchestration; flows are written in code (Java, C#).
    • Apache ODE or Oracle BPEL Process Manager
      • for lots of conditional processing, dynamic paths and complex error handling
      • they use BPEL (Business Process Execution Language), an XML-like description with elements for error handling, redirection and multicasting, so architects usually use the engine's GUI tools.
    • BPEL is poor for long-running transactions with human intervention (for example a place_trade over a share threshold that needs a senior trader's manual approval): use a BPM engine such as jBPM.
    • Camel for long-running human events would be extremely hard; a BPM engine for simple flows would waste months on what Camel does in days.
  • Mediator delegation model (Figure 15-26):
    • classify events as simple, hard or complex, and send everything through a simple mediator (Camel or Mule)
    • It handles simple ones itself or forwards hard or complex ones to a BPEL or BPM mediator
    • The simple mediator may still track completion or delegate the whole workflow, including client notification.

The order flow with a mediator (Figures 15-27 to 15-32). The same initiating event (place order) goes to the Customer mediator:

  1. Create order: the mediator sends create order to the order placement queue; Order Placement validates, creates and returns an acknowledgment and order ID. The mediator may send the ID to the customer or continue, per business rules.
  2. Three messages at once: email customer, apply payment, adjust inventory. The mediator waits for all three acknowledgments before step 3; on an error it can take corrective action.
  3. Fulfil: fulfill order and order stock together, to Order Fulfillment and Warehouse.
  4. Ship: ship order and another contextual email customer (ready to ship). Step 3 must complete before step 4.
  5. Final notice: email customer that it has shipped. The mediator marks the flow complete and removes all state.

The mediator knows the workflow, keeps event state and handles error handling, recoverability and restart. Example: an expired card means payment failed, so the mediator stops before step 3, records state in its own persistent store, and restarts at step 3 once payment succeeds.

Disadvantages of the mediator topology:

  • It is very hard to declaratively model the dynamic processing of a complex flow, so many flows use a hybrid (mediator for general processing, choreography for out-of-stock and other atypical cases).
  • The mediator must scale too, and can become a bottleneck.
  • Processors are less decoupled than in the choreographed topology.
  • Performance is lower because the mediator controls processing.
  • Trade-off: workflow control and error handling versus the highest performance and scalability.

15.5 Data topologies

Database topology is a distinctive part of EDA. The simplified order flow (Figure 15-33): Order Placement creates the order and emits order placed; Payment and Inventory respond; after payment Order Fulfillment helps the packer and emits order fulfilled; Shipping ships.

A complication: Order Placement needs how many items are in stock and the shipping options for the customer's location. How it gets them depends on the topology.

Topology Data access Strengths Weaknesses
Monolithic database (the most common) Any processor queries the central database directly, with no synchronous call to another processor Preserves decoupling and limits communication Fault tolerance (database down means all processors unavailable); scalability (every processor hits one database that must scale to the combined concurrency); change control (dropping a column affects many processors); a single quantum
Domain database (processors grouped by domain, each domain owning a database) Order Placement reads inventory from its domain database but must make a synchronous call to Order Shipping for shipping options Better fault tolerance (if the order-processing database is down, order placement still works; the payment applied channel acts as a backpressure point), scalability and change control The synchronous call couples services and erodes those benefits. If too much synchronous communication is needed, rethink the domains, merge them, or return to a monolithic database
Dedicated database (database per event processor, as in microservices) Order Placement must call both Inventory and Order Shipment synchronously Highest fault tolerance, scalability and change control; failures are isolated to one processor Often expensive; many synchronous coupling points. Good when processors are mostly self-contained within their bounded context; otherwise move to domain or monolithic. Frequent structural database changes can justify trading operational characteristics to limit the processors affected

15.6 Cloud, risks, governance, teams

  • Cloud: EDA matches cloud environments: highly decoupled, easily using cloud vendors' asynchronous services, and elastic infrastructure matches its shape.
  • Common risks:
    • Nondeterministic processing
      • causes side effects (processors unexpectedly triggering derived events or not responding)
      • flows get complex and it is hard to know what happens when an event fires.
    • Too much static coupling
      • through payload contracts
      • changing one is daunting since you do not know who responds. Key-based payloads help but bring scalability, performance and anemic-event risks.
    • Too much synchronous communication between processors: a sign EDA is the wrong style.
    • State management:
      • hard to know when an initiating event has been fully processed or its current state. Occasionally the initiating processor can subscribe to a known "ending" event
      • usually not.
  • Governance: mostly nonstructural and based on observability (logs, as part of a governance mesh), sometimes collected manually. Two areas, both structural decay in EDA:
    • Static coupling through contracts:
      • track the rate of change of payload contracts and stamp coupling by recording which fields consumers never use, so contracts shrink
      • Changing a contract, especially one with no schema, can break a downstream processor and is hard to test in nondeterministic flows.
    • Dynamic coupling through synchronous calls:
      • write fitness functions to track synchronous communication via logs, source code annotations or custom-identifier libraries
      • discuss each one, especially with domain or dedicated databases.
  • Team topologies: EDA is largely technically partitioned, but can work with domain-aligned teams.
Team type Fit
Stream-aligned A domain is several processors and derived events, so domain changes (adding a step to order placement) may touch many processors and restructure event triggers. The bigger the system, the less effective they are
Enabling Does not work well: integration through derived events and contracts means experiments disrupt a stream's understanding of the flow and need too much coordination
Complicated-subsystem Works well: complex processing isolates in separate processors; coordination only for event-payload contracts and derived events
Platform Works well, especially if brokers, event hubs, buses and channels are treated as platform artifacts

15.7 Style characteristics

It is primarily technically partitioned: a domain spreads over processors tied by brokers, contracts and topics, so a domain change usually affects several processors and messaging artifacts; it is not generally domain partitioned.

  • Quanta: one to many,
    • depending on database interactions and request-reply
    • Several processors sharing a database instance are one quantum
    • Request-reply also ties processors together: if the processor that places an order and returns an order ID is down, the requester cannot continue, so they share a quantum even though both use asynchronous messages.
  • Performance, scalability and fault tolerance
    • are the main strengths
    • Performance comes from asynchronous communication with highly parallel processing
    • Scalability comes from programmatic load balancing (competing consumers and consumer groups) adding processors as load rises
      • it earns four stars, not five, because of the database (space-based architecture, Chapter 16, gets five)
    • Fault tolerance comes from decoupled, asynchronous processors giving eventual consistency: if downstream processors are unavailable and no immediate response is needed, the event is processed later.
  • Low simplicity and testability (2 stars)
    • from nondeterministic dynamic event flows. Request-based flows are deterministic and easy to test
    • in EDA architects often do not know how processors will react, and event tree diagrams can generate hundreds or thousands of scenarios.
  • Evolvability (5 stars): adding features via existing or new processors is easy, because derived events provide hooks and the data is already available: no change to infrastructure or other processors.
  • Disadvantages:
    • hard to control the overall workflow and to know when a business transaction from an initiating event has completed
    • error handling:
      • with no mediator (except in the mediator topology) other services do not know about a crash
      • If Payment dies, Inventory still adjusts stock and everything else carries on as if fine
    • recoverability: restarting a business transaction is very hard, because other actions were taken asynchronously and resubmitting the initiating event is often not feasible

Choosing between request-based and event-based

  • Request-based: well-structured, data-driven requests (such as retrieving a customer profile) when certainty and control over the workflow matter most.
  • Event-based: flexible, action-based events needing high responsiveness and scale with complex, dynamic user processing.
Event-based advantages over request-based Trade-offs
Better response to dynamic user content Only supports eventual consistency
Better scalability and elasticity Less control over processing flow
Better agility and change management Less certainty over the outcome of the flow
Better adaptability and extensibility Difficult to test and debug
Better responsiveness and performance
Better real-time decision making
Better reaction to situational awareness

15.8 Examples and use cases

  • Good candidates:
    • problems about responding to things happening inside or outside the system
    • order entry (parallel, decoupled processing)
    • systems needing high responsiveness, performance, scalability, fault tolerance and elasticity.
  • Going, Going, Gone auction.
    • The number of bidders is unknown, so it needs scalability and elasticity (especially near the close of a timed auction) and high responsiveness
    • Best of all, EDA treats placing a bid as an event that has happened, not a request.

When a bidder places a bid:

  1. Bid Capture receives the initiating event, checks whether it beats the prior bid, and emits bid placed.
  2. Auctioneer updates the website with the item's new price.
  3. Bid Streamer simultaneously streams the bid to the website's bid history or to individual bidders.
  4. Bidder Tracker persists the bidder and bid for tracking and auditing (back-end processing).

Many more processors and derived events are involved, but this shows responsiveness, fault tolerance, scalability and elasticity.

EDA is very complicated but very powerful: analyse the workflows to decide whether its complexity is worth its superpowers. If most processing is request based, consider microservices (Chapter 18) instead.

Summary points

  • Four components: initiating event, broker, processor, derived event; broadcast, asynchronous, decoupled.
  • Events are broadcast facts; messages are commands; choose data-based or key-based payloads per event; avoid anemic events and Swarm of Gnats.
  • Asynchrony raises responsiveness and separates quanta; handle errors (Workflow Event), loss (Event Forwarding) and replies (correlation ID).
  • Mediator topology trades throughput for control; database topology trades isolation for synchronous coupling.
  • Strong on responsiveness, evolvability, fault tolerance and scale; weak on simplicity and testability.
