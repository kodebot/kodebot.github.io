Google Code Review Guide 1: The Standard and What to Look For

Source: Google Engineering Practices Documentation, "Code Review" (overview, "The Standard of Code Review", "What to look for in a code review"), licensed CC BY 3.0. Own-words summary of the reviewer's guide. Next: Google Code Review Guide 2: Navigating, Speed, Comments and Pushback.

Takeaways
  • The aim of review is that the overall code health improves over time. Every process serves that.
  • The senior rule: approve once a change definitely improves code health, even if it is not perfect. There is no perfect code, only better code.
  • Review eight things: design, functionality, complexity, tests, naming, comments, style, documentation. Read every line and look at the context.
  • Say what is good, not only what is wrong.

Terminology: Google calls a change under review a CL (changelist), roughly what GitHub calls a pull request.

1.1 What a code review is

  • A review is someone other than the author examining the code. Google uses it to maintain quality.
  • Three documents make up the guide: this overview, How to do a code review (reviewers) and The CL author's guide (Google Code Review Guide 3: The Change Author's Guide).

1.2 The standard of code review

  • Two pressures pull against each other:
    • Progress: if nothing is ever submitted, the codebase never improves, and a reviewer who makes every change hard discourages future improvement.
    • Code health:
      • codebases decay through many small drops in health, especially when a team is rushed and takes shortcuts
      • The reviewer owns the consistency and maintainability of the code being reviewed.
  • Therefore reviewers lean towards approving a change that clearly improves code health, even when it is imperfect. Seek continuous improvement, not perfection
    • do not hold a change for days over polish.
  • Optional polish is welcome if labelled, for example with a "Nit:" prefix so the author knows it can be ignored.
  • Limit: a reviewer may still refuse a change that adds a feature they do not want, however well designed.
  • Nothing here justifies a change that definitely worsens code health, except in an emergency (Google Code Review Guide 2: Navigating, Speed, Comments and Pushback).
  • Mentoring: teaching comments are fine; mark purely educational ones as not mandatory.

Principles for deciding

  • Technical facts and data overrule opinions and personal preference.
  • On style, the style guide is the absolute authority. A style point not in the guide is personal preference
    • stay consistent with the surrounding code, and where there is no precedent accept the author's choice.
  • Software design is almost never pure preference. If the author shows by data or sound engineering principle that several approaches are equally valid, accept their choice
    • otherwise standard design principles decide.
  • If no other rule applies, ask for consistency with the existing codebase, provided that does not worsen code health.

Resolving conflicts

  1. Try for consensus using the guide's own documents.
  2. If that is hard, talk face to face or on video, and record the outcome as a comment on the change.
  3. Otherwise escalate (team discussion, technical lead, code maintainer, engineering manager). Do not let a change sit because two people cannot agree.

1.3 Who should review

  • Pick the best reviewer you can who will respond in reasonable time, usually the owner of the code
    • Different people can review different parts
    • If the ideal reviewer is unavailable, at least copy them in.
  • Pair programming counts as review if your partner was qualified to review it. A reviewer-led in-person review, where the author speaks only when asked, also counts.

1.4 What to look for

Aspect The question Example
Design do the pieces interact sensibly; does it belong in this codebase or a library; is now the right time? a feature added to the wrong layer
Functionality does it do what the author intended and is that good for users (end users and future developers)? edge cases, a UI change (ask for a demo), concurrency: races and deadlocks need careful thought because running the code rarely exposes them
Complexity can readers understand it quickly, and will callers introduce bugs? Check lines, functions and classes over-engineering: solve the problem you know now, not one you speculate about
Tests unit, integration or end-to-end as fitting, in the same change as the code (except emergencies) tests do not test themselves; will they fail when the code breaks, or give false positives? Tests are code that must be maintained
Naming long enough to communicate, short enough to read
Comments clear and necessary; they should explain why, not what exceptions: regular expressions and complex algorithms
Style follow the style guide; label purely personal improvements "Nit:" do not mix a large reformat with functional changes; send the reformat separately
Consistency the style guide wins; where it only recommends, bias towards it unless local inconsistency is too confusing file a bug and add a TODO for cleaning up the old code
Documentation if the change alters how people build, test, use or release, update READMEs and reference docs; remove docs for deleted code

Reading the change

  • Every line:
    • look at every human-written line you are assigned (generated code and big data files you may skim)
    • If you cannot understand it, ask the author to clarify, because other readers will struggle too.
  • If you are not qualified for part of it (privacy, security, concurrency, accessibility, internationalisation), make sure a qualified reviewer is on the change.
  • If you review only some files or aspects, say so in a comment and prefer "LGTM with comments".
  • Context:
    • look at the whole file and the system. Four added lines may sit in a 50-line method that now needs splitting. Do not accept a change that degrades code health
    • small complexities add up.
  • Good things: tell the author about good work. Praise can mentor more effectively than criticism.

Summary points

  • Approve changes that improve code health; use "Nit:" for optional polish.
  • Review design first, then function, complexity and tests; check naming, comments, style and docs.
  • Read every line, view context, and praise what is good.
Terms to carry forward
  • CL: changelist; a change under review.
  • Code health: how maintainable, readable and understandable the codebase is.
  • Nit: a prefix marking an optional point.
  • LGTM: "looks good to me", approval.
  • Over-engineering: generality or features not needed now.
