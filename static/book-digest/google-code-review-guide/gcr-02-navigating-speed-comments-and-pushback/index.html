Google Code Review Guide 2: Navigating, Speed, Comments and Pushback

Source: Google Engineering Practices Documentation, "Navigating a CL in review", "Speed of code reviews", "How to write code review comments", "Handling pushback in code reviews" and "Emergencies", licensed CC BY 3.0. Own-words summary. Previous: Google Code Review Guide 1: The Standard and What to Look For. Next: Google Code Review Guide 3: The Change Author's Guide.

Takeaways
  • Review in three steps: broad view, main part first, then the rest. Send major design problems at once.
  • Respond within one business day at most; fast responses matter more than fast completion. Do not interrupt a focused task to review.
  • Comment on the code, not the person; explain why; label severity.
  • "I'll clean it up later" rarely happens, so insist on cleanup now. Emergencies are narrow: a launch-week wish is not one.

2.1 Navigating a change

  1. Broad view. Read the description: should this change exist at all? If not, say so immediately, politely, and suggest what to do instead (the guide's example: tell them the area is being removed and point to the replacement class). If many changes are unwanted, fix the process so there is discussion before code is written.
  2. Main parts first. Find the file with the most logical change. If it has major design problems, send those comments straight away, even before reading the rest. Two reasons:
    • Authors often start new work on top of the change; late news forces them to rework that too.
    • Big redesigns take time, and authors have deadlines.
  3. The rest, in sequence. Go through the remaining files in order without skipping any; reading tests first can show what the change is meant to do.

2.2 Speed of reviews

  • Why fast:
    • Google optimises the speed of the team, not the individual
    • Slow reviews cut team velocity, make authors resent the process, and hurt code health (more pressure to accept weak changes, fewer refactorings)
    • The guide says most complaints about strictness fade when reviews get faster.
  • How fast: if you are not in the middle of focused work, review soon after it arrives. One business day is the maximum to respond (first thing the next morning).
  • Interruption:
    • if you are in focused work, do not interrupt yourself
    • reply at a natural break (after finishing a task, lunch, a meeting). Interruptions cost the team more than a short wait.
  • Responses over completion:
    • quick individual responses ease frustration even when the whole review takes long
    • If too busy, send a quick note saying when you will look, suggest another reviewer, or give broad comments first.
  • Make sure your LGTM really means the change meets the standard.
  • Time zones: reply while the author is still working, or finish before they start next day.
  • LGTM with comments
    • is right when you trust the author to address the comments, when comments are optional, or when they are minor (sort imports, fix a typo, apply a suggested fix, remove an unused dependency)
    • Say which.
  • Large changes: ask for a split into smaller dependent changes. If it cannot be split and you lack time, at least send design comments so the author is unblocked.
  • Reviews speed up over time as authors learn what is expected; do not lower the standard for imagined speed.

2.3 Writing comments

  • Be kind. Comment on the code, not the developer.
    • Instead of "Why did you use threads here when there's obviously no benefit?" write that the concurrency adds complexity without a visible performance benefit, so single-threaded is better.
  • Explain why: the intent, the best practice, how the change improves code health.
  • Guidance:
    • fixing the change is the author's job; you need not design the solution or write the code
    • Pointing out a problem often teaches more and may yield a better solution because the author knows the code
    • Give direct instructions when that helps
    • Goals: the best change first, better developers second.
  • Praise what is good, with the reason.
  • Label severity: "Nit:" (minor), "Optional" or "Consider" (not required), "FYI" (not for this change). Without labels, authors may treat everything as mandatory.
  • Accepting explanations:
    • if you ask what code means, the answer should usually be a rewrite for clarity, occasionally a code comment
    • An explanation that lives only in the review tool does not help future readers.

2.4 Handling pushback

  • First ask whether the author is right. They are closer to the code; if their argument improves or does not harm code health, say so and drop it.
  • If not, explain again, showing you understood their reply and why you still ask
    • Code health improves in small steps and may take several rounds
    • Stay polite: you hear them, you just do not agree.
  • Worry that authors get upset is usually in the reviewer's head; upset is mostly about how comments are written.
  • "Clean it up later":
    • later cleanups mostly never happen because other work crowds them out, so insist on it now
    • New complexity must be cleaned before submission unless it is an emergency
    • If surrounding problems cannot be fixed now, file a bug assigned to the author and optionally add a TODO referencing it.
  • Complaints about strictness:
    • if you moved from lax to strict reviews, expect loud complaints
    • faster responses make them fade, sometimes over months, and loud critics can become supporters.
  • Unresolved conflicts: see the standard in Google Code Review Guide 1: The Standard and What to Look For.

2.5 Emergencies

  • An emergency change is small and, for example, lets a major launch proceed instead of rolling back, fixes a bug that significantly affects users in production, handles a pressing legal issue, or closes a major security hole.
  • In an emergency only, speed of the whole review and correctness of the fix outrank other concerns, and emergency reviews take priority over other reviews
    • Afterwards, review the change again more thoroughly.
  • Not emergencies:
    • wanting to launch this week rather than next
    • a long-running feature the author wants in
    • reviewers being in another time zone or away
    • Friday-evening wishes
    • a manager citing a soft deadline
    • rolling back a change that broke tests or the build.
  • A hard deadline is one where something disastrous follows a miss (a contractual obligation, product failure in the market, a once-a-year hardware shipping window). A week's delay is not disastrous
    • most deadlines are soft.
  • Habitually rushing "must get in" changes at the end of a long release cycle builds technical debt; schedule large feature changes early enough for good review.

Summary points

  • Reply within a day, but never at the cost of the standard.
  • Label comments, explain reasons, praise good work.
  • Cleanups promised "later" should happen now.
Terms to carry forward
  • LGTM with comments: approval while leaving comments the author can handle alone.
  • Hard and soft deadline: a miss is disastrous versus merely unwelcome.
  • Emergency change: a small urgent fix that gets a fast, narrower review followed by a fuller one.
