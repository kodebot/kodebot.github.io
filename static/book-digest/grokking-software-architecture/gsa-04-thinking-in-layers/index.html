Grokking Software Architecture 4: Thinking in Layers

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 4. Previous: Grokking Software Architecture 3: The Principles of Sound Structure. Next: Grokking Software Architecture 5: Hexagonal Architecture (Ports and Adapters).

Takeaways
  • Layered architecture = Separation of Concerns scaled to the whole application: horizontal layers, each depending only on the layer directly beneath.
  • Modern four layers: Presentation, Application, Domain, Infrastructure. The golden rule is the Downward Dependency Rule: commands and source dependencies go down; data may flow both ways.
  • Layers are logical (code structure); tiers are physical (deployment).
  • Handle cross-cutting concerns (logging, auth, caching) by injecting abstractions, not static calls.
  • Classic trap: Fat Controller + Anemic Domain Model; fix with a Rich Domain, thin controller and service.
  • Enforce with separate projects (compiler stops violations) and fitness functions.

4.2 Layered architecture

  • Command flow
    • (top to bottom: Presentation commands Application, which commands Domain...) vs data flow (both ways: input goes down, results come back up)
    • The source-code dependency never points up: the business layer returns data to the UI but never knows the UI exists.
  • Classic 3 layers: Presentation (UI), Business Logic, Data Access.
  • Evolution to 4 (or 5) layers.
    • Split a layer when you see: the junk-drawer effect (one layer mixing workflows and low-level rules)
    • team scaling (developers colliding in the same files)
    • blurry boundaries (cannot say where a tax calculation belongs).
    1. Presentation: shows information and captures input (web pages, API responses/requests); knows how to show, not the rules.
    2. Application (service layer): orchestrates use cases ("Create New Order"), coordinates domain objects/services, handles transactions; contains no core business rules.
    3. Domain (business logic): core knowledge, rules, state: entities (Order, Customer), value objects, domain services; independent of presentation and storage.
    4. Infrastructure: the "how" of external concerns: database (ORM like Entity Framework or SQL), email, third-party APIs, log files, message queues; implements interfaces defined above it.
    • Very large systems may split Infrastructure into a Data Access Layer and an Infrastructure layer as siblings (not vertical pass-through).
  • Layers vs tiers:
    • layers = logical separation (departments in one building)
    • tiers = physical (separate buildings: web server, app server, database server)
      • A 3-layer app can sit on one tier or three
      • Scaling is not tiering: presentation on 10 servers is one tier scaled horizontally
    • a new tier appears only when you cross a network boundary.
  • Newer patterns that challenge strict horizontal slicing:
    • Hexagonal (ch. 5), Clean, Onion (dependencies point inward to the domain)
    • also Vertical Slice Architecture (group by feature, like pizza slices, though layers persist inside slices)
    • micro-frontends in ch. 12.

4.3 The Downward Dependency Rule

An upper layer may depend on layers below; a lower layer must never depend on one above. Org chart analogy: CEO (Presentation) commands VP (Application), who commands Manager (Domain), who commands Team Lead (Infrastructure); never the reverse. Why it matters:

  1. Lower complexity, better maintainability: an Infrastructure developer needs no UI knowledge; a lower layer's implementation can be rewritten (SQL to Mongo) if its contract holds.
  2. Testability: test Domain with fake Infrastructure interfaces.
  3. Replaceability: swap web UI for mobile/desktop (Domain and Application do not know Presentation); with DIP, Application depends on IOrderRepository, so SqlOrderRepository can become MongoOrderRepository.
  4. Minimised blast radius: a UI bug is unlikely to break database code.
class OrderService {
  constructor(repo) {                 // depends on an abstraction
    this.repo = repo;
  }
  saveOrder(order) {                  // doesn't know how save works
    this.repo.save(order);
  }
}

class SqlOrderRepository {            // knows nothing about OrderService
  save(order) { /* SQL */ }
}
  • "Garbage in, garbage out": layering protects source code, not data; every layer should validate input; the Domain is the final line of defence.
  • Closed vs open layers:
    • in strict layering every layer is closed (requests pass through all layers)
    • open layers (layer bridging)
      • let upper layers bypass one for high-speed read-only queries (e.g. a public product catalogue querying a read-only view repository)
      • Closed layers enforce business rules, security, transaction boundaries (new orders must pass the Application layer)
      • Open layers cut boilerplate but risk abuse for writes
    • default to closed, open only when performance data justifies.
  • Violation 1: upward dependency.
    • SomeRepository grabs PresentationLayer.instance and calls updateStatusLabel("Data saved!")
    • Consequences: spaghetti code, lost replaceability, untestable, circular dependencies
    • Fix: the repository returns data (boolean or saved object) to the Application service, which decides how to notify the UI: data flows up without the source dependency pointing up.
  • Violation 2: skipping layers downward.
    • ProductController does new SqlProductRepository() and GetProductsSql() directly
      • Bypasses business logic (a "filter out Discontinued Products" rule), security (user permissions), caching
    • the UI breaks if SQL becomes Mongo.
  • AOP "weaving":
    • frameworks insert cross-cutting calls (e.g. "before any public method in OrderService, call _logger.Log()") at compile or run time
      • Caveats: uniform not contextual (knows "Executing SaveOrder", not "User #12 saved Order #456")
    • performance overhead
    • in cloud/microservices these concerns often move out of code to sidecars, API gateways, service meshes.

4.4 Physically structuring layers

Make the architecture obvious and the wrong thing hard.

  • Folders (Python/JavaScript):
    • /app (Presentation), /api (controllers, routes) and /services (orderService.js) = Application, /domain (order.js) = Domain, /repositories and /lib (emailClient.js) = Infrastructure
    • Keep siblings decoupled (SqlDatabase and EmailService must not depend on each other; the Application layer coordinates).
  • Separate projects (Java/C#): MySolution.Domain, .Application, .Infrastructure, .Presentation, with references only downward: the compiler enforces it (a controller in Domain does not compile).
  • Fitness functions
    • (Neal Ford, Rebecca Parsons, Patrick Kua, Building Evolutionary Architectures: https://nealford.com/books/buildingevolutionaryarchitectures.html): automated checks of the code's structure ("does the UI layer respect the database boundary?")
      • Tools: dependency-cruiser (JS/TS)
    • NetArchTest or NDepend (.NET), Pyright rules (Python)
    • ArchUnit (Java), run locally or in CI/CD.

4.5 Cross-cutting concerns

Logging, authentication, caching, error handling serve many layers (electricity serving every room). Problems:

  • Tangling (SRP violation): StaticFileLogger.log("Saving order...") before and after repo.save(order).
  • Scattering: the same logging calls in hundreds of methods across layers; switching to a cloud logger means hunting them all.
  • Solution:
    • invert the dependency; OrderService takes a logger in its constructor and calls logger.Log(...)
    • Gains: DIP, swap FileLogger for CloudLogger in one registration place, fake logger in tests, SRP
    • The Four-Layer diagram: four horizontal layers, downward arrows only, and a vertical Cross-Cutting Concerns bar accessible to all layers.

4.7 Anti-patterns

An anti-pattern is a common, well-intentioned solution that consistently backfires (catalogues: Fowler's Refactoring; Brown et al. AntiPatterns). The two most common, almost always together:

  • Fat Controller / bloated service:
    • createOrder in a controller does validation, new MyDbContext() lookups, total calculation, a magic-number Gold discount (total *= 0.9), persistence with a random id, new SmtpEmailService().Send(...)
    • At least five responsibilities (HTTP, validation, totals, saving, email): untestable discount logic (needs a web server, DB, email), huge blast radius, no replaceability
    • A tool measuring cyclomatic complexity (number of paths:
      • each if, while, for, case adds one
      • 1 to 5 good, 20+ red flag
      • use SonarQube or NDepend
      • show on the dashboard
      • a smoke alarm, not dogma) flags it.
  • Anemic domain model:
    • Order has only id, total, customerEmail, items set from anywhere (order.total = -100): violates encapsulation, zero cohesion
    • behaviour (calculateTotal, validate) is scattered.
  • After (C#): rich domain, thin orchestration.
    • Rich Order:
      • GOLD_DISCOUNT_RATE = 0.9m
      • Total { get; private set; }
      • Customer set once in the constructor (ArgumentNullException if null)
      • private _items exposed as IReadOnlyList<Item>
      • IsEligibleForDiscount => Customer.Type == "Gold"
      • calculated property TotalPrice => _items.Sum(price*quantity) * (eligible ? 0.9 : 1) (an "atomic truth": cannot be out of sync)
      • AddItem rejects non-positive prices.
    • Contracts in the Domain layer: IOrderRepository, ICustomerRepository, IItemRepository, IEmailService.
    • Infrastructure implements them: SqlOrderRepository, SqlCustomerRepository, SqlItemRepository, SmtpEmailService.
    • Thin OrderService.CreateOrder:
      • get customer, new Order(customer), for each item fetch the real price from the database, not the user JSON (secure lookup), AddItem, save, send email, return an OrderResponse DTO
      • catch, log and throw ApplicationException("Order creation failed..."). Thin OrderController calls _orderService.CreateOrder(request) only.
    • The paradox:
      • IOrderRepository lives in the Domain, so Infrastructure imports from Domain: source dependencies point up (inward), control flow points down
      • Both Application and Infrastructure point inward to the Domain: the breakthrough that leads to Hexagonal Architecture (ch. 5).
  • The mandate:
    • ask not "how do I write this?" but "where does this code belong?": core rules in Domain, orchestration in Application, HTTP in Presentation, database and email in Infrastructure
    • Entropy erodes boundaries, so enforce with fitness functions ("trust, but verify").

4.8 The Dork Side: the 7-layer sandwich (OSI)

1970s networking was a Tower of Babel: an IBM machine could not talk to a DEC machine; applications had to know everything from meaning to cable voltage (the ultimate fat controller).

ISO's 7-layer OSI model applied SoC ("Grandma's letter"): 7 Application (you write the letter), 6 Presentation (translate to Polish, standard envelope), 5 Session ("Dear Grandma"/"Love, Archie", manages the conversation), 4 Transport (TCP) (10 numbered postcards, resend lost #4), 3 Network (IP) (address and global route), 2 Data Link (local hop, the mail truck), 1 Physical (paper, ink, tyres; in networks: electrical signals, radio waves, light pulses).

Point: replaceability: swap copper for fibre and no other layer changes, like swapping MockOrderRepository for SqlWidgetRepository. (See also Understanding Distributed Systems 2: Reliable links for the network stack in UDS.)

4.9 Mission, checklist, recap

  • Mission (5 min):
    • sketch the four layers for a blog (list posts; submit a comment), at least two components per layer, asking "How (Infrastructure) or Why (Domain)?"
    • Extra credit: a banking transfer system (overdraft protection, currency conversion, international gateways: a high-stakes rich domain)
    • Guided solution in Appendix A.
  • Lingering problem: in classic layering the core still points down at the database ("Infrastructure Anchor"). Ch. 5 flips it: an "architectural airlock".
  • Recap:
    • layered = SoC for the application
    • four layers
    • downward rule is golden
    • layers logical vs tiers physical
    • cross-cutting by injected abstractions
    • avoid Fat Controller + Anemic Domain
    • use a Rich Domain
    • the idea mirrors OSI.
