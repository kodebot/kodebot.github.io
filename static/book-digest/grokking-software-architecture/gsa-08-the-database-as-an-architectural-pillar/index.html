Grokking Software Architecture 8: The Database as an Architectural Pillar

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 8. Previous: Grokking Software Architecture 7: Event-Driven Architecture (temporal decoupling and async communication). Next: Grokking Software Architecture 9: Architecting for the Cloud (pets for cattle, concrete for code).

Takeaways
  • The database is a pillar, not a magic bucket: a poor choice or schema cannot be rescued by clean controllers.
  • Three families: SQL (strict order), NoSQL (massive scale), Vector (semantic meaning). The SQL vs NoSQL feud is largely over: they converged.
  • Default to PostgreSQL until you hit an empirical limit.
  • ORMs are productive but leaky (N+1, massive objects, client-side evaluation).
  • Normalise by default; denormalise, cache or add read replicas only for a measured bottleneck.
  • Index columns used in WHERE, JOIN, ORDER BY; indexes carry a write penalty.
  • Parameterised queries stop SQL injection. "Data outlives code."

8.2.1 The relational model (SQL)

A relational database (RDBMS) stores data in tables (rows and columns). Three traits:

  1. Strict schema: define structure upfront. You cannot add FavoriteColor to one row without adding the column to the table.
  2. Normalisation: split data into logical pieces linked by foreign keys. Store the customer's address once in an Address table, not in every order.
  3. Declarative integrity: the engine rejects invalid writes. No child without a valid parent (no "orphans").

Keys

  • Primary key (PK): the row's unique, non-null identity. It must never change (use an integer or UUID, not an email).
  • Foreign key (FK):
    • an explicit constraint (e.g. Orders.CustomerId references Customers.Id)
    • Merely naming a column CustomerId does not create it
    • Docs: https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints.
  • Guardrail: cannot create an order for a customer that does not exist. Safety net: cannot delete a customer with open orders.
  • Why PKs matter: two users named John Smith; DELETE ... WHERE Name = 'John Smith' removes both; WHERE UserId = 101 removes one.

History: before 1970 databases were hierarchical or network models; apps navigated physical record paths. **E. F.

(Ted) Codd** at IBM published "A Relational Model of Data for Large Shared Data Banks" in 1970 (https://doi.org/10.1145/362384.362685): flat tables ("relations") linked by common values, and normalisation to reduce redundancy.

It shifted the industry from imperative to declarative retrieval.

Champions

  • PostgreSQL: the all-rounder and reliability standard.
  • SQL Server / Oracle: enterprise scale and support.
  • MySQL: read-heavy web apps (WordPress, early Facebook).
  • SQLite: a single file, no server: mobile, small tools, local testing.

ACID (coined 1983 by Theo Härder and Andreas Reuter, building on Jim Gray's transaction research; "Principles of Transaction-Oriented Database Recovery": https://dl.acm.org/doi/10.1145/289.291). Example: buying the last limited-edition sneakers.

Letter Meaning Sneaker example
Atomicity all or nothing no inventory deduction without an order record; payment timeout rolls back everything
Consistency only valid-to-valid states "inventory cannot drop below zero" rejects a sale a millisecond after sell-out
Isolation transactions don't peek others see "1 pair left" or "Sold out", never the half-done maths
Durability committed = permanent survives the server catching fire
  • Durability is NOT a backup. A DELETE with no WHERE is durably deleted. Configure automated point-in-time backups (a reason to prefer managed PaaS).
  • Isolation levels
    • are a volume dial: Serializable (strictest, slow; financial ledgers)
    • Read Committed (default in PostgreSQL; right for ~95% of apps)
    • Read Uncommitted ("Wild West", dirty reads; non-critical analytics only).

Choose by data access patterns (how data moves: query shapes, read/write ratio, payload size, latency, lookups), not feature lists. SQL fits when:

  • it is your default: ~90% of business data (users, orders, inventory, financials), until evidence says otherwise;
  • you need ad-hoc, complex joins across domains ("active orders by customers in Asia in the last 30 days with payment history");
  • query shapes are unpredictable;
  • integrity constraints must hold at the storage layer.

Counter-case: if you always read or write a whole entity by one key (e.g. a full UserProfile), spreading it over five tables adds join overhead; document or key-value stores shine.

The SQL landscape

Database Archetype Pros Cons
PostgreSQL modern standard advanced open source; JSON, PostGIS, vector search tooling (pgAdmin) less polished
SQL Server enterprise workhorse SSMS tooling; Azure SQL serverless tier licensing cost; tied to the Windows ecosystem
MySQL / MariaDB web scale powers Facebook, WordPress, Uber; cheap reads historically looser constraints; fewer analytics features
Oracle "too big to fail" banks and airlines; granular hardware/locking control astronomical cost; steep curve; needs a DBA

PaaS = treat the database as a managed utility: the provider handles OS, patching, upgrades, backups, scaling (https://azure.microsoft.com/en-us/resources/cloud-computing-dictionary/what-is-paas). More in ch. 9.

Author's advice: default PostgreSQL; high-scale reads MySQL/MariaDB; mobile/IoT SQLite.

8.2.2 The document model (NoSQL)

SQL is a strict librarian; NoSQL is the collector with a bin. NoSQL emerged for scale, speed and unstructured data; it scales horizontally.

  • Aggregate orientation: group related data (profile, addresses, recent orders) into one aggregate (a JSON document) fetched in one operation (Fowler: https://martinfowler.com/bliki/AggregateOrientedDatabase.html).
  • Pros: looks like your classes (serialise a User to JSON); no join tax (the address is a nested object).
  • Con: harder to update across many documents (changing every red brick: one drawer in SQL, every box in NoSQL).

Champions

  • Document: MongoDB, CosmosDB, DynamoDB (variety, prototyping).
  • Key-value: Redis (caching, sessions, sub-millisecond; "coat check ticket").
  • Wide-column: Cassandra (write throughput; IoT, activity tracking, millions of events per second).

The hidden trap: "schema-less" is a myth. You only choose whether the database enforces the schema (SQL) or your application code scatters it (NoSQL).

  • Schema drift: different services write fullName, name, or nested firstName/lastName into one collection.
  • Application-level migration pain: no single migration query; code needs defensive if (doc.has("legacyField")) blocks or risky back-fill scripts.
  • Consistency trade-off: BASE is fine for a "like" count, not for balances or inventory.

Three conventions: (1) standardise key naming (camelCase, userId); (2) application-layer validation (Zod, JSON Schema); (3) keep embedded sub-documents identical (street, city, zipCode, not addr).

BASE (https://queue.acm.org/detail.cfm?id=1394128):

  • Basically Available: if a node fails another takes over.
  • Soft state: state changes without input; replication lag means Server A may show the new profile picture while B is catching up.
  • Eventually consistent: stop writing and all readers converge.

SQL vs NoSQL

Requirement SQL (librarian) NoSQL (collector)
Structure predictable fluid (shirts, shoes, electronics)
Integrity absolute ($1 discrepancy is a disaster) flexible ("like" count)
Relationships complex joins isolated aggregates
Scaling vertical, one big source of truth horizontal, many cheap servers
Best for accounting, ERP, medical records, inventory IoT logs, leaderboards, CMS, prototyping

Blurring lines / tunable consistency. MongoDB 4.0+ and DynamoDB offer multi-document ACID transactions. Tunable consistency lets you choose per request how many servers must confirm a write (e.g. MongoDB write concern: https://www.mongodb.com/docs/manual/reference/write-concern/):

  • fastest: one server acknowledges (a video "Like"; may be lost if that server crashes);
  • quorum: a majority confirms (a profile bio edit);
  • strict: every server confirms (a $500 payment).

("NoSQL" can be read as "Not Only SQL"; Fowler, NoSQL Distilled: https://martinfowler.com/books/nosql.html.)

8.2.3 Vector databases

SQL and NoSQL are literal: "puppy" finds only the characters P-U-P-P-Y. Vector databases search meaning.

  • Embeddings:
    • an AI model turns text or an image into a vector (a long list of numbers; one number may score "red-ness", another "casualness")
    • Real models: 768 dims (BERT), 1536 (OpenAI ada-002), 3072 (text-embedding-3)
    • Illustration: dog [0.1, 0.9, 0.3, …], puppy [0.1, 0.85, 0.3, …] (close), car [0.9, 0.1, 0.0, …] (far)
    • Docs: https://platform.openai.com/docs/guides/embeddings.
  • A query for "Canine" is embedded and matched to nearest neighbours: dog and puppy.
  • Players: Pinecone (managed; https://www.pinecone.io), Weaviate (open source; https://weaviate.io), pgvector (Postgres plugin; https://github.com/pgvector/pgvector), Azure AI Search.
  • Use for: semantic search ("something to wear to a wedding"), recommendations ("users who liked this movie..."), RAG (retrieval-augmented generation: give an LLM your private documents).
  • Two taxes: accuracy (ANN, approximate nearest neighbours: probabilistic; "mathematically close" can be dangerously wrong in medical or legal apps) and infrastructure (memory-hungry indexes, plus embedding API cost).

Same task, three styles (saving and finding a Lasagna recipe):

-- SQL: exact match
INSERT INTO Recipes (id, name, type) VALUES (1, 'Lasagna', 'Pasta');
SELECT * FROM Recipes WHERE type = 'Pasta';      -- "Italian" finds nothing

// MongoDB: flexible keys, still exact words
db.recipes.insertOne({ name: "Lasagna", tags: ["pasta","cheese","italian","dinner"] });
db.recipes.find({ tags: "pasta" });

# Vector: similarity
vector = openai.Embedding.create(input="Lasagna", model="text-embedding-ada-002")['data'][0]['embedding']
vector_db.upsert(id="recipe_1", values=vector, metadata={"name": "Lasagna"})
q = openai.Embedding.create(input="Comfort Food", model="text-embedding-ada-002")['data'][0]['embedding']
vector_db.query(vector=q, top_k=1)               # returns "Lasagna"

SQL = structure first, NoSQL = code first, Vector = meaning first.

8.2.5 The verdict: convergence

Neither side won; they merged. Today the choice is structure vs scale.

  • JSON columns: SQL got flexible.
  • Sharding:
    • SQL got scalable (Citus for Postgres: https://www.citusdata.com, Vitess for MySQL: https://vitess.io)
    • Sharding = splitting one database horizontally across servers (10 TB becomes 10 x 1 TB; users 1 to 1,000,000 on shard 1, etc.).
  • ACID transactions: NoSQL got safe.
  • Vectors: everyone got smart (pgvector).
  • Tip: standardise on PostgreSQL (relational + JSON + vectors) until a clear empirical limit (petabyte write volumes, very low-latency key-value cache).

8.2.6 Choosing your pillar

PACELC (ch. 7): always a latency vs consistency choice.

Question SQL (accountant) NoSQL (collector) Vector (brain)
Data type structured, strict relationships variable JSON high-dimensional embeddings
Consistency absolute (ACID) flexible (BASE/eventual) probabilistic
Priority integrity, complex joins write speed, horizontal scale semantic similarity
Search logic exact match key-value or field filter "neighbourhood" distance
Maintenance high (DBA for tuning) low to medium medium (needs an AI service)
Skills well-understood schema drift in code, clusters vector indexing, RAM, AI pipeline sync
Cost predictable (server size) pay per request/storage premium (RAM + embedding calls)
Trade-off speed for bulletproof accuracy strict structure for unlimited growth literal truth (and cash) for meaning

Video streaming example (hybrid):

  • Watch progress: raw write speed, millions of pauses per second → NoSQL (losing a few ms means resuming 3 s earlier: acceptable).
  • Billing and subscriptions: cannot double-charge or lose history → SQL.
  • Recommendations: semantic "mood" similarity → Vector DB.

The polyglot tax (never free):

  1. Cognitive load: PostgreSQL tuning, MongoDB aggregation pipelines and Pinecone indexing at once dilute depth; outages are debugged blind.
  2. CI/CD and infra: versioned SQL migrations (Flyway), document validation, vector reindexing; heavy Docker Compose locally.
  3. Cost and backups: baseline PaaS cost per engine, connection pools, monitoring, and synchronised point-in-time backups across paradigms.
  • Operational Tax Audit: is the gain worth a second pipeline, double monitoring and fragmented backups? If not a clear, data-backed yes, keep it in the primary engine.

8.3 ORMs and query builders

Object-relational impedance mismatch: objects (behaviour, encapsulation, references) vs relational tables (flat, set logic). An ORM translates; the abstraction is leaky: magic for ~90% of cases, spectacular failure for the other 10%.

Declarative querying: declare what, not how. Raw SQL: SELECT * FROM Users WHERE Age > 21 AND IsActive = 1 ORDER BY LastName;. Equivalents:

// C# Entity Framework / LINQ (https://learn.microsoft.com/en-us/ef)
var users = context.Users.Where(u => u.Age > 21 && u.IsActive).OrderBy(u => u.LastName).ToList();

# SQLAlchemy (https://www.sqlalchemy.org)
users = session.query(User).filter(User.age > 21, User.is_active == True).order_by(User.last_name).all()

// Prisma (https://www.prisma.io)
const users = await prisma.user.findMany({ where: { age: { gt: 21 }, isActive: true }, orderBy: { lastName: 'asc' } });

Why it matters: type safety (renaming Age to YearsOld breaks compilation, not production); security (parameterisation prevents SQL injection); refactoring (swap SQL Server for Postgres, often without rewriting queries).

The Law of Leaky Abstractions ("all non-trivial abstractions, to some degree, are leaky"):

  1. Massive object / SELECT *: db.Users.Find(1) pulls a 5 MB ProfilePicture; 100 users = 500 MB. Fix: projections (.Select(u => new { u.Name, u.Email })).
  2. Client-side evaluation: db.Users.Where(u => CalculateAge(u.DOB) > 18); SQL Server cannot run your C# function. Old EF6 silently downloaded the whole table and filtered in memory (10 rows wanted, 10 million fetched); EF Core 3+ throws InvalidOperationException: The LINQ expression 'CalculateAge(u.DOB)' could not be translated. Fix: rewrite with SQL-compatible logic (DateDiff/DATEADD), or .ToList() first for small datasets only.
  3. Hidden network I/O and N+1: lazy loading makes person.Address or user.Orders a silent query. Risks: thread timeout explosions under load; N+1 cascade (1,000 users = 1 + 1,000 queries). Fix: eager load or dedicated DTO queries; treat data access as explicit network operations.
  • Tip: ORM for ~90% of CRUD; for complex reports (window functions, CTEs, aggregations across a dozen tables) drop to raw SQL or a micro-ORM like Dapper.

8.4 Normalisation vs denormalisation

Normalisation ("one truth") Denormalisation ("speed demon")
Rule each fact lives in exactly one place duplicate data where it is read
Goal integrity: move once, every order sees the new address read speed: snapshot the address in the order, no join
Cost slower reads (invoice → customer → address joins) update the profile plus last 10 orders plus pending invoices (the "Hydra")
Analogy one library copy of The Hobbit 100 flyers with a typo
  • Verdict: normalise by default; denormalise only for a specific bottleneck (e.g. "Order History under 100 ms").
  • Three read-speed levers: denormalise, add a cache (Redis), use read replicas.
  • Schema migrations: version-controlled upgrade/rollback scripts (Flyway, Liquibase, ORM migrations) so local equals production.

Schema checklist

Element Clarity check
Primary keys every table has a unique, immutable ID
Foreign keys relationships enforced (no ghost records)
Unique constraints tell the database an email is unique, do not hope code catches it
Check constraints business rules at the bedrock (price > 0)
Correct types native DATE/BOOLEAN, not lazy strings
Sanity do not over-normalise (no EyeColor table for a string column)

8.5 Performance reality: indexing and types

The database is a physical machine: finite RAM, CPU, SSD IOPS.

Indexing ("phone book")

  • Without an index: full table scan (every row).
  • With an index:
    • a sorted B-tree lookup. A B-tree (balanced tree) keeps data sorted and supports search and insert in logarithmic time
    • "balanced" means every path is the same length (https://www.youtube.com/watch?v=SI6E4Ma2ddg).
  • Write penalty:
    • each INSERT/UPDATE/DELETE also updates every index B-tree (and may cause an expensive page split)
    • A table with 5 indexes means 1 table write plus 5 index maintenance operations.
  • Numbers: a good index can speed reads 100 to 1000x; each index costs 10 to 20% write speed.
  • Rule of thumb for user-perceived speed:
    • under 100 ms feels instant
    • 100 to 300 ms fine
    • 300 ms to 1 s noticeable
    • over 1 s frustrating (denormalise, cache, index). Mobile: add 200 to 500 ms for network.
  • Index:
    • columns in WHERE, JOIN, ORDER BY (Email, ForeignKeyId, CreatedDate)
    • Don't index low-cardinality columns (Gender, IsActive) or huge text (Bio, Comments) without full-text features
    • Resource: https://use-the-index-luke.com.

Data types (the "String trap")

  • Dates as strings ("2026-02-09") or booleans as text ("True") hurt performance (parsing every query) and storage (a boolean is ~1 byte in SQL Server; "False" is 5 bytes).
  • Use INTEGER (status code/enum), BOOLEAN, TIMESTAMP/DATETIME.
  • Guardrail: a DATE column rejects "February 31st" instantly; a string saves it and reporting crashes three months later.
  • A schema is a contract (like interfaces in ch. 3 and APIs in ch. 6).

8.6 Case study: the Hydra revisited

Original developers confused data with logic: a Retail scorecard looks different from a Manufacturing one, so they built 35 applications in one codebase: 35 classes, 35 stored procedures, 35 tables. Adding a "Global Risk Factor" meant 35 code changes and 35 SQL statements.

Hardcoded trap:

CREATE TABLE Retail_Scorecard (id INT PRIMARY KEY, revenue DECIMAL, same_store_sales DECIMAL);
CREATE TABLE Mfg_Scorecard    (id INT PRIMARY KEY, revenue DECIMAL, inventory_turnover DECIMAL); -- revenue duplicated

Fix ("Platform" approach): dynamic rows. "Same Store Sales" and "Inventory Turnover" are just attributes with definitions.

CREATE TABLE LoanApplication (id INT PRIMARY KEY, business_name VARCHAR(255), scorecard_type_id INT);
CREATE TABLE ScorecardAttributes (id INT PRIMARY KEY, scorecard_type_id INT, attribute_name VARCHAR(100), weight DECIMAL);
CREATE TABLE ApplicationValues (application_id INT, attribute_id INT, value DECIMAL);
  • Result: one engine rendering fields from the database; adding the Global Risk Factor = one row, no schema change, downtime or deployment.
  • Warning: Entity-Attribute-Value (EAV)
    • destroys type safety and kills query performance for cross-record filtering or reporting (https://www.dremio.com/wiki/entity-attribute-value-model/)
    • It worked because scorecards were fetched by ID
    • Use only for dynamic configuration or truly variable metadata, never for stable entities like Users or Orders.
  • "Data outlives code": model data correctly and you can rewrite the application a dozen times.

8.7 The Dork Side: Little Bobby Tables

xkcd "Exploits of a Mom" (https://xkcd.com/327): a school registers a child named Robert'); DROP TABLE Students;--.

  • SQL injection (SQLi): attacker input is executed as a command (https://owasp.org/www-community/attacks/SQL_Injection).
  • Vulnerable: "SELECT * FROM Students WHERE Name = '" + userName + "'" becomes ... Name = 'Robert'); DROP TABLE Students; --': a harmless SELECT, then DROP TABLE, then -- comments out the rest.
  • Fix:
    • parameterised queries (or an ORM): the template SELECT * FROM Students WHERE Name = @Name plus command.Parameters.AddWithValue("@Name", userName)
    • The engine compiles the SQL before inserting data, so the input is only a (weird) name
    • News-anchor analogy: concatenation = he reads "Go home early" and leaves; parameterised = "Please welcome Mr
    • Go Home Early".
  • SQLi dates to the 1990s and is still on the OWASP Top 10 (https://owasp.org/Top10/2025)
    • Never concatenate, even "internal" tools: any input crossing a trust boundary is hostile until proven otherwise.
  • More DB security:
    • least-privilege DB user (read/write only; never DROP/alter schema)
    • hash passwords (bcrypt or Argon2 with a random salt), never plaintext or reversible encryption
    • secrets in a key vault or environment variables, not source code.

8.8 Mission, checklist, recap

Mission: "Shop-Zilla". A legacy giant crashes every Black Friday (one SQL Server at 100% CPU). The CTO demands a full MongoDB migration ("Web Scale, schema-less"). Assign an engine to each workload:

  1. Shopping cart (thousands of writes/s, loss tolerable).
  2. General ledger (100% accurate, instant rollback).
  3. Similar products (distance maths, not keywords).
  4. Product catalogue (1 million reads per write, wildly varying structure).

Guided solution in Appendix A. (Hint from the text: ledger on NoSQL is a "suicide mission"; session data in SQL is what is killing the CPU.)

Recap: the database is a physical machine; polyglot persistence (SQL for ACID, NoSQL for scale, vectors for semantics); ORMs give productivity but leak; normalise by default; the Hydra shows bad modelling cannot be fixed by clean code; indexes are phone books with a write penalty; use native types; parameterise.
