Grokking Software Architecture 9: Architecting for the Cloud (pets for cattle, concrete for code)

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 9. Previous: Grokking Software Architecture 8: The Database as an Architectural Pillar. Next: Grokking Software Architecture 10: Architecting for Resilience and Scale.

Takeaways
  • The cloud is someone else's multi-tenant computer. Moving there is an architecture change, not a relocation; otherwise you buy "Very Expensive Web Hosting".
  • Treat servers as cattle, not pets: numbered, disposable, stateless (state lives in a database or object store).
  • The compute spectrum trades control for convenience: IaaS, CaaS, PaaS, FaaS, AIaaS.
  • Build infrastructure with Infrastructure as Code (Terraform), never ClickOps; read the execution plan; protect the state file.
  • Immutable infrastructure: never patch a live server; build a new image, switch traffic (blue-green), destroy the old one.
  • Cloud cost is an architectural constraint (FinOps). "Friends don't let friends type in production" (AWS S3 outage, 2017).

9.1 The cloud is not magic

  • Multi-tenancy:
    • you share physical CPUs and cables with strangers (an apartment building)
    • Noisy neighbour: another tenant hogging bandwidth or disk slows you even if your code is perfect.
  • Mindset change:
    • hardware used to be costly, permanent, fragile
    • now it is cheap, temporary, disposable. Uploading a tightly coupled stateful app to an AWS server is "Very Expensive Web Hosting".
  • IaC definition: automated provisioning with version-controlled text files: consistent, repeatable, restorable (Kief Morris, Infrastructure as Code: https://infrastructure-as-code.com/book/).
  • Scope:
    • the book is not about being a cloud administrator (no dashboards, virtual networks, OS tweaks)
    • But infrastructure can no longer be ignored:
      • on-premises hardware was a fixed sunk cost with a hard scalability ceiling
      • the cloud trades that for operational complexity and cost potential
    • Dropping rigid on-prem design into an elastic cloud makes the bill and the system blow up.
  • How to start:
    • Install Terraform (https://developer.hashicorp.com/terraform/install), write a "Hello World" resource (a storage bucket) in main.tf.
    • Prefer Terraform (cloud-agnostic) over CloudFormation or Azure Bicep for a first project.
    • Practise on free tiers (12 months) or LocalStack (simulated AWS on your laptop).
    • Delete something by mistake? Re-add it and rerun; the engine compares your file with reality.
    • Day one: set a billing alarm (e.g. $5) and always terraform destroy practice resources.

9.2 The cloud-ready diagnostic

Kelsey Hightower (Kubernetes: Up & Running: https://www.oreilly.com/library/view/kubernetes-up-and/9781098110192/) stresses a different mindset for state and failure. Three tests:

Test Question A "yes" means
Wipeout If I deleted your server now, would you lose data? stateful (images or sessions on local disk); not cloud-native
Midnight patch Do you log in and type commands to fix vulnerabilities? manual patches, configuration drift, unreproducible servers
Meteor Is everything in one Availability Zone (one data centre)? one power cut or lightning strike takes the business offline

9.3 Pets vs cattle

  • Pets:
    • early servers were expensive, hand-built and named (Zeus, Apollo, Gandalf). If Zeus dies he is irreplaceable and rebuilding takes weeks
    • pets are usually stateful (sessions, temp files, uploads on local disk).
  • Cattle: you can spawn 50 servers in under ten seconds. Number them (web-server-001...), terminate a sick web-server-042, and automation starts 043.
  • The rule: do not maintain state on the local server. An auto-scaler may destroy any instance at any moment, so sessions, temp files and uploads must go to an external database or object store (S3).
# Wrong (stateful): fragile local filesystem
with open('profile.jpg', 'wb') as f: f.write(user_upload)
# Right (stateless): external S3 bucket
import boto3
boto3.client('s3').put_object(Bucket='mybucket', Key='profile.jpg', Body=user_upload)

Statelessness is the "price of admission"; it levels up every earlier pattern:

  • -ilities (ch. 2): more scalability and reliability: add identical servers; any can die without data loss.
  • SOLID (ch. 3): loose coupling (DIP) lets you swap a local disk for a cloud bucket.
  • Layers (ch. 4): a stateless application layer can be cloned behind a load balancer.
  • Hexagonal (ch. 5): swap a "Local File System Adapter" for an "AWS S3 Adapter".
  • APIs (ch. 6): REST's "stateless" fits; send a JWT per request instead of server session memory, so a gateway can route request 1 to server A and request 2 to B.
  • EDA (ch. 7): any consumer can process any message and vanish when the queue is empty.
  • Database (ch. 8): the servers have "amnesia", so your database choice becomes the architectural anchor.
  • "Swiftie" payoff: a stateless shipping consumer lets the cloud spawn 500 identical servers, drain a million messages in minutes, then delete them all.

9.4 The compute spectrum: control vs convenience

Left = control and grunt work; right = convenience and surrendered control.

1. IaaS: virtual machines (EC2, Compute Engine, Azure VM)

  • Analogy: renting an empty warehouse. Provider: hardware. You: OS, runtime, network drivers, code.
  • Pro: root access, any OS tweak, legacy software as-is.
  • Con: the 3 a.m. tax: you patch; you pay 24/7 even at zero traffic.
  • Use:
    • lift and shift of a big stateful "pet" with no budget to rewrite (you only "moved the cage")
    • COTS software needing a dedicated server
    • custom kernel modules. Avoid for brand-new projects. (https://azure.microsoft.com/en-us/resources/cloud-computing-dictionary/what-is-iaas)

2. CaaS: containers (Docker, Kubernetes), the "sweet spot"

  • Analogy: the steel shipping container (1956) standardised loading; software containers standardise your code.
  • Provider:
    • hardware and host OS. You hand over an image: app + runtime + dependencies, a frozen blueprint
    • every container is a 100% identical clone (Docker docs: https://docs.docker.com/get-started/).
  • Pro: portable; "works on my machine" disappears; lighter than a VM.
  • Con: orchestration overhead: 500 containers need Kubernetes (the "port authority"); the meter runs while they run.
  • Use: microservices (containers are the engine behind them; ch. 12), polyglot estates (Python analytics, Node frontend, Go payments), cloud agnosticism.

3. PaaS (Heroku, AWS Elastic Beanstalk, Azure App Service)

  • Analogy:
    • a furnished hotel room
    • You hand over raw code (e.g. a GitHub repo); the provider provisions, installs the runtime, sets up the load balancer
    • You control code, environment variables, basic scaling rules (e.g. 2 to 5 instances by CPU).
  • Pro: top developer velocity; health checks, OS patches, scaling handled.
  • Con: the black box: a custom low-level library (e.g. C++ for video rendering) is impossible; lock-in.
  • Use:
    • startups/MVPs, standard stateless web apps (Spring Boot, Django, Express), zero-ops teams
    • Rules: stateless and config separate from code: Twelve-Factor App (https://12factor.net/).

4. FaaS: serverless (Lambda, Azure Functions, Cloud Functions)

  • Analogy: an on-demand Uber: car and driver exist only for the trip.
  • Almost no infrastructure control. You upload one function; the provider listens for a trigger, provisions, runs, destroys.
  • Pro: idle = $0.00; 100,000 fans = 100,000 parallel clones; pay per millisecond.
  • Con: cold start (a second or two to boot after scaling to zero); time limits (usually up to ~15 minutes).
  • Use:
    • spiky traffic, event-driven glue, async background work
    • It dictates how you write code (zero local state, strict time limit)
    • Fowler: https://martinfowler.com/articles/serverless.html.

5. AIaaS (OpenAI, Anthropic APIs)

  • Analogy: a self-driving taxi: you give the destination, not the directions. You abstract away the logic itself.
  • Pro: instant ML, vision and NLP in an afternoon.
  • Con: non-deterministic (may hallucinate; different Tuesday vs Monday) and expensive vs a database query.
  • Use: unstructured parsing (PDFs, messy emails), natural-language interfaces, generative workflows. Never for strict mathematical business logic.
  • "Confident know-it-all":
    • an LLM is a probabilistic prediction engine, not a database; it guesses the next word and sounds confident
    • Fix: RAG (Retrieval-Augmented Generation): retrieve real facts from a database, append them to the prompt, instruct "answer using ONLY this text" (open-book test taker)
    • Overview: https://aws.amazon.com/what-is/retrieval-augmented-generation/.

Cheat sheet

Model What you rent Control Best for Hidden trap
IaaS the metal high (OS) legacy, legal/compliance lift-and-shift; paying 24/7 for idle
CaaS the shipping port medium (environment, runtime) portable, standardised deployments orchestration overhead (Kubernetes)
PaaS the runtime medium-low (code, config) MVPs, standard web apps black box; vendor lock-in
FaaS the millisecond low (code only) spiky traffic, new startups cold starts; hard time limits
AIaaS the reasoning zero (prompts, payload) language/data processing without ML infra hallucinations: need RAG guardrails

Quick guide: custom OS or extreme control → IaaS; avoid lock-in and want portability → CaaS; focus on code with zero infra → PaaS; unpredictable spiky traffic → FaaS.

9.5 Spotlight: serverless in action

Moving a VM or container is mostly an infrastructure change; serverless dictates your code. You do not write app.listen(8080); the provider listens and your function is a dormant reaction to an event:

import json, boto3
def lambda_handler(event, context):                           # called when an event occurs (e.g. S3 upload)
    bucket_name = event['Records'][0]['s3']['bucket']['name']  # stateless: context comes from the event
    file_name   = event['Records'][0]['s3']['object']['key']
    print(f"Resizing {file_name} from {bucket_name}...")       # do the work
    return {'statusCode': 200, 'body': json.dumps('Image successfully resized!')}

Rules of the road

  • No luggage: total amnesia each run; no local disk, no global session variables.
  • Short fuse: a hard limit (often 5 to 15 minutes); a two-hour 4K video is the wrong vehicle. Pre-cut large workloads into bite-sized pieces.
  • Fast ignition: minimise dependencies and package size; no heavy frameworks.

Sweet spots

  1. Spiky API: 10 requests/hour on weekdays, 10,000/second during a Sunday broadcast.
  2. Cloud glue: webhooks and triggers (new user → welcome email).
  3. Nightly janitor: a 2 a.m. cron function that runs ~30 seconds a day.
  4. Shared utility: one function (e.g. state sales tax) called by five apps (even serving a shared JS UI component).
  5. Compute offload: a 5 GB CSV or a heavy AI image filter out of the phone or main web server.
  6. Message courier: consumers of a queue (1,000 functions drain a million ticket requests, then vanish).
  • -ilities:
    • serverless helps Usability (responsive, quiet laptop fans) and Affordability (no 24/7 servers). Cost: portability. A container moves AWS to Google in an afternoon
    • a Lambda is tied to proprietary triggers, security roles, and per-language signatures, so moving means a painful rewrite of routing logic.

9.6 IaC: defeating "ClickOps"

  • ClickOps:
    • building through the web portal creates a snowflake server: unique, fragile, unreplicable (Fowler: https://martinfowler.com/bliki/SnowflakeServer.html)
      • Scaling to 100 servers by hand means a missed firewall port by server 47
    • docs go stale as consoles change
    • configuration drift makes staging and production diverge.
  • Declarative vs imperative:
    • ClickOps tells the cloud how (click, wait, attach)
    • IaC states the what ("one database, 50 GB, two serverless functions") and the engine works out the steps. Terraform is the engine
    • HCL (HashiCorp Configuration Language) is the syntax (like Node.js vs JavaScript). Alternatives: CloudFormation, Bicep.
  • Three superpowers
    1. Peer review for servers: infrastructure in Git; a pull request before a firewall change. Win: fewer self-inflicted outages.
    2. Perfect replication: staging is a 1:1 clone in minutes. Win: speed to market.
    3. Disaster recovery as a keystroke: run the pipeline and rebuild the whole estate. Win: ten minutes instead of ten days.

9.7 IaC in practice (Terraform)

Terraform is "SQL for infrastructure": you declare a result and the engine plans the steps. It translates a plain-text blueprint into API calls; it relies on a state file of what it has built.

The monthly bill as a constraint: on-prem was a capital expense (pay once); cloud is an operating expense (a taxi meter).

Examples: a dev environment upgraded for load testing and forgotten ran up $10,000; a 96-core database where 2 cores suffice ("renting a warehouse for one bicycle"); an event-driven serverless function triggering itself in an infinite loop can cost tens of thousands in hours.

FinOps = cloud financial management (https://www.finops.org/).

Reviewing a blueprint (the questions to ask):

provider "aws" { region = "us-east-1" }                     # Why only one region? DR?
resource "aws_db_instance" "primary_db" {
  identifier = "user-profile-database"
  engine = "postgres"
  instance_class = "db.t3.micro"                            # Big enough for launch traffic?
  allocated_storage = 50                                    # What happens when 50 GB fills?
}
resource "aws_s3_bucket" "profile_pictures" {
  bucket = "shopzilla-user-profiles-prod"                   # Automated backups enabled?
}
resource "aws_s3_bucket_public_access_block" "secure_pictures" {
  bucket = aws_s3_bucket.profile_pictures.id
  block_public_acls = true
  block_public_policy = true                                # GOOD: public access blocked
}

Identity as the boundary: with the physical perimeter gone, identity is the primary boundary (details in ch. 11). Authentication = who; authorisation = what they may touch. Rules: no hardcoded admin credentials; least privilege (an Order Service reads and writes only the Orders table); short-lived tokens or runtime roles, not static keys.

The execution plan (dry run): + create, ~ modify, - destroy.

+ resource "aws_instance" "web_server" { ami = "..."  instance_type = "t3.micro" }
~ resource "aws_security_group" "firewall" { description = "Allow web traffic" -> "Allow web and API traffic" }
- resource "aws_db_instance" "primary_db" { engine = "postgres" }
Plan: 1 to add, 1 to change, 1 to destroy.

A red - on a critical resource like primary_db: stop the deployment and ask why.

The state file

  • On the Tuesday run Terraform does a three-way comparison:
    • your code ("one Postgres"), the state file ("built one yesterday"), the real cloud ("it's there")
    • Difference zero → "Infrastructure is up to date." Change allocated_storage 50 → 100 → one API call to expand.
  • Single point of failure: lose terraform.tfstate and Terraform forgets, builds a second database, and orphans production's.
  • Teams: use remote state (a durable bucket such as S3) with state locking (often a database table) so two developers can't deploy at once.
  • Modules: split networking, database, serverless into independent pieces (separation of concerns) so a function mistake can't touch the database module.
  • Warning: state can contain secrets (master passwords) in plain text: .gitignore it, use an encrypted remote backend.

9.8 The immutable infrastructure mindset

  • Mutable vs immutable:
    • a var can be changed anywhere (race conditions); a const is replaced, not modified (age 30 → create a new object with 31)
    • A server is a large, expensive variable. Mutable servers were the on-prem norm (an admin patched the live box)
    • In the cloud forbid it
    • Bonus: it removes the nagging "what if someone changed production" stress.
  • Analogy: a dry-erase board (edit live, smudged, no undo) vs a printed flyer (fix the source file, print 100 new copies, replace).
  • The immutable pipeline (Figure 9.6):
    • update Terraform or the Dockerfile
    • build a new, fully patched server from scratch
    • route traffic to it
    • destroy the old one
    • verify. This is Blue-Green Deployment: blue = current production, green = the new version
      • flip traffic after verification, flip back instantly if it fails (https://martinfowler.com/bliki/BlueGreenDeployment.html)
  • Why architects demand it:
    • Zero configuration drift (same blueprint everywhere; only sizes differ).
    • Trivial rollbacks (re-route to the old frozen server).
    • Security by destruction: servers are routinely destroyed and rebuilt, deleting any attacker's backdoor.
  • The exception: stateful databases.
    • You cannot destroy and rebuild a live Postgres to patch its OS. Golden rule: the application layer is stateless and immutable
    • the data layer needs careful persistent change management.
  • "Do it tomorrow": pick one QA/staging server; plan to lock out manual logins, bake updates into a fresh image or container, and force all deployments through the pipeline.

9.9 The Dork Side: the AWS S3 outage

28 February 2017: half the internet went dark (Slack, Trello, Quora, IoT bulbs and thermostats). AWS US-EAST-1 S3 failed, cascading. Cause: a typo.

An authorised engineer debugging the billing system logged into a live production terminal to remove a small number of servers; the command removed a large set of core servers controlling S3 region metadata; the system obeyed; outage over four hours.

Lesson: not "hire engineers without typos" but "friends don't let friends type in production": via IaC the typo is caught in review or blocked by testing. Review checkpoint: "Does this plan delete any data?"

9.10 Mission, checklist, recap

Mission (Shop-Zilla Recommendation Engine; needs an API runtime, an in-memory cache for sessions, and a secure bucket for compiled ML models):

  1. Choose a spot on the compute spectrum for the API and defend it.
  2. List the three Terraform resource blocks.
  3. A critical OS vulnerability appears; the CTO orders you to patch live: explain why you refuse and the exact steps you take instead (immutable pipeline). (Guided solution in Appendix A.)
