Grokking Software Architecture 11: Foundational Security Architecture

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 11. Previous: Grokking Software Architecture 10: Architecting for Resilience and Scale. Next: Grokking Software Architecture 12: The Great Debate: Monoliths vs Microservices.

Takeaways
  • Security is a first-class architectural attribute (one of the -ilities), not a launch-week checklist. Assume the perimeter will be breached; limit the blast radius.
  • Two mental models: Least Privilege and Defense in Depth.
  • Structural tools: API gateway (single chokepoint), Identity Provider (OIDC + OAuth 2.0, JWT), Zero Trust (mTLS, service mesh), Secrets Manager (rotation).
  • Practice: threat model with STRIDE; automate checks (policy as code, SAST, SBOM).
  • Lesson of Target 2013: a system is only as secure as its least secure integration.

11.2 The security mindset

Principle of Least Privilege (PoLP)

Restrict users, systems and processes to the minimum permissions needed. Keycard analogy: the receptionist's stolen card opens the coffee machine, not the server room.

  • Deny by default, grant granular capabilities (read-only on one table, call one internal API).
  • Monolith problem: one "God Mode" database login (admin/password123) means a bug in "Update Profile" can drop the database.
  • Where to enforce
    • Database: a reporting service connects with SELECT only.
    • Network: an email-queue worker denies all inbound traffic.
    • File system: a web app that only reads config gets no write or execute rights.
  • The wildcard danger:
    • developers reach for * to move fast
    • forgetting to remove it before production destroys least privilege. Ask the Boundary Keeper's question: "what is the narrowest set of data this service needs?"
  • Reduce friction so people don't bypass security: automate permissions with IaC; use Just-In-Time (JIT) access (temporary, auto-expiring elevated rights for debugging).
  • Splitting a "God database": Ambler and Sadalage, Refactoring Databases.

Defense in Depth (the castle approach)

The old perimeter model is an egg: hard shell (firewall), soft centre (trusted internal network). It is broken because the perimeter has dissolved (remote work, mobile, BYOD, third-party cloud integrations) and attackers bypass what remains (phishing, social engineering, supply-chain attacks). Defense in depth uses multiple independent layers:

  1. Passive network security (moat and walls): VPCs and strict subnet routing so the internet never reaches databases or workers.
  2. Active perimeter defences (archers): WAF, IPS, rate limiters; drop malicious traffic, ban IPs, stop brute force.
  3. Identity and access management (portcullis): strong authentication and authorisation on every request.
  4. Application defences (inner guards): account lockouts, input validation (SQL injection).
  5. Data security (vault): encryption at rest and in transit; a stolen database file is gibberish.

Combined with least privilege, a breach is contained while monitoring detects it.

11.3 API gateways, identity providers, zero trust

API gateway: the single chokepoint

A centralised edge server that is the single entry point for external requests. Fifty doors from the wilderness would be undefendable. External clients cannot talk to microservices directly.

  • Rate limiting: drop a single IP trying 500 logins in a minute before it reaches the auth service.
  • TLS termination: decrypt HTTPS once at the edge.
  • Request routing: GET /orders/123 goes to the right service.
  • Initial authentication: the bouncer checks the ticket.

Identity providers: OAuth 2.0 and OIDC

Don't roll your own crypto or password hashing. Use an Identity Provider (IdP) (Auth0, Okta, AWS Cognito): manages identities, authenticates, issues verifiable tokens, centralises MFA.

  • OIDC (OpenID Connect): authentication, who you are (a digital passport).
  • OAuth 2.0: authorisation, what you may do (a valet key: drive, not open the glovebox). Spec: https://tools.ietf.org/html/rfc6749.
Scenario OAuth 2.0 flow Characteristic
Human logging into a web or mobile app Authorization Code (with PKCE) redirect to the IdP's login page
Backend service to service (machine to machine) Client Credentials no human; the service uses its own ID and secret to get a token
  • PKCE
    • (Proof Key for Code Exchange, "pixy"): protects public clients (mobile, single-page apps) that cannot keep a secret
    • a unique temporary code challenge per login makes an intercepted login code useless.
  • Using a browser redirect flow for a background server process is a leading cause of vendor-integration failures.
  • The flow:
    • login (with MFA) at the IdP returns a signed JWT ("I am the IdP; this user is John Doe with role User"). The client attaches it to every request
    • the gateway verifies the signature before forwarding.

JWT verification minefield (security only exists on the backend: hiding an "Admin Dashboard" button in React stops nothing)

  1. Verify against JWKS: fetch the IdP's public keys from its JWKS endpoint (never hardcode keys); unsigned tokens let attackers forge admin.
  2. Validate expiry: check exp; a validly signed token from three days ago is useless.
  3. Pin the algorithm: attackers edit the header to {"alg": "none"}, set the payload to {"user":"attacker","role":"admin"} and delete the signature. A misconfigured library skips verification. Explicitly accept only the expected algorithm (e.g. RS256).

Zero Trust: never trust, always verify

"Past the gateway means safe" lets supply-chain attacks pivot from a low-priority service (an analytics dashboard) into the payment database. Zero Trust abolishes implicit trust: every request, internal or external, must be authenticated, authorised and cryptographically validated.

  • mTLS (mutual TLS):
    • standard TLS only proves the server (bouncer checks your ID, you don't check his)
    • mTLS is a two-way ID check (the "blind date": both show certificates) for all service-to-service calls.
  • Order Service → Customer Service flow
    1. mTLS: both verify cryptographic identity.
    2. Order Service presents its own application token.
    3. Customer Service validates it and checks least privilege for that data.
  • Stance: with AI output you "trust but verify"; in security, never trust, always verify.

Implementing it: service mesh and sidecars

  • Writing mTLS and token code in four languages is a nightmare
    • A service mesh (Istio, Linkerd) deploys a sidecar proxy beside each service to handle mTLS, identity-based authorisation, routing and retries; application code stays unaware
    • Pattern doc: https://learn.microsoft.com/en-us/azure/architecture/patterns/sidecar.
  • Start with a proof of concept in staging on a few services; expand incrementally.
  • Legacy migration roadmap (no downtime)
    1. Audit mode: log all traffic, block nothing.
    2. Baseline: which services really talk to which.
    3. Identity: certificates for every service.
    4. Policy: gradually add least-privilege rules matching the baseline.
    5. Deny by default: block unexpected traffic.
  • Google BeyondCorp:
    • after a major 2009 attack Google dropped its privileged intranet
    • an on-campus employee has the same access as someone in a coffee shop (none): access depends on device health and user identity only.
  • Rightsize tooling:
    • Vault or a full mesh is overkill for side projects
    • Startups/MVPs: managed services (Doppler, AWS Parameter Store, Auth0, Clerk)
    • Regulated healthcare/finance may need self-hosted for audit.

11.5 Secrets management

Hardcoded disaster: psycopg2.connect(host="prod-db.internal.castle.com", database="orders_db", user="admin", password="Password123!").

  • Source control leakage: the secret lives in git history forever, even after deletion.
  • God account: violates least privilege.
  • Static vulnerability: changing it means a full redeploy.

Fix: fetch credentials at runtime from a Secrets Manager (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault) using a short-lived IAM role on the server. The code holds only the secret's name:

def get_database_credentials():
    client = boto3.session.Session().client(service_name='secretsmanager', region_name="us-east-1")
    try:
        resp = client.get_secret_value(SecretId="prod/BillingDatabase/Credentials")
    except ClientError as e:
        raise e                         # lacks IAM permission? it fails (least privilege)
    secret = json.loads(resp['SecretString'])
    return secret['username'], secret['password']
  • Why it is secure: no credentials in code; identity-based access (decommissioned server = revoked); a specific read-only secret (small blast radius); ready for rotation.
  • IAM equivalents
Cloud VMs Containers / serverless Search terms
AWS IAM role via EC2 Instance Profile IAM role on ECS task, IRSA for EKS IAM Roles, Instance Profiles
Azure system-assigned Managed Identity Managed Identity on AKS pod / Container App Managed Identities
Google Cloud Service Account on Compute Engine Workload Identity for GKE, Service Account on Cloud Run Service Accounts
Alibaba RAM Role on ECS RRSA for ACK RAM Roles
Oracle Instance Principal Workload Identity for OKE Instance Principals
  • Small projects on Vercel, Heroku, DigitalOcean App Platform: inject secrets into the platform's encrypted environment variables instead.

Secret rotation (e.g. AWS Secrets Manager can change a database password every 30 days). A password cached at boot fails at midnight with "Unauthorized" and the app crashes. Mature apps, using the resilience patterns of ch. 10:

  1. Catch the specific "Unauthorized / Login Failed" error.
  2. Invalidate the cached password.
  3. Fetch the fresh secret.
  4. Retry the operation, before the user notices.
  • Spring Boot
    • automates this: connection pools (HikariCP) plus Spring Cloud Vault or AWS Secrets Manager integrations evict dead connections, flush with @RefreshScope, fetch the new secret and rebuild the pool
    • Check for "dynamic secrets" plugins before hand-rolling.
  • If rotation itself fails (Secrets Manager down or corrupt): trip a circuit breaker to stop hammering the DB, and page on-call with an alert citing an authentication failure (not a vague timeout).
  • Compromise playbook
    1. Immediate revocation: invalidate and regenerate.
    2. Forced re-authentication: sever connections or block affected services.
    3. Audit and scope: logs show timeline and what was accessed.
    4. Stakeholder notification: security, operations, legal.
    5. Root cause remediation: how it leaked (git commit, social engineering).

11.6 Threat modelling: STRIDE

Threat modelling means analysing the architecture before writing code ("shift left"), like a robber studying the blueprint, instead of waiting for pen tests. STRIDE (Microsoft: https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats) has six categories:

Threat Question and example Mitigation
Spoofing Can someone pretend to be a user or service? (a rogue container posing as OrderService) IdP for humans, mTLS for services
Tampering Can data be modified in transit or at rest? (changing a shipping address in a request) TLS 1.2+ in transit, database encryption at rest
Repudiation Can someone deny an action? (a rogue admin drops a table, logs don't say who) immutable, append-only audit logs tied to verified identity
Information disclosure Can someone see unauthorised data? (API returns whole user object incl. password hash and relies on the UI to hide it) least privilege; anti-corruption layer filters payloads
Denial of service Can they exhaust resources? rate limiting and WAF at the gateway
Elevation of privilege Can a user gain admin rights? (backend trusts a form's role parameter) backend-only authorisation on every route using the verified JWT

If you cannot explain how an attacker might spoof a service or tamper with a payload, scouting is unfinished. Reading: Tanya Janca, Alice and Bob Learn Application Security.

11.7 The Dork Side: Target's HVAC hack (2013)

Late 2013: attackers stole card and personal data of over 40 million customers in the holiday season; est. cost $292 million, damaged stock price, CEO resigned. No zero-day: they came through the air conditioning.

  • How it happened
    1. Target's HVAC/refrigeration vendor had credentials to an external vendor portal (billing, contracts).
    2. Attackers phished the vendor and stole those credentials.
    3. Target's network was the "egg": once inside the firewall, traffic was implicitly trusted; poor segmentation let them pivot from billing to the network controlling point-of-sale registers.
    4. They installed custom malware on registers; card data was decrypted momentarily in memory after a swipe, so it was scraped from memory and exfiltrated.
  • Lesson:
    • a system is only as secure as its least secure integration
    • Least-privilege segmentation (the billing portal should have no route to POS; vendor credentials should only submit invoices) would have ended it at step 2.

Third-party integration rules

  1. Short-lived tokens: no permanent vendor API keys; OAuth tokens that expire after e.g. 15 minutes.
  2. Egress filtering: most firms filter inbound only. Allow outbound connections only to approved domains (e.g. api.stripe.com); an attacker can't download malware or exfiltrate.
  3. Automated enforcement
    • Policy as code and IaC scanning:
      • Open Policy Agent (https://www.openpolicyagent.org/; CNCF graduated), Checkov, tfsec fail the build if Terraform opens a route from a vendor subnet to the POS subnet
      • policies can be unit-tested.
    • SAST
      • (SonarQube etc.) flags hardcoded secrets and injection flaws
      • NIST list of analysers: https://www.nist.gov/itl/csd/secure-systems-and-applications/source-code-security-analyzers
      • (Fitness functions: ch. 13-14.)
  4. Defend the supply chain: treat build pipelines and dependencies as primary attack vectors.
    • SolarWinds (2020): attackers compromised the build system and injected a backdoor into a legitimate update; 18,000 customers incl. the US Government downloaded it.
    • XZ Utils (2024):
      • an attacker spent over two years volunteering, earned maintainer access from an exhausted developer, and inserted a backdoor that would have compromised SSH on millions of Linux servers
      • a Microsoft engineer noticed a 500 ms delay and investigated.
    • event-stream (2018): the tired maintainer handed publishing keys to a "helper", who added encrypted malware flatmap-stream that activated only when compiled in the build of Copay (Bitcoin wallet), stealing private keys of users with over 100 BTC.
    • Axios (March 2026): a package with over 100 million weekly downloads was compromised in two versions (https://www.microsoft.com/en-us/security/blog/2026/04/01/mitigating-the-axios-npm-supply-chain-compromise/).
    • left-pad (2016):
      • not an attack
      • a developer unpublished his packages after a trademark dispute, including an 11-line left-pad used by thousands (React, Babel, Facebook, Netflix, Spotify): millions of builds failed
      • npm changed its unpublish policy.
    • Mitigation: SBOM
      • (Software Bill of Materials): a machine-readable inventory of every dependency ("ingredients list")
      • the pipeline cross-references it with known vulnerabilities and halts the deployment if one is flagged. Also run CI/CD runners with least privilege (segregated deployment keys, secondary approvals).
  5. Continuous assessment (the 3 A's, ch. 1)
    • Awareness: automation: SAST (SonarQube, Snyk, Semgrep), secrets scanning, contract tests (Pact, Postman), anomaly detection (Datadog, AWS GuardDuty).
    • Alignment: regular reviews; record security choices and threat models in ADRs, revisited at least quarterly or on major integration changes.
    • Accountability: explicit owner per external integration; anti-corruption layers mask and limit data sent out.

11.8 Mission, checklist, recap

Mission: Blast Radius Audit of the Chapter 3 Order Processor. Deliverable: an ADR (Scribe role).

  1. Map entry points: one API gateway or services exposing their own endpoints? Where is the perimeter?
  2. Kill the God account: create a restricted user:
    CREATE USER order_processor WITH PASSWORD 'your_secure_password';
GRANT SELECT, INSERT, UPDATE ON orders TO order_processor;
    No DROP or DELETE.
  3. Hunt the secrets: remove hardcoded keys; use environment variables (locally a .env file excluded from source control, loaded via python-dotenv or dotenv).
  4. Enforce MFA on developer accounts, cloud console and repositories. (Guided solution in Appendix A.) Next: monoliths vs microservices (ch. 12).

Recap: security is architectural; PoLP; defense in depth; API gateway chokepoint; IdP with OIDC and OAuth; zero trust with mTLS and a service mesh; secrets managers and rotation; the 3 A's; STRIDE; assume the outer wall fails and contain the intruder.
