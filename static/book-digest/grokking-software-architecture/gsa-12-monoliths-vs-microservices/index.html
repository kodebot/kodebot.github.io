Grokking Software Architecture 12: The Great Debate: Monoliths vs Microservices

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 12 (Part IV: Architecture in the real world). Previous: Grokking Software Architecture 11: Foundational Security Architecture. Next: Grokking Software Architecture 13: Architecting for the Delivery Lifecycle (CI/CD).

Takeaways
  • It is a spectrum, not a binary: monolith → modular monolith → microservices. No heroes or villains, only trade-offs (see Software Architecture: The Hard Parts, Ford et al.).
  • Microservices are mainly an organisational scaling tool (Conway's Law), not a speed-up.
  • "Monolith first." Pay the Microservice Premium only when team size, asymmetric scaling, polyglot needs or regulatory blast radius justify it.
  • Avoid the distributed monolith (shared database or synchronous chains).
  • Migrate with the Strangler Fig (never a Big Bang rewrite), moving data with a snapshot plus CDC or an outbox.
  • Distribution brings the Network Tax (8 fallacies); retries amplify like the Bullwhip Effect.

12.2 The architecture spectrum

Moving to microservices is a two-step evolution: first decouple logic with strict interfaces (modular monolith), then decouple infrastructure across a network.

The monolith

All code (UI, business logic, data access) in one deployable unit, one process, shared memory.

  • Strength: simple to deploy and test; in-memory calls take fractions of a millisecond with zero network latency.
  • Weakness: boundaries are easy to bypass (a junior calls the database from the UI under deadline), producing a Big Ball of Mud.
  • All-or-nothing deploy and scale:
    • fixing a typo in inventory means redeploying everything (risking checkout)
    • you cannot scale memory-heavy image processing separately from CPU-heavy checkout: you buy a bigger server.

Microservices

A suite of small, independently deployable services modelled around business domains. No shared memory, and no shared databases.

  • Pro: scale inventory horizontally by itself; teams deploy dozens of times a day.
  • Cost: you monitor dozens or hundreds of apps; need network security, complex pipelines, distributed data consistency.
  • A microservice is SRP at infrastructure level: a server and its database have one reason to change.

Conway's Law

Melvin Conway, 1967: "Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure."

  • Microservices solve a human scaling problem:
    • 500 developers on one repository queue for deployments behind each other's broken builds
    • Decoupled release schedules give autonomy (https://martinfowler.com/bliki/MicroservicePrerequisites.html).
  • 5 to 15 developers: build a monolith. Without a large organisation, microservices are "architectural self-sabotage".

The trap: the distributed monolith

Separately deployed services that are still logically coupled: physical separation, extreme logical coupling (the opposite of high cohesion and loose coupling).

  • Shared database: five services on one SQL schema all break together on a schema change.
  • Synchronous coupling: OrderService calls PaymentService live over HTTP (temporal coupling, ch. 6-7): if payment crashes, so does ordering.
  • You inherit latency, packet loss and debugging pain while gaining no agility: "a ball of mud stretched across a fragile network".

The modular monolith (golden middle)

One deployable unit whose internals are strictly separated into isolated modules that may not touch each other's internals or tables; communication only through well-defined interfaces. Like a cruise ship with watertight bulkheads.

Vertical Slice Architecture (Jimmy Bogard: https://jimmybogard.com/vertical-slice-architecture/)

  • Group code by business feature, not technical layer. A "Checkout" slice holds its own endpoint, logic and queries (a slice of cake: frosting, cake and filling together).
  • Horizontal grouping (all controllers in UI, all logic in Services, all queries in Data) forces you through three folders to understand one feature.
  • Result: highly cohesive modules; extracting Checkout later is "copy that folder into a new repository".

Enforce the boundaries

  • Human nature is the risk (importing the UserProfile model into Checkout).
  • Write automated architecture tests (ArchUnit for Java, NetArchTest for C#) in CI/CD; the build fails if the Checkout namespace references UserProfile.

Monolith Microservice Modular monolith
Deployment unit single executable multiple independent services single executable
Interaction in-memory calls network (REST/events) in-memory via strict interfaces
Scaling all-or-nothing (vertical) independent (horizontal) all-or-nothing (vertical)

12.3 Why "monolith" is not a dirty word

  • Resume-Driven Development: choosing Kubernetes and microservices to decorate a CV, not because the business needs them.
  • A monolith is optimal when the project is young, requirements fluid, team small.
  • The Majestic Monolith
    • (David Heinemeier Hansson, creator of Ruby on Rails, founder of Basecamp): Shopify, Stack Overflow and Basecamp serve huge scale on well-structured modular monoliths
    • Often you just need a bigger web server and a scaled database.
  • Developer velocity: early on the risk is building what nobody buys; time to market beats infinite scale.
  • Pivot example (Shop-Zilla): GuestUser and PayingCustomer are merged into Account.
    • Monolith: an IDE rename and a test run: a few hours.
    • Microservices: change API contracts in three services, deprecate old APIs, write cross-network data migrations, coordinate deployments: weeks.
  • The Microservice Premium
    • (Fowler: https://martinfowler.com/bliki/MicroservicePremium.html): microservices cost simplicity and money for independent scalability. You need CI/CD, centralised logging, distributed monitoring and container orchestration
    • a small team's productivity grinds to a halt.
  • "Monolith First"
    • (https://martinfowler.com/bliki/MonolithFirst.html): start with a well-structured modular monolith
    • split when developers constantly step on each other during deployments or a module needs drastically different hardware.

12.4 When microservices actually win

  1. Human scaling (Conway at scale): 200 engineers on one repository block each other. 20 services turn them into autonomous teams of ~10 who deploy 50 times a day with architectural accountability (the third A).
  2. Extreme asymmetric scaling: User Profiles need little compute; Video Transcoding needs expensive GPUs. In a monolith you run profile code on $5,000/month GPU servers. Extract transcoding to its own GPU cluster.
  3. Polyglot environments: Python for data science, C#/Java for the enterprise backend, Rust for high-frequency trading. Services talk over HTTP or brokers, language-agnostic (https://martinfowler.com/bliki/PolyglotPersistence.html).
  4. Regulatory and security blast radii: PCI-DSS audits cover everything sharing memory and infrastructure. A separate Payment service with its own database shrinks audit scope and cost; a hacker in "Product Reviews" is trapped in its container (enforce with mTLS, ch. 11).

12.5 The Strangler Fig pattern

Big Bang Rewrite ("stop features for 18 months"): requirements change and competitors move on; the "perfect" system is stale at launch.

Botanical inspiration: an Australian rainforest strangler fig starts in a host tree's canopy, sends roots down, encases the host; the host decays, leaving the fig. Grow the new system around the old until the old is unneeded (same idea as ch. 5, now at macro scale).

Extracting "Billing" in four steps

  1. Gateway intercept (plant the seed): put an API gateway in front of the monolith; 100% of traffic still goes to it; no legacy change.
  2. Build the new vine: build the Billing microservice in a separate repository with its own database (hexagonal, zero risk: no live users).
  3. Strangle the data (the hard part; "data is gravity"): Snapshot-and-Stream:
    • Snapshot: one-time bulk copy of historical data (pg_dump, AWS DMS).
    • Stream: capture and replay changes after the snapshot began, until both are in sync.
    • Option A: Change Data Capture (CDC):
      • a non-invasive tool reads the database's transaction log (running record of every INSERT, UPDATE, DELETE) and streams changes
        • industry standard Debezium (on Kafka: https://debezium.io/)
      • It bypasses messy legacy code
      • Log-purging trap: databases roll over and purge old WAL/redo logs, so a new CDC engine only sees changes from today: you cannot skip the snapshot.
    • Option B: application-level syncing via the Transactional Outbox
      • (when you lack log access)
      • Dual writes (save to both databases in code) are dangerous: a network blip after the first write leaves systems permanently out of sync (https://www.confluent.io/blog/dual-write-vs-change-data-capture/)
      • Outbox:
        • write business data and a message into an outbox table in the same local transaction
        • a relay (custom or Debezium) delivers messages and deletes them only after delivery (https://microservices.io/patterns/data/transactional-outbox.html).
  4. Reroute the traffic (the strangulation): gateway rule: /catalog and /checkout to the monolith, /billing to the new service. The old billing code is dead. Repeat for Inventory, Shipping...; finally every route points to a microservice and the monolith is starved and deleted.

12.6 The Network Tax

The unavoidable performance, reliability and operational overhead of replacing in-memory calls with network calls (Kleppmann, Designing Data-Intensive Applications, chapter 8 "The Trouble with Distributed Systems": https://dataintensive.net/; Fowler: https://martinfowler.com/articles/patterns-of-distributed-systems).

The 8 Fallacies of Distributed Computing (Sun Microsystems, 1994; originally drafted by L. Peter Deutsch and expanded by James Gosling; explained by Arnon Rotem-Gal-Oz: https://www.researchgate.net/publication/322500050_Fallacies_of_Distributed_Computing_Explained):

  1. The network is reliable.
  2. Latency is zero.
  3. Bandwidth is infinite.
  4. The network is secure.
  5. Topology doesn't change.
  6. There is one administrator.
  7. Transport cost is zero.
  8. The network is homogeneous.

The taxes

  • Latency tax (#2).
    • A dashboard needs profile, recent orders and shipping status
    • Monolith: one SQL JOIN, ~5 ms
    • Microservices: three calls (30 ms network + 5 ms JSON = 35; 30 + 10 = 40; 30 + 5 = 35) = 110 ms sequentially
    • Pay with parallel async calls, event-driven design, aggressive caching.
  • Reliability tax (#1). Every call can fail: timeouts, retries, circuit breakers (ch. 10).
  • Serialisation tax (#3).
    • Objects become JSON and back
    • a "God object" payload for three fields wastes bandwidth and CPU. Pay with pagination, GraphQL, or binary gRPC/Protobuf internally.
  • Security tax (#4). An attacker in a low-level service can eavesdrop on traffic to the core database. Pay with zero trust, mTLS, service mesh (ch. 11).
  • Data consistency tax. Database-per-service means no cross-network rollback. Inventory deducts a laptop, the network dies before Billing: inconsistent. Pay with the Saga pattern.
  • Observability tax.
    • A monolith gives one stack trace
    • a click crossing gateway, auth, order and payment shows only a 500. Pay with distributed tracing and a correlation ID injected at the gateway and propagated to every service (ch. 14).

Saga pattern

Because services own databases there is no single ACID transaction. Each service commits locally and publishes an event; on failure, compensating transactions undo earlier steps (https://microservices.io/patterns/data/saga.html). Introduced in a 1987 paper by Hector Garcia-Molina and Kenneth Salem (https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf).

  • Happy path: Checkout saves the order, publishes OrderPlaced; Inventory deducts stock and publishes InventorySecured; Billing charges the card and publishes PaymentSecured.
  • Failure path:
    • Billing's card is declined and it publishes PaymentFailed
    • Inventory and Checkout both hear it (pub/sub) and compensate simultaneously (restore stock; mark the order "Failed").

  • Orchestration: a central saga manager commands the services. Easier to trace, but a single point of failure.
  • Choreography: services react to each other's events, no central boss. Resilient but hard to debug (logic scattered).
  • Frontend analogy:
    • choreography is like Redux/NgRx (immutable actions on an event stream; reducers update local state)
    • orchestration is like redux-saga, named after this backend pattern.
  • Guaranteeing the event is published: if Inventory saves but crashes before publishing, the saga breaks: use the Transactional Outbox (at-least-once delivery).

Summary table: fallacy → tax → solution

Fallacy Tax Solution

Latency is zero latency (5 ms becomes ~150 ms) async, EDA, caching
Bandwidth is infinite serialisation pagination, GraphQL, gRPC/Protobuf

12.7 Code: the network tax in action (blog endpoint)

Fetch a blog post, its author and recent comments.

Monolith (C#): one query, ~5 ms

var blogPost = _dbContext.Posts.Include(p => p.Author).Include(p => p.Comments)
                  .FirstOrDefault(p => p.Id == blogId);
if (blogPost == null) throw new NotFoundException();
return new BlogDetailsViewModel(blogPost);   // DB down = whole query fails together

Microservices aggregator: 3 HTTP calls plus fallbacks

var postTask     = _httpClient.GetAsync($"http://post-service/api/posts/{blogId}");        // latency tax
var authorTask   = _httpClient.GetAsync($"http://author-service/api/authors/{blogId}");
var commentsTask = _httpClient.GetAsync($"http://comment-service/api/comments/{blogId}");
await Task.WhenAll(postTask, authorTask, commentsTask);                                   // reliability tax
if (!postTask.Result.IsSuccessStatusCode) throw new Exception("Core post data unavailable.");
List<Comment> comments = new();                                                           // partial failure
if (commentsTask.Result.IsSuccessStatusCode) comments = await ...ReadFromJsonAsync<List<Comment>>();
else _logger.LogWarning("Comment service is down. Serving page without comments.");       // fallback

Same requirement, far more complexity (async, independent status codes, partial-failure fallbacks). Litmus test: "does our need for independent scaling outweigh this tax?"

12.8 The Dork Side: MIT's Beer Game (the Bullwhip Effect)

1960s, Jay Forrester, MIT Sloan: the Beer Distribution Game with four players (Retailer, Wholesaler, Distributor, Factory) and two rules: no talking (only paper order slips, like JSON over HTTP) and built-in multi-week delays both ways.

  • Demand is steady at 2 cases a week
    • one customer buys 4 extra. The retailer runs low, orders more
    • delay means empty shelves, so the retailer panics and orders much more. The wholesaler sees a spike and over-orders
    • so does the distributor.
  • By the factory, a 4-case blip is 4,000 cases. Mountains of beer later arrive at a tiny warehouse
    • everyone is bankrupt. This is the Bullwhip Effect: small edge fluctuations amplified deeper in the chain (https://mitsloan.mit.edu/teaching-resources-library/mit-sloan-beer-game-online).
  • Architectural lesson: retry storms.
    • A 2-second delay in the Payment API makes the Order Service "re-order" via retries
    • A naive loop (while (!success && retryCount < 3) calling PostAsync("http://payment-api/charge", order) immediately) with 1,000 users fires 3,000 un-spaced requests, melting the payment database.
  • Dampen it with the ch. 10 shock absorbers: circuit breaker (break out and fail fast) and exponential backoff with jitter.

12.9 Mission, checklist, recap

Mission: Stream-Flix. A new streaming startup (10 engineers, tight budget, MVP in 4 months for VC funding). The CEO wants 20 microservices on day 1 because "Netflix uses microservices". Write an ADR answering:

  1. Context: hard constraints; which laws or "premiums" from this chapter prove copying Netflix would destroy a 10-person startup?
  2. Decision: proposed style for the MVP (the modular monolith with vertical slices) and how to keep it clean.
  3. Consequences and escape hatch: two future triggers (e.g. "50th engineer" or "Transcoding uses 80% of server resources") and the extraction pattern (Strangler Fig); extract only the module needing independent scale, keep the rest a modular monolith.

Template: # ADR 001: Stream-Flix MVP Core Architecture / ## Status: Proposed / ## Context / ## Decision / ## Consequences & Escape Hatch. (Guided solution in Appendix A.) Next: CI/CD (ch. 13).

Recap: a spectrum; monolith is not a dirty word; Conway's Law; the distributed monolith is the worst trap; modular monolith via vertical slices; pay the Microservice Premium only at real triggers; Strangler Fig, never Big Bang; data is gravity (CDC); the network tax; sagas and outboxes; the Bullwhip Effect and retry storms.
