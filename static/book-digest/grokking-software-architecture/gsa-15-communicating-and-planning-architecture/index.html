Grokking Software Architecture 15: Communicating and Planning Architecture

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), ch. 15 (final chapter). Previous: Grokking Software Architecture 14: Architecting for Quality and Observability. Next: Grokking Software Architecture: Appendix A, Guided Solutions.

Takeaways
  • The best design is worthless if you can't convince the team and stakeholders. Architecture is a human coordination task.
  • Escape the Whiteboard Box Trap with the C4 model: Context, Containers, Components, Code. Every box: name + type; every arrow: protocol + intent; stay at one level.
  • Tailor the message: L1 for business, L2 for ops/SRE/security, L3 for developers.
  • Reach consensus with an RFC (future tense, fluid), record it as an ADR (past tense, immutable). Use disagree and commit; separate two-way from one-way doors.
  • De-risk with time-boxed spikes (throw the code away) and a Minimum Viable Architecture with metric-based evolution triggers.
  • Use AI as an adversarial reviewer, never as the owner of the decision.

15.2 Why good diagrams matter

A contractor handing you a napkin labelled "The Foundation" gets fired; teams routinely build multimillion-dollar systems from equally ambiguous diagrams.

The Whiteboard Box Trap: a box labelled "Order Service" could be a C# class, a Docker container, a microservice on five AWS instances, or a logical layer. Three developers form three mental models (a folder; a new Kubernetes cluster; the whole billing pipeline).

A good diagram uses strict scoping, clear boundaries, standard nomenclature and the audience's needs, not everything at once (not streetlights, highways and tectonic plates on one map).

15.3 The C4 model

Created by Simon Brown (between 2006 and 2011; https://c4model.com, tooling https://structurizr.com). Four zoomable levels, like Google Maps: continent (Context), country (Containers), city (Components), house (Code).

History: the Method Wars of the late 1980s and early 1990s (Booch's bubbles, OMT's rounded rectangles, others' clouds) led Booch, Rumbaugh and Jacobson ("The Three Amigos") to merge at Rational Software in 1994; the OMG adopted UML in 1997.

UML's rigid notation (dozens of diagram types) became a bureaucratic paper mill of thousand-page class diagrams that were obsolete within hours; Agile threw it out, and ad-hoc boxes replaced it. C4 is the middle ground.

Level Purpose Audience Example label
1 System Context the system as one opaque box; users and external systems; no tech jargon (Docker, Redis, C#) product managers, business stakeholders, new engineers Shop-Zilla System [Software System]
2 Containers independently deployable or runnable units that run code or hold data (not necessarily Docker); technologies, network and data boundaries core engineers, ops, SREs, security, architects Order Service [Container: C# / .NET Web API]
3 Components internal modules and layer boundaries of one container developers in that repository Order Processor [Component: Domain Logic Module]
4 Code class layouts, entity-relationship, or the code itself; usually auto-generated (IDE plugins, PlantUML, fitness functions) developers and tooling OrderValidationComponent : AbstractValidator

Level 2 detail: sync vs async arrows

  • Order Service to Order Database is a synchronous "phone call": it needs certainty the row is committed now (money, receipts).

  • Order Service to Billing is a "sticky note":

    • it posts "Order #1042 was placed" to the broker and walks away
    • billing may process it in 3 seconds or 3 minutes
    • a billing crash has zero blast radius on checkout.

  • Draw it: a synchronous link is a direct line (tightly bound in time); an asynchronous link interposes the broker box: producer to broker, then a separate arrow broker to consumer.

Level 3 (Order Service container): Order Controller receives API traffic, an Order Validation Component checks input, an Order Processor Component applies domain rules, an Order Repository Component saves.

Level 4 example (PlantUML text kept beside the code):

@startuml
OrderController -> OrderProcessor : Validate(Order)
OrderProcessor -> InventoryGateway : CheckStock(ItemId)
InventoryGateway --> OrderProcessor : StockAvailable
@enduml

Add architecture-as-code linters (NetArchTest, ArchUnit): "core business classes may not talk to low-level database driver files": the build fails on a shortcut around the ports.

Three golden rules

  1. Every box has a label AND a type: Inventory Service [Container: Go Web API], Inventory DB [Container: MySQL Database].
  2. Every arrow describes intent: Sends OrderPlaced Event via AMQP, Queries inventory levels via SQL/TCP.
  3. Pick a level and stay there: don't mix business value paths and code class loops on one canvas.

Reading: Simon Brown, Software Architecture for Developers (https://leanpub.com/software-architecture-for-developers).

Starting on Monday: don't hold a meeting to "adopt a standard"; draw a clean L2 or L3 in your next ticket and let colleagues copy it. Tools: PlantUML, C4-Builder, Excalidraw, Miro for speed; then Mermaid.js or Structurizr.

15.4 Tailoring communication

Showing a Level 3 component diagram (Entity Framework repository paths) to the CFO means a shelved proposal "due to a lack of business alignment". Translate between strategy and source code.

Group Level They care about Avoid
Business / product L1 conversion rates, budgets, time to market, user experience REST, Docker, PostgreSQL, Inversion of Control
Infrastructure / SRE / security L2 (+ network topology: VPCs, gateways, read replicas, broker clustering) availability SLAs, blast radius, security, scalability; where data crosses network partitions, secret handling, timeout/retry tolerances, autoscaling code interfaces, libraries, domain validation
Software engineers L3 maintainability, interfaces, repo structure, testability; ports, layer boundaries, request/response payload separation, CI fitness functions business metrics, manual deployment scripts

Pitch example

  • Wrong: "break the monolith into microservice boundaries connected via event streams to eliminate blocking database thread pools..." (blank stares).
  • Right:
    • "On Black Friday surges checkout crashes and we lose $30,000 an hour
    • A separate asynchronous billing service lets customers keep ordering even when third-party processors are slow, protecting conversion and revenue."

15.5 Consensus: RFCs and design reviews

"If you want to kill a technical idea, put it in front of a committee." Unstructured reviews argue over database choices and tab spacing. Build consensus in writing first.

The asynchronous pipeline

  1. Scribing: draft a lightweight proposal (context, choices, quality-attribute impact).
  2. Asynchronous feedback: a strict multi-day window for inline comments and edge cases.
  3. Design review gate: a targeted live sync only for contested items.
  4. ADR receipt: lock the RFC and archive the conclusion as an immutable ADR in the repo (ch. 2).

RFC anatomy

  1. Context and problem statement.
  2. System requirements and scope (non-negotiables, success boundaries, non-goals).
  3. Proposed architectural options (at least two, pros and cons by quality attributes).
  4. Recommendation (data-backed).

Worked sample: RFC-024 (Shop-Zilla) (status: approved, archived to ADR-012)

  • Problem:
    • the monolith's checkout shares one database thread pool with live catalogue queries
    • Black Friday catalogue reads exhaust connections, cascading latency that fails payment authorisations: $30k/hour lost.
  • Requirements: sustain 5,000 catalogue reads/s; a catalogue lockup has zero blast radius on checkout; ship in 3 weeks with 3 backend developers.
  • Non-goals: no refactor of the payment gateway, billing schemas, multi-region replicas or warehouse fulfilment.
  • Option A: keep one datastore, scale up: no code change, but locks remain a single point of failure and cost scales exponentially.
  • Option B: decouple inventory into an asynchronous microservice: isolated resources and a bounded context, but a sync worker and temporary eventual consistency.
  • Recommendation: B, with a dedicated MySQL instance, accepting slight eventual consistency on browsing to guarantee checkout availability.

RFC vs ADR (legislative bill vs law)

RFC ADR
Phase pre-decision: proposal, feedback, adversarial alignment post-decision: archive, tracking, governance
Tense future/present: "we are proposing A and evaluating B" past: "we chose B because of timeline constraints"
Mutability fluid; changes with reviews immutable, versioned in Git; only superseded by a new ADR
Location wikis, collaborative boards, PR threads repository under /docs/adrs/ (or wiki)

Reading: Richards and Ford, Fundamentals of Software Architecture.

Driving live reviews

  • Pre-read rule: no one reads the RFC aloud; unprepared attendees observe.
  • Assign a timekeeper and a note-taker.
  • Police rabbit holes: "That is an implementation detail; capture it in the ticket and return to the container integration paths."

Winning buy-in: don't pitch docs as "keeping files clean". Frame it as waste reduction: "Last sprint we stalled three days on conflicting assumptions about the connection pool and the queue; twenty minutes writing a two-page RFC avoids that and protects the deadline."

Technical dissent: the three-tier escalation (disagree and commit)

  1. Isolate the true constraint: map choices to real constraints ("does A or B violate our three-week window?").
  2. Quantify the cost of reversal:
    • Two-way doors (a date-format or logging library): pick the lowest setup effort and move on.
    • One-way doors (splitting the database, choosing a cloud provider or language): need deep synchronous reviews and spikes.
  3. Executive gate: for a deadlocked one-way door, someone decides. Disagree and commit: log the minority view in the ADR, sign off, and everyone aligns behind it.

15.6 De-risking: spikes and MVAs

A design is a list of assumptions (the database handles the writes, the vendor API stays under 200 ms, the broker won't mangle schemas). Test risky ones before committing resources.

Architectural spike

A brief, strictly time-boxed experiment to evaluate unknowns and gather baselines (a recon scout). Example: before migrating transactional inventory to a document store, one engineer gets 48 hours to write a throwaway script firing 10,000 simulated inventory mutations at a mock database.

  • Spike code is trash code: never merged into production branches (no review, no edge-case handling, no tests); delete or archive it.
  • Strict time box: one or two business days; if viability can't be shown, the option is too complex or volatile.
  • AI can generate sample schemas, mock drivers and throwaway configs, and act as an adversarial reviewer first.

Minimum Viable Architecture (MVA)

The leanest end-to-end design supporting the required quality attributes without early complexity; it avoids the perfection traps of ch. 2 (six months of multi-region clustering for zero users).

  • Early stage: a thin single-container modular monolith with one database (priority: time to market).
  • Scale stage: because modules are behind port boundaries (ch. 5), billing can later move to async workers without rewriting core rules.
  • Not sloppy code or skipped tests: a footprint matched to current scale. Reading: Building Evolutionary Architectures.

Architectural inflection points (triggers) for Shop-Zilla

  1. Database connection lockout: CPU pinned at 100%, or the database drops more than 1% of orders for lack of connections.
  2. Domain team split: the organisation grows from 3 to 12 developers; merge friction justifies separate services.
  3. Asymmetric scaling surge: on a sale, 49,500 of 50,000 users are browsing and searching (heavy reads) while only 500 swipe a card (heavy write). Splitting Inventory lets you run 50 cheap read-only instances while checkout stays small, isolated and fast.

15.7 AI as a brainstorming partner

You lean toward patterns you know; AI can be an unbiased challenger. A generic prompt ("a good backend architecture for e-commerce") yields buzzwords. Use the adversarial prompt blueprint:

Element Example
1 Role and persona "Take on the role of a Principal Software Architect and an aggressive Risk Scout."
2 Local constraints "Time to Market 3 weeks, team of 3 backend developers."
3 Proposed blueprint "A synchronous REST wrapper connecting our Order Container to a local database."
4 Adversarial attack "Identify structural failure vectors and data-integrity risks under high concurrency. Be critical but fair."
5 Constrained alternative "Propose an alternative MVA that fits our timeline."
6 Trade-off summary "Summarise the liabilities of my plan and compare with the alternative."
  • Warning: never paste proprietary source code or connection keys into a commercial model; describe integrations abstractly.
  • Hansel and Gretel trap: never surrender accountability (see "AI Didn't Ruin Your Codebase. You Did.": https://www.linkedin.com/pulse/ai-didnt-ruin-your-codebase-you-did-codeliftsleep-sdnse).
  • Three risks
    • Prompt injection and data security: leaking boundaries or keys into public models.
    • Hallucinated trade-offs: confident fabricated performance numbers or compatibility claims.
    • Capacity-planning illusion: AI cannot estimate real latency or compute thresholds without baseline data.

15.8 The Dork Side: the first software diagram (1947)

In the mid-1940s programming ENIAC (18,000 vacuum tubes) meant physically rerouting coaxial cables across plugboards and flipping dials; early programmers included Kathleen Antonelli, Jean Bartik and Frances Spence.

In 1945 John von Neumann wrote First Draft of a Report on the EDVAC proposing stored-program architecture (data and instructions as binary in the same memory). But then logic became invisible, and humans could not audit state by eye.

  • In 1947, at the Institute for Advanced Study (Princeton), von Neumann and Herman Goldstine published Planning and Coding of Problems for an Electronic Computing Instrument, arguing it was "absolute madness" to code complex logic without first mapping its paths, and introduced the Flow Diagram (ancestor of the flowchart).
  • Vocabulary: operation boxes (rectangles: variable updates), alternative boxes (diamonds: conditional forks), substitution boxes (index mutations in loops).
  • Lesson: as systems get more abstract and distributed, diagrams must become clearer and more precise.

15.9 Mission, checklist, recap

Mission: a C4 Level 2 Container diagram for the fragmented checkout. Product brief: browser frontend (catalogue, real-time stock, "Place Order"); immediate card authorisation through an external Payment Gateway API and a "Success" screen; stock checks must not lock the order-history database; a finalised order sends a shipping manifest to an external warehouse fulfilment system.

Solve: (1) containers and databases as distinct boxes; (2) data isolation (no service touches a foreign database); (3) label every arrow with protocol and intent (HTTPS REST, gRPC, AMQP, SQL/TCP) deciding sync vs async; (4) place the two external systems visibly outside the boundary.

Check that a warehouse outage cannot block checkout. (Guided solution in Appendix A; the diagram above is the model layout.)

Closing (the author's): stay curious; "A journey of 1,000 miles begins with a single step" (Lao Tzu); every time you refuse a lazy shortcut, document a decision, and defend a boundary you take that step. Sign-off: "Code Hard. Lift Heavy. Sleep More."

Recap: standard blueprints beat whiteboard amnesia; abstractions target audiences; RFCs vs ADRs; escalate with disagree-and-commit; spikes and MVAs destroy unknowns; AI maps options but architects stay accountable; diagrams have made invisible logic visible since 1947.
