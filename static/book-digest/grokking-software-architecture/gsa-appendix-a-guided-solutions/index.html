Grokking Software Architecture: Appendix A, Guided Solutions

Source: Matt Erman, Grokking Software Architecture (Manning, MEAP V07), Appendix A. Previous: Grokking Software Architecture 15: Communicating and Planning Architecture.

[!abstract] Takeaways Model answers to each chapter's "In Action" mission. Use them to check your own reasoning (the numbers matter less than the reasoning).

  • Ch. 1-2: decision "receipts" and a full ADR for a cache TTL.
  • Ch. 3-5: refactor a God class, design four layers, plug ports and adapters.
  • Ch. 6-8: resource-oriented REST, async toxicity filter, polyglot persistence.
  • Ch. 9-11: cloud blueprint, resilience parameters, security ADR.
  • Ch. 12-15: modular-monolith ADR, CI/CD with expand/contract, telemetry and C4.

Ch. 1: a mini defensible decision

Order-processing logic:

  • Option A: one main file. Pro: fastest to ship. Con: low maintainability, violates SoC.
  • Option B: three files (dataReader, taxCalculator, receiptPrinter). Pro: tax maths isolated. Con: small setup overhead passing data.
  • Decision: B, because upcoming discount features can't break receipt printing.
  • Lessons: Separation of Concerns; a small up-front cost is a deliberate trade for fewer regressions.

Ch. 2: ADR-002, default cache TTL for user profiles

Slow profile queries on every page load. The 5-step process:

  1. Spark: the profile page runs slow database queries per load.
  2. Inquiry: prioritise Performance and Scalability, sacrifice Consistency.
  3. Sketch: Tradeoff Triangle with the decision dot on the Performance/Scalability edge, away from Consistency.
  4. Options: A no cache (perfect consistency, heavy DB load); B 5-minute TTL; C 24-hour TTL (too stale).
  5. Decision: B, recorded as ADR-002.

ADR parts:

  • Risk: a user uploads a new picture and sees no change.
  • Mitigation: explicitly clear the cache for their ID on "Save".
  • Review trigger: database load drops significantly, or support receives stale-data complaints.
  • Share: "FYI team, decided on a 5-minute cache TTL for user profiles... Link to ADR-002."

Ch. 3: structural audit of ProcessOrder

Comment each block: (1) validation (empty order or zero total), (2) external payment (_gateway.Authorize), (3) inventory DB (_db.UpdateStock), (4) email (_smtpClient.Send).

Criterion Finding
Cohesion low: four responsibilities in one method
Coupling tight: payment logic directly references DB and SMTP clients
The "and" test fails: validates AND charges AND updates stock AND emails
Refactor OrderValidator, PaymentService, InventoryManager, NotificationService, coordinated by OrderService via constructor DI

Payoff: reduced blast radius (email formatting can't crash payment), testable in isolation.

Ch. 4: four layers

Blog (list posts, submit comment):

  • Presentation: PostController, CommentController, PostViewModel.
  • Application: PostQueryService, CommentSubmissionService (coordinates the use case, transactions, no domain maths).
  • Domain: Post and Comment (rich entities; a post must be Open to receive comments), IPostRepository interface.
  • Infrastructure: SqlPostRepository, MongoPostRepository, AkismetSpamClient (a tool; deciding what to do when it flags a comment lives in Application).

Banking transfer (high stakes):

  • Presentation: AccountController, TransferRequest, AccountStatementViewModel.
  • Application: FundTransferService, StatementGenerationService.
  • Domain: Account (owns Debit()/Credit(), enforces overdraft limits), Money (value object, can't add Yen to Dollars), IAccountRepository.
  • Infrastructure: SqlAccountRepository, SwiftPaymentGateway.
  • Cross-cutting: AuditLogger, SecurityContext via abstractions.
  • Tip: "how to talk to a tool (SQL, API, SMTP)" = Infrastructure; "why the business allows an action (rules, limits, maths)" = Domain.

Ch. 5: hexagonal crypto tracker

  • Port (in Core):

    interface IPriceProviderPort
{
    Task<decimal> GetBitcoinPrice();
}

  • Core: PortfolioManager(IPriceProviderPort); CalculateTotalValue(btcAmount) is btcAmount * await _priceProvider.GetBitcoinPrice(): pure maths, no JSON.

  • Fake adapter: FakePriceAdapter returns 50_000m; test: 2 BTC gives 100_000m.

  • Production wiring: new PortfolioManager(new CoinGeckoAdapter()); in ASP.NET Core use builder.Services.AddScoped<IPriceProviderPort, CoinGeckoAdapter>().

  • Gains: domain ownership of the contract; offline deterministic tests; vendor independence (a Binance or CoinMarketCap adapter changes nothing in the core).

Ch. 6: REST contract refactor

Step Anti-pattern Refactor
Resource /api/changeUserAddress, /api/data/user_info /api/users/{id} (or /api/me)
Verbs POST for everything GET /api/users/{id}; PATCH (partial) or PUT (full) to update
Payload raw string "123 Main St, New York, NY" extensible object 
GET /api/users/123 -> { "id": 123, "fullName": "Archie Gumdrop",
  "address": { "street": "123 Main St", "city": "New York", "state": "NY", "zip": "10001" } }
PATCH /api/users/123 {"address": {...}} -> 200 OK { ..., "updatedAt": "2026-09-28T14:30:00Z" }
  • Never return raw primitives: objects can gain fields (e.g. "Last Login") without breaking old clients.
  • Parallel development: once the JSON contract exists the frontend can mock it while you design the database.

Ch. 7: toxicity filter (event-driven)

  • Event: record CommentPosted(Guid CorrelationId, string Text, DateTime OccurredOn).
  • Producer: creates a correlationId, writes to a Channel, immediately logs "HTTP 200 OK returned" at T+00s.
  • Consumer: await foreach (var @event in _channel.Reader.ReadAllAsync()), Task.Delay(3000) to simulate the LLM, logs "TOXICITY DETECTED" with the same ID at T+03s.
  • Comparison: sync blocks the client 3+ seconds and an AI outage crashes the API; async gives temporal decoupling and one correlation ID across the boundary.

Ch. 8: polyglot persistence for Shop-Zilla

Subsystem Type Choice Constraint Trade-off accepted
Shopping cart key-value Redis sub-millisecond writes for sessions strict structure and absolute durability
General ledger and billing relational PostgreSQL strict ACID horizontal write scalability
Similar products vector Pinecone / pgvector distance over embeddings exact keywords for semantic similarity
Product catalogue document MongoDB variable schema per category cross-document transactions

Three stress tests: the "Bobby Tables" test (any string concatenation in queries means parameterise); the N+1 check (eager load); the "Amnesia" test (don't use BASE for an ACID requirement).

  • Defence script: "We use SQL for the money (we don't want to go to jail), Redis for speed, vectors for the AI features. Ledger in Mongo might double-charge customers."
  • Polyglot tax: multiple connection strings, migration pipelines and backups; default to PostgreSQL and add stores only when limits are hit.

Ch. 9: Recommendation Engine on the cloud

  1. Compute: PaaS / managed containers (raw IaaS rejected as wasted engineering time). Trade-off: you surrender kernel/OS control for velocity.
  2. Terraform (three resource blocks): aws_fargate_service (compute), aws_elasticache_redis (session cache), aws_s3_bucket (compiled ML model/CSV storage).
  3. Immutable mindset (refusing the CTO's live patch): update the Terraform base image → spin up a patched Green beside Blue → shift traffic → destroy the old instance ("cattle"). Result: no drift, zero downtime, peer-reviewed in Git.

Ch. 10: resilience parameters (FlakyPayments)

Guardrail Value Why Trade-off
Timeout 2.0 s (monitoring shows healthy requests finish under 2 s; 8 s is far too long) free threads fast live checkout drops, site stays responsive
Retries and backoff max 3; backoff 1 s, 2 s, 4 s blips self-heal, no self-DDoS abandon after ~7 s total
Circuit breaker open on 5 consecutive failures or 50% errors in a 10 s window; 30 s cooldown stop wasting threads live payments blocked while open
Fallback asynchronous queue PENDING_PAYMENT: save the cart and encrypted payment token, show a confirmation page no lost Black Friday sales moves to async processing

Implementation: declarative policies at the infrastructure boundary (not hand-rolled while/sleep), domain vocabulary (OrderStatus) separate from PaymentService.

Ch. 11: ADR 005, hardening ingress and least privilege

Context: after the Ch. 3 split, there are no operational boundaries; public routes hit the orchestrator; a root database account (postgres/admin); API keys in raw config.

Step Risk Action Benefit
1 exposed entry points consolidate behind an API gateway with RS256 JWT validation (JWKS, exp, pinned algorithm) no direct internet exposure
2 God account restricted user: CREATE USER order_processor ...; GRANT SELECT, INSERT, UPDATE ON orders TO order_processor; (no DELETE/DROP) RCE can't wipe tables
3 hardcoded secrets remove from source; local .env (git-ignored, python-dotenv) or cloud Secrets Manager; os.getenv(...) no Git-history leaks; ready for rotation
4 developer laptops/CI mandatory MFA stops lateral pivoting
  • Positive: reduced blast radius, no Git leaks, defence in depth.
  • Negative: .env onboarding overhead; migrations (ALTER TABLE, CREATE INDEX) now need a separate pipeline runner under a distinct migration role.

Ch. 12: ADR 001, Stream-Flix MVP

  • Context:
    • four-month MVP for VC funding
    • one team of 10
    • Day-1 microservices would burn three months on Kubernetes, network latency, distributed consistency and CI/CD, and mismatches Conway's Law.
  • Options:
    • (1) 20 microservices (slow to market; severe Conway mismatch; Sagas/Outboxes)
    • (2) modular monolith (fast; one team, one codebase; simple local transactions; extraction path via Strangler Fig).
  • Decision: modular monolith with bounded contexts (User Management, Billing, Video Transcoding, Content Delivery) communicating only through interfaces, never through each other's tables.
  • Consequences: all components scale together; a Billing bug could crash everything.
  • Escape hatch triggers:
    • organisational (growth beyond 40 to 50 developers with merge conflicts and deployment jams) and technical (Video Transcoding consistently above 80% of CPU/memory)
    • Extract only the bottlenecked module (e.g. transcoding onto GPU instances).

Ch. 13: Shop-Zilla delivery blueprint

  1. Gated verification (CI): syntax and unit tests (G1) → architectural fitness functions (G2, a zoning officer rejecting circular dependencies) → bake the immutable container image (G3).
  2. Promotion runway: Local workspace → ephemeral PR sandbox (temporary production replica, destroyed on merge) → the same immutable container to the production cluster; no permanent staging.
  3. Zero-downtime release (rename billing_address to address_invoice):
Node Schema App behaviour Flag X1 Guarantee
D1 Expand add nullable address_invoice beside billing_address reads and writes legacy only off purely additive; no locks
D2 Migrate both columns active dual-writes both; X1 flips the read path to the new column on turning X1 off instantly falls back
D3 Contract backfill nulls, drop billing_address new column only; flag pruned retired rename done with zero downtime or divergence

Ch. 14: telemetry for the high-volume tenant

Task Layer Mechanism Tells us
1 Metrics application and database planes Four Golden Signals at gateway and DB pools p99 spikes and pool saturation
2 Traces network and service boundaries correlation_id in HTTP headers at the edge end-to-end journey
2 Logs application threads structured JSON via OpenTelemetry-compliant sinks indexable context, not prose
3 MDC thread-local storage keys tenant_id, correlation_id, cart_size, execution_phase who and where, without polluting signatures

Task 4 remedies: rejected vertical scaling (a band-aid); rejected indexing (doesn't fix 10,000 sequential N+1 round trips); accepted: bulk WHERE id IN (...) queries in InventoryRepository plus a hybrid L1 (in-memory) / L2 (Redis) cache isolating the mega-tenant.
