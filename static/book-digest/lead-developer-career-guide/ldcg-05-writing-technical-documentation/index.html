Lead Developer Career Guide 5: Writing technical documentation

Source: Shelley Benhoff, Lead Developer Career Guide (Manning), ch. 5. Previous: Lead Developer Career Guide 4: Learning any developer skill. Next: Lead Developer Career Guide 6: Optimizing the development process.

Takeaways
  • Documentation gives one central reference, survives turnover, eases onboarding, and keeps technical debt down.
  • Document everything about process: coding standards, development workflow, deployment, and the why behind decisions.
  • Structure with chunking, visuals, an intro and a summary; outline first; numbered, specific steps; get to the point; follow a style guide (Google or Microsoft).
  • Maintain it: test it, ask for feedback, schedule maintenance windows, track changes in a changelog; delegate to the team.

5.1 Setting the team up for success

With proper documentation Without it
Developers understand how the code works and is used They figure things out alone: confusion and mistakes
Information is easy to find Time lost searching and experimenting
Bugs and changes are found and fixed quickly Harder to identify and fix
Easy collaboration Team not on the same page
Easy onboarding Newcomers lack what they need

Without it, decisions are lost over time, raising technical debt and maintenance costs.

Documenting everything

Tools: Confluence, Microsoft Word, Google Docs, GitHub Wiki.

  • Coding standards
    • A guide for writing code and a reference for code review; prevents common mistakes.
    • Make them accessible (intranet, shared drive, code review process), keep them current, take team feedback.
    • Some companies set them organisation-wide.
  • Development workflow
    • Gather team input on the current flow, then document it step by step: handling bugs, reviewing and merging code, testing and deploying.
    • Example flow: planning → development → code review → testing → deployment (to staging first) → maintenance.
    • Gitflow:
      • main holds production-ready code
      • development is where features are built. Document branch naming for features and hotfixes, pushing to QA, merging to main, merge errors, cherry-picking, deployment.
  • Deployment process
    • Gather the existing steps, tools and best practices; document step by step with problem handling; use diagrams or flowcharts.
    • Example chart (figure 5.1): developer opens a pull request → merge code → build and run unit tests (fail: fix errors) → deploy to staging → test → deploy to production → user acceptance testing → release approved.
  • It also serves experienced developers who must troubleshoot, and reduces errors.

Managing technical debt

  • Technical debt
    • is the cost of maintaining and updating code written in a hurry or without attention to quality
    • It isn't always bad: it lets you hit deadlines, like a mortgage or credit card, but you pay interest (complexity, maintenance cost, longer cycles).
  • Developers waste 33% of their time on technical debt on average (the book gives no source in this chapter).
  • Documentation reduces time spent on "unknowns", rework that misses standards, and new errors.
  • Keep a historical record of decisions:
    • why a pattern or technology was chosen and the trade-offs. This lets newcomers reuse the reasoning
    • knowledge transfer before departures doesn't always happen.

Onboarding new developers

Onboarding documentation should include:

  • Code of conduct (behaviour, communication, conflict resolution)
  • Coding standards (naming, formatting, commenting)
  • Development workflow and deployment process
  • Tools and technologies (required software, libraries)
  • Communication channels
  • Resources and documentation (wikis, tutorials)
  • Onboarding checklist (training, code reviews)
  • Technical debt management
  • Mentorship program

Case from the author: with no docs, she spent two weeks reverse engineering a development environment after all previous developers had left, writing every step and error down; new hires then took one day. Have new developers edit the docs as they onboard; maintenance is a team effort.

5.2 Structuring documentation

Unstructured docs are hard to navigate, especially on large projects.

Chunking

Break content into small pieces for busy developers:

  • Headings and subheadings for scanning
  • Bullets and numbered lists
  • Images and diagrams
  • Examples and case studies
  • Simple language without jargon

Visual aids

Aid Purpose
Flowcharts flow of control, user paths, logic of a function or module
Diagrams architecture, component relationships, data or control flow
Screenshots UI, program output, test results (use callout boxes and highlights; they go stale as tools change)
Code snippets how to use a function or class

The author relies heavily on screenshots and code snippets for setup walkthroughs.

Introduction and summary

  • Introduction: purpose, background, assumptions and prerequisites (e.g. "this guide assumes basic computer systems knowledge and covers Windows").
  • Summary after it: high-level contents so the reader can judge relevance (e.g. environment setup: prerequisites, compilers, editors, package managers, environment variables and paths, troubleshooting).
  • Conclusion with key takeaways and further reading.
    • For a how-to (deep technical): list the steps again (install web server Apache or Nginx; database MySQL or PostgreSQL; runtime PHP or Python; Git; clone repo; virtual host; environment variables; setup scripts and migrations; test) plus related documents (contact list, stakeholders, API docs).
    • For reference (e.g. API docs with endpoints, parameters, responses): a paragraph, not bullets (support contact, check for updates).

5.3 Creating the content

Delegate content creation; documentation frees your time later.

Start with an outline

  • Know the audience, goal, and needed information; break into sections, then subheadings; use lists; review and ask other developers.
  • User manual sections: Introduction, Getting started (installing, creating an account, navigating the UI), Using the application, Troubleshooting, References.
  • Developer guide outline: Introduction (description, audience and purpose) → Summary → Getting started (environment, clone, dependencies) → Application architecture (overview, each component) → Building and deploying (environments, options, best practices) → Troubleshooting and maintenance (common problems, upgrading, maintenance tasks) → Conclusion → Appendices (references, glossary).

Writing specific instructions

  • Active voice, numbered steps in logical order, specific ("configure the settings in the config.txt file", not "configure the settings"), screenshots or diagrams.
  • Example, pull a Docker image:
    1. Open a CLI.
    2. Check Docker with docker --version.
    3. Search: docker search <image_name>.
    4. Pull: docker pull <image_name>.
    5. Verify: docker images.
  • Put code in a different font so it can be copied and pasted (fewer typos); write full sentences; add tips, best practices, examples.
  • Test the instructions with developers unfamiliar with the content before publishing.

Get to the point

Most developers skim for the key steps.

Overly wordy Concise
a paragraph on installing the necessary components, configuring external dependencies, and running tests "Install the programming language, libraries, and frameworks. Then, connect to the remote database. Finally, run tests to ensure everything is working properly."

Style guide

  • A set of rules for grammar, punctuation, word usage, structure and layout.
  • Google developer documentation style guide (https://developers.google.com/style): clarity and concision.
  • Microsoft Writing Style Guide (https://learn.microsoft.com/en-us/style-guide/welcome): professionalism, accessibility and inclusivity.
  • Choose: Microsoft guide for Microsoft technologies (.NET); otherwise Google.

5.4 Documentation maintenance cycle

Docs are not a one-time task; outdated docs cause confusion, errors, delays. The review process: test, solicit feedback, publish regular updates.

Testing

  • Test in the environment where it will be used; fix problems before publishing.
  • Have testers list environmental errors (instructions correct but environment differs) and put them in Known Issues / FAQs
    • Example: contractors have different hardware than full-time staff, so have at least one contractor test.
  • Automation: Doxygen checks syntax and broken links; Grammarly for spelling and grammar. Avoid contractions; have non-native English speakers test it.

Feedback

  • Ask prompting questions ("Is this clear?", "Did you find everything?") via Confluence, Word, Google Docs or GitHub comments.
  • Ask different stakeholders (developers, QA, project managers, end users). Even inapplicable feedback helps UX: a user asking for a missing feature may mean the code lacks it too.

Maintenance window

  • A dedicated recurring time to fix typos, update code samples, verify accuracy. Weekly or monthly depending on size
    • the author updated at least quarterly or after big updates
    • calendar reminders.
  • Assign tasks (one person on code samples, another on user docs); delegating levels up the team.
  • Tools: Docusaurus, Read the Docs, MkDocs; Word and Google Docs collaboration if not.
  • Track progress with a changelog or release notes (can join deployment release notes).

5.5 Case study: Edidiong Asikpo (senior developer advocate, Lagos; 100+ talks; Certified Kubernetes Application Developer)

  • Hashnode (no product docs): users asked on Discord and the small team kept retyping answers. New docs became a one-stop place, removed waiting, and ended confusion inside the team.
  • Interswitch (largest fintech in Africa, 300+ staff):
    • several teams built duplicate APIs
      • She met all engineering managers, compiled and merged similar APIs, made each team own its docs, added short descriptions and snippets in several languages
    • APIs became discoverable and sales increased.
  • Feedback:
    • docs were outdated, so they used Swagger to publish updates automatically from the deployment pipeline
    • docs lacked organisation by API type, so they adopted Readme and made docs open source for external contributions.
  • Starting out, five tips:
    1. Take a course (Google's free technical writing course).
    2. Read more ("Read a thousand books, and your words will flow like a river", Lisa See).
    3. Follow a style guide (sentence vs title case, intros, summaries).
    4. Understand the goal (answer only the question, e.g. how to centre a div: give the code).
    5. Proofread after a break of an hour or so, reading from the reader's mindset.
  • AI tools:
    • Grammarly (grammar, tone, plagiarism check)
    • ChatGPT (shorten, code snippets, topics, explain like I'm five)
    • Inkeep (AI documentation search on their site)
    • WriterAI (a colleague's trial was impressive).

Summary points

Good docs yield understanding, consistency, readability, maintainability, faster problem resolution; absence loses decisions and raises debt; docs help newcomers and experienced developers; structure with headings, intro, summary, visuals, code samples; outline first; test and revise like code.
