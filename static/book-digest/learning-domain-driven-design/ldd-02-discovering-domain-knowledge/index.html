Learning DDD 2: Discovering Domain Knowledge

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 2. Previous: Learning DDD 1: Analyzing Business Domains. Next: Learning DDD 3: Managing Domain Complexity.

Takeaways
  • Software solves business problems; to solve them, engineers must grasp domain knowledge, which belongs to domain experts.
  • Knowledge normally passes through translations (analysis model, design model, code), like the game Telephone, so it is distorted.
  • DDD's answer is a ubiquitous language: one shared business language used by every stakeholder, with one meaning per term and no synonyms.
  • The language is a model of the business domain: a purposeful simplification that captures domain experts' mental models.
  • It is a continuous effort, supported by wiki glossaries and Gherkin tests, but usage matters more than tools.
Epigraph

"It's developers' (mis)understanding, not domain experts' knowledge, that gets released in production." Alberto Brandolini.

Business problems

  • This chapter goes deeper into a subdomain: its business function and logic. The tool is the ubiquitous language, used to learn the domain now and model it in software later.
  • A business problem is not a puzzle to solve and finish
    • It can be optimising workflows and processes, minimising manual labour, managing resources, supporting decisions, managing data and so on.
  • Problems exist at domain and subdomain level. A company solves its customers' problems (FedEx customers need packages shipped in limited time, so it optimises shipping).
  • Subdomains are finer-grained problem domains solving specific business capabilities: knowledge management (store and retrieve information), clearing (execute financial transactions), accounting (track funds).

Knowledge discovery

  • Designing effectively needs at least basic knowledge of the business domain, which belongs to domain experts
    • We cannot and should not become experts, but we must understand them and use their terminology.
  • Software must mimic the experts' mental models
    • Without understanding the reasoning behind requirements we only "translate" requirements into code, and may miss a crucial edge case or fail to describe a concept needed for future requirements.
  • Brandolini: software development is a learning process; working code is a side effect. Success depends on knowledge sharing between domain experts and engineers.

Communication

  • Most projects need many roles:
    • domain experts, product owners, engineers, UI/UX designers, project managers, testers, analysts
    • Do they agree on the problem, the solution, and the functional and non-functional requirements?
  • Research on why projects fail (Sudhakar, 2012, "A Model of Critical Success Factors for Software Projects") shows effective communication is essential, yet rarely seen.
  • Often businesspeople and engineers do not interact directly: knowledge is pushed down through "translators" (systems/business analysts, product owners, project managers).
  • Each hand-off is a translation and information is lost:
    • domain knowledge becomes an analysis model (a description of requirements, not of the business domain);
    • the analysis model becomes a software design model (a design document);
    • that becomes an implementation model (source code).
  • Documents go stale, so source code ends up communicating domain knowledge to later maintainers.
  • The result resembles the children's game Telephone (players whisper a message down a line, last player says what they heard): the message is garbled
    • Engineers build the wrong solution, or the right solution for the wrong problems, and the project fails.

What is a ubiquitous language?

  • The cornerstone practice of DDD: instead of translations, parties speak the same language. "Common sense is not so common" (Voltaire).
  • It replaces four translations: domain knowledge to analysis model, to requirements, to system design, to source code.
  • All stakeholders
    • (engineers, product owners, domain experts, UI/UX designers) use it to describe the business domain
    • Domain experts must be comfortable reasoning in it, since it represents the domain and their mental models
    • Only continuous use builds shared understanding.

Language of the business

  • It is the language of the business: business terms only, no technical jargon. You are not teaching experts singletons or abstract factories.
Business language (ubiquitous) Technical (not ubiquitous)
An advertising campaign can display different creative materials The advertisement iframe displays an HTML file
A campaign can be published only if at least one of its placements is active A campaign can be published only if it has at least one associated record in the active-placements table
Sales commissions are accounted for after transactions are approved Sales commissions are based on correlated records from the transactions and approved-sales tables
  • Engineers who know only the technical view cannot fully understand the business logic or why it works that way, limiting their ability to model and implement well.

Consistency

  • The language must be precise and consistent: no need for assumptions and the logic is explicit. Each term has one and only one meaning.
  • Ambiguous terms:
    • policy may mean a regulatory rule or an insurance contract
    • People resolve it by context, software cannot
    • Model both explicitly as regulatory rule and insurance contract.
  • Synonymous terms:
    • two terms must not be interchangeable
    • User may be used with visitor, administrator, account and so on, but they usually denote different concepts: unregistered versus registered users have different roles and behaviours (visitor data is used for analysis; accounts actually use the system)
    • Use each term explicitly in its context for simpler, clearer models.

Model of the business domain

What is a model?

  • A model is "a simplified representation of a thing or phenomenon that intentionally emphasises certain aspects while ignoring others
    • Abstraction with a specific use in mind" (Rebecca Wirfs-Brock)
    • It is a human construct, not a copy of the real world.
  • Canonical example: maps (navigation, terrain, world, subway, nautical, aeronautical, time zones). None shows every detail; each has just enough for its purpose.

Effective modelling

  • You will not see subway stops on a world map, and you cannot estimate distances from a subway map. "All models are wrong, but some are useful" (George Box).
  • A model is an abstraction:
    • omit unnecessary details to handle complexity
    • A bad abstraction removes necessary information or leaves noise
    • Dijkstra ("The Humble Programmer"): the purpose of abstracting is not to be vague but to create a new semantic level in which one can be absolutely precise.

Modelling the business domain

  • Cultivating a ubiquitous language builds a model of the business domain capturing the experts' thought processes: entities and behaviour, cause and effect, invariants.
  • It does not cover every detail (that would make everyone an expert), only enough to implement the required system. Later chapters show it driving low-level design.
  • The more complex the domain, the more vital communication:
    • a slight misunderstanding of a complicated domain leads to severe bugs
    • The only reliable check is to converse with domain experts in their language.

Continuous effort

  • Forming the language needs interaction with real domain experts, who alone uncover inaccuracies, wrong assumptions or a flawed understanding.
  • Use it in all project communication: requirements, tests, documentation, source code.
  • It is ongoing: validated and evolved constantly. Everyday use reveals deeper insights, and the language must evolve with new knowledge.

Tools

  • A wiki glossary documents the language and eases onboarding. Make maintenance a shared effort (any member updates it), not centralised on team leaders or architects.
  • Limit:
    • glossaries suit nouns (entities, processes, roles)
    • Behaviour (business logic with rules, assumptions and invariants) is harder, so pair glossaries with use cases or Gherkin tests.
  • Gherkin
    • automated tests capture the language and bridge experts and engineers, since experts can read them to verify expected behaviour (but do not assume experts will write them)
    • Managing a Gherkin suite can be challenging early on, but is worth it for complex domains.

  • Static code analysis tools can check usage of the language's terms, for example NDepend.
  • Tools are secondary to actual use: "Individuals and interactions over processes and tools" (Agile Manifesto).

Challenges

  • The only reliable way to gather knowledge is to converse with experts. The most important knowledge is often tacit: undocumented, in experts' heads, so you must ask.
  • Often you co-create the model with experts
    • Experts may have ambiguities and white spots, such as only "happy path" scenarios and no edge cases, or concepts with no explicit definition
    • Questions expose these, especially in core subdomains, and learning is mutual.
  • Brownfield projects
    • already have a language that is not DDD-driven and may be technical (database table names)
    • Changing it is hard: the tool is patience
    • Make sure the right language is used where it is easy to control: documentation and source code.
  • Non-English-speaking countries: at least use English nouns for domain entities, so code uses the same terminology.

Conclusion

  • Engineers must understand the domain. The ubiquitous language bridges the knowledge gap and is used in conversations, documentation, tests, diagrams and source code.
  • Terms must be consistent: no ambiguous and no synonymous terms. It is a continuous process that reflects new insights.
  • Wiki glossaries and Gherkin tests help, but the prerequisite is consistent usage in all communications.

Exercises

  1. Primary purpose of a ubiquitous language: a programming language for the functionality / a shared language bridging technical and business teams / formal requirements spec / a secret code for developers.
  2. Who contributes to defining it (select all): domain experts, software engineers, end users, all of the project's stakeholders.
  3. Where should it be used (select all): in-person conversations, documentation, code, all of the above.
  4. Which is correct: it should evolve as understanding improves / static once defined / reflects technology design decisions / only the development team uses it.
  5. Reflect on a project: business concepts you could use with experts; inconsistent terms (different meanings, or the same concept with different terms); inefficiencies from poor communication.
  6. Experts from different organisational units use policy for unrelated concepts, so the language fails "one meaning per term". How would you address it? (Answers: appendix B.)
Answers (book appendix B)
  1. B: bridge the gap between stakeholders for a shared understanding.
  2. D: all stakeholders must communicate in it, so all contribute.
  3. D: in all project communication (conversations, documentation, code, tests).
  4. A: it adapts and is refined as understanding deepens.

Summary points

  • Software mirrors experts' mental models, not translated requirements.
  • One ubiquitous language, in business terms, with one meaning per term.
  • A language is a purposeful model, not a copy of reality.
  • It is cultivated continuously, with glossaries and Gherkin as aids.
Terms to carry forward
  • Ubiquitous language: shared language of the business used by all stakeholders and in code.
  • Analysis model / design model / implementation model: successive translations of domain knowledge.
  • Model: purposeful simplification of reality (Wirfs-Brock, Box).
  • Tacit knowledge: undocumented knowledge in experts' minds.
  • Gherkin: given/when/then test language readable by experts.
  • Glossary: wiki of terms, best for nouns.
