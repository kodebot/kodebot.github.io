Learning DDD 5: Implementing Simple Business Logic

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 5. Previous: Learning DDD 4: Integrating Bounded Contexts. Next: Learning DDD 6: Tackling Complex Business Logic.

Takeaways
  • Business logic is the most important part of software; this chapter covers two patterns for simple logic: transaction script and active record.
  • Transaction script: one procedure per public operation, which must be transactional (succeed or fail, never leave invalid state). Deceptively easy to get wrong.
  • Three real corruption cases: no transaction, database plus message bus, implicit distributed transaction (the caller never learns the result and retries).
  • Active record: objects that wrap a table row, own CRUD, hold data structures with public getters and setters, for simple logic over complicated data structures.
  • Both suit supporting subdomains, integration adapters and anticorruption layers; never core subdomains. Be pragmatic: relax consistency where the business can bear it.

Why this matters

  • Business logic is the reason the software exists. A sexy UI and a fast database are an expensive tech demo if the software is not useful to the business.
  • Subdomains differ in strategic importance and complexity (chapter 2), so we start with two patterns for rather simple logic.

Transaction script

"Organizes business logic by procedures where each procedure handles a single request from the presentation." Martin Fowler (Patterns of Enterprise Application Architecture, 2002).

  • A system's public interface is a collection of business transactions that consumers run (Figure 5-1), retrieving information, modifying it, or both
    • The pattern organises logic into procedures, one per public operation: the public operations are the encapsulation boundaries.

Implementation

  • Each procedure is a simple procedural script. It may use a thin abstraction over storage or access databases directly.
  • The one requirement is transactional behaviour:
    • each operation succeeds or fails, never leaving an invalid state
    • Even if it fails at the worst moment the system must stay consistent, by rolling back or by compensating actions
    • This gives the pattern its name.
  • Example: a script that converts batches of JSON files to XML:
// ConvertJob transaction script
DB.StartTransaction();

var job = DB.LoadNextJob();
var json = LoadFile(job.Source);
var xml = ConvertJsonToXml(json);
WriteFile(job.Destination, xml.ToString());
DB.MarkJobAsCompleted(job);

DB.Commit();
Book typos

It's not that easy!

  • Students ask "is it worth our time?" The pattern is the foundation of the advanced patterns, and, despite its simplicity, the easiest to get wrong: many production issues the author has debugged came from misimplemented transactional behaviour.

Lack of transactional behaviour

  • Two updates with no overarching transaction: update Users.last_visit, then insert into VisitsLog.
// LogVisit.cs (no transaction)
public class LogVisit
{
    public void Execute(Guid userId, DateTime visitedOn)
    {
        _db.Execute("UPDATE Users SET last_visit=@p1 WHERE user_id=@p2",
            visitedOn, userId);
        _db.Execute(@"INSERT INTO VisitsLog(user_id, visit_date)
            VALUES(@p1, @p2)", userId, visitedOn);
    }
}
  • A failure between the two statements (network outage, database timeout or deadlock, server crash) leaves Users updated with no VisitsLog row.
  • Fix: a proper transaction wrapping both, with rollback on error. Easy because relational databases support multi-record transactions.
// LogVisit.cs (with a transaction)
public class LogVisit
{
    public void Execute(Guid userId, DateTime visitedOn)
    {
        try
        {
            _db.StartTransaction();

            _db.Execute(@"UPDATE Users SET last_visit=@p1
                WHERE user_id=@p2",
                visitedOn, userId);

            _db.Execute(@"INSERT INTO VisitsLog(user_id, visit_date)
                VALUES(@p1, @p2)",
                userId, visitedOn);

            _db.Commit();
        }
        catch
        {
            _db.Rollback();
            throw;
        }
    }
}
  • It gets harder when the database lacks multi-record transactions, or when several storage mechanisms cannot be united in a distributed transaction.

Distributed transactions

  • Common in distributed systems: change the database, then publish a message to a bus.
// LogVisit.cs (database plus message bus)
public class LogVisit
{
    public void Execute(Guid userId, DateTime visitedOn)
    {
        _db.Execute("UPDATE Users SET last_visit=@p1 WHERE user_id=@p2",
            visitedOn, userId);
        _messageBus.Publish("VISITS_TOPIC",
            new { UserId = userId, VisitDate = visitedOn });
    }
}
  • A failure after the update and before the publish corrupts state: the table changed but others are never notified.
  • No easy fix:
    • distributed transactions across storages are complex, hard to scale, error prone, so usually avoided
    • Later: CQRS (chapter 8) to populate several stores and the outbox pattern (chapter 9) for reliable publishing after committing.

Implicit distributed transactions

  • A deceptively simple method that maintains a visit counter: one value, one table, one database.
// LogVisit.cs (counter)
public class LogVisit
{
    public void Execute(Guid userId)
    {
        _db.Execute("UPDATE Users SET visits=visits+1 WHERE user_id=@p1",
            userId);
    }
}
  • It is still a distributed transaction:
    • it communicates with the database and the external caller (Figure 5-2)
    • A void method still tells the caller success or failure (an exception on failure)
    • If it succeeds but the result is not delivered (REST network outage, or both in one process that fails before the caller records success), the caller assumes failure and retries: the counter goes up by 2 instead of 1.
  • No simple fix; it depends on the business domain. Options:
    • Make the operation idempotent: the caller reads the counter, increments it locally, and passes the new value. Repeating the call changes nothing.
// LogVisit.cs (idempotent)
public class LogVisit
{
    public void Execute(Guid userId, long visits)
    {
        _db.Execute("UPDATE Users SET visits = @p1 WHERE user_id=@p2",
            visits, userId);
    }
}
  • Use optimistic concurrency control: the caller passes the value it read, and the update applies only if the stored value still equals it, so repeats with the same inputs change nothing.
// LogVisit.cs (optimistic concurrency)
public class LogVisit
{
    public void Execute(Guid userId, long expectedVisits)
    {
        _db.Execute(@"UPDATE Users SET visits=visits+1
            WHERE user_id=@p1 and visits = @p2",
            userId, expectedVisits);
    }
}
Book typos

When to use transaction script

  • Suits the simplest domains where logic is simple procedural operations, for example ETL (extract from a source, transform, load into a destination, Figure 5-3).
  • Naturally fits supporting subdomains, and can be an adapter for external systems (generic subdomains) or part of an anticorruption layer (chapter 9).
  • Advantage: simplicity, minimal abstractions and overhead in runtime and in understanding.
  • Disadvantage: the same simplicity. As logic grows, duplication across transactions grows and copies drift out of sync, giving inconsistent behaviour.
  • Never for core subdomains.
    • Complex logic in transaction scripts becomes an unmaintainable big ball of mud, so the pattern even has a dubious reputation (sometimes called an antipattern)
    • Yet it is ubiquitous, and every business-logic pattern in the following chapters builds on it.

Active record

"An object that wraps a row in a database table or view, encapsulates the database access, and adds domain logic on that data." Martin Fowler (PoEAA, 2002).

  • Also for simple business logic, but over more complex data structures: object trees and hierarchies with one-to-many and many-to-many relations (Figure 5-4)
    • A plain transaction script would repeat the mapping to in-memory structures everywhere.

Implementation

  • Dedicated objects, active records, represent complicated structures and also implement CRUD data access
    • They are coupled to an ORM or data access framework
    • "Active" because each structure implements its own data access.
  • The business logic is still a transaction script, but it manipulates active records instead of the database directly, and the operation must still be atomic.
// CreateUser.cs
public class CreateUser
{
    public void Execute(UserDetails userDetails)
    {
        try
        {
            _db.StartTransaction();

            var user = new User();
            user.Name = userDetails.Name;
            user.Email = userDetails.Email;
            user.Save();

            _db.Commit();
        }
        catch
        {
            _db.Rollback();
            throw;
        }
    }
}
  • The goal is to encapsulate the complexity of mapping objects to the schema
    • Active records can hold business logic such as field validation or procedures on their data, but the distinctive feature is the separation of data structure and behaviour: fields usually have public getters and setters so external procedures change state.

When to use active record

  • It is a transaction script that optimises database access, so it supports only relatively simple logic (CRUD, at most input validation).
  • Like transaction script it suits supporting subdomains, integrating generic solutions, and model transformation
    • The difference: it handles complicated data structure to schema mapping.
  • It is also known as the anemic domain model antipattern
    • The author avoids the negative connotation: it is a tool, harmful only in the wrong context
    • Using an elaborate pattern for simple logic also harms, by adding accidental complexity
    • The next chapter shows how a domain model differs.
Pattern, not framework

Be pragmatic

  • Data integrity matters, but a pragmatic approach is sometimes better
    • At high scale, consistency guarantees can be relaxed
    • Is corrupting one record in a million a showstopper? For a system ingesting billions of IoT events a day, is it a big deal if 0.001% are duplicated or lost?
  • There are no universal laws; it depends on the domain. It is fine to cut corners if you evaluate the risks and business implications.

Conclusion

Pattern Summary Fit
Transaction script Simple procedural scripts per operation, each transactional (succeeds or fails) Supporting subdomains, ETL-like logic
Active record Data structures that provide simple CRUD access methods, used by a transaction script Simple logic over complicated data structures

Exercises

  1. Which pattern for a core subdomain? Transaction script / active record / neither / both.
  2. Which for a supporting subdomain? Transaction script / active record / neither / both.
  3. Given a CreateTicket method (below) with no high-level transaction, which consistency issues are possible (select all)? The agent's counter increases by more than 1; the counter increases but the agent gets no ticket; an agent gets a ticket but is not notified; all of the above.
  4. Is there at least one more edge case that can corrupt state? No / Yes.
// CreateTicket (exercise)
public void CreateTicket(TicketData data)
{
    var agent = FindLeastBusyAgent();

    agent.ActiveTickets = agent.ActiveTickets + 1;
    agent.Save();

    var ticket = new Ticket();
    ticket.Id = Guid.New();
    ticket.Data = data;
    ticket.AssignedAgent = agent;
    ticket.Save();

    _alerts.Send(agent, "You have a new ticket!");
}
Answers (book appendix B)
  1. C: neither can implement a core subdomain's complexity.
  2. D: both suit supporting subdomains.
  3. D: all issues are possible (retry increments the counter more than once; counter up without a ticket; ticket assigned but no notification).
  4. B: yes, for example a failure after line 12 then a retry persists and assigns the same ticket twice.

Summary points

  • Pick transaction script or active record only for simple logic; both are fine for supporting subdomains, never for core.
  • Always make operations transactional, mind distributed and implicit distributed transactions, use idempotency or optimistic concurrency where needed.
  • Weigh consistency against cost: be pragmatic.
Terms to carry forward
  • Transaction script: procedure per operation, transactional.
  • Active record: object wrapping a row with CRUD, data separate from behaviour.
  • Idempotent operation: repeating gives the same result.
  • Optimistic concurrency control: update only if the value is still the one read.
  • Anemic domain model: the criticism of active record when misapplied.
  • Big ball of mud: unmaintainable result of complex logic in scripts.
