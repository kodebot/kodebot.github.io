Learning DDD 7: Modeling the Dimension of Time

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 7. Previous: Learning DDD 6: Tackling Complex Business Logic. Next: Learning DDD 8: Architectural Patterns.

Takeaways
  • The event-sourced domain model is the domain model (complex logic, core subdomain, value objects, aggregates, events) with a different persistence: domain events are the source of truth, not the state.
  • A state table shows current state but not how it got there; events add the dimension of time.
  • State is projected by applying events in order, so you can time travel and build many projections (state, search, analysis) from the same events.
  • The event store is append-only, supports fetch-by-instance and append with an expected version (optimistic concurrency).
  • Gains: time travel, deep insight, audit log, smarter concurrency. Costs: learning curve, evolving event schemas, architectural complexity.
  • FAQs: performance (snapshots), scale (shard by aggregate ID), deleting data (forgettable payload), and why logs, history tables or triggers are not equivalent.

Premise

  • Same premise as the domain model:
    • complex business logic in a core subdomain, same tactical patterns
    • The difference is how aggregate state is persisted: instead of storing the state, the model generates domain events describing each change and uses them as the source of truth.

Event sourcing

"Show me your flowchart and conceal your tables, and I shall continue to be mystified. Show me your tables, and I won't usually need your flowchart; it'll be obvious." Fred Brooks (The Mythical Man-Month, 1974).

  • State-based model
    • (Table 7-1): a table of telemarketing leads with columns lead-id, first-name, last-name, status, phone-number, followup-on, created-on, updated-on
    • 20 sample rows with statuses NEW_LEAD, CLOSED, FOLLOWUP_SET, PENDING_PAYMENT, PAYMENT_FAILED, CONVERTED.
  • You can infer the ubiquitous language and the processing cycle:
    • The sales flow starts at NEW_LEAD.

    • the story of how each lead reached its state

Projecting state

  • The state is projected by applying a simple transformation sequentially to each event, one Apply overload per event type:
// LeadStateProjection.cs
public class LeadStateProjection
{
    public long LeadId { get; private set; }
    public string FirstName { get; private set; }
    public string LastName { get; private set; }
    public LeadStatus Status { get; private set; }
    public PhoneNumber PhoneNumber { get; private set; }
    public DateTime? FollowupOn { get; private set; }
    public DateTime CreatedOn { get; private set; }
    public DateTime UpdatedOn { get; private set; }
    public int Version { get; private set; }

    public void Apply(LeadInitialized @event)
    {
        LeadId = @event.LeadId;
        Status = LeadStatus.NEW_LEAD;
        FirstName = @event.FirstName;
        LastName = @event.LastName;
        PhoneNumber = @event.PhoneNumber;
        CreatedOn = @event.Timestamp;
        UpdatedOn = @event.Timestamp;
        FollowupOn = null;
        Version = 0;
    }

    public void Apply(Contacted @event)
    {
        UpdatedOn = @event.Timestamp;
        FollowupOn = null;
        Version += 1;
    }

    public void Apply(FollowupSet @event)
    {
        UpdatedOn = @event.Timestamp;
        FollowupOn = @event.FollowupOn;
        Status = LeadStatus.FOLLOWUP_SET;
        Version += 1;
    }

    public void Apply(ContactDetailsChanged @event)
    {
        FirstName = @event.FirstName;
        LastName = @event.LastName;
        PhoneNumber = @event.PhoneNumber;
        UpdatedOn = @event.Timestamp;
        Version += 1;
    }

    public void Apply(OrderSubmitted @event)
    {
        UpdatedOn = @event.Timestamp;
        Status = LeadStatus.PENDING_PAYMENT;
        Version += 1;
    }

    public void Apply(PaymentConfirmed @event)
    {
        UpdatedOn = @event.Timestamp;
        Status = LeadStatus.CONVERTED;
        Version += 1;
    }
}
  • Feeding all events through the right Apply overloads reproduces exactly the table row
    • Version counts the modifications
    • Time travel: apply only a subset (the first five events give the state at version 5).

Search

  • Agents may not know a lead's contact data changed, and want to find leads by historical names and phone numbers. Project sets of every first name, last name and phone number seen:
// LeadSearchModelProjection.cs
public class LeadSearchModelProjection
{
    public long LeadId { get; private set; }
    public HashSet<string> FirstNames { get; private set; }
    public HashSet<string> LastNames { get; private set; }
    public HashSet<PhoneNumber> PhoneNumbers { get; private set; }
    public int Version { get; private set; }

    public void Apply(LeadInitialized @event)
    {
        LeadId = @event.LeadId;
        FirstNames = new HashSet<string>();
        LastNames = new HashSet<string>();
        PhoneNumbers = new HashSet<PhoneNumber>();

        FirstNames.Add(@event.FirstName);
        LastNames.Add(@event.LastName);
        PhoneNumbers.Add(@event.PhoneNumber);

        Version = 0;
    }

    public void Apply(ContactDetailsChanged @event)
    {
        FirstNames.Add(@event.FirstName);
        LastNames.Add(@event.LastName);
        PhoneNumbers.Add(@event.PhoneNumber);

        Version += 1;
    }

    // Contacted, FollowupSet, OrderSubmitted, PaymentConfirmed:
    // each only does Version += 1
}
  • For Casey Davis it yields: LeadId: 12, FirstNames: ['Casey'], LastNames: ['David', 'Davis'], PhoneNumbers: ['555-2951', '555-8101'], Version: 6.

Analysis

  • Business intelligence wants the number of follow-up calls per lead, then filtering converted and closed leads to optimise sales:
// AnalysisModelProjection.cs
public class AnalysisModelProjection
{
    public long LeadId { get; private set; }
    public int Followups { get; private set; }
    public LeadStatus Status { get; private set; }
    public int Version { get; private set; }

    public void Apply(LeadInitialized @event)
    {
        LeadId = @event.LeadId;
        Followups = 0;
        Status = LeadStatus.NEW_LEAD;
        Version = 0;
    }

    public void Apply(FollowupSet @event)
    {
        Status = LeadStatus.FOLLOWUP_SET;
        Followups += 1;
        Version += 1;
    }

    public void Apply(OrderSubmitted @event)
    {
        Status = LeadStatus.PENDING_PAYMENT;
        Version += 1;
    }

    public void Apply(PaymentConfirmed @event)
    {
        Status = LeadStatus.CONVERTED;
        Version += 1;
    }

    // Contacted and ContactDetailsChanged: Version += 1
}
  • For lead 12: LeadId: 12, Followups: 1, Status: Converted, Version: 6.
  • These are in-memory projections; persisting them for real needs CQRS (chapter 8).

Source of truth

  • All state changes are represented and persisted as events:
    • the source of truth (Figure 7-1)
    • The database holding them is the only strongly consistent storage: the event store.

Event store

  • Append-only: no modifying or deleting events (except exceptional cases such as data migration). Minimum functions: fetch all events of an entity and append events.
// IEventStore.cs
interface IEventStore
{
    IEnumerable<Event> Fetch(Guid instanceId);
    void Append(Guid instanceId, Event[] newEvents, int expectedVersion);
}
  • expectedVersion
    • gives optimistic concurrency: if new events were appended after that version, the store raises a concurrency exception
    • CQRS needs extra endpoints (next chapter).
Not new

Event-sourced domain model

  • The plain domain model keeps a state representation and emits selected events
    • The event-sourced model uses events exclusively to model the lifecycle: every state change is a domain event.
  • Each operation follows this script:
    1. Load the aggregate's events.
    2. Reconstitute state by projecting them, to make business decisions.
    3. Execute the command: business logic produces new events.
    4. Commit the new events to the event store.

  • Applied to the Ticket aggregate of chapter 6. The application service loads events, rehydrates, executes, commits with the original version:
// TicketAPI.cs
public class TicketAPI
{
    private ITicketsRepository _ticketsRepository;

    public void RequestEscalation(TicketId id, EscalationReason reason)
    {
        var events = _ticketsRepository.LoadEvents(id);
        var ticket = new Ticket(events);
        var originalVersion = ticket.Version;
        var cmd = new RequestEscalation(reason);
        ticket.Execute(cmd);
        _ticketsRepository.CommitChanges(ticket, originalVersion);
    }
}
  • The aggregate rehydrates in its constructor through a state projector (TicketState) and AppendEvent, which dispatches dynamically to the matching Apply overload:
// Ticket.cs
public class Ticket
{
    private List<DomainEvent> _domainEvents = new List<DomainEvent>();
    private TicketState _state;

    public Ticket(IEnumerable<IDomainEvents> events)
    {
        _state = new TicketState();
        foreach (var e in events)
        {
            AppendEvent(e);
        }
    }

    private void AppendEvent(IDomainEvent @event)
    {
        _domainEvents.Append(@event);
        // Dynamically call the correct overload of the "Apply" method.
        ((dynamic)_state).Apply((dynamic)@event);
    }

    public void Execute(RequestEscalation cmd)
    {
        if (!_state.IsEscalated && _state.RemainingTimePercentage <= 0)
        {
            var escalatedEvent = new TicketEscalated(_id, cmd.Reason);
            AppendEvent(escalatedEvent);
        }
    }
}
  • Unlike chapter 6, RequestEscalation does not set IsEscalated: it creates the event and passes it to AppendEvent. The projection mutates the state:
// TicketState.cs
public class TicketState
{
    public TicketId Id { get; private set; }
    public int Version { get; private set; }
    public bool IsEscalated { get; private set; }

    public void Apply(TicketInitialized @event)
    {
        Id = @event.Id;
        Version = 0;
        IsEscalated = false;
    }

    public void Apply(TicketEscalated @event)
    {
        IsEscalated = true;
        Version += 1;
    }
}

Why "event-sourced domain model"?

Advantages

  • More modelling effort than persisting state, but significant gains:
    • Time travelling: restore all past states to analyse behaviour, inspect decisions, optimise logic, and debug retroactively (revert the aggregate to the state when a bug was seen).
    • Deep insight: core subdomain optimisation matters; you can always add new projections from existing events.
    • Audit log: a strongly consistent log of everything that happened; some domains require it by law. Ideal for money (trace decisions and flows between accounts).
    • Advanced optimistic concurrency:
      • classic OCC just raises an exception on stale data
      • With events you can query exactly which events were appended meanwhile and make a domain-driven decision about whether they collide with the attempted operation or are irrelevant so it is safe to proceed.

Disadvantages

  • Not the ultimate pattern: design must follow the domain's needs.
    • Learning curve: a sharp break from traditional data management; training and a new way of thinking.
    • Evolving the model: events are immutable, so changing an event's schema is not like altering a table (a whole book covers it: Versioning in an Event Sourced System, Greg Young).
    • Architectural complexity: many moving parts (next chapter on CQRS).
  • Worse if the task does not justify the pattern. Chapter 10 gives rules of thumb.

Frequently asked questions

Question Answer
Performance: rebuilding from events slows as they grow? Benchmark with hundreds or thousands of events against the aggregate's expected lifespan. In most systems the hit shows only beyond 10,000+ events per aggregate; in the vast majority a lifespan is under 100 events. If it does matter, use snapshots. Before that, re-check the aggregate's boundaries.
Scale: enormous data? Easy: operations touch a single aggregate, so shard the event store by aggregate ID; all events of one aggregate live in one shard (Figure 7-3).
Deleting data (for example GDPR)? Forgettable payload pattern: put sensitive data in events encrypted; keep the key in an external key-value store (key = aggregate ID, value = encryption key). To delete, delete the key; the data becomes unreadable.
  • Snapshot pattern (Figure 7-2):
    1. A process continuously iterates new events in the store, generates projections and caches them.
    2. When an action needs an in-memory projection, it fetches the current snapshot from the cache, fetches the events after the snapshot version, and applies them in memory.
    • It is an optimisation that must be justified; under 10,000 events per aggregate it is accidental complexity.

Why can't I just...?

  • ...write logs to a text file as an audit log?
    • Writing to a database and a file is a transaction across two stores
    • if the database fails nobody removes the log lines. Logs are eventually inconsistent.
  • ...keep state and append to a logs table in the same transaction?
    • Consistent, but error prone: a future engineer may forget the log record
    • and the log table's schema degrades into chaos (no enforcement of required, correctly formatted data).
  • ...add a database trigger that copies the record into a history table?
    • No manual calls, but the history has only dry facts (which fields changed) and misses the business context: why
    • Without the why you cannot project additional models.

Conclusion

  • All changes to an aggregate's state are a series of domain events, unlike updating a record
    • Events project the current state and many representation models, each optimised for a task.
  • It fits cases needing deep insight (analysis, optimisation) or a legally required audit log.
  • This chapter completes the business logic implementation patterns; next, architectural patterns.
Pattern Business logic State persisted as
Transaction script Simple procedures Records, via direct DB access
Active record Simple, complex data structures Records, via CRUD objects
Domain model Complex Current state of aggregates
Event-sourced domain model Complex, needing time and insight Domain events (source of truth)

Exercises

  1. Domain events and value objects: events use value objects to describe what happened / value objects must become event-sourced aggregates / value objects are replaced by events in the event-sourced model.
  2. Projecting state from events: a single representation / multiple, but events must be modelled for multiple projections / multiple, and you can always add more later.
  3. State-based versus event-sourced aggregates (select all): only event-sourced produce events / both produce events, but only event-sourced use them as the source of truth / event-sourced aggregates ensure events for every state transition.
  4. In the WolfDesk company (book's Preface), which functionality suits an event-sourced domain model? The ticket lifecycle algorithm / administration interface / management of agents' schedules.
Answers (book appendix B)
  1. A: events use value objects to describe what happened.
  2. C: multiple projections, and you can add more later.
  3. B and C: both aggregates emit events, only event-sourced ones emit an event for every state transition.
  4. A: the ticket lifecycle algorithm (more convenient to project extra representations for fraud detection and support autopilot).

Summary points

  • Persist events, derive state; keep the event store append-only with expected version.
  • Many projections from one stream; time travel; audit log for free.
  • Pay with learning curve, schema evolution and architectural complexity; use snapshots, sharding and forgettable payload when needed.
Terms to carry forward
  • Event sourcing / event store: persist all changes as events in an append-only store.
  • Projection: state derived by applying events in order.
  • Rehydration: rebuilding an aggregate from its events.
  • Snapshot: cached projection plus newer events.
  • Forgettable payload: encrypted sensitive data whose key is deleted to forget.
  • Ledger: financial append-only log; balance is a projection.
