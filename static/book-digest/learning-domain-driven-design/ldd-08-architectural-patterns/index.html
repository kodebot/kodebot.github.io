Learning DDD 8: Architectural Patterns

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 8. Previous: Learning DDD 7: Modeling the Dimension of Time. Next: Learning DDD 9: Communication Patterns.

Takeaways
  • Without organisation, business logic diffuses into the UI, database and duplicates, making change costly. Architectural patterns set boundaries and dependencies.
  • Layered architecture (presentation, business logic, data access, optionally a service layer) suits transaction script and active record.
  • Ports and adapters inverts the dependency (the business logic depends on nothing, the infrastructure implements its ports with adapters) and suits the domain model.
  • CQRS keeps one strongly consistent command model and many read models (projections); prefer synchronous projection via a checkpoint, optionally plus asynchronous.
  • Apply patterns per subdomain (vertical slices), not one pattern for the whole bounded context.

Business logic versus architecture

  • Tactical patterns so far model business logic
    • Software also has to interact with users, persist state, integrate with external systems
    • With many concerns the logic can diffuse (some in the UI or database, or duplicated), so a change may hit unexpected parts, or miss code that must change: maintenance cost rises dramatically.
  • Architectural patterns organise concerns and set clear boundaries: how the logic is wired to input, output and infrastructure, what knowledge they share and how they reference each other
    • Three predominant patterns: layered architecture, ports and adapters, CQRS.

Layered architecture

  • Horizontal layers, each with one technical concern (Figure 8-1). Classic form: presentation layer (PL), business logic layer (BLL), data access layer (DAL).

Presentation layer

  • The UI for consumers. Originally a graphical interface; in modern systems it covers all means of triggering behaviour, synchronous and asynchronous:
    • GUI, CLI, API for programmatic integration;
    • subscription to message-broker events;
    • message topics for publishing outgoing events.
  • Strictly, it is the program's public interface.

Business logic layer

  • Implements and encapsulates the business logic: where decisions are made, "the heart of software" (Evans). The patterns of chapters 5 to 7 live here (active records, domain model).

Data access layer

  • Access to persistence mechanisms. Broader than "the database":
    • multiple databases (document store as operational DB, search index, in-memory DB);
    • other media: cloud object storage (AWS S3, Google Cloud Storage) for files, or an internal message bus (if exposed publicly it belongs to the presentation layer);
    • external information providers: external APIs, cloud managed services (translation, stock market data, audio transcription).

Communication between layers

  • Top-down:
    • each layer depends only on the layer directly beneath it (Figure 8-5)
    • The presentation layer references only the business logic layer and knows nothing of data access decisions.

Variation: service layer

"Defines an application's boundary with a layer of services that establishes a set of available operations and coordinates the application's response in each operation." Fowler (PoEAA).

  • An intermediary between presentation and business logic. Starting point: an MVC controller doing orchestration itself (creating a User active record, saving it, managing a transaction):
// UserController.cs (orchestration in the presentation layer)
namespace MvcApplication.Controllers
{
    public class UserController : Controller
    {
        [AcceptVerbs(HttpVerbs.Post)]
        public ActionResult Create(ContactDetails contactDetails)
        {
            OperationResult result = null;

            try
            {
                _db.StartTransaction();

                var user = new User();
                user.SetContactDetails(contactDetails);
                user.Save();

                _db.Commit();
                result = OperationResult.Success;
            }
            catch (Exception ex)
            {
                _db.Rollback();
                result = OperationResult.Exception(ex);
            }

            return View(result);
        }
    }
}
  • To decouple, move orchestration to a service layer (a logical boundary, not a physical service)
    • It acts as a facade for the business logic layer, exposing operations that match the public interface without presentation details:
// CampaignManagementService.cs
interface CampaignManagementService
{
    OperationResult CreateCampaign(CampaignDetails details);
    OperationResult Publish(CampaignId id, PublishingSchedule schedule);
    OperationResult Deactivate(CampaignId id);
    OperationResult AddDisplayLocation(CampaignId id, DisplayLocation newLocation);
}

// UserService.cs
namespace ServiceLayer
{
    public class UserService
    {
        public OperationResult Create(ContactDetails contactDetails)
        {
            OperationResult result = null;

            try
            {
                _db.StartTransaction();

                var user = new User();
                user.SetContactDetails(contactDetails);
                user.Save();

                _db.Commit();
                result = OperationResult.Success;
            }
            catch (Exception ex)
            {
                _db.Rollback();
                result = OperationResult.Exception(ex);
            }

            return result;
        }
    }
}

// UserController.cs (after extraction)
namespace MvcApplication.Controllers
{
    public class UserController : Controller
    {
        [AcceptVerbs(HttpVerbs.Post)]
        public ActionResult Create(ContactDetails contactDetails)
        {
            var result = _userService.Create(contactDetails);
            return View(result);
        }
    }
}
  • Advantages:
    • reuse one service layer for several public interfaces (GUI, API) without duplicating orchestration
    • modularity
    • further decoupling
    • easier testing of business functionality.
  • Not always needed:
    • with a transaction script the logic already is a service layer, so one of them suffices
    • Required when the pattern needs external orchestration, as with active record: the service layer is the transaction script, the active records live in the business logic layer.

  • The author prefers "user interface layer", "infrastructure layer" and "application layer" (to avoid confusion with physical services) but uses the original terms here.

When to use layered architecture

  • The business-logic-to-data-access dependency suits transaction script and active record.
  • It makes a domain model hard:
    • aggregates and value objects should have no dependency or knowledge of infrastructure
    • top-down dependency requires "hoops". Possible, but the next pattern fits much better.
Optional: layers versus tiers

A layer is a logical boundary: all layers are implemented, evolved and deployed as one unit. A tier is a physical boundary: an independently deployable service, server or system. Example N-Tier (Figure 8-7): browser, reverse proxy, web application on a web server, database server. They may run on one machine (containers) or be spread out, but each is deployed and managed independently, so they are tiers. Layers are logical boundaries inside the web application.

Ports and adapters

  • Addresses the layered architecture's shortcomings, a better fit for complex logic. "Refactor" the layered architecture:

Terminology and dependency inversion

  1. Presentation and data access layers both represent integration with external components (databases, external services, UI frameworks): merge them into a single infrastructure layer (Figure 8-8).
  2. The dependency inversion principle (DIP): high-level modules (business logic) must not depend on low-level modules. In the traditional layering the BLL depends on the infrastructure. Reverse it (Figure 8-9): the business logic layer becomes central and depends on no infrastructure.
  3. Add an application layer as a facade for the public interface (like the service layer): it describes operations and orchestrates the logic (Figure 8-10).
  • Result: ports and adapters. The business logic depends on nothing below, as the domain model and event-sourced domain model require.

Integration of infrastructural components

  • Goal:
    • decouple the logic from infrastructure
    • Instead of calling components directly, the business logic layer defines ports (interfaces)
      • the infrastructure layer implements adapters, concrete implementations per technology (Figure 8-11)
    • Ports resolve to adapters through dependency injection or bootstrapping.
// IMessaging.cs (a port, in the business logic layer)
namespace App.BusinessLogicLayer
{
    public interface IMessaging
    {
        void Publish(Message payload);
        void Subscribe(Message type, Action callback);
    }
}

// SQSBus.cs (an adapter, in the infrastructure layer)
namespace App.Infrastructure.Adapters
{
    public class SQSBus : IMessaging
    {
        // ...
    }
}

Variants

  • Also known as hexagonal, onion and clean architecture: same principles, components and relationships, different terminology (application = service = use case layer; business logic = domain = core layer)
    • Mistaking them for different patterns shows why a ubiquitous language matters.

When to use

  • A perfect fit for domain model business logic (decoupled from all technology concerns).

Command-query responsibility segregation (CQRS)

  • Same organisational principles as ports and adapters, but data is represented in multiple persistent models.

Polyglot modelling

  • One model may not serve all needs: OLTP and OLAP need different representations (chapter 7).
  • Polyglot persistence:
    • "there is no perfect database" (Greg Young): trade-offs of scale, consistency and querying
    • Use several: for example a document store as the operational database, a column store for analytics and a search engine for search.
  • CQRS began as a fix for the limited querying of event sourcing (you can query only one aggregate's events at a time): materialise projections into databases for flexible queries
    • The chapter decouples CQRS from event sourcing: it helps with any business logic pattern.

Implementation

  • Command execution model:
    • the single model for operations that change state: implements business logic, validates rules, enforces invariants
    • It is the only strongly consistent model, the source of truth, with optimistic concurrency on update.
  • Read models (projections):
    • as many as needed to show data or feed other systems
    • A read model is a precached projection, in a durable database, flat file or in-memory cache
    • A proper CQRS can wipe a projection and regenerate it from scratch, and add unforeseen projections later
    • Read models are read-only: no operation modifies them directly.

Projecting read models

  • Changes must flow from the command model to every read model (Figure 8-12), like a materialised view in a relational database.

Synchronous projections (catch-up subscription)

  1. The projection engine queries the OLTP database for records added or updated after the last processed checkpoint.
  2. It uses them to regenerate or update the read models.
  3. It stores the checkpoint of the last processed record for the next iteration.
  • The command model must checkpoint every appended or updated record and support querying by checkpoint. Databases may help: SQL Server's rowversion column gives unique incrementing numbers on insert or update (Figure 8-15)
    • otherwise keep a custom running counter on each modified record.
  • The checkpoint query must be consistent: if the last record seen was 10, no later record may get a value below 10, or the engine skips it and the models become inconsistent.
  • Advantage: adding or regenerating projections is trivial: reset the checkpoint to 0 and the engine rebuilds from the ground up.

Asynchronous projections

  • The command model publishes committed changes to a message bus; projection engines subscribe and update their read models (Figure 8-16).
  • Challenges: more prone to distributed-computing problems; out-of-order or duplicated messages project inconsistent data; adding or regenerating projections is harder.
  • Advice: always implement synchronous projection and optionally an asynchronous one on top.

Model segregation

  • A command operates only on the strongly consistent command model. A query cannot modify any persisted state (read models or command model).
  • Misconception: commands must never return data and results must come from read models. Wrong: it creates accidental complexity and bad user experience.
  • A command should tell the caller success or failure and why (validation or technical), so the caller can fix it
    • It can, and often should, return data (for example to update the UI), giving immediate feedback and avoiding round trips.
  • Limitation: returned data must come from the strongly consistent command model, since eventually consistent projections may not be refreshed yet.

When to use CQRS

  • When the same data needs multiple models, possibly in different databases
    • It supports DDD's core value of using the most effective model for the task and continuously improving the domain model.
  • Infrastructure benefit: for example a relational database for the command model, a search index for full text, prerendered flat files for fast retrieval, all reliably synchronised.
  • It suits event-sourced domain models naturally: events cannot be queried by aggregate state, but CQRS projects states into queryable databases.

Scope

  • These patterns are not system-wide principles, and not necessarily for a whole bounded context
    • A context may span several subdomains (core, supporting, generic; even those of the same type may differ, chapter 10), and one contextwide architecture causes accidental complexity (Figure 8-17).
  • Add vertical partitioning to the horizontal layers:
    • modules with logical boundaries per subdomain, each with the appropriate tools (Figure 8-18). This turns a monolithic bounded context into a modular one and avoids a big ball of mud
    • chapter 11 shows such logical boundaries refactored into physical ones (finer bounded contexts).

Exercises

  1. Architectural patterns usable with active record (select all): layered / ports and adapters / CQRS.
  2. Patterns that decouple business logic from infrastructure: layered / ports and adapters / CQRS.
  3. Integrating a cloud provider's managed message bus under ports and adapters: business logic layer / application layer / infrastructure layer.
  4. True about CQRS (select all): asynchronous projections are easier to scale / only one of sync or async can be used / a command cannot return information / a command can return information if it comes from a strongly consistent model.
  5. CQRS lets the same business objects live in multiple persistent models inside one bounded context. Does this contradict a bounded context being a model boundary? Yes / No.
Answers (book appendix B)
  1. A and C: layered supports active record, and CQRS can help too.
  2. B and C: ports and adapters and CQRS both abstract infrastructure from business logic.
  3. C: infrastructure layer.
  4. A and D: asynchronous projections scale more easily; a command can return strongly consistent information.
  5. B (no contradiction): only one of the models is the source of truth used to change aggregates.

Summary points

  • Choose the architecture from the business logic pattern; apply it per subdomain.
  • Layered for scripts and active records; ports and adapters for domain models; CQRS for several models.
  • Prefer synchronous projections, optionally async on top.
Terms to carry forward
  • Layered architecture / service layer: horizontal layers, facade layer for orchestration.
  • Ports and adapters (hexagonal, onion, clean): infrastructure implements the logic's ports.
  • Dependency inversion principle: high-level modules do not depend on low-level ones.
  • Layer versus tier: logical versus physical boundary.
  • CQRS / read model / projection: separate command model and precomputed read models.
  • Catch-up subscription / checkpoint: synchronous projection mechanism.
  • Polyglot persistence: several databases, each for its strengths.
