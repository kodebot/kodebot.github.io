Learning DDD 10: Design Heuristics

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 10. Previous: Learning DDD 9: Communication Patterns. Next: Learning DDD 11: Evolving Design Decisions.

Takeaways
  • "It depends" is correct but impractical; this chapter bridges Parts I and II with heuristics (rules of thumb) that turn subdomain analysis into design decisions.
  • Bounded contexts: size is a function of the model, not a goal; start wide (logical boundaries are cheap to refactor), especially around core subdomains.
  • Business logic pattern: audit log, money or deep analysis gives event-sourced domain model; complex logic gives domain model; complex data gives active record; otherwise transaction script.
  • Architecture follows the logic pattern (event sourcing needs CQRS, domain model needs ports and adapters, and so on), and so does the testing strategy (pyramid, diamond, reversed pyramid).
  • Heuristics are guiding principles, not replacements for critical thinking.

Heuristic

  • "It depends" is the right answer to almost anything in software engineering, but not practical
    • This chapter explores what "it" depends on, bridging Part I (analysis, strategic design) and Part II (tactical patterns): (business) domain-driven (software) design.
  • A heuristic is a rule of thumb, not a hard rule proven correct in 100% of cases: sufficient for immediate goals, ignoring the noise of many cues to focus on the "swamping forces" of the most important ones (Gigerenzer et al., Simple Heuristics That Make Us Smart, 1999).

Bounded contexts

  • Wide or narrow can both be valid (chapter 3)
    • What is the optimal size, given the frequent equation of bounded contexts with microservices (chapter 11 covers the interplay)? Always the smallest?
  • Nick Tune:
    • "There are many useful and revealing heuristics for defining the boundaries of a service
    • Size is one of the least useful." Do the opposite of optimising for small: treat the context's size as a function of the model it encompasses.
  • Changes affecting several contexts are expensive
    • and need coordination, especially across teams (Figure 10-1)
    • They signal ineffective boundaries
    • Refactoring boundaries is costly, so bad ones often stay and accumulate technical debt.
  • Boundaries are invalidated when the domain is not well known or requirements change often: volatility and uncertainty, which are properties of core subdomains, especially early on
    • Use that as the heuristic.
  • Broad boundaries covering several subdomains
    • make it safer to be wrong, because refactoring logical boundaries is much cheaper than physical ones
    • Start wide, and split as you gain knowledge.
  • Mainly for contexts with a core subdomain (generic and supporting are more formalised and less volatile)
    • Protect against unforeseen change by including the subdomains the core interacts with most (other core, supporting or generic) (Figure 10-2).

Business logic implementation patterns

  • Four patterns (chapters 5 to 7): transaction script, active record, domain model, event-sourced domain model.
  • Transaction script and active record
    • suit simple logic (supporting subdomains, or integrating a third-party solution for a generic one)
    • Difference: simple data structures (script) versus complex data structures needing mapping encapsulation (active record).
  • Domain model and event-sourced domain model
    • suit complex logic: core subdomains
    • The event-sourced variant fits cores that handle money, must provide an audit log, or need deep behavioural analytics.
  • The questions, in order:
    1. Does the subdomain track money or monetary transactions, need a consistent audit log, or need deep analysis of its behaviour? Yes: event-sourced domain model. Otherwise...
    2. Is the logic complex? Yes: domain model. Otherwise...
    3. Does it have complex data structures? Yes: active record. Otherwise...
    4. Transaction script.

  • Complexity is not sharp, but:
    • complex logic has complicated rules, invariants and algorithms
    • simple mainly validates inputs. Also check the ubiquitous language: CRUD operations or complicated processes and rules?
  • The choice validates your subdomain-type assumptions
    • A "core" subdomain that needs only an active record or script, or a "supporting" one that needs a domain model, is a chance to revisit your assumptions
    • Remember: a core subdomain's advantage is not necessarily technical.

Architectural patterns

Business logic pattern Architecture
Event-sourced domain model CQRS (otherwise you can only fetch one instance by ID)
Domain model Ports and adapters (layered makes it hard to keep aggregates and value objects ignorant of persistence)
Active record Layered with the additional application (service) layer for the logic controlling the active records
Transaction script Minimal layered architecture of three layers
  • Exception: CQRS also helps with any other pattern when the subdomain needs its data in several persistent models (Figure 10-4).

Testing strategy

  • The logic and architecture patterns also guide the testing strategy (Figure 10-5), differing in emphasis on unit, integration and end-to-end tests.
Strategy Emphasis Best for Why
Testing pyramid Many unit tests, fewer integration, fewest end-to-end Both domain model variants Aggregates and value objects are perfect units for testing business logic
Testing diamond Mostly integration tests Active record Logic is spread across service and business logic layers, so test their integration
Reversed testing pyramid Mostly end-to-end tests Transaction script Simple logic and minimal layers: verifying the end-to-end flow is most effective

Tactical design decision tree

  • Business logic patterns, architectural patterns and testing strategy combine into one tactical design decision tree (Figure 10-7): identify the subdomain type and follow it.
The table is my summary of the rules above, not a copy of Figure 10-7.
Subdomain Business logic Architecture Testing
Core, money/audit/deep analysis Event-sourced domain model CQRS Testing pyramid
Core, complex logic Domain model Ports and adapters Testing pyramid
Complex data structures Active record Layered with service layer Testing diamond
Simple Transaction script Minimal layered Reversed pyramid

  • These are heuristics, not hard rules:
    • every rule has exceptions
    • The tree reflects the author's preference for simple tools, using advanced ones (domain model, event-sourced model, CQRS) only when necessary
    • Some teams experienced with event sourcing use it everywhere because it is simpler for them
      • the author cannot recommend that for everyone: in his companies, heuristics were more efficient than one solution for all problems.
  • Use the tree as guidance, not a replacement for critical thinking; alter or build your own if others fit better.

Conclusion

  • The chapter connects Parts I and II:
    • using subdomain knowledge to drive context boundaries
    • business logic modelling
    • architecture, and (a detour into a passionate topic) which tests matter most.
  • Making decisions matters, but verifying them over time matters more: the next chapter covers the evolution of design decisions.

Exercises

  1. WolfDesk's ticket lifecycle (core subdomain needing deep behavioural analysis to optimise the algorithm): domain model + CQRS + unit tests / active records + layered + integration tests / domain model + ports and adapters + unit tests / event-sourced domain model + CQRS + unit tests.
  2. WolfDesk's agents' shift management (supporting subdomain): active record, layered, integration tests / domain model, ports and adapters, unit tests / domain model, CQRS, unit tests / event-sourced, CQRS, unit tests.
  3. Integration with an external public holidays provider (periodically fetch dates and names): domain model, ports and adapters, integration tests / domain model, CQRS, unit tests / event-sourced, CQRS, unit tests / transaction script, layered architecture, end-to-end tests.
  4. What other aspects of the software development process could join the heuristics-based decision tree?
Answers (book appendix B)
  1. D: event-sourced domain model with CQRS and unit tests (core, deep analytics).
  2. A: active record in layered architecture, focused on integration tests.
  3. D: transaction script in layered architecture, end-to-end tests.

Summary points

  • Let the model set the context size; start wide around volatile cores.
  • Pattern by questions: audit/money/analysis, then complexity, then data structures.
  • Architecture and testing follow the logic pattern; heuristics guide, you decide.
Terms to carry forward
  • Heuristic: rule of thumb, not guaranteed.
  • Wide bounded context: several subdomains behind logical boundaries.
  • Testing pyramid / diamond / reversed pyramid: unit-heavy, integration-heavy, end-to-end-heavy.
  • Tactical design decision tree: subdomain type to logic, architecture and tests.
