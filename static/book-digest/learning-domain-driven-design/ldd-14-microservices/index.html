Learning DDD 14: Microservices

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 14. Previous: Learning DDD 13: Domain-Driven Design in the Real World. Next: Learning DDD 15: Event-Driven Architecture.

Takeaways
  • A service is defined by its public interface (its front door); a microservice is a service with a micro public interface, which is why it never exposes its database.
  • One method per service fails: integration methods widen every interface and you get a distributed big ball of mud. Global complexity matters more than local complexity.
  • Microservices should be deep modules (Ousterhout): a simple interface hiding complex logic. Splitting past the microservice threshold makes them shallow and raises cost of change.
  • All microservices are bounded contexts, but not all bounded contexts are microservices. A bounded context is the widest safe boundary, the microservice (often a subdomain) the narrowest; the aggregate is too narrow in most cases.
  • Open-host service and anticorruption layer compress public interfaces.

Context

  • In the mid-2010s microservices took off to meet fast change, scale and cloud-fit
    • Many companies ended with distributed big balls of mud, more fragile, clumpy and expensive than the monoliths.
  • Microservices and bounded contexts are often used interchangeably. This chapter tests that.

What is a service?

  • OASIS: a mechanism that enables access to one or more capabilities, via a prescribed interface (any way of getting data in or out): synchronous (request/response) or asynchronous (producing and consuming events) (Figure 14-1).
  • Randy Shoup:
    • the interface is a front door: all data in and out passes through it
    • The public interface defines the service: a well-expressed interface describes its functionality (Figure 14-2).

What is a microservice?

  • Since a service is defined by its public interface, a microservice is a service with a micro public interface: a micro front door.
  • Benefits: easier to understand the function and the integration; fewer reasons to change; more autonomy for development, management and scale.
  • It also explains why microservices do not expose their databases: that would make the interface huge (how many SQL queries can you run? effectively infinite)
    • Data is accessed only through a compact, integration-oriented interface.

Method as a service: perfect microservices?

  • Naive idea: one public method per service. Take a backlog management service with eight public methods and apply it (Figure 14-3).
  • Each service encapsulates its own database, so none can read another's
    • They must work together and synchronise changes, so we add integration methods to the interfaces
    • The integrations and data flows look like a distributed big ball of mud (Figure 14-4).
  • Shoup's metaphor: we minimised the front doors but added enormous "staff only" entrances to every service.

Design goal

  • Why the heuristic is wrong:
    1. It is not possible: services must cooperate, so interfaces grow with integration methods.
    2. Won the battle, lost the war: each service is simpler, the system orders of magnitude more complex.
  • The goal is a flexible system. A system is "a set of connected things or devices that operate together"
    • it cannot be built from independent components, so services still have to be integrated.

System complexity

  • Forty years ago there was no cloud or global scale or deployments every 11.7 seconds, but complexity still had to be tamed. Glenford Myers (Composite/Structured Design): minimising the local complexity of each part is not enough
    • the more important type is global complexity: the complexity of the overall structure, the degree of association or interdependence among major pieces.
  • Local complexity = each microservice's implementation. Global complexity = interactions and dependencies between services.
    • Minimise global: put everything in one monolith (no interactions), possibly yielding a big ball of mud (highest local complexity).
    • Optimise only local: the distributed big ball of mud (Figure 14-5).
  • Optimising either alone is a local optimum; the global optimum balances both.

Microservices as deep services

  • A module has a function (what it does) and logic (how)
    • John Ousterhout (A Philosophy of Software Design) proposes depth as a heuristic: draw a module as a rectangle whose top edge is the function (interface complexity, wider = broader function) and whose area is the logic (implementation) (Figure 14-6).
  • Deep modules: a simple interface encapsulating complex logic. Shallow modules encapsulate little. The extreme shallow case:
// AddTwoNumbers
int AddTwoNumbers(int a, int b)
{
    return a + b;
}
  • Interface and logic are the same: it adds moving parts and accidental complexity rather than encapsulating it.

Microservices as deep modules

  • Same principles, different terms; the difference: modules can be logical or physical boundaries, microservices are strictly physical.
  • Services of a single business method (Figure 14-3) are shallow, with wider interfaces than necessary. A deep module lowers global complexity; a shallow module raises it.
  • Shallow services explain why many projects fail
    • Definitions such as "no more than X lines of code" or "easier to rewrite than to modify" focus on the individual service and miss the system.
  • The microservice threshold is set by the system's use cases
    • Decomposing a monolith lowers the cost of change, minimised at microservices
    • Decomposing further makes deep services shallow again, interfaces grow back, cost of change rises and the architecture becomes a distributed big ball of mud (Figure 14-7).

DDD and microservices' boundaries

  • DDD boundaries: the bounded context (model), the subdomain (business capability), aggregates and value objects (transactions). Which suit microservices?

Bounded contexts

  • Both are physical boundaries, owned by one team, and neither can hold conflicting models (which complicates interfaces)
    • Microservices are bounded contexts. Is the reverse true?
  • Example: an advertising management system where the entity Lead has different models in Promotions and Sales (Figure 14-8): those are bounded contexts, each with one model of Lead.
  • With no other conflicts, the contexts are naturally wide and may hold several subdomains, which can move between contexts
    • Any decomposition without model conflicts is a valid context (Figure 14-9)
    • Different decompositions suit different team sizes, lifecycle dependencies and so on
    • But are all of them microservices? No, especially given the wide functionality of the two contexts in decomposition 1.
  • So the relation is asymmetric:
    • **microservices are bounded contexts
    • not every bounded context is a microservice.** Bounded contexts mark the largest valid monolith (not a big ball of mud): a viable design that protects the consistency of the language
    • chapter 15 shows broad boundaries beat microservices in some cases.
  • Figure 14-10:
    • the area between bounded contexts (widest) and microservices (narrowest) is safe. No proper bounded contexts gives a big ball of mud
    • decomposing past microservices gives a distributed big ball of mud.

Aggregates

  • The aggregate is the narrowest possible boundary; splitting an aggregate into several physical services or contexts is suboptimal and (appendix A) has undesired consequences.
  • It is an indivisible business functionality unit. But a service must be seen with its interactions:
    • Does the aggregate talk to other aggregates in its subdomain?
    • Does it share value objects with them?
    • How likely do its logic changes affect other components of the subdomain, and vice versa?
  • The stronger the relationships, the shallower it is as a service
    • Sometimes an aggregate as a service gives a modular design, but much more often such fine-grained services raise global complexity.

Subdomains

  • A more balanced heuristic:
    • align services with business subdomains
    • Subdomains are fine-grained business capabilities (the "what" not the "how") and, technically, sets of coherent use cases using the same model, the same or closely related data and a strong functional relationship: a change to one use case likely affects the others (Figure 14-11).
  • Granularity and the "what over how" focus make subdomains naturally deep modules
    • splitting coherent use cases usually makes the interface more complex, so the module shallower. Subdomains are a safe boundary and give optimal solutions for the majority of microservices.
  • Exceptions:
    • stay in the wider bounded context, or use an aggregate as a microservice because of non-functional requirements
    • The answer depends on domain, organisation structure, strategy and non-functional requirements, and must keep adapting (chapter 11).
Candidate boundary Verdict
Bounded context Widest valid; some are too wide for a microservice
Subdomain Balanced and safe for most services
Aggregate Narrowest; usually too fine-grained and shallow

Compressing microservices' public interfaces

  • DDD also helps make services deeper.

Open-host service

  • Decouples the context's domain model from the integration model (Figure 14-12). The published language:
    • lets the implementation evolve without affecting consumers (translate the new model to the existing language);
    • is a more restrained model designed around integration needs, hiding irrelevant complexity (less data, more convenient shape).
  • A simpler public interface (function) over the same logic makes the service deeper.

Anticorruption layer

  • The reverse:
    • it reduces the complexity of integrating the service with other contexts. Traditionally it lives inside the context it protects
    • as in chapter 9 it can be a standalone service (Figure 14-13).
  • It reduces local complexity of the consumer (business complexity is separated from integration complexity) and global complexity
    • The consumer works with a convenient integration-oriented model, so its public interface is compressed.

Conclusion

  • All microservices are bounded contexts, not all bounded contexts are microservices. A microservice defines the smallest valid boundary, a bounded context the widest (protecting model consistency). Wider than a bounded context gives a big ball of mud
    • narrower than a microservice gives a distributed one.
  • The DDD-microservices link is tight: use DDD tools to find effective boundaries. Next: event-driven architecture and event message types that further optimise boundaries.

Exercises

  1. Relationship: all microservices are bounded contexts / all bounded contexts are microservices / same concept / unrelated.
  2. What should be "micro"? Pizzas for the team / lines of code / certified middleware / the knowledge of the business domain exposed across the service boundary and reflected by its public interface.
  3. Safe component boundaries: wider than bounded contexts / narrower than microservices / between bounded contexts (widest) and microservices (narrowest).
  4. Align microservices with aggregates? Always / never / impossible / it depends on the business domain.
Answers (book appendix B)
  1. A: all microservices are bounded contexts, not all bounded contexts are microservices.
  2. D: manage local and global complexity by encapsulating domain knowledge in service boundaries.
  3. C: the range between the widest bounded contexts and microservices is the safe zone.
  4. D: depending on aggregate interactions, exposing aggregates as microservices can help or not.

Summary points

  • Micro means a micro public interface over deep logic, not few lines of code.
  • Balance local and global complexity; avoid both big balls of mud.
  • Default to subdomain-aligned services, between microservice and bounded context limits.
Terms to carry forward
  • Front door / public interface: what defines a service.
  • Local versus global complexity: inside a service versus between services.
  • Deep versus shallow module: simple interface over rich logic versus the opposite.
  • Distributed big ball of mud: over-decomposed system.
  • Microservice threshold: point past which cost of change rises.
