Learning DDD 15: Event-Driven Architecture

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 15. Previous: Learning DDD 14: Microservices. Next: Learning DDD 16: Data Mesh.

Takeaways
  • EDA is asynchronous integration by exchanging event messages; it concerns communication between services, while event sourcing happens inside a service.
  • An event (already happened, cannot be rejected) differs from a command (to be carried out, can be rejected). Both are messages.
  • Three event types: event notification (small, consumer queries for details), event-carried state transfer (full state, local cache) and domain event (models the business domain).
  • Careless EDA yields a distributed big ball of mud with temporal, functional and implementation coupling.
  • Heuristics: assume the worst, separate public and private events, and choose the event type by consistency requirements.

Premise

  • Like microservices, EDA is ubiquitous and often advised as the default integration mechanism for loosely coupled, scalable, fault-tolerant systems
    • It is tied to DDD through events (domain events, events as source of truth), but is leaning on DDD's events a good idea?
  • Events are not secret sauce to pour over a legacy system
    • Careless EDA can turn a modular monolith into a distributed big ball of mud. The chapter covers building blocks, common causes of failed EDA projects and how DDD tools help.

Event-driven architecture

  • An architectural style where components communicate asynchronously by exchanging event messages (Figure 15-1): instead of calling endpoints synchronously they publish events to notify others of domain changes and subscribe to react
    • Typical example: the saga (chapter 9).
  • EDA versus event sourcing:
    • both use events but differ conceptually. **EDA is communication between services
    • event sourcing happens inside a service.** Event-sourcing events represent aggregate state transitions and capture business intricacies
    • they are not meant to integrate the service with others. There are three event types, some better for integration.

Events

Events, commands and messages

  • An event is a message, but a message is not necessarily an event (Hohpe and Woolf). Two kinds:
    • Event: a message describing a change that has already happened.
    • Command: a message describing an operation to be carried out.
  • Both can be sent asynchronously. A command can be rejected (invalid or contradicts rules)
    • an event cannot be cancelled, only overturned by a compensating action, which is a command (as in sagas).
  • Names: events in the past tense (DeliveryScheduled, ShipmentCompleted, DeliveryConfirmed).

Structure

  • An event is a serialisable data record with metadata and payload:
{
    "type": "delivery-confirmed",
    "event-id": "14101928-4d79-4da6-9486-dbc4837bc612",
    "correlation-id": "08011958-6066-4815-8dbe-dee6d9e5ebac",
    "delivery-id": "05011927-a328-4860-a106-737b2929db4e",
    "timestamp": 1615718833,
    "payload": {
        "confirmed-by": "17bc9223-bdd6-4382-954d-f1410fd286bd",
        "delivery-time": 1615701406
    }
}

Types of events (Fowler)

Event notification

  • A message about a business change others will react to (PaycheckGenerated, CampaignPublished). It should be succinct: notify, but not carry all the data subscribers need
    • they fetch more via a link:
{
    "type": "paycheck-generated",
    "event-id": "537ec7c2-d1a1-2005-8654-96aee1116b72",
    "delivery-id": "05011927-a328-4860-a106-737b2929db4e",
    "timestamp": 1615726445,
    "payload": {
        "employee-id": "456123",
        "link": "/paychecks/456123/2021/01"
    }
}
  • Flow in Figure 15-2
    • Analogy: the Wireless Emergency Alert system (US) and EU-Alert broadcast messages of at most 360 characters: enough to alert you, but you must seek details elsewhere (Figure 15-3).
  • Preferable for:
    • Security: forcing recipients to query keeps sensitive data off the messaging infrastructure and requires extra authorisation.
    • Concurrency:
      • asynchronous data may already be stale
      • querying gets the up-to-date state if race-sensitive. For concurrent consumers where only one should process an event, the query can use pessimistic locking, so no other consumer handles it.

Event-carried state transfer (ECST)

  • Notifies subscribers about changes in the producer's internal state and includes all the data reflecting the change
    • Two forms: a complete snapshot, or only the modified fields (for large structures):
{
    "type": "customer-updated",
    "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
    "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
    "timestamp": 1615728520,
    "payload": {
        "first-name": "Carolyn",
        "last-name": "Hayes",
        "phone": "555-1022",
        "status": "follow-up-set",
        "follow-up-date": "2021/05/08",
        "birthday": "1982/04/05",
        "version": 7
    }
}

{
    "type": "customer-updated",
    "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
    "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
    "timestamp": 1615728520,
    "payload": {
        "status": "follow-up-set",
        "follow-up-date": "2021/05/10",
        "version": 8
    }
}
  • A stream of ECST events lets consumers hold a local cache of the entities: asynchronous data replication
    • It makes the system more fault tolerant (consumers work even if the producer is down) and faster for components combining several sources (Figure 15-4: backend for frontend).

Domain event

  • From chapter 6: in between notification and ECST: it describes a significant business event and carries all data describing the event. Still conceptually different.
  • Versus event notification:
    • a domain event includes all information about the event, with no follow-up needed
    • modelling intent:
      • notifications are designed to ease integration, domain events model and describe the business domain, and are useful even with no external consumer, especially in event-sourced systems where they model all state transitions
      • Having external consumers interested in all domain events would be a suboptimal design
  • Versus ECST:
    • ECST gives enough to cache the producer's data
    • no single domain event should expose such a rich model, and one event does not cover a field affected by other events the consumer does not subscribe to. The intent differs: domain events describe what happened in the lifecycle, not the aggregate's state.

Example: three events for a marriage

// event notification
eventNotification = {
    "type": "marriage-recorded",
    "person-id": "01b9a761",
    "payload": {
        "person-id": "126a7b61",
        "details": "/01b9a761/marriage-data"
    }
};

// event-carried state transfer
ecst = {
    "type": "personal-details-changed",
    "person-id": "01b9a761",
    "payload": {
        "new-last-name": "Williams"
    }
};

// domain event
domainEvent = {
    "type": "married",
    "person-id": "01b9a761",
    "payload": {
        "person-id": "126a7b61",
        "assumed-partner-last-name": true
    }
};
  • marriage-recorded is a notification: only the fact; follow the details link for more.
  • personal-details-changed is ECST: the last name changed, but not why (marriage or divorce?).
  • married is a domain event: modelled as close as possible to the business, with the person's id and whether they assumed the partner's name.

Designing event-driven integration

  • Design is about boundaries (chapter 3):
    • what is in, out, and what crosses
    • Events are first-class design elements affecting integration and the boundaries themselves
    • The right event type decouples; the wrong one couples.

A distributed big ball of mud (Figure 15-5)

  • CRM
    • is an event-sourced domain model
    • To integrate Marketing, teams let Marketing subscribe to CRM's domain events and project its own model
    • Later AdsOptimization did the same
    • Both ended up projecting the same model: a flattened snapshot of each customer's state.
  • Reporting
    • subscribed to a subset of the CRM's domain events, used as notifications to fetch calculations made in AdsOptimization
    • Both use the same events as triggers, so to make Reporting see updated data, AdsOptimization delayed processing by five minutes.
  • "This design is terrible":
Coupling What happened
Temporal AdsOptimization must finish before Reporting runs, or Reporting gets inconsistent data. The five-minute delay does not guarantee order: AdsOptimization may be overloaded, a network issue may delay delivery, or it may suffer an outage.
Functional Marketing and AdsOptimization duplicate the same projection logic (events to a state-based customer view) with the same reason to change; a change in one must be copied to the other.
Implementation Both subscribe to all CRM domain events, so adding an event or changing a schema must be reflected in both; otherwise projections become inconsistent (a changed schema breaks projection; a new event ignored gives inconsistent state).
  • The example "is based on a true story".

Refactoring the integration (Figure 15-6)

  • Exposing all of CRM's domain events couples subscribers to implementation. Expose a much more restrained set of events or another type.
  • Functional and implementation coupling:
    • encapsulate the projection in the producer (CRM)
    • Following the consumer-driven contract pattern, CRM projects the model consumers need as part of its published language, an integration model decoupled from its implementation
    • Consumers get the data without knowing the CRM's model.
  • Temporal coupling: AdsOptimization publishes an event notification, triggering Reporting to fetch the data it needs.

Event-driven design heuristics

Assume the worst

  • Andrew Grove:
    • only the paranoid survive
    • Assume: the network is slow, servers fail at the worst moment, events arrive out of order and duplicated, and most often on weekends and public holidays.
  • "Event-driven" means the whole system depends on successful delivery. So:
    • use the outbox pattern for reliable publishing;
    • let subscribers deduplicate and reorder messages;
    • use sagas and process managers for cross-context processes with compensating actions.

Use public and private events

  • Do not expose implementation details, especially of event-sourced aggregates
    • Treat events as part of the context's public interface: with an open-host service, reflect events in the published language (chapter 9 translation).
  • Use the types for public interfaces:
    • ECST compresses the implementation model into a compact one
    • event notifications minimise the interface further
    • use domain events sparingly externally, and consider a dedicated set of public domain events.

Evaluate consistency requirements

  • Eventually consistent data is acceptable: use ECST.
  • The consumer needs the last write: use an event notification plus a query for the producer's up-to-date state.

Conclusion

Event type Summary
Event notification Something important happened; consumer queries the producer for more
Event-carried state transfer Message-based replication; each event has a state snapshot for a local cache
Domain event Describes an event in the producer's business domain
  • The wrong event types derail EDA into a big ball of mud
    • Choose by consistency requirements, avoid exposing implementation details, design public and private events, and ensure delivery despite failures.

Exercises

  1. Correct statements (select all): EDA defines events intended to cross component boundaries / event sourcing defines events intended to stay within the context / EDA and event sourcing are the same.
  2. Best type for communicating changes in state: notification / event-carried state transfer / domain event / all equal.
  3. Which integration pattern calls for explicitly defined public events? Open-host service / anticorruption layer / shared kernel / conformist.
  4. S1 sends data asynchronously, S2 must read the last written data: ECST / public event notifications, then a synchronous query for the latest data / domain events.
Answers (book appendix B)
  1. A and B: EDA is events across components, event sourcing events within a context.
  2. B: event-carried state transfer is event-based state replication.
  3. A: the open-host service defines an integration model that separates public and private events.
  4. B: a synchronous call lets S2 read the last written data.

Summary points

  • EDA is between services, event sourcing within one.
  • Event, command, message; notification, ECST, domain event.
  • Avoid temporal, functional and implementation coupling; assume failures; separate public and private events; pick the type from consistency needs.
Terms to carry forward
  • Event notification / ECST / domain event: three event types.
  • Temporal / functional / implementation coupling: forms of coupling via events.
  • Consumer-driven contract: producer projects what consumers need.
  • Public versus private events: integration versus internal.
