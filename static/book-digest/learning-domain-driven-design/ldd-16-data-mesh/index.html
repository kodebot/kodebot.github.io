Learning DDD 16: Data Mesh

Source: Vlad Khononov, Learning Domain-Driven Design (O'Reilly, 2021), ch. 16. Previous: Learning DDD 15: Event-Driven Architecture. Next: Learning DDD 17: Closing Words.

Takeaways
  • Analytical (OLAP) models differ from operational (OLTP) ones: facts (append-only business activities) and dimensions (descriptions) in star or snowflake schemas, with unpredictable queries.
  • Data warehouses (ETL into one enterprise model) and data lakes (raw data, models later) both couple analytics to the operational implementation models and break at scale (thousands of ad hoc ETL scripts, the data swamp).
  • Data mesh is DDD for analytical data, built on four principles: decompose data around domains (bounded contexts), data as a product, enable autonomy (platform team) and build an ecosystem (federated governance).
  • DDD supports it: ubiquitous language, open-host service (the analytical model as a published language), CQRS (several model versions) and the integration patterns between data products.

OLTP and OLAP

  • So far we modelled operational systems:
    • real-time transactions that manipulate data and orchestrate day-to-day interactions (OLTP)
    • Another type needs modelling: online analytical processing (OLAP) data.
  • "Knowledge is power": analytical data lets a company optimise the business, understand customers and make automated decisions by training ML models.

Analytical versus transactional model

Operational (OLTP) Analytical (OLAP)
Built around Business entities: lifecycles and interactions (Figure 16-1) Business activities (facts) described by dimensions
Goal Support real-time transactions Provide insights: performance of activities and how to optimise them
Granularity Most precise data Often aggregated
Queries Predictable Unpredictable: analysts need flexible ways to view data

Fact table

  • Facts
    • are business activities that already happened, like domain events, but with no requirement to name them as past-tense verbs. Fact_CustomerOnboardings has a record per onboarded customer
    • Fact_Sales one per committed sale (Figure 16-2: cases solved by a support desk).
  • Like events, facts are never deleted or modified:
    • analytical data is append-only
    • to show current data is outdated, append a new record. Fact_CaseStatus (Figure 16-3) holds support case statuses over time, with snapshots every 30 minutes.
  • Granularity is chosen by analysts: a record for every change would be wasteful or technically impossible.

Dimension table

  • If a fact is a verb (process or action), a dimension is an adjective describing it
    • Dimensions describe the fact's attributes, are referenced by foreign keys from the fact, and hold data repeated across facts that does not fit one column (Figure 16-4: the SolvedCases fact surrounded by its dimensions).
  • They are highly normalised to support flexible querying: filtering and grouping facts across dimensions when future queries are unpredictable.

Analytical models

Schema Structure Trade-off
Star schema (Figure 16-5) Facts with many-to-one relationships to dimensions: each dimension record serves many facts, each fact points to one dimension record Simple, fast joins
Snowflake schema (Figure 16-6) Same blocks but multilevel dimensions, each further normalised into finer dimensions Less space, easier to maintain; but more joins and more computing to query
  • Both let analysts study performance and build BI reports.

Analytical data management platforms

  • Two common architectures and their challenges, as the base for data mesh.

Data warehouse (DWH)

  • Extract
    • data from all operational systems (databases, streaming events, logs), transform it into an analytical model, load it into an analysis-oriented database: the warehouse
    • Based on ETL scripts
    • Transformation may also remove sensitive data, deduplicate, reorder events, aggregate fine-grained events, sometimes using a staging area for temporary storage.
  • The warehouse covers all business processes, exposed in SQL to analysts and BI engineers (Figure 16-7).
  • Challenge 1: an enterprise-wide model
    • for all systems and all use cases (optimisation, cost reduction, decisions, reporting, ML training). As in chapter 3, that is impractical beyond the smallest organisations
    • models should be designed for the task.
    • Data marts
      • partly help: a database with data for a well-defined need (such as one department)
      • A mart can be fed from the warehouse (the enterprise model must still exist) or by its own ETL directly from operational systems (cross-mart queries then need cross-database queries and hurt performance) (Figure 16-8).
  • Challenge 2: coupling.
    • ETL couples OLAP to OLTP: scripts often read operational databases directly, though the schema is an internal detail, not a public interface
    • A small schema change breaks the ETL
    • Operational and analytical units are organisationally distant, so communication is hard and teams get friction (Figure 16-9).

Data lake

  • Also ingests operational data but stores it raw, in the original operational model, without transforming it first
    • Data and BI engineers later make sense of it and write ETL scripts to produce analytical models and feed a warehouse (Figure 16-10).
  • Advantages: several task-oriented models (reporting, ML training), and new models later from the existing raw data.
  • Costs:
    • delayed model generation raises complexity; engineers maintain multiple versions of the same ETL script for different versions of the operational model (Figure 16-11)
    • Lakes are schema-less with no quality control, so at scale the data becomes chaotic: a data swamp
    • Ingestion is easy, use is hard.

Challenges of both

  • Both assume more ingested data means more insight, and both break under "big data": the transformation converges to thousands of unmaintainable ad hoc ETL scripts.
  • Modelling: both trespass the operational systems' boundaries and depend on their implementation details, so friction can prevent changing operational models to avoid breaking ETL jobs.
  • Knowledge: analysts and data engineers sit in a separate unit and lack the business domain knowledge of the operational teams; they specialise in big data tooling.
  • Worse in DDD projects, where operational models are continuously evolved: changes have unforeseen consequences for analytical models and cause R&D versus data team friction.

Data mesh

  • Data mesh is, in a sense, DDD for analytical data:
    • as DDD patterns draw and protect boundaries, it defines and protects model and ownership boundaries for analytical data
    • Four principles:

1. Decompose data around domains

  • Warehouses and lakes unify everything into one big model, ineffective for the same reasons as an enterprise-wide operational model, and it blurs ownership
    • Data mesh applies chapter 3's solution: multiple analytical models aligned with the origin of the data, with ownership aligned to bounded contexts (Figure 16-12)
    • Product teams become responsible for generating the analytical data.
  • Each bounded context owns both its OLTP and OLAP models, and the same team transforms one into the other.

2. Data as a product

  • Classic architectures make quality analytical data hard to discover, understand and fetch (especially lakes)
    • Treat analytical data as a first-class citizen: instead of scraping internal databases or log files, bounded contexts serve analytical data through well-defined output ports (Figure 16-13: polyglot data endpoints).
  • Treat it like any public API:
    • discoverable endpoints (output ports);
    • a well-defined schema;
    • trustworthy, with monitored SLAs;
    • versioned, managing breaking changes.
  • It must meet consumers' needs; the context's team is accountable, and data quality is a top-level concern (unlike warehouses and lakes).
  • Fine-grained models must be combinable: a BI report across several contexts fetches their analytical data, transforms locally and produces the report.
  • Data products are polyglot: SQL for some, object storage for others.
  • Teams need data specialists added: the missing piece in cross-functional teams (traditionally only operational specialists).

3. Enable autonomy

  • Teams must create their data products and consume others', and products must be interoperable
    • If each team built its own serving solution it would be wasteful and hard to integrate, so a platform abstracts building, running and maintaining interoperable data products
    • It is a considerable undertaking needing a dedicated data infrastructure platform team, defining blueprints
      • unified access patterns
      • access control and polyglot storage, plus monitoring and meeting SLAs.

4. Build an ecosystem

  • Appoint a federated governance body to ensure interoperability and ecosystem thinking: typically the bounded contexts' data and product owners plus representatives of the platform team (Figure 16-14)
    • It defines rules applying to all data products and interfaces and ensures adherence enterprise-wide.

Combining data mesh and DDD

  • Boundaries and encapsulation behind well-defined output ports show data mesh follows DDD's reasoning. DDD patterns support it:
    • Ubiquitous language and domain knowledge are essential for designing analytical models; traditional architectures lack them.
    • Exposing a context's data in a model different from its operational one is the open-host service: the analytical model is an additional published language.
    • CQRS
      • generates several models of the same data and can transform operational into analytical models
      • its ability to build models from scratch lets you serve several schema versions at once (Figure 16-15).
    • The context integration patterns apply to analytical models too: teams can evolve models in a partnership, use an anticorruption layer against an ineffective model, or go separate ways and duplicate.

Conclusion

  • Analytical models (star and snowflake), traditional management (warehouse, lake) and their challenges
    • data mesh applies DDD's principles to analytical data: decompose the model into manageable units, reliably accessible through public interfaces
    • CQRS and context integration patterns support it.

Exercises

  1. Differences between OLTP and OLAP (select all): OLAP should expose more flexible querying / OLAP gets more updates and must optimise for writes / OLTP is optimised for real-time operations, waiting seconds or minutes for OLAP is acceptable.
  2. Integration pattern essential for data mesh: shared kernel / open-host service / anticorruption layer / partnership.
  3. Architectural pattern essential for data mesh: layered / ports and adapters / CQRS / none.
  4. DDD's term for data mesh "domains": bounded contexts / business domains / subdomains / no synonym.
Answers (book appendix B)
  1. A and C: OLAP is optimised for reading, OLTP for writing.
  2. C: open-host service (integration-specific models share analytical data).
  3. C: CQRS (multiple persistent models, convenient for analytical models).
  4. A: bounded contexts are the closest to data mesh domains.

Summary points

  • Facts (append-only verbs) and dimensions (adjectives); star and snowflake schemas.
  • Warehouse and lake couple to operational internals and scale badly.
  • Data mesh = four principles, DDD for analytical data, with OHS and CQRS as the supporting patterns.
Terms to carry forward
  • OLTP / OLAP: operational versus analytical models.
  • Fact / dimension: activity record / its descriptive attributes.
  • Star / snowflake schema: single versus multilevel dimensions.
  • Data warehouse / data mart / data lake / data swamp.
  • Data product / output port: analytical data served as a product.
  • Federated governance: group that keeps the mesh interoperable.
