Monolith to Microservices 3: Splitting the Monolith

Source: Sam Newman, Monolith to Microservices (O'Reilly, 2019), chapter 3. Previous: Monolith to Microservices 2: Planning a Migration. Next: Monolith to Microservices 4: Decomposing the Database.

Takeaways
  • First decide whether you can change the monolith. The patterns split into those that intercept calls at the edge (strangler fig, UI composition), those that change the code inside (branch by abstraction), those that verify (parallel run) and those that react to events or data (decorating collaborator, change data capture).
  • Strangler fig is Newman's first port of call: put a proxy in front, build the new service, redirect calls, roll back by redirecting again. Separate deployment from release.
  • Branch by abstraction replaces long-lived branches for functionality deep inside the monolith. Parallel run compares old and new before trusting the new.
  • When migrating functionality, freeze its behaviour (no new features or bug fixes) to keep rollback possible.
  • Most teams mix several patterns; none is universally right.

3.1 To change the monolith, or not?

  • If you can change the code you have the most options
    • A hard constraint can deny it: vendor software without source, or a technology you lack skills for
    • Softer drivers: the monolith is so bad you want to start again (Newman worries people reach that conclusion too easily), or many others work in it and you would get in their way (branch by abstraction can mitigate, but you may still judge the impact too great).
  • Anecdote:
    • a heavy-computation C library full of memory leaks and a poor API; the team asked for months for the source and was refused
    • Years later the sponsor admitted they had lost the source and were too embarrassed to say
    • Several patterns here work without changing the monolith.

Cut, copy or reimplement?

  • If the code is well factored you may move it, but copy it and leave it in the monolith at first: it gives a rollback point or a parallel run
    • Remove it later once the migration succeeds.
  • Refactoring the monolith:
    • the main barrier is that code is organised by technology (model, view, controller packages) not business domain, so even finding the code is hard
    • Recommended:
      • Michael Feathers, Working Effectively with Legacy Code (2004), whose seam is a place to change behaviour without editing existing behaviour
      • define a seam, build a new implementation, swap it in
    • Seams fit bounded contexts well.
  • A modular monolith?
    • Extract seams as modules (Java JAR files, Ruby gems): still one deployment, many benefits, can be the sweet spot
    • some teams found it solved most of their problems.
  • Incremental rewrites:
    • Newman prefers salvaging code first, but few teams do
    • most do a clean-room reimplementation of each new service. That is safe if you rewrite only small pieces and ship regularly: a few days or weeks is fine, months means re-examine.
Caution

Each pattern has pros and cons; none is universally the right way. Understand them before choosing.

3.2 Pattern: strangler fig application

  • Captured by Martin Fowler, inspired by figs that seed in a tree's upper branches and descend to root, enveloping the host, which may die and rot away
    • Here the new system is initially supported by and wraps the old; both coexist so the new can grow and possibly replace the old
    • Benefit: incremental migration, and the ability to pause or stop while keeping what has been delivered
    • Each step is easily reversible.
  • How it works:
    • identify what to migrate (use the Chapter 2 trade-off thinking),
    • implement it in a new microservice (copying or reimplementing; migrate state if needed, Chapter 4),
    • reroute calls (Figure 3-1)
      • Until the redirect, the new functionality is not live even if deployed, so you can take your time, deploy to production safely and use parallel run for confidence
Deployment is not release

Software deployed to an environment is not necessarily used by customers. Separating the two lets you validate in the real production environment first. Strangler fig, parallel run and canary release all use this.

  • If other functionality in the monolith also uses what you extract, change those calls too (later techniques).
  • Where to use it:
    • no change to the monolith, so it suits monoliths others are working on and black-box or SaaS systems. Sometimes an entire end-to-end slice moves (Inventory Management, Figure 3-2)
    • extracting larger groups simplifies integration but is more work
      • Smaller bites mean "shallow" extractions (Payroll, Figure 3-3) that still use monolith functionality (User Notifications), which then must be exposed by the monolith (a change to it)
      • It fails when the functionality is deep inside and fired by many inbound calls (Notifications, Figure 3-4)
      • HTTP has transparent redirection built in
    • some RPC protocols are harder. Despite limits, it is Newman's usual first choice.

Example: HTTP reverse proxy

  • Insert an HTTP reverse proxy between upstream callers (a UI or headless) and the monolith (Figure 3-5).
  • Step 1, insert the proxy
    • (Figure 3-6): pass everything through unchanged
    • Check the extra hop (a few milliseconds for a decent proxy and network), set up monitoring, let it settle
    • If you already have a proxy, still experiment with redirection first so there is no nasty surprise before going live.
  • Step 2, migrate functionality
    • (Figure 3-7), in stages: first a basic service that returns 501 Not Implemented, deployed to production to get comfortable with deployment (deployed, not released)
    • then add behaviour.
  • Step 3, redirect
    • (Figure 3-8) only when all the functionality has moved
    • revert the redirection for fast rollback. A feature toggle makes the state clear
    • the proxy is also the place for a canary rollout or parallel run.
  • Data: if the Payroll service needs data in the monolith's database, see Chapter 4.
  • Proxy options:
    • with HTTP, a dedicated proxy such as NGINX is the choice. Redirection by URI path or REST resource is easy (Figure 3-9: the whole Invoice resource)
    • switching on a POST body parameter is harder but possible. Newman wrote two hand-built proxies (Java and Python) and both were inefficient and laggy
    • instead extend a proxy (NGINX allows Lua).
  • Incremental rollout
    • (Figures 3-10, 3-11): slice smaller if needed, even splitting Payroll between monolith and service, though both seeing the same data implies a shared database
    • No stop-the-line re-platforming: stop dividing the backlog into "feature" and "technical" stories and get good at architectural change alongside features.

Changing protocols

  • A proxy could transform a SOAP interface into gRPC (Figure 3-12), but logic accumulates in a shared layer that multiple teams edit, adding contention against independent deployability
    • Remember "keep the pipes dumb, the endpoints smart".
  • Better:
    • have the service support both the old and new protocol and map internally (Figure 3-13): the service controls its own change, and consumers have time to move before the old API retires
    • A microservice is a collection of functionality on a network endpoint, exposed in different ways to different consumers.
  • Service meshes
    • (Figure 3-14): each instance talks through its own local proxy, with central control and monitoring through a control plane, so there is no shared smart pipe
    • At Square they moved from a homegrown RPC mechanism to gRPC and, because of how their architecture evolved, built their own mesh on the Envoy proxy rather than using Linkerd or Istio
    • The idea is "spot on", but tooling took long to stabilise (Istio leading); give it time if you can.

Example: FTP and messaging

  • FTP (Homegate, Swiss real estate):
    • customers upload listings by FTP, handled by the monolith
    • They wanted a new REST upload standard without changing the customer experience, so they detected uploads from the FTP server log and sent the files through an adapter to the new REST-based listings service (Figure 3-15)
    • Listings went live faster; both paths ran together (a parallel run).
  • Message interception: the same idea with a broker.
    • Content-based router
      • (Figures 3-16, 3-17, from Enterprise Integration Patterns): intercept all messages and forward them to monolith or service
      • The monolith is untouched but there is another queue on the path (latency, management) and arguably a "smart pipe".
    • Selective consumption
      • (Figure 3-18): monolith and service share one queue and each filters (a JMS message selector)
      • No extra queue, but the technology must allow it, and cut-over and rollback each need two coordinated changes
      • Overlapping rules can deliver a message twice or drop it, so use it with few consumers and simple rules; routing suits more consumer types.
    • Asynchronous request-response also needs a route back to the client.
  • Other protocols:
    • for batch uploads, intercept the file, pull out the calls you want and forward the rest. The pattern was used long before Fowler wrote it up in 2004
    • ThoughtWorks used it often (Paul Hammant lists projects: a trading blotter, an airline booking application, a rail ticketing system, a classified ad portal).

Changing behaviour while migrating

Freeze behaviour

If the migrated service gets bug fixes or new features that the monolith version lacks, a rollback reintroduces the bugs or removes features. Try to eliminate changes to the behaviour being moved until the migration is done. The longer it takes, the harder the freeze, so keep migrations small.

3.3 Pattern: UI composition

  • Splice functionality served by the old and new systems in the user interface
    • At The Guardian (a content management system moved to a custom Java platform), the cut-over was phased by vertical (travel, news, culture), starting with Travel.
  • Page composition:
    • different look and feel per section, with old links redirected
    • Later, when The Guardian left the Java monolith, they migrated a vertical at a time again and used the Fastly CDN as the routing layer (the "new" system lasted almost 10 years)
    • REA Group (Australian property listings) has teams owning whole commercial or residential channels with different branding, which suits page composition.
  • Widget composition:
    • the first Guardian release was a single top-10 travel destinations widget spliced into old pages with Edge-Side Includes on Apache (Figure 3-19), a low-key, low-risk release
      • Today it is more often done in the browser, which has the benefit that one failed widget degrades only part of the page
      • Orbitz had UI modules (search form, booking form, map) served from one Content Orchestration service, a monolith causing delivery contention (Figure 3-20)
    • they delegated modules one at a time to new services, starting with editorial (Figure 3-21). Already-decomposed UIs with clear ownership make this easier
    • not every UI splits into widgets.
  • Mobile:
    • both major app stores vet each release, and a native app is itself a monolith users must download
    • Fix: change things server-side (embedded web views; Spotify defines layout declaratively on the server, with components backed by microservices, so views change without store submissions).
  • Micro frontends:
    • single-page apps (Vue, Angular, React) cannot use page composition
    • Web Components was slow to gain traction
    • people explore how to combine bits of different frameworks without dependency clashes. Out of scope for the book.
  • Where to use: migrates whole vertical slices, but you must be able to change the existing UI. Websites are easy; single-page apps add complexity.

3.4 Pattern: branch by abstraction

  • Strangler fig needs calls at the edge
    • For functionality deeper inside (Notification, Figure 3-4) you must change the monolith, and doing it on a long-lived branch causes painful merges and runs against continuous integration (the 2017 State of DevOps Report links trunk-based development and short-lived branches to higher performance)
    • Branch by abstraction lets old and new implementations coexist in the same version of the code.
  • Five steps, shown with Notification:
    1. Create an abstraction for the functionality (Figure 3-22): an Extract Interface refactoring if well factored, otherwise a seam; search for code that sends emails or SMSs.
    2. Use the abstraction: change clients incrementally (Figure 3-23), usually by tracking inbound calls manually; no functional change.
    3. Create the new implementation (Figure 3-24), which calls the new service; it is dormant (it can return Not Implemented) while the service grows, and the service can be deployed to production. This can last long: Jez Humble described a months-long iBatis to Hibernate switch in GoCD (then Cruise) while shipping twice weekly.
    4. Switch the implementation (Figure 3-25) with an easily toggled mechanism, commonly a feature toggle (Figure 3-26, configuration file; Pete Hodgson has a write-up) so you can switch back. Both implementations exist, so you can compare them with tests or in production (parallel run).
    5. Clean up: remove the old implementation (Figure 3-27) and the toggle (leftover feature flags are a real problem), and optionally the abstraction (Figure 3-28), which may have improved the code.
  • As a fallback mechanism:
    • Steve Smith's verify branch by abstraction (Figure 3-29) uses the old implementation if calls to the new one fail
    • Costs: more code, harder reasoning (both may be active), and consistent shared data if either is stateful, since you can switch per request.
  • Where to use:
    • changes that take time without disrupting colleagues
    • better than long-lived branches nearly always. Prefer strangler fig first, and note it requires changing the existing code.

3.5 Pattern: parallel run

  • Pre-release testing cannot cover everything
    • Strangler fig and branch by abstraction run old or new; parallel run calls both and compares, with one as the source of truth (the old, until the new is trusted)
    • It verifies correct answers and acceptable non-functional behaviour (latency, time-outs).
  • Credit derivative pricing:
    • at a bank, a replacement for the calculation platform ran side by side with daily reconciliation (a program and an Excel report)
    • A few real issues were found, plus many discrepancies caused by bugs in the old system, which meant explaining the correct results from first principles
    • After a month they switched the source of truth, and kept the old system a few months for audits
    • (Newman notes the financial industry was "terrible at this" and expresses regret about his part in it.) Homegate ran both listing importers together, then disabled the monolith's FTP import.
  • N-version programming: fly-by-wire aircraft use several implementations and pick the answer by quorum; unlike migration the aim is to keep them all.
  • Verification:
    • compare functional equivalence like pure functions, and check non-functional aspects
    • Spies (a testing pattern) stand in for a side effect such as sending an email so it is not done twice and can be verified afterwards (Figure 3-31)
    • A spy inside the monolith skips testing the remote call; an out-of-process spy complicates when you can verify (record interactions and verify out of band, perhaps daily)
    • The more you replace with a spy, the less you test
    • GitHub Scientist (Ruby, with ports to Java, .NET, Python, Node.js and others) helps run implementations side by side.
  • Dark launching and canary releasing:
    • a canary release sends some users to the new functionality
    • a dark launch deploys it invisibly
    • a parallel run is a way of dark launching. They are part of progressive delivery (James Governor's umbrella term).
  • Where to use: rarely trivial, so reserve it for high-risk functionality (Chapter 4 has a medical records example). Newman has used it once or twice.

3.6 Pattern: decorating collaborator

  • To trigger behaviour on something that happens inside the monolith without changing it, let the call through and then, based on the result, call your microservices: the decorator pattern, so the monolith appears to call the services.
  • Loyalty programme at Music Corp:
    • earn points when an order is placed. The monolith's order placement stays
    • a proxy intercepts, and on success calls the Loyalty service to add points (Figure 3-32). The proxy now has "smarts" and tunnels responses back
    • watch the complexity, because the more code, the more it becomes a technical microservice.
  • It needs enough information in the request or response. If the order value is not there, the service may call back into the monolith (Figure 3-33): extra load and a circular dependency
    • better to change the monolith to supply it, or use change data capture.
  • Where to use: keep it simple; it is more elegant and less coupled than change data capture when request or response has the data. If not, think hard.

3.7 Pattern: change data capture

  • React to changes in the datastore instead of calls. The capture system must be coupled to the monolith's datastore, which is unavoidable.
  • Loyalty cards:
    • at enrolment the monolith returns little (Figure 3-34), but a card needs more customer details, so detect inserts into the LoyaltyAccount table and fire a Loyalty Account Created event to the printing service (Figure 3-35)
    • printing works best in batch, so events queue in a broker.
  • Implementations (trade-offs in complexity, reliability, timeliness):
    • Database triggers
      • (Figure 3-36): custom behaviour on change (for example a call on INSERT)
      • no new software, but like stored procedures a slippery slope. Randy Shoup: one or two triggers is not terrible
      • building a whole system from them is. Tooling and change management suffer
      • use sparingly.
    • Transaction log pollers
      • (Figure 3-37): a separate process reads the database transaction log
      • only committed changes appear
      • no need to work out what changed
      • can run off a replica
      • but tools depend on the log format of each database. Many tools exist, some mapping log changes to messages. Generally the neatest.
    • Batch delta copier: a scheduled job (cron) scans for changed data and copies it. The hard part is knowing what changed (table-level metadata only, or you add timestamps).
  • Where to use:
    • useful for replicating data (Chapter 4)
    • In migration, the sweet spot is reacting to monolith data changes when you cannot intercept at the edge or change the code
    • Keep use minimal because trigger and log-based implementations add complexity.

Summary points

  • Combine patterns; most migrations need several.
  • Prefer the least invasive pattern that works: strangler fig, then branch by abstraction, with parallel run for risky parts.
  • Keep rollbacks possible: freeze behaviour, separate deploy from release, remove toggles afterwards.
  • Data was glossed over; Chapter 4 tackles it.
Terms to carry forward
  • Strangler fig, branch by abstraction, parallel run, decorating collaborator, change data capture, UI composition.
  • Seam; feature toggle; service mesh; content-based router; selective consumption.
