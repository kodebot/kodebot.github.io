Monolith to Microservices 4: Decomposing the Database

Source: Sam Newman, Monolith to Microservices (O'Reilly, 2019), chapter 4. Previous: Monolith to Microservices 3: Splitting the Monolith. Next: Monolith to Microservices 5: Growing Pains.

Takeaways
  • Microservices work best when they own their data, so you generally need to split the monolith's database. It is hard: synchronisation, logical versus physical separation, transactional integrity, joins and latency.
  • If you cannot split yet, cope without making it worse: a database view, a database wrapping service, or a database-as-a-service interface. Sharing a database directly is right only for read-only static reference data or a deliberately managed endpoint.
  • Move data with synchronize data in application or a tracer write (two sources of truth, eventual consistency, reconcile).
  • Splitting a table or foreign key means moving joins into code and deciding how to handle deletion; keep aggregates together.
  • Avoid distributed transactions (two-phase commit). Use sagas: a sequence of local transactions with compensating transactions, orchestrated or choreographed.

4.1 Pattern: the shared database

  • Of the coupling types from Chapter 1, implementation coupling dominates when services share a database (Figure 4-1)
    • The major problem:
      • you cannot decide what is shared and what is hidden, so you do not know what is safe to change, and it is unclear who controls the data and where the business logic lives
      • logic spreads across services, giving low cohesion
    • If three services can change order information inconsistently, changes must be applied everywhere.
  • Where sharing is appropriate: only
    • read-only static reference data (currency codes, postal code tables) with change control as an admin task, and
    • a service deliberately exposing a database as a defined endpoint for many consumers
  • But it cannot be done:
    • splitting is nearly always preferred but not always feasible at first (too long, or too sensitive)
    • Use coping patterns that stop things getting worse and act as stepping stones.
  • Schemas and databases:
    • a schema is a logically separated set of tables; several schemas can sit on one engine (Figure 4-2)
    • In this chapter "database" means a logically isolated schema
    • NoSQL stores may lack the concept (DynamoDB has only tables, with role-based access control).
Agree to fix it

You will meet problems that seem impossible now. Agree with the team that it is a problem to fix, and start doing the right thing from now on; with new skills and experience they become easier.

4.2 Pattern: database view

  • A view gives a service a limited projection of the underlying schema, hiding what it should not see.
  • The database as a public contract:
    • on a bank re-platforming project (credit derivatives) a restructured schema would have increased write throughput, but more than 20 applications (estimated from network calls) used shared credentials with read or even read/write access, so no one knew who they were
    • They disabled the shared account and waited for complaints
    • Most of those applications were not maintained, so the schema had become a contract that could not change.
    • Tip:
      • give each actor its own credentials so you can restrict, revoke and rotate per party and know what each does
      • dedicated secret stores such as HashiCorp Vault can generate short-lived, scoped per-actor database credentials.
  • Views to present:
    • first remove external writers
    • for readers, create a dedicated schema hosting views that look like the old schema (many stored procedures), and move clients to it (Figure 4-3). A simple use (Figure 4-4): a view exposing only customer ID and loyalty ID for the Loyalty service, hiding the rest of the Customer table.
  • Materialised views are precomputed (cached), faster but possibly stale.
  • Limitations:
    • usually read-only (a query result)
    • not all databases support them (Cassandra and Mongo do)
    • source and views often must be on the same engine (physical deployment coupling, possible single point of failure).
  • Ownership: treat published views like a service interface, kept up to date by the team owning the source schema.
  • Where to use: when full decomposition is impractical; try to avoid needing one if the goal is a service interface. It is a step in the right direction.

4.3 Pattern: database wrapping service

  • Hide the mess behind a thin service, so database dependencies become service dependencies (Figure 4-5).
  • Bank entitlements example:
    • a 30-year-old business banking system managed entitlements (which individuals may view or move how much in which companies' accounts) almost entirely in stored procedures
    • the database was buckling ("we've given all the money it's possible to give to Oracle") and untangling it was too risky (a wrong step could block access or grant access to the wrong person)
      • Plan: stop making it worse by introducing an Entitlements service (little behaviour at first, since stored procedures held the logic) so other teams treat the schema as someone else's and store their own data locally (Figure 4-6)
    • then extract the easier parts to reduce load.
  • Like a view, it controls what is shared
    • Advantages over a view: richer projections, code, and writes through the API
    • Cost: consumers must change from direct access to API calls
    • Works best when one team owns both schema and service layer
    • It makes stubbing in tests easier
    • Ideally a stepping stone; it could be called a bandage, but incremental improvement is the point.

4.4 Pattern: database as a service interface

  • Sometimes clients need a database to query (large amounts of data, or tools such as Tableau that need a SQL endpoint)
    • Keep the exposed database separate from the internal one: a dedicated read-only database populated when the internal data changes (Figure 4-7, the Orders service with a read/write API and a read-only database), fed by a mapping engine that works out what to change.
  • Fowler calls it the reporting database pattern; Newman uses a different name because reporting is only one use, and ad hoc queries have wider scope.
  • Mapping engine options:
    • change data capture (most robust and current, for example Debezium; Newman has been bitten by batch jobs not running or taking too long), a batch copy (longer lag, hard to know what to copy), or listening to events the service fires. It will lag behind writes, so consumers may see stale data
    • consider exposing when it was last updated.
  • Compared to views:
    • the exposed database can be a different technology (Cassandra inside, SQL outside); more flexible, more work
    • Start with a view and move later if needed
    • Fits reporting that joins large datasets, and can feed a data warehouse (see Building Microservices, Chapter 5)
    • Keeping it up to date can be complex.

4.5 Transferring ownership

  • So far we only bandaged. Decide where each piece of data should live: data for aggregates a service manages moves with it
    • data it only needs from the monolith is accessed through a well-defined interface.
  • Pattern: aggregate exposing monolith:
    • the new Invoicing service needs Employee data held in the monolith (Figure 4-8)
    • Expose it from the monolith via an API or event stream, which makes the need explicit
    • Treat the monolith as owning allowed state changes, exposing operations to query state and request transitions (not just a database wrapper)
    • It can reveal future boundaries: here an Employee service next (Figure 4-9)
    • Prefer this to a database view unless the monolith cannot change (then a view, change data capture or a wrapping service).
  • Pattern: change data ownership:
    • invoice data should move into the Invoice service, with the monolith calling it as the source of truth (Figure 4-10)
    • Untangling means breaking foreign keys and transaction boundaries
    • If the monolith only reads invoice data, you could project a view from the service's database (Figure 4-11), but calling the service is greatly preferred
    • Clear-cut: if the new service holds the logic that changes the data, the data should move.

4.6 Data synchronisation and migration patterns

  • The strangler fig lets you switch back, but if the service manages data that both the monolith and service use (Figure 4-12), both must see it consistently
    • If either needs total consistency, keep the data in one place: the service reads the monolith data directly for a very short time (perhaps via a view), then migrate with change data ownership
    • A big-bang batch copy loses state on fallback.

Pattern: synchronize data in application

  • Trifork and Danish medical records:
    • a consolidated view of Danish citizens' medical records moved from MySQL to Riak for scale and resilience, with little tolerated downtime and no data loss
    • The application itself kept the two in sync:
    1. Bulk synchronise a snapshot (the source kept running), then apply changes since the import with change data capture (Figure 4-13).
    2. Synchronise on write, read from the old schema (Figure 4-14): write to both, read from MySQL, so a Riak failure loses nothing.
    3. Synchronise on write, read from the new (Figure 4-15): Riak is the source of truth, still writing to both for fallback.
    4. Once it has bedded in, remove the old schema.
  • For monolith and microservice, it suits splitting the schema before the code (Figure 4-16: the monolith writes to two schemas), with fast switching for rollback
    • If both the monolith and the service must keep both schemas in sync (Figure 4-17) it gets complex: workable if only one writes at a time (simple switchover), not if requests can hit either (a canary).

Pattern: tracer write

  • Arguably a variation of the above
    • Move the source of truth incrementally, tolerating two sources during migration (Figure 4-18)
    • The old system keeps a local copy and also writes through the new service's interface
    • consumers move over
    • then the old source is retired
      • Newman values a single source of truth but notes insisting on it forces a big-bang switchover
      • It is called a "tracer" because you start with a small set of data and grow it and its consumers: basic invoice data, then contact information, then payment records (Figure 4-19)
      • In Figure 4-20 the monolith starts reading from the service for more and more data.
  • Synchronisation options:
    • write to one source and synchronise afterwards
    • send writes to both (client calls both, or an intermediary broadcasts)
    • or accept writes at either with two-way sync, which should be avoided because it is very hard
      • There is always a window of inconsistency: a nightly batch can be 24 hours stale, streaming change data capture seconds or less
      • This is eventual consistency
    • choose the tolerable window.
  • Warning: keep a reconciliation process (even a couple of SQL queries on each side); run the new source with no consumers for a while (as Square did).
  • Square orders:
    • one Order concept bound three workflows (customer, restaurant, delivery driver) causing delivery contention
      • They created a Fulfillments service for restaurant and delivery data (Figure 4-21)
    • a background worker copied existing data via the service's API (not direct inserts), controlled by a feature flag removed once trusted
      • Updates then went to both systems through API calls (Figure 4-22)
    • callers handle partial failure, creating a brief eventual consistency window that did not matter here (only changes delivery or restaurant clients care about are copied)
      • With an event-driven system both could subscribe to the same events (Figure 4-23), still eventually consistent
      • Consumers then migrated, which was "pretty much a non-event"
    • more functionality was added as needed
      • Derek Hammer (who shared this) would ideally split Fulfillments further (restaurants and delivery drivers are different bounded contexts)
      • Square kept the duplicated data so restaurant and delivery information stays visible if the Fulfillments service is down
    • this may be revisited.
  • Where to use:
    • the synchronisation is most of the work
    • avoid two-way sync
    • existing event-driven systems or change data capture make it easier
    • the shorter the tolerated inconsistency the harder.

4.7 Splitting apart the database

  • Physical versus logical separation
    • (Figures 4-24, 4-25): logical decomposition gives independent change and information hiding; physical gives robustness and less resource contention
    • Several schemas on one engine is a single point of failure, though clusters, multi-primary modes and warm failover exist, and one resilient cluster may be cheaper than many (licence fees)
    • Views need the same engine
    • You need logical decomposition first.
  • Sequencing:
    • an extraction is not done until the code runs in its own service and its data is in its own isolated database
    • Options: split the database first, split the code first, or both at once.
    • Split the database first
      • (Figure 4-26): more calls (joins in memory), lost transactional integrity
      • but you can revert or tweak without affecting consumers and spot performance and consistency problems early. Little short-term benefit (a pain felt over time)
      • not available for black-box monoliths.
    • Split the code first
      • (Figure 4-29): what most teams do
      • short-term improvement and clearer data needs
      • but teams may stop and leave a shared database ("storing up trouble"; JustSocial finished the job), and nasty join surprises are delayed.
    • Both at once (Figure 4-33): a bigger step, slower feedback; avoid.
    • Newman's hot take:
      • if you can change the monolith and worry about performance or data consistency, split the schema first
      • otherwise split the code and use that to learn data ownership.
  • A note on tooling:
    • databases lack refactoring tools and are stateful. Newman co-created DBDeploy (now defunct) with Nick Ashley and Graham Tackley (versioned SQL delta scripts with a tracking table)
    • now use Flyway or similar, capturing each change as a version-controlled delta script.

Preparation patterns

  • Repository per bounded context
    • (Figure 4-27): split repository (Hibernate-style) code by bounded context so you can see which context touches which tables. It misses database-level constraints such as foreign keys
    • SchemaSpy draws table relationships.
  • Database per bounded context
    • (Figure 4-28): give each context its own schema even within one deployable
      • ThoughtWorks' revenue forecasting (Peter Gillard-Moss) built three isolated contexts as JAR files with separate databases
    • it was never split and stays a modular monolith. It hedges your bets
    • Newman nearly always recommends it for new systems, and avoids microservices for startups because the domain is not understood yet.
  • Monolith as data access layer
    • (Figure 4-30, from Susanne Kaiser of JustSocial): add an API in the monolith (Employee API) so the Invoice service does not bind to its data
    • avoids data decomposition for now, and may reveal an Employee service (Figure 4-31). Use it when the code managing that data should stay in the monolith
    • if the data should be owned by the service, split the data instead. It is under-used because people think of the monolith as dead.
  • Multischema storage
    • (Figure 4-32): do not make things worse: new data a service needs (for example invoice reviewers) goes into the service's own schema while the old data stays in the monolith, then migrate table by table
    • Combine with monolith as data access layer for data you never plan to move
    • A foreign key now spans schemas (next).

4.8 Schema separation examples

  • Relational examples are used; the ideas mostly apply to NoSQL too, perhaps with fewer constraints.

Pattern: split table

  • A table spanning two bounded contexts (Item holding catalogue data and stock levels, Figure 4-34) is split into two tables, first inside the schema, then across schemas (a foreign key between them would not be enforced across databases).
  • A column updated by several code areas (Customer Status:
    • NOT_VERIFIED to VERIFIED at sign-up, SUSPENDED by finance
      • Figure 4-35): it belongs to the customer's state machine, so the Customer service owns it and the Finance service calls it (Figure 4-36)
    • You lose database transactions
    • Decide who owns shared data by the domain concept.

Pattern: move foreign-key relationship to code

  • Ledger rows reference Albums by SKU (Figure 4-37); the monthly best-seller report joins them, and the database enforces consistency and optimises the join. After the split:
    • Moving the join
      • (Figure 4-38): Finance queries its Ledger for SKUs and sales, then asks Catalog for details (bulk lookup, or cached locally)
      • Latency will rise; it may be acceptable (monthly report, cacheable)
      • Measure with tracing (Jaeger) against what is acceptable.
    • Data consistency: the schema no longer prevents deleting an album still referenced.
      • Check before deletion: racy (a reference appears during deletion), needs locks, and creates a reverse dependency on every consumer. Newman urges you not to.
      • Handle deletion gracefully:
        • Finance shows "Album Information Not Available"
        • Catalog returns 410 GONE (it existed) rather than 404
        • or Finance subscribes to deletion events and copies the data.
      • Do not allow deletion: soft delete with a status column, or move rows to a "graveyard" table (event sourcing if you have heavy historical needs).
    • Newman would do both of the last two, because a Catalog restored from an earlier state could lose a record and Finance should not fall over.
  • Where to use:
    • first make sure you are not breaking an aggregate in two: Order and Order Line should move together (the lines are part of the order)
    • Sometimes a bigger bite lets you take both sides of the foreign key.

Example: shared static data

  • Country codes (Figure 4-39) show up in many databases; there are options:
    • Duplicate the data
      • (Figure 4-40): each service has its own copy
      • Concerns: changing many places (the last new country was South Sudan, code SSD, in 2011) and inconsistency
      • It matters only if the data is part of communication between services; for local use inconsistency is fine
      • Duplication may be the lesser evil if it avoids coupling
      • Use rarely (maybe large volumes such as UK postal code files).
    • Dedicated reference data schema
      • (Figure 4-41): one source of truth, a versioned interface, joins possible on one engine (extra mapping and single point of failure concerns)
      • breaking changes hurt.
    • Static reference data library
      • (Figure 4-42): small, rarely changing data (249 ISO country entries) in a shared library or config file
      • Stitch Fix does this for things like clothing sizes (Randy Shoup: the sweet spot is small volume and infrequent change with warning)
      • Drawbacks: mixed technology stacks, and updating means redeploying all services (lock-step release); accept that versions can differ in production (Figure 4-43), which is visible.
    • Static reference data service
      • (Figure 4-44): splits rooms: those who find creating a service cheap say yes
        • where a new service takes days or weeks (Kief Morris's UK bank needed nearly a year and over 10 teams to approve a first release) it looks like overkill
      • 249 entries can be held in memory without a datastore, fit a function-as-a-service platform (Azure Functions, AWS Lambda), and be cached client-side or refreshed by update events (Figure 4-45)
      • Use it when you manage the data's life cycle in code (an update API, events) or want a stub-friendly contract.
  • Newman's choice:
    • a shared library if consistency at all times is not needed
    • larger or more complex data in each service's local database
    • a dedicated service if the data must be consistent
    • a dedicated schema only if a service is hard to justify. See Refactoring Databases (Scott J. Ambler and Pramod J. Sadalage).

4.9 Transactions

  • Splitting databases breaks referential integrity, adds latency and complicates reporting, and loses the transaction.
  • ACID:
    • atomicity (all or nothing), consistency (valid state), isolation (interim states invisible to other transactions), durability (completed work survives failure)
    • Not all databases provide it (relational ones do, Neo4j does; MongoDB supported it only for a single document for years, and added multi-document ACID transactions in 4.0)
    • Recommended: Designing Data-Intensive Applications
    • The chapter focuses on atomicity.
  • Still ACID, but lacking atomicity:
    • in one database, setting a customer's status to VERIFIED and deleting the PendingEnrollments row is one transaction (Figure 4-46)
    • Across two databases they are two independent transactions (Figure 4-47)
    • Sequencing helps but the whole operation is no longer atomic
    • Reordering steps will matter for sagas.

Two-phase commits

  • A voting phase (the coordinator asks all workers if the change can be made; Figure 4-48) and a commit phase (Figure 4-49)
    • A yes is a promise to make the change later, usually by locking the record
    • If any vote no, a rollback is sent so workers release locks.
  • Problems:
    • commits are not simultaneous, so you can see one change before the other (isolation lost)
    • it is essentially coordinating distributed locks
    • many failure modes (a worker votes yes then does not respond to the commit) can need manual unpicking
    • more participants and latency mean more trouble
    • used only for short operations because resources stay locked.
  • Distributed transactions, just say no:
    • avoid them
    • First option: do not split data that needs atomicity yet (keep it in one database and one service, and work on another area)
    • Otherwise, sagas.

4.10 Sagas

  • A saga coordinates several state changes without locking resources for long, by modelling the steps as discrete independently executed activities, and it forces you to model the business process explicitly
    • Originally from Hector Garcia-Molina and Kenneth Salem (1987) for long-lived transactions (minutes, hours, days): split into a sequence of shorter transactions that each touch part of the data, reducing lock contention
    • It works for coordinating several services too.
  • A saga does not give ACID atomicity
    • for the whole. Each step can be a local ACID transaction (the Warehouse service creates a Reservation row in its own transaction, Figure 4-50), and the saga gives enough information to know what state it is in
    • handling the implications is up to you.
  • Failure modes:
    • backward recovery (roll back with compensating actions) and forward recovery (retry from the failure point, needing persisted state)
    • Mix as the process requires.
  • Rollbacks:
    • if packaging finds the item missing after payment and points were awarded (Figure 4-51), there is no simple rollback
      • trigger a compensating transaction for each committed step (Figure 4-52)
    • These are semantic rollbacks: the originals did happen (you cannot unsend an email, so send a second email saying the order was cancelled)
    • Keeping a record of the aborted order is appropriate.
  • Reordering steps: award points only at dispatch (Figure 4-53); pull forward steps likely to fail so later compensations are not needed.
  • Mixing: once money is taken and the item packed, rolling back for a dispatch failure is odd; retry, then human intervention.

Implementing sagas

  • Orchestrated sagas:
    • a central orchestrator defines the order and triggers compensations (command and control), usually with request and response calls
      • in the order example an Order Processor (Figure 4-54) calls Payment Gateway, Warehouse and others
    • Benefits: the process is explicit in one place, easier onboarding and tracking
    • Downsides: domain coupling (it must know all the services) and logic being absorbed into the orchestrator, leaving anaemic services
    • "If logic has a place where it can be centralized, it will become centralized!" Mitigate by using different orchestrating services for different flows (Order Processor, Returns, Goods Receiving), all reusing Warehouse.
    • BPM tools:
      • Newman dislikes them: the central conceit that non-developers define the process is almost never true; GUI-based flows are hard to version or test
      • Let developers write code and project a visual view from it
      • Open source developer-oriented orchestration frameworks: Camunda and Zeebe.
  • Choreographed sagas:
    • responsibility is spread (trust but verify)
    • services react to events broadcast through a message broker topic (Figure 4-55: Order Placed, then Warehouse reserves stock and fires an event; Insufficient Stock aborts the order)
      • Many services (a Recommendation service) can react to the same event
      • No service knows another, so it is loosely coupled with no central logic
    • but the process is implicit and saga state is hard to know
      • Fix: a correlation ID (the saga's unique ID) in every event and a service that consumes the events and projects each order's state, perhaps acting to resolve issues.
  • Mixing styles is fine (an orchestrated flow inside Warehouse within a larger choreographed saga), but keep a clear way to understand what happened.
  • Which?
    • Newman finds the extra tracking complexity of choreography almost always outweighed by looser coupling. General advice: relaxed about orchestration when one team owns the whole saga
    • prefer choreography with several teams, so responsibility can be distributed.
  • Sagas versus distributed transactions:
    • Pat Helland ("Life Beyond Distributed Transactions"):
      • in most distributed transaction systems the failure of one node stalls the commit, so the larger the system the more likely it is down
      • like adding an engine to a plane that needs all engines
    • Modelling processes as sagas avoids this and makes processes first class
    • Further reading: Building Microservices chapter 4 and Enterprise Integration Patterns (sagas are not named in either)
    • Nested sagas (Garcia-Molina et al, 1991) are out of scope.

Summary points

  • Find seams along which boundaries emerge; the work is painstaking but can be incremental.
  • Cope first (view, wrapper, exposed database), then move ownership, then sync with tracer writes or application sync, with reconciliation.
  • Replace joins and foreign keys with calls and graceful handling; replace transactions with sagas.
  • Next: the problems that appear once you have many services (Chapter 5).
