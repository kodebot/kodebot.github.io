OWASP Top 10:2025 2: A04 to A06

Source: OWASP Foundation, "OWASP Top 10:2025" (owasp.org/Top10/2025), categories A04 Cryptographic Failures, A05 Injection and A06 Insecure Design; the owasp.org page footer states a Creative Commons Attribution 3.0 Unported licence. Own-words summary. Previous: OWASP Top 10:2025 1: Overview and A01 to A03. Next: OWASP Top 10:2025 3: A07 to A10.

Takeaways
  • Cryptographic failures: missing, weak or leaked cryptography. Use TLS 1.2 or higher with forward secrecy, strong adaptive password hashing, authenticated encryption, and proper key management.
  • Injection: untrusted input reaches an interpreter as a command. Fix it by keeping data separate from commands with parameterised interfaces.
  • Insecure design: missing or ineffective control design. A perfect implementation cannot fix a design that never included the control; threat model and use secure patterns.

2.1 A04:2025 Cryptographic Failures (#4)

  • What:
    • lack of cryptography, insufficiently strong cryptography, leaked keys and related errors
    • Common CWEs involve weak random number generators and broken or risky algorithms
    • It often leads to sensitive data exposure or system compromise.
  • Context:
    • all data in transit should be encrypted at the transport layer
    • modern CPUs accelerate encryption and services such as Let's Encrypt and cloud certificate managers ease certificate handling. Decide what data also needs encryption at rest or extra application-layer protection (passwords, card numbers, health records, personal data, business secrets), especially under privacy laws such as GDPR or PCI DSS.
  • Ask yourself:
    • Are old or weak algorithms or protocols used?
    • Are default keys, weak keys, reused keys or missing rotation present, or keys checked into repositories?
    • Is encryption enforced (security headers), and are server certificates and the trust chain validated?
    • Are initialisation vectors ignored or reused, an insecure mode such as ECB used, or encryption used where authenticated encryption is needed?
    • Are passwords used as keys without a key derivation function, or non-cryptographic randomness or hashes (MD5, SHA1) used?
  • Prevent:
    • Classify data; do not store sensitive data you do not need (tokenise or truncate); keep sensitive keys in an HSM or cloud HSM.
    • Use well-trusted implementations; encrypt all sensitive data at rest; manage keys properly.
    • In transit: TLS 1.2 or higher only, forward-secrecy ciphers, drop CBC ciphers, HSTS for HTTPS; no unencrypted FTP or STARTTLS; avoid SMTP for confidential data.
    • Disable caching of sensitive responses (CDN, web server, Redis and so on).
    • Passwords: Argon2, yescrypt, scrypt or PBKDF2-HMAC-SHA-512 with a work factor (see the OWASP Password Storage cheat sheet for bcrypt on legacy systems).
    • Never reuse an IV with the same key
      • always use authenticated encryption
      • generate keys randomly and derive them from passwords only with a proper function
      • avoid MD5, SHA1, CBC and PKCS#1 v1.5.
    • Have settings reviewed by specialists or tools, and start preparing for post-quantum cryptography.

2.2 A05:2025 Injection (#5)

  • What:
    • untrusted input goes to an interpreter (browser, database, command line) and is executed as part of a command
    • All tested applications were tested for some injection; this category has the most CVEs (cross-site scripting: high frequency, lower impact; SQL injection: lower frequency, high impact)
    • Prompt injection in language models is covered separately in the OWASP LLM Top 10.
  • Vulnerable when:
    • input is not validated or sanitised
    • dynamic queries or non-parameterised calls are used without context-aware escaping
    • unsanitised data is used in ORM search parameters
    • hostile data is concatenated into SQL, commands or stored procedures.
  • Kinds: SQL, NoSQL, OS command, ORM, LDAP, expression language and OGNL injection.
  • Detect with source code review combined with automated testing (including fuzzing) of all inputs (parameters, headers, URL, cookies, JSON, SOAP, XML), and SAST, DAST and IAST in CI/CD.
  • Prevent:
    • Preferred: a safe API that avoids the interpreter or is parameterised, or an ORM. Even parameterised stored procedures can still be injectable if they concatenate queries and data.
    • When separation is impossible:
      • positive server-side validation (not a complete defence) and escaping for the specific interpreter
      • Table and column names cannot be escaped, which is a common problem in report-writing software
      • These techniques are error-prone.

2.3 A06:2025 Insecure Design (#6)

  • What:
    • "missing or ineffective control design"
    • Design flaws and implementation defects differ in cause, timing and fix
    • A secure design can have bugs; an insecure design cannot be fixed by perfect code because the control was never designed
    • A contributing factor is skipping business risk profiling, so nobody decides how much security the system needs
    • Industry improvement in threat modelling and secure design has moved it down two places.
  • Three parts of secure design: gathering requirements and managing resources (protection needs for confidentiality, integrity, availability and authenticity; how exposed the application is; tenant segregation; budget for security work), creating a secure design (a culture of continually evaluating threats, with threat modelling in refinement sessions and failure states agreed up front), and a secure development lifecycle.
  • Prevent:
    • Use a secure development lifecycle with application security specialists.
    • Maintain a library of secure design patterns or "paved road" components.
    • Threat model critical parts (authentication, access control, business logic, key flows), also as a training tool.
    • Put security language and controls into user stories; add plausibility checks at every tier.
    • Write unit and integration tests for critical flows, with use cases and misuse cases for each tier.
    • Segregate tiers at system and network level by exposure; segregate tenants robustly through all tiers.

Summary points

  • Pick strong, standard cryptography and protect the keys more than the data.
  • Never build commands by joining strings with input; use parameters.
  • Design the control in before you code it; test the misuse case.
Terms to carry forward
  • Forward secrecy: past sessions stay safe even if a long-term key leaks later.
  • Authenticated encryption: encryption that also detects tampering.
  • Parameterised query: command and data sent separately.
  • Misuse case: a test of how an attacker might abuse a feature.
  • Paved road: pre-approved secure components teams can reuse.
