Podman for DevOps 1: Introduction to container technology

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, February 2026), ch. 1. Read through O'Reilly: https://learning.oreilly.com/library/view/podman-for-devops/9781835886625/. Next: Podman for DevOps 2: Comparing Podman and Docker.

Takeaways
  • A container is an isolated process, not a virtual machine: it shares the host kernel and is isolated by Linux namespaces (what it sees) and cgroups (what it may use).
  • Images (read-only, layered, copy-on-write, OCI standard) make containers portable; a running container adds a thin ephemeral read/write layer, so data lives outside it.
  • Engines (Podman, Docker, CRI-O, containerd) take user requests; runtimes (runc, crun) start the process. They are separate, swappable pieces.
  • Containers are not automatically more secure: add SELinux or AppArmor, capabilities and seccomp.
  • The lineage runs chroot (1979), FreeBSD jails (2000), Solaris Zones (2004), LXC (2008), Docker (2013), OCI (2015), Podman (2017), which is daemonless and supports rootless containers.

The chapter answers four questions: what containers are, why you need one, where they come from, and where they are used today. It needs no setup. A shell prompt $ means a standard user, # means root, and \ continues a long command onto a new line.

1.1 What are containers?

Process basics first

  • A process is an instance of an executing program (the book cites Michael Kerrisk, The Linux Programming Interface). A program is a file; it can link libraries dynamically or statically (Go links statically by default).
  • A process runs on the CPU in user space with its own memory. To reach disks, network or terminals it makes a system call into the kernel.
  • It touches storage through a filesystem, a multi-layer abstraction. The kernel scheduler shares CPU cores across many processes.
  • Running several versions of one program on a host makes the administrator manage conflicts: ports, binaries, libraries, dependencies.

A container is a form of application isolation on six levels:

Isolation What the containerised process gets
File system its own filesystem view; programs run from it
Process ID an independent set of PIDs
User its own UIDs and GIDs; privileged inside the container only
Network separate devices, IPv4 and IPv6 stacks, routing tables, firewall rules
IPC separate POSIX message queues and System V IPC objects
Resource usage limits and monitoring through Linux cgroups (CPU, memory, disk)

Without containers, native applications share binaries, libraries, kernel, filesystem, network and users, so a new version can hit conflicting libraries or unmet dependencies (Figure 1.1). Containers let a new deployment just run the new containerised version beside the others.

Namespaces

Namespaces abstract a system resource so the process believes the isolated copy is the host's. There are eight kinds:

Namespace Isolates
Mount the list of mount points
PID process IDs (two namespaces can reuse the same PID)
User UIDs, GIDs, root directory, keyrings, capabilities (root inside, unprivileged outside)
UTS hostname and NIS domain name
Network devices, IP stacks, routing tables, firewall rules, port numbers; veth pairs tunnel between namespaces
IPC System V IPC objects and POSIX message queues
cgroup cgroup directories (a virtualised view)
Time system time, so a process can run with an offset from host time

Resource usage with cgroups

  • cgroups organise processes in a hierarchical tree and limit or monitor their resources. The interface is the cgroupfs pseudo-filesystem, usually mounted at /sys/fs/cgroup (like /proc).
  • Controllers (subsystems) limit CPU share, memory, or freeze and resume processes.
  • v1 vs v2:
    • v1 mounts different controllers on different hierarchies.
    • v2 has one unified hierarchy, with processes in leaf nodes.
    • v1 is being deprecated, though some distributions keep it for compatibility.
  • Containers use cgroups for a CPU quota (microseconds of CPU per period) or CPU shares (a weighted proportion of cycles).

Running isolated processes by hand

Linux offers everything needed through the unshare() and clone() system calls and the unshare command. A shell in its own PID namespace:

# unshare --fork --pid --mount-proc /bin/sh

Inside it ps aux shows the shell as PID 1, the first process of the new namespace:

sh-5.0# ps aux
USER PID %CPU %MEM VSZ    RSS  TTY   STAT START TIME COMMAND
root 1   0.0  0.0  226164 4012 pts/4 S    22:56 0:00 /bin/sh
root 4   0.0  0.0  227968 3484 pts/4 R+   22:56 0:00 ps aux

Only the PID namespace is isolated; everything else is still the host's. Adding --net isolates the network stack too:

# unshare --fork --net --pid --mount-proc /bin/sh

sh-5.0# ip addr show
1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN group default qlen 1000
link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00

The host's network devices are no longer visible. Lesson: containers are built from native Linux features, and a container runtime abstracts that complexity. Mount isolation is the most important piece.

Isolating mounts

  • To avoid binary and library conflicts a process needs its own directory tree (binaries and libraries of choice), built from mount namespaces plus bind mounts. Mount namespaces arrived in 2002 with Linux kernel 2.4.19.
  • Doing this by hand is hard: you extract archives of directory trees from different distributions and bind mount them into separate namespaces. Early Linux containers worked this way.

Container images

  • Docker introduced the clever storage method; images later became the Open Container Initiative (OCI) image specification (https://github.com/opencontainers/image-spec).
  • An image is a filesystem bundle pulled from an image registry (specialised object storage for image data and metadata) and unpacked before the first run. Public free registries include quay.io and docker.io; private ones run on-premises or in the cloud.
  • Images are built from a Dockerfile (the recipe). Multi-stage builds compile source in a first stage with a full toolchain, then copy only the artifacts into a minimal second-stage image for fast startup and small size (Figure 1.2). Built images are pushed to registries.
  • Why images matter: a self-consistent package deployable anywhere with no further software dependencies, the answer to "it works on my machine". Developers know their execution environment; operations stop maintaining a server's library dependencies.
  • Layers: an image is many tar archives called blobs or layers, composed by metadata into one filesystem view, usually through a union filesystem.
    • OverlayFS (https://www.kernel.org/doc/html/latest/filesystems/overlayfs.html) is the most used; it lives in the kernel tree, though not fully POSIX-compliant.
    • It combines an upperdir stacked on a lowerdir; the unified view is merged. It supports up to 128 layers. It knows nothing about images; it is only the foundation.
  • Immutability: all image layers are read-only. To change a lower layer, rebuild the image. In cloud computing an instance, container or cluster is replaced by a new version, never modified, so we do not install packages or edit config inside a running container, and all copies stay in sync.
  • When a container runs, a thin read/write layer is added on top; it is ephemeral and lost when the container is destroyed (Figure 1.3). So store nothing inside containers: use bind mounts or network storage (NFS, S3, iSCSI).

Security considerations

A process in a container is not inherently more secure; an attacker may still reach host filesystem and memory. Extra features:

Feature Role
Mandatory access control (SELinux, AppArmor) policy-based isolation of filesystem and network access against the host
Capabilities independently enabled privileges for an unprivileged process (effective UID not 0); a container run can add or drop them
Seccomp (secure computing mode) a kernel feature restricting the syscalls a process can make; profiles shrink the attack surface

Applying these by hand has a learning curve, so tools that automate them declaratively add value. Chapter 10 covers security in depth.

Container engines and runtimes

Running and securing containers manually does not reproduce or automate well and causes configuration drift between hosts. Engines and runtimes exist for that, and the two are often confused:

Container engine Container runtime
Role accepts user requests and orchestrates everything needed for a container the lower-level piece that actually runs the containers
Does CLI and/or REST interface; pulls and extracts images; manages the mount point and bind-mounts the extracted image; handles metadata; calls the runtime starts the process at the target mount point with metadata; manages cgroup resource allocation; manages MAC policies (SELinux, AppArmor) and capabilities
Examples Docker (best known, not the first), Podman, CRI-O, containerd, LXD runc (most common), crun, kata-containers, youki, gVisor
  • The engine also creates the thin R/W layer and presents the merged directory stack to the runtime.
  • Most runtimes follow the OCI runtime spec (https://github.com/opencontainers/runtime-spec), an industry standard for runtime behaviour and interface.
  • Swappable runtimes, a real example: Fedora 33 introduced the cgroups v2 hierarchy; runc did not initially support it, so Podman simply swapped in crun, which did. Now runc supports cgroups v2, so Podman can use it again with no impact on users.

Containers versus virtual machines

Containers are not virtual machines. A containerised process talks to the host kernel directly through system calls (it may be unaware of host namespaces, but still context-switches into kernel space for I/O). A VM runs on a hypervisor with its own guest OS, filesystem, network, storage (usually image files) and kernel; its system calls go to the guest kernel (Figures 1.4 and 1.5).

Container Virtual machine
Kernel shared with the host own guest kernel
Security isolation refined features and strict policies (CIS Docker, NIST, HIPAA); hard to exploit stronger by default, though CPU attacks (Spectre, Meltdown) can reach VM address spaces
Startup milliseconds if the image is on the host (no kernel to boot) boots kernel and initramfs, pivots to root filesystem, runs init (systemd) and services
Resources lighter more RAM, CPU and storage for the guest OS
Workloads one container per workload (best practice) several workloads together

Example (LAMP or WordPress): a small environment might run Apache, PHP, MySQL and WordPress on one VM. As containers this splits into a front-end container (Apache, PHP, WordPress) and a MySQL container with a volume for the database files; the front end scales up and down easily.

Virtual machines in containers

  • Traditionally containers ran inside VMs. Tools such as KubeVirt reverse that: VMs inside containers, managed by Kubernetes.
  • Why: run legacy software that suits VMs beside container applications on one platform, add an isolation layer, and have Kubernetes manage both.
  • QEMU emulates hardware so the VM thinks it has its own machine; KVM (a kernel module) lets VMs use the server's hardware directly, speeding QEMU up.

Bootable containers

  • Powered by the open source project bootc: a specialised container image holding a complete OS (kernel, libraries, system tools) that can be booted directly like a traditional OS, and is OCI compliant.
  • Benefits: more isolation and control than application containers; no hypervisor or guest OS, so faster boot, lower memory use, better performance. Fits embedded systems, edge computing, specialised machine-learning servers.
  • Podman Desktop has a bootable-containers extension for building and managing them.

1.2 Why do I need a container?

Companies watch ROI while keeping TCO under control; containers help on both. The book gives seven reasons:

Reason What it means
Open source the technology is open source and open standards; community-driven, inspectable (transparency aids robustness and security); only the best software gets adopted
Portability an image runs on any host with a container engine, whatever the distribution (a CentOS or nginx image pulls on Fedora or Debian and behaves the same); reduces vendor lock-in
DevOps facilitators ends "it works on my machine"; developers get self-consistent bundles, operations stop managing dependency constraints or one VM per application; developers become aware of the OS layer in their image and work with operations on build templates
Cloud readiness built around immutability: redeploy a modified image, never patch in place; build pipelines go from build and image creation through registry push and tagging to deployment; Kubernetes (chapter 14) automates scheduling at scale
Infrastructure optimisation lighter than VMs, so containerised servers pack onto fewer hosts with resource limits and requests; a bare-metal hypervisor can become a container worker node
Microservices one container per fine-grained service: independent scaling, clearer team responsibilities, different technology stacks, finer security control (public exposure, mTLS); orchestration needs Kubernetes, a service mesh (Istio, Linkerd) and tracing (Jaeger, Kiali)
AI/ML isolate Jupyter notebooks in custom environments; fine-tune a foundation model in a container training pipeline; serve models through inference APIs in dedicated containers (MLOps)

Monolithic applications fit containers; microservices are the ideal match.

1.3 Where do containers come from?

Year Milestone What it added
1979 chroot (Unix V7); added to BSD in 1982 change the root directory of a process and its children so it cannot reach files outside the subtree; not built for security and discouraged as an isolation mechanism
2000 FreeBSD jails built on chroot; virtualises networking, users and processes too (four features below); each jail has its own users and root with no power over other jails or the host
2004 Solaris Containers (Zones) a virtualised application environment helped by ZFS (snapshots, cloning); branded zones can hold different binaries or even a different OS; own networking, users, time zone
2008 Linux Containers (LXC) first complete Linux container manager; its authors built many kernel features other runtimes use; goal: VM-like isolation without hardware simulation or a new kernel; unprivileged containers by mapping container UID 0 to a high host UID
2013 Docker first used LXC; a year later libcontainer replaced it; needs a daemon; brought OverlayFS, container images, registries and the Dockerfile
2014 to 2015 rkt (CoreOS, later bought by Red Hat) daemonless: each container is an ordinary process; CNCF adopted it in 2017; discontinued after the Red Hat acquisition, but influenced Podman
2015 to 2017 OCI and CRI-O OCI formed in 2015 under the Linux Foundation (Docker with Red Hat, AWS, Google, Microsoft, IBM); runtime spec and image spec; first runtime runc; Kubernetes CRI plugin interface; CRI-O (Red Hat, 2017) is a lightweight CRI implementation
2017 Podman first commit in 2017; name = POD MANager
  • FreeBSD jail features: directory subtree (as chroot), an independent IP address, hostname, and the command to run (path relative to the jail). A jail can be created from binary (like the host OS) or from source (built from scratch for the application). FreeBSD itself dates from 1993, derived from BSD.
  • LXC kernel functions: namespaces, mandatory access control, cgroups. SELinux was developed by the US National Security Agency (NSA) and adds role-based access control and multi-level security through labels (security contexts) on every file, device and directory.
  • containerd: the Docker team extracted the core runtime from the daemon and donated it to the CNCF.
  • Kubernetes ("helmsman" in Greek, K8s) was open sourced by Google and is maintained by the CNCF.
  • Pod: the smallest deployable unit in Kubernetes, one or more containers scheduled together with a shared context.

Podman in brief

  • Manages containers, images, volumes and pods, built from scratch to follow OCI standards.
  • No central daemon: containers start as standard system processes. A Docker-compatible CLI eases migration.
  • Rootless containers: a normal user can run restricted containers with no privileges beyond that user's, with no OS-level setup by an administrator.
  • Release milestones:
    • 3.0: Docker Compose support.
    • 4.0: new network stack from Netavark and Aardvark.
    • 5.0: rewritten Podman Machine (needed on macOS and Windows) and a new rootless network stack based on pasta.
  • CNCF: Red Hat announced in late 2024 the intent to donate Podman, Podman Desktop, Buildah, Skopeo, bootc and composefs; they joined the CNCF Sandbox in January 2025.

1.4 Where are containers used today?

  • Adoption spans every business sector, from automotive to healthcare, speeding project delivery. Companies move new applications from the VM model to containers.
  • Evolution: first a packaging method for monolithic runtimes; then the cloud-native wave (build and deploy scalable apps in public, private or hybrid clouds) and microservices made containers the de facto packaging standard. Kubernetes added service meshes and serverless for microservice architecture (MSA, loosely coupled fine-grained services over lightweight protocols).
  • Example web store (Figure 1.6): mobile or browser clients reach three decoupled services over a REST API; each service has its own database, making them independent in development and deployment. One container per service plus Kubernetes completes the solution, each with a base image containing just the runtimes it needs.
  • CI/CD (continuous integration and delivery or deployment) automates build, test and run, and containers fit it naturally.
  • Containers were born for system administrators but became the developers' favourite, linking dev and ops and speeding DevOps (practices linking Dev and Ops to shorten the application life cycle and release more often).
  • Legacy workloads too: enterprises with proprietary virtualisation face hardware, licences, expertise, resource-hungry VMs. Containers offer lower overhead, faster deployment, greater density and savings, and one platform can manage both VMs and containers (less training). Base images have shrunk: a minimal Red Hat Enterprise Linux base image is about 30 MB to download and 84 MB extracted. Kubernetes added features for stateful workloads and persistent storage.
  • Statistic quoted: 66% of organisations run half of their application base as containers in production, from the CNCF 2023 Annual Survey (https://www.cncf.io/reports/cncf-annual-survey-2023/).
