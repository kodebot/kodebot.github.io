Book digests/Podman For Devops

Podman for DevOps 3: Running the first container

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 3. Previous: Podman for DevOps 2: Comparing Podman and Docker. Next: Podman for DevOps 4: Managing running containers.

Takeaways
  • Podman installs from the distribution's package manager (dnf, apt-get, zypper, emerge, pacman); on macOS and Windows it runs a Linux VM (podman machine) or acts as a remote client.
  • The book's reference OS is Fedora Workstation 40.
  • Config lives in TOML and JSON files with a system-wide, then per-user override order: registries.conf, containers.conf, storage.conf, mounts.conf, seccomp.json, policy.json.
  • An optional socket-activated API (podman.socket) serves Docker-compatible and libpod REST calls and stops after 5 seconds idle.
  • podman run has about 120 options; the first ones to know are -i -t, -d, -p, --tz, --dns, --add-host and --env. Containers are ephemeral, so use environment variables for configuration.

3.1 Choosing an operating system and installation method

  • Podman is supported on many distributions and packaged by each; the book also covers macOS, Windows and building from source, with focus on Linux.
  • Distribution differences: filesystem structure, libraries, packaging, and the mandatory access control system. Fedora, CentOS, RHEL and derivatives use SELinux; Debian, Ubuntu and derivatives use AppArmor. Podman works with both, through different interfaces. DistroWatch (https://distrowatch.com) tracks distributions.
  • Reference environment: all examples were written and tested on Fedora Workstation 40. To reproduce it:
    • the Fedora 40 Vagrant box (https://app.vagrantup.com/fedora/boxes/40-cloud-base); Vagrant is a HashiCorp tool for fast lightweight VMs (https://www.vagrantup.com/)
    • the cloud image (https://alt.fedoraproject.org/cloud/) on a public or private cloud or a hypervisor
    • a manual install of Fedora Workstation (https://docs.fedoraproject.org/en-US/workstation-docs/)
    • public clouds (AWS, Google Cloud, Azure, DigitalOcean) offer Fedora instances at low prices and free learning tiers when you cannot run VMs locally
  • Windows and macOS: containers are Linux-based. Windows has native containers, but only Windows-based images run natively and few engines support them. macOS uses the hybrid Mach/BSD kernel XNU ("X is not Unix") with no Linux kernel features. Both need a virtualisation layer. Apple's container tool (Swift, optimised for Apple silicon) runs Linux containers as lightweight VMs and uses OCI images. Podman offers remote client functions; Windows can also use WSL 2 (a lightweight Hyper-V VM exposing Linux kernel interfaces). Chapter 15 covers the Podman Desktop GUI.

The RHEL 8 container-tools module installs, with Podman and libraries:

  • Skopeo: manages OCI images and registries
  • Buildah: builds OCI images from Dockerfiles or from scratch
  • CRIU: checkpoint/restore for Linux
  • Udica: generates SELinux security profiles for containers

macOS

  • Use the installer from Podman.io, or (not recommended by the Podman team) Homebrew: $ brew install podman.
  • Then initialise and start the Linux VM that runs the containers:
$ podman machine init
$ podman machine start
$ podman machine init --now    # does both
  • Alternatives: connect to an external Linux host with the remote client, or use Vagrant VMs provisioned with Podman.

Windows

  • Recommended: Podman on WSL 2; needs a recent Windows 10 or 11 and virtualisation support. Hyper-V is an alternative (see the Podman docs).
  • Download podman-x.y.z-setup.exe from https://github.com/containers/podman/releases/, run it, then:
PS C:\Users\User> podman machine init
PS C:\Users\User> podman machine start
  • podman machine init installs WSL 2 components if missing (with reboots, or you can install manually); if WSL 2 exists it downloads a minimal Fedora distribution and imports it.
  • Remote client only: podman system connection add edits the config for you. The manual (not recommended) way: extract the release .zip and set the TOML containers.conf:
[engine]
remote_uri = "ssh://root@10.10.1.9:22/run/podman/podman.sock"

The remote Linux machine exposes Podman on a Unix socket managed by a systemd unit (covered in chapter 15).

Building from source

Benefits: inspect and customise code, cross-compile, build a subset of binaries, learn the project, get the latest development features (bugs included). On Fedora:

# git clone https://github.com/containers/podman/ && \
    cd podman
# dnf builddep -y rpm/podman.spec

dnf builddep installs the build dependencies declared in rpm/podman.spec. Then the runtime dependencies (the book's list is cut off after nftables):

$ sudo dnf -y install \
    conmon \
    containers-common \
    crun \
    netavark \
    nftables

Build and install:

$ make BUILDTAGS="selinux seccomp" PREFIX=/usr
$ sudo make install PREFIX=/usr
  • The tags enable SELinux and seccomp support, though recent releases auto-detect them. Installation goes under /usr/bin.
  • Check: $ podman version (example: Client Podman Engine, version 5.3.0-dev, API 5.3.0-dev, Go go1.22.7, built Tue Sep 24 2024, linux/amd64).
  • A binary release like the GitHub .tar.gz: $ make podman-release.
  • Bonus tip: build another version by checking out its tag: $ git checkout v5.3.0.

3.2 Preparing your environment

Podman works out of the box; these tweaks help interoperability and runtime behaviour.

Customising the registries search list

  • /etc/containers/registries.conf (TOML) controls the registries allowed for searching and pulling, registry mirroring, and insecure registries without TLS. The key unqualified-search-registries lists registries searched for names without a registry. On a new Fedora install:
unqualified-search-registries = ["registry.fedoraproject.org", "registry.access.redhat.com", "docker.io", "quay.io"]
  • Add or remove entries. Use only trusted registries to avoid images containing malicious code. The default list suffices for all the book's examples.
  • Private registries usually need authentication with podman login (chapter 9).
  • $HOME/.config/containers/registries.conf overrides the system file, so users can have their own whitelists and mirrors.

Optional: socket-based services

Podman needs no daemon, but you may want its libpod APIs or its Docker-compatible APIs (useful when migrating from Docker). The socket is a Unix socket (default) or TCP; TCP is less secure (reachable from outside) but needed for clients on Windows or macOS; consider SSH instead. A TCP endpoint on an internet-exposed machine is globally accessible. One-off command:

$ sudo podman system service --time=0 \
    unix:///run/podman/podman.sock

Better: a systemd socket (man systemd.socket). Socket units are service activators: a connection to the endpoint makes systemd start the same-named service. Installing Podman creates podman.socket and podman.service:

# /usr/lib/systemd/system/podman.socket
[Unit]
Description=Podman API Socket
Documentation=man:podman-system-service(1)

[Socket]
ListenStream=%t/podman/podman.sock
SocketMode=0660

[Install]
WantedBy=sockets.target

ListenStream expands to /run/podman/podman.sock.

# /usr/lib/systemd/system/podman.service
[Unit]
Description=Podman API Service
Requires=podman.socket
After=podman.socket
Documentation=man:podman-system-service(1)
StartLimitIntervalSec=0

[Service]
Type=exec
KillMode=process
Environment=LOGGING="--log-level=info"
ExecStart=/usr/bin/podman $LOGGING system service

[Install]
WantedBy=multi-user.target

ExecStart is the same podman system service command; Requires= says the service needs the socket. Enable it and test:

# systemctl enable --now podman.socket
# curl --unix-socket /run/podman/podman.sock \
    http://d/v3.0.0/libpod/info
  • The reply is a JSON payload with the engine configuration. The first call has a delay of about 1/10 s because the service starts on demand.
  • After 5 seconds of inactivity podman.service stops again: the default timeout of podman system service; --time sets another value (0 means forever).

Optional: customising Podman's behaviour

File Format Purpose Locations (default, then overrides)
containers.conf TOML runtime configuration and search paths for conmon and runtime binaries; logging, DNS, environment variables, shared memory, cgroup management; man containers.conf /usr/share/containers/; override /etc/containers/containers.conf (system) and $HOME/.config/containers/containers.conf (user)
storage.conf TOML storage driver (default overlay) and the read/write directory (graph root) /usr/share/containers/storage.conf; override /etc/containers/storage.conf; rootless: $XDG_CONFIG_HOME/containers/storage.conf or $HOME/.config/containers/storage.conf
mounts.conf text volume mounts auto-mounted in every container, e.g. to pass secrets such as keys and certificates /usr/share/containers/mounts.conf; override /etc/containers/mounts.conf; rootless $HOME/.config/containers/mounts.conf
seccomp.json JSON allowed and blocked syscalls inside containers (chapter 10; man seccomp) /usr/share/containers/seccomp.json
policy.json JSON signature verification /etc/containers/policy.json; override $HOME/.config/containers/policy.json

policy.json accepts three policies (man containers-policy.json):

  • insecureAcceptAnything: accept any image from the registry (the default)
  • reject: reject any image from the registry
  • signedBy: accept only images signed by a specific known entity (custom GPG keys can verify signatures and identity)

3.3 Running your first container

The shortest form: $ podman run <imageID>. Replace the placeholder with the image name, location or tag; Podman pulls the image if it is not cached. podman run takes many options for behaviour, isolation, communication and storage.

Interactive and pseudo-tty

$ podman run -i -t fedora /bin/bash
Resolved "fedora" as an alias (/etc/containers/registries.conf.d/000-shortnames.conf)
Trying to pull registry.fedoraproject.org/fedora:latest...
Getting image source signatures
Copying blob dbe590460ba2 done  |
Copying config 5eea52ff5b done  |
Writing manifest to image destination
[root@a45628efe4b8 /]#

What Podman did:

  1. Recognised fedora as an alias for the latest Fedora image.
  2. Found it missing from the local cache (first run).
  3. Pulled it from the right registry (the Fedora Project registry, matching the aliases in the registry configuration).
  4. Started the container and gave an interactive Bash shell.
Option Effect
--tty, -t allocate a pseudo-tty (man pty) and attach it to the container's standard input
--interactive, -i keep stdin open and ready to attach to that pseudo-tty

Processes write on a writable layered-overlay root filesystem, but changes last only while the container runs (ephemeral). Example: inside the container, install tools and ping the default router, then everything is lost after stopping:

[root@a45628efe4b8 /]# dnf install -y iputils iproute
[root@a45628efe4b8 /]# ip r
default via 192.168.124.1 dev eth0 proto dhcp metric 100
192.168.124.0/24 dev eth0 proto kernel scope link metric 100
[root@a45628efe4b8 /]# ping -c2 192.168.124.1
64 bytes from 192.168.124.1: icmp_seq=1 ttl=255 time=0.354 ms
64 bytes from 192.168.124.1: icmp_seq=2 ttl=255 time=0.516 ms

Exit with Ctrl+D or exit: the container terminates because its main process (/bin/bash) ended.

Detaching from a running container

Interactive attachment is not the preferred way to run containers. Run a web server with a tty:

$ podman run -i -t quay.io/fedora/httpd-24
  • It logs the startup scripts and Apache "resuming normal operations" (Apache/2.4.62 on Fedora, httpd -D FOREGROUND).
  • Detach with Ctrl+P, Ctrl+Q: you return to your prompt while the container keeps running.
  • Re-attach: find the ID with podman ps (covered in chapter 4), then:
$ podman ps
CONTAINER ID  IMAGE                                COMMAND            CREATED        STATUS            PORTS  NAMES
685a339917e7  registry.fedoraproject.org/httpd:latest  /usr/bin/run-http...  3 minutes ago  Up 3 minutes ago         clever_zhukovsky
$ podman attach 685a339917e7
  • Start detached directly with -d: $ podman run -d registry.fedoraproject.org/httpd.

Network port publishing

A container gets a virtual network isolated from the host, so publish ports to reach it or expose it outside the host. The -p option:

-p=ip:hostPort:containerPort/protocol
  • hostPort and containerPort can be ranges. An unset host IP or 0.0.0.0 binds all IPv4 addresses; [::] binds all IPv6. The optional protocol restricts to TCP or UDP.
$ podman run -p 8080:8080 -d registry.fedoraproject.org/httpd
$ podman ps
CONTAINER ID  IMAGE                                COMMAND  CREATED         STATUS          PORTS                   NAMES
fc9d97642801  registry.fedoraproject.org/httpd:latest  ...      10 minutes ago  Up 10 minutes ago  0.0.0.0:8080->8080/tcp  confident_snyder
$ podman port fc9d97642801
8080/tcp -> 0.0.0.0:8080
$ curl -s 127.0.0.1:8080 | head

The reply is the "Test Page for the Apache HTTP Server on Fedora". A browser works too.

Configuration and environment variables

podman run has around 120 options (at the time of writing). Examples:

$ date
Wed Sep 25 09:57:25 AM UTC 2024
$ podman run --tz=Asia/Shanghai fedora date
Wed Sep 25 17:57:33 CST 2024

$ podman run --dns=1.1.1.1 fedora cat /etc/resolv.conf
nameserver 1.1.1.1

$ podman run --add-host=my.server.local:192.168.1.10 \
    fedora cat /etc/hosts
192.168.1.10 my.server.local
127.0.0.1 localhost localhost.localdomain localhost4 localhost4.localdomain4
::1 localhost localhost.localdomain localhost6 localhost6.localdomain6
192.168.124.6 3497f23d8551 serene_shannon
  • HTTP proxy: Podman passes many host environment variables by default, including http_proxy, https_proxy, ftp_proxy and no_proxy.
  • Custom variables with --env:
$ podman run --env MYENV=podman fedora printenv
container=oci
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MYENV=podman
HOME=/root
HOSTNAME=1db6008431c2

Best practice: pass configuration as environment variables, because containers are immutable and ephemeral.
