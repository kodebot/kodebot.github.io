Podman for DevOps 4: Managing running containers

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 4. Previous: Podman for DevOps 3: Running the first container. Next: Podman for DevOps 5: Implementing storage for the container's data.

Takeaways
  • Images: podman search (filter, format, --list-tags), pull, images, inspect, image mount, rmi, image prune. The name format is <registry>[:<port>]/[<namespace>/]<name>:<tag>; avoid relying on :latest.
  • Container life cycle: ps, stop (SIGTERM, then SIGKILL after 10 s), start, restart, create, rm, kill, pause and unpause (cgroup freezer, not signals), container prune.
  • Inspect: top, stats, inspect --format (Go templates), and the overlay directories (MergedDir, LowerDir, UpperDir).
  • Logs: write to STDOUT and STDERR; podman logs reads them (journald by default on recent Fedora).
  • Debug in place: podman exec. Pods: containers sharing network, IPC and storage, plus a hidden infra (pause) container.

4.1 Managing container images

  • Podman pulls an image automatically on first run, but pulling and inspecting in advance makes a container start faster from the local store.
  • Registries: public (docker.io, gcr.io, quay.io; often with paid private hosting) or private (inside an organisation, focused on security and content filtering). The main registry projects are CNCF graduated (https://landscape.cncf.io/card-mode?category=container-registry&grouping=category) and offer multitenancy, authentication, RBAC, vulnerability scanning and image signing. Most expose the Docker Registry HTTP API V2 (https://docs.docker.com/registry/spec/api/), so curl works. Chapter 9 covers registries in depth.

Searching for images

# podman search nginx
  • It searches all whitelisted registries; results can be clumsy, with unknown and unreliable repositories. The web search of public registries is higher quality. Syntax: podman search [options] TERM.
  • Output fields:
Field Meaning
INDEX the registry indexing the image
NAME full name with registry and namespaces
DESCRIPTION short description of the image's role
STARS user stars (only registries that support it, such as docker.io)
OFFICIAL whether the image is official
AUTOMATED OK if automated

[!warning] Never trust unknown repositories; prefer official images Understand what a niche image contains before running it, since an attacker can hide malicious code. Even trusted repositories can be compromised: in enterprise scenarios verify image signatures.

# podman search nginx --filter=is-official          # prints docker.io/library/nginx:latest
# podman search fedora \
    --filter is-official \
    --format "table {{.Index}} {{.Name}}"
INDEX      NAME
docker.io  docker.io/library/fedora

Image name format: <registry>[:<port>]/[<namespace>/]<name>:<tag>

  • registry: where it is stored (docker.io for nginx); an optional port, and registries by default expose TCP 5000 (the book's claim).
  • namespace: optional hierarchy: parent organisation, repository owner's username, or image role.
  • name: the repository, usually the application name (nginx).
  • tag: unique per image, mapped to a SHA256 digest; :latest can be omitted.

Show tags with --list-tags:

# podman search quay.io/prometheus/prometheus --list-tags
NAME                           TAG
quay.io/prometheus/prometheus  0.19.0
quay.io/prometheus/prometheus  latest
quay.io/prometheus/prometheus  main
quay.io/prometheus/prometheus  v1.0.0
[...output omitted...]

[!warning] :latest is not a version It is expected to point to the newest image but need not: an untagged image can keep it while the newest push has a different tag, and maintainers can push incompatible updates to it and break deployments. With semantic versioning, pull the most recent version tag.

Pulling and viewing images

# podman pull docker.io/library/nginx:latest    # root: /var/lib/containers/storage
$ podman pull docker.io/library/nginx:latest    # rootless: $HOME/.local/share/containers/storage/
  • podman pull nginx without a registry tries aliases; if ambiguous a prompt asks which registry.
# podman images
REPOSITORY               TAG     IMAGE ID      CREATED     SIZE
docker.io/library/nginx  latest  7f553e8bbc89  6 days ago  196 MB
# podman images --sort=created      # sort by size, date, ID, repository or tag
# podman images -qa                 # IDs of all images, including intermediate layers
  • -a (--all) and -q (--quiet) combine to print only IDs. Intermediate layers are the read-only filesystem snapshots created during the build: each RUN, COPY or ADD instruction in a Dockerfile or Containerfile adds one, stacked into the final image. See man podman-images.

Inspecting images

# podman inspect docker.io/library/nginx:latest     # same as podman image inspect
# podman inspect docker.io/library/nginx:latest \
    --format "{{ .Config.Cmd }}"
[nginx -g daemon off;]
  • The JSON holds config, architecture, layers, labels, annotations and the image history, useful to learn how an image was built when the Dockerfile is missing. --format takes a Go template.
  • Look at the filesystem with podman image mount:
# podman image mount docker.io/library/nginx
/var/lib/containers/storage/overlay/11174639fa91.../merged
# ls -al /var/lib/containers/storage/overlay/11174639fa91.../merged/
# podman image unmount docker.io/library/nginx
  • Rootless mount: with the default OverlayFS driver, mount and unmount only work after podman unshare, which opens a shell in a new namespace where your UID and GID map to 0:
$ podman unshare
# podman image mount docker.io/library/nginx:latest
.local/share/containers/storage/overlay/11174639fa91.../merged
# podman image unmount docker.io/library/nginx:latest
# exit      # leave the temporary unshared namespace

Deleting images

# podman rmi docker.io/library/nginx:latest
Untagged: docker.io/library/nginx:latest
Deleted: 7f553e8bbc897571642d836b31eaf6ecbe395d7641c2b24291356ed28f3f2bd0
# podman rmi $(podman images -qa)       # all images (root; as a user, run it with $)
$ sudo podman image prune -af           # all unused images, no confirmation
  • rmi fails for images used by a container: stop and remove those containers, or use --force, which also removes the containers.
  • image prune keeps only images tied to containers, running or stopped. It works in rootless mode too, on the user's store.

4.2 Operations with running containers

$ podman run -d -p 8080:80 docker.io/library/nginx
$ curl localhost:8080          # "Welcome to nginx!" default page

[!tip] Rootless containers add a security layer If a malicious process breaks out of isolation (for instance through a host vulnerability), it gains at best the privileges of the user who started the rootless container.

Viewing and handling status

podman ps columns:

Column Meaning
CONTAINER ID unique hex ID; 64 characters, the short form is 12
IMAGE image used
COMMAND command executed inside
CREATED creation date
STATUS current state
PORTS open ports; 0.0.0.0:8080->80/tcp means host 8080 on all interfaces maps to container 80
NAMES user-given or random (adjective plus a notable scientist or hacker, from Docker's github.com/docker/docker/namesgenerator package, vendored by Podman)
  • podman stop sets the state to stopped and sends SIGTERM, then SIGKILL after a 10 second timeout if unresponsive. podman ps -a lists stopped containers too (Exited (0)).
  • podman start resumes it: config, storage and metadata are kept while stopped, but a new process starts inside. man podman-start.
  • podman restart restarts using the same data and process definition; the filesystem and configuration are reused but all namespaces are new, which can fix many networking problems because configuration is redone.
  • podman create builds a container without starting it (podman create -p 8080:80 docker.io/library/nginx); then podman start <ID or name>. Handy to prepare an environment or to mount a container filesystem as non-root:
$ podman unshare
$ podman container mount <Container_ID_or_Name>
/home/<username>/.local/share/containers/storage/overlay/bf9d8df2.../merged

podman container mount (short podman mount) mounts a container's root filesystem on the host so you can browse and edit its files without a shell inside.

  • podman rm removes stopped containers (all storage, config and metadata are discarded); -f removes running ones.

Bulk operations

$ for i in {1..5}; do podman run -d docker.io/library/nginx; done
$ podman ps -qa                       # IDs only
$ podman stop $(podman ps -qa)
$ podman rm $(podman ps -qa)
  • Shell expansion $(...) passes the output as arguments. Most commands (start, stop, rm) also support -a.
  • Filter by status: created, exited, paused, running, unknown.
$ podman ps --filter status=exited
$ podman rm $(podman ps -qa --filter status=exited)
$ podman container prune              # removes all stopped containers
$ podman ps -q --sort id
$ podman ps -a --format "{{.ID}} {{.Command}}" --no-trunc
$ podman ps --format "{{ .Pid }}"     # host PID of the container process
$ podman ps --namespace
CONTAINER ID  NAMES                 PID     CGROUPNS    IPC         MNT         NET         PIDNS       USERNS      UTS
f2666ed4a46a  unruffled_hofstadter  437764  4026533088  4026533086  4026533083  4026532948  4026533087  4026532973  4026533085

--namespace shows the container's namespaces, a starting point for advanced troubleshooting. Filters are listed on the podman-ps man page.

Pausing and unpausing

  • podman stop sends SIGTERM and SIGKILL to the parent process; podman pause uses cgroups (the freezer) to suspend the processes without terminating them; unpausing resumes the same process transparently. The logic lives in the runtime (in crun at the time of writing: https://github.com/containers/crun/blob/7ef74c9330033cb884507c28fd8c267861486633/src/libcrun/cgroup.c#L1894-L1936).
$ podman run --name timer docker.io/library/fedora bash -c "while true; do echo $(date); sleep 2; done"
$ podman ps --format "{{ .Pid }}" --filter name=timer     # 816807
$ podman pause timer
$ podman unpause timer
$ podman ps --format "{{ .Pid }}" --filter name=timer     # same PID: 816807
  • Output stops while paused and resumes after; the PID is unchanged. Check the cgroup (root shell, replace the ID): the file cgroup.freeze flips between 0 and 1.
$ sudo -i
$ cd /sys/fs/cgroup/user.slice/user-1000.slice/user@$UID.service/user.slice/libpod-<CONTAINER_ID>.scope/container
  • Cleanup: the bash -c loop ignores SIGTERM, so podman kill timer (or podman stop and wait 10 s; --time 0 skips the wait).

Inspecting processes inside containers

$ podman top f2666ed4a46a
USER   PID  PPID  %CPU  ELAPSED          TTY  TIME  COMMAND
root   1    0     0.000 3m26.540290427s  ?    0s    nginx: master process nginx -g daemon off;
nginx  26   1     0.000 3m26.540547429s  ?    0s    nginx: worker process
...
$ podman top f2666ed4a46a pid comm args       # custom fields
  • Output resembles ps, not the interactive top.
  • Container PIDs start at 1 inside; the engine maps them to host PIDs. Get the host PID from podman ps --namespace, or podman top $CONTAINER_ID pid hpid (hpid = host PID). Then:
$ sudo strace -p <PID>                      # syscalls (see man strace)
$ pidstat -p <PID> [<interval> <count>]     # resource usage over time (see man pidstat)
  • podman kill sends SIGKILL by default (--signal for SIGTERM, SIGHUP and others). A killed container is not removed: it stays, in exited state.
$ podman run --name custom-webserver -d docker.io/library/httpd
$ podman kill custom-webserver

Chapter 11 covers nsenter and more troubleshooting.

Monitoring container stats

podman stats opens a self-refreshing top-like view. Default columns:

Column Meaning
ID, NAME container ID and name
CPU % total CPU usage
MEM USAGE / LIMIT memory against a limit (system capabilities or cgroup limits)
MEM % memory percentage
NET IO, BLOCK IO network and disk I/O
PIDS number of PIDs inside
CPU TIME, AVG CPU % total and average CPU 
$ podman stats --no-stream            # one snapshot
$ podman stats --format=json
[
  {
    "id": "d19dbb81a0f3",
    "name": "admiring_bouman",
    "cpu_time": "16.773ms",
    "cpu_percent": "0.01%",
    "avg_cpu": "0.01%",
    "mem_usage": "1.884MB / 475.4MB",
    "mem_percent": "0.40%",
    "net_io": "0B / 796B",
    "block_io": "0B / 0B",
    "pids": "2"
  }
]
$ podman stats -a --no-stream --format "{{ .ID }} {{ .CPUPerc }} {{ .MemUsageBytes }} {{ .PIDs }}"

--format=json works on most commands (e.g. podman ps --format=json) for machine-readable output.

4.3 Inspecting container information

podman inspect <ID or name> prints a large JSON. Notable fields:

Field Content
Path, Args entry point and its arguments (together, the command run)
State current state, executed PID, common PID, OCI version, health check
Image, Name image ID and container name
MountLabel, ProcessLabel SELinux labels
EffectiveCaps effective capabilities
GraphDriver storage driver (default overlay) and the upper, lower and merged directories
Mounts user-specified mounts
NetworkSettings internal IP, exposed ports, port mappings
Config environment variables, hostname, command, working directory, labels, annotations
HostConfig cgroup quotas, network mode, capabilities 
$ podman inspect <ID or Name> --format "{{ .State.Pid }}"
  • {{ .ResolvConfPath }} shows where resolv.conf comes from: rootless /run/user/<UID>/containers/overlay-containers/<Container_ID>/userdata/resolv.conf; rootful /var/run/containers/storage/overlay-containers/<Container_ID>/userdata/resolv.conf.
  • Overlay directories, worked example (rootful):
# podman run --name logger -d docker.io/library/fedora bash -c "while true; do echo test >> /tmp/test.log; sleep 5; done"
# podman inspect logger --format "{{ .GraphDriver.Data.MergedDir }}"
/var/lib/containers/storage/overlay/4372e7c8.../merged       # /tmp/test.log is here
# podman inspect logger --format "{{ .GraphDriver.Data.LowerDir }}"
/var/lib/containers/storage/overlay/b0d5c42c.../diff        # read-only image layers: no log file
# podman inspect logger --format "{{ .GraphDriver.Data.UpperDir }}"
/var/lib/containers/storage/overlay/27d89046.../diff        # read-write container layer: has /tmp/test.log
# podman stop logger && podman rm logger
  • MergedDir is where overlayfs merges all layers; LowerDir holds the read-only base layers (not written); UpperDir is the container's read-write layer, containing only what was written since startup. Chapter 5 returns to this.

4.4 Capturing logs from containers

  • Writing log files inside a container is fragile (read-only filesystems, permissions). Best practice: write to the standard streams, STDOUT and STDERR. Standard streams are channels connected to a process; in an interactive shell they connect to your terminal.
  • Podman attaches STDIN, STDOUT and STDERR depending on the run options, and stores the output in a local file, or in journald on systemd distributions. From Fedora 35 the default log driver changed from k8s-file to journald:
# grep ^log_driver /usr/share/containers/containers.conf
log_driver = "journald"
  • podman run -d -i -t docker.io/library/httpd = detached (-d), pseudo-terminal attached to STDIN (-t), stdin kept open (-i).
  • The hard way: note the container name from podman ps, then journalctl --user -t cranky_wu (the output shows the Apache AH00558 warning and "resuming normal operations").
  • The easy way: podman logs:
# podman logs cranky_wu
# podman logs --tail 2 a068c7db7ff9       # only the last two lines
  • Tip: most commands accept --latest, acting on the most recently created container (podman logs --latest).

4.5 Executing processes in a running container

podman exec finds the container's Linux namespaces and starts the given process inside them, in the same environment as the original process, preserving isolation.

# podman run -d -i -t docker.io/library/httpd
e768bf9723687194329b6d6854605849529c79f1d19...
# podman exec -ti e768bf972368... /bin/bash
root@e768bf972368:/usr/local/apache2# ps aux
bash: ps: command not found
root@e768bf972368:/usr/local/apache2# ls -l /proc/*/exe
lrwxrwxrwx. 1 root root 0 Oct 10 09:36 /proc/1/exe -> /usr/local/apache2/bin/httpd
  • Useful for troubleshooting and testing. The image lacks ps (probably the procps package was left out to shrink the image), so the example reads /proc ("everything is a file"); alternatively install the package inside. Options mirror podman run (-t, -i); see man podman exec.

4.6 Running containers in pods

A pod is the smallest execution unit in Kubernetes. Grouping containers in one pod gives:

  • one shared network namespace and IP address
  • shared storage volumes for persistent data
  • shared configuration
  • joint life cycle (start, stop, restart as one unit)
  • a shared IPC namespace, useful for apps using shared memory
# podman pod create --name myhttp
7a566073adb31df12286bfa82586d82b5004396ff10a2235d9d7cf7e7a49cb9f
# podman pod ps
POD ID        NAME    STATUS   CREATED             INFRA ID      # OF CONTAINERS
7a566073adb3  myhttp  Created  13 seconds ago      b5483a84d10b  1
# podman pod start myhttp
# podman ps
CONTAINER ID  IMAGE                                  COMMAND  CREATED        STATUS             PORTS  NAMES
b5483a84d10b  localhost/podman-pause:5.2.2-1724198400         2 minutes ago  Up About a minute         7a566073adb3-infra
  • An empty pod already runs one container: the infra container (image podman-pause). It does nothing; it holds the namespaces so the engine can connect other containers to the pod.
  • Add a container with --pod:
# podman run --pod myhttp -d -i -t docker.io/library/httpd
# podman pod ps        # now 2 containers
# podman ps -p         # adds POD ID and PODNAME columns

[!note] Lab cleanup Clean the lab between chapters with podman rm --all --force and podman system reset (resets Podman to default configuration). Extra material: https://github.com/PacktPublishing/Podman-for-DevOps-Second-Edition (folder AdditionalMaterial).

[!warning] Grouping containers in a pod is an anti-pattern for containers Kubernetes treats the pod as the smallest unit scheduled on one node, so containers in one pod always run together on the same node and the orchestrator cannot spread their load across machines.
