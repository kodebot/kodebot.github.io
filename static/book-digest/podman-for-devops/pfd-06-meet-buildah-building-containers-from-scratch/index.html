Podman for DevOps 6: Meet Buildah, building containers from scratch

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 6 (Part 2: Building your container from scratch with Buildah). Previous: Podman for DevOps 5: Implementing storage for the container's data. Next: Podman for DevOps 7: Integrating with existing application build processes.

Takeaways
  • An image is a stack of immutable COW layers; a Dockerfile (or Containerfile, same syntax) is a list of instructions run in order. Only RUN, COPY, ADD create filesystem layers; CMD, ENV, LABEL, EXPOSE and similar add metadata-only (empty) layers.
  • podman build has no learning curve from Docker and builds rootless without a daemon; --layers=false squashes layers.
  • Buildah (Apache 2.0, in the same containers family) is the scriptable builder: from, run, config, copy, add, mount, commit, build. Its working containers are short-lived and are not shown by podman ps without --external.
  • Three strategies: from an existing base image, from scratch (install packages into the mounted empty root with dnf --installroot), from a Dockerfile.
  • Layer caching trades build speed and deduplication against filesystem complexity.

6.1 Building basic images with Podman

An OCI image is a set of immutable layers stacked with copy-on-write logic. A build creates layers in a precise order, then pushes them to a registry that stores them as tar archives plus metadata (the manifest, the image index and the image configuration from chapter 2).

Builds under the hood

  • The most common approach is the Dockerfile: the main Docker build file, a plain list of actions executed in order. It became a standard of OCI image builds. Containerfile is the brand-neutral name with identical syntax, supported natively by Podman; the book uses the two interchangeably.
FROM docker.io/library/fedora
RUN dnf install -y httpd && dnf clean all -y
COPY index.html /var/www/html
CMD ["/usr/sbin/httpd", "-DFOREGROUND"]
Instruction Role
FROM the base image the build starts from
RUN executes commands during the build (here, install packages with dnf)
COPY copies files or directories from the build directory into the image
CMD the command to execute when the container starts
  • RUN and COPY results are cached in intermediate layers (temporary images), reused on later builds when nothing changed in that layer. The engine automates this: temporary containers run the instruction and commit. All intermediate layers are read-only and merged by the overlay graph driver.
  • Squashing layers into one avoids a negative effect on overlay performance; Podman lets you choose between caching and not.
  • Only RUN, COPY and ADD create real layers (they change the filesystem); every other instruction (like CMD) produces an empty layer with metadata only. Keep the number of RUN, COPY and ADD instructions limited: too many layers is a poor pattern and hurts graph-driver performance.
  • Image history (podman inspect myhttpd) shows each layer's action. Entries marked "empty_layer": true (LABEL, ENV, CMD) are metadata; ADD ...tar, the dnf install and COPY entries are real layers. The last three entries match the Dockerfile exactly, including the CMD that adds only metadata to the image config.

Dockerfile and Containerfile instructions

All instructions follow INSTRUCTION arguments (with # comments):

Instruction What it does
FROM <image>[:<tag>] first instruction of a build stage; the base image
RUN <command> runs in a temporary container using the build's filesystem; the binary or script must exist in the base image or an earlier layer; creates a layer, so chain commands: RUN dnf upgrade -y && \ dnf install httpd -y && \ dnf clean all -y
COPY <src>... <dest> copies from the build directory into the image; --chown=<user>:<group> sets ownership directly
ADD <src>... <dest> like COPY but also takes remote URLs and auto-extracts tar files
ENTRYPOINT the executed command; receives arguments from the command line (podman run <image> <arguments>) or from CMD; cannot be overridden by command-line arguments (in the book's words). Exec form ["command","param1"] or shell form; default is bash -c, so ps aux becomes bash -c "ps aux". Teams often replace it with a custom script for finer control
CMD default arguments passed to the ENTRYPOINT: exec form, parameter form (for a custom ENTRYPOINT) or shell form
LABEL <k>=<v> image metadata at build or run time
EXPOSE <port>/<protocol> metadata about listening ports; not forwarded by default
ENV <k>=<v> environment variables for following build steps and at runtime (a RUN can set its own, scoped to that instruction)
VOLUME a volume created at runtime in Podman's default volume directory (["/path"] or /path; see chapter 5)
USER user and optional group for following RUN, CMD, ENTRYPOINT: USER <username>[:<group>] or USER <UID>[:<GID>]
WORKDIR working directory during the build, retained at runtime
ONBUILD a trigger run when the image is used as a parent in another build: ONBUILD ADD . /opt/app, ONBUILD RUN /opt/bin/custom-build /opt/app/src

Running builds with Podman

Same commands and syntax as Docker, so no learning curve. A real advantage: Podman builds rootless with fork/exec; Docker's build talks to a daemon on a Unix socket.

$ podman build -t myhttpd .
STEP 1/4: FROM docker.io/library/fedora
STEP 2/4: RUN dnf install -y httpd && dnf clean all -y
--> 50a981094eb
STEP 3/4: COPY index.html /var/www/html
--> 73f8702c5e0
STEP 4/4: CMD ["/usr/sbin/httpd", "-DFOREGROUND"]
COMMIT myhttpd
--> e773bfee6f2
Successfully tagged localhost/myhttpd:latest
  • Layers persist as cache until podman image prune. FROM pulls the base if missing. RUN executes as bash -c '...'; with no ENTRYPOINT, CMD becomes bash -c '/usr/sbin/httpd -DFOREGROUND'.

A custom web-server example shows several practices:

FROM docker.io/library/fedora
# Install required packages
RUN set -euo pipefail; \
    dnf upgrade -y; \
    dnf install httpd -y; \
    dnf clean all -y; \
    rm -rf /var/cache/dnf/*
# Custom webserver configs for rootless execution
RUN set -euo pipefail; \
    sed -i 's|Listen 80|Listen 8080|' \
    /etc/httpd/conf/httpd.conf; \
    sed -i 's|ErrorLog "logs/error_log"|ErrorLog /dev/stderr|' \
    /etc/httpd/conf/httpd.conf; \
    sed -i 's|CustomLog "logs/access_log" combined|CustomLog /dev/stdout combined|' \
    /etc/httpd/conf/httpd.conf; \
    chown 1001 /var/run/httpd

# Copy web content
COPY index.html /var/www/html
# Define content volume
VOLUME /var/www/html
# Copy container entrypoint.sh script
COPY entrypoint.sh /entrypoint.sh
# Declare exposed ports
EXPOSE 8080
# Declare default user
USER 1001
ENTRYPOINT ["/entrypoint.sh"]
CMD ["httpd"]

What it illustrates:

  • Minimal packages: clean the package cache after installing httpd to shrink the image.
  • Fail-safe chained commands: set -euo pipefail stops the build if any command fails; the \ splits lines for readability.
  • Non-root process: workarounds (permissions, group ownership) let httpd run as generic user 1001, a security best practice that reduces the attack surface (unnecessary with rootless containers).
  • Logs to stdout and stderr by editing httpd.conf with sed.
  • EXPOSE 8080, and a CMD ["httpd"] with no arguments to show how ENTRYPOINT interacts with CMD.

The entrypoint.sh script checks whether the container runs as root and inspects the first CMD argument:

#!/bin/sh
set -euo pipefail
if [ $UID != 0 ]; then
    echo "Running as user $UID"
fi
if [ "$1" == "httpd" ]; then
    echo "Starting custom httpd server"
    exec $1 -DFOREGROUND
else
    echo "Starting container with custom arguments"
    exec "$@"
fi

  • Squash: podman build -t myhttpd --layers=false . leaves two layers (base plus one squashed). Trade-off: a minimal overlay, but you rebuild the whole image for every configuration change, with no cache.
  • Rootless vs rootful: rootless builds are valued (no privilege needed), rootful (# podman build -t myhttpd .) is fully supported, storing layers under /var/lib/containers/storage/.

6.2 Introducing Buildah, Podman's companion

  • Plain Dockerfile builds suit teams keeping existing pipelines, but offer rigid workflow logic with no scripting. The Podman community created Buildah (pronounced "build-ah") to manage OCI builds with several strategies; its images are fully portable and Docker-compatible.
  • Open source, Apache 2.0 (https://github.com/containers/buildah). Podman vendors Buildah's libraries: the statically linked Go Podman binary embeds the Buildah packages for basic builds.
  • Shared libraries: containers/image (image life cycle and registries) and containers/storage (image and container layers), now under containers/container-libs (https://github.com/containers/container-libs).
  • Two build modes in parallel: Dockerfile/Containerfile builds (buildah build, alias buildah bud) and native Buildah commands that replicate Dockerfile instructions, making builds scriptable with shell conditionals, loops and variables (RUN becomes buildah run).
  • Rootless and socket-free; every build runs in working containers on top of the base image.
Command Equivalent / purpose Example
buildah from start a working container from a base image buildah from fedora
buildah run the RUN instruction; -- separates options from the command buildah run <ID> -- dnf install -y nginx
buildah config metadata instructions (entrypoint, cmd, port, label...) buildah config --entrypoint /entrypoint.sh <ID>
buildah add ADD: files, directories, URLs buildah add <ID> index.php /var/www.html
buildah copy COPY buildah copy <ID> entrypoint.sh /
buildah commit create the final image from the working container (usually last) buildah commit <ID> myhttpd
buildah build like podman build; buildah build [options] [context] buildah build -t <imageName> .
buildah containers list working containers and base images (aliases ls, ps) buildah containers
buildah rm remove working containers (-a removes all; alias delete) buildah rm <ID>
buildah mount mount a working container's root filesystem (no argument lists mounts) buildah mount <ID>
buildah images list local images; --json buildah images --json
buildah tag name and tag a local image buildah tag myapp quay.io/packt/myapp:latest
buildah push push to a registry or a local directory in Docker or OCI format buildah push <ID> docker://<URL>/repository:tag; buildah push <ID> oci:</path/to/dir>:image:tag
buildah pull pull from a registry, OCI archive or directory buildah pull dir:</path/to/dir>

Each has a man page: man buildah-<command> (e.g. man buildah-run).

Minimal example (Fedora with httpd), in a few lines you can put in a script:

$ container=$(buildah from fedora)
$ buildah run $container -- dnf install -y httpd; dnf clean all
$ buildah config --cmd "httpd -DFOREGROUND" $container
$ buildah config --port 80 $container
$ buildah commit $container myhttpd
$ buildah tag myhttpd registry.example.com/myhttpd:v0.0.1
  • buildah from pulls the image from an allowed registry and starts a working container, printing its name; capturing it in $container is the common pattern for scripts.
  • The "secret weapon" is buildah mount: the container's root filesystem is mapped to a host path, so you modify files directly from the host instead of add and copy.
  • Containers differ: Buildah containers are short-lived entities to be modified and committed; Podman containers run long-lived workloads. podman ps does not show Buildah containers without --external.
  • Integration: Ansible (native connection plugins for working containers); CI pipelines such as Jenkins, Tekton, GitLab CI/CD (Tekton Hub has Buildah tasks: https://hub.tekton.dev/tekton/task/buildah; Tekton: https://tekton.dev/); Buildah can run inside a container; Shipwright (https://github.com/shipwright-io/build), an extensible Kubernetes build framework using custom resource definitions, offers Buildah as a build tool.

Buildah also runs as a container, with nested builds (chapter 7).

Verify: buildah images as a user and as root shows the same lists as podman images (shared stores: rootless vs system-wide). A test script builds a minimal Python 3 image on Alpine:

#!/bin/bash

BASE_IMAGE=alpine
TARGET_IMAGE=python3-minimal

if [ $UID != 0 ]; then
    echo "### Running build test as unprivileged user"
else
    echo "### Running build test as root"
fi

echo "### Testing container creation"
container=$(buildah from $BASE_IMAGE)
if [ $? -ne 0 ]; then
    echo "Error initializing working container"
fi

echo "### Testing run command"
buildah run $container apk add --update python3 py3-pip
if [ $? -ne 0 ]; then
    echo "Error on run build action"
fi

echo "### Testing image commit"
buildah commit $container $TARGET_IMAGE
if [ $? -ne 0 ]; then
    echo "Error committing final image"
fi

echo "### Removing working container"
buildah rm $container
if [ $? -ne 0 ]; then
    echo "Error removing working container"
fi

echo "### Build test completed successfully!"
exit 0

It runs the same for root and non-privileged users; test the result with $ podman run -it python3-minimal /usr/bin/python3.

6.4 Choosing our build strategy

Three strategies:

  1. From an existing base image (e.g. extend a prebuilt application-server image with troubleshooting tools or libraries, or add your own PHP modules and application files to the httpd library image).
  2. From scratch (a legacy app needing old libraries no longer in current distributions; also a way to distribute super-minimal images, even single-file images with one static binary). In practice you always start from some initial image, so it is similar to strategy 1.
  3. From a Dockerfile (Buildah parses it and ends up in one of the previous strategies; good for sharing build steps with a team or community).
  • Why build your own: you can't always find your configuration or tool bundle; you may bundle your own configuration; security constraints demand reduced attack surfaces; in enterprises images are almost always built from scratch or from minimal bases.
  • There is no ultimate answer: look for prebuilt images first, fall back to from-scratch, and use Dockerfiles to share.

6.5 Building images from scratch

Podman and Buildah share storage, so previous examples fill the cache. Start a working container from nothing:

# buildah from scratch
# buildah containers
CONTAINER ID  BUILDER  IMAGE ID  IMAGE NAME  CONTAINER NAME
af69b9547db9     *               scratch     working-container
# buildah run working-container bash
executable file `bash` not found in $PATH: No such file or directory

The scratch image is not listed in buildah images, and the container is empty: no executables.

Fill it from the host's package manager (mount, then use --installroot):

# buildah mount working-container
/var/lib/containers/storage/overlay/b5034cc8.../merged
# scratchmount=$(buildah mount working-container)
# dnf install --installroot $scratchmount --releasever 40 bash coreutils --setopt install_weak_deps=false -y
# buildah run working-container bash
bash-5.2# cat /etc/fedora-release
Fedora release 40 (Forty)
  • Rootless: Buildah runs the mount in another namespace, so with a driver other than vfs the mount may not be visible from the host; run the commands in a podman unshare shell.
  • On a Fedora release other than 40 you must import Fedora 40's GPG keys or add --nogpgcheck.

Add a command script and metadata, then commit:

# cat command.sh
#!/bin/bash
cat /etc/fedora-release
/usr/bin/date
# chmod +x command.sh
# buildah unmount working-container
# buildah copy working-container ./command.sh /usr/bin
# buildah config --cmd /usr/bin/command.sh working-container
# buildah config --created-by "Podman for DevOps example" working-container
# buildah config --label name=fedora-date working-container
# buildah commit working-container fedora-date
# buildah rm working-container
# podman images
localhost/fedora-date  latest  e24a2fafde  About a minute ago  366 MB
# podman run -ti localhost/fedora-date:latest
Fedora release 40 (Forty)
Tue Nov 01 21:18:29 UTC 2024

podman inspect shows labels (io.buildah.version: 1.37.3, name: fedora-date), the created_by history entry and annotations. buildah copy lets you inject files without handling the mount yourself.

[!tip] Minimal base images Building from scratch is not typical; often a Fedora or Alpine base plus packages is enough. Some distributions ship minimal flavours (e.g. fedora-minimal) with fewer packages and smaller images.

6.6 Building images from a Dockerfile

# Start from latest fedora container base image
FROM fedora:latest

# Update the container base image
RUN echo "Updating all fedora packages"; dnf -y update; dnf -y clean all

# Install the httpd package
RUN echo "Installing httpd"; dnf -y install httpd

# Expose the http port 80
EXPOSE 80

# Set the default command to run once the container will be started
CMD ["/usr/sbin/httpd", "-DFOREGROUND"]

[webserver]# buildah build -f Dockerfile -t myhttpdservice .
STEP 1/6: FROM fedora:latest
STEP 2/6: MAINTAINER podman-book # this should be an email
STEP 3/6: RUN echo "Updating all fedora packages"; dnf -y update; dnf -y clean all
STEP 4/6: RUN echo "Installing httpd"; dnf -y install httpd
STEP 5/6: EXPOSE 80
STEP 6/6: CMD ["/usr/sbin/httpd", "-DFOREGROUND"]
COMMIT myhttpdservice
Successfully tagged localhost/myhttpdservice:latest
  • -f names the Dockerfile (default Dockerfile); -t names and tags (default tag latest); the final argument is the build directory (.). (The book's listing shows six steps because its output includes a MAINTAINER step that is not in the printed Dockerfile.)
  • Run and test:
# buildah images
localhost/myhttpdservice  latest  14a2226710e7  2 minutes ago  497 MB
# podman run -d localhost/myhttpdservice:latest
# podman logs 133584ab526f...        # shows the AH00558 ServerName warning and the container IP 10.88.0.4
# curl 10.88.0.4                     # "Test Page for the HTTP Server on Fedora"
# ip a show dev cni-podman0          # inet 10.88.0.1/16: the container IP is in this network

The --layers option

  • Added in Buildah 1.2 to switch layer caching on or off. Per the book, the default is --layers=false: no intermediate layers kept, all changes squashed into one layer. Enable caching with export BUILDAH_LAYERS=true.
  • Trade-offs of keeping layers: more storage at first, but layers are shared across images (10 images with the same base layers store and pull them once), saving space and bandwidth. The downside: each layer adds union-filesystem complexity, slightly slower start and more kernel merge overhead.
  • Trade-offs of squashing: faster startup and permanent removal of files deleted in upper layers (which otherwise stay hidden but present), but it destroys deduplication, so total storage may grow with several similar images.
  • Verdict: you trade a bit of filesystem complexity for large gains in build speed and storage efficiency.
