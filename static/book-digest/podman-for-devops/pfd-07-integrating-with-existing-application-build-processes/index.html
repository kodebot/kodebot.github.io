Podman for DevOps 7: Integrating with existing application build processes

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 7. Previous: Podman for DevOps 6: Meet Buildah, building containers from scratch. Next: Podman for DevOps 8: Choosing the container base image.

Takeaways
  • Multistage builds keep images small: build in a first stage (compilers, source), copy only the artifact into a minimal runtime stage with COPY --from=<stage>. The Go example drops to 36.1 MB.
  • Buildah native commands allow variables, conditionals, loops and steps between stages (for instance extracting an artifact into a versioned archive).
  • Buildah in a container (quay.io/buildah/stable, --device /dev/fuse) suits Kubernetes and CI; the store can be a volume, a bind mount, or a read-only shared store (/var/lib/shared). It trades isolation against speed.
  • Never pass registry passwords on the command line: mount an auth.json and use --authfile.
  • Buildah's Go libraries can power a custom builder (unsupported; the stable interface is the Podman REST API). Podman also underlies Quarkus native builds.

7.1 Multistage container builds

Image size is the result of the number of layers and the number of changed files. Small images pull faster and use less local disk. Known tricks: build from scratch, clean package-manager caches, limit RUN, COPY and ADD.

  • The problem: to build a Go app you start from a base with Go runtimes, copy the source, download packages, compile, and clean up. The final image still contains the Go toolchain from the base image.
  • Old workarounds: binary builds (inject an externally compiled artifact), which shrinks the image but loses the standard compiler environment; or share volumes between containers and have the final image grab the artifacts.
  • The standard answer: Docker, then the OCI specs, introduced multistage builds: several FROM instructions, later stages copy from earlier ones.

Multistage with a Dockerfile or Containerfile

Each stage begins with FROM; use --from to name the source stage. Example (Chapter07/http_hello_world/Dockerfile):

# Builder image
FROM docker.io/library/golang

# Copy files for build
COPY go.mod /go/src/hello-world/
COPY main.go /go/src/hello-world/

# Set the working directory
WORKDIR /go/src/hello-world

# Download dependencies
RUN go get -d -v ./...

# Install the package
RUN go build -v

# Runtime image
FROM registry.access.redhat.com/ubi9/ubi-micro:latest
COPY --from=0 /go/src/hello-world/hello-world /
EXPOSE 8080

CMD ["/hello-world"]
  • Stage 1 copies main.go and go.mod, downloads dependencies and builds. Stage 2 copies the artifact into the new image root; --from=0 selects the first stage.
  • Stage 1 uses the official golang image; stage 2 uses ubi-micro, Red Hat's minimal image for microservices and statically linked binaries (Universal Base Image: chapter 8).
  • The app is a Go web server on 8080/tcp that answers GET / with an HTML page "Hello World!" (knowing Go is not required, but most container software, such as Podman, Docker, Buildah, Skopeo, Kubernetes and OpenShift, is written in Go):
package main

import (
    "log"
    "net/http"
)

func handler(w http.ResponseWriter, r *http.Request) {
    log.Printf("%s %s %s\n", r.RemoteAddr, r.Method, r.URL)
    w.Header().Set("Content-Type", "text/html")
    w.Write([]byte("<html>\n<body>\n"))
    w.Write([]byte("<p>Hello World!</p>\n"))
    w.Write([]byte("</body>\n</html>\n"))
}

func main() {
    http.HandleFunc("/", handler)
    log.Println("Starting http server")
    log.Fatal(http.ListenAndServe(":8080", nil))
}

$ cd http_hello_world
$ buildah build -t hello-world .
$ buildah images --format '{{.Name}} {{.Size}}' localhost/hello-world
localhost/hello-world 36.1 MB

Named stages with AS (file Dockerfile-builder): the builder is builder, the final stage srv, and COPY --from=builder replaces the numeric index:

# Builder image
FROM docker.io/library/golang AS builder
COPY go.mod /go/src/hello-world/
COPY main.go /go/src/hello-world/
WORKDIR /go/src/hello-world
RUN go get -d -v ./...
RUN go build -v ./...

# Runtime image
FROM registry.access.redhat.com/ubi9/ubi-micro:latest AS srv
COPY --from=builder /go/src/hello-world/hello-world /
EXPOSE 8080
CMD ["/hello-world"]

$ buildah build -f ./Dockerfile-builder -t hello-world-v2 .

Dockerfile builds are the most common but lack flexibility for custom workflows; native Buildah commands fill that gap.

Multistage with Buildah native commands

Native commands allow extra steps between stages, for instance mounting the build container's overlay to extract the artifact and release alternate packages before building the runtime image. buildah-commands.sh:

#!/bin/bash
# Define builder and runtime images
BUILDER=docker.io/library/golang
RUNTIME=registry.access.redhat.com/ubi9/ubi-micro:latest

# Create builder container
container1=$(buildah from $BUILDER)

# Copy files from host
if [ -f go.mod ]; then
    buildah copy $container1 'go.mod' '/go/src/hello-world/'
else
    exit 1
fi
if [ -f main.go ]; then
    buildah copy $container1 'main.go' '/go/src/hello-world/'
else
    exit 1
fi

# Configure and start build
buildah config --workingdir /go/src/hello-world $container1
buildah run $container1 go get -d -v ./...
buildah run $container1 go build -v ./...

# Create runtime container
container2=$(buildah from $RUNTIME)

# Copy files from the builder container
buildah copy --chown=1001:1001 \
    --from=$container1 $container2 \
    '/go/src/hello-world/hello-world' '/'

# Configure exposed ports
buildah config --port 8080 $container2

# Configure default CMD
buildah config --cmd /hello-world $container2

# Configure default user
buildah config --user=1001 $container2

# Commit final image
buildah commit $container2 helloworld

# Remove build containers
buildah rm $container1 $container2
  • Two working containers (container1, container2); buildah copy --from= names the source container and --chown sets the owner. The script adds conditionals (checking that go.mod and main.go exist).
  • Release variant (buildah-commands-release.sh): adds RELEASE=1.0.0, extracts the artifact with buildah unshare --mount (the unshare namespace lets it run rootless), writes a README, creates hello-world-${RELEASE}.tar.gz, then builds the runtime image and tags it with the release. The key part:
RELEASE=1.0.0
# ... build steps as above ...
# Extract build artifact and create a version archive
buildah unshare --mount mnt=$container1 \
    sh -c 'cp $mnt/go/src/hello-world/hello-world .'
cat > README << EOF
Version $RELEASE release notes:
- Implement basic features
EOF
tar zcf hello-world-${RELEASE}.tar.gz hello-world README
rm -f hello-world README
# ... runtime container as above ...
buildah commit $container2 hello world:$RELEASE

(The book prints hello world:$RELEASE with a space, which looks like a typo for helloworld:$RELEASE.)

Semantic versioning

X.Y.Z: major, minor, patch (https://semver.org/).

7.2 Running Buildah inside a container

  • Podman and Buildah's fork/exec design makes them easy to run in containers, including rootless. The common scenario: application builds on a Kubernetes cluster (a control plane scheduling containers on worker nodes whose engine implements the CRI).
  • Vanilla Kubernetes has no native build feature; solutions that appeared: OpenShift Source-to-Image and build APIs (from the Kubernetes 1.0 era), Google's kaniko (builds in user space in a cluster), Cloud Native Buildpacks (like Source-to-Image with advanced multi-process and bill-of-materials features), and your own Buildah in containers.
  • Tekton Pipelines (CNCF) runs CI/CD driven by Kubernetes custom resources; tasks come from Tekton Hub (https://hub.tekton.dev/), including Buildah (https://hub.tekton.dev/tekton/task/buildah).
  • Focus here: builds inside containers with attention to security. The image used is quay.io/buildah/stable (latest stable Buildah).

Rootless Buildah containers with volume stores

$ podman run --device /dev/fuse \
    -v ./http_hello_world:/build:z \
    -v storevol:/var/lib/containers quay.io/buildah/stable \
    buildah build -t build_test1 /build
Option Why
--device /dev/fuse provides the fuse device needed by fuse-overlay to mount the container filesystem
-v ./http_hello_world:/build:z bind-mounts the source with a shared SELinux label (:z)
-v storevol:/var/lib/containers a fresh volume on the default container store, where layers are created

Inspect the result from another container, or the volume on the host:

$ podman run --rm -v storevol:/var/lib/containers quay.io/buildah/stable buildah images
localhost/build_test1                      latest  3605829966b5  41 seconds ago  33.9 MB
registry.access.redhat.com/ubi9/ubi-micro  latest  e279e18c7ef8  3 days ago      26.4 MB
docker.io/library/golang                   latest  0457bb691895  9 days ago      862 MB
$ ls -alR $(podman volume inspect storevol --format '{{.Mountpoint}}')

Then tag, log in and push from a new container, and delete the volume (# podman volume rm storevol):

$ podman run --rm -v storevol:/var/lib/containers \
    quay.io/buildah/stable \
    sh -c 'buildah tag build_test1 \
    registry.example.com/build_test1 \
    && buildah login -u=<USERNAME> -p=<PASSWORD> \
    registry.example.com && \
    buildah push registry.example.com/build_test1'

Limits and fixes

  • The volume store is not isolated: any container can read it. Use SELinux MCS with :Z so only the running container can access it. A second container would run with different categories, so pass the volume's categories: --security-opt label=level:s0:<CAT1>,<CAT2>.
  • Or do build, tag and push in one container:
$ podman run --device /dev/fuse \
    -v ~/build:/build \
    -v secure_storevol:/var/lib/containers:Z \
    quay.io/buildah/stable \
    sh -c 'buildah build -t test2 /build && \
    buildah tag test2 registry.example.com/build_test2 && \
    buildah login -u=<USERNAME> -p=<PASSWORD> registry.example.com && \
    buildah push registry.example.com/build_test2'
Passwords on the command line are not acceptable practice

Mount the authentication file with a session token instead:

$ podman run --device /dev/fuse \
    -v ~/build:/build \
    -v /run/user/<UID>/containers/auth.json:/auth.json:z \
    -v secure_storevol:/var/lib/containers:Z \
    quay.io/buildah/stable \
    sh -c 'buildah build -t test3 /build && \
    buildah tag test3 registry.example.com/build_test3 && \
    buildah push --authfile /auth.json \
    registry.example.com/build_test3'
  • Authenticate on the host first: $ podman login -u <USERNAME> -p <PASSWORD> <REGISTRY>; the token is stored in /run/user/<UID>/containers/auth.json (a tmpfs), a JSON object {"auths": {"registry.example.com": {"auth": "<base64_encoded_token>"}}}.
  • Security alert: if that file has records for several registries, all of them are exposed inside the build container, which could then authenticate to each.
  • The volume approach costs a little performance versus a native host build, but gives better isolation, a smaller attack surface (rootless) and a standardised build environment across hosts.

Bind-mounted stores

Highest isolation (zero trust): every build container has its own store, created for the build and destroyed after, with SELinux MCS. Create a unique store (run as root):

# BUILD_STORE=/var/lib/containers-$(echo $RANDOM | md5sum | head -c 8)
# mkdir $BUILD_STORE
# podman run --device /dev/fuse \
    -v ./build:/build:z \
    -v $BUILD_STORE:/var/lib/containers:Z \
    -v /run/containers/0/auth.json:/auth.json \
    quay.io/buildah/stable \
    sh -c 'set -euo pipefail; \
    buildah build -t registry.example.com/test4 /build; \
    buildah push --authfile /auth.json \
    registry.example.com/test4'

Best isolation, slowest (base-image layers are re-pulled on every build, never cached).

The opposite, fastest and least isolated: mount the host store itself, and disable SELinux separation for the container:

# podman run --device /dev/fuse \
    -v ./build:/build:z \
    -v /var/lib/containers:/var/lib/containers \
    --security-opt label=disable \
    -v /run/containers/0/auth.json:/auth.json \
    quay.io/buildah/stable \
    sh -c 'set -euo pipefail; \
    buildah build -t registry.example.com/test5 /build; \
    buildah push --authfile /auth.json \
    registry.example.com/test5'

Compromise: a secondary read-only image store. Buildah supports several image stores; the stable image's /etc/containers/storage.conf already points additionalimagestores at /var/lib/shared:

# AdditionalImageStores is used to pass paths to additional Read/Only image stores
# Must be comma separated list.
additionalimagestores = [
    "/var/lib/shared",
]

Bind-mount the host store there read-only: good isolation plus cached images. The store can be pre-populated with the most used images or mounted from a network share:

# podman run --device /dev/fuse \
    -v ./build:/build:z \
    -v $BUILD_STORE:/var/lib/containers:Z \
    -v /var/lib/containers/storage:/var/lib/shared:ro \
    -v /run/containers/0/auth.json:/auth.json:z \
    quay.io/buildah/stable \
    bash -c 'set -euo pipefail; \
    buildah build -t registry.example.com/test6 /build; \
    buildah push --authfile /auth.json \
    registry.example.com/test6'

The examples draw on an article by Dan Walsh (one of the Buildah and Podman project leads) on the Red Hat Developer blog (link in Further reading).

Store approach Isolation Speed
Per-build bind-mounted store with :Z highest slowest (re-pulls base layers)
Host store with label=disable lowest fastest (cached layers)
Per-build store plus read-only /var/lib/shared good good

Native Buildah commands inside containers

# BUILD_STORE=/var/lib/containers-$(echo $RANDOM | md5sum | head -c 8)
# mkdir $BUILD_STORE
# podman run --device /dev/fuse \
    -e REGISTRY=<USER_DEFINED_REGISTRY:PORT> \
    --security-opt label=disable \
    -v $BUILD_STORE:/var/lib/containers:Z \
    -v /var/lib/containers/storage:/var/lib/shared:ro \
    -v /run/containers/0:/run/containers/0 \
    quay.io/buildah/stable \
    sh -c 'set -euo pipefail; \
    container=$(buildah from fedora); \
    buildah run $container dnf install -y python3 python3; \
    buildah commit $container $REGISTRY/python_demo; \
    buildah push --authfile \
    /run/containers/0/auth.json $REGISTRY/python_demo'

(The book prints -authfile with one dash and python3 python3, apparently typos.) For many commands, put them in a script and inject it with a volume:

# BUILD_STORE=/var/lib/containers-$(echo $RANDOM | md5sum | head -c 8)
# PATH_TO_SCRIPT=/path/to/script
# REGISTRY=<USER_DEFINED_REGISTRY:PORT>
# mkdir $BUILD_STORE
# podman run --device /dev/fuse \
    -v $BUILD_STORE:/var/lib/containers:Z \
    -v /var/lib/containers/storage:/var/lib/shared:ro \
    -v /run/containers/0:/run/containers/0 \
    -v $PATH_TO_SCRIPT:/root:z \
    quay.io/buildah/stable /root/build.sh

7.3 Integrating Buildah with custom builders

Podman inherits Buildah's build capabilities through podman build; likewise you can embed Buildah's interfaces and engine in your own builder, easiest in Go (the language of Podman, Buildah and most of the ecosystem).

Unsupported scenario

Stability of the Buildah Go APIs (deprecations, changes) is not guaranteed. For supported, stable use cases, use the Podman REST APIs.

Including Buildah in a Go build tool

Prepare the environment and project:

# dnf install -y golang git go-md2man btrfs-progs-devel gpgme-devel device-mapper-devel
$ mkdir ~/custombuilder
$ cd ~/custombuilder
[custombuilder]$ export GOPATH=`pwd`

Get the code from https://github.com/PacktPublishing/Podman-for-DevOps (git clone), copy Chapter07/* into ~/custombuilder/. The module directory ~/custombuilder/src/builder contains custombuilder.go, go.mod, go.sum and script.js. Fetch dependencies:

$ go mod tidy -v
go: finding module for package github.com/containers/storage/pkg/unshare
go: finding module for package github.com/containers/image/v5/storage[...omitted output...]

(It downloads modules from the internet, so be patient.) On Fedora 40 you may also need btrfs-progs-devel and libgpgme-devel; see https://podman.io/docs/installation#build-and-run-dependencies.

Key parts of custombuilder.go:

  1. Rootless support at the start of main (Go unshare package, github.com/containers/storage/pkg/unshare):
if buildah.InitReexec() {
    return
}
unshare.MaybeReexecUsingUserNamespace(false)
  1. A store (storage.Store from github.com/containers/storage) holds intermediate and result images:
buildStoreOptions, err := storage.DefaultStoreOptions()
buildStore, err := storage.GetStore(buildStoreOptions)
  1. BuilderOptions: starting image node:23-alpine (a Node.js app simulation), chroot isolation ("less isolation but fewer requirements"), default build, network and system contexts (SystemContext carries values from configuration files):
builderOpts := buildah.BuilderOptions{
    FromImage:        "node:23-alpine",      // Starting image
    Isolation:        define.IsolationChroot, // Isolation environment
    CommonBuildOpts:  &define.CommonBuildOptions{},
    ConfigureNetwork: define.NetworkDefault,
    SystemContext:    &types.SystemContext{},
}
builder, err := buildah.NewBuilder(context.TODO(), buildStore, builderOpts)
  1. Add the application file (a JavaScript file kept next to the module) into /home/node/, the default location the base image expects, and set the command:
err = builder.Add("/home/node/", false, buildah.AddAndCopyOptions{}, "script.js")
builder.SetCmd([]string{"node", "/home/node/script.js"})

script.js: an HTTP server on 8080 returning the Node.js version:

var http = require("http");
http.createServer(function(request, response) {
    response.writeHead(200, {"Content-Type": "text/plain"});
    response.write("Hello Podman and Buildah friends. This page is provided to you through a container running Node.js version: ");
    response.write(process.version);
    response.end();
}).listen(8080);
  1. Commit with an image reference and name:
imageRef, err := is.Transport.ParseStoreReference(buildStore, "podmanbook/nodejs-welcome")
imageId, _, _, err := builder.Commit(context.TODO(), imageRef, define.CommitOptions{})
fmt.Printf("Image built! %s\n", imageId)

Run and test:

[builder]$ go run custombuilder.go
Image built! e60fa98051522a51f4585e46829ad6a18df704dde774634dbc010baae4404849
[builder]$ podman run -dt -p 8080:8080/tcp podmanbook/nodejs-welcome:latest
[builder]$ curl localhost:8080
Hello Podman and Buildah friends. This page is provided to you through a container running Node.js version: v23.1.0

(-d detached, -t pseudo-TTY, -p publish the port.) More in the Go docs: https://pkg.go.dev/github.com/containers/buildah.

Running Quarkus native executables in containers

  • Quarkus is a Kubernetes-native Java stack built on OpenJDK and GraalVM (a JVM that compiles Java apps for fast startup and low memory). Its native-image tutorial uses a Maven wrapper that calls Podman:
$ ./mvnw package -Pnative -Dquarkus.native.container-build=true -Dquarkus.native.container-runtime=podman
  • The wrapper invokes a Podman build with a preconfigured Quarkus environment and your binary. It works because podman build vendors Buildah's logic (chapter 6). Guide: https://quarkus.io/guides/building-native-image.
