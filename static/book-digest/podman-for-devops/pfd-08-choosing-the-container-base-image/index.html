Podman for DevOps 8: Choosing the container base image

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 8. Previous: Podman for DevOps 7: Integrating with existing application build processes. Next: Podman for DevOps 9: Pushing images to a container registry.

Takeaways
  • A base image is the operating-system layer your application depends on, so choose it for security and updates.
  • The OCI image = manifest, optional image index, filesystem layers, configuration. The manifest gives a hashable ID, enables multi-architecture images, and maps to the runtime spec.
  • Prefer official images and registries with vulnerability scans (Docker Hub with Scout; Quay.io with Clair; Red Hat Ecosystem Catalog). Read the Dockerfile and the scan before you run an image.
  • Control sources with registries.conf: unqualified vs fully qualified names, [[registry]] prefix/location/insecure/blocked, mirrors, and short-name aliases.
  • Red Hat UBI is the freely redistributable RHEL-based base in four flavours: Standard (~230 MiB, yum), Minimal (microdnf, about half), Micro (distroless, no package manager), Init (systemd as PID 1).

8.1 The Open Container Initiative image format

  • Recap: 2013 Docker introduced images and registries; its containerd was extracted and donated to the CNCF; in 2015 Docker with Red Hat, AWS, Google, Microsoft, IBM and others formed the OCI under the Linux Foundation. It produced the runtime-spec and image-spec, then runc as the first runtime implementation.
  • An OCI image consists of:
    • Manifest: metadata of contents and dependencies, identifying one or more filesystem archives to unpack into the runnable filesystem.
    • Image index (optional): a list of manifests and descriptors giving different implementations by target platform.
    • Set of filesystem layers: merged to build the final filesystem.
    • Configuration: what the runtime needs to run the app (arguments, environment variables).

OCI image manifest

It defines the layers and configuration of one image for one architecture and OS:

{
  "schemaVersion": 2,
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "size": 7023,
    "digest": "sha256:b5b2b2c507a0944348e0303114d8d93aaaa081732b86451d9bce1f432a537bc7"
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "size": 32654,
      "digest": "sha256:9834876dcfb05cb167a5c24953eba58c4ac89b1adf57f28f2f9d09af107ee8f0"
    }
  ],
  "annotations": {
    "com.example.key1": "value1",
    "com.example.key2": "value2"
  }
}
Key Meaning
schemaVersion must be 2, for backward compatibility with Docker
config references the image configuration through a digest; mediaType gives the format (just one currently)
layers array of descriptors; each mediaType must be an allowed layer media type
annotations extra metadata for the manifest

Three goals of the spec:

  1. Hash the image configuration to produce a unique ID.
  2. Allow multi-architecture images through the high-level manifest (image index) pointing to platform-specific manifests.
  3. Translate easily into the OCI Runtime Specification.

8.2 Where do container images come from?

Docker introduced images and public registries; other cloud registries followed:

Registry type Details
Docker Hub Docker Inc.'s hosted registry; hosts official repositories and security-verified images of popular open source projects
Quay.io born at CoreOS, now Red Hat; private and public repositories, automated security scanning, image builds, integration with public Git repositories
Linux distribution registries community (Fedora) or enterprise (RHEL); usually only for projects already packaged by the distribution; fed by maintainers, not open to end users
Public cloud registries Amazon, Google, Microsoft and others offer public and private registries

Chapter 9 explores them further. Docker Hub and Quay.io host images created by anyone, handy for quick tests, but just pulling and running one is risky: outdated software with known vulnerabilities, or malicious code that compromises the infrastructure. Both registries offer features showing where an image comes from.

Docker Hub

  • Official Image tag after the name: images in Docker's Official Images program are curated by the Docker team with upstream maintainers. The image page shows the latest tags, supported architectures and links to documentation and issue tracking (e.g. https://hub.docker.com/_/alpine; Figure 8.1).
  • You can read the Dockerfile behind any tag: the edge tag leads to https://github.com/alpinelinux/docker-alpine/blob/edge/x86_64/Dockerfile. Always prefer official images; if none fits, inspect the publisher's Dockerfile and image.
  • Docker Scout: scans images for vulnerabilities, gives remediation advice, integrates with CI/CD.
  • Limits: non-paying authenticated and unauthenticated users face limits, commonly the number of images pulled per hour (https://docs.docker.com/docker-hub/download-rate-limit/).

Quay.io

  • Quay was acquired by CoreOS in 2014, now part of Red Hat. Quay.io is the managed SaaS of the open source Quay.
  • It adopts Clair, a leading container vulnerability scanner, with reports on the repository tags page (SECURITY SCAN; Figure 8.2; example https://quay.io/repository/openshift-release-dev/ocp-release?tab=tags).
  • At the time of writing: no pull limits; the free tier has five private repositories and unlimited public ones.

Red Hat Container Registry

  • Default registry for RHEL and OpenShift Container Platform (OCP). The web interface is public, but almost all images are reserved for paying users. It offers official Red Hat images, Containerfile/Dockerfile sources, and security reports per image.
  • The Red Hat Ecosystem Catalog page for an image (Figures 8.3 to 8.5; example MariaDB https://catalog.redhat.com/software/containers/rhel9/mariadb-105/61a6084dbfd4a5234d596220) shows description, version, architectures and tags, with Security and Dockerfile tabs. The Security tab lists vulnerability scan status (at the time of writing a vulnerability affecting three packages) with a Red Hat Advisory ID linked to public CVEs.
  • UBI (Universal Base Image; Figure 8.6, https://catalog.redhat.com/software/containers/ubi9/ubi/615bcf606feffc5384e8452e): a Red Hat initiative that lets every user, customer or not, use Red Hat container images, with the catalog's services and Red Hat package updates. One UBI version per RHEL release.

8.3 Trusted container image sources

  • Running a pulled image without control means implicitly trusting the author not to have tampered with it. Chapter 10 covers attacks from containers: privilege escalation, data exfiltration, crypto miners; in Kubernetes clusters, malicious pods can spread across the infrastructure.
  • The MITRE ATT&CK matrices list attack strategies and techniques with real cases, detection and mitigation; one matrix is for containers, with techniques that rely on insecure images.
  • Prefer registries that support vulnerability scans, read the results, and avoid images with critical vulnerabilities.
  • The first step to a secure cloud-native infrastructure: pull only from trusted sources, configure trusted registries and block disallowed ones.

Managing trusted registries

/etc/containers/registries.conf (overridden by $HOME/.config/containers/registries.conf) lists registries Podman may contact:

unqualified-search-registries = ["docker.io", "quay.io"]

[[registry]]
location = "registry.example.com:5000"
insecure = false
  • Fully qualified image: registry FQDN, namespace, name and tag, e.g. docker.io/library/nginx:latest: unambiguous.
  • Unqualified image: only the name (nginx); several candidates may exist across searched registries; most podman search nginx results are not official, so analyse them and filter by OFFICIAL and stars (more is better).
  • unqualified-search-registries is the search list for unqualified images. Removing a registry stops Podman searching it, but Podman can still pull a fully qualified image from it.

[[registry]] TOML tables (per registry or image pattern):

Setting Role
prefix image name pattern: host[:port]/namespace[/namespace...]/repo(:tag|@digest), or simpler host[:port], host[:port]/namespace, [*.]host; with two partially matching prefixes the longest match wins
insecure true allows unencrypted HTTP or TLS with untrusted certificates
blocked true blocks registries or images matching the prefix
location the registry's location; defaults to prefix; if different, a matching prefix resolves to this location

Mirrors with [[registry.mirror]] tables: Podman tries the mirrors first, then falls back to location.

unqualified-search-registries = ["docker.io", "quay.io"]

[[registry]]
location = "registry.example.com:5000/foo"
insecure = false

[[registry.mirror]]
location = "mirror1.example.com:5000/bar"

[[registry.mirror]]
location = "mirror2.example.com:5000/bar"

Pulling registry.example.com:5000/foo/app:latest tries mirror1.example.com:5000/bar/app:latest, then mirror2..., then the main location. With a prefix (prefix = "example.com/foo", same location and mirrors), pulling example.com/foo/app:latest goes through the mirrors, then registry.example.com:5000/foo/app:latest.

Private mirrors in disconnected environments remap public registries:

[[registry]]
prefix = "quay.io"
location = "mirror-internal.example.com/quay"

[[registry]]
prefix = "docker.io"
location = "mirror-internal.example.com/docker"
Keep mirrors current

Blocking (an image, a namespace, or a whole registry):

# whole registry
[[registry]]
location = "registry.rogue.io"
blocked = true

# a namespace: blocks quay.io/foo/nginx:latest and quay.io/foo/httpd:v2.4, not quay.io/bar/fedora:latest
[[registry]]
prefix = "quay.io/foo/"
location = "quay.io"
blocked = true

# a single image tag
[[registry]]
prefix = "internal-registry.example.com/dev/app:v0.1"
location = "internal-registry.example.com"
blocked = true

Combine blocking rules with mirror tables. With many machines running Podman (developer workstations), keep the file updated with configuration-management tools and apply the filters declaratively.

Short-name aliases

  • Fully qualified names such as quay.io/podman/stable:latest are the gold standard for security and automation but cumbersome to type. For an unqualified name (podman pull fedora) Podman would walk the registries search list, which can be slow and, if misconfigured, insecure.
  • Aliases short-circuit the search: a matching short name resolves immediately to the mapped fully qualified name, bypassing the search registries entirely. Fedora and RHEL ship a large trusted list at /etc/containers/registries.conf.d/000-shortnames.conf, maintained by the community and OS vendors:
[aliases]
"fedora" = "registry.fedoraproject.org/fedora"
"ubi8" = "registry.access.redhat.com/ubi8"
"alpine" = "docker.io/library/alpine"
  • Add custom aliases in extra files under /etc/containers/registries.conf.d/ to keep the main file clean.
  • Boundaries: aliases resolve the repository path, not a version: if my-app aliases quay.io/org/my-app, podman pull my-app:v2 resolves to quay.io/org/my-app:v2. Local user aliases (e.g. $HOME/.config/containers/registries.conf.d/) typically override the system ones.

Blocking untrusted sources is a security best practice but does not replace choosing an image that is trustworthy with the smallest attack surface; UBI helps here.

8.4 Introducing the Universal Base Image

  • Why UBI: many enterprises use RHEL; RHEL-based images share the OS release's package versions and get RHEL security updates immediately. But RHEL images are not public without a subscription and cannot be freely redistributed without breaking the Red Hat enterprise agreement. Red Hat created UBI: freely redistributable, usable for applications, middleware and utilities, continuously maintained and upgraded.
  • UBI images are based on currently supported RHEL versions (UBI 8, 9 and 10 for RHEL 8, 9 and 10 at the time of writing) and are in effect a subset of RHEL. They are on registry.access.redhat.com and docker.io.
  • Bridge from development to production: build on a Fedora laptop or a cloud CI/CD pipeline and deploy to production RHEL or OpenShift with no compatibility concerns, and share anywhere including public registries without a subscription.

Four flavours

Flavour Description
Standard most features and package availability; closest to RHEL
Minimal stripped down, minimal package management
Micro smallest footprint, no package manager
Init includes systemd to run multiple services in one container

UBI Standard

  • Has yum; customise with packages from ubi-8-baseos and ubi-8-appstream. Includes a curated set of tools (curl, tar, vi, sed, gzip) and OpenSSL libraries, about 230 MiB: fewer packages mean a lighter image and smaller attack surface.
FROM registry.access.redhat.com/ubi8

# Update image and install httpd
RUN yum update -y && yum install -y httpd && yum clean all

# Expose the default httpd port 80
EXPOSE 80

# Run the httpd
CMD ["/usr/sbin/httpd", "-DFOREGROUND"]

UBI Minimal

  • Built for self-consistent applications and runtimes (Python, Ruby, Node.js). About half the size of Standard; no yum, replaced by microdnf.
# Based on the UBI8 Minimal image
FROM registry.access.redhat.com/ubi8-minimal

# Upgrade and install Python 3
RUN microdnf upgrade && microdnf install python3

# Copy source code
COPY entrypoint.sh http_server.py /

# Expose the default httpd port 80
EXPOSE 8080

# Configure the container entrypoint
ENTRYPOINT ["/entrypoint.sh"]

# Run the httpd
CMD ["/usr/bin/python3", "-u", "/http_server.py"]

The Python web server prints "Hello World!" on GET and handles SIGTERM and SIGINT so the container stops gracefully:

#!/usr/bin/python3
import http.server
import socketserver
import logging
import sys
import signal
from http import HTTPStatus

port = 8080
message = b'Hello World!\n'
logging.basicConfig(
    stream=sys.stdout,
    level=logging.INFO
)

def signal_handler(signum, frame):
    sys.exit(0)

class Handler(http.server.SimpleHTTPRequestHandler):
    def do_GET(self):
        self.send_response(HTTPStatus.OK)
        self.end_headers()
        self.wfile.write(message)

if __name__ == "__main__":
    signal.signal(signal.SIGTERM, signal_handler)
    signal.signal(signal.SIGINT, signal_handler)
    try:
        httpd = socketserver.TCPServer(('', port), Handler)
        logging.info("Serving on port %s", port)
        httpd.serve_forever()
    except SystemExit:
        httpd.shutdown()
        httpd.server_close()

The entry point is minimal; the -u flag on Python makes output unbuffered so access logs appear in real time:

#!/bin/bash
set -e
exec $@

$ buildah build -t python_httpd .
$ podman run -p 8080:8080 python_httpd
INFO:root:Serving on port 8080

UBI Micro

  • The newest: a distroless image with a stripped-down package manager, minimal attack surface, little data to download on first use or update. Great in multistage builds (build in one stage, copy into Micro):
# Builder image
FROM registry.access.redhat.com/ubi8-minimal AS builder

# Install Golang packages
RUN microdnf upgrade && \
    microdnf install golang && \
    microdnf clean all

# Copy files for build
COPY go.mod /go/src/hello-world/
COPY main.go /go/src/hello-world/

# Set the working directory
WORKDIR /go/src/hello-world

# Download dependencies
RUN go get -d -v ./...

# Install the package
RUN go build -v ./...

# Runtime image
FROM registry.access.redhat.com/ubi8/ubi-micro:latest
COPY --from=builder /go/src/hello-world/hello-world /

EXPOSE 8080

CMD ["/hello-world"]

The result is about 45 MB. (The book's comment says the build runs in a "UBI Standard container", but the code uses ubi8-minimal.)

  • Adding packages to Micro with Buildah: it has no package manager, but on RHEL (with Red Hat GPG keys) you can install into the mounted root with the host's yum:
#!/bin/bash

set -euo pipefail

if [ $UID -ne 0 ]; then
    echo "This script must be run as root"
    exit 1
fi

container=$(buildah from registry.access.redhat.com/ubi8/ubi-micro)
mount=$(buildah mount $container)

yum install -y \
    --installroot $mount \
    --setopt install_weak_deps=false \
    --nodocs \
    --noplugins \
    --releasever 8 \
    python3

yum clean all --installroot $mount

buildah umount $container
buildah commit $container micro_python3

--installroot $mount makes the working container's mount point the temporary root. Minimal and Micro suit microservice architectures with one container per service.

UBI Init

  • The normal pattern is one component per container, each doing one thing (the KISS philosophy from UNIX), with multi-tier apps as several orchestrated containers. Exceptions: processes that need to share all container namespaces, or a single "uber image".
  • Container images normally have no init system; the CMD process gets PID 1. UBI Init runs a minimal systemd inside, so several systemd units run under PID 1. It is slightly smaller than Standard but has more packages than Minimal.
  • Default CMD is /sbin/init. systemd ignores SIGTERM and SIGKILL (what Podman uses to stop containers), so the image sets STOPSIGNAL SIGRTMIN+3.
FROM registry.access.redhat.com/ubi8/ubi-init

RUN yum -y install httpd && \
    yum clean all && \
    systemctl enable httpd

RUN echo "Successful Web Server Test" > /var/www/html/index.html

RUN mkdir /etc/systemd/system/httpd.service.d/ && \
    echo -e '[Service]\nRestart=always' > /etc/systemd/system/httpd.service.d/httpd.conf

EXPOSE 80
CMD [ "/sbin/init" ]

$ buildah build -t init_httpd .
$ podman run -d --name httpd_init -p 8080:80 init_httpd
$ podman exec -ti httpd_init /bin/bash
[root@b4fb727f1907 /]# ps aux
root     1   /sbin/init
root     10  /usr/lib/systemd/systemd-journald
root     20  /usr/sbin/httpd -DFOREGROUND
dbus     21  /usr/bin/dbus-daemon --system --address=systemd: --nofork --nopidfile --systemd-activation --syslog-only
apache   23  /usr/sbin/httpd -DFOREGROUND   (plus workers 24, 25, 26)
root     238 /bin/bash

/sbin/init is PID 1 and spawns httpd; dbus-daemon lets systemd expose its API, and systemd-journald handles logs. The unit-file edit could instead be a copy of pre-edited unit files when several services are needed.

Other UBI-based images

  • Red Hat builds many pre-built runtime images on UBI (Python, Quarkus, Golang, Perl, PHP, .NET, Node.js, Ruby, OpenJDK), usually without redistribution limits.
  • UBI is the base of the Source-to-Image (S2I) framework that builds applications natively in OpenShift without Dockerfiles (assemble images from custom scripts and source code).
  • Red Hat's supported Buildah, Podman and Skopeo container releases use UBI 8 images.
  • Other vendors use UBI too for official images on the Red Hat Marketplace: Intel, IBM, Isovalent, Cisco, Aqua Security and others.
