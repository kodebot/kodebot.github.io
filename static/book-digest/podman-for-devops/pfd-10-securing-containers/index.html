Podman for DevOps 10: Securing containers

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 10 (last chapter of Part 2). Previous: Podman for DevOps 9: Pushing images to a container registry. Next: Podman for DevOps 11: Troubleshooting and monitoring containers.

Takeaways
  • Rootless containers map the user to UID 0 in a user namespace via /etc/subuid and /etc/subgid (default 65,536 IDs): an escaped process gets only that user's privileges.
  • Don't run as UID 0 inside the container either: use USER in the Containerfile and fix permissions (ports below 1024 are not allowed for unprivileged users).
  • Sign images (Sigstore with Cosign keys, or GPG), store signatures as OCI artifacts in the registry (Podman 5.x), and enforce with policy.json (sigstoreSigned, signedBy); the default insecureAcceptAnything accepts everything. Rekor adds a public transparency log.
  • Capabilities split root into units; Podman gives containers a default set; tune with --cap-add and --cap-drop (dropping CHOWN breaks nginx).
  • SELinux: container processes run as container_t; Udica generates a custom profile from a container's spec instead of relabelling directories or going permissive.

10.1 Running rootless containers with Podman

Rootless containers (standard users without administrative privileges) bring:

  • An extra security layer against attackers trying to gain root on the host even if the engine, runtime or orchestrator is compromised. A container escape (any flaw letting a process leave its security constraints) in a rootless container yields only non-root user privileges.
  • Many unprivileged users running containers on the same host, useful for high-performance computing environments.

The same least-privilege logic as services: installing Apache normally creates a dedicated apache user. Podman is daemonless, so it just creates a child process, with no extra privilege escalation.

subuid and subgid

Modern shadow-utils use /etc/subuid and /etc/subgid to decide which UIDs and GIDs can be mapped into a user namespace; the default allocation is 65,536 UIDs and 65,536 GIDs per user.

$ id
uid=1000(alex) gid=1000(alex) groups=1000(alex),10(wheel)
$ podman run alpine cat /proc/self/uid_map /proc/self/gid_map
0       1000          1
1     100000      65536
0       1000          1
1     100000      65536
  • Container UID/GID 0 maps to the current user (1000); UID/GID 1 onward map from 100000 to 165536 (start plus range 65,536).
  • Compare with the host:
$ cat /proc/self/uid_map /proc/self/gid_map
0 0 4294967295
0 0 4294967295

Start 0 on both sides covering the full 32-bit range (4294967295): no translation, UID 1000 on the host is 1000 to the process.

10.2 Avoiding running containers with UID 0

  • Runtimes can run the container process as a user other than the one that created it. A vulnerability in the engine or kernel could let UID 0 in the container break out and become UID 0 on the host; a non-zero UID limits privilege escalation inside and outside the container.
  • Containerfiles default to root (UID 0). Use the USER instruction (e.g. USER 1001). In the worst case an escape reaches the files and resources of the host user with that same UID. Forcing a UID means adjusting permissions of any file, folder or mount you use.

Worked example: adapt nginx to run as a normal user.

server {
    listen 80;

    location / {
        default_type text/plain;
        expires -1;
        return 200 'Hello Podman user!\nServer address: $server_addr:$server_port\n';
    }
}

Dockerfile (root version), built as nginx-root:

FROM docker.io/library/nginx:mainline-alpine
RUN rm /etc/nginx/conf.d/*
ADD hello-podman.conf /etc/nginx/conf.d/

$ buildah bud -t nginx-root:latest -f .
$ podman run --name myrootnginx -p 127.0.0.1::80 -d nginx-root
$ podman port myrootnginx 80
127.0.0.1:38029
$ curl localhost:38029
Hello Podman user!
Server address: 10.0.2.100:80
$ podman exec 364ec7f5979a id
uid=0(root) gid=0(root)

The container runs as root. Now the fix, step by step:

  1. Change the port to 8080 in the config (listen 8080;): unprivileged users cannot bind ports below 1024.
  2. Edit the Dockerfile: fix permissions of the main folder and PID file, expose 8080, set the user:
FROM docker.io/library/nginx:mainline-alpine
RUN rm /etc/nginx/conf.d/*
ADD hello-podman.conf /etc/nginx/conf.d/

RUN chmod -R a+w /var/cache/nginx/ \
    && touch /var/run/nginx.pid \
    && chmod a+w /var/run/nginx.pid
EXPOSE 8080
USER nginx

$ buildah bud -t nginx-user:latest -f .
$ podman run --name myusernginx -p 127.0.0.1::8080 -d nginx-user
$ podman port myusernginx 8080
127.0.0.1:42209
$ curl 127.0.0.1:42209
Hello Podman user!
Server address: 10.0.2.100:8080
$ podman exec 299e0fb727f3 id
uid=101(nginx) gid=101(nginx) groups=101(nginx)

The process now runs as the unprivileged nginx user. Ready-made example: https://github.com/PacktPublishing/Podman-for-DevOps.

10.3 Signing our container images

  • Pulling from external registries exposes you to attack tactics against containers (see MITRE ATT&CK [1]), notably masquerading (manipulating image components to look legitimate) and man-in-the-middle (MITM) attacks over the wire.
  • Best mitigation: a detached image signature to trust the provider and guarantee reliability. When pulling, Podman can verify signatures and reject images without valid ones.

Signing with Sigstore and Podman

Key pair recap: a private key (never shared) signs; the public key (shared) verifies that the image was not tampered with and truly came from the sender. The image owner pushes to the registry and stores the detached signature where users can fetch it; the registry holds image blobs, the signature store holds signatures.

Cosign is a lightweight tool for signing and verifying container images, following OCI standards. Install on a Fedora-like system:

$ LATEST_VERSION=$(curl https://api.github.com/repos/sigstore/cosign/releases/latest | grep tag_name | cut -d : -f2 | tr -d "v\", ")
$ curl -O -L "https://github.com/sigstore/cosign/releases/latest/download/cosign-${LATEST_VERSION}-1.x86_64.rpm"
$ sudo rpm -ivh cosign-${LATEST_VERSION}-1.x86_64.rpm
$ cosign version        # example output: GitVersion v3.0.4, GoVersion go1.25.5, linux/amd64

Generate a key pair (it asks for a passphrase; unlike GPG it just writes two files in the current directory, already in PEM format):

$ cosign generate-key-pair
Private key written to cosign.key
Public key written to cosign.pub

cosign.pub goes into the verification policy; cosign.key must be kept secure (it signs your pushes).

Run a plain local registry to push test images (as root):

$ mkdir ./registry_data
$ podman run -d \
    --name local_registry \
    -p 5000:5000 \
    -v ./registry_data:/var/lib/registry:z \
    --restart=always registry:2

The registry itself is unaware of detached signatures. Podman writes them to a staging sigstore configured in /etc/containers/registries.d/default.yaml:

default-docker:
  # sigstore: file:///var/lib/containers/sigstore
  sigstore-staging: file:///var/lib/containers/sigstore
  use-sigstore-attachments: true
  • sigstore-staging must be a writable folder (customisable); use-sigstore-attachments: true lets Podman upload signatures as sidecar files in OCI artifact format. Rootless users set a custom path in $HOME/.config/containers/registries.d/default.yaml.
  • Podman 5.x: the preferred method stores signatures directly in the registry as OCI artifacts, so no separate sigstore directory or cross-user permission worries; rootless users can sign and push as long as they can read cosign.key.

The example image (Chapter11/image_signature/Dockerfile, a path the book prints for this chapter):

FROM registry.access.redhat.com/ubi9
# Update image and install httpd
RUN yum install -y httpd && yum clean all
# Expose the default httpd port 80
EXPOSE 80
# Run the httpd
CMD ["/usr/sbin/httpd", "-DFOREGROUND"]

$ cd Chapter11/image_signature
$ podman build -t custom_httpd .
$ podman tag custom_httpd localhost:5000/custom_httpd
$ podman push \
    --tls-verify=false \
    --sign-by-sigstore-private-key ./cosign.key \
    localhost:5000/custom_httpd
Creating signature: Signing image using a sigstore signature
Storing signatures

Configuring Podman to pull signed images

Podman needs access to the signature (in a store, or in the registry) and to the public key. Enable sigstore attachments for the registry in /etc/containers/registries.d/default.yaml (the printed listing is flattened and shows a stray http://localhost:8080/; reconstructed here):

docker:
  localhost:5000:
    use-sigstore-attachments: true

External signature stores for other registries, e.g. the public Red Hat registry:

docker:
  registry.access.redhat.com:
    sigstore: https://access.redhat.com/webassets/docker/content/sigstore

Verification rules live in /etc/containers/policy.json. This one requires a valid Sigstore signature for any image from localhost:5000 (the book prints " sigstoreSigned " with stray spaces):

{
  "default": [
    {
      "type": "insecureAcceptAnything"
    }
  ],
  "transports": {
    "docker": {
      "localhost:5000": [
        {
          "type": "sigstoreSigned",
          "keyPath": "/etc/pki/containers/cosign.pub",
          "signedIdentity": { "type": "matchRepository" }
        }
      ]
    },
    "docker-daemon": {
      "": [
        {
          "type": "insecureAcceptAnything"
        }
      ]
    }
  }
}
  • The public key must exist at keyPath and be readable by Podman.
  • default is the global fallback: with no specific rule for a registry, insecureAcceptAnything makes Podman perform no cryptographic checks: "the equivalent of leaving your front door wide open and hanging a Welcome sign". Most distributions ship it for a smooth out-of-box experience.
$ podman pull --tls-verify=false localhost:5000/custom_httpd
Checking if image destination supports signatures
Writing manifest to image destination
Storing signatures

Succeeds after verifying the signature; a missing or tampered signature would be rejected.

Testing signature verification failures

A policy is only as good as its ability to block untrusted content. First podman rmi localhost:5000/custom_httpd to force a pull and check.

# unsigned image
$ podman tag custom_httpd localhost:5000/custom_httpd:unsigned
$ podman push --tls-verify=false localhost:5000/custom_httpd:unsigned
$ podman pull --tls-verify=false localhost:5000/custom_httpd:unsigned
Error: unable to copy from source docker://localhost:5000/custom_httpd:unsigned: Source image rejected: A signature was required, but no signature exists

# wrong public key: generate a dummy key, point keyPath at dummy.pub, pull again
$ cosign generate-key-pair --output-key-prefix dummy
$ podman pull --tls-verify=false localhost:5000/custom_httpd
Error: Source image rejected: Invalid signature: key mismatch

These confirm Podman enforces trust, preventing MITM attacks and accidental deployment of unvetted images. Restore the valid public key in policy.json afterwards.

Managing trust with podman image trust

Hand-editing policy.json is error-prone and hard to automate; use podman image trust:

$ podman image trust show
TRANSPORT      NAME             TYPE            ID   STORE
all            default          accept
repository     localhost:5000   sigstoreSigned  N/A
docker-daemon                   accept

Add Red Hat's public GPG key to check UBI signatures:

$ sudo wget -O /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat \
    https://www.redhat.com/security/data/fd431d51.txt
$ sudo podman image trust set -f /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat registry.access.redhat.com/ubi9

(Red Hat product signing keys: https://access.redhat.com/security/team/key.) The command adds an entry to policy.json:

"registry.access.redhat.com/ubi9": [
  {
    "type": "signedBy",
    "keyType": "GPGKeys",
    "keyPath": "/etc/pki/rpm-gpg/RPM-GPG-KEY-redhat"
  }
]

The Red Hat sigstore configuration for this registry already ships in /etc/containers/registries.d/registry.access.redhat.com.yaml (from the Podman package; Red Hat registry files are in github.com/containers/common). Create per-provider files in /etc/containers/registries.d/ (e.g. redhat.yaml) to keep configuration maintainable and versioned. After this, every UBI 9 pull from registry.access.redhat.com fetches its signature from the Red Hat store and validates it with the key.

Managing signatures with Skopeo

Skopeo uses the public key path in policy.json automatically, and refuses to copy an image whose signature does not match.

# verified copy (same effect as podman pull, more control over transports)
$ skopeo copy --src-tls-verify=false \
    docker://localhost:5000/custom_httpd \
    containers-storage:localhost:5000/custom_httpd

# sign while copying
$ skopeo copy \
    --dest-tls-verify=false \
    --sign-by-sigstore-private-key ./cosign.key \
    containers-storage:localhost:5000/custom_httpd \
    docker://localhost:5000/custom_httpd

Generating a Sigstore key with Skopeo

$ mkdir .skopeo
$ skopeo generate-sigstore-key --output-prefix .skopeo/sig-ubi8-httpd
Key written to ".skopeo/sig-ubi8-httpd.private" and ".skopeo/sig-ubi8-httpd.pub"

It asks for an optional passphrase; then follow the previous sections to sign and trust images.

10.4 Customising Linux kernel capabilities

Capabilities (introduced in Linux kernel 2.2) split elevated privileges into single units assignable to a process or thread, so you can give an unprivileged process a restricted subset instead of effective UID 0.

How capabilities work

They are tied to executables through extended attributes (man xattr) and granted to the process on execve(), subject to kernel transition rules. Examples:

Capability Allows
CAP_CHOWN change a file's UID and GID
CAP_KILL bypass permission checks to signal a process
CAP_MKNOD create special files with mknod()
CAP_NET_ADMIN privileged network configuration: interfaces, promiscuous mode, routing tables, multicasting
CAP_NET_RAW RAW and PACKET sockets (e.g. ping sending ICMP)
CAP_SYS_CHROOT chroot() and setns()
CAP_SYS_ADMIN near-total root: mount filesystems, bypass container isolation; effectively full control of the host kernel
CAP_DAC_OVERRIDE bypass discretionary access control checks on files
CAP_BPF privileged BPF operations (kernel 5.8)

(man capabilities has the full list.) Assign with setcap (+p = Permitted) and read with getcap:

$ sudo setcap 'cap_net_admin,cap_net_raw+p' /usr/bin/ping
$ getcap /usr/bin/ping
/usr/bin/ping cap_net_admin,cap_net_raw=p

Inspect a running process in /proc/<PID>/status:

$ ping example.com > /dev/null 2>&1 &
$ grep 'Cap.*' /proc/$(pgrep ping)/status
CapInh: 0000000000000000
CapPrm: 0000000000003000
CapEff: 0000000000000000
CapBnd: 000000ffffffffff
CapAmb: 0000000000000000
$ capsh --decode=0000000000003000
0x0000000000003000=cap_net_admin,cap_net_raw

CapPrm (permitted) decodes with capsh; it matches getcap, showing the file's permitted capabilities propagated to the process. The constants: https://github.com/torvalds/linux/blob/master/include/uapi/linux/capability.h.

[!tip] Ping without capabilities Older RHEL and CentOS used file capabilities (or setuid 0) so everyone could ping, an insecure approach if the binary has a bug. Fedora 31 moved to the kernel parameter net.ipv4.ping_group_range, set wide so users can send ICMP without CAP_NET_ADMIN and CAP_NET_RAW; RHEL and others inherited it (https://fedoraproject.org/wiki/Changes/EnableSysctlPingGroupRange).

Capabilities in containers

By default Podman runs containers with the set in /usr/share/containers/containers.conf (commented defaults at the time of writing):

#default_capabilities = [
#    "CHOWN",
#    "DAC_OVERRIDE",
#    "FOWNER",
#    "FSETID",
#    "KILL",
#    "NET_BIND_SERVICE",
#    "SETFCAP",
#    "SETGID",
#    "SETPCAP",
#    "SETUID",
#    "SYS_CHROOT"
#]

Check on nginx's PID 1:

$ podman run -d --name cap_test docker.io/library/nginx
$ podman exec -it cap_test sh -c 'grep Cap /proc/1/status'
CapInh: 0000000000000000
CapPrm: 00000000800405fb
CapEff: 00000000800405fb
CapBnd: 00000000800405fb
CapAmb: 0000000000000000
$ capsh --decode=00000000800405fb
0x00000000800405fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_sys_chroot,cap_setfcap
Set Meaning
CapInh (inheritable) preserved across execve; zero means nothing inherited by children unless configured
CapPrm (permitted) the limiting set: the maximum the process can use; capabilities move from it into effective
CapEff (effective) what the kernel actually checks (e.g. CAP_SYS_TIME to change the clock)
CapBnd (bounding) limits what a process can ever gain; you cannot promote into permitted what isn't in bounding
CapAmb (ambient) added in Linux 4.3; preserves capabilities for non-root users running programs that are not setuid

The list equals Podman's default and applies in rootless and rootful modes; the container runtime (runc or crun) sets them up.

Customising a container's capabilities

Static: edit default_capabilities in containers.conf. Runtime: --cap-add and --cap-drop (repeatable):

$ podman run -d --name cap_test2 --cap-drop=DAC_OVERRIDE docker.io/library/nginx
$ podman exec cap_test2 sh -c 'grep Cap /proc/1/status'     # CapPrm: 00000000800405f9
$ podman run -d --name cap_test3 \
    --cap-drop=KILL \
    --cap-drop=DAC_OVERRIDE \
    --cap-add=NET_RAW \
    --cap-add=NET_ADMIN \
    docker.io/library/nginx

Be careful dropping defaults: dropping CHOWN breaks nginx:

$ podman run --name cap_test4 --cap-drop=CHOWN docker.io/library/nginx
[emerg] 1#1: chown("/var/cache/nginx/client_temp", 101) failed (1: Operation not permitted)

Rootless containers get namespaced capabilities, more limited and unable to change the host: --cap-add=MKNOD in a rootless busybox container still fails, but as root it works:

$ podman run -it --cap-add=MKNOD docker.io/library/busybox /bin/sh
/ # mkdir -p /test/dev
/ # mknod -m 666 /test/dev/urandom c 1 8
mknod: /test/dev/urandom: Operation not permitted
# podman run -it --cap-add=MKNOD docker.io/library/busybox /bin/sh      # as root
/ # mknod -m 666 /test/dev/urandom c 1 8                                # succeeds

[!tip] Keep the defaults Adding capabilities enlarges the attack surface. If unnecessary, keep the defaults and drop the unwanted ones only after analysing side effects.

10.5 Understanding SELinux interaction with containers

SELinux works in kernel space with a least-privilege model, using labels to define types. By default it is in Enforcing mode (deny except as policy allows); Permissive only audits violations.

[!warning] Don't switch to Permissive or disable SELinux It exposes you to threats; create custom policies for the needed exceptions instead.

  • The default policy type is targeted (confines specific object types: processes, files, devices).
  • Access control kinds:
Kind What it does
Type Enforcement (TE) access by process type (domain) and file type; the main use
Role-Based Access Control (RBAC) SELinux users (mappable to system users) and roles
Multi-Level Security (MLS) all processes at the same sensitivity level get read/write
Multi-Category Security (MCS) plain-text categories make compartments; only processes in the same category access the resource (chapter 5)
  • TE: files get types, processes domains. Example: Apache's httpd_t domain can access httpd_sys_content_t files.
  • Policy pattern: POLICY DOMAIN TYPE:CLASS OPERATION; where POLICY is allow, allowxperm, auditallow, neverallow, dontaudit...; CLASS is file, dir, lnk_file, chr_file, blk_file, sock_file, fifo_file; OPERATION like open, read, use, lock, getattr, revc (as printed).
allow myapp_t myapp_log_t:file { read_file_perms append_file_perms };
  • Modular policies, loaded and unloaded without recompiling the whole set:
# semodule -i custompolicy.pp
# semodule -l

On Fedora, CentOS, RHEL the binary policy is in /etc/selinux/targeted/policy (the book prints polixy.XX), and container policies come from the container-selinux package (source https://github.com/containers/container-selinux) with three key source files:

  • container.fc: files and directories bound to the module's types

  • container.te: policy rules, attributes, aliases

  • container.if: the module interface (public macros)

  • A container process runs in the container_t domain: read/write on container_file_t, read/execute on container_share_t. While a container runs, podman, the runtime and conmon run as container_runtime_t, allowed to transition only to types in the container_domain attribute (inspect with seinfo -a container_domain -x from the setools-console package): container_t, container_init_t, container_engine_t, container_kvm_t, container_userns_t and others.

attribute container_domain;
attribute container_user_domain;
attribute container_net_domain;
typeattribute container_t container_domain, container_net_domain, container_user_domain;

This isolates processes across containers and from the host: an escaped process cannot reach host resources or other containers.

Labels on storage: the image's read-only LowerDirs are labelled container_ro_file_t (the container cannot write there); the MergedDir is writable, labelled container_file_t. Prove it with MCS categories:

# podman run -d --name selinux_test1 --security-opt label=level:s0:c1,c2 nginx
# find /var/lib/containers/storage/overlay -type f -context '*container_file_t:s0:c1,c2*' -printf '%-50Z%p\n'
system_u:object_r:container_file_t:s0:c1,c2 /var/lib/containers/storage/overlay/4b14.../merged/lib/x86_64-linux-gnu/libreadline.so.8.1
# podman inspect selinux_test1 --format '{{.GraphDriver.Data.LowerDir}}'
# ls -alZ /var/lib/containers/storage/overlay/2edcec35.../diff
dr-xr-xr-x. 21 root root unconfined_u:object_r:container_ro_file_t:s0 4096 Jan 5 23:16 .

LowerDir layers are shared across containers using the image, so no MCS categories appear there.

The problem: containers cannot read/write files not labelled container_file_t. The :z suffix or manual relabelling works, but relabelling /home or /var/logs is a very bad idea (other processes lose access). Hand-writing custom policies is too complex for everyday use. The tool for it is Udica.

Udica

Udica (https://github.com/containers/udica) was created by Lukas Vrabec, SELinux evangelist and team leader of the SELinux and Security Special Projects engineering teams at Red Hat. It generates SELinux profiles for containers that let them access resources the common container_t domain would block.

$ sudo dnf install -y udica setools-console container-selinux
# other distributions, from source:
$ sudo dnf install -y setools-console git container-selinux
$ git clone <the Udica repository URL>      # the book's URL is missing here
$ cd udica && sudo python3 ./setup.py install

Demo: a container writing to the host's /var/log (bind-mounted). By default container_t cannot write to var_log_t. Chapter10/custom_logger/logger.sh loops forever writing a dated line with a counter:

#!/bin/bash
set -euo pipefail
trap "echo Exited; exit;" SIGINT SIGTERM

# Run an endless loop writing a simple log entry with date
count=1
while true; do
    echo "$(date +%y/%m/%d_%H:%M:%S) - Line #$count" | tee -a /var/log/custom.log
    count=$((count+1))
    sleep 2
done

(set -euo pipefail exits on errors; tee writes to stdout and appends to /var/log/custom.log.) Dockerfile:

FROM docker.io/library/fedora
# Copy the logger.sh script
COPY --chmod=755 logger.sh /
# Exec the logger.sh script
CMD ["/logger.sh"]

--chmod=755 gives the script execute permission at startup.

# cd /Chapter10/custom_logger
# buildah build -t custom_logger .
# podman run -v /var/log:/var/log:rw \
    --name custom_logger1 custom_logger
tee: /var/log/custom.log: Permission denied

Generate a profile from the container's spec:

# podman inspect custom_logger1 > container.json
# udica -j container.json custom_logger
Policy custom_logger created!

Please load these modules using:
# semodule -i custom_logger.cil /usr/share/udica/templates/{base_container.cil,log_container.cil}
Restart the container with: "--security-opt label=type:custom_logger.process" parameter

The profile is in CIL (Common Intermediate Language); the Udica templates it inherits come along. Load and rerun:

# semodule -i custom_logger.cil /usr/share/udica/templates/{base_container.cil,log_container.cil}
# podman run -v /var/log:/var/log:rw \
    --name custom_logger2 \
    --security-opt label=type:custom_logger.process \
    custom_logger
22/01/08_09:05:19 - Line #1
...

It writes successfully. The process now has the custom_logger.process domain (a superset of the default), visible on the host:

# ps auxZ | grep 'custom_logger.process'
system_u:system_r:custom_logger.process:s0:c159,c258 root 26633 ... /bin/bash /logger.sh

Udica parses the JSON spec for mount points, ports and capabilities. The generated custom_logger.cil:

(block custom_logger
    (blockinherit container)
    (allow process process ( capability ( chown dac_override fowner fsetid kill net_bind_service setfcap setgid setpcap setuid sys_chroot )))

    (blockinherit log_rw_container)
)
  • The profile is a block; the allow rule enables the default capabilities; blockinherit pulls in the container and log_rw_container blocks.
  • Templates (installed by container-selinux in /usr/share/udica/templates/): base_container.cil (always included), config_container.cil, home_container.cil, log_container.cil, net_container.cil, tmp_container.cil, tty_container.cil, virt_container.cil, x_container.cil; others are added according to what the container does (here log_rw_container from log_container.cil).
  • Generated profiles can be versioned in a GitHub repository and reused for similar containers on other hosts. CIL syntax: https://github.com/SELinuxProject/cil/wiki.

Summary points

Rootless containers and avoiding UID 0 shrink the attack surface; signing and trusting images blocks MITM attacks; capabilities and SELinux (with Udica) fine-tune a container's privileges. Next: advanced container networking.
