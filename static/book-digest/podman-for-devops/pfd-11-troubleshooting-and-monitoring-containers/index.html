Podman for DevOps 11: Troubleshooting and monitoring containers

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 11 (Part 3: Managing and integrating containers securely). Previous: Podman for DevOps 10: Securing containers. Next: Podman for DevOps 12: Implementing container networking concepts.

Takeaways
  • A container is just a host process, so troubleshoot top-down: application, then container, then host. Helpers: podman logs, inspect, system df, info.
  • Permission denied on a volume has layers: SELinux label (:z shared, :Z private), then user namespaces (podman top user,huser; fixes :U, podman unshare chown, --userns=keep-id).
  • Health checks separate "running" from "healthy": --health-cmd, interval, retries, start period, timeout; scheduled by systemd transient timers; --health-on-failure (none, restart, stop, kill) gives self-healing; or embed HEALTHCHECK in the image.
  • Build failures come from a non-zero RUN exit code, a wrong repository or tag, or missing registry authentication; start scripts with set -euo pipefail.
  • nsenter runs host tools inside a container's namespaces (network, mount...), which podman exec cannot do for minimal images.

11.1 Troubleshooting running containers

  • Start from the commands you know: podman logs, podman inspect, plus podman system df (storage used by containers and images) and podman info (host information).
  • A running container is a process on the host, so all host tools are available for the OS and its resources.
  • Best practice: top-down. Application layer first, then the container layer, then the base host. The Podman team keeps a list of common issues: https://github.com/containers/podman/blob/main/troubleshooting.md.

Permission denied on storage volumes

Common on RHEL, Fedora and other SELinux distributions with SELinux in Enforcing mode (the recommended setting).

Layer 1, SELinux contexts. SELinux labels (extended attributes) keep container processes from reaching host or other containers' files. A host directory mounted into a container does not have the right label, and Podman does not change OS labels unless you ask:

$ mkdir ~/mycontent
$ podman run -v ~/mycontent:/content fedora \
    touch /content/file
touch: cannot touch '/content/file': Permission denied

Fix: relabel with :z or :Z (chapter 5):

Suffix Effect
:z (shared) shared content label, for multiple containers
:Z (private) private, unshared label; the more secure choice when one container needs the data 
# Using :Z to grant exclusive access to the container
$ podman run -v ~/mycontent:/content:Z fedora \
    touch /content/file

Layer 2, user namespaces (rootless). A user namespace isolates UIDs and GIDs, so a process can have a different identity inside than on the host. Rootless: you are UID 1000 on the host and root (UID 0) inside, an alias for your host user. A process running as another container user (mysql, nginx with UID 999) maps to a sub-UID from /etc/subuid that may not be allowed to write your mounted folder.

$ podman run -d --name web -v ~/data:/data:Z nginx
$ podman top web user,huser
USER   HUSER
root   1000      # inside is root, outside is your local user
nginx  100098    # inside is nginx (999), outside is a sub-UID

Here nginx runs as host UID 100098, but ~/data is owned by 1000, so it is blocked. Fixes:

Fix Command Notes
:U flag (Podman 3.1+) $ podman run -v ~/mycontent:/content:Z,U fedora touch /content/file automatically chowns the host directory to the UID and GID used inside the container; the most efficient
podman unshare $ podman unshare chown -R 0:0 ~/mycontent for manual fixes: plain sudo chown won't do; unshare runs the command in the container's user namespace, so the directory becomes owned by the container's internal root
--userns=keep-id $ podman run --userns=keep-id -v ~/mycontent:/content:Z fedora ... keeps UID 1000 on the host as UID 1000 inside; common for development tools

ping in rootless containers

On hardened systems ping may be restricted to a group range, and the container's mapped user ID can fall outside it. Fedora uses the ping_group_range kernel parameter; a fresh install allows everyone:

$ cat /proc/sys/net/ipv4/ping_group_range
0 2147483647

Reproduce a failure by restricting it (make it persistent with a file in /etc/sysctl.d containing net.ipv4.ping_group_range=0 0):

$ sudo sysctl -w "net.ipv4.ping_group_range=0 0"
$ container=$(buildah from docker.io/library/fedora) && \
    buildah run $container -- dnf install -y iputils && \
    buildah commit $container ping_example
$ podman run --rm ping_example ping -W10 -c1 redhat.com
PING redhat.com (209.132.183.105): 56 data bytes
--- redhat.com ping statistics ---
1 packets transmitted, 0 packets received, 100% packet loss

100% packet loss because ping cannot send over a raw socket. The fix is a range large enough to include the user's private group GID or a secondary group. Restore the default afterwards: sudo sysctl -w "net.ipv4.ping_group_range=0 2147483647" and remove any persistent file under /etc/sysctl.d.

11.2 Monitoring containers with health checks

  • A health check determines the health or readiness of the process in a container, from "is the process running" to "does it respond over the network".
  • Running vs healthy: Podman treats a container as up while PID 1 hasn't exited, yet a web server can be deadlocked, out of memory, or unable to reach its database. A health check proactively runs a command inside the container at intervals to verify the service works.
  • Two sources: built-in (many official images, e.g. databases, carry a HEALTHCHECK in their Containerfile, so Podman starts monitoring automatically) and manual (--health-cmd overrides or adds one, e.g. to check an API endpoint or a lock file).
  • Status phases in podman ps:
Status Meaning
Starting just launched; the initial grace period is active
Healthy the check exited with code 0
Unhealthy failed the consecutive number of times set by retries

Five components (command and interval are required; the rest optional):

Component Role
Command run inside the container; exit 0 = success, any other = failure, e.g. a curl to the web port
Retries consecutive failures before marking unhealthy; a success resets the counter
Interval time between checks, formats like 30s or 1h5m; too small wastes resources, too large risks catching timeouts; needs trial and error
Start period failures are ignored (grace period for the app to come up)
Timeout how long one check may take before counting as failed

Manual run (--health-interval=0 disables scheduling):

$ podman run -dt --name healthtest1 --health-cmd 'curl http://localhost || exit 1' --health-interval=0 quay.io/libpod/alpine_nginx:latest
$ podman ps
... Up 8 seconds (starting) 80/tcp healthtest1
$ podman healthcheck run healthtest1
$ echo $?
0
$ podman ps
... Up 41 seconds (healthy) 80/tcp healthtest1

(The book writes --health-interval and --healthcheck-interval interchangeably.) In real use Podman schedules checks automatically and you never need podman healthcheck run.

Scheduling uses systemd timers, which is why systemd is required for automatic scheduling; without systemd use another tool such as cron, set up manually. With an interval:

$ podman run -dt --name healthtest2 --health-cmd 'curl http://localhost || exit 1' --healthcheck-interval=10s quay.io/libpod/alpine_nginx:latest
$ ls /run/user/$UID/systemd/transient/69f3*
/run/user/1000/systemd/transient/69f3ca0ce7aa...-6433a92c3f3c8479.service
/run/user/1000/systemd/transient/69f3ca0ce7aa...-6433a92c3f3c8479.timer

Podman creates a transient systemd service and timer for each scheduled health check (not permanent; recreated when the container restarts):

# service
[Unit]
Description=/usr/bin/podman healthcheck run 69f3ca0ce7aa...

[Service]
LogLevelMax=5
Environment="PATH=/home/vagrant/.local/bin:/home/vagrant/bin:/usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin"
ExecStart=
ExecStart="/usr/bin/podman" "healthcheck" "run" "69f3ca0ce7aa..."

# timer
[Timer]
OnUnitInactiveSec=10s
AccuracySec=1s

Filter by health: $ podman ps -a --filter health=healthy.

Self-healing with --health-on-failure

By default a repeatedly failing container is only marked unhealthy, which suits external monitoring but doesn't fix a stalled service. --health-on-failure makes the engine act:

Value Action
none (default) only update status to unhealthy
restart restart the container: the most common self-healing, for services that deadlock or leak
stop stop it: for services that might corrupt data if left running
kill send SIGKILL immediately 
$ podman run -d \
    --name self_healing_web \
    --health-cmd "curl -f http://localhost/ || exit 1" \
    --health-on-failure=restart \
    nginx

This gives "a mini-orchestrator capability directly to the Podman CLI".

Health checks in the image

The most robust way: a HEALTHCHECK instruction in the Containerfile, so anyone pulling the image (a Fedora developer or a production cluster) gets the same monitoring without remembering CLI flags:

FROM registry.access.redhat.com/ubi9/ubi-minimal

# Install a simple web server (microdnf is the package manager for ubi-minimal)
RUN microdnf install -y python3 && microdnf clean all

# Define the health check: try to fetch the local index every 10 seconds
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s \
    --retries=3 CMD curl -f http://localhost:8080/ || exit 1

EXPOSE 8080
CMD ["python3", "-m", "http.server", "8080"]

(The book installs only python3, yet the check uses curl; ubi-minimal may need curl too.) This chapter's examples live under Chapter11/ in the book repository.

11.3 Inspecting your container build results

Builds print each instruction's output and errors to stdout; errors from RUN commands are propagated.

Failure Cause and message Solution
RUN command error the command exits non-zero; the build fails and prints the error and exit status. Example RUN yum install -y htpd && yum clean all -y (typo): No match for argument: htpd / Error: Unable to find a match: htpd / error building at STEP "RUN yum install -y htpd && yum clean all -y": error while running runtime: exit status 1 use the message to find the failing RUN and fix the command; the step message comes from the stage executor of Buildah's imagebuildah package (https://github.com/containers/buildah/blob/main/imagebuildah/stage_executor.go)
Repository not found (FROM registry.access.redhat.com/ubi_8) ... reading manifest latest in registry.access.redhat.com/ubi_8: name unknown: Repo not found fix the repository name, or check the registry holds it
Tag not found (FROM docker.io/library/fedora:sometag) registry 404: manifest unknown: manifest unknown find a valid tag: skopeo list-tags docker://docker.io/library/fedora (shows 39, 40, branched, heisenbug, latest, modular, rawhide ...)
Authentication (FROM local-registry.example.com/ubi8) unauthorized: authentication required podman login or buildah login, or provide an auth file with a valid token

(The three example Dockerfiles RUN_command_error, FROM_repo_not_found, FROM_tag_not_found and FROM_auth_error share the same httpd body: EXPOSE 80, CMD ["/usr/sbin/httpd", "-DFOREGROUND"].)

Troubleshooting Buildah-native scripts

Bash runs a script to the end despite intermediate errors, so start with:

set -euo pipefail
  • -e: exit immediately if a command or pipeline fails.
  • -o pipefail: a pipeline returns the exit code of the rightmost failing command.
  • -u: treat unset variables as errors.
#!/bin/bash

set -euo pipefail
# Trying to pull a non-existing tag of Fedora official image
container=$(buildah from docker.io/library/fedora:non-existing-tag)
buildah run $container -- dnf install -y httpd; dnf clean all -y
buildah config --cmd "httpd -DFOREGROUND" $container
buildah config --port 80 $container
buildah commit $container custom-httpd
buildah tag custom-httpd registry.example.com/custom-httpd:v0.0.1

$ ./custom-httpd.sh
Trying to pull docker.io/library/fedora:non-existing-tag...
initializing source docker://fedora:non-existing-tag: reading manifest non-existing-tag in docker.io/library/fedora: manifest unknown: manifest unknown

Same message as the Dockerfile build, minus the step number (there are no steps in a script). Same solution: skopeo list-tags.

11.4 Advanced troubleshooting with nsenter

  • Basics (podman logs, inspect, exec, tailored health checks) often suffice. But images are small now, and increasingly have no package manager, not even curl or wget, so you can't install tools inside.
  • A container is a process in namespaces and cgroups; nsenter (man nsenter, not tied to any engine or runtime) runs a command inside one or more of a process's namespaces while you keep the host's tools.
nsenter [options] [<program> [<argument>...]]
 -a, --all        enter all namespaces
 -t, --target <pid>   target process to get namespaces from
 -m, --mount      -u, --uts      -i, --ipc      -n, --net
 -p, --pid        -C, --cgroup   -U, --user     -T, --time
 -S, --setuid <uid>   -G, --setgid <gid>   --preserve-credentials
 -r, --root[=<dir>]   -w, --wd[=<dir>]   -F, --no-fork
 -Z, --follow-context   set SELinux context according to --target PID

One option per namespace. Get the container's main PID:

$ CNT_PID=$(podman inspect <Container_Name> \
    --format '{{ .State.Pid }}')
$ ls -al /proc/$CNT_PID/ns      # symlinks: namespace type -> inode number

(Hint: an inode stores information about a file or directory; the inode number uniquely identifies it in a filesystem.)

Worked example: a database client failing silently

A web app queries Postgres and prints JSON, but logs almost nothing (an alpha app); code and a SQL script are at https://github.com/PacktPublishing/Podman-for-DevOps-Second-Edition/tree/main/Chapter11/students. Build (Dockerfile Chapter11/students/Dockerfile):

FROM docker.io/library/golang AS builder

# Copy files for build
RUN mkdir -p /go/src/students/models
COPY go.mod main.go /go/src/students
COPY models/main.go /go/src/students/models

# Set the working directory
WORKDIR /go/src/students

# Download dependencies
RUN go get -d -v ./...

# Install the package
RUN go build -v

# Runtime image
FROM registry.access.redhat.com/ubi9/ubi-minimal:latest as bin
COPY --from=builder /go/src/students /usr/local/bin
COPY entrypoint.sh /

EXPOSE 8080

ENTRYPOINT ["/entrypoint.sh"]

# buildah build -t students-image .
Rootless networking

Flags: -database (default students), -host (default localhost), -password (default password), -port (default 5432), -username (default admin). Run with the supplied values (pghost.example.com, port 5432, user students, a lab password from the book):

# podman run students-image students -help
# podman run --rm -d -p 8080:8080 \
    --name students_app students-image \
    students -host pghost.example.com \
    -port 5432 \
    -username students \
    -password Podman_R0cks#
# podman logs students_app
2021/12/27 21:51:31 Connecting to host pghost.example.com:5432, database students
$ curl localhost:8080/students
Internal Server Error

Logs say nothing more, and the UBI minimal image has no troubleshooting tools. Attach to the network namespace only, keeping host binaries:

$ CNT_PID=$(sudo podman inspect students_app --format '{{ .State.Pid }}')
$ sudo nsenter -t $CNT_PID -n /bin/bash
# or run a single command: sudo nsenter -t $CNT_PID -n ip addr show
# ip addr show        # lo and tap0 (10.0.2.100/24)
# ip route            # default via 10.0.2.2 dev tap0
# ss -atunp
tcp  TIME-WAIT  0  0  10.0.2.100:50728  10.0.2.100:8080
tcp  LISTEN     0  128  *:8080  *:*  users:(("students",pid=402788,fd=3))

No established connection to the database host, so likely routing, firewall or name resolution. Test with the host's psql and dig:

# psql -h pghost.example.com
psql: error: could not translate host name "pghost.example.com" to address: Name or service not known
# dig pghost.example.com
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN

NXDOMAIN means the name doesn't exist. The development team confirmed the real name had a dash: pg-host.example.com. Rerun with the right name and the query works:

$ curl localhost:8080/students
{"Id":10149,"FirstName":"Frank","MiddleName":"Vincent","LastName":"Zappa","Class":"3A","Course":"Composition"}
  • nsenter can attach to several namespaces; -a (all) simulates podman exec, including the mount namespace, giving the container's filesystem view: $ sudo nsenter -t $CNT_PID -a /bin/bash.
  • Why not just podman exec? It can only run binaries that already exist in the image. Production images (ubi-micro, ubi-minimal) often lack ip, ps, tcpdump or even bash, so podman exec fails; nsenter borrows the host's tools.
