Podman for DevOps 12: Implementing container networking concepts

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 12. Previous: Podman for DevOps 11: Troubleshooting and monitoring containers. Next: Podman for DevOps 13: Docker migration tips and tricks.

Takeaways
  • Each container has its own network namespace. Podman 5 uses Netavark (Rust; bridge, macvlan; IPv4/IPv6) with aardvark-dns for names; CNI is deprecated in 5.0 and removed in 6.
  • Rootful: a Linux bridge (podman0, then podmanN) plus a veth pair per container. podman network create/connect/disconnect/inspect/rm/prune manage networks; a container can sit on several.
  • Same network = same subnet, no routing; different networks are routed through the host. User-created networks get DNS by name; the default podman network does not. In Podman 6 networks become isolated by default.
  • Pods share one network namespace and IP (containers reach each other as localhost); an infra container holds the namespaces.
  • Expose with -p ip:host:container/proto (or -P); --network=host removes isolation (insecure). Rootless uses pasta (default since 5.0): no root, no veth, no NAT, host IP and interface name copied; ports below 1024 are unavailable.

12.1 Container networking and Podman setup

  • Network isolation gives each container a separate stack through network namespaces; Podman manages interfaces across them. Examples are Podman v5.x with its default network backend. Basic networking knowledge (routing, IP, DNS, firewalling) is assumed.
  • History: Podman 3 and 4 used the Container Network Interface (CNI), a plugin-based specification created for Kubernetes (a network config format plus an execution protocol between plugin binaries and runtimes; vendors and communities can write plugins). Podman 4 introduced Netavark; CNI is deprecated in Podman 5 and will be removed in Podman 6, so the book covers only Netavark.

Netavark

  • A container-native network stack written in Rust (good memory management and C-like performance), built for Podman. Advantages:
    • dual IPv4/IPv6 stacks
    • native DNS resolution through the companion project aardvark-dns
    • rootless container support
    • several firewall implementations (nftables suggested)
  • Configuration: JSON files under /etc/containers/networks (rootful) or ~/.local/share/containers/storage/networks (rootless). A compact example:
[
  {
    "name": "netavark-example",
    "id": "d98700453f78ea2fdfe4a1f77eae9e121f3cbf4b6160dab89edf9ce23cb924d7",
    "driver": "bridge",
    "network_interface": "podman1",
    "created": "2025-02-17T21:37:59.873639361Z",
    "subnets": [
      {
        "subnet": "10.89.4.0/24",
        "gateway": "10.89.4.1"
      }
    ],
    "ipv6_enabled": false,
    "internal": false,
    "dns_enabled": true,
    "ipam_options": {
      "driver": "host-local"
    }
  }
]
Field Meaning
name, id network name and unique ID
driver default bridge; MACVLAN also supported
network_interface for bridge, the Linux bridge name (here podman1)
created creation timestamp
subnets subnet and gateway objects; assigned automatically, or give a custom CIDR; multiple allowed
ipv6_enabled native IPv6 on or off
internal internal-only network, blocks external routing
dns_enabled DNS for the network, served by aardvark-dns
ipam_options IPAM parameters; here driver host-local (like the CNI plugin)
  • The default network, named podman, uses a bridge named podman0. The netavark binary lives in /usr/libexec/podman/netavark with setup and teardown commands (man netavark); users are never expected to run it (it is deliberately outside the default $PATH and undocumented for direct use).

What happens when a container is created

Netavark creates the network setup in the container's namespace and the host's: the veth pair and the Linux bridge. Before the first container there are only the loopback and host interfaces. After podman run -d -p 8080:80 --name nginx-netavark docker.io/library/nginx:

  • the bridge podman0 (10.88.0.1/16) appears, plus a veth0@if2 interface attached to it (master podman0). A veth pair spans namespaces: a packet sent into one end is received immediately on the other.
  • The other end lives in a network namespace named like netns-d490e486-..., visible with ip netns (a file with the same name under /var/run/netns/ has the inode that /proc/<PID>/ns/net points to).
# ip netns
netns-d490e486-f67a-08f4-c066-d87915abadbf (id: 0)
# ip netns exec netns-d490e486-... ip addr show
2: eth0@if4: ... inet 10.88.0.2/16 brd 10.88.255.255 scope global eth0
# ip netns exec netns-d490e486-... ip route show
default via 10.88.0.1 dev eth0 proto static metric 100
10.88.0.0/16 dev eth0 proto kernel scope link src 10.88.0.2
  • The container IP (10.88.0.2) comes from the end of the veth in the container; outbound traffic goes through 10.88.0.1, the bridge. With the default host-local IPAM, container IPs are persisted in /run/containers/networks/ipam.db.
  • Rootless: the bridge and veths are created in a rootless network namespace (inspect with podman unshare --rootless-netns, Podman 4).
  • Firewall rules Podman creates (nftables): # nft list table inet netavark.

Managing networks with podman network

Subcommand Does
create create a network
connect connect a container to a network
disconnect disconnect
exists check whether a network exists
inspect dump the configuration
prune remove unused networks
reload reload container firewall rules
rm remove a network 
# podman network create \
    --driver bridge \
    --gateway "10.89.0.1" \
    --subnet "10.89.0.0/16" example1
# podman network inspect example1       # shows podman1, subnet 10.89.0.0/16, dns_enabled true
# podman network ls
NETWORK ID    NAME      DRIVER
a8ca04a41ef3  example1  bridge
2f259bab93aa  podman    bridge

Bridge names follow podmanN with N >= 0. Run a container on the new network:

# podman run -d -p 5432:5432 \
    --network example1 \
    -e POSTGRES_PASSWORD=password \
    --name postgres \
    docker.io/library/postgres
# podman inspect postgres --format '{{.NetworkSettings.Networks.example1.IPAddress}}'
10.89.0.2
# ls -la /run/containers/networks/
aardvark-dns  aardvark.lock  firewall  ipam.db
# bridge link show
4: veth0@eth0: ... master podman1 state forwarding priority 32 cost 2
  • ipam.db is a BoltDB key-value file (binary). The new bridge podman1 (10.89.0.1/16) has one veth peer in the container's namespace, which holds 10.89.0.2/16.
  • Connect a running container to another network without restarting: it keeps its first interface and gains a second (useful for reverse proxies):
# podman run -d -p 8080:80 --name net_example docker.io/library/nginx
# podman network connect example1 net_example
# podman inspect net_example      # "Networks": example1 (10.89.0.3) and podman (10.88.0.2)
# podman network disconnect example1 net_example
# podman network rm example1       # not the default network `podman`
  • rm fails with Error: "example1" has associated containers with it if containers (running or stopped) use it: remove or disconnect them first. podman network prune removes all networks not used by at least one container (asks y/N).

12.2 Interconnecting two or more containers

  • Containers in the same network reach each other on the same subnet without external routing. Containers in different networks reach each other on different subnets by routing through the host.
  • Same network demo (--cap-add=net_admin,net_raw lets ping and traceroute work):
# podman run -d --name endpoint1 --cap-add=net_admin,net_raw busybox /bin/sleep 10000
# podman run -d --name endpoint2 --cap-add=net_admin,net_raw busybox /bin/sleep 10000
# podman exec -it endpoint1 traceroute 10.88.0.4
1  10.88.0.4 (10.88.0.4)  0.009 ms  0.007 ms  0.005 ms

One hop: the packet stays on the internal network.

  • Different networks:
# podman network create --driver bridge --gateway "10.90.0.1" --subnet "10.90.0.0/16" --opt isolate=false net1
# podman run -d --name endpoint3 --network=net1 --cap-add=net_admin,net_raw busybox /bin/sleep 10000
# podman exec -it endpoint1 traceroute 10.90.0.2
1  host.containers.internal (10.88.0.1)  0.003 ms
2  10.90.0.2 (10.90.0.2)  0.001 ms

--opt isolate=false disables isolation: in Podman 6 and up, containers in one network cannot contact another network by default. The packet crosses the default gateway 10.88.0.1 and is routed to the net1 bridge.

Container DNS resolution

DNS lets a webapp container look up a db container's IP. The default podman network has no DNS resolution; user-created networks do (enabled by default). On Netavark, aardvark-dns serves it.

Demo reusing the students app from chapter 11 (https://github.com/PacktPublishing/Podman-for-DevOps/tree/main/Chapter11/students), both containers on net1:

# podman run -d \
    --network net1 --name db \
    -e POSTGRES_USER=admin \
    -e POSTGRES_PASSWORD=password \
    -e POSTGRES_DB=students \
    postgres
# cd Chapter11/students
# cat db.sql | podman exec -i db psql -U admin students
# buildah build -t students .
# podman run -d \
    --network net1 \
    -p 8080:8080 \
    --name webapp \
    students \
    students -host db -port 5432 \
    -username admin -password password
# curl localhost:8080/students
{"Id":10149,"FirstName":"Frank","MiddleName":"Vincent","LastName":"Zappa","Class":"3A","Course":"Composition"}

The host is the container name db (no IP), and the database has no port mapping: it is reached directly over net1.

DNS on Netavark: aardvark-dns

  • A lightweight authoritative DNS service written in Rust (companion of Netavark): IPv4 A and IPv6 AAAA records; resolves external and internal requests; containers resolve each other by name or alias (aliases can be added at creation).
  • Only within the same network: a container in net1 cannot resolve db if it is in net2; Aardvark knows each container's networks and answers only for those.
  • One aardvark-dns process serves networks with DNS on:
# ps aux | grep aardvark-dns
root 9115 ... /usr/libexec/podman/aardvark-dns --config /run/containers/networks/aardvark-dns -p 53 run
  • It listens on port 53/udp of the host network namespace (rootful) or the rootless network namespace; change it with dns_bind_port in containers.conf so it can coexist with another DNS server.
  • Per-network config files live in /run/containers/networks/aardvark-dns/ (named after the network). The first line is the listening address (the network gateway); then one line per container: ID, IP and name,shortID:
# cat /run/containers/networks/aardvark-dns/net1
10.90.0.1
d397b12635f1... 10.90.0.2 endpoint3,d397b12635f1
1d140d617b04... 10.90.0.3 db,1d140d617b04
70c0dbfba6f2... 10.90.0.6 webapp,70c0dbfba6f2

Name test:

$ podman network create web-stack
$ podman run -d --name web-service --net web-stack nginx:latest
$ podman run --rm --net web-stack fedora sh -c "curl -I http://web-service"
Server: nginx/1.29.5

Running containers inside a Pod

  • Quote from the Kubernetes docs: "A Pod is a group of one or more containers, with shared storage and network resources, and a specification for how to run the containers." It is the smallest deployable unit in Kubernetes. Containers in a Pod share the network, UTS (the book writes UTC), IPC and (optionally) PID namespaces: services refer to each other as localhost; outside callers use the Pod's single shared IP.
  • Use case: sidecars (a reverse proxy or OAuth proxy beside the main container, for authentication or service-mesh functions).
# podman pod create --name example_pod
# podman create --name c1 --pod example_pod busybox sh -c 'sleep 10000'
# podman create --name c2 --pod example_pod busybox sh -c 'sleep 10000'
# podman pod start example_pod
# podman pod ps
POD ID        NAME         STATUS    CREATED        INFRA ID      # OF CONTAINERS
8f89f37b8f3b  example_pod  Degraded  8 minutes ago  95589171284a  4
# podman pod top example_pod
# ip netns                  # only ONE namespace exists
# podman exec -it c1 ip addr show        # same 10.88.0.3 as c2 and the namespace
# podman pod stop example_pod
# podman pod rm example_pod
  • An empty Pod also creates an infra container that initialises the namespaces when the Pod starts (k8s.gcr.io/pause in Podman 3, a locally built podman-pause in Podman 4; the top output shows /catatonit -P). Start clean (remove other containers and Pods) before the exercise. Chapter 14 covers Pods further.

12.3 Exposing containers outside the host

Useful during adoption, to connect containerised services with legacy ones. Podman uses different stacks for rootless and rootful, but the command-line options for exposing ports are the same. The examples run as root to show firewall configuration.

Port publishing

A temporary mapping between container ports and random or custom host ports with -p or --publish: -p=ip:hostPort:containerPort.

  • Add a protocol: -p 127.0.0.1:8080:80/tcp; Podman forwards TCP, UDP and SCTP; each mapping needs its own -p.
  • For ranges, the host and container ranges must be the same length. Omit ip to bind all host IPs; omit the host port to get a random one.
# podman run -dt -p 8080:80/tcp docker.io/library/httpd
# podman ps
... 0.0.0.0:8080->80/tcp  ecstatic_chaplygin
# podman port ea23dbbeac2e
80/tcp -> 0.0.0.0:8080
# curl localhost:8080
<html><body><h1>It works!</h1></body></html>

-P / --publish-all publishes every port the image exposes (from EXPOSE 80/tcp, EXPOSE 80/udp in the Containerfile) to random host ports.

Attaching the host network

--network=host attaches the container to the host network namespace, removing isolation: easy but insecure and not recommended, since the container reaches all host ports, including the host's localhost where many secure services listen.

# podman run --network=host -dt docker.io/library/httpd
# netstat -nap | grep ::80
tcp6  0  0  :::80  :::*  LISTEN  37304/httpd
# curl localhost:80
<html><body><h1>It works!</h1></body></html>
# podman exec -ti deea584a393e /bin/bash        # inside: ifconfig shows the host eth0 192.168.122.175

From inside the container you can see the host's interfaces and services.

Host firewall

Opening a port to the outside means interacting with the host firewall. With firewalld (Fedora and similar), Podman automatically allows the traffic; no firewalld configuration is needed for port forwarding. firewalld is dynamic: rules are created, changed and deleted without restarting the daemon. Open ports carefully.

12.4 Rootless container network behaviour

  • Rootful containers use Netavark and need privileges to change the host network. Until Podman 4.3.z, rootless networking used only slirp4netns, which creates interfaces inside a rootless network namespace.
  • Podman 4.4.0 added pasta (https://github.com/containers/podman/blob/main/RELEASE_NOTES.md#440), and since Podman 5.0.0 it is the default.
  • Names: pasta = Pack A Subtle Tap Abstraction; it is a variant of passt = Plug A Simple Socket Transport (https://passt.top/passt/about/), which gives VMs full network connectivity in user mode by translating Layer 2 interfaces to Layer 4 sockets on the host. pasta does this for a network namespace, replacing slirp4netns. Neither needs root or CAP_NET_RAW/CAP_NET_ADMIN.
  • Why: a veth pair needs CAP_NET_ADMIN, normally denied to unprivileged users. pasta creates a tap interface in the container namespace and maps outgoing traffic to host L4 sockets, without a full TCP/IP stack between container and host (which hurt slirp4netns performance). Speed: both are slower than rootful veth, but pasta is much faster than slirp4netns and almost as fast as root in some cases.
  • How it works: one pasta process per rootless container; it creates a namespace under /run/user/<user_ID>/netns, copies all host IPv4 and IPv6 addresses and routes; the tap keeps the host's primary interface name; port forwarding preserves the source IP, and no NAT is used. (slirp4netns used a tap0 with 10.0.2.100/24.) Example: a rootless busybox shows eth0 with 192.168.122.94/24, the same as the host.
  • Misconception: rootless containers do have their own IPs, inside a private namespace managed by the user: they talk to each other but the host cannot ping or reach those internal IPs. Strategies to connect rootless services:
    1. Group them in a Pod (shared namespace and IP, localhost).
    2. A custom bridge network: containers get their own IP and resolve each other by name.
    3. Port mapping (-p) for host or external access (e.g. host 8080 to container 80).
$ podman network create rootless-net
$ podman run -d --net rootless-net --name endpoint1 --cap-add=net_admin,net_raw busybox /bin/sleep 10000
$ podman run -d --net rootless-net --name endpoint2 --cap-add=net_admin,net_raw busybox /bin/sleep 10000
$ podman exec -it endpoint1 ping -c1 endpoint2
64 bytes from 10.89.2.5: seq=0 ttl=64 time=0.023 ms
$ cat /run/user/1000/containers/networks/aardvark-dns/rootless-net
10.89.2.1
fe27f8d6... 10.89.2.4 endpoint1,fe27f8d65338
19a43075... 10.89.2.5 endpoint2,19a4307516ce
$ podman unshare --rootless-netns ip link | grep 'podman'
3: podman3: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
4: veth0@if2: ... master podman3 ...
5: veth1@if2: ... master podman3 ...

The bridge and veths exist only inside the rootless namespace (not visible with ip link on the host); enter it with podman unshare --rootless-netns.

  • ping in rootless containers: unprivileged users lack CAP_NET_RAW; enable ping with # sysctl -w "net.ipv4.ping_group_range=0 2000000" (any process of those groups can then send pings).
  • Legacy slirp4netns-compatible configuration under pasta:
$ podman run \
    --network=pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp \
    --rm -d busybox sleep 1000
  • Tweak pasta, e.g. keep defaults but set the MTU:
$ podman run --network=pasta:-m,1500 \
    --rm -d busybox sleep 1000
  • Port mapping works like rootful, but you can't update the firewall, so you may need to add rules to let traffic through:
$ podman run -d --rm -p 8000:8000 \
    registry.access.redhat.com/ubi9/python-312 \
    python -m http.server
$ ps aux | grep pasta
/usr/bin/pasta --config-net -t 8000-8000:8000-8000 --dns-forward 169.254.1.1 -u none -T none -U none --no-map-gw --quiet --netns /run/user/1000/netns/netns-fa625228-... --map-guest-addr 169.254.1.2

-t configures TCP forwarding to the guest (the container).

  • Port publishing is limited to ports above 1024 for unprivileged users.

Summary points

Network namespaces segregate containers; Podman automates the plumbing (Netavark, aardvark-dns, pasta); you can interconnect containers, expose their ports, and live with rootless limits. Next: Docker migration tips.
