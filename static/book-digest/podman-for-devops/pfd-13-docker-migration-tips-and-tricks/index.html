Podman for DevOps 13: Docker migration tips and tricks

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 13. Previous: Podman for DevOps 12: Implementing container networking concepts. Next: Podman for DevOps 14: Interacting with systemd and Kubernetes.

Takeaways
  • Podman's CLI is Docker-compatible: alias docker=podman, or install podman-docker (a docker script that execs Podman and links the man pages).
  • No direct container migration: recreate containers from their images and reattach volumes (or docker export / podman import; skip it if you use a registry).
  • A few commands behave differently (volume create fails if it exists, -v fails if the path is missing, --restart needs podman-restart.service); some Docker commands are missing (plugin, swarm, trust becomes podman image trust) and Podman has extras (generate, kube, pod, play, machine, unshare, volume export/import...).
  • Compose: Podman 3.0's Docker-compatible socket lets the official docker-compose (Go, v2) work rootful; podman-compose (community Python wrapper) works rootless. Service names resolve via aardvark-dns (round-robin for replicas).
  • The direction of travel: Quadlets with systemd on one host and podman kube for Kubernetes or OpenShift (next chapter).

13.1 Migrating existing images and playing with a command alias

Podman offers complete CLI compatibility with Docker, so Docker users switch easily.

# alias docker=podman
# docker
Error: missing command 'podman COMMAND'
Try 'podman --help' for more information.

The output comes from Podman. Alternative: the podman-docker package installs a docker script emulating the Docker CLI on top of Podman (and links man pages, so man docker shows Podman's):

$ sudo dnf install podman-docker
$ cat /usr/bin/docker
#!/usr/bin/sh
[ -e /etc/containers/nodocker ] || [ -e "${XDG_CONFIG_HOME-$HOME/.config}/containers/nodocker" ] || \
    echo "Emulate Docker CLI using podman. Create /etc/containers/nodocker to quiet msg." >&2
exec /usr/bin/podman "$@"

Create /etc/containers/nodocker to silence the message. Try it:

# docker version                         # prints "Client: Podman Engine, Version 5.4.2 ..."
# docker run --rm -it docker.io/wernight/funbox nyancat       # a running cat (Figure 13.1)
# docker run -dp 80:80 docker.io/docker/getting-started       # Docker's tutorial on http://localhost (Figure 13.2)

Follow the Docker Labs tutorial to check the alias at each stage, but stop before the "Using Docker Compose" section (covered next).

Migrating existing containers: there is no direct way to move running containers from Docker to Podman. Recommended: recreate them from their images and reattach volumes with Podman. Images can be exported with docker export (a TAR archive) and imported with podman import; skip this if you use a registry.

13.2 Podman commands versus Docker commands

Many names are identical (ps, pull, push, rename, restart, rm, rmi, run), but architecture differences (no daemon) mean some behaviours differ or need workarounds.

Behavioural differences (intentional)

Command Podman behaviour Docker behaviour
podman volume create fails if the volume already exists idempotent: skips if it exists (the Podman team considers Docker's behaviour inconsistent with its other commands)
podman run -v /tmp/noexist:/tmp fails if the source path doesn't exist creates the folder (Podman treats that as a bug and changed it)
podman run --restart older releases didn't persist restart policy across reboot; on modern Fedora and RHEL run sudo systemctl enable --now podman-restart.service, which scans for containers with always or unless-stopped policies at boot and starts them persists via the daemon

Missing in Podman

Docker command Podman situation
docker plugin no plugin support at the time of writing; the team suggests alternative OCI runtimes or OCI runtime hooks
docker swarm Docker Swarm is not supported; for multi-node clustering and orchestration move to Kubernetes (in production the cluster typically uses a bare-bones runtime like CRI-O, not the Podman CLI)
docker trust implemented as podman image trust (chapter 10)

Missing in Docker

Podman command What it does
podman generate structured output (e.g. YAML) for a container, pod or volume
podman healthcheck manage container health checks
podman machine manage Podman's VM on macOS and Windows (works on Linux but rarely useful)
podman mount, podman unmount mount or unmount a container's root filesystem on the host
podman play create containers, pods or volumes from a structured file such as YAML
podman pod manage pods
podman unshare run a process in a new user namespace (rootless)
podman untag remove one or more tags from stored images (the book's text says "removes one or more stored images")
podman kube work with Kubernetes YAML: podman kube play launches a local pod from a manifest; podman kube generate exports your container configuration for a cluster
podman volume export / import tarball a volume's contents and move it between systems or backups (Docker typically needs manual copying or scripts)

A missing command does not mean the feature is missing from the other tool.

13.3 Using Docker Compose with Podman

Compose orchestrates multi-container applications on a single host from a declarative YAML file (docker-compose.yaml): services (and volumes) that talk to each other with transparent name resolution. Good for quick single-host testing; for production-like multi-node setups use a clustered orchestrator such as Kubernetes.

History: early Podman had no daemon or REST API for the original docker-compose to talk to. The community built podman-compose, an independent, community-maintained Python wrapper that translated Compose YAML into podman commands (not maintained by the core Podman team). Podman 3.0 introduced a native Docker-compatible Unix socket and REST API, so the official docker-compose (written in Go) can talk to Podman as if it were the Docker daemon.

Docker Compose quick start

Spec: https://docs.docker.com/reference/compose-file/; examples: https://github.com/docker/awesome-compose.

Single container (Chapter13/registry/docker-compose.yaml):

services:
  registry:
    ports:
      - "5000:5000"
    volumes:
      - registry_volume:/var/lib/registry
    image: docker.io/library/registry
volumes:
  registry_volume: {}

WordPress with MySQL (Chapter13/wordpress/docker-compose.yaml):

services:
  db:
    image: docker.io/library/mysql:latest
    command: '--default-authentication-plugin=mysql_native_password'
    volumes:
      - db_data:/var/lib/mysql
    restart: always
    environment:
      - MYSQL_ROOT_PASSWORD=wordpressroot
      - MYSQL_DATABASE=wordpress
      - MYSQL_USER=wordpress
      - MYSQL_PASSWORD=wordpress
    expose:
      - 3306
      - 33060
  wordpress:
    image: docker.io/library/wordpress:latest
    ports:
      - 8080:80
    restart: always
    environment:
      - WORDPRESS_DB_HOST=db
      - WORDPRESS_DB_USER=wordpress
      - WORDPRESS_DB_PASSWORD=wordpress
      - WORDPRESS_DB_NAME=wordpress
volumes:
  db_data:

Two top-level objects: services (here db and wordpress) and volumes. Volumes can be created by Compose or reuse existing ones marked external.

Service key Meaning
image image used by the container
command extra arguments for the entry point
volumes volumes mounted with mount points; host directories can also be bind-mounted
restart restart policy on error
expose ports exposed by the container
ports host-to-container port mappings
environment environment variables (here the WordPress DB connection parameters)

Go REST API with Redis (Chapter13/golang-redis/docker-compose.yaml):

services:
  web:
    build:
      context: ./app
      labels:
        - "com.example.description=Golang Redis App"
    ports:
      - "8080:8080"
    environment:
      - REDIS_HOST=redis
    depends_on:
      - redis
  redis:
    image: docker.io/library/redis
    deploy:
      replicas: 1
Key Meaning
build the image to build, with custom labels
context build path (./app holds the source and Dockerfile)
labels labels passed as strings in the build
depends_on other services this one depends on (here redis)
environment here the name of the redis service
deploy custom parameters such as the number of replicas

Commands:

$ docker-compose up               # create the stack and volumes, print to stdout
$ docker-compose up -d            # detached
$ docker-compose up --build       # build the images, then start
$ docker-compose build            # build without starting
$ docker-compose down             # shut down a detached stack (Ctrl+C for a foreground one)
$ docker-compose kill [SERVICE]   # kill an unresponsive container; -s SIGNAL for other signals

Configuring Podman to work with docker-compose

Podman must expose its REST API on a local Unix socket (Docker-compatible and native libpod APIs). On Fedora:

$ sudo dnf install docker-compose podman-docker
$ sudo systemctl enable --now podman.socket       # listens on /run/podman/podman.sock
  • The docker-compose package on Fedora 42 installs version 2.37.3 at the time of writing; v2 was rewritten in Go (1.x was Python), much faster; releases at https://github.com/docker/compose/releases.
  • docker-compose looks for /run/docker.sock by default; podman-docker creates a symlink to /run/podman/podman.sock:
# ls -al /run/docker.sock
lrwxrwxrwx. 1 root root 23 Feb 3 21:54 /var/run/docker.sock -> /run/podman/podman.sock
  • The socket is accessible only by root by default; you could open access to all users or custom ACLs for a group, but rootless stacks are better served by podman-compose (below). The next examples run rootful.

Running a Compose workload (Go and Redis)

Chapter13/golang-redis/Dockerfile (multi-stage; the Go binary is copied into UBI minimal):

FROM docker.io/library/golang AS builder

# Copy files for build
RUN mkdir -p /go/src/golang-redis
COPY go.mod main.go /go/src/golang-redis

# Set the working directory
WORKDIR /go/src/golang-redis

# Download dependencies
RUN go get -d -v ./...

# Install the package
RUN go build -v

# Runtime image
FROM registry.access.redhat.com/ubi9/ubi-minimal:latest as bin
COPY --from=builder /go/src/golang-redis/golang-redis /usr/local/bin
COPY entrypoint.sh /

EXPOSE 8080

ENTRYPOINT ["/entrypoint.sh"]

The web front end listens on 8080/tcp and has two endpoints: an HTTP POST to upload a JSON object (name, email, ID of a user) and a GET to retrieve it, stored in Redis (source: Chapter13/golang-redis/app/main.go).

# cd Chapter13/golang-redis
# docker-compose up --build -d
Successfully tagged localhost/golang-redis_web:latest
Creating golang-redis_redis_1 ... done
Creating golang-redis_web_1 ... done
# podman ps
4a5421c9e7cd  docker.io/library/redis:latest      redis-server  ...  golang-redis_redis_1
8a465d4724ab  localhost/golang-redis_web:latest   ...  0.0.0.0:8080->8080/tcp  golang-redis_web_1
  • Container names follow <project_name>_<service_name>_<instance_count>; with replicas: 3 the redis service gives three instances.
  • Name resolution: Compose creates a network named <project_name>_default and an aardvark-dns process resolves container IPs to the service names. The config file lists replicas under the same redis name:
$ ps aux | grep aardvark-dns
/usr/libexec/podman/aardvark-dns --config /run/user/1000/containers/networks/aardvark-dns -p 53 run
$ cat golang-redis_default
10.89.5.1
843bfd9c... 10.89.5.2 golang-redis-redis-1,golang-redis-redis-1,redis,843bfd9cf8f7
776daece... 10.89.5.3 golang-redis-redis-2,golang-redis-redis-2,redis,776daece0e23
adc43444... 10.89.5.4 golang-redis-redis-3,golang-redis-redis-3,redis,adc434444922
  • With several replicas the resolution works like round-robin DNS: a lookup of the service name returns as many IPs as there are replicas, a minimal load-balancing scheme.
  • REDIS_HOST=redis injected in the web container is the service name the Go app uses to connect; the container name and IP are irrelevant. Verify:
# docker-compose exec web env
REDIS_HOST=redis
Keep configuration out of code

Storing configuration such as connection strings as constants in the application code is an anti-pattern, especially for cloud-native apps. Strictly separate logic from configuration: use environment variables or config/secret files injected at runtime. See the Twelve-Factor App (https://12factor.net/).

Test:

$ curl -X POST -d \
    '{"name":"jim", "email":"jim@example.com", "id":"0001"}' \
    localhost:8080
$ curl -X POST -d \
    '{"name":"anna", "email":"anna@example.com", "id":"0002"}' \
    localhost:8080
# docker-compose logs web
2022/02/06 00:58:06 Storing data: {"name":"jim","email":"jim@example.com","id":"0001"}
$ curl -X GET -d '{"id": "0001"}' localhost:8080
{"name":"jim","email":"jim@example.com","id":"0001"}
# docker-compose down

down destroys the containers and their resources including the custom network, but not volumes (add -v to remove volumes).

Using podman-compose

  • It predates Podman 3.0 and gives rootless Compose support. Install with dnf, or pip3 (broader OS support; the CLI is Python):
$ sudo dnf install -y podman-compose
$ pip3 install podman-compose

Commands compatible with docker-compose:

Command Purpose
help, version help and version
systemd create systemd unit files and register Compose tasks
pull, push, build stack images
up, down create and start, or tear down, the stack or services
ps, images, config, port status, images used, show the Compose file, public port of a binding
run, exec one-off container for a service, run a command in a running container
start, stop, restart, pause, unpause, kill control services or containers
logs, stats logs; CPU, memory, network I/O, block I/O, PIDs 
$ podman-compose up
$ podman-compose up --build -d
$ podman-compose down

systemd integration:

$ sudo podman-compose systemd -a create-unit
$ sudo podman-compose systemd -a register

The first creates a template unit (the book prints Sudo and register loosely):

# /etc/systemd/user/podman-compose@.service
[Unit]
Description=%i rootless pod (podman-compose)

[Service]
Type=simple
EnvironmentFile=%h/.config/containers/compose/projects/%i.env
ExecStartPre=-/usr/bin/podman-compose up --no-start
ExecStartPre=/usr/bin/podman pod start pod_%i
ExecStart=/usr/bin/podman-compose wait
ExecStop=/usr/bin/podman pod stop pod_%i

[Install]
WantedBy=default.target

$ systemctl --user start 'podman-compose@golang-redis'
$ systemctl --user stop 'podman-compose@golang-redis'
$ systemctl --user status 'podman-compose@golang-redis'

Which one? podman-compose has unique features (automatically grouping services into Pods), but this pod-first approach can cause friction with complex Compose files designed for Docker's individual-container model. For most developers docker-compose remains the gold standard for high-fidelity compatibility ("without the debugging tax of translation layers"). podman-compose is community-driven and Python-based, while Podman itself is moving toward Quadlets (next chapter) as the native way to manage service life cycles with systemd on one host, and podman kube towards multi-node production on OpenShift or Kubernetes.

Summary points
