Podman for DevOps 15: Managing containers, Kubernetes and AI workloads from a graphical interface

Source: Alessandro Arrichiello and Gianni Salinetti, Podman for DevOps, 2nd ed. (Packt, 2026), ch. 15 (last chapter). Previous: Podman for DevOps 14: Interacting with systemd and Kubernetes.

Takeaways
  • Podman Desktop is an open source GUI for containers, Pods, images, volumes, and Kubernetes contexts; installs by Flatpak or dnf (Linux), .dmg or Homebrew (macOS), an .exe that sets up WSL 2 (Windows).
  • Everything from earlier chapters has a button: pull, run (name, ports, volumes), stop/start/delete, Logs / Inspect / Terminal tabs, volumes, networks (assign only; create networks by CLI).
  • It reads ~/.kube/config, switches the UI to a minikube or kind cluster, and lists Pods, Deployments, Services with logs and a terminal.
  • Podman AI Lab (extension) downloads a model from a catalogue and starts a containerised inference server with an OpenAI-compatible endpoint, built on RamaLama.
  • End-to-end demo: a private chatbot, AnythingLLM in one container talking to the model container via host.containers.internal.

The chapter shifts from the terminal to a GUI: day-to-day tasks (logs, several environments, exploring new technology) benefit from an at-a-glance view, and the CLI remains the scriptable foundation.

15.1 Setting up the host operating system

Podman Desktop (https://podman-desktop.io/) is an open source graphical tool for containers and Kubernetes: manage containers, build images, use registries, connect to clusters.

Linux

  • Flatpak (a universal sandboxed packaging system; setup guide https://flatpak.org/setup/) is the recommended method:
# flatpak install flathub io.podman_desktop.PodmanDesktop
# flatpak run io.podman_desktop.PodmanDesktop

The first launch shows a welcome screen and checks dependencies such as a working Podman engine (Figure 15.1). The book also mentions a native package-manager method for Fedora, but prints no command.

macOS

  • Download the .dmg from the website and drag the icon to Applications, or:
# brew install --cask podman-desktop

On first run it guides you through creating the Podman machine, the lightweight VM Podman needs on macOS (Figure 15.2).

Windows

Uses WSL 2 for the Podman engine. Download the .exe from the website, run the wizard; if WSL 2 or Podman is missing, the wizard offers to configure them. On first launch it finalises the WSL 2 integration and checks the Podman machine (Figure 15.3). Instructions may change slightly by OS release.

15.2 Managing containers with the interface

The main dashboard has a left sidebar: Containers, Pods, Images, Volumes, Settings (Figure 15.4).

Running a container from an image

  1. Images, then Pull an image; enter docker.io/library/nginx (no tag means latest); Pull image. It appears in the list (Figure 15.5).
  2. Click the Run icon (a play symbol) in the Actions column. On Create a container: set a name (e.g. my-web-server) and port mapping (host port 8080 to container port 80; if Podman Desktop recognises exposed ports, enter only the host port) (Figure 15.6).
  3. Start Container: it opens the Containers list with the container Running (green icon). Open http://localhost:8080 for "Welcome to nginx!".

Persistent storage with volumes

  1. Volumes, Create, name it (e.g. web-content).
  2. Images, Run nginx again; name persistent-web-server, ports 8081:80.
  3. In the Volumes section map the volume (paste its path from the volume's details) to /usr/share/nginx/html (Figure 15.8).
  4. Start Container. Even if the container is removed, the volume and its data remain and can attach to another container.

Networking

Port mapping at creation is the main interaction. During creation you can assign a pre-existing network from the Networking dropdown (advanced settings), but creating and managing networks is typically a command-line operation. The container's Summary tab shows port mappings (host port to container port).

15.3 Connecting to and managing Kubernetes

Background: Kubernetes grew out of Google's internal need to manage applications at scale; it is an open source orchestration platform that automates deployment, scaling and management, groups containers into Pods, and is declarative (you define the desired state and it maintains it, handling failures, scaling and service discovery). Podman Desktop has a built-in client for any cluster, so one interface manages local Podman containers and remote Kubernetes workloads (Figure 15.9).

Connecting

  • A kubeconfig file holds credentials and endpoints; Podman Desktop auto-detects ~/.kube/config.
  • The context button at the bottom of the window (default "Podman") lists detected contexts; or Settings | Kubernetes (Figure 15.10). Select, e.g., the minikube context (set up in chapter 14): the whole UI switches from local Podman to that cluster, with Pods, Deployments, Services in the sidebar.

Local clusters

  • minikube (https://minikube.sigs.k8s.io/): a single-node cluster in a VM or container; see chapter 14.
  • kind (Kubernetes in Docker): no VM; the control plane runs inside containers (Docker or Podman). Create via Settings | Resources | Create new... (Kind box) (Figure 15.11): choose the name (default kind-cluster), provider (default Podman), default HTTP/HTTPS ports, and the Ingress controller setup (Figure 15.12); then Create and wait (Figure 15.13). It appears under Kubernetes resources (Figure 15.14); the Stop and Play icons in Resources stop and start it.

Exploring resources

  • Pods: the list covers all namespaces; filter with the Namespace dropdown (default, kube-system); shows name, status (Running, Pending, Error) and namespace (Figure 15.15). The Details view has Logs (choose a container if there are several), Inspect (JSON) and Terminal (shell into a container).
  • Deployments: desired vs available replicas; details show the managed Pods; you can delete a Deployment (which terminates its Pods).
  • Services: type (ClusterIP, NodePort, LoadBalancer) and exposed ports (Figure 15.16).
  • Practical example (the WordPress stack from chapter 14): find the wordpress-pod and mysql-pod Deployments, the NodePort Service for the setup port, and use Logs or Terminal on a misbehaving Pod. It removes switching to a terminal for kubectl.

15.4 Deploying local AI inference

Generative AI: deep-learning models that generate content (text, images, code). The Transformer architecture (2017) was the turning point and enabled large language models (GPT, Llama, Mistral). The trend is from cloud-only giants to smaller models on personal hardware: privacy, lower cost, offline use.

Podman AI Lab

An extension of Podman Desktop to download, run and manage AI models locally. It leverages containers for a one-click local inference server with a ready API endpoint. Features:

  • a curated catalogue of popular open source models
  • simplified download and setup
  • automatic provisioning of a containerised inference server
  • clear presentation of API endpoints

Enable it: Settings | Extensions | Podman AI Lab toggle (a restart may be needed) (Figure 15.17); an AI Lab icon appears in the sidebar.

Running a model

  1. AI Lab | Catalog; pick a model. The text says Phi-3-mini in one place and Phi-2-GGUF in the steps; the book chooses a model "for its reduced footprint".
  2. Click the Download icon; when done it becomes a rocket icon (create the model service).
  3. A dialog appears; defaults suffice; Create service (Figure 15.18).
  4. Ignore a RAM warning on Linux; elsewhere follow the instructions to adjust memory.

Behind the scenes it pulls the ramalama image, starts a container, loads the model and exposes ports.

RamaLama

An open source tool to run and serve AI models locally using OCI container workflows. It detects hardware (NVIDIA, AMD, Apple GPUs) and pulls the matching accelerated image, so no complex host setup. Commands like run, pull, serve; runs models in isolated rootless containers with no network access by default; pulls from Hugging Face and Ollama among others; accessed via REST API or as a chatbot. https://ramalama.ai/

Verify: the Containers list shows a new container (e.g. ramalama-llama-server); AI Lab simply orchestrated an ordinary Podman container, so you can inspect it, read logs, check ports and open a terminal (Figure 15.19).

Get the endpoint: AI Lab dashboard | Services tab (status Running) | click the model: an OpenAI-compatible API endpoint URL such as http://localhost:8080/v1/chat/completions appears with a copy button (Figure 15.20). Test it with curl from the host.

15.5 Building a chatbot: AnythingLLM with the local model

A private chatbot entirely on your machine, with AnythingLLM (an open source web interface for a custom personal assistant). It needs an LLM that exposes an OpenAI-compatible API, which AI Lab servers provide.

Step 1: keep the model server running from the previous section.

Step 2: run AnythingLLM from the image mintplexlabs/anythingllm:

  1. Images | Pull an image; enter the name; then Run.
  2. On Create a container:
    • Port 3001:3001 (the web server listens on 3001).
    • Volume anythingllm-storage (create it in Volumes first), mapped to /app/server/storage, so chat history and configuration persist.
    • Create an empty .env file in the volume's directory and open permissions (paths shown for the book's user alex; the book names the volume anythingllm in the commands):
$ touch /home/alex/.local/share/containers/storage/volumes/anythingllm/_data/.env
$ chmod -R 777 /home/alex/.local/share/containers/storage/volumes/anythingllm/_data
  • Map that .env file to /app/server/.env in the container.
  • Append :z to the container path strings so SELinux allows writing.
  • Set the environment variable STORAGE_DIR=/app/server/storage.
  • In the Security tab add the capability SYS_ADMIN.
  • Name it (e.g. anything-llm) and Start Container (Figure 15.21).

(chmod -R 777 and SYS_ADMIN are broad: chapter 10 warns that CAP_SYS_ADMIN is near-total root.)

Step 3: connect them.

  1. In AI Lab, open the running model's Details and copy the API endpoint (e.g. http://localhost:43717/v1).
  2. Open http://localhost:3001 (Figure 15.22) and follow the one-time setup. At LLM Preference (Figure 15.23):
Setting Value
LLM Provider Generic OpenAI
Chat Endpoint the URL, with the host changed to the special DNS name host.containers.internal: http://host.containers.internal:43717/v1 (the container reaches the host through it)
API Key blank (not needed for local models served this way)
Chat Model Name the model identifier, e.g. /models/phi-2.Q4_K_M.gguf; list it with curl -H 'accept: application/json' -X 'GET' 'http://localhost:43717/v1/models'
Token context window max tokens the model sees at once (roughly words or sub-words); start conservative at 4096, raise later

Step 4: test. Select the first workspace and ask "What is Podman?". The request goes from the AnythingLLM container to the inference-server container; the model replies, streamed back (Figure 15.24). The Containers list now shows at least the inference server and anythingllm.

Summary points

Podman Desktop bridges the CLI and a GUI: install on Linux, macOS and Windows; pull, run, inspect, persist and port-map containers; manage a Kubernetes cluster from one pane; provision a local AI inference server with Podman AI Lab; and build a full chatbot stack. The authors close by inviting readers to join the community on IRC, Matrix or Discord and the mailing lists.
