The Practical Test Pyramid 1: The Pyramid and Unit Tests

Source: Ham Vocke, "The Practical Test Pyramid", martinfowler.com, 26 February 2018. Own-words summary, much shorter than the source; the article's code listings are not reproduced. Next: The Practical Test Pyramid 2: Integration, Contract and End-to-End Tests.

Takeaways
  • Automating tests is what makes continuous delivery and fearless refactoring possible; manual click-through testing is slow, repetitive and error-prone.
  • The test pyramid is a rule of thumb: tests of different sizes, many small and fast ones, few big and slow ones.
  • Unit tests form the base. Test observable behaviour, not internal structure, so refactoring does not break them.
  • Do not test trivial code. If a private method seems to need its own test, the class probably does too much.

1.1 Why automate

  • Delivering faster without losing quality needs continuous delivery: a pipeline that automatically builds, tests and deploys so the software can be released at any time.
  • Manual testing (deploying to a test environment and clicking through the UI against scripts) is time-consuming, repetitive and tedious, and tedium leads to mistakes.
  • With automated tests you can change a large codebase and learn within seconds whether you broke something. A large refactoring without tests is the author's example of a frightening job.

1.2 The test pyramid

  • Mike Cohn introduced it in Succeeding with Agile (2009, per the article). His three layers, bottom to top: unit tests, service tests, user interface tests.
  • The article calls the original naming and concepts a bit misleading today: "service test" is hard to grasp (Cohn himself noted many developers ignore it), and with single page application frameworks, UI tests do not have to sit at the top because you can unit test a UI.
  • Keep two ideas from it:
    1. Write tests with different granularity.
    2. The more high-level the test, the fewer of them you should have.
  • The shape to avoid is the test ice-cream cone: many slow high-level tests, few unit tests, which is a maintenance and run-time burden.
  • Names of layers may differ as long as they are consistent in your team.

1.3 The sample application

  • A small Spring Boot microservice with a REST interface (a hello endpoint, a person lookup by last name, and a weather endpoint), a database and a call to an external weather API.
  • Internal structure:
    • controllers (REST endpoints)
    • repositories (database)
    • clients (other APIs)
    • domain classes (model and logic). The author deliberately omits a service layer and warns that business logic placed wholly in service classes leaves an anemic domain model.
  • Tools used: JUnit (runner), Mockito (mocks), Wiremock (fake external services), Pact (contract tests), Selenium (UI tests), REST-assured (API tests).

1.4 Unit tests

  • A unit test checks that one unit (the subject under test) works as intended. It has the narrowest scope and unit tests should outnumber every other kind.
  • What is a unit? There is no canonical answer: a function in a functional language; in object-oriented code anything from a method to a class.

Solitary and sociable

  • Solitary
    • tests replace all collaborators with mocks or stubs
    • Sociable tests let real collaborators run and stub only slow or side-effect-heavy ones such as databases and network calls
    • (The terms come from Jay Fields, per the article.)
  • The author says the choice matters less than writing tests, and uses both.

Mocks and stubs

  • Both are test doubles:
    • fake stand-ins that look like the real thing and answer with canned responses you set up at the start of the test
    • The article asks you to keep the distinction in mind rather than use the words interchangeably.
  • Unit tests stay fast by avoiding databases, the file system and HTTP calls; thousands can run in minutes.
  • The article suggests trying test-driven development, "no silver bullet" but a way to get good design and a full suite.

The private method urge

  • If you feel you must test a private method, the author reads this as a design problem: the class is too complex and violates the single responsibility principle
    • Split the class, move the method to the new class, and it can be tested via a public method.

What to test

  • One test class per production class is a good start. Test the public interface, covering non-trivial code paths including the happy path and edge cases.
  • Do not tie tests to the implementation
    • Tests that mirror internal structure break at every refactoring and lose their value as a safety net
    • Ask "if I enter x and y, is the result z?" not "does it call class A, then B, then add the results?"
  • Do not test trivial code such as simple getters and setters with no conditional logic; the article cites Kent Beck as saying that is fine.

Structure

  • Arrange, act, assert
    • (or given, when, then from BDD): set up data, call the code under test, check the result
    • The same structure works for higher-level tests, keeping them short and readable.

Specialised helpers

  • Framework helpers can test things a plain method call cannot
    • The article's example: Spring MockMVC fires fake requests at a controller to check paths, verbs and parameter parsing that annotations declare.

Summary points

  • Many fast unit tests, fewer broader ones, very few end-to-end ones.
  • Test behaviour through the public interface; leave trivial code and private methods alone.
  • Use arrange-act-assert everywhere.
Terms to carry forward
  • Test pyramid / ice-cream cone: healthy versus top-heavy test suite shapes.
  • Test double, mock, stub: stand-ins for collaborators.
  • Solitary vs sociable unit test: all collaborators faked versus real ones allowed.
  • Arrange-act-assert / given-when-then: test structure.
  • Anemic domain model: a model that is only data, with logic elsewhere.
