The Practical Test Pyramid 2: Integration, Contract and End-to-End Tests

Source: Ham Vocke, "The Practical Test Pyramid", martinfowler.com, 26 February 2018. Own-words summary, much shorter than the source; the article's code listings are not reproduced. Previous: The Practical Test Pyramid 1: The Pyramid and Unit Tests.

Takeaways
  • Integration tests check your code against the parts outside it (database, file system, other services), one integration point at a time; replace other teams' services with fakes.
  • Consumer-driven contract (CDC) tests let the team that consumes an API specify what it needs, and the provider runs those tests continuously.
  • End-to-end tests give the most confidence but are slow, flaky and costly: keep only the few most valuable user journeys.
  • Put tests in the pipeline by speed and scope, push each test as low in the pyramid as it can go, and keep test code as clean as production code.

2.1 Integration tests

  • Non-trivial applications talk to databases, file systems and other applications
    • unit tests leave those out, so integration tests cover them. Your tests must run the real component you integrate with (a database for database tests; a real file written and read for file tests).
  • "Integration test" is vague
    • The author uses it narrowly: test one integration point at a time, replacing other services and databases with test doubles
    • Combined with contract tests, this gives faster, more independent, easier-to-reason-about tests than a wide one through the whole stack.
  • Narrow integration tests sit at your service's boundary and trigger an action that crosses it.

Database integration

  • Pattern: start a database, connect the application, trigger code that writes, read the data back and check it.
  • In the sample, the repository has almost no hand-written code (Spring Data derives it from a method name), yet the author still writes a database test to check the behaviour
    • The tests use an in-memory database instead of production PostgreSQL.

Integration with separate services

  • The sample calls a third-party weather REST API
    • Tests should not hit the real servers: quota limits are one reason, but the main one is decoupling from the other party's outages and changes.
  • Run a fake server (the article uses Wiremock) with canned responses, call the code that talks to the service, and check the response is parsed correctly.
  • A fake only proves your code against your assumptions about the real service, which is the gap contract tests close.

2.2 Contract tests

  • When services are built by different teams, the interface between provider (serves data; or publisher in event-driven systems) and consumer (uses the data; or subscriber) is a contract
    • Interfaces include REST with JSON, RPC such as gRPC, and queues.
  • The traditional route:
    • write a long specification, build the provider, throw the specification to the consumer team, wait, run a big manual system test, hope nobody deviates
    • Automated contract tests replace the last steps.
  • Consumer-driven contract (CDC) tests go further:
    1. The consuming team writes automated tests of exactly the data it needs from the interface.
    2. It publishes them for the providing team.
    3. The providing team runs them continuously in its pipeline and keeps them green.
    4. When a CDC test breaks, the two teams talk.
  • Benefits:
    • the provider builds only what is needed
    • as long as tests stay green the provider can change things without worrying about other teams
    • breaking changes are caught before release
      • The article ties this to autonomous teams in microservice organisations, and calls failing CDC tests a prompt to go and talk to the other team.
  • A naive CDC test just fires requests and checks responses, packaged and shared through an artifact repository
    • Pact is the best-known tool, with consumer-side and provider-side testing, ready-made stubs and support for JVM languages, Ruby, .NET, JavaScript and more
    • Its documentation can feel overwhelming at first.
  • The sample shows three roles: a consumer test (our team consuming another team's API), a provider test for the other team, and a provider test for our own API.

2.3 UI tests

  • A UI is any interface users touch: a web page, a REST API or a command-line tool. UI tests check that input triggers the right actions and the display changes as expected.
  • The article separates UI tests from end-to-end tests (Cohn treats them as the same)
    • End-to-end tests often go through the UI, but UI tests need not be end to end: frontend code can be unit tested with the backend stubbed
    • A REST API's "UI" is covered by integration tests around it.
  • With traditional web applications use tools such as Selenium. Behaviour is simple to test; layout, usability and corporate design are other aspects worth separate attention.

2.4 End-to-end tests

  • Testing the deployed, fully integrated system through the UI (also called broad stack tests) gives the most confidence that the software works
    • Selenium and the WebDriver protocol drive a headless browser against deployed services.
  • Costs:
    • Flaky: browser quirks, timing, animations and unexpected dialogs cause false positives; the more complex the UI, the worse.
    • Ownership:
      • in a microservice world no single team owns a test that spans the system. A central QA team is, the article says, an anti-pattern in DevOps
      • maybe a community of practice or quality guild.
    • Slow and hard to run locally: you cannot start hundreds of services on a laptop.
  • Therefore keep them to a bare minimum:
    • translate the most valuable user journeys into tests
    • For a shop, searching for a product, adding it to the basket and checking out may be the only one needed.
  • Do not repeat at this level the edge cases tested lower down.

2.5 Acceptance tests and exploratory testing

  • Acceptance (functional) tests
    • check that a feature works from the user's perspective rather than the technical one, in given-when-then terms (given a logged-in user and an article, when they click "add to basket", then it is in the basket)
    • The names are debated; the article says pick a term and write the tests
    • BDD style can help shift the thinking.
  • Exploratory testing
    • is manual testing with creativity: regularly try to break the running application with a destructive mindset and note bugs, design issues, slow responses and misleading errors
    • Automate what you find so it cannot regress, and treat what slipped through as feedback on the pipeline.

2.6 Terminology

  • There is no settled vocabulary: "integration test", "component test" and "service test" overlap. Agree names and scope within your team and stick to them; do not argue about labels.

2.7 Tests in the pipeline

  • The principle is fast feedback: fast tests in early stages so you learn in seconds or minutes that you broke something; slower, broader tests in later stages.
  • Stages are decided by speed and scope, not test type. A fast, narrow integration test can sit beside unit tests.

2.8 Avoiding duplication

  • Every test costs writing, reading, maintenance and run time, so there can be too many.
  • Two rules:
    1. If a higher-level test finds an error and no lower-level test fails, write a lower-level test (it pinpoints and replicates the fault and becomes a regression test).
    2. Push tests as far down the pyramid as you can.
  • A higher-level test is worth having when it adds confidence the lower ones cannot: a controller unit test does not prove the REST endpoint answers HTTP, so add a test for that only, not for the logic again.
  • The author deletes or replaces redundant high-level tests and warns about the sunk cost fallacy.

2.9 Clean test code

  • Test code is as important as production code.
  • Test one condition per test; use arrange-act-assert or given-when-then.
  • Readability beats strict DRY; accept some duplication (DAMP).
  • When unsure, use the Rule of Three: use before reuse.

Summary points

  • Integration tests: one boundary at a time, fakes for other teams' services.
  • CDC tests keep teams' APIs compatible without big system tests.
  • Few end-to-end tests, chosen by user value; push everything else down.
Terms to carry forward
  • Narrow integration test: one integration point, other parts faked.
  • Contract / CDC test: consumer-written tests of an interface; run by the provider.
  • Broad stack (end-to-end) test: the whole deployed system through the UI.
  • Acceptance test: feature checked from the user's perspective.
  • Exploratory testing: unscripted manual probing.
  • DAMP vs DRY: favour readable tests over eliminating all repetition.
