Principles and Patterns for Distributed Application Architecture 1: Cloud Infrastructure Is Not Enough

Source: Jonas Bonér, Principles and Patterns for Distributed Application Architecture (O'Reilly, 2025), chapter 1. Next: Principles and Patterns for Distributed Application Architecture 2: Principles of Distributed Application Architecture.

Takeaways
  • Cloud and edge are a continuum, not two separate things; distributed applications there must cope with uncertainty, partial failure, and unreliable networks.
  • Infrastructure alone is not enough: Kubernetes manages the "empty boxes" (containers), but what goes inside them and how they are stitched together is the application layer's job.
  • The end-to-end argument (Saltzer, Reed and Clark, 1984) explains why: some guarantees can only be implemented correctly with the help of the application at the endpoints.
  • Stateless design ignores the hardest part of distributed systems, managing state; the chapter argues for data-driven, stateful services.
  • Three things can never be delegated to a platform: business logic, domain data model, API definition. The framing for the whole book is the Reactive Manifesto (2014).

1.1 Cloud and edge

The chapter treats cloud and edge as complementary capabilities.

What it offers
Cloud computing Scalable, on-demand resources over the internet; lower infrastructure cost, flexibility, collaboration; centralised data centres give automatic updates, disaster recovery and global accessibility; large data volumes aggregated centrally enable analytics and machine learning
Edge computing Computation and storage closer to where they are needed: lower latency and faster responses for time-sensitive work, better resilience; suits mobile and IoT devices; less data sent to central servers cuts bandwidth costs and congestion; local processing helps privacy and security (healthcare, manufacturing, autonomous driving)
  • Embracing both enables rapid time to market, elasticity and high availability
    • Hybrid applications mix in-house data centres and ephemeral resources, for cost optimisation, ownership and flexibility.
  • Modern cloud and edge applications are radically different from a single-machine monolith and need new tools, practices, design and architecture.
  • Their distributed nature brings concerns the book says it will discuss in detail:
    • uncertainty and nondeterminism
    • distributed state and communication
    • failure detection and recovery
    • data consistency and correctness
    • message loss, partitioning, reordering and corruption
  • Infrastructure can hide some of the complexity, but only partially. The application and infrastructure layers must cooperate to give a coherent experience and keep end-to-end guarantees.
  • You cannot keep the idealistic model of a single node (strong consistency, minimal latency, closed world)
    • Local in-process calls become remote, unreliable network calls and parts of the system can fail at any time (partial failures), so requirements must be relaxed to stay available and scalable.
  • The principles and patterns aim to nudge designs away from shared mutable state, synchronous communication, blocking I/O and strongly coupled service architectures
    • Other benefits listed: services that need less code, shorter time to market, better maintainability and extensibility.

1.2 What is a cloud application?

  • Like a native species, a cloud application adapts to its environment: the cloud is harsher than a dedicated single node, so the application becomes distributed and must be resilient to hardware and network unpredictability, from varying performance to all-out failure.
  • The book's framing: ensuring responsiveness and reliability is difficult, but applications built this way better match how the real world works, so users (human or software) get better experiences.
  • The cloud operating model constraints:
    • applications are limited in scaling vertically on commodity hardware, which leads to many isolated, autonomous services (often called microservices)
    • all interservice communication is over unreliable networks
    • hardware can fail, be restarted or be moved at any time
    • services must detect and manage failures of peers, including partial failures
    • strong consistency and transactions are expensive because of the coordination required, so it is hard to make data services available, performant and scalable at once
  • A cloud application is therefore designed to leverage that model: predictable, decoupled from the infrastructure, right-sized for capacity, and enabling tight collaboration between development and operations
    • It decomposes into loosely coupled, independently operating services that are resilient to failure, driven by data, and intelligent across geographic regions.

1.3 Why cloud infrastructure is not enough

  • Cloud applications need a scalable, available infrastructure layer (for example Kubernetes and its tools) and a scalable, available application layer.
  • The infrastructure layer excels at managing, orchestrating, scaling and keeping available the "empty boxes", the containers
    • But managing containers "only gets you halfway there": equally important is what you put inside and how you stitch them into one coherent system.
  • The chapter quotes Kelsey Hightower:
    • there is a ton of effort to "modernize" applications at the infrastructure layer, but without equal investment at the application layer (frameworks, application servers) "we're only solving half the problem"
    • even with the best orchestration, logging, security and debugging infrastructure, code must be written to make best use of it.
  • The two layers manage resilience and scalability at different granularities:
    • the application layer: fine-grained, service-level, working closely with application code
    • the infrastructure layer: coarse-grained, acting as a "cloud OS" where containers are like processes with isolation, resource management and resiliency, offering persistence, I/O, communication, monitoring and deployment

1.4 Toward a holistic view of system design

  • A common question: "Now that my application is containerised, I assume I don't need to worry about all that hard distributed systems stuff, since Kubernetes solves my problems around resilience, scalability, stability and safety, right?" The answer: no, it is not that simple.
  • End-to-end argument.
    • The 1984 paper "End-To-End Arguments in System Design" by Saltzer, Reed and Clark says many infrastructure functions can be completely and correctly implemented only with the help of the application at the endpoints. Functions placed at low levels may be redundant or of little value compared with their cost there
    • an incomplete low-level version can still help as a performance enhancement.
    • This is not an argument against tools like Kubernetes, which add a lot of value, but a call for closer collaboration between the layers.
    • Correctness, consistency and safety mean different things per service and cannot be fully outsourced
      • The chapter quotes Pat Helland ("Life Beyond Distributed Transactions"): "The management of uncertainty must be implemented in the business logic." A holistically stable system is the application's responsibility, not the infrastructure tooling's.
  • Two examples where application-level semantics matter:
    • Message delivery: is a message delivered when it reaches the destination's network interface card? When it reaches the application's networking library? When the processing callback is invoked? When it completes successfully? When the acknowledgement has gone back and been consumed by the sender? It depends on the use case.
    • Flow control: fast producers must not overload slow consumers; business logic, application libraries and infrastructure must all take part to keep the data flow steady.
  • The chapter calls for raising the abstraction level with programming models and runtimes that do the heavy lifting, so teams build business value, not network-programming details.
  • The hard part is the space between services.
    • A single service is not that useful
    • The hard things enter when services collaborate: data consistency guarantees, reliable communication, replication and failover, failure detection and recovery, sharding, routing, consensus algorithms.

1.5 The unfortunate trend of stateless protocols

  • Most developers building on Kubernetes rely mainly on stateless protocols and design, holding on to habits made for monolithic single-node systems on top of "the almighty SQL database".
  • That ignores the hardest part of distributed systems:
    • managing the state of your data
    • Applications are increasingly data-centric, so owning, processing, transforming and enriching data close to the application matters more than ever.
  • Many applications cannot afford a round trip to the database for every access and must process data in close to real time from never-ending streams, often in a distributed way before persisting.
  • A cache in front of the database helps latency but brings cache coherency, consistency, invalidation, resilience and operational complexity.
    • Example:
      • in an online store's flash sale, each service caches item stock levels
      • One service's updated stock may not immediately sync with the others, risking overselling
      • Invalidation can fail if messages are delayed or lost
      • If a cache node fails, other resources take its load
      • Managing synchronisation, failover and consistency models adds a heavy operational burden, and small misconfigurations can cause inconsistent data or degraded performance.
  • This needs a design that puts data at the center, not on the sidelines.

1.6 Data-driven stateful services

  • Companies try to capture "everything" in data lakes, though the urge must be balanced against legal mandates and users' rights such as GDPR and the right to be forgotten.
  • Nightly batch jobs over all that data are often too slow; systems need to extract knowledge as data flies by, from thousands of users, in close to real time.
  • The move: from high-latency, stateless, behaviour-driven services to low-latency, stateful, data-driven services, taking back ownership of data.

1.7 Tackling the constraints of the edge

Organisations turn to edge computing for low latency, resilience, performance and data compliance. Edge applications face these constraints:

Constraint Meaning
Limited resources Confined to the hosting device; more compute or storage only from locally reachable peers
Lack of global consistency A consistent global view and consensus across large groups is prohibitively expensive
Lack of stable networks Links such as multi-hop mesh networks are unreliable and possibly slow
Mobile devices Devices move and may become unreachable from earlier networks
Ephemeral devices Devices can fail, restart or suspend at any time
Ephemeral connections Because devices are mobile and autonomous, partners are only temporarily connected
Radically different environment Infrastructure, tools and products differ from the cloud
  • Edge applications need programming models and runtimes with decentralisation, location-transparent and mobile services, physical co-location of data and processing, temporal and spatial decoupling of services, and automatic peer-to-peer data replication
    • The core principle: autonomous operation without dependence on central infrastructure or persistent connectivity.

The cloud-to-edge continuum

  • Cloud and edge are one continuum of layers, from centralised cloud to near edge, far edge and devices (Figure 1-1)
    • Where a service should run is use-case dependent and may change over an application's life
    • Parameters such as latency, throughput, consistency, availability, scalability and compute change drastically along it.

Further out, toward the device Further in, toward the cloud
10,000s to 100,000s of points of presence to coordinate (millions of "things" counting devices) 10s to 1,000s of nodes to coordinate
Unreliable networks and hardware Reasonably reliable network and hardware
Limited resources and compute power Vast resources and compute power
Local, faster, less accurate decisions Global, slower, more knowledgeable decisions
Low-latency real-time streaming through in-process processing Batch-oriented, with high latency to backend services (from the edge user's view)
Weaker consistency guarantees (eventual or causal) Stronger guarantees (ACID and linearizability)
More resilient and available: data, compute and user co-located Less resilient and available: depends on a fast, reliable connection to the backend cloud
Fine-grained, adaptive, selective data replication and mobility Coarse-grained, batch-oriented replication; data can be stationary
  • Because users create ever more data, serving them well means managing and processing it where it is created: at the far edge or on the devices
    • That cuts latency, improves availability (everything needed is in the user's location) and gives flexibility such as regional data compliance.
  • Ideally where something runs (on prem, cloud, edge or device) should not dictate how it is designed, implemented or deployed
    • The principles to rely on: data and service mobility, location transparency, self-organisation, self-healing, and physical co-location of data, processing and end user, so the right data is where it is needed for as long as needed, even as the user moves
    • This calls for climbing the ladder of abstraction.

1.8 Climbing the ladder of abstraction

  • Cloud infrastructure is "fantastic" and the Kubernetes ecosystem easy to take for granted, but richness has a price: drowning in complexity, too many products, decisions and worries
    • How to pick, compose, guarantee correctness across product boundaries, observe the whole system, and evolve it?
  • Businesses need to move and innovate faster at growing user and data volumes, and "we can't just move fast and break things": changes need predictability, repeatability and reusability.
  • The chapter quotes Alfred North Whitehead:
    • "Civilization advances by extending the number of important operations which we can perform without thinking about them." We must learn to let go of control: we do not need every knob, and delegating frees us for more important work
    • It also quotes Timothy Keller on "liberating restrictions": embrace constraints.
  • Three things we can never delegate to a product or platform:
    1. Business logic: what drives business value; how to act on data (store, query, transform, downsample, relay, mine, trigger side effects).
    2. Domain data model: the structure, constraints, guarantees, storage and query model of the business data.
    3. API definition: how a service presents itself to the outside world, communicates and coordinates with others, and what data it exposes under what guarantees.
  • The aim is to free developers to write business logic, model domain data and define APIs, through unified cloud-and-edge programming models powered by runtimes and data meshes that hide the underlying infrastructure differences.

1.9 Think reactive

  • In 2014 the author and friends Dave Farley, Roland Kuhn and Martin Thompson wrote The Reactive Manifesto, a conceptual framework for thinking, architecting and designing applications for multicore, cloud and edge systems, with a shared vocabulary
    • The author calls the initiative immensely successful, saying it inspired tens of thousands of companies (his claim, no source given) (unverified).
  • Its tenets (Figure 1-2), best understood as:
    • Value: responsive, maintainable and extensible
    • Form: elastic and resilient
    • Means: message-driven (or event-driven)
  • This framing underlies the principles and patterns in the rest of the guide, which the next chapter introduces.

Summary points

  • Cloud and edge form a continuum; distributed applications must manage uncertainty, partial failure and unreliable networks.
  • Containers and Kubernetes cover half the problem; the application layer must cooperate to keep end-to-end guarantees.
  • State and data belong at the centre: low-latency, stateful, data-driven services.
  • Never delegate business logic, the domain data model or the API definition.
  • The Reactive Manifesto (responsive, maintainable, extensible; elastic, resilient; message-driven) frames the rest of the book.
Terms to carry forward
  • Cloud operating model: the constraints of the cloud environment (unreliable networks, failing hardware, expensive strong consistency).
  • End-to-end argument: some functions can be completely and correctly provided only with the help of the application at the endpoints.
  • Cloud-to-edge continuum: centralised cloud, near edge, far edge, devices.
  • Partial failure: part of a distributed system fails while the rest keeps running.
  • Reactive Manifesto: value (responsive, maintainable, extensible), form (elastic, resilient), means (message-driven).
