Principles and Patterns for Distributed Application Architecture 4: Designing Distributed Applications

Source: Jonas Bonér, Principles and Patterns for Distributed Application Architecture (O'Reilly, 2025), chapter 4. Previous: Principles and Patterns for Distributed Application Architecture 3: Patterns of Distributed Application Architecture.

Takeaways
  • The chapter's answer to "how do we put this into practice": event-driven architecture with microservices, which models the domain in line with how distributed systems work.
  • Five microservice principles: isolation of components, autonomous operation, single responsibility, exclusive state ownership, mobility with addressability.
  • Beware microliths: single-instance, synchronous, blocking, shared-database "microservices" that are just small monoliths; containers and Kubernetes do not fix that.
  • Events-first domain-driven design (a term from Russell Miles): model the verbs (events), not the nouns; use commands for intent and events for facts.
  • Define consistency boundaries around entities, keep the strongly consistent dataset minimal, and allow protocols to evolve (Postel's law, anti-corruption layer).

4.1 Fundamental principles of microservices

  • Microservices offer speed, efficiency, predictability and safety and help scale organisations: complex applications decompose into decoupled services using well-defined protocols, so teams develop, deploy and evolve them independently.
  • Five key principles:

Isolation of components

  • Isolation
    • is "the most important trait" and the cornerstone of many higher-level benefits
    • It has the biggest design impact, slices the whole architecture and must be considered from day one.
  • It even affects how teams and responsibilities are organised, per Conway's law (Melvin Conway, 1967): an organisation that designs a system produces a design that copies its communication structure.
  • Six things to isolate:
Isolation What it gives
Code Each service has its own codebase as a boundary for state and logic and acts as a bulkhead; teams develop, debug and release independently, often with dedicated CI/CD pipelines
Packaging (containers) A consistent runtime bundling code, dependencies and configuration, isolating each service at the operating-system level; avoids dependency conflicts and gives portability
Compute (pods) In Kubernetes, pods encapsulate containers and give resource isolation (allocated CPU, memory, network) so a hungry service cannot starve others, important in large multi-tenant clouds
API and event Services talk through APIs or asynchronous messaging, separating internals from outside interaction; they handle timeouts and retries without leaking problems to clients; key for eventual consistency
Database A separate database per service stops services affecting each other's data, eases schema changes, and lets each choose the best storage
Operational and failure Metrics, logging and monitoring scoped per service so problems are confined; circuit breakers and load balancing isolate fault domains
  • With isolation across these dimensions services evolve independently, scale as needed and reduce the risk of system-wide failures.

Autonomous operation

  • Isolation is a prerequisite for autonomy: only truly isolated services can decide and act independently and cooperate with others to solve problems.
  • Quote from Mark Burgess (promise theory):
    • "With a promise model, and a network of autonomous systems, each agent is only concerned with assertions about its own policy
    • no external agent can tell it what to do, without its consent."
  • Autonomous services give flexibility in orchestration, workflow management, collaborative behaviour, scalability, availability and runtime management, at the cost of more thoughtful design of well-defined, composable APIs.
  • It extends to teams, who can roll out services and features independently. Autonomy is the foundation for scaling both the system and the development organisation.

Single responsibility

  • The Unix philosophy (programs with a single, well-defined purpose that compose well) predates **Robert C
    • Martin's single responsibility principle (SRP)**: a class or component should "have only one reason to change".
  • Debate about microservice size ("What qualifies as micro?", "How many lines of code?") misses the point. Micro refers to the scope of responsibility: do one thing and do it well.
  • A single reason to exist prevents entanglement of business domains, makes each service more generally useful, and the system easier to scale, more resilient, simpler to understand, and easier to extend and maintain.
  • Figure 4-1:
    • an ordering system of three services (orders, payment, inventory), each with one well-defined function, encapsulated by bounded contexts
    • A bounded context acts as a complexity bulkhead, keeping unnecessary complexity from leaking out while keeping one domain model and language inside.

Exclusive state ownership

  • Microservices are typically stateful, encapsulating state and behaviour; isolation extends to state, so state and behaviour are treated as one unit.
  • Services must own their state exclusively (partition state)
    • Consequence: data is strongly consistent only within each service
    • Between services you rely on eventual consistency and forgo traditional transactional semantics.
  • That means abandoning a single all-encompassing database, full normalisation and cross-service joins. Figure 4-2 shows "a monolith disguised as a set of microservices".

Mobility with addressability

  • Containers and virtualisation are wasted if services are locked into a fixed topology or deployment. Mobility means moving services at runtime
    • paired with location transparency, services stay agnostic of the current deployment and topology.
  • Situations where it is essential:
Situation Example
Scaling and load balancing A seasonal sales event: new checkout and inventory instances across nodes or regions; location transparency lets balancers and discovery redirect traffic unseen
Failover and disaster recovery A banking application reroutes to a backup instance in another region during a regional outage
Edge and proximity City traffic monitoring: services migrate between edge nodes to handle local spikes or failures while keeping low-latency real-time data for emergency response
Cluster maintenance and upgrades A Kubernetes cluster reschedules pods onto other nodes to apply updates
Cost optimisation Workloads move to cheaper instances or regions automatically
  • In all cases clients and other services need no update when a service moves.

4.2 Slaying the monolith

  • The typical three-tier monolith (servlets, EJB, Java Persistence API, SQL database, or modern Spring) couples components inside and across services (Figure 4-3).
    • Deep synchronous call chains entangle services and prevent independent evolution; each service holds its caller hostage until all methods execute.
    • All services must be upgraded together; failures are hard to isolate and can cascade through the tiers; try-catch is "a blunt tool".
    • No isolation means you cannot scale one service; you scale the whole monolith.
    • Traditional application servers bundle services into one instance and manage "isolation" through class loader magic, a fragile model where services compete for CPU, memory and storage.

Avoid microliths

  • Refactoring to microservices by the path of least resistance (scaffolding tools, containers, synchronous APIs) yields microliths: small monoliths (Figure 4-4).
  • A microlith is a single-instance service that replaces synchronous method calls with synchronous blocking RPC while still using blocking database access (CRUD through JPA on a SQL database, sometimes still shared). It keeps the monolith's coupling and adds network latency
    • a single instance cannot scale out or stay available if it fails.
  • Docker or LXC containers and orchestration like Kubernetes manage and scale instances but do not solve the fundamental distributed-systems challenges of Chapter 1.
  • "Real complexity lies in the space in between services": communication, coordination, consistency, shared state and resources
    • These belong to the application's design and cannot easily be added afterwards.

Microservices come in systems

  • "One actor is no actor. Actors come in systems" (attributed to Carl Hewitt); likewise "One microservice is no microservice. Microservices come in systems."
  • The real difficulty is managing the space between services: how they interact, coordinate and share responsibilities
    • It forces you to embrace uncertainty, failure, autonomy, decoupling, asynchronous messaging and data partitioning, and to give up some consistency.
  • One of the best ways to design such systems is event-driven architecture and domain-driven design, in particular events-first DDD.

4.3 Events-first domain-driven design

  • The term was coined by Russell Miles:
    • design principles for scalable distributed systems that focus on the events (verbs) of the domain, not the domain objects (nouns)
    • It clarifies dataflow and communication patterns and leads to scalable event-driven architectures.

Focus on the behaviour of the system

  • OOP and DDD traditionally start with nouns to find domain objects and build up from there, which "forces us to focus on structure too early".
  • Focus on events to see how changes propagate, including communication patterns, workflows and data ownership
    • Greg Young (creator of CQRS): "When you start modeling events, it forces you to think about the behavior of the system, as opposed to thinking about structure inside the system."
  • Events add a temporal dimension, so time is a design element and causal relationships between events matter, especially where managing time and change is crucial.

Commands for intent, events for facts

  • Commands express an intent to act, often with side effects (changing state, triggering processes, sending more commands).
  • Events
    • are facts about the domain and part of the ubiquitous language, helping define the bounded context
    • Facts are immutable, cannot be changed or retracted, knowledge is cumulative (new facts, or facts derived from existing ones), and existing knowledge is invalidated by adding facts that refute it (facts are not deleted, only made irrelevant).
Commands Events
All about intent Intentless
Directed (sender to receiver) Anonymous (no address)
One clear destination (retaining the server address) Just happens, for 0 to N others to observe
Mimics a conversation (personal one-to-one) Mimics broadcast ("speaker's corner"; does not care who is listening)
Distributed focus (moves across address spaces) Local focus (no notion of communication, network or addresses; wrapped in messages to travel)
Command and control Autonomy

Understand causality by mining the facts

  • Model causality centrally with an event log, or decentrally with vector clocks or CRDTs.
  • Event storming
    • (Alberto Brandolini's book is the suggested start) gathers stakeholders (domain experts and programmers) in one room with sticky notes to define the language for events and commands
    • Three steps:
    1. Explore the domain by examining what happens to find events and their causal links.
    2. Identify the triggers of those events: command execution, user interactions, requests from other services, external inputs.
    3. Determine the endpoints for commands: typically a component that decides whether to execute side effects, possibly creating events that add new facts.
  • That leads to the components (entities) where events culminate, the source of truth.
  • Designing consistency boundaries (guided by Pat Helland's "Data on the Outside Versus Data on the Inside"):
    1. Avoid starting with behaviour; focus on the underlying data (the facts) and their coupling and dependencies.
    2. Identify and model the integrity constraints, with domain experts and stakeholders.
    3. Start with zero guarantees on the smallest dataset, adding the minimal guarantees needed while keeping the dataset small.
    4. Use the single responsibility principle as a guide.
  • The goal is to minimise the dataset that needs strong consistency; then define behaviour and protocols with other services, establishing the unit of consistency.

Localize mutable state and publish facts

  • Opening quote, John Backus (1977 Turing Award lecture): "The assignment statement is the von Neumann bottleneck of programming languages."
  • Assignment is destructive and overwrites previous data
    • As Rich Hickey (creator of Clojure) has discussed, most OO languages (Java, C++, C#) treat value and identity as the same thing, so an identity cannot evolve without changing its value
    • Functional languages (Scala, Haskell, OCaml) with pure functions and immutable data give stable values for reasoning.
  • Mutable state is not inherently bad:
    • contain it, using it only for local computation inside the service instance's safe haven, unobservable by the world
    • When done, create an immutable fact and publish it
    • Others rely on stable values while you keep mutability's simplicity and efficiency.
  • So many principles can overwhelm; higher-level abstractions and guardrails help, for example entities and event sourcing, which naturally guide toward the right architecture.

Model consistency boundaries with entities

  • The consistency boundary is both a unit of consistency and a unit of failure: updates, relocations and failures occur atomically
    • When leaving a monolith's single schema, denormalise to split it into several manageable schemas.
  • Treat each unit of consistency as an entity, and have entities reference each other by identity, not direct references
    • That keeps isolation, cuts memory use (no eager loading) and enables location transparency.
  • Entities that do not reference each other directly can be repartitioned and moved around the cluster for "almost infinite scalability" (Pat Helland, "Life Beyond Distributed Transactions").
  • Outside an entity's boundary you need eventual consistency. Ask: "Who is responsible for ensuring data consistency?" If the service executing the business logic, confine it to a single entity for strong consistency
    • otherwise eventual consistency is acceptable.
  • Order management example from an event-storming session (drastically simplified):
    • Commands: CreateOrder, SubmitPayment, ReserveProducts, ShipProducts
    • Events: OrderCreated, ProductsReserved, PaymentApproved, PaymentDeclined, ProductsShipped
    • Entities: Orders, Payments, Inventory
    • Figure 4-5 shows the command flow between a client and the entities (dotted arrows: asynchronous); Figure 4-6 adds the events.

  • Payments and orders (Figure 4-7), with event sourcing and CQRS:
    1. The SubmitPayment command is sent to the payments service by an external user of the service, namely orders.
    2. It crosses the bounded context boundary and is received by the processing layer, which validates and translates it before the business logic runs.
    3. A new command, ApprovePayment, representing the intent to change state, goes to the entity.
    4. The entity processes it, producing the event PaymentApproved and storing it in its event log.
    5. Once saved, the event is pushed to the event stream and forwarded to subscribers: the orders service and the payment query database (the CQRS read side).
  • The design enhances scalability, resilience and consistency, letting services resume after failures or replay portions of the event stream.

Allow for protocol evolution

  • A protocol defines the rules for exchanging messages:
    • relationships between participants, the protocol's current state and the messages allowed at each step
    • Unlike a local programming interface it supports several participants and tracks ongoing state.
  • Kinds:
    • request-reply, repeated request-reply (like HTTP), publish-subscribe, streaming (push and pull). A protocol defines only which messages may be sent
    • codecs and transport are implementation details.
  • Microservices stay independent only if they evolve autonomously, so their protocols (HTTP APIs, RPC, events, commands, stored data, and ephemeral data such as sessions, credentials and caches) must tolerate change
    • Version interoperability is essential.
  • Postel's law
    • (the robustness principle, from Jon Postel in RFC 761 on TCP, 1980): "be conservative in what you do, be liberal in what you accept from others"
    • It influenced the tolerant reader pattern.
  • Tasks in managing change:
    • select extensible codecs for serialisation
    • ensure incoming commands are valid
    • keep a translation layer that upgrades or downgrades events or commands to the current version
    • version the service itself (a truly new service differs semantically from a new version of an existing one)
  • Use an anti-corruption layer, inside the service or in an API gateway, to protect the bounded context from changes elsewhere while letting both evolve.

4.4 Conclusion

  • The author says the guide has "just scratched the surface" and urges readers to try the ideas, read the references in the hyperlinks and footnotes, and learn from past failures and successes.
  • Failures worth studying:
    • SOA, CORBA, EJB and synchronous RPC
    • Successful platforms to learn from: Tandem Computer's NonStop platform, the Erlang platform and the BitTorrent protocol.

Summary points

  • Five principles: isolation, autonomy, single responsibility, exclusive state ownership, mobility with addressability.
  • Do not build microliths; microservices come in systems, and the hard part is the space between them.
  • Model events (verbs) first, separate commands (intent) from events (facts), and keep strongly consistent datasets minimal inside entity boundaries.
  • Let protocols evolve with Postel's law, translation layers and an anti-corruption layer.
Terms to carry forward
  • Microlith: a single-instance, synchronous, blocking service that is a small monolith.
  • Events-first DDD: model domain events (verbs) before objects (nouns).
  • Command vs event: intent directed at one recipient vs an anonymous immutable fact.
  • Event storming: workshop to discover events, triggers and command endpoints.
  • Consistency boundary / entity: unit of consistency and failure, referenced by identity.
  • Postel's law / anti-corruption layer: tolerant protocols and protection of the bounded context.
