Software Architecture Patterns 1: Introduction

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), chapter 1. Next: Software Architecture Patterns 2: Architectural Structures and Styles.

Takeaways
  • Starting to code with no formal architecture usually produces a big ball of mud: ill-defined components, tight coupling, brittle code, no clear direction.
  • An architecture style gives an application its basic characteristics and behaviour; knowing each style's strengths and weaknesses is how you pick one for a business goal.
  • The 2nd edition says style, not pattern, for the five architectures it covers, to separate them from patterns such as CQRS.
  • Three levels: styles (macro structure) contain architecture patterns (reusable structural building blocks), which contain design patterns (how the source code is designed).
  • Hybrid styles are common because no single style solves every business problem; learn each style alone first.

1.1 Why a style matters

  • Without a defined style, developers end up with a big ball of mud: ill-defined components, a tightly coupled, brittle architecture that is hard to change and has no clear vision.
  • The architecture's characteristics then cannot be read off the design. The questions the chapter asks:
    • Does it scale?
    • What are its performance characteristics?
    • How easy is it to change or add features?
    • How responsive is it?
  • Styles differ in what they favour: some lend themselves to highly scalable systems, others to letting developers respond quickly to change.
  • Choosing well means knowing each style's characteristics, strengths and weaknesses against your business needs and goals.

1.2 What changed since the 1st edition (2015)

  • Microservices and event-driven architecture have grown in popularity, with new techniques and tools for building them.
  • Wide use of domain-driven design improved understanding of how architectures are structurally partitioned and how that partitioning affects design and implementation.
  • Other additions in this edition:
    • more on the intersection of architecture and data
    • an expanded analysis section at the end of each chapter, with guidelines for when to use and when not to use each style

1.3 Style, pattern and design pattern

The 2nd edition calls the architectures in the report architecture styles rather than architecture patterns, to remove confusion between, for example, event-driven architecture (a style) and CQRS (a pattern).

Term What it describes Example in the chapter
Architecture style The macro structure of a system Event-driven architecture, microservices
Architecture pattern A reusable structural building block used inside a style to solve a particular problem CQRS: separate services and databases for read operations and write operations
Design pattern How the source code is designed Builder
  • A pattern can sit inside any style: CQRS could be applied to any style in the report to optimise database queries and updates.
  • Architecture patterns differ from design patterns because they affect the structure of the system, while design patterns affect how the code is written.
  • The chapter's worked chain: use the Builder design pattern to implement the CQRS architecture pattern, then use CQRS as a building block inside a microservices architecture.

1.4 Hybrid styles

  • Design patterns and architecture patterns are combined to form a complete solution, and styles combine the same way.
  • Hybrids are common in the real world because not every style can solve every business problem.
  • Hybrids the chapter names:
    • event-driven microservices: events between microservices
    • space-based microservices: processing units implemented as microservices
    • event-driven microkernel: events between the core system and remote plug-in components
  • The chapter's caution: understand each individual style, with its strengths and weaknesses, before combining them.

1.5 Goal of the report

The aim is unchanged from the first edition: help senior developers and architects understand common styles, how they work, when to use them and when not to, so they can make the right architecture choice for their systems.

Summary points

  • Pick a style deliberately; skipping it tends to give a big ball of mud.
  • Styles (macro structure) contain patterns (structural building blocks) which contain design patterns (code design).
  • Real systems often hybridise styles; know the parts first.
Terms to carry forward
  • Big ball of mud: an architecture with ill-defined components, tight coupling and no clear direction.
  • Architecture style: the macro structure of a system.
  • Architecture pattern: a reusable structural building block used within a style (for example CQRS).
  • Design pattern: a code-level design solution (for example Builder).
  • Hybrid style: a combination of styles, such as event-driven microservices.
