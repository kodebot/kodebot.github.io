Software Architecture Patterns 5: Event-Driven Architecture

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), chapter 5. Previous: Software Architecture Patterns 4: Microkernel Architecture. Next: Software Architecture Patterns 6: Microservices Architecture.

Takeaways
  • Asynchronous processing with highly decoupled event processors (services) that trigger events and respond to events.
  • Four components: event processor, initiating event, processing event (also called a derived event) and event channel.
  • Services should always advertise their state changes, even if no one listens yet: that is the hook for future extension.
  • Events versus messages: an event says what happened and the sender owns the channel and contract; a message is a command to a known service and the receiver owns them.
  • Excels at fault tolerance, scalability, performance and extensibility; avoid it for request-based processing, high data consistency, tight control of workflow and timing, and when error handling must be simple.

5.1 Topology

  • An architecture style that relies on asynchronous processing using highly decoupled event processors that trigger events and respond to events happening in the system.
  • The chapter says its popularity has grown so much that even the way we think about it has changed
    • It solves hard problems such as complex nondeterministic workflows and highly reactive and responsive systems, and new techniques, tools, frameworks and cloud services make it more accessible.
Component What it is
Event processor (today usually called a service) The main deployment unit. Ranges from a single-purpose function (validating an order) to a large process (executing or settling a financial trade). It can trigger events and respond to them; usually both.
Initiating event Usually comes from outside the system and starts an asynchronous workflow: placing an order, buying Apple stock, bidding in an auction, filing an insurance claim. Usually received by one service, but not always: an auction bid might be picked up by both a Bid Capture and a Bid Tracker service.
Processing event (today usually a derived event) Generated when a service's state changes and it advertises that change. One initiating event spawns many processing events: Place Order may lead to Order Placed, Payment Applied, Inventory Updated. Initiating events are usually noun-verb (Place Order); processing events usually verb-noun (Order Placed).
Event channel The physical messaging artifact (queue or topic) that stores triggered events and delivers them to responders. Initiating events usually use point-to-point channels (queues, messaging services); processing events usually use publish-and-subscribe channels (topics, notification services).

5.2 Example: ordering a book

A customer orders a copy of Fundamentals of Software Architecture (Mark Richards and Neal Ford, O'Reilly).

  1. The initiating event is Place Order, received by the Order Placement service, which places the order.
  2. It advertises what it did with an Order Placed processing event. It does not know which other services, if any, respond: this shows the highly decoupled, nondeterministic nature of the style.
  3. Three services respond: Payment, Inventory Management and Notification. Each does its business function and advertises what it did through further processing events.
  4. The Notification service generates a Notified Customer event that no other service responds to.
    • Why trigger an event nobody cares about? Architectural extensibility: it is a hook a future service (such as a notification-tracking service) can respond to without any other change to the system.
    • Rule of thumb:
      • always have services advertise their state changes, whether or not others respond
      • An unheard event simply disappears from the topic, or is saved for later processing, depending on the messaging technology.

5.3 Event-driven versus message-driven

The chapter calls the difference "subtle" but important: event-driven systems process events, message-driven systems process messages.

Event Message
What it is Tells others about a state change or something you did: "I just placed an order", "I just submitted a bid" A command or request to a specific service: "apply a payment to this order", "ship this item to this address", "give me the customer's email address"
Who responds The sender has no idea which services, or how many Usually directed to a single known service (for example Payment)
Channel and contract owner The sender owns the event channel and contract The receiver owns the message channel and contract
Typical channel Publish-and-subscribe: topics, notification services Point-to-point: queues, messaging services

  • Figure 5-3 (events):
    • Order Placement sends Order Placed, answered by Payment
    • The sender owns the channel and contract, so contract changes start with Order Placement and Payment (and every other responder) must conform.
  • Figure 5-4 (messages): Order Placement commands Payment to apply the payment. Payment owns the queue and the contract, so Order Placement must conform to changes Payment initiates.
  • Event-driven systems can use point-to-point messaging: sometimes it is needed to retrieve specific information from another service or to control the order or timing of events.

5.4 Considerations and analysis

Because it is asynchronous and decoupled, it excels at fault tolerance, scalability and high performance, and gives excellent extensibility when adding features. The chapter then lists reasons to be cautious.

When to consider this style

  • It is the architecture of choice for systems that need high performance, high scalability and high fault tolerance.
  • The business processing is reacting to things happening in and around the system, not responding to a user request.
    • Listen to stakeholders: do they say "event", "triggers", "react to something happening"?
    • Ask: am I responding to a user request, or reacting to something the user did?
  • Complex, nondeterministic workflows
    • that are hard to model
    • The chapter says developers have spent decades building complex decision trees for every outcome, "only to continually fail at this fool's errand"
    • Such systems are sometimes classed as CEP (complex event processing), which event-driven architecture manages natively.

When not to consider this style

  1. Mostly request-based processing: a user requesting data (a customer profile) or basic CRUD on entities. Also when most processing is synchronous and the user must wait for completion.
  2. High data consistency needs. All processing is eventually consistent, with little or no guarantee of when processing occurs. If you expect data at a certain time, look elsewhere, for example service-based, which helps preserve consistency.
  3. Control over workflow and timing. Example: Event A and Event B must complete before Event C; D and E must wait for C; D must start before E. The chapter says you are better off with orchestrated service-oriented architecture or orchestrated microservices for that coordination.
  4. Error handling. There is usually no central orchestrator, so a failing service must try to repair the error itself, and everything is asynchronous so other actions may already have happened.
    • Example: Order Placed triggers Notification, Payment and Inventory at the same time. Notification and Payment complete, but Inventory fails because there are no books left.
    • The customer is already notified and charged. Should payment be reversed? Another notification sent? Processing wait for stock? Which service does this?
    • The chapter calls error handling "one of the more complex aspects" of the style.

Summary points

  • Asynchronous, decoupled event processors; initiating events from outside, processing events advertised by services.
  • Advertise every state change: unheard events are cheap hooks for future features.
  • Events (sender owns channel) differ from messages (receiver owns channel).
  • Strong on scalability, fault tolerance, performance and extensibility; weak on simplicity, with eventual consistency and hard error handling.
Terms to carry forward
  • Event processor: a service, the main deployment unit.
  • Initiating event / processing (derived) event: the external trigger / the advertised state change.
  • Event channel: queue or topic that stores and delivers events.
  • Event-driven vs message-driven: events inform; messages command.
  • CEP: complex event processing.
  • Eventual consistency: no guarantee when processing happens.
