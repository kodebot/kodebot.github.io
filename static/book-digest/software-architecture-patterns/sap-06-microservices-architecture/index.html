Software Architecture Patterns 6: Microservices Architecture

Source: Mark Richards, Software Architecture Patterns, 2nd edition (O'Reilly, 2022), chapter 6. Previous: Software Architecture Patterns 5: Event-Driven Architecture. Next: Software Architecture Patterns 7: Space-Based Architecture.

Takeaways
  • An ecosystem of single-purpose, separately deployed services, usually reached through an API gateway. The chapter calls it "perhaps one of the most complicated architecture styles to get right".
  • "Micro" refers to what a service does, not its size: a service with 312 classes that only sends customer emails still counts.
  • Each service owns its data in a bounded context (term coined by Eric Evans); other services must ask the owner through a contract.
  • Three things make it unique: distributed data, operational automation and organisational change.
  • Strong on agility, scalability, fault tolerance and extensibility; weak on performance (network, security and data latency), cost and simplicity. If data is tightly coupled, consider service-based instead.

6.1 Basic topology

  • The style is an ecosystem of single-purpose, separately deployed services, typically accessed through an API gateway.
  • Client requests come from a user interface (usually a microfrontend) or an external request and hit well-defined endpoints on the API gateway, which forwards them to separately deployed services.
  • Each service accesses its own data, or requests data it does not own from other services.
  • Figure 6-1 shows a database per service, but that need not be so (and usually is not): each service owns its collection of tables, usually a schema housed in a single highly available database, or in one database devoted to a particular domain.
    • Only the owning service may access and update that data; others must ask the owner rather than read the tables.
  • The API gateway hides the location and implementation of the services behind its endpoints, and may perform cross-cutting infrastructure functions such as security, metrics gathering and request-ID generation.
    • Unlike the ESB in service-oriented architecture, it contains no business logic and does no orchestration or mediation. That is critical to preserve the bounded context.

6.2 What is a microservice?

  • A single-purpose, separately deployed unit of software that does one thing really, really well.
  • The name comes from what the service does, not its physical size (number of classes). They are generally fine-grained but need not be.
  • The chapter's example: a service of 312 class files that sends emails to customers, one class per each of 300+ emails. It does one thing really well, so it is a microservice.
  • Because services are single-purpose, an ecosystem can contain hundreds to thousands of separately deployed microservices; the sheer number is what makes the style unique.
  • They can be deployed as containerised services (such as Docker) or as serverless functions.

6.3 Bounded context

  • Each service typically owns its data. Example: a Wishlist service owns the wishlist tables; others must ask it for wishlist data.
  • This is a bounded context, a term coined by Eric Evans in Domain-Driven Design (Addison-Wesley): all the source code for a domain or subdomain (a customer's wish list) plus its data structures and data are encapsulated as one unit.
  • The chapter says microservices "wouldn't exist" without the notion of a bounded context.

  • Why it is critical.
    • Imagine 250 microservices all using one set of tables in a monolithic database
    • Drop a column or table that 120 of them access, and you must modify, test and deploy 120 services at the same time as the database change: "simply not feasible".

  • The bounded context gives agility and manages change control: only the owning service changes when data structure changes.
  • Other services get data through a separate contract, usually a different representation from the physical database structure, so they and their contracts usually need no change.

6.4 Unique features

The chapter says three things set the style apart from every other:

  1. Distributed data.
    • It is the only style that requires data to be broken up and distributed across services, because of the number of services
      • Other styles do not define fine-grained single-purpose services, so they can usually get by with one monolithic database.
    • In the real world the bounded context rarely holds completely
      • A handful of services (two to six) may need to share data, through table coupling, foreign key constraints, triggers, materialised views, performance optimisations or shared table ownership.
    • When data is shared, the bounded context is extended to include the shared tables and every service that accesses them.
  2. Operational automation.
    • Nobody can manage parallel testing, deployment and monitoring of hundreds to thousands of separately deployed units by hand, so containerisation is usually required, plus orchestration platforms such as Kubernetes.
    • DevOps becomes a requirement, not a nice-to-have. Services cannot be handed off to separate testing and release teams: teams own their services' testing and release.
  3. Organisational change.
    • It is the only style requiring cross-functional, domain-aligned teams with specialisation (UI, back-end and database developers in one team), and service owners (usually architects) per domain.
    • Testers, release engineers and DBAs are aligned to domain areas as "virtual teams" that test and release their own services.

6.5 Examples and use cases

  • Retail order entry is the classic fit: placing an order, applying a payment, notifying the customer, managing inventory, fulfilling, shipping, tracking, sending surveys and data analytics are separate, distinct functions that suit separately deployed services.
  • Business intelligence and analytics reporting: each report, query, data feed or analytic as its own microservice over a data lake or data warehouse.
    • There is no strict bounded context with the data, but it still works because a lake's or warehouse's schema rarely suffers breaking changes: older schemas are deprecated and new ones created, which eases the change-control problems of transactional data.

6.6 Considerations and analysis

The chapter calls it very popular and powerful but "perhaps the hardest architecture style to get right". Hard parts it lists:

  • Service granularity.
    • The single responsibility principle is highly subjective: is a notification service that sends email and SMS single purpose, or is notifying by email single purpose?
    • More objective justifications: code volatility, fault tolerance, scalability and throughput, access control.
  • Communication.
    • Asynchronous or synchronous?
    • Orchestration (a mediating orchestration service) or choreography (services talk directly)?
    • Each choice has trade-offs.
  • Data. If Wishlist needs product information from Product Catalog, should it ask over REST, cache the data in an in-memory data grid, expand its own table schema to hold the product data, or share the catalog data? All have trade-offs.
  • Also distributed transaction management, contracts, code reuse techniques and migration patterns
    • The chapter points to Software Architecture: The Hard Parts by Neal Ford et al
    • (O'Reilly), which covers them.

When to consider this style

  • Your application can be broken into dozens or hundreds of distinct, independent pieces of functionality: that is exactly the shape of microservices.
  • High agility:
    • the bounded context binds subdomain functionality to its data, so changes are easy to locate
    • testing scope shrinks to one single-purpose service, making full regression testing achievable
    • deployment risk drops because usually one service deploys, often as a hot deploy mid-day instead of weekend big-bang deployments
  • High fault tolerance and scalability, both at function level; MTTS and MTTR are usually hundreds of milliseconds, so it is also good for elastic systems.
  • Lots of extensibility:
    • "drop-in" functionality, which the chapter describes as creating a service, wrapping it in a container, creating an API endpoint and deploying it
    • It adds: "Sounds easy, right? Well, in theory it is."

When not to consider this style

  • Complex workflows. If the separately deployed functionality must be tied together with complex workflows and lots of inter-service communication or orchestration, do not use it.
  • Tightly coupled, monolithic data.
    • If you cannot break the data into dozens to hundreds of schemas or databases, "run away in the opposite direction"
    • Coupling can sit in foreign key constraints, triggers, views and even stored procedures
    • Consider service-based architecture instead.
  • Cost and time.
    • The chapter calls it perhaps the most complex style that exists, and very expensive: licensing fees for platforms, products, frameworks and databases rise with the number of services
    • Under tight cost and time constraints choose a hybrid such as service-based architecture.
  • Performance and responsiveness, because services communicate remotely and incur three latencies:
    • Network latency: packets reaching the target service, roughly 30 ms to 300 ms or more depending on protocol and distance.
    • Security latency: authenticating or authorising the request, from a few milliseconds to 300 ms or more.
    • Data latency:
      • the time for other services to query data you do not own for you. If Wishlist asks Product Catalog for descriptions, Product Catalog must make an additional database call
      • with a shared monolithic database that is a single call with a join.

Summary points

  • Single-purpose, separately deployed services behind an API gateway with no business logic.
  • Each service owns its data in a bounded context; others ask through a contract.
  • Unique demands: distributed data, operational automation, organisational change.
  • Best for separable, independent functionality needing agility, scale and fault tolerance; worst for tightly coupled data, complex workflows, tight budgets and high performance.
Terms to carry forward
  • Microservice: a single-purpose, separately deployed unit that does one thing really well.
  • API gateway: front door that hides service location; no business logic.
  • Bounded context: a domain's code and data encapsulated together (Eric Evans).
  • Microfrontend: the usual form of the user interface in this style.
  • MTTS / MTTR: mean time to start / recovery.
  • Network, security and data latency: the three costs of remote service calls.
