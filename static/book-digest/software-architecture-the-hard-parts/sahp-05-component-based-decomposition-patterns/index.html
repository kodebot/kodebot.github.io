Software Architecture: The Hard Parts 5: Component-Based Decomposition Patterns

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 5. Previous: Software Architecture: The Hard Parts 4: Architectural Decomposition. Next: Software Architecture: The Hard Parts 6: Pulling Apart Operational Data.

Takeaways
  • Six patterns, used in sequence to break a structured monolith into services, then individually during maintenance: Identify and Size Components, Gather Common Domain Components, Flatten Components, Determine Component Dependencies, Create Component Domains, Create Domain Services.
  • Each pattern has a description, fitness functions for governance (so the codebase stays correct while the migration runs) and a Sysops Squad worked example.
  • Changes are recorded as architecture stories, distinct from user stories and from technical debt stories.
  • Services are built from components (leaf-node namespaces holding code), not from classes; orphaned classes in root namespaces must be removed.
  • Sizes, shared-code percentages and coupling counts are the measurements that decide whether a migration is feasible.

5.1 The pattern roadmap

  • Logan says little is written on these patterns
    • he learned of them at a conference about four years earlier, in a session by an experienced architect, and has used them "with quite a bit of success" for an iterative, methodical, safe move from monolith to service-based architecture and microservices.
  • They suit a codebase that is "somewhat structured and grouped by namespaces (or directories)".
  • The six patterns (Figure 5-1):
Pattern Purpose
Identify and Size Components Usually first: identify, manage and properly size components
Gather Common Domain Components Consolidate duplicated business-domain logic, reducing duplicate services later
Flatten Components Collapse or expand domains, subdomains and components so code lives only in well-defined components
Determine Component Dependencies Identify and refine dependencies; judge feasibility and effort of the migration
Create Component Domains Group components into logical domains; align namespaces and directories to them
Create Domain Services Physically break the monolith by moving domains to separately deployed domain services
  • Each pattern is described in three sections: Pattern Description (how, why, outcome), Fitness Functions for Governance (automated checks during ongoing maintenance, since systems are moving targets) and a Sysops Squad illustration.

Architecture stories

  • An architecture story records code refactoring that affects the structure of the application and satisfies a business driver such as scalability or time-to-market
    • Example: "As an architect, I need to decouple the payment service to support better extensibility and agility when adding additional payment types."
  • Unlike user stories (features) and unlike technical debt stories (cleanup done later), an architecture story captures something that must change quickly to support an architecture characteristic or business need.

5.2 Identify and size components pattern

Pattern description

  • Services are built from components, so identify them and size them. Components too large (doing too much) are more coupled, harder to split into services and make the architecture less modular
    • components too small do not do enough.
  • Files, classes and lines of code are poor size metrics because programmers design differently
    • The useful metric is the total number of statements in a component (a single complete action terminated by a character such as a semicolon, or a newline in Python and Ruby).
  • Keep sizes consistent:
    • component size should fall within one to two standard deviations of the mean, and each component's share of the code should be somewhat evenly distributed
    • Static analysis tools usually show statements per file, so the architect post-processes to accumulate by component and compute percentages.
  • The inventory (Table 5-1) records:
Field Meaning
Component name Descriptive, consistent across diagrams; rename vague ones (a component called "Ticket Manager" leaves too many unanswered questions)
Component namespace Namespace, package or directory (dots replace separators: ss/customer/notification becomes ss.customer.notification); keep the identifier type consistent
Percent Statements in the component divided by statements in the whole codebase (5 for ss.billing.payment means 5% of the codebase)
Statements Sum of statements in all its source files; a "simple" Customer Wishlist with 12,000 statements is more complex than it looks
Files Number of source files (classes, interfaces, types); a component with 18,409 statements and only 2 files is a candidate for splitting into smaller classes
  • To resize a large component use functional decomposition or a domain-driven approach to find subdomains
    • Example: a Trouble Ticket component at 22% of the code, covering creation, assignment, routing and completion, could become four components
    • If no clear subdomains exist, leave it.

Fitness functions for governance

Automated holistic fitness functions run on deployment through CI/CD, custom code or open-source or COTS tools:

  1. Maintain component inventory: alerts the architect to components added or removed (Example 5-1):
# Get prior component namespaces that are stored in a datastore
LIST prior_list = read_from_datastore()

# Walk the directory structure, creating namespaces for each complete path
LIST current_list = identify_components(root_directory)

# Send an alert if new or removed components are identified
LIST added_list = find_added(current_list, prior_list)
LIST removed_list = find_removed(current_list, prior_list)
IF added_list NOT EMPTY
{
    add_to_datastore(added_list)
    send_alert(added_list)
}
IF removed_list NOT EMPTY
{
    remove_from_datastore(removed_list)
    send_alert(removed_list)
}
  1. No component shall exceed some percent of the codebase (Example 5-2). The threshold depends on size: 30% for a small application with 10 components, 10% for a large one with 50.
# Walk the directory structure, creating namespaces for each complete path
LIST component_list = identify_components(root_directory)

# Walk through all of the source code to accumulate total statements
total_statements = accumulate_statements(root_directory)

# Walk through the source code for each component, accumulating statements
# and calculating the percentage of code each component represents. Send
# an alert if greater than 10%
FOREACH component IN component_list
{
    component_statements = accumulate_statements(component)
    percent = component_statements / total_statements
    IF percent > .10
    {
        send_alert(component, percent)
    }
}
  1. No component shall exceed some number of standard deviations from the mean size (Example 5-3, three standard deviations). The sample standard deviation is s = sqrt( (1/(N-1)) * sum((x_i - mean)^2) ), with the mean the average of observed sizes.
# Walk the directory structure, creating namespaces for each complete path
LIST component_list = identify_components(root_directory)

# Walk through all of the source code to accumulate total statements and number
# of statements per component
SET total_statements TO 0
MAP component_size_map
FOREACH component IN component_list
{
    num_statements = accumulate_statements(component)
    ADD num_statements TO total_statements
    ADD component,num_statements TO component_size_map
}

# Calculate the standard deviation
SET square_diff_sum TO 0
num_components = get_num_entries(component_list)
mean = total_statements / num_components
FOREACH component,size IN component_size_map
{
    diff = size - mean
    ADD square(diff) TO square_diff_sum
}
std_dev = square_root(square_diff_sum / (num_components - 1))

# For each component calculate the number of standard deviations from the
# mean. Send an alert if greater than 3
FOREACH component,size IN component_size_map
{
    diff_from_mean = absolute_value(size - mean);
    num_std_devs = diff_from_mean / std_dev
    IF num_std_devs > 3
    {
        send_alert(component, num_std_devs)
    }
}

5.3 Gather common domain components pattern

Pattern description

  • Domain functionality
    • is part of the business logic and common to only some processes (notification, data formatting, data validation)
    • infrastructure functionality is operational and common to all processes (logging, metrics, security).
  • Consolidating common domain functionality removes duplicate services
    • the subtle differences between duplicated versions are usually easy to resolve in one common service or shared library.
  • Finding it is mostly manual
    • Hints: shared classes across components or a common inheritance structure
    • Example: an SMTPConnection class used by five classes in different namespaces suggests spread-out email notification.
  • Another hint is names. Ticket Auditing (penultimate.ss.ticket.audit), Billing Auditing and Survey Auditing all insert a row in an audit table
    • consolidate into penultimate.ss.shared.audit.
  • Not everything becomes a shared service: common code can go in a shared library bound at compile time (service versus library trade-offs in Chapter 8).

Fitness functions (somewhat manual)

Subjectivity limits automation, but these help:

  1. Find common names in leaf nodes of component namespaces (Example 5-4), with an exclusion file for known false positives such as .calculate or .validate:
# Walk the directory structure, creating namespaces for each complete path
LIST component_list = identify_components(root_directory)

# Locate possible duplicate component node names that are not in the exclusion
# list stored in a datastore
LIST excluded_leaf_node_list = read_datastore()
LIST leaf_node_list
LIST common_component_list
FOREACH component IN component_list
{
    leaf_name = get_last_node(component)
    IF leaf_name IN leaf_node_list AND
       leaf_name NOT IN excluded_leaf_node_list
    {
        ADD component TO common_component_list
    }
    ELSE
    {
        ADD leaf_name TO leaf_node_list
    }
}

# Send an alert if any possible common components were found
IF common_component_list NOT EMPTY
{
    send_alert(common_component_list)
}
  1. Find common code across components (Example 5-5), also with an exclusion file:
# Walk the directory structure, creating namespaces for each complete path and a list
# of source file names for each component
LIST component_list = identify_components(root_directory)
LIST source_file_list = get_source_files(root_directory)
MAP component_source_file_map
FOREACH component IN component_list
{
    LIST component_source_file_list = get_source_files(component)
    ADD component, component_source_file_list TO component_source_file_map
}

# Locate possible common source file usage across components that are not in
# the exclusion list stored in a datastore
LIST excluded_source_file_list = read_datastore()
LIST common_source_file_list
FOREACH source_file IN source_file_list
{
    SET count TO 0
    FOREACH component,component_source_file_list IN component_source_file_map
    {
        IF source_file IN component_source_file_list
        {
            ADD 1 TO count
        }
    }
    IF count > 1 AND source_file NOT IN excluded_source_file_list
    {
        ADD source_file TO common_source_file_list
    }
}

# Send an alert if any source files are used in multiple components
IF common_source_file_list NOT EMPTY
{
    send_alert(common_source_file_list)
}

5.4 Flatten components pattern

Pattern description

  • When components are built on top of other components, they "lose their identity". Flatten so that components are leaf nodes of the directory or namespace tree.
  • Extending a namespace (adding a node) turns the prior namespace into a subdomain
    • Example: ss.survey (5 class files) extended by ss.survey.templates (7 classes), Table 5-8
    • Treating Survey Templates as a subcomponent of Survey raises the question of whether they form one service or two.
  • The resolution: a component is the last (leaf) node of a namespace or directory. So ss.survey.templates is a component and ss.survey a subdomain.
Term Definition
Component A collection of classes in a leaf-node namespace doing specific functionality (payment processing, customer survey)
Root namespace A namespace node extended by another node (ss.survey is extended by .templates); also called a subdomain
Orphaned classes Classes in a root namespace, so belonging to no definable component
  • In Figure 5-6 (drawn bottom-up to emphasise "hills"), ss.survey and ss.ticket are root namespaces with orphaned classes
    • the only components are ss.survey.templates, ss.login, ss.ticket.assign and ss.ticket.route.
  • Two ways to flatten ss.survey:
    • move the template code down into ss.survey, making it one component (Figure 5-7)
    • apply functional decomposition or DDD to the orphaned classes to create new leaf components, for example ss.survey.create (creates and sends the survey) and ss.survey.process (processes a completed survey) (Figure 5-8)
  • Whichever direction, make sure code lives only in leaf nodes.
  • Shared code in a root namespace is also orphaned (Figure 5-9). Move it to a new component such as ss.survey.shared (Figure 5-10).
  • Name shared components with a unique word not used elsewhere, such as .sharedcode or .commoncode, so you can compute the percentage of code that is shared and the number of shared components. If shared-code namespaces total 45% of the code, a distributed architecture will probably drown in shared-library dependencies
    • the count of such components shows how many shared libraries (JAR, DLL) or shared services will result.

Fitness function

  • Some subjectivity remains (consolidate down or split up?)
    • This helps: no source code should reside in a root namespace (Example 5-6), alerting on orphaned classes at any time, including during ongoing maintenance:
# Walk the directory structure, creating namespaces for each complete path
LIST component_list = identify_components(root_directory)

# Send an alert if a non-leaf node in any component contains source files
FOREACH component IN component_list
{
    LIST component_node_list = get_nodes(component)
    FOREACH node IN component_node_list
    {
        IF contains_code(node) AND NOT last_node(component_node_list)
        {
            send_alert(component)
        }
    }
}

5.5 Determine component dependencies pattern

Three common questions: Is it feasible to break apart the monolith? What is the rough level of effort? Rewrite or refactor? A CIO once asked one author whether the migration was "a golfball, basketball, or an airliner"; applying this pattern answered it: an airliner, "but only a small Embraer 190 migration rather than a large Boeing 787 Dreamliner migration".

Pattern description

  • Analyse incoming and outgoing dependencies between components to predict the service dependency graph after the split. Each component is a service candidate, so interactions matter.
  • It concerns component dependencies, not class dependencies inside a component: a dependency forms when a class in one component's namespace uses a class in another. Example 5-7:
namespace ss.survey
class CustomerSurvey
{
    function createSurvey
    {
        ...
    }

    function sendSurvey
    {
        ...
        ss.notification.CustomerNotification.send(customer_id, survey)
    }
}
  • Survey has an efferent dependency on Notification; Notification has an afferent dependency on Survey. A component's internal class mess does not matter here.
  • Tools and IDE plug-ins draw component dependency diagrams, answering the three questions:
Diagram Feasible? Effort Rewrite or refactor?
Figure 5-13: a single dependency between components Yes Golf ball (relatively straightforward) Refactoring (move existing code into separately deployed services)
Figure 5-14: many dependencies, worst on the left, "typical of most business applications" Maybe Basketball (much harder) Some refactoring, some rewriting
Figure 5-15: too many dependencies No ("turn around and run in the opposite direction") Airliner Total rewrite
  • The diagrams are "a radar" to locate the enemy (high coupling) and picture the resulting service dependency matrix
    • Component coupling is one of the most significant factors in migration success and feasibility, and teams often jump to microservices without any such analysis and struggle.
  • Measure CA (afferent), CE (efferent) and CT (total = CA + CE)
    • Splitting a component can reduce coupling: if component A has CA 20 but 14 dependants need only a small part, split it into A1 (the small coupled part, CA 14) and A2 (the majority, CA 6).

Fitness functions

  • No component shall have more than some number of total dependencies
    • (Example 5-8, combined threshold of 15, relatively high for most applications; can be variants for incoming only or outgoing only). The pseudocode as printed has unbalanced braces
    • its intent is to count incoming and outgoing references per source file in each component and alert above the limit:
# Walk the directory structure, gathering components and the source code files
# contained within those components
LIST component_list = identify_components(root_directory)
MAP component_source_file_map
FOREACH component IN component_list
{
    LIST component_source_file_list = get_source_files(component)
    ADD component, component_source_file_list TO component_source_file_map
}

# Determine how many references exist for each source file and send an alert if
# the total dependency count is greater than 15
FOREACH component,component_source_file_list IN component_source_file_map
{
    FOREACH source_file IN component_source_file_list
    {
        incoming_count = used_by_other_components(source_file, component_source_file_map)
        outgoing_count = uses_other_components(source_file)
        total_count = incoming_count + outgoing_count
        IF total_count > 15
        {
            send_alert(component, total_count)
        }
    }
}
  • Component X should not depend on component Y (Example 5-9, ArchUnit): one function per restriction.
// DependencyRules.java
public void ticket_maintenance_cannot_access_expert_profile()
{
    noClasses().that()
        .resideInAPackage("..ss.ticket.maintenance..")
        .should().accessClassesThat()
        .resideInAPackage("..ss.expert.profile..")
        .check(myClasses);
}

5.6 Create component domains pattern

Pattern description

  • A service usually contains one or more components (one-to-many), so group components into component domains to create coarse-grained domain services
    • This tells you what becomes a service-based architecture's domain services.
  • Domains are expressed in namespaces (Figure 5-18): second node is the domain (.customer), third a subdomain (.billing), the leaf the component (.payment), and .MonthlyBilling a class in that component.
  • Older systems predate DDD, so namespaces often need refactoring to show domains. Table 5-13 lists customer-related components whose namespaces do not say so
    • Table 5-14 adds the .customer node:
Component Before After
Billing Payment ss.billing.payment ss.customer.billing.payment
Billing History ss.billing.history ss.customer.billing.history
Customer Profile ss.customer.profile ss.customer.profile
Support Contract ss.supportcontract ss.customer.supportcontract

Fitness function

  • All namespaces under a root node should be restricted to a list of domains (Example 5-10, ArchUnit), preventing teams from accidentally creating new domains:
// DomainRules.java
public void restrict_domains()
{
    classes()
        .should().resideInAPackage("..ss.ticket..")
        .orShould().resideInAPackage("..ss.customer..")
        .orShould().resideInAPackage("..ss.admin..")
        .check(myClasses);
}

5.7 Create domain services pattern

Pattern description

  • Move each well-defined component domain to a separately deployed domain service, producing a service-based architecture: coarse-grained services containing all functionality for a domain (Ticketing, Customer, Reporting).
  • Basic topology (Figure 5-20):
    • a user interface remotely accessing coarse-grained domain services that share one monolithic database
    • Variants exist (split UI, split database, API gateway), but this is a good starting point.
  • Benefit beyond those in Chapter 4:
    • teams learn about each domain service to decide whether to split it into microservices or leave it coarse
    • "Too many teams make the mistake of starting out too fine-grained", then must embrace all the trappings of microservices (data decomposition, distributed workflows and transactions, operational automation, containerisation) without needing them.
  • Figure 5-21: the Reporting domain is extracted into its own deployed Reporting service.
  • Do not apply the pattern until all component domains are identified and refactored. Otherwise a migrated service must be modified later, for example adding the Survey component to an already-created Ticket service.

Fitness function

  • All components in a domain service should start with the same namespace (Example 5-11, ArchUnit), so the service does not become its own unstructured monolith
    • one function per domain service:
// TicketServiceRules.java
public void restrict_domain_within_ticket_service()
{
    classes().should().resideInAPackage("..ss.ticket..")
        .check(myClasses);
}

Sysops Squad: creating domain services

  • Addison and Austen and the team plan a staged migration: extract each component domain from the monolith into a new project workspace, and make the user interface access the domain remotely.
  • They migrate component by component (Figure 5-22) until each domain is a separately deployed service: a service-based architecture.

Summary

  • "Seat-of-the-pants" migrations rarely work. These patterns give a structured, controlled, incremental way to break apart monoliths.
  • Next steps: decompose the monolithic data (Chapter 6) and, where needed, split domain services into microservices (Chapter 7).
Terms to carry forward
  • Architecture story: a structural refactoring story tied to a business driver.
  • Component: classes in a leaf-node namespace; root namespace (subdomain); orphaned classes.
  • Domain vs infrastructure functionality: business logic common to some processes vs operational concerns common to all.
  • CA, CE, CT: afferent, efferent, total coupling.
  • Component domain / domain service: grouped components / the separately deployed service made from them.
  • Golf ball, basketball, airliner: migration effort sizing.
