Software Architecture: The Hard Parts 6: Pulling Apart Operational Data

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 6. Previous: Software Architecture: The Hard Parts 5: Component-Based Decomposition Patterns. Next: Software Architecture: The Hard Parts 7: Service Granularity.

Takeaways
  • Breaking apart a database is harder and riskier than breaking apart application code: data is the company's most important asset and is tightly coupled to functionality.
  • Decide with six data disintegrators (change control, connection management, scalability, fault tolerance, architectural quanta, database type optimisation) against two data integrators (data relationships, database transactions).
  • Decompose with the five-step process built on data domains: analyse, assign tables to schemas, separate connections, move schemas to separate servers, switch over.
  • The end state is data sovereignty per service: each service owns its data and others must ask it through a contract.
  • Once data is split, each domain can pick the most suitable database type; the chapter rates eight types on seven characteristics.

6.1 The scene: justifying the split

  • The Sysops Squad application is now separately deployed domain services. Addison starts on the monolithic database, with the data architect Dana and DBA Devon.
  • Dana refuses to break it apart without a solid justification; only then will Dana discuss Devon's five-step process.
  • Parallels with code decomposition: components map to data domains, class files to tables, and coupling points between classes to foreign keys, views, triggers and stored procedures.
  • Some styles need split data (microservices: each service owns its data, forming a bounded context), others tolerate one shared database (service-based).

6.2 Data decomposition drivers

Data disintegrators (when to break data apart)

Driver Question
Change control How many services are hit by a database table change?
Connection management Can the database handle the connections of many distributed services?
Scalability Can the database scale to the demand of the services using it?
Fault tolerance How many services are hit by a database crash or maintenance downtime?
Architectural quanta Is the shared database forcing one undesirable quantum?
Database type optimisation Could multiple database types suit the data better?

Change control

  • Breaking changes (drop a table or column, rename, change a column type) break the SQL of every service using that table. Adding tables or columns generally does not.
  • With a shared database, every impacted service must be updated, tested and deployed together with the database change
    • The book's example: imagine coordinating 42 services for one change.
  • The bigger danger is a forgotten service that touches the changed table: it fails in production until redeployed
    • With 400 microservices sharing one clustered database, finding every user of a table is, in the authors' words, a mind-numbing exercise.
  • A bounded context (Eric Evans, Domain-Driven Design) encapsulates code, logic, data structures and data
    • Usually it forms around a service and the data it owns, meaning the service that writes to it (read-only access is not ownership; see chapter 9).
  • Another service needing that data must ask the owner (techniques in chapter 10), not read the database.
  • The contract returned to the caller can differ from the schema, which abstracts the caller from the database. Worked example:
-- Wishlist table in Database D
CREATE TABLE Wishlist
(
    CUSTOMER_ID VARCHAR(10),
    ITEM_ID VARCHAR(20),
    QUANTITY INT,
    EXPIRATION_DT DATE
);

{
    "$schema": "http://json-schema.org/draft-04/schema#",
    "properties": {
        "cust_id": {"type": "string"},
        "item_id": {"type": "string"},
        "qty": {"type": "number"},
        "exp_dt": {"type": "number"}
    }
}
  • The contract names the date exp_dt and sends it as an epoch number, while the table has a DATE column. If the business stops expiring wish lists:
-- schema.sql
ALTER TABLE Wishlist
DROP COLUMN EXPIRATION_DT;
  • Service D must change, but the contract need not: until it is changed on purpose, D can send a far-future date or zero for "does not expire". Service C is shielded from the schema.

Connection management

  • Opening a database connection is expensive, so a connection pool is used to speed things up and to cap concurrent connections. In a monolith the application server owns the pool
    • in a distributed system each service instance has its own.
  • The first sign of saturation is connection waits, which also show up as request time-outs or tripped circuit breakers. Look for them first.
  • Worked example:
    • a monolith with 200 connections becomes 50 services of 10 connections, minimum 2 instances each, which is 1,000 connections
    • if half scale to an average of 5 instances, 1,700.
  • Govern it with a connection quota per service (the maximum it may hold in its pool), either:
    • even distribution: simple, good at the start when needs are unknown, but wasteful because some services need more than others;
    • variable distribution: efficient but needs knowledge of each service's function and scalability needs.
  • The authors recommend starting even, measuring concurrent connection use with fitness functions, and keeping quotas in an external configuration server so they can be tuned manually or programmatically.
  • Tables 6-1 to 6-3 tune a 100-connection database across services A to E (even 20 each: B and D wait; after moving spare capacity, quotas of 8, 29, 20, 25 and 18 remove the waits).
  • Table 6-4 shows the catch:
    • once the services scale to 14 instances in total, 242 connections are used, 142 more than the database has
    • Quotas set per service stop working when instances multiply.

Scalability

  • A distributed system scales only if every part scales, including the database. Service scaling strains connections, throughput and capacity of a shared database.
  • Splitting into data domains or database-per-service means fewer connections to each database and less load on each, improving scalability and performance as the services scale.

Fault tolerance

  • A shared database is a single point of failure: if it goes down, all services stop. Fault tolerance here means parts of the system continue when a service or database fails.
  • Split data limits the blast radius: if Database B fails, only Services B and C (its users) stop; the rest continue.

Architectural quantum

  • Recall from chapter 2:
    • an architectural quantum is an independently deployable artifact with high functional cohesion, high static coupling and synchronous dynamic coupling
    • The database is part of it.
  • Services A and B may need different characteristics from C, D and E, but a single shared database keeps all five services and the database in one quantum
    • Splitting the database lets A and B with their data form a separate quantum from C, D and E.

Database type optimisation

  • A monolithic database forces all data into one type. Example: reference data such as country, product and warehouse codes is key-value in nature and awkward in a relational database
    • a key-value database would suit it better.

Data integrators (when to keep data together)

Data relationships

  • Tables are coupled by foreign keys, triggers, views and stored procedures, and by logical relationships (a ticket table and its status table).
  • Moving tables to another schema or database means removing those cross-domain artifacts. Within one bounded context (same schema or database) a foreign key can stay
    • across contexts it must go, and so must a view that spans them.
  • Putting every service in its own bounded context means removing every cross-domain foreign key and view, which is why this is a trade-off: is change control worth more than the foreign keys? Is fault tolerance worth more than the materialised views?

Database transactions

  • When one service writes several tables in the same database, an ACID transaction commits or rolls back the whole unit of work.
  • Once the data is in separate schemas or databases there is no single unit of work across remote calls: one write can commit while another fails, risking inconsistent data
    • Distributed transactions and sagas are covered in chapter 12.
Sysops Squad saga: justifying the split

Addison and Devon bring evidence to Dana:

  • Logs show ticketing freezes whenever operational reports run: reporting uses parallel threads that take all the database connections, so ticket queries time out.
  • Projected services and instances need about 2,000 more connections than the single database can give.
  • If the monolithic database fails or is down for maintenance, all services stop; split data gives ticketing standalone fault tolerance. Addison names this an architectural quantum.
  • Dana agrees, then asks how to cope with all the foreign keys and views. Answer: data domains and the five-step process.

6.3 Decomposing monolithic data

A data domain is a collection of coupled database artifacts (tables, views, foreign keys, triggers) that relate to one domain and are used together within a limited functional scope. Table 6-5 assigns the 24 Sysops Squad tables to six data domains: Customer, Survey, Payment, Profile, Knowledge Base, Ticketing.

Data domain Tables
Customer customer, customer_notification
Survey survey, question, survey_administered, survey_question, survey_response
Payment billing, contract, payment_method, payment
Profile sysops_user, profile, expert_profile, expertise, location
Knowledge Base article, tag, keyword, article_tag, article_keyword
Ticketing ticket, ticket_type, ticket_history
  • Picture the database as a soccer ball:
    • each white hexagon is a data domain. Inside a hexagon, all dependencies stay
    • lines crossing hexagons (foreign keys, views, stored procedures) must be removed when a domain is extracted.
  • Database teams can use the refactoring patterns in Refactoring Databases by Scott Ambler and Pramod Sadalage.
  • Worked example: the Payment view v_customer_contract joined the customer table from another domain. To extract Payment, the join and the customer_name column are removed:
-- before: v_customer_contract (Example 6-1)
CREATE VIEW [payment].[v_customer_contract]
AS
SELECT
    customer.customer_id, customer.customer_name,
    contract.contract_start_date, contract.contract_duration,
    billing.billing_date, billing.billing_amount
FROM payment.contract AS contract
INNER JOIN customer.customer AS customer
    ON ( contract.customer_id = customer.customer_id )
INNER JOIN payment.billing AS billing
    ON ( contract.contract_id = billing.contract_id )
WHERE contract.auto_renewal = 0

-- after: v_customer_contract (Example 6-2)
CREATE VIEW [payment].[v_customer_contract]
AS
SELECT
    billing.customer_id, contract.contract_start_date,
    contract.contract_duration, billing.billing_date,
    billing.billing_amount
FROM payment.contract AS contract
INNER JOIN payment.billing AS billing
    ON ( contract.contract_id = billing.contract_id )
WHERE contract.auto_renewal = 0
  • The bounded-context rule holds for data domains too: a service cannot talk to several data domains, so the Payment service now calls the Customer service for the customer name.

Step 1: analyse the database and create data domains

  • At the start, every service can reach all data, the shared database integration style (Hohpe and Woolf, Enterprise Integration Patterns), which couples services tightly to the data
    • Group related tables into candidate data domains (Table 6-5).

Step 2: assign tables to data domains

  • Give each data domain its own schema (a logical construct holding tables, views and functions; in Oracle the schema is the user, in SQL Server a logical space users get access to) and move tables into it.
  • **A data domain is an architectural concept
    • a schema is the database construct that holds it.** Usually one to one, but combined domains (tightly coupled data, chapter 9) can map to several schemas. The book uses the two terms interchangeably.
  • Moving a table:
-- move-table.sql
ALTER SCHEMA payment TRANSFER sysops.billing;
  • Synonyms (like symlinks) give a table in another schema an alternate name, so a cross-domain query can be rewritten without a cross-schema name:
-- synonym.sql
CREATE SYNONYM ticketing.sysops_user
FOR profile.sysops_user;
GO

-- history-query.sql
SELECT
    history.ticket_id, history.notes, agent.name
FROM ticket.ticket_history AS history
INNER JOIN ticket.sysops_user AS agent
    ON ( history.assigned_to_sysops_user_id = agent.sysops_user_id )
  • A synonym does not remove cross-schema access (it still needs read or write privileges)
    • it is a coupling point to break later, moving the integration from the database layer to the application layer. Its value is that dependency checking and code analysis become easier.
  • If tightly related tables belong to different domains, the domains must be combined, giving a broader bounded context owned by several services (chapter 9).

Step 3: separate database connections to data domains

  • Refactor each service so it connects to one schema with read and write access only to its domain's tables
    • This is the most difficult step because all cross-schema access must be resolved in services, and the synonyms are removed.
When data from another domain is needed, do not reach into its database. Ask the service that owns that data domain.
  • The end of step 3 is data sovereignty per service, which the authors call the nirvana state of a distributed architecture, with these trade-offs:
    • Benefit: teams change the schema without worrying about other domains.
    • Benefit: each service can use the database type best suited to it.
    • Shortcoming: performance problems when a service needs large volumes of another domain's data.
    • Shortcoming: referential integrity cannot be kept by the database, so bad data is possible.
    • Shortcoming: stored procedures and functions touching other domains must move into the service layer.

Step 4: move schemas to separate database servers

  • Needed because separate schemas on one server are still one quantum, with adverse effects on scalability, fault tolerance and performance. Two options:
Option Method Cost
Backup and restore Back up each schema, set up servers, restore, connect services, remove from the original Usually needs downtime
Replicate Set up servers, replicate schemas, switch connections, remove from the original No downtime, but more work to set up replication and more coordination

Step 5: switch over to independent database servers

  • Once schemas are replicated, switch the connections and remove the old connections and schemas
    • Each domain then has an independent server that can be tuned for availability and scalability, and its data can be analysed to pick the right database type: polyglot databases.

6.4 Selecting a database type

  • Since about 2005 a "revolution" in databases produced the Paradox of Choice: more products, more trade-off decisions
    • Each product is optimised for certain trade-offs, so the software and data architects must choose with the problem in mind.
  • Seven rated characteristics (star ratings in the book's figures; higher stars is better, except that low learning-curve stars mean harder to learn):
Characteristic What it asks
Ease of learning curve How easily new people can learn and adopt it
Ease of data modeling How well the domain maps to the data model, and how easy it is to change
Scalability/throughput Can it scale (horizontally, vertically or both) to higher throughput?
Availability/partition tolerance High-availability configurations and network-partition handling
Consistency ACID or BASE (eventual), tunable or not
Programming language support, maturity, SQL support, community Languages, maturity, and how easy it is to hire
Read/write priority Optimised for reads, writes, or balanced (a scale, not a binary choice)

The types in brief

Type Core idea Strengths Weak points Products
Relational Tables and rows, SQL, ACID Easy to learn, flexible modelling, strong consistency, mature, balanced read/write Mostly vertical scaling; replication and switchover are complex; favours consistency over availability and partition tolerance; arbitrary-depth graphs are hard PostgreSQL, Oracle, SQL Server
Key-value Hash table: key to opaque value; only get, put, delete Fast key lookups, easy scaling, tunable consistency, read priority No joins, where or order by; query by key only; aggregate changes rewrite the data; configurations differ between products Riak KV, DynamoDB, Redis
Document JSON or XML aggregates the database understands and can index Most popular NoSQL, easy to learn, forgiving aggregate design, read priority Complex indexing hurts scaling; sharding adds a sharding key and complexity; ACID only in some cases MongoDB, Couchbase, AWS DocumentDB
Column family Rows with varying name-value columns, row key Highly scalable (horizontal), high write volume, copes with sparse data, replication factor 3 by default Hard to learn and model; row-key design takes iterations; consistency level trades against availability Cassandra, Scylla, SimpleDB
Graph Nodes and directed edges as explicit objects Very fast relationship traversal, read-heavy, ACID in many (Neo4j), Cypher and Gremlin Steep learning curve, hard modelling, hard to shard so write throughput is constrained; changing a relationship type is expensive Neo4j, Infinite Graph, TigerGraph
NewSQL SQL and ACID with automatic sharding and multiple active nodes Familiar to relational users, horizontal scale, high availability (CockroachDB survives disk, machine and data-centre failure) Some are DBaaS only; sharding design is a wrinkle VoltDB, ClustrixDB, SingleStore (MemSQL)
Cloud native Cloud-only, managed, pay for use Little operational burden, easy to experiment, automatic scaling Varies widely; hard to find experienced people; cost is the trade-off; Datomic uses immutable atomic facts and Clojure Snowflake, Datomic, Redshift
Time-series Append-only data points, each with a timestamp and tags Easy to grasp, suited to read-heavy analysis over time windows Not general purpose; append-only needs unlearning of updates InfluxDB, kdb+, Amazon Timestream
Boxed terms
  • Aggregate orientation: a preference for operating on related data of complex structure (a Sysops Squad ticket with its dependent tables). Aggregate comes from Evans' Domain-Driven Design. Benefits: easy distribution across a cluster, fewer joins so faster reads and writes, less impedance mismatch with the application model. Shortcomings: proper aggregates are hard to find and change, and analysing across aggregates is difficult.
  • Sharding: like partitioning, but the data lives on different servers or nodes, and nodes decide where data goes using a sharding key; a shard is a horizontal partition.
  • Schema-less: NoSQL data always has a schema, even if implicit or held elsewhere; the application must handle several schema versions. "Entirely schema-less" is misleading.
  • Changing relationship types in a graph is expensive: both nodes must be visited, the new edge created and the old one removed.
  • Details the book adds: key-value stores are not all alike (Riak tunes quorum per query: one, quorum, all); in tunable consistency, higher consistency costs latency or availability; NewSQL was named by Matthew Aslett.

6.5 Sysops Squad saga: polyglot databases

  • Devon and Skyler (UI developer) want the Survey domain in a document database; Dana wants to stay relational ("the survey tables have always worked").
  • Skyler's point:
    • the relational survey data is a real pain for the user interface
    • Parker (product owner) confirms marketing is frustrated that even small survey changes take days, so they stop asking.
  • Addison builds the business justification:
    • survey flexibility and speed of change depend on how the data is stored
    • The technical point of friction becomes a business case, and Dana agrees.
  • Two document models are compared (the survey and question tables are one-to-many):
    • Single aggregate: the survey with its questions embedded, so one get returns it all and the UI renders it directly. Cost: a common question is replicated in every survey.
    • Split aggregates: the survey holds question references; questions are reusable but harder to retrieve and render.
{
    "survey_id": "19999",
    "created_date": "Dec 28 2021",
    "description": "Survey to gauge customer...",
    "questions": [
        {
            "question_id": "50001",
            "question": "Rate the expert",
            "answer_type": "Option",
            "answer_options": "1,2,3,4,5",
            "order": "2"
        },
        {
            "question_id": "50000",
            "question": "Did the expert fix the problem?",
            "answer_type": "Boolean",
            "answer_options": "Yes,No",
            "order": "1"
        }
    ]
}

{
    "survey_id": "19999",
    "created_date": "Dec 28",
    "description": "Survey to gauge customer...",
    "questions": [
        {"question_id": "50001", "order": "2"},
        {
          "question_id": "50000",
          "order": "1"
        }
    ]
}
  • The team picks the single aggregate:
    • only five survey types exist (one per product category), most changes add or remove questions, and the UI is where the complexity is
    • They accept duplicated question data in exchange for easier change and rendering.

ADR: use of document database for customer survey
  • Context: customers get one of five survey types after a repair or installation; it is stored relationally, and the team wants JSON in a document database.
  • Decision: use a document database for the customer survey, because marketing needs more flexibility and timely changes, and it simplifies the survey UI.
  • Consequences: with a single aggregate, a change to a common question touches multiple documents; survey functionality must be shut down during migration from relational to document.

Summary

  • Splitting data is justified by weighing the disintegrators against the integrators, with evidence (logs, connection projections), not by preference.
  • The five-step data-domain process moves a database apart iteratively and safely, ending in data sovereignty per service and the freedom to choose a database type per domain.
  • The next question is how big each resulting service should be (chapter 7), and later how services share and move data (chapters 9 and 10).
Terms to carry forward
  • Data disintegrator / integrator: a driver to split or keep data together.
  • Breaking change: a schema change (drop, rename, retype) that breaks existing queries.
  • Bounded context: code, logic, data structures and data encapsulated per service.
  • Connection quota: the cap on database connections per service.
  • Data domain / schema: architectural grouping / database construct holding it.
  • Data sovereignty per service: each service owns its own data.
  • Synonym: an alternate name for an object in another schema.
  • Polyglot databases: different database types per domain.
  • Aggregate, shard, sharding key: a unit of related data, a horizontal partition, the key that places data.
