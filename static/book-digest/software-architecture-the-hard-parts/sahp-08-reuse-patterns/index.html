Software Architecture: The Hard Parts 8: Reuse Patterns

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 8. Previous: Software Architecture: The Hard Parts 7: Service Granularity. Next: Software Architecture: The Hard Parts 9: Data Ownership and Distributed Transactions.

Takeaways
  • In a monolith reuse is an import; in a distributed architecture it is a hard part. Four techniques: code replication, shared library, shared service, sidecar / service mesh, each with trade-offs.
  • Shared library (compile time): versionable and no runtime cost, but dependency and version management is hard. Shared service (runtime): good for volatile code and polyglot estates, but costs latency, scalability, fault tolerance and change risk.
  • A sidecar is for operational coupling only (logging, monitoring, discovery, authentication, authorisation), never for domain classes.
  • Reuse is derived via abstraction but operationalised by slow rate of change: stable things are good coupling targets, volatile internal domain code is not.

8.1 The scene

  • Skyler wants one shared DLL
    • Taylen wants several libraries, and the authorisation code as a shared service. Addison proposes analysing the trade-offs of shared-library granularity and of library versus service instead of arguing.
  • Context:
    • formatters, calculators, validators, auditing, security, logging and metrics are all shared. In a monolith this is a class import
    • in distributed architectures it is complicated (Figure 8-1).
  • Microservices and serverless circles say "reuse is abuse" and "share nothing", and offer WET (write every time, or write everything twice) against DRY
    • The authors: limit reuse, but it is a fact of life that must be handled.

8.2 Code replication

  • Shared code is copied into each service's repository, so nothing is shared. It became popular in early microservices out of confusion about the bounded context ("share nothing")
    • in practice it quickly fell apart.
  • Risk: a bug or important change is hard and slow to apply to every copy.
  • It still suits highly static, one-off code
    • The example is a service-entry-point marker, which holds no functionality, only tags the class for metadata annotations (service type, domain, bounded context):
// ServiceEntrypoint.java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface ServiceEntrypoint {}

/* Usage:
@ServiceEntrypoint
public class PaymentServiceAPI {
...
}
*/

// ServiceEntrypoint.cs
[AttributeUsage(AttributeTargets.Class)]
class ServiceEntrypoint : Attribute {}

/* Usage:
[ServiceEntrypoint]
class PaymentServiceAPI {
...
}
*/
  • The book points to Kevlin Henney and Trisha Gee, 97 Things Every Java Programmer Should Know (chapter 89), for such metadata annotations.
  • During a monolith migration it can also work for common static utility classes: replicate a Utility.cs into each service, then let each trim or evolve it, much like the tactical forking of chapter 3
    • The risk of defect propagation remains.
  • The authors encourage looking at the other techniques first.

No code sharing Code inconsistency across services

8.3 Shared library

  • An external artifact (JAR, DLL and so on) with code used by many services, normally bound at compile time.

Dependency management and change control

  • The granularity trade-off pairs dependency management with change control.
    • Coarse-grained
      • library: simple dependencies (each service uses the one library), but a change to any class forces every service to adopt it eventually, because of version deprecation, even if it does not care
      • Large retesting and redeployment scope.
    • Fine-grained libraries (security, formatters, annotations, calculators): a change affects fewer services (a change to shared class C7 touches only Services D and E), but the dependency matrix between libraries and services becomes a distributed monolith or "big ball of distributed mud".
  • It matters little with a few services; with 200 services and 40 libraries it becomes unmaintainable.
  • Advice:
    • avoid large coarse-grained libraries and favour smaller functional ones, so favour change control over dependency management
    • Carve out relatively static code such as formatters and security (authentication, authorisation) so it does not drag other shared code into needless version deprecations.

Versioning strategies

  • Always version.
    • Example: Validation.jar used by 10 services
    • one service needs an immediate change, takes the new version and deploys without affecting the other nine. Without versioning all ten are retested and redeployed.
  • The authors call versioning the ninth fallacy of distributed computing: "versioning is simple" is false. Complexities:
    • Communicating a version change across teams (what changed, who is impacted), even with tools such as JFrog Artifactory.
    • Deprecation: either custom per library or global.
      • Custom
        • is usually right because libraries change at different rates: Security.jar rarely changes, so keep two or three versions
        • Calculators.jar changes weekly, so keep about 10 to avoid monthly or weekly forced upgrades. The cost: someone must track each library's deprecation.
      • Global (for example no more than four back versions for every library) is easy to govern but causes churn, constant retesting and redeploying for frequently changing libraries.
    • Serious defects or breaking changes override any deprecation policy: all services adopt the new version at once
      • One more reason for fine-grained libraries instead of a SharedStuff.jar.
    • Avoid LATEST as a version: emergency hot deployments hit incompatibilities.
Advantages Disadvantages
Ability to version changes Dependencies can be difficult to manage
Compile-based, reducing runtime errors Code duplication in heterogeneous codebases
Good agility for shared code changes Version deprecation can be difficult
Version communication can be difficult
  • When to use:
    • homogeneous environments where shared code changes at a low to moderate rate
    • Performance, scalability and fault tolerance are unaffected (bound at compile time) and the risk to other services is low thanks to versioning.

8.4 Shared service

  • Shared functionality goes into a separately deployed service, reached at runtime. The shared code must be composition, not inheritance
    • architecturally this matters (the book cites a Thoughtworks article, "Composition vs. Inheritance: How to Choose", and Martin Fowler's "Designed Inheritance").
  • Benefit: a change is isolated to the shared service and needs no redeployment of the callers (a discount calculator, for instance). The trade-offs:

  • Change risk: the change is at runtime, so a "simple" change can bring down the whole system. Versioning by endpoint is the usual answer:
app/1.0/discountcalc?orderid=123
app/1.1/discountcalc?orderid=123
app/1.2/discountcalc?orderid=123
app/1.3/discountcalc?orderid=123
app/1.4/discountcalc?orderid=123   (latest change)

Problems: callers must change to point at the right version; when to create a new version (an error message? a new calculation?) is subjective; and it assumes REST via a gateway, while access may use messaging or gRPC too.

  • Performance:
    • interservice calls add network and security latency (a library has none)
    • gRPC reduces network latency, and messaging lets a service send a request on a request queue, do other work, and read the reply from a reply queue by correlation ID (the book cites Java Message Service, 2nd edition, by Mark Richards and others).
  • Scalability: the shared service must scale as its callers scale; a library does not have this issue.
  • Fault tolerance: if the service is down, callers are nonoperational (multiple instances mitigate but do not remove it).
Advantages Disadvantages
Good for high code volatility Versioning changes can be difficult
No code duplication in heterogeneous codebases Performance impacted by latency
Preserves the bounded context Fault tolerance and availability depend on the service
No static code sharing Scalability and throughput depend on the service
Increased risk due to runtime changes
  • When to use: highly polyglot environments (several languages and platforms) and shared functionality that changes often, watching for runtime side effects.

8.5 Sidecars and service mesh

  • Operational coupling shows the "it depends" nature of architecture
    • In microservices the guideline is "duplication is preferable to coupling": for example two services pass customer information as name-value pairs in JSON, so each keeps its own internal Customer and may change technology stack freely
    • In service-based architecture the likely answer is couple.
  • But operational capabilities (monitoring, logging, authentication and authorisation, circuit breakers) benefit from consistency
    • If every team implements monitoring, how does operations know they did, and how does the whole organisation upgrade a monitoring tool?
  • The answer is the sidecar pattern, based on Alistair Cockburn's earlier hexagonal architecture (ports and adapters): domain logic in the centre, technical coupling at the edge
    • Difference from microservices: data fidelity
    • The hexagon treated the database as just another pluggable adapter, whereas Domain-Driven Design puts data schemas and transactionality inside the interior.
  • The sidecar splits each service into domain concerns and operational concerns
    • the operational part goes in a sidecar component, owned either by all teams jointly or by a central infrastructure group
      • If every service includes it (governed by fitness functions), it forms a consistent operational interface linked by a service plane
    • all the sidecars together form the service mesh, enabling dashboards, control of scale and more.
  • Governance benefit: unified governance without a common platform. Without a mesh, standardising on one monitoring solution means building a sidecar per platform anyway.
  • A sidecar is an orthogonal reuse pattern:
    • reuse cutting across the domain seams of the architecture. Orthogonal coupling means two distinct purposes that must still intersect (monitoring is independent of catalogue checkout but necessary to it)
    • recognising it helps find intersection points with the least entanglement.

Advantages Disadvantages
A consistent way to create isolated coupling A sidecar is needed per platform
Consistent infrastructure coordination The sidecar component may grow large and complex
Ownership per team, central, or a mix
  • Use it to spread a cross-cutting concern
    • the book likens it to the Decorator design pattern (Gang of Four) applied across a distributed architecture, and notes uses beyond operations (chapter 14).
Sysops Squad saga: common infrastructure logic
  • Duplicate log lines show the shared Message Dispatch library and the service both log. Addison: logging is operational shared behaviour, along with monitoring, service discovery and circuit breakers; a service mesh with a sidecar is being implemented.
  • A shared infrastructure team owns the sidecar and its pipeline runs fitness functions on it after binding.
  • Never put domain classes (Address, Customer) in the sidecar: that increases coupling the way microservices try to avoid, since a change forces every team to coordinate (the architects could decide otherwise, as an explicit trade-off; contracts handle such changes).
  • Utility libraries: the JSON-to-XML library is used by about 5 of 16 or 17 teams. Trade-off: every service pays the overhead versus how many teams need it. Rule of thumb from the saga: if fewer than half the teams use it, it is probably not worth the overhead, so it stays out for now.
ADR: using a sidecar for operational coupling
  • Decision: a sidecar with a service mesh for monitoring, logging, service discovery, authentication and authorisation, owned by the shared infrastructure team (service teams are its customers).
  • Consequences: no domain classes in the sidecar; shared operational libraries go in only if enough teams need them.

8.6 Code reuse: when does it add value?

  • Reuse is one of the most abused abstractions
    • organisations treat it as a laudable goal without weighing trade-offs. The danger was learned in the early 21st century with orchestration-driven SOA, where maximising reuse was a primary goal.
  • Example:
    • each division of an insurance company has its own view of the customer
    • architects were told to unify these into one central Customer service. The authors call this an architectural disaster:
    • the entity must be complex enough to handle every domain and scenario, making simple uses hard;
    • it creates brittleness: when the Customer service gains a capability for one domain, the change can ripple through all the others.
  • Reuse has two aspects
    • Architects got the first right, abstraction (how candidates are found)
    • The one that decides value is the second, rate of change
    • We happily reuse operating systems and open source libraries because their rate of change and update cadence are well understood
      • internal domain capabilities and fast-moving frameworks are terrible coupling targets.
Reuse is derived via abstraction but operationalised by slow rate of change.
  • Reuse via platforms:
    • the modern reuse target is the platform, with a well-defined API per domain capability hiding implementation details. The API can be loosely coupled so the internals change quickly
    • careful encapsulation and contracts (chapter 13) limit breaking change, though semantic changes in shared information remain a risk.

8.7 Sysops Squad saga: shared domain functionality

  • Core ticketing is split into Ticket Creation (customer facing), Ticket Assignment and Ticket Completion, all using common database logic over shared ticketing tables. Taylen wants a shared Ticket Data service (database abstraction layer)
    • Skyler wants a shared library.
  • Addison uses a hypothesis-based approach (hypothesise the shared service is right, then test it):
    • Costs of the service:
      • an interservice call for every query or update (performance), and all three services go down if it does (fault tolerance). Taylen says it is mostly backend
      • Addison notes Ticket Creation is customer facing.
    • Runtime change risk, and more testing of all ticketing services per change; the library can be versioned. Extra scaling coordination.
    • Benefits Taylen offers:
      • data abstraction, centralised connection pooling (minor with three services) and easier change control
      • The repository history shows the code rarely changes, so the change-control benefit is small.
  • Decision: shared library.
ADR: shared library for common ticketing database logic
  • Decision: shared library, improving performance, scalability and fault tolerance of Ticket Creation and Ticket Assignment; the logic is stable; versioning avoids redeploying all services on a change; fewer service dependencies, less HTTP traffic and bandwidth.
  • Consequences: a change to the DLL means testing and deploying the ticketing services, reducing agility for that logic; each service instance manages its own database connection pool.

Summary

  • Pick the reuse technique by the code's rate of change, the language mix (homogeneous or polyglot) and the cost of runtime coupling. Operational plumbing goes in a sidecar
    • domain code stays out of it.
  • Next: who owns data when services share it, and how to do transactions across services (chapter 9).
Terms to carry forward
  • Code replication, shared library, shared service, sidecar: the four reuse techniques.
  • Distributed monolith: a tangle of services and fine-grained shared libraries.
  • Versioning, deprecation strategy (custom or global), churn, LATEST.
  • Composition vs inheritance as the form of shared service code.
  • Hexagonal architecture / ports and adapters: domain logic separated from technical coupling.
  • Service mesh, service plane, operational coupling, orthogonal coupling.
  • Rate of change: the property that makes reuse valuable.
