Software Architecture: The Hard Parts 9: Data Ownership and Distributed Transactions

Source: Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, Software Architecture: The Hard Parts (O'Reilly, 2021), chapter 9. Previous: Software Architecture: The Hard Parts 8: Reuse Patterns. Next: Software Architecture: The Hard Parts 10: Distributed Data Access.

Takeaways
  • Once data is split it must be stitched back together: who owns each table, how to run distributed transactions, and (chapter 10) how to read data you do not own.
  • Rule of thumb: the service that writes to a table owns it. It gets messy with joint ownership (a few services in a domain write it) and common ownership (most or all services write it).
  • Joint ownership has four techniques: table split, data domain, delegate, service consolidation.
  • A business request spread across services is a distributed transaction: BASE, not ACID. Three eventual consistency patterns: background synchronisation, orchestrated request-based, event-based.
  • Every technique trades something away; the book frames the choice as availability versus consistency, response time versus data integrity, coupling versus independence.

9.1 The scene

  • Sydney put the expert-profile table in the Ticket Assignment service because assignment queries it constantly
    • Addison says the User Maintenance service does the writes, so it should own the table.
  • Sydney's workaround (let User Maintenance connect to the other database) hits Dana's rule: several services may connect to the same schema, but a service may not connect to several schemas or databases
    • More collaboration with the database team is needed.

9.2 Assigning data ownership

The service that performs write operations to a table is the owner of that table. Joint ownership makes this simple rule complex.
  • Running example (Figure 9-1): a Wishlist Service (writes Wishlist and Audit), a Catalog Service (writes Product and Audit) and an Inventory Service (writes Product and Audit).

Single ownership

  • One service writes the table, whatever read-only access others need (the Wishlist table belongs to the Wishlist Service)
    • Diagram it by drawing the table inside the service's bounded context
    • Resolve these first, to clear the field for the harder cases.

Common ownership

  • Most or all services write the same table (the Audit table), potentially hundreds or thousands of them
    • Putting it in a shared schema brings back the chapter 6 problems (change control, connection starvation, scalability, fault tolerance).
  • Popular answer: one dedicated service owns the table; the others send it their writes.
    • No reply needed:
      • persisted queue, asynchronous fire-and-forget
      • Persistent means the broker stores the message on disk, giving guaranteed delivery through a service or broker failure.
    • Reply needed (a confirmation number, a database key): REST, gRPC or request-reply messaging (pseudosynchronous).
  • Services that must read common data they do not own are covered in chapter 10.

Joint ownership

  • A couple of services within the same domain write the same table. Catalog inserts, removes and updates static product information
    • Inventory reads and updates the stock count. Techniques:

Table split technique

  • Split the table so each service owns its part (see Refactoring Databases): create an Inventory table keyed by product, copy the counts, then drop the column from Product.
-- split-product.sql
CREATE TABLE Inventory
(
    product_id VARCHAR(10),
    inv_cnt INT
);

INSERT INTO Inventory VALUES (product_id, inv_cnt)
AS SELECT product_id, inv_cnt FROM Product;

COMMIT;

ALTER TABLE Product DROP COLUMN inv_cnt;
  • Joint ownership becomes two single-ownership cases, but the services must talk: when Catalog adds a product it sends the new product ID (and perhaps initial counts) to Inventory
    • on removal Catalog removes the row, then tells Inventory to remove the inventory row.
  • Hard questions:
    • synchronous or asynchronous? What if Inventory is down when Catalog adds or removes a product? That is the availability versus consistency trade-off
      • Choose availability and Catalog can always add or remove products, perhaps without the matching inventory row
    • choose consistency and the operation fails if Inventory is down
      • Since network partitions must be accepted, the CAP theorem says only one of the two is possible
      • Synchronous confirmation gives better consistency at a cost in performance
    • fire-and-forget the reverse.
Advantages Disadvantages
Preserves the bounded context Tables must be altered and restructured
Single data ownership Possible data consistency issues
No ACID transaction between table updates
Data synchronisation is difficult
Data replication between tables may occur

Data domain technique

  • Both services own the table:
    • tables used by the same services share one schema or database, forming a broader bounded context (drawn with the table in a separate box outside both services)
    • It resolves performance, availability and consistency issues, and the services stay independent of each other, but sharing data is generally discouraged in distributed architectures, particularly microservices.
  • Re-ask why the services are separate at all, since they share data: valid reasons include scalability differences, fault tolerance needs, throughput differences or isolating code volatility (chapter 7).
  • Costs: schema changes involve more services (more effort, testing scope and deployment risk), and write responsibility must be governed explicitly if it matters who writes what.
Advantages Disadvantages
Good data access performance Schema changes involve more services
No scalability or throughput issues Increased testing scope for schema changes
Data remains consistent Write-responsibility governance needed
No service dependency Increased deployment risk for schema changes

Delegate technique

  • One service is the delegate, the sole owner; the others ask it to update. Choosing the owner:
    • Primary domain priority: the service doing most CRUD on the main entity (Catalog owns Product; Inventory must call Catalog to read or update counts).
    • Operational characteristics priority: the service needing higher performance, scalability, availability or throughput (Inventory, whose updates are frequent and real time, owns the table and uses direct database calls).
  • The communication is synchronous (waits, consistent, slower) or asynchronous (faster, eventually consistent, and no guarantee the update ever succeeded, which hurts integrity).
  • The authors usually recommend domain priority, because under operational priority Inventory would take on managing static product data and its errors, which is not its domain
    • use a replicated in-memory or distributed cache to help performance and fault tolerance.
  • The delegate technique suits writes that do not need atomic transactions and tolerate eventual consistency through asynchronous communication.

Advantages Disadvantages
Forms single table ownership High level of service coupling
Good schema change control Low performance for non-owner writes
Abstracts data structures from other services No atomic transaction for non-owner writes
Low fault tolerance for non-owner services

Service consolidation technique

  • Merge the owning services into one coarser service, turning joint into single ownership
    • It keeps ACID transactions and performance and removes the service dependency, but increases testing scope and deployment risk, reduces fault tolerance (all parts fail together) and forces scalability to be uniform (catalogue maintenance must scale with inventory demand).
Advantages Disadvantages
Preserves atomic transactions More coarse-grained scalability
Good overall performance Less fault tolerance
Increased deployment risk
Increased testing scope

Data ownership summary

  • Figure 9-10:
    • Wishlist table to the Wishlist Service
    • Audit table to a new Audit Service fed by a persisted queue
    • Product table to the Catalog Service (delegate), with Inventory sending update requests.
  • Then validate ownership against business workflows and their transaction requirements.

9.3 Distributed transactions

ACID first

  • The book insists an architect cannot weigh distributed transactions without understanding ACID (see chapter 6).
    • Atomicity:
      • all updates commit or roll back as one unit. Customer registration inserts profile, wallet (credit card) and security rows
      • if the security insert fails, the other two roll back.
    • Consistency: the database is never left inconsistent or in violation of integrity constraints (no order detail row without the order row), although some databases defer the check to commit.
    • Isolation: uncommitted data from a transaction is not visible to others (a profile row inserted mid-transaction cannot be read until commit).
    • Durability: after a successful commit, the updates are permanent regardless of later failures.
  • ACID can exist inside each service, if its database supports it
    • A business request spanning services is not ACID but a distributed transaction: an atomic business request with several database updates done by separately deployed remote services.

Why a distributed transaction is not ACID

  • Registration spread across a Customer Profile Service, a Support Contract Service and a Billing Payment Service:
    • Atomicity is bound to the service, not the business request: each commits only its own part.
    • Consistency: a billing failure leaves profile and contract out of sync with billing; foreign-key constraints cannot span services.
    • Isolation: the profile row is visible to anyone before registration finishes.
    • Durability holds per service, not for the whole business transaction.
  • Instead, distributed transactions give BASE (the chemical opposite of ACID, the authors point out):
    • Basic availability: every participant is expected to be available (asynchronous communication helps decoupling but lengthens time to consistency).
    • Soft state: the request is in progress and the state is not yet complete, or even known (three services working in parallel report back, so the state is unknown until all do; with asynchronous workflows it is hard to determine).
    • Eventual consistency: given enough time, all parts complete and the data is in sync.

9.4 Eventual consistency patterns

  • Distributed architectures rely on eventual consistency as a trade for better performance, scalability, elasticity, fault tolerance and availability. Running example: customer 123 unsubscribes
    • the Customer Profile Service removes the profile row and confirms, but the Contract table (Support Contract Service) and Billing table (Billing Payment Service) still hold the customer's data.

Background synchronisation pattern

  • An external service or process (nightly batch, or a service waking hourly) checks the data sources and keeps them in sync
    • In the example, at 11:23:00 the user unsubscribes, at 11:23:01 gets confirmation, and at 23:00 the batch finds customer 123 removed (through an event stream, a trigger, or table deltas) and updates Contract and Billing.
  • Good responsiveness (the user does not wait), and for unsubscribe it hardly matters that contracts linger until night. Slowest consistency of the three.
  • Disadvantages:
    • the process needs write access to every table, so it couples all the data sources and breaks every bounded context (shared ownership between the services and the process; every schema change must be coordinated with it)
    • Business logic is duplicated: the contract and billing rows are kept three months after unsubscribe via a remove_date column (zero means active), and that logic lives in the services and again in the batch.
  • Unsuitable for tight bounded contexts such as microservices
    • Useful for closed, self-contained heterogeneous systems that do not communicate or share data, such as a contractor order entry system that feeds a separate invoicing system on another platform.
Advantages Disadvantages
Services are decoupled Data source coupling
Good responsiveness Complex implementation
Breaks bounded contexts
Business logic may be duplicated
Slow eventual consistency

Orchestrated request-based pattern

  • The whole distributed transaction is processed during the request, while the user waits, by an orchestrator: a designated existing service or a new one, which holds the business process knowledge, participants, multicast logic, error handling and contract ownership.
  • Using a primary service (Customer Profile) as orchestrator overloads it and encourages tight coupling and synchronous dependencies
    • The authors prefer a dedicated orchestration service
    • Timing example: request at 11:23:00
    • the Unsubscribe Orchestrator calls Customer Profile synchronously, then Support Contract and Billing Payment in parallel
    • it answers at 11:23:02.
  • Trade-offs:
    • it favours consistency over responsiveness (extra network hops, serial or parallel calls)
    • Profile is done first and synchronously for error handling: if the customer cannot be removed because of an outstanding charge, nothing needs reversing.
  • Complex error handling:
    • if the profile and contract removals succeeded but billing fails, the orchestrator must choose among retrying billing, compensating (reinserting the customer and resetting remove_date to zero), replying "error, wait" while repairing, or ignoring the error
    • With no other repair mechanism in this pattern, only the compensating transaction is really available
      • it needs all the information to reinsert the customer and no side effects when doing so (billing and contract initialisation)
    • If compensation itself fails, the data is out of sync with no other service to fix it, and a human usually must intervene
    • Details in the saga chapters (11 and 12).
Advantages Disadvantages
Services are decoupled Slower responsiveness
Timeliness of data consistency Complex error handling
Atomic business request Usually requires compensating transactions

Event-based pattern

  • "One of the most popular and reliable" patterns for modern distributed architectures (microservices, event-driven)
    • Events
      • (customer unsubscribed) or command messages (unsubscribe customer) go to a topic or stream through asynchronous publish-and-subscribe
      • interested services react in parallel
    • The consistency window is usually short, services are highly decoupled, and the triggering service returns at once (confirmation at 11:23:01).
  • Reliability:
    • with topic-based messaging (ActiveMQ, RabbitMQ, Amazon MQ) the subscribers must be durable subscribers, so a subscriber that is unavailable at publication still receives the message later
    • with event streaming (Apache Kafka) the broker must persist the message and keep it available long enough.
  • Main trade-off:
    • error handling
    • If a service fails while processing the event, brokers retry a number of times and then route the message to a dead letter queue (DLQ), where an automated process tries to fix it, falling back to manual processing.
Advantages Disadvantages
Services are decoupled Complex error handling
Timeliness of data consistency
Fast responsiveness

9.5 Sysops Squad saga: data ownership for ticket processing

  • After talking with Dana, Sydney and Addison recognise that data decomposition needs both teams working together
    • Rule applied: the writer owns the table, regardless of readers
    • The User Maintenance service owns the expert-profile table.
ADR: single table ownership for bounded contexts
  • Decision: when only one service writes a table, that service owns it; services needing read-only access cannot access the other database or schema directly. Table ownership means the service that performs writes.
  • Consequences: depending on the read technique, read-only users may suffer performance and fault-tolerance problems.
  • Then the Survey table:
    • Ticket Completion writes the completion timestamp and expert, and the Survey Service writes the sent timestamp and results (joint ownership)
    • Table split is not possible given the structure of the table
    • A common data domain would not work because Ticket Completion is already connected to the ticketing schema (no connections to several schemas), and adding the survey tables to it would slowly rebuild a monolithic database.
  • Solution (Addison's idea):
    • since Ticket Completion already sends the Survey Service a message to start the survey, include the needed data in that message
    • the Survey Service inserts it when creating the survey. Delegation, with the Survey Service as sole owner.

ADR: Survey Service owns the Survey table
  • Decision: Survey Service is the single owner; the completion data is passed in the existing notification event so Ticket Completion has no access to the table.
  • Consequences: all data Ticket Completion would have inserted must travel in the payload; and creating the survey record is now a separate activity handled by the Survey Service (in the monolith ticket completion inserted it).

Summary

  • Pick the ownership technique for each scenario, then choose the consistency pattern according to how much the business needs timeliness, responsiveness and a clean error path.
  • Next: how services read data they do not own (chapter 10), then workflows and sagas (11 and 12).
Terms to carry forward
  • Single, common, joint ownership; table split, data domain, delegate, service consolidation.
  • Primary domain priority / operational characteristics priority (choosing a delegate).
  • Distributed transaction, ACID, BASE (basic availability, soft state, eventual consistency).
  • Background synchronisation, orchestrated request-based, event-based patterns.
  • Compensating transaction, durable subscriber, dead letter queue (DLQ), persisted queue, fire-and-forget.
  • CAP theorem: consistency or availability, not both, once partitions occur.
