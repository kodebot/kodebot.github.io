Ch 1: Spring in the real world

Source book: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), local copy books/Spring_Start_Here_Second_Edition_v5_MEAP (1).pdf, ch. 1 (pp. 1-22). This chapter has no code; it builds the "why" before the "how".

Takeaways
  • A framework supplies the plumbing (security, logging, transactions, caching, comms) so you write only business logic.
  • Spring is an ecosystem of projects orbiting a core that runs on inversion of control.
  • Use it for:
  • most backend apps
  • automation test apps
  • even desktop apps

Skip it when:

  • you need a tiny footprint (e.g. serverless functions)
  • security rules demand custom-only code
  • you would customise it more than you reuse it
  • you already have a working app and switching gains nothing

1.1 Why frameworks?

  • Definition (book): a pre-built software foundation with an opinionated architecture and predefined structure, so you implement only app-specific logic.
  • Library vs framework:
    • you call a library
    • a framework calls your code. Example (illustrative): Collections.sort(list) is you calling a library
    • a Spring @RestController method that you never call yourself is the framework calling you.

  • Ikea analogy, with a twist:
    • a framework does not ship only the parts you need
    • It ships every part for any furniture, so the skill is choosing and assembling the right ones
    • That is why books like this exist.
  • Why frameworks appeared: every app repeats the same needs: logging, transactions (data consistency), protection against common vulnerabilities, app-to-app communication, performance tools (caching, compression).
  • Business logic vs plumbing:
    • business logic is the code behind a user expectation (e.g. "click a link, an invoice is generated"). It is the small tip of the iceberg
    • the plumbing is the hidden mass, and a framework provides it from dependencies.

  • Use case: a reason a user interacts with the app (ridesharing: "request a car"; food delivery: "order a pizza"). Two such apps differ in use cases but share the same plumbing needs.
  • Payoff of reuse: saves time and money; widely used code has fewer bugs because others tested it; a community understands it, whereas only your team understands your own code.
  • Author's story:
    • a Java system begun in 1995 became a "big ball of mud"
    • The team chose Spring over Java EE (now Jakarta EE) because it was lighter and easier to implement and maintain
    • Result: over 40% fewer lines of code
    • (Anecdote, author's own experience, not independently verified.)

1.2 The Spring ecosystem

Spring is "an ecosystem of frameworks", not one framework. The four parts people usually mean by "Spring framework":

Part What it gives you
Spring Core The Spring context (IoC container), aspects (AOP), Spring Expression Language (SpEL). The "star" of the solar-system picture.
Spring MVC Web apps serving HTTP requests, in the standard servlet style.
Spring Data Access JDBC tools, ORM integration (e.g. Hibernate), transaction management.
Spring Testing Tools for unit and integration tests. Author: "you're not a mature developer if you don't understand testing".
  • Inversion of control (IoC):
    • instead of your code controlling execution, the framework does
    • "Control" means creating instances and calling methods
    • Example: Spring can intercept a method to log any error during it
    • The IoC container, a.k.a
    • the Spring context, holds the objects you make known to Spring.

  • Aspecting: Spring intercepting methods of objects it manages (Spring AOP). It is one of the most common ways Spring touches your app's behaviour.
  • Other projects in the ecosystem (each with its own team and docs at spring.io/projects): Spring Data, Spring Security, Spring Cloud, Spring Batch, Spring Boot.
  • Spring Data Access vs Spring Data (easy to confuse):
    • Data Access is a module of Core (JDBC, transactions)
    • Spring Data is a separate project that sits on top: fewer lines of code, SQL and NoSQL.

  • Spring Boot: "convention over configuration". Start from sensible defaults and change only what differs.
  • This book covers: Spring Core, Spring Data, Spring Boot.
  • Alternatives exist per component, not for the whole ecosystem:
    • IoC/aspects: Java EE/Jakarta EE (CDI, EJB; aspects are "interceptors" there; open-sourced as Jakarta EE in 2017), Google Guice.
    • Security: Apache Shiro instead of Spring Security.
    • Web: Play framework instead of Spring MVC.
    • Cloud-native: Red Hat Quarkus.
    • Advice: never treat one solution as "the one".

1.3 Where Spring fits in the real world

  1. Backend app (the book's main focus): server-side app managing data and serving client requests. Example: a bank's backend behind online banking and the mobile app; it talks to other backends and persists to a database. Fits any architectural style.

2. Automation test app: a separate app that validates all flows of a system, run on a schedule by a CI tool (Jenkins) with feedback to the team. Used with Selenium, Cucumber, Gauge. Spring adds: IoC container for maintainable code, Spring Data for DB checks, messaging to brokers, calling external APIs. 3. Desktop app: rare today, but Spring's container, remote-call tools and caching still help.

Not limited to backend web apps; the author has seen all three succeed.

1.4 When not to use a framework

Chainsaw-to-cut-bread principle: an oversized tool gives a worse result.

  1. Small footprint needed. Containers (Docker, Kubernetes) should be disposable and start fast; a smaller app initialises seconds faster. Serverless functions are the textbook case: tiny, so skip the framework.
  2. Security forces custom code (defence, government). An open-source flaw becomes public knowledge a hacker can exploit. The author notes the counter-point: open source also gets flaws found by many eyes, and you could match that only with lots of time and money.
  3. Customisation overload. If you override so much you write more code than from scratch, you picked the wrong framework or none.
  4. No benefit from switching. Switch only for maintainability, performance or security gains.
  • Author's cautionary story:
    • a backend used raw JDBC on Oracle, with ugly multi-line queries
    • Colleagues pushed Hibernate (an ORM that treats tables as objects; fewer lines when used well, slower and buggier when misused)
    • A proof of concept ran a couple of months, then the team quit
    • They finished with Spring's JdbcTemplate: cleaner code, fewer lines, no new framework
    • Lesson: popularity is not a reason to adopt.

1.5 What you will learn (book roadmap)

  • Use the Spring context and write aspects around managed objects.
  • Connect to a database and work with persisted data.
  • Exchange data between apps via REST APIs.
  • Build basic apps with convention over configuration (Spring Boot).
  • Follow best practices in class design.
  • Test Spring implementations properly.

Chapter summary (book)

  • A framework supplies common functionality and structure.
  • Communities make solutions and best practices easier to find.
  • Evaluate purpose, alternatives, maturity and community adoption when choosing.
  • Spring = ecosystem; this book mainly uses Core, Data, Boot.
  • Usable beyond backends: desktop, testing tools, more.
