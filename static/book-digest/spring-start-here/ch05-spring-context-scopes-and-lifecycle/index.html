Ch 5: The Spring context, bean scopes and life cycle

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 5. Previous: Ch 4: The Spring context, using abstractions. Book projects: ssh_ch5_ex1 to ssh_ch5_ex8.

[!abstract] Takeaways A scope says how Spring creates and manages a bean. Two matter here:

  • Singleton (default): one instance per bean name, shared by everyone. Keep these immutable.

  • Prototype: a new instance every time you ask. Fine for mutable objects.

  • Within singleton you also choose eager (default, created at startup) or lazy (created on first use).

  • Beans are for things Spring must manage; not every object should be one.

5.1 Singleton scope

  • Spring creates the bean at context load and gives it a name (bean ID). Every reference to that name returns the same instance.
  • Singleton here is not the classic GoF singleton. In Spring it means unique per name, not unique per app: two beans of the same type with different names are two instances.

With @Bean (ssh_ch5_ex1)

// CommentService.java
public class CommentService { }

// ProjectConfig.java
@Configuration
public class ProjectConfig {
    @Bean
    public CommentService commentService() {
        return new CommentService();
    }
}

// Usage
var c = new AnnotationConfigApplicationContext(ProjectConfig.class);
var cs1 = c.getBean("commentService", CommentService.class);
var cs2 = c.getBean("commentService", CommentService.class);
System.out.println(cs1 == cs2);   // true

With only one bean of the type, you can fetch by type; the name was used here just to stress it is the same bean.

With stereotype annotations (ssh_ch5_ex2)

Same behaviour. Two services depend on one repository; Spring injects the same repository instance into both.

// CommentRepository.java
@Repository
public class CommentRepository { }

// CommentService.java
@Service
public class CommentService {
    @Autowired private CommentRepository commentRepository;
    public CommentRepository getCommentRepository() {
        return commentRepository;
    }
}
// UserService is identical

// ProjectConfig.java
@Configuration
@ComponentScan(basePackages = {"com.example.services", "com.example.repositories"})
public class ProjectConfig { }

// Usage
var s1 = c.getBean(CommentService.class);
var s2 = c.getBean(UserService.class);
System.out.println(s1.getCommentRepository() == s2.getCommentRepository());  // true

5.1.1 Singletons in real apps: keep them immutable

  • A web app runs on many threads sharing the same singleton instance. If threads mutate it at once you get a race condition (unpredictable results or exceptions).
  • You could synchronise a mutable singleton, but singletons are meant to be the app's backbone (delegating to each other), and synchronising a shared instance can hurt performance badly
    • Avoid it.
  • Constructor injection helps: final fields make the bean immutable.
@Service
public class CommentService {
    private final CommentRepository commentRepository;
    public CommentService(CommentRepository commentRepository) {
        this.commentRepository = commentRepository;
    }
    public CommentRepository getCommentRepository() {
        return commentRepository;
    }
}

Three rules for using beans (book sidebar):

  1. Make an object a bean only if Spring must manage it to add capabilities.
  2. A bean should be singleton only if it is immutable.
  3. If a bean must be mutable, consider prototype.

5.1.2 Eager vs lazy instantiation

  • Eager (default): all singletons are created when the context starts. Proof (ssh_ch5_ex3): the constructor prints even though nobody uses the bean.

    @Service
public class CommentService {
    public CommentService() {
        System.out.println("CommentService instance created!");
    }
}

    var c = new AnnotationConfigApplicationContext(ProjectConfig.class);   // prints the message

  • Lazy (ssh_ch5_ex4): add @Lazy on the class (stereotype) or on the @Bean method. Now the bean is created only when first referenced.

    @Service
@Lazy
public class CommentService { /* same constructor */ }

    var c = new AnnotationConfigApplicationContext(ProjectConfig.class);
System.out.println("Before retrieving the CommentService");
var service = c.getBean(CommentService.class);
System.out.println("After retrieving the CommentService");

    Before retrieving the CommentService
CommentService instance created!
After retrieving the CommentService

  • Why eager is the default pick:

    • Delegation is cheaper: the target bean already exists; lazy needs an existence check each time.
    • Failures surface at startup, not later while the app is running.

  • Where lazy helped (author's story):

    • a huge monolith installed at many clients, each using only part of it
    • Instantiating everything wasted memory and slowed startup, so most beans were lazy.

  • His advice:

    • stay eager
    • If you need lazy everywhere, the design is probably the problem (a modular design or microservices would let you deploy only what each client needs)
    • If you cannot fix the cause (cost, time), lazy treats the symptom.

5.2 Prototype scope

  • Spring stores the bean's type, not an instance. Every request creates a new object (the book draws a coffee plant instead of a bean).
  • Use @Scope: on the @Bean method, or on the class next to the stereotype annotation.
  • No concurrency problem: each thread that asks gets its own instance, so mutable prototypes are fine.

With @Bean (ssh_ch5_ex5)

@Bean
@Scope(BeanDefinition.SCOPE_PROTOTYPE)
public CommentService commentService() {
    return new CommentService();
}

// Usage
var cs1 = c.getBean("commentService", CommentService.class);
var cs2 = c.getBean("commentService", CommentService.class);
System.out.println(cs1 == cs2);   // false

With stereotype annotations (ssh_ch5_ex6)

@Repository
@Scope(BeanDefinition.SCOPE_PROTOTYPE)
public class CommentRepository { }

CommentService and UserService each inject it with @Autowired; comparing their repositories prints false.

5.2.1 A real use: mutable helper that needs DI (ssh_ch5_ex7)

A CommentProcessor stores a Comment as state and mutates it:

public class CommentProcessor {
  private Comment comment;
    public void setComment(Comment comment) {
        this.comment = comment;
    }
    public Comment getComment() {
        return this.comment;
    }
    public void processComment()  { /* changes comment */ }
    public void validateComment() { /* validates and changes comment */ }
}

A service that just does new CommentProcessor() per call does not need a bean at all. It becomes a bean only if it needs something Spring provides, e.g. a CommentRepository injected into it. Then it cannot be a singleton (threads would trample each other's comment), so make it a prototype:

@Component
@Scope(BeanDefinition.SCOPE_PROTOTYPE)
public class CommentProcessor {
    @Autowired private CommentRepository commentRepository;
    // ...
}

Trap: how you obtain a prototype. Inject the ApplicationContext and call getBean() inside the method, so each call gets a fresh instance:

@Service
public class CommentService {
    @Autowired private ApplicationContext context;

    public void sendComment(Comment c) {
      CommentProcessor p = context.getBean(CommentProcessor.class);   // new instance each call
      p.setComment(c);
      p.processComment(c);
      p.validateComment(c);
      c = p.getComment();
    }
}

Do not inject the prototype straight into the singleton (ssh_ch5_ex8, exercise on GitHub):

@Service
public class CommentService {
    @Autowired private CommentProcessor p;   // injected ONCE when CommentService is created
    ...
}

CommentService is a singleton, created once, so its dependencies are injected once; every call then shares one CommentProcessor and the race conditions return.

Author's opinion: he avoids prototypes and mutable instances where he can. He used prototypes while refactoring an old app to Spring, where mutating objects were everywhere and could only be refactored gradually.

Table 5.1 Singleton vs prototype

Singleton Prototype
Name maps to an actual instance a type
Each reference gives the same instance a new instance
Created at context load, or on first use if @Lazy always when you ask
Default yes must be declared
Mutable attributes not recommended fine

Chapter summary (book)

  • A scope defines how Spring creates and manages instances; main scopes: singleton and prototype.
  • Singleton (default): one instance stored in the context, same object every time. Created at startup unless lazy.
  • Most apps use singletons; because threads share them, they should be immutable (or you handle thread safety).
  • Prototype: new instance per request; useful for mutable objects.
  • Injecting a prototype into a singleton injects it once, defeating the point.
