Ch 9: Using the Spring web scopes

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 9. Previous: Ch 8: Implementing web apps with Spring Boot and Spring MVC. Book projects: ssh_ch9_ex1 to ssh_ch9_ex3. Builds on bean scopes from Ch 5: The Spring context, bean scopes and life cycle.

[!abstract] Takeaways Beyond singleton and prototype, web apps get three web scopes that use the HTTP request as the reference point:

  • Request scope (@RequestScope): a new instance per HTTP request. Safe from threading problems.
  • Session scope (@SessionScope): one instance per client's HTTP session, shared by that client's requests.
  • Application scope (@ApplicationScope): one instance for the whole app, shared by everyone. Avoid it.

The chapter builds a login in three steps, one scope per step: request (credentials), session (logged-in user), application (login counter).

9.1 Request scope

A request-scoped bean is created fresh for each HTTP request (from any client) and usable only by that request; afterwards it is garbage-collected.

Table 9.1: key aspects

Fact Consequence To consider To avoid
New instance per HTTP request from any client Many instances created over the app's life Usually not a problem: they are short-lived and collected after the request Slow creation logic (database or network calls). No logic in the constructor or @PostConstruct of request-scoped beans
Only one request uses an instance No multithreading issues: one thread (the request's) touches it You can store per-request data in its attributes Do not synchronise its attributes: redundant and hurts performance

Login example (ssh_ch9_ex1)

Warning from the author: a hand-made login is only for teaching. In real apps use Spring Security (part of the Spring ecosystem); it avoids vulnerabilities you would introduce yourself. He recommends his book Spring Security in Action, 2nd ed. (Manning, 2024). Here the credentials are baked in (user natalie, password password); real apps keep users in a database and encrypt passwords.

Dependencies: spring-boot-starter-thymeleaf and spring-boot-starter-webmvc.

resources/templates/login.html:

<!DOCTYPE html>
<html lang="en" xmlns:th="http://www.thymeleaf.org">
<head><meta charset="UTF-8"><title>Login</title></head>
<body>
  <form action="/" method="post">
     Username: <input type="text" name="username" /><br />
     Password: <input type="password" name="password" /><br />
     <button type="submit">Log in</button>
  </form>
  <p th:text="${message}"></p>
</body>
</html>

Controller (first version: no logic yet, loggedIn always false). Returning "login.html" from the POST keeps the user on the same page:

@Controller
public class LoginController {
    @GetMapping("/")
    public String loginGet() {
        return "login.html";
    }

    @PostMapping("/")
    public String loginPost(@RequestParam String username,
                            @RequestParam String password,
                            Model model) {
      boolean loggedIn = false;
      if (loggedIn) {
          model.addAttribute("message", "You are now logged in.");
      } else {
          model.addAttribute("message", "Login failed!");
      }
      return "login.html";
    }
}

Where is the request scope? The controller is a singleton and stores nothing, so it is fine. But the login logic holds credentials, which (1) are sensitive, so should not live in memory longer than the request, and (2) differ between users logging in at the same time. A bean for that logic must be per request.

@Component
@RequestScope
public class LoginProcessor {
    private String username;
    private String password;

    public boolean login() {
      String username = this.getUsername();
      String password = this.getPassword();
      if ("natalie".equals(username) && "password".equals(password)) {
          return true;
      } else {
          return false;
      }
    }
    // getters, setters
}

(The book's text writes "@RequestScoped", the code uses @RequestScope.) The controller injects it by constructor and calls it:

private final LoginProcessor loginProcessor;
public LoginController(LoginProcessor loginProcessor) {
    this.loginProcessor = loginProcessor;
}

@PostMapping("/")
public String loginPost(@RequestParam String username, @RequestParam String password, Model model) {
  loginProcessor.setUsername(username);
  loginProcessor.setPassword(password);
  boolean loggedIn = loginProcessor.login();
  if (loggedIn) {
      model.addAttribute("message", "You are now logged in.");
  } else {
      model.addAttribute("message", "Login failed!");
  }
  return "login.html";
}

9.2 Session scope

A session-scoped bean is created when the client's HTTP session is created and reused for all that client's requests while the session is active. Each user has their own session and instance.

Typical uses: remembering the logged-in user while they browse, an online shopping cart.

Table 9.2: key aspects

Fact Consequence To consider To avoid
Instance lives for the whole HTTP session Longer life, collected less often Data stays in memory longer Too much data in the session (performance). Never store sensitive data (passwords, private keys, secrets) in session bean attributes
Several requests can share one instance If one client sends concurrent requests that change data, race conditions Synchronise only as a last resort
It is a way to share data between requests, kept server side Requests become dependent on each other Stateful data ties clients to that app instance Consider storing shared data in a database so requests stay independent

Extend the app (ssh_ch9_ex2)

Steps: (1) session bean for the logged-in user, (2) a page only logged-in users can reach, (3) block access without login, (4) redirect after login.

@Service
@SessionScope
public class LoggedUserManagementService {
    private String username;
    // getters, setters
}

LoginProcessor stays request-scoped (credentials needed only during the request) and, on success, stores the username in the session bean:

@Component
@RequestScope
public class LoginProcessor {
    private final LoggedUserManagementService loggedUserManagementService;
    private String username;
    private String password;

    public LoginProcessor(LoggedUserManagementService loggedUserManagementService) {
      this.loggedUserManagementService = loggedUserManagementService;
    }

    public boolean login() {
      String username = this.getUsername();
      String password = this.getPassword();
      boolean loginResult = false;
      if ("natalie".equals(username) && "password".equals(password)) {
        loginResult = true;
        loggedUserManagementService.setUsername(username);
      }
      return loginResult;
    }
}

You need not worry about several users being logged in: the framework links each HTTP request to the right session.

Bean Scope Holds
LoginController singleton no state
LoginProcessor request username and password, gone after the request
LoggedUserManagementService session the logged-in username for this client
LoginCountService application login attempts from everybody

Redirect: return the string "redirect:" followed by a path.

@Controller
public class MainController {
    private final LoggedUserManagementService loggedUserManagementService;
    public MainController(LoggedUserManagementService loggedUserManagementService) { ... }

    @GetMapping("/main")
    public String home(@RequestParam(required = false) String logout, Model model) {
      if (logout != null) {
        loggedUserManagementService.setUsername(null);          // log out
      }
      String username = loggedUserManagementService.getUsername();
      if (username == null) {
        return "redirect:/";                                    // not logged in
      }
      model.addAttribute("username", username);
      return "main.html";
    }
}

main.html:

<h1>Welcome, <span th:text="${username}"></span></h1>
<a href="/main?logout">Log out</a>

After a successful login, redirect to the main page:

@PostMapping("/")
public String loginPost(@RequestParam String username, @RequestParam String password, Model model) {
  loginProcessor.setUsername(username);
  loginProcessor.setPassword(password);
  boolean loggedIn = loginProcessor.login();
  if (loggedIn) {
      return "redirect:/main";
  }
  model.addAttribute("message", "Login failed!");
  return "login.html";
}

Behaviour: correct login goes to the main page; the logout link returns you to login; opening /main unauthenticated redirects to login.

9.3 Application scope (ssh_ch9_ex3)

All requests from all clients share one instance. It is like a singleton, except (the book says) the context cannot hold several instances of the same type. The lifecycle is described with the HTTP request as reference point.

  • Same concurrency problem as a mutable singleton: keep attributes immutable. But immutable means you can simply use a singleton.
  • Author's advice: avoid it. Use a persistence layer (a database) for shared data.

Example: count login attempts from every user.

@Service
@ApplicationScope
public class LoginCountService {
    private int count;
    public void increment() {
        count++;
    }
    public int getCount() {
        return count;
    }
}

(Notice the unsynchronised count++: exactly the race-condition risk the author warns about.)

LoginProcessor.login() now calls loginCountService.increment() first (the service is injected by constructor next to LoggedUserManagementService). MainController sends the count to the view:

int count = loginCountService.getCount();
model.addAttribute("loginCount", count);

<h1>Welcome, <span th:text="${username}"></span>!</h1>
<h2>Your login number is <span th:text="${loginCount}"></span></h2>
<a href="/main?logout">Log out</a>

Book typo to know: listing 9.15 declares public LoginController(...) inside MainController and omits the LoggedUserManagementService field it uses.

Closing thought: HTTP is often used between services too, and frontends and backends talk through endpoints designed in the REST style: next chapter.

Chapter summary (book)

  • Three web scopes: request (one instance per HTTP request), session (one per HTTP session, shared by that client's requests), application (one for the whole app).
  • Request scope: usually no concurrency worry; short-lived. Avoid costly constructor or @PostConstruct logic.
  • Session scope shares data across a client's requests, but the same client can send concurrent requests, so changing session bean data can race; avoid it or synchronise.
  • Application scope: shared by everyone; avoid for mutable data (writes need synchronisation, hurting performance; data stays in memory for the app's life). Prefer a database.
  • Session and application scopes make the app stateful: requests depend on data the app stores. Stateful apps are harder to design and scale, so consider alternatives when possible.
