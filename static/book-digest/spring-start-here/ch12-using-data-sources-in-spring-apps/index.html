Ch 12: Using data sources in Spring apps

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 12. Previous: Ch 11: Consuming REST endpoints. Book projects: ssh_ch12_ex1 to ssh_ch12_ex3. Starts the data persistence part.

Takeaways
  • A data source manages and reuses database connections for your app (instead of opening and authenticating a new connection for every operation).
  • Spring Boot gives you HikariCP by default.
  • JdbcTemplate is Spring's simplest tool to run SQL: update() for INSERT/UPDATE/DELETE, query() with a RowMapper for SELECT.
  • Repositories hold all persistence code.
  • You configure the database in application.properties, or define your own DataSource bean when you need runtime control.

12.1 What is a data source?

  • DBMS
    • (database management system): software that lets you add, change and retrieve persisted data efficiently and securely
    • A database is a persistent collection of data managed by a DBMS.
  • A data source manages connections to the DBMS
    • The app asks it for a connection instead of creating one each time
    • It reuses connections, requests new ones only when needed, and closes them when released.
  • Without it, each operation would pay for a network round trip plus authentication: very slow in production.
  • Author's analogy: you order a beer, the barman checks your ID. Fine once; tedious if he asks again for the second and third beer.

JDBC (Java Database Connectivity):

  • The JDK gives only the abstractions for working with a relational database, not an implementation for MySQL, Postgres or Oracle.
  • You add a runtime dependency, the JDBC driver, supplied by each vendor (not by the JDK or Spring).
  • Plain JDBC tutorials get connections with DriverManager:
    Connection con = DriverManager.getConnection(url, username, password);
    This reauthenticates every time, a waste for client and server. A data source avoids that.
  • The most used implementation is HikariCP (Hikari connection pool), and it is Spring Boot's default: https://github.com/brettwooldridge/HikariCP (open source).

12.2 JdbcTemplate (ssh_ch12_ex1)

Plain JDBC is verbose even for one insert:

String sql = "INSERT INTO purchase VALUES (?,?)";
try (PreparedStatement stmt = con.prepareStatement(sql)) {
  stmt.setString(1, name);
  stmt.setDouble(2, price);
  stmt.executeUpdate();
} catch (SQLException e) {
  // do something when an exception occurs
}

JdbcTemplate is the simplest Spring tool for a relational database, ideal for small apps and for learning, and the right choice when you want no other persistence framework dependency.

Steps: (1) connect to a DBMS, (2) write the repository logic, (3) call repository methods from REST endpoint actions.

App: a table purchase (products bought from an online shop): id (auto-increment primary key), product, price. Two endpoints: add a record, get all records. Persistence code lives in classes named repositories by convention (a repository is a class that works with the database).

Database choice: examples use H2 (in-memory, ideal for examples) and MySQL (free, light, runs locally). Postgres, Oracle or MS SQL work too: use the right JDBC driver and adapt the SQL. For H2 the JDBC driver comes with the H2 dependency.

Prerequisites the author assumes (with refreshers): JDBC basics: chapter 15 of OCP Oracle Certified Professional Java SE 17 Developer Complete Study Guide, Jeanne Boyarsky and Scott Selikoff (Sybex, 2022). SQL: Learning SQL, 3rd ed., Alan Beaulieu (O'Reilly, 2020).

Dependencies:

<dependency>   <!-- REST endpoints -->
   <groupId>org.springframework.boot</groupId>
   <artifactId>spring-boot-starter-webmvc</artifactId>
</dependency>
<dependency>   <!-- JDBC starter -->
   <groupId>org.springframework.boot</groupId>
   <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
<dependency>   <!-- in-memory DB and its JDBC driver -->
   <groupId>com.h2database</groupId>
   <artifactId>h2</artifactId>
   <scope>runtime</scope>
</dependency>

schema.sql in resources: Spring runs it at startup (DDL, "data description language"):

CREATE TABLE IF NOT EXISTS purchase (
    id INT AUTO_INCREMENT PRIMARY KEY,
    product varchar(50) NOT NULL,
    price double NOT NULL
);

Note: schema.sql is fine for tutorials only. Real apps need versioned database scripts: the author recommends learning Flyway (https://flywaydb.org/) or Liquibase (https://www.liquibase.org/) right after the fundamentals.

Model:

public class Purchase {
    private int id;
    private String product;
    private BigDecimal price;
    // getters, setters
}

Why BigDecimal and not double? double and float can lose precision even in simple addition or subtraction because of how Java stores them. For prices and other sensitive values use BigDecimal. Spring's capabilities know how to use it.

Repository (@Repository is the focused stereotype for persistence classes, like @Service for services):

@Repository
public class PurchaseRepository {
    private final JdbcTemplate jdbc;
    public PurchaseRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }
}

Where does the JdbcTemplate come from? Boot sees the H2 dependency and auto-configures a DataSource and a JdbcTemplate. Without Boot you define both as @Beans yourself.

Write: update() runs any data-changing SQL (INSERT, UPDATE, DELETE); it gets the connection, builds the statement and handles SQLException.

public void storePurchase(Purchase purchase) {
  String sql = "INSERT INTO purchase (`product`, `price`) VALUES (?, ?)";   // ? = parameters
  jdbc.update(sql, purchase.getProduct(), purchase.getPrice());
}

Exceptions: JdbcTemplate translates SQLException into Spring's unchecked DataAccessException hierarchy, e.g. DataIntegrityViolationException (constraint violation) or BadSqlGrammarException (invalid SQL). Repositories need no throws.

  • Let it propagate to the service or presentation layer, to be logged and turned into a proper response
    • or catch a specific subclass when you can recover or give the user a better message.
  • Do not catch the general exception just to hide it: inside a transaction, letting it propagate also lets Spring roll back automatically.

Read: a RowMapper turns one ResultSet row into one object.

public List<Purchase> findAllPurchases() {
  String sql = "SELECT * FROM purchase";
  RowMapper<Purchase> purchaseRowMapper = (r, i) -> {
     Purchase rowObject = new Purchase();
     rowObject.setId(r.getInt("id"));
     rowObject.setProduct(r.getString("product"));
     rowObject.setPrice(r.getBigDecimal("price"));
     return rowObject;
  };
  return jdbc.query(sql, purchaseRowMapper);
}

Controller:

@RestController
@RequestMapping("/purchase")
public class PurchaseController {
    private final PurchaseRepository purchaseRepository;
    public PurchaseController(PurchaseRepository purchaseRepository) {
        this.purchaseRepository = purchaseRepository;
    }

    @PostMapping
    public void storePurchase(@RequestBody Purchase purchase) {
      purchaseRepository.storePurchase(purchase);
    }

    @GetMapping
    public List<Purchase> findPurchases() {
      return purchaseRepository.findAllPurchases();
    }
}

12.3 Customising the data source

H2 suits examples (and sometimes integration tests); production uses a real DBMS.

Way What you do Boot's role
H2 (examples) add the H2 dependency Boot builds the DataSource and JdbcTemplate
MySQL or another DBMS swap in the JDBC driver and set spring.datasource.* properties Boot still builds the DataSource
Your own DataSource bean a @Bean method, e.g. HikariDataSource Boot backs off and uses yours

Define your own when the implementation depends on a runtime condition, you have several databases (use @Qualifier), the pool size depends on the environment, or you use Spring without Boot.

12.3.1 Via application.properties (ssh_ch12_ex2)

Switch to MySQL: (1) exclude H2 and add the MySQL JDBC driver, (2) add connection properties. The logic does not change.

<dependency>
   <groupId>mysql</groupId>
   <artifactId>mysql-connector-java</artifactId>
   <scope>runtime</scope>
</dependency>

spring.datasource.url=jdbc:mysql://localhost/spring_start_here?useLegacyDatetimeCode=false&serverTimezone=UTC
spring.datasource.username=<dbms username>
spring.datasource.password=<dbms password>
spring.sql.init.mode=always
  • spring.sql.init.mode=always makes Boot run schema.sql (with H2 Boot runs it by default if the file exists).
  • You need a MySQL server and a database (spring_start_here); install steps are in Appendix E.
  • Secrets such as passwords do not belong in the properties file in production; use secret vaults (out of scope).

Boot builds the DataSource bean from the spring.datasource.* properties.

12.3.2 Your own DataSource bean (ssh_ch12_ex3)

Prefer the simplest solution (properties). Define the bean yourself when:

  • you need a specific DataSource implementation chosen from a runtime condition;
  • the app uses several databases: several data sources told apart by qualifiers;
  • parameters depend on runtime conditions, e.g. more or fewer pool connections per environment;
  • you use Spring without Spring Boot.

It is "just a bean": a @Bean method in a configuration class. If a DataSource bean exists, Boot uses it instead of its default.

@Configuration
public class ProjectConfig {
    @Value("${custom.datasource.url}")      private String datasourceUrl;
    @Value("${custom.datasource.username}") private String datasourceUsername;
    @Value("${custom.datasource.password}") private String datasourcePassword;

    @Bean
    public DataSource dataSource() {
      HikariDataSource dataSource = new HikariDataSource();
      dataSource.setJdbcUrl(datasourceUrl);
      dataSource.setUsername(datasourceUsername);
      dataSource.setPassword(datasourcePassword);
      dataSource.setConnectionTimeout(1000);   // how long to wait for a connection (ms)
      return dataSource;
    }
}

custom.datasource.url=jdbc:mysql://localhost/spring_start_here?useLegacyDatetimeCode=false&serverTimezone=UTC
custom.datasource.username=root
custom.datasource.password=

The word custom is deliberate: these property names are your own, not Boot's. Behaviour and curl results are identical to the previous two projects (if you did not clean the table, earlier records appear).

Chapter summary (book)

  • The JDK provides abstractions to connect to a relational database; the app always adds a runtime JDBC driver that implements them.
  • A data source manages connections; without it the app would request connections too often and slow down.
  • Boot configures HikariCP, a connection pool, by default; you may use another implementation.
  • JdbcTemplate simplifies JDBC code and depends on a data source.
  • Use update() for mutations and query() for SELECTs.
  • To customise, declare your own java.sql.DataSource bean; Boot then uses it instead of its default. Same for a custom JdbcTemplate. Boot's defaults are usually enough.
  • Several databases: several data sources, each with its own JdbcTemplate, told apart with @Qualifier in the Spring application context.
