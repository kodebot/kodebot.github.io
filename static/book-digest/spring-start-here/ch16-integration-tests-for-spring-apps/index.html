Ch 16: Implementing integration tests for Spring apps

Source: Laurentiu Spilca, Spring Start Here, Second Edition (Manning, MEAP V05), ch. 16. Previous: Ch 15: Unit testing in Spring apps. Uses the money transfer use case from ssh_ch14_ex1. Last chapter of the book (appendices follow: Appendices B to G: projects, HTTP, JSON, MySQL, tools, further reading).

Takeaways
  • A unit test asks "does this method work alone?".
  • An integration test asks "does this part work together with what it depends on?".
  • In Spring that means running with the Spring context (@SpringBootTest), optionally swapping a bean for a mock (@MockitoBean), or testing the web layer through MockMvc, which sends simulated HTTP requests without starting a server.
  • Use many unit tests, fewer integration tests, and targeted controller tests.

16.1 Spring integration tests

Analogy: the car dashboard again. The tank is full and works alone, but the fuel line to the engine is broken: the car will not start and the fuel indicator says nothing. Parts correct in isolation can still fail to talk to each other.

What can you integration-test?

  • Two or more of your objects talking to each other (catches problems after one changes).
  • An object with a capability the framework adds
    • (transactions, DI, security, caching)
    • Upgrade Spring and, if the capability changes, the test fails even though your code did not change.
  • The app with its persistence layer (repository against a database), to detect problems after upgrading or swapping a dependency such as the JDBC driver.

The structure is the same as a unit test (assumptions, call, validations), but you do not have to mock every dependency: you may let a real object be called when you want to test that two objects communicate (e.g. the real AccountRepository). You can still mock what you do not care about.

Note on databases: if you do not mock the repository, use an in-memory database such as H2, or Testcontainers (a containerised local database). A real external database adds latency and fails on infrastructure or network problems, and you are testing the app, not the infrastructure.

A Spring integration test

A Spring integration test lets Spring create the beans and configure the context as when the app runs.

  • @SpringBootTest starts the Spring context.
  • @Autowired TransferService is the real bean, built by Spring with real DI and transactions.
  • @MockitoBean AccountRepository is a mock registered as a bean that replaces the real repository.
  • The test body uses given / when / verify as in a unit test.
  • Boot 4 name: @MockitoBean. Before Spring Boot 4 it was @MockBean (same behaviour).
@SpringBootTest
class TransferServiceSpringIntegrationTests {
    @MockitoBean                       // a mock that is also a bean in the context
    private AccountRepository accountRepository;

    @Autowired                         // the real TransferService from the context
    private TransferService transferService;

    @Test
    void transferServiceTransferAmountTest() {
      Account sender = new Account();
      sender.setId(1);
      sender.setAmount(new BigDecimal(1000));

      Account receiver = new Account();
      receiver.setId(2);
      receiver.setAmount(new BigDecimal(1000));

      when(accountRepository.findById(1L)).thenReturn(Optional.of(sender));
      when(accountRepository.findById(2L)).thenReturn(Optional.of(receiver));

      transferService.transferMoney(1, 2, new BigDecimal(100));

      verify(accountRepository).changeAmount(1, new BigDecimal(900));
      verify(accountRepository).changeAmount(2, new BigDecimal(1100));
    }
}
  • @MockitoBean is like @Mock but also puts the mock in the Spring context so @Autowired works. Before Spring Boot 4 it was called @MockBean; same behaviour.
  • It looks like a unit test but Spring now owns the tested object: if DI broke after an upgrade, this test would fail with no change to your code
    • The same goes for transactions, security, caching.

Do not use integration tests to cover every scenario of the logic. They are slower: they start the Spring context, and each call triggers the Spring mechanisms attached to the method. Validate logic with unit tests; use integration tests to validate integration with the framework.

16.2 Controller integration tests

They check how the app exposes functionality through web endpoints: not just a Java method but the endpoint contract: URL, HTTP method, request body, response status and body, headers, validation, sometimes security.

Why test controllers: they are the entry point of a web app. Service logic can be right while the endpoint is mapped wrong, the request body is not deserialised as expected, validation does not run, or the response shape differs from what the client expects.

Tools:

  • MockMvc: calls Spring MVC controllers without starting a real HTTP server; you choose which objects in the flow are real and which mocked.
  • TestRestTemplate: sends real HTTP requests to the app started on a test port.
  • WebTestClient: commonly used with Spring WebFlux (reactive) but useful elsewhere.

Step 1: configure MockMvc. @SpringBootTest starts the context; inject the WebApplicationContext and build the client before each test.

@SpringBootTest
public class TransferMoneyTests {
    @Autowired
    private WebApplicationContext context;
    private MockMvc mockMvc;

    @BeforeEach
    void setup() {
      this.mockMvc = MockMvcBuilders.webAppContextSetup(context).build();
    }
}

Step 2: the test. The repository is replaced with @MockitoBean, so the controller and web setup are real while the repository is controlled (the book simplifies; you could use H2 or Testcontainers).

@SpringBootTest
public class TransferMoneyTests {
  @Autowired private WebApplicationContext context;
  private MockMvc mockMvc;
  @MockitoBean private AccountRepository accountRepository;

  @BeforeEach
  void setup() {
      this.mockMvc = MockMvcBuilders.webAppContextSetup(context).build();
  }

  @Test
  @DisplayName("""
    GIVEN Two accounts exist with IDs 1 and 2, and both have 1000 balance.
    WHEN A transfer of 100 is requested from account 1 to account 2.
    THEN The response status is OK and both accounts' balances are updated
   """)
  void transferMoneySuccess() throws Exception {
    Account sender = new Account();
    sender.setId(1);
    sender.setAmount(new BigDecimal("1000"));
    Account receiver = new Account();
    receiver.setId(2);
    receiver.setAmount(new BigDecimal("1000"));
    given(accountRepository.findById(1L)).willReturn(Optional.of(sender));
    given(accountRepository.findById(2L)).willReturn(Optional.of(receiver));

    mockMvc.perform(post("/transfer")
           .contentType(MediaType.APPLICATION_JSON)
           .content("""
               {
                 "senderAccountId": 1,
                 "receiverAccountId": 2,
                 "amount": 100
               }
               """))
           .andExpect(status().isOk());

    verify(accountRepository).changeAmount(1L, new BigDecimal("900"));
    verify(accountRepository).changeAmount(2L, new BigDecimal("1100"));
  }
}

What the call does:

  • mockMvc.perform(post("/transfer")): a simulated POST, the same contract a real client uses.
  • .contentType(MediaType.APPLICATION_JSON): tells Spring the body is JSON (a real client sends Content-Type: application/json) so Spring can deserialise it.
  • .content(...): the JSON body
    • Wrong field names, a missing required field, or JSON that cannot become the controller's object all fail the test: it validates the contract, not only the Java logic.
  • .andExpect(status().isOk()): asserts 200 OK; clients see HTTP responses, not service methods.
  • verify(...): the effect on the application logic.

MockMvc can also set path variables, request parameters, headers, cookies, authentication details. On the response you can check not just the status but the body, content type, specific JSON fields, headers, cookies, redirects, error messages. The more important the contract, the more you should validate.

Comparing the three kinds of tests

Unit test Spring integration test Controller integration test
Scope one piece of logic, in isolation logic together with Spring features the web layer / endpoint contract
Starts Spring? usually no yes (context boots every time) yes
Strength smallest and fastest; easy to run often and to debug; good for business rules, calculations, validations confidence it works as a Spring app: DI, config, transactions, repositories, services, scheduled components, event listeners tests from an API client's view; catches wrong mappings, bad JSON formats, missing validation, unexpected response structures
Weakness does not prove it works when Spring wires, injects, configures, manages transactions slower; harder to maintain (more parts) specific to the web contract; more setup with security, validation, many dependencies

Practical advice: many fast unit tests, fewer Spring integration tests for important framework interactions, and targeted controller tests for important endpoints.

Chapter summary (book)

  • Integration tests validate how multiple parts of an app work together, including framework capabilities: DI, configuration, transactions, persistence, security, web endpoints.
  • Spring integration tests start the Spring context, so they run slower than unit tests. Use @SpringBootTest and @Autowired to inject the object you test.
  • @MockitoBean replaces a Spring bean with a mock when you need to control that dependency.
  • You do not always mock all dependencies; use real objects when the aim is to check how they interact.
  • Controller integration tests validate endpoint contracts: URL, method, request data, response status and body, headers, cookies, validation behaviour.
  • Tools: MockMvc (no real server), TestRestTemplate (real requests to a test port), WebTestClient (often reactive).
  • MockMvc lets you set content type, body, parameters, headers, cookies, then validate the response.
  • Balanced strategy: many unit tests, fewer Spring integration tests, targeted controller tests.
