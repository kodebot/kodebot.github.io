The Kubernetes Book 1: Kubernetes Primer

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 1. Previous: The Kubernetes Book 0: Preface. Next: The Kubernetes Book 2: Kubernetes Principles of Operation.

Takeaways
  • Kubernetes orchestrates containerised, cloud-native, microservices apps: it deploys, scales, self-heals and updates them without you stepping in.
  • It came from Google engineers, partly in response to AWS and Docker, and was open-sourced and donated to the CNCF in 2014.
  • The CRI made the container runtime pluggable; Kubernetes 1.24 removed Docker as a runtime, and containerd is now the usual default.
  • Kubernetes shares DNA with Google's Borg and Omega but is not an open-source version of either.
  • It is the "operating system of the cloud": it abstracts clouds the way Linux abstracts servers.

The chapter has two parts: important background, then Kubernetes as the OS of the cloud.

1.1 Important Kubernetes background

The book's opening sentence: "Kubernetes is an orchestrator of containerized cloud-native microservices applications." Four terms need unpacking.

Orchestration

An orchestrator deploys applications and responds dynamically to change. Kubernetes can:

  • deploy applications
  • scale them up and down with demand
  • self-heal them when things break
  • perform rollouts and rollbacks

You configure a few things up front, then Kubernetes does the rest.

Containerisation

  • Packaging an app and its dependencies as images, then running them as containers.
  • Containers are the next generation of VMs: smaller, faster, more portable.
  • They have not replaced VMs; the two run side by side, but containers are first choice for most new apps.

Cloud native

  • Apps with cloud-like features: auto-scaling, self-healing, automated updates, rollbacks.
  • Running a regular app in a public cloud does not make it cloud native.

Microservices

An app built from many small, specialised, independent parts. The book's e-commerce example has six features, so six microservices:

  1. Web front-end
  2. Catalog
  3. Shopping cart
  4. Authentication
  5. Logging
  6. Store
  • Each has its own small team and release cycle, and is scaled and updated independently.
  • The usual pattern is one container per microservice, so scaling a part means adding or removing its containers.

Jargon translated: Kubernetes deploys, scales, self-heals and updates apps whose individual features are packaged and deployed as containers.

1.2 Where Kubernetes came from

  • Built by a group of Google engineers, partly in response to AWS and Docker.
    • AWS invented modern cloud computing, and the industry had to catch up.
    • Google had its own cloud and wanted to abstract away AWS's value, making it easy for customers to move onto Google's cloud.
    • Google ran Search and Gmail on billions of containers per week.
    • Docker was booming and users needed help managing explosive container growth.
  • Lessons from Google's internal container tools produced Kubernetes, open-sourced in 2014 and donated to the newly formed Cloud Native Computing Foundation (CNCF).
  • Still, at its core, it does two things:
    • abstracts infrastructure (such as AWS)
    • simplifies application portability

Kubernetes and Docker

  • Early Kubernetes shipped with Docker as its container runtime (create, start, stop containers).
  • Docker got bloated and many alternatives appeared, so Kubernetes created the container runtime interface (CRI) to make the runtime layer pluggable.
    • Examples of why to choose differently: better isolation, better performance, Wasm support.
  • Kubernetes 1.24 removed Docker as a runtime.
  • Most new clusters now default to containerd ("container dee"): a stripped-down Docker optimised for Kubernetes.
  • Docker, containerd and Kubernetes all work with OCI (Open Container Initiative) images and containers, so Docker-built apps still run.
  • Figure 1.2: a four-node cluster where some nodes run multiple runtimes, which is supported and increasingly common. Chapter 9 uses this with a Wasm app.

Docker Swarm

  • In 2016 and 2017 Docker Swarm, Mesosphere DCOS and Kubernetes competed to be the standard orchestrator. Kubernetes won.
  • Swarm is still developed and used by small companies wanting a simple alternative.

Kubernetes and Borg

  • Google's in-house orchestrators were Borg and Omega.
  • Kubernetes is not an open-source version of either; it shares "DNA and family history" with them.

The name

  • Pronounced "koo-ber-net-eez", though the community does not mind variants.
  • From the Greek word for helmsman (ship steerer), hence the ship's wheel logo.
  • Some original engineers wanted Seven of Nine (a Borg drone from Star Trek: Voyager); copyright forbade it, so the logo has seven spokes.
  • K8s ("kates"): the 8 stands for the eight letters between K and s.

1.3 Kubernetes: the operating system of the cloud

Kubernetes is the de facto platform for cloud-native apps, called the OS of the cloud because it abstracts cloud differences as Linux and Windows abstract servers.

Operating system Kubernetes
Abstracts server resources Abstracts cloud resources
Schedules application processes Schedules application microservices
  • You can schedule apps without caring whether they run on AWS, Azure, Civo Cloud, GCP or on-premises.
  • This enables hybrid cloud, multi-cloud and cloud migrations: deploy to one cloud today, migrate to another tomorrow.

Application scheduling

  • An OS hides CPU, memory, storage and networking. Few developers care which CPU core, memory DIMM or flash chip their code uses; the OS decides.
  • Kubernetes does the same for clouds and data centres: you rarely care which node, failure zone or storage volume your app uses.

Summary points

  • Kubernetes was created by Google engineers from lessons running containers at hyper-scale, and is now an open-source CNCF project under Apache 2.0.
  • It is the industry standard for deploying and managing cloud-native apps on any cloud or on-premises.
  • Because it abstracts infrastructure, it enables hybrid clouds and moving on, off and between clouds.
Terms to carry forward
  • Orchestrator: deploys apps and responds to change (scale, heal, roll out, roll back).
  • Cloud native: has auto-scaling, self-healing, automated updates and rollbacks.
  • Microservices: an app built from small, independent, separately deployed parts.
  • CRI: container runtime interface; makes runtimes pluggable.
  • containerd: default runtime in most new clusters.
  • OCI: Open Container Initiative image and container standards.
  • CNCF: Cloud Native Computing Foundation, owner of Kubernetes.
  • Borg and Omega: Google's internal orchestrators.
  • K8s: shorthand for Kubernetes.
