The Kubernetes Book 4: Working with Pods

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 4. Previous: The Kubernetes Book 3: Getting Kubernetes. Next: The Kubernetes Book 5: Virtual Clusters with Namespaces.

Takeaways
  • Every app runs in a Pod: deploy, terminate, scale and update all mean creating or removing Pods.
  • Pods are an abstraction layer (containers, Wasm, VMs and serverless all fit) and give resource sharing, scheduling control, probes, restart policies and more.
  • Pods are mortal and immutable; "restart" or "update" a Pod really means replace it. Only the kubelet restarts containers, governed by restartPolicy.
  • Always set resource requests and limits; the scheduler uses requests, the runtime enforces limits.
  • Multi-container patterns: init containers (run once, finish first) and sidecars (init containers with restartPolicy: Always; start first, run alongside, stop last).

The chapter has two parts: Pod theory, then hands-on.

4.1 Pod theory

Pods are an abstraction layer

  • Containers, VMs, serverless functions and Wasm apps all run in Pods; Kubernetes does not know the difference.
  • Benefits:
    • Kubernetes manages Pods without caring what is inside.
    • Different workloads run side by side and use the full declarative API.
  • Containers and Wasm apps use standard Pods, controllers and runtimes.
  • Serverless functions run in standard Pods but need extra apps such as Knative (custom resources and controllers). VMs need KubeVirt.
  • Figure 4.1: four workloads on one cluster; VM workloads run in a VirtualMachineInstance (VMI), similar to a Pod.

Pods augment workloads

Features Pods add:

  • resource sharing
  • advanced scheduling
  • application health probes
  • restart policies
  • security policies
  • termination control
  • volumes

Despite all this, Pods are lightweight with very little overhead.

Pods enable resource sharing

All containers in a Pod share its execution environment:

Shared Linux namespace
Filesystem and volumes mnt
Network stack net
Memory IPC
Process tree pid
Hostname uts
  • Figure 4.2: a multi-container Pod sharing IP and volume. Clients reach the main container on 10.0.10.15:8080 and the sidecar on 10.0.10.15:5005.
  • Containers talk to each other over the Pod's localhost and mount the same volume.
  • Example: a sidecar syncs static content from a remote Git repo into the volume; the main container reads it and serves it as a web page.

Pods and scheduling

  • All containers in a Pod are scheduled to the same node (nodes are physical servers, VMs or cloud instances).
  • Put containers in one Pod only if they need to share memory, volumes or networking. If you merely want two workloads on the same node, use separate Pods plus one of:
    • nodeSelectors
    • affinity and anti-affinity
    • topology spread constraints
    • resource requests and limits
Mechanism Behaviour
nodeSelector Simplest. Give labels; scheduler picks only nodes with all of them.
Affinity / anti-affinity A more powerful nodeSelector: schedule alongside (affinity, attracts) or away from (anti-affinity, repels) resources; hard rules must be obeyed, soft rules are best effort; can select on Pods as well as nodes.
Topology spread constraints Spread Pods across infrastructure for availability, performance or locality, for example across availability zones for HA; custom domains allowed (close to data sources, close to clients for lower latency).
Requests and limits Tell the scheduler how much CPU and memory a Pod needs. Every Pod should set them; without them the scheduler may place a Pod on a node without enough resources.

Affinity example: a hard node affinity for project=tkb only runs on nodes with that label, and the Pod is not scheduled if none exists. A soft rule tries first but still schedules elsewhere. Anti-affinity looks for nodes without the label. Pod-based rules work the same way.

Deploying Pods

  1. Define the Pod in a YAML manifest.
  2. Post it to the API server.
  3. The request is authenticated and authorised.
  4. The Pod spec is validated.
  5. The scheduler filters nodes using nodeSelectors, affinity and anti-affinity, topology spread constraints, resource requirements and limits.
  6. The Pod is assigned to a healthy node meeting all requirements.
  7. The node's kubelet notices the assignment through the API server.
  8. The kubelet downloads the spec and asks the local runtime to start it.
  9. The kubelet monitors status and reports changes to the API server.
  • No suitable node: the Pod is pending.
  • Deployment is atomic: the Pod serves requests only when all containers are running.

Pod lifecycle

  • Mortal: you cannot restart a failed or deleted Pod. A controller replaces it, which is not the same as restarting and fixing it.
  • Immutable:
    • you cannot modify a deployed Pod
    • To change one, create a new Pod with the change, delete the old one
    • To write data, attach a volume so the data outlives the Pod
    • (A shift for people used to patching live servers.)
  • Lifecycle:
    • you post the YAML, the Pod is Pending while the scheduler finds a node, the kubelet starts the containers, then Running once all are up. Long-lived Pods (web server) stay Running
    • short-lived ones (batch job) reach Succeeded when all containers finish (Figure 4.3).
  • VMs are the opposite: mutable and immortal (restart, reconfigure, migrate). KubeVirt wraps them in a modified Pod, the VMI, with custom controllers.

Restart policies

  • They apply to individual containers, not the Pod.
  • A Deployment replaces a Pod on a failed node with a new one:
    • same spec, but new UID, new IP and no state
    • The same happens on node eviction, scale-down (deletes Pods), scale-up (new Pods), updates and rollbacks.
  • So "update or restart Pods" always means replace them.
  • Kubernetes can restart containers, always via the local kubelet, governed by spec.restartPolicy:
Value Meaning Typical use
Always Always restart Long-living: web servers, data stores, message queues
OnFailure Restart only on an error exit code Short-living batch jobs
Never Never restart Short-living, when failure does not matter
  • The policy is Pod-wide, except for init containers.

Static Pods vs controllers

Deployment style Frequency Behaviour
Directly from a Pod manifest (static Pod) Rare Managed only by the node's kubelet: no self-healing, scaling or rolling updates; if the node fails the kubelet fails with it
Via a workload resource and controller Most common Highly available controller restarts Pods on other nodes, scales, does rolling updates and versioned rollbacks; kubelet still restarts failed containers

Workload controllers are covered in chapter 6.

The pod network

  • Every cluster runs a pod network connecting all Pods; usually a flat Layer-2 overlay spanning all nodes so every Pod can talk directly to every other Pod.
  • Implemented by a third-party plugin via the Container Network Interface (CNI), chosen at cluster build time. Plugins differ
    • at the time of writing Cilium is most popular, with security and observability features.
  • Figure 4.4: three nodes, five Pods, one pod network; nodes connect to external networks but not directly to the pod network.
  • New clusters are often very open with little security. Use Network Policies and other measures to secure it.

Multi-container Pods

  • Microservice design says one container, one clearly defined responsibility (separation of concerns, single responsibility principle)
    • Keeps containers small, reusable and easier to troubleshoot.
  • Example: an app that syncs content from a repo and serves it as a web page has two responsibilities, so design two microservices, one container each.
  • Usually they sit in separate Pods and talk over the pod network
    • Sometimes one Pod is better: the sync container stores content in a shared volume and the web container serves it (Figure 4.5).
  • Two main patterns: init containers and sidecars.

Init containers

  • A special container type in the API. Kubernetes guarantees it starts and completes before the main app container starts, and runs only once.
  • Purpose: prepare the environment for the app.
  • Examples:
    • Wait for a remote API: the init container polls the API until it responds; the app is blocked until then, then Kubernetes starts it.
    • One-time repo clone: instead of bloating the app with the remote address, certificates, auth, sync protocol and checksum logic, an init container does it first.
  • You can list several; they run in manifest order and all must finish before app containers start.
  • A failed init container is restarted; with restartPolicy: Never the Pod fails.
  • Limitation: they only run before the app starts.

Sidecars

  • A sidecar adds functionality without putting it in the app container
    • Examples: scraping logs, monitoring and syncing remote content, brokering connections, munging data, encrypting network traffic.
  • Figure 4.6: a service mesh sidecar intercepting and encrypting all traffic; it must start before the app and run for the Pod's whole life, otherwise the app cannot use the network.
  • Old Kubernetes had no sidecar concept, so they were regular containers, with no reliable way to start them first, keep them running or stop them after the app.
  • Native sidecars:
    • alpha in v1.28, beta in v1.29
    • as of v1.32 still beta (use with caution) but enabled by default and used by projects including Argo CD and Istio
    • GA expected soon.
  • Definition: an entry in spec.initContainers with restartPolicy: Always. Kubernetes guarantees they:
    1. start before the main application container
    2. keep running alongside it
    3. terminate after it
  • Otherwise they follow init container rules (startup order, probes attach to them).

Pod theory summary

  • The Pod is the atomic unit of scheduling and abstracts the workload.
  • Multi-container Pods tightly couple workloads that share resources, augment apps (sidecar) and initialise environments (init).
  • Usually you deploy via controllers for self-healing and autoscaling.

4.2 Hands-on with Pods

Clone the book's repo (see The Kubernetes Book 0: Preface) and run all commands from the pods folder.

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025

Pod manifest files

# pod.yml
kind: Pod
apiVersion: v1
metadata:
  name: hello-pod
  labels:
    zone: prod
    version: v1
spec:
  containers:
  - name: hello-ctr
    image: nigelpoulton/k8sbook:1.0
    ports:
    - containerPort: 8080
    resources:
      limits:
        memory: 128Mi
        cpu: 0.5
Field Meaning
kind Object type (Pod; for a Deployment it would say Deployment)
apiVersion API version to use (v1 Pod schema)
metadata Name hello-pod and two labels (used later to connect to a Service)
spec One container hello-ctr from nigelpoulton/k8sbook:1.0, port 8080, max 128MB memory and half a CPU

Manifest files: Empathy as Code

  • YAML manifests document the app: newcomers learn its functions and requirements; ops teams see ports, CPU and memory needs.
  • They can live in source control for versioning and diffs.
  • Nirmal Mehta called this empathy as code in his 2017 DockerCon talk A Strong Belief, Loosely Held: Bringing Empathy to IT (as cited by the book).

Pod hostnames

  • The Pod's metadata.name becomes the hostname of every container in the Pod.
  • Check from inside the exec session (case-sensitive):

  • Pod names should be valid DNS names: a-z, 0-9, minus and period.

Check Pod immutability

Immutability has two levels:

  • Object immutability (the Pod): Kubernetes prevents config changes to a running Pod.
  • App immutability (containers): Kubernetes cannot stop you changing the app or filesystem in a container; you must keep containers and apps stateless and immutable.

Try kubectl edit pod hello-pod (opens vi on Mac and Linux, notepad.exe on Windows) and change the container name, port or resources:

Resource requests and limits

  • Requests are minimums; limits are maximums, set per container.
resources:
  requests:        # minimums for scheduling
    cpu: 0.5
    memory: 256Mi
  limits:          # maximums for the kubelet to cap
    cpu: 1.0
    memory: 512Mi

How it plays out:

  1. The scheduler finds a node with at least 256Mi and half a CPU; if none, the Pod is pending and the Cluster Autoscaler tries to add a node.
  2. The kubelet downloads the spec, reserves the requested resources and asks the runtime to cap the container at 1 CPU and 512Mi.
  3. Runtimes mostly enforce limits, though the implementation varies.
  4. The container is guaranteed its requests, may burst above them if the node has spare capacity, but never exceeds its limits.
  5. For multi-container Pods the scheduler sums the requests of all containers.
  • hello-pod only set limits, yet outputs show requests too: Kubernetes sets requests equal to limits when you omit requests.

Multi-container Pod example: init container

# initpod.yml
apiVersion: v1
kind: Pod
metadata:
  name: initpod
  labels:
    app: initializer
spec:
  initContainers:
  - name: init-ctr
    image: busybox:1.28.4
    command: ['sh', '-c', 'until nslookup k8sbook; do echo waiting for k8sbook service; sleep 1; done; echo Service found!']
  containers:
  - name: web-ctr
    image: nigelpoulton/web-app:1.0
    ports:
    - containerPort: 8080
  • spec.initContainers entries run to completion first; regular containers (spec.containers) wait.
  • init-ctr loops looking for a Service named k8sbook and exits when it exists.

Multi-container Pod example: sidecar

  • A sidecar augments the app (log scraping, remote repo sync), shares volumes, starts first, runs as long as the app and terminates after it.
  • Defined under spec.initContainers with restartPolicy: Always; app containers under spec.containers. The container-level restartPolicy overrides any Pod-level policy.
apiVersion: v1
kind: Pod
metadata:
  name: git-sync
  labels:
    app: sidecar
spec:
  initContainers:
  - name: ctr-sync            # sidecar
    restartPolicy: Always     # "Always" makes this a sidecar
    image: k8s.gcr.io/git-sync:v3.1.6
    volumeMounts:
    - name: html
      mountPath: /tmp/git
    env:
    - name: GIT_SYNC_REPO
      value: https://github.com...
    - name: GIT_SYNC_BRANCH
      value: master
    - name: GIT_SYNC_DEPTH
      value: "1"
    - name: GIT_SYNC_DEST
      value: "html"
  containers:
  - name: ctr-web             # app container
    image: nginx
    volumeMounts:
    - name: html
      mountPath: /usr/share/nginx/
  volumes:
  - name: html
    emptyDir: {}
  • ctr-sync watches a GitHub repo and syncs into the shared html volume; ctr-web serves a page from it.
  • Prerequisites: Kubernetes v1.29 or later and a (free) GitHub account.

Clean up

Deployed objects: Pods hello-pod, initpod, git-sync; Services k8sbook, svc-sidecar.

kubectl delete pod hello-pod initpod git-sync
kubectl delete svc k8sbook svc-sidecar

Or via the YAML files:

kubectl delete -f initsidecar.yml -f initpod.yml -f pod.yml -f initsvc.yml

You may also delete your GitHub fork.

Summary points

  • All apps (containers, serverless, Wasm, VMs) run inside Pods; usually containers.
  • Pods give a shared execution environment, advanced scheduling, probes and more.
  • Multi-container Pods share networking, volumes and memory.
  • Usually deploy via higher-level controllers (Deployments, Jobs, DaemonSets); Knative and KubeVirt extend the API for serverless and VMs.
  • Define Pods declaratively and post with kubectl apply.
Terms to carry forward
  • Pod: atomic unit of scheduling; shared execution environment.
  • Static Pod: Pod deployed directly, managed only by its node's kubelet.
  • restartPolicy: Always, OnFailure, Never; restarts containers, not Pods.
  • Pod network / CNI: flat overlay network for all Pods via a plugin.
  • Init container: runs once to completion before app containers.
  • Sidecar: init container with restartPolicy: Always.
  • Requests / limits: scheduling minimum / enforced maximum.
  • nodeSelector, affinity, topology spread constraints: placement controls.
  • VMI, Knative, KubeVirt: VM and serverless support.
  • spec vs status: desired vs observed state.
