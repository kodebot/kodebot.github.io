The Kubernetes Book 6: Kubernetes Deployments

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 6. Previous: The Kubernetes Book 5: Virtual Clusters with Namespaces. Next: The Kubernetes Book 7: Kubernetes Services.

Takeaways
  • A Deployment wraps a Pod template and adds self-healing, scaling, rolling updates and versioned rollbacks to stateless apps.
  • Under the hood a ReplicaSet provides self-healing and scaling; you manage everything through the Deployment, never the ReplicaSet or Pods.
  • Everything is reconciliation: a controller compares observed state with desired state and fixes the difference.
  • A rollout creates a new ReplicaSet, scaling it up while the old one scales down; old ReplicaSets are kept (up to revisionHistoryLimit) so rollback is just the reverse.
  • Prefer declarative changes: scaling with kubectl scale leaves your YAML out of sync.

6.1 Deployment theory

  • Deployments are the most popular way to run stateless apps, adding self-healing, scaling, rollouts and rollbacks.
  • Example flow: write the app, containerise it, define a Pod, wrap the Pod in a Deployment, post it; the Deployment controller deploys the Pod.
    • Pod fails: replaced by a new one.
    • Demand rises: more identical Pods.
    • App updated: old Pods deleted, new ones created.
  • A shopping cart service gets its own Pod and its own Deployment, so two microservices means two Deployments.
  • Figure 6.1: web Deployment manages four identical web Pods; cart Deployment manages two cart Pods.
  • Standard Kubernetes architecture: a resource defines objects, a controller manages them.
    • The Deployment resource lives in the apps/v1 API and defines the attributes.
    • The Deployment controller is a control plane service reconciling observed with desired state.

Deployments and Pods

  • Every Deployment manages one or more identical Pods, defined in an embedded Pod template.
  • Figure 6.2: YAML requesting four replicas; raising to six adds two identical Pods.

Deployments and ReplicaSets

  • Behind the scenes a ReplicaSet provides self-healing and scaling.
  • Posting one Deployment YAML creates a Deployment, a ReplicaSet and the identical Pods (Figure 6.3, where rs is ReplicaSet)
    • The Pods are managed by the ReplicaSet, which is managed by the Deployment.

A quick word on scaling

Manual scaling is possible, but Kubernetes also has autoscalers:

Autoscaler What it does Notes
Horizontal Pod Autoscaler (HPA) Adds and removes Pods to meet demand Installed on most clusters; widely used
Cluster Autoscaler (CA) Adds and removes cluster nodes so all scheduled Pods fit Installed by default; widely used
Vertical Pod Autoscaler (VPA) Raises or lowers CPU and memory of running Pods Not installed by default; known limitations; replaces the Pod on every resize (disruptive, may land on another node); in-place updates are early alpha
  • Community projects such as karmada scale apps across multiple clusters.
  • HPA + CA example:
    1. An HPA keeps an app between 2 and 10 Pods.
    2. Demand rises, so the HPA asks for 4 Pods, then 2 more.
    3. The scheduler finds no node with room and marks the 2 new Pods pending.
    4. The CA notices and adds a node; the scheduler places the pending Pods there.
    5. Scaling down works in reverse: fewer Pods may make the CA remove a node, and Kubernetes evicts that node's Pods and replaces them on surviving nodes.
  • Multi-dimensional autoscaling means combining methods (Pods and nodes, horizontal and vertical).

It's all about the state

Three concepts:

  • Desired state: what you want.
  • Observed state (actual or current state): what you have.
  • Reconciliation: a controller brings observed into line with desired.

The declarative model states the desired outcome and leaves the how to Kubernetes.

Declarative vs imperative

Model Analogy Real example
Declarative "Give me a chocolate cake to feed ten people." YAML asking for five front-end Pods on port 80 and two back-end Pods on port 27017
Imperative Drive to the store, buy ingredients, drive home, preheat, mix, bake 30 or 40 minutes depending on oven, cool, frost Long command lists with no desired state
  • Imperative problems: endless variations (commands to start containerd containers differ from CRI-O), more work, more errors, and no self-healing because no desired state is declared.
  • Kubernetes supports both and strongly prefers declarative.
  • containerd and CRI-O are runtimes on worker nodes doing low-level work like starting and stopping containers.

Controllers and reconciliation

  • ReplicaSets run as a background reconciliation loop: too few Pods, add; too many, terminate.
  • Desired state ten, observed eight: the ReplicaSet controller creates two, whether the cause is failures or an autoscaler.
  • The same mechanism gives self-healing, scaling, rollouts and rollbacks.

Rolling updates with Deployments

Zero-downtime rollouts work best if apps are:

  • loosely coupled via APIs, so any microservice can be patched without affecting others
  • backward and forward compatible, so you can update without caring which client versions consume you

Analogy: a car exposes a standard "API" (steering wheel, pedals). Re-map the engine or change the exhaust and the driver need not learn anything new.

Rollout with five stateless replicas: create one new-version replica, terminate one old, giving 4 old and 1 new; repeat until all five are new. Multiple replicas stay up, so clients see no downtime.

Mechanics:

  1. Each microservice is a container, wrapped in a Pod, wrapped in a Deployment.
  2. A Deployment describes: replica count, container images, network ports and how to do rolling updates.
  3. You post the YAML; the ReplicaSet controller schedules the right number of Pods and keeps watching. The Deployment sits above the ReplicaSet, governing it and adding rollouts and rollbacks.
  4. To ship a vulnerability fix, edit the same Deployment YAML (new Pod spec) and re-post. Desired state now says five new Pods; observed is five old.
  5. The Deployment controller creates a new ReplicaSet (same Pod count, new version) and incrementally scales it up while scaling the old one down.
  6. Keep the manifest in version control.

Figure 6.4: after one update, the first ReplicaSet manages no Pods and the second manages three live Pods.

Rollbacks

  • Old ReplicaSets wind down to zero Pods but keep their configuration, so rollback is the reverse of rollout: wind the old ReplicaSet up while the current one winds down (Figure 6.5).
  • You can also insert delays, control pace and cadence, and probe the health of updated replicas.

6.2 Create a Deployment

Clone the repo, switch to branch 2025 and run from the deployments folder:

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025
cd deployments

# deploy.yml
kind: Deployment
apiVersion: apps/v1
metadata:
  name: hello-deploy         # Deployment name (must be valid DNS name)
spec:
  replicas: 10               # number of Pod replicas to deploy and manage
  selector:
    matchLabels:
      app: hello-world
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 300
  minReadySeconds: 10
  strategy:                  # rolling update settings
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  template:                  # below here is the Pod template
    metadata:
      labels:
        app: hello-world
    spec:
      containers:
      - name: hello-pod
        image: nigelpoulton/k8sbook:1.0
        ports:
        - containerPort: 8080
Field Meaning
apiVersion: apps/v1, kind Create a Deployment from the apps/v1 resource
metadata.name hello-deploy; use valid DNS names (alphanumerics, dot, dash)
spec.replicas Ten Pod replicas of the template
spec.selector Labels the Deployment and ReplicaSet controllers use to find the Pods they manage; must match spec.template.metadata.labels (both app=hello-world)
spec.revisionHistoryLimit Keep the previous five ReplicaSets for rollback; more options but too many can bloat the object on large busy clusters
spec.progressDeadlineSeconds Each new replica gets its own five-minute window before it is reported stalled
spec.strategy How rollouts work (explained later)
spec.template The Pod this Deployment manages 
kubectl apply -f deploy.yml

deployment.apps/hello-deploy created
  • The configuration is persisted in the cluster store as a record of intent, ten replicas are scheduled, and the Deployment and ReplicaSet controllers keep watching
    • kubectl sends your kubeconfig credentials with every command.

Accessing the app

You need a Service to reach the Pods (chapter 7). lb.yml:

apiVersion: v1
kind: Service
metadata:
  name: lb-svc
  labels:
    app: hello-world
spec:
  type: LoadBalancer
  ports:
  - port: 8080
    protocol: TCP
  selector:
    app: hello-world       # send traffic to Pods with this label

$ kubectl apply -f lb.yml
service/lb-svc created

$ kubectl get svc lb-svc
NAME     TYPE           CLUSTER-IP       EXTERNAL-IP   PORT(S)
lb-svc   LoadBalancer   10.100.247.251   localhost     8080:31086/TCP
  • Browse to the EXTERNAL-IP on port 8080: localhost:8080 on local Docker Desktop (some show a wrong 172 address; use localhost), or the public IP or DNS name in the cloud.

6.3 Manually scale the app

Two ways: imperative (kubectl scale) or declarative (edit YAML, re-post). Kubernetes prefers declarative.

$ kubectl scale deploy hello-deploy --replicas 5
deployment.apps/hello-deploy scaled

$ kubectl get deploy hello-deploy
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   5/5     5            5           29m

The catch: the cluster now has five replicas but your YAML still says ten. Later, updating the image in that YAML and re-posting also resets replicas to 10, maybe unwanted. Keep manifests in sync with the live environment, ideally by making all changes declaratively.

Re-post to restore ten:

$ kubectl apply -f deploy.yml
deployment.apps/hello-deploy configured

$ kubectl get deploy hello-deploy
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   10/10   10           10          38m

Scaling is almost instant; rolling updates are not.

6.4 Perform a rolling update

  • Rollout, release, zero-downtime update and rolling update all mean the same here.
  • The new version is nigelpoulton/k8sbook:2.0 on Docker Hub; the book ignores CI/CD and version control to keep the focus.
  • All updates are replacement operations: Pods are immutable, so updating one means deleting and replacing it.

Edit deploy.yml and change the image to 2.0:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-deploy
spec:
  replicas: 10
  # <Snip>
  template:
    # <Snip>
    spec:
      containers:
      - name: hello-pod
        image: nigelpoulton/k8sbook:2.0    # update this line to 2.0
        ports:
        - containerPort: 8080

Settings that govern the rollout:

revisionHistoryLimit: 5          # keep the config from the five previous versions
progressDeadlineSeconds: 300     # give each new replica five minutes to start
minReadySeconds: 10              # wait 10 seconds after the previous replica started
strategy:
  type: RollingUpdate            # incrementally replace replicas
  rollingUpdate:
    maxUnavailable: 1            # can take one replica away during the update
    maxSurge: 1                  # can add one extra replica during the update
  • minReadySeconds throttles the rollout: longer waits catch problems before all replicas are replaced with broken ones; in the real world set it large enough to trap common failures.
  • With desired state 10: maxSurge: 1 allows up to 11, maxUnavailable: 1 allows down to 9, so Pods are replaced two at a time.
  • Labels tell Kubernetes which Pods to replace: the Deployment selector (app=hello-world) matches the template's Pod labels:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-deploy
spec:
  selector:              # the Deployment will manage all
    matchLabels:         # replicas on the cluster with
      app: hello-world   # this label
  # <Snip>
  template:
    metadata:
      labels:
        app: hello-world   # matches the label selector above
  • The selector and labels are immutable after creation.
$ kubectl apply -f deploy.yml
deployment.apps/hello-deploy configured

$ kubectl rollout status deployment hello-deploy
Waiting for deployment "hello-deploy" rollout... 4 out of 10 new replicas...
Waiting for deployment "hello-deploy" rollout... 4 out of 10 new replicas...
Waiting for deployment "hello-deploy" rollout... 6 out of 10 new replicas...
^C
  • Two Pods at a time with a 10-second wait: about a minute or two.
  • Mid-rollout, kubectl get deploy can show 6 updated and 9 available (one fewer than 10 because maxUnavailable=1):
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   9/10    6            9           63m

Pausing and resuming rollouts

$ kubectl rollout pause deploy hello-deploy
deployment.apps/hello-deploy paused

$ kubectl describe deploy hello-deploy
Name:         hello-deploy
Namespace:    default
Annotations:  deployment.kubernetes.io/revision: 2
Selector:     app=hello-world
Replicas:     10 desired | 6 updated | 11 total | 9 available | 2 unavailable
StrategyType: RollingUpdate
MinReadySeconds: 10
RollingUpdateStrategy: 1 max unavailable, 1 max surge
<Snip>
Conditions:
  Type          Status  Reason
  ----          ------  ------
  Available     True    MinimumReplicasAvailable
  Progressing   Unknown DeploymentPaused
OldReplicaSets:  hello-deploy-54f5d46964 (3/3 replicas created)
NewReplicaSet:   hello-deploy-5f84c5b7b7 (6/6 replicas created)
  • Revision 2 means this is the second release (revision 1 was the initial rollout); Progressing is paused; the old ReplicaSet manages 3 Pods and the new one 6.
  • A scale-up during a rollout is balanced across both ReplicaSets: scaling to 20 by adding 10 gives about 3 new replicas to the old ReplicaSet and about 6 to the new one.
$ kubectl rollout resume deploy hello-deploy
deployment.apps/hello-deploy resumed

$ kubectl get deploy hello-deploy
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   10/10   10           10          71m

Refresh the browser to see the new version (it now says "WebAssembly is coming!" where 1.0 said "K8s rocks!"; the author may change it).

6.5 Perform a rollback

kubectl rollout history deployment hello-deploy

deployment.apps/hello-deploy
REVISION   CHANGE-CAUSE
1          <none>
2          <none>
  • Revision 1: initial release (1.0 image). Revision 2: the rollout to 2.0.
kubectl get rs

NAME                      DESIRED   CURRENT   READY   AGE
hello-deploy-5f84c5b7b7   10        10        10      27m
hello-deploy-54f5d46964   0         0         0       93m

kubectl describe rs on the old ReplicaSet still shows Image: nigelpoulton/k8sbook:1.0, so flipping back replaces all Pods with 1.0 Pods. (Rollbacks are updates: terminate Pods with the current image and replace them with Pods using another image, in this case older.)

kubectl rollout undo deployment hello-deploy --to-revision=1

deployment.apps "hello-deploy" rolled back
  • This is imperative and not recommended, but convenient for quick rollbacks; update your source YAML afterwards.
  • It is not instant: same rules as a rollout, two Pods at a time with a 10-second wait.
$ kubectl get deploy hello-deploy
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   9/10    6            9           96m

Rollouts and labels

  • Deployments and ReplicaSets use labels and selectors to decide which Pods they own.
  • Older Kubernetes let a Deployment seize static Pods whose labels matched
    • Example: five static Pods labelled app=front-end plus a Deployment asking for ten with that label would seize the five and create only five new ones, even if the static Pods ran a different app.
  • Modern Kubernetes adds a system-generated pod-template-hash label to Pods created by a Deployment (ReplicaSet), preventing that.
  • The hash connects Deployment to ReplicaSet to Pods:
$ kubectl describe deploy hello-deploy
Name:           hello-deploy
<Snip>
NewReplicaSet:  hello-deploy-54f5d46964

$ kubectl describe rs hello-deploy-54f5d46964
Name:      hello-deploy-54f5d46964
<Snip>
Selector:  app=hello-world,pod-template-hash=54f5d46964

$ kubectl get pods --show-labels
NAME                        READY   STATUS    LABELS
hello-deploy-54f5d46964..   1/1     Running   app=hello-world,pod-template-hash=54f5d46964
<Snip>
  • ReplicaSet selectors include pod-template-hash; Deployment selectors do not, which is fine since ReplicaSets manage the Pods. Do not modify this label.

6.6 Clean up

kubectl delete -f deploy.yml
kubectl delete -f lb.yml

Summary points

  • Deployments manage stateless apps and add self-healing, scaling, rolling updates and rollbacks; they are apps/v1 objects with a reconciliation-loop controller; use them declaratively.
  • ReplicaSets create, terminate and count replicas; configure them only through the Deployment.
  • Scale manually by editing YAML and re-posting, or let autoscalers react to demand.
  • Rolling updates delete old Pods and replace them with new ones in a controlled way.
Terms to carry forward
  • Deployment / ReplicaSet / Pod template: wrapper, replica manager, embedded Pod definition.
  • HPA, VPA, CA: autoscale Pods horizontally, Pod resources, and nodes.
  • Declarative vs imperative: desired outcome vs command lists.
  • maxSurge / maxUnavailable / minReadySeconds / progressDeadlineSeconds / revisionHistoryLimit: rollout controls.
  • pod-template-hash: label tying Pods to a ReplicaSet, hash of the Pod template.
  • Rollout / rollback: scale one ReplicaSet up while the other goes down.
  • Multi-dimensional autoscaling: combining scaling methods.
