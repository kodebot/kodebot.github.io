The Kubernetes Book 8: Ingress

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 8. Previous: The Kubernetes Book 7: Kubernetes Services. Next: The Kubernetes Book 9: Wasm on Kubernetes.

Takeaways
  • Ingress exposes many web apps through one cloud load balancer, using host-based and path-based routing at layer 7.
  • Without it, every internet-facing app needs its own LoadBalancer Service, so 25 apps need 25 paid cloud load balancers (and your cloud may cap the number).
  • Ingress needs a resource (routing rules, networking.k8s.io/v1) and a controller (implements them). Kubernetes has no built-in controller; you install one (the book uses NGINX).
  • Ingress classes let several controllers coexist; each Ingress names its class.
  • Ingress only supports HTTP and HTTPS, and overlaps with service meshes: with a mesh you may not need Ingress.

Conventions: LoadBalancer is a Service of type=LoadBalancer; load balancer is the cloud's internet-facing load balancer. Creating a LoadBalancer Service makes Kubernetes ask the cloud for a load balancer. Ingress went GA in Kubernetes 1.19 after being beta for over 15 releases; during its 3+ years in alpha and beta, service meshes grew popular.

8.1 Setting the scene for Ingress

  • NodePort Services use only high ports and clients must track node IPs.
  • LoadBalancer Services fix that but map one Service to one cloud load balancer: 25 apps, 25 load balancers, which cost money and may hit cloud limits.
  • Ingress creates a single load balancer on port 80 or 443 and uses host-based and path-based routing to reach different Services.

8.2 Ingress architecture

  • Defined in the networking.k8s.io/v1 API sub-group, with the usual two parts:
    • resource: defines the routing rules
    • controller: implements them
  • Unlike Deployments, ReplicaSets or Services, there is no built-in Ingress controller; install one (some clouds offer one at cluster build time).
  • Ingress works at layer 7 (application layer) of the OSI model, so it can read HTTP headers and route on hostnames and paths.

[!note] OSI model (as the book explains it) The industry reference model for TCP/IP networking, seven layers. Lowest layers deal with signalling and electronics, middle layers with reliability (acknowledgements, retries), higher layers with services like HTTP.

Host-based Path-based Backend Service
shield.mcu.com mcu.com/shield shield
hydra.mcu.com mcu.com/hydra hydra

Figure 8.1: DNS maps both hostnames to the same load balancer IP; the Ingress controller reads the hostname in the HTTP headers and routes shield.mcu.com to the shield ClusterIP Service and hydra.mcu.com to hydra. Path-based works the same way.

Configure host-based and path-based routing

Two apps and one Ingress route through a single load balancer (a cloud one, or localhost on some local clusters). Steps:

  1. App shield fronted by ClusterIP Service svc-shield.
  2. App hydra fronted by ClusterIP Service svc-hydra.
  3. One Ingress with four rules:
    • host shield.mcu.com to svc-shield
    • host hydra.mcu.com to svc-hydra
    • path mcu.com/shield to svc-shield
    • path mcu.com/hydra to svc-hydra
  4. DNS so shield.mcu.com, hydra.mcu.com and mcu.com point to the load balancer.

Traffic to shield (Figure 8.2):

  1. Client sends to shield.mcu.com or mcu.com/shield.
  2. DNS sends it to the cloud load balancer.
  3. The Ingress controller reads the hostname or path from the HTTP headers.
  4. The Ingress rule routes it to the svc-shield ClusterIP Service.
  5. That Service sends it to a shield Pod.

Deploy the sample environment

app.yml creates shield (port 8080, behind svc-shield) and hydra (port 8080, behind svc-hydra):

$ kubectl apply -f app.yml
service/svc-shield created
service/svc-hydra created
pod/shield created
pod/hydra created

Create the Ingress object

ig-all.yml defines Ingress mcu-all with four rules (the book prints line numbers; they are removed here):

# ig-all.yml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mcu-all
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: shield.mcu.com        # host rule block for shield app
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: svc-shield
            port:
              number: 8080
  - host: hydra.mcu.com         # host rule block for hydra app
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: svc-hydra
            port:
              number: 8080
  - host: mcu.com
    http:
      paths:
      - path: /shield           # path rule block for shield app
        pathType: Prefix
        backend:
          service:
            name: svc-shield
            port:
              number: 8080
      - path: /hydra            # path rule block for hydra app
        pathType: Prefix
        backend:
          service:
            name: svc-hydra
            port:
              number: 8080

(The book's listing labels the /hydra block "for shield app" and refers to lines up to 49 although the listing ends at line 46.)

Part Meaning
apiVersion, kind An Ingress from the networking.k8s.io/v1 schema
metadata.name mcu-all
rewrite-target: / annotation NGINX-specific, best-effort: rewrites incoming paths to /, so mcu.com/shield arrives at the app as mcu.com/. Comment it out for other controllers.
spec.ingressClassName: nginx Managed by the NGINX controller; change or comment out for another controller
Four rules Two host rules (shield, hydra) and two path rules under host mcu.com

The two rule styles, in isolation. A host-based rule (traffic arriving via shield.mcu.com at the root path goes to svc-shield on 8080):

# host-based rule (excerpt)
- host: shield.mcu.com        # traffic arriving via this hostname
  http:
    paths:
    - path: /                 # arriving at root (no subpath)
      pathType: Prefix
      backend:                # send to an existing "backend" ClusterIP Service
        service:
          name: svc-shield    # called "svc-shield"
          port:
            number: 8080      # listening on port 8080

A path-based rule (traffic via mcu.com/shield goes to the same Service and port):

# path-based rule (excerpt)
- host: mcu.com               # traffic arriving via this hostname
  http:
    paths:
    - path: /shield           # arriving on this subpath
      pathType: Prefix
      backend:
        service:
          name: svc-shield
          port:
            number: 8080

$ kubectl apply -f ig-all.yml
ingress.networking.k8s.io/mcu-all created

Inspecting Ingress objects

On a cloud, ADDRESS can take a minute while the load balancer is provisioned.

$ kubectl get ing
NAME      CLASS   HOSTS                                ADDRESS         PORTS
mcu-all   nginx   shield.mcu.com,hydra.mcu.com,mcu.com 212.2.246.150   80
Column Meaning
CLASS Which Ingress class handles the rules (may show <None> with a single controller and no classes)
HOSTS Hostnames the Ingress handles
ADDRESS Load balancer endpoint: public IP or DNS name in the cloud, probably localhost locally
PORTS 80 or 443

Ingress only supports HTTP and HTTPS.

$ kubectl describe ing mcu-all
Name:             mcu-all
Namespace:        default
Address:          212.2.246.150
Ingress Class:    nginx
Default backend:  <default>
Rules:
  Host            Path      Backends
  ----            ----      --------
  shield.mcu.com  /         svc-shield:8080 (10.36.1.5:8080)
  hydra.mcu.com   /         svc-hydra:8080 (10.36.0.7:8080)
  mcu.com         /shield   svc-shield:8080 (10.36.1.5:8080)
                  /hydra    svc-hydra:8080 (10.36.0.7:8080)
Annotations:      nginx.ingress.kubernetes.io/rewrite-target: /
Events:
  Type    Reason  Age                From                      Message
  ----    ------  ----               ----                      -------
  Normal  Sync    27s (x2 over 28s)  nginx-ingress-controller  Scheduled for sync
  • Address: the load balancer the Ingress created (localhost on local clusters).
  • Default backend: where traffic with no matching route goes; not every controller implements one.
  • Rules: host and path mappings to backends (usually ClusterIP Services).
  • Annotations: controller-specific features and cloud back-end integrations; this one rewrites all paths to /, best effort, and does not work with all apps.
  • The load balancer now exists and may be visible in your cloud console (Figure 8.3 shows it in Google Cloud on GKE).

You now have two apps with ClusterIP Services, a load balancer, and an Ingress (controller and resource). Only DNS remains.

Configure DNS name resolution

  • Real world: configure internal or internet DNS to point the hostnames at the Ingress load balancer; how depends on your environment and DNS provider.
  • To follow along, edit your hosts file:
    • Mac and Linux: /etc/hosts (needs root)
    • Windows: C:\Windows\System32\drivers\etc\hosts (open Notepad as administrator; set the open dialog to All files)
  • Add three lines mapping the names to the IP from kubectl get ing mcu-all (use 127.0.0.1 if yours says localhost):
$ sudo vi /etc/hosts

# Host Database
<Snip>
212.2.246.150 shield.mcu.com
212.2.246.150 hydra.mcu.com
212.2.246.150 mcu.com

Save. Traffic to those names now goes to the Ingress load balancer.

Test the Ingress

Browse to shield.mcu.com, hydra.mcu.com and mcu.com.

  • Figure 8.4: traffic hits the auto-created load balancer on port 80 and the Ingress routes to the ClusterIP Service by hostname.
  • Requests to mcu.com go to the default backend, because no rule covers the bare host
    • What you see depends on the controller, which may not implement a default backend
    • GKE's built-in Ingress returns "response 404 (backend NotFound), service rules for [ / ] non-existent".
  • Now try mcu.com/shield and mcu.com/hydra: path routing uses the rewrite-target annotation, but the image does not display, because path rewrites do not work for all apps.

Result: two apps behind two ClusterIP Services, published through one load balancer managed by Ingress.

Summary points

  • Ingress exposes multiple apps (ClusterIP Services) through a single cloud load balancer; stable API object whose features overlap with service meshes.
  • Many clusters require installing an Ingress controller; some hosted services ship one.
  • Ingress objects are rule lists for host-based and path-based HTTP routing.
Terms to carry forward
  • Ingress resource / controller: rules / implementation (controller not built in).
  • Ingress class: maps Ingress objects to a controller.
  • Host-based / path-based routing: route on hostname / URL path.
  • Layer 7: application layer, HTTP-aware.
  • Default backend: handles unmatched hosts and paths.
  • rewrite-target: NGINX annotation, best-effort path rewriting.
  • LoadBalancer vs load balancer: Service type vs cloud device.
