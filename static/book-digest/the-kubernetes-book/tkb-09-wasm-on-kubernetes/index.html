The Kubernetes Book 9: Wasm on Kubernetes

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 9. Previous: The Kubernetes Book 8: Ingress. Next: The Kubernetes Book 10: Service Discovery Deep Dive.

Takeaways
  • The book frames Wasm as the third wave after VMs and containers: smaller, faster, more portable.
  • Wasm is a binary instruction set (like ARM or x86) that runs in a deny-by-default sandbox; WASI lets sandboxed apps reach external services.
  • On Kubernetes with containerd, you swap runc and its shim for a Wasm shim (built on runwasi); Kubernetes sees nothing below containerd.
  • To schedule Wasm Pods: install a shim on a node, label the node, create a RuntimeClass (nodeSelector + handler), and reference it from the Pod.
  • Wasm suits event handlers, fast startup, IoT, edge and plugins; Linux containers are still better for traditional cloud apps with heavy networking and I/O.

The chapter has three parts: a Wasm primer, how Wasm works on Kubernetes, and hands-on. The book notes that tools like SpinKube (from Fermyon) automate much of the manual work you do here; the manual route is for understanding.

Terminology: Wasm and WebAssembly mean the same thing; Wasm is a short form and not an acronym, so "Wasm", not "WASM". Wasm on Kubernetes is one case of "WebAssembly outside the browser, on the server, in the cloud, at the edge". Figure 9.1 shows the waves: VMs, containers, Wasm.

9.1 Wasm primer

  • WebAssembly appeared in 2017, first speeding up web apps
    • Eight years on (per the book) it is an official W3C standard, in all major browsers, and the go-to for high-performance, secure, portable web games and apps.
  • Cloud entrepreneurs saw it as a fit for cloud apps
    • The book reports a widely circulated tweet by Docker founder Solomon Hykes saying that had Wasm plus WASI existed in 2008, Docker would not have been needed, and that a standard system interface was the missing link (paraphrase; the tweet is not linked in the book)
    • He followed up expecting Linux and Wasm containers to run side by side with Docker working with both.
  • That future has arrived:
    • Docker supports Wasm, and Linux containers and Wasm containers can run side by side in the same Kubernetes Pod
    • But the standards and ecosystem are young, so Linux containers remain best for many use cases.

What Wasm is

  • A binary instruction set architecture (ISA) like ARM, x86, MIPS and RISC-V: languages compile to Wasm binaries that run on any system with a Wasm runtime.
  • Apps run in a deny-by-default sandbox: access to everything is denied unless explicitly allowed. Containers start with everything open.
  • WASI
    • (WebAssembly System Interface) lets sandboxed apps securely reach key-value stores, networks, the host environment and more. It is vital outside the browser
    • WASI Preview 2 (also written WASI 0.2 or wasip2) is out at the time of writing.

Security, portability, performance

Aspect Wasm Containers
Security Deny-by-default sandbox; runtime must explicitly allow outside access; sandbox battle-hardened for years in browsers Allow-by-default with broad access to a shared kernel; much community effort has made secure containers easier, but the model always poses challenges
Portability Build once as a Wasm binary, run on any host with a Wasm runtime, including exotic IoT and edge architectures Architecture-dependent: an ARM container cannot run on AMD, a Windows container cannot run on Linux; leads to image sprawl
Performance Start in about 10 ms or less, some in microseconds; enables true scale-to-zero and serverless VMs take minutes, containers seconds
  • The author's example of sprawl:
    • he keeps two images per app (Linux on ARM and AMD64) and sometimes forgets to rebuild one, breaking examples for some readers
    • The chapter's app was built on an ARM Mac and compiled to Wasm, so it runs on any cluster.
  • Wasm apps are typically much smaller than Linux containers, so they fit resource-constrained edge and IoT where containers cannot.

Quick recap: Wasm apps are smaller, faster, more portable and more secure than traditional containers, but it is early days.

  • Good choices now: event handlers, super-fast startup, IoT, edge, extensions and plugins.
  • At the time of writing, containers may be better for traditional cloud apps needing networking, heavy I/O and connections to other services.

9.2 Understanding Wasm on Kubernetes

This overview covers clusters using containerd (other ways exist).

  • Kubernetes is a high-level orchestrator
    • containerd does the low-level container work. Figure 9.2: containerd receives tasks and tells runc to build containers and start apps
    • runc then exits, leaving shim processes to maintain connections between running containers and containerd.
  • Everything below containerd is hidden from Kubernetes, so you can replace runc and the standard shim with a Wasm runtime and a Wasm shim. Figure 9.3 shows the same node with two extra Wasm workloads
    • there is still a single containerd and it is a fully supported setup.
  • A Wasm shim differs from a runc shim: it is a single binary with the shim code and the Wasm runtime embedded (Figure 9.4).
    • The shim code that talks to containerd is runwasi.
    • Each shim embeds a particular runtime. The Spin shim embeds runwasi plus the Spin runtime; the Slight shim embeds runwasi plus the Slight runtime.
    • The runtime creates the Wasm host and runs the app; runwasi translates and interfaces with containerd.
  • Shim naming (mandated by containerd): prefix containerd-shim-, then the runtime name, then the version. Example: containerd-shim-spin-v2.
  • Mixed nodes need help scheduling (Figure 9.5: one node with the WasmEdge shim, one with the Spin shim). Use node labels and RuntimeClass objects: Node 2 has label spin=yes
    • a RuntimeClass selects that label and names the runtime in its handler, so Pods referencing it land on Node 2 and use Spin.

Deploy workflow (containerd):

  1. Write the app and compile it as a Wasm binary.
  2. Package the binary as an OCI image and store it in an OCI registry.
  3. Install the Wasm shim on at least one node and label the node.
  4. Create a RuntimeClass specifying the node labels and the shim.
  5. Create a Pod for the Wasm app (image from step 2).
  6. Reference the RuntimeClass in the Pod.
  7. Deploy the Pod.

On deploy: Kubernetes schedules the Pod to a node matching the RuntimeClass node selector; the kubelet passes the work to containerd with the shim info; containerd starts the app with that shim.

9.3 Hands-on with Wasm on Kubernetes

Clone the repo, switch to branch 2025 and use the wasm folder:

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025
cd TKB/wasm

Steps:

  1. Install and test prerequisites.
  2. Write and compile the Wasm app.
  3. Build an OCI image and push it to a registry.
  4. Build and configure a multi-node Kubernetes cluster for Wasm.
  5. Deploy the app.

Prerequisites

Tool Version
Docker Desktop with Wasm support enabled up to date
Rust (with the wasm32-wasip1 target) 1.82 or later
Spin 3.1.2 or later
k3d 5.8.1 or later

Install Rust from https://www.rust-lang.org/tools/install, then add the target:

$ rustup target add wasm32-wasip1
info: downloading component 'rust-std' for 'wasm32-wasip1'
info: installing component 'rust-std' for 'wasm32-wasip1'

Spin is a popular Wasm framework with a runtime and tooling; search for "install Fermyon Spin" and follow your platform's steps:

$ spin --version
spin 3.1.2 (3d37bd8 2025-01-13)

Write and compile the Wasm app

From the wasm folder, scaffold an app answering web requests on the /tkb path (TKB for The Kubernetes Book):

$ spin new tkb-wasm -t http-rust
Description []: My first Wasm app
HTTP path [/...]: /tkb

$ cd tkb-wasm
$ tree
├── Cargo.toml
├── spin.toml
└── src
    └── lib.rs

2 directories, 3 files

(Use ls -R if you lack tree.) Two files matter: spin.toml (how Spin builds and runs the app) and src/lib.rs (the source). Change only the response body text to The Kubernetes Book loves Wasm!:

// src/lib.rs
use spin_sdk::http::{IntoResponse, Request, Response};
// <Snip>
fn handle_tkb_wasm(req: Request) -> anyhow::Result<impl IntoResponse> {
    println!("Handling request to {:?}", req.header("spin-full-url"));
    Ok(Response::builder()
        .status(200)
        .header("content-type", "text/plain")
        .body("The Kubernetes Book loves Wasm!")   // only change this line
        .build())
}

spin build compiles to Wasm; behind the scenes it runs a more complex cargo build:

$ spin build
Building component tkb-wasm with `cargo build --target wasm32-wasip1 --release`
Updating crates.io index
<Snip>
Finished building all Spin components

The binary is target/wasm32-wasip1/release/tkb_wasm.wasm; it runs on any machine with the Spin Wasm runtime.

Build an OCI image and push it

Create a Dockerfile in tkb-wasm (keep the periods at the end of the last two lines):

# Dockerfile
FROM scratch
COPY /target/wasm32-wasip1/release/tkb_wasm.wasm .
COPY spin.toml .
  • FROM scratch packages the app in an empty image instead of a Linux base image, keeping it tiny
    • Wasm apps do not need a Linux filesystem, but Docker and Kubernetes tooling expect basic container constructs, so the scratch image satisfies them
    • At runtime the app and Wasm runtime run in a minimal container that is basically namespaces and cgroups (no filesystem etc.).
  • The first COPY puts the Wasm binary in the container's root; the second copies spin.toml.
  • spin.toml tells Spin where the app is and how to run it
    • It currently expects the binary under target/wasm32-wasip1/release, but the image places it in /, so strip the leading path from the source field:
# spin.toml
# <Snip>
[component.tkb-wasm]
source = "tkb_wasm.wasm"      # remove the leading path from this line
# <Snip>

(The annotation is only to show which line changes; leave it out of the file.)

You now have a Wasm binary, a spin.toml and a Dockerfile. Build the image (use your own Docker Hub username if you will push):

docker build \
  --platform wasi/wasm \
  --provenance=false \
  -t nigelpoulton/k8sbook:wasm-0.2 .

--platform wasi/wasm sets the image's OS and architecture, which docker run and containerd read to create the container.

$ docker images
REPOSITORY             TAG       IMAGE ID       CREATED          SIZE
nigelpoulton/k8sbook   wasm-0.2  a003c43b1308   7 seconds ago    104kB

The image is about 104 kB; a similar hello-world Linux container is usually several megabytes. docker inspect shows the OS and architecture. Pushing is optional, since the book provides a pre-created image; if you push, you need a registry account and must use your own tag.

$ docker push nigelpoulton/k8sbook:wasm-0.2
The push refers to repository [docker.io/nigelpoulton/k8sbook]
4073bf46d785: Pushed
7893057c9bbc: Pushed
wasm-0.2: digest: sha256:a003c43b1308dce78c8654b7561d9a...779c5c9f9b51979c9925f6f size: 695

Build and configure a Wasm-capable k3d cluster

The cluster uses a custom k3d image with pre-installed Wasm shims, so build exactly this one to follow along. Steps:

  1. Install k3d.
  2. Build a 3-node cluster (one control plane, two workers).
  3. Inspect the Wasm configuration on a worker.
  4. Label one worker as Wasm-capable.
  5. Create a RuntimeClass.

Install k3d from k3d.io and check k3d --version. Then create the cluster (this also switches your kubectl context):

k3d cluster create wasm \
  --image ghcr.io/deislabs/containerd-wasm-shims/examples/k3d:v0.11.1 \
  -p "5005:80@loadbalancer" --agents 2
Part Meaning
cluster create wasm New cluster named wasm
--image Special image with containerd Wasm shims
-p "5005:80@loadbalancer" Load balancer to an Ingress in the cluster, mapping host port 5005 to Ingress port 80
--agents 2 Two worker nodes 
$ kubectl get nodes
NAME                STATUS   ROLES           AGE   VERSION
k3d-wasm-server-0   Ready    control-plane   17s   v1.27.8+k3s2
k3d-wasm-agent-1    Ready    <none>          15s   v1.27.8+k3s2
k3d-wasm-agent-0    Ready    <none>          15s   v1.27.8+k3s2

A node needs both containerd running and a containerd Wasm shim installed and registered. Exec onto a worker and check:

$ docker exec -it k3d-wasm-agent-1 ash
$ ps | grep containerd
PID   USER   COMMAND
98    0      containerd
<Snip>

Shims live in /bin and follow the naming convention. containerd-shim-runc-v2 is the default for Linux containers; the other four are Wasm shims, and the Spin one is containerd-shim-spin-v2:

$ ls /bin | grep shim
containerd-shim-lunatic-v1
containerd-shim-runc-v2
containerd-shim-slight-v1
containerd-shim-spin-v2
containerd-shim-wws-v1

A shim file is not enough: it must be registered in containerd's config. k3d keeps it at /var/lib/rancher/k3s/agent/etc/containerd/config.toml rather than /etc/containerd:

# /var/lib/rancher/k3s/agent/etc/containerd/config.toml (Wasm runtimes only)
[plugins.cri.containerd.runtimes.spin]
runtime_type = "io.containerd.spin.v2"

[plugins.cri.containerd.runtimes.slight]
runtime_type = "io.containerd.slight.v1"

[plugins.cri.containerd.runtimes.wws]
runtime_type = "io.containerd.wws.v1"

[plugins.cri.containerd.runtimes.lunatic]
runtime_type = "io.containerd.lunatic.v1"

Verify the active config for Spin:

$ containerd --config \
    /var/lib/rancher/k3s/agent/etc/containerd/config.toml \
    config dump | grep spin
<Snip>
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.spin]
  runtime_type = "io.containerd.spin.v2"
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.spin.options]

containerd runs and the Spin shim is present and registered, so the node can run Spin apps.

All nodes here run the same shims, so nothing more is strictly needed. Real environments are heterogeneous, so the book labels agent-1 with wasm=yes and creates a RuntimeClass targeting that label. Type exit to leave the exec session first:

# exit
$ kubectl label nodes k3d-wasm-agent-1 wasm=yes
node/k3d-wasm-agent-1 labeled

$ kubectl get nodes --show-labels | grep wasm=yes
NAME               STATUS   ROLES    VERSION        LABELS
k3d-wasm-agent-0   Ready    <none>   v1.27.8+k3s2   beta.kubernetes...,wasm=yes

(The output the book prints names agent-0 although the label was applied to agent-1; shown as printed.) Create the RuntimeClass:

$ kubectl apply -f rc-spin.yml
runtimeclass.node.k8s.io/rc-spin created

$ kubectl get runtimeclass
NAME      HANDLER   AGE
rc-spin   spin      14s
  • scheduling.nodeSelector limits Pods using this RuntimeClass to nodes with wasm=yes.
  • handler tells containerd on the node to use the spin shim.

Deploy and test the app

app.yml has a Deployment, a Service and an Ingress; the Deployment's key line is runtimeClassName:

# app.yml (Deployment excerpt)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: wasm-spin
spec:
  replicas: 3
  # <Snip>
  template:
    metadata:
      labels:
        app: wasm
    # <Snip>
    spec:
      runtimeClassName: rc-spin          # referencing the RuntimeClass
      containers:
      - name: testwasm
        image: nigelpoulton/k8sbook:wasm-0.1   # pre-created image
        command: ["/"]
  • The reference ensures all three replicas go to a node matching the RuntimeClass nodeSelector: agent-1.
  • Not shown: the Ingress sends traffic on / to a ClusterIP Service which forwards to Pods labelled app=wasm on port 80 (Figure 9.6).
  • To use your own image, edit the image field.
$ kubectl apply -f app.yml
deployment.apps/wasm-spin created
service/svc-wasm created
ingress.networking.k8s.io/ing-wasm created

Clean up

Artifacts: the wasm k3d cluster, the Wasm image in a registry and locally, and the Spin app directory. Delete the whole cluster:

$ k3d cluster delete wasm

Or keep the cluster and delete only the resources:

$ kubectl delete -f app.yml
deployment.apps "wasm-spin" deleted
service "svc-wasm" deleted
ingress.networking.k8s.io "ing-wasm" deleted

$ kubectl delete runtimeclass rc-spin
runtimeclass.node.k8s.io "rc-spin" deleted

Delete the local image (substitute your image name; the book's command names the wasm-0.1 tag):

docker rmi nigelpoulton/k8sbook:wasm-0.1

Delete the tkb-wasm directory (check you pick the right one). Then restore your kubectl context (Docker Desktop: whale menu, Kubernetes context):

Summary points

  • Wasm is the third wave of cloud computing; Docker builds, runs and hosts Wasm apps, and containerd plus runwasi (and SpinKube) make them run on Kubernetes.
  • Wasm is a compilation target:
    • apps compile to tiny binaries that run anywhere with a Wasm runtime
    • smaller, faster, more portable and more secure than Linux containers, though not yet able to do everything they can.
  • Process: write, compile to Wasm, build an OCI image, push to an OCI registry, wrap in a Pod and run.
  • On containerd, install and register a Wasm shim on at least one worker, label it, and reference the label via a RuntimeClass.
  • Further reading suggested: the SpinKube project and the containerd shim lifecycle community proposal.
Terms to carry forward
  • Wasm / WebAssembly: binary ISA compilation target, runs in a deny-by-default sandbox.
  • WASI: system interface for sandboxed apps; Preview 2 (wasip2, 0.2).
  • Wasm runtime: executes Wasm binaries (Spin, Slight, WasmEdge...).
  • shim / runwasi / runc: containerd-facing processes; runwasi is the Wasm shim library.
  • containerd-shim-<runtime>-<version>: mandated shim naming.
  • RuntimeClass: handler plus scheduling.nodeSelector, picks shim and nodes.
  • FROM scratch: empty base image for Wasm OCI images.
  • SpinKube: automates Wasm on Kubernetes.
