The Kubernetes Book 10: Service Discovery Deep Dive

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 10. Previous: The Kubernetes Book 9: Wasm on Kubernetes. Next: The Kubernetes Book 11: Kubernetes Storage.

Takeaways
  • Apps need two things to call each other: the name of the other app's Service (the developer's job) and a way to turn it into an IP (Kubernetes' job).
  • The cluster DNS (CoreDNS, fronted by the kube-dns Service in kube-system) is the built-in service registry; it registers every new Service automatically.
  • Every container's /etc/resolv.conf points at the cluster DNS and lists search domains, so short names resolve in the local Namespace.
  • ClusterIPs live on a virtual service network with no routes; kube-proxy programs each node's kernel to redirect ClusterIP traffic to healthy Pod IPs.
  • Across Namespaces you must use the FQDN <service>.<namespace>.svc.cluster.local.

10.1 Setting the scene

  • Clusters run hundreds or thousands of microservices, most behind their own Service with a reliable name and IP
    • When one app talks to another it really talks to the other's Service
    • (Figure 10.1: app-a calls app-b through its Service.)
  • Two requirements for one app to call another:
    1. Know the name of the other app's Service: the developer's job.
    2. Convert the name to an IP: Kubernetes' job.
  • Figure 10.2 flow:
    1. The developer configures app-a to talk to app-b.
    2. app-a asks Kubernetes for app-b's IP.
    3. Kubernetes returns the IP.
    4. app-a sends requests to that IP.
  • Step 1 is the only manual one.

10.2 The service registry

  • A service registry maintains a list of Service names and their IPs.
  • Every cluster has a built-in cluster DNS as its registry: a Kubernetes-native app on the control plane, running as two or more Pods managed by a Deployment (usually coredns or kube-dns) and fronted by its own Service, always named kube-dns (Figure 10.3).

The Pods (normally the registry.k8s.io/coredns/coredns image; some clusters use another image and call Pods and Deployment kube-dns):

$ kubectl get pods -n kube-system -l k8s-app=kube-dns
NAME                       READY   STATUS    RESTARTS   AGE
coredns-76f75df574-d6nn5   1/1     Running   0          13d
coredns-76f75df574-n7qzk   1/1     Running   0          13d

The Deployment (keeps the right number of DNS Pods):

$ kubectl get deploy -n kube-system -l k8s-app=kube-dns
NAME      READY   UP-TO-DATE   AVAILABLE   AGE
coredns   2/2     2            2            13d

The Service (always kube-dns, but a different IP per cluster; Kubernetes configures every container to use this IP):

$ kubectl get svc -n kube-system -l k8s-app=kube-dns
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.96.0.10   <none>        53/UDP,53/TCP,9153/TCP   13d

10.3 Service registration

It is automatic. Three steps:

  1. Give the Service a name (developer).
  2. Assign the Service an IP (Kubernetes).
  3. Register the name and IP with the cluster DNS (Kubernetes).

Example: deploy a web app behind a Service called valkyrie-web. Kubernetes ensures the name is unique, assigns a ClusterIP and registers both with the cluster DNS.

  • It works because the cluster DNS watches the API server for new Services and registers each one. Your apps need no registration logic.

Figure 10.4 flow:

  1. You post a YAML with a Deployment and a Service; it is authenticated and authorised.
  2. Kubernetes allocates a ClusterIP and persists the config in the cluster store.
  3. The cluster DNS sees the new Service and registers A and SRV records.
  4. Associated EndpointSlices are created to hold healthy Pod IPs matching the label selector.
  5. kube-proxy on every node sees the new objects and creates local routing rules (IPVS) so requests to the ClusterIP reach Pods.

10.4 Service discovery

Apps use names but need IPs.

Example: apps enterprise and cerritos; Services ent and cer (Figure 10.5).

App Service name ClusterIP
Enterprise ent 192.168.201.240
Cerritos cer 192.168.200.217
  • The enterprise developers configure the app with the name cer. The container sends cer to the cluster DNS, gets the ClusterIP back, and sends the request to that IP.
  • Kubernetes makes this work by configuring each container's /etc/resolv.conf with the cluster DNS IP, plus search domains to append to unqualified names (short names like ent)
    • Appending turns ent into an FQDN such as ent.default.svc.cluster.local.
$ cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10          # ClusterIP of internal cluster DNS
options ndots:5

The nameserver matches the kube-dns Service:

$ kubectl get svc -n kube-system -l k8s-app=kube-dns
NAME       TYPE        CLUSTER-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.96.0.10   53/UDP,53/TCP,9153/TCP   13d

ClusterIP routing

  • ClusterIPs are on a special service network and there are no routes to it
    • Each container sends ClusterIP traffic to its default gateway (where a system sends traffic when it does not know where else to send it, hoping the next device does).
  • The gateway is the node, which has no route either, so it sends it to its own default gateway. That makes the node's kernel process the traffic.
  • Every node runs kube-proxy, a controller watching the API server for new Services and EndpointSlices
    • It creates kernel rules that intercept ClusterIP traffic and redirect it to individual Pod IPs.
  • So whenever a node's kernel handles traffic for a ClusterIP, it redirects it to a healthy Pod matching the Service's label selector.

Summary

  1. The app sends to cer.
  2. The container asks the cluster DNS (from /etc/resolv.conf) for the IP.
  3. The DNS returns the ClusterIP.
  4. No route exists, so the traffic goes to the container's default gateway, then the node, then the node's default gateway.
  5. The node's kernel redirects it to a Pod IP matching the selector.

10.5 Service discovery and Namespaces

  • Every object gets a name in the cluster address space, partitioned by Namespaces. The cluster domain is usually cluster.local, and names must be unique within it.
  • FQDN format: <object-name>.<namespace>.svc.cluster.local. Example: Service cer in default is cer.default.svc.cluster.local.
  • With Namespaces dev and prod:
    • dev: <service-name>.dev.svc.cluster.local
    • prod: <service-name>.prod.svc.cluster.local
  • Names must be unique within a Namespace, not across them, so both can have an identical cer Service (Figure 10.7), letting you run parallel dev and prod configs on one cluster.
  • Short names (ent, cer) reach Services in the local Namespace; you need FQDNs for remote Namespaces.

Service discovery example

sd-example.yml (folder service-discovery) deploys Figure 10.8: two Namespaces, two Deployments, two Services and a standalone jump Pod in dev only. The search domain includes dev.svc.cluster.local. Install curl and call the local Service:

<snip>

Short names resolve to the local Namespace; you need FQDNs across Namespaces. Type exit to leave.

10.6 Troubleshooting service discovery

The cluster DNS parts, all in kube-system with label k8s-app=kube-dns:

Component Detail
Pods Managed by the coredns Deployment
Service ClusterIP Service kube-dns, port 53 TCP/UDP
EndpointSlices Names prefixed kube-dns 
$ kubectl get deploy -n kube-system -l k8s-app=kube-dns
NAME      READY   UP-TO-DATE   AVAILABLE   AGE
coredns   2/2     2            2           14d

$ kubectl get pods -n kube-system -l k8s-app=kube-dns
NAME                       READY   STATUS    RESTARTS   AGE
coredns-76f75df574-6q7k7   1/1     Running   0          14d
coredns-76f75df574-krnr7   1/1     Running   0          14d

Logs from a healthy DNS Pod (use a Pod name from your cluster):

$ kubectl logs coredns-76f75df574-n7qzk -n kube-system
.:53
[INFO] plugin/reload: Running configuration SHA512 = 591cf328cccc12b...
CoreDNS-1.11.1
linux/arm64, go1.20.7, ae2bbc2

Check the Service and EndpointSlice. The kube-dns ClusterIP must match the nameserver in every container's /etc/resolv.conf, otherwise DNS requests go to the wrong place:

$ kubectl get svc kube-dns -n kube-system
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.96.0.10   <none>        53/UDP,53/TCP,9153/TCP   14d

$ kubectl get endpointslice -n kube-system -l k8s-app=kube-dns
NAME             ADDRESSTYPE   PORTS       ENDPOINTS                 AGE
kube-dns-jb72g   IPv4          9153,53,53  10.244.1.9,10.244.1.14    14d

Then deeper troubleshooting:

  • Start a Pod with networking tools (ping, traceroute, curl, dig, nslookup). A popular image: registry.k8s.io/e2e-test-images/jessie-dnsutils
    • browse the repo at explore.ggcr.dev for newer versions.
kubectl run -it dnsutils \
  --image registry.k8s.io/e2e-test-images/jessie-dnsutils:1.7
  • Test the cluster DNS by resolving the kubernetes Service (exists on every cluster, exposes the API server to Pods):
# nslookup kubernetes
Server:         10.96.0.10
Address:        10.96.0.10#53
Name:   kubernetes.default.svc.cluster.local
Address: 10.96.0.1

The first two lines show the cluster DNS IP; the last two show the FQDN and ClusterIP (verify with kubectl get svc kubernetes).

  • Errors like nslookup: can't resolve kubernetes mean DNS is not working. A possible fix: delete the coredns Pods so the Deployment recreates them (exit dnsutils first):
$ kubectl delete pod -n kube-system -l k8s-app=kube-dns
pod "coredns-76f75df574-d6nn5" deleted
pod "coredns-76f75df574-n7qzk" deleted

Re-run kubectl get pods -n kube-system -l k8s-app=kube-dns to see them restart, then test DNS again.

10.7 Clean up

kubectl delete pod dnsutils
kubectl delete -f sd-example.yml

Summary points

  • The cluster DNS is the service registry for registration and discovery
    • it watches the API server for new Services and registers their names and IPs. The kubelet configures every container to use it.
  • It resolves Service names to ClusterIPs:
    • stable virtual IPs on the service network, which has no routes
    • kube-proxy configures every node to redirect ClusterIP traffic to Pod IPs on the Pod network.
Terms to carry forward
  • Service registry / cluster DNS: CoreDNS Pods plus kube-dns Service in kube-system.
  • Service registration: automatic name and IP registration (A and SRV records).
  • /etc/resolv.conf, search domains, unqualified name, FQDN.
  • Service network / ClusterIP: virtual IPs with no routes.
  • kube-proxy: programs kernel rules (IPVS) to redirect to Pod IPs.
  • Cluster domain: cluster.local.
  • <service>.<namespace>.svc.cluster.local: FQDN format.
