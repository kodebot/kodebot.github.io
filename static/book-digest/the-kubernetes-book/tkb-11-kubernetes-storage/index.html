The Kubernetes Book 11: Kubernetes Storage

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 11. Previous: The Kubernetes Book 10: Service Discovery Deep Dive. Next: The Kubernetes Book 12: ConfigMaps and Secrets.

Takeaways
  • Kubernetes connects to external storage (block, file, object; cloud or on-premises) through CSI plugins and exposes it with three API objects: PV, PVC, StorageClass.
  • PVs map to external volumes, PVCs grant Pods access to PVs, and StorageClasses make the whole thing automatic and dynamic.
  • The reclaim policy decides what happens to the PV and volume when the PVC is released: Delete (default for dynamic PVs, dangerous) or Retain (safe, manual cleanup).
  • Volume binding mode Immediate creates the volume at once; WaitForFirstConsumer waits for a Pod so the volume lands in the Pod's region and zone.
  • The hands-on uses LKE and will not work on other clouds; GKE files are included in the repo.

11.1 The big picture

  • Kubernetes supports block, file and object storage from many external systems, on-premises (EMC, NetApp) or from cloud providers.
  • The hands-on examples run on Linode Kubernetes Engine (LKE): simple and cheap, but they will not work elsewhere, because each cloud has its own storage plugins and options
    • The repo includes files for Google Kubernetes Engine (GKE).

Figure 11.1 architecture, left to right:

Layer What it is
Storage providers (left) External systems: on-premises arrays or cloud storage services
Plugin layer (middle) Interface between storage and Kubernetes; modern plugins use the Container Storage Interface (CSI), an industry-standard interface for container orchestrators
Persistent volume subsystem (right) Standard API objects apps use to consume storage

[!note] In-tree vs out-of-tree Before CSI, storage plugins lived in the main Kubernetes code tree (in-tree). They had to be open source, and updates and bug fixes were tied to the Kubernetes release cycle. CSI plugins are out-of-tree: they need not be open source and can be released whenever needed.

Core objects (referred to by PascalCase name, acronym, or plain words):

  • PersistentVolumes (PV)
  • PersistentVolumeClaims (PVC)
  • StorageClasses (SC)

Volume provisioning workflow (AWS example)

  1. A Pod needs a 50GB volume and requests it via a PVC.
  2. The PVC asks the StorageClass to create a new PV and the volume on the AWS backend.
  3. The SC calls the AWS backend through the AWS CSI plugin.
  4. The plugin creates a 50GB EBS volume.
  5. The plugin reports the creation back to the SC.
  6. The SC creates the PV and maps it to the EBS volume.
  7. The Pod mounts the PV and uses it.

Kubernetes prevents multiple Pods writing to the same PV, and forces a 1:1 mapping between external volumes and PVs: you cannot map one 50GB volume to two 25GB PVs.

11.2 Storage providers

  • Providers (or provisioners) each supply a CSI plugin exposing their features and options, usually delivered as a Helm chart or YAML installer
    • Installed, it runs as Pods in the kube-system Namespace.
  • Restrictions: you cannot mount AWS EBS volumes from a cluster on Azure; locality may apply (Pods may need to be in the same region or zone as the storage).
  • Volume size, protection level, snapshot schedule, replication, encryption and more are configured through the backend's CSI plugin
    • Backends differ, so read the plugin's documentation: it is your responsibility.

11.3 The Container Storage Interface (CSI)

  • An open-source project defining an industry-standard interface so orchestrators use external storage uniformly
    • Storage providers get a documented interface, and CSI plugins should work on any orchestration platform supporting CSI.
  • A reasonably current plugin list (called "drivers"): https://kubernetes-csi.github.io/docs/drivers.html
  • Most clouds pre-install CSI plugins for their native storage. Third-party plugins you install yourself, typically from Helm charts or YAML, and they run as Pods in kube-system.

11.4 The Kubernetes persistent volume subsystem

A set of API objects letting apps request and access storage:

  • PVs make external volumes available (to use a 50GB AWS volume you map it to a PV).
  • A Pod needs a PVC granting access to the PV.
  • SCs let apps create PVs and backend volumes dynamically.

Example with four tiers on an external system, one StorageClass each:

External tier StorageClass CSI plugin
Flash sc-fast-block csi.xyz.block
Flash encrypted sc-fast-encrpted (as printed) csi.xyz.block
Mechanical disk sc-slow csi.xyz.block
NFS Filestore sc-file csi.xyz.file

To deploy an app needing 100GB of fast encrypted block storage, define a Pod referencing a PVC requesting 100GB from sc-fast-encrypted. After posting to the API server: the SC controller sees the PVC and tells the CSI plugin to provision 100GB of encrypted flash; the external system creates it and reports back; the controller maps it to a new PV; the Pod uses the PVC to mount the PV.

11.5 Dynamic provisioning with StorageClasses

  • Resources in the storage.k8s.io/v1 API group, kind StorageClass, shortname sc. (kubectl api-resources lists all resources, shortnames, API groups and kinds.)
  • You choose how to define classes based on available storage; a cloud might offer fast SSD block, fast encrypted SSD block, slow mechanical block and NFS file.

A StorageClass YAML

fast-local provisions encrypted SSD volumes at 10 IOPS per GB in the Ireland AWS region:

# StorageClass fast-local
kind: StorageClass
apiVersion: storage.k8s.io/v1
metadata:
  name: fast-local
provisioner: ebs.csi.aws.com          # AWS Elastic Block Store CSI plugin
parameters:
  encrypted: true                     # create encrypted volumes
  type: io1                           # AWS SSD drives
  iopsPerGB: "10"                     # performance requirement
allowedTopologies:                    # where to provision volumes and replicas
- matchLabelExpressions:
  - key: topology.ebs.csi.aws.com/zone
    values:
    - eu-west-1a                      # Ireland AWS region
  • provisioner says which CSI plugin to use (must be installed); parameters define the storage type; allowedTopologies says where replicas go.
  • Notes:
    • StorageClasses are immutable: no modification after deploy.
    • Give metadata.name a meaningful value, since it is how you and other objects refer to the class.
    • Provisioner, plugin and driver are used interchangeably.
    • parameters is plugin-specific and different for every plugin; read the plugin docs.

Working with StorageClasses

Workflow:

  1. Install and configure the CSI plugin.
  2. Create one or more StorageClasses.
  3. Deploy Pods with PVCs that request volumes through the classes.

(Assumes external storage is connected. Hosted services often pre-install CSI drivers for the cloud's native backends.)

One file can hold all three objects, separated by --- (truncated here as in the book; GKE example):

# Pod, PVC and StorageClass in one file
apiVersion: v1
kind: Pod                             # 1. Pod
metadata:
  name: mypod
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: mypvc                # 2. request volume via the "mypvc" PVC
  containers: ...
# <SNIP>
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mypvc                         # 3. this is the "mypvc" PVC
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 50Gi                   # 4. provision a 50Gi volume...
  storageClassName: fast              # 5. ...based on the "fast" StorageClass
---
kind: StorageClass
apiVersion: storage.k8s.io/v1
metadata:
  name: fast                          # 6. this is the "fast" StorageClass
provisioner: pd.csi.storage.gke.io    # 7. use this CSI plugin
parameters:
  type: pd-ssd                        # 8. provision this type of storage

Walkthrough: a normal Pod (1) requests a volume via PVC mypvc (2); mypvc (3) asks for 50Gi (4) from StorageClass fast (5); fast is defined (6), uses the pd.csi.storage.gke.io plugin (7), which provisions pd-ssd storage from Google Cloud (8).

Additional volume settings

Access mode (three):

Mode Meaning
ReadWriteOnce (RWO) One PVC can bind in read-write mode; binding from several PVCs fails
ReadWriteMany (RWM) Many PVCs can bind read-write; file and object storage usually support it, block usually does not
ReadOnlyMany (ROM) Many PVCs can bind read-only

A PV can only be opened in one mode: you cannot bind one PV to a PVC in ROM and another in RWM.

Reclaim policy (what happens to a PV and external storage when its PVC is released):

Policy Behaviour
Delete Most dangerous; default for dynamically created PVs. Deleting the PVC deletes the PV and the external storage.
Retain Keeps the PV and external storage after the PVC is deleted. Safer, but you reclaim resources manually.

Summary: SCs represent tiers of storage apps use to create volumes dynamically. Defined in YAML, each references a plugin and ties to a storage type on an external system (for example, fast AWS SSD in Mumbai versus slow AWS storage elsewhere). The SC controller watches for new PVCs referencing the class and, for each, creates the volume on the external system and maps it to a PV.

11.6 Hands-on

Demos (LKE only):

  1. Use an existing StorageClass.
  2. Create and use a new StorageClass.

Assumes the repo clone on branch 2025 and a connection to your LKE cluster (see The Kubernetes Book 3: Getting Kubernetes):

Use an existing StorageClass

Most environments pre-create at least one (output trimmed):

$ kubectl get sc
NAME                          PROVISIONER               RECLAIM POLICY  VOLUME BINDINGMODE  ALLOWVOLUME EXPANSION
linode-blck-stg               linodebs.csi.linode.com   Delete          Immediate           true
linode-blck-stg-retain (def)  linodebs.csi.linode.com   Retain          Immediate           true
  • Two classes, both via the linodebs.csi.linode.com plugin and the Immediate binding mode; one Delete, one Retain.
  • The class marked (default) is used by PVCs that name no class. Specify a class for important production apps, since defaults differ between clusters.

It uses Delete: Kubernetes will delete the PV and backend volume when you stop using the PVC. Check nothing exists first:

$ kubectl get pv
No resources found
$ kubectl get pvc
No resources found in default namespace.

PVC pvc-test requests a 10GB volume from linode-block-storage:

# lke-pvc-test.yml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-test
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: linode-block-storage
  resources:
    requests:
      storage: 10Gi

$ kubectl apply -f lke-pvc-test.yml
persistentvolumeclaim/pvc-test created

$ kubectl get pvc
NAME       STATUS   VOLUME                 CAPACITY   ACCESS MODES   STORAGECLASS
pvc-test   Bound    pvc-cc3dd8716c7d46c9   10Gi       RWO            linode-block-storage

$ kubectl get pv
NAME                   CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM      STORAGECLASS
pvc-cc3dd8716c7d46c9   10Gi       RWO            Delete           Bound    pvc-test   linode-block-storage
  • The PVC is already Bound because Immediate creates the PV and backend storage without waiting for a Pod. The PV is bound to pvc-test.
  • In the LKE dashboard (cloud.linode.com, Volumes tab) you see a 10GB volume in your cluster's region (Figure 11.3: how everything maps; only the Pod is missing).
  • With WaitForFirstConsumer, nothing would be created until a Pod used the PVC.
$ kubectl delete pvc pvc-test

$ kubectl get pv
No resources found

Deleting the PVC also deletes the PV and Linode volume (reclaim policy Delete); confirm in the Volumes tab.

Create and use a new StorageClass

A class implementing topology-aware provisioning (also called provision on demand): it delays volume creation until a Pod requests it, so the volume lands in the Pod's region and zone. lke-sc-wait-keep.yml defines block-wait-keep:

  • block storage
  • volumeBindingMode: WaitForFirstConsumer
  • reclaimPolicy: Retain (keep volume and data when the PVC is deleted)
# lke-sc-wait-keep.yml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: block-wait-keep
provisioner: linodebs.csi.linode.com      # CSI plugin
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer   # provision on demand
reclaimPolicy: Retain                     # keep volume when PVC released

$ kubectl apply -f lke-sc-wait-keep.yml
storageclass.storage.k8s.io/block-wait-keep created

$ kubectl get sc
NAME                          PROVISIONER               RECLAIM POLICY  VOLUME BINDINGMODE    ALLOW VOLUME EXPANSION
block-wait-keep               linodebs.csi.linode.com   Retain          WaitForFirstConsumer  true
linode-blck-stg               linodebs.csi.linode.com   Delete          Immediate             true
linode-blck-stg-retain (def)  linodebs.csi.linode.com   Retain          Immediate             true

PVC pvc-wait-keep requests 20GB from that class:

# lke-pvc-wait-keep.yml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-wait-keep
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  storageClassName: block-wait-keep

$ kubectl apply -f lke-pvc-wait-keep.yml
persistentvolumeclaim/pvc-wait-keep created

$ kubectl get pvc
NAME            STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
pvc-wait-keep   Pending                                      block-wait-keep

$ kubectl get pv
No resources found

The PVC stays Pending and no PV exists, because WaitForFirstConsumer waits for a Pod to reference it. Pod volpod (annotated) uses it:

# lke-app.yml
apiVersion: v1
kind: Pod
metadata:
  name: volpod
spec:
  volumes:
  - name: data                          # create a volume called "data"
    persistentVolumeClaim:
      claimName: pvc-wait-keep          # from the PVC called "pvc-wait-keep"
  containers:
  - name: ubuntu-ctr
    image: ubuntu:latest
    command:
    - /bin/bash
    - "-c"
    - "sleep 60m"
    volumeMounts:
    - name: data                        # mount the "data" volume
      mountPath: /tkb                   # to /tkb

$ kubectl apply -f lke-app.yml
pod/volpod created

$ kubectl get pvc
NAME            STATUS   VOLUME                 CAPACITY   ACCESS MODES   STORAGECLASS
pvc-wait-keep   Bound    pvc-279f09e083254fa9   20Gi       RWO            block-wait-keep

$ kubectl get pv
NAME                   CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM           STORAGECLASS
pvc-279f09e083254fa9   20Gi       RWO            Retain           Bound    pvc-wait-keep   block-wait-keep

The PVC is Bound, a PV of the same name exists, and capacity, reclaim policy and class are as expected. Confirm the Pod mounts it:

    <Snip>

What happened:

  1. You created block-wait-keep (Linode block storage).
  2. The SC controller started watching for PVCs referencing it.
  3. Your PVC created no volume, because of WaitForFirstConsumer.
  4. Deploying a Pod that used the PVC requested the 20GB volume.
  5. The SC controller dynamically created the PV and the Linode volume.

Clean up

Five steps:

  1. Delete the Pod using the PVC.
  2. Delete the PVC.
  3. Delete the PV.
  4. Manually delete the volume in the Linode backend.
  5. Delete the SC.
$ kubectl delete pod volpod
pod "volpod" deleted

$ kubectl delete pvc pvc-wait-keep
persistentvolumeclaim "pvc-wait-keep" deleted

$ kubectl delete pv pvc-279f09e083254fa9
persistentvolume "pvc-279f09e083254fa9" deleted

$ kubectl delete sc block-wait-keep
storageclass.storage.k8s.io "block-wait-keep" deleted
  • The PV and external volume survived the PVC deletion because of Retain; you deleted the PV by hand (yours has a different name).
  • In the Linode console delete the volume with the same name as the PV; it shows as unattached in the Attached to column. Not deleting it incurs Linode costs.

Summary points

  • Kubernetes has a powerful storage subsystem for dynamically provisioning and using storage from many external providers.
  • Each provider has a CSI plugin that creates volumes and surfaces them; hosted clusters pre-install plugins as Pods in kube-system.
  • After installing the plugin, create StorageClasses mapping to storage types
    • the SC controller (a reconciliation loop on the control plane) watches for PVCs, creates the requested volume and maps it to a PV
    • Pods claim and mount it through the PVC.
Terms to carry forward
  • PV / PVC / StorageClass: external volume mapping / access claim / dynamic provisioning tier.
  • CSI: Container Storage Interface; plugins run as Pods in kube-system; in-tree vs out-of-tree.
  • Access modes: RWO, RWM, ROM.
  • Reclaim policy: Delete or Retain.
  • Volume binding mode: Immediate or WaitForFirstConsumer (topology-aware, provision on demand).
  • Default StorageClass: used when a PVC names none; differs between clusters.
