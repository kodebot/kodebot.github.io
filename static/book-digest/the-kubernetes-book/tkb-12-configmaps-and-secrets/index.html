The Kubernetes Book 12: ConfigMaps and Secrets

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 12. Previous: The Kubernetes Book 11: Kubernetes Storage. Next: The Kubernetes Book 13: StatefulSets.

Takeaways
  • Packaging an app and its configuration together is an anti-pattern; decouple them so you build one image and apply per-environment config at run time.
  • A ConfigMap is a map of key-value pairs (up to 1 MiB) for non-sensitive config; it has a data block, not spec and status.
  • Inject into containers as environment variables, startup-command arguments or files in a volume. Only volumes receive live updates (after a minute or two).
  • Secrets work the same way but are not secure by default: base64 is encoding, not encryption, and most clusters store them unencrypted.
  • A real secrets solution needs encryption at rest and in flight, strict RBAC, etcd protection, and often an external vault.

[!note] Anti-pattern Something that seems like a good idea but turns out to be a bad one (the book's definition).

12.1 The big picture

Most apps are an application plus a configuration (NGINX and Apache are useless until configured). Early cloud-native microservices packaged the two as one unit. Decoupling gives:

  • reuse
  • simpler development and testing
  • simpler, less disruptive changes

The coupled world

A company with Dev, Test and Prod environments, each with its own network and security policies, credentials and certificates. Packaging config in the image means, for every app:

  • build three images (dev, test, prod configs)
  • store them in three repositories
  • run a different configuration in each environment

Even a typo fix needs a build, test, store and redeploy three times, and troubleshooting is harder because every update mixes code and config.

The decoupled world

Build a hardened NGINX base image with no embedded configuration, then create three configs (app config, policy settings, credentials per environment) applied at run time. Result:

  • one image built and tested once, stored in one repository, same version everywhere
  • any developer can pull it, because it holds no sensitive data
  • code and config can be pushed independently: fix a homepage typo in the config and push it to existing containers in all three environments without replacing containers
  • other teams reuse the base image with their own configs

12.2 ConfigMap theory

A ConfigMap (CM) stores config outside Pods and injects it at run time. It is a first-class object in the core API group, v1, which means:

  • stable (v1)
  • long-standing (new things never go in the core group)
  • definable in YAML
  • manageable with kubectl

Use ConfigMaps for non-sensitive data:

  • environment variables
  • configuration files (web server, database)
  • hostnames
  • Service names and ports
  • account names

Never put sensitive data (certificates, passwords) in ConfigMaps: Kubernetes makes no effort to protect their contents. Use Secrets within a wider secrets-management solution.

How ConfigMaps work

A ConfigMap holds a map of key-value pairs:

  • Keys: arbitrary names; alphanumerics, dashes, dots, underscores.
  • Values: anything, including whole multi-line config files.
  • Size limit: 1 MiB (1,048,576 bytes).

Three entries:

# ConfigMap epl
kind: ConfigMap
apiVersion: v1
metadata:
  name: epl
data:
  Competition: Premier League    # 3 map entries (key: value pairs)
  Season: 2024-2025
  Champions: Liverpool

A value that is a complete config file:

# ConfigMap cm2
kind: ConfigMap
apiVersion: v1
metadata:
  name: cm2
data:
  test.conf: |            # key
    env = plex-test       # value starts here
    endpoint = 0.0.0.0:31001
    char = utf8
    vault = PLEX/test
    log-size = 512M

Three ways to inject at run time:

  1. Environment variables
  2. Arguments to the container's startup command
  3. Files in a volume

(Figure 12.1: the ConfigMap lives outside the app and its values map to environment variables and volumes apps already understand.) None needs Kubernetes knowledge added to the app; volumes are most flexible because they enable updates.

Kubernetes-native apps know they run on Kubernetes and talk to the API server, so they can read ConfigMaps directly and see live updates. But they only work on Kubernetes (lock-in). The book's examples use environment variables and volumes so existing apps need no rewrite.

12.3 Hands-on with ConfigMaps

Clone the repo, switch to 2025, and run from the configmaps folder:

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025

Creating ConfigMaps imperatively

kubectl create configmap (shortened to cm) takes two data sources:

  • literals: --from-literal
  • a file: --from-file

Windows users replace trailing backslashes with backticks.

$ kubectl create configmap testmap1 \
    --from-literal shortname=SAFC \
    --from-literal longname="Sunderland Association Football Club"

$ kubectl describe cm testmap1
Name:         testmap1
Namespace:    default
Labels:       <none>
Annotations:  <none>
Data
====
shortname:
----
SAFC
longname:
----
Sunderland Association Football Club
BinaryData
====
Events:  <none>

It is just a map of key-value pairs dressed as a Kubernetes object. From a file (cmfile.txt, one line):

$ kubectl create cm testmap2 --from-file cmfile.txt
configmap/testmap2 created

Inspecting ConfigMaps

$ kubectl get cm
NAME       DATA   AGE
testmap1   2      11m
testmap2   1      2m23s

(The book's header prints AME; shown as NAME.) For testmap2 there is one entry; the key is the file name and the value is the file contents:

$ kubectl describe cm testmap2
Name:         testmap2
Namespace:    default
Labels:       <none>
Annotations:  <none>
Data
====
cmfile.txt:               # key
----
Kubernetes FTW!           # value
BinaryData
====
Events:  <none>

$ kubectl get cm testmap2 -o yaml
apiVersion: v1
data:
  cmfile.txt: |
    Kubernetes FTW!
kind: ConfigMap
metadata:
  creationTimestamp: "2025-02-04T14:19:21Z"
  name: testmap2
  namespace: default
  resourceVersion: "18128"
  uid: 146da79c-aa09-4b10-8992-4dffa087dbfb

There is no spec or status: ConfigMaps have no desired and observed state; they have a data block instead.

Creating ConfigMaps declaratively

Two entries (firstname, lastname), with data instead of spec:

# fullname.yml
kind: ConfigMap
apiVersion: v1
metadata:
  name: multimap
data:
  firstname: Nigel
  lastname: Poulton

$ kubectl apply -f fullname.yml
configmap/multimap created

One entry whose value is a whole config file; the pipe (|) tells Kubernetes to treat everything after it as a single value:

# singlemap.yml
kind: ConfigMap
apiVersion: v1
metadata:
  name: test-config
data:
  test.conf: |            # key
    env = plex-test       # value
    endpoint = 0.0.0.0:31001
    char = utf8
    vault = PLEX/test
    log-size = 512M
Object name Key Value
test-config test.conf env = plex-test, endpoint = 0.0.0.0:31001, char = utf8, vault = PLEX/test, log-size = 512M 
$ kubectl apply -f singlemap.yml
configmap/test-config created

$ kubectl describe cm test-config
Name:         test-config
Namespace:    default
Labels:       <none>
Annotations:  <none>
Data
====
test.conf:
----
env = plex-test
endpoint = 0.0.0.0:31001
char = utf8
vault = PLEX/test
log-size = 512M
BinaryData
====
Events:  <none>

Injecting ConfigMap data into Pods and containers

Three ways: environment variables, startup-command arguments, volume files. The first two inject at creation only, with no update to a running container; volumes also inject at creation but push updates to live containers.

ConfigMaps and environment variables

Figure 12.2: create the ConfigMap, map entries to env vars in the Pod template's containers section; at start they appear as ordinary Linux or Windows environment variables, so apps need no ConfigMap knowledge. multimap holds firstname=Nigel and lastname=Poulton. podenv.yml maps them (the variable names are capitalised to tell them apart; any name works):

# podenv.yml (excerpt)
apiVersion: v1
kind: Pod
# <Snip>
spec:
  containers:
  - name: ctr1
    env:
    - name: FIRSTNAME         # environment variable called FIRSTNAME
      valueFrom:              # based on
        configMapKeyRef:      # a ConfigMap
          name: multimap      # called "multimap"
          key: firstname      # populated by the "firstname" entry
    - name: LASTNAME
      valueFrom:
        configMapKeyRef:
          name: multimap
          key: lastname
    # <Snip>

$ kubectl apply -f podenv.yml
pod/envpod created

$ kubectl exec envpod -- env | grep NAME
HOSTNAME=envpod
FIRSTNAME=Nigel
LASTNAME=Poulton

(Windows: replace grep NAME with Select-String -Pattern 'NAME'.) Environment variables are static: updating the map does not update envpod.

ConfigMaps and container startup commands

Pass env vars as arguments to the startup command. podstartup.yml (container args1, busybox) uses the same mappings as above and adds a command line:

# podstartup.yml (excerpt)
spec:
  containers:
  - name: args1
    image: busybox
    env:                       # same mappings as the previous example,
    - name: FIRSTNAME          # this time used by the startup command below
      valueFrom:
        configMapKeyRef:
          name: multimap
          key: firstname
    - name: LASTNAME
      valueFrom:
        configMapKeyRef:
          name: multimap
          key: lastname
    command: [ "/bin/sh", "-c", "echo First name $(FIRSTNAME) last name $(LASTNAME)" ]

(Figure 12.3: entries populate env vars, then the startup command references them.)

$ kubectl apply -f podstartup.yml
pod/startup-pod created

$ kubectl logs startup-pod -c args1
First name Nigel last name Poulton

$ kubectl describe pod startup-pod
<Snip>
Environment:
  FIRSTNAME:  <set to the key 'firstname' of config map 'multimap'>
  LASTNAME:   <set to the key 'lastname' of config map 'multimap'>
<Snip>

It still uses env vars, so it has the same limit: ConfigMap updates are not pushed. The Pod prints once and completes; delete it:

$ kubectl delete pod startup-pod
pod "startup-pod" deleted

ConfigMaps and volumes

The most flexible option: reference whole config files and get updates (they can take a minute or two to appear). Process (Figure 12.4):

  1. Create the ConfigMap.
  2. Define a ConfigMap volume in the Pod template.
  3. Mount the volume into the container.
  4. Entries appear as files inside the container.

podvol.yml defines Pod cmvol: volume volmap from multimap, mounted at /etc/name:

# podvol.yml
apiVersion: v1
kind: Pod
metadata:
  name: cmvol
spec:
  volumes:
  - name: volmap              # create a volume called "volmap"
    configMap:                # based on the ConfigMap
      name: multimap          # called "multimap"
  containers:
  - name: ctr
    image: nginx
    volumeMounts:             # mount the "volmap" volume
    - name: volmap
      mountPath: /etc/name    # into the container at "/etc/name"

$ kubectl apply -f podvol.yml
pod/cmvol created

$ kubectl exec cmvol -- ls /etc/name
firstname
lastname

Two files, one per entry (use cat to see the contents). Now edit the map. kubectl edit cm multimap opens the YAML in your editor (vi on Linux and Mac, notepad.exe on Windows); alternatively edit the file elsewhere and kubectl apply it. Change the entries (the book changes them to City and Country):

$ kubectl edit cm multimap
# Please edit the object below. Lines beginning with a '#' will be ignored,
# and an empty file will abort the edit. If an error occurs while saving
# this file will be reopened with the relevant failures.
#
apiVersion: v1
data:
  City: Macclesfield          # changed
  Country: UK                 # changed
kind: ConfigMap
metadata:
<Snip>

After a minute or so the container sees the change:

$ kubectl exec cmvol -- ls /etc/name
City
Country

$ kubectl exec cmvol -- cat /etc/name/Country
UK

The ConfigMap surfaces in the container filesystem through a volume, and the volume received your updates.

12.4 Hands-on with Secrets

Secrets work like ConfigMaps (config injected at run time) but are meant for sensitive data (passwords, certificates, OAuth tokens) within a wider secrets-management solution. Everything about ConfigMaps applies.

Are Kubernetes Secrets secure?

Short answer: no. A secure system also needs:

  • encryption of secrets at rest in the cluster store
  • encryption in flight on the network
  • protection when surfaced in nodes, Pods and containers
  • least-privilege RBAC on API access to secrets
  • controlled access to etcd nodes
  • preventing privileged containers from reaching secrets
  • preventing exposure through source repos like GitHub
  • securely deleting secrets no longer needed

Most new clusters do none of this: secrets sit unencrypted in the cluster store, travel in plain text, and mount as plain text. You can add:

  • EncryptionConfiguration objects for encryption at rest
  • a service mesh to encrypt all network traffic
  • strong RBAC
  • restricted access to control plane and etcd nodes

Real-world clusters often use a service mesh and keep secrets in third-party vaults (HashiCorp Vault or cloud equivalents). Kubernetes has a native Secrets Store CSI Driver to integrate with external vaults. The book covers only what ships out of the box.

A typical Kubernetes-Secrets-only workflow:

  1. You create the Secret; Kubernetes persists it unencrypted in the cluster store.
  2. You schedule a Pod with a container that uses it.
  3. Kubernetes sends the unencrypted Secret over the network to the node.
  4. The kubelet starts the Pod and containers.
  5. The runtime mounts the Secret into the container through an in-memory tmpfs filesystem and decodes it from base64 to plain text.
  6. The app consumes it.
  7. Deleting the Pod deletes the node's copy (the cluster-store copy stays).

Use case: a TLS termination proxy: one image with three different Secrets for three environments, each holding that environment's TLS certificates, loaded at run time (Figure 12.5).

Creating Secrets

Most installs do not encrypt Secrets at rest or in flight, and even if you do, they always surface as plain text in containers so apps can use them. Imperatively (Windows: backticks for backslashes):

$ kubectl create secret generic creds \
    --from-literal user=nigelpoulton \
    --from-literal pwd=Password123

Kubernetes obscures values as base64:

$ kubectl get secret creds -o yaml
apiVersion: v1
kind: Secret
data:
  pwd: UGFzc3dvcmQxMjM=
  user: bmlnZWxwb3VsdG9u
<Snip>

Decoding needs no key (needs the base64 utility, or use an online decoder):

$ echo UGFzc3dvcmQxMjM= | base64 -d
Password123

This proves base64 is not security: never store Secrets on GitHub or similar, since anyone with access can read them. Declaratively:

# tkb-secret.yml
apiVersion: v1
kind: Secret
metadata:
  name: tkb-secret
  labels:
    chapter: configmaps
type: Opaque
data:                          # change to "stringData" for plain text entries
  username: bmlnZWxwb3VsdG9u
  password: UGFzc3dvcmQxMjM=

(Either form must stay out of public repos.)

$ kubectl apply -f tkb-secret.yml
secret/tkb-secret created

Inspect with kubectl get and kubectl describe.

Using Secrets in Pods

Secrets inject as environment variables, command-line arguments or volumes; volumes are most flexible. secretpod.yml mounts tkb-secret as volume secret-vol at /etc/tkb:

# secretpod.yml
apiVersion: v1
kind: Pod
metadata:
  name: secret-pod
  labels:
    topic: secrets
spec:
  volumes:
  - name: secret-vol           # volume name
    secret:                    # volume type
      secretName: tkb-secret   # populate the volume with this Secret
  containers:
  - name: secret-ctr
    image: nginx
    volumeMounts:
    - name: secret-vol         # mount the volume defined above
      mountPath: "/etc/tkb"    # into this path

Secret volumes are mounted read-only automatically, to prevent accidental changes by containers or apps. Deploying sends the unencrypted Secret to the node's kubelet, and the runtime mounts it with tmpfs:

$ kubectl apply -f secretpod.yml
pod/secret-pod created

$ kubectl exec secret-pod -- ls /etc/tkb
password
username

$ kubectl exec secret-pod -- cat /etc/tkb/password
Password123

One file per entry, in plain text so apps can use them. As you used a volume, updates to the Secret reach the app. A complete solution needs encryption at rest and in flight, API access control, restricted etcd access, handling of privileged containers, keeping Secret manifests off public repos, and more; most real solutions keep secret data in a third-party vault outside Kubernetes.

Summary points

  • ConfigMaps and Secrets decouple apps from config; both are first-class API objects, creatable imperatively and declaratively and inspectable with kubectl.
  • ConfigMaps hold app config parameters and whole files; Secrets are for sensitive data in a wider secrets-management solution.
  • Inject via env vars, container start commands or volumes; volumes are preferred as they propagate changes to live containers.
  • Kubernetes does not encrypt Secrets in the cluster store or in transit by default.
Terms to carry forward
  • ConfigMap (cm): key-value config, data block, 1 MiB limit.
  • --from-literal / --from-file: imperative creation sources.
  • configMapKeyRef / ConfigMap volume: env-var and file injection.
  • Secret: like a ConfigMap, base64-encoded, not encrypted by default.
  • data vs stringData: base64 vs plain-text entries.
  • tmpfs: in-memory filesystem used to mount Secrets.
  • EncryptionConfiguration, Secrets Store CSI Driver, Vault: real secrets management.
  • Kubernetes-native app: reads the API directly; lock-in.
