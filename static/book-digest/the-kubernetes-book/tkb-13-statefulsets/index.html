The Kubernetes Book 13: StatefulSets

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 13. Previous: The Kubernetes Book 12: ConfigMaps and Secrets. Next: The Kubernetes Book 14: API Security and RBAC.

Takeaways
  • A StatefulSet manages stateful apps (databases, key-value stores, session stores) and gives Pods a sticky ID: a predictable, persistent name, DNS name and volume binding.
  • Pods are named <StatefulSetName>-<ordinal> (tkb-sts-0, tkb-sts-1...), created one at a time in order, each waiting for the previous to be running and ready.
  • Each Pod gets its own PVC from volumeClaimTemplates; scale-down deletes Pods but never PVCs, so scale-up reattaches the same volumes.
  • A headless Service (clusterIP: None) named as the governing Service creates DNS records for every Pod so clients can reach specific Pods.
  • Scale to zero before deleting a StatefulSet, because deleting it does not terminate Pods in order. StatefulSets are only a framework; apps must be designed to use them.

13.1 StatefulSet theory

The chapter defines a stateful application as one that creates and saves valuable data: databases, key-value stores, apps that store client session data for later sessions.

StatefulSets and Deployments are both API resources using the controller pattern (reconciliation loops) and both add self-healing, scaling and rollouts. StatefulSets add three things Deployments do not:

  1. Predictable and persistent Pod names and DNS names.
  2. Predictable and persistent volume bindings.
  3. Predictable startup and shutdown order.

Points 1 and 2 form a Pod's state, or sticky ID. They persist across failures, scaling and other scheduling events.

  • A failed StatefulSet Pod is replaced by a new Pod with the same name, same DNS hostname and same volumes, even on a different node.
  • Same after a scale-down then scale-up.

A simple StatefulSet tkb-sts, three mongo:latest replicas:

# StatefulSet tkb-sts (excerpt)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: tkb-sts
spec:
  selector:
    matchLabels:
      app: mongo
  serviceName: "tkb-sts"
  replicas: 3
  template:
    metadata:
      labels:
        app: mongo
    spec:
      containers:
      - name: ctr-mongo
        image: mongo:latest
...

StatefulSet Pod naming

  • Format <StatefulSetName>-<Integer>, a zero-based index ordinal: tkb-sts-0, tkb-sts-1, tkb-sts-2.
  • Names drive how StatefulSets start, self-heal, scale, delete Pods and connect them to volumes.
  • The StatefulSet name also forms each replica's DNS name, so avoid exotic characters that make invalid DNS names.

Ordered creation and deletion

Controller How Pods start
StatefulSet One at a time, waiting for each to be running and ready before the next
Deployment (via ReplicaSet) All at once, which can cause race conditions
  • Figure 13.1: tkb-sts-0 starts first, then -1, then -2. "Running and ready" means all containers in the Pod run and the Pod can serve requests.
  • Scaling 3 to 5 starts tkb-sts-3, waits for it, then tkb-sts-4.
  • Scaling down is the reverse: terminate the highest ordinal first and wait for it to terminate fully before the next.
  • Guaranteed order and no parallel termination matter for stateful apps; a clustered app can lose data if several replicas stop together.
  • The StatefulSet controller does its own self-healing and scaling, unlike Deployments, which use the ReplicaSet controller.

Deleting StatefulSets

  1. Deleting a StatefulSet object does not terminate its Pods in order, so scale to zero replicas first.
  2. Use terminationGracePeriodSeconds to control Pod termination; commonly at least 10 seconds so apps can flush buffers and commit in-flight writes.

StatefulSets and volumes

  • Volumes are part of the sticky ID
    • The controller creates the volumes Pods need and gives them special names linking them to the right Pods (Figure 13.2: tkb-sts with three Pods, one volume each).
  • Volumes stay decoupled through the regular PVC system, so they have separate lifecycles and survive Pod failure and termination
    • Replacement Pods reconnect to the surviving volumes and data, even on another node.
  • The same applies to scaling: a scale-up attaches new Pods to surviving volumes. This can save you if you accidentally delete a Pod, even the last replica.

Handling failures

  • Pod failure: with five replicas and tkb-sts-3 failing, the controller starts a new Pod with the same name and attaches it to the surviving volumes.
  • Node failure
    • is harder, and some older versions needed manual intervention to replace Pods on failed nodes
    • Reason: Kubernetes cannot always tell a genuinely failed node from one rebooting after a transient event
    • If a "failed" node recovers after its Pods were replaced, identical Pods might write to the same volume and corrupt data
    • Newer versions handle this better.

Network ID and headless Services

  • For apps needing predictable, long-lived Pods (for example, an external app that reconnects to the same Pod), a StatefulSet uses a headless Service instead of a load-balancing one: it creates predictable DNS names per Pod so apps query DNS (the service registry) for the Pod list and connect to specific Pods directly.
  • A headless Service is a regular Service with no ClusterIP (spec.clusterIP: None). Listing it in the StatefulSet's spec.serviceName makes it the governing Service.
# headless Service plus StatefulSet (excerpt, one file)
apiVersion: v1
kind: Service                  # Service
metadata:
  name: mongo-prod
spec:
  clusterIP: None              # make it a headless Service
  selector:
    app: mongo
    env: prod
---
apiVersion: apps/v1
kind: StatefulSet              # StatefulSet
metadata:
  name: sts-mongo
spec:
  serviceName: mongo-prod      # governing Service
  • The headless Service creates DNS SRV and A records for every Pod matching its label selector, so other apps can query DNS for all Pod names and IPs
    • Developers must code their apps to query DNS like this.

13.2 Hands-on with StatefulSets

Tested on LKE and a local Docker Desktop multi-node cluster; other clouds need a different StorageClass (the book says when). Clone the repo, branch 2025, run from the statefulsets folder:

git clone https://github.com/nigelpoulton/TKB.git
cd TKB
git fetch origin
git checkout -b 2025 origin/2025

Three objects to deploy: a StorageClass, a headless Service and a StatefulSet. They are deployed one by one for clarity, though they can be combined in app.yml.

Deploy the StorageClass

StatefulSets need a StorageClass and a PVC to create volumes dynamically. lke-sc.yml defines class block (LKE block storage CSI driver). For Docker Desktop multi-node use dd-kind-sc.yml instead. On another cloud: create your own class named block (set provisioner and parameters), or reuse an existing class and change the name in the PVC later.

# lke-sc.yml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: block                              # the PVC will reference this name
provisioner: linodebs.csi.linode.com       # LKE block storage CSI plugin
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete

$ kubectl apply -f lke-sc.yml
storageclass.storage.k8s.io/block created

$ kubectl get sc
NAME    PROVISIONER               RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUME EXPANSION
block   linodebs.csi.linode.com   Delete          WaitForFirstConsumer   true

Create a governing headless Service

Picture a Service with a head (the stable ClusterIP) and a tail (the Pods it forwards to). A headless Service has no head. Its main purpose is to create DNS SRV records for StatefulSet Pods, so clients look up individual Pods and talk to them directly instead of via a ClusterIP.

# headless-svc.yml
apiVersion: v1
kind: Service                  # normal Kubernetes Service
metadata:
  name: dullahan               # only valid DNS characters in the name
  labels:
    app: web
spec:
  ports:
  - port: 80
    name: web
  clusterIP: None              # make this a headless Service
  selector:
    app: web

The only difference from a regular Service is clusterIP: None.

$ kubectl apply -f headless-svc.yml
service/dullahan created

$ kubectl get svc
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
dullahan   ClusterIP   None         <none>        80/TCP    31s

Deploy the StatefulSet

# sts.yml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: tkb-sts                # call the StatefulSet "tkb-sts"
spec:
  replicas: 3                  # deploy three replicas
  selector:
    matchLabels:
      app: web
  serviceName: "dullahan"      # make this the governing Service
  template:
    metadata:
      labels:
        app: web
    spec:
      terminationGracePeriodSeconds: 10
      containers:
      - name: ctr-web
        image: nginx:latest
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: webroot                       # mount this volume
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:                       # dynamically create a 10GB volume
  - metadata:
      name: webroot
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "block"               # via the "block" storage class
      resources:
        requests:
          storage: 10Gi
  • tkb-sts is the base name for every replica and volume.
  • replicas: 3 creates tkb-sts-0, -1, -2 in order, each running and ready before the next.
  • serviceName designates the governing Service: it is in charge of the StatefulSet's DNS subdomain.
  • spec.template is the Pod template (image, ports).
  • volumeClaimTemplates creates a unique PVC per Pod: three Pods from the template and three PVCs from the claim template, with linked names
    • The claim template webroot asks for 10GB from class block.
  • On another cloud using its own class, edit storageClassName in sts.yml (fine if you created your own class called block).
$ kubectl apply -f sts.yml
statefulset.apps/tkb-sts created

$ kubectl get sts --watch
NAME      READY   AGE
tkb-sts   0/3     14s
tkb-sts   1/3     30s
tkb-sts   2/3     60s
tkb-sts   3/3     90s

Each replica took about 30 seconds: the controller starts each in turn and waits until it is running and ready. Check the PVCs:

$ kubectl get pvc
NAME                STATUS   VOLUME          CAPACITY   MODES   STORAGECLASS   AGE
webroot-tkb-sts-0   Bound    pvc-1146...f274 10Gi       RWO     block          100s
webroot-tkb-sts-1   Bound    pvc-3026...6bcb 10Gi       RWO     block          70s
webroot-tkb-sts-2   Bound    pvc-2ce7...e56d 10Gi       RWO     block          40s

Each PVC was created with its Pod. PVC names combine the claim template name, the StatefulSet and the Pod:

volumeClaimTemplate Pod PVC
webroot tkb-sts-0 webroot-tkb-sts-0
webroot tkb-sts-1 webroot-tkb-sts-1
webroot tkb-sts-2 webroot-tkb-sts-2

Testing peer discovery

Names live in the cluster address space, usually the cluster.local domain. Pod DNS names follow:

<object-name>.<service-name>.<namespace>.svc.cluster.local

So the three Pods (in default, governed by dullahan) get predictable FQDNs:

  • tkb-sts-0.dullahan.default.svc.cluster.local
  • tkb-sts-1.dullahan.default.svc.cluster.local
  • tkb-sts-2.dullahan.default.svc.cluster.local

The headless Service registers these Pods and IPs against dullahan.default.svc.cluster.local. Test from a jump Pod with dig:

$ kubectl apply -f jump-pod.yml
pod/jump-pod created

$ kubectl exec -it jump-pod -- bash
root@jump-pod:/# dig SRV dullahan.default.svc.cluster.local
<Snip>
;; QUESTION SECTION:
;dullahan.default.svc.cluster.local. IN SRV
;; ANSWER SECTION:
dullahan.default.svc.cluster.local. 30 IN SRV... tkb-sts-1.dullahan.default.svc.cluster.local.
dullahan.default.svc.cluster.local. 30 IN SRV... tkb-sts-0.dullahan.default.svc.cluster.local.
dullahan.default.svc.cluster.local. 30 IN SRV... tkb-sts-2.dullahan.default.svc.cluster.local.
;; ADDITIONAL SECTION:
tkb-sts-0.dullahan.default.svc.cluster.local. 30 IN A 10.60.0.5
tkb-sts-2.dullahan.default.svc.cluster.local. 30 IN A 10.60.1.7
tkb-sts-1.dullahan.default.svc.cluster.local. 30 IN A 10.60.2.12
<Snip>
  • QUESTION SECTION: what the client asked.
  • ANSWER SECTION: maps the Service name to the three Pod names.
  • ADDITIONAL SECTION: maps each Pod name to its IP.

Type exit to leave the jump Pod.

Scaling StatefulSets

  • Scale-up creates new Pods and PVCs. Scale-down terminates Pods only, so later scale-ups only create Pods and reattach them to the original PVCs.
  • Edit sts.yml to replicas: 2 and re-post:
$ kubectl apply -f sts.yml
statefulset.apps/tkb-sts configured

$ kubectl get sts tkb-sts
NAME      READY   AGE
tkb-sts   2/2     12h

$ kubectl get pods
NAME        READY   STATUS    RESTARTS   AGE
tkb-sts-0   1/1     Running   0          12h
tkb-sts-1   1/1     Running   0          12h

The highest ordinal was deleted, yet all three PVCs remain:

$ kubectl get pvc
NAME                STATUS   VOLUME          CAPACITY   MODES   STORAGECLASS   AGE
webroot-tkb-sts-0   Bound    pvc-5955...d71c 10Gi       RWO     block          12h
webroot-tkb-sts-1   Bound    pvc-d62c...v701 10Gi       RWO     block          12h
webroot-tkb-sts-2   Bound    pvc-2e2f...5f95 10Gi       RWO     block          12h

webroot-tkb-sts-2 is still Bound; kubectl describe shows Used by: <none>. Set replicas back to 3 and re-apply:

$ kubectl apply -f sts.yml
statefulset.apps/tkb-sts configured

$ kubectl get sts tkb-sts
NAME      READY   AGE
tkb-sts   3/3     12h

$ kubectl describe pod tkb-sts-2 | grep ClaimName
ClaimName:  webroot-tkb-sts-2

(Windows: replace grep ClaimName with Select-String -Pattern 'ClaimName'.) The new Pod mounted the right volume.

  • Kubernetes puts scale-down on hold if any Pod is failed, to protect resilience and data integrity.
  • spec.podManagementPolicy changes start and stop behaviour:
Value Behaviour
OrderedReady (default) One Pod at a time, waiting for the previous to be running and ready
Parallel Like a Deployment: create and delete in parallel (2 to 5 creates the three new Pods at once; 5 to 2 deletes three in parallel)

Naming rules still apply; the setting affects scaling only, not rollouts and rollbacks.

Rollouts

  • Update the image in the YAML and re-post
    • The controller replaces Pods from the highest ordinal downwards, one at a time, waiting for each new Pod to be ready before replacing the next-lowest.
  • More: kubectl explain sts.spec.updateStrategy.

Test a node failure

More complex and version-dependent: modern clusters replace Pods from failed nodes automatically, older ones may need manual help (to avoid misreading transient events as node failure).

$ kubectl get pods -o wide
NAME        READY   STATUS    RESTARTS   AGE   IP          NODE
tkb-sts-0   1/1     Running   0          11m   10.2.0.132  lke343745-544835-5547cbe00000
tkb-sts-1   1/1     Running   0          12h   10.2.0.3    lke343745-544835-1fbc7b870000
tkb-sts-2   1/1     Running   0          21m   10.2.1.7    lke343745-544835-2b6286320000

Each replica is on a different node. Simulate failure for the node running tkb-sts-0:

  • LKE: in cloud.linode.com open the Kubernetes tab, your cluster, scroll to the Node Pool and Recycle a node running a replica (deletes and replaces it) (Figure 13.3).
  • Docker Desktop multi-node (kind):
    • only works for kind clusters (not the single-node kubeadm one), and you must delete and recreate the cluster afterwards to get three nodes back. Nodes run as containers named desktop-control-plane, desktop-worker, desktop-worker2
    • in the Containers tab click the trash icon on the worker running a replica (Figure 13.4 shows desktop-worker2).

Watch recovery (a minute or two):

$ kubectl get pods -o wide --watch
NAME        READY   STATUS              RESTARTS   AGE    IP          NODE
tkb-sts-0   1/1     Running             0          14m    10.2.0.132  lke343745...cbe00000
tkb-sts-1   1/1     Running             0          12h    10.2.0.3    lke343745...7b870000
tkb-sts-2   1/1     Running             0          30m    10.2.1.7    lke343745...86320000
tkb-sts-0   1/1     Terminating         0          14m    10.2.0.132  lke343745...cbe00000
<Snip>
tkb-sts-0   0/1     Completed           0          14m    10.2.0.132  lke343745...cbe00000
<Snip>
tkb-sts-0   0/1     Pending             0          0s     <none>      <none>
tkb-sts-0   0/1     Pending             0          0s     <none>      lke343745...7b870000
tkb-sts-0   0/1     ContainerCreating   0          0s     <none>      lke343745...7b870000
tkb-sts-0   0/1     ContainerCreating   0          110s   <none>      lke343745...7b870000
tkb-sts-0   1/1     Running             0          111s   10.2.0.4    lke343745...7b870000

Reading it: the Pod goes Terminating, Completed, Pending (the scheduler is placing it), ContainerCreating (image pulled, container started), then Running.

  • Kubernetes notices the missing node, the StatefulSet drops to two, and the controller recreates tkb-sts-0.
  • It may appear to hang in ContainerCreating while Kubernetes releases the previous PVC attachment before binding the PVC to the new Pod.
  • The replacement landed on a different node, since the old one is gone. On LKE a new node replaces the recycled one, but Kubernetes does not rebalance existing replicas onto it.

Deleting StatefulSets

Deleting does not stop Pods in order, so for order-sensitive apps and data, scale to zero first:

$ kubectl scale sts tkb-sts --replicas=0
statefulset.apps/tkb-sts scaled

$ kubectl get sts tkb-sts
NAME      READY   AGE
tkb-sts   0/0     13h

$ kubectl delete sts tkb-sts
statefulset.apps "tkb-sts" deleted

(You can dig again from jump-pod to see the SRV records gone, if the Pod still exists.)

13.3 Clean up

The jump Pod, headless Service, volumes and StorageClass still exist. Not deleting the volumes incurs cloud costs.

kubectl delete pod jump-pod
kubectl delete svc dullahan
kubectl delete pvc webroot-tkb-sts-0 webroot-tkb-sts-1 webroot-tkb-sts-2
kubectl delete sc flash

(The book's last command deletes a class named flash, although the class created above is block; shown as printed.) Deleting the PVCs also deletes the PVs and Linode backend storage; with your own StorageClass confirm the external volumes are gone. If you deleted a kind node, rebuild the cluster to the desired node count.

Summary points

  • StatefulSets deploy and manage apps with persistent data and state; they self-heal, scale and roll out; rollbacks require manual attention.
  • Each Pod has a predictable, persistent name, DNS hostname and its own volumes for its whole lifecycle, including failures, restarts and scaling
    • names are integral to scaling and to connecting the right volumes.
  • StatefulSets are only a framework: design applications to take advantage of them.
Terms to carry forward
  • Sticky ID: persistent Pod name, DNS name and volume binding.
  • Ordinal: zero-based index in the Pod name.
  • Headless Service / governing Service: clusterIP: None, set in spec.serviceName; creates SRV and A records per Pod.
  • volumeClaimTemplates: per-Pod PVC template.
  • podManagementPolicy: OrderedReady or Parallel.
  • Running and ready: all containers up and able to serve.
  • terminationGracePeriodSeconds: shutdown grace for flushing writes.
