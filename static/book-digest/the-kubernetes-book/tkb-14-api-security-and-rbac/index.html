The Kubernetes Book 14: API Security and RBAC

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 14. Previous: The Kubernetes Book 13: StatefulSets. Next: The Kubernetes Book 15: The Kubernetes API.

Takeaways
  • Every API request, from kubectl, Pods, kubelets, control plane services or native apps, passes three checks in order: authentication, authorization, admission control. The connection itself is secured with TLS.
  • Kubernetes has no built-in identity database; authN is pluggable (client certificates, webhooks, external IAM such as Active Directory or cloud IAM).
  • Authorization is usually RBAC: deny by default, allow rules only, built from Roles, RoleBindings, ClusterRoles and ClusterRoleBindings.
  • A ClusterRole bound through RoleBindings defines a role once and reuses it across Namespaces.
  • Admission controllers enforce policy on write requests: mutating ones run first and can modify; validating ones can only reject.

CRUD-style requests (create, read, update, delete) to the API server come from:

  • operators and developers using kubectl
  • Pods
  • kubelets
  • control plane services
  • Kubernetes-native apps

14.1 API security big picture

Figure 14.1: the same flow whatever the origin; authN is authentication, authZ is authorisation.

Example: user grant-ward creates a Deployment hive in Namespace terran.

  1. kubectl apply sends the YAML; kubectl builds a request with the user's credentials embedded, over TLS.
  2. The authentication module decides whether it is really grant-ward or an imposter.
  3. The authorisation module decides whether grant-ward may create Deployments in terran.
  4. Admission controllers check that the Deployment meets policy.
  5. Only after all three does the request execute.

Airport analogy: authenticate with a passport (authN), the system checks you bought a seat (authZ), airline policies restrict hand luggage and alcohol (admission control), then you fly.

14.2 Authentication

  • Authentication (authN, "auth en") proves identity. All requests carry credentials and the authN layer verifies them. Failure returns HTTP 401 and denies the request.
  • The layer is pluggable: client certificates, webhooks, and integration with external identity systems such as Active Directory (AD) and cloud IAM.
  • Kubernetes has no identity database of its own, to avoid yet another identity silo; it offloads to an external system.
  • Most clusters support client certificates out of the box, but real clusters integrate with the cloud or corporate identity system; many hosted services do so automatically.

Checking your current authentication setup

Credentials and cluster details live in the kubeconfig file config:

  • Windows: C:\Users\<user>\.kube\config
  • Linux and Mac: /home/<user>/.kube/config
# ~/.kube/config
apiVersion: v1
kind: Config
clusters:                          # cluster block: one or more clusters and certs
- cluster:
    name: prod-shield              # a cluster called "prod-shield"
    server: https://<url-or-ip-address-of-api-server>:443    # the cluster's URL
    certificate-authority-data: LS0tLS1C...LS0tCg==          # cluster's certificate
users:                             # users block: one or more users and credentials
- name: njfury                     # user called njfury
  user:
    as-user-extra: {}
    token: eyJhbGciOiJSUzI1NiIsImtpZCI6IlZwMzl...SZY3uUQ     # user's credentials
contexts:                          # a context is a cluster + user
- context:
    name: shield-admin             # context called "shield-admin"
    cluster: prod-shield           # cluster
    user: njfury                   # user
    namespace: default
current-context: shield-admin      # context used by kubectl

Four top-level sections:

  • clusters: friendly name, API server endpoint, the CA's public key.
  • users: a name and a token (often an X.509 certificate signed by the cluster's CA or one it trusts).
  • contexts: user and cluster pairs.
  • current-context: the pair kubectl uses.

This snippet sends all requests to prod-shield as njfury:

# ~/.kube/config (excerpt)
current-context: shield-admin      # current context
contexts:
- context:
    name: shield-admin
    cluster: prod-shield           # send commands to this cluster
    user: njfury                   # user to authenticate as
    namespace: default

The cluster's authentication module decides whether the user is genuinely njfury (handing off to an external IAM if integrated). On success the request proceeds to authorisation.

14.3 Authorization (RBAC)

  • AuthZ ("auth zee") runs right after successful authentication
    • It is pluggable and a cluster can run several modules; the moment any one authorises a request, the rest are skipped and it moves to admission control
    • Most clusters use RBAC.
  • Sections: RBAC big picture, users and permissions, cluster-level users and permissions, pre-configured users and permissions.

RBAC big picture

Role-Based Access Control answers: which users can perform which actions against which resources.

User (subject) Action Resource Effect
Bao create Pods Can create Pods
Kalila list Deployments Can list Deployments
Josh delete ServiceAccounts Can delete ServiceAccounts
  • Enabled on most clusters; least-privilege, deny by default. You write allow rules to open things up.
  • Kubernetes has no deny rules, only allow rules, which makes implementation and troubleshooting simpler.

Users and permissions

Two key concepts: Roles define permissions; RoleBindings bind them to users.

Role read-deployments grants get, watch, list on Deployments in Namespace shield:

# Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: shield
  name: read-deployments
rules:
- verbs: ["get", "watch", "list"]     # allowed actions
  apiGroups: ["apps"]                 # on resources
  resources: ["deployments"]          # of this type

A Role does nothing until bound. This RoleBinding binds it to user sky:

# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-deployments
  namespace: shield
subjects:
- kind: User
  name: sky                           # name of the authenticated user
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: read-deployments              # bind this Role to the user above
  apiGroup: rbac.authorization.k8s.io

Deploying both lets authenticated user sky run kubectl get deployments -n shield. The username in the RoleBinding must be a string that matches an authenticated user.

Looking closer at rules

A Role's rules have three properties:

  • verbs: permitted actions
  • apiGroups: which API group
  • resources: which objects

Example (read access to Deployments):

# rules excerpt
rules:
- verbs: ["get", "watch", "list"]
  apiGroups: ["apps"]
  resources: ["deployments"]
apiGroup resource Kubernetes API path
"" pods /api/v1/namespaces/{namespace}/pods
"" secrets /api/v1/namespaces/{namespace}/secrets
"storage.k8s.io" storageclass /apis/storage.k8s.io/v1/storageclasses
"apps" deployments /apis/apps/v1/namespaces/{namespace}/deployments

An empty "" apiGroup means the core group; all other groups are strings in quotes.

Verbs map to HTTP methods (showing the REST nature of the API):

Kubernetes verb(s) HTTP method Common responses
create POST 201 created, 403 Access Denied
get, list, watch GET 200 OK, 403 Access Denied
update PUT 200 OK, 403 Access Denied
patch PATCH 200 OK, 403 Access Denied
delete DELETE 200 OK, 403 Access Denied

List resources and supported verbs when building rules:

$ kubectl api-resources --sort-by name -o wide
NAME          APIGROUP           KIND         VERBS
deployments   apps               Deployment   [create delete ... get list patch update watch]
ingresses     networking.k8s.io  Ingress      [create delete ... get list patch update watch]
pods                             Pod          [create delete ... get list patch update watch]
secrets                          Secret       [create delete ... get list patch update watch]
services                         Service      [create delete get list patch update watch]
<Snip>

* stands for all API groups, resources and verbs. This Role grants everything everywhere (demo only; you probably should not write rules like this):

# Role granting everything (demonstration)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: shield
  name: read-deployments
rules:
- verbs: ["*"]            # all actions
  resources: ["*"]        # on all resources
  apiGroups: ["*"]        # in every API group

Cluster-level users and permissions

Four RBAC objects:

Object Scope
Role Namespaced
RoleBinding Namespaced
ClusterRole Cluster-wide (all Namespaces)
ClusterRoleBinding Cluster-wide

They share an API sub-group and nearly identical YAML structure.

Powerful pattern: define a role once as a ClusterRole and bind it per Namespace with RoleBindings, reusing common roles. Figure 14.2: one ClusterRole applied to two Namespaces via two RoleBindings.

read-deployments as a ClusterRole (differences: kind: ClusterRole, no metadata.namespace):

# ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole                 # cluster-scoped role
metadata:
  name: read-deployments
rules:
- verbs: ["get", "watch", "list"]
  apiGroups: ["apps"]
  resources: ["deployments"]

Real-world example: Docker Desktop cluster-admin

Most clusters ship pre-created roles and bindings. This walkthrough uses the Docker Desktop multi-node cluster from The Kubernetes Book 3: Getting Kubernetes; other clusters differ in detail but not in principle. Docker Desktop writes a client certificate for an admin user into your kubeconfig, signed by the cluster's built-in CA, so the cluster trusts it.

$ kubectl config view
<Snip>
users:
- name: docker-desktop                    # Docker Desktop kubeconfig entry for the built-in user
  user:
    client-certificate-data: DATA+OMITTED # including client certificate
    client-key-data: DATA+OMITTED
<Snip>

docker-desktop is only a friendly name; the username kubectl uses is embedded in the certificate. Decode it (Linux-style systems only, needs jq, context set to Docker Desktop):

kubectl config view --raw -o json \
  | jq ".users[] | select(.name==\"docker-desktop\")" \
  | jq -r '.user["client-certificate-data"]' \
  | base64 -d | openssl x509 -text | grep "Subject:"

Subject: O=kubeadm:cluster-admins, CN=kubernetes-admin

Commands authenticate as user kubernetes-admin, member of group kubeadm:cluster-admins. (Certificates encode the username in CN and groups in O.) The CA signature makes it pass authN.

Many clusters grant admin through the cluster-admin ClusterRole, so the user or group must be bound to it (Figure 14.3).

$ kubectl describe clusterrole cluster-admin
Name:         cluster-admin
Labels:       kubernetes.io/bootstrapping=rbac-defaults
Annotations:  rbac.authorization.kubernetes.io/autoupdate: true
PolicyRule:
  Resources  Non-Resource URLs  Resource Names  Verbs
  ---------  -----------------  --------------  -----
  *.*        []                 []              [*]
             [*]                []              [*]

All verbs on all resources in all Namespaces: the equivalent of root, "powerful and dangerous". Which ClusterRoleBindings reference it?

$ kubectl get clusterrolebindings | grep cluster-admin
NAME                      ROLE
cluster-admin             ClusterRole/cluster-admin
kubeadm:cluster-admins    ClusterRole/cluster-admin

Inspect the kubeadm:cluster-admins binding:

$ kubectl describe clusterrolebindings kubeadm:cluster-admins
Name:         kubeadm:cluster-admins
Labels:       <none>
Annotations:  <none>
Subjects:                              # bind subjects (users) that are
  Kind   Name                          # members of the "kubeadm:cluster-admins" group
  ----   ----
  Group  kubeadm:cluster-admins
Role:                                  # to the ClusterRole
  Kind:  ClusterRole                   # called "cluster-admin"
  Name:  cluster-admin

Summary (Figure 14.4): the certificate identifies kubernetes-admin, in group kubeadm:cluster-admins, signed by the CA (passes authN); the ClusterRoleBinding kubeadm:cluster-admins binds that group to ClusterRole cluster-admin, which grants admin rights on all objects in all Namespaces.

Summarising authorization

AuthZ ensures authenticated users may perform actions. RBAC implements least privilege on a deny-by-default model. Roles and ClusterRoles grant permissions; RoleBindings and ClusterRoleBindings bind them to users.

14.4 Admission control

Runs right after authN and authZ; it is about policy. Two types:

Type Behaviour
Mutating Checks compliance and can modify requests
Validating Checks compliance but cannot modify requests (only reject)
  • Mutating controllers always run first.
  • Both apply only to requests that modify the cluster; reads are not subject to admission control.
  • Example:
    • a production policy requires env=prod on all new and updated objects. A mutating controller can add the label if missing
    • a validating controller can only reject if it is missing.

On Docker Desktop the API server uses the NodeRestriction admission controller:

$ kubectl describe pod kube-apiserver-desktop-control-plane \
    --namespace kube-system | grep admission
--enable-admission-plugins=NodeRestriction
  • Real clusters run many more. Example: the AlwaysPullImages mutating controller sets imagePullPolicy to Always on all new Pods, forcing every node's runtime to pull from the registry (no locally cached images)
    • this needs every node to have valid pull credentials.
  • If any admission controller rejects a request it is denied immediately without consulting the others; all must approve before a request runs.
  • Admission controllers are very important in real production clusters.

Summary points

  • Every API request carries credentials and must pass authN, authZ, then admission control, over a TLS connection.
  • Authentication: most clusters support client certificates; production should use enterprise IAM.
  • Authorization: pluggable, most commonly RBAC with four objects.
  • Admission: validating controllers reject non-compliant requests; mutating controllers modify them to comply.
Terms to carry forward
  • authN / authZ: authentication (who are you) / authorisation (what may you do).
  • 401 / 403: authentication failure / access denied.
  • RBAC: Role, RoleBinding, ClusterRole, ClusterRoleBinding; deny by default, allow rules only.
  • verbs, apiGroups, resources: the parts of a rule.
  • cluster-admin: root-equivalent ClusterRole.
  • CN / O in client certs: username / groups.
  • Mutating vs validating admission controllers; NodeRestriction, AlwaysPullImages.
