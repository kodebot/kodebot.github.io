The Kubernetes Book 17: Real-World Kubernetes Security

Source: Nigel Poulton and Pushkar Joglekar, The Kubernetes Book, 3rd ed. (Packt, 2025), ch. 17. Previous: The Kubernetes Book 16: Threat Modeling Kubernetes. Next: The Kubernetes Book: Terminology and Outro.

Takeaways
  • The chapter takes a security architect's high-level view, not cookbook recipes, across four areas: the software delivery pipeline, workload isolation, identity and access management, security monitoring and auditing.
  • Secure the supply chain: approved base images, controlled registry access, vulnerability scanning in CI/CD, scanning configuration as code, signing images, and a promotion workflow with quarantine.
  • Kubernetes does not support secure multi-tenant clusters: Namespaces are for grouping, quotas and RBAC, not security boundaries. Hard isolation needs separate clusters.
  • Containers share the host kernel, so for isolation virtual machines win; add AppArmor, SELinux, seccomp and capabilities, or use stronger runtimes (gVisor, Kata) via RuntimeClasses.
  • Plan for breach: audit, centralise logs, alert on privileged Pods, human exec sessions and internet access to the control plane, and migrate apps crawl, walk, run.

17.1 Security in the software delivery pipeline

Containers made it easier than ever to run dangerous code. This section secures the supply chain from a developer's laptop to production.

Image repositories

  • Images live in public and private registries, divided into repositories.
  • Public registries are the easiest way to push and pull, but:
    • protect the images you store there
    • do not trust images you pull from them
  • Some have official and community images
    • Official images are generally safer: vendor-provided, vetted, expected to follow good practice, regularly scanned and patched, sometimes supported
    • Community images are not vetted: use extreme caution
    • Always do due diligence.
  • Give developers a standard, frictionless way to obtain and consume images, so they do not feel the need to bypass it.

Use approved base images

  • Most images have a base layer plus further layers. Figure 17.1 (oversimplified): base layer = core OS and filesystem, middle = libraries and dependencies, top = your app
    • together they are the image.

  • Keep a small number of approved base images, derived from official images and hardened to corporate policy
    • Example: an official Alpine Linux image tweaked with patches, drivers and audit settings.
  • Figure 17.2: three apps on two approved bases. The left app builds on the approved Alpine base; the other two (web apps) build on an approved Alpine plus NGINX base.

  • Up-front effort, but the benefits are:
    • a standard set of drivers
    • known patches
    • standardised audit settings
    • less software sprawl (fewer unofficial bases)
    • simpler testing (a small set of known bases)
    • simpler updates (fewer bases to patch)
    • simpler troubleshooting
  • Developers can ignore OS concerns; you may also need fewer support contracts and suppliers.

Manage the need for non-standard base images

Bespoke needs are legitimate, so have a process to:

  1. Identify why an approved base cannot be used.
  2. Decide whether an approved base can be updated instead (and whether it is worth the effort).
  3. Determine the support implications of a wholly new image.

Usually update an existing base (for example add a GPU device driver) rather than introduce a new one.

Control access to images

  • A secure, practical option: private registries inside your own firewalls, controlling deployment, replication and patching, and integrating with identity providers such as Active Directory.
  • Otherwise use private repositories on public registries, choosing and configuring the registry with great care.
  • Host only approved images (trusted sources vetted by infosec) and restrict push and pull to approved users.
  • Also:
    • restrict which cluster nodes have internet access (your registry may be on the internet)
    • let only authorised users and nodes push
    • if nodes must pull from a public registry, limit internet access to the registry's addresses and ports
    • apply strict RBAC on the registry: for example developers push and pull dev and test repositories, operations teams production repositories
    • consider letting only build nodes, or only automated build systems, push to specific repositories

Moving images from non-production to production

Development environments have fewer rules and may use non-standard images developers later want in production. Measures to keep production safe:

Vulnerability scanning is top of the list.

  • Scans images at the binary level against databases of known vulnerabilities (CVEs).
  • Integrate it into CI/CD, with policies that fail builds and quarantine images containing certain categories of vulnerability (for example fail on known critical ones).
  • Solutions differ in how customisable their policies are. Example: a Python TLS-verification method may be vulnerable to DoS with many wildcards in the Common Name
    • if you never use Python that way you may mark it a false positive, which not every scanner allows.

Configuration as code

  • Scanning app code is accepted hygiene; scanning Dockerfiles, Kubernetes YAML, Helm charts and other config is less common.
  • Well-publicised example:
    • an IBM data science experiment embedded private TLS keys in its container images, so attackers could pull the image and get root on the nodes
    • A security review of the Dockerfiles would have prevented it.
  • Tools implementing policy as code rules are advancing.

Sign container images

  • Developers cryptographically sign images and consumers verify them at pull and run time, giving confidence the image is correct and untampered
    • Kubernetes and most runtimes support it, usually implemented by the runtime (Figure 17.3).
  • Use tools that define and enforce enterprise-wide signing policies, so it is not left to individuals.

Image promotion workflow. Your pipelines should include as many of these as possible:

  • policies forcing signed images
  • network rules restricting which nodes push and pull
  • RBAC protecting repositories
  • approved base images
  • scanning for known vulnerabilities
  • promotion and quarantine based on scan results
  • review and scan of infrastructure-as-code files

The list is not an exact workflow.

17.2 Workload isolation

Starts at the cluster level, then the runtime level, then infrastructure outside the cluster such as firewalls.

Cluster-level workload isolation

  • Kubernetes does not support secure multi-tenant clusters. The only way to isolate two workloads is separate clusters on separate hardware.
  • The only way to divide a cluster is Namespaces:
    • little more than grouping resources and applying limits, quotas and RBAC rules
    • They do not stop a compromised workload in one Namespace affecting others, so never run hostile workloads on the same cluster
    • Use Namespaces, but not as security boundaries.
Model Meaning Fit
Soft multi-tenancy Multiple trusted workloads on shared infrastructure (no absolute guarantee of non-interference) Example: an e-commerce app with a web front-end service and a back-end recommendation service, each with its own limits managed by different teams: one cluster, one Namespace each
Hard multi-tenancy Untrusted, potentially hostile workloads on shared infrastructure Not currently possible: workloads needing a strong boundary need separate clusters

Hard-boundary examples:

  • production versus non-production
  • different customers
  • sensitive projects and business functions

The Kubernetes project has a **Multitenancy Working Group** working on models, so future releases may offer better hard multi-tenancy.

Node isolation

  • Apps needing non-standard privileges (run as root, non-standard syscalls) may not justify their own cluster, but may justify a ring-fenced subset of worker nodes, limiting a compromise to workloads on the same node.
  • Apply defence in depth: stricter audit logging and tighter runtime defences on those nodes.
  • Target workloads to nodes with labels, affinity and anti-affinity rules, and taints.

Runtime isolation

  • For isolation, virtual machines win
    • Most container platforms (Docker, containerd, CRI-O) use namespaced containers: all containers share the host kernel, isolated by kernel constructs (namespaces, cgroups) never designed as strong security boundaries
    • A hypervisor gives every VM its own kernel with hardware enforcement.
  • Containers can be hardened with AppArmor, SELinux, seccomp, capabilities and user namespaces; runtimes and hosted services default sensibly, but troubleshooting is complex.
  • Consider other runtime classes: gVisor and Kata Containers give stronger isolation and integrate easily through the CRI and RuntimeClasses.
  • Kubernetes can also orchestrate VMs, serverless functions and WebAssembly.

Options summary:

Option Trade-off
Virtual machines Dedicated kernel per workload; excellent isolation, comparatively slow and resource-hungry
Namespaced containers Share the host kernel; fast and lightweight, extra effort to isolate
Every container in its own VM Combines container versatility with VM security via lightweight VMs, but loses much of containers' appeal; not popular
Different runtime classes Run everything as containers but send workloads needing stronger isolation to a suitable runtime
Wasm containers OCI packaging for Wasm apps; at run time they execute in a secure deny-by-default Wasm host (chapter 9)

Network isolation

  • Firewalls are part of layered security; the goal is to allow only authorised communications.
  • Pods talk over the pod network, but Kubernetes does not implement it: the CNI plugin model lets third parties do
    • Plugins fall into two broad categories, overlay and BGP, each affecting firewalls differently.

Overlay networking

  • Most clusters use a simple flat overlay that hides network complexity: nodes could be on ten networks joined by routers, yet Pods see one flat network (Figure 17.4: four nodes on two networks, Pods on a single overlay).
  • Overlays use VXLAN to encapsulate container packets over a flat Layer-2 network on top of Layer-3 infrastructure (Figure 17.5)
    • Encapsulation hides the original source and destination IPs, so firewalls struggle to know what is going on.

BGP

  • BGP powers the internet: a simple, scalable protocol creating peer relationships that share routes.
  • Book analogy:
    • you want to send a birthday card to a lost friend
    • Your child's school friend's parents are still in touch, so the card passes child, school friend, parents, friend
    • BGP routing works through a network of peers helping each other find routes.
  • BGP does not encapsulate packets, so firewalls have an easier time (Figure 17.6: no encapsulation).

Impact on firewalls

  • Firewalls allow or deny by source and destination address (for example allow 10.0.0.0/24, deny 192.168.0.0/24).
  • With an overlay, all traffic is encapsulated, so only firewalls that can open packets and inspect contents can decide usefully. If yours cannot, consider a BGP pod network.
  • Choose physical firewalls (dedicated hardware, usually run by a central team), host-based firewalls (OS features, run by the OS team), or both (often most secure)
    • Consider whether your organisation's change procedure for physical firewalls suits Kubernetes.

Packet capture

Pod IPs are sometimes obscured by encapsulation and are dynamic and recycled (IP churn), so they identify workloads poorly. Being able to associate IPs with Kubernetes identifiers (Pod IDs, Service aliases, container IDs) during packet capture is very useful.

17.3 Identity and access management (IAM)

  • Kubernetes has robust RBAC that integrates with existing IAM providers: Active Directory, other LDAP systems, cloud IAM
    • Organisations typically already have a central IAM tied to HR.
  • Joiners get an identity in the corporate IAM
    • with the right groups they get Kubernetes permissions automatically. Leavers are removed by the HR process and their access stops. RBAC has been stable since v1.8
    • use its full capabilities.

Managing remote SSH access to cluster nodes

Almost all administration is REST calls to the API server, so users rarely need SSH to nodes. Reserve it for:

  • node management you cannot do via the Kubernetes API
  • break-the-glass activities, such as an API server outage
  • deep troubleshooting

Multi-factor authentication (MFA)

Accounts with root on the API server and on nodes are prime targets for attackers and disgruntled employees. Protect them with MFA:

  • Stage 1: tests knowledge of a username and password.
  • Stage 2: tests possession of something, like a one-time password.

Also secure workstations and user profiles that have kubectl installed.

17.4 Security monitoring and auditing

  • No system is 100% secure; plan for breach
    • Be able to recognise a breach and build a detailed, non-repudiable timeline: what, how, when and who (in extreme cases called upon in court)
    • Auditing also finds weaknesses in your security
    • Do not go to production without robust auditing and monitoring.

Baseline best practices

  • The Center for Information Security (CIS) publishes an industry-standard Kubernetes benchmark
    • Aqua Security's kube-bench runs the CIS tests and reports. It cannot inspect control plane nodes of hosted Kubernetes services.
  • Run kube-bench during node provisioning and pass or fail the node on the result. Reports also serve as before and after baselines around an incident.

Container and Pod lifecycle events

Pods and containers are ephemeral, so expect many create and terminate events. Configure log retention to keep logs from terminated Pods; the runtime may also keep lifecycle logs.

Forensic checkpointing

  • Forensics collects and examines evidence to build a trail of events when you suspect malice. Ephemeral containers made that hard.
  • CRIU
    • (Checkpoint/Restore in Userspace) can silently capture a running container's state and restore it in a sandbox for analysis
    • At the time of writing it is alpha in Kubernetes and only CRI-O supports it.

Application logs

Some apps log to stdout or stderr (picked up with container logs); others write proprietary files in bespoke locations. Check each application and configure collection so you miss nothing.

Actions performed by users

  • Most admin goes through the API server, where all requests should be logged. But attackers might get SSH to control plane nodes and manipulate objects directly, including etcd.
  • Limit SSH, add MFA, log all SSH activity to a secure aggregator, and consider requiring two competent people for all SSH to control plane nodes.

Managing log data

Container density produces massive log and audit data; specialised tools store it and analyse it proactively and after events.

Alerting for security-relevant events

Some events deserve immediate investigation:

Event Why
Privileged Pod creation by a human Privileged Pods can often get root on the node; policy normally forbids them, and rare legitimate ones come from automated processes with service accounts
Exec sessions by humans Shell-like access, normally for troubleshooting only; investigate others and consider deleting the session to prevent tampering
Attempts to reach the cluster from the internet Control plane access from the internet is usually blocked; watch for successful and failed attempts, and treat a success as a misconfiguration to fix

17.5 Migrating existing apps to Kubernetes: crawl, walk, run

  • Crawl: threat-model your existing apps to learn their current posture (for example which use TLS).
  • Walk: keep the posture unchanged during migration (an app without TLS stays without TLS).
  • Run:
    • improve security after migration, starting with simple non-critical apps and working up to mission-critical ones
    • deepen gradually, for example one-way TLS first, then two-way TLS.
  • Key point: do not change an app's security posture as part of migrating it, or you may misdiagnose problems (was it the security change or the migration?).

17.6 Real-world example

CVE-2019-5736 (February 2019) let a container process running as root gain root on the worker node and on all containers on the host. Three things from this chapter would have prevented it:

  • image vulnerability scanning (it has a CVE number, so scanners would have found it)
  • not running processes as root
  • enabling SELinux

Even if scanners missed it, policies preventing root containers and standard SELinux policies would have blocked exploitation.

Summary points

  • Secure the pipeline:
    • approved base images, controlled registries, scanning, signing
    • isolate workloads at cluster, node and runtime level
    • use IAM with MFA
    • audit and alert
    • migrate carefully.
  • The chapter intends you to go and start securing your own clusters.
Terms to carry forward
  • Approved base image: a small set of hardened bases derived from official images.
  • Vulnerability scanning, configuration as code, image signing, promotion and quarantine.
  • Soft vs hard multi-tenancy: trusted workloads on Namespaces vs separate clusters.
  • gVisor, Kata Containers, RuntimeClass: stronger runtime isolation.
  • Overlay (VXLAN encapsulation) vs BGP: effect on firewalls.
  • IP churn: recycled, dynamic Pod IPs.
  • MFA, break-the-glass.
  • kube-bench, CIS benchmark.
  • CRIU, forensic checkpointing.
  • Crawl, walk, run.
