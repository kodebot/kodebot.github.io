Understanding Distributed Systems 1: Preface and introduction

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd edition (v2.0.0, March 2022), preface, chapter 1 and the Part I introduction. Book site: https://understandingdistributed.systems/. Next: Understanding Distributed Systems 2: Reliable links.

The one-minute version

A distributed system is a group of nodes (a phone, a browser, a process) that cooperate by exchanging messages over communication links to achieve a task. Building one raises five recurring challenges, which are the five parts of the book: communication, coordination, scalability, resiliency, maintainability. Everything else in the book is a technique for one of them.

Preface (the author's pitch)

  • Learning to build large-scale distributed systems is hard not for lack of material but because it is spread out: lots at the theory end (academic papers) and at the practice end (engineering blogs), little in the middle
    • The book brings the core theory and practice together "with just enough details and external references to dive deeper"
    • The author's words: "the guide I wished existed when I first started out."
  • For:
    • developers on the backend of web or mobile apps (or who want to be). You need the network stack, data consistency models, scalability and reliability patterns, observability practices
    • without them you spend hours debugging and re-architecting.
  • Not for: experts with years of highly available, fault-tolerant, million-user systems: they want depth, this book gives breadth.
  • The second edition is a complete rewrite of the first
    • every page reviewed. Digital version is updated occasionally (hence the version number)
    • feedback to roberto@understandingdistributed.systems.

Chapter 1: Introduction

"A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable." (Leslie Lamport; the book gives the quote without a source URL)

Why build one at all?

  • Some applications are inherently distributed: the web (browsers on billions of devices).
  • High availability: survive single-node failures. Dropbox replicates your data across nodes so losing one loses nothing.
  • Workloads too big for one node: Google handles tens of thousands of search requests per second worldwide.
  • Performance impossible on one node: Netflix streams at high resolution because a data centre is close to you.

1.1 Communication

  • Nodes must talk over the network. Loading a page: the browser resolves the server's IP from the URL, sends an HTTP request, the server answers.
  • Questions: how are messages represented on the wire? What if the network is briefly out, or a faulty switch flips bits? How do you stop an intermediary from snooping?
  • You would like a library to hide all of it, but abstractions leak (Joel Spolsky's "The Law of Leaky Abstractions", https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/), so you must understand the stack.

1.2 Coordination

Nodes need coordination to work toward one goal, hard under failure. The two generals thought experiment: two generals command separate armies and must agree on an attack time; messengers may be captured.

  • General 1 proposes a time but cannot know it was delivered; General 2 confirms, but cannot know the confirmation arrived, and so on
    • No number of confirmation rounds makes either certain
    • Part II covers the fundamental algorithms for coordination.

1.3 Scalability

  • Performance = how efficiently the application handles load (anything consuming CPU, memory, bandwidth; e.g. concurrent users, write-to-read ratio).
  • Measured by throughput (requests handled per second) and response time (seconds from sending a request to receiving the response).
  • As load grows the app hits capacity:
    • a resource is exhausted, performance plateaus or worsens, and eventually most operations fail or time out
    • The throughput of requests handled without errors and with low response times is its goodput.
  • Capacity depends on architecture, implementation and physical limits (memory, clock cycles, network bandwidth and latency)
    • An app is scalable if more load does not degrade performance, which needs the ability to raise capacity at will.
  • Scaling up
    • (better hardware) hits a wall when such hardware does not exist; scaling out (more commodity machines working together) is the alternative
    • Cloud made machines trivial to obtain: 2006, Amazon launched AWS including EC2 (https://aws.amazon.com/ec2/)
    • Part III covers the patterns.

1.4 Resiliency

  • Resilient = keeps doing its job despite failures
    • At scale "anything that can go wrong will go wrong": every component has some failure probability, and more components and operations mean more failures
    • A failure can raise the probability of another one if components are not isolated.
  • Availability
    • = uptime / (uptime + downtime), described in nines. Three nines is typically acceptable to users
    • above four nines is highly available (reference: AWS Well-Architected Framework, Availability).
Availability Downtime per day
90% (one nine) 2.40 hours
99% (two nines) 14.40 minutes
99.9% (three nines) 1.44 minutes
99.99% (four nines) 8.64 seconds
99.999% (five nines) 864 milliseconds
  • A system must embrace failures: redundancy, fault isolation, self-healing (Part IV).

1.5 Maintainability

  • Most software cost is after initial development: fixing bugs, adding features, operating it. Aim to make it easy to modify, extend and operate.
  • "Any change is a potential incident waiting to happen." Good tests (unit, integration, end-to-end) are the minimum, then safe releases that do not hurt availability.
  • Operators must monitor health, investigate degradations and restore service when it cannot self-heal, which needs behaviour changes without code changes (toggle a feature flag, scale out via configuration).
  • Historically developers, testers and operators were separate teams
    • microservices and DevOps
      • changed that: the team that builds a system tests and operates it ("no better way to discover where a system falls short than being on call for it")
      • Part V.

1.6 Anatomy of a distributed system

The book looks at backend applications on commodity machines implementing a business service, from three views:

  • Machines communicating over network links;
  • Run time: software processes communicating via inter-process communication (IPC) such as HTTP;
  • Implementation: loosely coupled components (services) communicating via APIs.

A service implements one part of the system's capabilities. At its core is business logic, exposing interfaces: some define operations offered to users, others operations the service invokes on other services (data stores, message brokers).

Processes cannot call each other's interfaces directly, so adapters connect IPC mechanisms to service interfaces: an inbound adapter (part of the API) handles requests from an IPC mechanism like HTTP by invoking service-interface operations; an outbound adapter gives business logic access to external services like data stores.

  • This is the ports and adapters architecture (http://wiki.c2.com/?PortsAndAdaptersArchitecture): business logic does not depend on technical details
    • technical details depend on it (dependency inversion principle, https://en.wikipedia.org/wiki/Dependency_inversion_principle)
      • In the book's Figure 1.2 the business logic uses a repository interface implemented by a PostgreSQL adapter, while an HTTP adapter handles incoming requests by calling service-interface operations.
  • Conventions for the book:
    • a process running a service is a server
    • a process sending requests is a client (a process can be both)
      • Each service instance runs in a single server process, and a process has a single thread, to avoid distracting implementation detail.

Part I: Communication (introduction)

"The network is reliable." (Fallacies of distributed computing, L. Peter Deutsch: listed as a fallacy, i.e. false.)

IPC is what makes distributed systems distributed. Processes agree on rules for formatting and processing data: network protocols, arranged in a stack where each layer builds on the one below (lower = closer to the hardware). Data moves down the stack at the sender and up at the receiver.

  • Link layer: protocols on local links (Ethernet, Wi-Fi); switches forward Ethernet packets by destination MAC address.
  • Internet layer:
    • routes packets between machines across networks
    • IP delivers on a best-effort basis (packets can be dropped, duplicated, corrupted)
    • routers forward to the next router.
  • Transport layer: carries data between two processes, addressed by port numbers; TCP builds a reliable channel on IP.
  • Application layer: high-level protocols (HTTP, DNS); where your apps usually live.
  • Abstractions sometimes leak
    • knowing the lower layers is needed to troubleshoot, and appreciating what happens in a network call makes you a better systems builder (reference for the suite: https://en.wikipedia.org/wiki/Internet_protocol_suite).

Roadmap of Part I: ch. 2 builds a reliable channel (TCP) on an unreliable one (IP), "a common pattern" in the book; ch. 3 a secure channel (TLS) on a reliable one; ch. 4 DNS, a distributed, hierarchical, eventually consistent key-value store (first taste of eventual consistency, see ch. 10); ch. 5 APIs: how loosely coupled services talk, via a RESTful HTTP API built on these protocols.
