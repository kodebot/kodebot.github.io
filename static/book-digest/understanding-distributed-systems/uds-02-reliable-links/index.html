Understanding Distributed Systems 2: Reliable links

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 2. Previous: Understanding Distributed Systems 1: Preface and introduction. Next: Understanding Distributed Systems 3: Secure links.

[!abstract] The one-minute version IP only delivers on a best-effort basis (it may drop, duplicate or corrupt packets). TCP builds a reliable byte stream between two processes on top of it with sequence numbers, acknowledgements, retransmission and checksums, plus two stability mechanisms: flow control (do not overwhelm the receiver) and congestion control (do not flood the network). Both make new connections start slowly and make latency decide bandwidth, which is why you reuse connections and put servers near clients. UDP drops all of that for custom protocols.

Addressing and routing (internet layer)

  • Reaching a node needs a way to address it and a way to route packets across routers.
  • IP handles addressing. Example: IPv6 has a 128-bit address space, so 2^128 addresses.
  • A router consults a local routing table mapping a destination address to the next router on the path
    • Building and communicating the tables across routers is the job of the Border Gateway Protocol (BGP) (RFC 4271: https://datatracker.ietf.org/doc/html/rfc4271).
  • IP gives no guarantee the data arrives (e.g. an overloaded router may drop packets)
    • TCP (RFC 793: https://tools.ietf.org/html/rfc793) is the transport-layer protocol that exposes a reliable channel between two processes: a stream of bytes arriving in order, without gaps, duplication or corruption.

2.1 Reliability

To create the illusion of a reliable channel TCP:

  1. Partitions the stream into segments, sequentially numbered, so the receiver detects holes and duplicates.
  2. Requires the receiver to acknowledge every segment; if no ack arrives, a timer fires on the sender and the segment is retransmitted.
  3. Uses a checksum so the receiver can verify the segment was not corrupted in transit.

2.2 Connection lifecycle

A connection must be opened before data flows. The OS tracks connection state through a socket. High-level states: opening, established (data transfer), closing (really there are more states: https://en.wikipedia.org/wiki/Transmission_Control_Protocol).

A server must be listening first. TCP opens a connection with a three-way handshake:

  1. Sender picks a random sequence number x and sends SYN.
  2. Receiver increments x, picks a random y, replies SYN/ACK.
  3. Sender increments both numbers and replies ACK plus the first bytes of application data.

Sequence numbers make in-order, gap-free delivery possible.

  • The handshake costs a full round trip with no application data, so bandwidth is essentially zero until the connection is open
    • The lower the round-trip time (RTT), the faster it opens: servers closer to clients cut this cold-start penalty.
  • Closing releases resources on both ends and takes several round trips. If another transmission will follow soon, keep the connection open to avoid the cold-start tax again.
  • Closing a socket does not dispose of it at once:
    • it goes to a waiting state, TIME_WAIT, lasting several minutes and discarding any segments received
    • It stops delayed segments from a closed connection being taken as part of a new one
    • But if many connections open and close quickly, sockets in TIME_WAIT pile up until the maximum number of sockets is reached and new connection attempts fail
    • Another reason processes use connection pools.

2.3 Flow control

A backoff mechanism that stops the sender from overwhelming the receiver.

  • The receiver stores incoming segments in a receive buffer until the application processes them, and reports the buffer size to the sender in every acknowledgement (in the ack headers)
    • A well-behaved sender never sends more than fits.
  • Compared to service-level rate limiting (reject a request once a quota is exceeded, see section 28.3), except TCP rate-limits per connection instead of per API key or IP address.

2.4 Congestion control

TCP also guards against flooding the underlying network.

  • The sender keeps a congestion window:

    • the total number of outstanding segments sendable without an acknowledgement
    • The smaller it is, the fewer bytes in flight and the less bandwidth used.

  • At connection start the window is a system default; for each acknowledged segment it grows exponentially up to an upper limit

    • So the network's full capacity cannot be used right after a connection opens
    • A shorter RTT lets the sender reach full bandwidth quicker.

  • When the sender detects a missed acknowledgement via timeout, congestion avoidance kicks in and the window shrinks

    • afterwards time grows it by some amount and timeouts shrink it (the growth function is described in the CUBIC paper cited by the book).

  • The window is the max bytes sendable before an acknowledgement, and an ack needs a full round trip, so the theoretical maximum:

    Bandwidth = WinSize / RTT

    Bandwidth is a function of latency (see "bandwidth-delay product": https://en.wikipedia.org/wiki/Bandwidth-delay_product). TCP tunes the window but cannot change RTT; the shorter the RTT, the better the network is used: more reason to place servers geographically close to clients.

2.5 Custom protocols

  • TCP's reliability and stability cost lower bandwidth and higher latency than the network can deliver
    • Drop them and you get UDP (User Datagram Protocol, RFC 768: https://datatracker.ietf.org/doc/html/rfc768): a connectionless transport protocol.
  • UDP has no byte-stream abstraction:
    • clients send discrete packets of limited size called datagrams
    • No sequence numbers, no acks, no flow or congestion control: "lean and bare-bones"
    • It is used to bootstrap custom protocols with some but not all of TCP's guarantees
    • (HTTP/3 is based on UDP to avoid some of TCP's shortcomings.)
  • Example: multiplayer games.
    • Clients sample gamepad events several times per second and send them to a server holding the global game state
    • the server sends snapshots back several times per second. If a snapshot is lost, retransmitting it is worthless: the game has moved on. UDP shines
    • TCP would try to redeliver and degrade the experience.
