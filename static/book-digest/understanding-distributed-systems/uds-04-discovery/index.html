Understanding Distributed Systems 4: Discovery

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 4. Previous: Understanding Distributed Systems 3: Secure links. Next: Understanding Distributed Systems 5: APIs.

The one-minute version

Before opening a connection you must discover the IP address of the remote process. The usual way is DNS, the "phone book of the internet": a distributed, hierarchical, eventually consistent key-value store (RFC 1035: https://datatracker.ietf.org/doc/html/rfc1035). Resolution walks a hierarchy (root, top-level domain, authoritative) but caching with a TTL makes it fast; the TTL is a trade-off, and DNS can easily become a single point of failure.

How a browser resolves www.example.com

(The process is similar for other clients. A deep-dive video is cited: https://www.youtube.com/watch?v=drWd9HIhJdU.)

  1. The browser checks its local cache. If found, done; otherwise it asks a DNS resolver, a server typically hosted by your ISP.
  2. The resolver resolves iteratively on behalf of its clients ("why iterative will be obvious in a moment"). It checks its own cache; if missing, it queries a root name server (root NS).
  3. The root NS maps the top-level domain (TLD) (.com) to the address of the name server responsible for it.
  4. The resolver asks the TLD name server about example.com.
  5. The TLD name server maps example.com to the address of the authoritative name server for the domain.
  6. The resolver queries the authoritative name server for www.example.com, which returns the IP address.
  • For a subdomain like news.example.com, the authoritative server would return the address of the name server responsible for the subdomain, and one more request is needed.
  • The original protocol sent plain-text messages mostly over UDP for efficiency
    • Anyone watching could snoop, so the industry mostly moved to secure alternatives such as DNS over TLS (RFC 7858: https://en.wikipedia.org/wiki/DNS_over_TLS).
  • Worst case:
    • several round trips
    • Its beauty: the address of a root name server is all you need to resolve any hostname
    • But it would be slow if every request did several lookups, and the global resolution load is enormous, so caching is used: the browser, operating system and DNS resolver all cache, because name-to-IP mappings change rarely.

TTL: how caches expire

  • Every record has a time to live (TTL) telling caches how long the entry is valid
    • But clients may not enforce it: after changing a DNS entry, a small number of clients may still connect to the old address long after the TTL expired.
  • Trade-off:
    • a long TTL means many clients do not see a change for a long time
    • too short increases load on name servers and the average response time (clients resolve more often).
  • If your name server becomes unavailable, the smaller the TTL, the more clients are impacted.

DNS as a single point of failure

  • If your DNS name server is down, clients cannot find your application's IP and cannot connect: this can cause massive outages (example cited: the 2016 DDoS attack on Dyn, https://en.wikipedia.org/wiki/2016_Dyn_cyberattack).
  • Observation:
    • DNS would be more robust if caches served stale entries when they cannot reach a name server, rather than treating TTLs as time bombs
    • Since entries rarely change, a stale entry is arguably far more robust than none
    • The principle that a system should keep functioning even when a dependency is impaired is called static stability; the resiliency part returns to it.
Terms to carry forward

DNS · resolver · root name server · TLD · authoritative name server · iterative resolution · TTL · DNS over TLS · single point of failure · static stability.
