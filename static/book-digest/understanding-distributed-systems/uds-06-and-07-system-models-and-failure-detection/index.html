Understanding Distributed Systems 6 and 7: Part II intro, system models, failure detection

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), Part II introduction, chapters 6 and 7. Previous: Understanding Distributed Systems 5: APIs. Next: Understanding Distributed Systems 8: Time.

Takeaways
  • System model = assumptions about links, processes and timing, so you can reason about algorithms without implementation detail.
  • Links: fair-loss (lose and duplicate) becomes reliable (exactly once) by de-duplicating at the receiver; add authentication for an authenticated reliable link.
  • Processes: arbitrary-fault (Byzantine), crash-recovery (the book's default), crash-stop.
  • Timing: synchronous (unrealistic), asynchronous (many problems unsolvable), partially synchronous (the book's default).
  • Failure detection: you cannot tell slow from crashed from lost, so use timeouts, pings or heartbeats; a perfect detector cannot exist.

Chapter 6: System models

A system model encodes expectations about processes, communication links and timing: a set of assumptions that lets you reason about distributed systems ignoring the complexity of the technologies that implement them.

Communication links

  • Fair-loss link: messages may be lost and duplicated, but if the sender keeps retransmitting, eventually the message is delivered.
  • Reliable link: each message is delivered exactly once, no loss or duplication. Can be built on a fair-loss link by de-duplicating at the receiver.
  • Authenticated reliable link: reliable, plus the receiver can authenticate the sender.
  • They are abstractions, but they let you verify algorithm correctness. As seen: TCP gives reliable transmission (and more), TLS gives authentication (and more).

Processes (types of failures expected)

  • Arbitrary-fault model:
    • a process may deviate from its algorithm in arbitrary ways: crashes or odd behaviour from bugs or malice
    • Also called the "Byzantine" model (historical reasons; "The Byzantine Generals Problem", https://lamport.azurewebsites.net/pubs/byz.pdf)
    • It can be proven that such a system can tolerate up to one third of faulty processes and still work correctly (the book writes "3 1" for 1/3)
    • Used for safety-critical systems (airplane engines, nuclear plants) and where no single entity controls all processes (e.g. Bitcoin); out of the book's scope.
  • Crash-recovery model: the process follows its algorithm but can crash and restart at any time, losing its in-memory state. The book generally assumes this one.
  • Crash-stop model:
    • the process follows its algorithm but does not come back after a crash
    • Seems unrealistic for software crashes, but models unrecoverable hardware faults and generally simplifies algorithms.

Timing

  • Synchronous model:
    • sending a message or running an operation never takes more than a fixed time
    • Not realistic: network messages can take very long, and processes slow down (garbage-collection cycles, page faults).
  • Asynchronous model:
    • operations can take an unbounded time
    • Many problems cannot be solved this way (algorithms may get stuck and make no progress), but it is simpler, so algorithms for it are easier to implement (see the unreliable failure detectors paper: https://www.cs.utexas.edu/~lorenzo/corsi/cs380d/papers/p225-chandra.pdf).
  • Partially synchronous model: behaves synchronously most of the time; "typically representative enough of real-world systems".

The book's default: fair-loss links, crash-recovery processes, partial synchrony. For other models see Introduction to Reliable and Secure Distributed Programming (https://www.distributedprogramming.net/). Models are abstractions ("all models are wrong": https://en.wikipedia.org/wiki/All_models_are_wrong); question their assumptions and imagine how algorithms relying on them could break in practice.

Chapter 7: Failure detection

When a client sends a request and no response comes back, it is impossible to tell whether the server is slow, crashed, or a message was lost or delayed by the network. Worst case the client waits forever; the best it can do is an educated guess after some time.

  • Configure a timeout:
    • if no response arrives in time, treat the server as unavailable and throw an error or retry
    • The hard part is choosing the duration: too short wrongly assumes the server is down; too long wastes time waiting
    • A perfect failure detector cannot be built.
  • A process need not wait until it sends something: it can proactively maintain a list of available processes with pings or heartbeats.
    • Ping:
      • a periodic request to another process, expecting a reply within a time frame
      • no reply triggers a timeout and the destination is marked unavailable, but pings continue to detect when it returns.
    • Heartbeat:
      • a message a process periodically sends to another
      • if it does not arrive within a time frame the destination triggers a timeout and treats the sender as unavailable
      • if the process later resumes sending, it is considered available again.
  • Pings and heartbeats suit processes that interact frequently and where an action must be taken as soon as one becomes unreachable
    • Otherwise detecting failures at communication time is good enough.
