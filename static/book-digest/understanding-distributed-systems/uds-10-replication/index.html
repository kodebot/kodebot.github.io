Understanding Distributed Systems 10: Replication

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 10. Previous: Understanding Distributed Systems 9: Leader election. Next: Understanding Distributed Systems 11: Coordination avoidance.

[!abstract] The one-minute version Replication keeps copies of data on several processes for availability (switch to a copy if one dies) and scalability/performance (more replicas, more concurrent clients). The hard part is keeping replicas consistent despite failures. Raft does it with state machine replication: a leader logs operations and replicates the log; an entry is committed once a majority has it. That solves consensus. What a client sees depends on the consistency model (linearizable, sequential, eventual), and CAP/PACELC say you pay for stronger guarantees in availability or latency. Chain replication is an alternative that moves coordination off the critical path.

Raft's replication (state machine replication)

  • Raft offers the strongest consistency guarantee:
    • to clients, the data appears stored on a single process even though it is replicated
      • Paxos is arguably the most popular protocol with this guarantee ("Paxos Made Simple": https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)
    • the book uses Raft as more understandable (https://raft.github.io/raft.pdf).
  • Idea:
    • a single leader broadcasts operations that change its state to the followers (replicas)
    • If followers execute the same operations in the same order, they end in the same state
    • A large part of the algorithm handles failures: any process can fail and the network can lose messages.
  • Why "state machine":
    • each process is a state machine (https://en.wikipedia.org/wiki/Finite-state_machine) moving between states in response to inputs
    • Deterministic machines with identical input in identical order stay consistent, so a failed one is replaceable by any copy
    • Powerful for making any service fault-tolerant, if it can be modelled that way.
  • Example:
    • a fault-tolerant key-value store: each node is a state machine with put(k, v) and get(k) over a dictionary
    • if every node executes the same puts, they have the same state.

10.1 How it works

The system starts with a leader elected by chapter 9's algorithm (no external dependencies). Only the leader changes replicated state, by storing operations in a local log that it replicates.

  • A log is an ordered list of entries, each with: the operation to apply (e.g. assign 3 to x; must be deterministic, but can be complex such as compare-and-swap or a multi-operation transaction), its index in the log, and the leader's election term.
  • Flow:
    • the leader appends the entry to its log (not applied yet), then sends an AppendEntries request to each follower
    • (It is also sent periodically with no entries: it doubles as the heartbeat.) A follower appends the entry to its own log without executing it and acknowledges
    • When a majority has acknowledged, the leader considers the entry committed and executes it on its local state
    • It tracks the highest committed index and sends it in later AppendEntries; a follower applies an entry only after learning the leader committed it.
  • Quorum:
    • the leader waits for just a majority, so with 2f + 1 followers the system tolerates f failures
    • A committed entry is durable and will eventually be executed by all processes, not only the original majority.
  • Leader failure:
    • a follower is elected. But a majority is enough to progress, so some processes may be behind
    • to avoid an out-of-date leader, a process cannot vote for a candidate with a less up-to-date log: a process cannot win unless it contains all committed entries
      • Comparing logs: compare the term and index of the last entries
    • the higher term is more up to date
    • with the same term, the longer log wins
      • Since election needs a majority and the winner's log must be at least as up to date as any other in that majority, the winner has all committed entries.
  • Undeliverable AppendEntries:
    • the leader retries indefinitely until a majority appended it
    • Retries are harmless because the request is idempotent and followers ignore entries already appended.
  • Follower comes back:
    • each AppendEntries includes the index and term of the entry preceding the new one
    • If the follower cannot find it, it rejects (to avoid a gap)
    • The leader retries with the last two entries (hence "Entries", not "Entry"), then three, and so on, to find the latest entry where the logs agree, delete the follower's entries after it, and append the leader's entries from there
    • (In practice there are ways to reduce the number of messages.)

10.2 Consensus

State machine replication solves consensus (https://en.wikipedia.org/wiki/Consensus_(computer_science)): a group of processes must decide a value so that

  • every non-faulty process eventually agrees on a value;
  • the final decision is the same everywhere;
  • the value was proposed by some process.

Another view: the API of a write-once register (WOR) (a thread-safe, linearizable register written once, read many times; "Paxos made Abstract": https://maheshba.bitbucket.io/blog/2021/11/15/Paxos.html). Raft's replicated log is a sequence of WORs, so Raft is a sequence of consensus instances.

  • Uses: agreeing on who acquires a lease; state machine replication itself.
  • You will almost never implement it yourself (nor want to:
    • "Paxos Made Live", https://static.googleusercontent.com/media/research.google.com/en//archive/paxos_made_live.pdf)
    • Use off-the-shelf coordination services such as etcd (https://etcd.io/) and ZooKeeper (https://zookeeper.apache.org/), which replicate their state with consensus, expose a hierarchical key-value store, and let clients watch for changes
    • Leader election via lease: a client tries to create a key with a TTL; if it exists the operation fails, so only one client gets the lease
    • This needs the lease manager itself to be fault-tolerant, which is why it relies on consensus.

10.3 Consistency models

In an ideal world a request executes instantaneously. In reality it must reach the leader, be processed and answered, so the best guarantee is that it executes somewhere between invocation and completion. In a single-threaded program, assigning 42 to x and reading it gives 42; with replication, "all bets are off".

  • Only the leader changes state, so writes go through the leader
    • Reads need not: they can be served by the leader, a follower, or both
    • If all reads go through the leader, read throughput is that of one process; if followers serve reads, two clients (observers) can see different state since followers lag.
  • Trade-off: how consistent observers' views are vs performance and availability. Consistency models (https://jepsen.io/consistency) formally define the possible views.

10.3.1 Strong consistency (linearizability)

If clients send reads and writes only to the leader, every request appears to take place atomically at one point in time, as if there were a single copy; its side effects are visible to all observers once it completes.

The real-time guarantee is the model linearizability (https://jepsen.io/consistency/models/linearizable), "the strongest consistency guarantee for single-object requests" (what you would expect from a coordination service managing leases).

  • Catch:
    • the leader cannot serve a read from local state, since by the time it gets the request it might no longer be the leader
    • It must first contact a majority to confirm it still is; otherwise it becomes a follower and fails the request
    • This confirmation considerably increases read time.

10.3.2 Sequential consistency

Serialising reads through the leader creates a chokepoint and costs a majority round trip. Let followers serve reads: a follower lags but receives updates in the same order as the leader. A client pinned to follower 1 and another to follower 2 see the state evolve at different times.

  • Sequential consistency
    • (https://jepsen.io/consistency/models/sequential): operations occur in the same order for all observers but with no real-time guarantee about when side effects become visible: that is what separates it from linearizability
    • Example: a producer/consumer system synchronised with a queue: both see items in the same order, the consumer lags.

10.3.3 Eventual consistency

Pinned clients lose access if their follower dies. Allow any follower: better availability, at a steep price: say follower 2 lags follower 1; a client querying 1 then 2 sees an earlier state, which is confusing. The only guarantee: if writes stop, all followers eventually converge. This is eventual consistency.

  • Hard to build on:
    • behaviour differs from single-threaded intuition, so subtle, hard-to-reproduce bugs appear
    • But not every app needs linearizability: counting visitors to a website is fine if a read is slightly out of date.

10.3.4 The CAP theorem

When a network partition happens, some clients cannot reach the leader. The system can (a) stay available by letting clients query reachable followers (giving up strong consistency) or (b) stay strongly consistent by failing reads that cannot reach the leader.

  • CAP:

    • "strong consistency, availability and partition tolerance: pick two out of three" ("Perspectives on the CAP Theorem": https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf)
    • Since network faults are a given, the real choice is consistency vs availability.

  • Confusing detail:

    • CAP's availability means every request eventually gets a response, but real systems cannot be perfectly available and "a very slow response is just as bad as one that never occurs", so many highly available systems are not "available" in CAP's sense
    • Its definitions of consistency and partition tolerance are also very precise, limiting practical use (see "A Critique of the CAP Theorem": https://www.cl.cam.ac.uk/research/dtg/www/files/publications/public/mk428/cap-critique.pdf; talk: https://www.youtube.com/watch?v=hUd_9FENShA)
    • Better to think of a spectrum: a strongly consistent, partition-tolerant system in CAP's sense is just one point.

  • PACELC

    • (https://en.wikipedia.org/wiki/PACELC_theorem): partitions are rare within a data centre, yet even without a partition there is a trade-off between consistency and latency: the stronger the guarantee, the higher an operation's latency
    • In case of partition (P) choose availability (A) or consistency (C); else (E) choose latency (L) or consistency (C)
    • In practice it is a spectrum, not binary.

  • Why some data stores have counter-intuitive guarantees:

    • to provide high availability and performance
    • Others have knobs: Azure Cosmos DB (https://docs.microsoft.com/en-us/azure/cosmos-db/consistency-levels) and Cassandra (https://docs.datastax.com/en/cassandra-oss/3.0/cassandra/dml/dmlConfigConsistency.html).

  • Another reading of PACELC:

    • a trade-off between coordination and performance
    • Design around it by moving coordination off the critical path
    • Raft pays a "coordination tax" on every strongly consistent read (contact a majority)
    • Chain replication avoids that.

10.4 Chain replication

(Paper: https://www.cs.cornell.edu/home/rvr/papers/OSDI04.pdf; the book describes the CRAQ extension, https://www.usenix.org/legacy/event/usenix09/tech/full_papers/terrace/terrace.pdf.)

Processes form a chain: leftmost the head, rightmost the tail.

  • Writes go only to the head,
    • which updates its state and forwards to the next process, and so on to the tail
    • The tail applies the update and acknowledges to its predecessor: committed
    • The ack flows back to the head, which then replies to the client.
  • Reads are served only by the tail. Without failures it is strongly consistent, since the tail processes all reads and writes one at a time.
  • Fault tolerance
    • is delegated to a configuration manager / control plane that monitors health and removes a faulty process, and ensures one agreed view of the topology
    • It must itself be fault-tolerant, so it uses state machine replication (e.g. Raft)
    • The chain tolerates up to N - 1 failures (N = chain length); the control plane only a minority (the book writes C/2 for C replicas, i.e. fewer than half).
  • Three failure modes:
    • Head fails:
      • the control plane makes its successor the head and notifies clients
        • If the head committed locally but crashed before forwarding, no harm: the write never reached the tail, the client got no ack, and from its view it is a timed-out request to retry
      • nobody else saw the write.
    • Tail fails: its predecessor becomes the tail; all updates the tail got must have reached the predecessor too.
    • Intermediate process X fails:
      • the control plane links X's predecessor to X's successor
      • X may have applied updates it never forwarded, so X's successor reports the sequence number of the last committed update it saw, and X's predecessor sends the missing updates downstream.
  • As processes fail it tolerates fewer failures, so replace a failing process: the new one becomes the tail after syncing with its predecessor.
  • Beauty: only a handful of simple failure modes, because a committed write has been processed by every process in the chain, unlike quorum protocols such as Raft where only some replicas may have seen a committed write.
  • Versus Raft:
    • simpler to understand and more performant, since the leader's work is split between head (sequences writes) and tail (serves reads, interleaved with updates from its predecessor)
    • A read is served from the tail's local state without contacting other replicas: higher throughput, lower latency.
  • Costs:
    • write latency: an update must traverse the whole chain, so one slow replica slows all writes
    • Raft waits only for a majority and tolerates transient degradation. And if a process is unavailable, writes cannot commit until the control plane detects it and removes it
    • in Raft one failure does not stop writes.
  • Upsides:
    • writes can be pipelined (higher throughput)
      • Read throughput can be raised further by spreading reads across replicas while staying linearizable: replicas keep multiple versions of an object, each with a version number and a dirty flag
    • an update is dirty while moving head to tail
    • once the tail commits and acks back along the chain, replicas mark it clean. A replica serves a read immediately if its latest version is clean
    • otherwise it asks the tail for the latest committed version.
  • Data plane vs control plane:
    • the data plane (client requests on the critical path) needs no leader because it does not handle failures; it focuses on throughput and efficiency
    • The control plane needs a leader and consensus, but only for the occasional failure, off the critical path
    • This splitting data plane from control plane is a common pattern (chapter 22)
    • It cuts the coordination needed per request.

The chapter ends by asking whether data can be replicated without consensus at all (consensus is required for state machine replication): the next chapter.
