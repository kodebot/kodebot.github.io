Understanding Distributed Systems 11: Coordination avoidance

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 11. Previous: Understanding Distributed Systems 10: Replication. Next: Understanding Distributed Systems 12: Transactions.

The one-minute version

State machine replication needs total order broadcast (and so consensus), which is a scalability bottleneck (one process sequences updates) and unavailable during partitions. If you drop total order, any replica can accept writes, and replicas only need to converge. CRDTs make convergence automatic; Dynamo-style stores use quorums plus anti-entropy; the CALM theorem says which programs need coordination at all (the non-monotonic ones); and causal consistency is the strongest model that is still available and partition-tolerant.

Why avoid coordination

State machine replication = (1) a fault-tolerant total order broadcast so every replica gets the same updates in the same order, and (2) a deterministic function applying updates. Total order broadcast is equivalent to consensus (see the Chandra-Toueg paper: https://www.cs.utexas.edu/~lorenzo/corsi/cs380d/papers/p225-chandra.pdf), and:

  • updates are processed sequentially by a single process (e.g. Raft's leader): a bottleneck;
  • the CAP theorem applies, so it is unavailable during network partitions.

11.1 Broadcast protocols

Wide-area networks like the internet offer only point-to-point (unicast) protocols such as TCP. Reaching a group needs broadcast (multicast) built over unicast, with multiple senders and receivers that can crash.

  • Best-effort broadcast:
    • if the sender does not crash, the message reaches all non-faulty processes
    • Simple: send to each one over reliable links
    • If the sender dies midway, some never get it.
  • Reliable broadcast:
    • the message is eventually delivered to all non-faulty processes even if the sender crashes mid-way. Eager reliable broadcast: each process retransmits on first delivery
    • costly: N^2 messages for N processes.
  • Gossip broadcast
    • (https://en.wikipedia.org/wiki/Gossip_protocol): retransmit only to a random subset (e.g. 2), like rumours spread
    • Probabilistic, so no certainty every process gets it, but tuning can make a miss negligible
    • Useful for very large groups where a deterministic protocol would not scale.
  • Total order broadcast:
    • reliable broadcast plus the same delivery order at every process
    • Reliable broadcast alone does not order messages (two processes may receive the same messages in different orders)
    • A fault-tolerant implementation requires consensus.

11.2 Conflict-free replicated data types (CRDTs)

Idea: use a broadcast without total order, so any replica accepts writes (no single leader). Replicas may receive messages in different orders and diverge, but only temporarily: this is eventual consistency, which requires:

  • eventual delivery: every update applied at one replica is eventually applied at all;
  • convergence: replicas that applied the same updates eventually reach the same state.

Conflicts (the same object updated at different replicas) can be reconciled with consensus off the critical path: better availability and performance than total order broadcast, but the reconciliation logic is not trivial.

Can replicas resolve conflicts with no consensus at all? Yes, if every possible conflict has a deterministic outcome (e.g. the write with the greatest timestamp wins): then there are no conflicts by design.

That gives strong eventual consistency (https://www.microsoft.com/en-us/research/video/strong-eventual-consistency-and-conflict-free-replicated-data-types/): eventual delivery plus strong convergence (replicas that executed the same updates are in the same state).

It allows systems that are available, (strongly eventually) consistent and partition tolerant.

Conditions for strong convergence. Replicate an object (integer, string, set...) across N replicas. A client can send queries and updates to any replica:

  • a query is answered immediately from the local copy;
  • an update is applied locally, then the updated object is broadcast to all replicas;
  • a received broadcast is merged with the local object.

Replicas converge if:

  • the object's states form a semilattice (a set whose elements can be partially ordered), and
  • the merge returns the least upper bound of two states (so it is idempotent, commutative and associative).

Such a type is a convergent replicated data type, part of the CRDT family (https://hal.inria.fr/inria-00609399v1/document). It sounds harder than it is: for integers, merge = maximum; replicas converge to the global maximum even if messages arrive out of order or multiple times.

  • Replicas can even use an unreliable broadcast if they periodically exchange and merge state (anti-entropy), though naive periodic exchange is expensive.
  • Many types converge when replicated:

    • registers, counters, sets, dictionaries, graphs

    • A register is a memory cell of opaque bytes with an assignment operation; to converge it needs a partial order over values and a merge

    • Two common designs:

    • Last-writer-wins (LWW):

      • each update carries a timestamp (a Lamport timestamp to keep happened-before, plus a replica ID to avoid ties)
      • A replica generates a new timestamp on a client update, stores value+timestamp and broadcasts; on receiving a peer's state it keeps the greater timestamp and discards the other
      • Problem: concurrent conflicting updates are resolved by the greater timestamp, which may not make sense.

    • Multi-value (MV):

      • keep all concurrent updates and return them to the client application to resolve
        • Updates are tagged with a vector clock (in practice version vectors: https://pages.cs.wisc.edu/~remzi/Classes/739/Fall2017/Papers/parker83detection.pdf)
      • merge returns the union of all concurrent updates.
  • CRDTs compose: a dictionary of LWW or MV registers is a convergent key-value store: this is the approach of Dynamo-style stores.

11.3 Dynamo-style data stores

Dynamo ("Amazon's Highly Available Key-value Store": https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf) is arguably the best-known eventually consistent, highly available key-value store; it inspired Cassandra (https://cassandra.apache.org/) and Riak KV (https://riak.com/products/riak-kv/).

  • Every replica accepts reads and writes.

    • A write is sent to all N replicas in parallel but the client waits for W acknowledgements (write quorum)
    • A read goes to all but waits for R replies (read quorum) and returns the most recent entry
    • Conflicts are resolved with LWW or MV behaviour, depending on the flavour.

  • If W + R > N,

    • the quorums intersect, so at least one read returns the latest version
      • Not linearizable on its own: a write that succeeded on fewer than W replicas leaves them inconsistent and some clients read the new version, others not
    • to avoid that, bundle writes in an atomic transaction (chapter 12).

  • Normally W and R are majority quorums (more than half the replicas)

    • Other choices shift performance: a read-heavy workload benefits from a smaller R (but writes become slower and less available while W + R > N)
    • W = R = 1 maximises performance at the expense of consistency (W + R < N).

  • Problem: a write sent to a replica may never arrive, so it would never converge. Two anti-entropy mechanisms help (quorum replication = best-effort broadcast + anti-entropy):

    • Read repair:
      • done by clients on read
      • If some of the R replies are older, the client writes the latest entry back to the out-of-sync replicas
      • Good for frequently read entries; not enough to guarantee all replicas converge.
    • Replica synchronisation:
      • a continuous background process on every replica that periodically talks to others to find and repair inconsistencies: if replica X has an older version of key K than Y, X fetches it
      • To detect differences with minimal data exchange, replicas exchange Merkle tree hashes (https://en.wikipedia.org/wiki/Merkle_tree) over a gossip protocol.

11.4 The CALM theorem

How do you know whether an application needs coordination such as consensus? CALM ("Keeping CALM: When Distributed Consistency is Easy", https://arxiv.org/pdf/1901.01930.pdf): a program has a consistent, coordination-free distributed implementation if and only if it is monotonic.

  • Monotonic:

    • new inputs refine the output and cannot retract any prior output
    • Example: the union of a set: once an element is added it cannot be removed
    • CRDTs are monotonic. Non-monotonic: a new input can retract a prior output, e.g
    • variable assignment overwrites the previous value.

  • A monotonic program can be consistent, available and partition tolerant at once

    • But CALM's "consistency" is not linearizability (CAP's C, narrowly about reads and writes): CALM concerns consistency of the program's output: it yields the same output whatever the input order, despite conflicts
    • Make sure you know what "consistency" means each time you meet it.

  • Counter example: with only write and read, order matters: `write

    • gives 2. With anincrementabstraction,increment
    • ` three times gives 3 in any order. So read/write-level consistency can limit the solution space: you can be consistent at the application level but not at the storage read/write level ("Building on Quicksand": https://dsf.berkeley.edu/cs286/papers/quicksand-cidr2009.pdf)

  • CALM also flags programs that cannot be consistent without coordination because they are non-monotonic

    • But assignment combined with a logical clock becomes monotonic, as LWW and MV registers show.

11.5 Causal consistency

Eventual consistency gives monotonic apps consistency, availability and partition tolerance, but is not enough for many applications: it does not guarantee that an operation that happened-before another is observed in that order by replicas.

Example: you upload a picture to a social network and add it to a gallery; with eventual consistency the gallery may reference the image before it is available, showing a missing-image placeholder.

Strong consistency preserves happened-before (cause before effect), but you do not need it for that: causal consistency (https://jepsen.io/consistency/models/causal) is weaker than strong but stronger than eventual, attractive because:

  • for many applications it is "consistent enough" and easier to work with than eventual consistency;

  • it is provably the strongest consistency model that still allows availability and partition tolerance ("Consistency, Availability, and Convergence": https://apps.cs.utexas.edu/tech_reports/reports/tr/TR-2036.pdf).

  • It imposes a partial order:

    • processes agree on the order of causally related operations, but may disagree on unrelated ones
    • For any two operations either one happened-before the other, or they are concurrent and cannot be ordered (unlike strong consistency's global order).

  • Example:

    • process 1 updates entry A
    • process 2 reads it (B) and then updates another entry (C). Everyone must agree A happened-before C. For concurrent X and Y, some may see X first, some Y first.

COPS: a causally consistent store (available under partitions)

Based on COPS ("Clusters of Order-Preserving Servers", "Don't Settle for Eventual", https://www.cs.princeton.edu/~mfreed/docs/cops-sosp11.pdf), which gives causal consistency across geographically distributed clusters.

In COPS a cluster is a strongly consistent partitioned store; the book treats it as one logical node without partitions (chapter 16 covers partitioning; COPS can track causality across partitions, unlike simple version vectors, see https://www.cs.utexas.edu/users/dahlin/Classes/GradOS/papers/SessionGuaranteesPDIS.pdf).

  • First define causal+:
    • no disagreement about the order of unrelated operations (disagreements make replicas diverge forever)
    • Use LWW registers (object + logical timestamp = version) so replicas converge under concurrent writes.
  • Any replica accepts reads and writes; clients use their closest (local) replica.
  • Read: the local replica returns the most recent local value; the client records the value's version in a local key-version dictionary to track dependencies.
  • Write:
    • the client sends the write with a copy of its dependency dictionary
    • The replica assigns a version, applies the change locally (allowed even if others updated the key meanwhile, because values are LWW registers), acknowledges with the version, and broadcasts asynchronously to other replicas.
  • Receiving a replication message:
    • the replica does not apply it immediately
    • it first checks that the write's dependencies are committed locally, waits until the required versions appear, then applies it. This guarantees causal consistency.
  • Failure:
    • the store stays available (any replica accepts writes). A replica could fail after committing locally but before broadcasting, losing data
    • COPS accepts that trade-off to avoid waiting on long-distance requests to remote replicas before acknowledging a write.

11.6 Practical considerations

Across the replication chapters: a trade-off between consistency and availability/performance; to build scalable, available systems minimise coordination.

Many large systems have knobs: Azure Cosmos DB lets you choose among 5 consistency models, from eventual to strong, weaker ones having higher throughput (https://azure.microsoft.com/en-gb/blog/azure-cosmos-db-pushing-the-frontier-of-globally-distributed-databases/).
