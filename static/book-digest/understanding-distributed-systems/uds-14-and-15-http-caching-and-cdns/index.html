Understanding Distributed Systems 14 and 15: Part III intro, HTTP caching, CDNs

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), Part III introduction, chapters 14 and 15. Previous: Understanding Distributed Systems 13: Asynchronous transactions. Next: Understanding Distributed Systems 16: Partitioning.

Takeaways
  • Part III opens the scalability section; this note covers client-side caching (the replication pattern) and CDNs, with partitioning next.
  • HTTP caching works for safe methods (GET, HEAD) via Cache-Control (TTL) and ETag (version); stale entries revalidate with a conditional GET (If-None-Match).
  • Make static resources immutable and publish changes under a new URL: cache "forever", and clients never see a mix of old and new files.
  • A reverse proxy shares one cache across all clients and can also authenticate, compress, rate-limit and load-balance.
  • A CDN is an overlay of reverse proxies whose main win is the network (lower latency than BGP routing), with caching layers on top; prefer it over building your own cache.

Part III: Scalability (introduction)

"Treat servers like cattle, not pets." (Bill Baker)

  • In 1996 only 1% of people worldwide had internet access

    • today over 65%. That grew the addressable market of online businesses and created the need for systems that handle millions of concurrent users.

  • To scale, an app must run without performance degradation as load increases; as chapter 1 said, the only long-term solution is to architect it to scale horizontally.

  • The part follows the journey of scaling Cruder, a simple CRUD web app: a single-page JavaScript app talking to an application server over a RESTful HTTP API

    • the server stores large files (images, videos) on its local disk and state in a relational database
    • app server and database share one machine on a compute platform like AWS EC2
    • the public IP is advertised by a managed DNS service like AWS Route 53 (https://aws.amazon.com/route53/)
      • A browser resolves the domain via DNS (if not cached), opens a TLS connection and sends its first HTTP GET.

  • Fine for a proof of concept, not scalable or fault-tolerant. As requests grow the server needs more CPU, memory, disk and network and degrades

    • the database slows as it stores and serves more while competing with the server for resources.

  • Scale up

    • (quickest): more processors or cores (more threads at once), more disks (RAID) for disk throughput, more NICs for network throughput, SSDs for lower random-access latency, more memory for fewer page faults
    • Caveat: the app must be able to use the extra hardware (more cores do nothing for a single-threaded app), and eventually you hit a hard physical limit regardless of money.

  • Scale out:

    • distribute across nodes
    • more complex, but it pays off
      • First step: move the database to its own machine, so server and database no longer compete: an example of functional decomposition (breaking an app into components, each with a well-defined responsibility).

  • Three general patterns to exploit and combine: functional decomposition, partitioning (split data into partitions spread across nodes) and replication (copy functionality or data across nodes, a.k.a. horizontal scaling).

Chapter 14: HTTP caching

Cruder's server currently serves static resources (rarely change between requests: JavaScript, CSS) and dynamic ones (generated on the fly: a JSON user profile).

A static resource can be cached by the client for some time so the next access needs no network call, reducing server load and response time. (This is the replication pattern; MDN guide: https://developer.mozilla.org/en-US/docs/Web/HTTP/Caching.)

How it works. HTTP caching is limited to safe methods that do not alter server state, like GET or HEAD.

  1. A client requests a resource it has not accessed. The local cache intercepts, finds nothing, and fetches from the origin server for the client.
  2. The server marks the resource cacheable with response headers: Cache-Control (how long to cache: the TTL) and ETag (a version identifier). The cache stores the resource and returns it. (An Age header shows how many seconds the object has been in the cache.)
  3. Later access: the cache checks whether the resource is still fresh (not expired). If so, it returns it immediately. Even if fresh from the client's view, the server may have updated it, so reads are not strongly consistent: an acceptable trade-off here.
  4. If expired (stale), the cache sends a conditional GET with a header like If-None-Match carrying the stale resource's version. If a newer version exists the server returns it; if not, it replies 304 Not Modified.

Make static resources immutable. They can then be cached "forever" (the HTTP spec's maximum is one year). To change one, publish a new resource under a new URL so clients must fetch it.

  • Bonus: atomic updates of related resources.
    • A new site release has an updated HTML index that references new URLs for the JS and CSS bundles
    • A client sees either the old site or the new one depending on which index file it read, never a mix (old JS with new CSS).

Read path vs write path. Reads (GET) are treated differently from writes (POST, PUT, DELETE) because there are orders of magnitude more reads: a pattern called CQRS (Command Query Responsibility Segregation: https://martinfowler.com/bliki/CQRS.html), another instance of functional decomposition.

14.1 Reverse proxies

A reverse proxy is a server-side proxy that intercepts all communication with clients; it is indistinguishable from the real server, so clients do not know there is an intermediary.

  • Common use: cache static resources. The cache is shared among clients, so it cuts server load far more than any client-side cache.
  • A middleman can also authenticate requests for the server
    • compress responses
    • rate-limit specific IPs or users, and load-balance across servers (explored in later chapters).
  • NGINX
    • (https://www.nginx.com/) and HAProxy (https://www.haproxy.com/) are widely used
    • But many reverse-proxy uses are commoditised by managed services, so rather than building a server-side cache, use a CDN.

Chapter 15: Content delivery networks

A CDN is an overlay network of geographically distributed caching servers (reverse proxies), architected around the design limitations of the network protocols that run the internet. Clients hit URLs that resolve to CDN caching servers.

On a request the CDN server checks its cache; if missing it transparently fetches from the origin server (our application server) using the original URL, caches the response and returns it.

Examples: AWS CloudFront (https://aws.amazon.com/cloudfront/) and Akamai (https://www.akamai.com/).

15.1 Overlay network

You might think caching is the main benefit; it is actually the underlying network.

  • The public internet is thousands of networks
    • its core routing protocol BGP was not designed for performance: it mainly uses the number of hops to cost a path and ignores latency and congestion.
  • A CDN is an overlay network built on top of the internet (see "The Akamai Network": https://groups.cs.umass.edu/ramesh/wp-content/uploads/sites/3/2019/12/The-akamai-network-a-platform-for-high-performance-internet-applications.pdf) using techniques that cut response time and raise transfer bandwidth.
  • Recall TCP (chapter 2):
    • latency matters
    • No matter how fast the server, a client on the other side of the world sees over 100 ms just from network latency, physically limited by the speed of light, plus a higher error rate over long public-internet distances.
  • So CDN clusters are placed in many geographic locations near clients
    • How do clients find the closest? Global DNS load balancing (https://landing.google.com/sre/sre-book/chapters/load-balancing-frontend/): a DNS extension that infers the client's location from its IP and returns the geographically closest clusters, also considering network congestion and cluster health.
  • CDN servers also sit at internet exchange points, where ISPs connect, so almost the whole path from origin to client runs on CDN links, with short low-latency hops at either end.
  • The overlay's routing algorithms pick paths with lower latency and congestion based on continuously updated network health data, and exploit TCP optimisations: pools of persistent connections between servers (no setup overhead) and optimal TCP window sizes to maximise bandwidth.
  • The overlay also speeds up dynamic resources that cannot be cached: the CDN becomes the application's frontend, shielding it from distributed denial-of-service (DDoS) attacks (https://en.wikipedia.org/wiki/Denial-of-service_attack).

15.2 Caching

A CDN can have several caching layers: the top is edge clusters in different locations. Infrequently accessed content may be missing at the edge; the edge then fetches from the origin, more efficiently and reliably thanks to the overlay.

  • Trade-off: more edge clusters serve more dispersed clients, but the cache hit ratio (the likelihood of finding the object in the cache; a hit vs a miss) drops, so origin load rises.
  • Remedy: intermediate caching clusters in fewer locations that cache a larger fraction of the content.
  • Within a cluster, content is partitioned across servers (no single server holds it all). Partitioning is a core scalability pattern: the next chapter.
