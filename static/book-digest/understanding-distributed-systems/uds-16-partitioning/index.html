Understanding Distributed Systems 16: Partitioning

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 16. Previous: Understanding Distributed Systems 14 and 15: Part III intro, HTTP caching, CDNs. Next: Understanding Distributed Systems 17: File storage.

The one-minute version

Why partition and what it costs

  • Data eventually does not fit on one machine: split into partitions small enough for individual nodes. The capacity to handle requests also grows, since access load is spread.
  • A request must be routed to the responsible node(s). A gateway service (a reverse proxy) usually does this
    • the mapping of data to partitions and nodes is typically held by a fault-tolerant coordination service like etcd or ZooKeeper.

Not a free lunch, it adds a lot of complexity:

  • a gateway is needed to route requests;
  • roll-ups across partitions must be pulled from several partitions and aggregated (think of a GROUP BY across partitions);
  • transactions are needed to atomically update data spanning partitions, which limits scalability;
  • a partition accessed much more often than others limits the system's ability to scale (hotspot);
  • adding or removing partitions at run time is hard since data must move between nodes.

Why right after CDNs? A cache lends itself well to partitioning: it generally needs no atomic cross-partition updates and no cross-partition aggregations.

Prerequisite: the number of possible keys must be very large. A boolean key with two values allows at most two partitions.

16.1 Range partitioning

Split the data by key range into lexicographically sorted partitions. To make range scans fast, each partition is usually stored in sorted order on disk.

  • Challenge 1: boundaries.
    • An even split of the key range works if keys are roughly uniform
    • otherwise (e.g. an English dictionary) partitions are unbalanced, some with many more entries.
  • Challenge 2: hotspots.
    • Access patterns can concentrate load
    • If data is range-partitioned by date, all requests for the current day go to one node
    • Workaround: add a random prefix to the partition keys, at the price of more complexity.
  • Rebalancing:
    • when data or requests grow, add nodes; when they shrink, remove nodes to cut cost
    • Adding and removing nodes to balance load is rebalancing
    • It must minimise disruption (the system keeps serving requests), so minimise the data transferred.
    • Static partitioning:
      • create many more partitions than needed at start and assign several per node
      • A new node takes some partitions from existing nodes, keeping balance
      • Drawback:
        • the number of partitions is fixed, and hard to get right: too many add overhead and slow things down, too few limit scalability
        • some partitions may still be hotter than others.
    • Dynamic partitioning:
      • create partitions on demand
      • Start with one partition; when it grows above a size or gets too hot, split it into two sub-partitions with about half the data each and move one to a new node
      • When two adjacent partitions become small or cold enough, merge them.

16.2 Hash partitioning

Use a hash function that deterministically maps a key (string) to a seemingly random number in a range (e.g. 0 to 2^64 - 1), so key hashes are uniformly distributed. Assign a subset of the hashes to each partition, e.g. hash(key) mod N with N partitions.

  • Partitions get about the same number of entries, but this does not remove hotspots if access is not uniform: a single very popular key overloads its partition's node
    • Fix: split the partition further (more partitions) or split the key into sub-keys with a random prefix.
  • Problem with modulo:
    • when a partition is added, most keys change assignment and must be shuffled, which is extremely expensive (network bandwidth and more)
    • Ideally only K/N keys move (K keys, N partitions)
    • A widely used strategy with that property is consistent hashing ("Consistent Hashing and Random Trees": https://www.cs.princeton.edu/courses/archive/fall09/cos518/papers/chash.pdf).

Consistent hashing: a hash function randomly maps both partition identifiers and keys onto a circle; each key is assigned to the closest partition that appears clockwise on the circle. When a new partition is added, only the keys that now map to it need to be reassigned (in the book's example, adding P4 reassigns the key 'for' to P4 while all other assignments stay).

  • Drawback vs range partitioning:
    • the sort order across partitions is lost, so you cannot efficiently scan everything in order
    • Data within one partition can still be sorted by a secondary key.
