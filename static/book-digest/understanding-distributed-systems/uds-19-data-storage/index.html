Understanding Distributed Systems 19: Data storage

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 19. Previous: Understanding Distributed Systems 18: Network load balancing. Next: Understanding Distributed Systems 20: Caching.

[!abstract] The one-minute version Cruder's stateless app tier scales out, but the single relational database will hit its capacity. Replication (leader and followers) scales reads and availability but not writes, and the data must still fit on one machine. Partitioning scales reads and writes but is daunting to bolt onto a relational database. Hence NoSQL, built for scale and availability, which demands that you know your access patterns upfront and model data around them. NewSQL adds ACID back.

19.1 Replication

Leader-follower topology: clients send writes exclusively to the leader, which persists them to its write-ahead log. Followers (replicas) connect, stream the log entries and commit them locally. Entries have sequence numbers, so a follower can disconnect and later resume by telling the leader the last number it processed.

  • Benefits:
    • read-only followers behind a load balancer increase read capacity
    • Availability improves: the balancer removes faulty replicas, and if the leader fails a replica can take its place
    • Followers can also isolate workloads, e.g
    • periodic expensive analytics queries that must not hurt the leader and other replicas.
  • Fully asynchronous:
    • the leader broadcasts the write and replies to the client without waiting for followers. Fast
    • not fault-tolerant: the leader may crash after acknowledging and before broadcasting
    • losing data.
  • Fully synchronous:
    • the leader waits for follower acknowledgements before replying. Costly: a single slow replica slows every request, and an unreachable replica makes the store unavailable
    • it does not scale, since more followers means more chance one is slow or down.
  • In practice a mix:
    • in PostgreSQL followers can individually be configured synchronous (default is asynchronous) (https://www.postgresql.org/docs/14/runtime-config-replication.html)
    • Example: one synchronous follower as an up-to-date backup, so you can fail over without data loss.
  • Failover
    • must: detect the leader's failure, promote the synchronous follower and reconfigure the others to follow it, and make sure clients send requests to the new leader
    • Managed services (AWS RDS, Azure SQL Database) offer read replicas (https://aws.amazon.com/rds/features/read-replicas/) and automated failover (https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.html), plus patching and backups.
  • Caveats:
    • replication scales reads, not writes, and the entire database must fit on one machine. Moving some tables to other nodes only delays the inevitable
    • partitioning is the answer.

19.2 Partitioning

Partitioning scales reads and writes. Traditional (centralised) relational databases generally do not support it out of the box; you can do it at the application layer, but it is hard:

  • decide how to partition and rebalance when a partition is too hot or big;
  • split queries that span partitions into sub-queries and combine the results (aggregations, joins);
  • support atomic cross-partition transactions with a distributed transaction protocol like 2PC;
  • and combine all that with replication.

Why relational databases struggle: they were designed assuming data fits on one beefy machine, so they support features hard to scale, like ACID transactions and joins.

They date from when disk was costly, so normalising to save space was a priority, at the price of joins to un-normalise at query time. Now storage is cheap and CPU time is not, so in the early 2000s large tech companies built bespoke stores for high availability and scale.

(Footnote: normalisation also protects data integrity: update a datum in one place.)

19.3 NoSQL

Early systems lacked SQL and implemented only a fraction of relational features.

White papers Bigtable (https://static.googleusercontent.com/media/research.google.com/en//archive/bigtable-osdi06.pdf) and Dynamo (section 11.3) "revolutionised the industry" and inspired open-source stores such as HBase and Cassandra.

They were called NoSQL because they lacked SQL; today the name misleads as many support SQL dialects.

  • Consistency: relational supports strong models up to strict serialisability; NoSQL embraces relaxed models (eventual, causal) for availability.
  • Data model:
    • generally no joins
    • data (key-value pairs or documents such as JSON) is un-normalised
      • A key-value store maps an opaque key to an opaque value
      • A document store maps a key to a (possibly hierarchical) document without a strictly enforced schema
    • unlike key-value, documents are interpreted and indexed, so you can query by internal structure.
  • Transactions: since they partition natively, support is limited (e.g. Azure Cosmos DB supports transactions scoped to a single partition); un-normalised data reduces the need.
  • Use NoSQL correctly and it handles many relational use cases while scaling from day 1 (what works on day 1 for a relational database may not at day 10 or 100)
    • Use one as a relational database and you get "the worst of both worlds".

Modelling data around access patterns (Amazon DynamoDB)

(DynamoDB: https://aws.amazon.com/dynamodb/; deep dives: https://www.youtube.com/watch?v=HaEPXoXVf2k and https://www.youtube.com/watch?v=yvBR71D0nAQ.) The main requirement: know the access patterns upfront and model the data accordingly.

  • Abstraction:
    • a table of items
    • items can have different attributes but need a primary key: either a partition key alone, or a partition key + sort key
      • The partition key decides how data is partitioned across nodes
    • the sort key orders data within a partition for efficient range queries.
  • Replication:
    • three replicas per partition kept in sync with state machine replication; writes go to the leader and are acknowledged when two of three have them
    • Reads are eventually consistent (any replica) or strongly consistent (the leader)
    • Confusingly, DynamoDB's architecture is very different from the Dynamo paper.
  • API:
    • CRUD on single items
    • query items sharing a partition key (optionally conditions on the sort key)
    • scan the whole table. No joins, by design (they do not scale well), and do not implement joins in the application: model the data so joins are not needed.
  • Example. Most common access pattern: orders of one customer, sorted by date. So customer ID = partition key, order date = sort key:
Partition Key Sort Key Attribute Attribute
jonsnow 2021-07-13 OrderID: 1452 Status: Shipped
aryastark 2021-07-20 OrderID: 5252 Status: Placed
branstark 2021-07-22 OrderID: 5260 Status: Placed

To also get the customer's full name, store customers and orders in the same table (a NoSQL table can hold several entity types):

Partition Key Sort Key Attribute Attribute
jonsnow 2021-07-13 OrderID: 1452 Status: Shipped
jonsnow jonsnow FullName: Jon Snow Address: ...
aryastark 2021-07-20 OrderID: 5252 Status: Placed
aryastark aryastark FullName: Arya Stark Address: ...

Customer and orders share a partition key, so one query fetches all of the customer's entities: the table is structured by access pattern, no join needed. In a normalised relational design you would have orders and customers tables and a join at query time, slower and harder to scale.

  • Secondary indexes
    • model more complex patterns: local secondary indexes give alternate sort keys within the same table
    • global secondary indexes give different partition and sort keys, but index updates are asynchronous and eventually consistent.
  • Misconception:
    • NoSQL is not more flexible because it "scales without modelling upfront"
    • "Nothing is further from the truth": it needs more care in modelling, and being tightly coupled to access patterns it is less flexible than a relational database.
  • The one concept to take away:
    • using a NoSQL store requires identifying access patterns upfront and modelling data accordingly
    • Recommended: The DynamoDB Book (https://www.dynamodbbook.com/), useful even for other NoSQL stores.

NewSQL

The latest trend combines NoSQL's scalability with relational ACID guarantees. NoSQL prioritises availability over consistency under network partitions; NewSQL prefers consistency.

The argument: with the right design the availability lost to strong consistency is hardly noticeable for many applications (see https://dbmsmusings.blogspot.com/2018/09/newsql-database-systems-are-failing-to.html), and 100% availability is impossible anyway (availability is measured in nines).

Examples: CockroachDB (https://github.com/cockroachdb/cockroach) and Spanner (section 12.4). Retrospective talk by Andy Pavlo: https://www.youtube.com/watch?v=LwkS82zs65g.
