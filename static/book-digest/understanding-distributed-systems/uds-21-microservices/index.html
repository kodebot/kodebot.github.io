Understanding Distributed Systems 21: Microservices

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), chapter 21. Previous: Understanding Distributed Systems 20: Caching. Next: Understanding Distributed Systems 22: Control planes and data planes.

[!abstract] The one-minute version A successful monolith keeps accumulating components, which become coupled, slow every developer down and force whole-app deploys and rollbacks. Functionally decomposing it into independently deployable services that talk via APIs lets small teams own services end to end. But it adds a great deal of complexity, worth paying only if amortised across many teams. Start with a monolith, decompose when there is a good reason. An API gateway then hides the internal services from the outside world.

The monolith's growing pains

  • Components get increasingly coupled; developers step on each other's toes; eventually nobody understands every part, and features and fixes take longer.
  • A change to one component can force rebuilding and deploying the whole app
    • A deployment bug (memory or socket leak) can hit unrelated components
    • Reverting affects every developer's velocity, not only the author's.

The microservice answer

  • Functionally decompose into independently deployable services communicating via APIs, which create boundaries that are hard to violate, unlike boundaries between components in one process.
  • Small teams own and operate
    • each service
    • Smaller teams collaborate better: communication overhead grows quadratically with team size (The Mythical Man-Month: https://en.wikipedia.org/wiki/The_Mythical_Man-Month)
    • Each team controls its codebase and release schedule, so less cross-team talk; a service's smaller surface is easier for new hires.
  • Teams may pick the tech stack and hardware that suit them (API consumers do not care), so experimenting is easy; each service can have its own data model and data store(s).
  • "Micro" is misleading:
    • nothing has to be micro
    • A service that does little only adds operational overhead and complexity
    • Rule of thumb: APIs should have a small surface area and encapsulate a significant amount of functionality (the idea is from John Ousterhout's A Philosophy of Software Design)
    • A more apt name is service-oriented architecture, but that has baggage too.

21.1 Caveats

Splitting adds a lot of complexity, worth it only if amortised across many development teams.

  • Tech stack:
    • nothing forbids different stacks, but it makes it harder for developers to move between teams and multiplies the libraries to support (one per language) for common needs like logging
    • Enforce some standardisation: e.g
    • loosely encourage technologies by giving teams a great development experience if they stay on the recommended portfolio.
  • Communication:
    • remote calls are expensive and introduce non-determinism
    • much of the book is about taming that. A monolith still faces external requests and third-party APIs, but on a smaller scale.
  • Coupling:
    • services must be loosely coupled so a change in one does not force changes elsewhere
    • Otherwise you get the dreaded distributed monolith: all the downsides of a monolith, an order of magnitude more complexity
    • Causes: fragile APIs needing client updates on every change, shared libraries updated in lockstep across services, static IP addresses to reference external services.
  • Resource provisioning: new machines, data stores and other commodity resources must be simple to provision (not each team's own way), then configured: needs a fair amount of automation.
  • Testing: testing one microservice is not harder than testing a monolith, but testing their integration is much harder: subtle, unexpected behaviours appear only when services interact at scale in production.
  • Operations:
    • a common way to continuously deliver and deploy safely so no team reinvents it
    • Debugging is harder: you cannot load the whole app on your machine and step through it, so a good observability platform is crucial.
  • Eventual consistency:
    • the data model no longer lives in one store
    • atomically updating data across stores with strong consistency is slow, expensive and hard, so the architecture usually has to embrace eventual consistency.

Summary advice: generally start with a monolith and decompose it only when there is a good reason (Fowler: https://martinfowler.com/bliki/MicroservicePremium.html). You can still componentise the monolith, and boundaries are far easier to move as it grows. Once it is mature and growing pains appear, peel off one microservice at a time.

21.2 API gateway

After decomposing, rethink how the outside world talks to the app.

  • A client may need several requests to different services for one operation: expensive on mobile, where each network request costs battery.
  • Clients must know implementation details like internal service DNS names, so architecture changes force client changes, hard when you do not control them
    • "Once a public API is out there, you had better be prepared to maintain it for a very long time."
  • Solution (a layer of indirection): hide internal APIs behind a public API that acts as a facade or proxy: the API gateway (a reverse proxy).

21.2.1 Core responsibilities

  • Routing:
    • forward inbound requests to internal services using a routing map from the public API to internal APIs
    • Internal APIs can change without breaking external clients: with a 1:1 mapping between a public and an internal endpoint, if the internal one changes clients keep using the public one.
  • Composition:
    • data now lives in many services and stores
    • the gateway can offer a higher-level API that queries several services and composes the responses, sparing the client from knowing which services to ask and cutting its request count
      • But not simple: availability of the composed API drops as internal calls increase (each can fail), and data may be inconsistent if updates have not propagated
    • the gateway must resolve discrepancies.
  • Translation:
    • from one IPC mechanism to another (e.g. REST over HTTP to internal gRPC), and different APIs for different clients: a desktop app can get more data than a mobile one (more screen estate; for mobile, network calls cost more and requests are batched to save battery)
    • Graph-based APIs
      • are increasingly popular: a schema of types, fields and relationships
      • clients query for exactly the data they need and the gateway turns that into internal calls
    • Less development time (no per-use-case APIs)
    • GraphQL (https://graphql.org/) is the most popular.

21.2.2 Cross-cutting concerns

As a reverse proxy the gateway can do what each service otherwise would: cache frequently accessed resources, rate-limit to protect services. The most critical are authentication and authorisation:

  • Authentication:
    • validating that a principal (human or application) is who it says
    • Authorisation: granting the authenticated principal permissions (create, read, update, delete a resource), typically via roles.
  • Monolith approach: sessions.
    • HTTP is stateless, so the app creates a session object with an ID (a cryptographically strong random number), stores it in an in-memory cache or external store, and returns the ID in a cookie
    • On login success the principal's ID and roles are stored in the session and later used to decide on requests.
  • In microservices it is not obvious which service authenticates and authorises, since handling a request can span services.
  • One approach:
    • the API gateway authenticates external requests (it is the entry point), centralising support for different authentication mechanisms and hiding the complexity
    • Authorisation is best left to individual services to avoid coupling the gateway to domain logic.
  • After authenticating, the gateway creates a security token, passed with the request to internal services, which pass it downstream
    • A service must validate the token and get the principal's identity and roles
    • Opaque token: carries no information, so validation calls an external auth service
    • Transparent token: embeds the principal's information, eliminating that call but making it harder to revoke compromised tokens.
  • JSON Web Token (JWT) (https://jwt.io/introduction) is the most popular transparent token: a JSON payload with an expiration date, the principal's identity and roles and other metadata, signed with a certificate trusted by internal services, so no external call is needed.
  • API keys: a custom key that lets the gateway identify the principal and limit what they can do; popular for public APIs like GitHub's or Twitter's.
  • The topic is barely scratched; see Microservices Security in Action (https://www.manning.com/books/microservices-security-in-action).

21.2.3 Caveats

  • It can become a development bottleneck: tightly coupled to the internal APIs it shields, so each internal API change means changing the gateway.
  • It is one more service to maintain and must scale to the combined request rate of all services behind it.
  • With many services and APIs the pros outweigh the cons.
  • Build or buy: roll your own from a reverse proxy like NGINX, or use managed Azure API Management (https://azure.microsoft.com/en-gb/services/api-management/) or Amazon API Gateway (https://aws.amazon.com/api-gateway/).
