Understanding Distributed Systems 22: Control planes and data planes

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 22. Previous: Understanding Distributed Systems 21: Microservices. Next: Understanding Distributed Systems 23: Messaging.

Takeaways
  • Split any component into a data plane (serves every request, fast and always up) and a control plane (manages config and metadata, consistent but low volume).
  • The data plane must keep running with stale config if the control plane is down (static stability). A hard dependency caps availability at the product of both.
  • Protect the control plane from the data plane's load with a buffer store, push instead of poll, and deltas plus snapshots.
  • Think of the control plane as a feedback loop: monitor, compare, act. Most designs miss the monitoring.

Why split

The API gateway is a single point of failure (if it dies, the app dies) and every external request passes through it, so it must be highly available and scalable. But its needs conflict:

  • A management endpoint (add, remove, configure API keys used for rate limiting) has far lower volume, so lower scale suffices.
  • Routing external requests should favour availability and performance over consistency; the management endpoint should favour consistency over availability.

So split it: a data plane service serving external requests to internal services, and a control plane service managing the gateway's metadata and configuration (https://brooker.co.za/blog/2019/03/17/control.html).

Seen before: chain replication's control plane holds the chain configuration (section 10.4); in Azure Storage the stream and partition managers are control planes allocating streams and partitions (chapter 17).

Data plane Control plane
Role everything on the critical path, run for each request helps the data plane: manages metadata or config, coordinates complex, infrequent operations
Needs highly available, fast, scales with request count less strict scaling; consistent view of its state for the data plane
Favours availability consistency over availability

An app can have several independent control and data planes (e.g. one control plane scales a service by load, another manages its config).

The cost: hard dependencies

  • If the data plane stops serving when the control plane is unavailable, it has a hard dependency on it: either failing takes the whole system down.
  • Availability of a chain of dependent components = product of their availabilities: data plane 99.99% x control plane 99% = 0.9899 (98.99%)
    • A system is at best as available as its least available hard dependency.
  • Fix: improve the control plane, but above all make the data plane run on a stale configuration rather than stop. This is static stability (also DNS, chapter 4).

22.1 Scale imbalance

Data planes and control planes have very different scale, so the data plane can overload the control plane (https://aws.amazon.com/builders-library/avoiding-overload-in-distributed-systems-by-putting-the-smaller-service-in-control/).

  • Example:
    • data plane processes poll the control plane for config
    • Normally spread out in time, but if they all restart together and fetch config at once, they overload it
    • Resiliency mechanisms (chapter 28) help only so far
    • If the control plane goes down, new data plane instances cannot even start.

Ways to design around it:

  1. Buffer store. The control plane periodically dumps its entire state (changed or not) to a scalable file store (S3, Azure Storage); the data plane reads from the store. Sounds naive and costly but is reliable, and cheap if the state is small. It is CQRS in practice. Benefits: protects the control plane from load; the data plane can start and run even if the control plane is down. Cost: higher latency and weaker consistency (slower propagation).
  2. Push, no intermediary. The data plane connects to the control plane, which pushes config when it changes. Because the control plane sets the pace it slows down rather than falls over. (It can still be overloaded by too many connections.)
  3. Push deltas. Version changes and send only updates/deltas: more complex but much faster when state is large.
  4. Snapshot + delta. Many instances starting at once could still hammer the control plane reading the full config, so reintroduce a store holding a recent snapshot: instances read the snapshot at startup, then ask the control plane for a small delta. The store absorbs bulk reads; the control plane pushes small deltas.

22.2 Control theory

A controller monitors a dynamic system, compares its state to the desired state, and applies a corrective action to drive it there, minimising instability. Here the data plane is the system and the control plane the controller: a feedback loop.

  • Without all three ingredients (monitor, compare, act) you have no closed loop and the data plane cannot reach the desired state (a closed loop is necessary, not sufficient)
    • Monitoring is the most commonly missing piece. Talk: https://www.youtube.com/watch?v=O8xLxNje30M.
  • Chain replication:
    • the control plane should not just push chain config
    • it should check the data plane actually applied it within a reasonable time, else take corrective action (even naive: reboot nodes with stale config, or exclude them from any chain).
  • CI/CD pipeline
    • as a control plane: releasing a build blindly risks a catastrophic failure (e.g. an exception at startup)
    • Better: release incrementally while monitoring, stop the roll-out on clear evidence of trouble, and ideally roll back automatically.
  • Ask of any control plane: what is missing to close the loop? Further reading: "Designing Distributed Control Systems" (https://www.amazon.com/gp/product/1118694155).
