Understanding Distributed Systems 24: Part IV intro and common failure causes

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), Part IV introduction and ch. 24. Previous: Understanding Distributed Systems 23: Messaging. Next: Understanding Distributed Systems 25-26: Redundancy and fault isolation.

Takeaways
  • More moving parts (the price of scalability) means more failures: "anything that can go wrong will go wrong" (Murphy's law). Higher nines mean you must detect, react and repair faster.
  • Real causes are mostly mundane: bad error handling, config changes, SPOFs (humans, DNS, expiring certs), slow network calls, resource leaks, load surges, and cascading, self-sustaining (metastable) failures.
  • Do not fix everything: rank faults by probability x impact (risk score), then reduce probability or impact.

Part IV: Resiliency (introduction)

"Anything that can go wrong will go wrong." (Murphy's law)

  • Part III's patterns (decomposition, partitioning, replication) all add moving parts
    • each can fail, so overall failure chance rises: power outages, hardware faults, crashes, memory leaks.
  • Nines in time:
    • two nines allows about 15 minutes of downtime a day
    • three nines about 43 minutes a month. Too little for manual action, so systems must detect and repair automatically.
  • Roadmap:
    • ch. 24 failure causes
    • ch. 25 redundancy (only works if failures are not correlated)
    • ch. 26 fault isolation (shuffle sharding, cellular architecture)
    • ch. 27 downstream resiliency (timeouts, retries, circuit breaker)
    • ch. 28 upstream resiliency (load shedding, rate limiting).

Terms

  • Failure:
    • the system no longer provides a service that meets its specification (https://resources.sei.cmu.edu/asset_files/TechnicalReport/1992_005_001_16112.pdf)
    • A failure is caused by a fault: failure of an internal component or an external dependency
    • Some faults are tolerated invisibly; others become failures.

24.1 Hardware faults

Any physical part can fail: HDDs, memory, power supplies, motherboards, SSDs, NICs, CPUs; failures can corrupt data; whole data centres fail from power cuts or disasters. Largely addressable with redundancy. But hardware is not the main cause of distributed-app failures; mundane reasons are.

24.2 Incorrect error handling

A 2014 study of user-reported failures in five popular distributed data stores found that most catastrophic failures came from incorrect handling of non-fatal errors ("Simple Testing Can Prevent Most Critical Failures": https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf). Simple tests would have caught most:

  • handlers that ignored errors entirely;
  • handlers catching an overly generic exception (Java's Exception) and aborting the whole process for no reason;
  • half-implemented handlers with FIXME and TODO comments. Error handling is an afterthought (Go stresses it heavily for that reason). Testing: chapter 29.

24.3 Configuration changes

A leading root cause of catastrophic failures (post-mortems: https://github.com/danluu/post-mortems#config-errors). Not only misconfigurations: valid changes enabling rarely-used features that no longer work (or never did).

  • Dangerous because effects can be delayed: a value read only when needed may bite hours or days later, escaping early detection (https://www.usenix.org/system/files/conference/osdi16/osdi16-xu.pdf).
  • So version-control, test and release config like code, and validate preventively at change time. Safe release practices: chapter 30.

24.4 Single points of failure (SPOFs)

A component whose failure brings down the whole system. A system can have several.

  • Humans are great SPOFs: manual steps in a specific order without mistakes will eventually go wrong. Automate wherever possible.
  • DNS
    • ("it's always DNS": https://twitter.com/ahidalgosre/status/1315345619926609920): if clients cannot resolve the name they cannot connect
    • Causes range from expired domain registrations (Foursquare: https://techcrunch.com/2010/03/27/foursquare-offline) to whole TLDs going down (https://hackernoon.com/stop-using-io-domain-names-for-production-traffic-b6aa17eeac20).
  • TLS certificate: if it expires clients cannot open a secure connection (Microsoft Teams, after Microsoft forgot to renew one: https://www.theverge.com/2020/2/3/21120248/microsoft-teams-down-outage-certificate-issue-status).
  • Find SPOFs at design time:
    • examine every component and ask what happens if it fails
    • Some can be architected away with redundancy; otherwise reduce the blast radius (the damage when it fails)
    • Many later patterns exist to shrink blast radius.

24.5 Network faults

A client waiting on a server can keep waiting or fail with a timeout (chapter 7). Reasons for no prompt response: slow or crashed server, packet loss causing retransmissions.

  • Slow network calls are the silent killers of distributed systems
    • (fallacies of distributed computing: https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing)
    • The client may wait long, or forever, causing hard-to-debug degradation.
  • This is a gray failure: so subtle it cannot be detected quickly or accurately, and it can bring a whole system to its knees ("Gray Failure: The Achilles' Heel of Cloud-Scale Systems": https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf).

24.6 Resource leaks

To an observer a very slow process is no different from a dead one. Leaks are a top cause of slowness.

  • Memory:
    • steady growth
    • even garbage-collected languages leak (a kept reference prevents collection). As memory runs low the OS swaps aggressively and the GC runs often, burning CPU
    • eventually allocation fails and most operations fail.
  • Thread pools: a thread making a synchronous blocking HTTP call with no timeout that never returns is never given back; the pool (bounded) runs dry.
  • Async does not save you: modern HTTP clients use socket pools (chapter 2); a request without a timeout never returns its connection, so the pool empties.
  • Libraries you use hit the same limits on the same memory, threads and sockets.

24.7 Load pressure

Every system has a capacity. Organic growth lets you scale out; a sudden flood does not. Load shifts by:

  • seasonality (e.g. users in different countries by hour);
  • expensive requests that abuse the system (scrapers slurping data at super-human speed);
  • malicious requests (DDoS to saturate bandwidth). Some surges are met by autoscaling; others require rejecting requests to shield the system (chapter 28).

24.8 Cascading failures

Faults can spread virally: with interdependent components, one failure raises the failure probability of others. Worked example: two database replicas A and B behind a load balancer, each at ~50 transactions per second.

  1. B becomes unavailable (network fault); the balancer removes it.
  2. A now carries double the load and struggles; clients see timeouts and retry, adding even more load.
  3. A times out on most requests; the balancer removes A too. The original fault in B cascaded into A.
  4. B comes back and is the only replica in the pool: it is flooded, overloads, and is removed again.
  5. The loop continues after the network fault is gone: a feedback loop moving load from replica to replica. Such failures are metastable (https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf).
  • Breaking it usually needs a big corrective action (e.g. temporarily block traffic to the replicas). They are very hard to mitigate once started
    • prevention means stopping faults spreading between components.

24.9 Managing risk

Accept that faults are inevitable and be ready to detect, react to and repair them. But not every possible fault needs action: weigh probability it happens and impact on users; probability x impact = risk score (risk matrix: https://en.wikipedia.org/wiki/Risk_matrix).

Very likely and high impact: tackle head on. Low likelihood and low impact: can wait. Once chosen, reduce the probability and/or the impact: the next chapters.
