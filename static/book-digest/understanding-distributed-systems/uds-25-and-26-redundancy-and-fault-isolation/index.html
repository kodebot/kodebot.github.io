Understanding Distributed Systems 25-26: Redundancy and fault isolation

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 25 and 26. Previous: Understanding Distributed Systems 24: Part IV intro and common failure causes. Next: Understanding Distributed Systems 27: Downstream resiliency.

Takeaways
  • Redundancy (replicating functionality or state) is the first line of defence, but only helps if redundant parts do not fail for the same reason at the same time (uncorrelated failures).
  • Spread across Availability Zones for data-centre outages; across regions only with a very good reason (rare, async replication, often legal compliance).
  • Redundancy cannot stop correlated, logic-level failures (poison pills, noisy neighbours). Use partitioning for fault isolation: bulkheads, shuffle sharding, cells.

Ch. 25 Redundancy

It is why distributed apps can beat single-node availability, and the same replication that lets you scale out. Marc Brooker's four prerequisites for redundancy to actually help (https://brooker.co.za/blog/2019/06/20/redundancy.html):

  1. The complexity it adds must not cost more availability than it adds.
  2. The system must reliably detect healthy vs unhealthy components.
  3. It must be able to run in degraded mode.
  4. It must be able to return to fully redundant mode.

Worked example, stateless service behind a load balancer:

  • The balancer masks node faults using a pool; it adds complexity (it can fail too) but the benefits "almost always outweigh" the risk.
  • It detects bad nodes via health checks (chapter 18)
    • They are critical: with 10 servers and 1 unresponsive, 10% of requests fail until it is removed, so slow detection means visible failures.
  • Removing servers assumes the rest have capacity (degraded mode), and replacements must be added or capacity eventually runs out.
  • Stateful services are far harder: masking failures means replicating state (previous chapters).

25.1 Correlation

Redundancy helps only when failures are not correlated. A bad memory module crashes one server, not its peers. But servers in one data centre all die together on a fibre cut or electrical storm, so no number of servers helps: use more than one data centre.

  • Availability Zones (AZs):
    • each cloud region has several data centres cross-connected by fast links
    • Far enough apart to limit correlated failures (power cuts), close enough for low latency (bounded by the speed of light), low enough to allow synchronous replication without a big penalty.
  • Stateless: instances in several AZs behind a shared load balancer; an AZ loss does not hurt availability.
  • Stateful: use a replication protocol across AZs; latency is low enough for partially synchronous (Raft) or even fully synchronous (chain replication).
  • Multi-region:
    • for a whole-region disaster, duplicate the stack in several regions and spread traffic with global DNS load balancing
    • State must be replicated asynchronously because inter-region latency is high (Netflix: https://netflixtechblog.com/active-active-for-multi-regional-resiliency-c47719f6685b).
  • Region destruction is extremely unlikely:
    • have very good reasons first
    • A likelier driver is legal compliance (EU customers' data processed and stored in Europe: https://www.europarl.europa.eu/RegData/etudes/ATAG/2020/652073/EPRS_ATA(2020)652073_EN.pdf).

Ch. 26 Fault isolation

Some failures are too correlated for redundancy.

  • Poison pill: a user's malformed requests crash servers because of a code bug; the bug exists in every DC and region, so redundancy does not help.
  • Noisy neighbour: a user's requests need far more resources and degrade everyone.
  • Problem: the blast radius is the entire application. Fix: partition the stack by user (chapter 16 viewed from a resilience angle) so a user can only affect their partition.
  • Example: 6 stateless instances in 3 partitions: a bad user hits at most 33% of users; more partitions shrink it further.
  • This is the bulkhead pattern, named after a ship's hull compartments: a leak stays in its compartment.

26.1 Shuffle sharding

Weakness of plain partitioning: users on a degraded partition suffer. For stateless services, shuffle sharding (https://aws.amazon.com/blogs/architecture/shuffle-sharding-massive-and-magical-fault-isolation/) assigns each user a virtual partition: a random but permanent subset of instances.

  • 6 instances in virtual partitions of 2: C(6,2) = 6!/(2!4!) = 15 partitions instead of 3, so two users are much less likely to share one.
  • Virtual partitions partly overlap, but combined with a load balancer that removes faulty instances and clients that retry, isolation is much better than with physical partitions alone.

26.2 Cellular architecture

Partition the entire stack including dependencies (load balancers, compute, storage) by user into cells; each cell is independent and a gateway routes requests to cells. (Partitioning by user is only one choice; location or workload also works. New Relic talk: https://www.youtube.com/watch?v=eMikCXiBlOA.)

  • Azure Storage (chapter 17) is cellular: a cell is a storage cluster (stamp) and accounts are partitioned across clusters.
  • Unexpected benefit:
    • cap each cell's maximum size
    • to grow, add a cell rather than enlarge one. You can then test and benchmark at the maximum size and be sure of no future brick wall.
