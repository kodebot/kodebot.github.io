Understanding Distributed Systems 27: Downstream resiliency

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 27. Previous: Understanding Distributed Systems 25-26: Redundancy and fault isolation. Next: Understanding Distributed Systems 28: Upstream resiliency (and Part V intro).

[!abstract] Takeaways Tactical patterns that protect a service from failures of its downstream dependencies, stopping faults propagating:

  • Timeout: always set one; choose it from the downstream's percentile latency.
  • Retry: capped exponential backoff with jitter; retry at one level only; never retry non-transient errors.
  • Circuit breaker: stop calling a dependency that keeps failing; degrade gracefully.

27.1 Timeout

Always configure a timeout: a call with none may never return, and non-returning calls cause resource leaks (chapter 24). Timeouts detect connectivity faults and stop them cascading. Also essential for any operation that may never return, like acquiring a mutex.

Defaults are often bad:

  • JavaScript XMLHttpRequest: default timeout 0 = none (https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest/timeout):
var xhr = new XMLHttpRequest();
xhr.open("GET", "/api", true);
xhr.timeout = 10000; // 10K ms; must be set explicitly
xhr.onload = function () { /* finished */ };
xhr.ontimeout = function (e) { /* timed out */ };
xhr.send(null);
  • fetch: initially no way to set a timeout (https://github.com/whatwg/fetch/issues/951)
    • later added via the Abort API (https://developer.mozilla.org/en-US/docs/Web/API/AbortController).
  • Python requests:
    • default infinity (https://requests.readthedocs.io/en/master/user/quickstart/#timeouts)
    • Go's HTTP package: no timeouts by default (https://github.com/golang/go/issues/24138).
  • Modern Java and .NET clients do better
    • .NET Core HttpClient defaults to 100 s (lax but better than none) (https://docs.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.timeout?view=net-6.0#remarks).
  • Rule: always set timeouts on network calls, and beware third-party libraries that make calls without exposing timeout settings.

Choosing the value: base it on the false timeout rate (https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/). If you accept 0.1% of calls that would eventually have succeeded timing out, set the timeout at the 99.9th percentile of the downstream's response time.

Monitor the whole lifecycle of each call (duration, status code, whether a timeout fired): without measuring integration points, production issues are hard to debug. Best wrapped in a library function that sets the timeout and monitors, or via a co-located reverse proxy (sidecar / service mesh, section 18.3) that enforces timeouts and monitors.

27.2 Retry

After a failed or timed-out request: fail fast or retry. A short-lived connectivity glitch usually succeeds on retry after some backoff. If the downstream is overwhelmed, immediate retries make it worse, so slow retries with longer delays until a maximum number of retries or enough elapsed time.

27.2.1 Exponential backoff

Capped exponential delay: delay = min(cap, initial_backoff * 2^attempt). Example: cap 8 s, initial 2 s: retries wait 2 s, 4 s, 8 s, then 8 s (capped).

Problem: when the downstream degrades, many clients fail at the same moment and retry simultaneously, causing load spikes (a retry storm, "herding"). Fix: add random jitter (https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/): delay = random(0, min(cap, initial_backoff * 2^attempt)), spreading retries over time.

Other points:

  • Batch apps without real-time needs can park failed requests in a retry queue, read later by the same or another process.
  • Do not retry non-transient errors (e.g. not authorised): fail fast and cancel.
  • Understand the consequences of retrying non-idempotent calls whose side effects could break correctness (chapter 5.7).

27.2.2 Retry amplification

Chain: client calls A, A calls B, B calls C. If B-to-C fails and B retries, A sees a longer time and may time out and retry, making the client time out and retry. Retries at several levels multiply: the deeper a service in the chain, the more load it gets. This can overload downstream services. So in long chains retry at a single level and fail fast in the others.

27.3 Circuit breaker

If failures are not transient, retrying makes your service slower and the slowness spreads. We need to detect long-term degradation and stop sending requests: "the fastest network call is the one we don't have to make". The circuit breaker (from electrical circuits) lets a sub-system fail without slowing the caller, blocking calls temporarily and allowing them again once it recovers.

  • Retries help when the next call is expected to succeed; circuit breakers help when it is expected to fail, and they prevent the network call entirely.

A state machine with three states:

State Behaviour Moves on
Closed pass-through; counts failures (errors, timeouts) failures exceed a threshold within a time interval: trips to open
Open calls fail immediately, nothing sent after some time: half-open
Half-open the next call is allowed through success: back to closed; failure: back to open
  • Business impact of open:
    • if the dependency is non-critical, degrade gracefully instead of stopping. Analogies: an aeroplane losing a non-critical subsystem still flies and lands
    • Amazon's front page renders without recommendations when that service is down.
  • Tuning is context specific: how many failures count as "down"? How long before half-open? Use data about past failures to decide.
