Understanding Distributed Systems 29: Testing

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 29. Previous: Understanding Distributed Systems 28: Upstream resiliency (and Part V intro). Next: Understanding Distributed Systems 30: Continuous delivery and deployment.

Takeaways
  • Tests catch bugs early and, more importantly, let you change code without breaking behaviour; they also act as always up-to-date documentation and improve public interfaces (you must use them as a user would).
  • Testing is not a silver bullet: it only covers failures developers can imagine, not emergent behaviour in production (see Cindy Sridharan, https://copyconstruct.medium.com/testing-microservices-the-sane-way-9bb31d158c16).
  • Prefer small scope, small size; build a pyramid: many unit, fewer integration, fewest end-to-end tests. Flaky tests are nearly as bad as no tests.
  • Use real implementations > fakes > stubs and mocks; combine mocks with contract tests.
  • For hard-to-test design risks use formal specification (TLA+) to find bugs before writing code.
  • Rule of thumb: to be confident an implementation behaves a certain way, add a test for it. "The longer it takes to detect a bug, the more expensive it is to fix."

29.1 Scope

System under test (SUT) = the code paths a test actually exercises (vs ones merely run). Scope sets the category.

  • Unit test:
    • a small part of the codebase, like a class (the "sociable" kind: https://martinfowler.com/articles/2021-test-shapes.html)
    • It should be static in time: change only when the SUT's behaviour changes (refactors, bug fixes, new features should not break it)
    • So:
    • use only the SUT's public interfaces;
    • test state changes in the SUT, not predetermined sequences of actions;
    • test behaviours: how the SUT handles a given input in a specific state.
  • Integration test:
    • verifies the service interacts with an external dependency as expected
    • Fowler (https://martinfowler.com/bliki/IntegrationTest.html): narrow (only code paths that talk to one dependency, e.g. an adapter and its supporting classes) vs broad (code paths across multiple live services)
    • The book calls broad ones end-to-end tests.
  • End-to-end test:
    • behaviour spanning multiple services, a user-facing scenario
    • Runs in shared environments (staging or production) so it must not affect other tests or users
    • Slow, prone to intermittent failures, expensive to maintain, and a failure rarely shows which service caused it
    • A "necessary evil": uncovers unanticipated side effects and emergent behaviours.
  • User journey test:
    • a multi-step interaction (e-commerce: create an order, modify, cancel) as one test
    • usually faster than the parts as separate end-to-end tests, so it minimises their number.
  • Larger scope = more brittle, slow and costly.
    • Intermittent failures make developers ignore tests
    • Prefer small scope
    • Good trade-off: many unit tests, fewer integration tests, even fewer end-to-end tests (the test pyramid).

29.2 Size

Size = compute resources needed (e.g. number of nodes); correlated with scope but distinct (https://www.amazon.com/dp/B0859PF5HB, Software Engineering at Google).

  • Small: one process, no blocking calls or I/O: very fast, deterministic, very unlikely to flake.
  • Intermediate: one node, local I/O (disk, localhost network): more delay and non-determinism, more intermittent failures.
  • Large: multiple nodes: even more non-determinism and delay.
  • Larger tests are slower and flakier, so write the smallest possible test for a behaviour. Use test doubles to shrink it:
    • Fake: lightweight implementation behaving like the real one (an in-memory database).
    • Stub: a function that always returns the same value whatever the arguments.
    • Mock: has expectations on how it is called; tests interactions between objects.
  • Doubles do not capture the real thing's nuances: the weaker the resemblance, the less confidence. So:
    1. use the real implementation if it is fast, deterministic and has few dependencies;
    2. else a fake maintained by the dependency's own developers;
    3. stubs and mocks are last resort (least resemblance, brittle tests).
  • Contract tests
    • (https://martinfowler.com/bliki/ContractTest.html) are a good compromise for integration tests with mocking: a contract defines a request and its expected response (for REST: an HTTP request and response)
    • The test mocks the dependency from the contract, and the dependency's own test suite uses the same contract to simulate the client request and check the response, so the contract cannot silently break.

29.3 Practical considerations

Trade-offs. Example: end-to-end test one API endpoint of a service that talks to a data store, an internal service owned by another team, and a third-party billing API.

  • Endpoint does not call the internal service: safe to mock it.
  • Data store has an in-memory fake: use it, avoiding network calls.
  • Billing API: real calls would issue real transactions; without a fake, maybe the provider offers a testing endpoint issuing fake transactions.

Counter-example where smaller is riskier: testing that purging a user's data across the whole stack works. In Europe it is legally mandated (GDPR; fines up to EUR 20 million or 4% of annual turnover, whichever is greater). A silent break is high-risk, so use an end-to-end test that runs periodically in production against live services (no doubles).

29.4 Formal verification

Writing a specification (a high-level description of behaviour) before code reveals subtle bugs and architecture flaws early. It can range from an informal one-pager to a formal mathematical description a computer can check.

  • Benefits: forces you to understand what you specify; documentation for others; guide to the implementation; if formal, model checking can algorithmically find flaws.
  • Do not specify every corner: specify the parts most likely to contain errors and hard to catch with tests, at a chosen level of abstraction (which details to omit).
  • TLA+
    • (Temporal Logic of Actions; https://lamport.azurewebsites.net/tla/tla.html) is widely used, e.g
    • by Amazon (S3) and Microsoft (Cosmos DB) (https://lamport.azurewebsites.net/tla/industrial-use.html)
    • A behaviour is a sequence of states (assignments of values to global variables); a spec is the set of all possible behaviours.
  • Safety property:
    • something is true in all states (an invariant)
    • Liveness property: something eventually happens
    • TLA+ verifies these over all states and behaviours: powerful because a system at scale eventually meets all of them and humans are bad at imagining several rare events together.

Worked example (migrating from key-value store X to cheaper Y with no downtime):

  1. The service dual-writes to X and Y, still reading only from X.
  2. A one-off batch backfills Y with data from X older than the dual-write start.
  3. The app switches to read and write only Y. Will the stores end up in the same state? The model checker finds:
  • a liveness violation: an instance crashes after writing to one store but before the other, leaving them inconsistent;
  • modelling the two writes as atomic fixes that, but with two instances writing concurrently the stores can see writes in different orders and diverge;
  • fix: a message channel that serialises all writes into one global order (like the transactions discussion, section 13.1). A failing check returns an error trace, the exact sequence of states violating the property. Point: a formal model lets you test architectural decisions that are otherwise hard to verify.
