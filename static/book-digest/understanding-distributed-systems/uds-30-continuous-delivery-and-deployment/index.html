Understanding Distributed Systems 30: Continuous delivery and deployment

Source: Roberto Vitillo, Understanding Distributed Systems, 2nd ed. (v2.0.0, 2022), ch. 30. Previous: Understanding Distributed Systems 29: Testing. Next: Understanding Distributed Systems 31: Monitoring.

Takeaways
  • Manual releases are infrequent, so changes batch up (more risk, harder to find the breaking change) and tie up an engineer. Automate the whole path from merge to production, rollbacks included: a CD pipeline.
  • Releasing is a main source of failures, so CD needs heavy investment in safeguards, monitoring and automation. If a regression appears the artifact is rolled back or rolled forward to a hotfix. Balance safety vs release time.
  • Four stages: review, build, pre-production, production.
  • Make every change backward compatible; split incompatible ones into prepare, activate, cleanup.

30.1 Review and build

It starts with a pull request (PR), which must be compiled, statically analysed and validated by tests, all in a few minutes. Tests here should be small (single process or node) for speed and fewer flakes; larger ones run later.

A teammate must review and approve. The reviewer judges whether it is correct and safe to release automatically. A checklist helps:

  • unit, integration and end-to-end tests included as needed?
  • metrics, logs and traces included?
  • can it break production (backward-incompatible change, hitting a service limit)?
  • can it be rolled back safely?

Not only code: static assets, end-to-end tests and configuration should be version controlled (not necessarily in the same repo) and treated like code; a service can have several pipelines, one per repository, running in parallel.

The author stresses reviewing and releasing configuration changes through CD, as config changes applied globally without review or testing are a top cause of production failures (chapter 24).

Infrastructure as Code (IaC) (https://docs.microsoft.com/en-us/devops/deliver/what-is-infrastructure-as-code): declare cloud dependencies (VMs, data stores, load balancers) in code with tools like Terraform (https://www.terraform.io/), so provisioning is automated and infra changes are treated like software changes.

After merge to main, the build stage builds and packages the repository into a deployable release artifact.

30.2 Pre-production

The artifact goes to a synthetic pre-production environment. Less realistic than production but good for catching hard failures (e.g. a null pointer at startup from a missing config setting) and running end-to-end tests. It releases much faster than production, so bugs surface earlier.

  • Can be several environments:
    • from one created from scratch per artifact for simple smoke tests, to a persistent production-like one receiving a small fraction of mirrored production requests
    • AWS is known for multiple pre-production environments (https://aws.amazon.com/builders-library/automating-safe-hands-off-deployments/).
  • Judge health with the same signals as production (metrics, alerts, tests equivalent), so pre-production is not a "second-class citizen" with poor coverage.

30.3 Production

Start with a small number of production instances (canary testing) to surface undetected problems quickly before widespread damage. If all health checks pass, release incrementally to the rest of the fleet.

  • During rollout some instances are out of service, so remaining ones must have capacity to absorb the load.
  • Multiple regions:
    • start with a low-traffic region, then the rest in sequential stages
    • More stages mean longer release, so speed up once confidence builds: e.g
    • stage 1 a single region, stage 2 a larger region, stage 3 N regions at once.

30.4 Rollbacks

After each step the pipeline assesses health; if unhealthy, stop and roll back. Signals: end-to-end test results, health metrics (latencies, errors), alerts.

  • Watch also upstream and downstream services, to catch indirect impact.
  • Allow bake time between steps, as some issues appear later (e.g. a degradation visible only at peak time)
    • Bake time can shrink after each successful step, and can be gated on request counts for specific API endpoints so the API surface is properly exercised.
  • On degradation the pipeline stops, then either rolls back automatically or alerts the on-call engineer, who decides (pipelines can run only in business hours to spare on-call)
    • The engineer can have the failed stage retried (e.g. something else was deploying) or roll back entirely.
  • Or stop and wait for a hotfix rolled forward, needed when the release cannot be rolled back due to a backward-incompatible change
    • Roll forward is much riskier than rollback, so as a rule every change should be backward compatible (https://aws.amazon.com/builders-library/ensuring-rollback-safety-during-deployments/)
    • The commonest breaker is changing the serialisation format used for persistence or IPC.

Safely making an incompatible change: split it into backward-compatible steps, each individually safe to roll back. Example: changing the message schema between producer and consumer:

  1. Prepare: change the consumer to support both old and new formats.
  2. Activate: change the producer to write the new format.
  3. Cleanup: the consumer drops the old format, released only once confident the activate change will not need rolling back.

An automated upgrade-downgrade test in the pre-production stage of the pipeline can check that a change is actually safe to roll back.
