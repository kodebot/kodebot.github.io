Before you startLeading a Java Team: The Yard#

A short book for a lead who knows how software is built and has just inherited a team that builds it in Java. It covers 15 arguments the team will have in the first 90 days. For each one it explains the mechanism underneath, tells the history behind it, and shows the decision a lead makes and defends.

The promise

It is about four hours of reading, four or five evenings. Read it and you will walk into your first design review already knowing the shape of the arguments. You will know:

  • why the build takes 9 minutes, and whether switching to Gradle would fix it;
  • why the senior developer wants Lombok and the junior wants records;
  • why every test is green and nothing is actually tested;
  • why the database in the tests is not the database in production;
  • why a library upgrade broke a module nobody touched;
  • why a pod died at 2 in the morning with no stack trace;
  • why a few requests fail on every deploy.

For each argument you will know what the thing is called, what it actually does, who argued about it first and in what year, and what the lead in this book decided and why. You will also see where the lead was wrong. A lead who is never wrong is a lead nobody tells anything.

The book reads as one story. Each chapter opens on two people who want different things. The middle of the chapter explains the mechanism underneath their argument. The chapter ends with the lead's decision, said to the team in plain words, and with the crack that becomes the next chapter's problem.

The setting

Sorrel is a mid-sized insurer. It sells motor and home policies, takes claims, and pays them. It runs about 40 Java services, most of them built with Spring Boot, on a shared Kubernetes cluster.

The Payouts team has 6 developers. They pay approved claims. To pay one, their code reads the policy system (owned by another team), writes the payment to the ledger (owned by Bea's team) and sends an instruction to a bank gateway (run by an outside supplier).

The team's code is one Maven build with several modules. A module is one buildable part of the project, with its own pom.xml, much like one project in a .NET solution. Three of the modules are services that get deployed:

  • payouts-api: the main service. It takes payout requests and pays claims.
  • payouts-callbacks: receives the confirmations that other systems, such as the ledger, send back to Payouts.
  • payouts-reports: builds the monthly payout file for the finance team.

A fourth module, payouts-domain, is not deployed on its own. It is a library inside the build that holds the shared business code (Payout, PayoutService, PayoutRepository), and the services depend on it.

The cast

You meet five people. Each one is introduced again by role in every chapter, because you may come back to the book after a few days.

  • Sam is the new lead of the Payouts team. Sam spent 12 years leading .NET teams, and this is Sam's first Java team. Sam knows what good engineering looks like, but not yet what each thing is called in Java. Sam is the reader's eyes, and is wrong on the record more than once.
  • Rafael is the team's senior developer. He has been at Sorrel for 8 years and wrote most of the build, including the parent POM every module inherits from. He is right about most things and used to being right, though not always.
  • Aisha is the junior developer, 2 years in. She opens the file and reads it before anyone argues, and she asks the questions a lead cannot ask without looking lost.
  • Oren runs the platform team. His team looks after the shared Kubernetes cluster, the image registry where container images are stored, and the artifact repository the builds download libraries from. He measures everything and answers in numbers.
  • Bea owns the ledger service on another team. When Payouts breaks the ledger, she is the one who rings. She is the counterpart Sam negotiates with.

There is no villain. The arguments are ordinary ones, and both sides are usually right about something.

Who this is for

You lead, or are about to lead, a Java team, and you learned the trade somewhere else. Most likely that was .NET, but Go, Python or TypeScript will do. You can read Java code. What you cannot yet do is tell which of the team's arguments matter, who is right, and what it costs to decide either way. This book is for that.

It is not a Java tutorial. Its companion, Java for C# Developers, holds the detailed mechanics in about 170,000 words. Every chapter here ends by naming the handbook chapters that carry the detail. Read the story here, and look up the syntax there.

If you have led Java teams for years, this book will feel slow. Read the At the whiteboard boxes and the decision log in the epilogue, and argue with them.

Chapter 1 · Act IThree Services, Three Javas#

Sam's second day as the new lead, and the first surprise: the team says it runs Java 21, and one of its three services runs Java 11. This chapter explains how a Maven build decides which Java and which library versions each part of a project uses, why one module can quietly ignore the rules everyone else follows, and the one command that shows you the truth.

The problem

Sam had been at Sorrel for two days. Sorrel is an insurer, and Sam had been hired to lead the Payouts team: six developers who look after the services that pay approved insurance claims. Sam had spent twelve years leading .NET teams. This was the first Java team.

On the second morning, Oren, who runs the platform team that looks after the shared Kubernetes cluster every Sorrel service runs on, sent a spreadsheet. It had one row for every container image on the cluster, and one column showing which base image each was built on.

A base image is the starting layer of a container, the operating system and runtime the service sits on top of. For a Java service it usually carries the Java runtime. The Payouts rows said:

Service Base image
payouts-api eclipse-temurin:21
payouts-callbacks eclipse-temurin:21
payouts-reports eclipse-temurin:11

Eclipse Temurin is a free build of Java, the most common one in containers. The number after the colon is the Java version. So two services ran Java 21, and one ran Java 11.

Sam took the spreadsheet to the team's morning stand-up. Rafael, the team's most senior developer, eight years at Sorrel and the author of most of the build setup, answered before Sam had finished asking.

"We're on 21," he said. "It's in the parent POM. Has been since the Christmas before last."

A POM is a Maven project file, pom.xml. (The letters stand for Project Object Model.) It plays the part a .csproj plays in .NET: it names the project, its dependencies and how to build it. A parent POM is one that other POMs inherit settings from, much like a Directory.Build.props file that every project in a .NET solution picks up.

"And the third one?" Sam asked.

"Reports," Rafael said. "It builds the monthly file for finance. Nobody has touched it in three years and nobody wants to. It works."

Sam had been here before, in .NET. There, the answer was a Directory.Build.props with one target framework that every project inherited. Anyone who overrode it had to explain why in a pull request. Here the parent POM said 21, and Rafael said 21. But one of the three services was running a Java version two major releases older, which no longer gets free security updates.

Aisha, the team's junior developer, two years in and the person most willing to open a file and look, found the cause in ten minutes. The reports module's own pom.xml set the Java version back to 11, three lines below the line that said it inherited from the parent. It also pinned an older version of Spring Boot. Both lines had been added in a hurry during an incident, with no comment, by someone who had since left the company.

"So which Java are we on?" Sam asked.

"All of them," Aisha said.

The idea

What a parent POM looks like

Here is a cut-down version of Sorrel's parent POM, the file every Payouts module inherits from:

<project>
  <groupId>com.sorrel</groupId>
  <artifactId>sorrel-parent</artifactId>
  <version>12</version>
  <packaging>pom</packaging>

  <properties>
    <maven.compiler.release>21</maven.compiler.release>
    <spring-boot.version>3.5.16</spring-boot.version>
  </properties>

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-dependencies</artifactId>
        <version>${spring-boot.version}</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>
</project>

And here is the start of a module that inherits from it:

<project>
  <parent>
    <groupId>com.sorrel</groupId>
    <artifactId>sorrel-parent</artifactId>
    <version>12</version>
  </parent>
  <artifactId>payouts-api</artifactId>
</project>

The <parent> block is the whole link. Everything the parent declares, the child gets, unless the child says otherwise.

Three things a parent POM should say once

A good parent POM states three things once, for every module.

  1. Which Java release to compile for. This is the maven.compiler.release property, set to 21 above. (A property is a named value; ${spring-boot.version} further down reads one.) It does two jobs. It makes the compiler produce code that runs on Java 21. And it makes the compiler reject any call to a Java API newer than 21. Older builds used two settings called source and target instead. Those only did the first job, so code could compile fine and then crash on the older Java.
  2. Which version of each library the company has agreed on. These go in a dependencyManagement block. A version listed there does not add the library to any module. It only says: if a module uses this library, use this version. So a module can ask for spring-data-mongodb with no version number at all, and it gets the agreed one. In .NET terms this is close to central package management with Directory.Packages.props.
  3. Which build plugins to use, at which versions. Maven does its work through plugins: one compiles, one runs tests, one packages. Pinning them in the parent means every module is built with the same tools.

How Spring Boot's versions arrive

Spring Boot is the framework almost every Sorrel service is built on. It needs dozens of libraries, and they have to be versions that work together. Spring publishes that agreed list as a BOM, a bill of materials: a special POM whose only content is a list of library versions that are known to work together.

There are two ways to bring Boot's BOM into a build, and the choice matters.

  • Inherit from spring-boot-starter-parent. You make Spring's own POM your parent. You get Boot's versions, plus sensible plugin settings, for free.
  • Import spring-boot-dependencies into your own dependencyManagement. That is the <scope>import</scope> block in Sorrel's parent above. You get Boot's versions and nothing else.

The catch is that a POM can have only one parent. A company that wants its own parent, with its own rules for every team, cannot also make Spring's POM the parent. So it imports the BOM instead. That is what Sorrel does, and Rafael chose it eight years ago for that reason. Nobody had written the reason down. A lead from .NET tends to reach for the starter parent, because every tutorial uses it, and in doing so would quietly remove the company's rules.

How a module breaks the rules

Inheritance in Maven works like a default, not a law. Any module can redeclare any property, managed version or plugin setting, and the module's own value wins over the parent's. That is what the reports module had done:

<parent>
  <groupId>com.sorrel</groupId>
  <artifactId>sorrel-parent</artifactId>
  <version>12</version>
</parent>
<artifactId>payouts-reports</artifactId>
<properties>
  <maven.compiler.release>11</maven.compiler.release>
</properties>

The parent says 21. The module says 11. The module wins. Nothing warns you.

The effective POM: the one file that tells the truth

So how do you know what a module really uses? Reading its pom.xml is not enough, because most of its settings live in the parent and in the imported BOM. Reading the parent is not enough either, because the module can override it.

Maven can answer the question for you. The effective POM is the module's POM with everything merged in: the parent, the imported BOMs and the module's own overrides, all resolved into one file. Maven prints it on request with help:effective-pom. If you remember one command from this chapter, make it that one. It is how Aisha found the 11 in ten minutes.

Remember it as: the parent POM sets defaults any module can override; the effective POM shows what each module really uses.

Building one module at a time

Two flags come up constantly once you start working module by module.

  • -pl payouts-api (short for "projects list") builds only that module.
  • -am ("also make") also builds the modules it depends on.

The second one matters because of the local repository. Every time Maven builds or downloads a library, it keeps a copy in a folder on your machine, ~/.m2/repository. It is a cache, a bit like the NuGet packages folder. If you build payouts-api with -pl but without -am, Maven does not rebuild payouts-domain, which payouts-api depends on. It takes whatever copy of payouts-domain is sitting in the local repository, which may be last week's. The build passes on your laptop and fails on a colleague's, and neither of you knows why.

Sam's decision

Sam told the team that afternoon:

  • One parent, one Java release, one Spring Boot version. Every module inherits them.
  • Any override of a parent setting needs a comment saying why, and a date. An override is sometimes right. A silent one never is.
  • A pull request that changes a POM shows the effective POM before and after. That is the only way a reviewer can see what actually changed.
  • Reports moves to Java 21 this week. It already compiles on 21, and Oren already has the image.
  • Reports moves to Java 25 with everyone else, and not before. Sam had been there four days, and reports was the one module nobody on the team could explain.

Rafael asked whether the comment rule was a .NET habit. Sam said yes, and that it was a good one.

◷How we got hereMaven began with a problem every team that shares code eventually has.

Maven began with a problem every team that shares code eventually has.

In 2001 Jason van Zyl was working at the Apache Software Foundation on a web framework called Jakarta Turbine. Turbine was split into several subprojects. Each had its own build script, written in an older tool called Ant, and each script was slightly different. Each subproject also kept its own copies of the libraries it needed, as jar files checked straight into version control. When a shared library changed, someone had to copy the new jar into every subproject by hand, and hope they had not missed one.

In August 2001 van Zyl built a prototype of something different, and through 2002 he proved it on Turbine. His idea turned the arrangement around:

  • A project would describe itself in a model file, rather than script its build step by step.
  • The build would follow conventions (source code here, tests there) instead of custom scripts.
  • Libraries would be fetched by name and version from a shared repository, instead of being committed alongside the code.

Maven became a top-level Apache project in March 2003, and version 1.0 shipped on 13 July 2004.

That first version was still a scripting tool underneath, and it showed. So the project rewrote it. On 19 October 2005 Brett Porter announced Maven 2.0 as "a rewrite of the popular Maven application". It brought the two ideas this chapter is about. The first was transitive dependencies: a project names the libraries it uses, and Maven works out what those libraries need in turn. The second was POM inheritance: a parent POM can set rules for a whole family of modules.

The price was XML, and twenty years of jokes about it. The gain is what made Sam's second morning short. Two Maven projects at two different companies have the same shape. A new lead can open either one and know where to look.

⚙The kit

The legacy folder in the companion project contains a reports module with the same override Aisha found.

# Print the merged, effective POM of the legacy reports module to a file,
# then find the Java release it really compiles for (it says 11)
./mvnw -q -f examples/payouts/legacy/pom.xml -pl payouts-reports \
  help:effective-pom -Doutput=/tmp/eff.xml
grep -m1 'maven.compiler.release' /tmp/eff.xml

# List the modules in the build, in the order Maven will build them
./mvnw -f examples/payouts/pom.xml validate | grep -A4 'Reactor Build Order'

# Build one module and the modules it depends on (-pl picks it, -am adds its dependencies)
./mvnw -q -f examples/payouts/pom.xml -pl payouts-api -am compile

# Count how much a module inherits without ever writing it
./mvnw -q -f examples/payouts/pom.xml -pl payouts-api \
  help:effective-pom -Doutput=/tmp/api.xml
grep -c '<artifactId>' /tmp/api.xml

A few things in these commands are worth knowing once:

  • help:effective-pom has the shape plugin:goal. Maven does its work through plugins, and each plugin offers named tasks called goals. This one runs the effective-pom goal of Maven's help plugin.
  • -q keeps Maven quiet except for errors, and -f points Maven at a POM in another folder, so you can run everything from the root of the book's repository.
  • -pl picks a module and -am adds the modules it depends on, as explained above.
  • -Doutput=/tmp/eff.xml sets a parameter for the goal, here the file to write. Every -D in this book does the same job: it passes a named setting to Maven or to a plugin.
⚠The traps
  • The silent override: the sign is a property or a dependencyManagement block in a module's POM with no comment beside it. The module's value beats the parent's, and the parent's rule stops applying to that one module without any warning. Ask for the reason, and write it next to the override.
  • Two parents wanted: the sign is spring-boot-starter-parent appearing in a team that already has a company parent. A POM can have only one parent, so this quietly drops the company's rules. Import Spring's BOM into dependencyManagement instead.
  • source and target instead of release: the sign is <source> and <target> in the compiler plugin's settings. The code compiles to an old format, but calls to newer Java APIs still compile and then fail at runtime on the older Java. Use maven.compiler.release.
  • -pl without -am: the sign is a single-module build that passes on one laptop and fails on another. Without -am, the modules it depends on come from your local repository, which may hold an old copy. Add -am.
  • The version nobody can find: the sign is a dependency with no version number and no obvious place it comes from. It is coming from the parent, from an imported BOM, or from a plugin. The effective POM tells you which.
◉Spot itspot the flaw

Sorrel's parent POM pins Spring Boot through a property, <spring-boot.version>3.5.16</spring-boot.version>, and imports Boot's BOM at ${spring-boot.version}. Here is a module that inherits from it. Something in it is wrong.

<parent>
  <groupId>com.sorrel</groupId>
  <artifactId>sorrel-parent</artifactId>
  <version>12</version>
</parent>
<artifactId>payouts-reports</artifactId>
<properties>
  <spring-boot.version>2.7.18</spring-boot.version>
</properties>
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>
  </dependency>
</dependencies>
Show the answer

Answer The module redeclares spring-boot.version, the property the parent uses to choose which Boot BOM to import. So this one module silently imports Boot 2.7 while every other module uses 3.5. The starter has no version number, which hides the problem: you would never see "2.7" next to it. The sign is a child POM setting a property the parent uses for versions. The fix is to delete the property. If the module truly cannot move yet, keep the override but write the reason and a date beside it, so the next lead does not need Aisha's ten minutes.

✎At the whiteboard
  1. How many places can set this module's Java release, and which one wins?
  2. Does every module in the build inherit from our parent, or do some only sit in the build?
  3. If I change a library version in the parent today, which modules change, and which have overridden it?

Still argued: should a company inherit Spring's starter parent or import Spring's BOM? Spring Boot's own documentation recommends the starter parent, because it brings useful plugin settings that importing the BOM does not. The Maven project's own guidance treats a company parent as normal for any organisation with more than one build, and a company parent means importing the BOM. Both are right. The deciding question is simply whether you already have a company parent. Sorrel does.

What Sam learned

  • Ask for the effective POM before believing anyone, including the parent POM.
  • A rule in the parent is only a rule if overriding it costs a comment and a review.
  • Move the thing nobody understands last, and move it to where everyone else already is.

Chapter 2 · Act IThe Build That Downloads the Internet#

Aisha's new laptop takes 22 minutes to build code that compiles in under 2. The rest is downloading. This chapter follows one library from the internet into your build: the cache on every machine, the settings file that says where to look, and the company server that can see every download. It ends with the argument about whether that server should be the only way in, and with the commands that show where your jars really came from.

The problem

On Friday, the end of Sam's first week as the new lead of the Payouts team, Aisha, the team's junior developer, two years in, got a new laptop. She cloned the Payouts repository and started her first build. It took 22 minutes.

Most of that time the screen showed lines like these, scrolling faster than anyone could read:

Downloading from central: https://repo.maven.apache.org/maven2/io/github/resilience4j/resilience4j-core/2.4.0/resilience4j-core-2.4.0.pom
Downloading from central: https://repo.maven.apache.org/maven2/io/github/resilience4j/resilience4j-core/2.4.0/resilience4j-core-2.4.0.jar

Each line is Maven, the build tool, fetching one file. A jar (Java archive) is a zip file of compiled Java classes, the Java equivalent of the DLL inside a NuGet package. The .pom file next to it is that library's own project file, which tells Maven what the library needs in turn. Maven Central, the central in each line, is the public repository where nearly every open-source Java library is published. It plays the part nuget.org plays in .NET.

The build needed hundreds of these files. Payouts names a few dozen libraries in its POMs. (A POM, pom.xml, is a Maven project file, much like a .csproj.) But each of those libraries needs others, and those need others again. These indirect needs are called transitive dependencies, and Maven downloads all of them. It also downloads its own plugins, because the parts of Maven that compile, test and package are themselves jars fetched from Central.

Oren, who runs the platform team (the shared Kubernetes cluster, the image registry and the artifact repository every Sorrel team uses), had seen the same thing every night. His CI runners, the machines that build every team's code on each change and every night, start empty on purpose, so that no leftover file from yesterday can affect today's build. The Payouts nightly build took 13 minutes on them, and 4 of those minutes were a download progress bar.

Rafael, the team's most senior developer, eight years at Sorrel and the author of most of the build, was not worried.

"That's Maven," he said. "First build fills the cache. After that it's fast. Everyone's laptop has a gigabyte of jars in it and nobody notices."

The cache he meant is a folder on each machine where Maven keeps a copy of every file it has ever downloaded. Rafael's laptop had eight years of copies in it. Aisha's had none.

Oren had noticed. For two years the platform team had run an artifact repository: a server inside the company that holds copies of libraries, so that builds fetch them from Sorrel's own network instead of from the internet. Sorrel's runs Nexus, a product made by Sonatype. A .NET team would recognise it as a private NuGet feed, such as an Azure Artifacts feed. About half of Sorrel's builds went through it. The other half, Payouts included, went straight to Maven Central over the office internet connection. That was why the nightly builds of 20 teams all slowed down at the same time: they were all queuing for the same connection.

Oren wanted every download routed through the Nexus, and he wanted it in writing. A download that goes through his server is one he can count, store and, if a library turns out to be dangerous, block.

Rafael did not want that. "Central has been up for 20 years. The Nexus went down twice last quarter. If it's the only road, we can't build when it's down." Rafael's concern was the team's ability to ship a fix at two in the morning, not the platform team's dashboards.

Sam had seen this argument from the other side. In .NET it was a nuget.config file that cleared the default sources and named one private feed, and a packages.lock.json file that recorded the exact version of every package. With dotnet restore --locked-mode, the build failed loudly if what it was about to restore did not match the lock file. What worried Sam was not the 13 minutes. It was that nobody in the room could say, for any one jar in the build, where it had come from, whether it was the same bytes as last month, or what would happen if it stopped being there.

"Where does spring-core come from?" Sam asked. spring-core is the base library of the Spring framework, which every Payouts service is built on.

Three people gave three answers. "Central," said Rafael. "My .m2 folder," said Aisha. "The Nexus," said Oren, "for half of you." All three were partly right.

The idea

Where Maven looks, in order

Every dependency in a Maven build is found along the same path. A dependency is named by three parts, called its coordinates: a group (org.springframework), an artifact name (spring-core) and a version. Together they work like a NuGet package ID plus its version. Here is what Maven does with each one.

  1. It reads the POM and collects the coordinates of every dependency, direct and transitive.
  2. It looks in the local repository. The local repository is the cache Rafael meant: a folder on your machine, ~/.m2/repository, where Maven keeps every jar and POM it has downloaded, filed by coordinates. Version 2.4.0 of resilience4j-core lives in ~/.m2/repository/io/github/resilience4j/resilience4j-core/2.4.0/. If the file is there, Maven uses it and touches no network. In .NET terms this is the global packages folder, ~/.nuget/packages.
  3. On a miss, it asks a remote repository. By default the remote is Maven Central. A file called settings.xml, in ~/.m2/ on each machine, can change that. It is per machine, not per project, and is not normally committed to the code repository. It is close to a user-level NuGet.Config.
  4. A mirror redirects the request. A mirror is an entry in settings.xml that says: send requests for these repositories to this other address instead. With <mirrorOf>*</mirrorOf>, the star means every repository, so every download goes to one address.
  5. The company repository answers. Nexus, or a rival product called Artifactory, sits at that address. It acts as a proxy: it fetches from Central on the company's behalf, keeps a copy on its own disk, and answers from that copy from then on.
  6. Maven saves the file in the local repository, so the next build on that machine does not ask again.

This is the mirror entry that sends everything to the company's Nexus:

<settings>
  <mirrors>
    <mirror>
      <!-- Every download goes through the platform team's Nexus. Owner: Oren. -->
      <id>sorrel-nexus</id>
      <mirrorOf>*</mirrorOf>
      <url>https://nexus.sorrel.example/repository/maven-public/</url>
    </mirror>
  </mirrors>
</settings>

What follows from the path

That is the whole mechanism, and it explains everyone in the room.

  • The local repository is a cache that is never cleared. Maven never deletes from it. That is why Rafael's laptop was fast and Aisha's was slow. It is also why a CI runner that starts empty pays the full download every night.
  • The mirror is the only point where the company can see what it depends on. Downloads that go straight to Central leave no record at Sorrel. Downloads through the Nexus can be counted, kept and blocked. That is why Oren wanted it.
  • A build that cannot reach its mirror cannot build anything it has not already cached. If the mirror is the only road and the mirror is down, a new laptop or an empty runner stops. That is why Rafael did not want it.

Back to Sam's question about spring-core. Rafael's spring-core had come from Central, years ago. Aisha's build had just taken it from her new local repository, which had taken it from Central an hour earlier. And on the half of the company's machines with a mirror, it came from the Nexus.

The same Maven on every machine: the wrapper

The path above depends on which version of Maven is running it. Different Maven versions pick different plugin versions and resolve some things differently. So the next piece is the Maven wrapper. Here is the file that controls it in the companion project:

wrapperVersion=3.3.4
distributionType=only-script
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.10.0/apache-maven-3.10.0-bin.zip

The wrapper is a small script, mvnw, committed to the code repository next to the POM. When you run ./mvnw instead of mvn, the script reads .mvn/wrapper/maven-wrapper.properties, downloads the Maven version named on the last line if it is not already there, and runs it. Every laptop and every runner then builds with exactly Maven 3.10.0, and nobody has to install Maven at all. The nearest .NET idea is global.json, which pins the SDK version. The difference is that global.json only checks the version, while the wrapper fetches it for you.

The same bytes on every machine: reproducible builds

Sam's second question was whether a jar was the same bytes as last month. Ordinarily it is not, even when the code has not changed. A jar is a zip file, and every entry in a zip carries a timestamp. By default that timestamp is the moment of the build. So two builds of the same commit, a minute apart, produce two jars with different bytes.

The fix is one line in the parent POM. (The parent POM is the file every module in the build inherits its settings from.)

<properties>
  <project.build.outputTimestamp>2026-10-16T00:00:00Z</project.build.outputTimestamp>
</properties>

With this property set, Maven's plugins stamp every entry with that fixed time instead of the current one. The build becomes reproducible: the same sources produce byte-identical jars on any machine. You can then compare two builds by their SHA-256 checksums, and "is this the same build?" stops being a matter of opinion. The C# compiler has the same idea in its Deterministic setting, which SDK-style projects turn on by default.

Maven 3.10, released in September 2026, turns reproducible mode on by default. Setting the property is still useful: it lets you choose the timestamp, and it switches the mode on for anyone still running Maven 3.9. That is one more reason for the wrapper to name a current Maven.

Rafael's objection, answered

Rafael's worry is fair. A mirror that is the only road is a single point of failure. The answer is not to avoid the mirror. It is to make its condition visible, so that nobody finds out during an outage.

  • ./mvnw --offline tells you whether you depend on the network today. The flag makes Maven use only the local repository. If any file is missing, the build fails fast on the first one, in seconds. A build that passes offline will survive a mirror outage on that machine.
  • ./mvnw dependency:go-offline fills the cache on purpose. The name has the form plugin:goal: Maven's work is done by plugins, each plugin offers several tasks called goals, and this runs the go-offline goal of Maven's dependency plugin. It downloads everything the build will need, so you can do it before a flight or a planned outage instead of discovering a gap halfway through one.
  • The platform team owes the mirror an uptime it can state. A published figure, measured and reported, turns "the Nexus went down twice" from an anecdote into a number Sorrel can hold someone to.

Remember it as: every jar came from somewhere; settings.xml says where, the local repository says it was once, and the mirror is the only place anyone can count.

Sam told the team, and Oren:

  • Every download goes through the Nexus, in every settings.xml and on every runner. It is the only place the company can count and block what it uses.
  • The mirror entry carries a comment with Oren's name and the date. The next person to read it knows who to ask.
  • The wrapper is committed in every repository, and the team runs only ./mvnw. Every machine builds with the same Maven.
  • The parent sets the output timestamp. The same commit then gives the same checksum, wherever it is built.
  • CI caches the local repository between runs, keyed on the POM hashes. The runner saves ~/.m2/repository after a build and restores it before the next. The key is a fingerprint of every pom.xml, so the cache is reused until a POM changes, and rebuilt when one does. The runners stop spending 4 minutes a night downloading the same jars.
  • In return, the platform team publishes an uptime figure for the Nexus and a documented fallback. Rafael's two-in-the-morning fix then rests on a known number, not on luck.

"I'm not choosing between Oren and Rafael," Sam said. "Oren gets one road. Rafael gets to know what condition it is in, and what we do when it closes."

◷How we got hereMaven Central exists because the Apache Software Foundation would not host it.

Maven Central exists because the Apache Software Foundation would not host it.

When Jason van Zyl created Maven at Apache, the tool's whole idea was that a project names its libraries and Maven fetches them. That needed somewhere to fetch them from. Van Zyl asked around the foundation and found that Apache could only host software under licences like its own. Libraries under the LGPL or GPL licences were ruled out, and many important Java libraries used them.

So van Zyl looked elsewhere. He found ibiblio, a public archive run at the University of North Carolina, and got in touch with John Reuning there. Maven's default remote repository became an address on ibiblio. When the traffic grew too much for it, van Zyl bought a machine and had it installed at a hosting company in March 2007. By 2011 the repository belonged to Sonatype, the company van Zyl co-founded, and it still does.

What happens when a repository's address stops answering has been shown twice.

The first time was Codehaus, which hosted hundreds of Java projects and a repository for them. In 2015 it announced that it had "operated at a loss for several years", and it shut its services down around 17 May. Builds that still named repository.codehaus.org did not fail cleanly. They downloaded the farewell notice, an HTML page, and saved it under the name of the jar they had asked for. Then they failed later with "error in opening zip file". For weeks engineers on forums puzzled over corrupt jars that were really a goodbye letter.

The second time was JCenter, a repository run by a company called JFrog, which Gradle and Android builds used by default. On 3 February 2021 JFrog announced that it would shut down. Five days later, once the scale of the breakage was clear, it partly reversed itself and kept JCenter serving the packages it already had. JCenter finally became a redirect to Maven Central in August 2024.

Both stories teach what Sam had asked about. A build that fetches by name from a place it does not control depends on that place staying up, staying honest and staying the same. A company artifact repository is the company's answer to all three.

⚠The traps
  • The invisible cache: the sign is a build that is fast on one machine and slow on another. The local repository is never cleared and never counted, so each machine builds from whatever it happened to download in the past. That is how "works on my laptop" survives in a tool built to prevent it.
  • Half the builds through the mirror: the sign is some settings.xml files with a mirror and some without. The company can count only what passes through the mirror. When an auditor later asks which builds used a particular library (chapter 9), the unmirrored half will have no answer.
  • A system Maven: the sign is people typing mvn on their laptops while the repository has an mvnw. Two Maven versions can pick different plugin versions and resolve dependencies differently. Commit the wrapper and use only ./mvnw.
  • The mirror as a silent single point of failure: the sign is a platform team that cannot say what the mirror's uptime was last month. Route everything through it anyway, and publish its uptime and what happens when it is down.
  • Jars that differ by build: the sign is two builds of the same commit with different checksums. Set project.build.outputTimestamp in the parent, or every "is this the same binary?" gets a shrug.
✎At the whiteboard

  2. Does every laptop and every runner resolve through the same mirror, and who can prove it?
  3. If the artifact repository is down for an hour, what can we still build?

Still argued: should the artifact repository be the only road, or only the preferred one? Platform teams who have been woken by a mirror outage, a view stated in many postmortems since the 2016 npm incident, argue for falling back to the public repository, with the fallback logged: a build that cannot run is a cost too. Both sides agree the route and its fallback must be written down. Sorrel chose Oren's single route, on Rafael's conditions.

  • A build's dependencies have an address, and the address should be one that someone at the company owns.
  • The local repository is why builds are fast and why nobody can say what is in them, so count through the mirror instead.
  • Never make something the only road without a stated condition and a stated fallback.

Rafael wants to upgrade Spring Boot from version 3.5 to version 4, and says it is one line in the parent POM. He is right about the line and wrong about the work. This chapter explains what a major version of Spring Boot actually changes underneath your code, how to build the list of libraries that might not survive the move, and where the one-line change belongs in an upgrade.

The problem

It was Sam's second week leading the Payouts team at Sorrel. Payouts is the team of six that looks after the services paying approved insurance claims. Like almost every service at Sorrel, they are built on Spring Boot, the framework that sets up a Java web service for you: it starts a web server, wires your classes together and picks sensible defaults. Spring Boot sits on top of the Spring Framework, the older core library that does the actual wiring, web handling and data access.

The team was on Spring Boot 3.5. Spring Boot 4 had been out since November. Rafael, the team's most senior developer, eight years at Sorrel and the author of the build, including the parent POM, wanted it. (A POM, pom.xml, is a Maven project file, much like a .csproj. The parent POM is the one every module inherits its settings from, like a Directory.Build.props that every project in a .NET solution picks up.)

"One line in the parent," Rafael said. "Everything else is managed. We've done it for every minor since 2.1. And 3.5 went out of open-source support in June, so we're already running on borrowed time."

By "everything else is managed" he meant that Spring Boot chooses the versions of the libraries it works with. Boot publishes a long list of libraries and the version of each that it has tested together. That list is called a BOM, a bill of materials, and it works like a Directory.Packages.props that someone else maintains. Sorrel's parent POM imports it, so when Rafael changes the Boot version, the versions of all those libraries change with it.

"Out of open-source support" meant that Spring no longer publishes free fixes for 3.5. Each Boot version gets free security and bug-fix releases for a fixed window, and for 3.5 that window ended on 30 June 2026. Paid support continues for companies that buy it.

Oren, who runs the platform team that looks after the shared Kubernetes cluster every Sorrel service runs on, wanted the upgrade too, for a different reason. His team's dashboards used a metrics format that Boot 4 produced by default and Boot 3.5 needed configuring for. Two teams had moved already. Payouts was on the list of teams that had not, and Oren keeps lists.

Sam had done a framework major version before, from .NET Framework to .NET Core. Sam remembered a line in a project file that took an afternoon, and a migration that took a quarter. The difference between those two things was the question nobody in the room had asked.

"What does 4 remove?" Sam asked.

Rafael listed what he knew. The web starter had a new name. (A starter is a single dependency that brings in everything a kind of application needs. The web starter brings the web server, the JSON library and Spring's web layer.) Some configuration properties had moved, and a few things deprecated in 3.x were gone. "The migration guide has a list. It's mostly renames."

The migration guide is the page the Spring team publishes with each major release, listing what changed and what to do about it. Aisha, the team's junior developer, two years in and the person most likely to read the document instead of remembering it, had opened it while he spoke.

She read out the length of the list. Then she read out the Spring Framework version underneath Boot 4, and the Jakarta EE version underneath that. Then she read out three libraries in the parent POM whose versions Boot does not manage, and whose Boot 4 compatibility nobody had checked. One of them was the resilience library every service used to call the ledger, the accounting system Payouts writes every payment to.

"So it's one line," Sam said, "and we find out what the line costs after we've typed it."

The idea

What a major version moves

Here is the line Rafael meant, in Sorrel's parent POM:

<properties>
  <spring-boot.version>3.5.16</spring-boot.version>
</properties>

Change 3.5.16 to a 4.x version and Boot's BOM, imported a few lines further down, switches to the Boot 4 list. Every library on that list moves at once.

A minor release, such as 3.4 to 3.5, keeps the same foundations and adds things. A major release, such as 3 to 4, changes the foundations. That set of foundations is called the baseline, and for Boot 4 it moved in four places.

Layer Boot 3 Boot 4
Spring Framework 6.x 7.x
Jakarta EE 10 (Servlet 6.0) 11 (Servlet 6.1)
Minimum Java 17 17
Test framework JUnit 5 JUnit 6

Jakarta EE is the set of standard Java APIs that web servers and frameworks agree on. It covers the servlet API, which is how a Java web server hands an HTTP request to your code, and others such as bean validation and persistence. A library that touches any of those APIs has to be built for the right Jakarta level.

The baseline matters because of what it breaks around Boot, not in it. Two examples from the migration guide:

  1. Undertow is gone. Undertow is one of the web servers Boot 3 could run on. It does not yet support Servlet 6.1, so Boot 4 dropped it. A service on Undertow must switch to Tomcat, Jetty or Netty.
  2. Jackson moved. Jackson, the JSON library, is now Jackson 3, and its classes moved from the package com.fasterxml.jackson to tools.jackson. Every Jackson import in the code changes, except the annotations such as @JsonProperty, which stay where they were.

A major moves everything Boot manages. Anything in the build that Boot does not manage stays exactly where it was, and may no longer fit.

The release matrix

So the place to start is not the version number. It is the release matrix: a table of which Java, which Boot, which Framework, and which version of every library your parent POM pins outside Boot's BOM. "Pinned outside the BOM" means the parent names a version itself, either for a library Boot does not manage at all, or to override the version Boot would choose.

At Sorrel that list was short. Three entries on it mattered:

  • The resilience library, Resilience4j, which every service uses for retries and circuit breakers when calling the ledger. It is the Java counterpart of Polly in .NET.
  • The pin on the MongoDB driver, the library the services use to talk to DocumentDB, Amazon's database that speaks the MongoDB protocol.
  • A test library that had been added for one module and never revisited.

Each has its own compatibility statement on its own project page. A matrix row looks like this:

Library Boot 3 artifact Boot 4 artifact Ready?
Resilience4j resilience4j-spring-boot3 resilience4j-spring-boot4, from 2.4.0 yes

Each row is a thing a lead can check in an hour, before anyone types the line. The Resilience4j row also shows why the check matters. The Boot 4 support is a separate artifact with a different name, so changing the Boot version alone would leave the Boot 3 integration in the build.

Everything on the left moves together when the Boot version changes. The two red boxes are pinned by Sorrel's own parent, so they do not.

Cheap failures and expensive ones

Then come the renames. The web starter became spring-boot-starter-webmvc. The old name, spring-boot-starter-web, still works in Boot 4, but it is deprecated and will be removed in a later release. Tutorials written before Boot 4 use the old name. Some test annotations were removed outright: @MockBean, which replaces a Spring bean with a mock in a test, is gone in favour of @MockitoBean.

Renames are the cheap part. A build that fails to compile names the problem, and you fix it. The expensive part is behaviour that changes without failing. Two examples from the same guide, both relevant to a team that stores money in a document database:

  • A configuration property that is now ignored. Boot 4 renamed the database connection setting from spring.data.mongodb.uri to spring.mongodb.uri. A service that still sets the old name starts without error, ignores the line, and tries to connect to localhost:27017 instead.
  • A default that flipped. On Boot 3.5, a BigDecimal amount is stored in MongoDB as a string. On Boot 4 it is stored as a Decimal128, a numeric type. Nothing fails. One collection ends up with old payouts stored one way and new payouts stored the other.

The first is the kind of thing appsettings.json would do to a .NET team after a key was renamed: no error, just a setting with no effect. Failures like these are found by tests, which is why chapter 6, on whether the tests test anything, comes before anyone upgrades anything. They are also found by a canary, a release to a small share of traffic first, which is chapter 14's subject.

An upgrade is a project

So a Boot major is a project, with the shape every migration has:

  1. Inventory every library pinned outside the BOM, and its Boot 4 version.
  2. Read the guide for removals and renames, and mark the ones the code actually uses.
  3. Move one service, the one with the best tests.
  4. Run it beside the old version, and compare.
  5. Move the rest.

The one-line version of the story is true only of step 5. Rafael's history with minors was real. Minors never needed this, because a minor keeps the baseline.

Remember it as: a Boot major moves the baseline under every library you did not pin; the line in the parent is the last step, not the first.

  • Aisha owns the matrix. Every library the parent pins outside the BOM, its Boot 4 compatible version, and a yes or no.
  • Rafael picks the service with the best tests to go first. Its tests are what will catch behaviour changes. The choice will also tell everyone something about the tests.

◷How we got hereBefore Spring Boot, a Java web application did not start itself.

Before Spring Boot, a Java web application did not start itself. You packaged it as a file and deployed it into a separately installed server called a servlet container, such as Tomcat, much as an older ASP.NET application was deployed into IIS. The container owned the process. Your code was a guest, configured through XML files.

In October 2012 Mike Youngstrom, a Spring user rather than a member of the Spring team, filed an issue against the Spring Framework asking for something different. He wanted a Spring application started from a simple main() method, with no container to deploy into and sensible defaults a developer could override. He called it "containerless". ASP.NET Core developers will recognise the shape: a Program.cs that starts its own Kestrel server.

Phil Webb and Dave Syer, on the Spring team, answered the issue with a new project rather than a reply. On 6 August 2013 Webb closed the issue and announced the first milestone of Spring Boot. He wrote that the issue was "the genesis of Spring Boot". Version 1.0 shipped on 1 April 2014.

What Boot added was not new machinery. It was a set of decisions about defaults:

  • Auto-configuration, which looks at the libraries present and wires up what it finds.
  • Starters, which bundle the dependencies a kind of application needs.
  • An embedded server, so the application starts its own.
  • A managed list of library versions, so that the versions agree with each other.

That last item is the one this chapter is about. A Boot major is the moment the Spring team moves the whole managed list to a new baseline at once, which is why it lands as a project on every team downstream.

⚙The kit

Maven names a task as plugin:goal: help:evaluate runs the evaluate goal of Maven's help plugin, and dependency:tree runs the tree goal of its dependency plugin. -q keeps Maven quiet except for errors, -f points it at the companion project's POM, and -N (non-recursive) runs on the parent alone. -D sets a property that the goal reads. In the first command -Dexpression names the value to print and -DforceStdout prints it bare, without Maven's log around it. The companion project's parent inherits from Spring's own starter parent, so its parent version is the Boot version: the command prints 3.5.16.

-pl payouts-api (project list) builds only that module, and -am (also make) adds the modules it depends on. -Dincludes limits the tree to the matching library and the path that brought it in. dependency:list lists every resolved library; -DexcludeGroupIds drops Spring's own and -DoutputFile writes the list to a file.

⚠The traps
  • The one-line major: the sign is a pull request that changes the Boot version and nothing else. The build may even pass. The behaviour changes, such as an ignored property or a flipped default, arrive in production instead.
  • Pinned outside the BOM: the sign is a <version> on a dependency that Boot already manages. The pin overrides Boot's choice, and it survives the upgrade unchanged, so it is now a version Boot 4 was never tested with.
  • The tutorial from last year: the sign is spring-boot-starter-web or @MockBean in a Boot 4 build. The old starter still works for now but is deprecated and will be removed, and @MockBean has already been removed and fails to compile. Use spring-boot-starter-webmvc and @MockitoBean.
  • The minor that was a major: the sign is a team that upgrades minors by habit and treats a major the same way. Minors keep the baseline. Majors move it.
  • Moving the worst-tested service first: the sign is choosing the service that most wants the new feature. Choose the one whose tests will tell you what broke.
✎At the whiteboard
  1. Which dependencies in our parent are pinned outside Boot's managed list, and has each one published a Boot 4 compatible version?
  2. Which service has the tests that would catch a behaviour change, and is it the one we are moving first?
  3. Which items in the migration guide's removals list do we actually use?

For waiting: teams that moved to Boot 3 in 2023 had to rename javax packages to jakarta across every library at once, and many organisations' upgrade guidance since says the first minor of a major is where other libraries catch up, so arrive at the second. The field has not settled it. Sorrel's answer is a dated plan, which is neither.

The problem

It was the design review in Sam's second week as lead of the Payouts team. Six people were in the room, and one slide was on the screen.

Rafael, the team's most senior developer, eight years at Sorrel and the author of the team's Maven build, had made the slide. It had two numbers on it.

Build Time on a CI runner
Maven, today 9 min 10 s
Gradle, Rafael's branch 3 min 40 s

A CI runner is one of the machines that builds and tests the code on every change. These timings were taken with a warm cache, meaning the runner already had every library downloaded in its local repository, the folder where Maven keeps copies of everything it has fetched. So neither number included any downloading. Gradle is the other major Java build tool. Where Maven describes a build in an XML file, Gradle describes it in a script written in a programming language. Rafael had spent the weekend writing a Gradle build for the same code.

"Same tests, same modules, same machine," he said. "Gradle does incremental compilation and caches what it's already done. Maven rebuilds the world every time. We're paying 5 and a half minutes a build, 40 builds a day, for XML."

His arithmetic was right: across 40 builds a day, that is 220 minutes of waiting, nearly 4 hours.

The room was with him. Aisha, the team's junior developer, had just spent 2 days waiting on that build while she checked which libraries would survive the Spring Boot 4 upgrade. Oren, who runs the platform team that owns the shared cluster and the CI runners, was there too, and he liked any number that went down.

Sam liked the number as well, and distrusted the slide: nobody had asked what the 9 minutes were made of. In .NET, Sam had once replaced a build system to save 4 minutes. Afterwards it turned out that 3 of those minutes had been a single test that slept.

"Before we change the tool," Sam said, "can we see where the time goes?"

"It's Maven," Rafael said. "That's where the time goes."

Oren had the runner logs, which record when each stage of the build started and finished. He put the timings up beside Rafael's slide.

Stage Time
Compile both modules 1 min 50 s
Run tests 6 min 50 s
Package into jars 20 s

The tests had run one test class at a time, in a single process. A database container was started for each test class that needed one.

"So the build is 2 minutes," Sam said. "And the tests are 7."

The idea

A build is a pipeline of stages

A build is not one thing. It is a series of stages, and each stage grows for a different reason.

  • Compilation turns Java source into class files. Its time grows with the amount of source code, and the compiler sets the speed limit.
  • Tests run the test classes. Their time grows with the number of tests, how long each one takes, and how many run at the same time.
  • Packaging zips the compiled classes into jar files. It is usually small.

A build tool can shorten compilation by doing less of it. It can shorten the test stage only by running the tests differently: more of them at once, or skipping ones whose inputs have not changed. It cannot make a slow test fast.

Look at Oren's numbers again. Rafael's 5 minutes 30 seconds could not have come mostly from compilation, because compilation was only 1 minute 50 seconds to begin with. Most of the saving had to come from the test stage. Rafael had written the Gradle build fresh, and in it the tests ran in parallel. The Maven build ran them one at a time. So the benchmark had changed two things at once, the tool and the way the tests ran, and credited the tool with both.

What Gradle genuinely does better

Gradle's advantages are real, and worth stating fairly.

  1. Incremental compilation. Gradle tracks which classes changed and recompiles only those classes and the ones that depend on them. Maven's compiler plugin, by default, recompiles a whole module when any source file in it changes. .NET developers get something similar from MSBuild, which skips a build step when its inputs are older than its outputs.
  2. A build cache. Gradle stores the outputs of each task, such as "compile this module" or "run these tests", keyed on that task's inputs. If the inputs have not changed, the task does not run at all, and the stored output is used. The cache can live on one machine or be shared across a whole team, so one developer's test run can save another's.

On a large build with many modules, most of which do not change between runs, those two features are decisive. A change in one module means one module is rebuilt and retested, and the rest come from the cache.

Payouts is not that build. It has two modules, payouts-api and payouts-domain, and most changes touch both. Incremental compilation could save part of the 1 minute 50 seconds. It saves nothing of the 6 minutes 50 seconds.

Two Maven settings that were off

Maven has two settings that address the test stage, and both were off. To understand them you need two terms.

  • The JVM is the Java Virtual Machine, the process that runs Java code. It plays the part the .NET runtime plays for a C# program. Starting one takes a moment.
  • Surefire is the Maven plugin that runs unit tests during a build, much as dotnet test runs xUnit or NUnit tests. Surefire can run tests in separate JVMs, which it calls forks.

Here is the setting in the parent POM:

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <forkCount>1C</forkCount>
    <reuseForks>true</reuseForks>
  </configuration>
</plugin>

And here is what each part does.

  • forkCount sets how many test JVMs run at the same time. The default is 1: one JVM runs every test class in the module, one after another. 1C means one JVM per CPU core, so a runner with 4 cores runs 4 test classes at once.
  • reuseForks keeps each JVM alive after it finishes a test class, and gives it the next one. That saves starting a new JVM per class. It also means anything the tests hold in a static field survives. If the tests share a database container that way, the container started for one class serves the next, instead of a new container starting each time.
  • -T 1C is a flag on the Maven command line, not a Surefire setting. It builds independent modules in parallel, one thread per core. It helps only when modules do not depend on each other.

A .NET developer may be surprised that this is not the default. In xUnit, test classes run in parallel unless you say otherwise. In Maven, tests run one class at a time unless you say otherwise. The rule has an exception in both worlds. Tests that share state, such as rows in one database, will interfere when run in parallel. Those tests need their own data or their own container, or they must stay serial and accept the cost.

With both settings on, Oren's runner did the same build in 4 minutes 5 seconds. Compilation was unchanged. The tests dropped from 6 minutes 50 seconds to 2 minutes 10 seconds.

The fair comparison

That leaves a fair comparison: Gradle at 3 minutes 40 seconds against Maven at 4 minutes 5 seconds. The difference is 25 seconds, and most of it is incremental compilation, which a two-module build barely uses.

Against those 25 seconds sit the costs of moving:

  • A build file that is a program rather than a document. Anyone who reviews a change to it has to read it as code, and code can do anything.
  • Every other Sorrel team is on Maven. The company parent POM and the Nexus configuration, the company's own copy of the public library repository, are written for Maven.
  • A rewrite of the thing the team understands least, in a new lead's second week.

The condition for changing our minds

There is also a clear condition under which Sorrel should revisit the choice, and it is worth writing down.

The condition is a compile-bound build: one where compilation is most of the wall-clock time, across many modules that mostly do not change between runs. That is the shape Gradle was built for. It is not the shape of Payouts.

Remember it as: measure the stages before you change the tool; a slow build is usually slow tests, and the tool cannot fix a test.

Sam's decision

Sam wrote the decision on the whiteboard, under Rafael's slide:

  • Not now, and here are the numbers. Gradle would save 25 seconds on a 4-minute build, not 5 and a half minutes on a 9-minute one.
  • Parallel modules and forked, reused test JVMs go into the parent this week. That gets the build to about 4 minutes, for two settings and one flag.
  • The 2 minutes of tests that remain are chapter 6's problem, not a build tool's. That chapter asks whether the tests are worth the time they take.
  • Gradle is revisited when compilation is more than half of a build that takes more than 10 minutes. That sentence goes in the decision log, so nobody has to hold this meeting again from memory.

"You were right that the build was too slow," Sam told Rafael. "The numbers say it was the tests."

Rafael said he would hold Sam to the sentence about revisiting. Sam said that was the point of writing it down.

Hans Dockter began Gradle in late 2007. He had spent years with Ant, the scripting-style build tool Maven replaced, and with Maven itself. Each had a weakness he wanted to fix.

In a 2009 conference abstract he wrote that most Java projects used Ant or Maven, and that growing demands on project automation were "often very difficult to implement with Ant or Maven". Ant had no conventions, so every project's build looked different. Maven had conventions, but in 2013 he described it as having "a very inflexible model". What made Gradle matter was a decision made elsewhere. On 15 May 2013, at its Google I/O conference, Google announced Android Studio. It came with a new build system based on Gradle, replacing the Ant builds Android developers had used until then. From that point, nearly every new Android app was a Gradle build. That gave the tool more users than enterprise Java adoption alone could have.

Android builds have a particular shape. They are large, they have many modules, and most of those modules do not change between one run and the next. Incremental compilation and the build cache, the features Rafael's benchmark relied on, fit that shape exactly.

That history explains both halves of this chapter. Gradle is very good at the thing it was shaped for. And that thing was not what made Sorrel's build slow.

⚠The traps
  • The benchmark that changes two things: the sign is a before-and-after with a different tool and a different configuration. Whatever improves gets credited to the tool. Change one thing, measure, then change the other.
  • Serial tests by default: the sign is a Surefire configuration where nobody has set forkCount. One JVM runs one test class at a time, a container may start for each class, and the build tool is blamed for the test suite.
  • Parallel modules that depend on each other: the sign is -T on a build that gets no faster. Parallel module builds need independent modules, and a chain of three modules that each depend on the last is still a chain of three.
  • The cache that is not keyed: the sign is a CI cache of ~/.m2 keyed on the branch name. The cache then holds whatever the branch last downloaded, which may be the wrong libraries for this build. Key it on a hash of the POM files.
  • Moving the tool to fix the tests: the sign is a migration proposal whose savings come from the test stage. The tests will be as slow in the new tool as in the old one.
✎At the whiteboard
  1. What is the wall-clock time of compile, test and package, separately, on a warm runner?
  2. How many test JVMs run at once, and are they reused between test classes?
  3. What would have to be true of our build for the other tool's strengths to apply here?

Still argued: should a build file be a document or a program? Gradle's side, argued by Hans Dockter since the first release in 2008 and in Gradle's documentation since, is that real builds contain logic, and a programming language expresses logic better than XML with plugins. Maven's side, argued by the Apache Maven project since Maven 2.0 in 2005 and by many large companies' platform teams, is that a build written as a program can be anything, while a build written as a document has the same shape in every repository, which is what a company with 40 repositories needs most. Neither side has won. The Android world went one way and most enterprise Java went the other, for reasons that have more to do with the shape of their builds than with which tool is better.

Chapter 5 · Act IIThe Lombok Ban#

Sam's ninth day, and Sam's first wrong decision. A class with 11 annotations and no code inside leads Sam to ban the tool that writes the code, and the ban breaks 306 classes at once. This chapter explains what Lombok is, how it differs from an ordinary annotation processor, why Java records replace it for simple data classes, and why "stop adding it" was the right rule and "remove it" was not.

The problem

It was Sam's ninth morning at Sorrel, the insurer where Sam now leads the Payouts team. Sam had come from twelve years of leading .NET teams, and this was the first Java team. The week before had gone well. In chapter 4 Sam had cut the team's build from 9 minutes to 4, by running modules and tests in parallel, and the team was in a good mood.

The pull request under review changed one field's type in a class called Payout. A payout is one payment against one approved insurance claim. The diff was 2 lines. The file looked like this:

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
// ...and 7 more annotations
public class Payout {
    private String id;
    private Long version;
    private String claimId;
    private long amountMinor;
    // ...and 5 more fields
}

An annotation is the @Something above a class, field or method. It is the Java version of a C# attribute, such as [Required]. On its own an annotation does nothing. It is a label that some other piece of software reads and acts on.

The class had 11 annotations above its name and 9 fields below it, and nothing else. There was no constructor. There were no getters or setters. There was no equals method. Yet the rest of the code called payout.getClaimId() and Payout.builder() all the time, and it compiled. Sam could not tell from the file what the class could do.

"Lombok," said Rafael, the team's most senior developer, eight years at Sorrel and the author of most of the build. "It generates all of that at compile time. Every class in the repository uses it. It was there before me."

Lombok is a Java library that writes routine code for you while the compiler runs. @Data tells it to write getters, setters, equals, hashCode and toString. @Builder tells it to write a builder, a helper class for constructing an object one named field at a time. None of that code appears in the file.

Sam knew this argument from the .NET side. There, the same wish for less typing produced C# source generators, and the same objection: code you cannot read in the file is code you cannot review in the file. Twelve years of analyser rules had left Sam with a reflex, and the reflex fired.

By lunchtime Sam had posted a message in the team channel. Its first line named the parent POM, the shared Maven project file every module inherits its settings from, much like a Directory.Build.props file in .NET. Its last line named Aisha, the team's junior developer, two years in. The message read:

  • Lombok is removed from the parent POM.
  • New code does not use Lombok.
  • Existing classes are converted as people touch them.
  • Aisha will open the first pull request this afternoon.

Aisha did what she was asked. Her pull request, that afternoon, was 4,000 lines long.

The reason was simple to count, once someone counted. 306 classes used Lombok. Removing Lombok from the parent POM took it away from every module at once. So all 306 classes stopped compiling at once, and the change could not be done a piece at a time. Worse, the generated getters that nobody had read were called from every test, every mapper, and two other teams' client libraries.

Rafael said nothing in the channel. In the review he wrote one comment: "We could have just stopped adding it."

The idea

What happens when Lombok compiles a class

The Java compiler, javac, can run helper programs while it compiles. These are called annotation processors. An annotation processor is a plug-in that the compiler hands your annotated code to, so the plug-in can act on the annotations. You add one to the build in the POM, and from then on it runs every time the code compiles.

An ordinary annotation processor reads your annotations and writes new source files beside yours. For example, a mapping library can read @Mapper on an interface and write a new class, PayoutMapperImpl.java, that implements it. Your file is unchanged. The new file is real Java that you can open and read. This is close to how a C# source generator works: it can add new code, but it cannot change the code you wrote.

Lombok is an unusual annotation processor. It does not write a new file. While the compiler is working, it holds your class in memory as a syntax tree: a structure with one node for the class, one for each field, one for each method. Lombok reaches into that tree and adds new method nodes to your class before the compiler turns it into bytecode. So:

  1. Payout.java on disk has no getters.
  2. Payout.class, the compiled file, does have them.
  3. No source file anywhere contains them.

That is why the class works with no code in it. It is also why an IDE such as IntelliJ needs a Lombok plug-in to know the getters exist. Without the plug-in, the IDE reads the source file, finds no getClaimId(), and marks every call to it as an error.

There is a catch. The official rules for annotation processors allow them to add new files. They do not allow a processor to change a class that is being compiled. Lombok does it anyway, by using the compiler's internal classes. Those internals were never promised to anyone, and the JDK team can change them in any release. Lombok has worked since 2009, because its maintainers fix it every time the internals move. But each new Java release is a fresh chance for it to break.

What Sam was right about

The thing Sam had reacted to was real. When a class's behaviour is generated, you review it by trusting the generator. A reviewer cannot see what @Data wrote. They have to know what it writes. And when other teams call getClaimId(), a method that exists only because of an annotation, the generator has quietly become part of the code those teams depend on.

What Sam got wrong: the shape of the remedy

There are three ways out of a dependency on generated code, and their costs are very different.

  • Remove it. Take Lombok out of the build. Because the processor is configured once in the parent POM, removing it affects every module and every class on the same day. Every caller of every generated method must change in the same pull request. That is the 4,000 lines.
  • Stop adding it. Leave Lombok in the build, and write no new class with it. This costs nothing today. The problem shrinks each time someone rewrites a class for another reason.
  • Replace it where it fits. For classes that are only data, Java now has its own answer: records.

Records: the language does it

A record is a kind of Java class, final since Java 16, that is declared by listing its fields. Here is the companion project's Payout, shortened:

@Document("payouts")
public record Payout(
        @Id String id,
        @Version Long version,
        String claimId,
        long amountMinor,
        PayoutStatus status,
        Instant createdAt) {
}

From that one declaration the compiler writes a constructor, one accessor per field, equals, hashCode and toString. (The @Document, @Id and @Version annotations here are Spring Data's, for storing the record in the database. They generate nothing.) The fields cannot be changed after construction. There is no processor, no IDE plug-in and no reach into the compiler. If you know C# 9 records, this is the same idea.

One difference matters for a migration. A record's accessor is named after the field, with no get: payout.claimId(), not payout.getClaimId(). So turning a Lombok class into a record changes the name of every getter, and every caller has to change too. That is one more reason to convert a class only when you are already changing its callers.

Records fit some classes and not others:

  • Values fit. A Payout document is a value: some data, compared by its contents. A record is the better Payout.
  • Builder-heavy, changeable classes do not. A service class with mutable state, many optional fields, or a long builder is not a value. Forcing it into a record produces a record with a dozen components and a hand-written builder beside it, which is worse than what you started with.

What Sam got wrong: the order

The second mistake was about timing. A lead's first weeks are for finding out what is true. Sam issued a rule on day 9, by analogy with another platform, before counting the classes it would touch. The cost was concrete:

  • a week of noise in the team
  • a 4,000-line pull request, closed without merging
  • a message in the channel that Rafael had been too polite to answer.

What about Kotlin?

Aisha asked, the same week, whether Kotlin would have avoided all this. Kotlin is another language that runs on the Java runtime, and its data classes do what records do and more. Kotlin does work with Maven, through its own compiler plug-in. But almost nobody does it that way. Kotlin's tools, documentation and examples assume Gradle, the build tool the team had decided not to adopt in chapter 4 after measuring that the slow part of its build was tests, not the tool. A Kotlin module on a Maven team means a second language and a second compiler in the build, pulling the team towards Gradle. So the answer was "not now", for the same reason as Gradle. The reason is the pull of the ecosystem, not the merit of the language.

Remember it as: stop adding before you start removing, and never issue a rule before you have counted what it touches.

Sam's decision

Sam posted the decision in the channel, directly under the original message, and left both there:

  • The ban is withdrawn. Lombok stays in the parent POM. Removing it breaks all 306 classes at once.
  • New classes do not use Lombok. This stops the problem growing, and it costs nothing.
  • Documents and values become records when someone touches them for another reason. There is no migration ticket and no deadline, so nobody has to change 4,000 lines in one go.
  • Aisha's pull request is closed with thanks. The 3 classes in it that were already records are merged.

The message ended with the sentence Sam had wanted to avoid writing: "I should have counted first."

Rafael replied with a thumbs up. On this team that meant a great deal.

In 2009 two developers, Reinier Zwitserloot and Roel Spilker, were sharing a flat in Delft, in the Netherlands. There they built a tool that would write getters and setters for them.

On 28 July 2009 Zwitserloot announced the tool on an OpenJDK mailing list where people were proposing small changes to the Java language. He attached a screencast less than 4 minutes long. The trick was the one described above. Lombok registered as an annotation processor, which the compiler allows. Then, from inside, it changed the compiler's syntax tree, which the rules do not allow. People who build Java tools noticed. In January 2012 Markus Keller, a developer on the Eclipse IDE's compiler, put the objection plainly: Lombok "creates an incompatible dialect of the Java language and it modifies the IDE and the compiler in unsupported ways."

Lombok's answer was that it worked. For years it mostly did.

The bill came in December 2020. JDK 16 locked down the JDK's internal classes, including the compiler's, so that outside code could no longer reach into them. Lombok stopped working with an access error as soon as the compiler started. Teams trying the early test builds of JDK 16 had to wait until April 2021 for a Lombok release that found a new way in.

The same JDK 16, released in March 2021, made records a final part of the language. Their designers wanted a class that is only its data to be something the language does, not something a tool does. Sorrel's 306 Lombok classes were written on both sides of that change. That is why the right answer was to draw a line at today, and not to drag all of them across it at once.

⚠The traps
  • The all-or-nothing processor: the sign is an annotation processor configured in the parent POM that every class uses. Removing it from the parent breaks every module on the same day, so the migration cannot be done in pieces from the top. Stop adding it instead, and convert classes one at a time.
  • The rule by analogy: the sign is a new lead's first rule arriving before anyone has checked how much code it reaches. The remedy from another platform may not fit this one, and a team that sees one hasty rule learns to wait out the next.
  • A record where a builder was: the sign is a record with 12 components and a hand-written builder beside it. Records fit values. A class with many optional fields, or fields that change, may not be a value.
  • Generated code in the public surface: the sign is another team calling a getter that exists only because of an annotation. The generator is now part of your API, and so is the IDE plug-in their developers need to see it.
  • A second language for one module: the sign is a Kotlin module in a Maven build because one developer prefers Kotlin. That means two compilers and two skill sets in one team, and a pull towards a second build tool.
✎At the whiteboard
  1. How many classes would this rule touch, and can it be applied one class at a time?
  2. Which of these classes are values, and would a record replace their annotations outright?
  3. What in this module's public methods exists only because a tool generated it?

Still argued: does Lombok belong in a modern Java codebase at all? Its maintainers and its many users say yes. Routine code is a cost paid every day, records only cover data classes, and a tool that removes the rest earns its place. The designers of the Java language, in Brian Goetz's writing on records from 2019 onwards, say the language should absorb the common cases. A tool that edits the compiler's syntax tree is a risk that every new JDK release renews. Both are right about the cases they describe. The line most teams draw is the one Sorrel drew: records for values, no new Lombok, no forced removal.

  • A record is the language's own answer for data classes, while Lombok edits the compiler and has to be fixed again for each new JDK.
  • Reverse a wrong decision in the place it was made, in plain words, and say the part you would rather not.

The problem

The meeting was in the team room, a few days after the Lombok decision. Sam, the new lead from .NET, had asked for it because Aisha, the team's junior developer, two years in, had asked a question nobody could answer.

On the wall screen was the team dashboard. One number on it was 84%, in green. That was the team's test coverage, the same line-coverage figure a .NET team gets from Coverlet.

Rafael, the team's most senior developer, eight years at Sorrel, was proud of it, and he had reason to be: he had kept that number up for a long time. "We've held that line for three years," he said. "Every service over 80. And the platform team's gate won't merge anything below 75."

The gate is a check run on every pull request by Oren, who runs the platform team that looks after the shared Kubernetes cluster and the build servers. If coverage drops below 75%, the pull request cannot be merged. Oren wants a number he can enforce across 40 services without reading their tests.

Aisha put a test on the screen. It was called PayoutServiceTest and it was 40 lines long. Its core looked like this:

@Mock PayoutRepository repository;
@Mock PayoutService service;

@Test
void createPayoutReturnsPayout() {
    Payout payout = new Payout("p-1", 0L, "key-1", "claim-1", 12_50, PENDING, EPOCH);
    when(service.createPayout("claim-1", 12_50, "key-1")).thenReturn(payout);

    Payout result = service.createPayout("claim-1", 12_50, "key-1");

    assertEquals(payout, result);
}

A mock is a fake object that stands in for a real one during a test. You tell it what to return, and it returns that. Mockito is the Java library that makes mocks, much as Moq does in .NET. @Mock creates one. when(...).thenReturn(...) tells it what to answer. @Test marks a test method, like xUnit's [Fact], and comes from JUnit, Java's standard test framework.

Read the test step by step. It makes a fake repository and a fake PayoutService. It tells the fake service to return this payout when someone calls createPayout. Then it calls createPayout on the fake service, and checks that the answer is the payout it had just told the fake to return.

The real PayoutService never runs. The test had passed every day for three years, and it could not fail. It was not testing the service. It was testing Mockito.

"That one's old," Rafael said. "There are better ones."

There were. There were also 61 more like it, and Aisha had counted them. The pattern had a name on the team, "the template", and new tests were written by copying it. The coverage tool counted every line the mocks walked through.

Then Aisha showed the bug from the previous month. A payout had been marked paid without its version number going up. (Each payout carries a version field. The database checks it on every save, so that two writers cannot silently overwrite each other, like a row version in Entity Framework.) That bug had taken a day to find. Three green tests covered the code where it lived. All three mocked the very thing that was wrong.

Sam had seen this in .NET, where people called it the Moq tax. Sam had not known it could reach 84%.

"What does the number measure?" Aisha asked again. This time she was asking Rafael.

The idea

A test is a claim that can be false

A test is a claim about behaviour that could turn out to be false. That is the whole definition, and it is the one the template fails. A test that mocks the thing it is testing only claims that the mock library works. The mock library does work, so the test passes forever.

The coverage tool cannot tell the difference. It counts lines that executed, and the lines did execute. It does not look at what the test checked afterwards.

Coverage is still useful as a floor. A line with 0% coverage has certainly not been tested. But a line with 100% coverage may not have been tested either.

What to mock: the boundary

So what should be mocked? The boundary of the unit: the things it cannot run without, and cannot run truthfully inside a test. For PayoutService there are two:

  • The ledger. This is another team's service, across the network, owned by Bea, who runs the ledger team. A test cannot call it for real, and should not.
  • The bank gateway. A test must never send real money.

Two things are not boundaries:

  • The repository. PayoutRepository is a Spring Data interface over the database. (Spring Data writes the class behind the interface for you, from method names such as findByIdempotencyKey.) In chapter 7 the team runs it against a real database in a container that starts in about 2 seconds.
  • The service itself. It is the thing under test. Mocking it means testing nothing.

There is one honest exception. A test of the service's own decisions may replace the repository with a stub, if a different test runs the real query against a real database. The companion project's PayoutServiceTest does exactly that. What is never acceptable is a mocked repository in a test that claims to check a query, because then the query never runs.

How Mockito's strict mode helps

Mockito can catch part of the problem itself. Its strict stubs mode fails a test that sets up an answer (a stub) the test never uses. In JUnit 5 you turn Mockito on for a test class with @ExtendWith(MockitoExtension.class), and that extension has always used strict stubs by default.

The template's first symptom is exactly this: it stubs the repository, and nothing ever calls the repository, because the real service never runs. Strict stubs would fail it. That is why the companion project's copy of the template carries @MockitoSettings(strictness = Strictness.LENIENT), which switches the check off.

Note the difference from Moq. Moq's MockBehavior.Strict fails when code calls something you did not set up. Mockito's strict stubs fail when you set up something nobody called.

Strict stubs cannot catch a test with no real object in it at all. That is the reviewer's job: find the one real thing the test exercises.

Slice tests: the middle layer

Spring Boot adds a middle layer of testing that the team had skipped entirely. To see why it matters, you need two words.

  • The application context is Spring's container of all the objects the application is built from, wired together. Each such object is a bean. Starting the context means creating and wiring every bean. It is the equivalent of building the ASP.NET Core host with its whole service collection.
  • @SpringBootTest starts the full context for a test: every controller, service, repository and connection. It is the Java cousin of WebApplicationFactory in ASP.NET Core. At Sorrel it took about 20 seconds to start.

A slice test starts only one layer of the application. Two slices matter here:

  • @WebMvcTest starts only the web layer: the controller, request mapping, validation and JSON error handling, on a real HTTP stack. The service below the controller is replaced. It is the right test for "does this endpoint return 400 for a bad amount?"
  • @DataMongoTest starts only the MongoDB repositories, against a real database. It is the right test for "does this query find the right payouts?"

Slices start in a second or two. A full @SpringBootTest is the right test for the whole service working together. It is the wrong test for one controller's status code, because it pays 20 seconds of start-up for a check a slice does in 1. The team had been paying those 20 seconds in 60 places.

When a slice or full test needs a bean replaced by a mock, the current annotation is @MockitoBean. The template used the older @MockBean, which Spring Boot 3.4 deprecated. Spring Boot 4 removes it, so the Boot 4 upgrade from chapter 3 will remove it anyway.

The shape of a healthy suite

Put together, the usual shape is:

  1. Many unit tests with real domain objects, mocks only at the boundary.
  2. A handful of slice tests per service, for controllers and repositories.
  3. One or two full-context tests per service, to prove it starts and hangs together.

The team had this upside down. In chapter 4 they had run tests in parallel and brought the test stage down from 6 minutes 50 seconds to 2 minutes 10 seconds. Most of what remained was those 60 full contexts starting.

Remember it as: coverage counts what ran, not what was checked; a test that cannot fail is a line on a dashboard, not a test.

Sam's decision

When Aisha had finished, Sam gave the team the decision:

  • The template is deleted, with its 61 copies. They protect nothing.
  • Coverage is allowed to fall. Sam reports the new number honestly to the platform team, with the reason.
  • Rafael writes the replacement guidance. The next template will be copied too, so it should be written by the person the team trusts most.
  • Every new test names its one real object. If there is none, it is not merged.
  • Slices for controllers and repositories, one full-context test per service. That is the cheapest test for each question.
  • Mocks at the boundary: the ledger and the bank. The repository is real wherever the test is about data.
  • Aisha pairs with whoever writes the first 10 new tests. She found the problem, and she knows what a real test looks like.

"Probably," Sam said. "The gate measures the wrong thing. That's a conversation with Oren, not a reason to keep 61 tests that cannot fail."

In October 1997 Kent Beck and Erich Gamma were on a flight from Zurich to Atlanta, on their way to the OOPSLA programming conference. They spent the flight writing a test framework for Java, in pairs and test-first.

Beck had written a similar framework a few years earlier for Smalltalk, called SUnit. Gamma, one of the four authors of the book Design Patterns, wanted the same thing in Java, the language he was now using. By the time they landed they had JUnit. It had three parts:

  • a way to write a method that checks something
  • a runner that runs every such method and reports the ones that fail
  • a green bar when nothing fails.

It spread because it was small enough to understand on a flight. And its shape made a claim: a test is a method that can fail.

Mocking came later. By 2007 the common Java mock tool was EasyMock. A test using it had to record every call it expected, switch to replay mode, then verify. A test read like a script of everything the code would do.

In November 2007 Szczepan Faber was on a ThoughtWorks team in London, building the Guardian newspaper's new website. He started Mockito as a fork of EasyMock's code. It soon changed so much, in the project's own words, that it "evolved too much" to share any code with EasyMock. Its shape was the opposite. There was no record and replay. You stub what you need, run the real code, then check only what matters. Guardian developers were the first to use it in production, in early 2008.

The idea behind it is the idea of this chapter. A mock stands in for something you cannot run. It is not a replacement for the thing you are testing.

⚠The traps
  • The mocked subject: the sign is mock(PayoutService.class), or @Mock PayoutService, inside PayoutServiceTest. The test exercises Mockito and the service never runs, so it can never fail. Make the subject real and mock only what it calls across the boundary.
  • Coverage as the gate: the sign is a merge gate on a percentage with no review of what the tests check. Lines run through mocks count the same as lines checked, so the gate rewards the template. Review assertions, and treat coverage as a floor.
  • The full context for a status code: the sign is @SpringBootTest on a test of one controller. Each one waits for a whole application to start, when @WebMvcTest would answer the same question in about a second.
  • Lenient by habit: the sign is @MockitoSettings(strictness = LENIENT) on every test class. Strict stubs catch the stub nobody calls, and lenient mode hides it. Use lenient only on the one test that needs it, with a comment.
  • Mocking the repository: the sign is a mocked PayoutRepository in a test that claims to check a query. The query never runs. Test queries with @DataMongoTest against a real database, as chapter 7 does.
✎At the whiteboard
  1. In this test, which object is real, and could the assertion ever be false?
  2. What is the boundary of this unit, and is anything inside the boundary mocked?
  3. How many full-context tests does this service have, and what does each one check that a slice could not?

Still argued: how much should a test mock? The classicist view, set out by Martin Fowler in "Mocks Aren't Stubs" in 2004, uses real objects wherever they can run and fakes only awkward boundaries, so the test checks behaviour. The mockist view, from Steve Freeman and Nat Pryce's Growing Object-Oriented Software, Guided by Tests in 2009, mocks each neighbour of a class in turn, so the test pins down exactly how the class talks to them. Both produce good tests in practised hands. The template was neither, because it mocked the thing under test, which no school defends. Sorrel went classicist, because a team recovering from the template needs real objects it can see.

What Sam learned

  • Before reading a test's assertion, ask which object in it is real; if none is, nothing in it can be false.
  • Mock the boundary, such as the other team's system and the bank, and never the subject or the repository in a test of a query.
  • Treat coverage as a floor, never a target, because a gate on the percentage rewards exactly the template.

The idea

Amazon DocumentDB is not MongoDB

Amazon DocumentDB is a different database from MongoDB, built by Amazon, with its own storage engine. It emulates the MongoDB API. That means:

  1. It accepts the same wire protocol as MongoDB.
  2. For each operation it supports, it answers the way a MongoDB server would.
  3. For each operation it does not support, it returns an error.

The MongoDB driver cannot tell the difference. Neither can Spring Data MongoDB, the Spring library that sits on top of the driver and turns repository interfaces into queries. The only way to know the difference is to read Amazon's published lists of what is and is not supported. At Sorrel, the person who had read them left in 2021. The comment was all they left behind.

A .NET developer has seen this trap before: running Entity Framework tests against SQLite in memory when production runs SQL Server. The code is the same, the provider looks the same, and some queries behave differently.

What a retryable write is

A retryable write is a safety feature of the MongoDB driver. If a write fails because of a network error, the driver automatically sends it again, once, without your code having to do anything. It is a little like turning on EnableRetryOnFailure for SQL Server in Entity Framework, except that the MongoDB driver does it by default.

To make the retry safe, the driver attaches extra session information to every write, so the server can recognise a repeat and not apply it twice. A database that does not support that feature rejects the write. It rejects every write, not just the retried ones, because the extra information is on all of them. That is why Sorrel's service could read but not write.

retryWrites=false in the connection string turns the feature off. The driver then sends plain writes, which DocumentDB accepts.

How DocumentDB versions work

Amazon calls them engine versions, and they are one numbering scheme: the first two numbers name the MongoDB API the engine emulates, and the last is a minor release of that engine. So engine version 5.0.2 is a minor release of DocumentDB 5.0, which emulates the MongoDB 5.0 API. The major engine versions are 3.6, 4.0, 5.0 and 8.0. They are not MongoDB itself, and there was never a 6 or a 7.

Amazon's documentation says retryable writes are supported starting with engine version 8.0.2. On every earlier engine version they are not supported, and you must turn them off to avoid errors. Modern MongoDB drivers turn them on by default.

In 2024 a routine rebuild recreated Sorrel's cluster from a script that named no engine version, so Amazon gave it the default, 5.0. The 2021 comment predated the rebuild and still applied, because 5.0 refuses retryable writes too.

The shape of the gap

Three MongoDB words first. An aggregation pipeline is MongoDB's way of running a multi-step query, a little like a LINQ chain of Where, GroupBy and Select. Each step is a stage, such as $match or $group. An operator is one of the $-words inside a query, such as $regex.

Amazon's list of differences is long, and it changes with each engine version. Amazon publishes which operators and stages are supported and unsupported, version by version. The list has three kinds of entry, and each kind fails differently.

  1. Missing on your version, present on a later one. Retryable writes are one. Others: the $merge stage and collation (language-aware string comparison) exist only from 8.0. The $facet stage needs 8.0.2.
  2. Missing on every version. For example the $unionWith stage, hashed indexes and wildcard indexes.
  3. Present but different. Change streams (a feed of every change to a collection) are switched off by default and must be enabled per collection. Query plans differ. Results come back in no guaranteed order unless you sort.

None of this is hidden. It is all in Amazon's documentation. The failure at Sorrel was that nobody was reading that documentation against the code.

What Testcontainers proves, and what it cannot

Testcontainers is a Java library that starts a real database in Docker for the length of a test, then removes it. It is exactly what the team had asked for in chapter 6: a real database, not a mock. The repository test is a @DataMongoTest, a slice test in chapter 6's sense: it starts only the MongoDB part of Spring, not the whole application. It starts a mongo:7 container, the official MongoDB 7 image.

The trouble is that there is no DocumentDB container. DocumentDB is a managed service that runs only inside a private network in Amazon's cloud. Amazon's documentation offers no edition you can run on a laptop or in Docker. So the real database in the test is MongoDB, and the real database in production is an imitation of MongoDB.

The test proves the query runs on MongoDB. Whether it runs on DocumentDB is a second question, and the test cannot ask it.

The answer: a feature contract

There were two tempting wrong answers.

  • Stop using Testcontainers. No. It is the best testing tool the team has, and it catches most bugs.
  • Give every pull request a real DocumentDB to test against. Oren can provide one shared DocumentDB instance for a nightly run, but not one per pull request.

The answer is a feature contract: a short document, owned by one named person, that lists every MongoDB feature the code uses. Each line says whether DocumentDB supports the feature on the version Sorrel runs, and the date someone checked. It covers:

  • every query operator
  • every aggregation stage
  • every index type
  • every driver option.

The pull request that starts using a new feature adds a line to the contract. The reviewer checks the line against Amazon's list.

The test suite also gets one more test. It reads the production connection string and fails if retryWrites is not false. The next person who tidies the configuration meets the old comment as a red build, not as a Friday evening outage.

Remember it as: the test ran against a real database; production runs an emulation of it, and the gap is a list someone must own.

Chapter 8 · Act IIOne Document, Two Writers#

A customer was paid twice for one claim, because two copies of the service each checked for a payment, found none and made one. This chapter explains why "check, then write" is never safe when two copies run at once, how a unique index and a version field let the database refuse the second write, and when a transaction is worth its cost.

The problem

Claim 4471 was paid at 09:12:07 by one pod and at 09:12:11 by the other. A pod is one running copy of a service on Kubernetes, and payouts-api runs as 2 pods so that one can fail without the service going down. The bank gateway, the supplier's system that moves the money, does what it is told. It sent two payments. The customer, who was honest, rang up.

Rafael, the team's senior developer, eight years at Sorrel and the author of most of the build, had the sequence on the whiteboard by ten. He likes problems solved properly, once.

The claim had arrived from the policy system as a message on a queue. Pod A picked it up but did not confirm it in time, so the queue delivered it again, and pod B received the second copy. This is redelivery: a message that is not confirmed is assumed lost and sent again, as with any message queue. Each pod then asked the database whether a payout already existed for claim 4471, and each found none. Each created a payout, saved it and called the bank.

On each pod, the check and the save were 4 seconds apart. The two 4-second windows overlapped. Inside that overlap, neither pod could see what the other was doing.

"We need a transaction," Rafael said. "Check and insert, atomically. DocumentDB does transactions now. We should have used them from the start."

DocumentDB is Amazon's managed database that speaks the MongoDB protocol, and it is where Sorrel keeps its payouts. Rafael meant a transaction in the SQL Server sense: the check and the insert as one step, with nothing in between.

Aisha, the team's junior developer, two years in, had a different diagram. She reads the code before she reads the theory. On her diagram the payout record had a field called idempotencyKey, which held the claim number. Next to it she had written one question: why isn't this unique?

Sam, the team's new lead after twelve years of .NET, had met the same bug there, with a message queue and SQL Server, and had learned that the cheapest fix is often already in the database. "Before we add a transaction," Sam said, "what does the database already know how to refuse?"

"A duplicate key," Aisha said. "If we let it."

Rafael wants a transaction because it is the general tool, the one that makes any sequence of steps safe. Aisha wants a unique index because it is the smallest tool that makes this one step safe. Rafael said a unique index was not a design. Aisha said a transaction around a race was a lock around a bug. Both were partly right, and Sam asked them to draw the second write.

The idea

One payout, one document

Here is the payout as the code stores it, from the companion project:

@Document("payouts")
public record Payout(
        @Id String id,
        @Version Long version,
        @Indexed(unique = true) String idempotencyKey,
        String claimId,
        long amountMinor,
        PayoutStatus status,
        Instant createdAt) {
}

A document database such as DocumentDB or MongoDB stores each record as one document: a JSON-like object with all its fields together. Here one payout is one document, holding the claim, the amount, the status and the rest. It is written and read as a unit. @Document("payouts") tells Spring Data MongoDB, the library that maps Java objects to documents, to keep these in a collection called payouts. A collection is the document-database equivalent of a table.

This shape matters for concurrency. Most of what must stay consistent about a payout is inside one document. And a write to a single document is atomic without anyone asking. If two writes hit the same document at the same moment, the database applies one and then the other, never half of each.

The race: check, then write

What is not atomic is a check followed by a write. That is what both pods did:

if (repository.findByIdempotencyKey(key).isEmpty()) {
    repository.insert(Payout.pending(claimId, amount, key, now));
    bank.pay(...);
}

Each line on its own is safe. The gap between the first and second line is not. Pod A checks and finds nothing. Pod B checks and finds nothing. Then both insert. This is called a race: the result depends on which pod gets there first, and here both "won".

Let the write refuse

The fix is not to make the check-and-write atomic. It is to make the second write fail.

An idempotency key is a value that identifies one real-world request, so that repeating the request has no extra effect. Here it is the claim number: one claim, one payout. A unique index on that field tells the database to reject any second document with the same value. With the index in place:

  1. Pod A inserts the payout for claim 4471. The database accepts it.
  2. Pod B inserts a payout for claim 4471. The database refuses it with a duplicate-key error.
  3. Spring turns that error into a DuplicateKeyException. The service catches it, reads the payout pod A wrote, and returns that one. Pod B never calls the bank.

The check stays in the code, because it is a cheap way to answer the common case. But the index is what decides. A redelivered message now ends with pod B returning the payout pod A made.

The .NET version of this is familiar. In Entity Framework Core you would write HasIndex(p => p.IdempotencyKey).IsUnique(), and the second insert would throw a DbUpdateException wrapping SQL Server's duplicate-key error. The idea is identical. Only the names change.

The annotation that did nothing

The Payouts code already had @Indexed(unique = true) on the field. So why did both inserts succeed?

Because the index had never been built. Spring Data MongoDB used to create indexes from annotations when the application started. In its version 3.0 it stopped doing that by default. The behaviour is now behind a property, spring.data.mongodb.auto-index-creation, which is off unless you turn it on. Nobody had turned it on. So for four years the annotation had been a comment: it described an index that did not exist.

An annotation is a request to some piece of code. Whether anything acts on it depends on configuration you cannot see in the annotation.

The second race: two updates to one payout

The next race had not happened yet, but it would have. It involves two updates to the same existing payout.

Suppose one request marks payout 88 as paid, and at the same moment another cancels it. Each one does three things:

  1. Read the document.
  2. Change one field in memory.
  3. Save the whole document back.

The last save wins. The first update is lost, and nothing reports it. This is called a lost update.

The fix is optimistic locking. You add a version number to the document. That is the @Version Long version field above. Spring Data does two things with it:

  • On every save, it adds 1 to the version.
  • On every save, it tells the database: write this only if the stored version is still the one I read.

So if two writers both read version 3, the first save succeeds and the document becomes version 4. The second save says "only if version is 3", finds 4, and fails with an OptimisticLockingFailureException. The service can then read the document again and retry, or report a conflict. What it can no longer do is lose an update silently.

It is called optimistic because nothing is locked while you work. You assume nobody else will write, and the database checks that assumption at the last moment. In Entity Framework the same idea is a [ConcurrencyCheck] attribute or a rowversion column, and the failure is a DbUpdateConcurrencyException.

The team had seen this mechanism half-installed already. In chapter 6, a payout had been marked paid without its version going up, and three green tests had missed it because they mocked the repository. A version field only protects you if every update goes through it.

What a transaction is for

Rafael's transaction deserves a fair answer. DocumentDB does support multi-document transactions: several reads and writes, across several documents, that all succeed or all fail together. They arrived with its 4.0 compatibility version, and Sorrel runs 5.0, so they are available.

They also have costs and limits. Amazon publishes them:

  • Each transaction must finish within 1 minute, or it is aborted.
  • Each database instance has a cap on how many transactions can be open at once.
  • A transaction that conflicts with another must be retried by the application.

On top of that, a transaction costs extra round trips to the database and holds resources while it is open. For the double payment, all that cost buys nothing a unique index does not already give for free. The index refuses the duplicate in one write. The transaction would still need a retry on conflict, and the idempotency key is exactly what makes that retry unnecessary.

So the rule is:

  • One document, one write: no transaction. The write is already atomic. Use a unique index or a version to make it refuse.
  • Two documents that must agree: a transaction. Use it rarely, and list it in the feature contract.

The feature contract is the document the team started in chapter 7, after a test passed on MongoDB and the same code failed on DocumentDB. It lists every database feature the code relies on, each checked against what Sorrel's DocumentDB version supports.

What is left: the bank

One problem remains. The payout document and the instruction to the bank are two writes to two different systems. No database transaction can cover both, and once the bank has sent money, nothing in Payouts can take it back.

The usual answer is the transactional outbox. The service writes the bank instruction into the database, in the same write as the payout. A separate process then reads those instructions and delivers them to the bank. Chapter 11 is where Sorrel meets it.

Remember it as: let the database refuse the duplicate and the stale write; a transaction is for two documents that must agree, not for a race.

Sam's decision

Sam drew the decision between the two diagrams:

  • A unique index on idempotencyKey, created explicitly when the service starts. An annotation nobody checks is how the last four years happened.
  • The nightly run against the shared DocumentDB instance checks that the index exists. MongoDB in a test container is not the database Sorrel runs.
  • @Version on every document that is updated after it is created. Without it, two updates to one payout lose one silently.
  • A version failure is treated as a retry, not an error. It means someone else wrote first, which is normal with 2 pods.
  • The duplicate-key path is tested against a real index, not a mock. A mock cannot refuse anything.
  • Transactions only where two documents must change together. Today that is nowhere, and the feature contract says so.

"The database is better at saying no than our code is," Sam told the team. "Let it say no, and make the code ready to hear it."

Aisha asked whether the bank call was now safe. No, Sam said. It was now safe to retry, which was different. The rest was chapter 11's problem, and the phone number of Bea, who owns the ledger service on another team.

In 2007 three people who had built DoubleClick, the online advertising company, set up a new company in New York. They were Dwight Merriman, Eliot Horowitz and Kevin Ryan, and the company was called 10gen. They meant to build a cloud platform from open-source parts. Nothing they could buy fitted as its data layer, so they wrote a document store.

The platform failed. The data layer did not. They open-sourced it as MongoDB in February 2009 and shipped version 1.0 that August. It spread because of one property. A developer could store the object from their program as a document and get it back, with no schema and no mapping layer in between.

Another property came with it, and it is the one this chapter is about. The early server said a write had succeeded before the data reached disk. And by default, the driver in the application did not even wait for that answer.

The argument came to a head on 6 November 2011. An anonymous post titled "Don't use MongoDB" reached the top of Hacker News. It claimed the database "issues writes in unsafe ways by default in order to win benchmarks". Horowitz, by then the chief technology officer, answered in the thread the same day, under his own account. He wrote that the default had "absolutely nothing to do with benchmarks". He said he could find no customer with the record the post described. And he conceded that the global lock "is definitely an issue, but a lot of progress made and more to come".

By then the fixes had started. Journaling, which writes changes to a log on disk before applying them, arrived in March 2011 and became the default that September. In November 2012 the drivers changed too. A new MongoClient class appeared, and its default was to wait for every write to be acknowledged.

The durability a developer takes for granted in 2026 was argued into the product one default at a time.

⚠The traps
  • The annotation that creates nothing: the sign is @Indexed(unique = true) on a field, and no such index in the collection. Spring Data MongoDB has not created annotated indexes by default since version 3.0. Create the index explicitly at startup, or turn on spring.data.mongodb.auto-index-creation and check the result.
  • Check-then-insert: the sign is a findBy... followed by a save or insert in the same method, with nothing to stop a second caller in between. Two pods both find nothing and both insert. Put a unique index on the key and let the second write fail.
  • The version nobody bumps: the sign is a document that is updated by saving the whole thing back, with no @Version field. When two updates overlap, the last one wins and the first is lost without any error.
  • A transaction around a race: the sign is a multi-document transaction wrapped around a single-document insert. You pay for extra round trips and retries to solve a problem a unique index solves in one write.
  • Two systems, one hope: the sign is a database write followed directly by a call to the bank, with no outbox. If the service fails between the two, they disagree. The database can be made to refuse a duplicate, but the bank cannot be made to forget a payment.
✎At the whiteboard
  1. For this write, what makes a second identical request harmless, and is that enforced by the database or by a check in our code?
  2. Which documents are updated after they are created, and does every one of them carry a @Version field?
  3. Where in this service must two documents, or a document and another system, agree, and what guarantees it?

Still argued: should a document database offer multi-document transactions at all? From its founding until 2018, MongoDB said no. Horowitz argued in the 2011 thread, and the documentation of the time agreed, that keeping related data in one document makes most transactions unnecessary. A design that needs many of them is a relational design in disguise. The other view won inside MongoDB with version 4.0 in 2018, and Amazon followed with DocumentDB's 4.0 compatibility. Some rules span several documents, and a database that cannot protect them pushes the problem onto every application. Sorrel's rule keeps both views: design around the single document, and keep transactions for the rare rule that spans several.

What Sam learned

  • A check in code cannot stop two pods; a unique index can, because the database enforces it.
  • Every document that is updated after creation carries a version, and a version failure is a signal to retry.
  • Match the tool to the problem: the index for a race, a transaction for a multi-document rule, the outbox for a second system.

Chapter 9 · Act IIThe Jar in the Audit#

Security's scanner found a critical vulnerability in a library nobody on the team had heard of, and it was in the team's own image. This chapter explains why a Maven build ships far more libraries than its POM names, how Maven picks one version when two parts of the build ask for different ones, and how a lead sorts 41 findings into the few that matter.

The problem

The email came from security, with a spreadsheet attached and a deadline in the subject line.

Oren, who runs the platform team, had set it in motion. His team looks after the shared Kubernetes cluster, the image registry where container images are stored, and the artifact repository the builds download libraries from. It had installed a new scanner. It had opened every container image on the cluster and listed every library inside each one. Then it had checked each library against the public database of known vulnerabilities.

Each finding was a CVE, a known vulnerability with a public ID such as CVE-2022-42889 and a severity score from 0 to 10. The Payouts rows had 41 findings. 3 of them were rated critical. And one of the critical ones was in a library that Rafael, the team's senior developer, had never heard of.

Rafael has been at Sorrel for eight years and wrote the parent POM, the shared build file that every Payouts module inherits its settings from. If anyone knew what the build used, it was Rafael.

"We don't use that," he said. "It's not in any POM. Look." He searched the repository. The name was not in it.

"It's in the image," Oren said. "The scanner doesn't read POMs. It reads jars."

A jar is the file a Java library is shipped in: a zip of compiled classes, like a .dll inside a NuGet package. A Spring Boot service is packaged as one large jar with every library jar it needs inside it, and that goes into the container image. The scanner was not reading what the team had written down. It was reading what the team had shipped.

Sam, the team's new lead, had done this in twelve years of .NET, with a package graph that a tool could draw. The answer had always had the same shape: the library you have never heard of is a few steps below one you have.

Aisha, the team's junior developer, two years in, ran Maven's dependency tree for the reports module. The reports module is the one that had still been compiling for Java 11 in chapter 1, after a forgotten override in its POM. The tree showed every library the module pulls in, and what pulls in what. There it was, two levels down. The module used a configuration library, Apache commons-configuration2. That library used a text-handling library, commons-text, at version 1.9, from 2020. A critical finding had been published against that version in 2022.

"So it's transitive," Rafael said. "It's not our code."

A transitive dependency is one you did not ask for. A library you asked for asked for it. Rafael's point was fair: nobody on the team had chosen commons-text, and nobody had written a line that called it.

"It's in our image," Sam said. "With our name on it. And security is going to ask the question I'm about to ask. How long has it been there, and why did nobody know?"

Rafael did not have the answer. Nobody did, because nobody had ever asked the build to list what it shipped. Rafael wanted the finding filed under someone else's code. Sam wanted the team to own everything in its image, whoever had chosen it.

The idea

The tree, not the list

Here is the dependency tree for a cut-down copy of the reports module, from the companion project. The command is ./mvnw dependency:tree. That form, plugin:goal, runs one goal (one task) of a Maven plugin: here the tree goal of Maven's dependency plugin. This is its output:

com.sorrel:payouts-reports:jar:0.1.0-SNAPSHOT
+- org.apache.commons:commons-configuration2:jar:2.8.0:compile
|  +- org.apache.commons:commons-text:jar:1.9:compile
|  \- commons-logging:commons-logging:jar:1.2:compile
+- org.apache.commons:commons-lang3:jar:3.9:compile
\- com.sorrel:ledger-client:jar:1.0-SNAPSHOT:compile

Each line names a library by its Maven coordinates: group, name, packaging, version and scope. The indentation shows who brought it in. The POM names 3 libraries: commons-configuration2, commons-lang3 and ledger-client. Those 3 brought 2 more. commons-text is one of them, and nothing in the POM mentions it. (A version ending in -SNAPSHOT is a build still in progress rather than a finished release. Chapter 10 is about why that matters.)

What Maven builds from is a dependency tree: each library you name brings the libraries it names, and those bring theirs. For a real Spring Boot service the numbers grow fast. The POM might name about 30 libraries, and the tree might hold 200 or 300. So roughly 270 of them are in the image without anyone having written their names. The scanner is right to count them, because an attacker does not care who chose them.

.NET works the same way. A PackageReference brings its own dependencies, and dotnet list package --include-transitive shows them. The difference is in how a conflict is settled.

When two branches ask for different versions

Often two branches of the tree ask for the same library at different versions. A build can include only one copy, so Maven must choose. Its rule is called nearest wins:

  • Maven measures how many steps each request is from your project at the top of the tree.
  • The request with the fewest steps decides the version.
  • Every other branch gets that version too, even if it asked for a newer one.
  • If two requests are equally near, the one declared first wins.

Here is how that played out in the full reports module:

The fixed version, 1.14, was already in the build. It was on a different branch, 3 steps away. The vulnerable 1.9 was 2 steps away. 2 is nearer than 3, so 1.9 won, and 1.14 was silently dropped.

The rule is simple and predictable, and it has one consequence a lead must know. Adding a library can silently downgrade another one. Suppose the module had only the reporting library, so commons-text 1.14 was the only request, and it won. Then someone adds commons-configuration2 to read a config file. It brings commons-text 1.9 from 2 steps away. That is nearer, so 1.9 now wins. Nobody touched commons-text, and its version went backwards.

Other tools chose other rules. Gradle picks the highest version requested anywhere in the tree. In NuGet, a version you name directly in your project always wins. Otherwise NuGet picks the lowest version that satisfies every request.

Making the version a decision

The fix is to stop letting distance decide. You state the version once, in the parent POM's dependencyManagement block:

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.apache.commons</groupId>
      <artifactId>commons-text</artifactId>
      <version>1.14.0</version>
    </dependency>
  </dependencies>
</dependencyManagement>

A dependencyManagement block does not add a library to any module. It says: wherever this library turns up in the tree, at any depth, use this version. It overrides nearest-wins for every branch at once. It is close to pinning a version in Directory.Packages.props with central package management in .NET.

The managed version is a decision someone made and can defend. The nearest-wins version is an accident of how the tree happens to be shaped this week. Chapter 10 is about the tools that keep the decision true.

Triage: which findings matter

Finding the jar takes one command. Deciding what to do about it is triage, and that is the lead's job. For each finding, triage asks three questions:

  1. Is the vulnerable code reachable from ours? A vulnerability in a class we never load cannot be exploited through us, today.
  2. Is there a fixed version, and does it fit? A fix that needs a newer Spring Boot than the one we use is not a quick fix.
  3. What does the library in between say? Here that is commons-configuration2. Its maintainers may already have moved to a fixed version, or said the vulnerable path is not used.

Three tools help:

  • dependency:tree shows the path from our code to the vulnerable jar.
  • versions:display-dependency-updates, a goal of the versions plugin, lists the newer versions that exist for every dependency.
  • OWASP's dependency-check plugin does what the platform scanner did, but during the build, before any image exists. OWASP is a non-profit that publishes security tools and guidance. With the plugin in the build, a new finding turns up in a pull request instead of an email from security.

None of them answers the first question. Reachability is still a person reading the CVE and then reading the code. Honest triage says so.

When a finding is judged not to matter, dependency-check lets you add it to a suppression file, so the build stops reporting it. A suppression with no reason is how a real risk gets hidden.

Remember it as: the build ships a tree, not a list; nearest wins, and the jar you have never heard of has your name on it.

Sam's decision

Sam wrote the decision into the reply to security, and copied the team:

  • The 3 critical findings are fixed this week, by managing their versions in the parent POM. That overrides nearest-wins for every module at once.
  • Each fix's pull request shows the dependency tree before and after. A reviewer can then see exactly which jars changed.
  • The dependency-check plugin goes into the parent, and a serious finding fails the build. The next finding arrives in a pull request, not a spreadsheet.
  • Every suppression needs a reason and a review date. A finding that is unreachable today may be reachable after the next feature.
  • Aisha owns the triage document, one line per finding, including the 38 that are not critical. Somebody has to know all 41, not just the loud 3.
  • Rafael owns reading the trees. He wrote the parent and knows which branches are his.

"We ship everything in that image," Sam told the team. "So from now on, the build tells us what is in it before security does."

Oren asked whether Sam expected every team to do this. This team would, Sam said. The rest was Oren's call.

⚠The traps
  • Not in any POM: the sign is a finding for a library nobody can find in the source code. It is a transitive dependency, brought in by a library you did choose. dependency:tree shows the path, and the image shows what actually shipped.
  • The nearer downgrade: the sign is a library whose version went backwards after an unrelated dependency was added. Under nearest-wins, the new dependency's request was closer to the top of the tree. Manage the version in the parent's dependencyManagement so that distance no longer decides.
  • Unreachable, therefore ignored: the sign is a finding closed as "we don't call that code", with nothing written down. The next feature may call it. Record the reachability judgement with a date, so it gets checked again.
  • The suppression with no reason: the sign is a scanner suppression file whose entries are bare IDs. Nobody can tell which were judged carefully and which were silenced to get a build through. Every suppression needs why, who, and when it will be reviewed.
  • The list that exists only in the scanner: the sign is a team that learns what it ships from security's spreadsheet. The build can print the full list of jars. Make it print the list, and read it.

  1. For this service, how many jars ship in the image, and how many are named in the POM?
  2. For this finding, what is the path from our code to the vulnerable class, and can our code actually reach it?
  3. Where does a new critical finding reach us first: in a pull request, or in an email from security?

Still argued: should a vulnerability score fail the build? OWASP's dependency-check documentation, and most security teams, say yes. A warning that nobody has to act on is a finding nobody acts on, as Equifax's March email showed. Many engineering teams say no, and have argued it in the plugin's issue tracker since Jeremy Long first released it in 2012. A score says nothing about whether our code can reach the flaw. A build broken by an unreachable finding in a test library teaches people to suppress findings without thinking. And the check belongs on the finished image, not the build. Sorrel fails the build above a score and requires a reason for every suppression, which is each side's second choice.

  • What ships is whatever is in the image, so read the image or the full tree, never only the POM.
  • Because nearest wins, a version that matters is managed in the parent, where distance in the tree does not apply.
  • Triage is reachability, fix availability and fit, recorded per finding with a date, and the tool runs the first command while the lead does the rest.

Chapter 10 · Act IIThe Upgrade That Broke Something Else#

The nightly build broke after a weekend in which nobody had changed a line of code, because a shared library changed underneath it. This chapter explains the ways a Maven build's library versions can move on their own, why Maven has no lock file to stop them, and how the enforcer plugin turns "we agreed on this version" into a rule the build checks every time.

The problem

Sorrel's nightly builds run Monday to Friday. On Tuesday morning the team found that Monday night's build of payouts-api had failed. The error was a method-not-found error, in a class nobody had changed, in a module nobody had touched. Nobody had merged anything since Friday, when the nightly build passed.

Rafael, the team's senior developer, eight years at Sorrel, had the cause before stand-up. He wrote the parent POM, the shared build file every Payouts module inherits its settings from, and he takes a build failure on unchanged code personally.

The cause was a library called sorrel-commons, which every Sorrel service uses. It belongs to Oren, who runs the platform team: the people who look after the shared Kubernetes cluster, the image registry and the artifact repository, the server that holds the company's libraries for builds to download. The Payouts POM asked for sorrel-commons like this:

<dependency>
  <groupId>com.sorrel</groupId>
  <artifactId>sorrel-commons</artifactId>
  <version>1.4-SNAPSHOT</version>
</dependency>

A version ending in -SNAPSHOT is not a finished release. It means "the latest build of what will one day become version 1.4". Each time the platform team publishes a new build of the library, that build becomes what 1.4-SNAPSHOT means in the artifact repository. Builds that depend on it check the repository for a newer copy, by default once a day, and download it if there is one.

So a normal version, such as 1.4, is a fixed thing: once published, it never changes. A SNAPSHOT is a moving target, by design. The platform team had published a new build of sorrel-commons on Saturday. In it, a method that Payouts called had been renamed. Monday night's build was the first Payouts build to check after that. It downloaded the new copy, and could no longer find the old method.

"That's what SNAPSHOT is for," Oren said. "Teams get fixes without waiting for a release. It's been that way for years."

"It's been breaking people for years," Rafael said. "You changed a public method on a Saturday, and every service that uses the snapshot got it on their next build."

Oren said the rename had been in the changelog. Rafael said nobody reads a changelog for a library that changes under them without a version change, because the whole point of a version number is that it does not change. Oren wants his team to ship fixes quickly, without a release ceremony for every one. Rafael wants a build that passes on Friday to pass on Monday. Both looked at Sam.

Sam, the team's new lead after twelve years of .NET, had a reflex here and checked it before speaking. The reflex was a lock file: NuGet's packages.lock.json, with CI running dotnet restore --locked-mode so that any difference fails the build. Maven has nothing like it.

The question underneath was simpler, so Sam asked that instead. "Which of our dependencies can change without a change to our build?"

Aisha, the team's junior developer, two years in, ran the dependency tree with versions showing. The dependency tree is Maven's list of every library the build uses, laid out to show which library brought in which. She found three entries that could move. The first was the sorrel-commons snapshot. The second was a version range someone had written in 2022, asking for any version from 1.2 up to, but not including, 2.0. The third was a library the parent POM had pinned the previous week, when the team fixed security's critical findings in chapter 9. One module had declared its own, older version of it since before the pin existed, and a module's own version beats the parent's.

The idea

Maven has no lock file

Each time Maven builds, it works out the dependency tree afresh from the POM files. It does not record the result anywhere. So the build uses the same versions every time only if every version in the dependency tree is fixed.

Three things make a version not fixed.

A SNAPSHOT. As above, 1.4-SNAPSHOT names whatever the latest build is. It changes whenever the owning team publishes.

A version range. Maven lets you ask for a range instead of one version:

<artifactId>policy-client</artifactId>
<version>[1.2,2.0)</version>

NuGet uses the same notation, so [1.2,2.0) means what it means there: 1.2 or newer, below 2.0. The difference is the choice inside the range. NuGet picks the lowest version that fits; Maven picks the highest one in the repository. When someone publishes 1.9, the build quietly starts using 1.9.

A transitive dependency with no managed version. A transitive dependency is one you did not ask for, but a library you asked for did. When two libraries in the dependency tree ask for different versions of the same third library, Maven must choose one. Its rule is called nearest wins:

  • Maven counts how many steps each request is from your project, at the top of the dependency tree.
  • The request with the fewest steps sets the version for the whole build.
  • If two requests are equally near, the one declared first wins.

Here is an example. Your project uses library A, which uses library C, which asks for commons-text 1.14. That request is 3 steps away. Your project also uses library B, which asks for commons-text 1.9. That request is 2 steps away. 2 is fewer than 3, so the whole build gets 1.9. The choice changes whenever any nearer request changes, which can happen when anyone adds, removes or upgrades a library.

A build that contains any of these three can fail on unchanged code. Sorrel's contained all three.

Making a version a decision

The tool that turns a version into a decision is the one the team used in chapter 9 to fix the security findings. It is the parent POM's dependencyManagement block. A version listed there does not add a library to anything. It says: wherever this library appears in the dependency tree, at any depth, use this version. That overrides nearest-wins everywhere in the dependency tree at once.

There is one exception, and it was Aisha's third entry. If a module names a version directly in its own <dependencies>, the module's version wins over the parent's managed one. So the parent's decision is only the decision everywhere if no module has quietly made its own.

Keeping it a decision: the enforcer

A decision written in the parent still depends on everyone remembering it. The enforcer plugin (maven-enforcer-plugin) removes the need to remember. It checks a list of rules during the build, and fails the build when one is broken. The parent declares it like this:

<plugin>
  <artifactId>maven-enforcer-plugin</artifactId>
  <configuration>
    <rules>
      <requireUpperBoundDeps/>
      <banDuplicatePomDependencyVersions/>
    </rules>
  </configuration>
</plugin>

<profile>
  <id>release-checks</id>
  <build>
    <plugins>
      <plugin>
        <artifactId>maven-enforcer-plugin</artifactId>
        <configuration>
          <rules>
            <requireReleaseDeps/>
          </rules>
        </configuration>
      </plugin>
    </plugins>
  </build>
</profile>

The second block is a profile: a named block of POM settings that is switched on by a flag or a condition, much like a build configuration in .NET. Sorrel's pipeline activates the release-checks profile on builds of the main branch, and on no other branch.

Three of the enforcer's rules matter here.

  • requireReleaseDeps fails the build if any dependency is a SNAPSHOT. It lives in the release-checks profile, so it runs on main only. A team can use a snapshot on a feature branch while it tests a fix, but must switch to a released version before the branch is merged.
  • requireUpperBoundDeps runs on every build. It fails if nearest-wins has chosen a version lower than one that some other library asked for. This makes chapter 9's problem loud: there, an older commons-text had silently beaten a newer one because it was nearer.
  • banDuplicatePomDependencyVersions catches a module that declares the same dependency twice.

No enforcer rule here catches the version range. [1.2,2.0) resolves to one released version, so requireReleaseDeps passes it, and nothing is downgraded, so requireUpperBoundDeps passes it too. The range has to be fixed by hand.

Here is what a failure looks like, for the snapshot:

[ERROR] Rule 0: org.apache.maven.enforcer.rules.dependency.RequireReleaseDeps failed with message:
[ERROR] com.sorrel:payouts-api:jar:2.3.0
[ERROR]    com.sorrel:sorrel-commons:jar:1.4-SNAPSHOT <--- is not a release dependency

The message names the library and the version, and the build stops. Nobody has to read a changelog.

BOMs: a family's versions in one line

Some libraries come as a family of related jars that must all be the same version. Their authors publish a BOM, a bill of materials: a special POM whose only content is a list of versions known to work together. You import a BOM into the parent's dependencyManagement, and every library in the family is pinned at once.

Every Sorrel service already imports Spring Boot's BOM. Resilience4j, the library for retries and circuit breakers, and Testcontainers, the library that runs real databases in tests, publish BOMs of their own. Both were on the list Aisha drew up in chapter 3, of libraries whose versions the parent sets outside Boot's BOM.

What the dependency tree does not show

The command dependency:analyze runs the analyze goal of Maven's dependency plugin. A plugin is where Maven's work happens, and a goal is one task a plugin can do, so plugin:goal names one task. This one reports two things a dependency tree never shows:

  • Declared but unused: libraries the module names in its POM but never calls. They add weight to the image and more code for an attacker to aim at.
  • Used but undeclared: classes the module calls from a library it never names. That library arrives transitively today. It vanishes the day the library that brought it changes its own dependencies.

Oren's side

Oren's point stands, and deserves a proper answer. Teams do need fixes without waiting for a release ceremony. A SNAPSHOT on a feature branch, used by the one team testing the fix, is the right tool for that.

What is wrong is a SNAPSHOT on the main branch, used by 40 services that did not ask for the change. So the rule is about which git branch a SNAPSHOT is on, not about SNAPSHOTs as such. The other half falls on Oren's team: if main may not use the snapshot, the platform team has to publish real releases regularly.

Remember it as: Maven has no lock file, so every version is a decision or an accident; the enforcer is how a decision stays one.

Sam's decision

Sam posted the decision in the team channel, with Oren copied:

  • The enforcer goes into the parent. requireUpperBoundDeps runs on every build, and requireReleaseDeps runs in the release-checks profile on main. It will fail the build in 2 places today: the sorrel-commons snapshot, caught by requireReleaseDeps, and the downgraded transitive library, caught by requireUpperBoundDeps. Both are fixed today.
  • The version range from 2022 is replaced by hand with a single fixed version. No enforcer rule catches a range, and a range changes the build every time someone publishes.
  • The module's own older version is deleted. The parent's managed version should be the only one.
  • dependency:analyze runs in CI as a warning for a month, then as a failure. The team needs time to clean up what it finds.
  • The platform team publishes sorrel-commons as a release every fortnight. Payouts uses releases on main and snapshots only on feature branches.

"If a version can change without a commit," Sam told the team, "then our build can break without one. I want every version to move only when one of us moves it."

Oren said a fortnight was a lot of releases. Sam said a Saturday rename was a lot of broken builds, and that releases were cheaper.

◷How we got hereOn 19 October 2005 Brett Porter posted to the Maven users' mailing list: "We are pleased to announce that…

On 19 October 2005 Brett Porter posted to the Maven users' mailing list: "We are pleased to announce that Maven 2.0 has been released." The message called it "a rewrite of the popular Maven application", and listed what the rewrite brought.

The first item on the list is the one this chapter is about: "Enhanced Dependency Management - includes dependency closures (transitive dependencies), version ranges, automatic build numbering, and automatic updating on a configurable interval."

That one sentence introduced, as features, every way a version can move:

  • Transitive dependencies meant a project no longer had to name every library it shipped.
  • Version ranges meant it could ask for "any 1.x".
  • Automatic updating on a configurable interval is what a SNAPSHOT does.

The rule for choosing between two requested versions came with it. Maven 2 picks the "nearest definition", the version declared closest to your project in the dependency tree. The project's guide has said ever since that "you can always guarantee a version by declaring it explicitly in your project's POM". One case was left open. When two requests were equally near, which won was, by the guide's own admission, undefined. That lasted until Maven 2.0.9 in April 2008, which made the first declaration win.

Twenty years on, the rule is unchanged, and the guide's sentence is still the fix. The enforcer plugin and managed versions exist for a simple reason. A rule that a person can break by accident needs a check that the build runs on purpose.

⚙The kit

Find the moving versions, run the enforcer's rules, and list the unused and undeclared dependencies. The legacy reports module in the companion project carries a SNAPSHOT for this purpose.

# Every SNAPSHOT and every version range in the dependency tree:
# the versions that can move without a commit
./mvnw -q -f examples/payouts/legacy/pom.xml dependency:tree \
  | grep -E 'SNAPSHOT|[\[\(][0-9]'

# Run two enforcer rules once, from the command line:
# no snapshots, and no transitive version silently downgraded by nearest-wins
./mvnw -f examples/payouts/legacy/pom.xml enforcer:enforce \
  -Denforcer.rules=requireReleaseDeps,requireUpperBoundDeps

# Declared but unused, and used but undeclared: the two lists a dependency tree never shows.
# -DignoreNonCompile leaves out test and runtime dependencies, which only look unused.
./mvnw -f examples/payouts/pom.xml -pl payouts-api -am compile dependency:analyze \
  -DignoreNonCompile | grep -A6 'Used undeclared\|Unused declared'

# The BOMs the parent imports: each one pins a whole family of versions
grep -B2 -A2 '<scope>import</scope>' examples/payouts/pom.xml

Each plugin:goal names a goal of a Maven plugin: dependency:tree runs the tree goal of the dependency plugin, and enforcer:enforce runs the enforcer's check once. The flags:

  • -q (quiet) hides Maven's own progress messages.
  • -f points Maven at a POM other than the one in the current directory.
  • -pl payouts-api builds only that module, and -am ("also make") builds the modules it depends on first.
  • -D sets a property for the run: -Denforcer.rules=... names the rules to check, and -DignoreNonCompile is read by dependency:analyze.

The first command's pattern matches the word SNAPSHOT, or a [ or ( followed by a digit, which is how every version range starts. The enforcer run fails on the legacy module twice: once for its snapshot, once for a downgraded transitive library.

⚠The traps
  • SNAPSHOT on main: the sign is a -SNAPSHOT version in a POM on the main or release branch. The build can break with no commit, when the owning team publishes a new build, and the changelog nobody read is the only warning.
  • The range from years ago: the sign is square or round brackets in a version, such as [1.2,2.0). Maven picks the highest version available that fits, which is whatever was published last night.
  • The override older than the pin: the sign is a module that declares its own version of a library the parent manages. The module's version wins, so the parent's decision does not apply there. Delete the override, so the parent's version is the only one.
  • Used but undeclared: the sign is a class imported from a jar the module never names in its POM. It arrived transitively, and an upgrade of the library that brought it can remove it.
  • Enforcer as a warning: the sign is an enforcer configured with fail=false. It prints the broken rule and lets the build pass, and a warning in a green build is read about as often as a changelog. Leave fail at its default, true.
✎At the whiteboard
  1. Which versions in this dependency tree can change without a commit to this repository?
  2. What does the build do today if nearest-wins picks a lower version than another library asked for?
  3. How often does the platform team release sorrel-commons, and is that often enough that nobody needs the snapshot on main?

Still argued: should Maven have a lock file? The case for it is made in Gradle's documentation of dependency locking, available since 2018, and by npm and NuGet, which have lock files. A recorded result is the only reproducible one, and the enforcer is a patch over a missing feature. The case against is held by the Apache Maven project, in its guides and in the design of Maven 4. A POM with managed versions and imported BOMs is already a record people can read and reason about, and a generated file nobody reads is where surprises hide. Both agree on the discipline: fixed versions, decided in one place, checked by the build. Sorrel has the enforcer and the parent, so a lock file would be a third copy of the same decision.

What Sam learned

  • Find every SNAPSHOT, range and unmanaged transitive version first; each one is a way for the build to change with nobody changing it.
  • Snapshots stay on feature branches, and the answer to "we need it on main" is a release.
  • Agreed versions live in the parent, and the enforcer, set to fail, is what keeps them agreed.

Chapter 11 · Act IIIThe Ledger Is Down, So Are We#

Another team's service slows down, and Payouts stops answering altogether, even though nothing in Payouts is broken. This chapter explains why a service that calls another service inherits its failures, and the five defences that let it fail quickly and partly instead of slowly and completely: timeouts, retries with backoff, a circuit breaker, a bulkhead, and a tested contract with the other team. It ends with the settings Sam asked for and why.

The problem

At 11:20 on Tuesday the ledger slowed down.

The ledger is the service that records every payment Sorrel makes. It belongs to Bea, who leads the team that owns it. That team is not Payouts, and Bea answers for the ledger when anything goes wrong with it. Every time Payouts pays a claim, it calls the ledger over HTTP to record the payment. Normally the ledger answers in about 200 milliseconds.

That morning it did not fail. It answered every request, but each answer took 30 to 40 seconds. A reporting job on Bea's side was holding a database lock it should not have held, and every ledger request queued behind it.

By 11:26 Payouts was not answering anything at all.

payouts-api runs as 2 copies, called pods, on Sorrel's Kubernetes cluster. Each pod handles HTTP requests on a fixed-size pool of request threads, one thread per request from start to finish. Each payout request called the ledger and waited for the answer, and a waiting thread cannot serve anyone else. Within a few minutes every request thread in both pods was waiting on a ledger call that had not come back.

Kubernetes checks each pod at regular intervals with a readiness probe, a small HTTP request that asks "can you take traffic?". The probe needs a thread too. There were none, so the probe timed out. A pod that fails its readiness probe is taken out of service, and both pods failed. Payouts disappeared, with nothing wrong in its own code.

At 11:40 the two teams got on a call. Rafael, the team's most senior developer, eight years at Sorrel, spoke first. He wrote most of the build, and he wanted the service to survive a slow ledger without anyone getting paged.

"We need retries," he said. "Three attempts, then fail."

"You have retries," Bea said. "That's why I'm on this call. Every request you send me is arriving three times. My job is slow because you tripled my load the moment I got slow."

Bea wanted the opposite of Rafael. Her ledger was struggling, and every extra request from Payouts made it struggle more.

Rafael had not known about the retries. Aisha, the team's junior developer, two years in and the person most willing to open the code and look, found them. The retries came from a client library added in 2022. It retried every failure by default, instantly, three times. That included a timeout. It included a timeout on a write, which means the ledger might have recorded the payment the first time and then been asked to record it twice more.

Sam, the new lead, who came to Sorrel after twelve years of leading .NET teams, had sat on the other end of a call like this before. Sam listened, then asked the question this chapter answers.

"How long do we wait for the ledger before we give up?"

Nobody knew. Aisha found that too. The HTTP client had no timeout configured. With no timeout, it waited forever. That was why both pods had been waiting since 11:21 with every thread they owned.

The idea

What "no timeout" looks like

Here is the shape of the ledger client as it stood on Tuesday morning, simplified:

@Component
public class LedgerClient {
    private final RestClient client;

    public LedgerClient(RestClient.Builder builder) {
        this.client = builder.baseUrl("http://ledger").build();
    }

    public String record(Payout payout) {
        return client.post().uri("/ledger/entries")
                .body(payout).retrieve().body(String.class);
    }
}

RestClient is Spring's HTTP client, the Java counterpart of .NET's HttpClient. It builds a request, sends it and reads the answer. Nothing in this listing says how long to wait. Spring's RestClient sets no timeout of its own by default, so the wait has no end. (.NET's HttpClient at least gives up after 100 seconds by default. Here there is not even that.)

A service that calls another service inherits that service's failures. Without limits it inherits them completely:

  • A slow dependency makes a slow caller.
  • A stalled dependency makes a stalled caller.
  • A caller with a fixed pool of threads becomes a stalled caller with no threads left.

Resilience is the name for the set of mechanisms that let a caller fail partly, quickly and on purpose, instead of totally, slowly and by accident. There are five. If you know .NET, you have met most of them as Polly policies attached to IHttpClientFactory: AddRetry, AddCircuitBreaker and the rest. In Java the library that plays Polly's part is resilience4j.

1. Timeouts: bound the wait

This is the one Sam asked for. There are two kinds.

  • A connect timeout bounds how long to wait to open the connection. If the ledger's machine is unreachable, this is the one that fires.
  • A read timeout bounds how long to wait for the response once the request has been sent. If the ledger is up but slow, as on Tuesday, this is the one that fires.

Here is the client with both set. These are the companion project's numbers, and the ones Sam chose:

ledger:
  base-url: ${LEDGER_URL:http://localhost:8080}
  connect-timeout: 1s
  read-timeout: 2s

The client reads those two values when it is built and hands them to the underlying HTTP connection.

Work through Tuesday again with a 2-second read timeout. Each ledger call that takes 30 seconds now fails after 2 seconds. The thread returns to the pool. It can serve the next request, and it can answer the readiness probe. Payouts stays in service.

That alone would have kept Payouts up on Tuesday. It would still have failed every payout, but correctly: each one with a clear "ledger did not answer in time" error, instead of the whole service vanishing.

2. Retries: try again, gently

This is the one Rafael asked for, used the way Bea needs it used. A retry repeats a call that failed. Two conditions decide whether a retry helps or hurts.

It is safe only if the call is idempotent. An idempotent call is one you can repeat without changing the result: sending it twice has the same effect as sending it once. Reading a balance is idempotent. "Record a payment of £1,000" is not, unless the receiver can recognise the repeat. In chapter 8 the team made the ledger write idempotent: each payout now carries an idempotency key, a unique id the ledger uses to spot a request it has already processed and answer it without recording the payment again. Only because of that is retrying the ledger write safe at all.

It is kind only if it backs off. A retry sends more load to a service that is already in trouble. Three things limit the damage:

  1. Backoff. Wait before retrying, and wait longer each time: say 200 milliseconds, then 400, then 800. This is called exponential backoff. A hiccup of a few hundred milliseconds is absorbed, and a real outage is not hammered.
  2. Jitter. Add a small random amount to each wait. Without it, two pods that failed at the same moment retry at the same moment, and the struggling service gets the retries in waves.
  3. A budget. Cap the total number of retries, across all calls, in a period of time. A dependency in trouble should see a few extra requests, not a multiple of its normal load.

Compare that with the 2022 library. It retried instantly, three times, on everything. A slow ledger got three requests for every one it was already struggling with, which kept it slow for longer.

3. The circuit breaker: remember that it is failing

Timeouts and retries work one call at a time. Neither one remembers that the last 50 calls also failed. Each new request still tries the ledger and still waits its 2 seconds. The third defence is a memory.

A circuit breaker sits in front of the client and counts recent outcomes. It has three states.

  • Closed is normal. Every call goes through, and the breaker records whether it succeeded. It keeps only the most recent outcomes, say the last 10 calls. This moving record is called a sliding window.
  • Open is what happens when the failure rate in the window crosses a threshold, for example 50%. For a set time, say 20 seconds, every call fails at once without touching the ledger. Payouts gets an immediate error instead of a 2-second one, and Bea's ledger gets a rest, which gives her lock time to clear.
  • Half-open comes after the wait. The breaker lets a few trial calls through. If they succeed, it closes again. If they fail, it opens for another wait.

The companion project configures its ledger breaker like this:

resilience4j:
  circuitbreaker:
    instances:
      ledger:
        sliding-window-size: 10
        minimum-number-of-calls: 5
        failure-rate-threshold: 50
        slow-call-duration-threshold: 1500ms
        wait-duration-in-open-state: 20s
        permitted-number-of-calls-in-half-open-state: 2

The slow-call-duration-threshold line is worth noticing. A call that succeeds but takes longer than 1.5 seconds also counts against the ledger. So the breaker can open on a slow ledger, not only on a failing one.

4. The bulkhead: contain the damage

A bulkhead is a cap on how many calls to one dependency may be in flight at the same time. The name comes from the walls that divide a ship's hull, so that one flooded section does not sink the ship.

Say Payouts has 200 request threads and allows at most 20 concurrent calls to the ledger. However slow the ledger gets, it can tie up at most 20 threads. The other 180 keep serving everything else, including the readiness probe. A request that would be the 21st concurrent ledger call fails at once instead of joining the queue.

On which library provides what: Spring Framework 7, which Spring Boot 4 is built on, ships a retry and a concurrency limit (a bulkhead) in its core. It does not ship a circuit breaker. Resilience4j has all of them, which is why the companion project carries it.

5. The contract: agree what each side promises

The fifth defence is not a library. The ledger is Bea's. What it promises (which requests it accepts, how fast it answers, and what it returns when it cannot) is an agreement between two teams. Written down and checked automatically, that agreement is a contract.

A contract test checks the agreement from both sides. Payouts' build checks that Payouts sends the requests the contract describes and copes with every answer it allows. The ledger's build checks that the ledger really gives those answers. If either team changes something the other depends on, a build fails before anything reaches production.

One more call deserves a timeout. Sorrel's internal services prove who they are to each other with client credentials: before calling the ledger, Payouts asks the company's identity provider for a token, using its own id and secret, and sends the token with the request. That is the right way to do it. It also means every ledger call is really two calls, and the token request needs a timeout of its own.

Remember it as: a timeout bounds the wait, a retry with backoff forgives a blip, a breaker remembers, a bulkhead contains; without the first, the others never run.

The last half of that line is literal. A breaker counts failures, but a call with no timeout never finishes, so it never fails and is never counted. Timeouts come first.

Sam's decision

Sam decided on the call, with Bea listening.

  • Timeouts on every outbound call by Thursday: connect 1 second, read 2 seconds. Start with the ledger and the token endpoint, because those two took Payouts down.
  • The 2022 client library is removed. Its retries hit the ledger instantly, three times, on writes as well as reads.
  • Retries move to resilience4j: exponential backoff with jitter, on idempotent calls only, 3 attempts within a budget. Bea's ledger should see a few extra requests in a bad minute, not three times its load.
  • A circuit breaker and a bulkhead on the ledger. The thresholds go in configuration, where they can be reviewed. The breaker's state goes in a metric that Oren, who runs the platform team and its dashboards, can graph.
  • A contract test with Bea's team, owned by both teams and run in both pipelines. Each side then finds out about a breaking change from a failed build, not from an incident call.

"From now on," Sam told the team, "every call that leaves this service has a time limit and somebody's name next to it. When the ledger is slow, we fail fast and say so."

Rafael asked whether the breaker would make payouts fail when the ledger was merely slow. Sam said yes: fast and visibly, which was the point. A payout that failed in 2 seconds could be retried by whatever owned the retry. A pod that waited forever could not.

◷How we got hereThese five defences have a well-known origin, and it is a company that learned them the hard way.

These five defences have a well-known origin, and it is a company that learned them the hard way.

In 2011 the Netflix API team had a problem. Their API called dozens of other services behind the scenes. Again and again they watched one slow dependency, out of all those dozens, take the whole API down by using up its threads. It was Sorrel's Tuesday at a much larger scale.

The team built a library to stop it happening. On 26 November 2012 Ben Christensen of the Netflix API team published a post that introduced it to the world. It began with the sentence this chapter rests on: "In a distributed environment, failure of any given service is inevitable." The library was called Hystrix. It did three things:

  1. It wrapped every outbound call in a command with a timeout.
  2. It ran each dependency's calls on that dependency's own small thread pool, so one slow dependency could use up only its own threads. That is a bulkhead.
  3. It kept rolling statistics on each dependency and opened a circuit when the failure rate crossed a line. That is a circuit breaker.

Netflix was by then running, in its own words, tens of billions of such calls a day.

Hystrix's design became the industry's. Spring Cloud wrapped it, and a generation of Java services carried its dashboard.

Then, on 19 November 2018, the maintainers changed the project's README. Hystrix was "no longer in active development" and was "in maintenance mode". Netflix's own focus had moved on, to adaptive limits: limits that adjust themselves to how the dependency is measured to be performing, instead of fixed numbers. For new work, the README said, they intended "to leverage open and active projects like resilience4j", and they recommended that others do the same.

Resilience4j had been started by Robert Winkler in 2015 under another name and renamed in 2017. It took Hystrix's ideas and rebuilt them as small, separate modules: a breaker, a retry, a bulkhead, each usable on its own. That is the form Sorrel's companion project uses.

The mechanism is the one Hystrix introduced in 2012. Only the library that carries it has changed.

⚠The traps
  • No timeout at all: the sign is a RestClient (or any HTTP client) built with its defaults and no timeout set. The wait has no end, and one slow dependency takes every thread the caller has. Set a connect and a read timeout on every outbound client.
  • Retry on everything: the sign is a client that retries timeouts and writes alike, instantly, with no wait. The dependency in trouble sees its load multiplied by the retry count, and a non-idempotent write may happen twice. Retry only idempotent calls, with backoff, jitter and a budget.
  • The breaker with no metric: the sign is a circuit breaker whose state nobody can see on a dashboard. It opens, payouts fail, and the first person to know is the customer. Publish its state as a metric and alert on it.
  • The shared pool: the sign is one thread pool serving calls to every dependency. The slowest dependency takes all of it. A bulkhead per dependency keeps the others alive.
  • The token call nobody counted: the sign is a timeout on the business call and none on the token request that comes before it. The identity provider is a dependency too, and it can hang the service just as well.
✎At the whiteboard
  1. For each outbound call, what are the connect and read timeouts, and who chose them?
  2. Which calls are retried, are they idempotent, and how much extra load would a burst of retries put on the other team?
  3. When the breaker opens, where does it show, and what does our caller get back?

Still argued: fixed limits or adaptive ones. The fixed side is Hystrix's original 2012 design and resilience4j's default. A timeout, a failure threshold and a pool size are decisions a team makes from what it knows about its dependency, and a number in a configuration file can be reviewed and argued about. The adaptive side is the one Netflix stated when it retired Hystrix in 2018. The right limit changes minute by minute with the dependency's measured speed, so any fixed number is wrong most of the time. Both are right at their scale. Sorrel has a dozen dependencies and one platform team, so it chose fixed numbers it can read, and puts the breaker's state in a metric so the numbers can be argued about with evidence.

What Sam learned

  • Ask how long we wait before anything else, because until every outbound call has a timeout, nothing else protects the pod.
  • Count every retry as load on the other team, and retry only what is safe to repeat, spaced out and capped.
  • Put the breaker's state on a dashboard, because the other team's phone call is not a monitoring system.

Chapter 12 · Act IIILet's Go Reactive#

Rafael proposes rewriting payouts-api in a reactive style so that no thread ever sits waiting. Sam asks a cheaper question first: what does a waiting thread actually cost? This chapter explains why blocked threads used to be expensive in Java, what reactive programming does about it and what it costs, and how virtual threads, final since Java 21, make most of the rewrite unnecessary. The problem

Rafael, the team's most senior developer, eight years at Sorrel and the author of most of the build, brought his second proposal with a graph instead of a benchmark.

He likes architecture that removes a whole class of problem rather than patching it, and he had a class of problem in mind.

The graph showed the Thursday ledger stall. (The ledger is the service that records every payment. It belongs to Bea, who leads the team that owns it, and it had slowed down again.) Since the last chapter, every call from payouts-api to the ledger has a 2-second timeout. So this time payouts-api stayed up. But the graph showed what its request threads did during the stall.

payouts-api serves HTTP requests on a pool of request threads. One thread handles one request from start to finish. The pool had a ceiling of 200 threads. During the stall, every thread spent 2 seconds blocked: stopped, waiting for the ledger to answer, unable to do anything else. For most of a minute all 200 were blocked at once. On the graph that minute was a solid block of colour, a wall.

"Blocking is the disease," Rafael said. "The timeout treats the symptom. WebFlux stops threads waiting at all. Non-blocking end to end: the request, the ledger call, the database. One event loop, a handful of threads, no pool to exhaust."

WebFlux is Spring's reactive web framework, the alternative to the ordinary Spring MVC that payouts-api uses today. An event loop is a small, fixed set of threads that never wait. When a piece of work would have to wait, the thread registers "call me back when the answer arrives" and moves on to other work. Node.js works this way.

The idea

Two ways to write the same request

Here is the heart of a payout request as payouts-api handles it today:

public PayoutResponse pay(CreatePayoutRequest request) {
    Payout payout = payoutService.create(request);   // waits for MongoDB
    String entryId = ledgerClient.record(payout);    // waits for the ledger
    return PayoutResponse.of(payout, entryId);
}

It reads top to bottom. Each line runs, waits if it must, and returns its result. While it waits, the thread it runs on is blocked.

Here is the same thing written for WebFlux, with Reactor, the library WebFlux is built on:

public Mono<PayoutResponse> pay(CreatePayoutRequest request) {
    return payoutService.create(request)
            .flatMap(payout -> ledgerClient.record(payout)
                    .map(entryId -> PayoutResponse.of(payout, entryId)));
}

A Mono is Reactor's type for "one value that will arrive later", roughly what a Task<T> is in .NET. Its sibling Flux is "many values arriving over time", roughly IAsyncEnumerable<T>. This method does not pay anything when it runs. It builds a pipeline that describes what to do when each result arrives, and returns it at once. No thread waits. That is the whole appeal, and it is also the cost: every method in the path now returns a Mono or a Flux, including the ledger client and the repository.

Why a blocked thread was expensive

A blocked thread is only a problem if threads are expensive. Until Java 21, they were.

An ordinary Java thread, now called a platform thread, is a thin wrapper around a thread of the operating system, a kernel thread. Each one gets a stack: the memory where the thread keeps its local variables and the chain of method calls it is in the middle of. A platform thread's stack is reserved at a fixed size, about 1 megabyte by default.

So a service that gives each request its own thread can afford a few hundred threads, not tens of thousands. That is why thread pools exist and why they have ceilings. And it is why a stalled dependency fills the pool. Each request holds a thread while it waits, and when all 200 are holding, request 201 queues.

The reactive answer is never to block, so a handful of threads can serve thousands of requests. The throughput gain is real. The price comes in three parts:

  1. Every library in the path must be written the same way. A single blocking call inside the pipeline stalls one of the few event-loop threads, and with it every request that thread was serving.
  2. The code reads as a description of a pipeline, not as a sequence of steps. Loops, try/catch and early returns all become operators on Mono and Flux.
  3. A stack trace shows the pipeline's machinery, not your program. The method that started the work returned long ago, so it is not on the stack when something fails.

A .NET developer knows this story as "async all the way down". Once one method is async, its callers want to be too, and the change spreads.

Virtual threads: make the thread cheap instead

Java 21, released in 2023, offered a different answer: keep the blocking code, and make the thread cheap.

A virtual thread is a thread that the JVM schedules itself, instead of handing it to the operating system. Its stack lives in the JVM's ordinary memory, the heap, and grows only as far as it needs. A virtual thread that is waiting costs a few hundred bytes, not a megabyte.

Underneath, the JVM keeps a small pool of platform threads called carrier threads, by default one per CPU core. A virtual thread runs by riding on a carrier. Here is what happens when one makes a ledger call:

  1. The virtual thread runs on a carrier until it reaches the network call and has to wait.
  2. The JVM unmounts it: it saves the virtual thread's small stack to the heap and frees the carrier.
  3. The carrier immediately picks up another virtual thread that has work to do.
  4. When the ledger answers, the JVM mounts the waiting virtual thread on a free carrier, and it carries on from the line where it stopped.

The code does not change. The first listing above, the plain blocking one, runs on a virtual thread exactly as written. The ledger call still takes 2 seconds during a stall. But the waiting now costs nothing anyone can measure. There is no pool of 200 to fill, because each request gets its own virtual thread.

A note on what virtual threads do not remove. In the previous chapter the team put a bulkhead on the ledger client: a cap on how many ledger calls may be in flight at once, for example 20. With a pool of 200 threads, the pool was a crude limit of its own. With virtual threads there is no pool, so the bulkhead becomes the only thing that stops a stalled ledger from collecting thousands of waiting requests. Keep it.

Turning them on in Spring Boot

Spring Boot has supported virtual threads since version 3.2. It takes one property:

spring:
  threads:
    virtual:
      enabled: true

With spring.threads.virtual.enabled set to true, the web server handles each request on a new virtual thread, and most of Spring's own background executors use them too. The property defaults to false, so nothing changes until you set it.

The MongoDB driver Payouts uses is a blocking driver. That is fine. A virtual thread blocking on the database is exactly the case virtual threads were built for.

Two cautions

Pinning. Sometimes the JVM cannot unmount a waiting virtual thread. The virtual thread then holds its carrier for as long as it waits, which is called pinning. With only one carrier per core, a few pinned threads can stall everything, and virtual threads quietly behave like a small fixed pool again. Two causes matter:

  • synchronized blocks. synchronized is Java's built-in lock keyword, close to C#'s lock. Until Java 24, a virtual thread that waited inside one was pinned. Java 24, in 2025, removed that limitation.
  • Native code. Some libraries call into C code through the JVM's native interface. A virtual thread waiting inside native code is still pinned today. So one library that blocks inside native code can undo the benefit for the whole service.

CPU-bound work. Unmounting helps a thread that waits. It does nothing for a thread that is busy calculating. A job that spends its time computing gains nothing from virtual threads, because there is never a wait to unmount it during.

When WebFlux still wins

Rafael's architecture is not wrong in general. It wins when the work is genuinely a stream:

  • A feed of events pushed to thousands of open connections at once.
  • A fast producer and a slow consumer, where you need backpressure: the consumer's way of telling the producer to slow down instead of being flooded.
  • A stack that is already reactive end to end, which would lose by converting back.

Payouts is not like that. It receives a request, calls two systems and writes one document. It is the shape virtual threads were made for.

Remember it as: blocking is only a disease when threads are expensive; on Java 21 and later, turn on virtual threads before you rewrite anything.

◷How we got hereJava could have gone the way C# went.

Java could have gone the way C# went. It chose not to, and the choice was made on the first day.

On 26 September 2017 Ron Pressler posted a proposal to the OpenJDK discussion list for a new project. Pressler had spent years building lightweight threads for the JVM outside the JDK itself. The project's mission, in the proposal's words, was "to make it easier to write, debug, profile and maintain concurrent applications meeting today's requirements". The vote closed on 13 November: 20 in favour, none against. The project was called Loom.

By then other languages had answered the same problem with async and await, C# among them. The proposal explained why Java would not. That style, it said, "still requires significant changes to existing code, explicit support in libraries, and does not interoperate well with synchronous code". So it "does not solve what's known as the 'colored function' problem".

The colored function problem is the name for what Sam lived through in .NET. Every function becomes one of two colours, synchronous or asynchronous. An asynchronous function can call a synchronous one, but not comfortably the other way round. So once one function turns asynchronous, its callers turn too, and the colour spreads through the codebase.

Loom's alternative was to make the thread itself cheap. Then the existing blocking code, the existing libraries and the existing stack traces would all keep working.

It took 6 years. Virtual threads appeared as a preview in Java 19 and 20. They were delivered final by JEP 444, written by Pressler and Alan Bateman, in Java 21 on 19 September 2023. (A JEP, a JDK Enhancement Proposal, is the document that describes a change to Java.) The JEP restates the decision in its section on alternatives. Adding async/await, it says, "would split the world between APIs designed for threads and APIs designed for coroutines". Most languages that chose it "have done so due to an inability to implement user-mode threads", a limitation that "does not apply to Java".

The last large gap, pinning inside synchronized, was closed by JEP 491 in Java 24 in March 2025.

Sam's 18 months of watching async creep inward in .NET was the colored function problem. Loom was Java's decision not to have it.

⚠The traps
  • Rewriting before measuring: the sign is a reactive rewrite proposed with a graph of blocked threads, and no test of virtual threads. Switch them on and reproduce the slow dependency first; the rewrite can wait a week.
  • The pool ceiling from years ago: the sign is a max-threads or similar setting that someone chose when threads were expensive. It may now be the only limit in the service, and its origin is lost. Find out, or delete it.
  • Pinning in native code: the sign is virtual threads switched on and a graph that still shows a wall. A library waiting inside native code holds its carrier thread, and the carriers run out. Find it with the JDK's pinned-thread diagnostics.
  • Virtual threads for CPU work: the sign is a compute-heavy job moved to virtual threads to make it faster. It never waits, so it is never unmounted, and it runs no faster than before.
  • Half a reactive stack: the sign is a WebFlux controller calling a blocking driver or client. The blocking call stalls one of the few event-loop threads, and the service ends up slower than either design done properly.

  3. What in this service is really a stream that needs backpressure, rather than a request that waits?

Still argued: does reactive programming still have a future on the JVM now that threads are cheap? The reactive side is held by the Reactor and WebFlux maintainers and stated in Spring's documentation since 2023. Virtual threads fix the cost of threads and nothing else. The problem

The pod died at 02:14 and left nothing behind.

"The container was using more memory than its limit," he said. "The limit is 512 MiB. The Linux kernel killed it."

Rafael, the team's most senior developer, eight years at Sorrel and the person who gets called when a Payouts pod dies at night, answered first. He wanted it to stop dying.

"Then the limit's too low," he said. "It's a Java service. Give it a gigabyte."

"When it died it had 384 MiB of heap, all used, and 160 outside the heap. That's 544 in a 512 container," Oren said. "I don't give a service more because it asked. I give it more when someone tells me what it needs and why."

Oren wanted the opposite of Rafael. Every megabyte he gives one service is a megabyte the cluster cannot give another, so he wanted a reason, not a request.

Sam, the new lead after twelve years of .NET, had a memory of this too. In .NET the garbage collector's heap can be capped with DOTNET_GCHeapHardLimit (a size in bytes) or DOTNET_GCHeapHardLimitPercent (a share of the memory available). Inside a container with a memory limit, .NET sets that cap to 75% of the limit by default. Sam remembered a service that had grown past its container anyway, because the cap covered the managed heap and nothing else. It had taken a week to find out what the rest was.

"What does this service need," Sam asked, "and how would we know?"

Aisha, the team's junior developer, two years in, pulled the image's startup flags. The flag that mattered was -XX:MaxRAMPercentage=75, which told the JVM to give 75% of the container's 512 MiB to the heap: 384 MiB, leaving 512 − 384 = 128 MiB for everything else.

That 128 MiB was expected to cover everything the JVM needs that is not heap. Nobody could say what that everything was. The kernel had just said it did not fit.

The idea

Two different ways to run out of memory

A Java service can run out of memory in two ways, and they look completely different.

1. Java runs out of heap. The heap is the area where Java keeps its objects: every Payout, every string, every request body. The JVM has a maximum heap size. When a new object will not fit even after the garbage collector has freed everything it can, the JVM throws a java.lang.OutOfMemoryError.

This is Java's own error, inside the process. The JVM is still running when it happens. It can log the error with a stack trace. It can write a heap dump, a file holding every object in the heap, which you can open later to see what filled it. The process may limp on afterwards or exit, but it has a chance to say what went wrong.

2. The kernel kills the container. In Kubernetes, a container's memory limit is enforced by the Linux kernel, not by Java. The kernel counts every byte the whole process uses: the heap, and everything else the JVM has allocated outside it. When that total goes over the limit, the kernel kills the process with signal 9, SIGKILL.

SIGKILL cannot be caught or delayed. The JVM gets no chance to run any code at all, so it logs nothing and writes nothing. Kubernetes records the death as reason: OOMKilled (killed for being out of memory) with exitCode: 137. The 137 is the shell's convention for "killed by a signal": 128 plus the signal number, 9.

So the two cases leave very different evidence:

Java's OutOfMemoryError The kernel's OOM kill
What ran out The heap The container's memory limit
Who notices The JVM The Linux kernel
What you get A log line, a stack trace, optionally a heap dump OOMKilled, exit code 137, nothing else

The 02:14 death was the second kind. The heap was within its 384 MiB. It was everything outside the heap that pushed the process over 512 MiB.

How the JVM chooses its heap size

A JVM in a container has to answer one question at startup: how much memory is there?

Until 2018 it answered by asking the operating system. Inside a container, the operating system described the whole machine. So a JVM with a 1 GiB limit, on a host with 64 GiB, sized its heap as if it had 64 GiB. It then grew happily past its limit and was killed without warning.

Container awareness, on by default since JDK 10, fixed that. The JVM now reads the container's memory limit instead of the host's memory. It knows where the edge is. What it does with that knowledge is the next decision.

By default the JVM takes 25% of the limit for its maximum heap. The flag -XX:MaxRAMPercentage changes that share. Sorrel's image, like the companion project's, set it to 75. Setting it to 75 is common. It is also a claim: that everything the JVM needs outside the heap fits in the remaining 25%. For a 512 MiB container that is 128 MiB.

Everything that is not heap

That "everything" has parts, and each part has a name.

  • Metaspace holds the JVM's description of every class it has loaded: its methods, fields and other metadata. It grows with the number of classes, and a Spring Boot service loads many thousands of them, from Spring, from libraries and from your own code.
  • The code cache holds machine code. The JVM starts by interpreting your program, then compiles the methods it uses most into native machine code, and keeps that compiled code here.
  • Thread stacks. Every platform thread has a stack, the memory that holds its local variables and the chain of calls it is in the middle of. The previous chapter switched payouts-api to virtual threads, whose stacks live on the heap. The carrier threads underneath them (the few platform threads that virtual threads run on), and the JVM's own threads, still have ordinary stacks outside the heap.
  • Direct buffers are blocks of memory outside the heap that the network stack and the database driver use for input and output.
  • The garbage collector itself needs memory to keep track of the heap, and the JVM has smaller internal uses besides.

None of these appear on a heap graph. All of them count against the container's limit.

Measuring it: native memory tracking and jcmd

You do not have to guess these numbers. The JVM can report them.

Native memory tracking is a JVM feature that keeps a running account of the memory the JVM uses outside the heap, broken down by category. It is off by default. You turn it on with a startup flag:

-XX:NativeMemoryTracking=summary

It costs a little: Oracle's documentation puts the slowdown at 5 to 10%. That is a fair price for an hour of measurement.

You read the report with jcmd, a command-line tool that ships with the JDK. jcmd sends a diagnostic command to a running JVM, identified by its process id. Inside a container the JVM is usually process 1, so the command is:

jcmd 1 VM.native_memory summary

It prints a total, then one entry per category: Java Heap, Class (which is metaspace), Thread, Code (the code cache), GC, Internal and others. Reading it once, from a pod under real production load, is the hour of work that replaces the week of guessing.

Sorrel's report, taken under steady load, came to about 200 MiB outside the heap, not 128. Oren's 160 MiB had been a snapshot of the moment of the kill. The 200 MiB is what the service needs once it is running in earnest, and it is the figure to size from. The difference from 128 was mostly metaspace and the code cache. Both grow with the size of the application, and the 75% had budgeted for neither.

Making the death speak

Two more changes turn the kernel's silence into a message.

-XX:+ExitOnOutOfMemoryError tells the JVM to exit at the first OutOfMemoryError, with a short message naming the cause (Terminating due to java.lang.OutOfMemoryError: Java heap space), instead of limping on or dying silently. Without it, a JVM whose heap is nearly full can spend its last minutes running the garbage collector over and over, freeing almost nothing. With it, the heap case always ends in that one clear line. The kernel kill is then left for the case where the whole process goes over the limit, and a JVM whose heap is sized honestly rarely gets there.

Requests and limits should be equal for memory. Each container in Kubernetes can state two memory figures:

resources:
  requests:
    memory: 512Mi
  limits:
    memory: 512Mi
  • The request is what Kubernetes reserves for the container when it decides which node (which machine) to put the pod on. The scheduler adds up requests and only places a pod where its request still fits.
  • The limit is the ceiling the kernel enforces once the pod is running. Go over it and the container is killed.

If the request is lower than the limit, the scheduler is told that the pod needs less than it will really use. Two services that each fit their requests can be placed on a node that cannot hold both of them at their limits. When both grow, one of them dies. Setting request equal to limit means the scheduler reserves what the pod will really use.

Remember it as: the heap is the part you can see; the limit is the whole; size from a native memory report, not from a percentage someone chose.

Sam's decision

Sam decided in the incident review.

  • The limit is not raised until the service's footprint has been measured, and it is measured today. One pod under load, with native memory tracking on, read with jcmd. A bigger limit without a number is a bigger container with the same mystery inside.
  • The heap is then set as a fixed size from the measurement, and the percentage flag goes. The manifest carries a comment with the arithmetic: the heap, the measured non-heap total and the margin.
  • -XX:+ExitOnOutOfMemoryError goes into the image. The next time the heap runs out, the JVM exits with a line saying so, and the log names the cause.
  • The memory request equals the memory limit. The scheduler should reserve what the pod really uses.
  • Oren adds an alert on container memory at 90% of the limit. The heap graph everyone watches is the one graph that could not have predicted this. The container's total memory is what the kernel counts.

"We've been looking at the heap and arguing about the limit," Sam told the team. "The kernel counts the whole process. So that's what we measure."

Aisha asked whether the answer would turn out to be a gigabyte after all. It might, Sam said, and then it would be a gigabyte with a reason, which was the only kind Oren was offering.

The measurement came back that afternoon.

  • The heap stayed at 384 MiB. The heap had filled to its maximum on the night, but that is normal for a JVM: the garbage collector lets the heap grow to its ceiling before working hard. It was keeping up. The heap was not the problem.
  • Outside the heap: about 200 MiB under steady load, more than the 160 MiB Oren had seen at the moment of the kill.
  • 384 + 200 = 584 MiB in use. With headroom on top, the measured requirement came to 640 MiB.

Oren gave it 768 MiB.

◷How we got hereThe JVM's blindness inside containers was noticed early, and took more than two years to fix properly.

The JVM's blindness inside containers was noticed early, and took more than two years to fix properly.

On 23 December 2015 Karen Kinnear of Oracle's JVM team filed an issue, JDK-8146115, with a plain title: improve container detection and resource configuration. The JVM, it noted, "normally queries the operating system in order to setup runtime defaults" for things like the number of garbage-collector threads and the memory limits. Inside a container, those queries returned the figures for the whole host.

The failure that caused was the one Sorrel met. A JVM sized itself for a machine it did not have, ran past a limit it could not see, and was killed by the kernel without a word. Engineers running Java in Docker in 2016 learned to set the heap by hand, and were often surprised anyway, because the heap was not the only thing using memory.

Christine Flood at Red Hat shipped the first fix in December 2016, as an experimental flag. In April 2017 she explained the problem in the clearest sentence anyone has written about it. The JVM "historically looked in /proc to figure out how much memory was available", she wrote, and "containers like Docker don't provide container specific information in /proc". (/proc is the Linux directory where a program reads facts about the system, such as how much memory there is.)

Bob Vandette's full fix landed in JDK 10, released on 20 March 2018. Container support was on by default. A new flag, MaxRAMPercentage, set the heap's share of the container's memory, and it defaulted to 25%. Oracle backported the fix to Java 8 in October 2018, in update 191, so that the long tail of services still on Java 8 would stop sizing themselves for the host.

The 25% default is cautious because its authors had just watched what a JVM did when it thought it had the whole machine. The 75 in Sorrel's image was someone's later judgement that 25% was wasteful, made without measuring what the other 25% would have to hold.

⚠The traps
  • The percentage with no measurement: the sign is MaxRAMPercentage=75 and nobody who can say what the other 25% holds. The heap fits inside its share, and the whole process does not fit inside the limit. Measure the non-heap memory with native memory tracking.
  • Watching the heap graph: the sign is a memory dashboard that shows only the heap. The kernel kills on the whole container's memory, and the heap graph was green when it happened. Graph and alert on container memory.
  • Request below limit: the sign is a memory request at half the limit. The scheduler places pods by their requests, and the node runs out when they grow towards their limits. Set the memory request equal to the limit.
  • Silence as a symptom: the sign is a pod death with no log line and exit code 137. Add -XX:+ExitOnOutOfMemoryError so the heap case names itself, and alert on container memory for the rest.
  • Raising the limit as a fix: the sign is a gigabyte given because a service asked. Without a measurement, the same overflow returns at a higher number.
✎At the whiteboard
  1. What is this service's memory use outside the heap, measured on a pod under load, and when was it measured?
  2. Is the memory request equal to the limit, and does our alert fire on the heap or on the whole container?
  3. When this pod dies of memory, what will we have to read: a stack trace, a heap dump, or only an exit code?

Still argued: should the heap be a percentage of the limit or a fixed size? The percentage side is the JDK's own container work since 2018 and most platform teams' image guidance. A percentage follows the limit, so a service given more memory uses more without rebuilding the image. The fixed side is argued by many Java performance specialists and in a long line of production post-mortems. The memory outside the heap does not grow with the limit, so a percentage that is safe at 1 GiB is unsafe at 512 MiB. Only a measured, fixed heap with a measured, fixed margin is honest. Sorrel chose a fixed heap from a measurement, with the percentage flag removed and a comment explaining the arithmetic, because its limits are set per service and rarely change.

What Sam learned

  • The JVM knows its container's limit but not what the rest of the process needs, so read a native memory report before choosing a heap size.
  • A pod that dies silently needs two changes: ExitOnOutOfMemoryError, so running out of heap ends in a message, and an alert on the whole container's memory.
  • Answer "give it more" only after "how much does it need" has a measured answer.

A team on another floor has been quietly retrying a dozen failed calls a week, and every one of them failed during a Payouts deploy. This chapter walks through what Kubernetes and Spring Boot each do when a pod is replaced, why the two can disagree for about a second, and the handful of manifest settings that make a deploy drop nothing. The problem

The memory fixes from the last chapter had stopped the pods dying at night. Three weeks later Bea, who owns the ledger service on another team, rang Sam. The ledger records every payment Sorrel makes. Payouts writes to it, and when the ledger finishes posting a payment it calls Payouts back to confirm. Those confirmations are the ledger callbacks.

Bea had a chart. About 40,000 callbacks a week went from the ledger to Payouts. About 12 of them failed, some with a connection reset and some with a 502 from the load balancer. When Bea plotted the 12 against time, every one sat inside the 3 minutes around a Payouts deploy. Payouts deployed twice a day.

"Your rollouts drop requests," Bea said. "I've been retrying them from my side for a month. I'd rather you stopped dropping them."

Bea wanted this fixed because a retry hides a failure from the team that caused it. She also did not want to own retry code for someone else's bug.

Sam put the chart on the screen at stand-up. Rafael, the team's senior developer, eight years at Sorrel and the person who knows Spring Boot best on the floor, answered first.

"Boot does graceful shutdown," he said. "By default, since 3.4. The server stops taking new connections and finishes the ones in flight. We don't drop anything."

Graceful shutdown means that when the application is told to stop, it does not stop at once. It refuses new work, lets the requests it is already handling finish, and then exits. Rafael was right that Boot does this. Before Boot 3.4 the default was to stop immediately, and since 3.4 it is graceful. Payouts runs Boot 3.5, so it was on.

Oren, who runs the platform team that looks after the shared Kubernetes cluster, had the pod events. He trusts a timestamp more than a description, and his timestamps told a slightly different story.

A pod is the unit Kubernetes runs: one or more containers that start and stop together. A Payouts service runs as 2 pods. A Service in Kubernetes is the stable name other systems call, such as payouts-api. Behind it is a list of the pods currently allowed to receive traffic, called its endpoints.

On a deploy, Oren's events showed Kubernetes doing two things to each old pod at the same moment. It sent the pod SIGTERM, the polite "please stop" signal on Linux. And it began removing the pod from the Service's endpoints, so that new requests would go elsewhere. The two ran in parallel, and the second took longer. For about a second after the signal, the old pod's address was still being handed out. A request that arrived in that second met a server that had just stopped accepting new connections.

"So it's a race," Sam said. "Between the pod stopping and the cluster noticing."

"It's always a race," Oren said. "Nothing in that manifest tells the pod to wait."

Aisha, the junior developer, two years in, opened the manifest, the YAML file that tells Kubernetes how to run the service. She reads the file before anyone argues about it. There was no preStop hook. The termination grace period was 30 seconds, the same as Spring's default shutdown timeout. The readiness probe checked the same endpoint as the liveness probe. The rolling update was left on Kubernetes's defaults, on a deployment of 2 pods.

Each of those lines was a small decision nobody had made on purpose. Rafael's position was that the application already behaved correctly, which it did. Bea's position was that requests were still being dropped, which they were. Both were true.

The idea

What happens when a pod is replaced

Start with the manifest Payouts ended up with. This is the part that matters here, condensed from the companion project:

strategy:
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
template:
  spec:
    terminationGracePeriodSeconds: 40
    containers:
      - readinessProbe: { httpGet: { path: /actuator/health/readiness } }
        livenessProbe:  { httpGet: { path: /actuator/health/liveness } }
        startupProbe:   { httpGet: { path: /actuator/health/liveness } }
        lifecycle:
          preStop: { exec: { command: ["sleep", "5"] } }

Every line answers a question about the deploy. To see the questions, follow what Kubernetes does when you ship a new version.

A Deployment is the Kubernetes object that keeps a set number of identical pods running. When you change its image, it performs a rolling update: it replaces old pods with new ones a few at a time, rather than all at once. Each step of the rolling update has three handoffs:

  1. Start a new pod.
  2. Wait until the new pod is ready, then send it traffic.
  3. Stop an old pod.

A request is dropped whenever one side of a handoff moves before the other side has been told. The manifest's job is to make each handoff wait for the right signal.

Ready: three probes, three questions

A probe is a check Kubernetes runs against a container on a schedule, usually an HTTP request to a path. There are three kinds, and each has a different consequence:

  • The liveness probe asks "is this process still working?" If it fails 3 times in a row, Kubernetes restarts the container.
  • The readiness probe asks "can this pod take traffic right now?" If it fails, Kubernetes removes the pod from the Service's endpoints. Nothing is restarted.
  • The startup probe asks "has the application finished starting?" Until it succeeds, Kubernetes does not run the other two probes at all.

The consequences are what matter. Liveness restarts. Readiness routes. Startup gives time.

Spring Boot answers these questions through Actuator, its built-in module for health and metrics endpoints. Actuator exposes /actuator/health, and inside it two health groups: /actuator/health/liveness and /actuator/health/readiness. A health group is a named subset of health checks with its own URL. Boot turns these two groups on by default.

The readiness group does something useful by itself. When graceful shutdown begins, readiness switches to "not ready", while liveness stays "alive". That is the right answer to both questions at once: the pod is fine, but it should not receive new work.

Payouts' old manifest pointed both probes at the same endpoint. That asks one question and uses the answer for all three purposes. A pod that is alive but still warming up looks ready and gets traffic too early. A pod that is draining at shutdown looks dead, so the liveness probe may restart it in the middle of finishing its requests. In .NET terms this is like mapping ASP.NET Core's health checks to a single /health URL and pointing every probe at it, instead of tagging checks and mapping separate /health/live and /health/ready endpoints.

The startup probe exists because a Spring application can take a while to start, especially on a busy node. Without one, the liveness probe starts checking immediately, sees nothing answering, and kills the pod for being slow. The companion manifest gives the startup probe up to 5 minutes, which is generous on purpose.

Stop: the handoff no probe covers

Bea's 12 failures came from the third handoff, stopping the old pod. Here is the sequence that dropped them, and then the fix.

When Kubernetes decides to stop a pod, it starts two things at the same moment. The Kubernetes documentation says so in nearly those words.

  • On the pod: the kubelet, the agent that runs containers on each machine, sends SIGTERM to the container's main process. Spring receives it and begins graceful shutdown. Readiness goes false, and the web server stops accepting new connections.
  • On the network: the control plane removes the pod from the Service's endpoints. That change then has to reach every machine in the cluster. On each machine a component called kube-proxy keeps the routing rules that send traffic for payouts-api to a particular pod. Each one updates on its own schedule.

On Sorrel's cluster the network side took about a second. During that second, some machines still routed new requests to a pod whose server had already stopped accepting them. That is where the connection resets and 502s came from. Graceful shutdown could not help, because those requests never reached the application. They hit a closed door.

The fix is a preStop hook. A preStop hook is a command Kubernetes runs inside the container before it sends SIGTERM. The usual hook is a sleep:

lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]

Now the order changes. The network side starts removing the pod from the endpoints. Meanwhile the pod sleeps for 5 seconds, still serving every request that reaches it. By the time the sleep ends and SIGTERM arrives, every kube-proxy has caught up, and no new request is on its way. Only then does Spring begin its graceful shutdown and finish the requests already in flight.

The sleep looks like a hack, and people often call it one. It is the only way the pod has of waiting for a system it cannot see. There is no event inside the container that says "every proxy has stopped sending you traffic".

.NET has the same gap. An ASP.NET Core app uses IHostApplicationLifetime.ApplicationStopping to drain on SIGTERM, and it still needs a preStop sleep in the manifest, for the same reason.

The arithmetic of the grace period

The sleep has a cost, and the cost is time. Two settings decide how much time a stopping pod has.

  • terminationGracePeriodSeconds is set on the pod in the manifest. It is the total time Kubernetes allows from the start of termination until it kills the container outright with SIGKILL, which cannot be caught. The default is 30 seconds. Crucially, the preStop hook's time counts against it.
  • spring.lifecycle.timeout-per-shutdown-phase is set in Spring's configuration. It is how long graceful shutdown waits for in-flight requests to finish before giving up. The default is also 30 seconds.

Now add them up for the old manifest with a 5-second hook added:

  • preStop sleep: 5 seconds
  • Spring's graceful shutdown: up to 30 seconds
  • Total needed: 5 + 30 = 35 seconds
  • Grace period allowed: 30 seconds

So Spring could still be finishing a request when the 30 seconds ran out and SIGKILL arrived. A slow request would be cut off in the middle.

The rule is that the grace period must be longer than the hook plus the shutdown timeout. Sorrel's numbers became:

  • preStop sleep: 5 seconds
  • Spring's shutdown timeout: 20 seconds
  • Total needed: 5 + 20 = 25 seconds
  • Grace period: 40 seconds, leaving 15 seconds of margin

The 20 seconds for Spring is not arbitrary. The ledger client already has a 2-second read timeout (chapter 11 set it, after a slow ledger stopped Payouts). No Payouts request should still be running after 20 seconds unless something is badly wrong.

Remember it as: a deploy is three handoffs, start, ready, stop; the pod must wait for the cluster to notice, and the grace period must outlast the wait.

Start: the rolling update's two numbers

The last setting controls how many pods are replaced at a time. A rolling update has two knobs:

  • maxUnavailable: how many pods may be missing below the desired count during the update. The default is 25%, and Kubernetes rounds it down.
  • maxSurge: how many extra pods may be created above the desired count. The default is also 25%, and Kubernetes rounds it up.

Work them through for Payouts' 2 pods. 25% of 2 is 0.5. Rounded down, maxUnavailable is 0. Rounded up, maxSurge is 1. So on 2 pods the defaults happen to do the safe thing: start 1 new pod, wait until it is ready, then stop 1 old one.

Nobody chose those numbers, though. Scale the same deployment to 4 pods and 25% of 4 is 1, so 1 pod may be down at a time and capacity drops by a quarter during each deploy. The manifest has not changed, and the behaviour has.

Setting maxUnavailable: 0 and maxSurge: 1 explicitly says what the team wants at any size. Kubernetes always starts the new pod first and removes an old one only when the new one is ready. The cost is one extra pod's memory for about a minute per deploy. Capacity never drops.

When the rule bends

A preStop sleep is not free, and it is not always needed. Every pod now takes at least 5 seconds longer to stop. On a deployment of 50 pods rolled one at a time, that adds minutes to every deploy. A service that takes no traffic through a Kubernetes Service, such as a batch job reading a queue, gains nothing from it. For those, leave the hook out and say why in a comment.

Sam's decision

Sam held the review with Bea and Oren in the room, and told the team:

  • A 5-second preStop sleep on every Payouts service. Routing takes about a second to catch up, and the pod has no other way to wait for it.
  • A 40-second grace period, and Spring's shutdown timeout down to 20. The hook plus the shutdown must fit inside the grace period, with room to spare.
  • Separate readiness and liveness probes on Boot's health groups, plus a startup probe. Three questions get three answers.
  • maxUnavailable: 0 and maxSurge: 1, written down. The safe behaviour should not depend on rounding.
  • Aisha writes a deploy test on the kind cluster. It sends requests continuously through a rollout and counts failures. The count must be 0 before the change merges. (kind is "Kubernetes in Docker", a whole cluster running in containers on a laptop.)
  • Bea keeps her retries for one more month, then takes them out. By then the deploy test will have shown whether any failures remain, on Payouts' side where they belong.

"We weren't wrong about shutdown," Sam said. "We were wrong about who else had to be told."

Bea asked, politely, whether Boot's graceful shutdown had been doing anything at all. It had, Sam said: it finished every request that reached it. The dropped ones had never reached it.

The deploy test counted 0 on the third try. The first two runs found a load balancer timeout that was shorter than the hook.

kubectl -n payouts run load --rm -i --restart=Never --image=curlimages/curl:8.12.1 -- \
  sh -c 'for i in $(seq 1 300); do curl -s -o /dev/null -w "%{http_code}\n" --max-time 2 http://payouts-api/actuator/health/readiness; sleep 0.2; done' \
  | sort | uniq -c &
sleep 15; kubectl -n payouts rollout restart deploy/payouts-api && kubectl -n payouts rollout status deploy/payouts-api; wait

port-forward connects a port on your laptop to the Service inside the cluster. kubectl run load --rm -i --restart=Never starts a throwaway pod that runs the loop and is deleted when it finishes. --max-time 2 makes curl give up after 2 seconds, so a hung request counts as a failure (status 000). rollout restart replaces every pod with a fresh one, which is a deploy without a new image, and rollout status waits until it is done. A safe manifest shows 300 lines of 200 and nothing else.

⚠The traps
  • One probe for every question: the sign is readiness and liveness pointing at the same endpoint. A draining pod looks dead and may be restarted mid-request, and a slow-starting pod looks ready and gets traffic too early. Point each probe at its own Boot health group.
  • No preStop: the sign is graceful shutdown switched on in the application and no hook in the pod's manifest. The application drains correctly while some nodes are still routing new requests to it, and those requests hit a closed port. Add a short sleep.
  • Grace period equal to the shutdown timeout: the sign is 30 seconds in the manifest and 30 seconds in Spring. The hook's time counts against the grace period, so Kubernetes kills the pod while Spring is still finishing a request. Make the grace period larger than the hook plus the shutdown timeout.
  • Default rolling update on two pods: the sign is a deployment with no maxUnavailable or maxSurge. On 2 pods the 25% defaults round to 0 unavailable and 1 extra, which is safe by accident. Scale up and the same manifest starts taking pods away during deploys. Write the numbers down.
  • The retry on the other side: the sign is a partner team retrying your deploy failures for you. The failures are real and they are yours, and the retry hides them from your dashboards. Count them yourself, then ask the partner to remove the retry.
✎At the whiteboard
  1. During a rollout, how long does our cluster take to stop routing to an old pod, and is our preStop sleep longer than that?
  2. Do readiness, liveness and startup point at three different health checks?
  3. Is our grace period larger than the preStop sleep plus Spring's shutdown timeout?

Still argued: is a preStop sleep sound design or a workaround? One side, argued in the Kubernetes issue tracker over many years, says it is a workaround. A fixed sleep guesses how long routing takes to update, a busy cluster can take longer, and the right fix is for Kubernetes to finish removing the pod from routing before it sends the signal. The other side, held by most operators and reflected in Kubernetes's own documentation on pod termination, says it is sound. There is no event a pod can wait for, a short sleep is cheap and visible in the manifest, and a platform fix that has not shipped is not a plan. Sorrel sleeps for 5 seconds and checks that guess on its own cluster, which the deploy test does on every run.

What Sam learned

  • Readiness, liveness and startup are three questions with three consequences, so give each its own probe and its own health group.
  • The application's graceful shutdown cannot wait for the cluster to stop routing to it, so add a preStop sleep and make the grace period cover the sleep plus the shutdown.
  • Count the failures during a rollout in a test, before and after the change, because a partner team's retries are not a measurement.

The problem

The quarter had three weeks left. On a quiet Tuesday Sam started payouts-api on a laptop with Spring Boot's debug flag switched on, because nobody on the team ever had. The flag makes Boot print a conditions report at startup. The report lists every piece of configuration Boot considered while starting the application, and for each one, whether Boot applied it and why.

It ran to 400 lines. Most were dull. One was not:

TransactionAutoConfiguration.EnableTransactionManagementConfiguration:
   Did not match:
      - @ConditionalOnBean (types: org.springframework.transaction.TransactionManager;
        SearchStrategy: all) did not find any beans of type
        org.springframework.transaction.TransactionManager (OnBeanCondition)

In plain words: Boot had not switched on its transaction handling, because the application had no transaction manager. A transaction manager is the object that actually begins, commits and rolls back database transactions. Without one, nothing can open a transaction.

A month earlier Sam had written @Transactional on the markPaid method in PayoutService. @Transactional is the Spring annotation that says "run this method inside a database transaction". Sam had added it by .NET reflex. In .NET a unit of work that changes data gets a TransactionScope or a BeginTransaction() around it, and the annotation felt like the Java way of writing the same thing.

Sam asked the team how that method had been working, and admitted the awkward part first. "I wrote that after we agreed one document, one write, no transaction. It was my rule. My hands wrapped it in a transaction anyway."

Rafael, the senior developer, eight years at Sorrel and the person who knows Spring's habits best, answered.

"Spring Data Mongo doesn't make a transaction manager," he said. "You declare one if you want one. With no manager, that annotation has nothing to run with. It can't have done anything."

Spring Data MongoDB is the library Payouts uses to talk to its database. Rafael was right. Its reference documentation says that unless you declare a MongoTransactionManager, "transaction support is DISABLED".

Aisha, the junior developer, two years in, went further. She follows a call before she trusts a description of it. She opened PayoutService and found who called markPaid. It was another method in the same class, the one that handles the ledger's confirmation callback. Spring applies @Transactional through a wrapper object that sits in front of PayoutService. Only calls that come in from outside pass through the wrapper. A call from one method of PayoutService to another never meets it.

So there were two independent reasons, and either was enough on its own. Boot switches on transaction support only when a transaction manager bean exists. Payouts has none, so every @Transactional in the service is ignored. Separately, markPaid was called from inside its own bean, so even with a transaction manager the wrapper, which Spring calls a proxy, would never have seen the call. Meanwhile the test from chapter 8, which checks that a stale copy of a payout cannot overwrite a fresh one, had passed all along. It passed because the document's version check was doing the work, not the transaction.

"So the framework silently ignored an annotation I wrote," Sam said. "Twice over."

"It told us about the first one," Aisha said. She pointed at the line in the conditions report. Then she opened a stack trace from a test of markPaid. Between the caller and the method there was no transaction interceptor at all, which proved the annotation had never run. The second reason she had found by reading the code: one method in the class calling another on this.

Sam had spent twelve years with frameworks that did less and said more. Sam said the thing a lead is not supposed to say in the third month: "I do not trust what I cannot see."

Rafael's view was that Spring had behaved exactly as documented. Sam's view was that documented was not the same as visible. Both were true. The annotation had looked like a guarantee, and it was neither a transaction nor a warning.

The idea

Spring is three mechanisms, and each of them keeps a record.

1. The container: who creates your objects

Start with a plain class, the way Payouts writes them:

@Service
public class PayoutService {
    private final PayoutRepository repository;
    private final Clock clock;

    public PayoutService(PayoutRepository repository, Clock clock) {
        this.repository = repository;
        this.clock = clock;
    }
}

Nobody in the codebase ever writes new PayoutService(...). Spring does it. At startup Spring scans for classes marked @Service, @Component and similar, creates one instance of each, and passes each one the other objects its constructor asks for.

The part of Spring that does this is the container. Each object it creates and manages is a bean. The container also manages each bean's lifecycle: it creates the bean, injects its dependencies, calls any start-up methods, and at shutdown calls any clean-up methods and discards it.

This is the same job IServiceCollection and IServiceProvider do in ASP.NET Core. The difference is how beans are registered. In .NET you usually register each service by hand in Program.cs with AddScoped or AddSingleton. Spring finds most of them by scanning, and Boot adds many more without being asked, which is the second mechanism.

The record: Actuator, Spring Boot's module of built-in operational endpoints, has a /actuator/beans endpoint. It lists every bean in the running application, with its name, its type and the configuration that created it.

2. Auto-configuration: what Boot decides to create

Boot ships a long list of configuration classes, each of which can create beans. Only some of them should apply to any given application. A service that uses MongoDB needs a MongoDB client. A service that does not, does not.

Boot decides with conditions. Each auto-configuration class is guarded by @Conditional annotations, which say when it applies. Here is the shape of one:

@AutoConfiguration
@ConditionalOnClass(MongoClient.class)    // only if the MongoDB driver is on the classpath
public class MongoAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean             // only if you have not declared your own
    public MongoClient mongo(MongoProperties properties) { ... }
}

The common conditions are:

  • On a class being present: apply only if a certain library is on the classpath, the set of jars the application was started with.
  • On a bean being missing: apply only if the application has not already declared its own bean of that type. This is how you override Boot: declare your own, and Boot steps aside.
  • On a bean being present: apply only if some other bean exists.
  • On a property: apply only if a setting in application.yaml has a certain value.

This whole arrangement is auto-configuration. It is why adding one dependency to a POM can change what the application does at startup. The classpath itself is configuration.

At startup Boot evaluates every condition and keeps a report of the results. Run the application with --debug and Boot prints the report in full, in two lists:

  • Positive matches: every auto-configuration that applied, with the condition that let it.
  • Negative matches: every one that did not, with the reason.

The line Sam found was in the second list. Boot's transaction support carries a condition "on a bean being present": it switches on only if a TransactionManager bean exists. For a MongoDB service that is not true by default. Boot wires up the MongoDB client and the repositories, and leaves the transaction manager to you.

The record: the conditions report. It had been printing that line, for anyone who asked, for the whole life of the service.

3. Proxies: how annotations do their work

The third mechanism explains the self-invocation, and it is the one most worth understanding.

An annotation in Java is only a label. @Transactional on its own does nothing, in the same way a C# attribute does nothing until some code reads it. Something has to read the label and act on it. In Spring, that something is a proxy.

A proxy is a wrapper object that Spring creates around your bean. It has the same methods as your bean. When Spring hands PayoutService to another bean, such as the controller, it hands over the proxy instead of the real object. A call from the controller arrives at the proxy first. The proxy opens the transaction, calls the real method, then commits or rolls back.

The same trick powers @Cacheable, which checks a cache before calling the method. It also powers the resilience annotations such as @CircuitBreaker, which chapter 11 put on the ledger client to count its failures. In .NET, interception libraries such as Castle DynamicProxy work the same way, though ASP.NET Core does not use them for transactions.

Now the rule that follows, the one Sam fell over. Here is the shape of the code Aisha found:

@Service
public class PayoutService {

    public void confirmFromLedger(String payoutId) {
        // ... check the callback ...
        markPaid(payoutId);              // really this.markPaid(payoutId)
    }

    @Transactional
    public Payout markPaid(String payoutId) { ... }
}

The controller calls confirmFromLedger through the proxy. That method has no annotation, so the proxy just passes the call on. Inside the real object, confirmFromLedger calls markPaid. That call goes to this, the real object, not to the proxy. The proxy never sees it, so no transaction opens.

This is the self-invocation trap: a call from one method of a bean to an annotated method of the same bean bypasses the proxy, so the annotation does nothing. Spring's own documentation describes it plainly. No compiler catches it, and no warning is printed.

The fix is structural. The annotated method must be called from a different bean, so that the call crosses the proxy. In practice that means moving the caller, or the annotated method, into its own class. The boundary the annotation marks then becomes a real boundary between two objects.

The record: a stack trace. When the proxy did its work, the stack trace shows the interceptor's frames sitting between the caller and your method. When it did not, they are absent. Aisha's stack trace had none. Their absence proves the annotation never ran, but not why: a missing transaction manager and a call on this leave the same empty trace. The why comes from the conditions report and from reading the call.

Reading the records

What makes the three mechanisms trustworthy is that each one tells you what it did:

Mechanism What it does Where its record is
Container creates and wires beans /actuator/beans
Auto-configuration decides which beans Boot adds the conditions report, from --debug
Proxy applies annotations to calls from outside the stack trace, with or without interceptor frames

Read the three records once for each service when you inherit it, and again whenever anything surprises you.

Remember it as: Spring is a container, auto-configuration and proxies, and each keeps a record; the magic is only the part you have not read.

When to override, and when not

Auto-configuration is a default, and overriding it is normal. Declaring your own bean of a type makes Boot's version step aside, and that is the supported way to change behaviour. Excluding an auto-configuration outright is also allowed, and sometimes right: a library may drag in a component the service must not run. But exclude only after reading the condition that switched it on, and write the reason beside the exclusion. An exclusion made because something "looked odd" can remove the very thing a later change needs, such as transaction support on the day the service first needs a real transaction.

Sam's decision

On the Wednesday of the last week of the quarter, Sam told the team:

  • Everyone reads the conditions report and the beans list of one service they own, this month. Each person writes down the 3 things in it they did not expect. Until this week, nobody had opened either.
  • Self-invocation of an annotated method is a review rule, with the diagram above pinned beside it. The compiler will never catch it, so a reviewer has to.
  • markPaid loses its annotation. It writes one document, and chapter 8's rule for that is one write and no transaction. The version check already protects it, and the chapter 8 test proves that.
  • No transaction manager is declared until the first real transaction needs one. That will be the day two documents must change together. On that day the transactional method lives on a bean that is called from another bean, the report line flips to a match, and a test checks that the transaction actually opened.
  • Tests assert the effect of an annotation, never its presence. A test that checks a method is annotated proves nothing about what happens at runtime.

"I said I didn't trust what I couldn't see," Sam said. "It turns out I could see all of it. I just hadn't looked."

◷How we got hereIn October 2002 Rod Johnson published a book called Expert One-on-One J2EE Design and Development.

In October 2002 Rod Johnson published a book called Expert One-on-One J2EE Design and Development. J2EE was the official Java platform for enterprise applications at the time. On the surface the book explained how to use it. In practice it argued that much of it should be avoided, because it made simple things heavy.

The book came with 30,000 lines of framework code. Johnson wrote the code to show that an application could be built from plain objects, wired together by a container. Services such as transactions would be applied around those objects from outside, instead of being inherited from heavyweight base classes.

Two readers, Juergen Hoeller and Yann Caroff, persuaded Johnson to make that code the basis of an open-source project. Caroff suggested the name. He chose Spring because it stood for "a fresh start after the 'winter' of traditional J2EE". The first public release, 0.9, appeared on 25 June 2003. Version 1.0 followed on 24 March 2004.

Johnson and Hoeller stated the protest most plainly in their next book, J2EE Development without EJB, in 2004. EJB, Enterprise JavaBeans, was the heavyweight component model of J2EE. They wrote: "J2EE orthodoxy makes heavy work of many simple problems. Indeed it sometimes seems that the J2EE industry is committed to the belief that there are no simple problems."

Every mechanism in this chapter is that protest turned into code:

  • The container exists so that your objects can be plain classes.
  • Proxies exist so that a transaction can be declared on a plain method, rather than inherited from a framework base class.
  • Auto-configuration, which arrived about a decade later with Spring Boot, exists so that nobody has to write the wiring by hand.

What Sam distrusted on a Tuesday was a framework built from the start to do more, so that application code could do less. It was also a framework that had always written down what it did, so that the trade could be checked.

⚠The traps
  • Self-invocation: the sign is an annotated method called from another method of the same class. The call goes to this, not through the proxy, so the annotation silently does nothing. Move the annotated method or its caller into a separate bean.
  • The report nobody reads: the sign is a conditions report of hundreds of lines that no one on the team has ever opened. Every surprise in it was announced at every startup. Read it once per service, and again after any dependency change.
  • Excluding what you do not understand: the sign is an auto-configuration excluded because it looked odd. The exclusion may remove something a later change needs, such as transaction support. Read the condition first, and write the reason beside any exclusion.
  • A bean by accident, or by absence: the sign is a component Spring created because some library happened to be on the classpath, or one it did not create because nobody declared it. The conditions report says which happened and why.
  • Trusting the annotation over the trace: the sign is a test that checks a method carries @Transactional rather than checking that a transaction opened. An annotation is a label, and only its effect is evidence. Assert the effect.
✎At the whiteboard
  1. Has anyone on the team read this service's conditions report in the last quarter, and did anything in it surprise them?
  2. Is any annotated method in this service called from another method of its own class?
  3. For each @Transactional or @Cacheable in this service, is there a test that checks the effect rather than the annotation?

Still argued: should a framework do this much on your behalf? The case against has been made since Spring's early years by people who prefer lighter frameworks and wiring written out by hand. A framework that creates beans you did not ask for, and applies behaviour you cannot see in the code, has traded understanding for convenience, and the bill arrives on the first surprising Tuesday. The case for is Johnson's argument from 2002, restated by the Spring Boot team in 2014. Without it every team writes the same wiring by hand, less well, and a framework that records every decision is easier to check than thousands of lines of hand-written configuration that record none. Sorrel's answer is a habit rather than a side: read the report, test the effects, and keep the diagram pinned up.

What Sam learned

  • Spring is a container, a set of guarded auto-configurations and a set of proxies, and each of the three keeps a record you can read: the beans list, the conditions report and the stack trace.
  • An annotation on a method called from inside its own class does nothing, because the proxy only sees calls from other beans, so check who calls every annotated method.
  • Distrusting a framework is fine on the first day, but by the ninetieth the job is to know how to ask it what it did.

The fifteen decisions

An architecture decision record, or ADR, is a short note that records one decision: why it was needed, what was decided, and what followed. Michael Nygard set out the shape in 2011. Sam's records keep his shape and add two parts: who turned out to be right, and the condition under which the decision should be reopened. Each record has five labelled parts:

  • Context: what happened, and the argument it caused.
  • Decision: what Sam decided, one item per line.
  • Consequences: what followed.
  • Who was right: said plainly, including when it was not Sam.
  • Reopen when: the condition that should start the argument again, so nobody has it from memory.

ADR 1: One parent, one release, one Boot

Context. The team said it ran Java 21. One of its three services ran Java 11. The payouts-reports module overrode the parent POM's Java release, setting it back to 11, and also pinned its own older Spring Boot version. Neither override had a comment.

Decision.

  • Every module inherits sorrel-parent.
  • Any override of a parent property carries a comment with a reason and a date.
  • A pull request that changes a POM shows the effective POM before and after.
  • payouts-reports moved to Java 21 immediately, and moves to Java 25 with everyone else.

Consequences. Overrides are now visible and rare. Moving the least-understood module last cost a week and caused no incidents.

Who was right. Rafael, that the parent said 21. Aisha, that it did not matter what the parent said.

Reopen when a module has a documented reason to stay behind for more than one quarter.

ADR 2: Every dependency through the artifact repository

Context. Half of Sorrel's builds downloaded libraries straight from Maven Central, the public repository. Nobody could say where a given jar had come from.

Decision.

  • All downloads go through the company's Nexus mirror, set in every settings.xml and on every build runner.
  • The Maven wrapper is committed to the repository.
  • The build's output timestamp is set, so builds are reproducible.
  • CI caches the local repository, keyed on a hash of the POMs.
  • The platform team publishes an uptime figure for the mirror and a written fallback.

Consequences. The nightly build stopped spending 4 minutes downloading, and settled at 9 minutes with a warm cache (chapter 4 took it further). Every library now arrives by one route, and that route has a stated condition for failure.

Who was right. Oren, on the mirror. Rafael, that the mirror is a single point of failure.

Reopen when the Nexus misses its stated uptime for 2 months in a row.

ADR 3: Boot 4 is a project, not a version

Context. Spring Boot 3.5 had been out of open-source support since June. Someone proposed upgrading to Boot 4 by changing one line.

Decision.

  • Make an inventory first: every dependency pinned outside Boot's BOM, its Boot 4 compatible version, and whether one exists.
  • The best-tested service moves first and runs beside the old version.
  • Then the rest follow.

Consequences. A week of making the list. One service moved, and its tests caught 2 behaviour changes. The parent POM changed last.

Who was right. Rafael, on the urgency. Aisha, on how long the list would be.

Reopen when the next major version ships. Use this record as the template.

ADR 4: Maven stays; Gradle is revisited on a measurement

Context. A Gradle branch built in 3 minutes 40 seconds, against 9 minutes 10 seconds on Maven.

Decision.

  • Measure each stage of the build before changing tools.
  • Turn on parallel module builds, and forked, reused test JVMs, in the parent POM.
  • Reconsider Gradle when compilation is more than half of a build that takes longer than 10 minutes.

Consequences. The Maven build came down to 4 minutes 5 seconds. The condition is written here so the meeting is never held from memory.

Who was right. Rafael, that the build was slow. Oren, that the slow part was the tests.

Reopen when the written condition is met.

ADR 5: No new Lombok, records for values, no forced removal

Context. On day 9 Sam banned Lombok, by analogy with .NET. The codebase had 306 classes using it, and the first migration pull request was 4,000 lines long.

Decision.

  • The ban was withdrawn, in the same place it was announced.
  • Lombok stays in the parent POM.
  • New classes do not use it.
  • Values and documents that are touched for any reason become records.
  • There is no migration ticket.
  • Kotlin was declined, because adopting it pulls a team towards Gradle.

Consequences. A week of noise, then a count of Lombok classes that keeps shrinking. It was the lead's first public reversal.

Who was right. Rafael: "we could have just stopped adding it."

Reopen when the Lombok count falls below 50. At that point, removing the rest is one pull request.

ADR 6: A test names its one real object

Context. Test coverage was 84%, but 61 tests mocked the very class they claimed to test, so they could not fail.

Decision.

  • The test template that produced them was deleted.
  • Every test names the real object it exercises.
  • Slice tests for controllers and repositories, one full-application test per service.
  • Mocks at the boundary: the ledger and the bank. The repository is real wherever the test is about data.
  • Coverage is reported honestly, and the conversation about the coverage gate goes to the platform team.

Consequences. Coverage fell to 71%, and the number now means something. 2 minutes of tests became 40 seconds.

Who was right. Aisha, first.

Reopen when a slice test cannot express a test the team needs. That has not happened.

ADR 7: A feature contract for DocumentDB, owned and dated

Context. The Testcontainers suite ran green against real MongoDB. Production ran DocumentDB 5.0, which refused retryable writes. The lead had approved the change.

Decision.

  • Keep a feature contract: a list of every operator, aggregation stage, index type and driver option the code uses.
  • Check each line against Amazon's supported list for the engine version Sorrel runs, with a date on each line.
  • A test asserts the driver options.
  • A nightly run goes against a real DocumentDB instance.

Consequences. One compatibility gap was found in the first month, in a pull request rather than on a Friday.

Who was right. Rafael, that MongoDB and DocumentDB were only "mostly" the same. The lead was wrong to approve the change.

Reopen when Sorrel moves to engine 8.0. Then every line is checked again.

ADR 8: Let the database refuse

Context. Two pods paid the same claim. The annotation meant to create a unique index had never created one.

Decision.

  • @Version goes on every document that is updated after it is created, and a version failure is treated as a retry.
  • Transactions only where two documents must agree, which today is nowhere.
  • The ledger write goes through an outbox.

Consequences. The duplicate path is tested with 2 threads.

Who was right. Aisha, on the index. Rafael, that a transaction will one day be needed.

Reopen when a second document has to change together with a payout.

ADR 9: The image is the list

Context. The security scanner reported 41 findings. One was critical, in a transitive jar nobody had heard of, 4 levels down the dependency tree.

Decision.

  • Versions of critical libraries are managed in the parent POM.
  • The dependency-check plugin runs in the build and fails it at the critical threshold.
  • Its suppression file requires a reason and a review date for every entry.
  • A triage document has one line per finding, saying whether the code is reachable, with a date.

Consequences. The next critical finding failed a build on a Tuesday, instead of arriving by email on a Friday.

Who was right. Oren: the scanner reads jars.

Reopen when the suppression file has more than 20 entries. That is the sign the gate is being worked around.

ADR 10: No version moves without a commit

Context. The platform team published a new sorrel-commons snapshot on a Saturday, with a public method renamed. Monday night's build was the first to pick it up, and the team found the failure on Tuesday morning. The same dependency tree held a version range written in 2022 and a module override older than the parent's pinned version.

Decision.

  • The enforcer plugin runs in the parent POM. requireUpperBoundDeps runs on every build. requireReleaseDeps runs in the release-checks profile, which the pipeline switches on for main.
  • SNAPSHOT versions only on branches.
  • The 2022 version range is replaced by hand with one fixed version, because no enforcer rule catches a range.
  • The module's own older version is deleted.
  • dependency:analyze runs as a warning for a month, then as a failure.
  • The platform team releases sorrel-commons every 2 weeks.

Consequences. 2 enforcer failures on the first day, both fixed that day: the snapshot (requireReleaseDeps) and the downgraded transitive library (requireUpperBoundDeps). None since.

Who was right. Rafael, on the breakage. Oren, that teams need fixes fast, which is what the 2-week releases are for.

Reopen when the 2-week release schedule slips and teams start asking for snapshots on main again.

ADR 11: Every outbound call has a timeout before it has anything else

Context. The ledger slowed to 30 seconds per call. Payouts had no timeouts and a client that retried, so it stopped entirely and tripled the ledger's load.

Decision.

  • Connect timeout 1 second and read timeout 2 seconds, on every call, including the call that fetches the access token.
  • Retries only on idempotent calls, with exponential backoff and jitter, within a budget.
  • A circuit breaker and a bulkhead on the ledger, with the breaker's state exposed as a metric.
  • A contract test with Bea's team, in both teams' pipelines.

Consequences. The next ledger stall failed payouts within 2 seconds and kept the pods up.

Who was right. Bea.

Reopen when a dependency's measured latency makes the fixed numbers wrong twice in a quarter. Then adaptive limits are considered.

ADR 12: Virtual threads before any rewrite

Context. Rafael proposed rewriting on WebFlux, with a graph of blocked threads as the evidence.

Decision.

  • Switch on spring.threads.virtual.enabled.
  • Repeat the ledger stall in a test.
  • Delete the thread-pool ceiling set in 2019.
  • Reconsider WebFlux only for a genuine stream.

Consequences. By Friday the wall on the graph was gone. Rafael closed his own proposal.

Who was right. Rafael, that blocking was the symptom. The JDK, on the cure.

Reopen when a service is a stream that needs backpressure, or pinning in native code is found under load.

ADR 13: Size memory from a native memory report

Context. A pod was killed at 02:14 with exit code 137 and nothing else. The heap was set to 75% of a 512 MiB limit.

Decision.

  • Measure the footprint on a pod under load, with native memory tracking switched on.
  • Set the heap from the measurement, with the arithmetic in a comment in the manifest.
  • Remove the percentage flag.
  • Add -XX:+ExitOnOutOfMemoryError to the image, so the JVM exits at the first OutOfMemoryError with a short message naming the cause, instead of limping on or dying silently.
  • Set the memory request equal to the limit.
  • Alert on container memory at 90% of the limit.

Consequences. The measurement said 640 MiB with headroom, and Oren gave it 768 MiB, with a reason. No pod has died at night since.

Who was right. Oren: "I give it more when someone tells me what it needs."

Reopen when the measured non-heap footprint changes by more than a fifth after an upgrade.

ADR 14: A deploy waits for the cluster to notice

Context. About 12 ledger callbacks a week failed, all in the 3 minutes around a Payouts deploy. Boot's graceful shutdown was on, and it did everything except wait for the cluster to stop routing traffic to the pod.

Decision.

  • A 5-second preStop sleep.
  • A 40-second grace period, over a 20-second Spring shutdown timeout.
  • Readiness, liveness and startup as three separate probes on Boot's health groups.
  • Zero pods unavailable and one extra pod during a rolling update.
  • A deploy test that counts failures during a rollout, and must count 0.

Consequences. The test counted 0 on the third try. Bea removed her retries.

Who was right. Oren: "It's always a race. Nothing in that manifest tells the pod to wait."

Reopen when the measured endpoint propagation time on Sorrel's cluster is longer than the sleep.

ADR 15: Read the report, assert the effect

Context. Sam's @Transactional on markPaid had never opened a transaction, for two reasons. The service had no transaction manager, so Boot never switched its transaction handling on. And markPaid was called from another method in the same class, so even with a transaction manager the proxy that applies the annotation would never have seen the call. The two reasons were independent, and either was enough on its own. Sam had added the annotation by .NET reflex, after agreeing in chapter 8 that one document is one write and needs no transaction.

Decision.

  • Every engineer reads the conditions report and the beans list of one service they own, and records 3 surprises.
  • Self-invocation of annotated methods is a review rule, with the diagram pinned up.
  • markPaid loses its annotation. It writes one document, and the version check from chapter 8 already protects it.
  • No transaction manager until two documents must change together. From then on, a transactional method lives on a bean that is called from another bean.
  • Tests assert the effect of an annotation, never its presence.

Consequences. 4 surprises were found in the first month. One was a bean nobody wanted, and one a bean nobody had declared.

Who was right. Rafael, that Spring behaved as documented. Aisha, who found the second reason by reading the call rather than the annotation.

Reopen when the framework stops logging what it did, which it has not done in 23 years.

Glossary

Each entry says what the term means in plain words and names the chapter that explains it.

  • Actuator. Spring Boot's module of built-in operational endpoints, such as /actuator/health, /actuator/beans and the circuit breaker's state. Chapters 11, 14, 15.
  • Annotation processor. A plug-in to the Java compiler that reads annotations and generates code during the build. Lombok works this way. Chapter 5.
  • Artifact repository. The company's own server for jars and other build outputs. It stands in front of Maven Central and keeps a copy of everything downloaded, so it is the one place every dependency can be counted. Sorrel's is a Nexus. Chapter 2.
  • Auto-configuration. Spring Boot's long list of configuration classes, each applied only when its conditions hold, such as "this library is on the classpath" or "you have not declared your own bean". The conditions report says which applied. Chapter 15.
  • Bean. An object that Spring's container creates, wires to its dependencies and manages from startup to shutdown. Chapter 15.
  • BOM. A bill of materials: a special POM whose only content is a list of library versions known to work together. You import it into dependencyManagement to adopt the whole list. Spring Boot publishes one. Chapters 1, 10.
  • Bulkhead. A cap on how many calls to one dependency can be in flight at once, so a slow dependency cannot use up every thread. Chapter 11.
  • Carrier thread. One of the small number of ordinary platform threads that virtual threads run on. A virtual thread is mounted on a carrier while it runs and unmounted while it waits. Chapter 12.
  • Circuit breaker. A record of recent failures in calls to a dependency. Once failures cross a threshold, the breaker fails new calls immediately for a while, then lets a few through to test whether the dependency has recovered. Chapter 11.
  • Conditions report. The report Spring Boot prints at startup when run with --debug. It lists every auto-configuration that applied and every one that did not, with the reason for each. Chapter 15.
  • Container awareness. The JVM reading the container's memory and CPU limits, rather than the whole machine's. It has been the default since JDK 10. Chapter 13.
  • Dependency management. The dependencyManagement section of a POM. It fixes the version of a library for every module that uses it, without adding the library to any module. Chapters 1, 9, 10.
  • DocumentDB. Amazon's database service that offers the MongoDB API on top of Amazon's own engine. It supports a published list of MongoDB features, which differs by engine version. Chapter 7.
  • Effective POM. A module's POM with its parent, imported BOMs and its own overrides merged into one file. It is the only POM that shows what the module really uses. help:effective-pom prints it. Chapter 1.
  • Enforcer. The Maven plugin that fails the build when a rule is broken, such as "no SNAPSHOT dependencies" or "no version lower than another dependency asked for". Chapter 10.
  • Feature contract. Sorrel's owned, dated list of every database feature the code uses, checked line by line against what production's DocumentDB supports. Chapter 7.
  • Graceful shutdown. An application, when told to stop, refusing new requests and finishing the ones in flight before it exits. Spring Boot does it by default since 3.4. Chapter 14.
  • Health group. A named subset of Actuator's health checks with its own URL. Boot provides two for Kubernetes: /actuator/health/liveness and /actuator/health/readiness. Chapter 14.
  • Heap. The memory where a Java program's objects live, managed by the garbage collector. Its maximum size is set with -Xmx or a percentage flag. The JVM also uses memory outside the heap, and the container limit covers both. Chapter 13.
  • Idempotency key. A value sent with a request so that sending the same request twice has the same effect as sending it once. Sorrel enforces it with a unique index. Chapter 8.
  • kind. "Kubernetes in Docker": a tool that runs a whole Kubernetes cluster inside containers on a laptop. The book's cluster commands run against it. Chapters 13, 14.
  • Liveness probe. A check Kubernetes runs to ask "is this process still working?" If it fails repeatedly, Kubernetes restarts the container. Chapter 14.
  • Local repository. The folder on your machine, ~/.m2/repository, where Maven keeps a copy of every library it has downloaded or built. It works like the NuGet packages folder. Chapters 1, 2.
  • Maven wrapper. mvnw: a small script committed to the repository that downloads and runs the exact Maven version the repository names, so every machine builds with the same Maven. Chapter 2.
  • Metaspace. The JVM's memory for information about loaded classes. It sits outside the heap but inside the container's memory limit. Chapter 13.
  • Native memory tracking. A JVM feature that, once switched on, reports how much memory the JVM uses in each area: heap, metaspace, thread stacks, code and more. jcmd <pid> VM.native_memory summary prints it. Chapter 13.
  • Nearest wins. Maven's rule for choosing between two versions of the same library: the version declared closest to your project in the dependency tree wins, even if it is older. NuGet instead picks the lowest version that satisfies every request. Chapters 9, 10.
  • Optimistic locking. A version number on each document, checked on every write. A writer holding an out-of-date copy fails instead of overwriting someone else's change. In Spring Data it is the @Version field. Chapter 8.
  • Outbox. A pattern for writing to two systems safely. The service records the message for the second system in its own database in the same write, and a separate process delivers it later. Chapter 8.
  • Parent POM. A POM that other POMs inherit settings from, such as the Java release and library versions. It plays the part of Directory.Build.props in a .NET solution. Sorrel's is sorrel-parent. Chapter 1.
  • Pinning. A virtual thread that cannot be unmounted from its carrier thread while it waits, so it blocks the carrier too. It happened inside synchronized until JDK 24, and still happens in native code. Chapter 12.
  • POM. The Project Object Model, the pom.xml file that describes a Maven project: its name, its dependencies and how to build it. It plays the part of a .csproj. Chapter 1.
  • preStop. A hook Kubernetes runs inside a container before it sends the termination signal. A short sleep there gives the cluster time to stop routing requests to the pod. Chapter 14.
  • Proxy. A wrapper object Spring places in front of a bean. Calls from other beans pass through it, which is how annotations like @Transactional and @CircuitBreaker take effect. Chapter 15.
  • Readiness probe. A check Kubernetes runs to ask "can this pod take traffic right now?" If it fails, Kubernetes stops routing requests to the pod, without restarting it. Chapter 14.
  • Release flag. The maven.compiler.release setting. It compiles code for a given Java version and rejects any use of a newer Java API. Chapter 1.
  • Retry budget. A limit on the total extra load a retrying caller may put on a dependency. It is the difference between a retry and a retry storm. Chapter 11.
  • Retryable write. A MongoDB driver feature that automatically retries a write once after certain errors, such as a dropped connection. Most drivers switch it on by default. DocumentDB engines before 8.0.2 refuse it, so Sorrel's connection string sets retryWrites=false. Chapter 7.
  • Rolling update. The way a Kubernetes Deployment replaces pods: a few at a time, controlled by maxSurge (extra pods allowed) and maxUnavailable (pods allowed to be missing). Chapter 14.
  • Self-invocation. A call from one method of a bean to an annotated method of the same bean. It goes to the object directly, not through the proxy, so the annotation does nothing. Chapter 15.
  • Slice test. A Spring Boot test that starts only one layer of the application, such as the web controllers (@WebMvcTest) or the repositories (@DataMongoTest). It is faster than starting everything and more real than a mock. Chapter 6.
  • SNAPSHOT. A Maven version ending in -SNAPSHOT, which means "the latest build of this version". Its contents can change without the version number changing. Fine on branches, never on main. Chapter 10.
  • Startup probe. A check Kubernetes runs to ask "has the application finished starting?" Until it passes, the other two probes do not run, so a slow start is not mistaken for a dead process. Chapter 14.
  • Testcontainers. A library that starts a real database or other service in a Docker container for the duration of a test. Sorrel's tests run real MongoDB this way, which is not the same as DocumentDB. Chapters 6, 7.
  • Transitive dependency. A library your project gets because one of its own dependencies needs it, not because you declared it. Maven works these out for you. Chapters 1, 9.
  • Virtual thread. A thread scheduled by the JVM rather than the operating system. It is cheap enough that each request can have one and block while it waits. Final in Java 21. Chapter 12.
